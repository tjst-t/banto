## 背景

「`audit-fail-rework.spec.ts` の1件が全体テストでまれに落ちる」として handoff に**既知の
弱さ**として書いていたもの。PO 指示で調査した。**テストが遅かったのではなく、機構が
壊れていた。**

## 何が起きていたか

職人を起こすのは非同期で、`closeWorkerFor` と `worker.delegate_toolkit` の HTTP 往復を挟む。
その間にタスクが先へ進む（あるいは失敗して終端に着く）ことがあり、そうなると
**出来上がった職人を誰も畳まない**——終端に着いたときの後始末は「いま居る職人」を畳むので、
**まだ生まれていなかった職人は取りこぼす**。

実際の形：2回目の監査不通過でタスクが `failed` になったあと、1回目の不通過で頼んでいた
rework の職人が**遅れて生まれ**、工房の安全弁（既定15分）まで走り続ける。

失敗時の実物：

```
落ちたタスクの rework の職人は畳まれていること。
残っている: ["capture-task-double-fail-1:rework-1786096500516-614089"]
```

**20秒待っても畳まれない**——遅いのではなく、誰も畳まないから。

## なぜ「テストが遅い」と読まれていたか

混んでいるときだけ出る。単体では通り、全体テストでだけまれに落ちるので、
**待ち時間を延ばす方向の直しが2回入っていた**（コメントに「テストを並列に走らせると
数秒かかることがある」と書いてある）。待ちを延ばしても直らない類の壊れ方だった。

**まれに落ちる試験は、機構が壊れている合図として扱う**のが正しかった。

## 直したこと

`keepWorkerIfStillWanted`（`daemon.ts`）。職人が出来上がった直後に**帳簿を読み直し**、
その役目を要る状態でなければその場で畳んで、帳簿には載せずに戻る。

| 役目 | 要る状態 |
|---|---|
| `executor` | `planning` / `implementing` |
| `rework` | `implementing` |
| `audit` | `auditing` |

- **帳簿に載せない**のは、誰も使っていない職人だから。工房のイベントログには
  `worker_started` / `worker_closed` が残るので、事実は失われない
- **監査人は `audit_started` を積む前に確かめる**。積むと `countAuditAttempts`（task-0070）が
  数えてしまい、**誰も使っていない職人の分だけやり直しの回数が減る**

## 確かめ方（a4）

`FakeRuntimeDriver.spawnDelayMs`（新・既定0）で、**時間ではなく仕掛けで**競りを作る。
混んでいるかどうかに依らず、毎回同じ順序で再現する。

**直す前の実装で落ちることを確かめた**——判定を一時的に無効化して走らせ、3件中2件が落ちた。
落ちない検体は、無い検査より悪い（task-0068 で踏んだ形）。

## 同じ形が検証環境にもあった（ついでではなく、同じ穴）

`_autoProvisionOnReview` も fire-and-forget で、`listEnvironments` と `provisionEnv` の
往復を挟む。**立てている間にレビューが終わると、立てたばかりの環境を取りこぼす**——
終端の後始末（`_teardownTaskEnvs`）は「いま立っている環境」を畳むため。

環境は期限で必ず畳まれるので走り続けはしないが、**最長24時間は外で動く**（I3：消し忘れは
金銭的実害）。職人と同じ判定を入れた（立て終わったあとに `in-review` でなければ畳む）。

**P1 の線引き**：スコープ外の「ついで」ではなく、**同じタスクで直している穴の別の現れ**。
片方だけ塞ぐと、残った方が同じ形で再発する。

## 同じ形を全部探した（PO指示「全部やって」）

Kobo の中で「非同期で作ったものを、作り終える前に状態が変わると誰も片付けない」を洗った。
**4箇所あった**（最初に見つけたのは1箇所目だけ）：

| どこ | 何を取りこぼすか |
|---|---|
| `spawnReworkSession` | 終端に着いたあとに生まれた rework の職人 |
| `spawnAuditSession` | auditing を抜けたあとに生まれた監査人 |
| `spawnTask`（実装者） | **ready を抜けたあとに生まれた実装者**。次の `planning` への遷移が弾かれ、職人だけが宙に浮く |
| `_autoProvisionOnReview` | レビューが終わったあとに立ち上がった検証環境（最長24時間動く・I3） |

判定は `wantedIn`（その職人／環境を要る状態）を呼び出し側が明示する形にした——
役目から状態を推す表にすると、実装者だけ「起こした直後は `ready`、そのあと `planning`」と
ずれるのを吸収できない。

## 結果

`npm test` を**8回連続で通した**（1,285件）。直す前は3回中2回落ちていた。
