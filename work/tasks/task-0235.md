## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

2026-08-16、`banto-worker-pool.service` が OOM で繰り返し揺れた（00:30:50 / 01:26:51 / 03:06:40 / 03:51:07 / 03:54:58 / 04:06:33 / 04:35:35）。**その最中に、モジュールへの呼び出しが接続段で失敗し、タスクが中身と無関係に `failed` になっている。**

帳簿を突き合わせた実測（±60秒）：

| タスクが failed になった時刻 | 直前の worker-pool の OOM | 間隔 |
|---|---|---|
| 03:55:22（task-0160・報告なし） | 03:54:58 | **+24秒** |
| 04:07:20（task-0160・報告なし） | 04:06:33 | **+47秒** |

**数十秒後には同じ操作が通っている**（`kobo.reopen` が一度 `read ECONNRESET` で落ち、すぐ後に成功）。

いまの実装にはこの手当てが無い：

```ts
// packages/banto-core/src/module-invocation.ts:206-214
try {
  response = await fetchImpl(url, { method: "POST", ... });
} catch (err) {
  // I2: 到達できない相手を「結果なし」と混同しない
  throw new Error(`Failed to reach module "${moduleName}" at ${url}: ${String(err)}`);
}
```

**一度きりで、再試行が無い。** 相手が起き直っている最中の数十秒に当たると、そこで終わる。

**追記（2026-08-16 夜）**：この経路の失敗は dentaku task-0042 の rework でも出ている
（`rework session spawn failed: Failed to reach module "worker-pool" ... read ECONNRESET`）。**同じ穴である。**

## やること

**接続段の失敗だけを、短く再試行する。**

1. **再試行してよいのは「要求が相手に届いていないと言い切れる」失敗だけ。**
   - **`ECONNREFUSED` / `ENOTFOUND` / `EAI_AGAIN`** のような**接続確立の失敗**は、相手が受け取っていないので**安全に再試行できる**。
   - **`ECONNRESET` / socket hang up は、送ったあとにも起きる。** 相手が処理を始めてから切れた場合、**再試行すると同じ操作が二度走る**——このモジュール呼び出しには**職人を起こす（spawn）**ような**冪等でない操作が乗っている**ので、**既定では再試行しないこと**。
   - **冪等だと呼び出し側が知っている場合にだけ、送信後の失敗も再試行できる**ようにする（呼び出しごとの opt-in。既定は off）。**この線引きを実装のコメントに明記すること。**
2. **回数と間隔は控えめに**（例：2〜3回、100ms → 300ms → 900ms 程度の後退）。**合計の待ちが数秒を超えないこと**。値は**環境変数で変えられる**ようにし、既定と根拠をコメントに残す。
3. **最後まで駄目なら、いままでどおり例外を投げる**（I2：到達できない相手を「結果なし」と混同しない）。**握り潰さない。**
4. **再試行したことが分かるようにする**（何回目で通ったか／何回試して駄目だったかがログに残る）。**黙って直すと、次に同じことが起きたときに「何も起きていない」ように見える。**

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- **Kobo 側で「到達できなかった」を `failed` と区別する扱い**——これは task-0215 で着地済み（`unreachable:` の印）。**ここでは触らない。**
- `banto-daemon` / `banto-worker-pool` / `banto-host` の変更（**同じ夜に別のタスクが `claude-agent-driver.ts` の起動段の再試行をやっている。層が違うので混ぜないこと**）
- タイムアウトの値（`longCallFetch` の作り）そのものの変更
- OOM の側の手当て（cgroup・袋の大きさ・同時本数）

## 気をつけること

- **「とりあえず全部再試行」にしないこと。** 職人を起こす呼び出しが二重に走ると、**同じタスクに職人が2本立つ**。今日の事故（1本の OOM が別の職人を巻き添えにする）と同じ形で、**直したつもりが新しい壊れ方を作る**。
- **既存の呼び出し側の書き方を変えないこと**（既定の振る舞いは「接続確立の失敗だけ再試行」で、呼び出し側は何も書かなくてよい）。
- 新しい試験は **`tests/acceptance/module-connect-retry.spec.ts`** という名前で作ること（verify がこの名前を見ている）。
  **偽の fetch を渡して決定的に**再現させること（本物のポートを使って偶然を待つ形にしない）。
- ここは `banto-core`＝**4つの常駐サービス全部が通る道**である。**振る舞いを変えるのは失敗経路だけ**にすること。

## 走らせ方（2026-08-16 現在の実態。古い文面を写さないこと）

- **受け入れ基準に添えた検証コマンドは、Kobo が検証環境（あなたの外）で回します。**
  自分で**一式**（`npm ci` / `npm test` / `npm run typecheck` / `npm run build`）を叩かないこと——
  あなたは 2 GiB のメモリ上限の中にいて、一式を回すと上限に当たって**あなたごと**強制終了されます（2026-08-16 に実測で7回）。
- **自分で叩いてよいのは軽い確認だけ**：1本の spec（`npm run test:one -- tests/acceptance/module-connect-retry.spec.ts`）、
  1ファイルの型検査、`grep` / `git diff` などの読み取り。
- `report_done` を呼ぶと、Kobo が監査へ回す前に受け入れ基準の検証コマンドを**検証環境の中で**回し、
  落ちていれば落ちた基準・終了コード・ログを**あなたへ差し戻します**。**確かめるのをやめるのではなく、回す場所が変わるだけ**です（I1）。
- **「一式はゲートに任せるから自分は確かめない」は駄目です。** 1本の spec と読み合わせで自分で確かめてから `report_done` を呼ぶこと。
