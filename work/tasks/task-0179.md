## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

2026-08-14 00:27:55 UTC、職人が起こした claude CLI 1本が anon-rss 10.7 GiB に膨らみ、15 GiB の VM が global OOM で停止した。その後、稼働機に systemd の drop-in で封じ込めを入れてある。これは**実際に効いている**——2026-08-14 以降のカーネル OOM kill は**全件が cgroup 上限に当たったもの**（`constraint=CONSTRAINT_MEMCG`）で、**VM 全体の枯渇は1件も起きていない**。

**ところが、その設定は稼働機にしか無い。** リポジトリの `deploy/*.service`（banto / banto-daemon / banto-worker-pool / banto-environment-pool の4本）を grep しても `MemoryMax` / `OOMPolicy` / `MemoryHigh` は **0件**である。**稼働機を作り直した瞬間に封じ込めが消え、8/14 の事故に戻る。**

さらに 2026-08-16、凌ぎとして `systemctl set-property --runtime` で上限を動かしている。**`--runtime` の drop-in は `/run` に置かれ、サービスの再起動では消えないが（実測済み）、機械ごとの再起動では失われる。**この意味でも、リポジトリ側に恒久の形が要る。

## やること

**稼働機に現に入っている設定を、リポジトリの `deploy/` に書き戻して一致させる。**

1. **稼働機の現物を読む**（変更はしない。読むだけ）。
   - `/etc/systemd/system/banto.service.d/`、`banto-daemon.service.d/`、`banto-worker-pool.service.d/`、`banto-environment-pool.service.d/`、`/etc/systemd/system/system.slice.d/` 以下の `.conf` 全文
   - **`/run/systemd/system.control/*/` の drop-in も読むこと**（`set-property --runtime` で入れた一時の上限がここに居る。**恒久の値と一時の値を取り違えないこと**）
   - 実効値は `systemctl show <unit> -p MemoryAccounting -p MemoryMax -p MemoryHigh -p MemoryMin -p MemorySwapMax -p OOMPolicy -p OOMScoreAdjust -p TasksMax` で確かめる
   - **`systemctl` の start / stop / restart / daemon-reload / set-property / edit は絶対に呼ばないこと。** いま稼働中の banto で PO の作業が走っている。読み取り専用のサブコマンド（`show` / `cat`）だけ。
2. **`deploy/*.service` の `[Service]` に設定を書く。** 書くのは**恒久の値**（`/etc/systemd/system/*.service.d/` の側）。参考までに、2026-08-14 に決めた値は次のとおり（**現物が優先。食い違ったら現物に合わせ、報告に食い違いを書くこと**）：
   - `banto.service`: `MemoryAccounting=yes` / `MemoryMax=3G` / `MemoryMin=1G` / `OOMScoreAdjust=-500`
   - `banto-worker-pool.service`: `MemoryAccounting=yes` / `MemoryMax=9G` / `OOMPolicy=continue` / `OOMScoreAdjust=+500` / `TasksMax=2048`
   - `banto-daemon.service` と `banto-environment-pool.service`: `MemoryAccounting=yes` / `MemoryMax=1G` / `MemoryMin=256M`
   - `system.slice`: `MemoryMin=1536M`（unit ファイルではなく slice の drop-in。**`deploy/system.slice.d/oom.conf` のように置き場を新しく作ってよい**）
   - **2026-08-16 時点で `--runtime` の一時の上限（banto 5G / worker-pool 7G など）が乗っている。これは凌ぎであって恒久の値ではない**——`deploy/` に書くのは恒久の側。ただし**「一時の上限が乗っていること」はコメントで触れておくこと**（次に読む人が実機と見比べて混乱しないため）。
3. **なぜその値なのかを、設定のすぐ横にコメントで残す。** 根拠の出所は
   `/home/ubuntu/banto-desk/reports/2026-08-14-oom-containment-plan.md`（15.62GiB − OS 1.5G − 番頭 3G − Kobo 1G − 検証環境 1G ＝ 9.1GiB → 9G、など）と
   `/home/ubuntu/banto-desk/reports/2026-08-16-oom-host-facts.md`。**数字だけ写して根拠を落とさないこと**——次に誰かが値をいじるときに、根拠が無いと必ず壊れる。
4. **入れ方の手順を `deploy/` の中に残す**（`deploy/README.md` が無ければ新しく作る）。**drop-in が残っている限り drop-in が勝つ**という重なりの注意と、`--runtime` は機械の再起動で消えることを書くこと。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- **稼働機の設定を変えること・サービスの再起動・`daemon-reload`**。このタスクはリポジトリのファイルだけを直す
- `MemoryMax` の値そのものを新しく決め直すこと（**値を決めるのは PO**。ここは「いま効いている恒久の値を記録に戻す」だけ）
- `packages/**` `tests/**` `docs/**` の変更。**スコープは `deploy/**` だけ**である（他の仕事と直列化させないために、意図的にここまで絞ってある。**足りないと思っても広げないこと**——広げるとマージ前ゲートで落ちる）
