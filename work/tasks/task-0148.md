## 背景（これが職人に届く本文です。前提を知らない前提で書いています）

banto の Kobo（工場）は、タスク定義ファイルを取り込み → 依存ゲート → 職人が実装 → 別セッションの監査 →
マージ前ゲート（スコープ違反検査＋検証コマンド）→ マージ、と運ぶ機構です。実装は
`packages/banto-daemon`（daemon.ts / gate-evaluator.ts / merge-queue.ts ほか）、状態と帳簿は
`packages/banto-core`（state-machine.ts / events.ts / event-log.ts / state-store.ts）にあります。

2026-08-13 に、稼働中の帳簿 `/var/lib/banto/data/events/2026-08.jsonl`（1,947 イベント、6日分）を
集計した調査があります（`/home/ubuntu/banto-desk/reports/2026-08-13-kobo-rethink.md`。読んでよい）。
そこで分かった事実：

- 実際に手が動いている `implementing` の滞在時間は**中央値 6.6 分**、最長でも 1.1 時間。
- にもかかわらず投入からマージまでは **7.9〜19.4 時間**かかっている。
- 時間のほぼ全部は「待ち」と「落ちたまま放置」で消えている。滞在時間の p90 は
  queued 6.76h（最大 27.8h）、review-ready 28.56h、failed 16.77h、paused 0.97h（最大 21.0h）。
- 実例：task-0100 は 19.2 時間 queued に滞留した。理由は `blockedBy: [task-0099(review-ready)]` が
  18 時間変わらなかった、というただそれだけの事実だった。**それを言える機構が無かった。**

つまり工場には「時間」という次元が無い。イベントには timestamp があるのに、状態にも API にも
知らせにも滞在時間が出てこないので、詰まりに誰も気づけない。

## やること

**帳簿（イベントログ）から滞在時間を導出し、閾値を超えたら知らせる。** 新しい状態は作らない。
状態遷移も変えない。**純増の改修**です。

### 1. `packages/banto-core/src/dwell.ts`（新規）

イベント列から次を導出する純粋関数を置く（副作用なし・テスト可能に）:

- `stateEnteredAt(events, projectTag, taskId): string | undefined`
  — そのタスクの最後の `state_transitioned` の timestamp
- `dwellMs(events, projectTag, taskId, now): number`
- `lastObservableChangeAt(events, projectTag, taskId): string | undefined`
  — `agent_spawned` / `audit_started` / `merge_gate_evaluated` / `state_transitioned` などの
  「観測できる変化」の最大時刻。**職人の自己申告は根拠に使わない**（原則 I1）

既存のイベント種名は `packages/banto-core/src/events.ts` を読んで実在するものに合わせること
（この本文の種名は説明のための呼び名であり、正確とは限りません）。
`packages/banto-core/src/index.ts` から公開する。

### 2. `packages/banto-daemon/src/daemon.ts` に tick job を1本追加

`dwell-watch`。定期的に全タスクの滞在時間を見て、状態ごとの閾値を超えていたら
**`task_stalled` イベントを1回だけ**積む（同じ状態にいるあいだは再発火しない。
状態が変わったらまた1回積めるようになる）。

閾値は層B設定（`meta/config.yaml` の `limits` 相当。既存の設定読み出しの作法に合わせること）から
読み、設定が無ければ既定を使う:

| 状態 | 既定の閾値 |
|---|---|
| queued | 120 分 |
| implementing | 90 分 |
| review-ready | 240 分 |
| failed | 60 分 |
| paused | 240 分 |

`task_stalled` のペイロードには少なくとも `{ projectTag, taskId, state, dwellMinutes, blockedBy }`
を入れる。`blockedBy` は直近のゲート評価イベントに記録されている「何を待っているか」。

### 3. `packages/banto-daemon/src/kobo-tools.ts`

- `kobo.list` の各行に `since`（その状態になってからの経過時間。人が読める形。例「19.2h」）を足す
- `kobo.task` の冒頭に「この状態になってから N 時間」を出す

### 4. `packages/banto-host/src/kobo-notice.ts`

`task_stalled` を番頭への知らせの対象に足す。**文面に「なぜ止まっているか」を含める**こと。
「task-0100 が queued で 19.2 時間止まっています。待っているのは task-0099（review-ready）です」
のように、番頭が知らせを読んだだけで次の手を選べる文にする。同じタスクの同じ滞留について
何度も知らせない。

### 5. テスト

`tests/acceptance/kobo-dwell.spec.ts` に、既存の受け入れテストの作法（`tests/acceptance/` の
他のファイルを読んで合わせる）で:

- 合成したイベント列から `dwellMs` / `lastObservableChangeAt` が正しく出ること
- 閾値超過で `task_stalled` が**1回だけ**積まれ、同じ状態のあいだ再発火しないこと
- 状態が変わった後は再び積めること

## スコープ外（触らないこと）

- 状態機械（`state-machine.ts`）の遷移そのもの。**状態を増やさない・遷移を足さない**
- ゲートの判定ロジック（`gate-evaluator.ts`）、マージキュー（`merge-queue.ts`）
- 滞留を検知したときに**自動で何かを直すこと**。この仕事は「見えるようにする」までで、
  自動リトライ・自動 abandon・自動再開はいっさい作らない（それは別の判断）

## なぜこの順序でこれを最初にやるのか

以後のすべての改修の**効果測定基盤**になるからです。「滞留が減ったか」を測れないまま
並行制御やゲートを作り直すのは、原則 P6 が禁じている「計測なしの直し」そのものです。
実装は小さいのに、いま現に失われている 19.2h / 28.6h / 16.8h がその日から見えるようになります。
