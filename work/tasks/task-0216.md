## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

### 何が起きているか

banto は systemd の cgroup で封じ込めてある。2026-08-16 時点の実測：

- `banto-worker-pool.service`（工房全体）の上限は 7〜8 GiB（暫定で動かしている最中）。**旧上限 9G のときの実測 peak は 9.00 GiB＝上限に張り付いていた。**
- **職人1本ごとに 2 GiB の子 cgroup** が貼られている（`/sys/fs/cgroup/system.slice/banto-worker-pool.service/supervisor/w-*/memory.max` = 2GiB）。当たると `memory.oom.group` で**その職人の袋ごと全プロセスが kill される**（2026-08-16 01:26:51 に監査職人で実例。15プロセスが同時に死んだ）。
- **同時に9本走っていた。9×2 GiB ＝ 18 GiB は、工房の上限を構造的に超える。**
- **その結果、今日1日で `banto-worker-pool.service` が少なくとも7回 OOM で揺れ**（00:30:50 / 01:26:51 / 03:06:40 / 03:51:07 / 03:54:58 / 04:06:33 / 04:35:35）、巻き添えで**「中身は無罪なのに落ちた」タスクが7本**出た。

つまり、**いまは「何本まで走ってよいか」を誰も決めていない**。

### なぜ穴が空いているか（2026-08-14 の調査で特定済み）

| 経路 | 上限 | 場所 |
|---|---|---|
| Kobo（`banto-daemon`）が回すセッション | **あり。既定5** | `meta/config.yaml` の `limits.max_concurrent_sessions` ／ `packages/banto-daemon/src/daemon.ts`（`BANTO_MAX_CONCURRENT_SESSIONS`、既定5） |
| **番頭 → Worker Pool（`worker.delegate`）** | **無い** | `packages/banto-worker-pool/src/pool.ts`（spawn が `runtime.driver.spawn(...)` へそのまま抜ける。上限・待ち行列・拒否の判定が無い） |
| 起きたままの職人の畳み方 | アイドル安全弁 15分 | `packages/banto-worker-pool/src/pool.ts` の `DEFAULT_IDLE_TIMEOUT_MS` ／ `bin.ts` の `BANTO_WORKER_IDLE_MS` |

**決定23（ADR-0010）が課す制約が1つある**——「Worker Pool は Kobo から独立したモジュールで、Kobo が無くても単体で成立する」。したがって**上限は Worker Pool 自身が持たなければならない**。Kobo 側に持たせると「Kobo 無しでも職人へ委譲できる」が壊れる。

## やること

**Worker Pool 自身に「同時に走ってよい職人の本数」の上限を持たせ、超えたら断る。**

1. **上限を持つ**：既定値を決め、**環境変数で変えられる**ようにする（既存の `BANTO_WORKER_IDLE_MS` などと同じ流儀・同じ場所で読むこと。`settings.ts` / `bin.ts` を見て合わせる）。既定値の根拠を実装のコメントに残すこと——**「上限本数 × 職人1本の cgroup 上限（2 GiB）」が工房の上限（`MemoryMax`）を超えない**のが理屈だが、実測では平常時の職人1本は 0.23〜0.56 GiB であり、理屈どおりに置くと 3〜4 本で頭打ちになって実用に耐えない。**どちらの考え方を採ったのかを書くこと**（数字だけ置かない）。
2. **超えたら断る**（待ち行列は作らない）。理由は、待たせると「受理したが動いていない職人」が生まれ、D3（状態の真実は一箇所）と覗き窓に**待ち状態**を足すことになるため。このタスクではそこまで踏み込まない。
3. **断り方が要点**：番頭が次の手を選べる断り方にすること。**いま何本走っていて、上限が何本で、それぞれ誰が・いつから走っているか**（taskId と起動時刻）を断りの文面に含める。**「上限です」だけでは番頭は何を畳めばいいのか分からない。**
4. **数え方**：数えるのは**生きている職人**だけ（畳んだもの・落ちたものは数えない）。アイドル安全弁で畳まれた分は当然減る。**数え間違いが上限を無意味にする**ので、ここは試験で固定すること。
5. **いま何本走っているかが外から読めること**（既存の覗き窓・一覧＝`worker-tools.ts` の一覧に本数と上限が出るのが望ましい。既存の口の形を読んで、それに合わせること）。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- 待ち行列（超えた分を待たせる仕組み）
- Kobo 側（`banto-daemon`）の同時実行数の変更
- systemd の設定・cgroup の値（PO の判断）
- `packages/banto-host`（番頭側）の変更——**断りを受けた番頭がどう振る舞うかは、このタスクでは扱わない**。断りの文面が「読めば次の手が分かる」形であればよい
- 職人1本ごとの cgroup（2 GiB）の値の変更
- `worker-cgroup.ts` / `claude-agent-driver.ts` など、スコープに挙げていないファイル

## 気をつけること

**上限は「事故を防ぐ栓」であって、仕事を止める道具ではない。** 既定値を低く置きすぎると、工場（Kobo）が回す職人と番頭が直に起こす職人が食い合って**工場が止まる**。実測（平常時1本 0.23〜0.56 GiB、工房の上限 7〜8 GiB）から、**現実に耐える値**を選ぶこと。

**task-0165（アイドルな会話の SDK セッションを畳む・安全弁と同時本数の上限）が同じ `pool.ts` を触っており、いま着地の最中である。このタスクはその着地を待つ（depends）。** 着手したら、まず main を取り込んで 0165 の入った後の `pool.ts` を読むこと。
