## 背景（あなたは記憶を持たないので全部ここに書きます）

`system.deploy`（計画的デプロイ）は main に対して `npm test` を回し、通ったときだけ常駐サービスを起こし直す。2026-08-20 のデプロイでこのゲートが fail 2 で拒否した。そのうち1件は **試験が実行環境の環境変数を継承していること**による決定的失敗である。

- 落ちる試験: `tests/acceptance/browser-chromium-launcher.spec.ts:664`
  「BANTO_BROWSER_ALLOW_NO_SANDBOX が無ければ --no-sandbox は入らず、status も enabled」
- 試験は `createChromiumLauncher({ ..., allowNoSandboxEnv: undefined })` を渡して「環境変数が無い状態」を表現している。
- しかし実装は `packages/banto-host/src/browser/chromium-launcher.ts:505-506` で
  `const allowNoSandboxEnv = options.allowNoSandboxEnv ?? process.env["BANTO_BROWSER_ALLOW_NO_SANDBOX"];`
  と書かれているため、**明示的に渡した `undefined` が `??` で潰れ、実プロセスの環境変数に落ちる**。
- デプロイゲートは banto.service の環境（`deploy/banto.service:56` に `Environment=BANTO_BROWSER_ALLOW_NO_SANDBOX=1`）を継承して走るため、この試験は必ず落ちる。清潔な検証コンテナ（docker・BANTO_* なし）では通るので、「ゲートだけ落ちる」という食い違いになっていた。docker で対照実験済み：**変数なしで 43/43 合格、`=1` を与えると 42/43 が落ちる**。

## やること（形は1つに決まっています）

**`createChromiumLauncher` に「読む環境」の注入口を足す。それだけ。**

```ts
// options に追加（既定は process.env）
env?: NodeJS.ProcessEnv;

// 読むところ
const allowNoSandboxEnv =
  options.allowNoSandboxEnv ?? (options.env ?? process.env)["BANTO_BROWSER_ALLOW_NO_SANDBOX"];
```

試験は `env: {}` を渡して「環境変数が無い状態」を表現する。同ファイルの他の試験（`BANTO_BROWSER_ALLOW_NO_SANDBOX=1 のとき --no-sandbox が入る` など）も、同じ注入口を通して環境非依存にすること。

## 採ってはいけない形

- **`"allowNoSandboxEnv" in options` でキーの有無を見る方式は採らない。** 本番に `{ allowNoSandboxEnv: undefined かもしれない値 }` を渡す呼び出しがあると、環境変数の逃げ道が黙って死ぬため。
- **`process.env` を試験内で書き換えて復元する方式も採らない。** 並行実行で他の spec を巻き添えにする。
- 実装の変更は上記の注入口を足すことだけに限る。**既定の挙動（何も渡さなければ `process.env` を読む）は変えない**——本番はその挙動に依存している。

## やらないこと

- デプロイゲートの走らせ方（清潔な環境で回すか）は別途 PO 判断待ちなので、ここでは触らない。
- `packages/banto-host/src/deploy-verify.ts` は触らない（task-0311 / task-0313 で着地済みの領分）。
- `tests/acceptance/audit-checklist-assets.spec.ts` は別のタスク（task-0321）の持ち分。触らない。

## 完了条件

環境変数 `BANTO_BROWSER_ALLOW_NO_SANDBOX=1` が **設定されていても・されていなくても**、この spec が同じ結果（全件通過）になること。加えて、**何も渡さなければ `process.env` を読む**という本番の経路が試験で固定されていること。
