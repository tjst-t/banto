## なぜこれを直すのか（実測した事実。推測ではない）

マージ前ゲートは「受け入れ条件の verify を検証環境で走らせ、exit≠0 なら落とす」建て付けだが、
**verify を1本も持たない契約は、何も走らせずに緑になる。**

実例（Kobo の帳簿 `/var/lib/banto/data/events/2026-08.jsonl` の一次データ）:

```
{"type":"merge_gate_evaluated","projectTag":"banto","taskId":"task-0099","passed":true,
 "reasons":[],"logPaths":[],"eventId":828,"timestamp":"2026-08-13T08:19:12.857Z"}
```

- task-0099 の契約は `acceptance: [{id:a1, text:"コンフリクトが解消されており…"}]` の1本のみで **verify 無し**、`scope.paths: ["**"]`。
- つまり**範囲検査も空振り、検証も0本**。approved→merging→ゲート通過→マージまで **206ms**。
- `logPaths` は空、`/var/lib/banto/data/gate-logs/task-0099` は**そもそも存在しない**。貼るべきログが無いことがそのまま証拠。

帳簿上、受け入れ条件 **492本中95本（19%）に verify が無い**（banto だけで 248本中94本）。
いま queued の task-0175 / task-0176 も a1〜a5(a6) が verify 無しで、このままだと
**UI の振る舞いは一度も機械に触られないまま緑になる。**

## どこが穴か（読んで確認済み・ファイル:行）

- `packages/banto-daemon/src/merge-gate.ts:395` `const withCommands = acceptance.filter((ac) => ac.verify);`
- 同 `:405` `if (withCommands.length > 0) {` — **0本なら検証ブロックごと素通り**
- 同 `:536` `const passed = reasons.length === 0;` — reasons が空なので **passed=true**
- 飛ばしたことを警告・記録する箇所は**1つも無い**
- `packages/banto-core/src/task-frontmatter.ts:28` で `verify?: string`（任意）。契約検査（同 :484-496 と
  `packages/banto-daemon/src/daemon.ts:1068` 付近の `validateContractInput`）は `id` と `text` しか要求しない
- `packages/banto-daemon/src/review-policy.ts:389` `gateEvidenceBlockers` は `baseCommit` と
  `environmentDigest` の有無しか見ない。**「1本でも走ったか」しか見ていないので、大半が未検査でも自動着地が通る**

なお `kind: conflict` の自動起票は第4便で廃止済み（`daemon.ts` の `handleRebaseConflict` のコメント参照）なので、
fail-closed に倒してもコンフリクト経路で工場が詰まることはない。task-0099 は廃止前の遺物。

## 何をするか

### 1. 契約の時点で「機械が確かめない条」を明示させる

`packages/banto-core/src/task-frontmatter.ts` の受け入れ条件に **`unverifiable?: string`** を足す。
契約検査（`validateContractInput` と watcher の取り込み検査の**両方**）で、

- `verify` も `unverifiable` も無い条があれば **断る**（既存の `missing required field: scope.paths` と同じ形式・同じ経路で）
- 断り文には**どの条か（id）**と、`verify` か `unverifiable: "<なぜ機械で確かめられないのか>"` のどちらかが要ることを書く

**目的は「書けないなら諦めさせる」ことではなく、黙って消えるのをやめさせること。**
いまは条件のほうが静かに落ちる（task-0173/0174 → 0175/0176 で実際にそうなった）。

### 2. ゲートが「何も走らせなかった」ことを緑と呼ばない

`merge-gate.ts` の集計に足す:

- 受け入れ条件が1本以上あるのに、**実際に走らせた verify が0本**なら
  `reasons.push("no_verify_commands（受け入れ条件に検証コマンドが1本も無い）")` で**落とす**
- `merge_gate_evaluated` に **`unverifiedAcIds: string[]`** を**常に**刻む。中身は
  「`unverifiable` 印つきの条」＋「印も verify も無い旧契約の条」の id
- 既存の `verifyResults` の形は変えない（読む側が壊れる）

### 3. 自動着地は「全部走った」を求める

`review-policy.ts:389` の `gateEvidenceBlockers` に `unverifiedAcIds` を渡し、**空でなければ blocker** にする。
呼び出しは `merge-gate.ts:532` の `landedWithoutHumanApproval(...)` が真のときだけ、という**いまの非対称は維持する**
（人の承認を経た経路では落とさず、`unverifiedAcIds` を刻むだけ）。**この非対称は意図なので変えないこと。**

### 4. 番頭が読めるようにする

`kobo-tools.ts` の `kobo.task` の経緯表示で、マージ前ゲートの行に未検査の条を出す。
例: `merge_gate_evaluated — 通過（未検査: a1, a2）` / `merge_gate_evaluated — 落ちた: no_verify_commands`。

### 試験ファイルの名前は契約で固定してある（**この名前で作ること**）

verify がファイルを名指ししているので、**別の名前で書くとゲートで落ちる**。

| ファイル | 何を固定するか |
|---|---|
| `tests/acceptance/contract-requires-verify.spec.ts` | a1（契約検査。verify も unverifiable も無い条を含む契約が、id を名指しして断られる） |
| `tests/acceptance/gate-no-verify-commands.spec.ts` | a2・a3・a4（ゲートの fail-closed / `unverifiedAcIds` の刻み / 自動着地の扱い） |
| `tests/acceptance/kobo-task-unverified-display.spec.ts` | a5（`kobo.task` の表示） |

最低限、次を落ちる形で固定する:

1. verify を1本も持たない契約 → `passed === false`、`reasons` に `no_verify_commands` が含まれる
2. verify を1本持つ契約 → 従来どおり通る（退行させない）
3. `unverifiable` 印つきの条を含む契約 → `merge_gate_evaluated.unverifiedAcIds` にその id が入る
4. 自動着地（`landedWithoutHumanApproval` が真になるイベント列）＋未検査の条あり → 通らない
5. 人の承認を経た経路＋未検査の条あり → 通る（刻まれるだけ）
6. 契約検査: verify も unverifiable も無い条を含む契約を積もうとすると、id を名指しして断られる

**直す前の実装で 1・3・4・6 が落ちることを実際に確かめてから直すこと**（試験が何も見ていないのを防ぐため）。
確かめた出力（落ちていた事実）を報告に貼ること。

### 1本だけ回すときの verify の書き方（**知っておくこと**）

**`npm test -- <file>` は絞り込みにならない。** `package.json:20` の `test` は
`node --import tsx --test $(ls tests/acceptance/*.spec.ts | grep -vE …)` なので、`--` の後ろは
**追加の引数として足されるだけ**で、毎回 2420件の全量（約400秒）が走る。
だからこの契約の verify は、`test` スクリプトが立てている環境変数を明示したうえで
`node --import tsx --test <file>` を直接呼ぶ形にしてある。**この形を崩さないこと。**
