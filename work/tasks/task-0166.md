## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

2026-08-14 00:27:55 UTC、職人が起こした claude CLI 1本が anon-rss 10.7 GiB に膨らみ、15 GiB の VM が global OOM で停止した。その後、稼働機に systemd の drop-in（`/etc/systemd/system/<unit>.service.d/oom.conf` と `/etc/systemd/system/system.slice.d/`）で封じ込めを入れてある。これは実際に効いていて、2026-08-14 以降のカーネル OOM kill 12 件は**全件 cgroup 上限に当たったもの（`constraint=CONSTRAINT_MEMCG`）で、VM 全体の枯渇は1件も起きていない**。

**ところが、その設定は稼働機にしか無い。** リポジトリの `deploy/*.service`（banto / banto-daemon / banto-worker-pool / banto-environment-pool の4本）を grep しても `MemoryMax` / `OOMPolicy` / `MemoryHigh` は**0件**である。**稼働機を作り直した瞬間に封じ込めが消え、8/14 の事故に戻る。**

## やること

**稼働機に現に入っている設定を、リポジトリの `deploy/` に書き戻して一致させる。**

1. **稼働機の現物を読む**（変更はしない。読むだけ）。
   - `/etc/systemd/system/banto.service.d/`、`banto-daemon.service.d/`、`banto-worker-pool.service.d/`、`banto-environment-pool.service.d/`、`/etc/systemd/system/system.slice.d/` 以下の `.conf` 全文
   - 突き合わせは `systemctl show <unit> -p MemoryAccounting -p MemoryMax -p MemoryHigh -p MemoryMin -p MemorySwapMax -p OOMPolicy -p OOMScoreAdjust -p TasksMax` の実効値で行うこと（drop-in の書き間違いを写さないため）
   - **`systemctl` の start/stop/restart/daemon-reload/edit は絶対に呼ばないこと。** いま稼働中の banto で PO の作業が走っている。読み取り専用のサブコマンド（`show` / `cat`）だけ。
2. **`deploy/*.service` の `[Service]` に同じ設定を書く。** 参考までに、2026-08-16 時点で確認されている値は次のとおり（**現物が優先。食い違ったら現物に合わせ、報告に食い違いを書くこと**）：
   - `banto.service`: `MemoryAccounting=yes` / `MemoryMax=3G` / `MemoryMin=1G` / `OOMScoreAdjust=-500`
   - `banto-worker-pool.service`: `MemoryAccounting=yes` / `MemoryMax=9G` / `OOMPolicy=continue` / `OOMScoreAdjust=+500` / `TasksMax=2048`
   - `banto-daemon.service` と `banto-environment-pool.service`: `MemoryAccounting=yes` / `MemoryMax=1G` / `MemoryMin=256M`
   - `system.slice`: `MemoryMin=1536M`（unit ファイルではなく slice の drop-in。**`deploy/` に置き場が無いなら新しく作ってよい**。例: `deploy/system.slice.d/oom.conf`）
3. **なぜその値なのかを、設定のすぐ横にコメントで残す。** 根拠の出所は
   `/home/ubuntu/banto-desk/reports/2026-08-14-oom-containment-plan.md`（15.62GiB − OS 1.5G − 番頭 3G − Kobo 1G − 検証環境 1G ＝ 9.1GiB → 9G、など）と
   `/home/ubuntu/banto-desk/reports/2026-08-16-oom-host-facts.md`。**数字だけ写して根拠を落とさないこと**——次に誰かが値をいじるときに、根拠が無いと必ず壊れる。
4. **入れ方の手順を残す**（`deploy/` に置くのが自然。既に README 相当のものがあればそこへ、無ければ新しく1本）。drop-in で入っているものを unit ファイル本体に書くと、**drop-in が残っている限り drop-in が勝つ**——この重なりについて、次に環境を作る人が迷わない書き方にすること。

## やらないこと（スコープ外）

- **稼働機の設定を変えること・サービスの再起動・`daemon-reload`**。このタスクはリポジトリのファイルだけを直す
- `MemoryMax` の値そのものを新しく決め直すこと（**値を変えるのは PO の判断**。ここは「いま効いている値を記録に戻す」だけ）
- `packages/**` のコード変更

## 完了の確かめ方

受け入れテストを `tests/acceptance/` に置き、**`deploy/*.service` を機械で読んで必要な指定が入っていることを検査する**（既存のテストの流儀を先に読んで合わせること）。数字を直書きしたテストでよいが、**どのファイルにどの指定が要るか**が読めば分かる形にすること。
