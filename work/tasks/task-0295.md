## 実測した事実（2026-08-20）

`packages/banto-daemon/src/daemon.ts:1327` の `maxConcurrentSessions()` は、**登録されている全プロジェクトを回して最小値を採る**。

```ts
maxConcurrentSessions(): number {
  const koboDefault = this.config.maxConcurrentSessions ?? 5;
  let limit = koboDefault;
  for (const project of this.registry.list()) {          // ← 全プロジェクト
    const configured = this.projectConfig(project.id).limits.maxConcurrentSessions;
    if (typeof configured === "number" && configured >= 0) limit = Math.min(limit, configured);
  }
  return limit;                                          // ← 引数を取らない
}
```

**引数を取らない。つまり「どのプロジェクトの上限か」という区別が無い。**

いま登録されているのは5つ（loamium / banto / hiragana / mirante / dentaku）。

- `banto` の `meta/config.yaml:65` … `max_concurrent_sessions: 5`
- **`dentaku` の `meta/config.yaml:7` … `max_concurrent_sessions: 2`**

**結果、工場全体が2本に絞られている。** banto が5と宣言していても効かない。

呼び出し側（`runAutoSpawn`、`daemon.ts:4926`）はこう書かれている。

```ts
const maxSessions = this.maxConcurrentSessions();
...
if (live >= maxSessions) {
  return;              // ← 掃引ごと打ち切り。ready のタスクは1つも見ない
}
```

**上限に当たると、掃引そのものを打ち切る。** ログも出ない——だから**「なぜ着手しないのか」が外から一切見えない**。

## どういう害が出たか（実例）

2026-08-20、幹が「最優先で流す」と裁定した `task-0294` が、**席が空いている（工房 2/8・実装役 2/6）のに13分以上 `ready` のまま着手しなかった**。`task-0293` も15分待たされた。

そのとき生きていた職人2人は**どちらも `task-0292`**（契約改訂で rework が立ったのに、前の executor が畳まれず残っていた）。**関係のない dentaku の設定のせいで、banto の最優先タスクが1本も動けなかった。**

**コメントは「上限は層B設定（プロジェクト）＞ Kobo の既定。低い方を採る——プロジェクトが絞っているのに Kobo の既定で回すと、設定した意味が無い（決定67）」と書いてある。** 意図は正しい。**「そのプロジェクトが絞っているなら、そのプロジェクトは絞る」**という意味であって、**「どれか1つが絞ったら全部絞る」ではない**はずである。

## やること

**上限は、そのプロジェクトのものだけを見る。**

- `maxConcurrentSessions()` に**プロジェクトを渡す**（`maxConcurrentSessions(projectTag)`）。返すのは `min(Kobo の既定, そのプロジェクトの層B設定)`。
- `runAutoSpawn` の数え方も**プロジェクトごとに分ける**。「いま何人動いているか」も**そのプロジェクトの職人だけ**を数えること（いまは `liveKoboWorkers()` の全件を数えている）。
- **工場全体の上限が要るなら、それは別の概念として残す**（工房の `BANTO_WORKER_MAX_CONCURRENT` が既にその役をしている）。**プロジェクトの設定を全体の上限に流用しない。**
- **上限に当たって見送ったことを、ログに残すこと。** いまは黙って `return` するので、外から「なぜ着手しないのか」が分からない。**どのプロジェクトが、何人動いていて、上限がいくつだから見送ったのか**を書くこと。**これが無かったせいで、原因に辿り着くのにコードを読む必要があった。**
- **掃引ごと打ち切らないこと。** あるプロジェクトが上限に達していても、**他のプロジェクトの ready は見る**。いまは1つのプロジェクトが埋まると全部止まる。

## 変えないこと

- 「プロジェクトが絞っているなら、その値を優先する」という決定67 の趣旨
- 工房側の全体上限（`BANTO_WORKER_MAX_CONCURRENT`）と監査の予約席
