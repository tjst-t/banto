## 症状（実測。**3人が別々に踏んでいる**）

`inbox.post` に `canvasKind: "kobo.review"` と `canvasParams: {projectTag, taskId}` を**添えているのに**、こう言われて断られる：

> `approveAction` を結べません。`canvasKind: "kobo.review"` と `canvasParams: {projectTag, taskId}` を添えてください——どのタスクの判断かが札に載っていないと、POが押しても工場へ届きません。

- 枝 thread-114 は**書き方を3通り変えても全部同じ**（`approveAction` / `sendBackAction` / `sendBackReason` も付けた上で）
- 幹も別件で `approveAction: "now"` を付けて踏んでいる
- **3件目**：枝「決定番号の一意化」が `task-0159`（`review: po`）のレビューで踏んだ（2026-08-16）。`canvasKind` / `canvasParams` / `approveAction` / `sendBackAction` / `sendBackReason` を**全部そろえて**同じ断り文。直後に**同じ値**で `canvas.open({kind:"kobo.review", params:{projectTag:"banto", taskId:"task-0159"}})` を撃つと**通る**
- **`canvas.open({kind: "kobo.review", params: {projectTag, taskId}})` は同じ値で通る**（面は開く）

**添えているのに「添えろ」と言われる**——道具の言うことと実際が食い違っており、I2 のいちばん悪い形。**PO 必須のレビュー（決定113）が積めない**ので急ぐ。

### 実害の数え上げ（優先度の根拠）

**`review: po` のタスクでは、決定113 の形（押した答えがそのまま工場へ届く札）が事実上使えない。** 番頭に残る道は「レビュー面を `canvas.open` で開き、札には『判断は面で押してください』と書く」だけで、**PO は札を見てから面へ移り、もう一度押す**ことになる。task-0156 と task-0159 で実際にそうなった。**PO 必須のレビューが1本通るたびに、PO に二度手間が1回積まれる**——決定113 が「押した答えが届く」ために作った形が、いちばん要る場面だけ機能していない。

## 番頭が先に調べたこと（ここから続けてよい。ただし鵜呑みにせず現物で確かめること）

配線そのものは在る。`packages/banto-host/src/bin.ts`（会話ごとの道具を作るところ）で
`createInboxTools(inbox, { threadId, resolvePoDecisionEffect })` を渡しており、
`resolvePoDecisionEffect` は `koboReviewTarget(canvasKind, canvasParams)` を呼ぶだけ。
`koboReviewTarget`（`kobo-po-decision.ts`）は「`canvasKind === "kobo.review"` かつ
`canvasParams.projectTag` と `canvasParams.taskId` が空でない文字列」を要求するだけで、
ここに罠は無い。**つまり疑いは「値が execute まで届いていない」側にある。**

**有力な仮説（未確認）**：`canvasParams` は `OpenObject()`（`packages/banto-core/src/tool-schema.ts`）で
`{ type: "object", additionalProperties: true }` として書かれていて、**`properties` を持たない**。
これが2か所を通る：

1. **モデルに見せる定義**——現に番頭へ届いている `inbox.post` の定義では、この欄が
   `{"properties": {}, "type": "object"}` になっており、**`additionalProperties: true` が落ちている**
   （番頭の道具一覧で実物を確認済み）。つまりモデルには「中身の無い object」に見えている
2. **zod への変換**——`packages/banto-host/src/schema-to-zod.ts` の `jsonSchemaToZod` は
   `type: "object"` を `z.object(jsonSchemaToZodShape(node))` にし、`jsonSchemaToZodShape` は
   `node.properties ?? {}` を回すので **`z.object({})`＝shape が空**になる。
   zod の既定は未知のキーを**黙って落とす**（strip）ので、`{projectTag, taskId}` が
   `{}` になって execute に届く可能性がある

## 必ず解いてほしい矛盾（ここが山）

上の仮説が正しいなら、**同じ `OpenObject()` を使っている `canvas.open` の `params` も落ちるはず**なのに、
`canvas.open({kind:"kobo.review", params:{…}})` は現に効いている。**どちらかが間違っている。**

だから最初にやることは、**引数が execute にどう届いているかを現物で見ること**。例えば：

- Agent SDK の `tool()` が渡す前に zod で parse しているのか、生のまま渡しているのかを実際に確かめる
  （`packages/banto-host/src/claude-agent-harness.ts:303` が `jsonSchemaToZodShape` の結果を渡している）
- `canvas.open` の `params` が本当に届いているのか（届いているなら、なぜ `inbox.post` だけ駄目なのか）
- **`OpenObject()` を使っている道具を全部洗う**（`canvas.open` の `params`、`canvas.show` の `args`、
  `env.provision` / `env.verify` の `config`、`settings` の `values` など）。**同じ壊れ方をしているものが
  他にもあるなら、直しは1か所（`OpenObject` か `schema-to-zod`）に寄せる**

**原因を突き止めてから直すこと。** 「たぶんこれだろう」で `inbox-tools.ts` に
`canvasParams` の中身を書き足しただけでは、他の道具の同じ穴が残る。

## 直す方向（原因が分かってから選ぶ）

- 原因が **zod 変換で中身が落ちる**なら、`schema-to-zod.ts` を直す
  （`additionalProperties: true` かつ `properties` が無い object は、shape 空の `z.object({})` ではなく
  **未知のキーを通す形**にする）。I2 の方針は既にファイル冒頭に書いてある——
  「知らない形は黙って落とさない。落とすと引数が消えて、モデルには『その引数を渡す口が無い』ように見える」
- 原因が **モデルに見せる定義から `additionalProperties` が落ちること**なら、
  `OpenObject()` 側に**中身の項目を書ける口**を用意し、`inbox-tools.ts` の `canvasParams` には
  `projectTag` / `taskId` を明示する（`OpenObject` の意図＝「入れ子の部分スキーマを作らない」は壊さないこと。
  ADR-0019 決定84-3）
- 両方なら両方直す

**どちらに倒したかと、なぜそう言えるのか（何を見て確かめたのか）を、コミットの説明に書くこと。**

## 断り文（3つ目の受け入れ条件）

いまの断り文は、`canvasKind` が無いのか・`canvasParams` が無いのか・`taskId` だけ欠けているのかを
区別せず、**全部同じ文言**を出す。だから「添えているのに添えろと言われる」が起きたときに、
呼んだ側は何を疑えばいいのか分からない。**何が足りないのかを名指しする**形に直すこと
（例：「`canvasKind` が `kobo.review` ではありません（受け取った値: …）」「`canvasParams.taskId` が
空です」）。**受け取った値を文言に出す**と、次に踏んだ人がその場で気づける。
