## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

### 何が起きたか（実測）

職人は1本ごとに cgroup の袋（既定 **2 GiB**、`packages/banto-worker-pool/src/worker-cgroup.ts:43`）に入っている。2026-08-16、**その袋の上限に当たって職人が繰り返し殺された**。

- task-0160 の実装：opus の職人が**2回とも SIGKILL**（袋の peak **1.6 GiB** と **2.0 GiB＝上限ちょうど**に到達）
- task-0157 の監査：袋の中に **`npm test` と `npm run typecheck`** を抱えたまま上限に当たり、`memory.oom.group` で**15プロセスが袋ごと kill**
- task-0160 の rework：**`npm ci` が anon-rss 1.3 GiB** で kill
- 対照：`npm` を回さない職人（調べ物）は **250〜300 MiB** で収まっている

**つまり、袋を破っているのは職人の会話ではなく、袋の中で回している `npm` である。**

**今日1日の実害（2026-08-16 の実測）**：この穴が原因で `banto-worker-pool.service` が少なくとも7回 OOM で揺れ（00:30:50 / 01:26:51 / 03:06:40 / 03:51:07 / 03:54:58 / 04:06:33 / 04:35:35）、その巻き添えで**「中身は無罪なのに落ちた」タスクが7本**出た。工場の列が27本まで伸びて回らなくなった一次原因がこれである。

### なぜそうなっているか（出どころ）

**Kobo が指示文でそう命じている。**

- `packages/banto-daemon/src/daemon.ts:4575` 付近（実装者への「## 手順」の3番目）
  `3. 検証コマンドがあれば自分で実行して、通ることを確かめる（I1：通ったつもりで出さない）`
- 同 `:4478` 付近（`formatAcceptance`）が受け入れ基準に **「（検証コマンド: `npm test`）」** を添えて渡している
- 監査人への指示（`buildAuditInstruction`）と `skills/audit-checklist.md` には「実行しろ」と書いていないが、**実測では監査人も袋の中で `npm test` / `npm run typecheck` を回している**（各自の判断に委ねられている状態）

### 何を変えて、何を変えないか

**I1（通ったつもりで出さない）は1ミリも緩めない。** 検証をやめるのではなく、**回す場所を袋の外へ移す**。

- **マージ前ゲートは既に袋の外で回している**（`packages/banto-daemon/src/merge-gate.ts` が検証環境を立てて `acceptance[].verify` を実行）。**その仕組みを前倒しで使えるようにする**のがこのタスクである。
- **職人に `env.verify` は渡っていない**（道具は claude_code のプリセット＋`report` / `ask`＋Kobo の報告口だけ。`packages/banto-worker-pool/src/claude-agent/options.ts:106` と `claude-agent/host.ts:229` で確認済み）。だから**職人自身に環境を立てさせる形は採らない**。

## やること

**Kobo が検証コマンドを袋の外で回し、その結果を職人へ返す形にする。**

1. **職人が「検証してほしい」と言える口を作る**か、**Kobo が節目で自動的に回して結果を返す**か——**どちらでもよい**。既存の実装の流儀に合う方を選び、**選んだ理由を実装のコメントに残すこと**。参考になる形は2つある：
   - (i) 職人が `report_done` を呼んだ時点で、Kobo が**監査へ回す前に**検証を袋の外で回し、**落ちていれば結果を指摘（findings）として実装者へ差し戻す**（既存の findings の経路がある。`buildImplementInstruction` の「## <findingsHeading>」）
   - (ii) 職人が明示的に呼べる口（Kobo の報告チャネルに1つ足す）
2. **検証の実行は既存の経路を再利用する。** `merge-gate.ts` が持っている「検証環境を立てて `acceptance[].verify` を走らせ、結果とログを残す」仕組みを**共有の関数として切り出して使う**こと。**同じことを2箇所に実装しないこと**——ゲートと別実装になると「ゲートは通るのに職人のところでは落ちる」が起きる。
3. **指示文を書き換える。**
   - 実装者（`daemon.ts:4575` 付近の手順3）：**「検証コマンドを袋の中で直に叩かない」ことと、「ではどうやって確かめるのか」を明示する。**「回すな」だけ書くと、確かめずに終える職人が出る（I1 が壊れる）。
   - **監査人にも同じことを明示する**（`buildAuditInstruction`）。いまは何も書いていないため各自の判断に委ねられ、**実測では袋の中で回っている**。
   - **`formatAcceptance` が「（検証コマンド: `npm test`）」と見せている**のは、そのままだと「自分で叩け」と読める。**どこで回るのかが分かる文面にすること。**
4. **軽い確認は袋の中で構わない**（1ファイルの型検査、1本だけの spec 実行など）。**禁じるのは「一式」**（`npm ci` / `npm test` / `npm run typecheck` のような、リポジトリ全体を回すもの）。**その線引きを指示文に書くこと**——曖昧にすると各自の判断に戻る。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- 同時に走る職人の本数の上限（別タスクで積んである）
- `packages/banto-worker-pool` 側の変更——**このタスクは Kobo 側だけで完結させること**（職人の道具を増やす形は採らないと決めてある）
- マージ前ゲートの判定そのものの変更
- 稼働機の systemd 設定・cgroup の値

## 気をつけること

- **I1 を緩めない。** 「一式はゲートに任せて職人は確かめない」は**採らない**（今日、機械が1本も検証していない契約が通っていた事故＝inc-0076 があったばかりである）。**職人は確かめる。確かめる場所が変わるだけ。**
- **検証環境を立てる回数が増える**ことになる。既存のゲートは「**立てるのは1回**。受け入れ条件ごとに立て直すとテスト一式を何度も用意することになる」（`merge-gate.ts:390` 付近のコメント）としている。**同じ配慮をすること。**

