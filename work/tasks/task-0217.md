## 何が起きているか（別プロジェクトの実測・2026-08-16）

dentaku の task-0042 で、**同じ失敗の知らせが番頭へ繰り返し配られました。**

- **Kobo の帳簿の最後の出来事は `2026-08-16T08:40:39Z` の `rework session spawn failed: ... read ECONNRESET` 1件だけ**で、それ以降タスクは**一切動いていません**（`kobo.task` で確認済み）。
- **にもかかわらず、番頭のターンが同じ内容で3回起きました**：
  1. 「起きたこと: agent_exited_without_report」（**08:34 の分の再送**）
  2. 「【取り下げ】probe-worker-pool からの報告」（**既に読んで畳んだ職人の報告**が、取り下げ札として届いた）
  3. 「起きたこと: rework session spawn failed ... ECONNRESET」（**08:40:39 の分の再送**）
- そのたびに番頭は `kobo.task` を引いて「**新しい事故ではない**」と確かめる必要がありました。
- **しかもそのタスクは、既に PO 判断待ちの札（in-248b13b7）が立っていて先へ進めません。進めない件について、判断を促す知らせだけが増える**という形になっています。

**inc-0063 の「マージキューが同じタスクを積み続ける」と似た周回**です。

## どこを直すか（**スコープの根拠。2026-08-16 に番頭がコードで確かめた**）

元の起票は `packages/banto-daemon/src/daemon.ts` を指していましたが、**実測では配達そのものは番頭側（banto-host）で起きています**。したがってスコープは host 側だけです。

- `packages/banto-host/src/kobo-notice.ts:193` — `cursor = Math.max(cursor, event.eventId ?? 0)`。同ファイルに `readCursor(options.cursorPath)` があり、**配達位置は既にファイルへ永続化されている**。「配達済みの印」はこの仕組みの延長で持てる。
- `packages/banto-host/src/worker-notice.ts:152〜216` — **用が済んだ知らせを「【取り下げ】」として配り直す**経路。上記3番目の症状はここ。

**Kobo（`banto-daemon`）は触らないこと**（スコープ外。触ったらマージ前ゲートで落ちます）。

## 直す方針

1. **一度配った出来事を再配達しない。**同じ event id は**既配達として落とす**こと（配達済みの印をどこに持つかは実装者が決めてよいが、**再起動をまたいでも効くこと**。既存の cursor の永続化に倣う）。
2. **既に PO 判断待ちの札が立っているタスクについては、催促の知らせを抑える。同じ札が立っている間、同じタスクの同じ種類の知らせを繰り返し配らないこと。**
3. **ただし「新しい出来事」は必ず配ること。** 抑制は**同じ出来事の繰り返し**に対してだけ効かせること。**黙って落とすのがいちばん危ない**——落としたことが記録から読めること。

## 気をつけること

- **知らせを配らない方向へ倒しすぎないこと。**過去に「知らせが消えた」事故があります（inc-0069）。**落とすのは「同じ出来事の2回目以降」だけ**で、**新しい出来事・状態が変わった知らせは必ず届くこと。**
- **番頭が畳んだ職人の報告が「取り下げ札」として再度届く**経路も同じ穴の一部です。**畳んだ職人の報告は再送しないこと。**
- **`/var/lib/banto` 以下の実データに触らないこと。** 試験は必ず一時ディレクトリで。
