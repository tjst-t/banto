## なぜ変えるのか（PO の言葉のまま）

> **監査はプラスアルファの層にする。監査のせいで工程が止まる方が、いまは問題である。取りこぼしが出たら、そのとき別途直せばよい。**

発端は PO の疑問——「**Kobo はトークンを使いすぎではないか。opus 級を監査やレビューにも使う意味があるのか**」。
実測（2026-08-20）：`roleAssignments` は audit=**opus** / executor=sonnet / rework=sonnet。**実装より監査の方が高いモデルを当てている**。

そして実害が出ている。**監査人が袋の中で全量 `npm test` を起動し、「完了を待っています」と自由文で書いてターンを終え、`audit_reported_without_verdict` で failed になる型**（task-0219 で3回連続の実例。task-0246 / task-0242 も同型）。**判定を出し忘れただけで工程が止まる。**

これは**互いに整合する1つの設計転換**である。**①だけ入れて②を落とすと悪化する**（トークンは減っても failure は減らない）。**3つまとめて入れること。**

## やること

### ① 監査からテスト実行を剥がす。監査人に渡すのは diff。

**監査の役割は「受け入れ基準（`acceptance[].text`）への内容の適合」の判断であって、リポジトリ全体を読み直すことでも、テストを回すことでもない。**
検証は外の仕組み（**マージ前ゲート**）が受け入れ条件の `verify` を検証環境で回す——**そこと二重になっている。**

- `buildAuditInstruction()` に**そのタスクの diff を載せる**。
  - diff は職人のワークツリーで、タスクブランチと分岐元の差（`git diff <merge-base>...HEAD` 相当）を取る。**既にスコープ検査で diff を取っている実装があるはず**（`packages/banto-daemon/src/merge-gate.ts` / `gate-evaluator.ts` を読んで**同じ取り方を再利用**すること。新しい取り方を発明しない）。
  - **上限を設けること。** 大きすぎる diff は打ち切り、「ここで打ち切った・残りはファイル名だけ」と明記する（無言で切らない）。上限値は定数として名前を付けて定義する。
  - diff が取れなかったときは、**取れなかったと書いた上で従来どおりワークツリーを見てよい**と指示する（I2：黙って空の diff を渡さない）。
- 監査手順の文面を書き換える：
  - 「ワークツリーパスに移動して実装内容を確認してください」を落とし、**「渡された diff を読み、受け入れ基準を満たすか判断する。疑わしい箇所だけ他ファイルへ遡る。文脈は最小で足りる」**にする。
  - **「テストを回すのはあなたの仕事ではない」**と明示する。いまは「一式は自分で実行しないでください」止まりで、**回してよい軽い確認の余地を残している**——それが「袋の中で `npm test` を起動して待つ」型を生んでいる。**検証はマージ前ゲートが機械で回す、と言い切ること。**
- `skills/audit-system.md` と `skills/audit-checklist.md` も**同じ位置づけに書き直す**。「監査は合否の門ではなく、補助の目である」「見るのは diff と受け入れ基準の対応であって、コードベースの健全性一般ではない」。**チェックリストから、テストを回すこと・全体を読むことを前提にした項目を落とす。**

### ② 監査人が判定を出せる口を、確実に載せる。

**①だけやって②を放置すると、トークンは減っても failure は減らない。ここはセットで直すこと。**

- **監査役のセッションには `audit_report` が必ず載る**ことを、claude-agent 経路・pi 経路の**両方**で機構として保証し、**試験で縛る**。
  - `packages/banto-worker-pool/src/claude-agent/host.ts` の口の載せ方は条件分岐の中にある。**その条件を読み、監査役で必ず真になることを確かめる**。ならないなら直す。
  - `naming.ts` の道具名（`mcp__<server>__audit_report`）が、実際にモデルへ提示される名前と一致していることを確かめる。
- **指示文の中で、口の名前を正確に書く**こと（過去に監査人が「`audit_report` ツールはこの環境に存在せず」と書き残して落ちた実例がある）。
- 口が載っていないことが起動時に分かるなら、**監査を起こす前に理由を添えて止める**（I2：黙って始めさせない）。ただし③のフェイルオープンと矛盾させないこと——**止めるのではなく「既定で通す」に倒す**方が PO の意図に合う。迷ったら③を優先。

### ③ 判定は「明示の NG だけがブロック」＝フェイルオープン。

**監査人が NG を明示しなかったら自動で通す。忘れても通る。NG だけが止める。**

いまの失敗の大半は「**判定を出し忘れる**」型なので、**反転すればこの失敗型は原理的に消える。**

- `applyWorkerReport()` の audit 分岐：`audit_reported_without_verdict` で failed にするのをやめ、**pass 扱いで次段へ進める**（`review.policy` に従って `merging` / `review-ready`）。
- `handleAgentExited()` の audit 分岐：再試行（`AUDIT_ATTEMPT_LIMIT`）はそのまま残してよいが、**尽きたときに failed にせず、既定で通す**。
- `spawnAuditSession()` の spawn 失敗：**failed にせず、既定で通す**（監査が起動できないことでタスクを止めない）。
- **`verdict="fail"` が明示されたときだけ**、これまでどおり差し戻し（rework）にする。**そこは何も変えない。**
- **既定で通したことは帳簿に必ず残す。** 「監査が実質回っていないのに通った」件数を**あとから数えられる**ようにすること——`audit_verdict` イベント（`packages/banto-core/src/events.ts`）に**既定通過の印**（例：`byDefault: true` と、その理由の文字列）を持たせる。**新しいイベント種は増やさない**（既存の `audit_verdict` に印を足す）。これは下の「承知の上のリスク」を見張るための唯一の手段なので、**落とさないこと**。
- 番頭の会話へ流れる知らせ（`packages/banto-host/src/kobo-notice.ts`）も、**既定で通ったことが分かる文面**にする（黙って通すと、番頭が「監査が見た」と誤解する）。

## 承知の上のリスク（PO に説明済み・その上での決定）

**フェイルオープンにすると、監査が実質回っていないのにパス扱いになる経路ができる**（監査の起動自体が壊れていても通る）。

PO の判断：**「実装の正しさはゲートの機械検証が担保する。監査は補助の目に留め、忘れによる停止を根絶する方を取る」。**

**これは知らずに踏んだ穴ではなく、承知で選んだ設計である。** 将来ここで取りこぼしが出たときに「知らなかった」ではなく「承知で選んだ」と読めるよう、**この段落の趣旨をコードのコメントにも残すこと**（とくに③で failed をやめる3箇所）。**「なぜここで通すのか」がコードだけを読む人に伝わる形にする。**

見張りの手段は、上に書いた**帳簿の既定通過の印**である。**それが無いとリスクを承知したことにならない**ので、必ず入れること。

## 変えないこと（縮めない境界）

- **マージ前ゲートは何も変えない。** `verify` を検証環境で回すのはこれまでどおりで、そこが実装の正しさを担保する。
- **`verdict="fail"` の扱いは変えない。** 明示の NG は止める。
- **PO レビュー（`review.policy: po`）は変えない。** 統治コードが番頭を素通りしないことは決定57／ADR-0023 のまま。
- **職人（実装役）への指示は変えない。** 触るのは監査役の側だけ。
