## なぜこれを積むのか

**同じ穴に少なくとも14回落ちています。** 道具をモジュールの在庫（`BantoModule.tools`）に登録したのに、**提示の表（`packages/banto-host/src/presented-tools.ts` の `PRESENTED_TOOL_NAMES`）へ載せ忘れる**という穴です。載せ忘れると、**在庫には在るのにモデルからは存在しない**ことになります（決定82）。

`presented-tools.ts` 自身がこの穴を繰り返し警告しているのに、**同じファイルに落ちた実例の注記が13件並んでいます**：

1. `worker.keeps` — 機構が守った取り置きが「在るのに誰も気づけない」ものになっていた
2. `kobo.send_back` — 片方だけ提示され「通す」しか押せなかった
3. `kobo.abandon` / `kobo.supersede` — **在庫には最初からあったのに提示していなかった**。機構は「`kobo.abandon` で畳んでください」と案内し続けながら、番頭の手にその道具が無かった
4. `kobo.settle` — 「在庫に足すだけでは足りない。**ここに載せないとモデルには見えない**」
5. `kobo.projects` / `set_merge_queue` / `set_watch` — 工場が1分ごとに同じタスクを起票し続けたのに止める術が無かった（inc-0063）
6. `kobo.register_project` — 外す口だけ提示され、**入れる口が無かった**。職人に生 HTTP を叩かせて迂回した
7. `canvas.list_catalog` — プロンプトが「これで何が開けるか分かる」と書いているのに提示されていなかった
8. `thread.read` / `steer` / `consult` — 「在庫に足すだけでは届かない」
9. `thread.open_trunk` — プロンプトにも SKILL にも書いてあるのに提示されず、番頭は PO に「画面から作ってください」と頼んだ
10. `thread.settle` — 降ろす口が無く、一覧に「消えない行」だけが残った
11. `thread.rename` — 会話が仮の題のまま並んだ
12. `thread.close_trunk` — 自分で起こした幹を自分で終えられなかった
13. `system.restart` — SKILL が「これを呼ぶ」と書いているのに提示されず、職人に `kill -9` させていた

**14件目が共有ブラウザ（task-0178）です。** `browser.start` / `stop` / `status` が漏れ、**面は開くのに番頭がブラウザを起こせない**——面を開くと「browser.start で起こしてから開いてください」と言われて閉じるだけ、という**完全な行き止まり**でした（面から起こす口も HTTP の口も無いので迂回不能）。

**14回落ちているなら、注意力の問題ではありません。** 個々の受け入れ条件に「提示に載せること」と書き足しても、次のモジュールでまた忘れます。

## 検討した「もっと強い形」と、採らなかった理由（重要・実装者はここを読むこと）

防止の強さには序列があります（上ほど強い）：**①そもそも間違えられない形 ②機械の番人が落とす ③実行時に意図と現実を突き合わせる ④説明や SKILL に書く ⑤記憶**。今回 ④ は「警告が書いてあるファイルの中で」14回破られました。**だから ④ には戻しません。**

**①のうち「コンパイラが拒む」形は、この設計では取れません。** Tool 名は静的な union ではなく、`ToolRegistry.register()` が実行時に `assertNamespacedToolName` で検査する**ただの文字列**です（`packages/banto-host/src/tool-registry.ts`）。モジュールは実行時に差し替わる前提なので、全 Tool 名を静的に列挙した型は存在せず、`Record<ToolName, …>` の網羅性検査は成立しません。**「型で落とす」は諦めます。**

**①のうち「提示を在庫から完全に導出する（提示＝在庫−除外）」も採りません。** 一見これで「載せ忘れ」概念が消えますが、**既定が opt-in から opt-out に反転**します。その代償が具体的です：

- 提示する道具を選ぶ基準は「**番頭に持ってほしいか**」という **PO 裁定（2026-08-12・決定83）**です。opt-out にすると、新しいモジュールの道具が**誰も判断しないままモデルへ届きます**。
- inc-0057 の実測では、**道具が一覧の39番目にあると呼び出しが 0/10** でした。opt-out で一覧が黙って伸びると、**関係ない道具まで呼ばれなくなる**——これは**静かな劣化**で、今回の「行き止まり」より**気づきにくい**。

**採る形：「分類し忘れ」だけを構造的に潰す。**

- 意図して提示するもの＝これまでどおり `PRESENTED_TOOL_NAMES`（**並びには意味がある**——決定85・inc-0057）
- 意図して提示しないもの＝**明示の除外一覧に理由つきで**
- **どちらにも無い＝分類し忘れ → 隠さずに提示し、同時に大きな声でエラーを出す**

こうすると、**14回起きた失敗（＝道具が番頭の手に無い行き止まり）は構造的に起こりません**。忘れたときに起きるのは「並びの末尾に道具が1本増える」だけで、**行き止まりにはならない**。そして黙ってはいないので、次の一手で直せます。**意図（並び・除外）だけが手書きに残り、手書きの失敗が致命的でなくなる**——これがこの設計の狙いです。

**起動を止めないこと。** 分類の漏れ1件で番頭が上がってこない方が、害が大きい。

## やること

1. `presented-tools.ts` に**明示の除外一覧**を新設する（例 `INTENTIONALLY_NOT_PRESENTED`）。1件ずつ「なぜ番頭に渡さないのか」の理由を書く。**既存の未提示の道具を移すときは、表の既存コメントにある理由をそのまま引くこと**（例：「書き換え系は設定画面にあるので落とす（決定41c）」）。**理由を新しく創作しない。**
2. 提示集合を組むところで、**在庫にあってどちらの一覧にも無い Tool を末尾に足し、エラーを出す**（起動は止めない）。
3. `tests/acceptance/presented-tools-covers-inventory.spec.ts`（新規）に、全モジュール走査の試験と、分類し忘れの振る舞いの試験を書く。

**提示する道具の増減は、この作業で判断しないこと。** 何を番頭に持たせるかは PO と番頭の判断で、掃除のついでに変えるものではありません。
