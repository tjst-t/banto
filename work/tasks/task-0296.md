## 何が起きているか（実測。枝 thread-229 が確かめたもの）

`tests/acceptance/audit-crash-retry.spec.ts` の **「やり直し後の再監査では、試行回数が数え直される」** が、**フルスイートの負荷下でだけ落ちる**。

- **task-0283 のマージ前ゲート a6 で、2839本中この1本だけ落ちた**（`Error: 待っていた状態にならなかった`）
- **番頭が `env.verify`（profile `test`）で同じ spec を単体実行したら exit 0 で通過**——**恒常的な赤ではない**
- 原因は **`audit-crash-retry.spec.ts:49` の `until(check, timeoutMs = 10_000)`**——**壁時計で10秒・50ms 間隔のポーリング**。一式2839本と職人が同時に走る負荷下で、10秒に収まらない

## これは3度目の同じ失敗である

**「タイムアウトの数字を上げる」で済ませないこと。** 同じ形の間欠に対して、この repo では既に2回それをやって、3度目が出ている（`task-0267` の `93529a49`、`task-0269`。いずれも `BANTO_CLAUDE_START_TIMEOUT_MS` を 150ms → 1000ms に上げただけ）。**数字を上げる手当ては、負荷が上がればまた破れる。**

## やること

**`task-0291` と同じ直し方（壁時計依存を断つ）を使う。**

`task-0291`（「claude-agent-start-timeout の a3/a5 が負荷下で落ちる——3度目なので『数字を上げる』をやめて壁時計依存を断つ」）が**先に着地しているなら、その形をそのまま踏襲すること**。**新しい流儀を発明しない**——同じ問題に2つの解き方があると、次に読む人がどちらに合わせるべきか分からなくなる。着地していなければ、`work/tasks/task-0291.md` の依頼を読んで方針を合わせること。

方針の要点（`task-0291` と共通）：

- **「本物の非同期処理が N 秒以内に終わるか」を実時間で測るのをやめる。** 時間の進み方を試験が握るか、待っている対象の完了を試験が任意のタイミングで起こせるようにする。
- **負荷とは無関係に、決まった結果になること。** 遅いマシンでも、フルスイートの最中でも変わらない。
- **見ている振る舞いそのもの（やり直し後の再監査で試行回数が数え直される）は変えない。** 縛りを緩めない。
- **採った筋と、その理由をコメントに書くこと。**

`until()` がこのファイル内のヘルパなら、そこを直すのがいちばん狭い。**共有ヘルパに手を入れる必要が出たら、スコープ外なので手を止めて番頭に聞くこと**（勝手に触るとマージ前ゲートのスコープ検査で落ちる）。

## 確かめ方

**「単体で通った」を根拠にしないこと。** この間欠はまさに単体では通る。**フルスイート（`npm test`）で通ることを確かめる**。手元の袋の中で一式を叩かないこと——マージ前ゲートが検証環境で回す。
