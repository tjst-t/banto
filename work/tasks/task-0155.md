## 背景

imp-0062 の**前半（落ちる範囲を事実に合わせる）は既に着地している**——`system.restart` の
説明文（`packages/banto-host/src/restart-tool.ts`）も SKILL `safe-restart` も、いまは
「落ちるのは走行中のターンだけ／職人と検証環境は別ユニットなので落ちない」と正しく書いてある。
`tests/acceptance/restart-blast-radius.spec.ts` がそれを固定している。**そこは壊さないこと。**

**残っているのは imp-0062 の追記ぶん（「だから何を直すか（この追記の分）」）だけ**で、
中身は1つ：**`system.restart` が起こし直すのは `banto.service` だけなのに、それがどこにも
書かれていない**。

banto は3つの常駐サービスに分かれ、**どれも `--import tsx` で main のチェックアウトの .ts を
直に読む**（ビルド成果物を経由しない）：

| unit | 何を持つ | どのコード |
|---|---|---|
| `banto.service` | 番頭本体・会話 | `packages/banto-host/**` |
| `banto-worker-pool.service` | 職人の親 | `packages/banto-worker-pool/**` |
| `banto-environment-pool.service` | 検証環境の台帳・ドライバ・Caddy 公開 | `packages/banto-environment-pool/**` |

つまり **main にマージしただけでは、そのプロセスを起こし直すまで反映されない**。実際に踏んだ
形が inc-0073：検証環境のドライバを直して main に入れたのに `env.verify` は古い挙動のままで、
`system.restart` を撃っても直らなかった（**そこは別のサービスだから**）。

起こし直し方は 2026-08-15 に実測済み：`sudo` は通らない（`no new privileges`）。
`banto-environment-pool.service` / `banto-worker-pool.service` はどちらも `Restart=on-failure` /
`RestartSec=5` なので、**主プロセスを `kill -9` すれば systemd が拾って起こし直す**。

```
systemctl show banto-environment-pool.service -p MainPID -p ActiveState
kill -9 <MainPID>
sleep 15
systemctl show banto-environment-pool.service -p MainPID -p ActiveState -p SubState -p NRestarts
```

**巻き添えは無い**（実測）：立っていた検証環境2つは `Up` のまま（コンテナは
`docker-<id>.scope` に居て pool の cgroup とは兄弟）、Caddy の公開 route は `caddy.service`
自身が持つので pool の生死と独立、起動時の `sweep()` は生きている環境に触らず `reconcile()` は
孤児を知らせるだけで畳まない。
