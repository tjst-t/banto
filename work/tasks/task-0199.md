## なぜこれを積むのか

**同じ穴に少なくとも14回落ちています。** 道具をモジュールの在庫（`BantoModule.tools`）に登録したのに、**提示の表（`packages/banto-host/src/presented-tools.ts` の `PRESENTED_TOOL_NAMES`）へ載せ忘れる**という穴です。載せ忘れると、**在庫には在るのにモデルからは存在しない**ことになります（決定82）。

`presented-tools.ts` 自身が、この穴を繰り返し警告しています——「**在庫に足すだけでは足りない。ここに載せないとモデルには見えない**」。にもかかわらず、同じファイルには**落ちた実例の注記が並んでいます**：

1. `worker.keeps` — 「ここに無いと、機構が守った取り置きは**在るのに誰も気づけない**ものになる」
2. `kobo.send_back` — 片方だけ提示され「通す」しか押せなかった
3. `kobo.abandon` / `kobo.supersede` — 「**在庫には最初からあったのに提示していなかった**」。機構は「`kobo.abandon` で畳んでください」と案内し続けながら、番頭の手にその道具が無かった
4. `kobo.settle` — 「在庫に足すだけでは足りない。**ここに載せないとモデルには見えない**」
5. `kobo.projects` / `kobo.set_merge_queue` / `kobo.set_watch` — 工場が1分ごとに同じタスクを起票し続けたのに、止める術が無かった（inc-0063）
6. `kobo.register_project` — 外す口だけ提示され、**入れる口が無かった**。職人に生 HTTP を叩かせて迂回した
7. `canvas.list_catalog` — システムプロンプトが「これで何が開けるか分かる」と書いているのに提示されていなかった
8. `thread.read` / `thread.steer` / `thread.consult` — 「在庫に足すだけでは届かない」
9. `thread.open_trunk` — プロンプトにも SKILL にも書いてあるのに提示されず、番頭は PO に「画面から作ってください」と頼んだ
10. `thread.settle` — 降ろす口が無く、一覧に「消えない行」だけが残った
11. `thread.rename` — 会話が仮の題のまま並び、どれが何の話か分からなくなった
12. `thread.close_trunk` — 自分で起こした幹を自分で終えられなかった
13. `system.restart` — SKILL が「これを呼ぶ」と書いているのに提示されず、職人に `kill -9` させていた

**14件目が、共有ブラウザ（task-0178）です。** `browser.start` / `browser.stop` / `browser.status` が提示から漏れ、**面（`browser.viewer`）は開くのに番頭がブラウザを起こせない**——面を開くと「browser.start で起こしてから開いてください」と言われて閉じるだけ、という**完全な行き止まり**になっていました。面から起こす口も HTTP の口も無いので、迂回もできません。

**14回同じ穴に落ちているなら、それは人の注意力の問題ではありません。** 個々の受け入れ条件に「提示に載せること」を書き足しても、次のモジュールでまた忘れます。**機構で落とすのがこのタスクです。**

なお **`browser.*` を表に足す応急の直しは別に進んでいます**（task-0178 の作業。着地済みか着地間近）。**このタスクの目的はそこではなく、「次に誰かが忘れたとき、機械が落とすこと」**です。

## やること

### 1. 全モジュールを走査する試験を書く

`tests/acceptance/presented-tools-covers-inventory.spec.ts`（新規）に:

- **番頭ホストが登録する全モジュールの在庫（`BantoModule.tools` の名前）を集める**
- そのすべてが **`PRESENTED_TOOL_NAMES` に載っているか**、**または明示の除外一覧に理由つきで載っているか**を確かめる
- **どちらでもない Tool が1本でもあれば落ちる**。落ちるときは**その Tool 名と、どのモジュールのものか**をメッセージに出すこと（「どれが漏れているか」が一目で分かること）

**`browser` だけを見る試験にしないこと。** 特定のモジュール名をべた書きすると、次に増えたモジュールを見逃します。**モジュールの一覧から機械的に取る**こと。

モジュールの集め方は実装を読んで決めてください（`packages/banto-host/src/bin.ts` が `createModuleRegistry` へ登録している並びが手掛かりです）。試験のためだけに本番の構成を作り直すのが難しい場合は、**「登録されうるモジュール factory の一覧」を1箇所に出す**形にしてもよい——ただし**その一覧自体が漏れうる**ので、そうするなら**その一覧と `bin.ts` がずれていないことも機械で確かめる**こと。ずれを許すと、この試験は「漏れを見つける試験」ではなく「漏れを見逃す試験」になります。

### 2. 意図的に載せないものは、明示的に除く

提示しない判断そのものは正当です（表の冒頭にあるとおり、**選ぶ基準は使用頻度ではなく「番頭に持ってほしいか」**）。だから「全部載せろ」という試験にはしないこと。

- **除外一覧を `presented-tools.ts` に置く**（例 `INTENTIONALLY_NOT_PRESENTED`）
- **1件ずつ理由を書く**（なぜ番頭に渡さないのか）
- **黙って落ちるのをやめ、明示的に除く**のが目的です

いま提示されていない在庫（`llm.*` の書き換え系18本など）を除外一覧へ移すときは、**表の既存コメントに書かれている理由をそのまま引くこと**（例：「書き換え系は設定画面にあるので落とす（決定41c）」）。**理由を新しく創作しないでください。**

### 3. 「壊れていれば落ちる」ことを確かめる

`PRESENTED_TOOL_NAMES` から1本外すと**この試験が落ちる**ことを一度確かめ、元に戻してから報告に書くこと。**落ちない試験は、通っても意味がありません。**

## やらないこと

- **提示する道具の増減を、このタスクで判断しないこと。** いま提示されているものは提示されたまま、されていないものは除外一覧へ「現状の理由つきで」移すだけ。**何を番頭に持たせるかは PO と番頭の判断**であって、この作業で変えるものではありません
- 表の並び替え（並びには意味があります——決定85）
- `presented-tools.ts` と試験以外のファイルを触ること

- **`npm run test:ui`（Playwright）は書かないこと**——検証の器にブラウザが無く全滅します（imp-0068）
