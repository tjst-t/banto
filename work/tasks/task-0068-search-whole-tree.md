## 背景（PO報告 2026-08-07）

「grep のツールがファイル全体ではなく一部しか検索しないみたい」。**そのとおりだった。**

`file.grep` は自前でツリーを歩き、ファイルを1つずつ読んで正規表現に掛けていた。そこに
3つの「黙って一部だけ」があった。

| どこ | 何が起きていた |
|---|---|
| `limit` の頭打ち | `Math.min(params.limit ?? 200, 200)` ——**200 より多くは頼めない**。番頭が `limit: 1000` と書いても 200 で返り、しかも上限で走査ごと打ち切るので、結果はツリーの一角に偏る |
| 総数を返さない | 「… 上限 200 件で打ち切り」とは言うが、**あと何件あるのか言わない**。番頭は「だいたい網羅した」と読んでしまう |
| 1MB 超は未検索 | `MAX_SEARCH_BYTES` を超えるファイルは開かずに飛ばす。件数は返していたが、**探した範囲に穴がある**ことは変わらない |

実測では `"export function"` が本物の grep で 264 件、`file.grep` は 200 件で打ち切り。
`file.find`（上限200・頭打ち）と `file.list`（上限200・`limit` 引数すら無い）も同じ形。

**一番悪いのは「打ち切り」を件数抜きで言うこと**（task-0066 で踏んだ「空振りしている検査は
無い検査より悪い」と同じ形）。少なく返っているのに、返り値だけ見ると全部に見える。

## やったこと

1. `file-search.ts`（新）。**探すのは外の道具に委ねる**（PO 指示）：`rg` → `grep` →
   自前の走査。自前を最後に残すのは、どちらも無い環境で黙って0件にしないため（I2）
2. **総数を必ず返す**。上限で切っても数え上げは最後まで進める。数え上げ自体を打ち切った
   ときは `totalExact: false` を返す——**分からないことを分かったふりにしない**
3. 上限は既定 200 のまま、**天井を上げた**（grep 2000 / find 5000 / list 5000）。
   既定を上げないのは番頭の文脈を埋めないため。頼めば取れる、が要点
4. `file.list` に `limit` を足した（無かった）

## 正規表現の方言について（意識して変えた）

到達先が変わるので**方言も変わる**：rg は Rust regex、grep は PCRE（`-P` が使えるとき。
使えなければ ERE）、自前は JS の `RegExp`。`\d` `\b` `|` `()` といった日常の書き方は
3つとも同じに動くが、後読みのような端は揃わない。

- **受け付ける前に JS の `RegExp` で構文だけ検査する**（壊れた正規表現を黙って0件にしない・I2）
- **どの道具で探したかを返す**（`details.engine`）。揃わなかったときに追える

利用体験を変える変更だが、PO の明示の指示なので D9 の escalate には当たらない。

## 実機について

**この機械に ripgrep は入っていない**（apt にはある）。しかも `/usr/bin/grep` は GNU grep
ではなく **ugrep 7.5.0**。必要な旗（`-rnIZ` / `-P` / `--include` / `--exclude-dir`）は
揃っていることを実物で確かめた。ripgrep の経路は、本物の rg を持ってきて突き合わせた
（`BANTO_RIPGREP_BIN` で到達先を差せる——入れなくても使える口を残した）。
