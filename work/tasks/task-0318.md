## 背景

`task-0307`（知らせの退避・変更範囲は `packages/banto-host/src/server.ts` と `artifacts.ts`）の検証で、`tests/acceptance/audit-crash-retry.spec.ts` が**1本だけ**落ちた。同じ実行で **2902件中2896件通過**、`banto-host` を触った受け入れ基準のテストは全部通っている。追った職人の報告：

> 原因は `packages/banto-daemon/src/daemon.ts` 内の既存の競合状態。`runAuditWatchdog`（巡回）と `handleAgentExited`（監査人 exit の直接処理）が、どちらも「監査の再試行上限に達した」場面で `recordAuditPassByDefault` を呼ぶが、**先に着火した方の理由文字列（`audit_never_started` / `audit_session_exited_without_verdict`）がテストの期待と食い違う**。

このテストは `banto-host` を一切 import していないので、`task-0307` の差分とは無関係。**既存の不具合が、たまたま別のタスクの検証で表に出た**もの。

## なぜ直す価値があるか

これは単に「テストが揺れる」話ではない。**帳簿に残る「なぜ監査を既定で通したか」の理由が、実行のたびに変わる**ということ。あとから「この監査は何が起きて通ったのか」を辿るときに、記録された理由が競争の勝敗で決まっているのでは根拠にならない。

さらに実害として、**無関係なタスクのマージ前ゲートを巻き添えで落とす**。既に `task-0307` が1本これで止まっている。

## やること

1. `packages/banto-daemon/src/daemon.ts` の `runAuditWatchdog` と `handleAgentExited` を読み、**「監査の再試行上限に達した」ときに `recordAuditPassByDefault` を呼ぶ経路がなぜ2本あるのか**を把握する。
2. **どちらが先に着火しても、記録される理由が同じになるようにする。** 望ましい形は次のどちらか——実装を読んだうえで、理由を添えて選ぶこと：
   - (a) **着火点を1つにまとめる**（片方は判定だけして、実際の記録はもう一方に任せる）
   - (b) **理由を「どちらの経路から来たか」ではなく「実際に何が起きたか」から決める**（監査人が一度も起動しなかったのか、起動したが判定を出さずに終わったのかは、履歴を見れば経路によらず判る）
   **(b) のほうが望ましい**——理由文字列は帳簿に残る事実なので、観測された事実から決まるべきで、どちらのコードが先に走ったかで決まるべきではない。(a) を選ぶなら、なぜ (b) が採れないのかを書くこと。
3. **二重に記録されない**ことを保証する（片方が既に記録していたら、もう片方は何もしない）。
4. `tests/acceptance/audit-crash-retry.spec.ts` が**どちらの経路が先に走っても通る**ようにする。テストの期待をゆるめて通すのではなく、**理由が決定的になったことをテストで押さえる**こと。

## やらないこと

- 監査の再試行上限そのもの（回数・条件）を変えないこと。
- 「監査を既定で通す」という振る舞いの是非には触らないこと。今回直すのは**理由が決まらないこと**だけ。
- `task-0305` で入った `latestSpawnedSessionId` のガード（置き換えられた古い職人の終了で失敗にしない）を壊さないこと。同じあたりのコードなので気をつけること。

## 反映について

`packages/banto-daemon` は **banto-daemon.service** という別ユニットで動いている。`banto.service`（番頭本体）を起こし直してもこの変更は反映されない。**起こし直しは番頭が別途行うので、このタスクでは何もしないこと。**
