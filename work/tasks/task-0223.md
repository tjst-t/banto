## 背景

task-0216（`210000ce`）で工房に同時本数の栓（既定6本）が入ったが、**枠は完全な早い者勝ち**である。
`WorkerPool.reserveSlot()`（`packages/banto-worker-pool/src/pool.ts:1203`）は誰の依頼かを見ておらず、
`concurrency()` も役割を持たない。

そのため **実装の職人が6本で埋まると、監査の職人が起きられない**。監査が起きなければタスクは
`auditing` から出られず、レビューにも着地にも進めない——**実装だけが席を取り、判定が永久に待つ**
形になる。2026-08-16 は「監査が起動できない」で3回落ちており、これが上限のせいで恒常化する。

Kobo は既に役割を知っている（`packages/banto-daemon/src/daemon.ts` の `delegateWorker` は
`role: "executor"` / `"auditor"` を受け取っている）が、**工房へは渡していない**
（2476 付近の `worker.delegate_toolkit` の引数に `role` が無い）。

## やること

1. **役割を工房まで運ぶ。**
   `worker.delegate_toolkit` の入力に役割を1つ足し（`role`。値は `executor` / `auditor` の2つで足りる）、
   `DelegateInput` から `reserveSlot` まで通す。**省略時は `executor`**——番頭が直に起こす職人も
   実装側として数える。Kobo は `delegateWorker` が持っている `role` をそのまま渡す。
2. **判定側に席を確保する。**
   - 実装（`executor`）が取れるのは **上限 − 予約席** まで。
   - 監査・判定（`auditor`）は **上限** まで取れる。
   - 予約席は数（既定の提案は 2）で持ち、環境変数で変えられること
     （名前は `BANTO_WORKER_MAX_CONCURRENT` の流儀に合わせる。読めない値を黙って既定に落とさない・I2）。
   - 断りの文面には**どちらの枠で断ったか**を書く（「実装の枠が埋まっています（4/4。監査用に2席
     空けてあります）」のように、読んだ番頭が次の手を選べる形）。合印 `BANTO_WORKER_LIMIT` は
     そのまま使ってよい。
3. **覗き窓に出す。** `worker.list`（`packages/banto-worker-pool/src/worker-tools.ts`）の
   「同時に走っている職人: N / M 本」に、実装と判定の内訳が読めるよう足す。
4. **既定の内訳を書き直す。** いまの `DEFAULT_MAX_CONCURRENT_WORKERS = 6` の根拠コメントは
   「Kobo の5本＋番頭の1本」である。予約席を入れると実装の取り分が減るので、**6 の内訳を
   書き直すこと**。**既定の上限そのもの（6）は上げないこと**——上げるべきだと判断したら、
   根拠（実測 1本 0.23〜0.56 GiB、工房の MemoryMax 7〜8 GiB）を添えて報告に書くだけにする。
