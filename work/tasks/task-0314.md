## 背景（あなたは記憶を持たないので全部ここに書きます）

`system.deploy`（計画的デプロイ）は、常駐サービスを起こし直す前に main へ検証一式（既定 `npm test`）を回します。実体は `packages/banto-host/src/deploy-verify.ts` の `runDeployVerify()` で、`execFile` で `npm test` を起動しています。

問題は、この子プロセスが**番頭本体（banto.service）の環境変数をそのまま継承する**ことです。`deploy/banto.service` には次の Environment が並んでいます（実測）:

```
:25  NODE_ENV=production
:26  BANTO_DATA_DIR=/var/lib/banto
:30  BANTO_PLACES=banto:/home/ubuntu/ghq/github.com/tjst-t/banto:docs/**,work/**
:33  BANTO_KOBO_DATA_DIR=/var/lib/banto/data
:37  BANTO_WORKER_POOL_URL=http://127.0.0.1:4300/api/worker-pool
:38  BANTO_ENV_POOL_URL=http://127.0.0.1:4400/api/environment-pool
:41  BANTO_ENV_POOL_DATA=/var/lib/banto/environment-pool
:56  BANTO_BROWSER_ALLOW_NO_SANDBOX=1
```

いっぽうマージ前ゲートの検証コンテナ（docker/test.yaml）には **BANTO_* が1つもありません**。だから「main はゲートで緑なのに、デプロイ検証だけ落ちる」という食い違いが恒常的に起きます。

### 実際に落ちた2件（2026-08-20 のデプロイ検証・tests 2900 / fail 2）

```
✖ BANTO_BROWSER_ALLOW_NO_SANDBOX が無ければ --no-sandbox は入らず、status も enabled
  AssertionError: 既定なのに --no-sandbox が入っている
  tests/acceptance/browser-chromium-launcher.spec.ts:673
```
```
✖ [a2][a3][a4] 一方が上限に達しても他方の ready は進み、見送りはログに残る
  AssertionError: actual 'failed' / expected 'planning'
  tests/acceptance/kobo-cost-ceiling.spec.ts:512
```

1件目の因果は特定済みです。実装が `allowNoSandboxEnv ?? process.env.BANTO_BROWSER_ALLOW_NO_SANDBOX` と書いてあり、テストが「環境変数は無い」つもりで `undefined` を渡すと `??` の右辺（＝継承した実環境変数 `=1`）に落ちます。docker で対照実験済み：**変数なしで 43/43 合格、`BANTO_BROWSER_ALLOW_NO_SANDBOX=1` を与えると 42/43 が落ちる**。

つまり **コード側の欠陥ではなく、走らせ方（環境の混入）の欠陥**です。テストを書き換えて回避するのではなく、検証の走らせ方を直します。加えて `BANTO_DATA_DIR=/var/lib/banto` や `BANTO_KOBO_DATA_DIR` を継承したまま試験を回すのは、**本番のデータディレクトリを試験が触りうる**という意味でも危険です。

## やってほしいこと

`packages/banto-host/src/deploy-verify.ts` の `runDeployVerify()` が起動する子プロセスへ渡す環境を、**`BANTO_` で始まる変数をすべて落としたもの**にしてください（それ以外の変数——PATH・HOME・LANG など——は継承したまま）。ゲートの検証コンテナと条件を揃えるのが目的です。

- 落とす判定は名前付きの純関数に切り出し、`export` してテストから直接叩けるようにすること（例 `sanitizeVerifyEnv(env: NodeJS.ProcessEnv): NodeJS.ProcessEnv`）。
- `execFile` の `env` にその結果を渡すこと。既定の `process.env` 継承に頼らない。
- 生ログの置き場（`defaultRawLogDir()` が読む `BANTO_DATA_DIR`）は**親プロセス側**の話なので従来どおりで構いません。落とすのは子へ渡す環境だけです。
- 既存の呼び出し（`packages/banto-host/src/bin.ts` / `deploy-gate.ts`）は無改修で動くこと。
