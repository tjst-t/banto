## 何が起きているか（PO の実観測・2026-08-16）

**畳んだ枝が、一覧に開いたまま残り続ける。**

いまの振る舞い（`tests/acceptance/closed-thread-delivery.spec.ts` に固定済み）：
**畳んだ枝へ知らせが届くと、その枝が開き直り、その枝のターンが回る**（親の幹は 0 本）。
知らせを捨てないための正しい仕組みで、**PO の設計の土台でもあります。これ自体は残すこと。**

**穴はその先です。** 開き直した枝に渡るのは**畳んだときまでの記録**で、「あなたは開き直された」という情報がありません。したがって枝は**「私はもう畳んだ枝です」と認識したまま**返事をし、**`thread.merge` を呼びません。**畳む口を叩く者が誰もいないので、**開いたまま一覧に残り続けます。**

**この穴はこれから重くなります。**PO の設計（2026-08-16）では **Kobo の知らせは「そのタスクを積んだ枝」へ配られ、畳んでいても開き直す**——**開き直しが常態になる**ためです。

## 前の職人が調べ上げた事実（**読み直さなくて済むように写します**）

- **畳んだ宛先を開き直しているのは `server.ts` の `reopenClosedTarget()`（1108行〜）**。`ThreadRegistry.reopen()` を呼んだあと、system の印を `thread.record` しているだけ。
- **呼び出し元は `server.ts` の `deliverToThread()`（1029行〜）**。ここが
  `reopenClosedTarget → record(知らせ) → turn_start → await promptEvenWhileBusy → turn_end`
  という**ターン1本の全体**を持っている。**ターンの終わりを知っているのはここだけ。**
- 枝の LLM に渡るのは `thread.harness.prompt(text)` の `text` だけで、**`thread.record` した印は文脈に入らない**（既存試験でも `prompts` は知らせ本文1件のみ）。
  つまり**「あなたは開き直された」を枝に伝える口も `server.ts` 側**。
- **`threads.ts` だけで閉じようとすると**、`thread.notices` の Promise 鎖に畳み直しを継ぎ足す形になり、**配達の実装が変わった瞬間に黙って効かなくなる**（前の職人の判断。**採らないこと**）。

## 直す方針（**枝の自己申告に頼らないこと**）

**PO が承認した形**：**判断とデータは `threads.ts` / `thread-store.ts` に置き、`server.ts` へは繋ぎだけ**（知らせ本文を渡す・ターンの終わりに畳み直しを1行呼ぶ、の十数行）。**D5（判断を Surface に置かない）を保つこと。**

1. **知らせで開き直した枝は、そのターンが終わったら機構が自動で畳み直す。**
   **元の結論・investigated / decided / remaining は保つこと**（上書きしない・消さない）。
2. 開き直した枝の文脈に、**機構が「あなたは〈何の知らせ〉で一時的に開き直された。用が済んでいれば何もしなくてよい」**と明示する。
   **結論を書き換えたいときだけ枝が `thread.merge` を呼ぶ**——その場合は枝の結論が勝ち、自動の畳み直しは二重に走らないこと。
3. **一覧（`thread.list`・画面の枝タブ）で、「畳んである（知らせで一時的に起きた）」と読めること。**
   **残作業を抱えて畳んだ枝の「未処理 N件」表示（imp-0036）を壊さないこと。**

## 気をつけること

- **知らせを捨てる方向へ倒さないこと**（過去に消えた事故があります・inc-0069）。
- 開き直したターンの中で枝が `thread.consult` した／職人を起こした場合でも、**畳み直しでその所在が消えないこと**。
- **`/var/lib/banto` 以下の実データに触らないこと。** 試験は必ず一時ディレクトリで。
