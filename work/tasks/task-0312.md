## 背景

PO から「banto がトークンを食いすぎる」という指摘。外から SDK トランスクリプト
（`~/.claude/projects`、34時間分）を集計して原因を数字で確定した。

34時間で **$409**（≒ $289/日、$8,700/月）。内訳:

| 項目 | 金額 | 割合 |
|---|---|---|
| cache read（文脈の読み直し） | $252 | **62%** |
| cache write | $97 | 24% |
| output（生成） | $60 | 15% |

**出力は 15% しかない。**「番頭が喋りすぎ」ではなく、1リクエストあたり中央値
12万・p90 40万トークンの文脈を毎ターン読み直しているのが本体。

原因は `DEFAULT_CHAPTER_THRESHOLD_RATIO = 0.6` が**割合**である一方、
`opus[1m]` を採ったことで `BantoHarness.contextWindow()` が 1,000,000 を返すこと。
0.6 × 1,000,000 = **60万トークンまで畳まれない**。実測ログ:

```
章判定: tokens=478818 window=1000000 threshold=0.6 willClose=false
章判定: tokens=447637 window=1000000 threshold=0.6 willClose=false
```

なお Opus 5 は 1M が既定かつ最大で**長文脈の割増単価は無い**ので、`[1m]` 自体が
単価を上げてはいない。効いているのは「畳まれずに伸びる」ことだけ。

1ターンあたりの cache read 単価（$0.50/MTok）:
- 文脈 40万 → $0.20/ターン
- 文脈 12万 → $0.06/ターン

副次的に、アイドル5分超で cache TTL が切れたときの全プレフィックス書き直し
（50件・$60/34時間、うち33件がアイドル起因）も、書き直す量が減るぶん小さくなる。

## 直し方

**割合を下げるのではなく、判定に使う窓に上限を掛けた。** 割合は窓ごとに意味が
変わってしまう——0.6 は 20万窓なら 12万で妥当だが、1M窓では 60万になる。上限を
置けば、どのモデルへ差し替えても畳む位置が絶対値で決まる。

`DEFAULT_CHAPTER_WINDOW_CAP = 200_000`。20万 × 0.6 ＝ **12万で畳む**——0.6 が
置かれた当時の窓（20万級）での意味をそのまま保つ値であり、新しく選び直した数ではない。

上限は `ChapterKeeper.contextWindow()` の中で掛けている。この値を引くのは
`shouldClose()` だけなので、判定・記録（`ChapterEvaluation.window`）・ログの
どれもが同じ「実際に予算として使った窓」を指し、食い違わない（D3）。

`BANTO_CHAPTER_WINDOW_CAP` で差し替え可能（既存の `BANTO_CHAPTER_THRESHOLD` と同じ流儀）。
