## 背景（PO裁定 2026-08-07）

inc-0030 の続き。実機 `loamium/task-0002` が

```
task_failed — merge_gate_failed: verify_failed:a3(exit=124)
```

で落ちた。`exit=124` は**時間切れ**。追ったら **`verifyTimeoutMs` は daemon から一度も
渡されておらず、常に既定の 60 秒**だった。検証コマンドはテスト一式そのものなので、
1分で足りるわけがない。

**同じ問いは既に裁定済みだった。** 検証環境側は 2026-08-01 に「既定30秒では `npm test` が
途中で切れていた」として既定10分・上限60分に直している（spec-environment §5.1）。
**ゲート側だけ取り残されていた**——同じ穴を2度掘っている。

PO の裁定：

> failed になったタスクは、Kobo が自主的にリトライして NG だったら Banto に挙げる。
> Banto が判断できていれば OK。ユーザ判断が必要なら取次で良いのでは。
> task-0002 の失敗は検証の期限切れ。banto が受け取って試験の期限を延ばして実行とかはどう？
> もし検証が長すぎるのが問題なら banto が気づくし

## やったこと

### 1. 制限時間を層B設定にした（a1・a5）

`meta/config.yaml` の `limits.verify_timeout_minutes`。**既定10分・上限60分**——
数字は spec-environment §5.1 と揃える（同じ問いに2つの答えを作らない）。
上限超えは黙って丸めず断る（丸めると「30分にした」と思い込んだまま切られる）。

### 2. 時間切れは上限まで延ばして1回やり直す（a2・a3）

**Kobo が自分でやり直す**——PO の言う「Kobo が自主的にリトライ」。task-0070 の監査の事故と
同じ形で、**事故はやり直し、判断はやり直さない**：

| 落ち方 | 扱い |
|---|---|
| `exit 124`（時間切れ） | **事故**。上限まで延ばして1回やり直す |
| `exit ≠ 0, ≠ 124`（テストが落ちた） | **判断**。やり直さない——二度走らせても同じことを二度言われるだけ |

**倍ではなく上限まで一気に延ばす。** やり直しは1回きりなので、倍にしてまた足りなければ
時間を使ったうえで何も分からない。上限まで出したうえで駄目なら「**この検証は許された
範囲では終わらない**」という確かな答えになる——それが番頭に渡したい signal。

理由は `verify_timeout:a1(20分待っても終わらず・延長済み）` の形にした。
**`verify_failed` と混ぜない**——`exit=124` のままだと「テストが落ちた」と読める。

### 3. 知らせが「次にやること」を止まり方ごとに変える（a4）

「直して積み直すか、畳むか」だけでは足りない。時間切れのときにそう言うと、番頭は
**落ちてもいないテストを直そうとする**。時間切れ／監査の事故／スコープ違反で文面を分けた。

時間切れの札には手を3つ書いた：制限時間を延ばす（上限60分。**マージキューは直列なので
長い1本は後ろを全部止める**）／`verify` を分けて1本を短くする／検証そのものが遅いなら
それをタスクとして積む。**どれも利用体験を変えないので番頭が決めてよい**（D9）。

## PO の問い「failed を誰が拾うか」への答え

裁定どおりの鎖が、これで**実際に繋がった**：

1. **Kobo が自主的にリトライ**：監査の事故（task-0070）・検証の時間切れ（本タスク）
2. **NG なら Banto に挙げる**：宛先が無くても捨てない（task-0070）
3. **Banto が判断**：止まり方ごとの手が札に書いてある（本タスク）
4. **ユーザ判断が要るなら取次**：`inbox.post`（既存・決定58）
