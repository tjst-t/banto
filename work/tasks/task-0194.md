## なぜこれを作るか

ブラウザ試験（Playwright・152件）は、**マージ前ゲートの器では1件も走らない**。
`docker/Dockerfile.test` は `node:24-alpine` で、**ブラウザが入っていない**（導入初日の 2026-08-07 から
全4リビジョンとも入っていない）。alpine（musl）なので `playwright install` しても公式 chromium は動かない。

その結果どうなっているか——2026-08-16 に SHA `fc673a71` を固定して5回測った実測値：

- 152件中 **恒常赤16件＋間欠1件**。**それを誰も見ていない**（工場に届かないので）
- 内訳は `inc-0071`（strict mode 9件）・`inc-0074`（モデル選択 6件）・`inc-0078`（打鍵しきい値 2件）

**ブラウザはホストには入っている**（Chrome for Testing 151.0.7922.34 / Playwright 1.62.1）。
つまり「試験が書けない」のではなく**置き場所を間違えている**。

## 何を作るか

**既存の `test` プロファイルには触らない。** あれは今日ようやく「素のワークツリーで2400件 fail 0」に
持っていったばかりで、いま触ると地盤が揺れる。**新しいプロファイル `browser` を1本足す。**

1. `docker/browser.yaml`（新規）——**公式 playwright イメージ**を使う。
   `mcr.microsoft.com/playwright:v<版>-noble` のように**タグを固定**し、`package.json` の
   `@playwright/test` の版と合わせること（版がずれるとブラウザとドライバが噛み合わない）。
   **Debian 系なので glibc で、chromium がそのまま動く。**
2. `meta/environments.yaml` に `browser` プロファイルを足す。形は既存の `test` に倣う
   （`driver: docker` / `config.compose` / `setup` / `cache` / `ttl`）。
   - `setup` では依存を入れるだけでなく、**画面のビルド（dist）まで済ませること**。
     古い dist のまま測ると、直っているものが赤く出る（過去に一往復している）
   - `cache.key` には `package-lock.json` と `docker/browser.yaml` を入れる
   - **人が触る面は持たない**ので `config.port` は書かない（決定59）
   - `ttl` は `test` と同程度（45m）。上限を超える値は拒否される
3. `tests/acceptance/browser-profile.spec.ts`（新規）——上の受け入れ条件を機械で見る試験。

## 気をつけること（SKILL environment-profiles より）

- **`command` に走り終わるコマンドを書かない。** `npx playwright test` を `command` に書くと、
  compose も provision も成功するのに**環境が数十秒で消える**。検証コマンドは `env.run` が
  別の使い捨てコンテナで走らせるので、compose の `command` は**器を開けておくためだけ**にある
  （`sleep infinity` 相当）。マージ前ゲートでは「a1 だけ通って a2 以降が全滅」という
  紛らわしい落ち方になる
- `playwright.config.ts` が `webServer` を使っているなら、**器の中でそれが起動できること**を確かめること
- 秘密は書かない。`ttl` の上限は能力側が持つ

## この契約の限界（**正直に書いておく**）

**このタスク自身の検証には、作った `browser` プロファイルを使えない。**
マージ前ゲートはプロファイル定義を**main のリポジトリから読む**（`merge-queue.ts:446` が
`repoPathForProfile: repoPath` を渡している）ので、**まだ main に無いプロファイルは、
そのタスクのゲートでは使えない**——鶏と卵になる。

だからこのタスクの受け入れ条件は、**設定が妥当か**までしか機械で見ていない。
**「ブラウザ試験が実際に走る（0件ではない）」は、番頭が `env.verify` を職人のワークツリーに対して
直接回して確かめてから通す**（これは職人の自己申告ではなく、機構が返す事実・I1）。

**「職人がホストで回した出力を報告に貼る」は採らない。**
それは自己申告で緑にすることであり、いまこの枝が問題にしているものの再生産だからである。

**実際にブラウザ試験を機械で回すのは次のタスク**（`browser` を `environment` に名指しして、
`npx playwright test` を verify に書く）。そこが本番の検査になる。
