## 背景

PO から「banto が異様に Token を食う」という指摘があり、実ログを集計したところ **`env.verify` の戻り値が主因の一つ**であることが数字で確定した。

実測（本番 `threads/*.jsonl` 全走査・env.verify 520件）：

- 戻り値の本文合計 **359,958字**
- うち**通った231件が211,476字、そのログ本文が197,221字（全体の55%）**
- 2026-08-20 08:49 の1件は本文 **1,516字/44行**。意味のある行は「通りました」「終了コード: 0」「環境は畳みました。」の**45字だけ**で、残り約1,470字（97%）は**通ったテストの ✔ 一覧と docker のコンテナ作成ログ**
- 大きな戻り値を栞へ退避する仕組み（`packages/banto-host/src/artifacts.ts` の `withArtifactOffload`、配線は `host-session.ts:223`）は env.verify にも掛かっているが、**1,516字はしきい値に届かないのですり抜ける**。実際に退避されたのは520件中11件（2%）だけ
- 集計対象520件のうち91件は古い記録形式で本文が取れず落ちているので、**上の数字は下振れした値**

そして決定的なのは、**ログの場所（`logPath`）はすでに戻り値に入っているのに本文へ出していない**こと：

- 型は `packages/banto-environment-pool/src/pool.ts:203, 220`
- 詰めているのは `pool.ts:1538`（`logPath: runResult?.logPath ?? ""`）
- しかし `packages/banto-environment-pool/src/tools.ts` の本文組み立てには一度も出てこない
- 一方 `env.run` は `pool.ts:1137` で `ログ: ${outcome.logPath}\n${outcome.logTail}` と**すでにパスを出している**。env.verify だけが出していない

つまり現状は「**パスは持っているのに出さず、代わりに末尾を貼っている**」。PO の言う「Exit Code とログの場所を渡して、必要ならログを見る」がそのまま正しい。

## やること

`packages/banto-environment-pool/src/tools.ts` の `env.verify` の `execute` 内、戻り値の本文組み立て（現状はこうなっている）：

```ts
const passed = result.exit === 0 && result.failure === undefined;
...
if (result.failure) lines.push(`検証まで到達しませんでした: ${result.failure}`);
else {
  lines.push(`コマンドの終了コード: ${result.exit}`);
  if (result.logTail) {
    lines.push(result.truncated ? "ログ（末尾のみ）:" : "ログ:", result.logTail);
  }
}
```

`passed` を計算しているのに**ログを出すかどうかの判定に使っていない**。これを次のように変える。

1. **ログの場所は常に本文へ出す。** `result.logPath` が空でなければ `ログの場所: <logPath>` を1行出す。`failure`（検証まで到達しなかった）の枝でも、ログがあるなら出すこと。
2. **ログ末尾は通らなかったときだけ積む。** `if (result.logTail)` → **`if (!passed && result.logTail)`**。通ったときは末尾を1行も積まない。
3. **通ったときに「ログは載せていない」ことが分かる一言を添える**。番頭がログを見たくなったときに、パスを file.read で読めばよいと分かる形にする（例：`ログの場所: <path>（通ったので末尾は載せていません。要るときだけ読んでください）`）。ログが読めるのは保持期間内だけ（`docker-driver.ts:204` で7日）である点は本文に書かなくてよい。
4. **`logTailLines` を `env.verify` の parameters に通す。** `pool.verify` はすでに受け口を持っている（`pool.ts:1492` 付近）が、道具の parameters に無いため番頭から行数を指定できない。`env.run` と揃えて任意パラメータとして受け、`pool.verify` へ素通しすること。既定は現状のまま（`pool.ts:52` の40行）。
5. **道具の説明文を実態に合わせる。** `tools.ts` の `env.verify` の description にある「→ 通ったか＋終了コード＋ログ末尾」は嘘になるので、「通ったか＋終了コード＋ログの場所（落ちたときだけ末尾）」に直す。

## やらないこと（重要）

- **栞（artifact）のしきい値をいじらないこと。** 退避は「大きすぎるものを文脈から外す」仕組みであって「そもそも要らないものを消す」仕組みではない。しきい値を下げると `env.list` / `git.status` / `worker.list` まで栞になり、`artifact.read` の往復が増えて逆効果になる。直すのは env.verify 側の出し分けだけ。
- `pool.verify` の中身（provision→run→teardown の流れ）は変えないこと。`logTail` を作るのをやめるのではなく、**本文に積むかどうかだけ**を変える。`details`（`result`）にはこれまでどおり `logTail` も `logPath` も入れたままにすること——栞から読めるようにしておく。
- `env.run` / `env.provision` など他の道具の戻り値は今回触らないこと。

## 期待される効果

通ったときの本文が1,500字前後から100字前後へ落ちる。落ちたときだけ末尾が載り、そのときは2,000字を超えて自動的に栞へ退避されるので、退避の仕組みが狙いどおり効く形になる。実測ベースの見込み削減は**約18万字**（下振れ値）。
