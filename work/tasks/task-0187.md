## なぜ直すか（今日の実測）

`package.json:20` の `test` はこうなっている：

```
"test": "BANTO_WORKER_POOL_URL=http://127.0.0.1:1/api/worker-pool BANTO_ENV_POOL_URL=http://127.0.0.1:1/api/environment-pool node --import tsx --test $(ls tests/acceptance/*.spec.ts | grep -vE 'env-docker-|env-driver-contract|env-driver-timeout-budget|env-orphan-ownership|env-profile-setup')"
```

`$(ls ...)` で**ファイル一覧をすでに渡し切っている**ので、`npm test -- tests/acceptance/foo.spec.ts` と書いても
`--` の後ろは**引数として足されるだけ**。絞り込みにならず、**毎回 2420件の全量（約400秒）が走る**。

その結果：

- 受け入れ条件を3本書けば、**同じ全量を3回**。時間も負荷も3倍
- 負荷が上がるほど間欠失敗（`inc-0070` の `Error: write EPIPE`）を踏む確率が上がる。
  **契約の書き方で、自分から間欠を誘発していた**
- 実例：`work/tasks/task-0152.md` / `task-0153.md` / `task-0098.md` の verify が `npm test -- <file>` の形

## 何をするか

### 1. `package.json` に `test:one` を足す

`test` と**同じ環境変数**を立てたうえで、渡されたファイルだけを `node --import tsx --test` に渡す口。

```
"test:one": "BANTO_WORKER_POOL_URL=http://127.0.0.1:1/api/worker-pool BANTO_ENV_POOL_URL=http://127.0.0.1:1/api/environment-pool node --import tsx --test"
```

使い方は `npm run test:one -- tests/acceptance/foo.spec.ts`。

**環境変数を落とさないこと。** ここが肝で、`node --import tsx --test <file>` を素で呼ぶと
この2つが立たず、試験が本物の Worker Pool / Environment Pool を掴みに行く。
（`work/tasks/task-0155.md` / `task-0169.md` の verify が実際にその素の形になっている。
それらは直さなくてよいが、同じ轍を踏まないために口を用意する。）

**`test` スクリプトの定義そのものは変えない。** 全量を回す口は今のまま残す。

### 2. SKILL `kobo-enqueue` に1節足す

`packages/banto-daemon/skills/kobo-enqueue/SKILL.md` に「1本だけ回す verify の書き方」を書く。含めること：

- **`npm test -- <file>` は絞り込みにならない**（理由：`test` が `$(ls …)` で一覧を渡し切っているため）
- 1本だけなら **`npm run test:one -- tests/acceptance/foo.spec.ts`**
- **条件ごとに全量を回さない**。全量と型検査は最後の1条にまとめる
- 理由も1行添える：全量を条件の数だけ回すと、時間と負荷がその倍になり、間欠失敗を自分から誘発する

## やらないこと

- 既に積まれている他タスクの verify は**このタスクでは直さない**（各タスクの持ち主が `kobo.amend` で直す）
- `test` の除外リスト（`env-docker-` ほか）の中身には触らない
