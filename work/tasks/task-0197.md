## 何が起きたか（実データ・番頭が自分で踏んだ）

`task-0159` が **2回続けて `fast_forward_merge_failed`** で落ちた。

```
2026-08-16T06:45:58 merge_gate_evaluated — 通過［base 881371a8］
2026-08-16T06:45:58 task_failed — fast_forward_merge_failed: git merge --ff-only task/task-0159
                    fatal: Not possible to fast-forward, aborting.
2026-08-16T07:00:38 merge_gate_evaluated — 通過［base 00031cf0］
2026-08-16T07:00:38 task_failed — fast_forward_merge_failed:（同上）
```

**マージ前ゲートは2回とも通過している**（2回目は間欠の EPIPE も出ず、全条が緑）。
落ちたのは**最後の `git merge --ff-only` だけ**で、中身も契約も無罪。

## なぜ起きるか（コードで確認済み）

`packages/banto-daemon/src/merge-queue.ts` は、1本のタスクをこの順で処理する：

1. `rebaseTaskBranch(...)`（**:388**）——枝をそのときの main の上に乗せ直す
2. `runMergeGate(...)`（**:436**）——検証環境を立てて受け入れ条件を回す。**全量 `npm test` を含むと6〜8分**
3. `git merge --ff-only <taskBranch>`（**:748**）

**1 と 3 のあいだが6〜8分空く。** その間に main が1コミットでも進めば、枝はもう main の子孫ではなく、
**ff は必ず失敗する**。

実際の原因：

- 1回目 — `881371a8`（マージキューの外で行われた手動マージ）
- 2回目 — **`00031cf0`。番頭が記録の id 衝突を直して main へ直接コミットしたもの**

## 一般化（**次に同じ形を探すときの目印**）

**この機構は「重い仕事を罰する」形になっている。**

- **ゲートが長いほど、その間に main が動く確率が上がる**——つまり
  **全量の試験を回すタスクほど着地できない。いちばん慎重に検査しているものが、いちばん落ちる。**
- **記録を1つコミットするだけで踏む。** 番頭も職人も `work/inbox/**` へ直接コミットするので、
  **誰でも、いつでも、無自覚に他人のマージを落とせる。**

同じ形は今日すでにもう1つ出ている（重い検証を職人の袋の中で回すと死ぬ件）。
**「難しい仕事ほど落ちる」構造は、他にもあるはず。**

## 何をするか

**(1) ff の直前に rebase を取り直す。** `:748` の直前で mainline を取り直し、
枝がその子孫でなければ**もう一度 rebase してから** ff する。

**(2) それでも ff に失敗したら、同じ tick の中で1回だけ再試行する。**
（1 と 2 のあいだにもう一度 main が動く、という細い窓が残るため。）
**回数は1回。** 何度も回すと `inc-0063` の周回になる。

## やらないこと

- **「キューが回っている間は main を直接触らない」という規律で縛るのは採らない。**
  人の注意に頼る規律は、今日9回破られている（記録 id の衝突）。**機構で解く。**
- `--ff-only` をやめてマージコミットを作る、という直しは**採らない**（履歴が一直線でなくなる）。
- 失敗を握り潰して「成功した」ことにしない。**本物の衝突は落とす**（I2）。

## 試験の書き方（**ここが本体**）

`tests/acceptance/merge-queue-mainline-moved.spec.ts` を新しく作る。
**再現しない直しは、直したことにならない。**

- 一時的な git リポジトリを作り、main と task ブランチを用意する
- `processMergeQueue` に渡す**検証ランナーを差し替え**、`run` が呼ばれた**その中で main へ
  コミットを1本足す**（＝ゲートの最中に main が進む状況を、決定的に作る）
- **直す前の実装で、この試験が `fast_forward_merge_failed` で落ちることを先に確かめること。**
  確かめた出力を報告に貼ること
- 直したあとは `task_merged` が出て、**main の HEAD に「枝の変更」と「割り込んだコミット」の両方が
  入っている**ことを確かめる（片方だけ入っていたら、それは取りこぼし）
- 再試行が1回だけであること、本物の衝突は落ちることも、同じ試験で固定する
