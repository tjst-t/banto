## 背景

banto の記録（`work/inbox/improvement/imp-NNNN-*.md`、`work/inbox/incident/inc-NNNN-*.md`）の id は、**ファイル名の慣習で採番している**。誰も検査していないため、複数の作業が同時に走ると同じ番号が別々の内容で作られる。

2026-08-15 の実例（すべて現物で確認済み）:
- `inc-0070` が **2つ**ある（`acceptance-suite-flaky-under-added-load` と `model-select-e2e-broken`）
- `imp-0058` が別内容で衝突し、片方を `imp-0060` へ採番し直した
- `inc-0072` も衝突し、`inc-0073` へ譲った
- `adr-0024` が欠番

衝突するたびに人手で採番し直しており、そのたびに他の記録からの参照（`refs`）が食い違う危険がある。

## やること

1. **いま在る重複を解消する。** `work/inbox` 配下を走査して、同じ id を持つ記録を洗い出す。**内容が別物なら、後から書かれた方を空き番号へ採番し直す**（ファイル名と front matter の `id` の両方）。どちらが先かはファイルの中身・git の履歴で判断すること。**内容が同じ（単なる重複）なら統合して1本にする。**
2. **他の記録・ドキュメントからの参照を追随させる。** 採番し直した id を `refs` や本文で参照している箇所を全部探して直す（`work/`・`docs/` 配下を grep する）。**参照の付け替え漏れが無いことを、自分で確かめること。**
3. **欠番を埋めるのではなく、記録する。** `adr-0024` のような欠番は、勝手に別の文書で埋めない。**欠番があること自体は異常ではない**（起票して消した等）ので、検査は「重複を落とす」ことを主とし、欠番は**警告として一覧できれば十分**。
4. **同じことが二度と起きないように、機械で落とす受け入れ試験を1本置く。** `work/inbox` 配下（および `docs/adr`）を走査し、**同じ id が2つ以上あれば失敗する**試験。ファイル名の id と front matter の `id` が食い違っていても失敗させること。欠番は失敗させず、一覧に出すだけでよい。

## やらないこと

- 記録の中身の書き換え（誤字直し・status の整理など）はしない。**この仕事は id の一意性だけを扱う。**
- 採番の仕組みそのものの作り直し（起票専用の口を作る等）はしない。それは imp-0054 として別に検討中で、**この仕事の結果はその検討の土台になる**。

## 完了の形

- `work/inbox` と `docs/adr` に重複 id が1つも無い
- 重複を検出する試験があり、いまの状態で通る（わざと重複を作れば落ちることも確かめてあること）
- 採番し直した id への参照が全部追随している
