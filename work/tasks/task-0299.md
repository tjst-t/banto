## 背景（職人が実測した数字。番頭がコードを現物で確認済み）

`packages/banto-host/src/deploy-verify.ts` の `runDeployVerify` は

```ts
const { stdout } = await execFileAsync(exe, argv, { cwd, timeout: 20 * 60_000 });
```

と呼んでいる。**`maxBuffer` を指定していない。** Node の `execFile` の既定 `maxBuffer` は 1MiB で、超えると子プロセスは殺され Promise は reject する。`runDeployVerify` の catch は

```ts
} catch (err) {
  const e = err as { stdout?: string; stderr?: string; code?: number };
  const code = typeof e.code === "number" ? e.code : 1;
  return { passed: false, report: extractFailures(output, code) };
}
```

と**あらゆる reject を「検証が落ちた」として扱う**。maxBuffer 超過かどうかを見る分岐は無い。

### 実測（2026-08-20）

- `npm test` の全出力は **1,826,561 バイト / 13,222 行** — 1MiB(1,048,576) の **1.74 倍**。恒常的に超える。
- その `npm test` 自体は **exit=0 / tests 2858 / pass 2858 / fail 0**、`npm run typecheck` も exit=0。つまり**1件も落ちていない**。
- 先頭 1MiB を切り出すと `not ok` / `AssertionError` / `# fail` は **0 件**、`Error:` を含む行が **4,470 件**（うち ECONNREFUSED が 4,435 件）。切れ目はテスト実行のごく序盤に落ちており、サマリ行も本物の失敗行も**先頭 1MiB の外にしか無い**。
- `execFile` を maxBuffer 未指定で 1MiB 超の出力に対して実際に踏むと:
  `err.code = "ERR_CHILD_PROCESS_STDIO_MAXBUFFER"` / `err.message = "stdout maxBuffer length exceeded"` / `err.stdout.length = 1048576`（ちょうど 1MiB で打ち切り）/ `err.stderr = undefined` / `err.killed = undefined`。
  `err.code` が**文字列**なので `typeof e.code === "number"` を満たさず、無条件に `code = 1` に落ちる。
- timeout で殺した場合は `err.code = null` / `err.killed = true` / `err.signal = "SIGTERM"`。**`killed` と `signal` を見れば maxBuffer 殺しと timeout 殺しは区別できる**が、いまのコードはどちらも見ていない。

### 何が起きているか

**テストが1件も落ちていなくても、出力が 1MiB を超えた時点で `system.deploy` は機械的に「拒否」を返す。** 実際 journal には `deploy-rejected` が記録される一方、`deploy-pass` は一件も無い。つまり**このゲートは一度も通ったことがない**疑いが濃い。計画的デプロイの正式な口が、機能していない。

さらに `extractFailures` の目印が広すぎて、本物の失敗を隠す:

```ts
const FAILURE_MARKERS =
  /(fail [0-9]+|# fail|not ok|✗|FAILED|AssertionError|Error:|npm ERR!|failing tests?)/i;
const hit = lines.filter((line) => FAILURE_MARKERS.test(line.trim())).slice(0, 30);
```

- 素の `Error:` が、試験がわざと出す `Error: connect ECONNREFUSED 127.0.0.1:1`（`package.json` の `test` スクリプトが `BANTO_ENV_POOL_URL` を到達不能アドレスへ意図的に向けている）に毎回ヒットする。
- `i` フラグのため、**合格した試験の説明文**（例 `✔ [AC-...] GET non-existent task returns 404 with error: not_found`）にもヒットする。
- `.slice(0, 30)` は**ノイズを除く前**に効くので、先頭30件がノイズで埋まると本物の `not ok` が1行も出ない。
- 生の stdout/stderr はどこにも永続化されないので、**後から「本当は何が落ちたのか」を辿れない**。今回まさにそれで当時のログが失われた。

## やること

`packages/banto-host/src/deploy-verify.ts` を直す。

1. **`maxBuffer` を十分大きく取る**（例 `64 * 1024 * 1024`）。いまの出力 1.74MiB に対して余裕を持たせること。
2. **打ち切りと本物の失敗を区別する。** catch で `err.code === "ERR_CHILD_PROCESS_STDIO_MAXBUFFER"`（および `err.killed === true` / `err.signal` による timeout）を判定し、**それぞれ別の理由として報告する**。「テストが落ちた」と「出力が上限を超えて打ち切られた」「時間切れで殺された」が同じ文面になってはいけない。maxBuffer を広げてもなお超えることはあり得るので、この分岐は maxBuffer を上げたうえで**残すこと**。
3. **失敗抽出の目印から素の `Error:` を外す。** `not ok` / `# fail` / `AssertionError` / `FAILED` / `npm ERR!` / `failing tests` で足りる。`✗` は残してよい。ノイズ除外を先に行い、**`.slice()` はノイズを除いた後に効かせる**こと。
4. **失敗時の生ログを残す。** stdout/stderr の全文をファイルへ書き出し（置き場は `os.tmpdir()` 配下でも `/var/lib/banto` 配下でもよいが、**どこに書いたかを report に含めること**）、report 本文には要約＋パスを出す。次に拒否が起きたとき、現物を掴めるようにする。

## やらないこと

- **`system.deploy` の検証を回す場所（`process.cwd()`）は変えない。** 使い捨ての worktree で回す案は筋としてあり得るが、この一件の範囲を超える。別途 PO の判断を仰ぐ。
- ゲートを緩めない。maxBuffer 超過を「通った」扱いにしないこと——**分からないものは通さない**。
- `package.json` の `test` スクリプト（意図的な到達不能アドレス）は触らない。

## テスト

`tests/acceptance/` に追記または新規（既存の `kobo-deploy-gate.spec.ts` / `deploy-unit-restart-policy.spec.ts` の流儀に合わせること）:

- `extractFailures` 相当に、**合格行だけのログ**（`✔ ... error: not_found` や `Error: connect ECONNREFUSED` を大量に含むもの）を渡したとき、「落ちた箇所」として何も拾わないこと。
- 本物の `not ok` / `AssertionError` 行が**ログの後方 30 行目以降**にあるとき、それが報告に現れること（ノイズで押し出されないこと）。
- `runDeployVerify` が 1MiB を超える出力を出すコマンドに対して、**成功なら passed:true を返すこと**（maxBuffer を上げた効果の担保）。
- maxBuffer 超過が起きた場合の report が、テスト失敗の report と**区別できる文面**になっていること。
