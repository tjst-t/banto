## やること

### 1. `ThreadStore.replace()` に「縮む書き戻し」を拒む番人を入れる

`Thread.transcript` は `record()` の性質上、**要素数が減ることはない**（末尾の連結・実行中の行の更新はあっても削除は無い）。この不変条件を書き手側が検査していないのが穴である。

- `ThreadStore` が threadId ごとに「**このプロセスが最後に書いた／読み込んだ行数**」をメモリに持つ
- `replace(threadId, entries)` で `entries.length` がその値より小さければ、**書き込みを拒む**
- **黙って拒まないこと（I2）**。拒んだ内容を `<threadId>.jsonl.rejected-<ISO8601>` のような別名で退避し、`console.error` で「何本が何本に縮もうとしたか」を出す。退避しておけば原因調査にも復旧にも使える
- **基準は「実ファイルの行数」ではなく「このプロセスがメモリに載せた行数」にすること。** 起動時に壊れた行を飛ばして読んだ場合（`transcript()` は壊れた行をスキップする）、実ファイルより1行少ないのは正常なので、実ファイル基準だと誤検知する

### 2. 章畳みの後も記録が残ることを、試験で固定する

新しい受け入れ試験（例 `tests/acceptance/chapter-close-persists.spec.ts`）を置く。**LLM 無しで機械的に再現できる形にすること。**

既存の2つの型を合成するのが自然：
- `tests/acceptance/thread-persistence.spec.ts` … `ThreadRegistry` + `ThreadStore` + `FakeSession` で再起動を跨いだ永続化を検証
- `tests/acceptance/chapters.spec.ts` … `ChapterKeeper` に偽の `summarize` を渡して章畳みの機構だけを検証

骨格：
1. `thread.record({role:"po",...})` / `{role:"banto",...}` を数件積む
2. `ChapterKeeper` を組み立て、`onChapterClosed` に `server.markChapter` 相当（＝`thread.record({role:"chapter",...})` を呼ぶ関数）を渡す
3. `await keeper.closeChapter()` を成功させる（偽の `summarize` は即解決）
4. **核心のアサーション**：`flush` した直後、**別インスタンスの** `new ThreadStore(dir).transcript(id)` でディスクから読み直し、`role:"chapter"` のエントリが読めること
5. さらに章畳みの**後**に `record()` を1件積み、**再度ディスクから読み直して**それも読めること（＝今回の核心の疑問をそのまま試験にする）

### 3. 縮む書き戻しの回帰試験

意図的に短い `entries` で `replace()` を呼び、ディスクの内容が保たれること・退避ファイルができること・ログが出ることを確かめる。
