## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

### 今日の実例（これが無いと、なぜ区別が要るのか伝わらない）

2026-08-16、`banto-worker-pool.service` が OOM で繰り返し揺れた（00:30:50 / 01:26:51 / 03:06:40 / 03:51:07 / 03:54:58 / 04:06:33 / 04:35:35 の少なくとも7回）。**その最中に、Kobo の操作がモジュールへ届かず、タスクが `failed` になっている。**

| タスクが failed になった時刻 | 直前の worker-pool の OOM | 間隔 |
|---|---|---|
| 03:55:22（task-0160・報告なし） | 03:54:58 | **+24秒** |
| 04:07:20（task-0160・報告なし） | 04:06:33 | **+47秒** |

実際に `kobo.reopen` が `Failed to reach module "worker-pool" ... read ECONNRESET` で落ち、**数十秒後には同じ操作が通っている**。**中身は何も悪くない。声が届かなかっただけである。**

### なぜ困るか

**帳簿を読む側（番頭・PO・次に見る人）から、2つが区別できない。**

- **中身が悪くて落ちた** → 直す（`kobo.reopen` の `rework`、契約の訂正、原因の調査）
- **声が届かなかった** → **待てばよい**（相手が起き直れば同じ操作が通る）

いまは**どちらも `failed`** なので、**毎回「何が悪かったのか」を人が調べ直す**ことになる。今日は実際に、番頭が journal と帳簿を突き合わせるまで分からなかった。

## やること

**「相手に届かなかった」で終わった試行を、中身の失敗と区別できる形で残す。**

1. **区別の付け方は実装者が決めてよい**が、**帳簿（イベント）を読むだけで区別できること**。例：
   - 遷移理由（reason）に機械が読める印を付ける（`unreachable:<module>` など）
   - あるいは `failed` とは別の理由コードで残す
   **状態そのものを増やすかどうかは慎重に**——状態機械を膨らませると、既存の遷移の検査が全部揺れる。**まず「理由の側で区別する」形を検討し、状態を増やすなら理由を実装のコメントに残すこと。**
2. **判定は「モジュールへ届かなかった」に限る。** `packages/banto-core/src/module-invocation.ts` が投げる
   `Failed to reach module "<name>" at <url>: ...` がその印である。**ツール側が返したエラー**（HTTP のエラー応答）は**中身の失敗**なので、**区別の対象に含めない**。
3. **番頭と人に見える形にする。** `kobo.task` の経緯や、判断待ちの札・知らせの文面で、**「届かなかった」と分かること**。「なぜ落ちたか」を読む人が、**調べ直さずに『待てばよい』と判断できる**のが目的。
4. **振る舞いは変えなくてよい。** 自動で再試行する・自動で復帰させるのは **task-0190（接続段の短い再試行）**の担当。**このタスクは「見え方」だけを直す**——両方を1つにしないこと。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- 再試行の実装（**task-0190**）／`packages/banto-core` の変更
- OOM の側の手当て（cgroup・袋の大きさ・同時本数）
- 状態機械そのものの作り替え（状態を増やすなら**最小限**にとどめ、既存の遷移の意味を変えない）
- `packages/banto-host` / `packages/banto-worker-pool` の変更

## 気をつけること

- **「届かなかった」を握り潰して成功に見せないこと**（I2）。区別するのであって、無かったことにするのではない。
- **既存の `failed` の扱い（一覧・再開・帳簿の集計）を壊さないこと。** 区別を足しても、**いままで `failed` として数えていたものが黙って数から消えない**ようにする。
