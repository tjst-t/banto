## 背景

`system.deploy`（計画的デプロイ）は main に対して `npm test` を回し、通ったときだけ常駐サービスを起こし直す。2026-08-20 のデプロイでこのゲートが fail 2 で拒否した。そのうち1件は **試験が実行環境の環境変数を継承していること**による決定的失敗である。

- 落ちる試験: `tests/acceptance/browser-chromium-launcher.spec.ts:664`
  「BANTO_BROWSER_ALLOW_NO_SANDBOX が無ければ --no-sandbox は入らず、status も enabled」
- 試験は `createChromiumLauncher({ ..., allowNoSandboxEnv: undefined })` を渡して「環境変数が無い状態」を表現している。
- しかし実装は `packages/banto-host/src/browser/chromium-launcher.ts:505-506` で
  `const allowNoSandboxEnv = options.allowNoSandboxEnv ?? process.env["BANTO_BROWSER_ALLOW_NO_SANDBOX"];`
  と書かれているため、**明示的に渡した `undefined` が `??` で潰れ、実プロセスの環境変数に落ちる**。
- デプロイゲートは banto.service の環境を継承して走るため、そこに `BANTO_BROWSER_ALLOW_NO_SANDBOX=1` が入っていると、この試験は必ず落ちる。手元の `env.verify`（清潔な検証コンテナ）では通るので、「ゲートだけ落ちる」という食い違いになっていた。

## やること

**「呼び出し側が明示的に指定したこと」と「指定していないこと」を区別できるようにする。** 実装の既定挙動（何も渡さなければ process.env を見る）は変えないこと——本番はその挙動に依存している。

推奨する形はどちらでもよい:

- (1) `options` にキーが在るかで判定する（`"allowNoSandboxEnv" in options ? options.allowNoSandboxEnv : process.env[...]`)。明示 `undefined` は「環境変数なし」を意味するようになる。
- (2) launcher が読む環境そのものを注入口にする（`env?: NodeJS.ProcessEnv`（既定 `process.env`）を受け、試験は `env: {}` を渡す）。

いずれの場合も、**試験側は実プロセスの `process.env` に一切依存しない形にする**。`process.env` を試験内で書き換えて復元する方式は、並行実行で他の spec を巻き添えにするため採らないこと。

同ファイルの他の試験（`BANTO_BROWSER_ALLOW_NO_SANDBOX=1 のとき --no-sandbox が入る` など）も、同じ注入口を通して環境非依存にすること。

## やらないこと

- デプロイゲートの走らせ方（清潔な環境で回すか）は別途 PO 判断待ちなので、ここでは触らない。
- `packages/banto-host/src/deploy-verify.ts` は触らない（task-0311 / task-0313 の領分）。
- 実装の既定挙動（引数なしなら process.env を見る）は変えない。

## 完了条件

環境変数 `BANTO_BROWSER_ALLOW_NO_SANDBOX=1` が **設定されていても・されていなくても**、この spec が同じ結果（全件通過）になること。
