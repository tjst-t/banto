## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

banto ホスト（`banto.service`）が OOM killer に繰り返し殺されている（2026-08-15 だけで4回以上、同日12回再起動）。**書き込みの途中で殺されると会話の記録に半端な行が残る。**

8/16 00:48:50、OOM 直後の読み戻しで
`[banto] thread-61 の記録に読めない行があります（その行は飛ばします）`
が1回出た。その1行は `console.error` に出ただけで**中身はどこにも残らず**、直後の書き戻し（全文置換）で**永久に消えた**。しかも誰も気づかなかった（画面には出ない）。

### 現物のコード（2026-08-16 時点。先行タスク task-0161 で書き込み側が原子的になっているので、行番号はずれている可能性がある。**必ず現物を読むこと**）

`packages/banto-host/src/thread-store.ts` の `transcript()`：

```ts
try {
  entries.push(JSON.parse(trimmed) as TranscriptEntry);
} catch {
  // I2 の例外ではない: 1行壊れても残りは読める。1行のために会話全部を失わない
  console.error(`[banto] ${threadId} の記録に読めない行があります（その行は飛ばします）`);
}
```

例外も行の中身も束縛していない。**読み飛ばす判断そのものは正しい**（1行のために会話全部を失わない）。問題は「捨てている」ことと「気づけない」ことの2つ。

## やること

1. **壊れた行を退避する。** `transcript()` が読めない行に当たったら、その行の**生テキストをバイト単位でそのまま** `<記録ファイルと同じディレクトリ>/<threadId>.corrupt-<ISO8601>.jsonl` へ書き出す（1回の読みで複数行壊れていたら同じファイルへまとめる）。退避は追記でよいが、**退避に失敗しても読み自体は続けること**（退避が新しい落とし穴にならないように）。
2. **上書きの前に、現行ファイルも丸ごと退避する。** 壊れた行が見つかったスレッドについては、`replace()` が全文置換で上書きする前に**そのときのファイル全体**を退避側へ残す（同じ命名規則でよい）。これが無いと「壊れた行以外の、読めたが古い内容」も消える。**壊れが見つかっていないスレッドでは余計な退避をしないこと**（毎回コピーすると 2〜6MB の記録が積み上がる）。
3. **人に届ける。** 退避が起きたことを **取次（inbox）に1件積む**。`console.error` だけでは誰も気づかないことが 8/16 の実例で分かっている。**起動あたり1件だけ**にすること（スレッドごと・行ごとに積むと札で溢れる）。札には「どのスレッドか・何行壊れていたか・退避ファイルのパス」を書く。取次への積み方は `packages/banto-host/src` 内の既存の呼び出し箇所を読んで、その流儀に合わせること。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- 書き込みを原子的にする話（**task-0161 で済んでいる**。壊さないこと）
- `append()` を使う形への設計変更、`SAVE_DELAY_MS` の変更
- `turn-log.ts`（別タスク task-0162）
- 退避したものから自動で復元する仕組み（人が判断する。ここでは作らない）
- `/var/lib/banto` 以下の実データへの書き込み・移動・削除。**いま PO の記録の復旧作業が走っている。実データに触らないこと**（テストは必ず一時ディレクトリを使う）

受け入れテストを `tests/acceptance/thread-store-corrupt-line.spec.ts` に置く。既存の `tests/acceptance/` の流儀（テストランナー・一時ディレクトリ・後片付け）を先に読んで合わせること。
