## 背景

2026-08-20 の `system.deploy` がゲート（`npm test`）で拒否した。落ちた2件のうちの1件が
`tests/acceptance/audit-checklist-assets.spec.ts` 系。「間欠」に見えていたが、
**コードを読んで機構が確定した**ので、起票だけで済ませず直す。

## 原因（確定）

### 1. 試験がリポジトリ追跡下の実ファイルを書き換える

`tests/acceptance/audit-checklist-assets.spec.ts:255-271`、
describe「[AC-S75f66b-3-2] Checklist edit propagates to the audit agent」の `before` が、
**リポジトリの実ファイル** `skills/audit-checklist.md` に `CHECK-MARKER-42` を追記し、
`after` で書き戻している（`checklistPath = path.join(repoRoot, "skills", "audit-checklist.md")`、
`repoRoot` は spec からの相対で解決した本物のリポジトリルート）。

### 2. 読み手はキャッシュせず、毎回ディスクを読む

`packages/banto-core/src/prompt-assets.ts:39-49` の `loadPromptAsset` は
`fs.readFileSync` を**呼ばれるたびに**実行する。キャッシュは無い。

### 3. spec ファイルは並行プロセスで走る

`package.json:20` の `test` スクリプトは `node --import tsx --test <files...>` で、
**`--test-concurrency=1` が付いていない**（付いているのは `test:e2e` の方だけ）。
したがって acceptance の spec ファイルは既定の並行度（CPU数）で**別プロセスとして同時に**走る。

### 4. 落ちるのは、1つの試験の中で2回読むところ

上の1〜3が重なると、**同じ試験の中の読み1と読み2のあいだ**にファイルが書き換わる。
実際に踏むのは以下:

- `tests/acceptance/kobo-evidence-versions.spec.ts:167-169`
  「刻む指紋と、実際に渡している中身が同じもの」
  → `buildAuditInstruction(...)`（内部で読み1）→ `instruction.includes(loadPromptAsset(...))`（読み2）
- `tests/acceptance/kobo-evidence-versions.spec.ts:117-121`
  `verdict["checklistVersion"]`（記録時の指紋）vs `promptAssetDigest("audit-checklist")`（いま読む）
- `tests/acceptance/kobo-role-prompts.spec.ts:88,96`
  `instruction.includes(loadPromptAsset("audit-checklist"))`

読み1が素の中身、読み2が `CHECK-MARKER-42` 入り（またはその逆）になると assert が落ちる。

### 5. おまけの実害

`before` の直後にプロセスが落ちると、`CHECK-MARKER-42` が**追跡下のファイルに残る**。
`process.once("exit"/"SIGTERM"/"SIGINT")` で best-effort の復旧は入っているが、
SIGKILL では残る。作業ツリーが汚れ、マージ前ゲートの差分検査を狂わせる。

## やること

**試験が追跡下のファイルを一切書き換えないようにする。** 並行度を1に落として回避しない
（全量が遅くなるうえ、原因が残る）。

1. `packages/banto-core/src/prompt-assets.ts` に**資産の置き場の注入口**を足す。
   環境変数 `BANTO_SKILLS_DIR` が立っていればそこを、無ければ従来どおり
   `<repoRoot>/skills` を見る。既定の挙動は変えないこと。
   - 注入口は `loadPromptAsset` と `promptAssetDigest` の両方に効くこと
     （`promptAssetDigest` は `loadPromptAsset` を呼ぶので自然にそうなるはず）
   - `buildAuditInstruction`（`packages/banto-daemon/src/daemon.ts:5798-5799`）は
     `loadPromptAsset` を内部で呼ぶので、注入口はそこにも効く。**daemon.ts に引数を
     通し直す改修はしないこと**（スコープ外）

2. `tests/acceptance/audit-checklist-assets.spec.ts` の
   「Checklist edit propagates to the audit agent」を書き換える:
   - `before` で `fs.mkdtempSync` の一時ディレクトリに `skills/` を作り、
     **本物の `skills/*.md` をコピー**したうえで、コピー側の `audit-checklist.md` に
     `CHECK-MARKER-42` を追記する
   - `process.env["BANTO_SKILLS_DIR"]` を一時ディレクトリに向ける
   - `after` で環境変数を**元の値に復元**（元が undefined なら delete）し、
     一時ディレクトリを `fs.rmSync(..., {recursive:true, force:true})` で片づける
   - **本物の `skills/audit-checklist.md` へは一度も書かない**。
     `originalChecklist` を書き戻す `process.once("exit"/"SIGTERM"/"SIGINT")` の
     仕掛けは不要になるので消すこと
   - 同 spec の他の describe（ファイルの存在確認・`loadPromptAsset` が
     ディスクから読むことの確認）は**本物の skills/ を読んだまま**でよい。
     書き換えないなら奪い合わない

3. `BANTO_SKILLS_DIR` が立っていないときは従来どおり `<repoRoot>/skills` を読む、
   という試験を1件足すこと（既定を壊していないことを機械で固定する）。

## やらないこと

- `package.json` の `test` に `--test-concurrency=1` を足さない
- 試験を skip / 削除して回避しない
- `packages/banto-daemon/src/daemon.ts` を変更しない（スコープ外）
