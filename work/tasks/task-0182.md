## 背景（前提を全部ここに書く。あなたはこの案件の記憶を持っていない）

banto のレビューは3段（ADR-0013 決定57）。`auto`（人も番頭も見ずに着地）/ `banto`（番頭が受けて通す）/ `po`（PO 本人しか通せない）。

段を決めるのは `packages/banto-daemon/src/review-policy.ts` の `resolveReviewStage`（301行目付近）で、判定は上から順に

1. `governance: true` なら `po`
2. **層B設定 `meta/config.yaml` の `review.po_required_paths` に `scope.paths` が触れるなら `po`**（タスクの宣言より手前で勝つ）
3. タスクの宣言（`auto` / `po` / `banto` / 旧称 `manual`→`banto`）
4. 層Bの `review.default_policy`、無ければ `DEFAULT_REVIEW_STAGE`（＝`auto`）

いま banto 自身の `meta/config.yaml` には

```yaml
  po_required_paths:
    - packages/banto-web/**
    - docs/spec/design.md
    - prototype/**
```

が書かれている（ADR-0013 決定66、2026-08-06 の PO 裁定「banto の面＝利用体験は PO の領分」）。

**この規則が実地で関所として機能していない。** 2026-08-16 の一日で、task-0156・task-0159・task-0180 が `po` に上がったが、いずれも番頭が先に差分を読んで確かめたあとの形式的な一押しで、PO が中身を見て何かを止めたことは一度も無かった。PO の恒久指示はこうである：

> 私が明示的にお願いするとき以外、banto の開発でもユーザのレビューは省略してくれないかな。あんまり意味ないし。

## 方針（これは決定事項。動かさない）

- **仕組みは消さない。banto 自身の一覧を空にするだけ**にする。`po_required_paths` の機構（決定57・66）はそのまま残す——他のプロジェクト（dentaku・loamium・hiragana・mirante）では PO が実際に画面を見て判断する意味があり、あちらの設定には一切触らない。
- **PO が「これは見せて」と言ったときの道は必ず残る**：タスクが `review: {policy: "po"}` を宣言すれば `po` のまま（判定3）。`governance: true` も従来どおり `po`（判定1）。パスで縛り直したくなったら `meta/config.yaml` に1行足せば次の判定から効く（ビルドも再起動も不要）。
- **省くのは「差分を見て通す」形式のレビューだけ。** PO の判断が要る場面（後戻りできない変更・データを消す・外に出る費用・方針の転換・PO が待っているものの取り下げ）は従来どおり取次へ上げる。「レビューを省く」と「PO に諮らない」は別物であり、この線引きを記録に明記すること。
- **新しい決定番号は振らない。** 決定66 への日付つきの追記として書く。理由：決定番号の一意性を機械で守る task-0159 がちょうど着地しているところで、いま番号を増やすと衝突しうる。
