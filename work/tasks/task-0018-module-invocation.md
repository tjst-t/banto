## 背景

ADR-0010 決定27 (b) より。モジュール間の呼び出しをモジュール任せにすると、モジュール数の増加に対して O(N²) の結合作業（接続・発見・認証を各ペアで自作）が発生し、決定25 で登録の口を1つにした狙いと逆行する。そこでフレームワークが①レジストリ ②共通の呼び出し規約とクライアント実装を提供する。

**ブローカー方式は採らない。** 呼び出しが Banto プロセスを通ると、Banto が単一障害点になり、Kobo が Banto の稼働に依存する——ADR-0009・決定1 の「Kobo は独立、Banto は Kobo のクライアント」という依存の向きを逆に壊し、決定6 で守った Kobo のライフサイクル独立性にも反する。実際の呼び出しは当事者間で直接行う。

呼び出しの単位は既存の Tool 契約（決定9）を使う。同じ Tool を番頭も他モジュールも呼ぶ形になり、決定25 の「同じ能力に入口が複数あり、契約は1つ」の再適用になる。番頭（AIエージェント）は経路に入らない。

最初の利用者は Kobo → Worker Pool（Kobo が職人を使う経路。決定23・27c）だが、Kobo 側の実装は本タスクのスコープ外。

## スコープ外

- 認証・再試行・非同期・ストリーミング（決定27b：具体的な必要が出てから足す。P1）
- Kobo 側からこの仕組みを使う実装（Kobo接続後）
- モジュールの動的な追加・削除
