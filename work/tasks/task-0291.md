## 何が起きているか（実測）

`tests/acceptance/claude-agent-start-timeout.spec.ts` が**フルスイート実行時だけ落ちる**。

- 単体実行（`npm run test:one`）では**3回連続で全11件通過**。失敗は再現しない。
- 落ちるのは `npm test`（2830試験・約8.8分）の負荷下だけ。直近で落ちたのは **`[a3]`**。
- 落ち方：`BANTO_CLAUDE_START_TIMEOUT_MS=150` という短い値を使う試験で、**起こし直しの2回目の試行（成功を期待している側）が計測前に完了しなかった**。
- 2026-08-20 の観測時点で、この試験ファイル自体は当該タスクの変更で**一切触られていない**（`git diff` で確認済み）。**無関係のタスクを巻き添えで落としている。**

## これは3度目である（ここが肝心）

同じ間欠に対して、**「タイムアウトの数字を上げる」手当てが既に2回打たれている**。

1. `task-0267` のコミット `93529a49` — `BANTO_CLAUDE_START_TIMEOUT_MS` を 150ms → 1000ms
2. `task-0269`（2026-08-17 マージ済み・`merge_gate_evaluated` 通過）— 同じ内容を a2/a4 に適用。**失敗専用ブロック a3/a5 は 150ms のまま残した**

いまファイルには、その痕跡がコメントごと残っている。

- 240行目 `= "1000"`、266行目 `= "1000"; // P6: 上記 a2 と同理由でフルスイート負荷に耐える値`
- 310行目 `= "1000"; // P6: 退路（2回目の起動成功）を待つため、負荷に耐える値`
- **284行目 `= "150"`（a3）**、**350行目 `= "150"`（a5）**

**a3 が落ちたということは、「失敗専用ブロックは 150ms のままでよい」という task-0269 の判断が間違っていた**ということである。a3 は 150ms で「落ちること」を確かめたあと、**1000ms に戻して2回目の起動が成功することまで見ている**——つまり a3 は失敗専用ブロックではなく、**成功側も見ている**。そこが負荷で崩れる。

**だから、また数字を上げるのはやめる。** 3度目の同じ手当ては、直したことにならない。

## やること

**壁時計への依存そのものを断つ。** 「本物のプロセスが 150ms 以内に起動するか」を実時間で測るのをやめ、**時間の進み方を試験が握る**形にする。

考えられる筋（**どれを採るかは実装者が決めてよい。ただし選んだ理由を書き残すこと**）：

1. **時計を注入する。** `packages/banto-worker-pool/src/claude-agent-driver.ts` の起動待ちが使っている時刻源・タイマーを、外から差し替えられる口にする（既定は現状のまま）。試験は偽の時計を渡し、**実時間を1ミリ秒も待たずに**「間に合った／間に合わなかった」を作る。
2. **待たされる対象を偽物にする。** 素の node サブプロセスの bootstrap を待つのをやめ、**起動の合図を試験が任意のタイミングで送れる**仕掛けにする。

**どちらにせよ、次の性質を満たすこと。**

- **負荷とは無関係に、決まった結果になる。** 遅いマシンでも、フルスイートの最中でも、結果が変わらない。
- **「間に合わなかった」経路も「間に合った」経路も、両方を確かめられる。** 片方だけ確かめて済ませない。
- **`BANTO_CLAUDE_START_TIMEOUT_MS` が効くこと自体は、これまでどおり確かめる。** 環境変数の口を消さない（`claude-agent-driver.ts:53` に「環境ごとに変えられるように」と設計意図が書かれている）。

## 確かめ方

**「単体で通った」を根拠にしない。** この間欠はまさに単体では通る。
**フルスイート（`npm test`）で通ることを確かめる**こと。手元の袋の中で一式を叩かないこと——マージ前ゲートが検証環境で回す。

## 変えないこと

- `BANTO_CLAUDE_START_TIMEOUT_MS` という環境変数の名前と役割
- 既定のタイムアウト値（10s）
- この試験が見ている振る舞いそのもの（起動待ちが超過したら失敗し、起こし直しで回復すること）
