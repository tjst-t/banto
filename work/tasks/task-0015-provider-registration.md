## 背景

ADR-0010 決定25・27 より。モジュール（Kobo・将来の他領域・基本GUIセット・Worker Pool）は「接続情報＋Tool＋GUI＋SKILL」を1つの登録単位として Banto に登録する。基本GUIセットもこの同じ仕組みに乗る組み込みモジュールであり、特別扱いの経路を持たない（標準ライブラリと同じ位置づけ）。決定27 (a) により、旧称「店（Provider）」は「モジュール」と呼ぶ。

現状は、Tool（`createCanvasTools` / `createFileTools` / `createGitTools`）とカタログ（`demoCanvasViews`）を `bin.ts` がそれぞれ直に組み立てており、モジュールという単位が存在しない。このままではモジュールが増えるたび `bin.ts` に配線が積み上がり、決定25 の「Banto 中核はモジュールを登録する機構だけを持つ」が成立しない。

決定25 は「人が GUI でできることは番頭にもできる。ただし経路が異なる」とも定めている。UI はモジュールのデータAPIへ、番頭はモジュールの Tool へ向かう。**UI が番頭の Tool を呼ぶ構図は採らない**ため、本タスクで UI 向けの Tool 呼び出し経路は作らない。

決定26 により、登録単位には SKILL も含まれる（モジュールが既定を出し、番頭の学習層が上書きする3層構成）。本タスクは「モジュールの SKILL を受け取って番頭の手続き記憶へ載せる」ところまでを担い、学習層とオーバーライドの陳腐化検出は task-0017 とする。

## スコープ外

- 基本GUIセットを組み込みモジュールとして実装し直すこと（task-0016）
- Kobo をモジュールとして登録すること（Kobo接続後）
- 番頭の学習層による SKILL のオーバーライドと、その陳腐化検出（task-0017）
- モジュールの動的な追加・削除（起動時の登録で足りる。必要になってから）
- 認証（現状ローカル前提。決定19・§8の未決事項のまま）
