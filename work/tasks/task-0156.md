## 背景（これを読むだけで作れるように書いてある）

banto に「**AI（番頭）と人（PO）が同じブラウザを同時に触れる**」モジュールを作る。全体の判定と計画は `docs/proposals/2026-08-15-shared-browser-module-assessment.md` にある（**着手前に読むこと**）。要点だけ再掲する:

- 当初案（noVNC で画面共有 + mitmproxy で HTTPS 復号）は**両方とも捨てた**。理由は現物で確かめてある——公開の仕組み（`proxy-exposer.ts` / `caddy-exposer.ts`）は L7（HTTP/WS）でしか中継せず生 TCP（VNC の RFB）を通せない、`x11vnc` / `websockify` / `mitmdump` はこの機械に入っていない。
- 代わりに **CDP（Chrome DevTools Protocol）だけ**で作る。実測で、`Page.startScreencast` で画面が送れること、`Input.dispatchMouseEvent` だけでクリックが成立すること、`Input.insertText` で**日本語も入る**こと（IME 不要）を確認済み。実測スクリプトは `prototype/browser-probe/` にある。

この仕事（K1）は、その**最小の縦串**である。**「人が面を開くと画面が流れてきて、面から操作すると相手に届く」**まで。

## 作るもの

**置き場所は `packages/banto-host/src/browser/`**（新しい npm パッケージは作らないこと。`createSettingsModule` / `createStudioModule` と同じく、ホストの中に置くモジュールとして作る。将来切り出せる形にしておけばよい）。

1. **モジュール本体** `createBrowserModule()` が `BantoModule`（`packages/banto-host/src/module.ts:43`）を返す。`bin.ts` で register する（既存の `modules.register(createSettingsModule(...))` の書き方に倣う。**bin.ts に足すのは register の1行だけ**）。
2. **Tool 3本**（番頭用）: `browser.start` / `browser.stop` / `browser.status`。
3. **CDP クライアントは生の WebSocket で書く**（既存依存の `ws` を使う）。**playwright の高レベル API に依存しないこと**——後続の仕事で `Target.setAutoAttach` を使って service worker の通信を覗く必要があり、**高レベル API 越しでは子ターゲットへコマンドを送れない**ことが実測で判っているため。CDP はただの JSON-RPC（`{id, method, params}` を送って `{id, result}` が返り、`{method, params}` がイベントとして飛んでくる）。
4. **ブラウザの起こし方は差し替え可能な契約にする**。`launch(): Promise<{ webSocketDebuggerUrl, close(): Promise<void> }>` のような小さなインタフェースを1つ切り、モジュールはそれ越しにしかブラウザを知らない形にする（名前と形は任せる）。**この仕事では本物の chromium を起こす実装は書かなくてよい**（それは次の仕事でやる）。既定の実装は「まだ実装されていない」と分かる形で失敗してよい。**試験では偽の launcher を挿す。**
5. **面（canvas）** `browser.viewer` を `views` に足し、`packages/banto-web/src/views/registry.tsx`（84-106 行の REGISTRY）に登録する。既存例は worker-pool の `worker.viewer` と registry.tsx:94 の対。面は受け取ったフレーム（JPEG の base64）を描き、マウス・キーボードの操作を送り返す。
6. **面のための WebSocket を自分で生やす**。`packages/banto-host/src/server.ts:1253-1271` が、ホストが拾わなかった upgrade を各モジュールの `handleUpgrade` へ回してくるので、そこで自分のパスかどうかを判定して受ける。既存の書き方は `packages/banto-environment-pool/src/proxy-exposer.ts:58-79` と `packages/banto-host/src/remote-module.ts:114,164` にある。

## WS の作法（ここは必ず守る）

- 面が繋いだら CDP へ `Page.startScreencast`（`format: "jpeg"`, `quality`, `maxWidth`, `maxHeight`）を送る。
- `Page.screencastFrame` が来たら面へ流し、**必ず `Page.screencastFrameAck`（`sessionId` を添えて）を CDP へ返す**。返さないと次のフレームが来ない。
- 面から来た操作は次へ変換して CDP へ送る: クリック → `Input.dispatchMouseEvent`（`mouseMoved` → `mousePressed` → `mouseReleased`）／ホイール → `Input.dispatchMouseEvent`（`mouseWheel`）／文字入力 → **`Input.insertText`**（日本語はこれで通ることを実測済み）／特殊キー → `Input.dispatchKeyEvent`。
- **座標の変換**：面に表示している大きさとフレームの実寸は違う。`Page.screencastFrame` の `metadata`（`deviceWidth` / `deviceHeight` / `offsetTop` / `pageScaleFactor`）を使って、面から来た座標を実座標へ直す。**この変換は純関数として切り出すこと**（試験で固定するため）。

## この仕事でやらないこと（後続で別に積む）

通信の記録・要約 Tool・伏字／AI が操作する Tool（navigate・click・snapshot 等）／**本物の chromium を起こす実装**／アイドル TTL／HAR 出力。**混ぜないこと。**

## 試験の作り方（重要・ここを外すと通らない）

検証の器（`test` プロファイル）は **`node:24-alpine`** で、**chromium は入っていないし、playwright の chromium は glibc 版なので musl では動かない**（`docker/Dockerfile.test` と `docker/test.yaml` を見よ）。したがって:

- **本物のブラウザを起動する試験は書かないこと**（書くと検証が通らない）。
- 代わりに **`ws` で「偽の CDP エンドポイント」を立てて試験する**。受け取ったコマンドを配列に記録し、`id` に対する結果を返し、こちらから任意のイベント（`Page.screencastFrame` など）を投げられる小さなもので足りる。
- 試験は **`tests/acceptance/browser-module.spec.ts` の1本**にまとめる（既存の `tests/acceptance/*.spec.ts` の書き方に倣う。`node --import tsx --test` で走る）。
