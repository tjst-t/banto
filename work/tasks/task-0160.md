## 背景（なぜ作るか）

いま banto の「起票」は `work/inbox/**` に置いた md **だけ**で、**それを読むコードは packages/ tests/ 全体でゼロ**。誰も読まないので壊れても誰も困らず、実際に壊れている（2026-08-16 の現物調査）：

- 108件のうち `status` が **10種**に分裂（open/resolved/inbox/backlog/done/fixed/landed/closed/tasked/in-progress/accepted）。区別する規則はコードにも spec にも無い
- **id の衝突**が繰り返し起きている（起票を採番するコードが存在しないため。task-0152 で人手で振り直したが、**今日だけで6組目**）
- 決着済み45件のうち **31%はどの task になったか辿れない**
- 33件が書かれただけでコミットされず滞留していた

狙いは4つ：**書いたら残る／重複しない／どこへ行ったか辿れる／機械が読める**。

設計は既に確定している。**`work/inbox/proposal/prop-0003-backlog-store-with-seam.md` を最初に読むこと**（採用案とその理由、Seam の契約、段取り6本が書いてある）。**設計をやり直さないこと。** これはその段取りの**1本目**で、土台だけを作る。

## いま実際に起きている事故（採番をどう作るべきかの拠り所）

2026-08-16、**同じ日に6組の id 衝突**が起きた。直近の1件はこういう形だった：

1. 番頭が `file.write` で `imp-0070` を書いた。書き先は **main のチェックアウト**で、**未追跡（untracked）のまま**置かれた
2. task-0159 の職人は**別のワークツリー**で働いている。そこからは main の未追跡ファイルが**見えない**ので、`imp-0070` は空き番号に見えた。同じ番号を名乗った
3. ファイル名の実体は別なので **git の衝突にならず、枝の上では試験が緑のまま通った**
4. 監査が気づいて「`imp-0071` へ振り直せ」と指示したが、**`imp-0066 / 0068 / 0071 / 0072` も未追跡で既に置かれていた**。素直に従えば**番号を1つずらして同じ事故を再演する**ところだった

**教訓は3つで、これがこの仕事の設計制約になる：**

1. **「注意して採番する」では止まらない**（6組が実証）。人（番頭・職人）が id を決める形をやめる
2. **「その場のファイルを走査して空き番号を探す」形は、見る場所によって答えが変わるので破れる**。git の作業ツリーは、コミット済み・未追跡・どのワークツリーかで見え方が違う。**どこから見ても同じ答えになる採番**にすること
3. **書いたのに消える／見えないのが、一連の事故の共通項**。書いたら残る置き方にすること

## 1. レコード定義

```ts
export type BacklogStatus = "open" | "tasked" | "dropped" | "done";

export interface BacklogEntry {
  id: string;                 // "bl-0001" — **ローカル主権**。外部の番号は絶対にここへ入れない
  kind: "improvement" | "incident" | "proposal";
  title: string;
  body?: string;              // 本文（短いものはここ）
  bodyPath?: string;          // 長い本文・移行してきた md の在り処（リポジトリ相対）
  status: BacklogStatus;
  origin?: string;            // 自由文字列のまま持つ（潰さない。実データが自由文なので）
  projectTag?: string;        // 決まっていないことが多い。省略可
  refs?: string[];            // 関連 id の自由なメモ（従来の refs をそのまま受ける）
  tasks?: { projectTag: string; taskId: string }[];  // **どの task になったか**。refs とは別欄
  external?: { provider: string; id: string; url?: string; syncedAt?: string };
  clientKey: string;          // 冪等キー（クライアント側の一意キー）
  syncState?: "none" | "pending" | "synced" | "failed";
  syncError?: string;
  createdAt: string;          // ISO8601
  updatedAt: string;
}
```

- **`refs` と `tasks` を混ぜないこと。** いまの追跡不能 31% は「refs が関連 id の自由なメモでもあり、どの task になったかの欄でもある」ことが原因。`tasks` は構造化した別欄にする
- `status` は**4値だけ**。それ以外を渡されたら例外（I2：黙って捨てない・黙って通さない）

## 2. `BacklogStore` インタフェース（Seam）

PO 指示は「バックエンドを差し替えられるように。たとえば GitHub の Issue と同期できるように。最初はファイルでいい」。差し替えの形は2通りあり、性質がまるで違う：

- (i) Store をそのまま差し替える（GitHub 実装では `list` が API を叩く）→ **番頭の道具呼びがネットワークで失敗しうる**。「気づいた瞬間に1行で置ける」というこの機構の肝が、レート制限とタイムアウトの下に置かれる
- (ii) **ローカルが常に真実、外部は投影先**（ファイル実装＋同期アダプタ）

**採るのは (ii)。** インタフェースの doc コメントに、契約として次を明記すること：

> **読みはローカル索引から即答する（ネットワークを待たない）／書きはローカルに確定してから外へ送る（外への送信の失敗は起票の失敗ではない）**

口：

```ts
export interface BacklogStore {
  file(input: BacklogFileInput): Promise<BacklogEntry>;   // 新規起票（冪等）
  get(id: string): Promise<BacklogEntry | undefined>;
  list(query?: BacklogQuery): Promise<BacklogEntry[]>;    // ローカル索引から即答
  update(id: string, patch: BacklogPatch): Promise<BacklogEntry>;
  capabilities(): BacklogCapabilities;                    // { pull: boolean; push: boolean }
  pull?(since?: string): Promise<BacklogPullResult>;      // capability。ファイル実装は持たない
}
```

`pull` を**最初から口に定義しておく**のは、PO の狙いが「人が GitHub 側でも書いたり読んだりする」＝**双方向**だから。双方向が要ることで決まる設計を、いまの形に織り込む：

- **id 発行のきっかけが2つになる**（`file` と `pull`）。外で作られた Issue は取り込み時にローカル id を振り、`external` に GitHub 番号を持つ。**ローカル id 主権は維持**
- **競合は欄ごとに所有者を決める**——表題・本文は「最後に編集した側」（機械が人の文を潰さない）、状態と `tasks` は **banto が正**、コメントは外（ローカルには概念を作らない）
- **削除は無い**。`dropped` は外では closed＋ラベルへ投影する
- **状態語彙の変換表は Store 実装側に置く**。banto 本体は4値のまま何も知らない

これらは**この仕事では doc コメントとして書けば十分**（GitHub 実装は段取り6・別枠）。**実装が1つしかないうちに汎用化しないこと。**

## 3. 採番（**ここがこの仕事の肝。上の「事故」の節を読んでから設計すること**）

**採番の権威は Store 1箇所に寄せる。** 具体的に守ること：

1. **`file` の入力に `id` を渡す口を作らない。** 型に存在させないこと。呼ぶ側（番頭も職人も）は id を決められない。`BacklogFileInput` に `id` フィールドが無いことが、そのまま保証になる
2. **id を名指しできるのは取り込み経路だけ**（`pull` と、段取り3の移行）。そこは別の関数（例 `adopt(entry)`）にして、**既存 id と衝突すれば例外**にする。黙って上書きも黙って採番し直しもしない
3. **採番の根拠は jsonl だけ。** ディレクトリ走査（md を数える・ファイル名から最大値を拾う）で採番しないこと。**md は保険であって正ではない**——消えても・増えても・別のワークツリーから見ても、次の番号は変わってはいけない
4. **並行しても衝突しない。** 同一プロセス内の同時呼び出しは直列化し、追記は1行が途中で混ざらない形で書くこと（追記の最中に落ちても、次の読みで壊れた行が混ざらないこと）
5. **`packages/banto-daemon/src/task-record.ts` の `nextTaskNumber` を読むこと。** タスク側は「ファイル名と帳簿の両方の最大値を見る」形で衝突を避けている。**その考え方は参考にするが、ファイル名を見る側は真似しないこと**（それがまさに今日の事故の原因）

## 4. ファイル実装

- 真実は **`<dataDir>/backlog.jsonl`**（追記だけ。取次の `inbox.jsonl` の隣）。**`packages/banto-host/src/inbox.ts` が同じ形（追記だけのイベントログ＋起動時の読み直し）なので、それに倣うこと**
- **記録として md をリポジトリへ書き出す**（Kobo が `work/tasks/task-NNNN.md` を書くのと同じ形）。書き出し先は**コンストラクタのオプションで受ける**（既定を決め打ちしない。試験は tmpdir を渡す）。1件1ファイル、front matter に id/kind/status/createdAt/updatedAt/tasks/external、本文が続く形
- **jsonl から md を全件再生成できること**（md は保険であって正ではない。md を消しても jsonl から戻せる形にする）
- 冪等：`clientKey` が既にあれば**新規に採番せず既存を返す**
