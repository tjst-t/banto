## 番頭が先に読んだところ（鵜呑みにせず、現物で確かめること）

`packages/banto-worker-pool/src/pi-rpc-driver.ts` の 490 行あたり:

```ts
// After a brief startup delay, send get_state to obtain the session ID.
setTimeout(() => {
  if (settled) return;
  stateQueried = true;
  const cmd = JSON.stringify({ type: "get_state" }) + "\n";
  proc.stdin?.write(cmd, (err) => {            // ← 495 行目
    if (err && !settled) {
      settle({ ok: false, error: `Failed to write to pi stdin: ${err.message}` });
    }
  });
  ...
}, 200);
```

**200ms 後に書いている。その間に子プロセスが終了していると stdin は閉じており、書き込みが EPIPE になる。**

**コールバックを渡しているのに落ちるのが要点。** Node の Writable は、書き込みエラーを
**コールバックへ渡すと同時に `error` イベントとしても出す**。`proc.stdin` に `error` の受け手が
居ないので、**未捕捉のエラーになってプロセスごと落ちる**——だから「コールバックで処理しているつもり」でも
効いていない。**この仮説を必ず現物で確かめてから直すこと**（受け手を1つ足しただけで直るかどうかで判別できる）。

## 直す向き（原因を確かめてから選ぶ）

**握り潰さないこと（I2）。** 「子プロセスがもう居ない」は**はっきりした結末**なので、黙って無視するのではなく
**その結末として決着させる**のが筋:

- `proc.stdin` に `error` の受け手を置き、EPIPE（`code === "EPIPE"` / `ERR_STREAM_DESTROYED`）は
  **「pi が先に終了した」と読み替えて settle する**。既にフォールバック（3秒後に合成の sessionId で
  `ok: true` にする）が在るので、そこへ合流させるか、`ok: false` で理由を明示するかを**選んで理由を書く**こと
- 書く前に `proc.stdin` が生きているか（`writable` / `destroyed`）を見る。ただし**見てから書くまでの隙間は
  残る**ので、チェックだけで済ませないこと（受け手は必ず要る）
- `settled` になったあと・子プロセスが `exit` したあとは、**200ms と 3000ms のタイマーを両方止める**
  （止めないと、決着後に走って同じ書き込みを起こす）
- **EPIPE 以外のエラーまで一緒に飲み込まないこと。** 想定していない失敗は、いままでどおり出す
