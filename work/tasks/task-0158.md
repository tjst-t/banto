## 背景（何が起きたか）

2026-08-16、task-0152 が着地したのに幹（番頭）が次の一手（banto の再起動＝稼働への反映）を踏まなかった。PO の言葉：

> 「そのように段取りしました。流れ：task-0152 が着地 → 枝から私へ合図 → 私が再起動を踏む」と言ってくれていたのに、私が「0152 完了しましたね」と言うまでその先を実施してくれなかったのはなぜでしょうか。**私は枝からの通知を見て幹が自動で先に進んでくれることを期待していました。**

内訳（番頭の分析）：

1. adr-0025（決定120：知らせは幹のターンを起こさない）が効いていて、**枝が畳まれても幹は動かない**。`thread.merge` は幹の末尾に結論を1行積むだけで、幹のターンを回さない。
2. task-0152 を実際に握っていたのは、機構が T3 で自動的に立てた**用件枝 thread-119**。あの枝が承認もマージ確認も済ませ、**静かに畳んだ**。幹は起きなかった。
3. 番頭が「着地したら合図をくれ」と頼んだ相手は、工場の流れを**観測する役の枝 thread-118** で、タスクを握っている枝ではなかった。観測役は合図の契機を持っていなかった。
4. これは予測されていた副作用（`docs/proposals/2026-08-15-trunk-availability-plan.md:123`）。「未読で足りるか運用で見る」と先送りしてあったが、足りなかった。

## この仕事の線（壊してはいけないもの／足すもの）

- **保つ線**：知らせ（職人の報告・工場の進捗・env・system）は**幹のターンを起こさない**。これは PO の恒久方針（決定120）なので絶対に壊さない。
- **足す線**：**枝の結論に「幹が次に踏む一手」が含まれるときだけ、幹のターンを1本起こす。** 今回で言えば「着地したので再起動を踏んでほしい」。これは雑音ではなく**仕事の受け渡し**であり、幹が受け取るべきもの。
- `thread.consult`（枝が生きているうちに幹へ聞く）は**既に幹を起こす**ので触らない。穴は「畳むときに一手を渡す経路」が無いことだけ。

## 設計の決定（番頭が現物を読んで決めた。この通りに作ること）

案は2つあった。

- **(a) `thread.merge` に「幹の一手」を渡す欄を足し、非空なら幹のターンを1本起こす** ← **これを採る**
- (b) `remaining` の所在が「幹」を指しているときだけ起こす ← **採らない**

**(b) を採らない理由**（`packages/banto-host/src/remaining-whereabouts.ts` を読んで判断）：

1. 所在の語彙は**意図的に緩い**。`WHEREABOUTS_WORDS` には「幹へ」「幹で」「PO」「待ち」「委譲」「引き継」などが入っていて、これは「**誰が残作業を持っているか**」を言えていれば通す、という緩さ。ここを起床の条件に転用すると、**ごく普通の畳み方の多くで幹が起きる**——保つべき「幹は静か」が壊れる。
2. `remaining` は「**残っている作業**」であって「**いま幹が踏む一手**」ではない。前者は `thread.settle` で降ろすまで未処理として残り続けるもの、後者は幹が1回受け取れば消えるもの。**寿命が違うものを同じ欄に載せない**。
3. `remaining` の行からは「**何をしてほしいのか**」が読めない。「task-0092 を積んだ」を受け取った幹は、自分が何を踏むべきか分からない。

(a) は意図が明示で、機械で検査でき、既存の `remaining` 検査（imp-0036(d)）の意味を汚さない。

**この選定理由は記録に残すこと**（下の「記録」の節）。

## 実装（`packages/banto-host`）

### 1. `thread.merge` に `handoff` を足す（`packages/banto-host/src/thread-tools.ts`）

- パラメータ名は **`handoff`**（`Type.Optional(Type.String())`）。説明文は日本語で「**幹が次に踏む一手**。書かないと幹は動かない（結論の1行では幹のターンは起きない）。例：『task-0152 が着地したので banto を再起動して反映してほしい』」。
- **空白のみ／未指定なら従来どおり**——幹の末尾に結論1行が積まれるだけで、幹のターンは起きない。
- **非空なら、畳んだあとに幹のターンを1本だけ起こす**。起こし方は既存の `thread.consult` と同じ経路（`options.nudge` を `handOff(...)` で**待たずに**渡す。待つと幹が喋り終わるまで枝が固まる）。
- 幹へ渡す本文には、幹がこの枝の中を見ていないことを前提に、**枝の題・結論・一手・この枝を読み返す引き方**（`thread.read({ threadId: "<枝の id>" })`）を書く。
- **`options.nudge` が配線されていない構成で `handoff` を非空で渡されたら、畳む前に断る**（I2：渡したつもりにさせない）。断り文は `thread.consult` の「この構成では幹へ還せません（nudge が渡されていません）」に倣う。**状態は触らない**（枝は開いたまま）。
- `thread.consult` にある往復の上限（`allowSend`）は **`handoff` には掛けない**。畳むのは1枝1回であり、上限で弾くと**畳めなくなる**（弾くべきは往復であって受け渡しではない）。

### 2. 二重に起こさない（`packages/banto-host/src/threads.ts`）

- `ThreadRegistry.merge` は同じ結論での畳み直しを冪等に早期 return する。**畳み直しで幹をもう一度起こしてはいけない。**
- **一度きりの保証は帳簿（`threads.ts`）側で持つこと**——道具の側だけで見ると `merge` を呼ぶ経路が増えたときに素通りする（imp-0036(d) で `remaining` の検査を帳簿側に置いたのと同じ理由）。`merge` に `handoff` を受け取らせ、**まだ渡していない一手があるときだけ**道具へ「渡すべき一手」を返す形にする（例：`thread.handoff` と `thread.handoffDeliveredAt` を持ち、返り値で初回だけ知らせる）。
- **`handoff` は枝の詳細にも残す**（`renderMergeDetail` 相当）。あとから `thread.read` で「この枝は幹に何を渡したのか」が読めること。
- **幹に積む結論の行は従来のまま1行**。一手を結論行に混ぜて幹の帯を太らせないこと（決定77・決定108 の縛り）。

### 3. 台帳（触らないが確認すること）

幹のターンの出所は `thread.consult` と同じ `nudge` になる。`worker` / `kobo` / `env` / `system` ではないので、**決定126 の判定（幹の行にこの4つが出ていないか）は保たれる**。ここは変えないこと。

### 4. 説明文と手順書（**これがこの仕事の半分**）

機構が自動で立てた用件枝（T3）を畳むのは**番頭**（決定122：機構は結論を捏造しない）。つまり**用件枝の中の番頭が、自分で一手を書く**しかない。書けと言われていなければ書かないので、次の3か所に明記する：

- `packages/banto-host/src/thread-tools.ts` の `thread.merge` の説明文——「**幹が次に踏む一手があるなら `handoff` に書く。書かなければ幹は動かない**」。あわせて既存の一文「幹の判断が要ることは remaining に書いても誰にも届かない」との**使い分け**も書く（枝が生きているうちの問い＝`thread.consult`／畳むときの受け渡し＝`handoff`）。
- `packages/banto-host/src/bin.ts` の会話の節（`- **Work left over in a branch does not reach the trunk by itself.**` の周辺）と、**枝のシステム文言**（`Stay on this one question. …` の周辺・494行目付近）——「畳むときに幹が踏む一手があるなら handoff に書く」。
- `packages/banto-host/skills/trunk-and-branch/SKILL.md`——畳む前の手順に「幹の一手があるなら渡す」を足し、**今日の運用の教訓**も残す：**「合図を頼む相手は、そのタスクを握っている枝でなければならない。工場を観測しているだけの枝に頼んでも合図は来ない」**。
