## 背景

**挙動は正しい。壊れているのは説明文だけ。この仕事で挙動を変えないこと。**

`kobo.approve` の説明文（`packages/banto-daemon/src/kobo-tools.ts`）は、いまこう言っている：

> **既定は自動着地**（realign 第3便）なので、ここへ来ているのは条件を満たさなかったものだけ
> ——刻みが無い／契約に検査コマンドが1本も無い／**`manual` や `po` を名乗っている**、のいずれか。

**`banto` を名乗っている場合が抜けている。** `review: banto` のタスクは、刻みも検査コマンドも
揃っていても review-ready へ来る——`resolveReviewStage`（`review-policy.ts`）は宣言をそのまま
返し、`autoLandBlockers` は `stage === "auto"` のときしか呼ばれない（`daemon.ts` の
`handleAuditVerdict`）。列挙に無いので、読んだ側は**「`banto` は自動着地する側だ」**と受け取る。

`kobo.amend` の説明文は「`review` は `po` > `banto` > `auto` の順に厳しく」と書いていて、
そちらは実態と合っている。**2つの説明文が互いに矛盾している。**

**実害が出ている。** 番頭がこれを誤読し、PO に「`review: banto` を指定しても番頭を通らずに
通ってしまう」と報告した（機構の欠陥ではないものを欠陥として伝えた）。

判断待ちの札（`packages/banto-host/src/kobo-notice.ts`）にも同じ穴がある。「**なぜあなたに
来たか**」の節は、遷移理由が `自動着地の条件を満たさない: …` に一致したときだけ出る
（`fellBack`）。`banto` を名乗って来たタスクには理由が何も書かれず、番頭は「なぜ自分に
来たのか」を毎回 `kobo.task` で調べ直すことになる。

## この件の判別法（記録として残すこと。次に同じ疑いが出たときは帳簿だけで決着する）

**「自動着地したのか、人が通したのか」は帳簿の遷移だけで判別できる：**

| 何が起きたか | 帳簿に出るもの |
|---|---|
| **自動着地**（realign 第3便） | `auditing → merging` を理由 **`audit_passed:auto`** で1回。`review_opened` も `task_approved` も**書かない** |
| **人（番頭）が通した** | `auditing → review-ready`（`audit_passed:banto`）→ `review_opened:banto` → `task_approved` → `approved_by:banto` |
| **自動着地の条件を満たさず落ちた** | `auditing → review-ready` を理由 `audit_passed:auto→banto（自動着地の条件を満たさない: …）` で |
| **PO が通した** | `task_approved` の `approvedBy` が `po`、`via`（どの画面から来たか）付き |

**`approved_by:banto` を書ける口は `kobo.approve` 道具ひとつだけ**である（`by: "banto"` を渡す
実装はそこだけ。HTTP の `po-decision` は `by: "po"` で `via` 必須、自動承認の実装は存在しない
——`autoApprove` の類は grep 0件）。だから `approved_by:banto` が帳簿にあるなら、**必ずどれかの
番頭セッションが `kobo.approve` を呼んでいる**。呼んだ覚えが無いなら疑うべきは機構ではなく
**別の枝**である（task-0152 の実例：観測していた枝ではなく、機構が自動で開いた用件枝が、
差分と試験の中身を確かめたうえで通していた）。
