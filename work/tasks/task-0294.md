## 実測した事実（2026-08-20）

`task-0289` の帳簿（`/var/lib/banto/data/events/2026-08.jsonl`）を直に読んだ結果。

```
05:52:18 agent_spawned    3dd46d97-2          （実装役）
05:55:30 state_transitioned → auditing
06:01:36 agent_exited     f54fbb8e-4          （実装役・古い方）
06:11:36 agent_exited     3dd46d97-2          （実装役）
```

**`auditing` へ入ってから、`audit_started` も監査役の `agent_spawned` も1件も積まれていない。** 2件の `agent_exited` はどちらも**実装役**である。タスクは25分以上 `auditing` のまま動いていない。

## 何が穴なのか

task-0287（ADR-0027 決定142）で入れたフェイルオープンは、**3つの起点すべてが「監査人が起きたあと」にぶら下がっている**。

1. `applyWorkerReport()` — 監査人が**報告した**とき
2. `handleAgentExited()` — 監査人が**落ちた**とき（`role === "audit"` の分岐）
3. `spawnAuditSession()` の catch — spawn が**例外で失敗した**とき

**「監査人が一度も起きていない」状態には、どれも引き金が無い。** `auditing` に居座るタスクを誰も助けに来ない。

**これは PO 裁定「監査のせいで工程が止まる方が、いまは問題である」が消そうとしていた失敗型そのもの**が、別の入口から残っている状態である。しかも**フェイルオープンを入れたことで見えにくくなった**——以前なら `task_failed` が立って番頭が `kobo.reopen` を打てたが、いまは静かに `auditing` のまま止まる。

## どうしてそうなるのか（推定。実装者が確かめること）

`spawnAuditSession()` は **`auditing` への遷移のときにだけ**呼ばれる。この呼び出しは `_trackBackground` の非同期で走るので、**その途中で daemon が落ちる（再起動・kill）と、そのまま消える**。再起動後の daemon は帳簿から状態を組み直すが、**`auditing` に居るタスクに監査人が居るかどうかは確かめない**——起動時の照合にも巡回にも、その仕事が無い。

実際、2026-08-20 に `banto-daemon.service` を 05:58:34 に起こし直しており、task-0289 の `auditing` 遷移（05:55:30）はその直前である。**再起動が引き金だった可能性が高い**が、**原因を1つに決め打ちしないこと**——他の経路（`keepWorkerIfStillWanted` が false を返して静かに戻る、工房が満杯で断られる等）でも同じ形になり得る。**直すべきは「なぜ起きなかったか」ではなく「起きていないことに誰も気づかない」方**である。

## やること

**巡回（`Scheduler` の登録ジョブ。`daemon.ts:737` 付近に `rotation-check` / `gate-reeval` / `auto-spawn` / `worker-events` / `merge-queue` / `dwell-watch` がある）で、`auditing` に居るタスクに生きた監査人が居るかを照合し、居なければ起こし直す。**

- **既存のジョブに足すか、新しいジョブを1つ足すかは実装者が決めてよい**（`auto-spawn` が近い。増やすなら理由を書くこと）。
- 判定材料は帳簿から取れる：そのタスクの最後の `audit_started` / `agent_spawned`（role=audit）と、そのセッションが生きているか。
- **起こし直しの回数は `AUDIT_ATTEMPT_LIMIT` の数え方と揃えること**（`countAuditAttempts` は `audit_started` を数えている）。**無限に起こし直さない。**
- **上限まで起こしても監査人が立たないなら、既定で通す**（`recordAuditPassByDefault`）。理由の接頭辞は他の3つと**混ぜないこと**——例 `audit_never_started:`。ADR-0027 決定143 の「内訳を読み分けられること」がここでも要る。
- **起動直後に1回だけでなく、巡回のたびに効くこと。** 再起動以外の経路でも同じ形になり得るため。

## 変えないこと

- 明示の `verdict: "fail"` は、これまでどおりブロックする
- 既存の3つの既定通過の理由と、その接頭辞
- `AUDIT_ATTEMPT_LIMIT` の値そのもの
