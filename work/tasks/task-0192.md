- `tests/acceptance/spawn-args.spec.ts [AC-S254276-5-1]`

## どこが穴か（読んで確認済み）

`packages/banto-worker-pool/src/pi-rpc-driver.ts` の起動直後、**200ms 待ってから** `get_state` を子の stdin へ書く：

```ts
setTimeout(() => {
  if (settled) return;
  stateQueried = true;
  const cmd = JSON.stringify({ type: "get_state" }) + "\n";
  proc.stdin?.write(cmd, (err) => {
    if (err && !settled) settle({ ok: false, error: `Failed to write to pi stdin: ${err.message}` });
  });
  ...
}, 200);
```

**穴は2つある。**

1. **子の生存を見ずに書いている。** 負荷が高いと子は 200ms を待たずに死ぬことがある
   （spawn 直後に落ちる／メモリ不足）。死んだ子の stdin へ書けば EPIPE になる。
   **EPIPE は結果であって原因ではない**——いまの文言は `Failed to write to pi stdin: write EPIPE` にしかならず、
   **子が何で死んだのか（exit code・signal・stderr）がどこにも出ない**。
2. **`proc.stdin` に `error` ハンドラが無い。** write のコールバックで受けても、
   stdin（Socket）側の `error` イベントは別に上がる。**listener が無い `error` は uncaughtException になり、
   親プロセスごと落ちる**。試験ではこれがそのまま `Error: write EPIPE` として出ている。
   **これは試験の都合ではなく製品コードの脆さで、稼働中の Worker Pool でも同じことが起きうる。**

同じ形の write が他にもある。**全部同じ扱いにすること**：

- `packages/banto-worker-pool/src/pi-rpc-driver.ts` の `:495` / `:587` / `:654`
- `packages/banto-worker-pool/src/claude-agent-driver.ts` の `:324` / `:395` / `:425`

（`:654` と `:425` は**コールバックすら渡していない**ので、いちばん危ない。）

## 何をするか

1. **書く前に子の生存を見る。** `proc.exitCode !== null || proc.signalCode !== null` なら書かず、
   「子が exit=N / signal=S で先に終わっている」と**子の stderr の末尾を添えて**失敗させる。
2. **`proc.stdin` に `error` ハンドラを付ける**（EPIPE を uncaughtException にしない）。
   握り潰すのではなく、**そういう状態であると記録して失敗させる**（I2）。
3. 子の stderr は**捨てずに保持**しておき、1. の文言に使えるようにする。
4. 上の6箇所すべてに同じ扱いを行き渡らせる。
5. **決着後・子の `exit` 後は、走り残っているタイマーを止める**（`pi-rpc-driver.ts` の 200ms と 3000ms の2本）。
   止めないと、決着したあとにタイマーが起きて同じ書き込みをやり直す。

## やらないこと（**ここが肝**）

- **リトライ・sleep・待ち時間の延長で隠さない。** 200ms を 500ms にするような直しは禁止——
  それは「たまに通る」を「もう少し通る」に変えるだけで、**子が死んでいる事実を隠す**
- **例外を握り潰して黙って続けない**（I2）
- **落ちる2本の試験の側をいじって通す、という直し方をしない。**
  `pi-rpc-system-prompt-tools.spec.ts` と `spawn-args.spec.ts` は**症状が出た場所であって原因ではない**。
  **あれを書き換えて緑にするのが、いちばんやってはいけないこと**（そもそもスコープに入れていない）
