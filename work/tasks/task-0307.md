## 背景

PO から「banto が異様に Token を食う」と指摘があり、本番の記録（`threads/*.jsonl` 218本・LLM リクエスト 29,337回）を集計した。送信入力の推定合計は 71.8億字 ≒ 26.5億トークン。その内訳の**第3位が「知らせ（notice）の全文注入」で 12.6億字 ≒ 4.64億トークン、全体の 17.5%**（暴走した thread-4 を除いても 10.9%）。

内訳の実測：

- notice のうち **2,000字を超えるものが 407件・183万字**。これは notice 全体の **48.4%**
- **最大 60,471字**の notice が1件ある
- 知らせは会話の履歴に積まれるので、**以後のターンで毎回再送される**。一度の大きい notice が延々と効き続ける

原因ははっきりしている。**道具の戻り値には「大きいと栞（artifact）へ退避して本文には要約とポインタだけ載せる」皮がかかっている**（`packages/banto-host/src/artifacts.ts` の `withArtifactOffload`、配線は `host-session.ts:223`、しきい値 2,000字）。ところが **notice は道具の戻り値ではないので、この皮がかからない**。

`packages/banto-host/src/server.ts` の `notify()`（978行目付近）はこうなっている：

```ts
async notify(text: string, options: NotifyOptions = {}): Promise<void> {
  const source = options.source ?? "system";
  const routed = await this.routeNotice(text, options, source);
  return this.deliverToThread(routed.text, routed.threadId, source, (thread) => {
    thread.record({ role: "notice", source, text: routed.text });
    this.broadcast({ type: "notice", threadId: thread.id, source, text: routed.text });
  });
}
```

`routed.text` を**長さを一切見ずにそのまま**記録している。

## やること

**`notify()` の1箇所で、既存の栞の仕組みを掛けるだけ。新しい仕組みを作らないこと。**

1. `artifacts.ts` が持っている「栞へ書き出す」処理と「本文に載せる要約＋ポインタを組み立てる」処理を、`notify()` から呼べる形にする。既に `withArtifactOffload` の内部で使われているものを取り出して再利用すること。**退避のしきい値・要約の書式・観測 id の採番は道具の戻り値と同じものを使う**（番頭から見て「大きいものは栞に置かれる」という一つの規則にする）。
2. `routed.text` がしきい値を超えていたら、栞へ全文を書き、**`thread.record` に積むのは要約＋ポインタだけ**にする。しきい値以下ならこれまでどおり全文。
3. **画面（`broadcast`）には全文を送ること。** PO は画面で知らせの中身を読む。トークンを食っているのは番頭の文脈に積まれる側だけなので、**記録に積む本文と画面へ流す本文を分ける**。ここを一緒に切ると PO が知らせを読めなくなるので必ず分けること。
4. 退避された notice は `artifact.read` で全文が読めること。要約の行に「全文は artifact.read で読める」ことが分かる書式を含めること（道具の戻り値の退避と同じ書式でよい）。

## やらないこと

- 知らせの配達・宛先の振り分け（`routeNotice`・T3 の「幹のターンを起こさない」規則）は**一切変えないこと**。変えるのは「記録に積む本文の長さ」だけ。
- しきい値の値そのものを変えないこと（別タスクで扱う）。
- 職人や工房が出す報告の中身を短くしにいかないこと。短くするのは受け側の1箇所だけで足りる。
