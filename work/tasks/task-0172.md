## 先に読むこと（2）：**a9 の根拠は否定された。`unref()` を外さないこと**

a9 に「`timer.unref()` のせいで遅延 flush が発火しないことがある」と書いたが、**これは誤りである。2段階で訂正する。**

**① 実測の読み違い**：「38分間 flush されず、言伝で一斉に書き出された」と書いたが、**その会話の記録は0件だった**（書き出されたファイルの1行目が言伝そのもので、それより前が1行も無い。`replace()` はメモリ全件を書き直すので、溜まっていたなら先頭に並ぶ）。**flush が遅れていたのではなく、record が1件も無かった**（`imp-0067`）。

**② 仕組みとしても成り立たない**：`unref()` が変えるのは「そのタイマーがイベントループを**生かし続けるか**」だけである。libuv の `uv__next_timeout()` は**タイマーヒープの最小値をそのまま返し、ref 状態を見ない**。banto は待ち受けソケット（ref 済み）を持つのでループは生き続け、**`unref` されたタイマーも定刻で発火する**。
**この機械の実測でも裏が取れている**——`unref` は banto 全体で常用されており（`server.ts:620` の WS ハートビート、`worker-notice.ts` / `env-notice.ts` / `kobo-notice.ts` の知らせの引き、`threads.ts:1729` の枝の見張り）、**外から何も来ていない時間帯に定刻で回った跡が journal に残っている**（例：2026-08-15 06:26:12〜:20 に2秒おきで6回）。

### したがって、この2つを守ること

- **`persist()` の `timer.unref?.()` を外さないこと。** 直る問題が無いうえ、**外すと終了時に毎回ループが延命され、`close()` の「必ず返る」保証（imp-0037 原因3）に手を入れることになる**
- **a9 の「見張りが確実に発火することを試験で固定する」だけは、そのまま残してよい**（害は無く、将来 `unref` の扱いを変えたときの回帰になる）。**`unref` を外す作業だと読み替えないこと**

**`pendingSaves` に張った時刻を持たせて、一定を過ぎたら別経路で書く**という保険は、**この見張り（a1）と同じ性質**なので、**そちらへ寄せてよい**。

## 背景

2026-08-16、幹 thread-61 の記録が **8/14 15:22 〜 8/16 00:48 の33時間ぶん、ディスクへ書かれていなかった**（inc-0075）。PO が「履歴が吹っ飛んだ」と気づくまで、**誰も気づかなかった。**

調査で分かったこと：
- **ハーネスは生きていた。**その間、会話は普通に回っていたし、章も21回畳めていた
- **死んだのは記録へ届ける経路だけ。** しかも **`record()` がメモリの `transcript` に積まれていなかった**ことまで確定している——`replace()` はメモリ全件の全文上書きなので、「メモリに在ったが flush されていなかった」なら、その後の書き込みで**必ず全部出てくる**。出てこなかった＝**メモリに無かった**
- **止まったのは thread-61 だけ**で、他の会話は正常に書けていた
- **原因は未確定。** 15プロセスを跨いで毎回同じ形に壊れ直しており、**正常終了（`flushAll()` が走る）を8回以上挟んでも書かれなかった**。なぜ治ったのかも説明が付いていない

**原因が分からないままでも、被害は止められる。** 「書いたつもり」と「実際に届いている」を突き合わせて、ずれたら知らせればよい。**今回はそれが無かったので、33時間ぶんが失われるまで誰も気づかなかった。**

## やること

`Thread` は `record()` のたびに `lastActivityAt` を更新している。これに対して、**記録ファイルの実体**（行数か更新時刻）を突き合わせる見張りを置く。

- **「書き戻しをスケジュールしたか」ではなく「実際に届いているか」を見ること。** 今回の事故は、まさに「書いたつもり」の側だけを見ていては絶対に気づけない形だった
- ずれを見つけたら**取次へ知らせる**（`inbox`）。ログだけにしないこと——**誰かが journal を見に行かないと分からない形では、また33時間気づけない**
- **過検知でうるさくしないこと。** 遅延保存（`SAVE_DELAY_MS = 400`）の途中や、静かな会話を誤って拾わないこと。**まだ一度も発言の無い会話**（記録0件でファイルが無いのは正常）も拾わないこと。しきい値は実装者の判断でよいが、**なぜその値にしたかをコメントに書くこと**
- **同じ会話について何度も鳴らさないこと**（一度知らせたら覚えておく。`watchStaleBranches` が同じ作りになっているので、それに倣うのが自然）
