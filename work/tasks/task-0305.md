## 実測した事実（2026-08-20 / task-0301）

番頭が `banto-worker-pool.service` を起こし直した直後、`task-0301` が落ちた。

```
09:13:30  state_transitioned → auditing
09:15:06  （番頭が工房を kill -9。工房は resume.ts で職人を起こし直す）
09:19:13  state_transitioned → implementing   （監査前検証が落ちた）
09:19:15  agent_spawned  9f759d5e            ← 新しい rework が立つ
09:19:17  agent_exited   e3204f69            ← **古い** rework の終了が、あとから届く
09:19:18  state_transitioned → failed
09:19:18  task_failed    agent_exited_without_report
```

**新しい職人が立った2秒後に、古い職人の終了が届いて、それでタスクが死んでいる。**

## 何が抜けているか

`daemon.ts` の `handleAgentExited`（3560行付近〜）には、役ごとに2つの分岐がある。

**監査の分岐にはガードがある。**

```ts
if (role === "audit" && current.status === "auditing") {
  // **いま動いている監査人の分だけ数える。** 置き換えられた古い監査人の終了も
  // ここへ来る（同じ taskId で起こし直すと、工房が前の1人を畳む）——それで数えると
  // 1回の事故で2人起こしてしまう。実際そうなった（試験で捕まえた）
  if (event.sessionId !== latestSpawnedSessionId(history)) return;
  ...
```

**その真下、実装役の分岐には無い。**

```ts
if (
  (role === "executor" || role === "rework") &&
  (current.status === "planning" || current.status === "implementing")
) {
  this.recordTaskFailed(projectTag, taskId, "agent_exited_without_report");
}
```

**同じ理由が同じように当てはまるのに、片方にしか手当てが入っていない。** 監査側のコメントは「実際そうなった（試験で捕まえた）」と書いており、**その知見が隣の分岐へ運ばれていなかった**。

## なぜ普段は出にくいか（そして、これから出やすくなる理由）

古い職人の終了が**新しい職人の spawn より後に届く**必要があるので、ふだんは順序が味方して表に出ない。**表に出るのは、複数の職人が同時に入れ替わるとき**——たとえば**工房を起こし直したとき**である。

工房の再起動は今後増える見込みがある。`packages/banto-worker-pool/src/resume.ts` の復帰の仕組みにより、**工房の再起動は安全**だと分かった（外から殺された職人だけを起こし直す）。**安全だと分かった以上、これからは気軽に再起動される。** そのたびにこの穴を踏む。

## やること

**実装役の分岐にも、監査と同じガードを入れる。**

```ts
if (event.sessionId !== latestSpawnedSessionId(history)) return;
```

- **監査側と同じ形・同じ理由づけで書くこと。** 新しい流儀を発明しない。**なぜガードが要るのかをコメントに残す**（「置き換えられた古い職人の終了もここへ来る。それで failed にすると、いま働いている職人ごとタスクを殺す」）。
- **`planning` / `implementing` の両方に効かせること。**
- **試験で縛る**こと。形は「①職人Aを立てる ②職人Bを立てる（Aを置き換える）③**Aの終了を後から届ける** ④タスクが failed になっていないこと」。**順序が逆に届くことこそが本題**なので、そこを試験の中で明示的に作ること。

## 変えないこと

- **いま働いている職人が報告せずに終わったら、これまでどおり failed にする。** 落とすのは「古い職人の終了で落ちる」経路だけ。**「報告せずに終わったことに気づかない」方へ倒さない**（task-0215 の趣旨）。
- 監査側のガードと `AUDIT_ATTEMPT_LIMIT` の数え方
- `worker_asked` / `worker_answered` の扱い
