## 何が起きているか（現物・2026-08-16）

**`work/tasks/task-0152.md` から `task-0197.md` まで46件が、まるごと未追跡（`??`）です。** Kobo が書いた契約の写しが、1本も履歴に入っていません。

性質が悪いのは、**誰も委譲する人が居ない**ことです。番頭が `file.write` で書いた起票なら「番頭が職人へ委譲すれば入る」——実際 2026-08-16 にそれで片付けました。しかし `work/tasks/*.md` は**機構が書いて、機構は commit しない**。放っておくと永久に入りません。

履歴を見ると、これまでは**人が手で入れていました**（最後は `895da7fe`「task-0151 の定義を履歴に入れる」2026-08-15）。**規律で回していたものが、規律どおりに回らなくなっただけ**です。

## 調べた現物（この判断の根拠。実装前にあなたも確かめてよい）

1. **書き手**：`packages/banto-daemon/src/task-record.ts`（「タスクの**記録ファイル**（`work/tasks/task-NNNN.md`）を Kobo が書く（第4便）」）。呼び出しは `packages/banto-daemon/src/daemon.ts:964` 付近（「記録ファイルを書き、`task_created` を出す——この順」）
2. **読み手**：`work/tasks/*.md` を読む watcher は**第4便で廃止済み**（`packages/banto-daemon/src/kobo-tools.ts:11`「入口はここだけ。`work/tasks/*.md` を読む watcher は廃止した」／`packages/banto-core/src/events.ts:283`）。**機構としては、いま読んでいるのは `nextTaskNumber`（`task-record.ts:108`）が採番のためにディレクトリ名を見る所だけ**
3. **`.gitignore` は `work/tasks` を無視していない**（`data/` `.banto/` `work/attachments/` などは無視している）。**つまり宣言としては「リポジトリの一部」**
4. **Kobo は既に main のチェックアウトで git を書いている**（`packages/banto-daemon/src/merge-queue.ts` が `execFileAsync("git", ...)` で checkout / rebase / merge。D6「git CLI（stdlib の child_process）。新しい依存は足さない」）

## 決めたこと：**(a) Kobo が書いたら Kobo がコミットする**

**なぜ (a) か**（4つ）:

1. **宣言と振る舞いの不一致を、宣言の側へ揃える。** `.gitignore` が無視していない・履歴に手で入れ続けてきた——**意図はずっと (a)** だった。振る舞いだけが追いついていない
2. **(b) は、今日の実害を恒久化する。** task-0160 の職人は**自分の契約（`work/tasks/task-0160.md`）も設計文書も worktree から読めなかった**。未追跡だったからである。(b)（md をリポジトリの外へ）を選ぶと、**職人と監査が契約を git で読めない状態が仕様になる**
3. **新しい危険を持ち込まない。** Kobo は既に main で git を書いている（4）。git を触る主体が増えるのではなく、既に触っている主体に1手足すだけ
4. **この線全体の原則が「書いたら残る」だから。** 番頭は同じ日に `BacklogStore`（起票の置き場）を「書いたら残る」で作っている。**task の md だけ「書いても残らない」に倒すのは筋が通らない**

**やらない方（b）を選ばない理由の補足**：帳簿（EventLog）が真実であることは変わりません。md は**投影**です。投影を捨てるのではなく、**投影が途中で消えるのをやめる**、というのがこの直しです。

## やること

### 1. 記録を書いたら、その場でコミットする

`packages/banto-daemon/src/task-record.ts` が記録ファイルを書く所（新規作成のときも、契約の改訂で書き直すときも）で、**そのリポジトリの `work/tasks/` 配下だけ**をコミットする。

- git は `execFileAsync("git", [...])` で叩く（`merge-queue.ts` に前例がある。**新しい依存を足さない**・D6）
- **`git add` はパスを名指しで**。`git add -A` / `git add .` は使わない
- コミットメッセージは機械が書いたと分かる形で（例：`docs(work): task-0181 の記録を履歴に入れる`）
- git を叩く部分は `packages/banto-daemon/src/task-record-git.ts` に切り出してよい（試験しやすくするため）

### 2. 溜まっている分も同じ機会にまとめて入れる

**1件だけ入れて他を置き去りにしない。** 書いたときに `work/tasks/` 配下の未追跡・変更済みを**まとめて**コミットする。これで46件のような溜まりが、次の起票1本で自力で解消される。

### 3. **他人の作業を壊さないこと**（ここが実装のいちばん難しい所）

Kobo は**マージキューと同じチェックアウト**で git を触ります。**rebase / merge の最中にコミットすると壊します。**

- `.git/rebase-merge` / `.git/rebase-apply` / `MERGE_HEAD` のいずれかが在れば、**コミットせずに見送る**。次に記録を書く機会に入るので、見送っても失われない
- **`git checkout` / `git reset` / `git stash` を絶対に使わない。** できるのは「名指しの `add`」と「名指しの `commit`」だけ
- **`work/tasks/` の外を1つも add しない。** 同じチェックアウトには番頭が書いた起票や、他の未追跡ファイルが在る。それらを巻き込まないこと

### 4. **黙って失敗しないこと**（I2）

- **git が失敗しても起票そのものは落とさない。** 記録ファイルは書けているので、例外を上へ投げて `kobo.enqueue` を失敗させてはいけない
- **ただし黙って捨てない。** 失敗したこと・見送ったことは、後から読める形で残す（帳簿のイベントか、少なくともログ）。「入ったつもりで入っていない」が今回の病気そのものなので、**同じ病気を作らないこと**

## やらないこと

- **`nextTaskNumber`（`task-record.ts:108`）の採番の仕方は変えない。** ディレクトリ名と帳簿の両方を見る形は、**新しく登録したリポジトリに既存の md だけが在る場合に効く**ので、いまは正しい。ここは触らないこと
- `.gitignore` を変えない
- `daemon.ts` を変えない（記録を書く側に閉じる。呼び出し順は既に「記録を書く→`task_created`」になっている）
- `git push` はしない（コミットまで）

## 気をつけること

- **軽く作ること。** 直近のタスクで職人が2回メモリ上限で SIGKILL された（peak 1.6GiB / 2.0GiB）。`daemon.ts`（大きい）や `merge-queue.ts` は**必要な箇所だけ**読む。全文を開かない。`packages/**` を横断する広い grep を繰り返さない
- **長く沈黙しない。** 区切り（git の口を書き終えた／記録の書き手に繋いだ／試験を書き終えた）で報告を挟む

- 溜まっていた分も同じ機会に入る
