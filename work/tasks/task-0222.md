## 背景

task-0216（`210000ce`）で工房に同時本数の栓が入り、上限に達すると工房は
`BANTO_WORKER_LIMIT:<running>/<limit>` の合印つきで**断る**ようになった
（`packages/banto-worker-pool/src/pool.ts` の `WORKER_LIMIT_CODE` / `reserveSlot`）。

**Kobo 側はこれを「中身の失敗」として受け取る。**
`packages/banto-daemon/src/daemon.ts` は職人を起こす3か所すべてで、例外を
`recordTaskFailed(..., taskFailureReason(...))` に落としている:

- 2647 `spawn failed`（実装の職人。`_spawnTaskBody`）
- 3534 `audit session spawn failed`（監査）
- 3787 `rework session spawn failed`（やり直し）

task-0215（`a04c10bb`）で入った `unreachable:` の印は、**`Failed to reach module "..."`
（声が届かなかった）だけ**を拾う設計で、コメントに
「ツール側が返したエラー（HTTP 500）は相手には届いているので中身の失敗であり、ここでは拾わない」
と明記されている。**満杯の断りはまさにその HTTP 500 の側**なので、task-0215 とは噛み合っていない
——**満杯になるほど「中身は無罪なのに failed」が増える**。2026-08-16 は同じ形で7本が巻き添えになった。

**満杯は「あとでもう一度」であって、失敗ではない。**

## やること

**`packages/banto-daemon/src/daemon.ts` だけを触る**（＋試験1本）。

1. **合印で見分ける。** 例外の文言に `BANTO_WORKER_LIMIT` が含まれていたら「工房が混んでいる」と
   判定する関数を daemon 側に置く（`unreachableModuleOf` と同じ流儀で輸出し、帳簿を読む側から
   使えるようにする）。**日本語の言い回しでは判定しないこと**（文言を直した日に黙って壊れる）。
   - 合印の文字列は工房の `WORKER_LIMIT_CODE` が正。daemon から工房のソースを import せず
     文字列で照合してよいが、**試験の側で工房の `WORKER_LIMIT_CODE` を import して同じ値である
     ことを固定する**こと（ずれたら試験が落ちる）。工房が Kobo を読み込まない依存の向き
     （task-0216 の a6）は壊さないこと。
2. **実装の職人（`_spawnTaskBody`）**：満杯で断られたら **`recordTaskFailed` を呼ばない**。
   タスクは `ready` のまま残し、**次の周回で起こし直させる**（4417 付近の巡回は `ready` の
   タスクを毎回拾う。`failed` にすると二度と拾われない、という現在のコメントの裏返し）。
   黙って見送らないこと——「工房が満杯だったので見送った（N/M 本）」をログに残す。
   `spawnTask` は従来どおり投げてよい（呼び出し側は既に握れる形になっている）が、
   **帳簿に `task_failed` を書かない**のが要件。
3. **監査（3534）とやり直し（3787）**：この2つは巡回が拾い直さないので、状態は従来どおり
   `failed` に落としてよい。ただし**理由の先頭に「待てばよい」と読める印**を付ける
   （`unreachable:` と同じ流儀。例 `busy:worker-pool `）。文面には「工房が満杯だっただけで
   中身の失敗ではない・しばらく置いて `kobo.reopen` で動かし直せばよい」ことと、
   そのときの本数／上限を残すこと。元の文言は消さず後ろに残す（I2）。
4. **状態も新しいイベント型も足さないこと**（task-0215 と同じ理由・D9）。区別は理由の側で付ける。
