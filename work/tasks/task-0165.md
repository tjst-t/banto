## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

banto ホスト（systemd unit `banto.service`、`packages/banto-host/src/bin.ts` を tsx で直読み）のプロセスが OOM killer に繰り返し殺されている。**原因は特定済み**で、このタスクはその本命の直しである。

### 確定している事実（機械の記録。推測ではない）

- 2026-08-14 以降のカーネル OOM kill 12 件は**全件 `constraint=CONSTRAINT_MEMCG`**。VM 全体の枯渇（global OOM）は1件も無い。現在も MemAvailable は 7.3 GiB ある。
- banto.service の4回（8/15 13:59:54 / 14:46:40 / 22:56:25 / 8/16 00:48:38）はすべて `oom_memcg=/system.slice/banto.service`、`memory: usage 3145728kB, limit 3145728kB`。**上限 3.00 GiB にきっかり当たっている**（`MemoryMax=3221225472` / `OOMPolicy=stop`）。
- OOM 時のカーネルの Tasks state ダンプで、3 GiB のうち **`claude` の子プロセス 12〜13 本が 2.29〜2.40 GiB（76〜80%）**を占めていた。node 本体は 0.56〜0.66 GiB。**1本あたり anon 189〜200 MiB でほぼ一定。**
- 60秒×10分の採取で、伸びは**階段状**（1本→4本で +637 MB）。プロセス数が変わらない区間は横ばい〜微減。**固定集合の中で漏れている証拠は無い＝本数がすべて。**
- いま開いている会話は **21 本**。全部に一度ずつ発話すれば 21×0.19 GiB ＝ **3.99 GiB** で、node 本体を足さずとも上限を超える。**上限到達は時間ではなく「触った会話の本数」で決まる**（実測の到達時間は 29分／47分／8時間04分とばらばらで、いずれも到達時 12〜13 本）。

### 原因（コードで確認済み。行番号は 2026-08-16 時点）

- `packages/banto-host/src/claude-agent-harness.ts:548` のコメント：「`PromptQueue` は空になっても終わらせない設計なので、**参照を落とすだけでは `query()` が生き続け、往復のたびに Claude Code の子プロセスが積み上がる**」。
- その後始末 `dispose()`（同 :555、**冪等**）の呼び口は6箇所しか無く（`bin.ts:1423 / 1502 / 1688 / 1691`、`server.ts:1217`、`threads.ts:1684-1685`）、**全部がバックエンドの差し替えか、ホスト全体の終了**である。**「しばらく触られていない会話を放す」経路が1つも無い。**
- 一方で**畳んでも会話は失われない**。`resumeToken()`（同 :540 付近）が SDK 側の会話の札を返し、`thread-store.ts:70` のとおりその札は記録に保存されている（決定97・task-0104）。`bin.ts:1422-1426` は現に「前のを dispose して、札を引き継いで作り直す」形になっている。**この材料はすでに揃っている。**

## やること

**アイドルな会話の SDK セッションを畳んで子プロセスを放す。次に発話が来たら札で戻す。**

1. **アイドル安全弁**：最後にその会話が触られてから一定時間（**既定を決めて実装のコメントに根拠を書くこと**。職人側の安全弁が 15 分＝`packages/banto-worker-pool/src/pool.ts` の `DEFAULT_IDLE_TIMEOUT_MS` なので、揃えるなら 15 分。揃えない理由があるなら書くこと）発話が無い会話の harness を `dispose()` する。
2. **戻す**：畳んだ会話に次の発話が来たら、保存してある resume 札で作り直し、**同じ会話の続きとして**続く。文脈も記録も失わない。**畳まれていたことが利用者の目に見える形で会話を乱さないこと**（前置きや断りを勝手に喋らない）。
3. **同時に生かす本数の上限**：生きているセッションの本数に上限を設け、超えたら**最も長く触られていないものから畳む**（LRU）。既定値は根拠つきで決めること——実測は1本あたり anon 約 190 MiB、上限 3.00 GiB、node 本体が 0.56〜0.66 GiB なので、**上限本数×0.19 GiB ＋ 0.7 GiB が 3.00 GiB を超えない**ことが条件。
4. **畳まないもの**：走行中のターン（応答を流している最中）・章を畳んでいる最中（`chapters.ts` の `ChapterKeeper.closing`）の会話は畳まない。**ここを間違えると返事が途中で切れる。**
5. **値は設定で変えられるようにする**（既存の流儀に合わせる。環境変数か `settings-store` のどちらかで、既存の同種の設定と同じ形にすること）。既定値をコードのコメントに明記する。
6. **畳んだ・戻したことが観測できること**（既存のログの流儀 `console.error("[banto] …")` 等に合わせる。いま何本生きているかが分かる形が望ましい）。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- systemd の設定（`MemoryMax` の値そのもの）の変更——別タスク・PO の判断
- 章畳み（chapter close）の条件・`contextTokens` の計測の直し——**別件で調査中**
- 記録の書き込みの原子性・壊れた行の退避（task-0161 / task-0163 で進行中。**`thread-store.ts` を触らないこと**）
- 職人（banto-worker-pool）側の変更
- `/var/lib/banto` 以下の実データへの書き込み・移動・削除。**いま PO の記録の復旧作業が走っている。テストは必ず一時ディレクトリを使うこと。**

## 気をつけること

**これはホストの中枢で、壊すと PO が会話できなくなる。** 既存の会話の起こし方・畳み方（`bin.ts:1400-1550` 付近の harness の組み立てと `harnessSwitchers`）を先に読み切ってから手を入れること。安全弁は「効かなくても壊れない」側に倒す——畳むのに失敗したら例外を握り潰さず記録し、会話は続けられること。
