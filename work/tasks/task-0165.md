## このタスクの目的（PO の言葉・2026-08-16）

> **アイドルな会話は手放す仕組みがあってもいいのでは？ もし再開するときにはプロセスを再開すればいい。
> つまり、banto としての会話の Open/Close と、claude code や Pi のプロセスの生きている・死んでいるは
> デカップリングできるのでは？**

**これがこのタスクの狙いである。**「アイドルなセッションを畳む」は手段であって、
**目的は「論理的な会話の開閉」と「プロセスの生死」を切り離すこと**。

- **会話が開いている**＝PO がその会話を続けられる（記録も文脈も生きている）
- **プロセスが生きている**＝`claude` の子プロセスがメモリを掴んでいる

**いまはこの2つが同じもの**になっていて、**会話を1本触ったら、その `claude` はホストが死ぬまで居座る。**

### 「落として、必要になったら起こす」は既に成立している（根拠）

**再起動のたびに、会話を丸ごと読み戻して続きから話せている**（2026-08-16 だけで3回、実際に起きた）。
**つまりプロセスを落としても会話は続く。** **アイドルの間だけ落とすのは、その延長にすぎない。**
材料も揃っている——`resumeToken()` が SDK 側の会話の札を返し、その札は記録に保存されている
（`thread-store.ts:70`・決定97）。**新しく作る必要があるのは「いつ放すか」と「どう起こし直すか」だけ。**

## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

banto ホスト（systemd unit `banto.service`、`packages/banto-host/src/bin.ts` を tsx で直読み）が
**OOM killer に繰り返し殺されている**（2026-08-15〜16 で5回、8/15 の再起動は12回）。**原因は特定済み**で、
このタスクはその本命の直しである。

### 確定している事実（機械の記録。推測ではない）

- カーネルの OOM kill は**全件 `constraint=CONSTRAINT_MEMCG`**＝**自分の cgroup 上限に当たっている**
  （VM 全体の枯渇ではない。当時 MemAvailable は 7.3 GiB あった）。
- OOM 時のダンプ：3 GiB のうち **`claude` の子プロセス 12〜13本が 2.29〜2.40 GiB（76〜80%）**。
  node 本体は 0.56〜0.66 GiB。**1本あたり anon 189〜200 MiB でほぼ一定。**
- 伸びは**階段状**（1本→4本で +637 MB）。**本数が変わらない区間は横ばい〜微減**
  ＝**固定集合の中で漏れている証拠は無い。本数がすべて。**
- 上流（Claude Agent SDK）側の異常では説明しなくてよい：`/proc/<pid>/smaps_rollup` で
  **1本あたり anon 199〜227 MB**、実行バイナリ（300MB）は file-backed で**複数プロセス間に共有**される。
  **番頭の 2.6〜3.0 GiB は「約200MB × 本数」で説明が付く**——**1本の大きさではなく、本数が減らないことが問題。**
- **開いている会話は 21本。**全部に一度ずつ発話すれば 21×0.19 GiB ＝ **3.99 GiB**。
  **上限到達は時間ではなく「触った会話の本数」で決まる**（実測の到達時間は 29分 / 47分 / 8時間04分と
  ばらばらで、いずれも到達時 12〜13本）。

### なぜ放されないか（コードで確認済み。行番号は 2026-08-16 時点）

- `packages/banto-host/src/claude-agent-harness.ts:548` のコメント：
  「`PromptQueue` は空になっても終わらせない設計なので、**参照を落とすだけでは `query()` が生き続け、
  往復のたびに Claude Code の子プロセスが積み上がる**」。
- `dispose()`（同 :555・**冪等**）の呼び口は6箇所（`bin.ts:1423 / 1502 / 1688 / 1691`、`server.ts:1217`、
  `threads.ts:1684-1685`）で、**実質2つ——バックエンドの差し替えと、ホスト全体の終了**。
  **「しばらく触られていない会話を放す」経路が1つも無い。**
- `bin.ts:1422-1426` は既に「前のを dispose して、札を引き継いで作り直す」形になっている
  ——**この材料をそのまま使える。**

## やること

**会話の開閉と、プロセスの生死を切り離す。**

1. **放す**：しばらく触られていない会話の harness を `dispose()` する。**既定の時間を決めて、根拠を実装の
   コメントに書くこと**（職人側の安全弁が 15 分＝`packages/banto-worker-pool/src/pool.ts` の
   `DEFAULT_IDLE_TIMEOUT_MS`。揃えないなら理由を書く）。
2. **起こし直す**：放した会話に次の発話が来たら、保存してある resume 札で作り直し、
   **同じ会話の続きとして**続く。**文脈も記録も失われないこと**——**ここがこのタスクの唯一の要**である。
   **利用者の目に見える形で会話を乱さない**（前置きや断りを勝手に喋らない）。
3. **同時に生きている本数の上限**：本数に上限を設け、超えたら**最も長く触られていないものから放す**（LRU）。
   **放す仕組みと上限は別物である**——**放せても上限が無ければ、短時間に何本も触った瞬間に同じ壁に当たる。**
   既定値は根拠つきで決めること（**上限本数 × 0.19 GiB ＋ node 本体 0.7 GiB が cgroup の上限を超えない**）。
4. **放さないもの**：走行中のターン（応答を流している最中）・章を畳んでいる最中
   （`chapters.ts` の `ChapterKeeper.closing`）。**ここを間違えると返事が途中で切れる。**
5. **外から分かること**：**放したこと・起こし直したこと・いま何本生きているか**が読めること。
   **黙って放して黙って起き直すと、遅延の原因が誰にも読めなくなる**——
   **今日の教訓：静かに起きることは、静かに壊れることと見分けが付かない。**
6. **再開にかかった時間が測れること**：数字が出れば、**体感が悪いときに「放す条件」を緩める判断材料**になる。
7. **値は設定で変えられるようにする**（既存の流儀に合わせる。既定値はコメントに明記）。

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- systemd の設定・cgroup の値（別タスク。PO の判断）
- 章畳み（chapter close）の条件・`contextTokens` の計測の直し
- 記録の書き込みの原子性・壊れた行の退避（task-0161 / task-0164 / task-0167。**`thread-store.ts` を触らないこと**）
- 職人（banto-worker-pool）側の変更・SDK の版上げ
- `/var/lib/banto` 以下の実データへの書き込み・移動・削除（**テストは必ず一時ディレクトリを使う**）

## 気をつけること

**これはホストの中枢で、壊すと PO が会話できなくなる。** 既存の会話の起こし方・畳み方
（`bin.ts:1400-1550` 付近の harness の組み立てと `harnessSwitchers`）を先に読み切ってから手を入れること。
**安全弁は「効かなくても壊れない」側に倒す**——放すのに失敗したら例外を握り潰さず記録し、会話は続けられること。
