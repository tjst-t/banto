### 「母集団を役の面の絞り込みにも効かせる」について（結論）

**追加の絞りは入れない。** 役の面の選択肢は既に母集団で絞られている——pi の側は
`policy.includes(...)`＝母集団の導出で、工房の `selectableModels()` も同じ。絞られて
いないのは Claude の側だが、**Claude には供給の面が無い**（決定102：認証の状態だけ）ので、
そこを母集団で絞ると**採用する口がどこにも無くなる**（選べない → 採用できない → 永久に選べない）。

したがって形はこうなる：**供給の面を持つバックエンドは母集団で絞り、持たないバックエンドは
名乗ったものを並べて、選んだ時点で採用が立つ**（決定101e「役の面で選べば採用も立つ」）。
「採用」の意味は1つ（この店で使う気があるモデル）に揃った。

### 残す穴（承知のうえ・小さい）

**Claude のモデルは採用を外す口が無い。** `llm.set_policy` と採用チップは `backend: "pi"` 固定
で、pi の供給の面にしか出ていない。したがって Claude 側の母集団は増えるだけになる。
役に割り当てた分（最大でも5件）しか増えず、`unadopt` は割り当て済みを断るので実害は無い。
**口を足すのは、外したい場面が実際に出てから**（いま足すと呼び手のいない引数が増える・D6）。

## 【解決済み】残っていること（a2 が未達・2026-08-13 に自分で確認）

**`a2` 「Claude のモデルにも採用の旗が立つ（症状1が消える）」は満たしていない。**
台帳（`LedgerModelRef`）は `backend` を持てるようになったが、**書く経路が無い**:

```ts
// llm-registry.ts setRole() — この番人がまだ居る
if (backend === undefined || backend === "pi") {
  this.allowUse(provider, model, ...);   // ← pi のときだけ母集団へ入れる
}
```

コメントも「Claude Code のモデルは登録に載らないので、採用の旗を立てる先が無い」のまま。
**入れ物は移したが、症状1そのものは治っていない。**

さらに、母集団が効くのは pi の一覧の絞り込みだけで、**Claude のモデルは母集団に依らず
選べる**（`models()` は pi の供給しか並べない）。つまりいまは「採用」という概念が
バックエンドによって意味が違う。

### やること

- `setRole` の pi 限定の番人を外し、**どのバックエンドのモデルも母集団へ入る**ようにする
- 母集団を**役の面の選択肢の絞り込み**にも効かせる（いまは pi の一覧だけ）
- 供給の面が pi 専用である以上、**Claude のモデルを採用する口をどこに置くか**を決める
  （役の面で選んだら自動で採用、が素直）
