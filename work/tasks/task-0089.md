# 依頼

## 何が起きたか（2026-08-10 実機で踏んだ事実）

banto に PO がブラウザで触れる dev プロファイル（vite dev server を docker で立てる構成）を新設した際、provision が失敗した。

- Environment Pool の provision フロー（`packages/banto-environment-pool/src/pool.ts` の setup 処理）は「**先に compose up、後から setup（npm ci）**」の順で回る
- dev プロファイルは長命の dev server（vite）を起動するので、起動時点で node_modules キャッシュが空だと `vite: not found` → コンテナが **exit 127** で即死する
- setup（npm ci）はその後 `compose run --rm` で実行され完了するが、**既に落ちたコンテナは復帰しない**
- 従来の test プロファイル（sleep infinity で待機するだけ）は起動時に依存が要らないため、この順序でも問題にならなかった——**dev server 系プロファイルを初めて作ったときに発覚した**

## 副次問題（同じ provision フローに潜むもの）

1. **healthcheck の誤判定**: provision の healthcheck は、コンテナが running だった約1秒の窓で `ok: true` を返し「使えます」と誤報告した（実際は起動直後に exit 127 で落ちる）
2. **マーカー書き込みの握りつぶし**: `.banto-primed` マーカー書き込みも `env.run`（＝コンテナ内実行）経由のため、コンテナ死亡後に失敗し、`.catch(() => undefined)` で握りつぶされた（`cache-dir.ts` の契約違反・I2）。次回 provision でも npm ci が再実行される

## いまの暫定回避策

`docker/dev.yaml` の command に `test -d node_modules/.bin/vite || npm ci; npm --prefix packages/banto-web run dev` を前置きして、vite 起動前に node_modules を用意するようにしている。**これはプロファイル側のハック**で、dev server 系プロファイルを使うすべてのプロジェクトが同じ問題に当たる——本体で直すのが本筋。

## 期待する直し方（方向性。実装の詳細は職人に委ねる）

- **setup を compose up の前に完了させる**（順序の入れ替え）、または
- **setup 完了後にコンテナを再起動する**（dev server 系の長命コマンドが落ちた場合に復帰させる）
- マーカー書き込みの失敗を握りつぶさず、エラーとして表面化させる（I2）

## 完了条件

上記 acceptance をすべて満たすこと。特に a1 は「キャッシュが空の状態から provision しても dev server 系コマンドが即死しない」ことを、テストで再現・検証できる形にすること。
