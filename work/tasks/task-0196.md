## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

### 何が起きているか

2026-08-15〜16、**番頭ホスト（`banto.service`）が cgroup の上限に当たって OOM killer に殺され続けている。今日だけで5回**：

| 時刻 | 何が起きたか |
|---|---|
| 8/15 13:59:54 / 14:46:40 / 22:56:25 / 8/16 00:48:38 | いずれも `oom_memcg=/system.slice/banto.service`、`memory: usage 3145728kB, limit 3145728kB`（**3G にきっかり当たっている**） |
| 8/16 **06:34:59** | 同上。`MainThread` と **claude 5本が巻き添えで kill**、06:35:13 に再起動 |

**番頭は平常時 2.6〜3.0 GiB を使う**（会話を触るたびに `claude` の子プロセスが増える構造。詳細は inc-0077）。**3G は、実測のピークより低い上限である。**

### なぜ「一時の上限」では駄目なのか

凌ぎとして `systemctl set-property --runtime banto.service MemoryMax=5G`（工房は 8G）を入れてあったが、
**2026-08-16 06:34:58 に `sudo systemctl daemon-reload` が打たれた1秒後、番頭は 3G に当たって落ちた。**

理由は drop-in の適用順である：

```
$ systemctl show banto.service -p DropInPaths
/run/systemd/system.control/banto.service.d/50-MemoryMax.conf   ← --runtime（5G）が先
/etc/systemd/system/banto.service.d/oom.conf                    ← 恒久（MemoryMax=3G）が後
```

**後に来る `/etc` 側が勝つ。** 設定が読み直された瞬間、一時の 5G は 3G に上書きされる。
**`/run` のファイルは残っているのに効かない**——「ファイルが在る＝効いている」ではない。

**したがって、恒久側（`/etc/systemd/system/<unit>.d/oom.conf` と、その元であるリポジトリの `deploy/*.service`）を直さないかぎり、`--runtime` が消えるたびに再発する。**

## やること

**`deploy/` に書いてある恒久の上限を、実測に合わせて直す。**

1. **`deploy/banto.service`：`MemoryMax=3G` → `MemoryMax=5G`**
2. **`deploy/banto-worker-pool.service`：`MemoryMax=9G` → `MemoryMax=8G`**
3. **`deploy/README.md` の値の表も、同じ値に直す**（片方だけ直すと、次に読む人がどちらを信じるか分からなくなる）
4. **なぜその値なのかを、設定のすぐ横のコメントに残す**（既存のコメントの体裁に合わせる）。**必ず含めること**：
   - **判断の基準**：**「上限が実測ピークより低ければ、当たるのは『時間の問題』ではなく、もう当たっている」**
   - **番頭の実測**：平常 2.6〜3.0 GiB。**3G のままで 2026-08-15〜16 に5回 OOM**（時刻は上の表）
   - **合計の制約**：**5 + 8 + 1 + 1 ＝ 15 GiB ≦ MemTotal 15.6 GiB**。
     **工房を 9G のままにすると 16 GiB になり、MemTotal を超える。**
     **上限は予約ではないので普段は動くが、重なった瞬間に VM ごと死ぬ**（2026-08-14 の global OOM がその形）
   - **恒久側が古いままだと、`--runtime` が消えるたびに再発する**という構造（上記の DropInPaths の順）
5. **「これで足りる」とは書かないこと。** 今日の実測では**工房は 8G でも落ちている**（`memory.events` の `oom_kill` が 116 → 139）。
   **この修正は「もう当たっている状態を解く」ためのもので、根治ではない。**
   **根治は task-0186（検証を袋の外で回し、結果も切り詰める）・task-0165（アイドルな会話のセッションを畳む）・task-0168（同時に走る職人の本数の上限）である**——**この3本を名指しでコメントに書くこと。**

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- **稼働機の設定を変えること。** `/etc/systemd/system/**` の書き換え・`systemctl set-property`・`daemon-reload`・サービスの再起動は**すべて禁止**（root が要り、**PO の操作**である。**このタスクはリポジトリのファイルだけを直す**）
- 他の unit（`banto-daemon` / `banto-environment-pool`）の値の変更（1G のままでよい）
- `packages/**` `tests/**` `docs/**` の変更
- 職人1本ごとの袋（`BANTO_WORKER_MEMORY_MAX=2G`）・`Delegate` まわりの変更

## 完了の確かめ方

**新しいテストファイルは作らない**（`tests/**` はスコープ外）。受け入れ条件は `deploy/` のファイルを直接読む形（`grep`）で機械が確かめる。
