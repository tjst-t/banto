## 実測した事実（2026-08-20 / task-0292）

契約改訂（`kobo.amend`）でスコープが変わると、Kobo は監査を無効にして `implementing` へ戻し、手直しの職人を起こす（`daemon.ts:1673` 付近）。**このとき、前の職人が畳まれていない。**

工房の一覧に、**同じタスクに職人が2人**並んだ。

```
● task-0292:rework  running  sessionId=cc72dda4-...   （改訂後に立った・現役）
● task-0292         running  sessionId=f4b546b9-...   （改訂前の executor・畳まれていない）
```

**両方とも同じワークツリー `/home/ubuntu/worktrees/github.com/tjst-t/banto/task-task-0292` に着いている。**

### 何が起きたか（実害）

1. **番頭の指示が、死んだはずの職人に吸われた。** 番頭は改訂の答え（スコープを広げた旨）を `worker.steer` で渡したが、**届いた先は古い executor** だった。現役の rework は答えを受け取れず、**同じ質問をもう一度出してきた**。**指示が届かない**——今日ほかにも見た「言葉が届かない」型の一種である。
2. **席を二重に食う。** このとき工場の実効同時上限は2で、**その2席を1つのタスクが占め、`ready` が4本まったく着手できなかった**（上限の数え方そのものは別件 task-0295）。
3. **同じワークツリーを2人が同時に編集する。** これは**壊れ方が読めない事故**である。

### 差分は混ざっていなかった（確認済み）

**番頭が自分の目で確かめた。** 作業ツリーは綺麗（未コミットなし）、`task/task-0292` にコミットは1本だけ（`c447215c`）、触っているファイルは `packages/banto-daemon/src/daemon.ts` と `tests/acceptance/kobo-cost-ceiling.spec.ts` の**スコープ内2本のみ**。

**今回はたまたま実害が出なかっただけ**である。2人が同時に同じファイルを書けば、片方の編集がもう片方に上書きされる・中途半端な状態でコミットされる、といった壊れ方が起こり得る。**運に頼らない。**

## やること

**契約改訂で `implementing` へ戻すとき、そのタスクに付いている職人を先に畳む。**

- `daemon.ts:1673` 付近（改訂 → `implementing` へ戻す道）で、**新しい職人を起こす前に** `closeWorkerFor(projectTag, poolTaskId(taskId, role))` を呼ぶこと。**畳む対象は executor / rework / audit のすべて**——どの役が付いていても、契約が変わった時点でその職人は古い契約を握っている。
- **既に同じ形をしている箇所がある**ので、それに揃えること。`spawnAuditSession()`（`daemon.ts:3911-3912`）は監査を起こす前に executor と rework を畳んでいる。**新しい流儀を発明しない。**
- **畳めなかったときに黙って進めないこと**（I2）。畳めなければログに残す。**「畳んだつもり」で2人目を起こすのがいちばん悪い。**
- **同じ穴が他の遷移にも無いか確かめること。** 「職人が付いたまま状態を戻す／進める」道がほかにもあるなら、そこも同じ扱いにする（`kobo.send_back` / `kobo.reopen` の道など）。**見つけたら直すか、直さない理由を書くこと。**

## 番頭が畳めないのは正しい（変えないこと）

番頭が `worker.stop` を撃ったら、機構はこう断った。

> Kobo が起こした職人は Kobo が畳みます——Kobo の職人を畳むと、Kobo は動いているつもりのまま実体が消えます。

**この断りは正しい。** 番頭に畳ませる方向で解決しないこと。**畳む責任は起こした側（Kobo）にある。**

## 確かめ方

一式は袋の中で叩かないこと。手元では `npm run test:one tests/acceptance/kobo-worker-integration.spec.ts` に留めること。マージ前ゲートが検証環境で回す。
