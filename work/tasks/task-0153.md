## 背景

task-0152（c7ebce88）で記録 id の重複は解消したが、**決定番号（「決定NNN」）の層に重複が残っている**。task-0152 の職人が残懸念として自己申告し、番頭も差分で確認した。

いま `docs/adr/**` の見出し（`### 決定NNN:`）を全部拾うと、こうなっている：

- `adr-0023-po-approval-is-separated-by-route-not-by-secret.md` … **決定113**（1本）
- `adr-0026-one-entrance-contract-from-the-tool.md` … **決定113〜123**（11本）
- `adr-0025-notices-do-not-wake-the-trunk.md` … **決定120〜126**（7本）

つまり **113 が adr-0023 と adr-0026 で衝突し、120〜123 が adr-0025 と adr-0026 で衝突している**。原因は id 衝突と同じで、3本の ADR が別々の枝で並走して書かれ、どれも「決定112（ADR-0022）の続きから採る」と書いたため。

## どちらを動かすか（判断の根拠——調べ直さなくてよいが、確かめること）

番頭が `docs/adr/` の外を全部 grep して確かめた事実：

- **決定113 を外から参照している 10箇所以上は、すべて adr-0023（合言葉ではなく経路／PO 承認）を指している**。`packages/banto-daemon/src/http-server.ts` `daemon.ts` `index.ts`、`packages/banto-core/src/events.ts`、`packages/banto-host/src/bin.ts` `kobo-po-decision.ts`、`packages/banto-web/src/views/KoboReview.tsx`、`docs/adr/adr-0013-kobo-uses-modules.md`、`tests/acceptance/kobo-po-approve-from-ui.spec.ts` `kobo-po-approve-from-inbox.spec.ts`
- **決定120〜126 を外から参照している箇所は、すべて adr-0025（知らせは幹のターンを起こさない）を指している**。`packages/banto-host/src/remaining-whereabouts.ts` `bin.ts`、`packages/banto-host/skills/trunk-and-branch/SKILL.md`、`work/inbox/improvement/imp-0036-*.md`、`tests/acceptance/branch-remaining-whereabouts.spec.ts`
- **adr-0026 の決定番号を、adr-0026 自身の外から参照している箇所は1つも無い**（adr-0026 の中の実装対応表が自分の決定番号を引いているだけ）

したがって **動かすのは adr-0026 だけ**でよく、そうすれば `packages/**` は1行も触らずに済む。これは task-0152 で「参照の所在で残す側を決めた」のと同じ判断のしかたである。

## やること

### 1. adr-0026 の決定番号を振り直す

`docs/adr/adr-0026-one-entrance-contract-from-the-tool.md` の中だけで、**決定113〜123 を 決定127〜137 へ、順序を保ったまま +14 で移す**（113→127, 114→128, … 123→137）。127 から始めるのは、いま使われている最大の決定番号が adr-0025 の 126 だから——**着手時に `docs/adr/**` の `### 決定NNN` を全部拾い直して最大値が 126 であることを確かめ、127 より大きい番号が既に使われていたら空いている先頭から11本の連番へずらすこと**（その場合は何番にしたかを報告に書く）。

直すのは見出しだけではない。**adr-0026 の本文・実装対応表・移行表の中で自分の決定番号を引いている箇所も全部追随させる**こと（例: 実装対応表の「削除（決定113）」「削除（決定113・118）」「（決定123）」「（決定120）」）。

**冒頭の「決定番号は 112（ADR-0022）の続きから採る」という記述も直す**——実際に採る番号が変わるので、そのまま残すと同じ衝突をもう一度起こす。

### 2. 決定の中身は変えない

番号だけを移す。決定の文言・順序・意味は1文字も変えないこと。**adr-0023 と adr-0025 は触らない。**

### 3. 再発を機械で落とす

`tests/acceptance/` に検査を1本置く。task-0152 が置いた `tests/acceptance/record-id-uniqueness.spec.ts` と**同じ作り方に揃えること**（あれを読んでから書く）：

- `docs/adr/**/*.md` を走査し、`^### 決定NNN` 形式の見出しから決定番号を拾う
- **同じ決定番号を2つ以上の ADR が名乗っていたら落とす**。落ちたときのメッセージには「どの番号が、どのファイルとどのファイルで衝突しているか」を出す
- `### 決定105〜108:` のような**範囲見出しも1つ残らず拾う**（拾えない形式は落とすのではなく一覧に出す。取りこぼして緑になるのがいちばん悪い）
- **走査の空振りで緑にならないよう、「決定番号が50件以上拾えていること」を先に検査する**（record-id-uniqueness.spec.ts が 100件でやっているのと同じ趣旨）
- 欠番は落とさない（起票して消した跡かもしれない）

### 4. わざと落ちることを確かめる

置いた検査が、衝突を作ったときに**実際に落ちる**ことを自分の目で確かめてから消すこと（task-0152 の職人がやったのと同じ）。「通った」だけでは、走査が空振りしていないことの証明にならない。
