## 背景

task-0312 の実測で、職人（sonnet）側は34時間で $121、うち cache read が $84。
72セッションを数えると**中央値は健全**で、費用は裾に集中していた:

| | 値 |
|---|---|
| セッション数 | 72 |
| ターン数 中央値 | 31 |
| 到達した文脈長 中央値 | 8万トークン |
| 最長の1本（task-0287） | 302ターン・40万トークン・cache read $13.9 |

## PO 裁定（2026-08-20）

選択肢を出して「**まず可視化だけ**」を選んでもらった。

**打ち切りはしない。** 途中で切られた仕事はやり直しになり、かえって高く付きうる
——ここは本物のトレードオフなので、上限を入れるかどうかは
「どのタスクが伸びるのか」が数えられるようになってから決める（P6「根拠は計測」）。

## 直し方

`ContextWatch` を新設し、`host.ts` の SDK ストリームの assistant 分岐で
`message.message.usage` を読ませる。刻み（既定20万トークン）を越えるたびに
**1回だけ**標準エラーへ出す——毎ターン出すと journal が埋まって、かえって気づけない。

職人の標準エラーは `claude-agent-driver.ts` が工房の標準エラーへ素通しするので、
`journalctl -u banto-worker-pool` に出る（番頭ホストの `章判定` と同じ口）。

`host.ts` ではなく別ファイルに置いたのは、あちらが `main()` を即実行する入口で
**試験から import できない**ため。判定そのものは純粋なので、分ければ直に確かめられる。
`env` と `write` は差し替え可能にしてあり、試験がグローバルを触らずに済む。

- 番頭の画面への表示：まず journal で数える。刻みが妥当かも分かっていないので、
  先に出し先を増やすと「うるさいだけの知らせ」を作りかねない
