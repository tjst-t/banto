## 何が壊れているか（実測・調べ直さなくてよい）

PO のレビュー用環境（`dev` プロファイル・判断待ちの札に出る URL）は、**web だけをブランチのビルドに差し替え、ホストは本番の banto を見ている**。

- `docker/dev.yaml` の web サービスは `BANTO_HOST_URL: http://host.docker.internal:4100` を持ち、`extra_hosts: host.docker.internal:host-gateway` でホストの本番 banto（:4100）へ抜けている。
- vite（`packages/banto-web/vite.config.ts`）は `/ws` と `/api` を `BANTO_HOST_URL` へ中継するだけなので、**画面に映る中身は本番（main）のホストの応答**である。
- マウントされているのはワークツリーと node_modules 置き場と `.git` だけ。ブランチのホストはどこにも立っていない。

**結果として、`packages/banto-host` を触るタスクは PO レビューで原理的に確認できない。** 実害が出た：task-0279（発言に時刻を持たせる）で PO が2回「直っていない」と差し戻し、職人が2回「もう直っている」と返す往復が起きた。実装は正しく、レビュー環境が新しいホストを見ていなかっただけ。同じ事故はホスト側を触る全タスクで再発する。

## 直す形

**`dev` の compose にブランチの banto-host を1つ足し、web はそれだけを見る。**

1. `docker/dev.yaml` にホストのサービス（例 `host`）を足す。
   - 土台・マウントは web と同じ（`..:/app` と node_modules 置き場、`.git` の read-only）。
   - `command` は `node --import tsx packages/banto-host/src/bin.ts serve --port 4100` 相当。**マウントされたワークツリーの実装が動くこと**が要点。
   - `environment` に **`BANTO_DATA_DIR` をコンテナ内の使い捨てパス**（例 `/tmp/banto-review-data`）で渡す。
   - **`ports` を書かない**。ホスト側へは publish せず、compose のネットワーク内だけで web から届けばよい（別ポートを取り合わない・本番の 4100 に近寄らない）。
   - `BANTO_WORKER_POOL_URL` / `BANTO_ENV_POOL_URL` は**到達しない先**（既存の試験と同じ `http://127.0.0.1:1/api/...` の書き方でよい）を与える。レビュー環境のホストが本物の工房・環境プールを動かせないようにするため。
2. web は `BANTO_HOST_URL: http://host:4100` を見るようにし、**`host.docker.internal` の綴りと `extra_hosts` の host-gateway を web から外す**。抜け道を残さない。
3. `depends_on` などで、web が立つときにホストも立つようにする。
4. `meta/environments.yaml` の `dev` の注記を、この形に合わせて直す（cache の鍵に `docker/dev.yaml` が入っているので、compose を変えれば置き場は自動的に切り替わる。鍵の定義は変えなくてよい）。

### 絶対に踏んではいけない線

- **本番の 4100 と本番のデータ置き場（`/var/lib/banto` 配下）には一切触れない。** マウントもしない、環境変数で指さない。ここを踏むと PO の会話が壊れる。
- **ホスト側のポートを固定しない。** 判断待ちが2本並ぶと同じプロファイルで2つ立つ。web の `ports` は今のまま `- "4200"`（コンテナ側だけ）にしておくこと。新しいホストのサービスは publish しないので、そもそも衝突しない。
- **`test` / `test-docker` プロファイルには触らない。** 検証用と実行環境用を兼ねさせない分離（PO裁定 2026-08-11・案B）は維持する。
- compose の `command` に**走り終わるコマンドを書かない**（環境が数十秒で消える。SKILL environment-profiles の「サービスは常駐させる」）。

### 「本当にブランチのホストを映しているか」を機械で確かめる

「立ち上がること」だけでは今回の欠陥は防げない。**映っているホストの同一性**を見る。

- `packages/banto-host/src/server.ts` に `GET /api/instance` を足す。返すのは `{ instanceId, dataDir, startedAt }` 程度でよい。`instanceId` は**起動ごとに変わる値**（乱数の UUID など）。`/api` は vite が中継しているので、**web の公開URL越しにそのまま届く**（`/health` は中継されていないので、そちらは使わないこと）。
- 構造の試験 `tests/acceptance/review-env-shows-branch-host.spec.ts`（docker 不要・`npm test` で回る）で、受け入れ基準 a1・a2・a3 を YAML と package.json を読んで確かめる。
- 生きた試験 `tests/acceptance/env-docker-dev-branch-host.spec.ts`（docker が要る。名前が `env-docker-` で始まるので `npm test` からは自動的に外れる）で、**dev の compose を実際に立てて**
  1. compose 内のホストコンテナが名乗る `instanceId` を取り、
  2. **公開された web のポート越しに `/api/instance` を取り**、
  3. 2つが一致することを確かめる。
  一致しなければ、web は別のホスト（＝本番）を映している。片付けは既存の docker 試験と同じく `after` で必ず行う（I3）。
  この試験を `package.json` の `test:docker` の一覧に足す。
  既存の docker 試験（`tests/acceptance/env-docker-published-port.spec.ts` など）が、ドライバを直に呼んで compose を立てる書き方の手本になる。**立てるときは node_modules の用意（`npm ci`）が要る**ことに注意——プールは provision の前に `setup` を済ませるが、ドライバを直に呼ぶ試験では自分で面倒を見る必要がある。素直に運べないなら、fixture の compose ではなく**本物の `docker/dev.yaml`** を使うこと（この試験が守りたいのは本物の定義である）。

## やらないこと

- 常駐サービスの起こし直しはしない（反映は番頭がまとめて行う）。
- レビュー環境のホストに PO の会話を持ち込む仕掛け（本番データの複製・モデル設定の引き継ぎ）は**今回は作らない**。データ置き場は素のまま。PO はレビュー環境で新しく会話を作って触る。
- `packages/banto-web/vite.config.ts` は変えない（`/api` は既に中継されている）。

## 見届け方

着地の前に、番頭が実機で `dev` を立てて公開URL越しの `/api/instance` を確かめる。だから**「立つはず」で終わらせず、compose の定義が実際に立つ形になっていること**を確かめて出すこと。
