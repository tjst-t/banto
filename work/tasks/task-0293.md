## 背景（番頭が確かめた事実）

環境プールの照合（`Pool.reconcile()`、packages/banto-environment-pool/src/pool.ts:658）が返す「台帳に無い実リソース＝Banto 以外が作ったかもしれないもの」という判定に、**2つの取りこぼし**がある。どちらも同じ突き合わせのコードが原因で、実害も同じ——片付けるものが無いのに `env_orphans_found` が鳴り、誤った前提の知らせが繰り返し番頭を起こす。

### 取りこぼし① 畳み済みエントリを見ていない

```ts
const known = new Set(this.ledger.listLive().map((e) => identity(e.handle)));
```

`EnvLedger.listLive()`（packages/banto-environment-pool/src/env-ledger.ts:233）は `tornDownAt` が付いたエントリを落とす。つまり **Banto 自身が作り、台帳にも載っていて、既に畳んだ印が付いている環境**の実体がまだドライバから見えている間（畳みの実行中・畳み損ね）、その実体は `known` に入らず「台帳に無い」と判定される。

実際に起きていること:
- 2026-08-20T06:19:27Z `env_orphans_found`（`env-19218aaa52-env` / process）。その後 `env.list` の orphans は 0 件で、片付ける対象は残っていなかった。
- 同じ形が 2026-08-17T15:34（`banto-env-env-78964eb0ef`）、2026-08-20T04:47（`env-642e6aeb52-env`）にも出ている。
- 名前の形 `env-<envId>-env` は **Banto 自身の命名規約**（imp-0033 / commit a12f2c66「検証環境の名前を envId ごとに分ける」）であり、外部が作ったものではない。

### 取りこぼし② 照合の走行中に立った環境（TOCTOU）

`reconcile()` は **先頭で台帳のスナップショット（`known`）を取り、そのあとで**各ドライバの `list` を子プロセスで呼ぶ。一方 `provision` は「ドライバが資源を作る（＝資源の名前を state に書き、プロセスを起こす）→ 返ってから `ledger.add`」の順（pool.ts:866〜）。

したがって **照合が走っている最中に立った環境は、実体はドライバの `list` に映るのに、スナップショットには載っていない**——必ず「台帳に無い＝他人のリソース」と判定される。

実測（2026-08-20、台帳の createdAt と孤児の知らせの時刻）:
- `env-19218aaa52` — 台帳 createdAt `06:19:25.543` / 孤児の知らせ `06:19:27.111`（1.6 秒差）
- `env-642e6aeb52` — 台帳 createdAt `04:47:25.299` / 孤児の知らせ `04:47:25.956`（0.7 秒差）

どちらも adhoc:process として台帳に正しく載っている、Banto 自身の環境である。

## やること

1. `reconcile()` の突き合わせを **台帳の全エントリ（`ledger.list()`、畳み済みを含む）** に対して行う（取りこぼし①）。
2. **ドライバの `list` が返ったあとに台帳を取り直し、`found` を突き合わせ直す**（取りこぼし②）。照合の走行中に `ledger.add` されたエントリが孤児に落ちないようにする。取り直しでも拾えない隙間が残るなら、**作られてから間もない実体（例: 直近 60 秒以内）は孤児にしない**という保険を併せて入れてよい。どちらの方針で直したかをコードのコメントに1行残すこと。
3. 実リソースを3つに分ける:
   - **生きているエントリに一致** → これまでどおり何も言わない。
   - **畳み済みのエントリに一致** → 孤児ではない。「畳み損ね（Banto のものだが実体が残っている）」として扱い、`env_orphans_found` には**含めない**。既存の畳み損ね系の扱いに合流させるか、既存に無ければ別の出来事種別（例 `env_teardown_incomplete`）を event-log.ts に足して、そちらで記録する。**「Banto 以外が作ったかもしれない」という文面は使わないこと**（台帳に載っている以上、持ち主は分かっている）。
   - **台帳のどのエントリにも一致しない** → これまでどおり孤児として `env_orphans_found` で報告する。
4. 畳み済みエントリに一致した実体は `env.list` の `orphans` にも出さない（`env.teardown_orphan` の対象一覧を汚さない）。ただし `Pool` の内部で握り潰さず、上の3で記録は残すこと。
5. 一度きりの通知の抑制（`this.notified`）の鍵の作り方は変えなくてよいが、種別を分けたことで「同じ実体が孤児→畳み損ねと二重に鳴る」ことが無いか確かめること。

## やらないこと

- **孤児を機構が自動で消す口は作らない。** 一括で畳む口を作らないという PO 裁定（2026-08-08、pool.ts のコメントに残っている）はそのまま。
- 畳み損ねに分類された実体を勝手に畳まない。分類と記録の直しだけ。
- ドライバ（process-driver.ts / docker-driver.ts）の `list` の実装は変えない。
- **`provision` の順序は変えない**（先に台帳へ書いてからドライバを呼ぶ、という作り替えはしない）。直すのは照合側だけ。

## テスト

**新しいファイルは作らず、`tests/acceptance/env-orphan-ownership.spec.ts` に追記する**（スコープを広げないため）:

- 台帳に **畳み済み** エントリがあり、ドライバの `list` が同じ handle を返す状況で、`env_orphans_found` が出ない（孤児 0 件）こと。
- 台帳の **どのエントリにも無い** handle をドライバが返したら、これまでどおり孤児として報告されること。
- 生きているエントリに一致する handle は孤児にならないこと（既存の担保が壊れていないこと）。
- **照合の走行中に provision された環境が孤児にならないこと**（取りこぼし② / 受け入れ条件 a5）。時間の擬装で再現できる: ドライバの `list` を、呼ばれたときに**まず台帳へ新しいエントリを足してから**（＝照合の最中に provision が完了した状況を作ってから）その handle を含む一覧を返す差し替え実装にする。この handle が `env_orphans_found` にも `env.list` の orphans にも出ないことを確かめる。
