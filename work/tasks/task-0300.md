## 背景（あなたは記憶を持たないので全部ここに書きます）

`system.deploy` は main のチェックアウトに対して `npm test` を回し、**通ったときだけ** `banto.service` を起こし直す仕組みです。実装は `packages/banto-host/src/deploy-verify.ts`。

2026-08-20 08:15:34 に実際にデプロイが拒否されました。ところが番頭に返ってきた「落ちた箇所」は、こういう行ばかりでした：

```
[banto] module "environment-pool" への接続に失敗（connect、1回目）。50ms後に再試行します: Error: connect ECONNREFUSED 127.0.0.1:1
[banto-daemon] 検証環境の写しを取り直せませんでした: Failed to reach module "environment-pool" at http://127.0.0.1:1/...
```

`127.0.0.1:1` は `package.json` の `test` スクリプトが**わざと**差している到達不能アドレスで（environment-pool 不在時の経路を試験している）、失敗の原因ではありません。**実際にどの spec が落ちたのかは、いまも分かっていません**——生ログがどこにも保存されていないためです。

## 原因（実測で特定済み。あなたは調べ直さなくてよい）

`packages/banto-host/src/deploy-verify.ts` に3つの欠陥があります。

1. **正規表現が広すぎる**
   ```ts
   const FAILURE_MARKERS =
     /(fail [0-9]+|# fail|not ok|✗|FAILED|AssertionError|Error:|npm ERR!|failing tests?)/i;
   ```
   素の `Error:` が入っているため、上のノイズ行が全部ヒットします。さらに `i` フラグのため、**通過した試験の名前に "error:" が含まれているだけで誤ヒットします**（実例: `✔ [AC-S654396-3-1] ... error: not_found`）。

2. **先頭30件で打ち切っている**
   ```ts
   const hit = lines.filter((line) => FAILURE_MARKERS.test(line.trim())).slice(0, 30);
   ```
   ノイズは出力の早い段階から数百件出るので、**本物の `not ok` / `AssertionError` が出力の後方にあると、先頭30件がノイズで埋まって報告に一切出ません**。今回の症状そのものです。

3. **生ログを捨てている**
   `runDeployVerify` は `e.stdout` / `e.stderr` を `extractFailures` に通した要約しか返さず、生の出力はどこにも永続化されません（`record` は `console.log` で journal に出るだけ）。今回の失敗ログは既に失われ、事後の切り分けが不可能になりました。

## やること

`packages/banto-host/src/deploy-verify.ts` を次のように直します。

### (1) 失敗行の判定を締める
- `FAILURE_MARKERS` から**素の `Error:` を外す**。`not ok` / `# fail` / `fail [0-9]+` / `AssertionError` / `FAILED` / `npm ERR!` / `failing tests?` / `✗` で実失敗は十分拾えます。
- **合格行を除外する**：`✔` で始まる行、`ok ` で始まる TAP 行は、何が書いてあっても失敗行とみなさない。
- **既知ノイズを除外する**：`ECONNREFUSED 127.0.0.1:1` を含む行、`module "` + `への接続に失敗` の行、`Failed to reach module` の行、`verify_env_unavailable` を含む行。除外は**関数に切り出して名前を付ける**こと（`isKnownNoise` 等）——将来ノイズが増えたときに足す場所が一目で分かるように。
- 大文字小文字の扱い：`i` フラグを外し、必要なマーカーだけ明示的に大小両方書く方が誤検知が減ります(判断は任せます)。

### (2) キャップの当て方を直す
- 上限（30件）は**ノイズを除いたあと**に掛ける。
- 上限で打ち切ったときは、報告に「他に N 件」と件数を出す（消したことが分かるように）。

### (3) 生ログを必ず残す
- 検証が**落ちたとき**、`stdout` と `stderr` を連結した全文をファイルへ保存する。
- 置き場所は `process.env.BANTO_DATA_DIR ?? "/var/lib/banto"` の下の `deploy-verify/` に、`deploy-verify-<ISO8601 の : を - に置換>.log` の名前で。ディレクトリは `mkdir -p` 相当で作る。
- 保存したパスを `report` の末尾に必ず載せる（例: `生ログ: /var/lib/banto/deploy-verify/deploy-verify-2026-08-20T08-15-34.123Z.log`）。
- **保存に失敗しても検証結果は返すこと**（ログが書けないことでデプロイ判定が壊れてはいけない）。握り潰さず、報告に「生ログの保存に失敗: <理由>」と1行足す。
- 保存先は `runDeployVerify` の引数で差し替えられるようにする（第3引数の任意オプションなど）。**テストが実ディレクトリを汚さずに済む形にすること**。既定値は関数の中で決め、`bin.ts` 側の呼び出しは変えなくても動くようにしてください（`bin.ts` はこのタスクのスコープ外です）。

## やらないこと

- `runDeployVerify` の cwd を使い捨て worktree にする案は**このタスクではやらない**（別途 PO 判断）。
- `bin.ts` / `deploy-gate.ts` の呼び出し側は触らない。
- 間欠故障そのものの原因追及はしない（このタスクは「次に落ちたとき現物を掴めるようにする」ための機構の直しです）。

## テスト

新規 `tests/acceptance/deploy-verify-failure-extraction.spec.ts` を書いてください。既存の `tests/acceptance/kobo-deploy-gate.spec.ts` の書き方に倣うこと。少なくとも次を覆います。

- ノイズ行だけを含む出力から、失敗行が**1件も**抽出されないこと（`✔ ... error: not_found` の行、`Error: connect ECONNREFUSED 127.0.0.1:1` の行を入れる）。
- ノイズ行を数百行並べたあとに `not ok 2 - some spec` を1行置いた出力から、**その `not ok` 行が報告に出る**こと（＝先頭キャップで消えない）。
- 失敗時に生ログが指定ディレクトリへ書かれ、そのパスが report に載ること。
- 生ログの保存に失敗しても `passed: false` の判定自体は返ること。
