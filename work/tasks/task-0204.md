## 背景（前提。あなたは記憶を持たないので、ここに書いてあることが全部）

### 何が起きているか（2026-08-16・複数プロジェクトで実測）

**工房（`banto-worker-pool.service`）が職人を起こせないことがある。**2つの形で出ている。

```
① Module "worker-pool" tool "worker.delegate" failed (500):
   Failed to start worker for "...": [claude-agent] ホストが 10000ms 以内に応答しませんでした。
② rework session spawn failed: Failed to reach module "worker-pool" at
   http://127.0.0.1:4300/api/worker-pool/tools/worker.delegate_toolkit: Error: read ECONNRESET
```

**いま立っている筋は2本ある。どちらか一方に決めつけないこと。**

- **(A) 既存セッションの「再開」が即死する。**
  dentaku の task-0042 で**計5回**。`kobo.reopen` の rework で**落ちた職人のセッションを起こし直すときだけ**落ちる。
  直前に `agent_exited_without_report`（再開した職人が報告せず即終了。そのセッションの peak は 855.6MiB）があり、
  工房の journal には同時刻に **`[claude-agent] turn_ended failed: TypeError: fetch failed`** が1件。
  **結果、そのタスクでは rework が永久に通らなくなる**——`reverify` は監査の実績が要り、`approve` は review-ready でないと使えないので、**袋小路**。**証拠は強い。**
- **(B) 新規の起動が時々10秒に間に合わない。**
  banto 側で複数回（**過去のセッションを持たない新しい職人**でも timeout している）。
  **原因は未特定。**

### **否定された見立て（大事なので残す）**

番頭は当初「**工房が 8 GiB の 82%・`oom_kill` 144 だから、混んでいて10秒に間に合わない**」と見ていた。
**dentaku 側の実測がこれを否定した**：

- `free -m` は 15993 中 **available 6176**、`/proc/pressure/memory` は **avg 全て 0.00**、`dmesg` に OOM も killed process も**無し**
- **工房は落ちていない**：`NRestarts=1` / `ExecMainStartTimestamp=2026-08-15 06:26:17`＝**今日は一度も入れ替わっていない**
- **失敗の合間（08:39）に、新しい職人が普通に起動して仕事をして報告している**

**＝ メモリ逼迫では説明が付かない。(B) の原因は分かっていない。**

### いまの作り（現物・行番号は 2026-08-16 時点）

`packages/banto-worker-pool/src/claude-agent-driver.ts`

```ts
:48  const INJECT_TIMEOUT_MS = 10_000;   // inject の応答を待つ上限
:51  const START_TIMEOUT_MS  = 10_000;   // 起動直後の状態問い合わせに答えが返るまでの待ち
:325 proc.stdin?.write(JSON.stringify({ type: "get_state" }) + "\n", …)
:330 const timer = setTimeout(() => {
:332   settle({ ok:false, error: `[claude-agent] ホストが ${START_TIMEOUT_MS}ms 以内に応答しませんでした。` });
:334 }, START_TIMEOUT_MS);
:340 if (!start.ok) { proc.kill("SIGKILL"); … }
```

工房は職人1本ごとに子プロセスを起こし、`get_state` を書いて名乗りを待つ。**10秒で返らなければ失敗にして SIGKILL する。**
**この10秒は固定値で、環境変数でも設定でも変えられない。**
既存セッションを続けるときは、この起動に **`--resume <sessionId>`** が付く（`claude-agent/host.ts` が受け取る）。

## やること

### 1. 待ちを設定で変えられるようにする

`START_TIMEOUT_MS` と `INJECT_TIMEOUT_MS` を**環境変数で上書きできる**ようにする
（既存の流儀に合わせる。`BANTO_WORKER_MEMORY_MAX` / `BANTO_WORKER_IDLE_MS` が参考）。
**既定値は変えても変えなくてもよいが、選んだ理由をコメントに書くこと。**

### 2. 起動の名乗りが返らなければ、1回だけ起こし直す

- **やり直すのは「起動」だけ**（`get_state` の名乗り待ち）。**まだ職人に何の指示も渡していない段階なので、
  起こし直しても二重に仕事が走らない。**
- **`inject`（指示の差し込み）は再試行しないこと。**同じ指示が二度届くと、職人が同じ作業を2回する。
- 起こし直す前に、**失敗した子プロセスを確実に始末する**（孤児を残さない）。

### 3. **再開が駄目なときの退路を作る（追加）**

**`--resume` 付きの起動が失敗したら、`--resume` を外して新しいセッションとして起こし直すこと。**

- **いまは袋小路になる**：再開が失敗し続けると `rework` が永久に通らず、`reverify` も `approve` も使えない
  （dentaku の task-0042 で実際に起きた）。**仕事が止まる方が、会話の続きを失うより高くつく。**
- **退路を通ったことは、必ず記録に残すこと**（下記4）。**黙って新しいセッションにすると、
  職人が前の文脈を持っていないことに誰も気づけない。**
- **この退路は `claude-agent-driver.ts` の中で完結させること。**`claude-agent/host.ts` は**スコープ外**（触らない）。

### 4. **失敗と再試行が、次の切り分けに使える形で記録に残る（追加）**

- **何回目で起きたか／何回試して駄目だったか**
- **再開だったのか、新規だったのか**（`--resume` の有無）
- **退路（新しいセッションで起こし直し）を通ったかどうか**
- **切り分けの材料**：**再開しようとしたセッションの大きさ**（jsonl のバイト数など、**その場で安く取れるもの**）。
  **「大きすぎると再開できない」という仮説はまだ確かめられていない**——**条件として書かないこと。
  次に確かめられるように、数字を記録に残すだけでよい。**

## やらないこと（スコープ外。触ったらマージ前ゲートで落ちる）

- **子の起動を軽くする（tsx の直読みをやめて事前ビルド）**——効くが重く、常駐サービス3つの起こし方が変わる。**別の判断。**
- モジュール呼び出しの接続段の再試行（`ECONNRESET`）——**task-0190 の担当。別の層である。**
- `claude-agent/host.ts` / `pool.ts` / `banto-daemon` / `banto-host` の変更
- cgroup・systemd の設定・袋の大きさ・同時本数の上限（task-0168）

## 気をつけること

- **「起こせなかった」を握り潰さないこと**（I2）。再試行しても駄目なら、**いままでと同じ形で失敗を返す**。
- **(A) と (B) は別の原因かもしれない。** このタスクは**どちらにも効く手当て**（待ちを可変に・1回だけ再試行・退路・記録）であって、
  **原因の特定ではない。**「これで直った」と書かないこと。
- **待ちを延ばすだけでは、遅さそのものは直らない。** これは**時間を買う手当て**である。
