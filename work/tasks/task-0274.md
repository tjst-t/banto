## 背景（PO 裁定 2026-08-17）
「マージゲートは修正したところだけにして、デプロイゲートで回帰テストしてください。仕組化してください（AI の心がけではなく機構で）」
- 実測: banto のフル npm test は5〜6分（2700超テスト・docker 環境を立てる acceptance が重い）。マージキューは直列なのでタスクごとに全回帰を払うと累積で待ちが大きい。
- banto の構造: サービスは main の .ts を直読みし、**再起動で反映**される（デプロイ = 起こし直し）。マージ ≠ 反映なので、フル回帰は起こし直しの前に1回走らせれば足りる。
- つまり2段構え: (1) マージ前ゲート = 変更対象 spec + typecheck のみ、(2) デプロイゲート = 起こし直しの直前に main に対して npm test 一斉、pass したときだけ再起動。

## やること

### 1. マージ前ゲートの限定（banto プロジェクト）
- マージ前ゲートがフル npm test を走らせない仕組にする。ゲート定義（banto-daemon 側）を読み、acceptance の verify がフルスイート相当（npm test / test:all 等）を含むときは**明示的な警告**か**PO 承認**を要求する（またはゲート自体が変更対象 spec と typecheck に限定される設定へ）。
- 既存タスクの acceptance で npm test を verify に持つもの（例: 過去の a1）は、この仕組に合わせて扱いを整理する（変更不要ならそのまま、警告の対象にならない形に）。

### 2. デプロイゲート付き再起動の仕組化（packages/banto-host）
- 再起動（デプロイ）の口を新設または拡張する（例: `system.deploy` 相当の工具）。動作は:
  1. 対象 main に対して env.verify（npm test 一式）を実行
  2. pass → 指定ユニット（banto.service / banto-daemon.service / banto-worker-pool.service / banto-environment-pool.service の計画的再起動）を起こし直す
  3. fail → **拒否**し、失敗内容（落ちた spec）を報告する
- **強制フラグ**（例: force）で明示的にのみゲートを迂回できる。強制したことは記録（ログ・台帳）に残る。
- **クラッシュ復旧は対象外**: Restart=on-failure による自動再起動はデプロイではなく、テストしてから起こすことはできないので、ゲートを通さない（従来どおり即復旧）。計画的デプロイだけがゲートを通る——この区別を設計の中心に置く。
- 既存の `system.restart`（素通し）との関係を整理する: デプロイ時の正式な口はゲート付きにする（素通しは緊急/強制のみ、明示的に）。
- 現状の手順（safe-restart SKILL）の表に **banto-daemon.service（ExecStart: node --import tsx packages/banto-daemon/src/index.ts）が欠けている**——4ユニット構成に更新する。

### 3. テスト
- 新設 tests/acceptance/kobo-deploy-gate.spec.ts: ゲートが npm test 失敗で再起動を拒否する／pass で通る／強制フラグで明示的に通る（記録あり）／クラッシュ復旧は対象外
- 新設 tests/acceptance/kobo-merge-gate-scope.spec.ts: banto のマージ前ゲートがフルスイートを走らせない（またはフルスイートには明示承認が要る）
- 既存の守り（acceptance・監査・PO レビュー）を壊さないこと（kobo-worker-integration.spec.ts が通ること）
- npm run typecheck が通ること
