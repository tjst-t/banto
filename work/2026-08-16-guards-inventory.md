## 結論

**この工場の「緑」は、これまで「マージ前ゲートが赤を出さなかった」以上のことを保証していなかった。**
検証を1本も走らせなかったもの、器で走りようがない試験を書いたもの、走ったが間欠で揺れたもの、
そもそも工場を通っていない自己申告、誰も見ていない恒常赤——**すべてが同じ「緑」として並んでいた。**

**そして今日、同じことが赤の側でも起きた。**
機構は task-0164 の失敗理由に **「このランタイムには監査の口が載っていません」** と書いた。
**その文言は `daemon.ts:2740` の決め打ちで、口の有無はどこでも観測されていない。**
実際には口は載っており（同じ日・同じランタイムで別のタスクの監査は判定を返している）、
起きていたのは「監査人が背景実行を待つと言ってターンを終えた」ことだった。

> **緑が信用できないのと同じ理由で、赤も信用できない。**
> 「機械が言っているから正しい」ではなく、**機械が何を見て言っているか**を見る。

## 見出しA：**この機構は「重い・遅い・大きいもの」を罰する**

今日見つかった穴の**過半が、たった1つの勾配の別々の症状**だった。

| 症状 | 何が起きるか | 実例 |
|---|---|---|
| **袋が破れる** | 重い検証を職人の袋（cgroup 2.0GiB）の中で回すと **SIGKILL**。`npm test` は全量2420件を並列プロセスで走らせ、その全部が袋に乗る | `imp-0074`。task-0193 の職人が起動2分で kill（`⚠上限で kill された peak=2.0GiB`）、task-0164 の職人も上限に張り付き |
| **着地に負ける** | ゲートが6〜8分かかる間に main が進むと `git merge --ff-only` が必ず失敗。**長い検証を持つタスクほど負ける** | `inc-0079`。task-0159 が今日3回 |
| **監査の判定が返らない** | `npm test` が400秒かかるので監査人は背景実行を選び、「待っています」でターンを終える → 工場は「終わった」と受け取り、判定が無いので即 failed | task-0164 → `task-0201` |

**慎重にやるほど罰せられる。** 放っておけば、人も職人も**軽い検査・狭い検証・自己申告**へ自然に流れる——
実際、今日その産物を3つ拾った（`npm run test:ui` を契約から落とす／grep で済ませる verify／
「ホストで回した出力を貼る」で通す）。**個々の怠慢ではなく、勾配である。**

根治は **task-0186**（検証を袋の外で Kobo が回し、結果だけ職人へ返す）。
それまでは運用で避ける——**職人に全量を回させず、番頭が `env.verify` で袋の外から確かめる。**

## 観点1：**番人が居ないもの＝次に落ちる穴**

✕ が **16件**。うち**この枝が直しに入っているのが5件**（9・11・12・15・23）。
**起票すら無いのが3件** — **#5**（`work/tasks` 未追跡）・**#21**（帳簿外の done）・**#24**（main のチェックアウトを渡せる）。
**#5 と #21 は「記録と帳簿が別々に生きている」という同じ根**から出ている。

## 観点2：**番人が居るのに効いていない＝今日いちばん多かった形**

- **#1** 記録 id — 番人は着地しているのに**今日10組**。**枝の上では片方しか見えないので緑**になり、
  **落ちるのはマージ後で、そのときには誰も見ていない**
- **#3** 道具の一覧 — 番人が**3本**在って、なお11件目
- **#12** ブラウザ試験 — **152件書かれているのに、器にブラウザが無く1件も走らない**。
  **書いてあることと走っていることが、初日から一度も一致していなかった**
- **#18** 設定 — 7件が「在るのに効いていない」
- **#22** 監査の起こし直し — 「落ちた」は見るが「**判定なしで報告した**」は通り抜ける

**「置いた」で満足しているのが共通形。置いたものが効いているかを見る番人は、どこにも居ない。**

## 観点3：番人の型が守られているか

| 型 | 守れている例 | 破れている例 |
|---|---|---|
| **全件を走査する** | `record-id-uniqueness`（欠番も一覧に出す）・`decision-number-uniqueness` | #3（3本在って11件目） |
| **空振りで緑にならない** | 上の2本は「**そもそも記録が拾えている**」を条として持つ（実行出力で確認） | **マージ前ゲート自身**——検証0本で緑（#9）。ブラウザ試験も0件実行で誰も気づかない（#12） |
| **例外は理由つきの除外一覧** | `record-id-uniqueness` の欠番一覧・`test` の除外リスト | — |
| **直す前に落ちることを確かめる** | task-0177 / 0195 / 0197 / 0193 / 0201 の契約に明記（この枝） | 過去タスクの多く（確かめた記録が残っていない） |
| **機構の文言が観測に基づく** | — | **#23**（「口が載っていません」は決め打ち）。**型として誰も要求していなかった** |

**いちばん重い破れは「空振りで緑にならない」がゲート自身に無いこと。**
**番人を何本足しても、番人を呼ばずに緑を出す道が空いていれば意味がない。**それが #9 であり、
**task-0177 がそこを塞ぐ**（`unverifiedAcIds` を必ず刻む／検証0本なら落とす／自動着地は未検査を許さない）。

## 再発防止として、機構に残すべきもの

1. **採番を人にやらせない**（#1・BacklogStore へ）。**注意力の問題ではない**——**今日10回破られた**
2. **記録を書いたら履歴に入るまでを機構の仕事にする**（#4・#5）
3. **「置いた設定が効いているか」を見る番人**（#18）。存在ではなく**実効値**を見る
4. **空振りを緑と呼ばない**を全部の検査の型にする（#9・#12）。**件数を数える条を必ず1本入れる**
5. **重いものを罰する勾配を平らにする**（見出しA・#14/#15/#20/#22）。**根治は task-0186**
6. **機構が理由を書くときは、観測したことだけを書く**（#23）。**確かめていない原因を文字列で決め打ちしない**
