# 決定64 を見直す — 契約は「凍結」ではなく「改訂できる（ただし差し戻る）」

PO 指摘 2026-08-08：「test の契約が間違っていたら、実装がちゃんと終わっていても、
再作成で一から実装しなおし？ もしそうなら決定64が間違っていたかも」。

## まず事実（実装を確かめた）

**はい、そうなっています。** そして指摘のとおり、これは高くつきます。

- 新しいタスクの worktree は `task/<新id>` を **HEAD（main）から切る**
  （`addTaskWorktree`）。**前の成果は入っていません**
- 引き継ぐには、タスク本文に「`<sha>` を cherry-pick せよ」と書いて**職人に手でやらせる**
  ——実機の loamium/task-0005 がまさにこれをやりました
- 引き継いでも払うものは変わりません：**職人セッション1回・監査1回・レビュー1回**。
  そして**経緯が別 id に分かれます**（task-0081 で PO が嫌がった形そのもの）

つまり「検証コマンドの書き方を1箇所間違えた」の代償が、**実装のやり直し一式**です。

## 決定64 は何を守っていたか

「**何に対して監査したのか**が答えられなくなる」——これは本物の不変条件です（I1）。
後から `scope.paths` を広げられたら、範囲外の変更を事後に正当化できてしまう。

**問題は、守り方が「凍結」だったこと。** 契約の中身は危険度が同じではありません：

| 部分 | 変えると何が壊れるか | 直したくなる頻度 |
|---|---|---|
| `scope.paths`（広げる） | 範囲外の変更を事後に正当化できる。ゲートの検査が無意味になる | 低 |
| `acceptance[].text` | 緩めると「できていないもの」を「できた」にできる | 低 |
| `acceptance[].verify` | 弱めると（`npm test` → `true`）検証が空振りする | **高**——書き方を間違えやすい |
| `title` / `body` | 判断の材料。監査の対象ではない | 中 |

**`verify` は「何をもって完了とするか」ではなく「どう確かめるか」**です。
loamium/task-0005 の a3 は、

- text: 「UI の型チェックが通る」← **正しい。変える必要はない**
- verify: `npm ci --include=dev && cd packages/ui && npm run lint` ← **ここだけ間違い**
  （環境の用意が焼き込まれている。task-0080 の `setup` に移った仕事）

**基準は合っているのに、確かめ方が壊れている。** 凍結はこの2つを区別しません。

## 提案：改訂を認める。ただし**依存するものを差し戻す**

危ないのは「変えること」ではなく、**黙って・自分に有利に・再評価なしに変えること**です。
3つとも潰せば、凍結しなくても不変条件は守れます。

### 1. 改訂は必ずイベントにする（黙って起きない）

`kobo.amend(projectTag, taskId, reason)` を足す。**ファイルを読み直すのは、
呼ばれたときだけ**——今の「書き換えても黙って無視」（inc-0028 で直した挙動）は残したまま、
**明示すれば取り込める**道を開けます。D4「ファイルは意図」もそのまま。

`task_contract_amended` に **変更前・変更後・誰が・なぜ** を残す。
`kobo.task` に出す。**改訂した回数も数える**（P6 と同じ扱い）。

### 2. 何を変えたかで、差し戻す先が変わる

| 変えたもの | 監査 | 戻す先 |
|---|---|---|
| `acceptance[].verify` **だけ** | **有効のまま**（基準は変わっていない） | そのまま。マージ前ゲートは元々毎回回る |
| `acceptance[].text` / `scope.paths` | **無効**（違うものに対して監査していたことになる） | `implementing` へ戻して監査からやり直す |
| `title` / `body` | 影響なし | そのまま |

**これが要点**：`verify` だけの訂正なら、**実装も監査もやり直さずに**マージ前ゲートへ進めます。
loamium/task-0005 は、これで**そのまま通せます**。

### 3. 広げる方向は PO へ（狭めるのは番頭でよい）

`scope.paths` を**広げる**のと `acceptance` を**減らす／緩める**のは、
「できていないものを通す」方向です。ここは層B の `po_required_paths` と同じ発想で
**PO の判断**にする。狭める・厳しくする・`verify` を直すのは番頭でよい。

## なぜこれが「凍結」より強いか

凍結は「何に対して監査したのか」に**"取り込み時のもの"** としか答えられません。
改訂＋差し戻しなら **"バージョン V の契約に対して、時刻 T に監査した"** と答えられます。
**記録として厳密になり、しかも間違いが直せます。**

いまは間違いが直せないので、**運用が「新しいタスクを立てる」に逃げます**——
その結果が task-0004 → task-0005 の分断で、**帳簿の追跡性はむしろ落ちました**。
凍結が守ろうとしたものを、凍結が壊しています。

## 決めていただきたいこと

1. **決定64 を改訂してよいか**（ADR-0013 の決定を差し替える。ADR が要ります）
2. **差し戻しの表**（上記2）でよいか。とくに「`verify` だけなら監査は有効のまま」を
   認めてよいか——ここが一番効くが、一番緩む所でもある
3. **広げる方向を PO 判断にする**線引きでよいか
4. 入れるなら **loamium/task-0005 を amend で通す**か（abandon せずに済みます）
