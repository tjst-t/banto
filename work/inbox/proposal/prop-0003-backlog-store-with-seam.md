# Kobo に積む前段の「起票（バックログ）」に機構を持たせる

枝「バックログの仕組み」（thread-104・幹 banto開発 thread-61）の結論。
PO 指示：「Kobo に入れる前段のバックログ管理の仕組みを banto プロジェクトとして作るかが問題。
あとはそのバックログを、どう Kobo に流し込んでいくか」。

## 1. なぜ要るか（現物・2026-08-16 調査）

**いまの起票は「記録」ですらなく「メモ」である。**

- `work/inbox` を読むコードは **packages/ tests/ 全体でゼロ**。唯一のヒットは
  `packages/banto-host/src/bin.ts:296-298` のコメント（「番頭はそこへ書けない」）。
- 誰も読まないので壊れても誰も困らず、実際に割れている：**108件**（improvement 53 /
  incident 53 / proposal 2）で、
  - `status` が **10種**に分裂（open 45 / resolved 35 / inbox 6 / backlog 6 / done / fixed /
    landed / closed / tasked / in-progress / accepted）。区別する規則はコードにも spec にも無い
  - `origin` の約半分が自由文（spec は system/po/agent の3値を想定）
  - **6件は frontmatter を持たない**（imp-0015, imp-0019, imp-0022, inc-0064〜0066）
  - **id の衝突が3組**（imp-0040 / imp-0041 / inc-0070 が同番号2本ずつ）＝ imp-0055 の実体。
    タスク側は `nextTaskNumber`（`packages/banto-daemon/src/task-record.ts:108`）が
    ファイル名と帳簿の両方の最大値を見るので衝突しないが、**起票を採番するコードは存在しない**
  - 決着済み45件のうち **31%（14件）はどの task になったか辿れない**。
    `imp-0001` は `status: tasked` なのに task 参照ゼロ。`refs:` は「関連 id の自由なメモ」で
    あって「どの task になったか」の欄ではなく、書式も
    `task-0102-banto-live` / `dentaku/task-0020` / `dentaku-task-0020` の3通りが混在
  - git の初コミット日は起票日として信用できない（08-15 に33件がまとめて入っている＝ imp-0054）
- **未処理は51件**（open 45 / inbox 6）。選ぶ儀式は存在しない。
  `docs/spec/improvement-loop.md` が設計する集計・ケイデンス・評価カードは全て未実装で、
  イベント型 `card_generated`（`packages/banto-core/src/events.ts:148-156`）は
  型と素通しの case があるだけ、実機の帳簿 2,983 件中 **発火0件**。
- 結果として、**索引は番頭の記憶だけ**になっている。文脈を畳むと索引が消える。

**起票の置き場を持つのは banto だけ**（loamium / dentaku / hiragana-app / Mirante-demo の4つとも
無い。loamium は `docs/memo_todo.txt` の5行メモ）。したがってこれは運用の約束事ではなく
**banto の機能**として作る。

## 2. 検討した3案

### A. 約束事だけ整える（機構ゼロ）
md のまま、スキーマ・採番・status 語彙を規約で固定し、番頭が規律で守る。費用ほぼゼロ。
**却下**：この方式が壊れることは上の数字で実証済み。10種の status も3組の id 衝突も
31%の追跡不能も、規律で防ぐ建て付けの結果であり、同じ病気が再発する。

### B. Kobo に第一級の「起票」を持たせる
帳簿にレコード種別を足し、`kobo.file` / `kobo.promote` を作る。追跡は同じ帳簿で閉じるので最も綺麗。
**却下（当面）**：`SnapshotState`（`packages/banto-core/src/event-log.ts:46-48`）は
トップレベルの入れ物が `tasks` 1つしかなく、2本目を足すのは
**イベントログ形式の変更＝後戻りできない（D1・PO 判断）**。加えて起票には projectTag が
決まる前のものが多く、Kobo の「機構は契約を作らない／入口は一本」（第4便・
`packages/banto-daemon/src/kobo-tools.ts:11-14`、`task-record.ts:5-8`）とも噛み合わせが要る。
なお **`work/tasks/*.md` の watcher は 2026-08-14 の `c1ba54b3` で削除済み（main 入り・実機でも停止）**
なので、「ファイルを置いて機構が読む」形へ起票で戻るのは、決めたばかりの線の逆走になる。

### C. 番頭側に持ち、Kobo へは昇格の時だけ渡す ← **採用**
置き場は番頭ホストのデータ置き場（`/var/lib/banto/backlog.jsonl`、取次の `inbox.jsonl` の隣）。
**真実は jsonl、記録は md をリポジトリへ書き出す**——Kobo が task の md を書くのと同じ形にして、
git で読める道も残す。帳簿形式（後戻りできない側）に触らず、費用は banto-host 側だけ。
役割分担も素直：**Kobo は「決まった仕事」の器、番頭は「まだ決まっていないこと」の器**。
後から B へ寄せる道も塞がない。

## 3. Seam（PO 指示：バックエンドを差し替え可能に。将来 GitHub Issues と同期）

差し替えの形は2通りあり、性質がまるで違う。

- (i) Store をそのまま差し替える（GitHub 実装では `backlog.list` が API を叩く）
  → **番頭の道具呼びがネットワークで失敗しうる**。「気づいた瞬間に1行で置ける」という
  この機構の肝が、レート制限とタイムアウトの下に置かれる
- (ii) **ローカルが常に真実、外部は投影先**（ファイル実装＋同期アダプタ）

**採る形：(ii) を契約として明記した上での `BacklogStore` インタフェース。**
口は差し替え可能にするが、インタフェースの契約に

> **読みはローカル索引から即答する（ネットワークを待たない）／
> 書きはローカルに確定してから外へ送る（外への送信の失敗は起票の失敗ではない）**

と書く。こうすれば GitHub 実装も必然的に「キャッシュ＋非同期送信」の形になり、
後から足しても設計が崩れない。

### 最初のファイル実装に織り込む3点（これが実質の Seam）

実装は1本でよいが、GitHub で必ずぶつかる3つは最初の形に入れる（後から入れると移行を伴う）。

1. **id はローカル主権**。`bl-NNNN` は banto が振り、外部の番号は
   `external: { provider, id, url, syncedAt }` という別欄に持つ。
   id を Store に委ねると `originRef` も md も記憶も provider 依存になり、切り替えで過去の参照が死ぬ
2. **状態語彙は banto が正、外へは変換して投影**。GitHub は open/closed しか持たないので、
   `tasked` / `dropped` はラベル（`banto:tasked`）へ落とす。**変換表は Store 実装側**に置き、
   banto 本体は4値のまま何も知らない
3. **書きは非同期・冪等**。起票にクライアント側の一意キーを持たせ、外部への送信が失敗しても
   起票は成立して pending として再送する

**やらないこと**：実装が1つしかないうちに汎用化しない。

### 双方向（PO 判断：人が GitHub 側でも書き・読む）

`pull(since)` を **capability として最初から口に定義する**（実装は後回しでよい）。
双方向が要ることで決まる設計：

- **id 発行のきっかけが2つになる**（`backlog.file` と `pull`）。外で作られた Issue は
  取り込み時にローカル id を振り、`external` に GitHub 番号を持つ。ローカル id 主権は維持
- **競合はフィールド単位で所有者を決める**——**人が書く欄は人が正、機構が知っている欄は機構が正**：

  | 欄 | 正 |
  |---|---|
  | 表題・本文 | 最後に編集した側（外で人が編集したら外が正。機械が人の文を潰さない） |
  | 状態（open/tasked/dropped/done） | banto（タスク化の事実は Kobo 側にしかない） |
  | task へのリンク（originRef） | banto |
  | コメント | 外（ローカルには概念を作らない） |

- **削除は無い**。GitHub の Issue は消せないので、`dropped` は closed＋ラベルへ投影する
- **取り込みは背景で定期 pull → ローカルへ反映**（読みの即答契約を守るため）。webhook は後
- **ループ防止**：`external.syncedAt` と `updatedAt` の比較＋冪等キーで、
  push した変更が pull で戻って再 push されるのを止める
- **同期対象は全件ではない**。プロジェクトが決まらない起票は Issue の受け皿が無いので、
  **未整理はローカルのみ、外へ出すのは「これはやる」と決めたもの**（＝ `external` を持つものが
  共有されているもの）。push は昇格時が既定
