# task-0165 を工場の外へ出しかけて、戻した（**例外は結果として発生しなかった**）

## 何が起きたか

2026-08-16、**`task-0165`（会話の開閉とプロセスの生死を切り離す＝OOM の本命の直し）を、
工場の列に並べず職人へ直接委譲する**という判断が出た。PO の言葉：

> **「職人に直接実装させましょう。結構大きな問題になっているので。」**

**理由は「列が詰まっていて、割り込ませる手が無い」こと**だった——工場の実効的な同時実行数は **1本**
（`tests/acceptance/**` の重なりで直列化・imp-0072）で、task-0165 は積んでから **6時間以上 queued**。
ゲートは作成順に通すので、**急ぎのものを前に出す手が無い。**

**ところが、外の職人が着手する直前に、工場が同じタスクを始めていた。**

```
07:45:12 task-0165 queued → ready（gate_passed）      ← 列が流れた
07:45:19 agent_spawned → planning
07:50:07 task_contract_amended（受け入れ条件 a9〜a12 の追加・本文の書き直し）
07:50:08 planning → implementing
```

**外の職人を起こしたのは、この後である。** しかも工場の職人は、**改訂後の最新の契約**
（PO の言葉で書き直した目的と a9〜a12）を受け取ったうえで実装に入っていた。

**外へ出す理由（列に並べない）が消えたので、外の職人は降ろした。** 工場の経路なら
**監査とマージ前ゲートが自動で付く**——**「緑が信用できない」を直している最中に、
検証の薄い方を選ぶ理由は無い。**

## 残す価値のある点

1. **例外を通す前に、理由がまだ生きているかを確かめること。** 今回は「列が詰まっている」が
   **数分で解けていた**。**例外の理由は、状況とともに消える。**
2. **着手前に止まって聞いた職人の判断が、二重作業を数時間ぶん防いだ。**
   「同じタスクを別の職人が走らせている」と気づいた時点で**手を止めて聞く**のが正しい。
3. **急ぎのものを列の前に出す手が無い**、という不便は残っている。**そこが解ければ、この種の例外は要らない**
   （imp-0072）。**「急ぎだから外へ出す」を繰り返すなら、それは工場の速度が足りていないという合図。**

## 副次的に起きたこと（**他人のワークツリーで git を動かした**）

外の職人が、判断を仰ぐ前に **工場の職人のワークツリーで `git merge --ff-only main` を1回打った**
（`e0ebf3fb` → `8b0c7002`）。**入ったのは docs 1ファイル**（inc-0075・+21行）で、
**相手の未コミットの編集は無傷・衝突なし。害は出ていない。**

**原因は指示文の不足**（「他人のワークツリーでは読むだけ」と書いていなかった）。**当面は指示文で塞ぐ。**

> **ただし、これは注意力に頼る形である。** この現場の原則は
> **「同じ穴に複数回落ちるなら、機械で落とす」**——**2回目が起きたら、指示文ではなく機構側で塞ぐこと**
> （例：職人に渡すワークツリー以外での git 書き込みを拒む）。**次に踏んだら、すぐ機構の話に移る。**
