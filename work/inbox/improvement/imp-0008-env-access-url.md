## 内容

**「立てた検証環境にブラウザでアクセスして確かめる」が今はできない**（PO質問、2026-07-31）。

手元で確かめた事実：

- `env.provision` で `config: { cmd: "python3 -m http.server 5199", port: 5199 }` を渡すと、
  実際にサーバが立ち上がり、`healthcheck` は TCP 疎通まで見る（`port が届かない` を返せる）
- そのポートは**同じ機械の中からは実際に叩ける**（`curl localhost:5199` → 200）
- しかし **`env.list` にもどこにもポート／URL が出ない**。番頭も画面も「どこを開けばいいか」を知らない
- **外（POのブラウザ）から届く保証も無い**。banto は 4200 の1ポートだけを公開している構成で、検証環境が使う任意のポートは経路の外にある

つまり「機械が立てて自分で叩いて結果を返す」（＝`env.verify` の `cmd`）は成立しているが、
**人が目で見て確かめる**経路が無い。

## なぜ勝手に足さなかったか

手っ取り早いのは `handle.port` を読んで URL を組み立てることだが、`spec-environment` §2 は
**handle を不透明**と定めており（「呼び出し側は中身を解釈しない」・D1/D3）、config も
「daemon は中身を解釈しない」とされている。ここを覗くと、ドライバごとに違う内部表現へ
Environment Pool が依存し始める——契約を崩す方向なので、裁定を仰ぐ。

## 決めること

1. **到達先をドライバ契約に入れるか。** `healthcheck` の出力に `url?` / `endpoints?` を足すのが
   素直（既に疎通を見ている動詞であり、handle を覗かずに済む）。ドライバが「ここで見られる」と
   自分で答える形になる
2. **外からの到達をどうするか。** (a) 何もしない（同じ機械の中だけ）、(b) Banto ホストが検証環境へ
   逆プロキシする口を持つ、(c) 環境ごとにポートを公開する。(b) は 4200 の1ポートで足りるという
   いまの構成を保てるが、**Banto が検証環境への通り道になる**ので認証（モジュールHTTP面の
   未決事項）と地続きになる
3. **画面の出し方。** 到達先が分かれば `env.manager` にリンクを出すのは自明。共有ブラウザ
   モジュール（`docs/research/browser-module-research.md`）と組み合わせる案もある

## いま何ができるか（回避策）

- `env.verify` の `cmd` に検証を書けば、**機械が確かめた事実**としては受け取れる（これは動く）
- 目で見たい場合は、環境が使うポートに手元から直接届く経路（SSHポートフォワード等）を
  自分で用意すれば見られる。banto は関与しない

## 対応（2026-07-31・resolved）

ADR-0010 決定39。**Caddy 一択にはしなかった**——実測で、いまの配置（Palmux 管理のコンテナ内）からは Caddy の admin API に届かないことが分かったため。公開の口を `EnvExposer` として切り、実装を2つ持つ形にした。

- 既定：番頭ホストが `/env/<envId>/` で中継。どの配置でも動き、**banto を守っている認証をそのまま継承する**
- 設定で有効化：Caddy の admin API へ route を注入（Palmux と同じ `@id` 冪等 upsert）
- ポートは `env.provision` の `expose` で呼び出し側が明示する（handle を覗かない）

**この作業中に別の漏れを見つけて直した**：`env.teardown` が成功を返すのに実サーバが生き残っていた。`shell: true` で起こすので記録される pid はシェルのもので、それだけ殺すと本体が PPID=1 で動き続けていた。`detached: true` によりプロセスグループのリーダーになっているので、負の pid へシグナルを送って木ごと落とすようにした（I3）。

## 追記（2026-07-31・番頭の指摘で発覚した2件）

番頭が spec と実装を突き合わせて3点指摘した。うち2件は**実際の欠陥だった**。

1. **TTL 執行と照合が Environment Pool 側に無かった**（実害最大・その通り）。`spec-environment` §5 は
   「執行は Environment Pool の台帳が行う。モジュール側に無いと誰も片付けない」と明記しているのに、
   実装は `ttlDeadline` を記録するだけで、執行は Kobo（`daemon.ts`）にしかなかった。しかも台帳が
   別（`<dataDir>/environment-pool`）なので、**番頭が立てた環境は誰の掃除対象でもなかった**。
   さらに悪いことに `env.provision` は「期限を過ぎると自動で畳まれます」と返しており、**嘘だった**。
   → `startMaintenance()` / `runMaintenance()` / `reconcile()` を pool に実装。ホスト起動時に回す。
   執行が回っていないときは「自動では畳まれません」と正しく返すようにした。
2. **既定TTLが spec と違った**（30分 → 実装は4時間）。spec §5.1 の表を見ずに数字を選び、
   「手元の検証には十分」という理屈を後から付けていた（P3）。→ 30分に直した。
3. ドライバ実行主体が移行途中（Kobo がライブラリ参照で直接実行）は**既知で意図的**——
   決定32a の2段階の1段目。Environment Pool 自身は自分の環境を自分で起こしている。
