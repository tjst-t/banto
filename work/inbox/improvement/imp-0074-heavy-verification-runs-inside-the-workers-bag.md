## 何が起きているか

職人は1本ごとに cgroup の袋（既定 **2 GiB**）に入っている（inc-0066 第2段）。
2026-08-16、**その袋の上限に当たって職人が繰り返し殺されている。**

- task-0160 の実装：opus の職人が**2回とも SIGKILL**（peak **1.6 GiB** と **2.0 GiB**＝上限に到達）。
  **`model_tier` を standard に落としたら完走**（枝 thread-125 の実測）。
- task-0157 の監査：`npm test` と `npm run typecheck` を袋の中に抱えたまま上限に当たり、
  `memory.oom.group` で**15プロセスが袋ごと kill**（01:26:51）。
- task-0160 の rework：**`npm ci` が anon-rss 1.3 GiB** で kill（04:06:33）。
- **task-0176 は `planning` の段で死んだ**（枝 thread-126 の実測）。**実装に入る前、13分で peak 2.0 GiB**、
  **報告を書く前に消えた**（`agent_exited_without_report`）。直前にやっていたのは
  **ブラウザ試験152件を引数なしで丸ごと回すこと**（11分・**出力が巨大**）。
  同じことをした task-0175 の職人も**上限に張り付いた（peak 2.0 GiB）が、こちらは生き延びた**。

**「難しい仕事ほど落ちる」**という、いちばん質の悪い形になっている。

## 軸は「モデル」でも「`npm`」でもなく、**文脈へ載る出力の大きさ**

最初はこれを「袋の中で `npm` を回すから破れる」と書いた。**それは狭かった。**
task-0176 は **`planning` の段**——実装もコミットもしていない段階で 2.0 GiB に達している。
やっていたのは**試験を丸ごと回して、その出力を読むこと**である。

| 職人 | 何をしていたか | 袋の peak |
|---|---|---|
| task-0175 / fix-env-container-parity / imp-0051-2（opus） | 実装（`npm` を回す） | **2.0 GiB（上限）** |
| **task-0176（opus）** | **planning。ブラウザ試験152件を引数なしで実行** | **2.0 GiB（上限）で kill** |
| task-0159-audit（opus） | 監査（`npm test` / `typecheck`） | 1.9 GiB |
| imp-0051 / imp-0034（opus） | 実装 | 1.7 / 1.4 GiB |
| task-B:rework（sonnet） | 小さい直し | **303 MiB** |
| `inv-*`（haiku・番頭の調べ物） | 数字を読むだけ（出力を絞っている） | **約 250 MiB** |

**共通しているのは「一度に大量の出力を受け取り、それを文脈に載せた」こと。**
`npm ci`（1.3 GiB の anon）や `npm test`（2399件）はその最大の例だが、**原因ではなく代表例**である。
**絞らずに回す試験・巨大なファイルの読み出し・広い grep も同じ型に入る。**

**まだ分けられていないこと（未確認）**：「同じ仕事でモデルだけ下げたら完走した」という観測が1件あり、
**モデルの寄与がゼロだとは言えない**（文脈が小さくなれば、その分の余裕ができる）。
> **確かめるなら**: 同じタスクを (a) 出力を袋の中で丸ごと受け取る (b) 出力を袋の外で回して要約だけ受け取る
> の2通りで走らせ、袋の `memory.peak` を比べる。1回ずつで足りる。

## なぜ「袋を広げる」で済ませてはいけないか

工房（`banto-worker-pool.service`）の上限は **8 GiB**、工房本体（supervisor）が **1.2〜1.5 GiB** を使う。

| 袋 | 同時本数 | 合計（＋本体 1.5） | 8 GiB に収まるか |
|---|---|---|---|
| 2 GiB | 3本 | 7.5 GiB | ○（余裕 0.5） |
| 2 GiB | **4本** | 9.5 GiB | **×** |
| 3 GiB | 2本 | 7.5 GiB | ○ |
| 3 GiB | **3本** | 10.5 GiB | **×** |

**袋を広げると、同時に走れる本数が減る。** そして**いま同時本数に栓が無い**（task-0168 が未着地）。
**栓が無いまま袋だけ広げると、工房の天井に前より早く当たる**——壊れ方が
「職人1本が死ぬ」から「工房全体が逼迫して**無関係な職人が巻き添えで死ぬ**」へ悪化する。
（後者は cgroup の `memory.events` が **`max: 0` なのに `oom_kill` が増える**形で見分けられる。実例あり。）

## 手（順序つき・幹が採用済み 2026-08-16）

1. **重い検証を袋の外へ出す。**`npm ci` / `npm test` / `npm run typecheck` を職人の袋の中で回さず、
   **Kobo が検証環境で回して結果を職人へ返す**（**task-0186** で積んである）。
   **同時本数の栓が無くても効く**——各袋の使用量そのものが下がる。**これが本命。**
2. **返す結果も丸ごと載せない。**task-0186 の受け入れ条件 **a8**：
   「職人へ返す検証の結果は、全出力をそのまま渡さず、上限を超える分は切り詰めて
   **『失敗した箇所と末尾』**を返す（切り詰めたことと、全文の置き場が分かる形で）」。
   **task-0176 の型（planning で巨大な出力を読んで死ぬ）に効くのはこちら**である。
3. **職人の作法にも同じ軸を書く。**「絞らずに回さない・測ってから読む」は既に
   `renderWorkerOffloadPrompt()` に入っている（2026-08-14 の調査で足した）。
   **ブラウザ試験を引数なしで丸ごと回すのは、この作法の対象だと明示されていない。**
4. **同時本数の栓を入れる**（task-0168。Worker Pool 自身が断る・決定23）。
5. **そのうえで袋を広げる**（`BANTO_WORKER_MEMORY_MAX`）。**1〜4 の後でなければ、広げてはいけない。**

**短期の凌ぎ**：重い実装を `model_tier: standard` に落とすと通る。**ただしこれは設計の後退**である
（「難しい仕事に reasoning を割り当てる」が成立しなくなる）。**落としたら、落としたと記録して使うこと。**

## 袋の大きさはどこで決まるか（変え方）

- **コード側**：`packages/banto-worker-pool/src/worker-cgroup.ts:43`
  `export const DEFAULT_WORKER_MEMORY_MAX = 2 * 1024 * 1024 * 1024;`（既定 2 GiB）
- **環境変数で上書きできる**：`BANTO_WORKER_MEMORY_MAX`（`packages/banto-worker-pool/src/bin.ts:101`。
  `2G` / `1536M` / バイト数の書式。読めない値は起動時に落とす）
- したがって **コードの変更なしに、`banto-worker-pool.service` の `Environment=` と再起動だけで変えられる**。
  **`deploy/banto-worker-pool.service` にも書くこと**（書かないと稼働機だけの設定になり、
  inc-0077 と同じ「作り直したら消える」形になる）。
- 隔離そのものの入切は `BANTO_WORKER_CGROUP`（既定 off。本番の cgroup を書き換える操作だから）。
- 参考：`worker-cgroup.ts:9` のコメントは「**実測で健全な1本は約 600MB**」と書いている。
  **その前提はもう成り立っていない**（いまの実装の職人は 1.4〜2.0 GiB）。
