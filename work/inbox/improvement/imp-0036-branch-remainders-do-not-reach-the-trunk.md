# 枝で「残ったこと」に書いた仕事が、幹に届かないまま消える

## 何が起きたか（2026-08-15・実例1）

枝「器が使えない件」(thread-86) は調査を終えて畳まれた。その `remaining` の1行目は

> 本命1本を幹で `kobo.enqueue`：器の寛容化＋栞に鍵名＋SKILL 誤例修正＋`facts` の偽成功を止める

**この仕事は誰にも渡らなかった。**起票も無く、職人も立たず、幹の番頭は別件（imp-0032 の
main 取り込み・再起動）へ移り、**PO が「修正は積んでいるのか」と聞くまで宙に浮いたまま**だった
（畳んだのは 03:21、気づいたのは PO の指摘）。調査だけが終わって直しが存在しない、という
いちばん質の悪い残り方をしていた。

## 何が起きたか（2026-08-15・実例2＝**問いが remaining に流れ込む**）

幹「電卓開発」(thread-85) の枝 thread-96（dentaku task-0027）。枝は仕事を終えたあと、
**幹の判断が要る事項**——「レビュー環境が task-0026 時点のままだが、立て直すか畳むか」——を
`thread.merge` の `remaining` に書いて畳んだ。幹に積まれたのは `conclusion` の1行だけで、
ターンは起きない。幹の番頭は気づかず **約25分放置**し、**PO の指摘**（「枝が問いかけたまま
閉じて幹が拾っていない」）で初めて `thread.list` を見て発見した。

実例1が「**残作業**が消えた」なら、実例2は「**問い**が消えた」。後者の方が悪い——答えを
待っている相手が居るのに、聞かれたことが誰にも届かない。

### なぜ「問い」が remaining に流れ込むのか（例外ではなく、起こりやすい経路）

1. 枝は「結論を1行で」求められて畳むフローに乗るので、**判断が要ると気づくのは畳もうとする瞬間**。
   そこから `thread.consult` へ戻るのは逆走で、心理的にも手続き的にも重い。
2. `remaining` は幹へ流れず、**幹のターンも起きない**（それ自体は ADR-0025 の方針どおり）。
   `thread.list` に「［畳んである・未処理 N件］」と出るだけで、
   **番頭が自発的に見に行かない限り気づく契機がゼロ**。
3. 枝は畳んだあと発話できないので、**問いの発生源が消えている**。再送する主体が居ない。

## なぜ落ちたか（機構の側）

1. **`thread.merge` の `investigated` / `decided` / `remaining` は枝に残り、幹へは流れない。**
   これは設計どおり（幹を読めるように保つため）。幹に積まれるのは **`conclusion` の1行だけ**。
2. その1行は判断の要約であって、**次に誰が何をするかは入っていなかった。**
3. 幹側に「枝から返ってきた未処理」を見る手段が無い。 → **一部は着地済み**（下記）。
4. 起票が無いので、**会話の外にも痕跡が残らない**。

つまり「枝は残作業を正しく書いていたのに、それを拾う受け皿がどこにも無かった」。
番頭の不注意は引き金だが、**引き金を引きやすい形になっていたのは機構の側**。

## すでに入っているもの（2026-08-15 時点）

- `thread.merge` が `remaining` を非空で受けたら、その枝を**未処理ありとして記録する**。
- **`thread.list` に、畳んだあとでも「未処理あり」の枝が出る**（既定で表示・片付くまで消えない）。
- 片付いたことを言う口 `thread.settle(threadId, where)`——**所在(where)は必須**。

**残っているのは「気づく契機」と「そもそも問いを流し込ませない」側**である。

## 番頭裁定（この線で実装する・2026-08-15）

候補は (a) `remaining` が非空なら幹の札＋ターンを起こす／(b) 「幹の判断待ち」を種別として
持たせ札・取次へ回す／(c) 幹がターンを起こすたびに未処理を抱えた枝の件数を文脈に注入する／
(d) `remaining` の行に所在(id)が無ければ `merge` を断って `consult` を促す、の4つ。

**採るのは (d) ＋ (c)。(a) は却下。(b) は作らない。**

### (d) が本筋 — 所在の無い `remaining` で畳ませない

`thread.merge` の `remaining` に**所在の無い行**（`imp-NNNN` / `inc-NNNN` / `task-NNNN` /
職人の `sessionId` / 「幹で委譲予定」等が無い行）があれば、**merge を断る**。
道具の説明には既に「残作業には所在を持たせろ」と書いてあるのに機構が強制していない＝
**書いてあるだけの規律**なので、ここを機械で担保する。

断り文には**直し方**を書くこと——所在を足す例と、**判断を仰ぐなら `thread.consult` で
枝が生きているうちに聞く**という道（例文まで）。断って終わりにしない。

### (c) を保険に — 未処理を抱えた枝の件数を、幹の文脈に1行

幹がターンを起こすときの文脈に「未処理を抱えた枝 N件」を1行入れる。
**ターンを起こさない**ので ADR-0025（知らせは幹のターンを起こさない）に反しない。
番頭の注意力に頼っていた部分を、目に入る形に変える。

### (a) を却下する理由

PO 方針「**知らせは幹のターンを起こさない**」（ADR-0025 決定120）に真っ向から反する。
判断を求めるものには `thread.consult`（枝が生きているうちに聞く）と取次が既にある。

### (b) を作らない理由

(d) を入れれば所在として「`consult` へ回した」と書けるので、別建ての種別は増やさない。

## あわせて決めること

**機構が自動で立てる用件枝（ADR-0025 決定121）が畳まれるときも、同じ経路を通る。**
機構は所在を書けないので、**そもそも `remaining` を持たせない形**が素直
（機構は畳まない＝畳むのは番頭、という決定122 とも噛み合う）。実装時に明示すること。

## 当座の運用（機構が入るまで）

- 枝を開く指示文に「**幹の判断が要るものは畳む前に `thread.consult` で聞け**」と明記する。
- 枝の完了通知を受けたら `thread.list` を見る（未処理を抱えた枝が出る）。
- `remaining` の各行は所在を持つこと。`conclusion` にも**次の一手とその所在**を書く。

## 優先度

P1。これは1件の取りこぼしではなく **取りこぼしを生む構造**で、枝を使うほど再発する。
ADR-0025 で知らせを枝へ逃がすと**枝の本数は増える**ので、橋の細さは今後さらに効く。
