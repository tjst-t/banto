## 何が起きているか

「幹で会話できない」の直接原因は機構ではなく **Web UI の門番**。`Room.tsx:620` の busy ガードが
走行中の入力を**黙って捨てている**。サーバ側は走行中の入力を既に受けられる
（`promptEvenWhileBusy()` が `streamingBehavior:"steer"` で走行中の `query()` へ差し込む）。

## やること（提案 §4 案I）

1. `packages/banto-web` の `Room.tsx:620` の busy ガードを外し、**走行中も送信できる**ようにする。
   送信と中断を併存させる。
2. **割り込みの意味論を UI に出す**：「いまの作業に足す」（走行中のターンへ融合＝steer 相当）／
   「止めて話す」（abort してから新しいターン）。**走行中に送ると現状は融合するのであって、
   割り込んで先に答えるのではない**——文言で明示しないと PO の期待とずれる。
3. **PO の発話を知らせの列より優先する**。いまは abort しても `thread.notices` の残りが
   すぐ走り出して再び塞がる（`abort` が列に触っていない・提案 §2.6-2）。

## 受け入れ基準の骨

1. ターン走行中に送信したメッセージが捨てられない（現状は黙って捨てる）
2. abort 後、列に残った知らせより PO の発話が先に処理される
3. 走行中に送った知らせ／発話が `PromptQueue` の入れ替えで消えない（提案 §2.6-2 の再現試験。
   解放された `.then` が `start()` の `finally` より先に `prompt()` を呼ぶと、閉じられる直前の
   キューへ push されて消えうる——**マイクロタスク順序次第なので、再現する形に落としてから直す**）

## 承知しておく副作用

abort 中断は履歴に `Claude Code process aborted by user` の system 通知として残り、
`tool_end` が来なかった道具は `running` のまま残る（次回起動時に `failed` へ確定）。
**imp-0037（再起動をまたぐ会話を落とさない）と同じ筋**なので、衝突しないか見ること。

（帳場・直近24時間で busy 時間の 44% が知らせ由来、うち相当量が相槌）。その数字を持って
PO へ案II の可否を上げ直す。**測って返すまでが、この仕事の完了。**
