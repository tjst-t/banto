# 常駐のプールと、毎回起こし直すドライバの間で版がねじれる（マージした瞬間に全環境が立たなくなる）

## 何が起きたか（2026-08-15・imp-0033 の反映中に実際に踏んだ）

`fix/env-compose-project-per-env` を main へマージした直後から、**`env.verify` が
すべて落ちた**（provision を通る動詞が全滅）。原因はコードの欠落ではなく、

- **環境プールは常駐プロセス**。起動時に読んだ `pool.ts` をメモリに持ち続ける（当時 02:34 起動＝旧）
- **docker ドライバは動詞ごとに `node --import tsx docker-driver.ts` で起こし直す**。
  main にマージした瞬間に新しくなる

の組み合わせで、**「envId を渡さない古い pool」＋「envId を要求する新しいドライバ」**が
同居した状態。**マージから常駐プロセスの再起動までの間だけ**起きる。
プールを入れ替えたら解消し、追加のコミットは要らなかった。

## なぜ試験で捕まらないか

受け入れ試験は `pool.verify()` を端から端まで実際に回しており、マージ前も後も通る。
この壊れ方は**1つのプロセスの中には存在しない**——古いプロセスと新しいソースが同居した
ときにだけ現れるので、**どんなプロセス内テストでも再現できない**。
捕まえる場所は試験ではなく、反映の手順か、pool↔driver の握手のどちらか。

## 直し方の候補（未決）

- (a) **手順で防ぐ**：pool↔driver の契約を変える回は、マージと常駐プロセスの再起動を
      続けてやる（SKILL environment / デプロイの作法に1行）。**今日から効くが、忘れる**
- (b) **版の握手**：pool がドライバを起こすときに自分の版（コミット or 契約のバージョン）を
      渡し、食い違えば**動く前に名指しで断る**。いまはドライバ側のガードが
      「envId がありません（imp-0033）」と言うところまでは出来ていて、番頭は数秒で
      原因を名指しできた（I2 として正しく働いた側）。**断る文面を「版がねじれています・
      環境プールを再起動してください」に格上げできれば、それで足りる**
- (c) **ドライバも常駐にする**（起こし直しをやめる）。影響が大きいので却下寄り

**(b) を推す。**(a) は同時に入れられる。

## 影響

- 次に pool↔driver の契約を変える回に、また同じことが起きる（ドライバだけ先に新しくなる）
- 症状が「全環境が立たない」なので、踏んだ瞬間は**新しいコードのバグに見える**。
  実際 imp-0033 では「職人のコードに欠落がある」と疑って差し戻しかけた
