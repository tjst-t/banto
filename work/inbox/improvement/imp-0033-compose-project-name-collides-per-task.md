# 同じ taskId で環境を2つ立てると、先に立てた方が黙って壊れる（しかも healthcheck が嘘をつく）

## 内容

docker ドライバの compose プロジェクト名は **envId ではなく taskId 由来**。
しかも **taskId だけで、プロファイルが入っていない**（実物: `banto-env-task-0006`）。

```
packages/banto-environment-pool/src/docker-driver.ts:73
function projectName(taskId: string): string {
  return `banto-env-${taskId}`;
}
```

だから同じ taskId で2つ立てると、サービスのコンテナが**両者で共有される**。後から立てた側の
`compose up` が前のコンテナを作り直すので、**先に立てた env の公開ポートは実体を失う**
（caddy 経由で 502）。台帳には env が2件とも生きたまま残る。
**プロファイルが名前に入っていないので、これは同じプロファイル同士に限らない**（下の実測2）。

さらに悪いのは `handleHealthcheck`（同 :788）が `docker compose ps` を**プロジェクト名で**
引いていること。プロジェクトは共有されているので、壊れた側の env の healthcheck も
**作り直された新しいコンテナを見て `ok: true` を返す**。つまり
**「使えます」と答えた環境が 502 を返す**——I1（機構が返すのは事実）に真っ向から反する。

## 実測1（2026-08-15・電卓の幹・task-0005）

- `review.policy: po` ＋ `environment: dev` のタスクがレビュー待ちになると、**Kobo が自動で
  dev 環境を立てる**。番頭はそれを知らずにレビュー用にもう1つ立て、衝突した。
- 先に立った側の公開ポート 32778 は実体が消え、**PO が Kobo のリンクを開いて 502 を踏んだ**。
- `env.healthcheck` は2件とも「使えます」と回答。

## 実測2（同日・task-0006）——プロファイルをまたいで消える

- dev のレビュー環境が立っている最中に、**同じ taskId で `env.verify`（test プロファイル）**を回した。
- 走行中に警告 `Found orphan containers (banto-env-task-0006-dev-1) for this project`（予兆）。
- **使い捨て側の後始末の `compose down` が、dev のレビュー環境のコンテナごと消した。**
- その後 `env.run` は「環境のコンテナが1つも見つかりません（project `banto-env-task-0006`）」。
  **PO が2度目の「環境が開けません」を踏んだ。**

つまり被害は「レビュー環境が 502」だけでなく、**検証を回すと他人の環境が消える**ところまで及ぶ。

## 直す筋

1. **compose プロジェクト名を envId 由来にする**（`banto-env-<envId>`）。envId は一意なので
   衝突しなくなる。名前は「二重の守りの片方」で所有の真実は台帳（`STATE_FILE`）が持つ、と
   `projectName` 冒頭のコメント自身が書いているので、思想は変わらない。
   **移行**：稼働中の環境は旧名のプロジェクトを持っているので、既存 handle の project を
   そのまま使い続けられること（handle に保存済みの名前で操作する形）を確かめること。
   孤児検出（`banto-env-` 接頭辞での照合）も両方の綴りを拾えるようにする。
2. **healthcheck が公開ポートの実際の応答を見る**。`compose ps` は「コンテナが動いている」
   ことしか言えず、**その env のものかどうかを言えない**。公開している env については
   exposed URL / ポートを実際に叩き、応答で答える。見ていれば今回は嘘をつかずに済んだ。
   叩けなかったものを「使えます」に丸めないこと（分からないなら分からないと答える）。

1 が根治、2 は 1 とは独立に効く防壁（別の理由でコンテナがすり替わっても検出できる）。
**両方入れる**のが筋だが、順序は 1 → 2。

## 受け入れ（職人へ渡した3本）

- (a) 同じ taskId・同じプロファイルで2つ立てても、先に立てた側が壊れない
- (b) 実体が消えた env の healthcheck が「使えます」と答えない
- (c) **dev 環境を立てたまま、同じ taskId で test プロファイルの `env.verify` を回しても dev が生き残る**
  （使い捨て側の `compose down` の効き先が、自分の env に閉じていること）

## 併せて考えること（別件にしてよい）

Kobo が自動で立てた dev 環境が、番頭から**見えていなかった**。`env.list` には出るはずなので、
レビュー用に環境を立てる前に一覧を見る運用でも防げる。ただし機構側で防げるものを運用で
支えるのは筋が悪いので、**「同じ taskId で既に立っている」ことを provision が知らせる**
（拒む必要はない・警告で足りる）ほうが穏当。
