# 広いスコープの1本が、工場ぜんぶを直列化する

## 何が起きたか（実測・2026-08-16）

`task-0159`（決定番号を本当に一意にする）のスコープはこうなっていた:

```
docs/adr/**, packages/**, docs/spec/**, tests/**, work/inbox/**
```

**`packages/**` を丸ごと押さえている。** Kobo のゲートはスコープ重複で待たせるので、
この1本が queued〜implementing で居る間、**packages 配下を触る仕事は1本も動けない**。

止まっていたもの（03:12 時点）:

| task | 何をするか | 待ち |
|---|---|---|
| task-0160 | バックログの土台 | 0159 |
| task-0161 | 会話の記録を原子的に書く（**OOM で記録が壊れる事故の直し**） | 0159, 0160 |
| task-0162 | 追記ログの千切れ行の検出 | 0159, 0160, 0161 |
| task-0164 | 縮む書き戻しを拒む（**33時間欠落の直し**） | 同上 |
| **task-0165** | **アイドルな会話のセッションを畳む（OOM の本命の直し）** | 同上 |
| task-0166 / 0167 / 0168 | 封じ込め設定の書き戻し・壊れた行の退避・職人の同時本数の上限 | 同上 |

`task-0161` と `task-0162` は **queued のまま2時間**で「止まっています」の知らせが鳴った。
経緯を読むと**詰まってはいない**（先頭の 0159 がゲートを通っていなかっただけで、
03:12:37 に通過して職人が着手した）。**待てば進む。ただし待ちが長い理由がスコープの広さだった。**

さらに `task-0159` は `review: po` なので、**実装が終わってもPOの判断を挟むまで列は解けない**。

## なぜ起きたか

**スコープは「壊してよい範囲の宣言」であると同時に、「他の仕事を止める範囲の宣言」でもある。**
後者は積むときに見えない。決定番号の振り直しは**実際には docs と一部のコードしか触らない**が、
「どこに決定番号が散っているか分からない」という不確かさを、**`packages/**` と書いて埋めた**。
その1文字あたりの代償が、**工場全体の直列化**だった。

積んだのは番頭（幹「banto開発」）自身である。**契約の書き方の誤りであって、機構の故障ではない。**

## どうするか

### 1. 積み方（いますぐ効く・番頭の作法）

- **スコープを書くとき、「これは他のどの仕事を止めるか」を必ず一度考える。** 特に
  `packages/**` `tests/**` のような**層まるごとの glob は、工場を1本ずつの直列にする**。
- **分からないから広く取る、をやめる。** 触る場所が分からないなら、**先に調べる仕事**（職人への
  委譲。工場を通さない）で場所を確定させてから、狭いスコープで積む。
- **広いスコープが本当に要るなら、それは「工場を占有する仕事」だと自覚して積む**——
  急ぎの直しが列に並んでいないことを確かめてから積むこと。

### 2. 機構（案。実装は別途）

- **積むときに、そのスコープが**「いま列に並んでいる何本と重なるか」**を返す。**
  `kobo.enqueue` の戻りに1行あればよい（「このスコープは queued 6本と重なります」）。
  積んだ後に `kobo.task` の待ち行列を読むまで気づけない、というのが今回の形だった。
- **重なりの粒度**：いまは glob の文字列で重なりを見ているため、`packages/**` と
  `packages/banto-host/src/thread-store.ts` は必ず重なる。**実際に触ったファイルで解けるのは
  着手後**なので、ゲートの段階では文字列で判定する以外にない——だからこそ 1（積み方）が効く。

## 出所

- `kobo.task({taskId: "task-0159"})` / `kobo.task({taskId: "task-0160"})` の経緯（2026-08-16 03:1x）
- 「2件が止まっています」の知らせ（task-0161 / task-0162、queued のまま2時間）
- 幹「banto開発」の判断（2026-08-16）：**動いているものを止めて契約を直すと監査もやり直しになり、
  かえって遅くなる。よって 0159 のスコープは今回は直さない。この事実を記録に残し、次の積み方に効かせる。**

## 2026-08-16 追記：**PO が絞り込みを承認したが、それでも狭められなかった**——スコープは後から狭められない

PO が明示的に承認した（「2もいいですよ、そうして」）。内容は
`packages/**` → 実際に触る2ファイル、`tests/**` → `tests/acceptance/**`。
にもかかわらず **task-0159 のスコープは狭めなかった。** 判断したのは枝「決定番号の一意化」の番頭で、
理由は3つ。**PO の承認が足りなかったのではなく、機構の側で成立しない**という理由である。

### 1. 狭めた瞬間、**もう触ってしまった差分がスコープ外になる**

`kobo.amend` は「スコープからパスを取り除く」向きなら番頭でも通る。**しかしそれは
「これから触らせない」ではなく「その枝の既存のコミットを違反にする」**。実測（`git diff main -- packages/`）:

```
packages/banto-host/src/llm-tools.ts               |  2 +-
packages/banto-web/src/views/LlmRegistryViewer.tsx |  4 +-
```

すでに触っている。`packages/**` を外せば、**マージ前ゲートのスコープ検査が確実に落とす**。
「純粋な削除だから安全」は、**まだ何も触っていない枝でしか成り立たない。**

### 2. コメントを元に戻せば、今度は**受け入れ条件が落ちる**

a3 は「振り直した番号に外部参照（`packages/**`・`docs/spec/**`・`tests/**`・`docs/adr/**` の相互参照）が
追随している」ことを求めている。packages のコメント3箇所を戻すと a3 が破れる。
**受け入れ条件そのものを緩めるのは PO の判断**で、しかも**基準を動かすと監査が無効になる**。
どちらへ転んでも落ちる。

### 3. タイミング——**そのとき task-0159 は `auditing` だった**

スコープの改訂は監査を無効にして implementing へ戻す。**PO が着地を待っている最中に、
通りかけの監査を捨てて振り出しへ戻す**ことになる。栓は「狭める」でも抜けるが、**着地でも抜ける**。
残り一手で着地するものを、栓を抜くために止めるのは本末転倒だった。

### だからここから引くべき規則

> **スコープは、積む瞬間にしか決められない。**
> 職人が1行でも触ったあとでは、広げるのは PO の判断、**狭めるのは機構が禁じるのと同じことになる**
> （既存の差分が違反になるため）。つまり **§1「積み方」は「気をつけよう」ではなく、唯一の機会である。**

`kobo.amend` の説明は「スコープからパスを取り除く向きは番頭が通せる」と読めるが、
**実際に安全なのは、その枝がまだそのパスを触っていないときだけ**である。
道具の説明にこの但し書きが無いのは、次に同じ判断をする者を必ず迷わせる（§2 の機構案に追加）。

### この一件で実際に採った手

**何もしない（task-0159 はそのまま着地させる）。** 栓は着地で抜ける。
PO の承認は無駄にはならず、**「次に同種の仕事を積むときは狭く積む」という形で効かせる**——
決定番号の振り直しが実際に触ったのは、この17ファイルだけだった:

```
docs/adr/*.md（5本）, docs/spec/chat-ui.md,
packages/banto-host/src/llm-tools.ts, packages/banto-web/src/views/LlmRegistryViewer.tsx,
tests/acceptance/decision-number-uniqueness.spec.ts, tests/acceptance/llm-registry.spec.ts,
work/inbox/improvement/imp-0073-decision-number-renumbering.md
```

**`packages/**` も `tests/**` も要らなかった。**次に「散らばった参照を追随させる」仕事を積むときは、
**先に grep で場所を確定させ、ファイルを名指しで並べること**（§1 のとおり）。
