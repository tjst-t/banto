# 権限で失敗を作る試験は、root で走る器では成立しない（**ゲートが実際に捕まえた例**）

## 何が起きたか（2026-08-16・task-0161）

`task-0161`（会話の記録を原子的に書く）は、**実装も監査も通り、PO が面から承認したあと**、
**マージ前ゲートで6本すべての検証が落ちた**（`verify_failed:a1〜a6(exit=1)`）。

ゲートの実ログ：

```
✖ [a1] ThreadStore.replace() が途中で失敗しても、元の記録は1バイトも変わらない
  AssertionError [ERR_ASSERTION]: root だと権限による失敗を作れない
      at tests/acceptance/thread-store-atomic-write.spec.ts:136:12
✖ [a2] ThreadStore.writeIndex() が途中で失敗しても、元の index.json は1バイトも変わらない
  （同じ理由・:159:12）
```

**原因は実装ではなく試験の作り方。** 試験が **`chmod` で書き込み権限を落として「書き込みの失敗」を作ろうとしていた**。

- **職人のワークツリー**は `ubuntu` 権限で走るので、`chmod` は効く → **通る**
- **マージ前ゲートの器（docker）は root で走る**ので、権限を落としても書けてしまう → **失敗を作れず、試験自身が assert で落ちる**

## なぜ記録する価値があるか

1. **これは「緑が信用できない」の逆向きの実例である。**
   今日は「機械が見ていないのに緑に見える」（inc-0076）を追っていたが、この件は
   **人が読んでも気づきにくい環境差を、機械（ゲート）が捕まえた**。**関所は仕事をしている。**
   承認は「差分の中身」を見るものであって、**別の環境で走らせたときの挙動は、承認では捕まらない**
   ——だから関所は承認の後に回る（決定57）。**この順序が効いた実例として残す。**
2. **同じ落とし穴は繰り返す。** 試験で失敗を作る手段が
   **「権限」「ディスクフル」「読み取り専用マウント」**のような**環境の性質に依存**していると、
   **走らせる器が変わった瞬間に成立しなくなる**。しかも**落ち方が「試験が落ちる」なので、
   本物の不具合と見分けがつきにくい。**

## どう書くべきだったか

**失敗は、環境ではなく口から作る。** `task-0161` の実装には最初からその口がある：

```ts
// packages/banto-core/src/atomic-write.ts
export interface AtomicWriteOps { mkdirSync/openSync/writeSync/fsyncSync/closeSync/renameSync/rmSync }
export function writeFileAtomicSync(file, data, ops = nodeAtomicWriteOps): void
```

**`ops` を差し替えて `writeSync` / `renameSync` を throw させれば、root でも一般ユーザでも同じ結果になる。**
（実装のコメントにも「**差し替えは試験のためにある**」と書いてあった。**使われていなかっただけ**。）

**作法として**：

- **試験は「誰が走らせても同じ結果になる」ように書く。** 権限・ディスク容量・時計・ネットワークに
  依存した判定を入れない（どうしても要るなら、**その環境でなければ skip** し、**skip したことを出す**）。
- **失敗の注入は、実装が持つ差し替え口から行う。** 口が無いなら、**口を作る方が試験を歪めるより安い**。
- **ワークツリーで通っただけで「通った」としない。** ゲートは**別の器・別の権限**で走る。

## 併せて記録：**`governance` を外すために積み直さない**（2026-08-16 の判断）

`governance: true` を付けて積んだタスクは、**PO のレビューが必須**になる（`review-policy.ts:302`）。
PO は同日「明示的に頼むとき以外レビューは省略してよい」と決めたが、**`kobo.amend` では `governance` を
変えられない**（訂正できるのは題・本文・スコープ・受け入れ・検証・環境・レビュー段・model_tier）。

したがって道は**「一押しをもらう」か「積み直す」の二択**になる。**このときは一押しが正しい**：

> **積み直すと新しい id は列の最後尾に行く**（ゲートは作成順で古い方を先に通す）。
> **本命のタスクを最後尾へ送ることになり、着地が何時間も遠のく。一押し3回の方がはるかに安い。**

**積み直しが正しいのは、待ちの列が短いか、契約そのものを変えたいときだけ**である。
