# banto は認証を持たないのに `0.0.0.0` で待ち受けている——前段で守られているかを、誰も確かめていない

## 事実だけ（2026-08-16 実測）

`task-0178` の作業で稼働機の systemd ユニットを読んだところ、こうなっていた。

**リポジトリ（`deploy/banto.service`）のコメントは、こう書いている:**

> **既定では 127.0.0.1 しか待ち受けない**（Banto は認証を持たないため）。
> 外に出すときは前段（Caddy 等）から 127.0.0.1:4100 へ中継すること。
> 前段を置かずに直接公開したい場合だけ BANTO_HOST_BIND を広げる（自己責任）。

**稼働機は、広げてある:**

```
# /etc/systemd/system/banto.service.d/override.conf
Environment=BANTO_HOST_BIND=0.0.0.0
```

`systemctl show banto.service -p Environment` にも `BANTO_HOST_BIND=0.0.0.0` が出る。
**この行はリポジトリのどこにも無い**（`imp-0076`）。

## 何が確かめられていないか

**「前段（Caddy 等）や FW で守られている」という前提が、本当に成立しているかを確認した人が居ない。**

- 番頭は**確認していない**。ユニットを読んで `0.0.0.0` だと分かっただけである
- `override.conf` に**なぜ広げたのかの理由が書かれていない**（コメントは
  「モデルの指定は削除した」の話だけで、`BANTO_HOST_BIND` には何も添えられていない）
- いつ・誰が・何のために広げたのかも、この起票の時点では追えていない

**推測で「たぶん Caddy が前に居るから大丈夫」とは書かない。**
確かめた人が居ない、というのがいま言える全部である。

## なぜ急ぐ側に置くか

banto は**認証を持たない**。到達できれば、会話・記憶・帳簿が読め、
**職人を起こせて任意のコードが動き、`place` の書き込み範囲に書ける**。
つまり**到達性がそのまま全権**になる。だから「前段が居るはず」が外れていたときの損害が大きい。

なお共有ブラウザ（`task-0178`）が入ると、そこに
**サンドボックス無しの chromium を任意の URL で開ける口**が加わる。
これ自体は PO 承知の上の判断だが、**到達制御が効いていることが前提**になっている。

## 何を確かめればよいか

1. **外から実際に届くのか。** 別のホストから `:4100` へ TCP が通るか
   （通るなら、それが答え）
2. **前段が居るのか。** Caddy 等のリバースプロキシ設定と、そこに認証が掛かっているか
3. **クラウド側の FW / セキュリティグループ**で `4100` が閉じているか
4. **なぜ `0.0.0.0` にしたのか**（履歴・経緯）。理由が「Caddy から届かせるため」なら、
   前段が `127.0.0.1` を向けば `BANTO_HOST_BIND` は戻せる

## 直す向き（案）

- **守られていた場合**：`override.conf` に**なぜ広げたのか・何が前段に居るのか**をコメントで書き、
  リポジトリにも書き戻す（`imp-0076`）。**「理由の書かれていない公開設定」を残さない**
- **守られていなかった場合**：`BANTO_HOST_BIND` を戻し、前段経由にする。
  戻すのは drop-in の1行なので、操作としては軽い
