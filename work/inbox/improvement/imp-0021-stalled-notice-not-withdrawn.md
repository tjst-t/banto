# 何が起きたか

2026-08-14 09:24、工場デーモン（`banto-daemon.service`）を新しいコードで再起動した直後に、
滞留検知（task-0148 の実装。realign 第2便で main に入った）が最初の走査を行い、
`task-0100` が `review-ready` のまま 23時間24分 であるとして**取次へ判断待ちを1件積んだ**。

ところが番頭は同じ秒に凍結タスク14本の始末を行っており、帳簿はこうなっている:

```
09:24:48.229  task_stalled          — review-ready のまま 23時間24分
09:24:48.952  state_transitioned    — review-ready → closed（settled_outside:landed_elsewhere）
```

**0.7秒差**。知らせが積まれた時点では正しかったが、直後に状態が動いたため、
取次には**既に片が付いたタスクについて「待てば進むのか、詰まっているのかを見分けてください」と
求める札**が残った。押しても、もう手は無い（`kobo.settle` 済み）。

# なぜ直すか

これは滞留検知そのものの欠陥ではなく、**知らせの寿命が管理されていない**という穴である。
放っておくと、次の性質を持つ:

- 判断待ちの件数が、実際には判断の要らないもので水増しされる
- 「取次に出ているものは、まだ手が要る」という信頼が壊れる。これは ADR-0022 で
  「知らせは判断待ちの件数に数えない」と分けたのと同じ動機であり、同じ理由で放置できない
- 頻度は低くない。滞留は「長く動いていないもの」に出るので、**番頭が棚卸しをして
  まとめて片付ける瞬間**とぶつかりやすい（まさに今回）

# どう直すか（案）

タスクの状態が動いたら、そのタスクについて出ている**未応答の知らせを自動で取り下げる**。

- 取り下げの契機は `state_transitioned`。対象は「そのタスクを出所とする、まだ答えの出ていない札」
- 取り下げた札は消さず、「状況が変わったため取り下げ」と分かる形で答え済みの側へ落とす
  （記録は消えない、という既存の作法に合わせる）
- `task_stalled` に限らず、**タスクを出所とする判断待ち全般**に効かせるのが筋
  （マージ衝突の知らせなども、タスクが畳まれれば同じことが起きる）

# 確かめ方（受け入れ基準の案）

1. `review-ready` のタスクに滞留の知らせが積まれたあと `kobo.settle` すると、
   その知らせが未応答のまま残らない
2. 取り下げられた知らせは記録には残り、「なぜ取り下げられたか」が読める
3. 状態が動いていない間は取り下がらない（滞留の知らせは今までどおり出続ける）
