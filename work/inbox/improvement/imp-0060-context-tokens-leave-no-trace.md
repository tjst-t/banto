## 背景

imp-0051 で contextTokens の算出を `result.usage` の足し算から `query.getContextUsage()` へ入れ替え、
稼働ホスト（2026-08-15 13:59:59 UTC 起動、main `46f7cfb0`）で効いていることを実測で確かめた。
確かめ方は「稼働中のプロセスへ WS で繋いで `context_state` を読み、SDK の会話記録
`~/.claude/projects/.../<backendSessionId>.jsonl` の生 usage と突き合わせる」というもので、
**プロセスが生きている間しか測れない**。

その過程で、次の2つが分かった。

## 何が困るか

### (1) contextTokens がどこにも永続化されていない

`packages/banto-host/src/server.ts` でメモリ上の Map に入り、WS の `context_state` として配られるだけ。
`journalctl -u banto` にも出ないし、会話の jsonl にも入らない。

- 再起動すると過去の値は消える。
- 「なぜあの章はあそこで畳まれたのか」を**後から追えない**。imp-0051 の事故（9.7倍の過大評価で
  不要な畳みが起きた）を突き止めるのに、PO 側の記録と現物の突き合わせで何往復もかかったのは
  これが理由。
- 次に閾値まわりで何か起きたとき、同じ苦労を繰り返す。

### (2) 落とし先に落ちたときの印が無い

`getContextUsage()` が取れなかったターンは、黙って落とし先（`lastIterationTokens`）へ落ちる。
ログも印も出ない。

今回は「落とし先は output_tokens を足す／本命は足さない」という差で見分けられたが、
これは偶然そう見分けられただけで、実装が変われば使えない。
**測り方が静かに劣化しても誰も気づかない。**

## 直しの当たり

- (a) `turn_end` のときに1行だけ残す（threadId / chapterId / contextTokens / window / 経路（本命か落とし先か）/ 道具の呼び出し回数）。
  置き場は既にある台帳（`/var/lib/banto/turns.jsonl`）が素直。**値の意味を変えないので安全。**
- (b) 落とし先へ落ちたことを、その1行の「経路」に出す。加えて、落ちた回数が続くようなら知らせる。
- (a) だけでも (2) は片付く。まず (a) を推す。

## やらないこと

- 閾値・窓の選び方には触らない（imp-0051 で直したばかりで、実測でも正しく効いている）。
- 会話の jsonl に混ぜない（会話の記録と観測の記録を混ぜない）。

## 根拠（2026-08-15 の実測）

稼働ホストの報告値は、そのターンの**最後の API 呼び出しのプロンプト側**（input + cache_read + cache_creation）と
5スレッドすべてで差 0 で一致した。同じターンを旧式で再計算すると 14〜28 倍に膨れる
（thread-105: 旧式 2,147,915 に対し報告 103,266 ＝ 20.8倍。道具22回のターンでは 28.3倍）。
再起動後45分で章畳みは 0 回（旧コードなら閾値 600,000 を10ターンが超えていた）。
