# 番頭が書いた記録が git に入らないまま溜まる——書く経路とコミットする経路が分かれている

## 何が起きているか

2026-08-15、PO の「起票済みですか？　起票しているように見えない」という指摘から確認したところ、
**書かれているだけでコミットされていない md が 30 件溜まっていた**。imp-0036（7,568 バイトの実体）に
対して `git log` は「コミットなし」を返す。作業ツリーを片付けたら消える置き方であり、
**履歴から見れば起票が存在しないのと同じ**である。

内訳（この起票の時点で cfab21dc / c70dc2ad / 86346af1 / 895da7fe として履歴に入れた）:

- `work/inbox/improvement/` の imp-0023〜0053 のうち 25 件
- `work/inbox/incident/inc-0074-model-select-e2e-broken.md`
- `docs/adr/adr-0026-one-entrance-contract-from-the-tool.md`、`docs/adr/adr-0025-notices-do-not-wake-the-trunk.md`
- `docs/proposals/2026-08-15-trunk-availability-plan.md`（未コミットの改訂）
- `work/tasks/task-0151.md`

**初発ではない。** `git log work/tasks` の直近は `7a9a59a3 2026-08-14 docs(work): 起票と記録をまとめて残す
（inc-0065/0066/0068/0069・imp-0019〜0022・task-0149/0150）` で、**前日にも同じ掃除をしている**。
人手の掃除でしか履歴に入らないので、掃除と掃除の間はいつでもこの状態になる。

## なぜ起きるのか（構造）

**書く経路とコミットする経路が分かれていて、書いた時点で満足して終われてしまう。**

1. **番頭は `file.write` で書ける**（place `banto` は `work/**` `docs/**` が書込可）。
2. **番頭は git の書き込みを持たない**（commit / push / branch は道具に無い）。コミットは職人への
   委譲が必要で、これは番頭が能動的に思い出さないと起きない。
3. **機構は誰もコミットしない。**

現物の裏取り（2026-08-15）:

- **タスク（task-NNNN）は Kobo が書く**が、**Kobo はコミットまではしない**。
  `packages/banto-daemon/src/task-record.ts` の冒頭に「以前このファイルは入力だった——番頭が md を
  書き、watcher が読んで積んだ。いまは記録である。契約は kobo.enqueue の引数から凍り（決定62c）、
  Kobo が採番して書き出す」とある。書き手は `fs` だけで、banto-daemon に `git commit` を呼ぶ箇所は
  **1つも無い**（`commit` の一致は merge-queue の職人ブランチ取り込みのみ）。
- **改善（imp-NNNN）・インシデント（inc-NNNN）には Kobo の口が無い。** 起票の口は `kobo.enqueue`
  （task 専用）だけで、`work/inbox/` へ書く経路は機構側に1箇所しかない——
  `packages/banto-host/src/bin.ts:294` の学習層陳腐化 incident で、そこには
  「リポジトリの `work/inbox/incident/` に書きたくなるが、**番頭はそこへ書けない（決定38b）**ので
  ホストのデータ置き場に書き、ログにパスを出す」と書いてある。
- **決定38b の前提はいまの place 設定では崩れている**（`work/**` は書込可）。結果、
  「書けない前提で機構がよそへ置く」と「書けるので番頭が直に書く（が履歴に入らない）」が同居している。
- banto 自体は Kobo の積む口・マージキューを PO 指示（2026-08-13）で停止しているため、
  そもそも Kobo を通していない。task-0151 も Kobo の帳簿に無く（`kobo.task` が「工場にありません」）、
  番頭の手書きだった。

## どう直すか

### 案 (a) `file.write` の対象が `work/` `docs/` ならコミットまで機構がやる

**採らない。** 番頭の書き込み全部に git 書き込みを与えることになり、他の枝の職人が同じ作業ツリーで
動いている最中に勝手なコミットが入る（2026-08-15 時点で枝が3本並走していた）。取り違えると
他の枝の作業を横取りする。

### 案 (b) 起票専用の口を足す（`kobo.file_issue` 相当）

imp / inc / proposal を**採番・記録・コミットまで機構がやる**。task と同じ建て付けに揃い、
番頭は「書く」ではなく「積む」だけになるので、書き逃げが原理的に起きない。
**id の衝突（imp-0055）も採番が機構に寄れば消える。** ただし実装は重い。

### 案 (c) 取り残しを検知して知らせる

`work/` `docs/` に未追跡・未コミットの記録が一定件数・一定時間 滞留したら知らせを立てる。
軽いが、知らせを無視できるので「書いた時点で満足する」構造そのものは残る。

## 推す案

**(c) を先に入れ、そのあと (b)。(a) は採らない。**

- (c) は小さく、今日のような「30件溜まってから気づく」を「数件で気づく」に変えられる。
  知らせは T3（adr-0025）の設計で枝に落ちるので幹を塞がない。
- そのうえで (b) を入れ、採番と記録とコミットを機構側へ寄せる。(b) が入れば (c) は保険になる。

## 受け入れの目安

- 記録類（`work/**` `docs/**` の md）が未コミットで N 件以上／M 時間以上 滞留したら、番頭に知らせが届く
- 知らせから「どのファイルが取り残されているか」がそのまま読める
- (b) まで進んだ場合、imp / inc を積む口が採番と記録の作成とコミットを一度に行い、番頭は md を書かない

## 出所

2026-08-15、PO の指摘（「起票済みですか？」）から枝「起票の未コミット」で調査。
溜まっていた 30 件は同日 cfab21dc / c70dc2ad / 86346af1 / 895da7fe で履歴に入れた（push はしていない）。

## 2026-08-16 追記：**この構造が、マージキューの着地そのものを潰していた**

いちばん重い実害が出たので残す。**「未追跡の起票を手でコミットする」という手当てが、
そのままマージキューの着地を壊す**——2つは無関係に見えて、1本の因果で繋がっている。

### 因果の鎖

1. Kobo は task の md を**書くがコミットしない**。`imp-` / `inc-` には Kobo の口が**無い**。
   番頭は git の書き込みを**持たない**（上の「なぜ起きるのか」のとおり）
2. → **未追跡の起票が溜まる**（2026-08-16 は33件。うち番頭が採番で踏んだ衝突が5組）
3. → **誰かが手で `main` へコミットするしかない**（今日それを実施した）
4. → **マージキューは `rebase → マージ前ゲート（全量1回で約8分）→ `git merge --ff-only`` の順に回す。
   その8分の間に main が1コミットでも進むと、ff マージが「枝が main の子孫でない」で失敗し、
   8分ぶんの検証を丸ごと捨ててタスクを `failed` に落とす**
5. → **さらに、手でコミットする者は他人の未コミットの作業を巻き込む。**
   `git add` した範囲に、別の担当が書きかけで置いていた md が入る

### 実測(1)：マージキューの着地が3回潰れた（task-0159・2026-08-16）

**中身は無罪で、マージ前ゲートは通過している。**

| 回 | ゲートの結果 | ゲート中に main へ入ったコミット |
|---|---|---|
| 1 | 通過［base 881371a8］ | `881371a8 Merge branch 'feat/browser-chromium-launcher' into main`（**キュー外の手動マージ**） |
| 2 | 通過 | `00031cf0 fix(work): inc-0077 の id 衝突を解消（しきい値の起票を inc-0078 へ振り直し）`（**この起票の手当てそのもの**） |
| 3 | 通過 | （静粛の依頼が届く前に同じ形で失敗） |

**2回目に負けた相手は、まさに「id 衝突を手で直すコミット」である。**
imp-0054 が残っている限り誰かが手でコミットし続け、そのたびにマージキューが着地に失敗する。

### 実測(2)：他人の作業が巻き込まれて main に入った（同じコミット `00031cf0`）

同じ `00031cf0` に、**別の担当（枝「決定番号の一意化」の番頭）が手元で書いていた
`work/inbox/improvement/imp-0055-record-ids-collide.md` への追記 約68行が一緒に入った。**
中身は「一意性を直すタスク自身が id を衝突させた」の分析で、**結果としては正しい内容だったので
そのままにした**（巻き込んだ側も revert していない——他人の作業を壊さない判断として正しい）。

**しかしこれは運が良かっただけである。** 書きかけだったら、途中の文章が履歴に入っていた。
**手でコミットする者は、いま作業ツリーに何が置かれているのかを知らない**——
**番頭が複数の枝で同じ作業ツリーへ書いている**以上、`git add` の範囲は必ず他人の手元を含みうる。

### 機構が自分で「起きないはず」と書いている

`packages/banto-daemon/src/merge-queue.ts:497` にこうある：

> `Fast-forward merge failure is unexpected after a successful rebase+gate.`

**想定外の並びを踏んでいる**ということ自体が、直すべき合図である。
直し（ff の直前に main を取り直して rebase し、失敗したらその場で1回だけ再試行する）は
**枝 thread-129 が担当**しており、あちらは自分のコミット `00031cf0` が原因だったことを自分で突き止めている。
**このタスクの実測は、その起票の優先度の根拠として参照してよい**（実例3回・想定外と書かれている事実）。

### だから

**根治はこの imp-0054 の案 (b)（起票の採番・記録・コミットを機構がやる）である。**
「気をつけて手でコミットする」は解にならない——**手でコミットすること自体が、
マージキューの着地を潰し、他人の書きかけを履歴に押し込む**からだ。
バックログの土台は既に着地しているので、**残りは口を配ることだけ**（`backlog.file` / `backlog.list` /
`backlog.update`）。**急ぐ根拠が2つ増えた。**
