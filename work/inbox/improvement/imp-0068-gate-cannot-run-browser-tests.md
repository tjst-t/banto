## 事実（番頭が env.verify で実測・2026-08-16）

`test` プロファイル（`docker/test.yaml` / `docker/Dockerfile.test` = `node:24-alpine`）の中で

```
npx playwright test --reporter=line
```

を回すと **152件すべて失敗**する。理由は中身と無関係で、全件これ：

```
Error: browserType.launch: Executable doesn't exist at
  /root/.cache/ms-playwright/chromium_headless_shell-1234/chrome-headless-shell-linux64/chrome-headless-shell
```

`Dockerfile.test` が入れているのは `git make g++ python3 docker-cli` だけで、
**ブラウザは入っていない**。さらに土台が **alpine（musl）** なので、
`playwright install` を足しても公式の chromium ビルドは動かない（musl 非対応）。

**器の全4リビジョン（2026-08-07 の導入時から今日まで）を `git show` で確認済み——
ブラウザが入っていた時期は一度も無い。**「昔は動いていた」という理解は誤り。

## なぜ問題か

1. **受け入れ条件に `npm run test:ui` と書いたタスクは、実装が正しくても必ずゲートで落ちる。**
   落ち方が「152件全滅」なので、原因を追う人は自分の変更を疑ってしばらく溶かす。
2. **UI の受け入れ条件を機械で守る手段が、いまは無い。**
   画面の変更は職人のワークツリー（ホスト側）で回した結果を報告に貼るしかなく、
   それは「職人の主張」であって機構が返した事実ではない（I1 の線を割っている）。
3. **誰も見ていない赤が溜まる。** 固定 SHA `fc673a71` で5回測ったところ、152件中
   **恒常赤16件＋間欠1件**。工場に届かないので、誰も拾っていなかった
   （`inc-0071` / `inc-0074` / `inc-0078` に分けて記録した）。

### 3. の「過去タスク」の疑いは決着した（2026-08-16）

`task-0077` / `0078` / `0086` / `0087` / `0088` は **Kobo の帳簿に存在しない**
（banto の帳簿の最古は `task-0089`）。着地はいずれも単親の直接コミットで、
**マージ前ゲートを一度も通っていない**。`status: done` は人の自己申告だった。
＝「当時は通っていた」のではなく「**一度も走っていない**」。詳細は `inc-0076`。

## 決着（幹の判断・2026-08-16）

**案(a) を採る——ブラウザ専用の検証プロファイルを別に立てる。**

- 決め手は「**既存の `test` を触らない**」こと。あれは今日ようやく
  「素のワークツリーで2400件 fail 0」に持っていったばかりで、いま土台を変えると地盤が揺れる
- (b)（`Dockerfile.test` を Debian 系へ移す）は**全タスクのゲートが重くなる**ので採らない
- (c)（ゲートで見ないと決める）は放置が続くので採らない

**実装**

| | |
|---|---|
| `task-0194` | `docker/browser.yaml`（公式 playwright イメージ・タグ固定）と `meta/environments.yaml` の `browser` プロファイル |
| `task-0195` | 最初の利用者。`environment: browser` で `tests/trunk-branch.spec.ts` の恒常赤11件を直す |

**受け入れ条件には「実行件数が 0 でないこと」を必ず入れる**——空振りで緑にならないように
（`inc-0076` の教訓）。

**「職人がホストで回した出力を報告に貼る」は採らない。**
それは自己申告で緑にすることであり、この件が問題にしているものの再生産だからである。

## 分かったことの副産物：プロファイルの鶏と卵

マージ前ゲートは**プロファイル定義を main のリポジトリから読む**
（`merge-queue.ts:446` が `repoPathForProfile: repoPath` を渡している）。
つまり **プロファイルを足すタスク自身は、そのプロファイルを自分のゲートでは使えない**。
`task-0194` はこの制約のため「設定が妥当か」までしか機械で見ておらず、
「ブラウザ試験が実際に走る」ことは**番頭が `env.verify` を職人のワークツリーへ直接回して**確かめる。

この鶏と卵は他のプロファイル追加でも起きるので、別途起票する価値がある（未起票）。

## この起票を閉じる条件

`task-0194` と `task-0195` が着地し、**ブラウザ試験がマージ前ゲートの中で実際に走って緑になった**とき。
それまでは open のまま置く（`inc-0038` が resolved のまま実は直っていなかった例があるため、
**着地の確認なしに閉じない**）。
