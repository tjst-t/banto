# 子プロセスの記録が「起動直後の1枚」しかないので、OOM のときに誰が食べていたか分からない

## 内容

`recordChildProcesses` は**職人を委譲した直後に1回だけ**走り、台帳の
`childProcesses` を上書きして `worker_child_pids` を1本積む。

ここに捻れがある。

> **記録しているのは「起動直後」なのに、問いが立つのは「OOM のとき」。**

`settleMs`（走査を畳むまでの猶予）をいくら伸ばしても、正確になるのは
「起動から数秒間の姿」だけで、**30分後に `claude` が生やしたプロセスは
永久に記録されない**。inc-0066 の目的（OOM のときに誰が食べていたかを
特定する）には、猶予の調整では届かない。

なお **`child-pids.ts` の打ち切り条件そのものは 2026-08-14 に直してある**
（猶予を「走査の回数」で持っていたため `intervalMs` に引きずられて 200ms に
縮んでいた。時間 `settleMs` で持つ形に変え、既定 1000ms は据え置き）。
本件はそれとは独立で、「1回の走査で取りこぼさない」ではなく
「**一度きりの走査をやめる**」話。

## 直し方の候補（未決）

| 案 | 中身 | 評価 |
|---|---|---|
| A. 問われた時に走査 | `worker.list` / `get` のたびに `/proc` を見る | **却下**。`list` は UI が頻繁に叩く。呼ぶ側の都合で重さが変わる |
| B. 生きている職人を定期的に採り直す | 数十秒ごとにサンプリングし、台帳へ**併合**（上書きしない） | **本命。ただし範囲が大きい** |
| C. OOM のときに走査 | 上限に当たった瞬間に採る | **成立しない**。`memory.oom.group` は袋ごと殺すので、走査できる頃には全員死んでいる |

## なぜ番頭が独断で入れなかったか（D1）

B は **`worker_child_pids` を職人×時間で積むことになる**。イベントログは
外に累積し、積んだものは消せない——D9 でいう「外に累積する副作用」に当たる。
決めどころが3つあり、いずれも番頭の一存で決めるところではない。

1. **どれくらいの間隔で採るか**（走査コストと、取りこぼしの粒度の釣り合い）
2. **毎回イベントを積むのか、変化があったときだけか**（累積量が変わる）
3. **台帳は最新1枚か、履歴か**（「ピークのとき何が居たか」を残すなら履歴が要る）

## 優先度についての見立て

**急がない。** OOM を止める本筋は cgroup による隔離
（`banto-worker-pool.service` に `Delegate=yes` を足し、工房が職人ごとに
子 cgroup を切る。→ imp-0011）であって、子 pid の記録はその**補助**にすぎない。
隔離が入れば「VM 全体を巻き込む」ことは起きなくなり、誰が食べていたかは
cgroup の側から分かる。本件を先に入れても、事故そのものは止まらない。

## 確かめていないこと

- `/proc` の定期走査が実際どれくらいの費用になるか（職人が数本のときの実測）
- 台帳へ「併合」する形にしたとき、死んだ子の pid をいつ落とすか
