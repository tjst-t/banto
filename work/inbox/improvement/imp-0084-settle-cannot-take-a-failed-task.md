# `kobo.settle` が `failed` を受け付けないので、「落ちたが外で決着した」を正しく記録できない

## 起きたこと（2026-08-16・task-0164）

`task-0164`（記録の書き戻しが縮むのを拒む・inc-0075 の再発防止）は、**中身が一度も落ちていない**。

- 実装は最初の試行で完成し、`npm test` が **2476件・失敗ゼロ**
- 番頭が袋の外から `env.verify` で回し直しても**失敗ゼロ**（`4f51d6a1`）
- **にもかかわらず、工場の口で3回落ちた**——監査人が判定を返さずターンを終えた／監査人の起動が 10000ms で timeout ／`worker-pool` への到達が `ECONNRESET`（inc-0082）。**3回とも「確かめる側」の設備であって、実装ではない**

そこで**工場を通さず手で着地させた**（main へ `--no-ff` マージ・`b91df9ff`）。**そのうえで帳簿を畳もうとしたら、断られた。**

```
kobo.settle(task-0164, handled_directly) →
  500: task-0164 を畳めませんでした:
       落ちたまま諦めるなら kobo.abandon（失敗ではないと言うのがこの口の役目です）
```

## 2つの食い違い

### 1. 説明と実装が食い違っている

`kobo.settle` の説明はこう言っている：

> **工場の外で決着したタスクを畳む**（失敗ではない）。中身が別の経路で main に入った・もう要らなくなった・
> あなたが職人へ直接投げて片づけた、のいずれか。**queued / paused / review-ready など、どの途中の状態からでも畳める。**

**`failed` は「途中の状態」に数えられていない。** 説明の「など」を読んで `failed` も入ると思うのが自然だが、
実装は弾く。**読んで分かることと、実際にできることが違う。**

### 2. 意味の側で、記録できない形がある

**`failed` から降ろす口は `abandon`（諦める）しかない。** しかし実際には、

> **落ちた。しかし中身は完成していて、外の経路で決着した。**

という形が起きる。**今日それが起きた。****`abandon` を使えば帳簿には「諦めた」と残り、`settle` は使えない**
——**実際に起きたことを、どちらの口でも正しく書けない。**

**しかも `settle` の `outcome` に並んでいる語は、まさに「落ちた後にこそ起きる」ものである**：
- `landed_elsewhere`（中身は別の経路で入った）… **工場の口が通らないから外で入れた、という形は落ちた後に起きる**
- `handled_directly`（番頭が直接片づけた）… **同上**

**「途中の状態でしか使えない」という制限は、この2つの語の用途と噛み合っていない。**

## なぜ困るか

**帳簿の数が事実とずれる。** `abandon` は「二度と動かない仕事を諦めた」件数として数えられる。
そこに「**完成して main に入った仕事**」が紛れると、**あとから「どれだけ諦めたか」を数えたときに嘘になる。**

そして**紛れたことが読めない**のがいちばん困る。**今回は `reason` に「この口を選んだのは `settle` が
使えなかったためで、諦めたのではない」と明記して仕分け直せるようにしたが、これは書き手が気づいた場合だけ効く。**

## 直しの向き（案・実装していない）

- **`kobo.settle` が `failed` を受けられるようにする。** `landed_elsewhere` / `handled_directly` は
  **落ちた後にこそ起きる**ので、状態で弾く理由が薄い
- 弾く理由があるなら（たとえば「落ちたものを黙って成功扱いにしないため」）、**説明の側を実装に合わせる**
  ——「**`failed` からは使えない。`abandon` を使うこと**」と明記する。**どちらでもよいが、食い違ったままにしない**
- **`abandon` の集計から、外で決着したものを分けられるようにする**のも一案（`outcome` を持たせる等）
