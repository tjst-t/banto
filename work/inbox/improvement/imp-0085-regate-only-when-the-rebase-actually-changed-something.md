# 乗せ直しで実際に差分が生じたときだけ、ゲートを回し直す

## いまどうなっているか（`task-0197` で採った形）

マージキューは `rebase → ゲート（6〜8分）→ ff` の順に回る。ゲートの最中に main が進むと
枝が main の子孫でなくなり、**ff が必ず失敗する**（`inc-0079`。2026-08-16 に3回踏んだ）。

`task-0197` はこれを **「ff の直前に mainline を取り直し、子孫でなければもう一度乗せ直してから ff する」**
で直した。**着地は必ずできるようになる。**

## その代償（**承知の上で選んでいる**）

**乗せ直したあとの木は、ゲートを通っていない。**

ゲートの緑は「**その時点の base の上でなら通る**」という主張でしかない。乗せ直すと base が変わるので、
**git 上は衝突しないが意味の上で壊れる組み合わせ**（片方が消した関数を、もう片方が呼んでいる等）が
**main に載りうる**。

**この危険は、確率は低いが確実にゼロではない。**

## 検討した選択肢と、なぜ (A) を採ったか

| | 形 | 着地 | ゲートの意味 | 代償 |
|---|---|---|---|---|
| **(A)** | **乗せ直して ff**（採用） | **必ずできる** | **一段弱い** | 稀に赤いものが載る |
| (B) | 乗せ直したらゲートを回し直す | **原理的に終わらない**——回している6〜8分の間にまた main が動く | 保たれる | 着地できない（今日の負け方が無限に続く） |
| (C) | ゲート中は main を凍結する | できる | 保たれる | **工場が完全に直列化**（いま解こうとしている問題そのもの） |

**(B) と (C) の代償は毎回確実に発生する。(A) の代償は稀にしか発生しない。** だから (A) を採った
（PO/幹の裁定・2026-08-16）。

## この起票が提案するもの——(A')

**乗せ直しで実際に差分が生じたときだけ、ゲートを回し直す。**

多くの rebase は**ただの再生**である（同じ変更が新しい base の上に、同じ内容で載り直すだけ）。
その場合、ゲートの主張は**そのまま有効**とみなしてよい。回し直しが要るのは、
**乗せ直しで木の中身が変わったとき**だけ——たとえば：

- rebase が**内容の異なるパッチ**を作った（コンテキストのずれを git が吸収した）
- 乗せ直しの相手（新しく入った main のコミット）が、**この枝が触るファイルに触っている**
- 型や依存の境界（`package.json` / `tsconfig` / 共有の型定義）が動いた

これなら **(A) の「必ず着地する」を保ったまま、危ない場合だけ (B) に倒せる。**

## なぜいま実装しないか

1. **判定そのものが難しい。** 「意味の上で壊れる」を git の差分から一般に判定することはできない。
   上の3条件は近似であり、**近似だと分かったうえで使う**なら価値があるが、
   **「これで安全」と誤解されると (A) より危ない**（守られていると思い込む分だけ悪い）
2. **回し直すなら、また6〜8分と、その間の main の動きに晒される。** つまり (A') は
   **(B) の問題を条件つきで持ち込む**。頻度が下がるだけで、消えはしない
3. **いまの実測では、意味の衝突は1件も起きていない。** 起きていない問題に、
   判定の難しい機構を先に入れない（D6）

## いつ効いてくるか

**この形で事故が起きたとき。** そのときに「知らなかった」ではなく
**「承知で選び、代案も検討し、実装しない理由も書いてあった」**と読めるように、この起票を残す。

**事故が1件でも出たら、この起票を backlog から上げること。**
