# 既定を自動着地へ反転すると、受け入れ試験が3回に1回ほど落ちる（毎回別の試験）

## 起きたこと

realign 第3便で `review.policy` の既定を `banto` → `auto` へ反転したところ、
**全量 `npm test` が3回に1回ほど落ちるようになった。落ちる試験は毎回違う。**

第3便で足した試験そのものは一度も落ちていない。落ちるのは**元からある、時間に依存した
試験**の方で、これまでに5種類が観測された。

| 落ちた試験 | 症状 |
|---|---|
| `audit-checklist-assets` / CHECK-MARKER-42 が監査人に届く | `test did not finish before its parent and was cancelled` |
| `worker-child-process`（inc-0066）/ 親の pid から子の pid を突き止められる | 失敗（1.0s） |
| 監査のやり直し / 試行回数が数え直される | 時間切れ（10.4s） |
| `env-notices` / 台帳に無い実リソース（孤児）が出来事として残る | 失敗（0.6〜1.0s） |
| `merge-queue-derive` / deriveQueue が帳簿から待ち行列を導ける | 順序の主張が崩れる |

## 計測（P6：根拠は分類ではなく数）

同じホスト（稼働中の banto が同居）。`npm test` を回した回数と、**第3便と無関係な試験が
落ちた**回数。

| 対象 | 走行 | 落ちた |
|---|---|---|
| `main`（8b42dd7） | 3 | **0** |
| `main`（4a75ac2・現在） | 4 | **0** |
| 第3便まるごと | 10 | **5**（別々の試験が1回ずつ） |
| 第3便から**新設試験3ファイルだけ外す**（製品コードは入れたまま） | 2 | **2** |
| 第3便のまま、**`DEFAULT_REVIEW_STAGE` だけ `banto` へ戻す**（新設試験も外す） | 2 | **0** |

**最後の2行が切り分けである。** 試験ファイルを増やしたことは原因ではない（外しても落ちる）。
**既定の反転そのものが引き金**で、そこだけ戻すと落ちなくなる。

## なぜ反転すると落ちるのか

反転前、契約に検査を持つ試験用タスクは監査を通ると `review-ready` で**止まっていた**。
反転後は `auditing → merging` へ進むので、**マージキューが実際に動く**——rebase・
マージ前ゲート・検証環境の立ち上げ・子プロセスの起動が、既存の試験の裏で走るようになった。

つまり試験一式の**同時に動くものの量が増えた**。落ちた5本はいずれも

- 本物のデーモン・工房・環境プールを起こし、
- **固定の待ち時間**（400ms・1s・10s）で結果を待つ

形をしており、機械の取り分が減ると待ち切れずに落ちる。`merge-queue-derive` に至っては
**稼働中のデーモンを 400ms 待ってから覗き、その瞬間の並び順を主張している**ので、
裏でキューが動く量が増えれば当然に崩れる。

**これらの試験は「機械が空いている」ことを暗黙の前提にしている。** 前提が書かれていないので、
工場が本来の仕事をし始めただけで壊れる。P6 の言う「機構が壊れている合図」はここを指す
——落ちた試験の中身が悪いのではなく、**待ち方が負荷に対して無防備**である。

## やってはいけないこと

- 待ちを延ばす／リトライを足す（P6 が名指しで禁じている）
- 「まれに落ちる」で先へ進む
- **既定の反転を戻す**（PO 裁定 2026-08-14。試験の都合で製品の判断を曲げない）

## 考えられる直し方（未着手）

1. **待ちを時計から外す。** 固定の ms ではなく、起きるべき出来事（イベントの出現）を待つ。
   `merge-queue-derive` は「400ms 待って覗く」をやめ、**動いていない帳簿の写しに対して
   `deriveQueue` を回す**形にすれば、そもそも競らない（純関数の試験に live daemon は要らない）
2. **重い試験を直列に寄せる。** 本物のデーモンを起こす試験を `--test-concurrency=1` の
   別プロファイルに分ける（e2e が既にこの形）
3. **同居している稼働中の banto を計測から外す。** ホストで回す限りノイズは消えない

## いま分かっていないこと

- 5本以外にも同じ前提を置いた試験があるか（数えていない）
- docker の使い捨てコンテナで回したときの再現率（番頭が回した1回では観測されていない）

## 直さない判断をした理由（**撤回**。下の「決着」を見ること）

realign 第3便のスコープ外（P1）。落ちる5本はいずれも `review.policy` とも
コンフリクト解消とも関係が無く、直すには待ち方の作り替えが要る。
**握り潰さないために起票する**（P6）。

# 決着（2026-08-14・番頭指示で第3便の責任範囲として直した）

**上の見立て（「負荷が上がって固定待ちが待ち切れなくなった」）は誤りだった。**
再現手順を絞ったら、**原因は3つあり、どれも「負荷」ではなかった**。

## 原因1: 検証コンテナが残した root 所有ファイル（→ imp-0023）

`audit-checklist-assets.spec.ts` は `skills/audit-checklist.md` に印を書き込んで
「基準が監査人に届くか」を見る。ところが**ワークツリーの `skills/*.md` 3本が root 所有に
なっていた**（`-rw-r--r-- 1 root root`、時刻は検証コンテナを回した直後）。

```
EACCES: permission denied, open '.../skills/audit-checklist.md'
```

書き込みフックが落ちるので、その суite の子テストが `cancelled` になる。

- **間欠ではなく決定的だった。** 近隣の spec だけ並べて回すと **4回中4回**落ちた
- 所有権を直したら **4回中0回**（`skills/` は ubuntu 所有なので、消して `git restore` で戻る）
- 「毎回違う試験が落ちる」ように見えていたのは、これと下の2つが混ざっていたため

**再発する。** 検証コンテナを回すたびに root 所有のファイルが残るなら、そのたびに
このテストは落ちる。器の側の手当ては imp-0023 の領分。

## 原因2: `merge-queue-derive` の主張そのものが誤っていた

「待ち行列全体が `mergingEntryEventId` 順」を主張していたが、`deriveQueue` は
**merging と approved を別々に整列してから連結する**（`[...merging, ...approved]`）。
まだ merging に入っていない approved の並び順キーが、先に merging へ入ったタスクの
キーより小さいことは普通に起きるので、**この主張は成り立たない**。

通っていたのは、稼働中のデーモンを 400ms 待って覗いた瞬間に**待ち行列が1本以下**だった
から。第3便で `merging` へ進むタスクが増え、2本並ぶ瞬間に当たるようになって表面化した。

直した形（`07f7ba96`）：**止まっている帳簿（作った並び）に当てる**。純関数の試験に
稼働中のデーモンは要らない。コードが実際に約束している「組の中の順」と「組の前後」に
分けて主張し、両方の組が入っていることを先に確かめる（空振り防止）。

## 原因3: `worker-child-pids` は **main に既に手当てがあった**（b94d695e）

「親の pid から子の pid を突き止められる」が落ちたときの中身：

```
sleep が居ない: [{"pid":204195,"ppid":204194,"comm":"sh","cmd":"sleep 30"}]
```

`comm` が `sh` のまま＝**fork と exec の隙で捕まえた子**。これは inc-0066 の既知の罠で、
`b94d695e`（`fork と exec の隙で捕まえた子の名前を書き直す`）が既に直していた。
**第3便の枝にその commit が入っていなかっただけ**——`main` を取り込んだら消えた。

## 残る2本について

`audit-checklist-assets` の cancel は原因1、`env-notices` の孤児検出は
**原因1と同じ回に落ちていたもの**で、所有権を直したあとは一度も再現していない。
`監査のやり直し` も同様。**固定待ちを条件待ちに書き換える必要は無かった**——
待ち方は壊れていなかった。

## 確かめ方（完了条件）

最終状態（`main` 取り込み済み）で **`npm test` を11回連続**（ホスト）：

| | 結果 |
|---|---|
| 11回すべて | `tests 2122 / pass 2122 / fail 0 / cancelled 0`、exit 0 |

第3便と無関係な試験が落ちた回数は **0/11**。

## 学び

**「毎回違う試験が落ちる」を負荷のせいにしたのが遠回りだった。** 落ちた試験の
**中身（失敗メッセージ）を先に読めば**、1本目で `EACCES` に行き着いていた。
計測（何回中何回）は分類を排すのに要るが、**それだけでは原因に届かない**——
P6 の「機構が壊れている合図」は、合図を読めという意味であって、
回数を数えれば済むという意味ではない。
