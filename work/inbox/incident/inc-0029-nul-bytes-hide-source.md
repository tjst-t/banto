## 内容

**ソースファイル2本に、生の NUL バイトが入っている。**

| ファイル | 数 | 何のため |
|---|---|---|
| `packages/banto-host/src/places.ts` | 6（375行目〜） | glob を正規表現へ写すときの目印（`**` の置き換え） |
| `packages/banto-web/src/useTabOverflow.ts` | 2（43行目） | 配列を1つの鍵に潰す区切り（`ids.join(...)`） |

どちらも意図的なコードだが、**エスケープ表記ではなく NUL 文字そのものがファイルに
書かれている**（この incident 自身にも書けないので、ここでは表記できない）。

## なぜ困るか

**grep 系の道具は NUL を見たファイルを「バイナリ」として丸ごと飛ばす。**

| 道具 | 振る舞い |
|---|---|
| ripgrep | 飛ばす（`binary file matches` とだけ言い、行は出さない） |
| grep / ugrep（`-I`） | **黙って**飛ばす。何も言わない |
| GitHub のコード検索 | 同様に扱われる見込み |

つまりこの2本は、**このリポジトリを grep しても存在しないファイルとして振る舞う**。
`places.ts` は場所の砦（決定36g）の実装が入っている、探し当てられないと困る側のファイル。

## どう見つかったか

task-0068 で `file.grep` を rg / grep へ委ねたとき、**3つの経路で結果が食い違った**
（rg 269 件 / 自前 276 件）。差分がすべて `places.ts` の行で、追ったらこれだった。

自前の走査は先頭 8000 バイトしか NUL を見ていなかったので**たまたま**読めていた
（そちらは task-0068 で全体を見るよう直した——先頭だけ見るのも「一部しか見ない」の一種）。
つまり**直した結果、places.ts は banto の道具からも見えなくなった**。他の道具に合わせた
形だが、見えないことに変わりはない。

## 直した（2026-08-07・PO指示 / task-0072）

生の NUL を、JS の文字列エスケープ（バックスラッシュ・x・ゼロ・ゼロ）で書き直した。
文字列リテラルでも正規表現リテラルでも同じ値になるので、**振る舞いは変わらない**
（`banto-places` / `banto-write-scope` の検査は全て通ったまま）。

**両方とも rg / grep から読めるようになったことを実物で確かめた。**

**再発を機械で見張る**（`source-hygiene.spec.ts`）：`git ls-files` の追跡ファイルを全件
走査し、テキスト種に NUL が無いことを確かめる。人が読んで気づける類ではない（P4）。
