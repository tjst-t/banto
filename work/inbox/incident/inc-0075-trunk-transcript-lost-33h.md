# 幹 thread-61 の画面用の記録から33時間が消え、番頭の文脈だけが残った

## 起きたこと

2026-08-16 朝、PO から「banto開発の幹の履歴が吹っ飛んだ。昨日一日ぶんが全部消えている」
という報告。実測の結果、**消えていたのは本当だった**——ただし消えたのは2つある保存の
うち**片方だけ**だった。

`thread-store.ts` の冒頭が、この事故をそのまま予言している:

> **2つの別々のものを残す必要がある。**
> 1. **POに見えていた会話**（`<BANTO_DATA_DIR>/threads/thread-NN.jsonl`）
> 2. **番頭の文脈**（Claude Agent SDK のセッションファイル）
> どちらか片方だけでは足りない。1 だけだと画面には会話が戻るのに番頭は何も覚えて
> おらず、**2 だけだと番頭は覚えているのに画面が空になる**。

起きたのは後者である。

| | 中身 | 状態 |
|---|---|---|
| ① `threads/thread-61.jsonl` | POに見えていた会話 | **8/14 15:22 〜 8/16 00:48 の約33時間が欠落** |
| ② `~/.claude/projects/.../<backendSessionId>.jsonl` | 番頭の文脈 | **無傷**（8/15 だけで user 128・assistant 185 件、壊れた行 0） |

`thread-61.jsonl`（全1778行）の並びが、そのまま証拠になっている:

- 1749〜1754行 … 2026-08-14 15:17〜15:22（「累計 7.823 GiB」「章を畳めませんでした（musl）」）
- **← ここに33時間の断絶**
- 1755〜1762行 … 2026-08-16 00:48:51 に `repairTrunkCards()` が立て直した枝の札8本
  （thread-114/118/119/120/122/124/125/126）
- 1763行 … PO の「幹の履歴が吹っ飛んだ」

## 「画面が壊れたのか、記録が消えたのか」を切り分けた筋道

**次に「履歴が見えない」が来たとき、この順で切れる。**

1. **サーバのデータの実体を数える**（画面の話をする前に）。`threads/thread-NN.jsonl` の
   行数・壊れた行の数・**PO が「最後に見えている」と言った本文がファイルの何行目か**。
   退避を取ってから触ること。
2. **ワイヤで確かめる**。生の WebSocket で `/ws?thread=<id>` に繋ぎ、`history` の
   entries 件数を数える。サーバが打ち切っているのか、そもそも持っていないのかが分かれる。
3. **窓の内側か外側かを見る**。画面は末尾 `CHAT_WINDOW`(=200) 件しか描かない
   （`Room.tsx`）。**PO が「最後に見える」と言った行が末尾から何件目か**を出す。
   200 の内側なら窓は無罪。
4. **末尾の中身の役を見る**。`role: "branch"`（枝の札）や `notice` は**本文ではなく
   カードで出る**ので、POにとっての「最後に読めるメッセージ」にはならない。
   **末尾200件が札と知らせで埋まっていれば、本文の最後が古く見えるのは正常な描画である。**
5. ここまでで「画面は正しくサーバの中身を描いている」と言えたら、**残るのは記録の欠落**。

**今回は 3 と 4 で決まった。**「7.823 GiB」は末尾から40件目（窓の内側）、その後ろは
枝の札8本と当日の対話だけ。つまり画面は正常で、記録に33時間が無かった。

**やってはいけなかったこと**: 職人の初期報告は「サーバは最新まで配っているのに画面が
古い＝クライアントの描画が止まっている」だった。この線で進むと **`banto-web` を直して
「直った」ことにして終わる**——直らないものを直したことにする、いちばん悪い決着になる。

## 分かっている引き金と、まだ分かっていないこと

**分かっていること**

- 書き戻しは `ThreadStore.replace`＝**全文上書き**（`threads.ts` の `persist()` →
  `flush()`）。**メモリが真実で、ファイルはその写し**。だからメモリに無いものは、
  次の書き戻しで**ファイルからも消える**。
- 2026-08-14 15:17:21 と 15:22:02 に「章を畳めませんでした（musl-linked binary の
  ReferenceError）」が2回。**以降このエラーは出ていない**（章は 8/15 08:49 の ch-0027 まで
  普通に畳めている）。**断絶の始まりはこの2回目の直後**。
- 8/15 は OOM killer によるSIGKILL が少なくとも4回（13:59:54 / 14:46:40 / 22:56:25 /
  8/16 00:48:38）、再起動は合計12回。**SIGKILL では `flushAll` が走らない**。
- 8/15 14:46:52 に「幹に札の無い枝 **1** 本に札を立てました」、8/16 00:48:51 に「**8** 本」。
  **これは欠落の痕跡**——記録から札が消えていたから立て直された。
- 8/16 00:48:50 の読み戻しで「thread-61 の記録に読めない行があります（その行は飛ばします）」
  が1回。書き込み中に殺されて壊れた1行が、読み戻しで捨てられ、次の書き戻しで永久に消えた。
- **いまは書き戻しが生きている**（調査中に 1776→1778 行へ伸びるのを実測）。

**分かっていないこと（再発防止の本体）**

> **なぜ「8/14 15:22 起動のプロセス」だけ、書き戻しが止まったのか。**

通常運転で `persist()` が動いていれば、SIGKILL で失われるのは遅延（`SAVE_DELAY_MS`）
のぶんだけで、33時間は説明できない。候補は次のとおりで、いずれも未確定:

- `persist()` の間引き（`if (this.pendingSaves.has(thread.id)) return;`）で、
  タイマーが発火しないまま残ると**以後の persist が永久に no-op** になる経路
- `flush()` 内の例外（8/14 はディスク逼迫。43.810 → 35.987 GiB まで掃除している。**ENOSPC**）
- `Thread.onRecord` が `attach()` 以外で外れる／別インスタンスに記録している経路
- 章畳みの失敗が、書き戻しを道連れにしている

## 直しの向き

- **失敗したときこそ記録を守る。** 章畳みが失敗しても、書き戻しは止まらないこと。
- **機械が落とす形で残す**（「気をつける」で終わらせない）。章畳みを跨いでも記録が
  ディスクに残ることを、試験で固定する。
- 全文上書き（`replace`）そのものの危うさも見直す余地がある——**メモリが縮んだら
  ファイルも縮む**という性質が、この事故の被害を「1行」ではなく「33時間」にした。

## 復旧

番頭の文脈（②）は無傷なので、そこから画面用の記録（①）へ**復元できる**。手順:

1. 退避を取る（`/home/ubuntu/banto-data-backup-20260816-0052/`。以後これは触らない）
2. SDK のセッションから欠落区間を `TranscriptEntry` の形へ変換し、**まず /tmp で検算**
3. **`kill -9` → 直後に差し替え**。`system.restart` も `systemctl restart` も**使えない**
   ——落ち際に `threads.flushAll()`（`bin.ts:1197`）が走り、**メモリの内容で復元ファイルを
   上書きして潰す**。SIGKILL ならハンドラが1つも走らないので安全（`Restart=always` が拾う）
4. 差し込み位置は**行番号ではなく内容で同定**する（会話は最後まで伸び続けるため）
5. 起き直したあと、**ファイルの行数だけで終わらせない**——①PO の画面に見えること
   ②プロセスのメモリにも載っていること（＝次の `flushAll` でまた消えない）

## 追記（2026-08-16・復元の実施結果と、残った穴）

欠落した33時間を、番頭の文脈（Claude SDK のセッション）から**画面用の記録へ復元した**。
**2回やっている**——1回目は失敗し、2回目で入った。**失敗の中身が、次に同じことをする人への
いちばんの申し送りなので、両方残す。**

### 1回目（失敗）: 役割を振り直さずに写した

材料に「章の要約器へ渡された書き起こし」を使い、**226行**を差し込んだ。結果、
**PO の発言でないものが全部 PO の発言（`role:"po"`）として描かれた**——職人からの報告・
他の幹からの言伝・知らせの取り下げ・章畳みの区切りまで。PO の言葉:

> あとほかの枝とかからの連絡もユーザの発言みたいに見えるようになっちゃってる。

原因は単純で、**SDK のセッションでは、知らせも職人の報告も道具の結果も「user ロール」で
入っている**（モデルへの入力なので当然）。それを1対1で写せば全部 PO の発言になる。

**さらに材料そのものが足りていなかった。** 章の要約器の書き起こしは、
**8/16 の分が最初から存在しない**（8/16 は章が1本も畳めていない）。SDK セッションの実測は
8/15 に313件・8/16 に122件＝**435件**あり、**226行では足りない**——この数の食い違いを
差し替える前に見ていれば、報告の前に気づけた。**PO の指摘「いま動いている枝の始点が
抜けているでしょう？」がそのまま当たっていた。**

### 2回目（成功）: 材料を SDK 本体にし、印で役割を振り直した

- 材料を **SDK のセッションファイル本体**に差し替え（要約器の書き起こしは、SDK 本体が
  覆っていない 8/14 15:22〜8/15 08:49 の区間だけに使う）
- user ロールを**内容の印で機械的に振り分けた**:
  `知らせ[...]:` ／ `幹「…」から言伝です`・`枝「…」からの問い/報告です` ／
  `…から報告：`＋`sessionId:` ／ `この知らせは取り下げます` ／ `取次「…」にPOが答えました` ／
  `再起動が完了しました…` ／ SDK の合成マーカー（`[Request interrupted by user]` 等）
  — **これらのどれにも当たらないものだけを `role:"po"` にした**
- **判定できないものは PO の発言にしない**（迷ったら `notice`）。誤って PO の発言にする方が、
  種別不明として置くより害が大きい

結果は **控え1796行 ＋ 復元523行 ＝ 2319行**。内訳は
banto 170 / **po 49** / reasoning 72 / tool 118 / notice 93（worker 50・thread 29・place 3・system 11）/ chapter 21。

### 撃ち方（`system.restart` を使ってはいけない）

**`system.restart` も `systemctl restart` も使えない。** 落ち際に `threads.flushAll()`
（`bin.ts:1197`）が走り、**メモリの内容で復元ファイルを全文上書きして潰す**。
気づかずに撃っていれば「復元したのにまた消えた」を踏んでいた。

**`kill -9`（SIGKILL）だけが安全。** ハンドラが1つも走らないので書き戻しが起きない。
`Restart=always` が拾う。手順は1本のスクリプトにまとめ、人手の隙を作らない:

1. `systemctl show -p MainPID` で pid を1つに絞る → `kill -9`
2. 直後に、現物を**別名で**退避（世代ごとに別ディレクトリ。前の世代を上書きしない）
3. **行番号ではなく内容で**差し込み位置を同定（会話は最後まで伸び続ける）。
   **見つからなければ何もせず異常終了**すること
4. 一時ファイルへ書いて `mv` で原子的に置換
5. systemd が起こしたあと、**ファイルとメモリの両方**を数える

### 切れたターンの起こし直しについて（2回とも出なかった）

`kill -9` は `settleInterrupted()` の担当範囲のはずだが、**2回とも**
「中断されたまま残っていた道具を確定させました」は出ず、「続きを進めてください」も
入らなかった。末尾が `role:"banto"` の本文（kill の瞬間の断片）で終わっており、
`lost-turn.ts` の判定が「末尾が番頭の本文なら動いた証拠＝失われていない」なので
**回収の対象にならない**、という説明は付く。**断定はしない**——事実として、
**2回とも出なかった**ことだけ記録する。
