# 職人の報告が番頭の会話に届かない

## 起きたこと

2026-08-14、職人 `task-0150`（sessionId 51e3504e-3911-416b-9687-b1b7ee0ae956）は
仕事を終えて報告まで出したのに、**番頭の会話にはその知らせが1件も積まれなかった**。
番頭は「まだ npm test を流している最中」と PO に伝え続け、PO の
「実はもう終わってない？」という問いかけで初めて発覚した。

工房側の帳簿には、すべて残っている（`worker.events`）。

| # | 時刻(UTC) | 種別 | 中身 |
|---|---|---|---|
| 6641 | 09:48:48 | `worker_reported`(claim) | 完了報告（本文あり・`done: true`） |
| 6642 | 09:48:58 | `worker_turn_ended`(fact) | `reported: true` / `waiting: false` / `settled: true` |
| 6643 | 09:50:03 | `worker_exited`(fact) | `exitCode: 143` / `expected: true` / `hitLimit: true` / peak 2.0GiB |
| 6644 | 09:50:03 | `worker_closed`(fact) | `reason: "done"` |

つまり**工房は報告を受け取り、正常に畳んでいる**。落ちているのは
工房 → 番頭ホスト → 会話、のどこか。

## なぜ問題か

- 番頭は「報告は自動で届く」という前提で手を離す（attach で待たない運用）。
  この前提が崩れると、**終わった仕事が誰にも拾われないまま放置される**。
  今回は PO が気づいたから助かっただけで、気づかなければ枝が宙に浮いたままだった。
- 同じターンで畳んだ職人 `chapter-handoff-retry` の報告は**届いている**。
  全滅ではなく取りこぼしなので、静かに繰り返す種類の事故になる。

## 調べる筋（未検証の仮説）

1. **番頭のターンと重なったときに落ちる。** 09:48〜09:50 は番頭が別の道具を
   叩いている最中だった。会話へ知らせを積む口が、ターン実行中は捨てているか、
   キューに入れたまま流していない可能性。
2. **メモリ上限に張り付いた職人の扱い。** #6643 は `hitLimit: true` / peak 2.0GiB /
   `exitCode 143`（SIGTERM）。上限に当たって工房が止めた個体で、
   `expected: true` の経路が「報告済みだから知らせは不要」と判断していないか。
3. **知らせの宛先が解けなかった。** この職人は帳場(thread-59)発ではなく
   Kobo 由来でもない直接委譲。origin の解決に失敗して宛先なしで捨てられていないか。

いずれも**工房の帳簿には出来事が残っている**ので、番頭ホスト側の購読と注入を
実物のログで追えば切り分けられる。

## 対処（案）

- 短期: 番頭が職人を出したら、次に手が空いたとき `worker.list` で
  `closed(done)` になっていないか自分で確かめる（運用でしのぐ）。
- 本筋: 会話への注入を「積んで消える」ではなく**未達なら再送する**形にする。
  imp-0021（状態が動いた札を取り下げる）と同じく、知らせの寿命の設計。

## 分かったこと（2026-08-14・実物のログで確定）

**仮説はどれも外れ。落ちていたのは「引き役が `await notify` で止まる」ことだった。**

`worker-notice.ts` の引き役は、読んだイベントを**その場で1通ずつ配り、番頭のターンが
終わるまで待って**いた。番頭のターンは数分かかる。その間 `running = true` のまま
なので、**引き役そのもの**が止まる——止まるのは1本の会話ではなく、全部の会話である。

thread-83 の帳簿がそれを示している（`/var/lib/banto/threads/thread-83.jsonl`）:

```
86  tool    worker.close      ← 番頭が畳んだ
87  tool    thread.merge      ← 枝を畳んだ
88  banto   「枝を畳みました。最終的な結果です」
89  chapter （章を閉じた）
90  notice  worker  「task-0150から報告：…」   ← ここでやっと届いた
```

**報告は消えていなかった。畳んだあと・章を閉じたあとに届いていた。** 09:48:48 の報告が
09:50:03 の `worker_closed` より後に配られている。番頭ホストの再起動は無い
（`journalctl` は 08:58 の次が 10:44）ので、起票時の仮説3つ——ターン中に捨てている／
`expected: true` で握り潰している／宛先が解けない——はいずれも当たっていない。

- 事象1「来ない」は、章が変わったあとに届いたため**番頭の文脈から見て存在しなかった**
- 事象2・3・4「遅れて古い写しで届く」は、この足止めの直接の帰結

番頭の見立て（「送られる瞬間の事実ではなく、出来事が起きた瞬間の写しのまま届く」）は
**症状の説明としては正しく、原因ではない**。写しが古くなるのは、配るまでが遅いから。

もう1つ、同じ経路に**静かな全損**の穴があった。`server.ts` の `deliverToThread` は
`thread.notices` に `.then` を継ぎ足す列で、記録・`ws.send`・`getLastError` のどれかが
1度でも投げると Promise が rejected のまま残り、**以後その会話の知らせは本体すら
走らない**。今回の実ログには出ていないが、踏めば「その会話だけ職人の報告が来なくなる」。

## 直したこと

- 引き役は**読むだけ**にし、配送は**会話ごとの列**へ渡す（会話をまたいで直列にしない）
- 配る直前に台帳を引き直し、用が済んでいれば**【取り下げ】として**配る（中身は残す）
- 読み位置を `worker-cursor.json` に持ち、**配り終えた分までしか進めない**
- `deliverToThread` の列を rejected のまま残さない

検体は `tests/acceptance/worker-notice-delivery.spec.ts`（修正前は6件落ちる）。

## 残っている論点

- 職人が 2.0GiB の上限に張り付いていた件そのもの（inc-0066 の 11GB 暴走とは別件だが、
  opus の職人が常用で 2GiB 天井に当たるなら、上限か使い方のどちらかが合っていない）。
- 工場（`kobo-notice.ts`）も同じ「その場で await して配る」形をしている。同じ足止めが
  起きうるが、今回の scope 外なので触っていない（P1）。
