## 内容

**章を畳んだのに、引き継ぎ資料が書けておらず、しかも読む手段も無かった。**

「ひらがな学習アプリ構想」の幹（thread-50）で章の切り替えが起きたとき、POから
「資料の作成に失敗、さらに読むことも失敗」という報告。**二重に落ちている**のが致命的で、
片方でも生きていれば文脈は繋がったはずだった。

## 実際に起きていたこと

`/var/lib/banto/handoffs/thread-50/ch-0001.md`（2026-08-10 08:51、16KB）：

```markdown
# 第1章の引き継ぎ — 前の章の続き

**トピック**: 前の章の続き

## 詳細


## この章で退避した観測
- `a-0001`（2,206字） — …
（以下、機械的に付けた観測の索引が16KB）
```

**詳細が空。** 「前の章の続き」は要約器の出力が読めなかったときの既定の見出しで、
中身があるのは後ろの索引だけ——それは要約器の出力とは無関係に機械が付けている部分。
つまり**要約器は何も返しておらず、それでも資料は書かれ、文脈は畳まれた**。

そして番頭は `handoff.read` を持っていなかった。会話の中で自分で調べて突き止めている。

## 原因（3つ。どれも「気づけない形」で落ちる）

### 1. 空の応答を「書けた」として通していた

`chapter-summarizer.ts` は `stopReason === "error"` だけを失敗とみなしていた。
本文が1文字も無くても、それは error ではない。空文字は `parseHandoff` に渡り、
`parseHandoff` は**捨てない方針**なので「読めなかった形」に仕立てて返す
——見出しは既定文字列、本文は空。それが書き出された。

`ChapterKeeper` には「資料を書けなかったら畳まない」という決めが**既にあった**が、
書けなかったことが失敗として伝わらないので空振りしていた。

### 2. 畳めなかったことがどこにも出ない

```ts
void this.maybeCloseChapter();   // ← 落ちたら unhandled rejection
```

仮に 1 を直して例外にしても、`void` のままではどこにも出ない。
握りつぶしですらなく、**気づけない形で消える**（I2）。

### 3. `handoff.read` が番頭の道具箱に入っていなかった（配線漏れ）

`handoff-tools.ts` は実装済みで、`bin.ts` にも `createHandoffTools(...)` の行があった。
**ただしそれは「サーバの逆引き用の写し」の配列**で、実際にモデルへ渡る道具は
`createBantoHostSession` が別に組んでいた（`ownTools` ＋記憶＋SKILL＋成果物）。
**同じものの一覧が2つあり、足したのは本物でないほう。**

次の章に載るのは見出しだけ、という設計（段階的開示）なので、読む口が無いと
**後半が丸ごと欠ける**。番頭は前提を憶測で埋めるしかなくなる。

## 直したこと

1. **空は失敗にする。** `parseHandoff` は空文字で例外を投げる（捨てないものが何も無い）。
   LLM 側でも空を弾き、`stopReason` を添えて何が起きたか分かるようにした
2. **畳めなかったことを知らせる。** `catch` してログに出し、`onCloseFailed` で
   POにも出す——文脈は伸び続けるので、黙って retry を重ねると
   「そのうち急に何も入らなくなる」形でだけ現れる
3. **配線を1箇所に寄せた。** `handoff.read` / `handoff.list` は
   `createBantoHostSession` が組む（記憶・SKILL・成果物と同じ場所）。
   `bin.ts` 側の逆引きの写しに足し忘れても、本物の道具箱には入る

## 確かめたこと

`tests/acceptance/chapters.spec.ts` に4件足して 33件が通る：

- 空を返したら畳まない（資料も書かれない・文脈も消えない）
- 空白だけの応答も空として扱う
- 畳めなかったことが `onCloseFailed` に届く（unhandled にしない）
- **`handoff__read` / `handoff__list` がセッションの道具一覧に載っている**
  ——登録の有無ではなく、実際にモデルへ渡る側を見る（これが今回の穴そのもの）

## 残っていること

**thread-50 の第1章は空のまま。** 元のやり取り（`threads/thread-50.jsonl` と pi の
セッションファイル）は残っているので、資料は書き直せる。自動では復元していない
——書き直すなら番頭に読ませて作らせるのが筋で、機械的に埋める話ではない。
