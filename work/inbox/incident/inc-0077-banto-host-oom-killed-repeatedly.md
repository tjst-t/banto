# 番頭ホストが OOM killer に繰り返し殺されていた（原因は「文脈の長さ」ではなく「会話の本数」）

## 起きたこと

2026-08-15、`banto.service`（番頭ホスト）のプロセスが **OOM killer に少なくとも4回**
（13:59:54 / 14:46:40 / 22:56:25 / 8/16 00:48:38）殺された。**同日の再起動は合計12回。**
さらに **8/16 06:34:59 に5回目**（下の「daemon-reload が引き金になった」を見よ）。
8/16 00:48:50 の読み戻しでは「thread-61 の記録に読めない行があります（その行は飛ばします）」が出て、
**書き込みの途中で殺されて壊れた行が捨てられ、次の書き戻しで永久に消えた**（記録側の被害は inc-0075）。

## 決着した原因（すべて機械の記録。推測ではない）

### 1. VM の枯渇ではなく、**自分の cgroup 上限に当たっていた**

- 2026-08-14 以降のカーネル OOM kill は**全件 `constraint=CONSTRAINT_MEMCG`**。
  `CONSTRAINT_NONE`（global OOM）は**1件も無い**。当時の MemAvailable は 7.3 GiB。
- banto.service の分はすべて `oom_memcg=/system.slice/banto.service`、
  **`memory: usage 3145728kB, limit 3145728kB`**＝8/14 に入れた `MemoryMax=3G` にきっかり当たっている。

### 2. 食っているのは **claude 子プロセスの本数**

- OOM 時のカーネルの Tasks state ダンプ：3 GiB のうち **claude 12〜13本が 2.29〜2.40 GiB（76〜80%）**、
  node 本体は 0.56〜0.66 GiB。**1本あたり anon 189〜200 MiB でほぼ一定。**
- 60秒×10分の採取では伸びは**階段状**（1本→4本で +637 MB）。本数が変わらない区間は横ばい〜微減
  ＝**固定集合の中で漏れている証拠は無い。**
- 原因はコードにある。`claude-agent-harness.ts:548` のコメント：
  「`PromptQueue` は空になっても終わらせない設計なので、**参照を落とすだけでは `query()` が生き続け、
  往復のたびに Claude Code の子プロセスが積み上がる**」。
  `dispose()`（同 :555・冪等）の呼び口は6箇所（`bin.ts:1423/1502/1688/1691`・`server.ts:1217`・
  `threads.ts:1684-1685`）で、**全部がバックエンドの差し替えかホスト全体の終了**
  ——**「しばらく触られていない会話を放す」経路が1つも無い。**
- 畳んでも会話は失われない材料は既にある（`resumeToken()` と `thread-store.ts:70` の札・決定97）。

### 3. **上限到達は「時間」ではなく「触った会話の本数」で決まる**

- 開いている会話 21本 × 0.19 GiB ＝ **3.99 GiB** で、node 本体を足さずとも 3 GiB を超える。
- 実測の到達時間は **29分 / 47分 / 8時間04分**とばらばらで、**いずれも到達時 12〜13本**。

> **この一行がこの事故の要点である。**「長く動かすと危ない」ではなく「**多くの会話を触ると危ない**」。
> だから直しの検査も、時間ではなく**本数**で書く（task-0165 の受け入れ条件 a8）。

## 立てて、実測で**否定した**仮説（残す価値がある）

**「章が畳めない → 会話が増える → OOM → また畳めない」の輪**——**成立していない。**

- 章畳みは 2026-08-15 12:06（thread-94/ch-0002）を最後に 0本で、**4回の OOM は全部その後**。
  「畳んでいる最中に殺された」重なりは無い。
- 畳めていないのは壊れているからではない。**文脈長の計測を直した `44616415`（8/15 11:31・反映は 12:59）以降、
  過大評価が消えた結果、正しく「まだ畳む時期ではない」と判定している**だけ（thread-61 の実文脈は
  約 297,000 / 窓 1,000,000 ＝ 0.30 で、閾値 0.6 の半分）。
- そして決定的なのは——**章を畳んでも claude 子プロセスは1本も減らない。**
  食っているのは文脈の長さではなく、**放されない子プロセスの本数**である。
- **したがって「章畳みの閾値を下げれば OOM が止まる」は成り立たない。**
  会話が増えるのは章が畳めないからではなく、**枝が開かれるから**。

（追跡は thread-127 が実施。この否定は、あとから「畳みを直せば直る」と誤読しないために残す。）

## 途中で私（番頭）が誤り、実測で訂正した見立て（3件）

1. **「職人の本数を運用で絞れば工房の圧が下がる」→ 誤り。**
   `worker.list` の内訳は、番頭が直に立てた職人は1本だけで、**残りは Kobo が工場の仕事のために
   立てている職人と、他プロジェクト（dentaku・hiragana）の分**。**減らす＝工場を止める**ことになる。
2. **「職人が11〜14本生きている」→ 誤り。**
   `supervisor/w-*` の**cgroup ディレクトリは職人が消えたあとも残る**。同時刻の `worker.list` では
   **生きているのは3本**（いずれも opus）。**畳める「用の済んだ職人」は1本も無かった。**
   → 実像は「12本が犯人」ではなく「**opus 3本で天井**」：
   **2.0 GiB × 3本 ＋ 工房本体 0.85 GiB ＝ 6.85 GiB**（当時の上限 7 GiB）。
3. **「番頭は 5G→4G に下げて工房へ回せる」→ 途中で取り下げた。**
   番頭の `memory.current` が 1.4 GiB → **2.6 GiB** へ増えたため。**下げる余地はもう無い。**

## `daemon-reload` が引き金になった（2026-08-16 06:34:58 → 06:34:59）

```
Aug 16 06:34:58 banto sudo[3862725]: ubuntu : PWD=/home/ubuntu/ghq/github.com/tjst-t/banto ;
                                     USER=root ; COMMAND=/usr/bin/systemctl daemon-reload
Aug 16 06:34:58 banto systemd[1]: Reloading requested from client PID 3862727 ('systemctl') (unit opencode.service)...
Aug 16 06:34:59 banto systemd[1]: Reloading finished in 651 ms.
Aug 16 06:34:59 banto kernel: ... oom_memcg=/system.slice/banto.service ... Killed process (MainThread) ＋ claude 5本
```

`systemctl show banto.service -p DropInPaths` は **ファイル名の辞書順**で並ぶ：

```
/run/systemd/system.control/banto.service.d/50-MemoryMax.conf   ← --runtime（5G）が先
/etc/systemd/system/banto.service.d/browser.conf
/etc/systemd/system/banto.service.d/kobo.conf
/etc/systemd/system/banto.service.d/oom.conf                    ← 恒久（3G）が後
/etc/systemd/system/banto.service.d/override.conf
/etc/systemd/system/banto.service.d/pools.conf
```

**ディレクトリではなく名前の順で、後に来たものが勝つ。** 設定が読み直された瞬間に一時の 5G が 3G に
上書きされ、2.6〜3.0 GiB を使う番頭が即座に上限に当たった。
**`/run` のファイルは残っているのに効いていない**——**「ファイルが在る＝効いている」ではない**
（一般則は imp-0079）。**確かめるなら `systemctl show -p MemoryMax` か cgroup の `memory.max`。**

**打った職人に落ち度は無い**（`daemon-reload` は unit を扱う仕事の普通の操作で、職人は
「いま一時設定で上限が持ち上がっている」ことを知りようがない）。**線引きの話は imp-0080。**

**恒久側を実測に合わせたので（task-0196・稼働機は `zz-memory.conf`）、この引き金はもう効かない。**

## 上流（Claude Agent SDK）はどうか

PO の問い「**claude 自体のメモリが異常ではないか。新しい版は出ていないか**」を調べた（2026-08-16）。

- **いま入っている版**（現物の `node_modules` で確認）：**番頭 0.3.229 / 工房 0.3.226**。**最新は 0.3.233**（08-14 公開）。
  **2つで版がずれている**——切り分けが読めなくなるので、**根治が着地したら揃える**（imp-0081）。
- **CHANGELOG（2.1.226〜2.1.233）に、メモリリーク・RSS・OOM・プロセスの終了漏れの項目は無い。**
  唯一近い 2.1.233 の「Bash ツール向けの opt-in な memory cgroup」は、**私たちが第2段で既にやっていること**。
  → **「上げれば直る」という根拠は無い。いまは上げない**（幹の判断）。
- **1本あたりの内訳**（`/proc/<pid>/smaps_rollup`・5本）：RSS 228〜342 MB のうち
  **anon 199〜227 MB（63〜87%）**。300MB のバイナリは **file-backed で複数プロセス間に共有**され、
  追加1本あたりの実コストは低い。**時間との単調増加は取れなかった**（1日動いた1本が5分の1本より少ない例あり）。
  **サンプル5本・仕事の重さを制御できていないので、「妥当か異常か」は判断がつかない**——**公式の目安が無い。**
- **したがって番頭の 2.6〜3.0 GiB は、上流の異常を持ち出さなくても「約200MB × 本数」で説明が付く。**
  **仮に1本あたりが半分になっても、本数が減らなければ同じ壁に当たる。直しの順番は変わらない。**

### 8/14 の 10.7 GiB に、名前が付いたかもしれない（上流の既知問題 #84960）

2026-08-14 の調査（`/home/ubuntu/banto-desk/reports/2026-08-14-oom-cause-and-fixes.md`）は、
**claude 1本が anon-rss 10.7 GiB まで膨らんだ確保経路を特定できず**、
「消去法で SDK/CLI 側の暴走が残るが、**どの確保経路かは未確認**」として閉じていた。

上流の OPEN issue **`anthropics/claude-code#84960`**（GitHub API で実在を確認）に、
**根本原因が特定済みとして次のように書かれている**：

> Bash ツールの `grep` が**内蔵 ugrep 7.5.0 に再 exec** され、
> `[^.]{0,110}...[^.]{0,90}` のような**二重の有界繰り返しを含む正規表現**で
> 正規表現コンパイルが**指数的に膨張**し、**毎秒 100〜200 MB を確保して**殺される。
> **全版で再現し、版を下げても直らない。**

**これは 8/14 の暴走の有力な説明である**（当時の調査中にも、同じ形の `grep -oE '.{0,120}…'` を1本打って
**120秒で打ち切りに掛かった**実測がある）。**ただし断定はしない**——当時、暴走した pid と
セッションの対応が付かず（`⚠ 前提とのずれ`）、**その1本が本当にこのパターンを打っていたかは確かめられていない。**

**次にスパイク的な OOM を見たら、まずこの経路を疑うこと。** 見分け方：
**秒単位で数百MB伸びる**（今回の「本数ぶんの階段」とは形が違う）／**Bash の子に `grep` / `ugrep` がいる**。

**なお、当時足した職人作法（`grep -o` を `.{0,N}` 付きで広い範囲に打たない）は、
偶然この線を踏んでいた。** 当時これは**メモリ対策ではなく CPU と待ち時間の対策として**入れたもので
（調査レポートにも「メモリ対策として売り込むと、次の事故のときに誤読される」と書いてある）、
**当てずっぽうが当たったのであって、分かっていたわけではない。**

## 残っている問い

1. **8G で足りるか。** opus の職人は袋の上限 2.0 GiB まで届く。**8G へ上げた後の 04:35:35 にも1件起きている**
   （`oom_kill` は 116 → 139）。**効くのは上限より、同時に走る本数（task-0168）と袋の中身を減らすこと
   （task-0186・imp-0074）**かもしれない。
2. **VM 全体の余裕。** 上限の合計は 5+8+1+1 ＝ **15 GiB**、MemTotal は 15.6 GiB。
   **上限は予約ではない**ので普段は問題ないが、**全部が上限まで使えば枯渇する**（8/14 の再来）。
3. **`--runtime` は機械の再起動で消えるのか**（未実測）。**恒久側は 5G/8G に揃えたので、消えても実害は小さい。**
4. **1本あたり anon 約200MB は上流として妥当か**（**判断がつかない**。公式の目安が無い）。
