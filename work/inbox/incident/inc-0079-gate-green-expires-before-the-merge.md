## 何が起きているか

マージキューは1本のタスクをこの順で処理する（`packages/banto-daemon/src/merge-queue.ts`）:

1. `rebaseTaskBranch(...)`（**:388**）——枝を、そのときの main の上に乗せ直す
2. `runMergeGate(...)`（**:436**）——検証環境を立てて受け入れ条件を回す。
   **全量 `npm test` を含むと6〜8分**
3. `fastForwardMerge(...)`（**:490**、実体は `git merge --ff-only`）

**1 と 3 のあいだが6〜8分空く。** その間に main が1コミットでも進めば、枝はもう main の子孫ではなく、
**ff は必ず失敗する**。ゲートは通っているので、**「緑を出したのに着地できない」**という形になる。

## 実例（task-0159・2026-08-16）

```
06:45:58 merge_gate_evaluated — 通過［base 881371a8］
06:45:58 task_failed — fast_forward_merge_failed: fatal: Not possible to fast-forward, aborting.
07:00:38 merge_gate_evaluated — 通過［base 00031cf0］
07:00:38 task_failed — fast_forward_merge_failed:（同上）
```

**2回ともマージ前ゲートは通過**している（2回目は間欠の EPIPE も出ず、全条が緑）。
負けた相手：

- 1回目 — `881371a8`（マージキューの外で行われた手動マージ）
- 2回目 — **`00031cf0`。番頭が記録の id 衝突を直して main へ直接コミットしたもの**

3度目の reverify を回すにあたっては、**幹が他の枝に「8分間 main へ直接コミットしないこと」を
依頼して静粛を作った**。**人の注意で守っている状態**であり、これは直しではない。

## 機構は「起きないはず」と書いていた

`merge-queue.ts:494` のコメント：

```ts
} catch (err) {
  // Fast-forward merge failure is unexpected after a successful rebase+gate.
  // I2: record and fail the task.
```

**「rebase とゲートが成功したあとに ff が失敗するのは想定外」**——この前提が誤っている。
rebase とゲートの成功は**その時点の main に対する主張**でしかなく、**6〜8分後にはもう有効ではない**。

## 一般化——**この機構は「重い仕事を罰する」形になっている**

- **ゲートが長いほど、その間に main が動く確率が上がる。**
  つまり**全量の試験を回すタスクほど着地できない**——
  **いちばん慎重に検査しているものが、いちばん落ちる。**
- **記録を1つコミットするだけで踏む。** 番頭も職人も `work/inbox/**` へ直接コミットするので、
  **誰でも、いつでも、無自覚に他人のマージを落とせる。**

同じ「難しい仕事ほど落ちる」形は、今日ほかに4つ出ている
（袋が破れる `imp-0074` / 監査の判定が返らない `task-0201` / 全体が直列化する `imp-0071` /
検証コンテナごと殺される）。

## 「緑が信用できない」の一形態である

ゲートの判定は**どのコミットの上で取ったか**まで帳簿に刻まれている（`merge_gate_evaluated.baseCommit`）のに、
**マージの瞬間にそれがまだ有効かを誰も見ていない。**
＝ **緑に有効期限があることを、誰も扱っていない。**

## 直し（`task-0197`）と、**承知で残した限界**

**直し**：ff の直前に mainline を取り直し、枝がその子孫でなければもう一度乗せ直してから ff する。
それでも失敗したら、同じ tick の中で**1回だけ**再試行する。

**限界（PO/幹の裁定 2026-08-16・(A) を採用）**：

> **ゲートの主張は base に対するものであり、乗せ直した後の組み合わせは検査されていない。**
> **したがって、git 上は衝突しないが意味の上で壊れる変更は、main に載りうる。**

**これは知らずに残した穴ではなく、承知の上で選んだ穴である。** 代案は2つあり、どちらも代償が重かった：

| | 形 | 着地 | ゲートの意味 | 代償 |
|---|---|---|---|---|
| **(A)** | **乗せ直して ff**（採用） | **必ずできる** | 一段弱い | **稀に**赤いものが載る |
| (B) | 乗せ直したらゲートを回し直す | **原理的に終わらない** | 保たれる | **毎回**着地できない |
| (C) | ゲート中は main を凍結する | できる | 保たれる | **毎回**完全に直列化 |

**(B) と (C) の代償は毎回確実に発生し、(A) の代償は稀にしか発生しない。** だから (A) を採った。

中間案 **(A')「乗せ直しで実際に差分が生じたときだけゲートを回し直す」**は
**`imp-0085` に、いま実装しない理由ごと記録してある**。
**この形で事故が1件でも出たら、`imp-0085` を backlog から上げること。**

## 採らなかったもの

- 「キューが回っている間は main を直接触らない」という**規律で縛る**——人の注意に頼る規律は、
  今日10回破られている（記録 id の衝突・`imp-0055`）。**機構で解く**
  （※ただし `task-0197` が着地するまでの当座は、`kobo.set_merge_queue` で**弁を閉じて**静粛を作る。
  「お願い」ではなく弁で作るのが要点——**いちばん main を動かすのは人ではなく工場のマージキュー**である）
- `--ff-only` をやめてマージコミットを作る（履歴が一直線でなくなる）
- 失敗を握り潰して成功にする。**本物の衝突は落とす**（I2）
