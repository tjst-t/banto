# 何が起きたか

2026-08-14、帳場の会話で章を畳もうとして次の断りが返った:

```
章を畳めませんでした（Error: 章の引き継ぎ資料が空で返りました（stopReason: length）。章は畳みません）。
文脈はそのまま伸び続けます
```

要約器が**本文を1文字も返さないまま出力上限に当たった**（`stopReason: length`）。
機構は「空の引き継ぎで畳むと前提が失われる」ため畳まない側に倒しており、その判断自体は正しい。
しかし結果として**章を畳む道が塞がったまま、文脈だけが伸び続ける**。長い会話ほど起きやすく、
長い会話ほど畳めないと困る、という向きに効く。

# なぜ起きるか（**検証済み**。2026-08-14 の調査で確かめた）

下の「仮説」は**半分当たっていて半分外れていた**。実機（PID 377010）で確かめた結果:

1. `BANTO_CHAPTER_MODEL` は確かに未設定（`/proc/377010/environ`）。
2. しかし要約に使われていたのは**会話のモデルではない**。thread-59 の会話モデルは
   `claude/opus`（backend `claude-agent-sdk`）で、これは **pi の台帳で解決できない**
   ——起動ログに `[banto] thread-59: claude/opus を解決できないため、起動時のモデルで
   開きます` が出ている。`sessionModel` は `llmCatalog.resolveHostDefault()` の
   フォールバック（policy=host・tier=standard の先頭）へ落ちており、実機の台帳で
   これを実行すると **`huihui/deepseek-v4-flash-abliterated`**（api `openai-completions`、
   contextWindow 128000、maxTokens 16384、自宅の vLLM）だった。
3. 「会話と同じモデルは思考を出す設定だから」も外れ。pi は `SimpleStreamOptions.reasoning`
   を渡さないと **anthropic / google では思考を明示的に切る**（`thinkingEnabled: false`）。
   要約器は `reasoning` を渡していないので、これらのAPIでは思考は出ない。
   **openai 互換だけが例外**で、`reasoning_effort` を送らない＝サーバ側の既定が効く。
   実機の vLLM は既定で `reasoning_content` を出し、**思考と本文が同じ `max_tokens` を
   分け合う**（実測：同じ入力で予算 4000 のとき思考 2,579字／予算 8000 のとき 6,788字。
   思考が予算に比例して伸びる）。pi にこれを切る seam は無い。
4. **効いていた本命は出力予算そのもの**。要約器は `maxTokens: 4000` 固定だったが、
   実機の資料本文は 5,800字前後（`/var/lib/banto/handoffs/thread-59/ch-0017.md` 実測）
   ＝日本語で 3,000〜4,800トークン。思考ゼロでも天井に当たる。実際に同じ形の要求を
   その vLLM へ投げると **予算 4000 でも 8000 でも `finish_reason: length`** で返る。
   思考が予算を食い切った回だけ本文が1文字も出ず、`stopReason: length` の空になる。
5. さらに保険で効く経路がもうひとつ。pi は出力予算を
   `contextWindow - 入力 - 4096` まで切り詰める（pi-ai `api/simple-options.ts` の
   `clampMaxTokensToContext`）。要約器のモデルの文脈長（128000）に入力が近づくと
   予算が 1トークンまで落ち、**確実に**「即 length・本文ゼロ」になる。閾値の判定は
   **会話側のハーネスの文脈長**（Agent SDK の Claude）で行うので、要約器のモデルが
   受け取れる大きさとは無関係に章が切られる——この食い違いは構造として残っている。

# なぜ起きるか（当初の仮説・**上のとおり一部外れ**）

- `BANTO_CHAPTER_MODEL` は未設定で、**会話と同じモデル**が要約に使われている
  （README のとおり既定は会話と同じモデル。`packages/banto-host/src/bin.ts:286` 付近）
- 会話と同じモデルは思考（thinking）を出す設定になっているため、**出力予算を思考で使い切り、
  本文に入る前に length で止まる**——という筋が疑わしい。長い章ほど思考が長くなり、当たりやすい
- 上限に当たったときの手当てが「断る」だけで、**やり直しが無い**
  （`bin.ts:1526` は「BANTO_CHAPTER_MODEL を見直してください」と案内するに留まる）

# 直す方向（案）

1. **上限に当たったら、そのまま諦めない**——出力予算を上げる／入力を削る（古い方から落とす）／
   より短い形式を求める、のいずれかで**一度はやり直す**。それでも空なら今までどおり断る
2. **空で返る＝出力予算を思考で使い切った**、が疑わしいなら、要約の呼び出しでは思考を抑える
   （要約は推論の要らない仕事なので、fast 等級で足りる）
3. 既定を「会話と同じモデル」に頼らず、**要約向けの既定**を持たせることも検討する
   （README には「安いモデルを指定してよい——本編のキャッシュに触らない」と既に書いてある）
4. 断りの文言に、**いま何が使われていたか**（プロバイダ/モデル・入力の大きさ・出力上限）を載せる。
   いまの文言では、見直すべき設定が何なのか利用者に判断できない

# 確かめ方（受け入れ基準の案）

1. 要約器が `length` で空を返す状況を作り、**やり直しが1回走る**こと（記録に残る）
2. やり直しで本文が得られれば章が畳まれること。それでも空なら畳まず、断りに
   モデル名・入力の大きさ・出力上限が載ること
3. 長い章（実ログ由来の長さ）で、既定の設定のまま畳めること

# やったこと（`fix/chapter-handoff-retry`）

- `chapter-summarizer.ts`: 空で返ったら**一度だけやり直す**。やり直しは①出力予算を
  4倍（モデル自身の上限で頭打ち）②書き起こしを 60,000字へ切り詰め（新しい側を残す）
  ③短い形式（考えを書かせない・2000字以内）を同時に打つ。やり直しで書けた資料には
  「2回目の試みで書いた」と残す。それでも空なら今までどおり畳まない
- 既定の出力予算を **4000 → 8000**（上の 4 の実測が根拠）
- 断りの文言に**使ったモデル・モデルの出力上限・各回の入力の大きさ・出力上限・
  stopReason** を載せる。`bin.ts` の知らせからは重複する助言を落とした
- 受け入れ試験: `tests/acceptance/chapters.spec.ts` に7件（LLM は叩かず `complete` を差し替え）

**残っている論点**（このタスクの外）: 章を切る閾値は会話側のハーネスの文脈長で決まるのに、
資料を書くのは別モデル（もっと小さい文脈長）という食い違い。上の 5 の経路はここから来る。

# 影響

- 帳場の会話は畳めないまま伸び続けている。**そのうち入らなくなる**
- 当座の逃げ道は「新しい幹へ移る」だが、帳場は畳めない会話なので逃げ切れない
