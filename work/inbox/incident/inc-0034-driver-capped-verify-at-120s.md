## 内容

**同梱の docker ドライバが、検証コマンドを 120 秒で切っていた。** 呼び出し側が何秒を
指定しても効かない。しかも**時間切れが時間切れに見えない**。

`docker-driver.ts` の `runCmd` は `timeout: opts.timeoutMs ?? 120_000` という既定値を
持っており、**全ての呼び出し箇所が `timeoutMs` を渡していなかった**。Pool 側が
`resolveRunTimeout`（既定10分・上限60分）で決めた値は、ドライバの subprocess timeout
にしか掛からず、その内側の `docker compose run` は常に 120 秒で殺されていた。

実測（実機・Environment Pool :4400 に直接）:

```
env.run(cmd="sleep 200", timeoutMs=1_500_000)  →  121 秒で exit 255
```

**255 なのが効いている。** `docker` は SIGTERM を捕まえて 255 で終わるので、
`spawnSync` から見れば「コマンドが 255 で終了した」——時間切れの痕跡が残らない。
ゲートは「検証コマンドが 255 で落ちた」と読む。

## なぜ困るか

1. **loamium はマージ前ゲートを永久に通れなかった。** `npm test` はホストで4分。
   コンテナでは `npm ci` 込みでさらに長い。**2分で必ず切られる**
2. **task-0071 の「時間切れなら延ばして再試行」が一度も発火していなかった。**
   あれは exit 124 を見ているが、返るのは 255。**入れた直しが効いていないことに
   誰も気づけない形**だった
3. **spec と実装が食い違っていた**（P3）。spec-environment §5.1 と §8 の裁定
   （2026-08-01）は「`run` のタイムアウトは能力側が既定と上限を持ち、呼び出し側は
   厳しくのみできる」と定めている。ドライバが自前の 120 秒を持つのは、
   **能力側の設定を無効化する第3の真実**（D3 違反）
4. **provision も同じ穴**。task-0075 が `DEFAULT_PROVISION_TIMEOUT_MS`（10分）を足したのは
   イメージのビルドが 30 秒を超えたから。だが**その 10 分も内側には届いていなかった**——
   ビルドが 2 分を超えるイメージは必ず落ちる（今のイメージがたまたま 2 分未満だったので
   表に出ていなかった。潜在）
5. `process` ドライバの `run` は**制限が全く無かった**。外側に殺されるとログも exit も
   返らず、Pool は `run が失敗しました` と投げるだけ——時間切れだったことが分からない

## 直したこと（task-0079）

- **持ち時間をドライバへ渡す**。`runDriverVerb` が `input.timeoutMs` に載せる
  （唯一の合流点なので、動詞ごと・ドライバごとに渡し忘れる形にならない）
- **ドライバは予算から取り分を引いて内側に掛ける**（`innerBudgetMs`）。取り分を残すのは、
  外側に殺される前に自分で時間切れを報告するため——同じにするとログごと消える
- **時間切れは exit 124 で返す**。ゲートの `VERIFY_TIMEOUT_EXIT` と同じ値であることを
  `env-driver-timeout-budget.spec.ts` が機械で見張る（散文の約束にしない）
- **`runCmd` の `timeoutMs` を必須にした**。既定値を持たせていたのが原因なので、
  省略できない形にして再発を型で塞ぐ
- **時間切れの直後に one-off コンテナを消す**。`--rm` はクライアント側の後始末なので、
  殺すと残る（task-0074）。teardown まで待つと、延長して再試行する間ずっと二重に走る。
  `oneoff=True` で絞る——プロジェクト名だけで消すと本体まで巻き込む
- `process` ドライバの `run` にも同じ予算と 124 を入れた

**予算が届かないときは内側で縛らない**（`undefined`）。短い既定に落とすのが今回の
壊れ方だったので、そこへは戻さない。外側の subprocess timeout が必ず居る。

## 直したあとに初めて測れたこと（実機・loamium）

2分で切られなくなったので、**コンテナの中での検証が実際に何分かかるかを初めて見た**：

| | 時間 |
|---|---|
| `npm ci --ignore-scripts` | 1分 |
| `npm test`（vitest 1,943件） | **9分19秒** |
| 合計 | **10分31秒** |

**ホストでは4分**。コンテナでは 2.3 倍かかる（ソースは bind mount なので I/O が効いていると見られる）。

**`DEFAULT_VERIFY_TIMEOUT_MINUTES`（10分）を超える。** ゲートは10分で一度切り、
60分に延ばして再試行して通る——task-0071 の機構は正しく働くが、毎回10分を捨てる。

**ここで既定を延ばすのは採らない。** inc-0031 の教訓（待ち時間を延ばす方向の直しは
症状を隠すだけだった）がそのまま当てはまる。直すべきは 2.3 倍の方で、
延ばすのは測ってから決める話。**PO判断に残す。**

### コンテナの中では10件落ちる（ホストでは通る）

道具立てが足りていない——**`Dockerfile.test` に書く話**（loamium 側の作業）：

- **7件：PDF 書き出し**（`export.spec.ts`）。ヘッドレスブラウザが入っていない
- **2件：`git check-ignore`**（`smart-folders.spec.ts`）

「何が足りないか」が一切見えなかった。いまは**足りない道具がログに名前で出る**。

## 残る問い（別件・PO判断）

**検証環境に「用意する」段が無い。** プロファイルは `driver` / `config` / `ttl` /
`quota` / `credentials` だけで、**立てたあと・検証を回す前に一度だけやること**を
書く場所がない。結果、受け入れ条件の `verify` が自分で環境を用意することになる：

- loamium/task-0004 → `npm run lint` が **exit 127**（node_modules が無い）
- loamium/task-0005 → 各 `verify` の頭に `npm ci --include=dev` を付けて再試行 →
  postinstall が走って `node-llama-cpp` のビルドで落ちる（**exit 1**）。
  正解は `--ignore-scripts`（loamium の `Dockerfile.test` のコメントに書いてある）

これは3つの点で歪んでいる：

1. **受け入れ条件ごとに繰り返す**。a3 と a4 が別々に `npm ci` を回した（各 ~100 秒）
2. **タスクを書く側が環境の用意を当てさせられる**。task-0005 を書いた番頭は
   `--include=dev` と書いて外した
3. **失敗の言葉が間違う**。`npm ci` がこけると `verify_failed:a3(exit=1)` と出る——
   「テストが落ちた」と読めるが、**テストは一度も走っていない**。
   task-0075 が立てた「『確かめていない』と『落ちた』を別の言葉にする」がここで破れる

**banto 自身も同じ形**（`meta/environments.yaml` の `test` は空の名前付きボリュームに
node_modules を隔離している）。受け持たせる全プロジェクトが最初のマージで踏む。

案：プロファイルに `setup`（立てたあと一度だけ走らせる）を足し、**Environment Pool が
provision の一部として回す**。失敗は `verify_failed` ではなく「環境が用意できない」に
なる。Kobo 側は既に `verify_env_unavailable` の道を持っているので、ゲートの変更は要らない。
ただし**プロファイルの書式は受け持つリポジトリが書く公開IF**なので、D1 として PO へ上げる。
