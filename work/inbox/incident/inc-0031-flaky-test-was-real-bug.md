## 内容

**「まれに落ちる試験」を、テストの遅さとして2回処理していた。実際は機構が壊れていた。**

`audit-fail-rework.spec.ts` の「no new rework session spawned after 2nd fail」が、全体テストを
混んだ状態で回すとまれに落ちていた。単体では通るので「並列で走らせると遅い」と読まれ、
**待ち時間を延ばす方向の直しが2回入っていた**。テスト内のコメントがそれを残している：

```
// 畳むのは背景の仕事で、HTTP を2往復する（一覧→close）。テストを並列に走らせると
// ここが数秒かかることがあるので、固定の待ちではなく状態を長めに待つ
const deadline = Date.now() + 20000;
```

**20秒待っても畳まれなかった。** 遅いのではなく、誰も畳まないから（task-0072）。
職人を起こしている間にタスクが終端へ着くと、**遅れて生まれた職人を後始末が取りこぼす**
——工房の安全弁（既定15分）まで走り続ける。

## なぜ気づけなかったか（センサー欠落・spec-improvement-loop §2）

1. **「まれに落ちる」を機構の合図として扱わなかった。** 単体で通ることを「テストの都合」の
   証拠として読んだが、実際は**競りの窓が狭いだけ**だった
2. **待ちを延ばす直しは、症状を隠す方向にしか働かない。** 20秒に延ばしたことで
   「たまに落ちる」頻度が下がり、余計に機構の問題に見えなくなった（→ P6 の形）
3. **職人が余分に走っていることを見る検査が無かった。** 落ちたタスクに紐づく職人が
   残っていないか、を機構側の不変条件として持っていなかった

## 直したこと

task-0072。職人が出来上がった直後に帳簿を読み直し、その役目を要る状態でなければ
その場で畳む。競りは `FakeRuntimeDriver.spawnDelayMs` で時間に依らず再現する。

## 同じ形を全部探した（2026-08-07・PO指示）

「非同期で作ったものを、作り終える前に状態が変わると誰も片付けない」を Kobo の中で洗った。
**3箇所あった**（最初に見つけたのは1箇所目だけ）：

| どこ | 何を取りこぼすか |
|---|---|
| `spawnReworkSession` | 終端に着いたあとに生まれた rework の職人（最初に見つけたもの） |
| `spawnAuditSession` | auditing を抜けたあとに生まれた監査人 |
| `spawnTask`（実装者） | **ready を抜けたあとに生まれた実装者**。次の `planning` への遷移が弾かれ、職人だけが宙に浮く |
| `_autoProvisionOnReview` | レビューが終わったあとに立ち上がった検証環境（最長24時間動く・I3） |

いずれも同じ判定（作り終えた直後に帳簿を読み直し、要らなければその場で片付ける）で塞いだ。
