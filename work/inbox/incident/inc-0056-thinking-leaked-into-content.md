## 内容

**番頭の思考が本文として PO に出て、そこでターンが終わる。**

PO報告（2026-08-11）：「`deepseek-v4-flash-abliterated` を使うと『何かをやります！』と
言ったまま何もせずに固まる、が繰り返される。Kimi に切り替えたら消えた」。

画面に出ていたのはこれ（実物）:

> 調査結果を記録した。PO の判断（TLS 方針）を待つ。**PO への報告を簡潔にまとめる。**
> 取次に積んだので、会話でも同じ内容を提示しておくとよい。ただし…

**これは番頭の独り言で、POへの返事ではない。** 「報告をまとめよう」と考えたところで
ターンが終わっている（`finish_reason: stop`・道具なし）。

## 原因（一本の線）

1. `deepseek-v4-flash` は**思考モデル**で、出力は `<think>…</think>` ＋
   `<｜DSML｜tool_calls>` という書式。vLLM の `deepseek_v4` パーサはこれを前提にしている
2. パーサの**初期状態**は `chat_template_kwargs` に `thinking` / `enable_thinking` が
   渡されたときだけ `REASONING` になる。**渡さなければ `CONTENT`**——モデルがリテラルの
   `<think>` を書き始めるまで、思考として扱われない
3. banto→LiteLLM の経路で **`enable_thinking` は vLLM まで届いていない**（実測：付けても
   `reasoning_content` は空・`content` は散文のまま。届いていれば逆になる）
4. その結果、**思考が `content` に入り、会話の記録として焼き付く**。実測で
   assistant 29件すべてが `content` と `tool_calls` のみ、reasoning 系のキーは **0件**
5. 以後モデルは「思考を本文に書く」自分の履歴を手本にする。**vLLM 版は拒否しないので
   静かに悪化する**——正式版（opencode-go 経由）は同じ履歴を **400 で拒否**した：
   「The `reasoning_content` in the thinking mode must be passed back to the API」

## 測り方を間違えていた（記録として残す）

当初は「道具呼び出し率」で追っていたが、**この物差しが症状を取り違えていた**。

同じ検体で kimi-k2.5 は 1/3 でしか道具を呼ばない。しかし呼ばなかった2回の中身は
**POへの正しい報告**だった（「調査結果をレポートにまとめ、取次に判断を積みました。
現在の状況: …」）。この場面では**道具を呼ばないのが正解**——前のターンでレポートは
書き終わり、取次にも積んである。

- `tool_choice: "required"` が 0/3 → 3/3 で「効いた」のは、**症状ではなく物差しに効いた**だけ。
  正しく「報告して待つ」べき場面で、要らない道具を強いることになる
- 当初案の**終端ガード（`stop`＋道具ゼロで `tool_choice: required` 再投）は撤回**する

**欠陥は「思考と発話が分離できていない」の一点。**

## 切り分け済み（もう疑わなくてよいもの）

すべて実測。temperature（0/0.2/0.7）・道具の数（2〜85個）・文脈長（30k）・依頼の形（5種）・
stream の有無——**いずれも関係なし**。系統プロンプトで「予告で終わるな」と指示しても **0/3**。

pi 側の思考の往復は**既に実装済み**（`pi-ai/dist/api/openai-completions.js`：応答の
`reasoning_content` / `reasoning` / `reasoning_text` を思考ブロックへ取り込み、次の要求で
`assistantMsg[signature]` として戻す）。**banto 側の改修は要らない。**

## 直すこと

- **サーバ側で `enable_thinking` を効かせる**（依頼済み・2026-08-12）。これが根本。
  効けば思考は `reasoning_content` に分離され、pi が往復させ、番頭は思考として畳んで表示する
- **既存の会話は直らない。** 汚染された記録は残るので、当該の枝は**章を区切る**
  （`closeChapter`）か、畳んで開き直す。章の境界は文脈を捨てて引き継ぎ資料から始め直すので、
  「思考を本文に書く」手本ごと落ちる
- 当座は **kimi / qwen へ寄せる**（思考を分離し、この場面で正しく報告を返す）

## A/B の結果（2026-08-12・サーバ側で `enable_thinking` 強制付与が入った後）

すべて再現検体（実会話 214KB・道具100個）を `10.10.254.20:8000` へ投げた実測。

| 条件 | 思考が分離したか |
|---|---|
| 単発（道具なし・履歴なし） | **分離する**（reasoning 1323字 / content 0字） |
| 検体そのまま（道具100個＋汚染履歴） | **0/5・0/4** |
| 検体の履歴 ＋ **道具なし** | **4/4** |
| 検体の履歴の思考を **`reasoning`** へ移す ＋ 道具100個 | **4/4** |
| 検体の履歴の思考を **`reasoning_content`** へ移す ＋ 道具100個 | **4/4** |

**引き金は「道具」と「汚染された履歴」の組み合わせ**だった。どちらか片方だけなら分離する。
先方が (d) で報告していた「マルチターン（tool_call→tool結果→続行）の2ターン目以降で漏れる」
と一致する。

**そして履歴に思考を戻すと、道具があっても分離が復活する（4/4）。**

### キー名：`reasoning` / `reasoning_content` の**両方**が読まれている（実測）

マーカー法（履歴の assistant に目印つきの思考を仕込み、次のターンで復唱させる）:

| 履歴のキー | 道具あり | 道具なし |
|---|---|---|
| `reasoning` | **2/3 復唱** | 0/3 |
| `reasoning_content` | **3/3 復唱** | 0/3 |

- **道具が無いと、どちらのキーでも届かない。** `drop_thinking` が
  「メッセージに tools があるときだけ無効化される」という実装と一致する
- **道具があれば `reasoning_content` でも読まれる。** ソース読解では
  「入力側は `reasoning` しか見ない」だったので**食い違う**——間に居る LiteLLM が
  正規化している可能性が高い。**実測を採る**

## 結び：番頭側のコード変更は不要

- pi は応答の `reasoning_content` を拾い、次の要求へ**同じ名前で戻す**（実装済み・確認済み）
- そのスタックで `reasoning_content` は**実際に読まれている**（上記 3/3）
- したがって **`before_provider_request` での名前の書き換えは要らない**

**残るのは既存の汚染された履歴だけ。** これは直らないので、当該の枝は**章を区切る**か
畳んで開き直す。新しい章は引き継ぎ資料から始まるので、「思考を本文に書く」手本ごと落ちる。

## 続き：元の症状は解決。別の症状が残り、このモデルの採用を見送る（2026-08-12）

サーバ側で `enable_thinking` が入り、**思考の分離は正しく働くようになった**。
thread-72 の記録でも `[reasoning]` として畳まれている。**本 incident の主題は解決。**

ただし別の壊れ方が出た。**モデルのツール呼び出し記法（DSML）が本文へ漏れ、
繰り返してターンが打ち切られる**：

```
<｜DSML｜ll__read id="thread-72/ch-0002" />
<｜DSML｜ll__list />          ← これが20回以上、そして Request was aborted
```

### 根本原因（サーバ管理側が vLLM のコードで特定）

`structural_tag_registry.py` の `get_model_structural_tag()`:

```python
if tool_choice == "auto" and not _any_tool_strict(tools):
    return None   # 文法制約なし＝完全な自由生成
```

**`tool_choice: "auto"` かつ strict なツールが1つも無いと、DSML を強制する文法制約が
まるごとスキップされる。** pi を含むほぼ全クライアントの標準的な渡し方がこれに当たる。
vLLM 本家 issue #40801 として既知。

観測がすべて説明できる：合成の単純なツールなら崩れない（生成が易しい）／実際の
100ツールだと崩れる（難しい）／`tool_choice: "required"` で直る（分岐を通らない）／
`-raw` でも起きる（vLLM 本体のロジックなので LiteLLM とは無関係）。

「ちょうど3文字欠ける」は自由生成のたまたまの出方で、規則ではなかった。

### `strict: true` は効かなかった（実測）

回避策として提案された「ツール定義に `strict: true` を付ける」を試した。

| 条件 | 道具を呼ぶ | DSML漏れ |
|---|---|---|
| そのまま（auto・strict なし） | 1/12 | **4/12** |
| `strict: true` | 3/12 | **3/12** |

**差は無い。** 最初 n=6 で測ったときは 3/6 → 0/6 で「消えた」ように見えたが、
n=12 で溶けた。**少ない試行で出た「効いた」は疑うこと**（P6 と同じ話）。

### 決めたこと

**`deepseek-v4-flash-abliterated` は番頭のハーネスに使わない。**

漏れが無い回でも、**本物のツール定義では道具をほとんど呼ばない**（1〜3/12）。
合成の単純なツールなら 5/5 呼ぶので、モデルと banto のツール定義（100個・長い日本語の
説明・入れ子スキーマ）の噛み合わせが悪い。kimi・qwen は 93%。

vLLM を新しいビルドへ上げれば直る可能性はある（本家で議論継続中）。そのときに再評価する。

## 確かめていないこと

- `enable_thinking` が効いた後に本当に消えるか（サーバ側の対応待ち。同じ検体で A/B する）
- abliteration の寄与。正式版 `deepseek-v4-flash` は履歴を拒否するため、**同じ検体での
  直接比較ができていない**。道具呼び出し率は正式版 69.3%（3689ターン）／abliterated
  73.1%（93ターン）で、**abliteration が犯人という説は支持されていない**——ただし
  配信スタックが違うので交絡している
