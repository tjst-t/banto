## 何が起きているか

`tests/trunk-branch.spec.ts` の「入力欄の速さ」2件が、**1文字あたりの所要を測って
`toBeLessThan(100)` で判定**している。

- `:815` 大きな Markdown の面を開いていても、打鍵が引っかからない（幹側）
- `:827` 枝でも同じ（面は枝のキャンバスに載る）

この2件は**ホストの負荷しだいで緑にも赤にもなる**。

## 実測（2026-08-16・SHA `fc673a71` を固定・変更なしで5回・`--workers=2`）

| 回 | :815（幹） | :827（枝） |
|---|---|---|
| run-1 | 326.4ms ✖ | 261.4ms ✖ |
| run-2 | 142.0ms ✖ | 242.0ms ✖ |
| run-3 | 190.8ms ✖ | 151.8ms ✖ |
| run-4 | 227.0ms ✖ | 116.0ms ✖ |
| run-5 | **100ms 未満 ✔** | 129.6ms ✖ |

**同じコミット・同じ環境・変更なしで、片方は4/5で失敗し1回だけ通った。**
理由は5回とも同一（`expect(received).toBeLessThan(100)`）で、**違うのは数値だけ**。

もう片方は5回とも超えたので「恒常赤」に分類されたが、実測値は 116〜261ms と**2倍以上ぶれて**おり、
**恒常赤と間欠の境目は、しきい値の位置がたまたまどこにあるかでしかない。**

## なぜ問題か

- **同じコミットが、回によって緑にも赤にもなる。** これは「緑が何を保証しているのか」を壊す。
  P6 のとおり、間欠に落ちる試験は機構が壊れている合図であって、無視してよい印ではない。
- このホストは**工場（Kobo）・職人・検証コンテナが同居している**。つまりこの試験は
  **その瞬間に他の誰が何をしていたか**を測っている。プロダクトの性能を測っているのではない。
- 「どうせ揺れる」と読み飛ばす癖がつくと、**本物の性能退行を見落とす**。

## 直す筋（案・未着手）

1. **しきい値をゆるめる**——いちばん安易で、いちばん悪い。退行を検出できなくなるだけ。**採らない。**
2. **絶対時間をやめて相対で見る**。たとえば「面を開いていないときの打鍵」と「開いているときの打鍵」を
   同じ回の中で測り、**比が一定倍を超えないこと**を見る。負荷は両方に等しく乗るので相殺される。
   **これが本筋**（測りたかったのは「面を開くと遅くなる」ことであって、絶対値ではないはず）。
3. **性能の見張りを、合否を出す試験から外す**（記録して推移を見るだけにする）。
   合否にするなら、負荷が制御された場所でだけ回すこと。

## 障害（先に決着が要る）

**この直しは工場の機械検査では確かめられない。** マージ前ゲートの器
（`docker/Dockerfile.test` = node:24-alpine）にブラウザが無く、ブラウザ試験は工場では1件も走らない
（`imp-0068`）。直したことを機械で示すには、**器にブラウザを入れるか、ブラウザ試験を回す別の器を
用意するか**の決着が要る。それが無いまま積むと、「ホストで回した出力を職人が貼る」＝
**自己申告で緑にする**ことになり、この枝が問題にしていることそのものを再生産する。
