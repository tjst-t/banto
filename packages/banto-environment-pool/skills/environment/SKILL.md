# 検証環境

## いつ使うか

**「このブランチでテストが通るか」を機構が返す事実として確かめるとき。** 検証は職人の自己申告では済まない——報告は主張であって完了の証明ではない（決定29a）。env.* は番頭自身が回し、結果を機構の出した事実として受け取る（I1 の道具）。

**職人には env.* を渡さない**（決定32c）。職人は成果を出す側で、自分の成果を自分で検証して「通りました」と言えてしまうと I1 が崩れる。

## 使い捨て検証は env.verify 一本

**「このブランチでテストが通るか確かめて」の答えになる道具。** 立てて→コマンドを走らせて→**必ず畳む**までを一息で回す。

1. `env.verify` に渡す：
   - `repoPath` — プロファイルのあるリポジトリのルート（`meta/environments.yaml` を読む）。`profile` でプロファイルを、または `driver` + `config` でその場限りの構成を直接指定
   - `workdir` — どこで動かすか。職人が作った worktree を指せば、そこでそのまま検証できる。省略時は既定の場所
   - `cmd` — 環境の中で走らせる検証コマンド
   - `taskId` — 何の検証かを台帳とログに残すラベル
2. 機構が provision →（必要なら deploy）→ healthcheck → run → collect → teardown を回す。**途中で失敗しても畳むところまで面倒を見る**
3. 返るのは事実：通りました/通りませんでした、終了コード、ログの末尾。`tornDown: false` で返ったら**畳めていない**——`env.list` で残骸を確認する

## 居座らせたいときは env.provision（低位動詞）

レビュー用の dev server のように**環境を残したい**ときは低位動詞で組む（`env.verify` との使い分けは `worker.delegate` と `worker.steer` / `worker.close` の関係と同じ）。

1. `env.provision` で立てる。返る `envId` で以降の操作を指す
2. `env.deploy` で成果物を配る（ドライバによっては立てた時点で動いているので何もしない）
3. `env.healthcheck` で使える状態か確かめる——**ここが通らないうちに走らせた結果は当てにならない**
4. `env.run` でコマンドを走らせる。ログは末尾だけ返る。制限時間は短くはできるが長くはできない
5. **使い終わったら `env.teardown` で必ず畳む。** 既に畳んであるものへ呼んでも問題ない（冪等）

期限（TTL）が過ぎれば機構も畳むが、**あれは安全弁であって主機構ではない**（決定30b と同じ構図）。`env.provision` の返り値が「自動では畳まれません」と言ったときは特に、畳む契機は自分で持つ。

## 畳み忘れ・孤児を見えるようにする

- `env.list` でいま立っている環境を確認する。畳み損ね（teardown-failed）は「（**畳み損ね**）」と出る
- 台帳に無い実リソース（孤児）も数が出る——消し忘れの元なので黙って放置しない（I3）
- **畳み損ね・孤児は PO への通知が来る**（Kobo のケイデンスが未配線のため、いまは番頭の会話へ流れる）。GUI（env.manager）でも見える——これは自分が畳み忘れていないかを番頭に気づかせるための口でもある
- 同時に立てられる数には上限がある。立てられなくなったら `env.list` を見る。使えるプロファイルと上限の確認は `env.list_profiles`

## 外から見せる（expose）

**PO がブラウザで自分の目で確かめたいときだけ**、`expose` でポートを渡す。機械が確かめるだけなら不要（返り値の URL を PO に伝える手間だけ増える）。

公開方式は `exposeMode` で選ぶ（`auto` / `proxy` / `caddy`、既定 `auto`＝caddy の口が設定されていれば caddy、無ければ proxy）。

- **caddy（サブドメイン公開）が基本形**：パス書き換え不要・URL が素直・**WS もそのまま通る**
- **proxy（banto の中継）**：`{baseUrl}/env/<envId>/` の URL で公開する。**HTTP も WebSocket（`/env/<envId>/ws`）も中継し**、中継 URL 配下で開いた WebUI の会話も検証環境に繋がる。banto を守っている認証をそのまま継承するので、環境ごとに認証を用意しなくてよい。制約：パス配下に置くので、絶対パス（`/assets/...`）で資源を引くアプリは壊れることがある——そこまで要るなら caddy

**この環境の Caddy は :80 のみ。** caddy exposer が返す URL は https:// と表示されるが**実態は http**——https でアクセスすると ERR_CONNECTION_REFUSED になる。URL を渡すときは http:// に直して伝える。

## 成果物を取り出す

- **畳むと環境の中身は消える。** 残したいもの（ログ・カバレッジ等）は畳む前に `env.collect` で取り出す
- 置き場所は**指定しない**——機構が決めて返す。返ってきた場所は読み取り専用の場所として登録されているので、`file.*` でそのまま読める
- 回収済みの成果物が溜まったら `env.cleanup` で捨てられる（期限が来れば機構も捨てるが、要らないと分かっているなら先に捨てた方が溜まらない）。**環境の記録（台帳）は消えない**——何を立てたかの記録は残る

## やってはいけないこと

- **職人に検証させない**。env.* を職人へ渡さない（決定32c）——「自分で検証して『通りました』」が I1 を崩す
- **畳まずに放置しない**。外に残ると費用がかかり続ける。自動で畳まれる仕組みに寄りかからない
- **`env.verify` が畳めなかったら無視しない**。`tornDown: false` が返ったら `env.list` で残骸を確認し、`env.teardown` で畳む
- **番頭ホスト（`banto.service`）の再起動を、環境の巻き添えと言わない**（2026-08-15 実測・imp-0062）。環境は別ユニット（`banto-environment-pool.service`）が立て、コンテナは `docker-<id>.scope` に入るので**落ちない**。再起動のたびに環境を畳む段取りは要らない
  - ただし **process driver のプロセスは環境プールの cgroup に入る**——`banto-environment-pool.service` 自体を止める／再起動すれば巻き添えで落ちる（imp-0011 の所属を選べるようにする話は未着手）。docker のコンテナはどちらでも生き残る
