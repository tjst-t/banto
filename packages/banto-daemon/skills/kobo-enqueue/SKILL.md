# 工場へ積む

## いつ使うか

**コードが変わる仕事のとき**（決定62a）。小さな修正も含む。

| 仕事 | 誰が |
|---|---|
| 調査・要約・下読み・その場の確認 | 職人へ直に（`worker.delegate`。工場は要らない） |
| **コードの変更（小さな修正も含む）** | **工場へ積む**（`kobo.enqueue`） |
| ADR・`work/` の起票・引き継ぎメモ | 自分で書く（`file.write`） |

「小さいから自分で直す」「小さいから職人に直させて終わり」をやると、**監査もマージ前ゲートも
通らない変更**が積み上がる。速さが要るなら経路を変えるのではなく、`review.policy: auto` と
model tier で調整する（決定62b）——つまみは既にある。

## 手順

1. **定義を書く**。`work/tasks/task-NNNN.md` に `file.write` で書く。番号は既存の最大＋1

   ```yaml
   ---
   id: task-0071
   type: task
   kind: fix          # feature / fix / refactor / chore / spike
   title: 一行で何をするか
   status: queued     # queued＝積んでよい。draft＝まだ積まないでほしい
   scope:
     paths: ["packages/banto-web/src/**"]   # 変えてよい場所。**マージ前に機械検査される**
   acceptance:
     - { id: a1, text: "満たすべきこと", verify: "npm test" }
   ---

   ここに依頼を書く。**これが職人に届く本文**なので、前提・目的・完了条件を書き切る
   （職人は記憶を持たない・D11）。
   ```

   - **`scope.paths` は狭く**。広げるとマージ前ゲートの検査が意味を失う
   - **`acceptance` に `verify` を付ける**と、機械が確かめられる（「動いた」の主張ではなく事実になる）
   - **`environment: <プロファイル名>`** を書くと、レビューのときに**触れる環境**が立ち、
     判断待ちの札から開ける（決定59）。プロファイルの書き方は SKILL `environment-profiles`
   - **`model_tier`** は既定 `standard`。難しい仕事だけ `reasoning`——ただし
     プロジェクトの上限を超えると**積む時点で拒否される**（決定67）
   - 統治コード（Kobo・番頭核）に触るなら `governance: true`。PO レビューが必須になる

2. **積む**。`kobo.enqueue` に `projectTag` と `taskId`、そして **`originRef`（なぜ積むのか＝
   PO の指示や経緯）**を渡す。工場は経緯を知らないので、これが無いと判断を求める札に
   「起きたこと」しか書けない（D8）

3. **以後は待つ**。ゲートを通ると職人が着手し、監査を経てマージまで運ばれる。
   **あなたが手を動かす必要は無い**（D10）

4. **返ってくる**：レビュー待ちと完了は、積んだこの会話へ届く。様子を自分から見たいときは
   `kobo.task`（そのタスクのいまと経緯）・`kobo.list`（全体）

**判断待ちが返ってきたら SKILL `kobo-review` を読むこと。** 通すか、取次で PO へ上げるかの
判断と、その積み方（`inbox.post` に何を書くか）がそこにある。

## 積んだ後に「やっぱり違った」となったら

**契約は訂正できます**（ADR-0014・決定69〜72）。ただし**定義ファイルを直しただけでは
反映されません**——改訂は記録に残す必要があるので、明示的に `kobo.amend` を呼びます。

### 手順

1. `work/tasks/<id>.md` を直す
2. `kobo.amend`（`reason` に**なぜ訂正するのか**を書く。帳簿に残ります）

### 何を変えたかで、その後が変わります

| 変えたもの | 監査 | どうなるか |
|---|---|---|
| **検証コマンド（`verify`）だけ** | **有効のまま** | 状態は動きません。マージ前ゲートで新しい検証が走ります |
| 基準（`acceptance[].text`）・条件の増減・`scope.paths` | **無効** | `implementing` へ戻り、監査からやり直しです |
| `title` / `body` | 影響なし | 状態は動きません |

**`verify` は「何をもって完了とするか」ではなく「どう確かめるか」です。** 基準は正しいのに
確かめ方だけ壊れている、というのがいちばん多い——実機では「UI の型チェックが通る」という
正しい基準に、環境の用意（`npm ci`）が焼き込まれた検証コマンドが付いていました。
**この場合は実装も監査もやり直しません。**

### あなたには通せないもの（PO の判断）

- **スコープに新しいパスを足す**（意味としては狭いものでも。glob の広い／狭いは文字列では
  解けないので、厳しすぎる側に倒しています）
- **基準（`text`）を変える** — 厳しくしたのか緩めたのか、機械には読めません
- **受け入れ条件を消す**

いずれも「できていないものを通す」方向になりうるので、**取次へ上げてください**。

### 別のものを作りたいなら

訂正ではなく**置き換え**です。新しいタスクを積み、元を `kobo.supersede` で置き換えてください。

## 落ちたとき（**タスクを切り直さない**）

**新しいタスクを積み直さないこと。** 落ちるたびに切り直すと、同じ依頼が
`task-0004` → `task-0005` → … と別 id に分かれ、**何度目の挑戦なのかが帳簿から読めなく
なります**（実機で実際にそうなりました）。同じタスクのまま、最後まで通します。

### 1. まず理由を読む（`kobo.task`）

落ちているタスクには「なぜ落ちたか」が付いてきます。**ゲートの不通過理由だけでなく、
検証ログの末尾まで**——`verify_failed:a4(exit=1)` から分かるのは番号だけで、
何が起きたかはログにしか無いからです。

### 2. どちらの問題か決める（`kobo.reopen`）

| 落ち方 | mode | 何が起きるか |
|---|---|---|
| スコープ違反・本当にテストが落ちる（**中身の問題**） | `rework` | `implementing` へ戻り、職人が起きる。**落ちた理由とあなたの指示が職人に渡ります** |
| 環境が立たない・道具が無い（**検証環境の問題**） | `reverify` | `approved` へ戻り、**中身は触らず**マージ前ゲートを回し直す |

- `reason` には**何が悪くて、どう直すのか**を書くこと。職人にそのまま渡り、帳簿にも残ります
- **`reverify` は承認まで行ったタスクにしか使えません**（監査を飛ばさせないため）。
  そこまで行っていないなら `rework` を使ってください
- **同じところで何度も落ちているなら、直し方ではなく前提を疑うこと**（P6）。
  戻した回数は `kobo.task` に出ます

### 3. どうしようもなければ畳む（`kobo.abandon`）

直せる見込みが無いときだけ。**記録は消えません**——経緯には落ちたことも畳んだ理由も
残ります。畳むと既定の一覧から外れるので、「まだ見る必要がある」ふりをしなくなります。

**`failed` のまま放置しないこと。** 既定の一覧に出続けるので、直すか畳むかを決めてください。

## 気をつけること

- **`status: draft` のまま積もうとしない。** draft は「まだ積まないでほしい」という意思表示
  なので、`kobo.enqueue` は拒む。積むと決めたら `queued` に直してから
- **新しいリポジトリを載せるなら** SKILL `kobo-onboarding`（登録・置き場・層B設定・最初の1本）
- **止まっていたら理由を読む**（`kobo.task`）。依存待ち・スコープ重複・上限のどれかで
  止まっていることがあり、黙って進まないのではなく理由が残っている
- **落ちたらタスクを切り直さない。** `kobo.reopen`（中身なら rework／検証環境なら reverify）・
  契約が間違っていたなら `kobo.amend`・どうしようもなければ `kobo.abandon`
- **承認しても関所は飛ばない**（決定57）。あなたが `kobo.approve` した後にマージ前ゲートが
  回り、スコープ違反と検証コマンドが機械的に確かめられる。飛ばす手段はあなたに無い
