# 工場へ積む

## いつ使うか

**コードが変わる仕事のとき**（決定62a）。小さな修正も含む。

| 仕事 | 誰が |
|---|---|
| 調査・要約・下読み・その場の確認 | 職人へ直に（`worker.delegate`。工場は要らない） |
| **コードの変更（小さな修正も含む）** | **工場へ積む**（`kobo.enqueue`） |
| ADR・`work/inbox` の起票・引き継ぎメモ | 自分で書く（`file.write`） |

**`work/tasks/*.md` は自分で書かないこと。** そこは Kobo が書く記録で、書いても読まれません
（第4便で入口を1つにしました）。タスクは `kobo.enqueue` から積みます。

「小さいから自分で直す」「小さいから職人に直させて終わり」をやると、**監査もマージ前ゲートも
通らない変更**が積み上がる。速さが要るなら経路を変えるのではなく、`review.policy: auto` と
model tier で調整する（決定62b）——つまみは既にある。

## 手順

1. **積む**。`kobo.enqueue` に依頼の中身をそのまま渡す。**ファイルは書かない**
   ——`task-NNNN` の採番も、`work/tasks/task-NNNN.md` の記録も **Kobo がやります**

   ```
   kobo.enqueue({
     projectTag: "banto",
     title: "一行で何をするか",
     kind: "fix",                          // feature / fix / refactor / batch / improvement
     body: "ここに依頼を書く。前提・目的・完了条件を書き切る",
     scope: { paths: ["packages/banto-web/src/**"] },
     acceptance: [{ text: "満たすべきこと", verify: "npm test" }],
     originRef: "PO の「札が飛ぶ」から"
   })
   → { taskId: "task-0042", path: "work/tasks/task-0042.md", status: "queued" }
   ```

   - **`body` が職人に届くもの**です。ここに書いていないことは伝わりません（職人は記憶を
     持たない・D11）
   - **`scope.paths` は狭く**。広げるとマージ前ゲートの検査が意味を失う
   - **`acceptance` の `id` は書かない**——Kobo が `a1`, `a2`… と振ります。
     `verify` を付けると機械が確かめられる（「動いた」の主張ではなく事実になる）
   - **`originRef`（なぜ積むのか＝PO の指示や経緯）は必須**。工場は経緯を知らないので、
     これが無いと判断を求める札に「起きたこと」しか書けない（D8）
   - **`environment: <プロファイル名>`** を書くと、レビューのときに**触れる環境**が立ち、
     判断待ちの札から開ける（決定59）。プロファイルの書き方は SKILL `environment-profiles`
   - **`model_tier`** は既定 `standard`。難しい仕事だけ `reasoning`——ただし
     プロジェクトの上限を超えると**積む時点で拒否される**（決定67）
   - 統治コード（Kobo・番頭核）に触るなら `governance: true`。PO レビューが必須になる
   - **`hypothesis: {expect, metric, horizon}`** を書くと、マージ後に `evaluating` へ回り、
     見込みが当たったかを確かめます

2. **以後は待つ**。ゲートを通ると職人が着手し、監査を経てマージまで運ばれる。
   **あなたが手を動かす必要は無い**（D10）

3. **返ってくる**：レビュー待ちと完了は、積んだこの会話へ届く。様子を自分から見たいときは
   `kobo.task`（そのタスクのいまと経緯）・`kobo.list`（全体）

**積めないと言われたら、理由を読むこと。** よくあるのは3つ：
必須が欠けている／プロジェクトの**積む口が止めてある**（PO が止めたものを勝手に開けない）／
`model_tier` が上限を超えている。

**判断待ちが返ってきたら SKILL `kobo-review` を読むこと。** 通すか、取次で PO へ上げるかの
判断と、その積み方（`inbox.post` に何を書くか）がそこにある。

## 1本だけ回す verify の書き方

**`npm test -- tests/acceptance/foo.spec.ts` は絞り込みになりません。** `test` スクリプトは
`node --import tsx --test $(ls tests/acceptance/*.spec.ts | …)` の形で**ファイル一覧をすでに
渡し切っている**ので、`--` の後ろに書いたパスは**引数として足されるだけ**。結果、毎回
全量（2400件超・約400秒）が走ります。

1本だけ確かめたいときは **`npm run test:one`** を使ってください。

```
acceptance: [
  { text: "マージゲートの不通過が failed になる",
    verify: "npm run test:one -- tests/acceptance/merge-gate-fail.spec.ts" },
  { text: "全量と型検査が通る", verify: "npm test && npm run typecheck" }
]
```

- **`node --import tsx --test <file>` を素で書かないこと。** `test:one` は全量と同じ
  `BANTO_WORKER_POOL_URL` / `BANTO_ENV_POOL_URL` を立てます。素で呼ぶとこの2つが立たず、
  試験が**本物の Worker Pool / Environment Pool を掴みに行きます**
- **走った本数を verify の中で数えるなら `--test-reporter=tap` を足すこと**
  （`npm run test:one -- --test-reporter=tap tests/acceptance/foo.spec.ts`）。Node 24 は
  パイプ越しでも既定が spec 表示（`ℹ tests 1`）なので、`# tests` を grep する書き方は
  そのままでは当たりません
- **条件ごとに全量を回さないこと。** 全量（`npm test`）と型検査は**最後の1条にまとめる**。
  理由：全量を条件の数だけ回すと時間と負荷がその倍になり、間欠失敗（`inc-0070` の
  `write EPIPE`）を**自分から誘発します**

## 積んだ後に「やっぱり違った」となったら

**契約は訂正できます**（ADR-0014・決定69〜72）。**変えたい中身を `kobo.amend` に渡す**と、
Kobo が契約を改訂し、記録ファイルも書き直します。改訂は帳簿に残ります——黙っては起きません。

### 手順

`kobo.amend` に `projectTag` / `taskId` / `reason`（**なぜ訂正するのか**）と、
**変える項目だけ**を渡します。`work/tasks/<id>.md` を自分で直しても何も起きません
（あれは Kobo が書く記録で、契約ではありません）。

```
kobo.amend({
  projectTag: "banto", taskId: "task-0042",
  reason: "環境の用意は setup に移ったので、検証コマンドから npm ci を外す",
  acceptance: [{ id: "a1", text: "満たすべきこと", verify: "npm test" }]
})
```

- **`acceptance` は全件を `id` つきで**渡します（一部だけだと、消したのか触っていないのか
  読めません）。増やすなら次の番号（`a2`, `a3`…）を自分で付けます
- 変えられるのは `title` / `body` / `scope` / `acceptance` / `environment` / `model_tier` /
  `review` だけ。**種類・親・依存を変えたいなら、それは訂正ではなく別の仕事**です

### 何を変えたかで、その後が変わります

| 変えたもの | 監査 | どうなるか |
|---|---|---|
| **検証コマンド（`verify`）だけ** | **有効のまま** | 状態は動きません。マージ前ゲートで新しい検証が走ります |
| 基準（`acceptance[].text`）・条件の増減・`scope.paths` | **無効** | `implementing` へ戻り、監査からやり直しです |
| `title` / `body` | 影響なし | 状態は動きません |

**`verify` は「何をもって完了とするか」ではなく「どう確かめるか」です。** 基準は正しいのに
確かめ方だけ壊れている、というのがいちばん多い——実機では「UI の型チェックが通る」という
正しい基準に、環境の用意（`npm ci`）が焼き込まれた検証コマンドが付いていました。
**この場合は実装も監査もやり直しません。**

### あなたには通せないもの（PO の判断）

- **スコープに新しいパスを足す**（意味としては狭いものでも。glob の広い／狭いは文字列では
  解けないので、厳しすぎる側に倒しています）
- **基準（`text`）を変える** — 厳しくしたのか緩めたのか、機械には読めません
- **受け入れ条件を消す**

いずれも「できていないものを通す」方向になりうるので、**取次へ上げてください**。

### 別のものを作りたいなら

訂正ではなく**置き換え**です。新しいタスクを積み、元を `kobo.supersede` で置き換えてください。

## 落ちたとき（**タスクを切り直さない**）

**新しいタスクを積み直さないこと。** 落ちるたびに切り直すと、同じ依頼が
`task-0004` → `task-0005` → … と別 id に分かれ、**何度目の挑戦なのかが帳簿から読めなく
なります**（実機で実際にそうなりました）。同じタスクのまま、最後まで通します。

### 1. まず理由を読む（`kobo.task`）

落ちているタスクには「なぜ落ちたか」が付いてきます。**ゲートの不通過理由だけでなく、
検証ログの末尾まで**——`verify_failed:a4(exit=1)` から分かるのは番号だけで、
何が起きたかはログにしか無いからです。

### 2. どちらの問題か決める（`kobo.reopen`）

| 落ち方 | mode | 何が起きるか |
|---|---|---|
| スコープ違反・本当にテストが落ちる（**中身の問題**） | `rework` | `implementing` へ戻り、職人が起きる。**落ちた理由とあなたの指示が職人に渡ります** |
| 環境が立たない・道具が無い（**検証環境の問題**） | `reverify` | `approved` へ戻り、**中身は触らず**マージ前ゲートを回し直す |

- `reason` には**何が悪くて、どう直すのか**を書くこと。職人にそのまま渡り、帳簿にも残ります
- **`reverify` は監査を通った実績があるタスクにだけ使えます**（監査を飛ばさせないため）。
  実績は「監査の合格」か「承認」のどちらかなので、**自動着地したタスク**
  （approve を通らず `auditing → merging` と進んだもの）にも使えます。
  監査まで行っていないなら `rework` を使ってください
- **同じところで何度も落ちているなら、直し方ではなく前提を疑うこと**（P6）。
  戻した回数は `kobo.task` に出ます

### 3. どうしようもなければ畳む（`kobo.abandon`）

直せる見込みが無いときだけ。**記録は消えません**——経緯には畳む前の状態も畳んだ理由も
残ります。畳むと既定の一覧から外れるので、「まだ見る必要がある」ふりをしなくなります。

**どの状態のタスクでも畳めます**（PO 裁定 2026-08-14）。`failed` だけでなく、`queued` の
まま依存で凍ったもの・`paused` から戻らないもの・`review-ready` で放置されたものも
畳めます。既に `closed` / `superseded` のものだけは断ります。
動いている職人が居れば止めます——止まらなければ、どのセッションが残ったかを返します。

**二度と動かないタスクを放置しないこと。** 既定の一覧に出続けるので、直すか畳むかを
決めてください。

## 気をつけること

- **積むかどうかは、積む前に決める。** `kobo.enqueue` を呼んだ時点で工場に載ります
  （`draft` で置いておく口はもうありません——迷っているものは、まだ積まないこと）
- **新しいリポジトリを載せるなら** SKILL `kobo-onboarding`（登録・置き場・層B設定・最初の1本）
- **止まっていたら理由を読む**（`kobo.task`）。依存待ち・スコープ重複・上限のどれかで
  止まっていることがあり、黙って進まないのではなく理由が残っている
- **落ちたらタスクを切り直さない。** `kobo.reopen`（中身なら rework／検証環境なら reverify）・
  契約が間違っていたなら `kobo.amend`・どうしようもなければ `kobo.abandon`
- **承認しても関所は飛ばない**（決定57）。あなたが `kobo.approve` した後にマージ前ゲートが
  回り、スコープ違反と検証コマンドが機械的に確かめられる。飛ばす手段はあなたに無い
