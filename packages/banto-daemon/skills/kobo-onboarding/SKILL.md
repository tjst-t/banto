# リポジトリを工場に載せる

## いつ使うか

**「このリポジトリも Kobo で回したい」と言われたとき。** 載せると、そのリポジトリの仕事は
「積む → ゲート → 職人が着手 → 監査 → レビュー → マージ」という同じ流れに乗る。

**載せる前に確かめること**：そのリポジトリに**テストか検証の手立てがあるか**。受け入れ基準の
`verify` が空だと、監査もマージ前ゲートも「読んで良さそう」以上のことができず、工場の値打ちが
半分になる。無いなら、**最初の1本を「検証の手立てを作る」タスクにする**。

## 手順

### 1. 検証環境を書く（**受け持たせる前に**）

**これが無いと受け持たせられません。** 工場は検証を**ホストで走らせません**——
受け持つプロジェクトのテストは、そのプロジェクトが宣言した環境の中で回します。
ホストで走らせると、ホストの状態（入っている道具・空いているポート）が検証結果に混ざり、
**コードは正しいのにテストが落ちる**からです（実際に起きた：inc-0032）。

`<repo>/meta/environments.yaml` に**プロファイルを1つ**。既定の名前は `test`：

```yaml
profiles:
  test:
    driver: docker
    config:
      compose: docker/test.yaml
    setup: "npm ci --ignore-scripts"   # 立てたあと一度だけ
    ttl: 30m
```

- **名前を変えるなら** `<repo>/meta/config.yaml` の `verify.profile` にも書く
- **道具立ては Dockerfile に書く**。ホストに `apt` するのではなく、イメージに入れる
  ——そこが「このプロジェクトの検証に何が要るか」の契約
- **依存の取得は `setup` に書く**（`npm ci` 等）。**受け入れ条件の `verify` に書かない**。
  立てただけでは node_modules は空（名前付きボリュームに隔離してあるため）なので、
  ここが抜けると検証コマンドが `command not found` で落ちます。`verify` 側に書くと
  ①受け入れ条件ごとに繰り返す②タスクを書く人が用意の仕方を当てさせられる
  ③**用意でこけたのに「テストが落ちた」と表示される**——実際に3つとも起きました（inc-0034）
  - `setup` がこけたら**環境は畳まれ、受け持ちも検証も進みません**（黙って使えない環境で
    検証したことにしない）
  - **成果が次に渡るのは名前付きボリュームのぶんだけ**。検証は毎回まっさらな
    one-off コンテナで走るので、`npm ci` の置き先（`/app/node_modules`）は
    compose でボリュームにしておくこと
- 書き方は SKILL `environment-profiles`、立てて使う手順は SKILL `environment`
- **`config.port` を持つ**プロファイルを別に用意すると、判断待ちの札に公開URLが載って
  PO が触れるようになる（決定59）。検証用（`test`）とレビュー用は分けてよい

**コミットすること。** 職人は worktree（ブランチのチェックアウト）で動くので、
**未コミットのファイルは職人からもゲートからも見えません**。

### 2. 受け持たせる（プロジェクトの登録）

工場は**プロジェクト（統治単位）ごと**に受け持つ。`kobo.register_project` に
`projectTag`（短い名前）と `repoPath`（絶対パス）を渡す。1回だけでよい。

- **名前は後から変えられない**——帳簿のイベントが全部この名前で残る
- **パスは登録された場所の中**であること（決定36g の砦）。場所として登録されていない
  リポジトリは受け持たせられない——先に PO に場所を足してもらう
- **検証プロファイルが無いと断られる**（手順1）。登録できてしまうと、最初のマージまで
  気づけない——受け持った時点で言う方が、10タスク積んだあとに言うより親切
- PO は GUI（工場のボードの「＋ 受け持たせる」）からも登録できる。**同じ口**を通る（決定25）

`kobo.projects` で確かめる。

### 3. タスクの置き場を作る

`<repo>/work/tasks/` に `task-NNNN.md` を置く。**無ければ最初に書いたときに作られる**。

**書き込みの許可が要る**（決定38）。番頭は既定でどの場所も読み取り専用なので、`file.write` が
断られたら**場所の許可を求める**——PO が許すと書けるようになる。求める範囲は**狭く**：
`work/**` と `docs/**` で足りる（コードを直すのは職人の仕事で、あなたではない・D10）。

### 4. 層B設定を置く（`<repo>/meta/config.yaml`）

**無くても動く**（既定は空）。置くと2つが効く：

```yaml
verify:
  # マージ前ゲートの検証を回すプロファイル（既定 test）。手順1 で書いたものの名前
  profile: test

review:
  # ここに触るタスクは**必ず PO まで上げる**（決定57・66）。番頭は通せない。
  # 利用体験そのもの（画面・言葉遣い）は PO の領分——番頭が「良さそう」で通す面ではない
  po_required_paths:
    - src/ui/**
    - docs/spec/**

limits:
  # 許す最大の等級。超える model_tier のタスクは**積む時点で拒否**される（決定67）
  # ——黙って下げると「安く速く終わった」と読まれ、要求水準を満たさない成果を受け取る
  max_model_tier: reasoning
  max_concurrent_sessions: 5
```

**壊れていると積めない**（I2）。書いたら1本積んで確かめること——黙って緩い方へは倒れません。

### 5. 最初の1本を通す

**小さく、検証コマンドが書けるものを選ぶ。** 通し方は SKILL `kobo-enqueue`。

最初の1本で見るのは成果物ではなく**流れが通るか**：

- ゲートを通って `ready` になるか（`kobo ready` / `kobo.list`）
- 職人が着手して `implementing` まで行くか
- 監査が回り、`review-ready` で止まって**会話に知らせが返る**か
- 通すとマージ前ゲートが回り、`merged` まで行くか

**どこかで止まったら、そこが配線の穴。** `kobo.task` に理由が残っているので読む
（I2：黙って進まないのではなく、理由が残る作りになっている）。

## 気をつけること

- **ブランチの慣習**：職人は `task/<taskId>` ブランチにコミットし、マージ先は `main`。
  別の運用（GitHub の PR 必須・保護ブランチ）があるなら、**先に PO と決める**——
  工場は fast-forward マージを直に行う
- **既にある CI と二重にならないか。** マージ前ゲートは受け入れ基準の `verify` を回す。
  CI と同じことを2回やるだけなら、`verify` を CI と揃えるか、片方に寄せる
- **コードを変える仕事は全部ここへ積む**（決定62a）。「小さいから自分で」を始めると、
  監査もゲートも通らない変更が積み上がる。速さが要るなら `review.policy: auto` と
  等級で調整する（決定62b）——つまみは既にある
- **積んだ後の契約は、`kobo.amend` でだけ変えられる**（決定64 改訂・ADR-0014）。
  ファイルを直しただけでは反映されません。検証コマンドの訂正なら監査はやり直しに
  なりませんが、基準やスコープを変えると監査からやり直しです。
  **別のものを作りたい**なら新しいタスク＋`kobo.supersede`
