# リポジトリとワークツリー

## いつ使うか

**作業できる場所の把握と用意のとき。** どのリポジトリで作業するか、同じリポジトリの別ブランチで同時に進めたい、というときに使う。repo-manager は ghq（リポジトリ）と gwq（ワークツリー）が知っている場所をそのまま提供する——独自の登録簿は持たない（決定36b）。

## 手順

1. **まず `repo.list` で何があるか把握する**
   - ghq のリポジトリ（id は `github.com/<owner>/<repo>` の形）
   - gwq のワークツリー（どのリポジトリの、どのブランチかも分かる）
   - 作業できる場所そのものの広い一覧が要るときは `place.list`（設定で足した作業領域も出る）
2. **同じリポジトリの別ブランチを別ディレクトリに置きたい** → `repo.worktree.add`
   - `repo` にリポジトリの id、`branch` にブランチ名を渡す。無ければ `createBranch: true` で作る
   - 置き場所は指定しない——gwq の規約に従う（この環境では `/home/ubuntu/worktrees/<host>/<owner>/<repo>/<branch>`）
   - **作られたワークツリーは場所として登録される**。そのまま `file.*` の `place` や `worker.delegate` の `worktreePath` に渡せる
3. **リポジトリが手元に無い** → `repo.clone`（ghq get）。**外に出ていく操作**（ネットワーク越しの取得）なので、頼まれたときだけ使う
4. **空のリポジトリを新しく作りたい** → `repo.init`（ghq create）。手元に空のリポジトリができるだけで、リモートは作らない——公開はしない

## 畳む・消す

- 用が済んだワークツリーは `repo.worktree.remove` で消す。消えるのは**作業ディレクトリだけ**で、コミット・ブランチは残る
- **未コミットの変更は消える**。消す前に `git.status` / `git.diff` で中身を確かめてから（I1）
- 消してもブランチ・履歴はリポジトリ本体に残る。取り返したくなったらまた `repo.worktree.add` すればよい

## やってはいけないこと

- **commit・push・branch の操作を探さない**。番頭は git の変更操作を持たない（決定37）。履歴を変える必要があるときは `worker.delegate` で職人へ委譲する
- **頼まれてもいない clone をしない**。リポジトリが増えるのは作業できる場所が増えることで、外とのやりとりを伴う。必要になったときだけ
- **知らない id を渡して作らない・消さない**。ghq / gwq が知らない場所への `worktree.add`・`worktree.remove` はエラーで止まり、既知の一覧が返る（I2）。黙って別の場所を触らない
