# 職人への委譲

## いつ使うか

**手を動かす仕事が出てきたとき。** 調査・実装・修正・検証は自分でやらず職人へ渡す（D10）。自分の文脈は記憶と判断に使う。

「ちょっとだけだから自分でやる」が積み上がると、番頭の文脈が実装の細部で埋まり、判断のための余地が無くなる。これがD10が防ごうとしている状態。

## 手順

1. **職人は記憶を持たない**（D11）。渡す指示に、前提・目的・完了条件を**書き切る**。「さっき話した件」は通じない
2. `worker.delegate` に渡す：
   - `taskId` — 台帳とログに残る識別子
   - `worktreePath` — 作業させるディレクトリ
   - `instruction` — 上記を書き切った指示
   - `modelTier` — 難しい仕事だけ `reasoning`。既定は `standard`（コスト）
   - `runtime` / `model` — 誰にやらせるか（下記）
3. 返ってきた `sessionId` を覚えておく
4. **見届ける**：`worker.attach` で出力を確認する。プロセスに割り込まないので稼働中でも安全
5. 方針を変えたい・文脈が足りなかったと分かったら `worker.steer` で追加の指示を渡す
6. 職人から報告・質問が来たら受け止める。質問への回答も `worker.steer`
7. **成果を確かめて良いと判断したら `worker.close` で畳む**（決定30a）
8. 続きを頼みたくなったら `worker.wake`。**元の会話ごと復元される**ので前提を書き直さなくてよい

## ランタイムとモデルを選ぶ

職人は**ランタイムを選べる**。省略すると既定（通常は pi）。

- `runtime: "claude-code"` — Claude Code（Agent SDK）で動かす。込み入った実装・長い調査など、
  読み書きの質が効く仕事に向く。**`model` でモデルを名指しできる**（`opus` / `sonnet` / `haiku`、
  または `claude-opus-5` のような具体名）
- `runtime: "pi"` — 既定。安いモデルを含め、LLM Registry の等級（`modelTier`）で選ぶ

選び方の目安：

- **既定のままでよい**仕事の方が多い。ランタイムを指定するのは、ふつうのやり方で足りないと
  分かったとき（難易度が高い／同じ仕事を安いモデルに任せて失敗した／道具の使い方が肝、など）
- `model` は `modelTier` より優先される。**名指しは高いものを選びうる**ので、難しさが実際に
  あるときだけ上げる（`worker.list` にはランタイムとモデルが出るので、あとから確かめられる）
- 選べないランタイムを頼むと、選べる名前を添えて断られる。黙って既定に落ちることはない

起こし直し（`worker.wake`）は**起こしたときと同じランタイム・同じモデル**で戻る。途中で
乗り換えたいなら、新しく `worker.delegate` する（会話は引き継がれない）。

## 畳むこと

職人は仕事を終えても待機し続ける。**放っておくとプロセスが積み上がる。**

- 畳む契機を持つのは番頭である。アイドル期限で勝手に閉じる仕組みもあるが、あれは安全弁で
  あって主機構ではない（決定30b）。「放っておけば消える」に寄りかからない
- **報告が来ただけでは畳まない。** 報告は主張であって完了の証明ではない（決定29a）。
  確かめてから畳む
- 畳んでも消えない（決定30c）。`worker.list` の履歴に残り、`worker.attach` で
  セッションの中身も読める。だから畳むのを惜しまなくてよい
- 履歴に `idle` で閉じた職人が並んでいたら、それは自分が職人の面倒を見ていない兆候

## やってはいけないこと

- **完了を職人の自己申告だけで判断しない**（I1）。テスト・ビルドの結果は直接確認する
- **指示を小出しにしない**。`steer` は方針変更のための手段で、書き切らなかった分の穴埋めに使うと職人が迷う
- **無闇に `reasoning` を選ばない**。コストが上がる。難しさが実際にあるときだけ上げる
- **畳まずに放置しない**。用が済んだ職人はプロセスとして残る
- **続きを頼むのに新しい職人を起こさない**。`worker.wake` なら元の会話が戻るので、前提を
  書き直す手間も、職人が同じ調査をやり直す手間も要らない
