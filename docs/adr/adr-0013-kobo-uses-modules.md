# ADR-0013: Kobo は工場のまま。ただし能力はモジュールから借り、レビューは番頭が一次受けする

> status: **accepted**（2026-08-06。PO 裁定）。ADR-0009 の二軸と ADR-0010 決定23・25・27・32・35・36・39・40 を Kobo 側へ適用し、`spec-daemon-core` の失効箇所を確定する。
> 決定番号は 55（ADR-0012）の続きから採る。**49・50 は既存の欠番**で、本 ADR では埋めない。

## 文脈

PO の提起（2026-08-06）——「Kobo を配線したいが、作りかけで banto の方向をピボットし、元々 Kobo に入れる予定だったものをどんどん別モジュールへ切り出している。**Kobo のコンセプトから今の banto になじむのか**含めて徹底的に見直してほしい」。

### 番頭の初版の誤読（記録として残す）

番頭は最初、**「構造逆転（ADR-0009）で自動パイプラインの前提は失効した」と判断し、Kobo をマージ前ゲートだけに縮める案を推した**。これは誤りだった。PO のイメージは一貫して工場——「番頭に頼んで Task を積み、Kobo が Worker を使って自動でさばき、状態遷移で完了まで運ぶ」——である。

誤読の原因は**観測から意図を推論したこと**である。「Kobo が3週間触られていない」「番頭ホストだけが育っている」「番頭が手でタスクを回している」という観測はいずれも正しかったが、そこから「前提が失効した」と読んだ推論が誤っていた。実際は**配線されていないだけで、中身は e2e まで通っていた**。I1（自己申告を信頼しない）は他人の報告だけでなく**自分の推論**にも掛かる、という教訓としてここに残す。

### 測った事実（2026-08-06）

- `packages/banto-daemon` は 6,564行（`daemon.ts` 3,372行）。受け入れテストは 1,203件中 1,189件 pass（fail 14件は調査環境の docker 権限で、コードの回帰ではない）
- **番頭ホストから Kobo へのコード参照は0件**。`kobo.*` Tool は0本、Kobo の GUI は0個
- 構造逆転以降の Kobo への commit は6件で、**すべて「外へ出す」作業**（Worker Pool・Environment Pool・repo-manager の切り出し）。機能追加は無い
- `tests/e2e/pipeline-merge.e2e.spec.ts` が**実 pi・実 LLM で通しを検証している**：タスク投入 → 取り込み → ready → 自動着手 → 実装 → 実監査（rework 込み）→ マージキュー → main へマージ
- 一方で `SpawnLedger` と `EnvLedger` は **Kobo と各モジュールの両方**で開かれている（決定23・32 の2段階の2段目が未了）

**照合の結論：骨格は在る。無いのは入口（番頭から積む）・出口（POへ判断を出す）・面（見る画面）と、独自台帳の後始末である。**

## 決定

### 56. Kobo のコンセプトは変えない。工場のまま維持する（2026-08-06、PO裁定）

- **`spec-daemon-core` の骨格をそのまま残す**：タスクの状態機械（13状態）・統治イベントログ・依存駆動ゲート（依存／スコープ重複／物理quota）・自動着手・監査の差配（別セッション・rework・失敗駆動の tier 昇格）・直列マージキュー・マージ前ゲート・コンフリクトの自動起票。
- ADR-0009 の二軸（体験・差配は番頭、**執行は Kobo**）は維持される。番頭が主体になったことで変わるのは**誰が仕事を積むか**であって、**積まれたものをどう回すか**ではない。
- **不採用**：Kobo をマージ前ゲート（関所）だけに縮める案。PO のイメージと噛み合わず、`spec-daemon-core` §1〜§5 の大半を失効させる代償に見合う利得が無い。
- **注記（2026-08-20 / ADR-0027 決定142）**: 骨格の「監査の差配（別セッション・rework・失敗駆動の tier 昇格）」のうち、**別セッションと rework は残る**が、**昇格が効くのは監査人が明示的に `fail` を出したときだけ**になった。判定を出し忘れた回は、もう失敗として数えない。

### 57. レビューは3段にする。番頭が一次受けし、捌けないものだけ PO へ（2026-08-06、PO裁定）

> **ADR-0023 決定113 で「番頭には通せない」の担保のしかたが変わった**（2026-08-15）。
> この決定そのもの（`po` 段を番頭が通せない）は**変えていない**——変えたのは線の引き方で、
> 「合言葉を知っているか」から「**Tool の経路か、人が押した経路か**」へ移した。
> 取次の札で PO が答えれば、そのまま Kobo の承認まで届く（imp-0034）。
>
> **ADR-0027 決定142 で「2つの機械的検査」の数え方が変わった**（2026-08-20）。
> 監査セッションはフェイルオープンになり、判定を出さなければ既定で通る——もう検査ではなく
> **補助の目**である。この節の最終段落「番頭のレビューは2つの機械的検査の上に乗る判断」は、
> これからは「**乗っている機械的検査はマージ前ゲート1つ**」と読む。決定57 そのもの
> （レビューの3段・`po` 段を番頭が通せない）は**変えていない**。

- **`review.policy` を2値から3値へ拡張する。**

  | 値 | 監査通過後 |
  |---|---|
  | `auto` | そのままマージ（人も番頭も見ない） |
  | **`banto`（新・既定）** | 番頭が受けてレビューする。捌けたら承認、捌けなければ取次へ |
  | **`po`（新）** | 必ず PO まで上げる。番頭は判断しない |

  現行の既定 `manual` は `banto` へ読み替える（人間＝PO 直行だった経路に番頭が入る）。
- **`po` は機械的に判定する。** 番頭の付け忘れに依存しない。判定材料は2つ。
  1. `governance: true`（統治コード。`spec-improvement-loop` §7 で既に「レビュー省略対象外」）
  2. **層B設定に列挙されたパスに `scope.paths` が触れるとき**（UI/UX 等）。**フレームワークはパス構成を知ってはいけない**（決定38f）ので、判定表はプロジェクト側（`meta/config.yaml`）に置く
- 同じ判定で**環境プロファイルの要求**も決まる（決定59）。「PO が触って判断する必要があるもの」と「触れる環境が要るもの」は同じ集合である。
- **番頭が `approved` にしても関所は飛ばない。** マージ前ゲートは `approved` の後に Kobo が回し、番頭に手段は無い。かつ、その前に実装者とは別の監査セッションが通っている。**番頭のレビューは2つの機械的検査の上に乗る判断**であって、検査の代わりではない——この関係が崩れたら vision の「番頭でも帳簿はごまかせない」が崩れる。

### 58. 判断待ちは番頭へ届き、番頭が捌けないものだけ取次へ上げる（2026-08-06、PO裁定）

- **Kobo は PO へ直接積まない。** `card_generated` を取次へ直結させる案は採らない——D9（利用体験を変え、かつ本物のトレードオフのときだけ PO へ）を機構に写すなら、一次受けは番頭である。
- **宛先は「積んだスレッド」。決定35 の機構をそのまま再利用する。** 番頭が `kobo.enqueue` するとき `origin`（スレッド）を渡し、番頭ホストが Kobo のイベントを購読して `origin` が自分のスレッドのものを会話へ流す。実装の型は `worker-notice.ts`（Worker Pool のイベントログを購読し `origin` で絞る／`after_event_id` で取りこぼさない）と同じで、**新しい通知系を作らない**（決定29b）。
- **起点の参照を積むときに渡す。** 取次の一通は「経緯（起点となったPOの指示）／起きたこと／求める判断」の三部構成が必須（`spec-ui` §3・`spec-design` §7）だが、**Kobo は経緯を知らない**——積んだのは番頭だからである。D8 の起点参照をモジュール跨ぎで繋ぐ。これを怠ると PO に届く札が「起きたこと」しか書けない。
- **`spec-ui` §1 の「アテンションキュー」は Kobo 独自の列としては作らない。** 判断待ちの列は取次に一本化する（`spec-design` §7・PO裁定 2026-08-05④）。Kobo が提供するのは**ボード**（状態機械のビューア）であって、判断待ちの受け口ではない。

### 59. レビューには「触れる環境」を添える。立てるのは Kobo、公開するのは Environment Pool（2026-08-06、PO裁定）

- **PO の判断が要るもの（とくに UI）は、見るだけでなく触れる状態で差し出す。** `in-review` に入ったら Kobo が `env.provision` を呼ぶ（`workdir` に職人の worktree・`expose` に公開ポート・TTL つき。`workdir` は決定34d で既に契約にある）。
- **公開は Environment Pool の責務**（決定39b）。既定の proxy 実装が `{baseUrl}/env/<envId>/` を生やし、**banto を守っている前段の認証をそのまま継承する**。番頭は中継役にならない。
- **提示は取次の `opens.canvas`**——押すと**会話と面が同時に開く**。面は基本GUIセット（ブラウザビュー／シェル／セッションビューア／DIFF）から選ぶ。
- **tmux は使わない。** 現行の「`in-review` で tmux ペインを足す」（`_autoProvisionOnReview`）は、ブラウザ面に置き換えて廃止する。Kobo から tmux 依存が消える（D6）。
- **環境の寿命は判断に紐づける。** 判断待ちの間は生かし、**判断が付いた瞬間に畳む**。放置された札の環境は TTL で落ちる。使い捨ての検証（`env.verify`）と居座らせる環境（低位動詞）の使い分けは決定34a のまま。

### 60. モジュールがあるものは Kobo 独自を使わない。基準は「台帳を持つか」（2026-08-06、PO裁定）

- **判断基準を明文化する。**

  | 種類 | 扱い | 理由 |
  |---|---|---|
  | **台帳（状態）を持つ能力**——職人・検証環境 | **必ずモジュール経由。独自実装は削除する** | 二重に持つと真実が割れる（D3）。現に `SpawnLedger`・`EnvLedger` が2つずつある |
  | **状態を持たない導出**——repo-manager（`ghq`/`gwq` から毎回導出） | ライブラリ参照でよい | 真実は `ghq`/`gwq` にあり、どこから呼んでも割れない |
  | **他モジュールの持ち物**——LLM・モデル選定 | **Kobo は関与しない。** 抽象（tier）だけを渡し、解決は持ち主がやる | 下記 (a) |

#### (a) Kobo が読んでよいのは、他モジュールが公開している API だけ（2026-08-06、PO裁定）

- **設定ファイルの相乗りも、状態を持つライブラリの共有もしない。** Kobo が他モジュールの内部（pi の `models.json` / `auth.json` など）を直接読むのは、たとえ「同じ真実を見ているだけ」でも禁じる——公開の口を通らない経路が1本でもあると、その口の変更が黙って Kobo を壊し、モジュールを差し替えられなくなる。
- **モデルは `tier` で渡す。** Kobo が知ってよいのは `reasoning` / `standard` / `fast` という**等級**までで、モデル名も鍵も知らない。`worker.delegate` は既に `modelTier` を受け取り、**解決は Worker Pool が行う**（`spec-daemon-core` §3.5「コードとタスクはモデル名を知らず、tier のみを参照する」がそのまま成立する）。
- 失敗駆動の昇格（監査2回不通過で一段上へ）も、Kobo 側は**渡す tier の文字列を変えるだけ**で足りる。
- 番頭核が `LlmCatalog` を持つ（ADR-0011 決定42）ことは変わらない。**変わるのは「Kobo はそこに触らない」**という点で、Kobo がモデル解決のために番頭ホストの稼働に依存することも無くなる（決定27b の依存の向きを守る）。

- **Kobo から削除するもの**：`EnvLedger`・provision/teardown/run/collect・TTL 執行・env 照合・**sops 復号**・プロファイル解決（`daemon.ts` の約995行）／`SpawnLedger`・`PiRpcDriver` の直呼び・孤児回収・**tmux 窓とペイン**／`BANTO_PI_PROVIDER`・`BANTO_PI_MODEL` による**モデルの直指定**（(a) のとおり tier だけを渡す）。
- **呼び出しは決定27b の規約**（`{baseUrl}/tools/{名前}` への POST・`createModuleClient`）。**到達先は `meta/modules.json` が決める**ので、どこで動かすかは配置の問題として切り離せる。
- **帰結（安全側）**：Kobo が credentials を一切見なくなる。sops 復号鍵は Environment Pool が持つ（決定32d）。
- **Kobo に残るのは統治だけ**：状態機械・帳簿・依存ゲート・監査の差配・マージキュー・マージ前ゲート・プロジェクト登録簿。`daemon.ts` は 3,372行 → 約2,100行になる見込み。

### 61. Environment Pool を独立プロセスにする（2026-08-06、PO裁定）

- 現状 Environment Pool は banto-host の中でしか動かない（`service.ts`・`bin.ts` が無い）。**Worker Pool と同じ形で独立サービスの口を足す**（`service.ts` は「Banto も Kobo もそれぞれのクライアント」という前提で既に書かれている）。
- **理由**：モジュールを banto-host の中に置いたまま Kobo から叩くと、**Kobo が番頭の稼働に依存する**。決定27b が「Banto が単一障害点になり、依存の向きが逆転する」として避けた状態そのものになる。
- デプロイは決定19 の枠（別 systemd ユニット＋依存順序＋単一インストーラ）に載せる。

### 62. 番頭と Kobo の分界（2026-08-06、PO裁定）

#### (a) コミットされるものは Kobo のタスクにする

| 仕事 | 誰が |
|---|---|
| 調査・要約・下読み・その場の確認 | 番頭が直に職人へ（決定23。Kobo 不要） |
| コードの変更（小さな修正も含む） | **Kobo のタスク** |
| ADR・`work/` の起票・引き継ぎメモ | 番頭が直に書く（`file.write`） |

3行目が Kobo を通らないのは、**番頭はコミットできない**（決定37）ため書いたものが必ず未コミットで残り、PO の diff レビューか職人のコミットを通るからである——まだ着地していない（決定38g）。

#### (b) 軽い変更のために経路を2本持たない

「小さな修正に起票→ゲート→監査→レビューは重い」への答えは**経路を分けることではない**。抜け道を作ると「面倒だから番頭に直接やらせる」が常態化し、ゲートが形骸化する。**速さは `review.policy`（`auto`）と model tier で調整する**——つまみは既にある。

#### (c) 番頭は進められるが、飛ばせない

| できる | できない |
|---|---|
| 積む・読む・進める（承認／差し戻し）・経緯を辿る | ゲートを飛ばす・帳簿を書き換える・監査を省く・**積んだタスクの契約を後から変える** |

最後の1つは既に機構で効いている：**取り込み済みのタスクは、ファイルを書き換えても更新されない**（watcher は既存タスクを読み飛ばす）。`scope.paths` は取り込み時点で固まり、マージ前ゲートはその値で diff を検査する。番頭が `work/tasks/*.md` を書けることと、積んだ後の契約を変えられないことが両立している。

#### (d) Kobo は記憶ではなく帳簿を持つ

| | 持つもの | 性質 |
|---|---|---|
| 番頭 | 記憶 | 主観的・選択的（好み・習慣・経緯） |
| 職人 | なし（D11） | 隠れ状態が無い＝再現可能 |
| **Kobo** | **帳簿** | 導出可能・監査可能・改竄不可。**要約も選択もしない** |

**Kobo に記憶を持たせない。** 「前もこうだったから今回は緩める」をしないことが、決定論的であることの意味である（D2）。D11 の非対称に Kobo を加えた形。

#### (e) タスクファイルの `status` は意図であって進捗ではない

watcher は `status: queued` を「積む合図」として読み、**ファイルには決して書き戻さない**（`no-writeback.spec.ts`）。`draft` は「まだ積まないでほしい」の意図表明である。2026-08-01 の暫定運用（番頭が完了タスクに `done` を書く）は、**Kobo 配線の完了と同時に終える**——PO 裁定Aの終端条件がこれにあたる。以後「何が終わったか」はボードと `kobo.list` から読む。

### 63. 機構の細目（2026-08-06、番頭裁定）

PO 判断を要する新しいトレードオフが無く、決定60・62 から機械的に導かれるため番頭が決めた（決定14 の運用に従い明記する）。

- **Kobo が起こした職人は、番頭からは畳めない。** `worker.close` / `worker.stop` は `origin` が Kobo のものを拒否する。畳めると Kobo の状態機械と実態が食い違う（Kobo は動いているつもりで職人が居ない）。
- **場所の砦の非対称を明文化する。** `worker.delegate` の `worktreePath` を「登録された場所の中か」検査しているのは番頭ホストが Tool を束ねる層（`bin.ts` の `guardPathArg`）であり、Kobo がモジュールを直接呼ぶ経路には掛からない。**砦が縛るのは「LLM が自由なパス引数を渡すこと」**であって、決定的コードである Kobo は対象外——これは穴ではなく設計である。書いておかないと、後から二重に検査を足すか、穴と誤読される。
- **Kobo のデータ置き場を番頭ホストの `protectedPaths` に入れる。** 現状は「場所として登録していないから書けない」という配置任せである。帳簿を番頭が触れないことは機構で担保する（決定38b と同じ考え方）。
- **テストを先に移してから実装を消す**（I1）。env の受け入れテスト16本が Kobo の実装を叩いており、先に消すと「移した先で通ること」を確かめられない。

### 64. 積んだ後の訂正は「新しいタスク＋元を `superseded`」で表す（2026-08-06、PO裁定）

- **取り込み済みタスクの契約は凍結したままにする。** ファイルを書き換えても反映しない現在の振る舞い（`task-watcher` が既存タスクを読み飛ばす）は**砦として維持する**——番頭は `work/tasks/*.md` を書けるので（決定38）、後から `scope.paths` を広げてマージ前ゲートを緩められては困る。決定62c はこの性質に依拠している。
- **訂正は新しいタスクを積み、元を `superseded` にする。** `superseded` は状態機械の横断遷移として既にある。着手後に契約が変わると「**何に対して監査したのか**」が答えられなくなるため、変更ではなく**置換**として扱う。
- **不採用**：`queued` / `ready` の間だけ再取り込みを許す案。「着手直前に広げる」が通る分だけ砦が緩み、境界（ready の瞬間）で挙動が変わる。
- **黙って失敗させない**（I2）。取り込み済みのファイルが書き換えられたことを検知したら、**反映しないという事実をイベントに残す**。いまは mtime を記録して読み飛ばすだけなので、番頭は「直したのに何も起きない」を踏む。→ inc-0028

### 65. タスクファイルの `status` を番頭が書く暫定運用は、Phase 2（入口と出口）まで続ける（2026-08-06、PO裁定）

- 決定62e は終端条件を「Kobo 配線の完了と同時」としていたが、**配線の1段目（掃除）が済んだ時点ではまだ早い**。番頭から積む口（`kobo.*`）とボードができるまで、`work/tasks/*.md` が PO にとって唯一の一覧だからである。いまやめると「終わっているのに `queued` のまま」の山が残り、**読めるものが無くなる**。
- **終端条件を差し替える**：epic-0010 の2段目（入口と出口）が入り、`kobo.list` とボードから「何が終わったか」を読めるようになった時点で暫定運用を終える。以後 `status` は意図だけを表す（決定62e の本旨は変えない）。

### 67. 費用の上限は Kobo が持ち、積む時点で拒否する（2026-08-06、PO裁定）

- **決定60a と矛盾しない**：`tier` は等級であってモデル名でも金額でもない。Kobo は「reasoning を許すか」までしか知らない。

### 139. 役割ごとに、モデルを名前で当てられる（2026-08-10、PO裁定。決定60a の改訂）

（旧・決定69。2026-08-16 に決定番号の一意化のため 139 へ移した（task-0159・imp-0073）。
ADR-0014 の決定69「契約は改訂できる」とは**別物**。2026-08-16 より前に書かれた文書の
「ADR-0013 決定69」は、この決定139 を指している。）

決定60a は「Kobo はモデル名を知らず、tier までしか渡さない」だった。PO が
**「実装やレビューを、どのモデルの職人にやらせるか、等級ではなく名前で決めたい」**と裁定した
ため、名指しの口を開く。

- **設定画面に工場の区画を出す**（決定41 の枠）。役割（実装／手直し／監査）ごとに、
  等級と**モデルの名指し**を持つ。名指しがあれば等級より優先し、監査不通過による昇格
  （決定67 の範囲内で行う `escalateTier`）も効かない——「監査は opus で」と決めたのに
  別のモデルへ化けるなら、決めた意味が無い
- **解決は Worker Pool のまま。** Kobo が知るのは `worker.models` が返す**名前**だけで、
  provider も鍵も tier→モデルの表も持たない。決定60a のうち「口を通らない経路を作らない」
  「鍵と表は能力側」は保たれる
- **ランタイム（pi / Claude Code）は名前から決まる**（`opus` → Claude Code、
  `provider/model` → pi）。起動元に併記させると、モデルを変えるたびに2か所を直すことになり、
  片方だけ直した指定が黙って通る
- 名前は**保存の時点で照合する**（I2）。打ち間違いが「実際に職人を起こす夜」に初めて
  failed として出るのでは、原因に辿り着けない
- 何も設定しなければ**これまでどおり**（タスクの `model_tier`・監査は reasoning）
