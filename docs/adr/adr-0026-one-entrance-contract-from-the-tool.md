# ADR-0026: 入口は1つ。契約は**道具の入力から**凍り、**機構は契約を作らない**

> status: **accepted**（2026-08-14。PO 指示 2026-08-13「Kobo の入口を一本化」＝ realign 第4便）。
> 決定番号は 112（ADR-0022）の続きから採る。
> **改訂するもの**：決定15 の「番頭が `work/tasks` を起票する」／ADR-0013 の「凍結の砦は
> watcher が既存タスクを読み飛ばすこと」／決定64 系（ADR-0014）の契約改訂の入口。
> 既に書いた本文は書き換えない（D3）ので、**読むときは本 ADR が優先**。

## 文脈

### 入口が3つあった

| 経路 | 何が入っていたか |
|---|---|
| 番頭の道具 `kobo.enqueue` | **`taskId` だけ**。中身は番頭が先に `work/tasks/task-NNNN.md` へ書く前提だった |
| `task-watcher` | `work/tasks/*.md` を監視し、未取り込みのものを読んで契約にしていた |
| `conflict-filer` | rebase が衝突したとき、**機構自身が**解消タスクを起票していた |

3つとも「Kobo に仕事が入る」経路なのに、**契約がどこで確定するのかが経路ごとに違った。**

### 何が壊れていたか（実測・2026-08-13〜14）

1. **凍結の砦が振る舞いの副作用に乗っていた。** ADR-0013 は「取り込み済みタスクの契約は凍結
   したまま」を、`task-watcher` が既存タスクを**読み飛ばす**ことで守ると書いていた。だが番頭は
   `work/tasks/*.md` を書ける（決定38）。守りが「読むが飛ばす」である限り、読む順番や取り込み
   判定が一箇所変わっただけで、後から `scope.paths` を広げられる。**砦は「飛ばすこと」ではなく
   「そもそも読まないこと」でなければならない。**
2. **採番の主が場面で入れ替わっていた。** 番頭が `task-NNNN` を決め、Kobo も帳簿に番号を持つ。
   ファイルと帳簿のどちらが真かが場面ごとに違い、ファイルを消すと番号が再利用された。
3. **契約が手書き YAML の往復でしか入らなかった。** 番頭が書き、パーサが読む。引用符の入れ子や
   block mapping で落ちると、**落ちたことに誰も気づかないまま契約が欠ける**。入力が文章の体裁を
   していたので、機械が受け取る形と人が書く形が同じものだと錯覚していた。
4. **機構が契約を作っていた。** `conflict-filer` の解消タスクは、受け入れ基準が「衝突が解けた
   こと」だけだった。**元タスクの受け入れ基準を誰も見ないまま main に入る**穴がここにあった。
   衝突は依頼が変わった出来事ではなく、同じ依頼の**やり直し**である。

### PO 裁定

> Kobo の入口を一本化してほしい。番頭は文章を道具で渡す。採番は Kobo。

「電卓（dentaku）の1本目は、この入口が入るまで積まない」——**廃止が決まっている経路で回しても、
古い形の確認にしかならない**ため（PO 裁定 2026-08-14）。

## 決定

### 決定113: **Kobo へ仕事が入る口は `kobo.enqueue` だけ**

`task-watcher` と `conflict-filer` の自動起票を**廃止**する。`work/tasks/*.md` が増えても Kobo は
読まない。入口が1つなので **`origin`（依頼元の会話）が必ず付き**、判断待ちと完了は積んだ会話へ
返る（決定58 がようやく例外なく成り立つ）。

### 決定114: **契約は道具の入力から凍る。ファイルは「入力」ではなく「Kobo が書く記録」**

番頭は本文を渡す——`title` / `kind` / `body` / `scope` / `acceptance` / `originRef`（任意で
`parent` / `depends` / `refs` / `environment` / `governance` / `model_tier` / `review.policy` /
`hypothesis`）。**`work/tasks/task-NNNN.md` を番頭が直しても契約は動かない。** 凍結の砦は
「watcher が読み飛ばす」から「**読み戻す経路が存在しない**」へ移った（決定62c はこの新しい
性質に依拠し直す。ADR-0013 の該当行は本決定で改訂）。

### 決定115: **採番は Kobo の責務**（`taskId` 引数は廃止）

プロジェクトごとの連番 `task-NNNN`。**「記録ファイル名の最大」と「帳簿の最大」の両方 +1** を
取る——片方だけだと、ファイルを消したときに番号が再利用されて帳簿と衝突する。

### 決定116: **順序は 採番 → 記録の書き出し → `task_created`。書けなかったら積まない**

記録が書けないのに積むと、帳簿にだけ在るタスクが生まれる（I2：黙って成功にしない）。書いた
記録は**その場で読み戻して契約と突き合わせる**——**読めない記録は記録ではない**。手書き YAML の
パーサに限界がある以上、「書けた」ではなく「読み戻して一致した」を成功条件にする。

### 決定117: **受け入れ条件の `id` は Kobo が振る**（`a1`, `a2`…）

番頭が id を決めると、改訂のたびに指し先がずれる。**何番目の基準に対して監査したか**を帳簿側で
固定する。

### 決定118: **機構は契約を作らない**（新しい原則）

rebase の衝突は、新しいタスクではなく**同じ契約の次の試行**として扱う。

- Kobo は `merging → implementing` へ戻し、衝突したファイルと git の出力を指摘として渡して
  職人を起こし直す。**やり直しは元の契約で審査される**（監査もマージ前ゲートも通常どおり）
- **2回目の衝突で `failed`**（同じところを何度も叩かない・P6）。回数は帳簿から導出する
- 印は `state_transitioned(→implementing, reason: rebase_conflict…)`。**新しいイベント型は
  足さない**（帳簿の形は one-way なので、増やすのは PO の判断・D9）

この原則は衝突に限らない。**機構が「何をもって完了とするか」を書き始めた瞬間、誰も見ていない
受け入れ基準が main に入る。**

### 決定119: **弁は watcher ではなく「積む口」に付ける**

`ProjectControl.watch` は消さず、意味を「取り込みの弁」から「**積む口の弁**」へ付け替える。
閉じているプロジェクトへは `kobo.enqueue` が断り、**止めた理由をそのまま返す**。道具名
`kobo.set_watch` は据え置く（改名は別の便）。

——**これをやらないと、PO が閉じた弁が watcher と一緒に消える**。banto 自身が「Kobo 停止中」で
運用されている以上、弁の消滅は統治の消滅である。

### 決定120: **契約を直すのも道具の入力から**（`kobo.amend` が中身を受け取る）

`kobo.amend` は**変える中身を引数で受け**、Kobo が記録ファイルを書き直す。番頭がファイルを直して
から `amend` を呼ぶ形は廃止——**書き手を1人にする**。守る3つ（黙って起きない／記録に残る／
基準が動いたら監査は無効）と、緩める方向は PO だけ、という線は ADR-0014 のまま変えない。

### 決定121: **HTTP の内部口は試験用として残す**

`POST /api/v1/projects/:proj/tasks` は残すが、**試験が Kobo の内部へ直接積むための口**である
ことを docstring と spec に明記する。運用の入口ではない。旧称の語彙（`review.policy: manual`
など）を帳簿に載せて「**読む側が旧称を人へ倒すこと**」を確かめるのに要る。

### 決定122: **過去の記録は消さない。読まれなくなるだけ**

既存の `work/tasks/*.md` は残す。消すと、いま動いているタスクの経緯が読めなくなる。

### 決定123: **退役させた設定は、消したうえで「書いてあっても壊れない」ことを試験で縛る**

層B設定 `verify.conflict_command` は、唯一の読み手（`conflict-filer`）が消えたので退役した。
**解析ごと消す**（残すと「効いている」と誤読される）。同時に、**稼働中の `meta/config.yaml` に
その欄が残っていても Kobo が起動できる**ことを試験で固定する——`loadProjectConfig` は未知の欄を
弾かない作りだが、それは**性質であって約束ではなかった**。誰かが未知キーの検査を足した日に、
稼働中の設定で起動できなくなる。

## 受け入れ（この ADR が満たされたと言える条件）

1. `work/tasks/*.md` を新しく置いても、Kobo が何も積まないこと
2. `kobo.enqueue` に `taskId` を渡せないこと。積むと `task-NNNN` が Kobo から返ること
3. 記録が書けない状況で積むと、**帳簿にもタスクが生まれない**こと
4. rebase が衝突したとき、新しいタスクが起票されず、同じタスクが `implementing` へ戻ること。
   2回目で `failed` になること
5. 弁を閉じたプロジェクトへ積むと、**止めた理由つきで**断られること
6. `meta/config.yaml` に `verify.conflict_command` が残っていても Kobo が起動すること

（1〜6 はいずれも受け入れ試験として存在する。ホスト全量 2108/2108 pass、docker では環境由来の
`source-hygiene`（worktree の `.git` がコンテナに入らない）1本を除いて緑。2026-08-14 実測）

## 残る論点

- **`kobo.set_watch` の名前**が実態（積む口の弁）とずれている。改名は道具の名前の変更なので別便
- **`docs/notes/handoff.md` と `docs/ROADMAP.json` の watcher 記述**が残っている（番頭の持ち物）
- **`kind: conflict`**（`docs/spec/schemas.md`）は語彙として残っているが、機構は使わなくなった
