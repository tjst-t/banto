# ADR-0010: 記憶 Substrate（記憶エントリのスキーマ）の確定 — Quirefold §2 を基礎に、閉じた列挙を開く

> status: **proposed**（探索ブランチ `explore/agent-primary` の working canon）。[agent-primary-inversion §11.6-③](../notes/agent-primary-inversion.md) の残り1決定に対応する。
> **改訂（2026-07-26 第2版）**：初版の内容を10シナリオでシミュレーション検証した結果（§6）、初版の確定事項のうち3点が破れたため書き直した。初版はコミットしておらず、本文が唯一の版である。
> 前提となる既決：決定①＝Kobo と Quirefold の完全分離（同ノート §11.6-①）、決定②＝Banto ハーネス自作（同 §13）。
> PO 裁定：横断の自動化と事後訂正（§2）／出典の持ち方（§4）／Quirefold の設計を変更してよい、の3点。それ以外は inversion §4 の境界により番頭決定。
> 補足（P3）：`status: proposed` は spec-schemas §3 の enum（`draft`/`accepted`/`superseded`）に無い。ADR-0009 が既に使用しており本ADRも揃えたが、正式化フェーズで解消する。

## 文脈

ADR-0009（番頭主体への構造逆転）で、記憶システムは「機能」から「番頭の核」へ昇格した。その核の詳細設計が [Quirefold](../spec/memory.md)（`spec-memory`）である。**Quirefold は banto の記憶サブシステムであり、別プロジェクトではない**（2026-07-26 に PO が位置づけを確定し、仕様書を `docs/spec/` へ統合した）。設計は可変であり、banto を作る過程で確定していく。

Quirefold は設計判断を可逆性で階層化しており（§0.5 原理3・§0.6）、**Substrate（記憶エントリのスキーマ・不変性・版管理・出典・時間）だけは後から変更できない**。スキーマに欠けた項目を後から足しても過去の記憶に遡及できず、「出所不明の古い記憶」が永久に残るためである。これは inversion §4「pre-release は壊してよい」の明示的な例外にあたり、実装に入る前に確定させる必要がある。ただし**凍結点は「記憶の蓄積開始時点」であってリリース時ではない**。

一方、既存の ADR-0003（記憶の二層モデル）は同じ領域に触れており、そのままでは並立できない。ADR-0003 は「記憶はイベントログから蒸留した**導出**であり、競合する真実を持たない（D3）」と定めているが、決定①で Kobo（実行の統治）と Quirefold（記憶）を**完全分離・ブリッジなし**と決めた時点でこの前提は成立しない。Quirefold は自前の出典グラフと版管理を持つ独立の真実であり、イベントログの射影ではない。

**本ADRの初版は、Quirefold §2 を素のまま採り、`fact_type` を3値に拡張し、`context.scope` を `person` / `project` の2値とした。** これを10のシナリオ（開発6・非開発4）でシミュレーション検証した結果、**閉じた列挙にした箇所がすべて破れた**（§6）。本版はその結果を反映して書き直したものである。

## 決定

**Quirefold §2 の記憶エントリスキーマを基礎として採用する。ただし Substrate に置く値域は、予測できるものだけを閉じ、予測できないものは開いた識別子とする。** 併せて ADR-0003 を置換し、その生き残る決定を本ADRに再掲する。

### 0. ADR-0003 の扱い＝全面 supersede ＋ 再掲

spec-schemas §3 の `supersedes` は id 単位で、部分supersede を表現できない。二重真実を作らないため（D3）、**ADR-0003 は全面 supersede** し、生き残る決定を本ADRに再掲する。

| ADR-0003 の決定 | 本ADRでの扱い |
|---|---|
| 記憶を二層（人＝横断／プロジェクト＝閉じる）で持つ | **維持・一般化**（§2。二層は閉包木の root と leaf という特殊ケースになる） |
| 統治の単位はプロジェクトなので混ぜない | **維持**（§2。閉包の境界として表現） |
| 中身は可視・編集可能＝PO主権・透明性 | **維持**（編集＝新版作成、§3 immutable） |
| 記憶はイベントログから蒸留した**導出**であり真実ではない | **置換**。決定①により Quirefold は記憶についての真実そのもの。二重真実の回避手段が「導出であること」から「領域を分けること」に変わる |
| 蒸留規則・鮮度管理は未設計 | **部分的に解消**（Quirefold §14 / §13 / §18）。ただし §6 の検証で発火条件が未定義と判明したため、完全な解消ではない |
| spec-ui に記憶モデルを追記する | **変更**。記憶モデルは `docs/spec/memory.md` に置く（番頭の核であり UI spec に間借りするものではない）。なお ADR-0003 のこの指示は実施されていなかった |

### 1. 共通コア

```
id                  mem-<ULID>（§3）
kind                episode | semantic | procedural
fact_type           preference_decision | state_fact | world_fact  ← kind: semantic のみ必須、他は null（§1.1）
content             { headline, summary, full }
created_at          記録時刻（減衰計算の基準）
valid_from          事実が真になった時点
valid_until         事実が真でなくなった時点（null = 現在も有効）
origin              user_explicit | agent_inferred | external      ← 判定基準は「情報の実質的な出所」（§1.2）
sensitive           機微フラグ（§5）
session_id          記録元セッション（並行識別）
context             { scope, …任意の検索用特徴量 }                 ← Substrate が保証するのは scope のみ（§2）
derived_from[]      出典エントリID。**版を pin する**（§4）
external_ref[]      ストア外にある権威ある実体へのポインタ（§4）
version             版番号
superseded_by       後継版のID（null = 最新版）
tombstone           削除マーカー。**立てるときは新版を作る**（§3）
strength            想起強度（単一スカラー）
salience            顕著性
```

Quirefold §2 が確定済みとした4点（strength は単一スカラー／confidence は持たず出典から都度算出／episode と semantic はスキーマ共通化／削除は tombstone＋アーカイブ降格）と、「ワーキングセットの滞在状態はエントリに書かず、セッション側テーブルに持つ」という規律を**そのまま採用する**。後者は分身（inversion §5）が同一記憶に対して独立の滞在状態を持つ前提そのものである。

**再掲（ADR-0003 より）**：記憶の可視範囲は二層以上に分かれる。人についての記憶は横断し、プロジェクトの記憶はそこに閉じる。統治の単位はプロジェクトなので混ぜない（spec-multi-project §1）。記憶の中身は PO に可視・編集可能とし、PO主権と透明性を担保する。

#### 1.1 `fact_type` は `kind: semantic` にのみ適用する

`fact_type` の唯一の役割は §12 の矛盾解決規則の分岐である。矛盾解決は意味記憶の運用であり（§19「エピソードログ＝完全並行・追記のみ」＝エピソードは版管理・矛盾解決の対象ではない）、手続き記憶の「やり方」は事実の種類ではない。したがって：

- **`kind: semantic` では必須、`episode` / `procedural` では null**。

値は3値とする。Quirefold §12 の2値（`preference_decision` / `world_fact`）に `state_fact` を加える（PO 裁定により spec-memory 側も同時に直す）。

| `fact_type` | 中身 | 矛盾時の規則 | 再検証 |
|---|---|---|---|
| `preference_decision` | **規範的言明**（「そう決めた」。真偽ではない） | **最新性が勝つ**。ただし §1.3 の origin 優先が先に効く | 不可＝PO に聞く／訂正を待つ |
| `state_fact` | 時とともに変わる客観的状態 | **観測し直して裁く**。観測できないときは最新性 | 可＝`external_ref` の先を見に行く |
| `world_fact` | 変わりにくい客観的事実 | **出典の数と独立性が勝つ** | 可（コスト高） |

初版は `preference_decision` を「**人**の選好・決定」と定義したが、これでは番頭自身の運用判断（PO 未承認）が3値のどれにも入らない（§6-S6）。**規範的言明かどうかで分類し、誰が決めたかは `origin` が持つ**、と定義を分離する。

分類ガイド（Policy／`docs/spec/memory.md` へ）：**主体が内部か外部かを問わず、時とともに変わる客観的状態は `state_fact`**。競合他社の現在のアーキテクチャ、電力の契約プラン、リポジトリの依存バージョンはすべてこれに当たる。ここを `world_fact` に倒すと「長く居座った誤りほど出典が多い」逆転（§12 が自ら警告）が再現する（§6-S8）。

#### 1.2 `origin` は「情報の実質的な出所」で決める

初版は「職人（Worker Agent）の出力 → `agent_inferred`」とした。これは**誰が `record()` を呼んだか**で決める規約であり、Quirefold §0.8 が要求する「外部由来は滞在・確信度・権限のすべてで厳しく扱う」の判定軸（＝情報の出所）と一致しない。両者は職人が自分の知識だけで推論するときにのみ一致するが、inversion §4 は「番頭は細かい仕事をしない、調査は職人へ投げる」と定めているため、**Web 由来の情報はほぼすべて職人経由で入る＝不一致が主経路になる**。この規約のままでは、汚染された外部情報が `agent_inferred` として記録され、§7 / §9 / §12 の三重の防御が丸ごと迂回される（§6-S10）。

- **`external`**：Web・サードパーティ・外部システムに**実質的に由来する**記述。誰が持ち込んだかを問わない。
- **`agent_inferred`**：番頭または職人**自身の推論・統合・判断**。
- **`user_explicit`**：PO の発話。

これを実現するため、Policy 側に次を課す（Substrate 変更なし）：職人の報告は、Web/外部ツールを使った場合 `citations[]`（取得元と引用文）を必須とし、番頭は**引用部分と職人の結論を別エントリに分割して記録**する。引用エントリは `origin: external` ＋ `external_ref` に取得元、結論エントリは `origin: agent_inferred` ＋ `derived_from` で引用エントリを指す。「外部ツールを呼んだのに citations が空」は**ルールベースで弾ける**（§0.5 原理2＝LLM の判断力に依存しない一次防御）。

#### 1.3 矛盾解決は `origin` を先に見る

Quirefold §12 の `preference_decision`「最新性が勝つ」には origin の例外がない。このままだと、番頭が後から作った `agent_inferred` の版が、PO の `user_explicit` の決定・訂正に**時刻の新しさだけで勝つ**（§6-S3 / S5 が独立に指摘）。これは §0.7 の1位（ユーザーの訂正が消える）そのものである。

- **`origin: user_explicit` は `agent_inferred` / `external` に無条件で優先する。同一 origin の中でのみ最新性で裁く。**
- これは**書き込み経路の実行層で強制する**（深い睡眠の統合処理が、最新版が `user_explicit` のエントリに対して `agent_inferred` の新版を作れないようにする）。プロンプトの記述に委ねない（§0.5 原理2）。

### 2. 可視範囲は `context.scope` ＝ 閉包識別子

```
context = {
  scope: <閉包識別子>      ← Substrate が保証する唯一のキー。可視範囲を決める
  …                       ← project / repo / tool / mode 等。検索用の任意特徴量（§11 文脈一致度）。可視範囲には影響しない
}
```

初版は `scope` を `person` / `project` の2値としたが、非開発ドメインで嵌らない（家計は「開始と終了のあるプロジェクト」ではなく、かといって全て `person` にすると将来の「健康」「育児」と混ざる。§6-S7）。3値（person/domain/project）にしても、1プロジェクト＝複数リポジトリ（ADR-0008）で repo 単位の規約が要るときに同じ問題が起きる。

- **`scope` はその記憶が有効な最小の閉包の識別子を持つ**。`person` を root の予約語とし、それ以外は閉包レジストリが解決する（例：`repo:banto/web` ⊂ `proj:banto` ⊂ `person`）。
- **注入可否は閉包の包含関係で決まる**：現在の実行文脈が属する閉包と、その祖先に属する記憶が候補になる。
- ADR-0003 の「二層」は、この木の **root（人）と leaf（プロジェクト）という特殊ケース**として保たれる。
- **`context` の他のキーは開いた任意の集合とし、Substrate は値域を規定しない**。初版は `{scope, project, repo, tool, mode}` と固定したが、`repo` は非開発ドメインで恒久的に無意味になり、`project` は Kobo のプロジェクト概念に暗黙に紐づく（＝不可逆層に開発語彙が残る。付録B のドメイン非依存性の主張と衝突する。§6-S7）。

**閉包の包含関係を解決するレジストリが必要になる**（Policy 側のデータ）。これは2つ目の店を増設する時点でどのみち要るものであり（inversion §12.2「スロット集合は open」）、Substrate の外に置ける。

#### 2.1 横断は番頭が自動判断し、PO が事後に訂正する【PO裁定】

事前承認のゲートは置かない。毎回別プロジェクトで言い直させる番頭は体験として成立しないため、安全側の担保を**事前のゲートではなく事後の可視性と訂正**に置く。成立条件を Substrate 側で満たす：

- **誰が決めたかが `origin` で判る**：番頭の自動判断は `agent_inferred`、PO 由来は `user_explicit`。Memory 面は「番頭が自動で広げた記憶」だけを絞って提示できる。
- **PO の訂正は新版として記録される**（§3 immutable）。`scope` を直した新版を `user_explicit` で作り、旧版に `superseded_by` を張る。
- **番頭は訂正された scope を上書きし返せない**（§1.3 の origin 優先を実行層で強制）。
- **前提条件**：Memory 面に「番頭が自動で広げた記憶」の一覧と訂正導線が要る。本ADRの範囲外だが、**これが無い限り「事後訂正で担保する」という主張は成立しない**（§6-S5）。実装順序として、自動横断を有効にする前にこの面を用意する。

### 3. ID・時刻・不変性

- **`id` は `mem-<ULID>`**。分身（§19 並行セッション）が中央採番なしに一意採番でき、時間順序を内包する。banto の文書ID（`task-0042`＝ツールが採番）とは別体系にする。記憶エントリは文書ではなくストアの行であり、採番のためにロックを取るのは並行前提と相容れない。ID の書式は不可逆。
- **時刻は ISO 8601 / UTC 文字列**（`created_at` / `valid_from` / `valid_until`）。表現形式は遡及して直せないため Substrate で固定する。
- **`tombstone` を立てるときも新版を作る**。Quirefold §3 は「エントリは immutable、上書きしない」と定め、§2 確定論点4 は「削除は tombstone で表現」と定めるが、**tombstone フィールドを立てる行為自体が改変**であり、両者が噛み合っていなかった（§6-S4）。immutable に例外を作らず、`tombstone: true` の新版を作って旧版に `superseded_by` を張る、に統一する。
- **再固定化のとき、旧版の `valid_until` を新版の `valid_from` で埋める**。埋めないと「今も真」と「置換済み」が同一エントリ内で矛盾する（§6-S2）。

### 4. 出典：`derived_from` は版を pin し、`external_ref` はストア外を指す

```
derived_from[] = [ <エントリID（版を特定する）> , … ]
external_ref[] = [ { system: <開いた識別子>, id: <その系での識別子> } , … ]
                 例: { system: "kobo", id: "task-0042" } / { system: "skill", id: "skills/release/v2/SKILL.md" }
```

- **`derived_from` は特定の版を指す（latest 追随ではない）**。監査可能性を優先する。代償として、出典が新版に置き換わったことは自動では伝播しないので、**出典の最新版が supersede された／tombstone されたエントリを再検証キューへ積む**規則が要る（Policy）。Quirefold §4「宙ぶらりんノードの防止」は出典が**全消滅**した場合しか定めておらず、部分喪失と版置換をカバーしていない（§6-S2 / S5 / S6 / S7 / S9 が独立に指摘）。
- **`external_ref` の `system` は列挙型にしない**【PO裁定】。Kobo 専用にせず、権威ある外部記録なら何でも指せる汎用の参照とする（inversion §12.2「サブシステムのスロット集合は open」と同じ規律）。`state_fact` の再検証先もこれを辿る。
- **`derived_from` は Quirefold エントリ、`external_ref` はストア外**。型を混ぜない。ADR-0003 の originRef は、ミラーではなく `external_ref` として生き残る（決定①：Kobo ログは取り込まない＝D3 の二重真実回避）。
- **出典の独立性判定（§4）に `external_ref` の一致を加える**（Policy）。§4 は独立性を `session_id` と `origin` で測るが、同一の外部ソースを別々に踏んだ複数エントリは、session_id が違っても独立ではない（§6-S10）。**フィールド追加は要らない。参照の一致で相関を測れる。**
- **再検証フラグはエントリに持たない**。出典の状態から導出できる（D3。confidence を保存しないのと同じ理屈）。キュー側またはセッション側に持つ。

**付随ルールの訂正**：初版は決定①に従い「Kobo ログの照会結果は再照会で再現できるので episode に退避しない」と書いたが、これは**生イベントには成立するが、集計・分類済みの事実には成立しない**（§6-S6）。「認証タスクの差し戻し率 8/12」の「差し戻しか否か」という分類はゲート構成に依存し、構成が変われば再照会で別の答えが返る。**集計・分類を伴う `state_fact` は、`context` にその判定に使ったルールの識別子を残す**（何のルールで導いたかへの参照だけ残せば、値そのものは外に置ける）。

### 5. `sensitive` — 機微フラグ

**boolean を1つだけ追加する。** 既定は false。番頭が判断して立て、PO が訂正でき、`user_explicit` が `agent_inferred` に勝つ（`scope` と同じ型）。

これが立っているエントリには Policy 側で次を課す：**職人への指示文に理由を含めない（確定した制約の結論だけ渡す）／番頭から自発的に持ち出さない／自動での可視範囲拡大の対象外**。

必要な理由：第三者の機微情報（同僚の異動意向など）は `fact_type` のどれにも属さず、`scope` を狭めるだけでは足りない（可視範囲と、職人へ渡してよいか・自発的に言及してよいかは別の制御）。判断を LLM のその場の良識に委ねると §0.5 原理2 に反する（§6-S9）。

**限界を明記する**：このフラグは**検知を信頼できるようにするものではなく、番頭の判断を可視化して訂正可能にするもの**である。立て忘れは起こりうる。段階を持つ列挙にはしない（列挙は §6 の教訓により Substrate では避ける）。

### 6. 本版の根拠＝10シナリオのシミュレーション検証（2026-07-26）

初版を、Kobo（開発）6件・非開発4件の計10シナリオで敵対的にシミュレートした。判定は「動く」0件、「動かない」2件、「実質動かない」1件、「条件付きで動く」7件。

**構造的な診断**：Quirefold は**規則を書いているが、発火条件を書いていない**。§12 は矛盾の裁き方を定めるが検出を定めず、§13 は減衰を定めるが休眠トピックの再浮上を定めず、§4 は出典の全消滅を定めるが部分喪失・版置換を定めていない。これは §0.2 の「memory はタイマーもループも持たない。判断は常に driver 側に置く」という規律の帰結であり、**判断を全部 driver に移したのに driver（§20・§21）が2節しかない**ことによる。Substrate は概ね健全で、欠けているのは Policy / Loop の配線である（10体中9体が「Substrate 変更不要」と判定）。

初版から本版で改めた点：`fact_type` の適用範囲（5シナリオが別々のカテゴリで3値に入らないケースを報告）／`preference_decision` の定義／`origin` の判定基準（S10）／矛盾解決の origin 優先（S3・S5）／`scope` の列挙をやめ閉包識別子へ（S7）／`context` の値域を開く（S7）／`tombstone` と immutable の統一（S4）／`derived_from` の版セマンティクス（S7）／`sensitive` の追加（S9）。

## 帰結

- (+) Substrate から**閉じた列挙が2つ（`scope`・`context` のキー集合）減り**、残る列挙は `kind`（認知アーキテクチャの骨格）・`fact_type`（semantic 限定・矛盾解決の分岐）・`origin`（信頼境界）の3つに絞られた。いずれも役割が単一で、検証で破れなかったもの。
- (+) 不可逆層から開発固有語彙（`project` / `repo` の必須化）が消え、Quirefold 付録B の汎用性主張が実態に追いついた。
- (+) `state_fact` の矛盾が「観測で裁く」に落ち、記憶の一部が LLM の判断を経ずに決着する（§0.5 原理2）。`external_ref` がその観測先を与える。
- (+) embedding をスキーマから外したことで、ベクトル索引・埋め込みモデル・保存ミドルウェアの選択がすべて Substrate の外（可逆）に落ちた。初期実装は embedding 無しで始められる。
- (+) 保存実装は記憶の種類ごとに分けてよい（Quirefold §1）。共通にするのは論理形だけで、索引・書き込み特性・実体の置き場所は種類ごとに異なってよい。単一ストア内でテーブルと索引を分ける（別ミドルウェアを4つ立てない。理由＝分身の一貫スナップショット §19 がストアを跨ぐと取りにくい／D6）。手続き記憶の実体は **SKILL.md を版付きパス**（`skills/<name>/v<N>/SKILL.md`）に置き、`external_ref` が版付きで指す。固定パスを上書きすると、エントリが immutable に版を刻んでいるのに実体だけが履歴を失う（§6-S4）。
- (−) **Policy / Loop に少なくとも7つの未定義がある**（§6）。矛盾の検出／訂正・削除の派生記憶への伝播／`superseded`・`tombstone` の候補からの除外／休眠トピックの再浮上／`state_fact` の観測トリガー／`record()` に `external_ref` を渡す引数／職人の失敗を番頭へ返すチャネル。**これらは ADR-0010 の範囲外だが、埋めない限り本スキーマは機能しない。** `docs/spec/memory.md` へ「未定義」として明記し、隠さない。
- (−) **決定①（Kobo 完全分離）の代償が3つ露呈した**：分身が Kobo に command を送って現実を変えた後、その学びが敗れても設定を戻す手順がない／「再照会で再現できる」が集計・分類済みの事実には成立しない／Kobo の「誤登録の削除」は append-only と矛盾する（**P3 の incident 案件**）。決定①自体は維持するが、これらは別途設計が要る。
- (−) `scope` を閉包識別子にしたため、**包含関係を解決するレジストリが必要**になる。また識別子の誤り（存在しない閉包）を検証する必要がある。
- (−) `sensitive` の立て忘れは防げない。フラグは訂正可能性を与えるだけである。
- (−) **spec-memory の本文を同時に直す必要がある**（本ADRが正典で、spec 本文が追随する。P3）：§2 スキーマ（`external_ref` / `sensitive` / `scope` の値域 / `fact_type` の適用範囲）、§4（独立性判定に `external_ref` 一致、部分喪失と版置換）、§12（`state_fact` と origin 優先）、§3（tombstone も新版）、§25 と §2 の物理削除条件の不一致、および §2 が参照する存在しない「§26」。
- (−) 記憶エントリのID体系が banto の文書ID規約と別になる。二系統を運用する認知コストは残る。
- 記憶の spec は `docs/spec/memory.md`（`spec-memory`）に統合済み。本ADRが Substrate の正典であり、spec 本文と食い違う場合は本ADRが優先する（P3）。方針変更はこのADRの supersede を要する。
