# ADR-0018: モジュールが登録する道具には**宛先**がある（**採らなかった**）

> status: **superseded**（2026-08-12）。**決定A・B・C・E は撤回**し、決定D は
> ADR-0019 決定87 が引き継ぐ。**`amends: adr-0010` は取り下げる**——決定25 の改訂は
> 行わない。この文書は**何を調べ、どこを間違えたか**の記録として残す。

## なぜ撤回したか（要約）

この ADR は「モジュールがプラガブルで増えるので、増えるたびに番頭の道具箱が太る。
**増えても太らない構造**を決める」という問題設定に立っていた。**その問題設定が
実態と合っていなかった。**

| ADR の前提 | 実測 |
|---|---|
| モジュールが増えて太る | モジュールは**8つ、全部自作**。第三者モジュールは**0**で、読み込む機構も無い（登録は `packages/banto-host/src/bin.ts:749` のハードコード配列だけ） |
| 太らせているのはモジュール | 100個のうち**48個は中核**（`llm.*` 19・canvas・thread・memory・skill・artifact・handoff）。宛先はモジュール契約なので**最大の膨らみに届かない**（`llm.*` は ADR-0011 決定42 で中核へ引き上げた） |
| 道具箱を絞るには新しい機構が要る | **pi が既に持っていた**。`AgentSession.setActiveToolsByName()` は banto が握っているセッションの公開 API（`node_modules/@earendil-works/pi-coding-agent/dist/core/agent-session.d.ts:308`） |

置き換える設計は **ADR-0019「在庫と提示を分ける」**。

## 決定ごとの処遇

| 決定 | 処遇 | 理由 |
|---|---|---|
| **A**（宛先＋2段の許可） | **撤回** | 守る対象（第三者モジュール）が存在しない。中核48本に効かない。目的は決定82（在庫と提示の分離）が新しい機構なしで満たす。加えて許可の置き場が既存機構と衝突する（決定41「値の持ち主はモジュール」・決定73「PO の判断は取次1本」） |
| **B**（遅延開示はしない） | **撤回** | 捨てた理由の中心は「約400行の自作・実機未検証」だった。**pi が公式に機構を持っている**（`docs/extensions.md` の "Dynamic Tool Loading"、`search_tools` の実装例つき）ので、費用の前提が消えた。ADR-0019 決定86 で条件つきの選択肢として残す |
| **C**（100個の仕分け） | **ADR-0019 決定83 へ移管** | 主題としては正しい。ただし表が実名と合っていなかった（下記「間違い④」） |
| **D**（職人には広げない） | **ADR-0019 決定87 が継承** | 結論は残す。根拠は差し替える（下記「間違い③」） |
| **E**（`worker.tools`） | **撤回** | **配線が存在しない。** モジュールの道具を職人に載せる口は `worker.delegate_toolkit` の `driverOptions.extensionPaths` だけで、これは番頭に渡さない `internalTools`（`packages/banto-worker-pool/src/worker-tools.ts:469-480`「番頭は LLM なので、指示次第で任意のパスを渡しうる」）。`worker.delegate` の `tools` は**許可リストであって、載っていない道具を生やすものではない**（`pool.ts:915-926`・`pi-rpc-driver.ts:307`） |

## 間違いの記録

**同じ轍を踏まないために残す。** 5件のうち4件は「測り方」ではなく「**確かめずに書いた**」。

### ① 出典に無い数字を、前提の全部に使った

本文は「約200個で 41〜83%、約740個で 0〜20%」「10〜15個を超えたあたりから落ち始める」と
書き、2件の URL を添えていた。**2人が別々に当たって、どちらの出典にも無かった。**

引いた論文（arXiv:2605.24660「How Many Tools Should an LLM Agent See?」）が実際に
言っているのは逆に近い——抄録より verbatim:

> On BFCL (370 tools), the learned policy nearly matches the coverage of showing 50 tools
> ($90.3\%$ vs $90.8\%$) while presenting only 7 on average.

**370個で 90.3%** は「200個で41〜83%」と矛盾する。さらに同論文の主張は
「**chance baseline を補正せずに道具数を跨いで raw accuracy を比べるな**」で、
この ADR の位置実測（16/16・0/10…）がまさにそれに当たる。

**代わりに使える、一次情報で確認できた数字**（ADR-0019 が引く）:

- Anthropic 公式: `Claude's ability to pick the right tool degrades once you exceed 30–50 available tools.`
  （https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool）
- OpenAI 公式: `Aim for fewer than 20 functions available at the start of a turn at any one time`
  （https://developers.openai.com/api/docs/guides/function-calling）

**前提そのものは正しかった。間違っていたのは引用だけだった**——それでも、根拠として
出した数字が出典に無いのは、この文書で最も重い欠陥だった。

### ② 「モデルの出来ではない」を、1モデルの実験から言った

位置の実測はモデルを固定して位置だけ振ったので、**モデル効果を測る自由度が無い**。
そこから「モデルの出来ではない」は原理的に出ない。

しかも自分が `refs` に挙げた inc-0056 が反証していた——同じ100個で
`deepseek-v4-flash-abliterated` は 1〜3/12、kimi・qwen は 93%。
tap の検体（`/home/ubuntu/banto-desk/reports/tap/req-0007.json`）の `model` は
**その abliterated 版**だった。ADR には**モデル名も日付も再現手順も書いていなかった**。

（なお PO 裁定により、番頭のモデルは**ローカルで無料に使える DeepSeek 系に固定**する。
したがって「別のモデルを使う」は逃げ道にならず、改善は必要——これは ADR-0019 の前提。）

### ③ 「60.9% が `worker.*`」を、D10 の裏書きとして使った

`worker.close` が単独で全体の **48.8%（5,479回）** を占めることは、`refs` に挙げた
inc-0057 に「**無駄か、機構の取り違えか、まだ見ていない**」と書いてあった。
本文はそれを伏せたまま主張の柱に使った。

**調べた結果、使い方ではなく暴走ループだった。** 5,479回のうち **5,045回が3セッションに
集中**し、その中に**同一引数で832回連続**という走りがある。原因は機構側:

```
packages/banto-worker-pool/src/pool.ts:1179-1181
  async close(sessionId, reason = "done") {
    const worker = this.requireWorker(sessionId);
    if (worker.state === "closed") return;      // ← 黙って成功
```

畳み済みでも `畳みました` を返すので、モデルは「効いていない」と読んで繰り返す。
`turn-budget.ts:36-41` が別件で既に言語化していた教訓（「空の結果は『何も無かった』と
読まれ、もう一度確かめに来る」）と同じ形。

差し引くと最大の実使用は `file.*`（24.7%）——**番頭が自分でファイルを読んでいる**回数で、
これは D10 の裏書きではなく反証である。

### ④ 決定C の表を、実名100個と突き合わせずに書いた

- 「`git.*` の**書き込み系**」→ **存在しない**。`git.*` 6本はすべて閲覧のみ
  （`packages/banto-host/src/modules/workspace.ts:155`「gitは閲覧のみで、変更操作は持たない（決定37）」）
- steward 列を足すと **36本**。本文の「**30個前後**」と合わない
- **28本がどの行にも現れない**（`kobo.*` 11・`git.*` 6・`skill.*` 4・`place.*` 2・
  `file.write/find/stat` 3・`system.restart`・`pi.agent.describe`）。既定が `worker` である以上、
  書き落としは「未定」ではなく**削除**になる。`kobo.enqueue` が落ちれば番頭は仕事を積めない

### ⑤ 決定D の標本から、いちばん危ない群を落としていた

「1〜7個。劣化帯 10〜15 に届いていない」の根拠にした分布は、**`tools` を省略した
起動を数えていなかった**。`resolveTools` は省略時に `[]` を返す（`pool.ts:915-926`）ので、
イベントに残る `tools` は空になる。

数え直すと **起動 1,187回のうち 369回（31.1%）が省略＝ランタイム既定の全部持ち**。
imp-0018 が「確かめていないこと」に挙げていた問いの答えがこれで、**いちばん道具が多く、
いちばん危ない群を標本から外して「届いていない」と言っていた**。

**結論（1〜7個では劣化帯に届かない／職人には広げない）は、別の根拠で残る**——
`CLAUDE_KOBO_TOOL_NAMES` の実機知見（`packages/banto-worker-pool/src/claude-agent/naming.ts:26-32`
「絞り込みで消してはいけない。…タスクが1本も完走しなくなる（実機でそうなった）」）。
そちらは標本の問題を受けない。ADR-0019 決定87 はこの根拠に差し替える。

## 採らなかった案（記録として残す）

### 遅延開示の自作（`tool.search` / `tool.call`）

**一度実装し、2巡のレビューで欠陥12件が出て捨てた。**

探し方の質（本物の道具100個・レビュー側が選んだ38件の問い合わせ）: **1位 18/38（47%）・
上位5に 28/38（74%）**。最初に「上位5に 7/8」と報告したが、8件では何も言えない
（95%信頼区間 53〜98%）。問い合わせも自分で選んでいた。

主な失敗原因は語彙のずれではなく、**同点の塊がアルファベット順で切られる**こと。
「環境」のような2文字では13件が全部同点になり、`canvas.show` が `env.*` より先に並んだ。

レビューの指摘: 1巡目7件（探す口だけが**退避を通らない**／探す口を**一覧の末尾**に置いていた／
`po` が `repo` に当たる／試験が不変条件を守っていない）、2巡目5件（**1巡目の直しが新しい穴を
開けた**——退避を通した結果、探し結果そのものが栞に化けて往復が2回増えた／`DESCRIPTION_CAP` は
一度も効かない死んだコード）。

**この判断は撤回する。** 捨てた理由の中心は「約400行・実機未検証」だったが、
**pi が公式に同じ機構を持っている**（`setActiveToolsByName` ＋ `docs/extensions.md`
"Dynamic Tool Loading"、`search_tools` の完全な実装例つき）。自作する必要が無かった。
——**「pi にその口は無い」という断定が誤りだったのは、これで2回目**である。

### 使用頻度による自動昇格

罠3つ（初期状態が均衡を決める／再現性が壊れる＝D11 の隠れ状態/プレフィックスキャッシュ）。
**この却下は維持する**（ADR-0019 決定83 が「版として固定する」を引き継ぐ）。

なお本文は罠1で「**最初にどちらへ置いたかがそのまま固定され、頻度が『実際の必要』を
測らなくなる**」と正確に書きながら、決定C の仕分けは頻度から出発していた。同じ文書の中で
自分の方法論を却下したまま採用していた。

### code mode（道具をやめてコードにする）

**却下は維持する。理由を1つ足す。**

banto の個別ツールは関所として働いている——place の砦（決定36g）、書き込み許可（決定38）、
ターン予算、成果物の退避（決定47a）、器への描画（決定81a）。コードにすると掛け金が外れる。

足す理由: 独立評価（arXiv:2608.06370）が、**ファイルシステムを漁って道具を発見する方式は
文脈汚染下で 32% 劣化**すると測っている。また Anthropic の公称「98.7%削減」は1シナリオの
見積りで、**複雑な調査タスクの平均実測は 37%**、連鎖タスクでは**入力トークンが1.5倍**。

職人の側は向いている（既にサンドボックスの中で動く）。将来の選択肢として残す。

### 1モジュール1道具（`action` 引数で分岐）

**却下は維持する。理由を1つ足す。** DeepSeek 系は入れ子スキーマで崩れるのに、
`action` ディスパッチは `anyOf` / `oneOf` を誘発する——**平坦なスキーマを保てない形は逆効果**。
