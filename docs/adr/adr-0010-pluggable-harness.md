# ADR-0010: 番頭ハーネスの差し替え可能性、Kobo/WorkerAgent・UIのTool/SKILL I/F、記憶システムの採用方針

> status: **accepted**（2026-07-27。PO 裁定）。ADR-0009 決定②・③の詳細を切り出したもの。

## 文脈

ADR-0009 で「番頭のハーネスは自作しない」と決めた。自作を前提にした旧ブランチ（`explore/agent-primary`）では、Banto ホストが Quirefold（自作記憶）とターンループを一体で持つ設計を取っていたため、既製ハーネス（pi 等）を主体として使う道が塞がれていた（当時の理由：ループ・履歴管理の二重化）。この前提を外した以上、**番頭とKobo・職人・UIの結合点を明文化しないと、ハーネスを差し替えるたびに結合コードを書き直す**ことになる。また、既存の記憶システムを採用する場合も、番頭がそれをどう呼ぶかが未定義だと同じ問題が起きる。

## 決定

### 1. Kobo／WorkerAgent との結合は Tool／SKILL の公開 I/F のみ

- 番頭（どのハーネスであっても）が Kobo・WorkerAgent（職人）とやりとりする経路は、**Tool（単発呼び出しの契約）または SKILL（SKILL.md 形式の手順資産）に限る**。ハーネス固有の内部API・直接プロセス制御からは呼ばない。
- Kobo 側の実装（イベントログ・ステートマシン・ゲート等）はこの I/F の背後にあり、**Kobo と番頭核は完全分離**（ADR-0009 決定①）。番頭は Kobo の状態を Tool 経由の公開クエリ（`spec-daemon-core` §6 の `ready` クエリ等）でしか読めない。
- ツール定義はランタイム中立の共通ライブラリ（banto-core）に置き、各ハーネスのアダプタは薄い皮（ツール登録とフック接続のみ）に留める（D5）。判断ロジックをアダプタに置かない。

### 2. UI: Kobo は独立したGUI/APIを持ち、Banto はチャット＋キャンバスでそれを操作・提示する

- **Kobo は独立したシステムとして自前の GUI・API を持つ。** 人が直接 Kobo を操作することもできるが、基本の操作者は番頭——番頭は Kobo API を叩くクライアントの一つであり、人の GUI 操作と同じ API を使う（真実は常に Kobo に一つ。D3）。
- **Banto の UI はチャット＋キャンバスの2エリア構成とする。** チャットは番頭との対話、キャンバスはその時の相談内容に応じて番頭が出し入れするコンテンツ（アテンションキューの一覧、レビュー対象の DIFF、デモ用のシェル、デモ用のブラウザ、Kobo のボード等）の領域。**PO が Kobo の GUI 画面を直接操作している最中でも、いつでも番頭を呼び出して相談できる**——GUI 操作と番頭への相談は排他ではない。
- キャンバスに出す内容は、可能な限り**Kobo の既存 GUI コンポーネントを埋め込む**（再実装しない。D6）。DIFF・シェル・ブラウザ（CDP転送）等、Kobo GUI の外にある要素は別途 Tool として提示する。
- この提示・切替操作は Kobo/WorkerAgent と同様、**Tool として明確な I/F を持つ**——UI側の実装がどうであれ、番頭からは同じ契約で呼べる。I/F は AI 実装（どのハーネス・どのモデル）に依存しない（D5 Surface原則の継続）。
- **番頭の分身（ADR-0009）とキャンバスの関係**：分身は会話スレッドごとに分かれるため、キャンバスもスレッド1本につき1つ持つ。新しい分身がカードで現れるのは新しいスレッド＋新しいキャンバスであり、既存の会話のキャンバスを上書きしない（「目の前の話は壊れない」の継続）。

### 3. 第一のハーネス実装は pi coding agent。記憶システムは自作しない

- **Banto ホストの第一実装は pi coding agent**（badlogic/pi-mono）とする。pi はすでに Kobo が spawn する職人ランタイムのドライバとして使っており、番頭のハーネスとしても同じランタイムを転用する。
- **記憶機構（Quirefold のようなコンテキスト基盤）は自作しない。既存の実績あるシステムを採用する**。参照実装として **Hermes Agent**（Nous, MIT）のアプローチ——SKILL.md形式の手続き記憶を含む——を挙げる。具体的にどのライブラリ・実装を採用するかは実装フェーズの調査タスクとする（本ADRでは「自作しない」がスコープ）。
- ハーネス・記憶システムのいずれも、将来別のものに置き換え可能であることを設計の前提とする（ADR-0009 決定②）。特定ハーネスの資産に番頭の思想を固定しない。

### 4. 番頭が設計文書を書くときの規約（Kobo への引き継ぎと決定主体の明示）

- PO はアーキテクトを兼ねられるため、設計判断を直接 Kobo に指示することもできるし、番頭に委ねることもできる。番頭が委ねられた場合、番頭は ADR／spec の起票・改訂を自律的に行いうる（D9 の範囲内）。
- **決定主体を明示する。** D9 は「番頭が決めたことは PO が事後に可視・訂正できる」ことを要求するが、現行の ADR／spec フォーマットには「誰が決めたか」を示すフィールドがない。番頭が自律的に書いた設計文書と、PO と相談して決めた設計文書を区別できる規約が要る。
- **Kobo への引き継ぎを明文化する。** `docs/` は Kobo が監視しない散文ゾーン（`spec-document-system`）のため、番頭が ADR／spec を書くだけでは Kobo は何も拾わない。設計文書には対応する `work/epics`・`work/tasks` の起票（`refs` で紐付け）が必ず伴うことを運用ルールとして明文化する。

### 5. Banto GUI プラグインフレームワーク（§2 キャンバスの一般化）

- キャンバスに出せる GUI は、**Banto がカタログとして管理する**。各エントリは「識別子・パラメータスキーマ・説明」を持つ——形状は Tool の契約（名前・パラメータの JSON Schema・説明）を流用し、`kind: canvas-view` 等で通常のアクション Tool と区別する。番頭はカタログから「何が呼べて、どんなパラメータが要るか」を把握し、Tool 経由でキャンバスに出す。
- **基本 GUI セット（banto-core が提供）**：ファイル／ディレクトリ表示、DIFF 表示、ブラウザビュー（CDP 転送）、シェル、セッションビューア（決定18で追加）。特定の店・サブシステムに紐付かない汎用部品として定義する。
- **プラガブル GUI（各サブシステムの Extension Pack が登録）**：Kobo のボード・アテンションキュー一覧・バックログ編集のような、特定の店に固有の GUI は、その Extension Pack がカタログへ登録する（D5：ロジックは Kobo・番頭核・Extension Pack にだけ書く、の延長で GUI 定義もここに置く）。
- これにより、**新しい店（開発以外の将来領域）を追加しても Banto 中核は変えず、その店の Extension Pack が GUI とツールを持ち込むだけで済む**（vision.md「開発は最初の領域にすぎない」の実装機構）。
- **複数 GUI を同時に出す場合の提示方式は、タブ切り替えに一本化する（2026-07-28、PO裁定）。** マルチウィンドウ（ドラッグで自由配置）は不採用。理由はモバイル対応（§8）——ウィンドウのドラッグ配置はタッチデバイスと相性が悪く、画面が狭い端末では並べて見比べる利点も薄い。banto-shell プロトタイプではウィンドウモードを実験実装したが、この裁定を受けて削除しタブのみに統一した。
- **番頭からのキャンバス操作は、要素が閉じるまでブロックしない単発の操作とする。** open／close に限らず、開いている要素への操作（表示中のファイルを切り替える、表示位置を変える等）もTool呼び出しとして許容するが、いずれも呼んですぐ返る単発アクションであり、要素が閉じるまで呼び出しが継続する形（モーダルな長時間呼び出し）にはしない。シェル内でコマンドを実行するといった、要素の中身そのものを動かす操作は、既存の別のツール（`spec-environment` §2 の `run` 等）を通す——キャンバスToolの責務は提示・表示状態の変更に閉じる。

### 6. Kobo は独立プロセスのまま。デプロイ・運用は一体的な体験にする（2026-07-28、PO裁定）

- **Kobo を番頭への in-process プラグインとして組み込むことはしない。現行どおり独立プロセス（HTTP API＋WebSocket 常駐）を維持する。**
- 理由: (a) Worker Pool（職人）は既に別プロセスで、Kobo へは元々ネットワーク越しにアクセスする必要がある。番頭だけを in-process 化しても、職人・GUI/CLI 向けの HTTP/WS 面は結局残り、「番頭だけ特別な内部経路を持つ」という一貫性のない構成になる。(b) 決定1（本ADR §1）が既に「番頭は Kobo の状態を Tool 経由の公開クエリでしか読めない」と規定しており、in-process 化はこれと整合しない。(c) Kobo が独立 GUI・API を持つからこそ、PO 直操作と番頭経由操作が同じ API を共有できる（§2）。(d) systemd 常駐によるライフサイクル独立性（番頭・ハーネスの再起動やクラッシュから統治状態が守られる）は、ハーネス差し替え可能性（§3）と相性が良い。
- **ただし、独立プロセスであることが運用の手間として利用者（PO）に露出してはならない。** デプロイ・起動・停止・更新・死活監視は一体的に扱えることを要件とする——たとえば単一のインストール/起動手順、Kobo の起動状態を Banto 側から可視化する（本プロトタイプの Settings › Kobo接続で先取り）、バージョン整合性の自動チェック等。具体的な実現方法（単一 systemd ユニットで両方管理するか、Banto 起動時に Kobo の存在確認〜起動まで面倒を見るか等）は実装フェーズで検討する（→ 未決事項）。
- 「プラグインらしい統合感」自体は、キャンバスの GUI プラグインカタログ（§5）で既に実現できる——Kobo の GUI 要素をカタログエントリとして番頭が呼び出す体験上の統合は、Kobo のコアエンジンを in-process 化しなくても得られる。

### 7. セッション開始リクエスト（お店 → Banto の汎用の受け口、提案・未決）

- **PO 提起（2026-07-28）**: 店（Kobo 等の Extension Pack）側で「PO と話したい」という状況（レビュー待ちが溜まった等）が発生したとき、店が Banto へ「セッション開始リクエスト」を積める仕組みが要るのではないか。POがリクエスト一覧から選ぶと、そのリクエストの文脈を注入した新しいセッションが始まる。
- **Kobo 自身のアテンションキュー（Kobo 独自 GUI・§2 でキャンバスに埋め込む対象）とは別物**と位置づける。アテンションキューは Kobo 内の判断待ち一覧（Kobo のステートマシンをそのまま描画するビューア）であるのに対し、セッション開始リクエストは「新しいセッションを始めてほしい」という、店をまたいで通用する Banto レベルの汎用の受け口とする（vision.md「開発は最初の店にすぎない」を踏まえ、将来の店にも同じ仕組みが使えることを狙う）。
- banto-shell プロトタイプに実験実装あり（📥 アイコンのピンタブ。履歴・設定と同じ「タブの汎用化」の枠に乗せた）。リクエストは文脈タグ（タスク定義・経緯・影響 等）を持ち、選ぶと新セッションの先頭にその文脈が注入された状態で始まる——`spec-ui` §2「カードの相談する」でカードの文脈をセッションへ注入する挙動と同じ発想を、システム起点（店発）に拡張したもの。
- **リクエストはキャンバスに開く GUI も指定できる（2026-07-28、PO 追加提起）。** リクエストのペイロードは文脈タグに加え、§5 の GUI プラグインカタログのエントリ（`queue`・`diff`・`shell` 等の kind）を「開いた状態でセッションを始めてほしい」として埋め込める。複数指定した場合は開いた状態のタブとして並び、最初の1つがアクティブになる（§5：提示方式はタブに一本化）。これにより PO は新セッションに入った瞬間、判断に要る画面が既に揃っている。
- **未決**: 店がリクエストを積む Tool/API の形（1件ずつ push か、Kobo 側のクエリを Banto がポーリングするか）、重複排除・既読管理、複数店が積んだ場合の優先順位付け、Kobo のアテンションキューとの役割分担の最終形（アテンションキューの各カードに「セッション開始リクエストとしても積む」ボタンを持たせるのか、自動で連動するのか）、埋め込む GUI 指定のバリデーション（カタログに存在しない kind を指定された場合の扱い）。

### 8. Banto UI はモバイル対応を最初から前提とする（2026-07-28、PO裁定）

- **Banto の UI（チャット＋キャンバス・履歴・設定・セッション開始リクエスト等すべて）は、後回しにせず最初からモバイル対応を前提に設計する。** キャンバスに出す GUI（基本 GUI セット・各店が登録するプラガブル GUI 双方）もモバイル対応を必須とする——狭い画面で崩れる GUI はカタログに登録できない、という制約として運用する。
- §5 の「複数 GUI 同時表示はタブに一本化」は、この方針が直接の理由。
- banto-shell プロトタイプでの対応例（実装フェーズでの参考になるよう記録）: セッション面（キャンバス＋チャット）は狭い画面で2ペイン同時表示をやめ、チャット⇄キャンバスをボタンで切り替える1ペイン構成に切替（キャンバスが新しく開いたら自動でキャンバス側を前面に出す）。履歴・設定のような2カラム面は、一覧→詳細のドリルダウン（設定は横スクロールのカテゴリタブ）に切替。セッションタブが増えて頭の帯を圧迫する問題は、タブの個々の表示幅を切り詰めつつ、全セッションを一覧できる「▾」ボタン（一覧から直接スイッチ／Close）を常設することで解決した（下記参照）。
- 実装フェーズでの検証事項: 実機（iOS/Android の実ブラウザ）での確認、タッチ操作（ドラッグではなくタップ主体になった影響）、Kobo 側の GUI（アテンションキュー・ボード等）を埋め込む際のモバイル対応をどちらが担保するか（Kobo 側 GUI 自体がモバイル対応している前提を置けるか、Banto 側で追加の変換が要るか）。

### 9. Tool／SKILL の境界線・命名規則（2026-07-28、PO裁定）

- **境界線：単発＝Tool、手順＝SKILL。** 呼んですぐ結果が返る単発の状態照会・単発アクション（Kobo状態クエリ、キャンバスのopen/close/switch、職人へのタスク投入等）はすべて Tool として定義する。複数の Tool 呼び出しにまたがる手順知識（例：「アテンションキューの捌き方」「Sprintの振り返りの進め方」）は SKILL.md（agentskills.io形式）として番頭の手続き記憶に置く。§1・§5 で既に定めた「単発Tool原則」「キャンバスToolは表示状態の変更に閉じる」とそのまま整合する。
- **命名規則：名前空間プレフィックス方式。** `kobo.query.ready` / `kobo.action.spawn_worker` / `canvas.open` / `canvas.switch` のように、契約の形状（名前・JSON Schemaパラメータ・説明）は Kobo・UI で共通のまま、名前空間プレフィックスで発生元ドメインを区別する。Kobo用・UI用で契約体系そのものを分けない。将来 Extension Pack が増えても同じ規則を使い回せる。

### 10. 記憶システムの採用方針：Hermes Agent 本体は組み込まず、設計のみ踏襲して自前実装（2026-07-28、PO裁定）

- **Hermes Agent（NousResearch/hermes-agent, MIT）本体は組み込まない。** 調査の結果、Hermes Agent は記憶コンポーネント単体ではなく、独自のターンループ・6種のターミナルバックエンド（ローカル/Docker/SSH/Singularity/Modal/Daytona）・20以上のメッセージングプラットフォーム統合を持つ、それ自体で完結したフルエージェントだと判明した。本体を組み込むことは「第一実装は pi coding agent」（本ADR §3）と競合する——Hermes を丸ごと採用するなら、それは pi ではなく Hermes をハーネスにする別の決定になってしまう。
- **代わりに、Hermes の記憶設計（三層メモリアーキテクチャ）を参考に、banto-core 内に薄く自前実装する。** 参考にする設計要素：(a) 好み・習慣の蓄積、(b) タスク完了ごとの SKILL.md 自動蒸留（procedural memory。手続き記憶は SKILL.md 形式、の既定方針と合流する）、(c) FTS5 全文検索＋LLM要約によるセッション横断検索。実装は SQLite 等の標準的な構成要素を使い、依存追加は最小限に留める（D6）。
- 「自作しない」（ADR-0009・本ADR §3のスコープ）という原則との関係：禁止しているのは記憶の**アーキテクチャ設計**をゼロから発明すること（旧ブランチのQuirefoldで頓挫した領域）であり、実績のある設計を踏襲した薄い実装は「自作しない」の範囲内と整理する。

### 11. pi coding agent 上での番頭ターンループ構成：SDKモードで自前ホストに埋め込む（2026-07-28、PO裁定）

> **改訂（2026-08-12・ADR-0020 決定88〜93）**：番頭ハーネスは `BantoHarness` 契約の
> 実装であり、**pi の SDK モードはその第一実装**。第二実装として Agent SDK がある。
> プロセス境界（`RuntimeDriver`）は差し替えの機構ではなく**関所**として別の層に置く。

- **pi Agent SDK を使い、自前の Node.js ホストプロセス内に pi のエージェントループを直接埋め込む。** pi が提供する3方式（Extension API／RPCモード／SDKモード）のうち、番頭の本質的な仕事である記憶注入・ターン制御（D11）には、セッションのメッセージ履歴への直接アクセスとターン境界イベントの購読が要る。
  - **Extension API は不採用**：Tool登録・イベント購読はできるが、コア状態（`session.agent.state.messages` 等）の直接操作やセッションループ自体の差し替えができない、pi のライフサイクル内に閉じた制約付きプラグインインターフェースのため。
  - **RPCモードは不採用**：プロセス分離・言語非依存という利点はあるが、TypeScript同士の直結という前提（banto-core は既にTypeScript strict）では型安全性と直接状態アクセスを失う代償の方が大きい。
  - **SDKモードを採用**：`createAgentSession()` 等でセッションを組み立て、メッセージ履歴の直接操作・ターン境界イベント購読（`steer()`/`followUp()`等）を使って、番頭側の記憶注入・Tool/SKILL登録・ターン制御を自前ホスト側に持つ。
- 参照：pi のドキュメント（`packages/coding-agent/docs/sdk.md`・`rpc.md`・`extensions.md`、[earendil-works/pi](https://github.com/earendil-works/pi)）。**移転前は badlogic/pi-mono**——決定当時のリンクはそちらを指していた（npm も `@mariozechner/*` から `@earendil-works/*` へ改称）。

### 12. Kobo GUI コンポーネントの埋め込み方式：iframe不採用、Reactコンポーネント直接importで統一（2026-07-29、PO裁定）

- **iframe/webview埋め込みは不採用。** 調査の結果、Kobo には現状 Web GUI が一切存在しない（`packages/banto-daemon` は REST API＋WebSocketイベント配信のみで、HTML配信コードはゼロ。アテンションキュー等は `spec-ui` の設計記述のみで実装なし）。つまり「Koboの既存GUIをどう埋め込むか」ではなく、Koboの独立GUI（§2）自体をこれから新規に作る必要があるという前提に立ち、その実現方式を決めた。
- **Kobo（各Extension Pack）は GUI 要素を React コンポーネントのパッケージとして公開する。** monorepo 内の共有パッケージとして実装し、Banto のキャンバスはカタログエントリ（§5）に紐づくコンポーネントを直接 import して自分の DOM ツリー内にレンダリングする。iframe・postMessage は使わない——テーマ（ダーク/ライト）・モバイルレスポンシブ（§8）が共通の CSS カスケードでそのまま効く。
- **Kobo の独立GUI要件（§2：PO が直接 Kobo を操作できる）は、Kobo 自身が同じコンポーネントパッケージを import した薄い自前シェルを持つことで満たす。** Kobo は自分の HTTP サーバーからこの自前シェルを配信する。バックエンドプロセスとしての独立性（§6 で決定済み：HTTP+WS 常駐）には影響しない——独立しているのは Kobo の API プロセスであり、GUI の見た目のコード自体はパッケージとして Kobo・Banto 両方の描画元から共有される。
- **副次的な決定：Banto 側のフロントエンドは React に統一する。** これまで未定だった Banto 自身のフロントエンド実装技術が、この埋め込み方式の帰結として React に定まる。将来 GUI を持ち込む Extension Pack も同じコンポーネント規約（React）に従う制約が伴う。

### 13. GUI操作中に番頭を呼び出す入口と文脈の渡し方（2026-07-29、PO裁定）

- **「呼び出す入口」は別チャネルを新設しない。** 決定12（React コンポーネント直接 import）の帰結として iframe の境界が存在しないため、チャットはデスクトップでは常時キャンバスと並んで表示され、モバイルでは既存の 💬 トグルボタン（banto-shell プロトタイプに実装済み）で常にアクセスできる。追加の召喚チャネルは不要。
- **文脈の渡し方は、暗黙の問い合わせ（Tool）と個別エンティティの明示アクション「相談する」を両立させる。**
  - 番頭は常に「今キャンバスに何が開いているか／表示状態」を照会できる Tool（`canvas.query_state` 相当。決定9の名前空間規則に従う）を持ち、PO の発言が「この画面」「これ」等キャンバスの現在状態を指すと判断したときに自分で参照する。PO 側の明示操作は不要。
  - 加えて、タスクカード等の個別エンティティは `spec-ui` §2「カードの相談する」と同じ発想の明示アクション「相談する」を持ち、クリックすると構造化された文脈（エンティティ種別・ID・関連情報）がチャットに注入される。精密な文脈が欲しいとき用の高精度パス。
  - この二段構えは、決定7（セッション開始リクエストの文脈タグ埋め込み）とも発想が一貫する。

### 14. 決定主体を区別する規約：ADRはインライン注記、specはfrontmatterフィールド（2026-07-29、PO裁定）

- **ADR：番号付き決定項目の見出しに「（日付、決定主体）」を付ける方式を正式ルール化する。** 本ADRの決定1〜13（2026-07-27・07-28・07-29に追加されたもの）で既に実施している書式——例：「### 12. Kobo GUI コンポーネントの埋め込み方式：...（2026-07-29、PO裁定）」——をそのまま規約とする。決定主体の値は「PO裁定」「番頭裁定」「PO×番頭協議」の3種。1つのADRが複数の決定を日をまたいで積み重ねる（本ADR自体がその例）ため、文書単位ではなく決定単位で主体を明示する。
- **spec：文書のfrontmatterに `decided_by:` フィールドを追加する。** spec は基本的に一つの設計判断のまとまりを一括で記述するため、ADRのような決定単位の粒度は不要。値は同じ3種（`po` / `banto` / `mixed`）。既存specへの遡及適用は改訂時に順次行う（強制の一括移行はしない）。

### 15. Kobo `work/` への引き継ぎ運用ルール：SKILL.md化＋P3棚卸し監査（2026-07-29、PO裁定）

- 不採用とした選択肢：Kobo 自身に `docs/` を監視させて技術的に強制する案は、`document-system.md` §1「docs/とwork/の分離が第一の骨格」という既存の設計原則を変更することになり、Koboがドキュメントの意味論を解釈するロジックを持つ必要も生まれるため、今回は採らない。

### 17. GUIカタログのエントリ形式：Tool契約を土台にキャンバス固有フィールドを拡張（2026-07-29、番頭裁定）

- **純粋な「Toolの契約そのまま流用」でも「専用スキーマの新設」でもなく、Tool契約（名前・JSON Schemaパラメータ・説明）を土台に、キャンバス固有のフィールドを拡張する。** 決定12（React コンポーネント直接 import）により、カタログエントリは「どの React コンポーネントを描画するか」への参照を持つ必要があり、これは通常の Tool 契約（呼び出し→結果が返るだけの単発アクション）のフィールドには存在しない。
- 拡張フィールドの例：`component`（描画する React コンポーネントの参照。パッケージ名＋エクスポート名）、`kind: canvas-view`（決定9で既出）、必要に応じて `icon`・`category`（カタログ表示用）。具体的なフィールド名・型定義は実装フェーズで確定する（本ADRのスコープは形状の方針まで）。
- PO判断を要する新しいトレードオフが無く、決定9・決定12から機械的に導かれるため、番頭が自ら決定した（決定14の運用規約に従いここに明記）。

### 18. 基本GUIセットの範囲：「セッションビューア」を別種として追加（2026-07-29、PO裁定）

- **基本GUIセット（§5）を5種に確定：ファイル／ディレクトリ表示、DIFF表示、ブラウザビュー（CDP転送）、シェル、セッションビューア。**
- **セッションビューア**を新規追加する。稼働中の職人（pi worker）セッションにライブアタッチして出力を見るもので、決定16で持ち越した「ドリルダウン」（カード→該当worktreeのpiセッションへワンアクション）の実体はこれになる。
- **シェル（コマンド実行用、`spec-environment` の `run` 相当）とは別コンポーネントとして分ける。** 目的が異なる（新規にコマンドを実行する vs 既存の稼働中セッションを覗く）ため、1つのコンポーネントにパラメータで分岐させるより、カタログ上も別種として提示する方が「番頭がカタログから何を呼べるか把握する」（§5）際に迷いが少ない。
- 具体的なフィールド定義（読み取り専用か双方向か等）は実装フェーズで確定する。ここでは「別種として存在する」ことのみを決定する。
- **将来ニーズを見越した追加は行わない。** ログビューア・Markdownビューア等、他に考えられる汎用GUIは、具体的な必要性が判明した時点で個別に追加を検討する（P1: スコープ外の先回りをしない、の精神）。

### 19. Kobo/Bantoの一体的デプロイ方式：別systemdユニット＋依存順序＋単一インストーラ（2026-07-29、PO裁定）

- **Kobo用・Banto用の2つの独立した systemd ユニットを維持する。** クラッシュ・再起動ポリシーはユニットごとに独立させ、§6 で決定した「Kobo のライフサイクル独立性（番頭・ハーネスの再起動やクラッシュから統治状態が守られる）」を壊さない。単一ユニットで束ねる案・Banto プロセス自身が Kobo を子プロセスとして監視する案は、いずれも Kobo のライフサイクルを Banto 側に従属させてしまうため不採用。
- **Banto側のユニット定義に `Wants=`/`After=` で Kobo ユニットへの起動順序依存を設定する。** Banto を起動すると Kobo が（未起動なら）先に起動してから Banto が立ち上がる。
- **単一のインストーラ（セットアップスクリプト）が両ユニットを一括で有効化・起動する。** 利用者（PO）から見た「単一のインストール/起動手順」（§6の要件）はここで満たす——ユニット自体は分かれているが、体験としては1コマンドで揃う。
- Banto 側の Settings › Kobo接続（banto-shell プロトタイプで先取り済み）で Kobo の起動状態を可視化する方針は維持。バージョン整合性チェックの具体的な実現方法は実装フェーズで詰める（本決定のスコープ外）。

### 20. セッション開始リクエストの仕組み（2026-07-29、PO裁定）

- **Tool/APIの形：Push型。** Kobo の Extension Pack がイベントとして発行し、既存の WebSocket イベント配信（`ws-server.ts`）で Banto がリアルタイム購読する。新規のポーリング機構は作らず既存インフラを再利用する（D6）。
- **重複排除・既読管理：Kobo 側のイベントログに一本化する。** Banto は別ストアを持たない（D3：状態の真実は一箇所）。重複生成の防止は発行元 Extension Pack の責務、「開始済み」は "consumed" イベントとして Kobo のログに記録する。
- **複数店の優先順位付け：今は作らない。** 現状は開発（Kobo）が唯一の店のため単純な時系列順で十分。優先順位ロジックは店が増えて具体的な必要性が出てから設計する（P1：先回りしない）。
- **Kobo アテンションキューとの役割分担：トリガーは Kobo の既存の状態遷移ロジックのみとする（手動昇格は今回は作らない）。**
  - 当初「アテンションキューのカードに『PO召集をリクエストする』ボタンを持たせる」という案を検討したが、これは§7の提起の趣旨（**店**が Banto へリクエストを積む、という店起点のプッシュ）と噛み合わない——ボタンだと「誰が押すのか」（PO が押すなら、その PO は既にその場にいるはずで、セッション開始リクエストの必要性自体が生じない）という矛盾が生じることが PO レビューで判明し、訂正した。
  - 正しい設計：Kobo には既に「PO判断がどれだけ緊急に必要か」を判定する状態遷移ロジックがある（`spec-daemon-core` の健康状態taxonomy＝stalled/no-progress/zombie、TTL超過検出、blocking発生等）。この既存ロジックが閾値を超えたと判定した瞬間に、Kobo 自身（Extension Pack）が人手を介さずセッション開始リクエストを自動発行する。状態遷移は冪等なため重複の心配もない。
  - アテンションキューに積まれるたびに無条件で連動するわけではなく、Kobo の既存の閾値判定を経由するため、「本当に緊急なもの」だけが上がってくる。PO/番頭による手動昇格（緊急でなくても今すぐ話したい場合）は今回は作らない——具体的な必要性が出てから検討する（P1）。
- **埋め込む GUI 指定のバリデーション：Banto 側（カタログの管理主体）が受信時に実施する。** カタログに存在しない `kind` を指定されたリクエストは、その GUI 指定を無視し、文脈タグのみのバナー表示にフォールバックする（リクエスト自体は無効化しない）。

### 21. モバイル対応の責任分担：コンポーネント実装者が担保、実機検証はタスク化して先送り（2026-07-29、番頭裁定）

- **Kobo 側 GUI のモバイル対応は、各コンポーネントの実装者（Extension Pack／banto-core の基本GUIセット提供者）が担保する。** Banto 側で後から変換・吸収する仕組みは持たない——決定12（React コンポーネント直接 import、iframe不採用）の帰結として、コンポーネントの中身がそのまま Banto の DOM に出るため、Banto が別途「翻訳」する余地が技術的に無い。
- **banto-core が共通のレスポンシブ基盤（ブレークポイントトークン・レイアウトプリミティブ）を提供し、GUI カタログへの登録要件とする。** §8 で既に定めた「狭い画面で崩れる GUI はカタログに登録できない」という制約を、この共通基盤への準拠として技術的に担保する。
- **実機（iOS/Android）での検証は設計判断ではなく実装フェーズの検証タスクとして先送りする。** 決定15の運用（SKILL化＋work/への起票）に従い、実装着手時に work/task として積む。
- PO判断を要する新しいトレードオフが無く、決定12・§8から機械的に導かれるため、番頭が自ら決定した（決定14の運用規約に従いここに明記）。

### 22. Tool名の論理名／wire名分離：決定9のドット記法は契約層に留め、プロバイダ変換はアダプタの責務と明文化（2026-07-29、PO×番頭協議）

- **背景（実機で判明した不具合）**：task-0004（`packages/banto-host` 雛形）の動作確認で、決定9のドット区切り命名（`kobo.query.ready` 等）をそのまま Tool の wire 名として opencode-go（deepseek-v4-flash、openai-completions 互換API）に渡すと `400 Upstream request failed` で拒否されることを確認した。同じ Tool 定義で名前をアンダースコア区切り（`kobo_query_ready`）に変えると、システムプロンプト注入・LLMからのTool呼び出し・実行結果返却まで含めて正常に動作した。Anthropic API はドット入りの名前を許容するため、これまで気づいていなかった。
- **決定：決定9のドット記法（`<domain>.<verb>`）は契約・論理層の識別子として維持する。** Kobo・UI・将来のExtension Packで共通の命名規則という決定9の狙い自体は変えない。
- **wire層（実際にLLM APIへ渡す関数名）でのプロバイダ制約吸収は、Toolアダプタの責務と明文化する。** これは新しい原則ではなく、本文（CLAUDE.md Tech Stack）に既にある「Toolは内部で正規化しプロバイダ毎のwire形式をアダプタで吸収する」の具体例として、今回のドット不許容プロバイダの実例で確認できたことを記録する。アダプタは論理名（ドット区切り）とwire名（例：アンダースコア区切り）を相互変換し、`tool_call` イベントの突き合わせも論理名側で行う。
- **不採用とした選択肢**：決定9自体をアンダースコア記法に変更する案は採らない。ドットは Kobo/canvas/将来のExtension Pack という3階層以上の名前空間を視覚的に区切る目的があり（決定9原文）、wire層の一プロバイダの制約のために契約層の可読性を犠牲にする理由がない。
- **スコープ**：具体的な変換アダプタの実装は task-0004（雛形立ち上げ、実Kobo Tool実装はスコープ外）には含めない。実Kobo/canvas Toolをbanto-hostに配線する後続タスクで実装する（決定15の運用に従い、着手時にwork/taskとして起票する）。

### 23. Worker Pool は Kobo から独立したモジュールとし、Kobo より先に作る（2026-07-29、PO裁定）

- **Worker Pool（職人ランタイム）は Kobo とは独立したモジュールとする。** Kobo のサブシステムではなく、Kobo が無くても単体で成立する。実装順としても **Worker Pool を Kobo より先に作る**。
- **これは既存記述の訂正である。** `CLAUDE.md` は「pi は **Kobo が spawn する**職人（Worker Pool）ランタイム」と書いており、実装上も spawn 系（`spawn-ledger.ts`・`pi-rpc-driver.ts`・`scheduler.ts`）は `packages/banto-daemon`（＝Kobo）の中にある。本決定はこの従属関係を解き、Worker Pool を独立させる。`CLAUDE.md` の当該記述は本決定に合わせて修正する。決定22までの他の決定（特に決定1・§6）は「職人は既に別プロセス」という前提のままで矛盾しない——変わるのは「誰が起動し、誰に属するか」である。
- **帰結：番頭は Kobo 無しでも職人に実作業を委譲できる。** D10（番頭は細かい仕事をせず職人へ委譲する）が Kobo の完成を待たずに成立する。ADR-0009 の「番頭が主体、開発システムが従」という構図とも整合的で、開発（Kobo）は番頭が扱う最初の店に過ぎず、職人という実行能力はその店に固有のものではない。
- **帰結：決定18 のセッションビューアは Kobo 非依存になる。** 「稼働中の職人セッションへライブアタッチする」対象は Worker Pool が作る職人であり、Kobo を経由しない。基本GUIセット5種はすべて Kobo 無しで価値を持つ。
- 既存の Kobo 内 spawn 実装をどう扱うか（切り出すか、Kobo が独立 Worker Pool を呼ぶ形に変えるか）は実装フェーズで決める。本決定のスコープは従属関係の解消と実装順まで。
- （2026-07-30 追記）Banto から見た Worker Pool の位置づけは決定27 (c) で確定した——**必須の組み込みモジュール**であり、Banto 内部の機能にはしない。

### 24. 基本GUIセットに Git 閲覧系を追加する（2026-07-29、PO裁定）

- **決定18 の基本GUIセットに、Git の閲覧系（履歴・状態・ブランチ・blame）を追加する。** 決定18 は「将来ニーズを見越した追加は行わない。他に考えられる汎用GUIは、具体的な必要性が判明した時点で個別に追加を検討する（P1）」と定めていた。Kobo 無しでも価値のある汎用GUIを Banto が既定で持つべき、という具体的な必要性が出たため、その手続きに従って追加する。
- **閲覧専用とし、変更操作（stage / commit / branch作成 等）は持たない。** 番頭の役割は「見て判断する」ことであり、リポジトリを変更する作業は職人へ委譲する（D10）。また変更操作を Banto に持たせると、Kobo のマージキュー・マージゲートと責務が競合する。
- 既存の「DIFF表示」（決定18）はこの Git 系の一部として整理する。基本GUIセットは「ファイル／ディレクトリ表示・Git閲覧（DIFF/履歴/状態/ブランチ/blame）・ブラウザビュー（CDP転送）・シェル・セッションビューア」となる。
- **これらは Kobo の Extension Pack が登録するプラガブルGUI（アテンションキュー・エージェントボード・バックログ編集）とは別枠で、Banto が既定で持つ。** カタログ上の扱い（エントリ形式）は決定17 のまま。
- （2026-07-30 追記）「別枠で持つ」の意味は決定25 で修正した。**機構としては別枠ではなく、他の店と同じ登録の仕組みに乗る組み込みの店**である。

### 25. 店（Provider）の登録単位：接続情報・Tool・GUI を1つにまとめ、基本GUIセットも同じ仕組みの組み込み店とする（2026-07-30、PO裁定）

> （2026-07-30 追記）本決定の「店（Provider）」は決定27 (a) により**「モジュール」**へ読み替える。以下の本文は追記のみの規律（`spec-schemas` §3）に従い当時のまま残す。

- **店（Provider）は次の3点を1つの登録単位として Banto に登録する。**
  1. **接続情報** — Banto および UI がその店に到達する先
  2. **番頭へ提供する Tool** — 番頭がその店を操作・照会するための契約（決定1・決定9）
  3. **キャンバスへ提供する GUI コンポーネント** — カタログエントリ（決定17）
- **基本GUIセット（ファイル／ディレクトリ表示・Git閲覧・ブラウザビュー・シェル・セッションビューア）も、この同じ仕組みで登録される組み込みの店とする。** プログラミング言語の標準ライブラリと同じ位置づけ——Banto に最初から同梱されるが、機構としては Kobo や将来の店と対等で、特別扱いの経路を持たない。決定24 の「Banto が既定で持つ」は、専用の裏道を持つという意味ではない。
- **人が GUI でできることは番頭にもできる。ただし到達経路が異なる。**
  - 人：GUI コンポーネント → **店のデータ API**
  - 番頭：**店が提供する Tool** → 店
  - 同じ能力に入口が2つあり、真実は店側に1つ（D3）。**Banto は UI のデータを中継しない**——UI が番頭の Tool を呼ぶ構図は採らない。
  - これは決定2 が Kobo について定めた構図（「番頭は Kobo API を叩くクライアントの一つであり、人の GUI 操作と同じ API を使う」）を、すべての店に一般化したものである。合流点は店側の API であって、Banto の Tool 層ではない。
- **UI コンポーネントの通信先は、店の登録情報にある接続情報から解決する。** コンポーネント側にエンドポイントを直書きしない。基本GUIセットの場合、その接続先は Banto ホスト自身になる（Banto が組み込み店の提供者を兼ねるため）。
- **帰結：Banto 中核が持つのは「店を登録する機構」と「キャンバスに描く機構」だけで、データの意味論を持たない（D5）。** 店が増えても Banto 中核は無変更で済む——決定5 で GUI をカタログ化した狙いを、Tool と接続情報まで含めて一般化した形。
- （2026-07-30 追記）登録単位には決定26 により **SKILL** が4つ目の要素として加わる。

### 26. SKILL の出所と改善の関係：店が既定を出し、番頭の学習が上書きする3層構成（2026-07-30、PO裁定）

> （2026-07-30 追記）本決定の「店」は決定27 (a) により**「モジュール」**へ読み替える。

- **論点**：店（Provider）はその店の捌き方を知っているのだから SKILL は店が提供すべきだが、番頭は実務の中で SKILL を改善したい。この2つは排他ではない。
- **`spec-multi-project` §1 の既存規則をそのまま適用する。** 同§は「Extension Pack、監査チェックリスト等の層A資産…はプロダクト側の既定とし、プロジェクトはオーバーライドのみを持つ。改善はまず既定側への提案として扱い、プロジェクト固有事情のみ差分に置く」と定めている。SKILL は `spec-improvement-loop` §1 の層A資産であり、この規則の対象。**新しい原則を作らず既存規則の適用として扱う。**
- **3層構成とする：**
  1. **番頭核の SKILL** — 番頭であることの手順（`work-handoff` 等）。Banto に同梱される
  2. **店の SKILL** — その店の捌き方（「アテンションキューの捌き方」等）。**決定25 の店の登録単位に4つ目の要素として含める**（接続情報・Tool・GUI・SKILL）
  3. **番頭の学習層** — 実務からの改善・追記。決定10 (b)（タスク完了ごとの SKILL.md 自動蒸留）の置き場
- **優先順位は学習層 > 既定。** 同名なら番頭の学習が勝つ。これにより**店を更新しても番頭の学びが消えず、番頭の学びが店の既定を汚さない**。どこを番頭が上書きしたかも差分として見える。
- **既定そのものを直すべき改善は、店へのフィードバック（改善提案）として上げる。** `spec-improvement-loop` 層Aの流れ（エージェントが直接編集提案、コミット＝POレビュー対象）に乗る。その店を使う全プロジェクトへ波及させたい改善は既定側へ、当該環境固有の事情のみ学習層に留める。
- **オーバーライドの陳腐化を検出する。** 学習層のオーバーライドには「どの版の既定を元にしたか」を記録し、既定が変わったら黙って古いまま使わず incident を積む（P3）。層Aは「壊れると静かに劣化する」性質（`spec-improvement-loop` §1）のため、この検出が無いと店の改良が永久に届かない状態が静かに続く。
- **実装上の注意**：agentskills.io の SKILL 名はディレクトリ名一致でドットが使えないため、店の SKILL は `kobo-attention-queue` のようなハイフン前置きで名前空間を作る。Tool 名のドット記法（決定9）とは別の規約になるが、決定22 と同じ「論理名と実体の形式は別レイヤー」の話として扱う。
- （2026-07-30 追記）決定25・26 の「店（Provider）」は決定27 により**「モジュール」**へ読み替える。`Provider` は「LLMプロバイダ」と衝突するため使わない。

### 27. 語彙を「モジュール」に統一し、モジュール間呼び出しはライブラリ＋レジストリ方式とする（2026-07-30、PO裁定）

#### (a) 語彙：「店」→「モジュール」

- **決定25 の登録単位を、技術用語として「モジュール（Module）」と呼ぶ。** 決定25・26 に現れる「店（Provider）」はこの語で読み替える。
- **`Provider` は使わない。** 既に「LLMプロバイダ層はプラガブル」（`CLAUDE.md`）で埋まっており、語彙が割れる。同様に `アダプタ`（ハーネス・LLM）、`ドライバ`（環境・ランタイム）、`Extension Pack`（Kobo 側の機構。`spec-improvement-loop` §1 で層Cに並記）、`Surface`（GUI/CLI 固有コード）も別の意味で使用中のため充てない。
- **「店」は `docs/vision.md` の商家の比喩として残す。** 番頭・職人と一体の世界観であり、そこを技術用語に置き換える利得がない。**散文で世界観を語るときは「店」、機構を指すときは「モジュール」**と意識的に使い分ける。
- **コード内では接頭辞を付ける**：`BantoModule` / `ModuleManifest` / `ModuleRegistry`。TypeScript では `module` が言語レベル（ES モジュール）で埋まっているため、無修飾では使わない。
- **「モジュール」と「ドメイン」の関係**：モジュールは登録単位、ドメインは決定9 の Tool 名前空間プレフィックス。**各モジュールは1つ以上の名前空間ドメインを持つが、逆は成り立たない**——`canvas.*` / `memory.*` / `skill.*` は Banto 中核自身の名前空間であり、モジュールではない。
- 決定5・7・8・20・23 等これ以前の決定に現れる「店」も、機構を指す文脈では本決定の「モジュール」と読む。**ADR 本文は追記のみで書き換えない**（`spec-schemas` §3）ため、遡っての置換はしない。

#### (b) モジュール間呼び出し：ライブラリ＋レジストリ方式

- **モジュール間の機能呼び出しの仕組みは Banto フレームワークが提供する。** 各モジュールペアが接続・発見・認証を自作すると、モジュール数の増加に対して O(N²) の結合作業が発生し、決定25 で「登録の口を1つにした」狙いと逆行する。
- **ただしブローカー方式は採らない。** フレームワークが提供するのは①**レジストリ**（誰がどこにいるか）と②**共通の呼び出し規約とクライアント実装**であり、**実際の呼び出しはモジュール同士が直接行う**。Banto プロセスは経路に入らない。
  - **不採用理由（ブローカー方式＝呼び出しが Banto プロセスを通る案）**：Banto が単一障害点になり、Kobo が Banto の稼働に依存する。これは ADR-0009・決定1 の「Kobo は独立、Banto は Kobo のクライアント」という依存の向きを逆に壊し、決定6 で守った Kobo のライフサイクル独立性にも反する。
- **呼び出しの単位は既存の Tool 契約（決定9）を使う。** 契約体系を2つ持たない。同じ Tool を番頭も他モジュールも呼ぶ形になり、決定25 の「同じ能力に入口が複数あり、契約は1つ」の再適用になる。
- **番頭（AIエージェント）は経路に入らない。** モジュール間呼び出しは機構レベルの話であり、番頭の判断を経由しない。
- レジストリは宣言的な設定に置く（既存の `meta/config.yaml`・`meta/environments.yaml`、および決定19 の単一インストーラによる配線に揃える）。
- **今回作るのは契約と最小実装（レジストリ・解決・呼び出し）までとする。** 認証・再試行・非同期・ストリーミングは具体的な必要が出てから足す（P1）。

#### (c) Worker Pool の位置づけ：必須の組み込みモジュール

- **Worker Pool は必須の組み込みモジュールとする。** 決定23 のとおり独立したサービスであり、Banto も Kobo もそれぞれのクライアントになる。Banto から見た登録形は他のモジュールと同じ（接続情報＋`worker.*` Tool＋セッションビューアGUI）。
- ただし**無いと番頭は職人へ委譲できず D10（番頭は細かい仕事をしない）が構造的に満たせない**ため、記憶（D11）と同様に外せない必須要素として扱う。標準ライブラリと同じ位置づけ——常に同梱されるが、機構としては他のモジュールと対等。
- **不採用：「Worker Pool を Banto の基本機能（中核）にする」案。** Worker Pool を Banto 内部に置くと、Kobo が職人を使うために Banto へ依存することになり、(b) のブローカー方式と同じ依存の逆転が起きる。

### 28. 記憶の自動抽出：背後のLLMで抽出し、注入は会話の区切りに限る（2026-07-30、PO裁定）

- **決定10 (b)(c) の実装方針を具体化する。** 現状の記憶は「覚えて」と言われたものを `memory.save` で保存するだけ。Hermes Agent の設計（セッションから記憶すべきことを背後のLLMで抽出する）を踏襲し、自前で薄く実装する。Hermes 本体は組み込まない（決定10 のまま）。
- **プロンプトキャッシュとの関係（実装調査で判明した制約）**：`pi-ai` は Anthropic 形式のプロンプトキャッシュに対応し、`cache_control` を**システムプロンプト**・最後のTool定義・最後のメッセージに付ける。したがって、
  - **抽出そのものはキャッシュを壊さない**——独立した別プロンプトの呼び出しであり、本セッションのプレフィックスに触らない。
  - **壊れるのは「抽出結果をセッション中にシステムプロンプトへ差し込む」場合**。記憶はシステムプロンプト（キャッシュされる先頭）に入るため、途中で書き換えると会話全体のキャッシュが無効になる。
  - よって **注入は次のセッション開始時に限る**。「抽出は随時、注入は区切り」で分ける。
- **抽出の契機は会話の区切りとする。** 具体的には「新しい会話」への切り替え時と、pi の圧縮境界（`compaction_end`）。圧縮時はどうせキャッシュが作り直されるため乗れる。毎ターン走らせる案は不採用——呼び出し回数が会話長に比例し、コストが見えないまま累積する（POのコスト感度は番頭の記憶にも入っている）。
- **抽出した記憶は自動で有効にする。ただし出所を残し、POが消せるようにする。** `origin`（`explicit` / `extracted`）を記録し、記憶ビューア（キャンバスGUI）で一覧・削除できる面を用意する。PO確認を必須にする案は不採用——「二度説明しなくてよい」（vision）の達成が確認の手間で相殺されるため。誤った記憶が一度は注入されうる欠点は、出所の可視化と削除の容易さで受け止める。
- **抽出対象はPOの発言と番頭自身の結論に限る。ツールの出力（ファイル内容・Web ページ等）からは抽出しない。** 記憶は長生きするため、外部の文字列が「POの好み」として混入すると影響が続く。番頭は `file.read` やブラウザで任意の文字列を読むので、この境界は明示的に引く。
- **抽出には安いモデルを使う。** LLMプロバイダ層はプラガブル（CLAUDE.md）なので、本セッションと別のモデルを指定できる形にする。
- **削除は追記で表す。** 記憶は追記のみのログ（task-0007）なので、削除も「忘れた」ことを追記して表し、有効な記憶は読み出し時に導出する（D3）。

### 29. 職人から起動元への報告経路：Worker Pool がイベントログを持ち、起動元が購読する（2026-07-30、PO裁定）

- **論点**：職人が「終わった」「これを聞きたい」を起動元へ伝える経路が無い。現状は起動元が `worker.attach` で覗きに行くしかなく、誰も見なければ気づかれない。番頭の職人向けシステムプロンプトは「足りない情報があれば報告してください」と指示しているのに、**報告先が存在しない**状態だった。
- **起動元は複数いる。** Kobo・番頭・将来のモジュールがそれぞれ職人を起こす。したがって「誰が起動したか」を報告の宛先として扱う必要がある——`projectTag`（作業の名前空間）は宛先ではない（Kobo は複数の projectTag を持つ）。

#### (a) 完了は「事実」と「主張」を分ける

- **プロセス終了は事実、職人の完了報告は主張**として別に記録する。番頭は主張を参考にしつつ、成果は自分で確かめる（I1：自己申告を信頼しない）。
- これは既存設計の踏襲である。Kobo の職人向け `report_done` は実装コメントで「executor は auditing / review-ready へ自己遷移してはならない」と明記されており、**完了報告は「検証へ回す合図」であって完了判定ではない**。同じ原則を Worker Pool でも守る。

#### (b) 質問は番頭が受け、手に余るものだけ PO へ

- 職人の質問は**まず起動元が受ける**。番頭が起動元なら、答えられるものは `worker.steer` で返す。
- **不可逆な選択・PO の意向が要るもの（D1）は決定20 のセッション開始リクエストの受け口へ上げる。** ここで別の通知系を新設しない——同種の仕組みを2つ持つと、Tool契約で現に払っているコスト（imp-0003）と同じ構図になる。
- 質問して待っている職人は**生きているが止まっている**。`alive` だけでは「動いている」と区別がつかず、待ちっぱなしが溜まっても気づけないため、`waiting` を別の状態として持つ。

#### (c) 届け方は Worker Pool のイベントログ＋購読

- **Worker Pool が職人のライフサイクルのイベントログを持ち、起動元が購読する。** 起動時にコールバックURLを渡す案は不採用——起動元が落ちている間の報告が消え、再送を作り始めると結局ログが必要になる。
- 決定20 が Kobo→Banto で採った形（Push 型・発行元のログに一本化・Banto は別ストアを持たない）を、Worker Pool→起動元にも適用する。`after_event_id` 相当での再開により取りこぼしを防ぐ。**職人の真実は Worker Pool に一箇所**（D3）。
- 呼び出しは当事者間で直接（決定27b）。Banto はこの経路の中継役にならない。

#### (d) Worker Pool は報告の「意味」を持たない（D5）

- Worker Pool が発行するのは中立な事実と主張だけで、**解釈は各起動元が行う**。Kobo は自分のステートマシンへ写す（監査も従来どおり走る）、番頭は会話に出す。
- そうしないと Worker Pool の中に Kobo の状態遷移と Banto の会話の両方の知識が入り、モジュールが増えるたび膨らむ。

#### (e) Kobo の既存経路とは層が違う（重複ではない）

- **`report_phase` / `report_done` は Kobo のドメイン語彙**（タスクの状態機械）であり、Kobo の持ち物。決定25「モジュールは自分の Tool を提供する」に従い、Kobo が自分の拡張（`banto-executor.ts`）で職人に渡す——現状のまま変えない。
- **`worker.report` / `worker.ask` は汎用の職人→起動元の経路**で、Worker Pool の持ち物。
- **真実は割れない**：タスクの状態は Kobo に、職人のライフサイクルは Worker Pool に、それぞれ一箇所（D3）。職人は「起動元のドメイン Tool」と「Worker Pool の汎用 Tool」の両方を持ちうる。
- 実装上の制約：職人は別プロセスなので、Tool を渡すには拡張か到達可能なエンドポイントが要る。Kobo は `--extension` ＋環境変数で実現しており、Worker Pool も同じ手を使える（決定27b で HTTP 面を持ったため）。

### 30. 職人の店じまい：番頭が畳むのを主とし、アイドル期限は安全弁。閉じた職人は履歴として残る（2026-07-30、PO裁定）

- **論点**：仕事を終えた職人のプロセスが生き続ける。pi は RPC モードでターンを終えても待機し続けるため、委譲するたびにプロセスが積み上がる。閉じる契機を誰が持つかが決まっていなかった。

#### (a) 主たる契機は番頭の判断（PO裁定）

- **番頭が「もう良い」と判断したら積極的に畳む。** 報告（主張）を受けて成果を確かめ、良ければ閉じる。
- **報告そのものは閉じる合図ではない。** 決定29(a) を崩さない——`worker.report` は検証へ回す合図であり、それだけで職人を消すと「聞き返す」経路が失われる。畳むのは番頭が確かめた後。

#### (b) アイドル期限は安全弁であって主機構ではない（PO裁定）

- 一定時間なにもしていない職人は Worker Pool が閉じる。**番頭が畳み忘れてもプロセスが積み上がらない**ための保険。
- 安全弁が主機構になってはいけない。「放っておけば勝手に消える」に寄りかかると、番頭が職人の面倒を見なくなる。
- **畳んだことは会話へ流さない**（2026-08-06、PO裁定・当初の裁定を差し替え）。職人が1人終わるたびに「畳みました」と「プロセスが終わりました」の2通が並んで届いており、同じ出来事を2度読ませていた。プロセスが終わったことは `worker_exited` の知らせで届くので、番頭が取り落とすものは無い。
  - 安全弁が働いたことに気づけるようにする、という上の狙いは**イベントログ側で保つ**——`reason`（`idle`）は今までどおり記録され、`worker.list` / `worker.events` と職人ビューアから引ける（決定30e）。会話へ押し込まないだけで、見えなくはしない。
  - 実体：`packages/banto-host/src/worker-notice.ts` の `isNoticeworthy`。

#### (c) 閉じた職人は消えない。履歴はイベントログから導く

- 台帳（`spawn-ledger`）は**生きているプロセスの帳簿**なので、畳んだ職人は外れる。しかし**イベントログには残る**ので、そこから履歴を導く（D3：導出する。別の一覧を持たない）。
- **GUI にも番頭にも見える。** 職人ビューアは終わった職人も一覧でき、セッションの中身も読める（セッションJSONLは消さない）。番頭は `worker.list` / `worker.events` で同じものを引ける。

#### (d) 起こし直しは同じセッションの再開を既定とする（PO裁定）

- pi の `--session` で元の会話を復元する。職人が読んだ内容・やったことが戻るので、番頭が前提を毎回書き直さずに済む。
- **D11「職人は記憶を持たない」と矛盾しない。** D11 が禁じているのは**隠れ状態**であって、文脈の保存ではない。セッションファイルは外から読める記録で、再開しても再現可能・監査可能は保たれる。むしろ番頭の記憶（好み・習慣）とは層が違うことがはっきりする。

#### (e) 畳んだ理由を記録する

- `done`（番頭が良しとした）／`idle`（安全弁が働いた）／`stopped`（強制的に止めた）を区別して残す。
- 理由が消えると、履歴が「なぜ終わったのか」に答えられない。とくに `idle` が多いなら、それは番頭が職人の面倒を見ていない兆候として読めるべき。

### 31. 記憶の分類に `fact`（事実）を追加する（2026-07-30、PO裁定）

- **論点**：`MemoryKind` は `preference`（好み）と `habit`（習慣）の2種しかなく、POの名前・役割・許諾範囲のような**属性情報**の置き場が無い。職人が起草した提案（`docs/proposals/2026-07-30-memory-kind-fact.md`）より。
- **問題は実在した。** 手元の記憶を確認したところ、「POの名前は『たくみ』である」が `preference` として保存されていた。仮定の話ではない。

#### (a) `fact` を追加する

- 導出できず（D3）、命題の真偽が一意に定まり、変わらないことが期待される情報を置く。名前・役割・連絡先・許諾範囲など。
- **好みと混ぜてはいけない。** 「好み」の一覧に名前が並ぶと、番頭が「変えてよいもの」として扱いうる。事実の訂正は「誤りの発見」であって「好みの変化」ではない。
- リテラルの追加なので既存の記憶には影響しない（JSONL の形式は変わらず、新しい値が出現するだけ）。

#### (b) `fact` は決定29(a) の「事実」と**同音異義**である。混ぜない

- 決定29(a) の `fact` / `claim` は**証拠の状態**を表す（観測された事実か、職人の自己申告か）。記憶の `fact` は**言明の種類**を表す（事実か、好みか、習慣か）。軸が違う。
- 記憶における証拠の状態は `kind` ではなく**出所**が担う（決定28：自動抽出した記憶は出所を持たせて消せるようにする）。**分類と確からしさを同じフィールドに載せない。**
- 語彙表の「充ててはいけない語」に `fact` を足すことはしない——別のフィールド名（`kind` と `origin`）で、別のドメイン（記憶と職人のイベント）に属しており、この注記があれば取り違えない。

#### (c) 命名は `fact` を採る

- 代替案は `attribute`（許諾範囲のような規則性のある情報に狭い）、`information`（広すぎて好み・習慣との境界が曖昧）。提案の推す `fact` が最も意味に合う。

#### (d) プロンプトでは「事実 → 好み → 習慣」の順に出す

- 事実が最も安定しており、先に読ませる方が判断が安定する。

### 32. 動作検証環境を Kobo から独立した Environment Pool モジュールにする（2026-07-30、PO裁定）

- **論点**：`EnvDriver` 契約（`spec-environment` §2 の7動詞 provision/deploy/healthcheck/run/collect/teardown/list）とその具象実装（docker/process ドライバ・環境台帳・sops）は現状 `banto-daemon` の中にあり、Kobo に従属している。決定23（Worker Pool の独立）とまったく同じ構図で、実行能力と統治が混ざっている。
- **番頭の急所との関係**：番頭は実行系の Tool を一つも持たない（D10・D5、意図的）。そのため「テストが通った」を職人の自己申告でしか得られず、決定29(a)「報告は主張であって完了の証明ではない」と噛み合っていなかった。動作検証を独立モジュールにすると、番頭は Kobo 無しでも**機構が返した事実**として検証結果を受け取れる——狭い自己開発が Kobo の完成を待たなくなる。

#### (a) `EnvDriver` の実行能力を Environment Pool モジュールへ切り出す

- 決定23（Worker Pool）と同じ扱い。契約は `banto-core` に既にある。具象（docker/process ドライバ・runner・台帳・sops）をモジュールへ移し、Kobo は当面ライブラリとして参照し続ける。
- **切り出しと提供元の差し替えは2段階に割る**（決定23・task-0010 の教訓）。まず振る舞いを変えず切り出し、その後 Kobo をサービス利用へ切り替える（Worker Pool の task-0010 → task-0024 と同じ）。e2e がこの経路を守っている。

#### (b) 名前は Environment Pool、ドメインは `env.*`

- Worker Pool と対称。どちらも台帳・quota・TTL を持つ「資源の汎用管理サービス」であり、`spec-environment` §5 にその機構が既にある。
- 「ドライバ」は語彙表で環境・ランタイム両方に使用中のためモジュール名に充てない。

#### (c) spec-environment §3「ドライバを起動するのは常にKobo」を第三者性の要件として読み替える（P3 の解消）

- §3 の字面（起動者は Kobo に限る／エージェントが直接叩く経路は提供しない）は、本決定と矛盾する。**黙って寄せず**、ここで裁定する。
- §3 が守る不変条件は「Kobo」という固有名詞ではなく、**ドライバを回して結果を記録するのは依頼者ではない信頼された第三者である**こと（I1「ずるは不可能にする」）。Environment Pool がその第三者になるなら不変条件は保たれる——番頭は `env.*` で依頼するが、自分でドライバを叩いて結果を作ることはできない。Worker Pool が職人の生死の真実を握るのと同じ構図。
- **番頭は `env.*` を直接呼べる。職人には直接経路を与えない**——職人は「成果を出す側」であり、自分の成果を自分で検証させると I1 が崩れる。職人は Environment Pool を直接持たず、検証は番頭（依頼元）が回す。
- `spec-environment` §3 の本文を、この第三者性の要件に沿って改訂する（下記）。

#### (d) sops の復号鍵は Environment Pool が持つ

- いま Kobo がやっていること（sops で復号し、ドライバプロセスの環境変数として直接渡す。§4）をそのまま移す。**番頭の文脈に credentials が出ない**という守るべき性質は変わらない。
- 帰結として Environment Pool は復号鍵を持つサービスになる。決定27b の HTTP 面に認証が無い現状は別途詰める（未決事項に追加）。

#### (e) 環境台帳・quota・TTL・reconcile は Environment Pool が持つ

- **作った者が片付ける責任を負う。** 番頭が Kobo 無しで provision できる以上、TTL と強制 teardown がモジュール側に無いと誰も片付けない。`spec-environment` §5 は「外部リソースの消し忘れは金銭的実害が出るため、本仕様で最も優先度の高い機構」としている。
- `SpawnLedger` を Worker Pool が持つのと同じ形。Kobo は自分の統治（どのプロファイルをどのタスクに使うか、検証が通ったら review-ready へ動かす）をこの上に重ねる。
- **外部VMコストは D9 で one-way（D1 に戻る）とされた副作用**。quota の上限を誰が決めるか（能力側の既定か、統治側の裁定か）は実装時に詰める。

### 33. 職人の外を読む口は、番頭が明示的に渡したときだけ（2026-07-30、PO裁定）

- **論点**：職人が調べものをするのに、ドキュメントや仕様を自分で引けないと、番頭が全部読んで渡すことになり D10（番頭は細かい仕事をしない）が空回りする（imp-0005、PO提起）。一方で外部ネットワークアクセスは職人に新しい能力を与えるため、既定にするかは D1 に触れる。
- **前提の変化**：imp-0004 を直すまで `worker.delegate` の `tools` は効いていなかった。道具を選べない状態では「全職人が常に web を持つ」形しか作れない。imp-0004 の解消が先行条件になっていた。

#### (a) 既定では渡さない。`worker.delegate` の `network: true` のときだけ載せる（PO裁定）

- 渡さなければ**拡張ごと載らない＝Tool が存在しない**。許可リストで隠すより強い（隠した Tool は許可リストの書き落としで復活しうる）。
- 番頭の負担はフラグ1つ。「調べさせる」と決めたときだけ渡す、が判断として自然な粒度。

#### (b) これは砂箱ではない。そう書く

- `bash` を持った職人は curl で外へ出られる。`network` が渡すのは `web.fetch` / `web.search` という**読みやすい口**であって、遮断の機構ではない。
- 本当に外を断ちたいなら `tools` から bash を外す（imp-0004 でそれができるようになった）。効かない保証を契約に書かない（I2）。

#### (c) 検索は鍵の要らない経路（PO裁定）

- DuckDuckGo lite の HTML を読み、取れなければ Wikipedia の全文検索に落とす二段。API キー・サインアップ・従量課金のいずれも要らない——**鍵を要求すると one-way な外部依存になる**（D1）ため、それを避けられる経路を選ぶ。
- 相手の HTML が変われば壊れる。壊れたときに黙って「該当なし」にならないよう落とし先を用意し、両方0件のときだけ「見つからなかった」と言う（I2）。正式な検索 API に差し替えたくなったらここを替える。

#### (d) 取得は公開 URL のみ。内側は門番で弾く

- 職人は Kobo・Worker Pool・番頭ホストと**同じマシンに居る**。門番が無いと `web.fetch` で `http://localhost:4110/tools/...` を叩けてしまい、報告経路を通らずにモジュールの Tool を呼べる。外を読む口が内側への抜け道になってはいけない。
- localhost・プライベート/ループバック/リンクローカル IP（IPv4・IPv6、埋め込みIPv4を含む）と http/https 以外のスキームを拒否する。DNS は引かない（リバインドは見ない）という割り切りは参照実装（loamium）と同じ。

#### (e) ドメインは `web.*`、持ち主は Worker Pool

- `worker.report` / `worker.ask`（決定29e）と同じく**職人側の Tool**で、番頭は呼ばない。番頭が web を見たくなったら職人に頼む（D10）。
- 実行は職人プロセスの中で完結させ、Worker Pool を経由させない。何を取ったかは職人のセッションに残り、`worker.attach` で辿れる（D3：導出できるものを二重に持たない）。

### 34. `env.*` Tool の契約と、Environment Pool の設定面（2026-07-30、PO裁定）

- **論点**：決定32 は「Environment Pool を独立モジュールにする」と決めたが、**中の契約は空白のまま**だった。task-0033 で切り出し（振る舞い不変）は済んだので、次は番頭が実際に何を呼ぶかを決める必要がある。既存実装は `(projectTag, taskId, profileName)` を鍵にし、`repoPath` を Kobo の `ProjectRegistry` から引いており、**Kobo を経由しない経路が成立していない**（決定32c と矛盾する）。
- **見つかった仕様の穴**：`spec-environment` §2 のドライバ契約に**作業ディレクトリの入力が無い**。`process` ドライバは継承した cwd で `cmd` を起こし、`docker` ドライバは相対 compose パスを `process.cwd()` で解決する。番頭が「職人が作った worktree で検証する」を頼めない——決定32 が狙った「番頭が機構の返す事実として検証結果を受け取る」がそもそも表現できない。

#### (a) 高位1本と低位動詞の両立て（PO裁定）

- **`env.verify`（高位）**：使い捨ての検証。provision →（deploy）→ healthcheck → run → collect → teardown を機構側が一息で回し、**畳みまで持つ**。番頭が teardown を忘れても漏れない（I3：外部リソースの消し忘れは金銭的実害で、本仕様で最も優先度の高い機構）。
- **低位動詞**（`env.provision` / `deploy` / `healthcheck` / `run` / `collect` / `teardown` / `list`）も残す。レビュー用 dev server のように**居座らせたい**環境（`spec-environment` §3 のレビューフロー）が高位1本では表現できないため。
- Worker Pool の `worker.delegate`（高位）と `worker.steer` / `worker.close`（低位）と同じ形。**畳むのが主で、安全弁が従**という関係も同じ（決定30b）。
- Kobo のマージ前ゲートの verify も最終的にはこの経路に乗る（実行系を二重に持たない・D3）。

#### (b) 識別子は `envId`。`projectTag` / `taskId` は台帳のラベル

- `env.provision` が `envId` を返し、以降の動詞は `envId` で指す。**Kobo のタスクIDに縛られない**——番頭は Kobo 無しでも呼べなければならない（決定32c）。
- `taskId` は Worker Pool の `worker.delegate` と同じ扱いで、「何の検証か」を台帳とログに残すためのラベル。Kobo のタスクIDを入れてもよいし、番頭が自分で付けてもよい。

#### (c) プロファイルの在り処は呼び出し側が渡す（PO裁定）

- `repoPath` を引数で受け取り、Environment Pool が `<repoPath>/meta/environments.yaml` を都度読む（D3：ファイルは意図。キャッシュしない）。
- **Environment Pool は独自のプロジェクト登録簿を持たない。** Kobo は自分の `ProjectRegistry` から、番頭は自分が知っている作業場所から渡す。持たせると Kobo の登録簿と二重管理になり、食い違ったときにどちらが正か決められない（D3）。

#### (d) どこで動かすかを契約に入れる（`workdir`）——ドライバ契約の改訂

- `provision` と `run` の入力に `workdir`（絶対パス）を追加する。ドライバはそこを cwd としてコマンドを起こし、`config` 内の相対パス（compose ファイル等）もそこから解決する。
- **これは `spec-environment` §2 のドライバ契約の変更**なので、プロジェクト独自のドライバも受け取れるようにする必要がある。省略時は現状どおり（Environment Pool の cwd）に落とし、既存プロファイルを壊さない。
- Environment Pool は `workdir` を台帳に残す。プロセスが落ちて起き直しても、後続の `run` に同じ場所を渡せる（D3：導出できる状態を別に持たない、の例外ではない——これは導出できない入力）。

#### (e) アドホック環境は既定でビルトインドライバのみ。外部は設定で開ける（PO裁定）

- `profile` の代わりに `driver` + `config` を直接渡せる。**既定では `process` / `docker` のみ**——線引きが「お金がかかるかどうか」で説明でき、I3 を守りつつ手元の検証は軽く回せる。
- 外部ドライバ（＝VM等、費用が出る側）のアドホックを許すかは**設定で開ける**（既定は閉じる）。プロジェクトによっては開けたい場面があるため、機構としては選べるようにし、既定を安全側に置く。
- アドホック環境にも**必ず既定 TTL を付けて台帳に載せる**。プロファイル経由かどうかで掃除の扱いを変えない。

#### (f) TTL と quota の既定・ハード上限は能力側（Environment Pool）が持つ（PO裁定）

- Environment Pool が既定 TTL・最大 TTL・プロファイルごと／全体の同時実行上限を持つ。**プロファイルはその範囲内でのみ指定できる**。
- 範囲を超えるプロファイルは**黙って丸めず拒否する**（I2）。既存の `env_profile_rejected` の経路に乗せ、なぜ拒否したかを残す。
- 理由：D9 で外部VMコストは one-way な副作用（D1 に戻る）とされている。プロファイルに `ttl: 720h` と書けば通る状態では quota が歯止めとして機能しない——**機構が上限を持たないと誰も止められない**。
- (e) の「外部ドライバのアドホック可否」も同じ設定面に置く。上限と許可は同じ性質（能力側が持つ安全側の既定）で、置き場を割らない。

### 35. 職人からの知らせは、起こした分身（会話スレッド）へ届く（2026-07-31、PO裁定）

- **論点**：決定29 は職人の報告・質問を `origin`（起動元）で宛てると定め、決定2 は番頭の分身が会話スレッドごとに分かれると定めたが、**両者の交点が未定義**だった。番頭が1人である現状は `origin: "banto"` がホスト全体で1つなので問題が出ないが、スレッドが増えた瞬間に「誰に届くのか」が決まらなくなる。

#### (a) 宛先は起こしたスレッド。`origin` をスレッド粒度にする

- 決定29 の機構をそのまま使う。`worker.delegate` は既に `origin` を引数で受け、購読側は `origin` で絞れる——**Worker Pool 側の改修は要らない**。ホストが渡す `origin` をスレッド単位にするだけで乗る。
- 理由は文脈の在り処。その職人に何を頼んだか・なぜ頼んだかはそのスレッドの会話にあり、別のスレッドへ流すと番頭は前提を持たないまま報告を読むことになる。

#### (b) 宛先スレッドが畳まれていたら、**起こし直して**届ける（PO裁定）

- 職人の**質問**は答えが来るまで職人を止める（決定29b の `waiting`）。宛先が不在だと誰も答えず、アイドル安全弁（決定30b・既定15分）で畳まれて**質問が黙って消える**——I2 に反する。
- 新しいスレッドを立てて質問だけ渡す案は採らない。番頭が「なぜその職人を起こしたか」を知らないまま答えることになる。
- 起こし直しても「目の前の話は壊れない」（決定2）は保たれる——増えるのはタブ1つで、既存スレッドのキャンバスも会話も触らない。職人の店じまいと再開（決定30d の `worker.wake`）と同じ発想を、分身の側にも適用する。

#### (c) 見えていないことと、届いていないことを混ぜない

- PO がそのスレッドを開いていないだけの状態は**届いている**。未読の印を出すのは UI の仕事で、宛先の決め方の問題ではない。
- `worker_exited`（プロセスが落ちた）のような**事実**は、宛先が不在でも Worker Pool のイベントログに残る（決定29c）。消えて困るのは、答えを待たせる質問だけ。

### 36. リポジトリとワークツリーは repo-manager が扱い、「場所」は共通契約にする（2026-07-31、PO裁定）

- **論点**：番頭は1つのルート（`BANTO_WORKSPACE` か cwd）しか見えず、複数のリポジトリを相手にできない。一方 Kobo は複数プロジェクトを統治する（`spec-multi-project` §1）。PO の要件は「**1つの番頭スレッドで何でも話せること**」——リポジトリごとに会話場所が分かれるのは受け入れられない。
- **経緯**：当初「スレッドをプロジェクトに束縛する」案を検討したが、会話が分断されるため却下。次に「焦点（いまどの店の話か、というスレッドの状態）」を検討したが、**副作用のある Tool が自由なパス引数を取り続ける限り札としてしか働かない**ことが分かり、これも採らなかった（Fable への設計相談で判明）。結論として**スレッドに新しい状態を持たせず、場所は呼び出しごとに明示する**形に落ち着いた。

#### (a) repo-manager が扱うのは Git リポジトリとワークツリー。**店（プロジェクト）の登録簿ではない**

- リポジトリとプロジェクト（統治の単位）は別物。混同しない。Kobo の `ProjectRegistry` は統治の単位であり続け、repo-manager はその下にある**作業場所の実体**を扱う。

#### (b) 状態を持たない。`ghq` / `gwq` から毎回導出する

- リポジトリの一覧は `ghq` の配置から、ワークツリーの一覧は `gwq`（`d-kuro/gwq`）から導出できる。**独自の台帳を作らない**（D3：導出できる値は保存しない）。
- Worker Pool が `SpawnLedger` を持つのとは対照的。あちらは「起こしたプロセス」という導出できない事実を持つ必要があったが、こちらは無い。
- `ghq` / `gwq` が未導入の環境では**場所を1つも返さない**。導入を強制せず、下記(d)の静的な場所だけで動く。

#### (c) 「場所」の共通契約を `banto-core` に置く。契約は極小にする

```ts
interface Place { id: string; label: string; path: string }
interface PlaceProvider {
  name: string;
  list(): Promise<Place[]>;
  /** 次の list で導出し直す（写しを持つ提供元だけ。下記 (j)） */
  refresh?(): void | Promise<void>;
}
```

- 砦が必要としているのは「**いま許されている場所の集合**」だけなので、契約はそれだけにする。
- **「作る・壊す」は共通契約に入れない。** `repo.worktree.add` は repo-manager 固有の Tool のままにする——静的パスに「ワークツリーを追加」は意味がなく、共通化すると片方が空実装になる（契約が間違っている印）。
- `RuntimeDriver`（決定11）・`EnvDriver`（決定32）と同じ形。実装が2つある時点で抽象化の閾値は超えており、決定18 の「将来ニーズを見越した追加はしない」には抵触しない。

#### (d) 静的な場所はホストの設定にする。モジュールにはしない

- Git 管理していない作業領域や、ホスト全体を触りたい場合のための口。
- **モジュールにしない**理由：モジュールの定義（決定25・27）は「接続情報＋Tool＋GUI＋SKILL を1単位で登録する」であり、そのどれも持たないものをモジュールと呼ぶと枠が緩む。必要になったら格上げする。
- **`/` を場所に登録することはできるが、それは砦の無効化と同じ。** 黙って広い場所が登録されている状態を作らないため、(i) 起動ログに警告を出す (ii) Tool の結果に場所名を必ず出す。決定33 で web を既定オフにしたのと同じ考え方。

#### (e) `workspace` は場所の**消費者**になる

- いま `createWorkspaceModule(root)` が1ルートを抱えているのをやめ、`file.*` / `git.*` が**場所を引数で受け取る**形にする。
- GUI（FileBrowser / GitViewer）も同じ Tool 契約を HTTP 経由で呼んでいるので、**引数が1つ増えるだけで場所の選択UIが成り立つ**（決定25 の「人も番頭も同じ契約、経路が違うだけ」がそのまま効く）。

#### (f) 番頭に「焦点」という状態は持たせない

- 場所は**呼び出しごとに明示**する。会話では自然に「banto の docs を見て」と言うので、番頭がそれを引数に写すだけ。**店名が Tool 呼び出しとして画面に出る**ので、取り違えても見える（長い絶対パスに埋もれる現状より監査しやすい）。
- スレッドの状態を増やさないことで、次の問題が**まとめて発生しない**：`BantoToolContext` の契約改訂（「ctx は当てにしない」との衝突）、HTTP 面へのスレッド識別の配管、複数クライアント間での一貫性、切り替えを LLM の推測に委ねる危険。
- 「いまどの店の話か」を画面に出したくなったら、**直近の Tool 呼び出しが指した場所を表示すればよい**（表示だけの機能。状態を持たない）。

#### (g) 砦：登録された場所の中だけ。`worker.delegate` も同じ砦に通す

- `file.*` には既に範囲チェック（`resolveInWorkspace`：シンボリックリンクを解決した後に判定）があり、`git.*` は `cwd` 固定で外を向けない。**`worker.delegate` の `worktreePath` だけが無検査**で、いま既に「番頭が任意のディレクトリを職人に書き換えさせられる」穴が空いている（複数リポジトリ化と関係なく塞ぐべきもの）。
- 砦の判定基準を「1つの固定ルート」から「**登録された場所のいずれかの中**」へ一般化し、読み取りも副作用も同じ砦を通す。
- 引数は消さない。**場所の外を指したときに弾く**形にすることで、既存の Tool 契約を壊さない。

#### (h) Kobo も repo-manager へ寄せる

- worktree の作成・削除は現在 Kobo が持つ（`daemon.ts` の `createWorktree`、`merge-queue.ts` の `removeWorktree`。関数の置き場だけが Worker Pool にあり、Worker Pool 自身は使っていない）。機能を2箇所に分散させない。
- 決定23（Worker Pool）・決定32（Environment Pool）と同じ2段階：**まず切り出し、Kobo は当面ライブラリとして参照 → 後でサービス利用へ切替**。

#### (i) `spec-multi-project` §1 の改訂が要る

- 「**検討エージェント**：プロジェクトのworktreeで起動する対話セッション。**横断させない**」は、番頭が複数プロジェクトを扱う本決定と矛盾する。黙って寄せず、改訂として起票する（P3）。

#### (j) 導出は重い。**待たせない写し**を挟む（2026-08-04、PO報告「全体的に遅い」を受けて (b) に追記）

- **実測**：`gwq list -g --json` は1回 430〜460ms かかる。場所の解決は Tool 呼び出しのたびに起きる（決定36e）ので、GUI を1つ開くだけでこれが4回積み上がっていた——Git を開いてコミット一覧が出るまで 1.7秒、ファイルの中身が出るまで 0.6秒、その大半がこれ。
- **決定**：導出結果を**短命の写し**として持ってよい（`RepoDiscovery`）。台帳（保存される状態）ではない——ファイルに書かず、プロセスが終われば消える。(b) の「独自の台帳を作らない」はそのまま生きている。
- **正しさは3つで保つ**：
  1. 一定時間（10秒）を過ぎたら**裏で**取り直す。返すのは手元の写しで、待たせない
  2. 自分で場所を増減したとき（`repo.clone` / `repo.init` / `repo.worktree.add` / `repo.worktree.remove`）は、その場で写しを捨てる
  3. 探している場所が写しに無ければ、呼び手（`PlaceRegistry`）が `refresh()` で取り直させてから断る。**「作った直後の場所が使えない」「あるのに無いと言われる」を起こさない**——砦の判定（決定36g）も同じ道を通る
- **写しを使うのは読み取りの一覧だけ。** 「実行の前後を比べて増えたものを見つける」道具（`repo.worktree.add` 等）は直接導出する。写し越しに見ると前後が同じに見えるため。
- 結果（実測）：場所の解決を伴う Tool が 500ms → 3〜35ms。Git を開いてコミット一覧まで 1687ms → 288ms、ファイルの中身まで 566ms → 64ms。

### 37. 番頭は Git の変更操作を持たない（決定24 を維持。2026-07-31、PO裁定）

- **論点**：`docs/proposals/2026-07-30-repo-manager-module.md` が `repo.commit` / `repo.push` / `repo.branch.*` / `repo.remote.*` / `repo.tag.*` を番頭へ渡すことを提案し、その1点目として「番頭が Git の変更操作を自分で持つべきか」の裁定を求めていた。決定36 はこれを含めず別途の裁定に回していた。
- **裁定：持たない。決定24 をそのまま維持する。**

#### (a) 提案の該当部分は却下する

- 提案は「`git.*`（閲覧専用）は変えないので決定24 は遵守している」としていたが、**別の名前空間に同じ能力を置けば決定24 が守ろうとしたもの（番頭が自分で手を動かさない・D10）は成り立たない**。名前空間の問題ではない。
- `repo.push` は提案自身が D1（不可逆）と認めていた。持たせない以上、この論点も消える。

#### (b) 決定36 との関係

- 決定36（場所の共通契約・repo-manager）は**そのまま有効**。repo-manager が扱うのは「どこで作業するか」であって、リポジトリの履歴を変えることではない。
- ワークツリーの作成・削除（決定36h）は残る。これは**作業場所の用意**であって Git 履歴の変更ではない——`git worktree add` は既に Kobo がタスクのライフサイクルで行っていることで、その置き場を移すだけ。

#### (c) 帰結：リポジトリを変えるのは職人と Kobo だけ

- コードの変更 → 職人が worktree で行い、Kobo がゲートを通してマージする（既存の流れ）
- 番頭が「コミットして」「push して」と頼まれたら、**職人へ委譲する**（`worker.delegate` に `bash` を持たせれば git は打てる）
- **残る論点**：番頭自身の成果物（ADR の決定・`work/` の起票・引き継ぎメモ）を**誰がファイルに書くか**は、Git の変更操作とは別軸であり本決定では決まらない。現状、番頭は `memory.save` 以外に書き込み手段を持たない一方、決定15 は「番頭が `work/epics`・`work/tasks` を起票する」と定めており、**実装と矛盾している**（P3）。別途裁定する。

### 38. 番頭の書き込みは、場所ごとに PO が許した範囲だけ（2026-07-31、PO裁定）

- **論点**：番頭は `memory.save` 以外に書き込み手段を持たない（30本の Tool はすべて読み取りか委譲）。ところが決定15 は「番頭が `work/epics`・`work/tasks` を起票する」と定めており、**実装と矛盾している**（P3）。決定37 で Git の変更操作は持たないと決めたが、**ファイルを書くこと自体は別の軸**であり、そこは決まっていなかった。
- **職人へ委譲する案も検討した**が、決定を1つ記録するたびに職人を起こすことになり、しかも記憶を持たない職人（D11）に全文を渡す必要があるため、**番頭が書いてから転記させる二度手間**になる。

#### (a) 書き込み範囲は**場所ごと**に与える。既定は読み取り専用

- 番頭は複数リポジトリを扱う（決定36）ので、グローバルに1つの範囲を決めても意味がない。`ghq` が見つけた全リポジトリは**既定で読み取り専用**。
- 決定33（web は既定オフ、許したときだけ）と同じ形。**許していないことが既定**である。

#### (b) 宣言は**番頭が書けない場所**に置く（I1：ずるは不可能にする）

- リポジトリ内の設定ファイル（`meta/config.yaml` 等）に置くと、**番頭がその宣言を書き換えて自分の権限を広げられる**。`meta/**` を範囲に含めた瞬間に自己昇格が成立する。
- したがって宣言はホスト側（リポジトリの外、起動時に読む）に置く。`spec-environment` §3 が「エージェントがドライバを直接実行する経路は提供しない（I1）」と機構で封じたのと同じ考え方。

#### (c) 番頭は範囲の拡大を**要求できる**。決めるのは PO、書くのはホスト

- 番頭が「この場所の `docs/**` も書きたい」と要求し、**PO が許可し、ホストが設定を書く**。番頭は最後まで設定に触らない。
- 職人が `worker.ask` で番頭に聞き番頭が答える（決定29b）のと同じ構図を、1段上に適用したもの。
- これにより PO が事前に全リポジトリを設定しておく手間が消える——必要になった場面で頼み、その場で許す。

#### (d) どんな設定でも書けない範囲がある

- **`.git/`**。ここを書けると、番頭は git コマンドを使わずに履歴を書き換えられる——**決定37 の抜け道**になる。
- **ホスト自身の設定とデータ置き場**。(b) の自己昇格を塞ぐため。
- これらは設定で `**` を許した場合でも例外として除く。

#### (e) いま何を許しているかが見えること

- 残る risk は「じわじわ広げる」——`docs/**` → `work/**` → `**` と段階的に要求されると、1回ごとの判断では気づきにくい。**機構では防げないので、見えるようにする**：現在の許可の一覧を GUI（studio）に出し、広い範囲（`**` 等）は起動ログにも警告を出す。
- 「理由を盛る」risk は、**要求されたパスそのものが実質**なので、理由文ではなく範囲を見れば判断できる。

#### (f) フレームワークはパス構成を知らない

- `docs/` `work/` という構成は**プロジェクト（と Kobo）側の語彙**であり、Banto 中核が知ってよいものではない。フレームワークが持つのは「**書いてよい範囲がある**」という概念だけで、それが何かは設定が与える。
- 実装上、`file.write` は workspace モジュールが持つ（`file.*` の一員）。判定は決定36(g) の砦に「書いてよい範囲か」が1段足されるだけ。

#### (g) 帰結：決定15 の文言は変えなくてよい

- 「番頭が `work/epics`・`work/tasks` を起票する」は、**許可された環境ではそのまま成立する**。許可していない環境では職人へ委譲する、と読める。
- **番頭はコミットできない**（決定37）ので、書いたものは必ず未コミットで残り、PO の diff レビューか職人のコミットを通る。書けることと残せることが分かれているのが安全装置になる——番頭が規則（`docs/principles.md` 等）を自分に都合よく書き換えても、差分に出て止まる。

### 39. 検証環境の公開は差し替え可能にする。既定は番頭ホストが中継する（2026-07-31、PO裁定）

- **論点**：imp-0008。`env.provision` で dev サーバは立つが、**POがブラウザで見る経路が無い**。ポート／URL がどこにも出ず、外から届く保証も無い。POから「Palmux のように Caddy と繋ぐのはどうか」という提案があった。
- **実測で分かった制約**：banto はいま Palmux 管理の incus コンテナの中で動いており、**Caddy の admin API（localhost:2019）には届かない**（Palmux の Caddyfile も `admin localhost:2019`）。80/443/8080 には届く。つまり Caddy 一択にすると**いまの配置で動かない**。

#### (a) 公開の口を差し替え可能な契約にする（`EnvExposer`）

- `EnvDriver`（決定11・32）・`PlaceProvider`（決定36c）と同じ形。**公開の手段は配置で決まる**ので、どちらか一方に決め打たない。実装が2つある時点で抽象化の閾値は超えており、決定18 には抵触しない。

#### (b) 既定は**Environment Pool 自身が中継する**（`{baseUrl}/env/<envId>/`）

- 新しい依存も DNS も TLS も要らず、banto が既に公開している1ポートの下、**そのモジュールの到達先**に生える。**どの配置でも動く**。
- **中継は Environment Pool の責務**（PO指摘）。banto-host に置くと (i) 検証環境へのトラフィックで Banto がブローカーになる（決定27 が避けたもの）、(ii) 独立サービス化（決定32a の2段目）で必ず移すことになる、(iii)「envId → ポート」の対応を台帳の外にもう1つ持つ（D3）、の3つが起きる。
- そのため `BantoModule` に **自分の到達先の下で任意のパスを捌く口**（`serve`）を足した。ホストは経路を渡すだけで中身を解釈しない。
- **banto を守っている認証をそのまま継承する**のが利点。banto の画面に入れる人だけが検証環境に届くので、検証環境ごとに認証を用意しなくても「無認証で外に出る」事故が構造的に起きない。モジュールHTTP面の認証（未決事項）が決まれば、そのまま効く。
- 制約：パス配下なので絶対パスで資源を引くアプリは壊れることがある。そこまで要るなら (c) を使う。

#### (c) Caddy 実装は設定で有効化する（`BANTO_CADDY_ADMIN` + `BANTO_ENV_DOMAIN`）

- Palmux と同じ形（`caddy_admin.go`）：静的な Caddyfile ではなく admin API に route を注入し、**安定した `@id` で冪等に upsert / delete** する。ワイルドカード証明書と apex の認証は静的側に置く前提。
- **banto が自分の VM に常駐して Caddy を持つ配置**のためのもの。片方だけ設定されていたら黙って既定へ落とさず起動を止める（I2：Caddy のつもりで中継されると気づけない）。

#### (d) どのポートを公開するかは**呼び出し側が明示する**

- ドライバの `handle` と `config` は不透明（`spec-environment` §2・D1/D3）。`handle.port` を覗くと Environment Pool がドライバごとの内部表現に依存し始めるので、`env.provision` の `expose` 引数で受ける。
- 公開は**環境が立ってから**行い、**畳むときは公開を先に取り下げる**。環境が消えたのにURLだけ生き残ると、開いた人は「壊れている」としか分からない。

#### (e) 認証は別途

- 公開した検証環境そのものへの認証は決めていない。(b) の既定では banto の認証を継承するので当面それで足りる——(c) を使う段になったら、モジュールHTTP面の認証と併せて決める。

### 39. 検証環境の公開は差し替え可能にする。既定は番頭ホストが中継する（2026-07-31、PO裁定）

- **論点**：imp-0008。`env.provision` で dev サーバは立つが、**POがブラウザで見る経路が無い**。ポート／URL がどこにも出ず、外から届く保証も無い。POから「Palmux のように Caddy と繋ぐのはどうか」という提案があった。
- **実測で分かった制約**：banto はいま Palmux 管理の incus コンテナの中で動いており、**Caddy の admin API（localhost:2019）には届かない**（Palmux の Caddyfile も `admin localhost:2019`）。80/443/8080 には届く。つまり Caddy 一択にすると**いまの配置で動かない**。

#### (a) 公開の口を差し替え可能な契約にする（`EnvExposer`）

- `EnvDriver`（決定11・32）・`PlaceProvider`（決定36c）と同じ形。**公開の手段は配置で決まる**ので、どちらか一方に決め打たない。実装が2つある時点で抽象化の閾値は超えており、決定18 には抵触しない。

#### (b) 既定は**Environment Pool 自身が中継する**（`{baseUrl}/env/<envId>/`）

- 新しい依存も DNS も TLS も要らず、banto が既に公開している1ポートの下、**そのモジュールの到達先**に生える。**どの配置でも動く**。
- **中継は Environment Pool の責務**（PO指摘）。banto-host に置くと (i) 検証環境へのトラフィックで Banto がブローカーになる（決定27 が避けたもの）、(ii) 独立サービス化（決定32a の2段目）で必ず移すことになる、(iii)「envId → ポート」の対応を台帳の外にもう1つ持つ（D3）、の3つが起きる。
- そのため `BantoModule` に **自分の到達先の下で任意のパスを捌く口**（`serve`）を足した。ホストは経路を渡すだけで中身を解釈しない。
- **banto を守っている認証をそのまま継承する**のが利点。banto の画面に入れる人だけが検証環境に届くので、検証環境ごとに認証を用意しなくても「無認証で外に出る」事故が構造的に起きない。モジュールHTTP面の認証（未決事項）が決まれば、そのまま効く。
- 制約：パス配下なので絶対パスで資源を引くアプリは壊れることがある。そこまで要るなら (c) を使う。

#### (c) Caddy 実装は設定で有効化する（`BANTO_CADDY_ADMIN` + `BANTO_ENV_DOMAIN`）

- Palmux と同じ形（`palmux2/internal/runtime/incus/caddy_admin.go`）：静的な Caddyfile ではなく admin API に route を注入し、**安定した `@id` で冪等に upsert / delete** する。ワイルドカード証明書と apex の認証は静的側に置く前提。
- **banto が自分の VM に常駐して Caddy を持つ配置**のためのもの。片方だけ設定されていたら黙って既定へ落とさず起動を止める（I2：Caddy のつもりで中継されると気づけない）。

#### (d) どのポートを公開するかは**呼び出し側が明示する**

- ドライバの `handle` と `config` は不透明（`spec-environment` §2・D1/D3）。`handle.port` を覗くと Environment Pool がドライバごとの内部表現に依存し始めるので、`env.provision` の `expose` 引数で受ける。
- 公開は**環境が立ってから**行い、**畳むときは公開を先に取り下げる**。環境が消えたのにURLだけ生き残ると、開いた人は「壊れている」としか分からない。

#### (e) 認証は別途

- 公開した検証環境そのものへの認証は決めていない。(b) の既定では banto の認証を継承するので当面それで足りる——(c) を使う段になったら、モジュールHTTP面の認証と併せて決める。


### 40. Banto は認証を持たない。守るのは前段。ただし既定で localhost に閉じる（2026-08-01、PO裁定）

- **論点**：`spec-environment` §8 の未決事項。モジュールの HTTP 面は無認証で、Environment Pool は sops の復号鍵を持つ——`env.provision` を叩ければ、鍵を盗まなくても復号された値を自分の指定したコマンドへ渡せる。Worker Pool の報告経路も同じ面。
- **裁定：Banto に認証を持たせない。** 気になる配置では前段（Caddy 等）に置いてもらい、まとめて入れて設定できるスクリプトを用意する方向にする。認証機構を自前で抱えると、そちらの正しさを永久に負うことになる。

#### (a) ただし**既定で localhost だけを待ち受ける**（そうしないと裁定が成り立たない）

- 裁定した時点の実装は全インターフェース（`*:4100`）で待っており、**前段を素通りして直に叩けた**。この状態では「前段で守る」は運用の心がけでしかなく、認証が飾りになる。
- 既定を `127.0.0.1` にし、広げるには `--host` / `BANTO_HOST_BIND` の明示を要求する。広げたときは起動ログに警告を出す（決定36d の場所の警告・決定38e の書き込み範囲の警告と同じ形）。
- I1: 心がけではなく機構で担保する。前段を置く／置かないは配置の判断だが、**素通りできないこと**は Banto 側の責任。

#### (b) 帰結として、公開する経路はすべて前段を通る

- 番頭のUI（決定39b の検証環境への中継を含む）・モジュールの HTTP 面・職人の報告経路は、いずれもホストの1ポートに乗っている。そのポートを守れば全部が守られる——**守る場所が1箇所で済む**のがこの形の利点。
- 職人と検証環境はホスト内から `127.0.0.1` で報告・中継するので、閉じても動く。


### 41. モジュールは設定画面に「項目の宣言」を出す。GUI は渡さない（2026-08-01、PO裁定）

- **論点**：prototype の設定面を実装するにあたり、モジュールが自分の設定を設定画面に足せるようにしたい。キャンバス（決定12・17）はモジュールが React コンポーネントを持ち込む形だが、設定も同じにするか。
- **裁定：GUI は渡さず、項目の宣言だけを渡す。描くのは設定画面。**

#### (a) 宣言だけを受け取る理由

- 設定は「名前と型と今の値」でほぼ尽きる。見た目まで各モジュールが持つと、**設定画面の中で書式がばらばらになる**——キャンバスは面ごとに独立しているので問題にならないが、設定は1つの画面に並ぶ。
- 宣言だけなら、**モジュールが増えても設定画面のコードは変わらない**。項目の型（`text` / `number` / `boolean` / `select` / `list`）を増やすときだけ描画側を足す。

#### (b) 値の持ち主はモジュール

- `read()` / `write()` はモジュールが実装する。どこにどう保存するか、変更をどう効かせるかはモジュールが決める（決定27：Banto をブローカーにしない）。
- 保存先を持ちたくないモジュールのために、ホストは自分の設定ファイルの一区画を `SettingsSection` として貸す。**使うかはモジュールの自由**——自前の保存先を持つモジュール（Kobo 等）はそちらを使えばよい。
- `write()` は**効いたかどうかを正直に返す**（`applied` / `restartRequired`）。その場で効かせられる設定（検証環境の上限・場所）はそうし、効かないもの（LLM・待ち受けアドレス）は画面が「次の起動から」と出す。I2：効いていないのに効いたように見せない。

#### (c) 設定の口は番頭に渡さない

- `settings.describe` / `settings.update` は `internalTools`（決定29e と同じ枠）。**設定を番頭が書き換えられると、場所の許可も上限も自分で広げられる**（決定38b の自己昇格）。書き込み許可のパネル（task-0042）と同じ形。
- 保存先はホストのデータ置き場で、`file.write` の砦が守っている。


### 47. 文脈の管理をコンパクションから「退避と章立て」へ移す（2026-08-05、PO裁定）

提案 `docs/proposals/2026-08-05-context-strategy.md` を採用する。**ADR 本文は追記のみ**（`spec-schemas` §3）なので、以下は決定10・28 を書き換えず、上書きする形で足す。

#### (a) 大きなツール出力は文脈に載せず、参照に置き換える

- 番頭の文脈を膨らませているのは会話ではなく**ツール出力**である（`file.read` が ADR を1本返せば4万字）。一定の大きさを超えたツール結果は `BANTO_DATA_DIR/artifacts/<threadId>/` へ書き、文脈には栞（見出し＋ID）だけを返す。全文は `artifact.read` で読み戻す。
- **要約ではないので情報を失わない。** 真実はファイル、文脈にあるのは参照（D3）。Anthropic の context editing API がサーバ側でやっていることを、pi / OpenAI 互換の経路では「そもそも大きいものを入れない」で達成する。
- **挿入時に決める。過去のメッセージは書き換えない**——遡って消すとプロンプトのプレフィックスキャッシュが飛ぶ。
- 退避しないもの: `artifact.*`（自分自身）・`memory.*`（予算で既に絞ってある）・`skill.*`（段階的開示が1段増えるだけ）。

#### (b) pi の自動コンパクションを既定で切り、章立てに置き換える

- 文脈が閾値（既定 0.6）に達したら、**番頭がターン境界で章を閉じる**。95%で強制的に走るのではなく、余力のあるうちに区切りで閉じる。
- 閉じるときに引き継ぎ資料を `BANTO_DATA_DIR/handoffs/<threadId>/ch-NNNN.md` へ書き、次の章には**見出しと参照だけ**を渡す（`handoff.read` で詳細を引く＝SKILL と同じ段階的開示）。
- 章の境界は **pi のコンパクションエントリ**として書く（`fromHook: true`）。`buildSessionContext` がそのまま解釈でき、セッションツリーの形も壊れない。違うのは中身だけ——pi が入れるのは会話のLLM要約だが、ここが入れるのは引き継ぎ資料への参照である。
- **元のトランスクリプトは pi のセッションファイルに残る**（D3）。資料は導出値でいつでも作り直せる。
- I2: 資料を書けなかったら**畳まない**。引き継ぎの無いまま文脈だけ消えるのは、コンパクションの失敗より悪い。

#### (c) 決定28 の抽出の契機を「圧縮境界」から「章の境界」へ読み替える

- 決定28 は契機に「新しい会話への切り替えと、pi の圧縮境界（`compaction_end`）」を挙げていた。(b) で自動コンパクションを切るため、**圧縮境界は章の境界と読む**。
- 「抽出は随時、注入は区切り」という骨格は変えない。むしろ章立てにすると**注入の機会が会話中に何度も現れる**——章の頭は決定28 が許した「セッション開始時」に当たる。

#### (d) 決定28 に「既存記憶の再蒸留を禁止し、差分追記のみとする」を足す

- 「Useful Memories Become Faulty When Continuously Updated by LLMs」（arXiv 2605.12978）は、LLM がエピソードを繰り返し統合すると**有用性が上がったあと下がり、記憶なしのベースラインを下回る**ことを示した（正解の軌跡から統合しても、以前は解けた問題の54%に失敗）。劣化の原因はエピソードではなく**統合ステップ**にある。
- したがって抽出器の出力は「新規追加」か「訂正（旧IDつき）」の**差分だけ**とし、記憶全体をまとめ直すプロンプトは作らない。生のエピソード（トランスクリプト・引き継ぎ資料）は一級の証拠として残す。
- 発火は章の境界だけ（明示的なゲート）。抽出の失敗は会話を止めない（ログには残す。I2）。

#### (e) 決定10(c) の「FTS5全文検索」を訂正する

- 前提が2つとも崩れている。**Node 20 は 2026-04-30 に EOL**、かつ **Node 22+ の `node:sqlite` は FTS5 を組み込まずにビルドされている**。Node を上げても FTS5 は素では手に入らず、`better-sqlite3` 等のネイティブ依存追加（D1・D6）になる。
- 第三層の検索は**全文スキャンで足りる**（PO一人・資料は合計数MB）。索引は持たない（D6）。遅くなったら ADR-0001 §3 が既に許している「導出インデックスとしての SQLite」へ進む。

#### (f) 記憶の注入に予算を入れる

- `renderMemoryForPrompt` は active な記憶を全件入れていた。件数上限もトークン予算も無く、(d) の自動抽出が入れば数百件規模になって破綻する。
- 層ごとにトークン予算を持ち、**種別（`fact` > `preference` > `habit`。決定31d）→ 出所（`explicit` > `extracted`）→ 新しさ**の順で選ぶ。溢れた分は件数をプロンプトに明示し、`memory.search` で引かせる（黙って落とさない。I2）。
- 記憶に `validFrom`（世界で真になった時刻）を任意で持たせる。`createdAt`（記録した時刻）とは別軸——Zep の valid time / ingestion time の最小版。
- 削除は追記で表す（`memory.forget`。決定28 のとおり）。

#### (g) ADR-0003 の二層を実装する

- ADR-0003（accepted）は「人の記憶＝横断／プロジェクトの記憶＝各リポジトリに閉じる」と決めているが、実装は単一のグローバルストアだけだった。決定36 で番頭は複数プロジェクトを扱うため、放置すればプロジェクト知識が混ざる（P3 の齟齬）。
- **ストアそのものを場所ごとに分ける**ことで「横断させない」を機構で担保する——同じファイルに `scope` フィールドで同居させると、絞り込みを1箇所書き忘れた時点で混ざる。
- プロジェクトの記憶は `BANTO_DATA_DIR/projects/<場所ID>/memory.jsonl`。**リポジトリの中には置かない**（決定38b：番頭が自分の記憶を書き換えられてしまう）。

#### (h) 記憶の評価セットを持つ

- `spec-improvement-loop` §1 の「層A資産は壊れると静かに劣化する」当の対象が記憶である。LongMemEval の6分類（単一セッション想起・選好想起・知識更新・時間推論・複数セッション想起・予算超過）に倣った問いを受け入れテストに入れ、**記憶が正しいものを差し出せているか**を毎回測る。
- 測るのはモデルの賢さではなく「届いているか」。LLM は呼ばない——評価が鍵とネットワークを要求すると、誰も回さなくなる。

### 48. 成果物の置き場所（書斎）を、フレームワークが既定で1つ持つ（2026-08-05、PO裁定）

- **論点**：リポジトリに紐づかない成果物——調査レポート・比較検討——を残す先が無い。番頭が書けるのは決定38 の「場所ごとに許した範囲」だけで、その場所は運用者が絶対パスで宣言する（決定36d）。これを前提に手順を書くと、**手順書の側に個人の実体パスが入る**。番頭の SKILL は配布物（`packages/banto-host/skills/`）に入るので、人やデプロイ先が変わるたびに SKILL を書き換えることになる。
- **退避（決定47a）では代われない**。artifact は「文脈に載せない観測」の引換券で、会話の中でしか意味を持たない。ホストのデータ置き場は決定38d でどう設定しても書けない——そこも置き場所にはできない。

#### (a) 場所IDだけを固定し、実体は環境が与える

- 場所ID **`desk`** を既定で必ず登録する。実体の既定は `~/banto-desk`（無ければ起動時に作る）。
- **SKILL・記憶・成果物の本文が指すのは `desk` という id と、そこからの相対パスだけ**。実体の絶対パスをそれらに書かない。人が変わってもデプロイ先が変わっても、書き換えるのは環境の設定だけで済む。
- 決定36d（静的な場所はホスト設定で与える）への追加であって、置き換えではない。**フレームワークが既定で1つ持つ場所**は、これだけである。

#### (b) 上書きできる。消しても既定に戻る

- `BANTO_PLACES` と設定画面のどちらからでも、同じ id の行を書けば場所も書き込み範囲も上書きできる。
- **行を消しても既定に戻る**——置き場所が消えると、番頭はリポジトリに属さない成果物をどこにも残せなくなる。設定漏れが機能の欠落にならないことが、この決定の値打ちそのもの。
- 「どれが効いているか」（設定 > 起動時指定 > 既定）の判断は**呼び手に1箇所だけ**置き、設定画面はそれをそのまま映す。両側に置くと、片方を直したときもう片方が古いまま残る（I2：画面と実態を食い違わせない）。

#### (c) 場所があることと、書けることは分ける

- **既定の書斎は読み取り専用**。決定38a（既定はどの場所も読み取り専用）を崩さない。番頭は `place.request_write` で範囲を頼み、PO が承認して初めて書ける。
- 許可は場所IDをキーに保存されるので、**後で実体のパスを変えても許可はそのまま繋がる**。
- `reports/` のようなパス構成を既定に埋めない（決定38f：フレームワークはパス構成を知らない）。構成を決めるのは SKILL（プロジェクト側の語彙）であって、フレームワークではない。

#### (d) 帰結：置き場所の性質は環境の判断に委ねる

- 実体を git リポジトリにするか（履歴が残る・戻せる）、ただのディレクトリにするかは**環境ごとの運用判断**。機構は git を要求しない——git の無いデプロイ先で壊れる。
- 番頭はコミットできない（決定37）ので、成果物は未コミットのまま残り、PO の目を通る。

## 帰結

- (+) ハーネスを差し替える際の変更範囲が「アダプタ層」に閉じる。Kobo・UI側のコードは無変更で済む。
- (+) 記憶システムの自作を避けることで、旧ブランチで頓挫した調整コストを負わない。
- (+) Kobo独立GUI＋Bantoチャット/キャンバスの分離により、PO直操作と番頭経由操作が同じKobo APIを共有し、真実が割れない。

## 未決事項

- Kobo/Banto デプロイ方式のバージョン整合性チェックの具体的な実現方法（決定19の残課題）
- モバイル実機（iOS/Android）での検証（決定21により実装フェーズのタスクとして先送り。設計判断としては解決済み）
- **モジュールの HTTP 面（決定27b）の認証**（決定32d の帰結）。Environment Pool は sops 復号鍵を持つため、その HTTP 面が無認証だと credentials 経路が露出する。Worker Pool の報告経路（決定29e）も同じ面を使っており、認証は Environment Pool 固有ではなくモジュール HTTP 面全体の課題として詰める
- **環境 quota の上限を誰が決めるか**（決定32e）。能力側（Environment Pool）の既定値か、統治側（Kobo）の裁定か。外部VMコストは D9 で one-way な副作用のため、実装時に決める
