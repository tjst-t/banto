# ADR-0027: 監査は合否の門ではなく、補助の目である

- status: accepted
- date: 2026-08-20
- decided-by: PO 裁定（帳場経由）＋ PO の詰め（同日）
- decisions: 決定140 / 決定141 / 決定142 / 決定143
- task: `task-0287`
- supersedes-in-part: ADR-0013 決定56・決定57（監査セッションを「機械的検査」の一つと数えていた箇所）

## 何が問題だったか

Kobo の工程は 実装 → **監査** → レビュー → マージ前ゲート → マージ と並んでいる。
このうち**監査だけが、判断を出さなかったときにタスクを殺していた**。

- 監査人が判定の口（`audit_report`）を呼ばずに「終わりました」と自由文で報告 → `audit_reported_without_verdict` で `failed`
- 監査セッションが判定を出さずに落ちた → 再試行の上限で `audit_session_exited_without_verdict` で `failed`
- 監査セッションを起こせなかった → `audit session spawn failed` で `failed`

**どれも「実装が悪い」ことを何ひとつ示していない。** それでもタスクは止まり、番頭が手を入れるまで永久に動かない。
実例：task-0219 で3回連続。task-0246 / task-0242 も同型（監査役に当てたモデルが道具呼び出しに乗れず、判定の口を一度も呼べなかった）。

原因を辿ると、監査人に渡していた指示そのものが失敗を誘っていた。

- 手順の1行目が **「ワークツリーパスに移動して実装内容を確認してください」**——つまり**リポジトリ全体を読み直すことを既定にしていた**。
- そのうえ監査人は袋の中で全量 `npm test` を起動し、「完了を待っています」と書いてターンを終えた。**判定を出す前に、待つことに使い切った。**

そして**その検証は、マージ前ゲートが検証環境で受け入れ条件の `verify` を回すことと二重になっている。**

### 発端

PO の疑問——「**Kobo はトークンを使いすぎではないか。opus 級を監査やレビューにも使う意味があるのか**」。

実測（2026-08-20 / `/var/lib/banto/data/kobo-settings.json`）：

| 役 | 当たっているモデル |
|---|---|
| 実装 executor | `sonnet` |
| 手直し rework | `sonnet` |
| **監査 audit** | **`opus`** |

**実装より監査の方が高いモデルを当てていた。** リポジトリ全体を読ませる指示と組み合わさって、いちばん高い読み方を、いちばん高いモデルにさせていたことになる。

## PO の裁定（言葉のまま）

> **監査はプラスアルファの層にする。監査のせいで工程が止まる方が、いまは問題である。取りこぼしが出たら、そのとき別途直せばよい。**

同日の詰め。

> **監査はまず diff をみて、diff だけだと分からなければ、ファイルもみる。**

---

## 決定140: 監査は**合否の門ではなく、補助の目**である

監査の役割は「**受け入れ基準（`acceptance[].text`）への内容の適合**」の判断に限る。
**リポジトリ全体を読み直すことでも、テストを回すことでもない。**

**実装の正しさを担保するのはマージ前ゲート**——受け入れ条件の `verify` を検証環境で機械が回す、そこである。
監査はその上に乗る**補助の目**であって、検査の代わりではないし、検査でもない。

この決定は工程の並びを変えない（監査は同じ場所に居続ける）。変えるのは**監査が持っていた拒否権の重さ**である。

## 決定141: 監査は**まず diff**。diff だけで分からなければ、**ファイルも見る**

**「diff だけを渡す」ではない。「diff から始めて、必要なら遡れる」である。** 順序を契約にする。

1. **既定は diff。** Kobo が監査人に最初に渡すのは、**そのタスクの diff と、受け入れ基準の text**。
2. **diff だけで受け入れ基準を満たすか判断できるなら、そこで判定してよい。**
3. **判断できないときだけ**、その箇所に関係する**ファイルへ遡ってよい**。

**ファイルを読むことを禁じない。** 禁じれば、diff だけでは判断できない変更で監査が嘘をつく。
**同時に、リポジトリを読み直すことを既定にしない。** 「ワークツリーへ移動して実装内容を確認せよ」に相当する全体走査の指示は落とす。
**この両方を試験で縛る**——片方だけを縛ると、次に読む人がどちらが正なのか判断できなくなる。

diff の作り方はマージ前ゲートのスコープ検査と**同じ取り方を再利用する**（新しい取り方を発明しない）。
diff が大きいときは**上限で打ち切り、打ち切ったことを明記する**。無言で切らない。diff が取れなかったときは**取れなかったと書く**（I2：黙って空を渡さない）。

### テストは回さない（ここは動かさない）

指示文に **「テストを回すのはあなたの仕事ではない。マージ前ゲートが検証環境で `verify` を回す」** と書き切る。
「一式は自分で叩かない」止まりでは、軽い確認の余地から「袋の中で `npm test` を起動して待つ」型が生まれ続ける。**二重にやることが、いまの失敗の原因である。**

`skills/audit-system.md` と `skills/audit-checklist.md` も同じ位置づけ・同じ順序へ書き直す。

## 決定142: 判定は **明示の NG だけがブロック**する（フェイルオープン）

**監査人が NG を明示しなかったら、自動で通す。忘れても通る。NG だけが止める。**

| 監査で起きたこと | これまで | これから |
|---|---|---|
| `verdict="fail"` を明示 | 差し戻し（rework） | **変わらず差し戻し** |
| `verdict="pass"` を明示 | 次段へ | 変わらず次段へ |
| 判定を出さずに報告して終えた | `failed` | **既定で通す** |
| 判定を出さずに落ちた（再試行も尽きた） | `failed` | **既定で通す** |
| 監査セッションを起こせなかった | `failed` | **既定で通す** |

いまの失敗の大半は「**判定を出し忘れる**」型である。**向きを反転すれば、この失敗型は原理的に消える。**

この向きは、リポジトリに既にある方針とも揃っている——監査役モデルのブラックリストは**白リストではなくブラックリスト**で、「確かめられないものは弾かない」（`kobo-settings.ts`：「空・未定義＝確かめられない。そのときは**通す**」／PO 指示 2026-08-18）。**確かめられないことを「弾くべき」と混同しない。**

**I1（自己申告を信頼する検証を書かない）は壊れない。** I1 が要求しているのは「機械が直接確かめること」であって「監査人が確かめること」ではない。確かめる役は**マージ前ゲートに残っている**。監査人の沈黙を pass と読むのは、そもそも監査人の言い分を検証の根拠に数えていない、ということである。

**あわせて、監査の口（`audit_report`）が監査役のセッションに確実に載ることを機構で保証し、試験で縛る**（claude-agent 経路・pi 経路の両方）。**決定141 だけを入れて口を放置すると、トークンは減っても失敗は減らない**——この2つはセットで初めて効く。

## 決定143: **既定で通したこと**と、**diff の外を読んだ理由**を、帳簿に残して数える

2つとも `audit_verdict` イベントに載せる。**新しいイベント種は増やさない。**

1. **既定通過の印**（理由つき）。番頭の会話へ流れる知らせにも、**既定で通ったと分かる文面**を出す(黙って通すと、番頭が「監査が見た」と誤解する)。
2. **diff の外で読んだもの・なぜ要ったか。** `audit_report` の口に書く欄を設け、指示文にも「diff の外を読んだら必ずここへ理由を書く」と明記する。例：「a2 の判断に `thread-store.ts` の既存の振る舞いが要ったため」。

1 は下に書く**承知の上のリスクを見張る唯一の手段**である。これが無ければ、リスクを承知したことにならない。

2 の狙いは2つ。**どれくらいの頻度で diff だけでは足りないのかが数字で分かる**こと——**「監査は diff で足りる」はいまは仮説**なので、次に絞るときの根拠を取れる形にしておく。もう1つは、**監査人が漫然とリポジトリを読み歩くのを抑える**こと——理由を書かせると、書けないものはやらなくなる。

**2 は監査人の自己申告であって、機械が検出した事実ではない（I1）。通す／通さないの判断材料には使わない——傾向を数えるためだけのものである。** この区別をコードのコメントにも残す。

## 注記：この指標は、どこで嘘をつくか（2026-08-20 実測）

**決定142（フェイルオープン）が、決定143 の指標の片方を欠測させる。**

`consultedBeyondDiff`（diff の外を読んだ理由）は **`audit_report` の欄**なので、**監査人が判定を出したときにしか埋まらない**。ところが決定142 により、**判定を出さない回は既定で通って先へ進む**——その回は「遡ったかどうか」も「なぜ遡ったか」も**丸ごと欠測する**。

実測（task-0292 の監査）：`byDefault: true` で既定通過したが、**監査人は実際に diff の外を3回読んでいた**（`docs/notes/handoff.md` と `docs/spec/daemon-core.md` を `sed` / `grep` で部分読み）。判定を出さなかったので、その事実は `audit_verdict` に残っていない。

**したがって「diff だけでは足りなかった頻度」は、実態より低く出る。** しかも偏り方が悪い——欠測するのは**監査人が判定を出せなかった回**であり、それは**手間取った回・迷った回**、つまり「diff だけでは足りなかった」側に寄っているはずの回である。**この数字を読むときは、既定通過した回が母数から落ちていることを前提にすること。「もっと絞れる」と読まないこと。**

直す方向は `work/inbox/improvement/imp-0087-fail-open-hides-the-metric-it-created.md` に置いた——**遡った事実は自己申告ではなく、監査セッションの実行記録から機構が数える**（「何を読んだか」は機構が数え、「なぜ読んだか」は監査人が書く）。急ぎではないので工場には積んでいない。

**教訓：安全側に倒す変更は、別の見えなさを作る。** 倒したあとに「**これで見えなくなるものは何か**」を必ず数えること。同じ日に同じ形の見落としを2回している（もう1つは決定142 の引き金が「監査人が起きたあと」にしか無く、**監査人が一度も起きなかった場合を誰も拾わない**という穴。task-0294 で直す）。

## 承知の上のリスク（PO に説明済み・その上での決定）

**フェイルオープンにすると、監査が実質回っていないのにパス扱いになる経路ができる。**
監査人がモデルの都合で一度も判定を出せなくても、監査セッションの起動そのものが壊れていても、タスクは通る。
**「監査を通った」という記録が、実際には誰も見ていないことを意味する場合がある。**

PO の判断はこうである。

> **実装の正しさはゲートの機械検証が担保する。監査は補助の目に留め、忘れによる停止を根絶する方を取る。**

**これは知らずに踏んだ穴ではなく、承知で選んだ設計である。**
将来ここで取りこぼしが出たとき、**「知らなかった」ではなく「承知で選んだ」と読むこと。** そのときの直し方は、フェイルオープンを戻すことではなく、**取りこぼした種類の検査をゲート側（機械が回す側）へ足すこと**である——PO の裁定は「取りこぼしが出たら、そのとき別途直せばよい」であって、「止まる方に戻せ」ではない。

見張りは決定143 の印で行う。**既定通過の割合が高止まりしているなら、それは「監査が要らない」ではなく「監査が動いていない」の兆候**なので、判定の口の側を疑うこと。

## 既存の決定との関係（矛盾する箇所）

### ADR-0013 決定57 の最終段落

> **番頭が `approved` にしても関所は飛ばない。** マージ前ゲートは `approved` の後に Kobo が回し、番頭に手段は無い。かつ、その前に実装者とは別の監査セッションが通っている。**番頭のレビューは2つの機械的検査の上に乗る判断**であって、検査の代わりではない

**「2つの機械的検査」のうち、監査セッションはもう検査ではない。** 決定142 により、監査は通らなくても通る。
したがってこの段落は、これからは次のように読む。

- **番頭のレビューが乗っている機械的検査は、マージ前ゲート1つである。**
- 監査セッションは**その手前に置かれた補助の目**であり、**明示の NG を出したときだけ**工程を止める。
- **決定57 そのもの（レビューの3段・`po` 段を番頭が通せない）は変えていない。** 変えたのは、その下敷きにしていた検査の数え方だけである。

vision の「番頭でも帳簿はごまかせない」は**壊れない**——ごまかせなさを担保していたのはマージ前ゲート（番頭に手段が無い機械検証）であって、監査セッションではない。

### ADR-0013 決定56

「監査の差配（別セッション・rework・**失敗駆動の tier 昇格**）」を骨格として残す、とある。
**別セッションであることも rework も残る。** 昇格は**明示の `fail` が続いたときだけ**効く（判定を出し忘れた回は、もう失敗として数えない）。

## モデル割当（この ADR では決めない）

決定140・141 により**監査はまず diff を見る層**になるので、監査に高い等級を当てる根拠は薄くなる。
**実装だけ高級モデル、監査は低 tier ＋機械検証**が自然な向きである。
ただし `roleAssignments` を書き換えるのは PO の判断なので、**この ADR では決めない**（実測を添えて幹へ提案する）。

なお `spawnAuditSession()` は名指しが無いときの既定として `modelTier: "reasoning"` をコードに直書きしている。名指し（`roleAssignments.audit.model`）があればそちらが優先されるため、いまは `opus` が当たっている。**既定の等級を下げるかどうかも、名指しの変更と合わせて一度に決めること。**
