# ADR-0014: 契約は凍結せず、**改訂できる**。ただし黙っては起きず、依存するものが差し戻る

> status: **accepted**（2026-08-08。PO 裁定）。**ADR-0013 決定64 を差し替える。**
> 決定番号は 68（ADR-0013）の続きから採る。

## 文脈

PO の指摘（2026-08-08）——「test の契約が間違っていたら、実装がちゃんと終わっていても、
再作成で一から実装しなおし？ もしそうなら決定64が間違っていたかも」。

### 決定64（もとの裁定）

> 積んだあとの契約は凍結される。訂正は**新しいタスクを積み、元を `superseded` にする**。

守ろうとしたものは本物だった：**「何に対して監査したのか」が答えられなくなる**（I1）。
番頭は `work/tasks/*.md` を書けるので、後から `scope.paths` を広げてマージ前ゲートを
緩められては困る。

### 実際に起きたこと（実機・loamium）

`task-0004` がマージ前ゲートで落ちた。原因は受け入れ条件の**検証コマンド**：

```
a3  text:   「UI の型チェックが通る」               ← 正しい
    verify: `npm ci --include=dev && npm run lint`  ← ここだけ間違い
```

環境の用意（`npm ci`）が検証コマンドに焼き込まれていた。これは task-0080 で `setup` に
移った仕事で、**基準は合っているのに確かめ方が壊れている**。

凍結はこの2つを区別しない。結果、`task-0005` を**切り直す**ことになり、

- 新しい worktree は HEAD から切られる（前の成果は入らない）
- 引き継ぐには本文に「`<sha>` を cherry-pick せよ」と書いて**職人に手でやらせる**
- 引き継いでも**職人1回・監査1回・レビュー1回**を払い直す
- **経緯が別 id に分かれる**

そして `task-0005` も同じ場所で落ちた。

### 何が間違っていたか

**凍結が守ろうとしたものを、凍結が壊していた。**

間違いが直せないので、運用が「新しいタスクを立てる」に逃げる。その結果が
`task-0004` → `task-0005` の分断で、**「何に対して監査したのか」の追跡性はむしろ落ちた**。

原因は、契約の中身を**一律に**扱ったこと。危険度は同じではない：

| 部分 | 変えると何が壊れるか | 直したくなる頻度 |
|---|---|---|
| `scope.paths`（広げる） | 範囲外の変更を事後に正当化できる | 低 |
| `acceptance[].text` | 緩めると「できていないもの」を通せる | 低 |
| `acceptance[].verify` | 弱めると検証が空振りする | **高**——書き方を間違えやすい |
| `title` / `body` | 判断の材料。監査の対象ではない | 中 |

**`verify` は「何をもって完了とするか」ではなく「どう確かめるか」**である。

## 決定

### 決定69：契約は改訂できる（決定64 を差し替える）

危ないのは「変えること」ではなく、**黙って・自分に有利に・再評価なしに変えること**。
3つとも潰せば、凍結しなくても不変条件は守れる。

1. **黙って起きない。** ファイルを書き換えただけでは反映されない（watcher は今までどおり
   読み飛ばす——inc-0028 の直しはそのまま）。`kobo.amend` を呼んだときだけ取り込む
2. **記録に残る。** `task_contract_amended` に**変更前後・誰が・なぜ**が載る。
   改訂後の契約そのものも載せる（D3：状態はイベントから作り直せること）
3. **依存するものが差し戻る。** 基準が動いたら監査は無効になり `implementing` へ戻る

### 決定70：何を変えたかで、差し戻す先が変わる

| 変えたもの | 監査 | 状態 |
|---|---|---|
| `acceptance[].verify` **だけ** | **有効のまま** | 動かさない。マージ前ゲートは元々毎回回る |
| `acceptance[].text` / 条件の増減 / `scope.paths` | **無効** | `implementing` へ戻す |
| `title` / `body` | 影響なし | 動かさない |

**`verify` だけの訂正で監査を有効のままにするのが、この ADR のいちばんの効き所。**
実装も監査もやり直さずにマージ前ゲートへ進める。

### 決定71：緩める方向は PO だけ

番頭が通せるのは：**検証コマンドの訂正・スコープからパスを取り除く・受け入れ条件を増やす**。

PO が要るのは：**スコープに新しいパスを足す・基準（`text`）を変える・条件を消す**。

**glob の広い／狭いは文字列では解けない。** `src/narrow/**` は `src/**` より狭いが、
機械に判定させると必ずどこかで取り違える。**間違えてよい方向は「厳しすぎる」側**なので、
いまの一覧に無い文字列が1つでも増えたら PO に上げる——意味としては狭くても、PO が見れば
1秒で通る話であって、緩い側に倒して事故るより安い。

### 決定72：承認のあとに基準が動いたら、その承認は使えない

`kobo.reopen` の `reverify`（＝中身を触らずマージ前ゲートを回し直す）は、
**承認まで行った実績があり、かつそのあと監査を無効にする改訂が無い**ときだけ通る。

改訂できるようにした以上、「承認まで行った」だけでは足りない——改訂で監査が無効になった
あとに `reverify` を通すと、**変わった基準を誰も見ていない**状態でマージされる。

## 得るもの・失うもの

- (+) **検証コマンドの書き間違いが、実装のやり直しを要求しなくなる**
- (+) 「何に対して監査したのか」に**版で**答えられる（`版 V の契約に対して時刻 T に監査した`）。
  凍結時代は「取り込み時のもの」としか言えず、しかも間違いが直せなかった
- (+) タスクを切り直す動機が減り、**経緯が1つの id にまとまる**（→ task-0081 と同じ狙い）
- (−) 状態機械に**後ろへ戻る道**が増えた（`approved/in-review/review-ready → implementing`・
  `auditing → planning`）。前へ飛ぶ道は増えていない——番頭は進められるが飛ばせない（決定62c）
- (−) 「緩める方向」の判定が保守的なので、**意味としては狭い訂正でも PO を通す**ことがある

## 影響

- `spec-daemon-core` §1.2（新設）に改訂の規則を書く
- `kobo.amend` を足す。`kobo.enqueue` / watcher の拒否メッセージは「新しいタスクを積め」から
  「`kobo.amend` を呼べ」へ
- SKILL `kobo-enqueue` / `kobo-onboarding` の「積んだ後に変えられない」を書き換える
