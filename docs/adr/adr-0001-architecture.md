# ADR-0001: Banto v3 のアーキテクチャ

> 2026-08-20。`docs/v3/requirements.md` から引いた。**過去の実装・過去の ADR は参照していない。**

## 前提として押さえた計測（2026-08-20 測り直し）

設計の一部がこの計測に乗っているので、先に置く。旧実装のトランスクリプトを外から
畳んだもの（LLM は呼んでいない）。

**母集団**：`~/.claude/projects` のうち、**2026-08-20 より前に始まったセッション**
919 本・43,169 ターン。v3 の作業で増えたセッションを除くための境界である。

```
キャッシュ読み  8,221,449,341  (98.5%)      ← キャッシュは効いていた
1ターンの文脈    p50 103,870  p90 524,552  p99 859,657  max 999,622
200k 超のターン  30.1%（12,990 / 43,169）
圧縮の発火        2 回
```

再現：`node packages/observer/dist/cli.js --transcripts --until 2026-08-20`

### 圧縮は「上限に当たったときだけ」発火する

| 系列 | 本数 | うち圧縮が発火 |
|---|---|---|
| 最大文脈 ≥ 990,000 | 2 | **2** |
| 最大文脈 < 990,000 | 917 | **0** |

200 ターン以上の長い系列 38 本のうち、**35 本は一度も文脈が下がらなかった**。
それらの最大文脈の中央値は **601,568**——**60万トークンを超えても、圧縮は動かない。**
動いたのは 1M の上限に触れた 2 本だけで、どちらも 999,0xx から 5.5〜5.7 万へ落ちている。

**何も失敗しないので、気づかれない。** この事実が決定7・決定8を直接規定している。
「増えている」は正常な会話でも起きるが、「**一度も下がらない**」は機構の故障を名指しする
（要件 F1 の不在の警報）。上限直前まで何も起きない以上、**圧縮が効いていることを
前提にした設計にはできない。**

### 前の版からの訂正（規則8）

この節の前の版は「1,059 セッション・88,711 ターン／キャッシュ読み 14,878,227,752（97.9%）／
p50 90,949・p90 465,712・p99 839,320／200k 超 25.4%／圧縮の発火 0 回」だった。2点直している。

1. **「ターン」の数えかたが違っていた。** 応答の streaming 中、SDK は完了した content block
   ごとに assistant メッセージを1通ずつ出し、どれも同じ累積 usage を載せる。前の版はその
   **行**を数えていたので、ターン数もトークン総量も約 1.8 倍に膨らみ、分位点は content block
   が多かったメッセージへ重みが寄っていた。いまは `message.id` 単位で畳んでいる
2. **圧縮は 0 回ではなく 2 回発火していた。** トランスクリプトに残る `compact_boundary` と、
   usage の下降から導いた発火が、系列まで完全に一致した

経緯は `docs/notes/2026-08-20-turn-count-discrepancy.md`。

> **母集団は動く。** 前の版の 1,059 セッションは 2026-08-20 の日中に測ったもので、
> 上の 919 本とも、いまの全件 1,108 本とも一致しない。**数字を比べる前に、必ず母集団の
> 定義を確かめること**——さもないと、コーパスが増えただけの差を実装の変化と読み違える。

## 決定

### 1. ランタイムは Claude Agent SDK 一本。抽象化しない

エージェントループはベンダ間で差がいちばん大きく、いちばん速く変わる。ここに境界を置くと、
差分を吸収するコードが増え続ける。**ループを差し替え可能にしない。**

会話も、Factory のサブエージェントも、同じランタイムの上で動く。

### 2. 移植可能な資産は4つだけと定義する

決定1 の代償を、資産の側で相殺する。

| 資産 | 形 |
|---|---|
| モジュール | **MCP サーバ**（他のクライアントからも使える） |
| 手順 | **SKILL.md** |
| 記録 | **自前の append-only イベントログ**（真実はここに1つ） |
| 画面 | **React コンポーネント** |

将来ランタイムを替えるとき、作り直すのは決定6 の Runner だけになる。

### 3. 会話の構造：Channel / Thread / base + 以降のメッセージ / Fork

要件 A1〜A3・G。

| 概念 | 対応 |
|---|---|
| Channel | プロジェクト（1リポジトリと、その worktree 群） |
| Thread | 会話。**base + 以降のメッセージ** を持つ |
| Fork | 返信ツリーのブランチ。**既定は base から切る** |

**分岐が安いのは、共有プレフィックスが小さいときだけである。** ブランチを「いまの続き」から切ると
ブランチも肥えたまま始まる。だから分岐点を、会話が今どこにいるかから切り離して **base** に固定する。

### 4. base は追記のみ

キャッシュは前方一致なので、base が**伸びる**分には既存のブランチのプレフィックスは1バイトも変わらない
——**ブランチのキャッシュは生きたまま**、新しいブランチだけが追記を見る。壊れるのは**書き換えたとき**だけ。

要件 R1〜R8 をそのまま実装契約とする。とくに：

- **R3** 追記できるのは「決まったこと」だけ。判定は「次のブランチがこれを知らないと困るか」の一問。
  要約による圧縮ではなく**種類による選別**なので安い
- **R5** 書き換えは許すが、そのときブランチは継承しない（＝新しい会話）。これで
  「壊すたびに全ブランチを再計算」が起きる経路が構造的に存在しなくなる
- **R7** プロジェクト恒久の事実は base ではなくリポジトリのファイルへ。
  **記憶ストアは作らない**——置きたかったものの大半はファイルに置くべきもので、
  専用ストアはリポジトリとの二重管理を生む

**R8 は警報ではなくゲートにする**（2026-08-21・レビュー指摘）。

R6 で追記の判断は AI に乗っているが、**誤りの向きが非対称である**——過小（追記しない）は
その枝が老いるだけで済む。過大（追記しすぎ）は base が肥え、**A4「分岐が安い」が
全ブランチに対して静かに壊れる。** 静かに壊れるものを警報で守ると、
「見えているのに誰も見なかった」に落ちる。だからゲートにする。

**ただし、自動で新しい会話へ移さない。** 閾値を超えたとき機構がするのは1つだけ：

> **追記を、理由を返して拒否する。**

R5（書き換え＝ブランチを継承しない）を選ぶのは人である。自動で会話を切り替えるのは
**回復できない操作を黙って行うこと**で、規則2 の「黙って別の経路へ落ちない」に正面から反する。
**拒否は「止まる」、切り替えは「別経路へ落ちる」。** 前者だけを機構がやる。
拒否と同時に、選択肢としての R5 を決定9 のキューに出す——肥大は滞留ではないので、
A7 の段0/1 を飛ばして扱ってよい。

**実装済み**（2026-08-21・`packages/core/src/base.ts`）。Phase 0 の完了条件に base サイズが
入っていなかったため、しばらく**文書にだけ在ってコードに無い**状態だった（規則8 の記録）。

**追記の経路を `appendBase` に1本化してある**——`log.append({ type: 'base.appended' })` を
直接呼ばせない。**ゲートは迂回できる場所に置くと迂回される。**

- 判定は追記**後**の大きさで行う。前で見ると、1回の巨大な追記が素通りする
- fork の継承分も数える（要件 R4）。数えないと fork のたびに上限が復活する
- 判断の id はスレッドごとに決まるので、何度拒否されても1つしか立たない
- 残量は `/api/state` に常時出す。**拒否されて初めて存在を知る、を避ける**
- 大きさは**文字数**。トークナイザは依存が1つ増える（規則10）ので代理を使い、
  返り値を `characters` と名乗らせて**代理であることを隠さない**
- 閾値 20,000 文字は**計測値ではなく出発点**（規則1）。実際の base が溜まったら測り直す

### 5. モジュール：ロジックは1つ・契約は MCP・境界はモジュールごとに選ぶ

要件 C1〜C12。

```
モジュール
  ├── core                    ドメインロジック。ここに1つだけ
  ├── ツールインターフェース    MCP サーバ（AI 向け）
  └── データ API               HTTP/WS（GUI 向け。各モジュールが自前で持つ）
```

```ts
export interface BantoModule {
  id: string
  isolation: "in-process" | "subprocess"   // 必須。既定値を持たない
  mcp: { inProcess: true } | { command: string; args?: string[] } | { url: string }
  api?: { url: string }              // GUI の接続先。任意
  gui?: { entry: string; views: CanvasView[] }
  skills?: string
  settings?: JSONSchema
  handles?: ("secrets")[]            // 宣言すると in-process を拒否される
  // tools は「相手の」ツール名（tools/list と突き合わせる）
  // usedBy は「自分の」ツール名（欠けたときに断るもの）。**別の名前空間**
  requires?: { module: string; tools: string[] }[]
  optional?: { module: string; tools: string[]; usedBy?: string[] }[]
}
```

- **ロジックは core に1つ。インターフェースはそこへの薄い委譲**（C8a）。以前は
  「1モジュール＝1プロセス」がこれを構造的に強制していたが、下記の理由で境界を緩めたため、
  **C8a は規約になった。** 破れたときの症状が「GUI にその機能が無い」と目に見えるので許容する
- **契約は MCP、境界はモジュールごとに選ぶ**（C8b）。`createSdkMcpServer` により
  MCP の契約のまま in-process で動かせるので、契約と境界は独立に選べる
- **`isolation` は既定値を持たない必須フィールド**（C8c）。既定値は「忘れられる」機構であり、
  「落ちてもホストが生きる」「鍵が AI 実行と同居しない」を静かに消す。秘匿情報を扱うと
  宣言したモジュールは `in-process` を拒否される。境界は台帳に常時表示する
- **インターフェースの形は共通化しない。** 縛るのは実装の単一性であって、インターフェースの形ではない
- **インターフェースにロジックを置かない**
- **最小実装はツールインターフェースだけ。** GUI は後付けでよい
- 人は GUI → データ API、AI は ツールインターフェース → core。**Banto は UI のデータを中継しない**
- 名前空間は MCP サーバ名がそのまま与える。Tool 名の変換層を作らない

**モジュール間呼び出し**：モジュールは**他のモジュールのツールインターフェースを
クライアントとして直接呼ぶ**。**Banto は経路に入らない**——経由させると単一障害点になり、
モジュールが Banto の稼働に依存する。最初の実例は **Repo → Vault**（git を実行するとき、
Repo が Vault に鍵の提示を頼む）。

**依存の宣言**：モジュールは `requires` / `optional` を宣言する（モジュール id ＋ 実際に呼ぶ
ツール名）。**宣言は自己申告なので、接続時に MCP の `tools/list` で実在を確かめる**
——Vault がツール名を変えたら、Repo は push のときではなく接続のときに落ちる。
必須が欠ければ起動せず何が足りないかを言い、任意が欠ければそれを使うツールだけが
理由つきで断る。循環は起動時に検出して止まる。

**`tools` と `usedBy` は別の名前空間である。** `tools` は相手のツール名で `tools/list` と
突き合わせるもの、`usedBy` は自分のツール名で欠けたときに断るものを指す。ここは
最初1つの配列に両方の意味を負わせていて、**3本目のモジュール（repo→vault）を書いた
ときに衝突して露見した**——vault の実ツール名を書くと push が断らず、断らせようと
自分のツール名を書くと `tools/list` との突き合わせが嘘になる。契約を先に決めて
中身を後にする進めかたが、狙いどおりに効いた例（教訓6）。解決するのは**モジュール起動時と
スレッドへの紐づけ時の2箇所だけ**で、実行中の追随はしない——常時追随する機構は、
それ自体が「黙って壊れる」候補になる。

**Repo が Channel の実体を提供する。** worktree は Repo が所有し、Factory は Repo に頼む
——決定10 のワークフローエンジンに git の知識を持たせない。


### 6. Runner：ベンダに触れる唯一の接点

```ts
interface Runner {
  query(input: {
    threadId: ThreadId
    queryId: QueryId            // 1回の問い合わせ。Factory の Run とは別物
    systemPrompt: string          // スレッド生存中は読み取り専用
    mcpServers: McpServerSpec[]   // そのスレッドに紐づくモジュールの分だけ
    skills: string[]
    model: ModelId                // スレッドに紐づく。変更＝新スレッド
    forkFrom?: { threadId: ThreadId; baseVersion: number }
    prompt: Content
  }): AsyncIterable<Event>
}
```

ランタイム固有の型・語彙をこの層の外に出さない。トークン規律を「気をつける」で担保せず、
**Runner の形が破れないようにする**——システムプロンプトは引数で、走行中は変えられない。
モデルはスレッドに紐づく（走行中に替えるとキャッシュがモデル単位で全損する）。

### 7. 状態は1つのイベントログ。導出できる値は保存しない

```
<data>/
  events/      append-only JSONL。真実はここだけ
  blobs/       添付・成果物（content-addressed）
  config.json  人が編集するもの
```

- スレッド一覧も Run の状態も、起動時にイベントを畳んでメモリに載せる。**写しを持たない**
- **どこまで読んだかを保存しない。** 起動のたびに 0 から読み直す
- 版印を持ち、**読めない版に当たったら止まる**

横断集約（要件 A5・A6）は後付けできないので、**状態遷移を一級のイベントとして記録する**：

```
thread.status      working | waiting-on-human | blocked | done
decision.requested / decision.resolved
query.step         ← 1回の問い合わせ。Factory の Run ではない
turn.usage         ← 決定8 の材料
base.appended
```

**項目の名前づけ**（2026-08-21。`run` の重なりを直したときに言語化した）。
ログは**イベントの型を跨いで読まれる**ので、名前が意味を決める：

1. **鍵になる項目は、名前だけで一意にする。** 結合や検索に使う項目は、型を見ずに
   読まれる——`queryId` / `sessionHandle` / `channelName` のように、
   **何の id か・何の名前かを名前に含める。** 素の `id` / `name` / `handle` は使わない
2. **同じ問いには同じ語を当てる。** 「どうなっているか」は `status` に統一する
   （スレッドも問い合わせも Factory の Run も）。値は別でよいが、**語が割れると
   `status` で絞ったときに片方だけが落ちる**
3. **値が1つしか無い項目を置かない**（規則3）。`step: 'query'` がそれで、
   情報を持たないまま名前だけを占めていた。**要るようになったら、そのとき足す**

**型の中に閉じた値は、この規則の対象外**である。イベントの型が分かれば意味も決まるため。
危ないのは、型を見ずに読まれるもの——それが 1 と 2 が言っていること。

### 8. 観測は外側に置く。警報は量と不在の2つ

> **観測は、観測される機構の外側に置く。** 中に置くと、機構が止まったとき観測も一緒に止まる。
>
> **任せてよいのは仕事であって、仕事が行われていることの確認ではない。**

- **測る主体は Banto Core。** エージェント自身に自分の文脈を診させない
- **材料は各ターンの `usage`**（`turn.usage` イベント）。イベントログの畳み込み。**LLM を呼ばない**
- **量の警報**：文脈サイズが閾値を超えた／base が肥えた。
  ただし **base だけは警報ではなくゲート**——超えたら追記を拒否する（決定4。理由もそこ）
- **不在の警報**：**文脈が一度も下がらないまま N ターン経過した**。
  「増えている」は正常な会話でも起きるが、「一度も下がらない」は故障を名指しする
- 圧縮そのものはランタイムに任せる。**監視は任せない**

先例：この計測は banto を起動せず、トランスクリプトを外から畳んで得た。
**外から測れたから、壊れていても測れた。**

### 9. 判断待ちは1つのキュー。発生ではなく滞留で鳴らす

要件 A5〜A7。出所（会話の質問／Factory の承認／決定8 の警報）が違っても、人にとっては同じ
「自分が見ないと進まないもの」。**3本の列を作れば見に行く先が3つになり、目的に逆行する。**

| 段 | 動作 | 条件 |
|---|---|---|
| 0 | 何もしない | オーバービューに状態として載るだけ |
| 1 | キューに立つ | 判断待ちが発生 |
| 2 | 端末へ push（Web Push） | 段1 が**解消しないまま滞留**／人が明示指定 |

**発生した瞬間には鳴らさない。** 画面を見ていればオーバービューで気づく。
目的は「人が思い出さなくてよい」であって「即座に反応させる」ではない。

### 10. Factory は小さな耐久ワークフロー

```
Run:  queued → running → review → merging → done | failed
```

- step handler は**冪等**。落ちたらその step から再開する。run log はイベントログの一部
- 実行はサブエージェント（ツールの allowlist 付き）
- **既定では人を待たない**（要件 B4）。待つ設定のとき、承認は決定9 のキューに出る
- 複数の依頼が同じ main を触るので、**順序づけと衝突の解決**を持つ（要件 B7）
- Factory は Channel に1つ

### 11. UI：Runtime だけ借りる。レイアウトと木は自前

> **この節は 2026-08-20（初日）の計画で、実装では一度も採用されなかった**
> ——書いたまま2日、直されずに残っていた（PO の質問で気づいた。規則8）。
> 実際に評価・採用したものは決定27を見よ：メッセージ列は assistant-ui ではなく
> shadcn/ui のチャット部品、状態管理ライブラリ（TanStack Query / Zustand）も
> 未採用（`useBantoState`/`useThreadSessions` の自前フックで足りている）。
> 表の他の行（PWA・ターミナル等）は Phase 4 の範囲外でまだ手を付けていない。

| 用途 | 採用（初日時点の計画。上の注記を見よ） |
|---|---|
| メッセージ列・ストリーミング・tool call 描画・添付 | ~~assistant-ui~~（`ExternalStoreRuntime` で決定7 のイベントログを真実として繋ぐ）——**不採用。決定27** |
| 基盤 | shadcn/ui + Radix + Tailwind |
| キャンバスのタブ・オーバービュー・スレッド木・レイアウト | **自前**（ui-kit） |
| ターミナル / DIFF / ファイル木 / Markdown | xterm.js / `@git-diff-view/react` / react-arborist / streamdown |
| 状態 | TanStack Query + Zustand |
| PWA・通知 | vite-plugin-pwa + Web Push |

**assistant-ui が引き取るのはメッセージ列まで。** タブ・オーバーフロー・モバイルヘッダ・
スレッド木・オーバービューは shell のレイアウトであり、自前で書く割合のほうが大きい。
「chat ライブラリに寄せる」と「自分で書く」を等価に見積もらない。

**不採用**：Vercel AI SDK の `useChat`（トランスポートも所有するため、Runner のイベントと二重管理になる）。

### 12. パッケージ構成

```
apps/
  web/        React PWA
  host/       Banto Core：HTTP + WS、Runner、モジュール解決、観測
packages/
  core/       ドメイン型、イベントログ、Channel/Thread/base/Fork
  runner/     Agent SDK 呼び出し（唯一のベンダ接点）
  module-kit/ モジュール作者向け（core + 2つのインターフェースの足回り）
  ui-kit/     React 共有部品
modules/
  repo/ shell/ fs/                    ← Phase 0/1
  env/ publish/ vault/ browser/ backlog/ worker/   ← Phase 3
```

### 13. 身元は統一しない

**GitHub の身元と Claude の身元を、1つの概念にまとめない。**

| | GitHub | Claude |
|---|---|---|
| 選ぶ軸 | **対象で決まる**（パターンマッチ） | **資源の残りで決まる**（述語と優先順） |
| 変わる理由 | 別のリポジトリを触った | **自分が使った**（時間とともに勝手に変わる） |
| 使う主体 | Repo モジュール | Banto Core（決定6 の Runner） |

まとめると `scope` の型が割れる。**これは決定1 で捨てたのと同じ誤り**——表面が似ているものを
1つの契約にすると、共通部分＝最小公約数しか表現できなくなる。

共通しているのは「資格情報は Vault が持ち、AI の文脈に出ない」だけで、それは要件 D3 に既にある。

- **GitHub** → Repo の中の割り当て表（`パターン → Vault の参照`）。Repo に閉じる
- **Claude** → 必要になったら Runner の引数が1つ増えるだけ。決定6 の
  「スレッドに紐づく・変更＝新スレッド」がそのまま効く。**いまは作らない**

**走行中に切り替えない。** プロンプトキャッシュはアカウント単位なので、切り替えた瞬間に会話全体が
再計算になる。実測でトークンの 98.5% はキャッシュ読みなので、深いところで切り替えると
1ターンの費用が一桁上がる。前の実装は走行中に差し替えていた（`swapHarness`）——同じ形にしない。

### 14. プラグインカーネル（Cordis）は**いまは**採用しない

DeepSeek Harness の基盤である Cordis（Shigma 作・Koishi のカーネル）を、
(a) コアだけに使う (b) モジュールも含めて使う、の2案で評価して**どちらも採らない**。

- Cordis が解くのは「多数の第三者が TypeScript で書いたプラグインを1つのランタイムに
  載せる」問題である（Koishi と DSH の状況）。**banto の第三者拡張は MCP 経由・
  言語非依存なので、同じ問題ではない**
- コアはサブシステム7つ・著者1人・ホットリロード不要で、DI とライフサイクル管理が
  解く問題を持っていない
- 唯一欲しかった「可逆な effect」は**標準ライブラリにある**（`AsyncDisposableStack` /
  `await using`。Node 20+ / TS 5.2+）
- (b) の利点（IPC 無し・1プロセス・薄い雛形）は、`createSdkMcpServer` により
  **MCP の契約のまま**得られる。Cordis を入れる動機が残らない
- (a) は不安定な中間点である。コアが Cordis アプリになると、新しい能力を足す最短経路が
  「Cordis プラグインにする」になり、決めないまま (b) へ滑る

**借りた考え方**：可逆な effect スコープ（標準ライブラリで実装）、イベントの配り方の
分類（`emit` / `waterfall` / `parallel` / `serial` — 必要になったものだけ実装）。

**「採らない」を「いまは採らない」に直した**（2026-08-21・PO 判断）。

上の理由を読み直すと、**ほとんどが「まだその問題を持っていない」という時期の話**で、
「Cordis が悪い」ではなかった。実際、Phase 2 で前提が1つ崩れた——上に
「banto の第三者拡張は MCP 経由・言語非依存なので、同じ問題ではない」と書いてあるが、
**Factory と worker は MCP に乗らなかった**（決定6 が Runner を中核に縛るため）。
結果として、拡張の機構が**MCP と素の TypeScript の口の2つ**に割れていた。

**その割れは、Cordis ではなく決定17 で閉じる**——中核にも MCP の面を付ければ口は1つになり、
既存の7モジュールを1つも触らずに済む。Python も**コネクター無しのまま**でいられる
（`hello-py` は 80 行・`json` と `sys` だけ。Cordis 化すると TS のコネクターが要る）。

**次のどれかが起きたら、Cordis を採る**：

1. **中核の資源を要するものが 3〜4 個を超えた**（2026-08-21 時点では Factory＝worker の1概念）
2. **第三者が banto の中核に触るプラグインを書く**ことが要件に入った
3. **ホットリロードが要件に入った**

**いま乗り換えないことで高くつく道理は無い。** モジュールの契約は MCP なので、
将来 Cordis を採っても MCP プラグインとして残せる。

DSH の Trajectory view（append-only なセッションログから resume / fork / search / replay）が
決定3・決定7 と独立に同じ結論へ到達している点は、設計の裏取りとして記録しておく。

### 15. Phase と完了条件

**完了条件は「要件を満たす」ではなく「計測が実際に走り、数値を返す」。**
この設計で担保されたのは設計であって、実装で再現される保証ではない。

| Phase | 完了条件 |
|---|---|
| **0** | 決定8 の観測が実際に走り、**文脈サイズと圧縮の発火回数を数値で返す**。判断待ちが1画面に出る |
| **1** | モジュール契約が確定し、**その契約で3つ書けた**。ツールを足してもキャッシュが落ちないことを数値で確認 |
| **2** | 3依頼を同時に投げて3つとも main に入る。落として再起動しても続く |
| **3** | 残りの標準モジュール6つ |
| **4** | 旧 Banto を止める |

**Phase 0/1 でモジュールを増やさない。** 契約は先に決め、中身は後。
Factory の一本の体験を磨き切るまで、生態系を作り始めない。

**F4 は恒久要件ではなく、Phase 2 の検証項目である**（2026-08-21・レビュー指摘）。

「平行数を上げても費用が線形以上に増えない」を守るべき要件として読むと、
**線形を超えた時点で要件違反と誤って判定する。** 枝が分かれて長く伸びれば
共有プレフィックスの割合は減るので、**いずれ線形に近づくのは機構の故障ではなく自然な挙動**である。

Phase 2 で測るのは **「どこで曲がるか」**であって、曲がらないことではない。
曲がる点が分かれば、そこが並行数の上限（仕様 §5.6）の根拠になる。

### 16. 環境は口で定義し、実装は差し替える。公開は環境から割る

要件 D1・D2・C5。詳しい形は `docs/specs/factory-environment-publish.md`。
決定5（モジュール契約）と決定10（Factory）を、Phase 2 に入れる形まで具体化したもの。

```
capability "environment"          capability "publish"
  create(spec)      → handle        publish(host:port, name?) → URL
  exec(handle, cmd) → 出力          unpublish(name)
  address(handle, port) → host:port
  destroy(handle)
```

**環境の実装を banto が選ばない。** コンテナでも VM でも Proxmox でも AWS でもよく、
モジュールで足せて、リポジトリが自前のものを持ち込める。これは名前のついた形である
（provider / driver モデル。Kubernetes の CRI、Terraform の provider、DevPod の provider）。

**公開を環境から割る理由**：全部を環境に入れると N×M（環境の種類 × 公開手段）になり、
process にも docker にも Proxmox にも cloudflared 対応を書くことになる。
割る位置は「**それは環境にしか答えられないか**」で決まる。`address` は環境にしか
答えられず、`publish` は答えられない。**N＋M になり、新しい公開手段を足すのに
環境実装を1つも触らない。** 要件 C5 が最初から公開を別モジュールに割っていたのは、
この形だったと解釈する。

**規則を1本置く**：**環境は、`address` が返す宛先が banto ホストから届くことを保証する。**
届かないならトンネルを張るのは環境の側の仕事。これが無いと公開モジュールが
「Proxmox のときはこう」と環境の事情を知る羽目になり、結局 N×M に戻る。
代償は環境の種類の数（N）だけで済む——**払う場所を選ぶ判断である。**

**依存は役割（capability）で書けるようにする。** いまの契約は `{ module: 'env-docker' }` と
実装を名指しする形で、差し替え可能にしたいのに契約が差し替えを許していない。
**役割の実体はツール名の集合**なので、既存の `tools/list` 突き合わせ（決定5）が
そのまま「この実装は environment を名乗ってよいか」の実測になる（規則1）。
**候補が1つでも自動で選ばない**——黙って選ばれた既定は忘れられる（C8c と同じ理由）。

**devcontainer.json は契約にしない**（仕様を実読して確認）。`image` /
`build.dockerfile` / `dockerComposeFile` のいずれかが必須で、非コンテナ環境を
対象にする手段が無い。**DevPod ですら越えていない**——無ければ自動生成してでも
用意するので、AWS も Proxmox も「Docker を動かす場所」を作っているだけである。
devcontainer.json は**コンテナ系 provider の入力形式**として扱う。

**リポジトリのスクリプトが実装になれる。** `env-script` という汎用アダプタを1つ持ち、
各動詞を宣言されたスクリプトへ委譲する（先例：DevPod の `exec:`、CNB buildpack の
`bin/build`、CNI プラグイン）。**4本のシェルスクリプトで満たせない口は大きすぎる口**なので、
これは拡張であると同時に**口の検査**である。ここで安全上2つ決めた：

- **隔離を作るコードは、その隔離の中では走れない。** `env-create` は banto ホストの
  権限で走るので、**リポジトリの中身だけでは有効化されない。** 運用者が banto 側の
  設定で明示的に許す
- **AI はそのスクリプトを書き換えられる**（＝自分を閉じ込める箱の作り手を書き換えられる）。
  **変更は判断待ちに立て、承認まで前の版を使う。** 決定9 の既存のキューを使い、新機構を作らない

**Factory 側で決めたこと**（詳細は仕様 §5）：

- **Run は Thread を1つ持つ。** 依頼は base に入る（R3 の表にそのまま書いてある）。
  会話の器を作り直さないので、セッション再開が B5 にそのまま効く
- **再開の判定にフラグを保存しない。現物を見る**（規則3）。worktree が在るか、
  main がそのブランチを含むか。git を使う段はほぼ全部が観測可能になる。
  **唯一 `test` だけは導出できない**ので記録するが、**commit の sha で鍵をつけて
  自己無効化させる**——古い結果が生き残る経路を作らない
- **順序づけは merge queue**（bors / GitHub merge queue / Zuul。教訓18 の名前つきの答え）。
  implement と test は並行、merge だけ直列。衝突したら main の先端に載せ直して
  **test から**やり直す（implement は済んでいる）。通らなければ failed にして
  **列を止めない**——要件 B の受け入れが「1つ失敗させても他の2つは進む」なので
- **環境は Run ごと**。B3 が並行を要求するので、共有すると Run が互いを汚す。
  費用は最初の provider が `process` なのでほぼ掛からない
- **失敗した Run の環境は畳まない**（人が中を見る）。畳む期限は設定で持ち、
  **公開も同じ期限に乗せる**——タイマーを2つ持たない
- **`status` は口に入れた**（2026-08-21）。当初は保留したが、`env-script` を書いた時点で
  足りないことが露見した——Factory の再開判定が「環境がまだ在るか」を外から聞けず、
  `exec` で代用すると「環境が無い」と「コマンドが落ちた」が混ざる。値は
  `ready` / `gone` の2つだけ。**`start` / `stop` は足さない**（中間状態を作ると呼び込む）
- **リポジトリのスクリプトは、承認が無ければ「前の版で走る」のではなく断る**
  （2026-08-21）。古い版を走らせるのは、リポジトリが言うことと banto がやることを
  黙ってずらすこと——規則2 に反する。**断るほうが安全側で、しかも初回と変更後を
  同じ道で扱える**（初回は「前の版」が存在しない）。R8 のゲートと同じ判断である
- **テストの走らせ方はリポジトリが持つ**（`script/test`）。Factory は組み立てない

**実装順**：capability 依存 → `process` ＋ `none` → `env-script` → `docker`。
**安全上の判断（上記2点）を最初の一歩に載せない**ので Phase 2 が止まらない。そして
**1つ目の実装では口の正しさは分からない。2つ目を足したときに分かる**ので、
1つ目は一番安いものにして早く2つ目へ行く。

**`run` の語が2つの意味を持っていた。直した**（2026-08-21・版2）。
`run.step` / `runId` は **Runner の1回の `query()`** を指していたが、Factory の Run は
別物である。**これは `Dependency.tools` が2つの名前空間を背負っていた失敗と同じ形**
（教訓6）。あのときは3本目のモジュールを書くまで露見しなかったが、今度は書く前に
気づいている。**Runner 側を `query.step` / `queryId` に改め、`run` / `runId` を Factory に空けた。**
`LOG_VERSION` を 2 に上げ、**1 を読む道を書いた**（`packages/core/src/migrate.ts`）。
実データ（版1・26件、うち16件が `runId` 持ち）で読み戻しを確認済み。

**同じ形の問題を洗い直し、見つかった分をすべて同じ移行に畳んだ**（4件）。
**版2 がまだ1行も書かれていないうちだけ、これが1回の移行で済む**——書かれた後は
2→3 が要る。だから「後で直す」と書かずに、その場で直した。

- **`thread.session.handle` → `sessionHandle`。** 環境モジュールも不透明な handle を
  返すので、鍵の名前が2つの意味を持つところだった
- **`run.step.state` → `status`。** 「どうなっているか」に2つの語を当てていた
  （スレッドは `status`、問い合わせは `state`）。Factory が3つ目を足す
- **`channel.created.name` → `channelName`。** 表示名であると同時に**引くための名前**
- **`run.step.step` を削除。** 常に `'query'` で情報を持たなかった（規則3）

この作業から出てきた規則を、決定7 に**名前づけ**として書いた。次に同じことをしないため
——**規則を書かずに直すと、直したこと自体が忘れられる。**

### 17. 中核も MCP の面を持つ。口は1つ

要件 C13。**2026-08-21 の PO 判断**で、決定14 の代わりに採った道。

**きっかけ**：「Factory の面はモジュールの I/F 経由か」という問いに、答えが「いいえ」だった。
調べると Factory と worker だけが MCP に乗らず、**拡張の機構が2つに割れていた。**
さらに、決定16 で作った役割（capability）の機構に**本物の利用者がいなかった**
——Factory は素の TypeScript の口に実体を直接注入していて、
「実装は差し替えられる」は試験の中でしか成り立っていなかった。

```
worker    ← Runner を包む、中核同梱のモジュール（決定6 は守られる：Runner に触るのは中だけ）
ledger    ← イベントログの面。**型の決まった操作だけ**（任意の追記は開けない）
factory   ← worker / environment / repo を役割で頼む、ただのモジュール
```

- **中核とモジュールの違いは、口ではなく出荷元だけになる。** 中核同梱のものは
  中核の資源を内側で握ってよいが、**外から見える口は他のモジュールと同じ**
- **決定6 は守られる。** Runner に触るのは `worker` の中だけで、外へはツールしか出ない
- **決定7 は守られる。** `ledger` が出すのは型の決まった操作だけ。「何でも追記できる」を
  開くと、真実が1箇所であることが壊れる
- **モジュール間の呼び出しは型つきで往復する**（2026-08-21 に訂正）。MCP の
  `outputSchema` / `structuredContent` を使う。**型は宣言ではなく強制**で、
  合わないものを返すと SDK が `Output validation error` で断る——
  「気をつける」ではなく**契約の形で破れないようにする**が、ここでも成り立つ。

  > **訂正の記録（規則8）。** 最初「MCP はテキストしか返せないので、口を跨ぐと
  > 呼び手が文字列を解く」と書き、実装もそうした（`yes` / `no` の判定、`JSON.parse`）。
  > **確かめる前に決めていた**（規則1）。PO の指摘で実物を見たら、仕様にも SDK にも
  > 最初から在った。**C13 の代償として数えていたものは、存在しなかった。**
- **既存の7モジュールは1行も変えない。** MCP の契約はそのまま

**これは前の実装の4層を、v3 の語で言い直したものでもある**——番頭＝会話、
Kobo＝Factory、**職人＝worker**。前の実装で職人は memoryless な worker として
4層の1つだったが、v3 では Factory のコンストラクタ引数に格下げされていた。
名前と格を戻す（`worker`。前の実装の独自語は持ち込まない・規則11）。

**決着（2026-08-21）**：**worker はセッションを再開する**（`resumeConversation` の既定は
そのまま）。前の実装は memoryless だったので、**設計の意図は反転している**（規則8 の記録）。
PO の裁定。**測ってから決めた**——`modules/worker/src/memory.measure.test.ts`
（`BANTO_E2E=1` で再現できる）。

分かれる場面は1つしかない。`implement` は `!hasCommits` のときだけ走るので、
**落ちて同じ Thread でもう一度走るとき**（要件 B5）だけである。そこを
`maxTurns` の打ち切りで作り、2回目だけを各4回測った：

| | 再開 | memoryless |
|---|---|---|
| 仕事が揃っていた | 4/4 | 4/4 |
| ターン数 | 3 | 6 |
| キャッシュ読み | 66,760 | 116,507 |
| 文脈の最大 | 21,230 | 20,414 |

**費用は memoryless が約1.6倍**（memoryless は「どこまでやったか」を毎回読み直す）。
**品質は同じ。文脈も膨らまない**（system prompt とツール定義が支配的で、
落ちたセッションの履歴は誤差）。

**前の実装が memoryless にした理由は、v3 では構造で解けている**——Run ごとに
専用の Thread を持つので、worker のセッションが会話の文脈を汚すことはない。

**「再開したセッションは自己申告である」という懸念は、上の層が既に消している。**
済んだかどうかを判定するのは worker ではなく `stage.ts` で、そこは commit と
sha 付きのテスト結果という現物を見る（規則1）。セッションが食い違っても、
機械は `implement` をやり直すだけである。

**残る難点（別で塞ぐ）**：再開を許すと、その Thread での雑談が
**R8 のゲートを通らない第二の入力経路**になる。ゲートは base の文字数しか
測らないので、要件 F1 から見える経路が1つ増えている。既定は変えずに塞げる。

**測っていないもの**（どちらも再開に不利な側なので、覆すならここから）：
**ツール実行の途中で落ちた場合**（打ち切りはターンの切れ目で止まる綺麗な落ち方）と、
**長く迷走した失敗セッションを担いだ場合**（この題材では、打ち切りを遅らせると
1回目で仕事が終わってしまい作れなかった）。

### 決定18. 判断は選択肢を出せる。ただし答えを選択肢に閉じない（2026-08-21）

**出所**：PO の指示（2026-08-21）——「Ledger は選択肢から選べるようにする＋
どの選択肢も選べない場合の対応もできる（LLM 相手なら自分で書き込むなど）」。

`decision.requested` に `options`（`{ id, label, detail? }` の並び）を、
`decision.resolved` に `optionId`（選ばなければ `null`）を足した。**ログ版 3。**

- **id で判定する。** 表示名は変わりうるが、答えを読む側が見るのは id（決定7 と同じ理由）。
  Factory の確認は `approve` / `reject` の2つを出す
- **選択肢が在っても、自由文で答えられる。** どれも選べないのは異常ではなく、
  **立てた側が答えの形を全部は知らない**という普通のことである。画面も口も、そこを塞がない
- **知らない id は断る。** 出していない id を「たぶんこれ」と読ませない（規則2）
- **「答えが出た」を「進んでよい」と読まない。** Factory の確認は、以前は
  *何か答えが在れば*マージへ進んでいた。いまは `optionId === 'approve'` のときだけ進み、
  自由文の答えは**まだ答えではない**ものとして聞き直す。
  却下（`reject`）は `failed` ではなく `rejected` で終える——
  **直せば通るもの**と**直しても通らないもの**を同じ語にしない
- **答えは、その判断が属するスレッドの会話に返る。** v2 の取次は「押されたときに効く口」
  （`InboxEffect`）という汎用の機構を持っていたが、v3 は作らない。
  答えを `message.recorded` として会話に置けば、**エージェントは次のターンでそれを読み、
  人も読み返せる**（要件 A8）。**新しい機構を1つも増やさずに、答えが効く**

**測った**：本物のブラウザで、選択肢を押す→列から消える→**会話に答えが着く**までを
`apps/host/src/ui-smoke.test.ts` が通す。この試験を足した時点で、
**会話の年表が `decision.*` を知らずに「未対応のイベント」を出していた**のが見つかった。

### 決定19. モジュールの画面は、AI が URI で指す（2026-08-21）

**出所**：PO の指示（2026-08-21）——「モジュールが持ち込む GUI は、AI が認識して
ユーザに動的に提示できる必要があります。たとえば AI がファイルを更新して、
そのファイルをファイルブラウザで開いて見せる」。要件 C14。

**機構には名前があった**（規則12）。**MCP の `resource_link` と `resources`** で、
しかも使っている SDK に**すでに入っている**——実測した（`@modelcontextprotocol/sdk` 1.30.0）：

```
tool 結果: [{"type":"text","text":"更新しました"},
            {"type":"resource_link","uri":"banto://fs/file?path=README.md",
             "mimeType":"text/markdown"}]
resources/list → banto://fs/file?path=README.md
resources/read → 中身が返る
```

**5分で通り過ぎるべきところだった。** 自分で「画面を開く」プロトコルを設計しかけたが、
それは既に解かれている問題である。

**決めたこと**：

- **AI は画面の名前を知らない。URI を指すだけ。** 道具の結果に `resource_link` を混ぜる
- **モジュールは自分の URI 空間を持つ**（`resources/list` / `read`・URI テンプレート）
- **URI → どの面で開くか、はホストが持つ。** モジュールは URI 形と mimeType を宣言する
- **人も同じ URI を開ける**（要件 C2：AI からも人からも同じもの）

**「開け」ではなく「指す」にした理由**は、3つとも既存の決めごとから出ている：

1. **真実が2つにならない**（規則3）。AI が画面を直接動かせると、
   「AI が開いたつもりの面」と「実際に開いている面」が別々に存在する
2. **勝手に画面が飛ばない。** 指しは会話に並ぶだけで、開くのは人が決める
   ——要件 A7「発生では鳴らさない。滞留で鳴る」と同じ考え
3. **読み返せる。** 指しは道具の結果としてログに載るので、要件 A8 が**何も足さずに**効く

3つ目は今日2回使った形と同じである——判断の答えは会話に返し（決定18）、
公開の URL は確認の文面に書いた（仕様 §5.2）。**新しい置き場を作らず、
既にあるものの上に置くと、読み返しも観測もそのまま効く。**

**実装した**（2026-08-21・Phase 2.5 の前半）。**契約は配り方を名指ししない**ので、
危ない側（他人の JS を画面で走らせる）を選ばずに先へ進めた：

| 誰が | 何を |
|---|---|
| モジュール | 自分の URI 空間（`banto://<id>/…`）を `resources` として持つ。道具は**作ったものの URI を返す** |
| AI | `show(uri)` で**指す**。画面の名前は知らない |
| ホスト | URI の**先頭で持ち主を決めて**読みに行く（`GET /api/resource`）。表を別に持たない（規則3） |
| 画面 | 指しを会話に並べる。**押されたら**中身を読みに行く |

**モジュールは画面を1つも持ち込まなくても、画面に出せる。** 標準の mimeType で
返せばホスト側の面が描くので、C9（最小実装はツールだけ）と C1 が両立する。
自前の面は**必要になったときの上積み**であって、入場券ではない。

**測って2つ分かった**（規則1）：

1. **`resource_link` は Agent SDK が潰す。** `[Resource link: name] uri` という
   テキストになり、`PostToolUse` フックで受けても同じだった。**それを解くのは
   「口を跨ぐ代償として文字列を解く」のやり直し**なので採らない。
   一方 `structuredContent` は潰れずに届く——だから**指すことを AI の明示的な
   道具呼び出しにした**。要件の言葉（「AI が認識して提示できる」）とも合う
2. **契約は道具の説明だけでは伝わらない。** 何も言わないと、モデルは
   `fs` モジュールに `write` があるのに**組み込みの `Write`** で
   `/home/ubuntu/note.md` を書こうとして権限で止まった。**どちらを使うかは方針**なので、
   ホストの system prompt に「mcp__ の道具を使う」「見せたいものは指す」を明記した。
   **伝わらないなら契約の側を直す**——モデルを責めても直らない

### 決定20. 画面の境界は、`isolation` と同じ2択にする（2026-08-21）

**出所**：PO の判断（2026-08-21）。「画面の実体をどう配るか」の答え。

> **新しい軸を作らない。** 「そのモジュールを自分のプロセスの中で走らせてよいか」と
> 「そのモジュールの画面を自分のページの中で走らせてよいか」は、同じ問いである。

| | プロセス | 画面 |
|---|---|---|
| 内側 | `in-process` | `in-page` |
| 外側 | `subprocess` | `sandboxed`（iframe） |

**`gui.kind` は既定値を持たない**（C8c と同じ理由）。既定値は「忘れられる」機構で、
ここで忘れられると**他人の JavaScript がページの権限で走る**
——合言葉の cookie も、他のモジュールの画面も触れてしまう。

**機械で押さえる分**（要件 C8c の「判定できる分は機械で押さえる」を画面にも）：

- `isolation: 'subprocess'` のモジュールは `in-page` を名乗れない。
  **プロセスで信用していないものを、画面で信用しない**
- `handles: ['secrets']` のモジュールも `in-page` を名乗れない
- **自分の URI 空間の外は開けない**（`banto://<自分の id>/` の下だけ）。
  名乗れると、他のモジュールが持っているものを横取りできる

**第三者は方針ではなく構造で `in-page` から外れる。** `in-page` の実体は
banto の束ね（`apps/web/src/views/registry.tsx`）に在るものだけなので、
束ねに入っていないモジュールは名乗っても実体が無い。

**実装した前半**（2026-08-21）：`fs` が `in-page` の面を持ち込み、
AI が指したファイルがその面で描かれるところまで、本物のブラウザで測った。
**割り当ては台帳から導く**（`GET /api/views`）ので、画面側は表を持たない（規則3）。

**後半も書いた**（2026-08-21）。**`sandboxed` の実行**：

- ホストが `GET /api/modules/<id>/view` で**器を配る**。モジュールの JS は
  **HTML に埋め込む**——`allow-same-origin` を渡していない iframe は生成元が
  不透明なので、別ファイルを取りに行けない。埋めれば取りに行く必要が無い
- iframe は **`sandbox="allow-scripts"` だけ**。cookie も DOM もオリジンも届かない。
  **CSP も併せて付ける**——安全は1枚では持たない
- **中身は親が押し込む**（`postMessage`）。取りに行く手段が無いので、
  **渡したものしか見えない**——制約への妥協ではなく、性質そのものである
- 高さは向こうから言ってくるが、**鵜呑みにしない**（上限を置く）

**要件 C6 の実物は `hello-py`。** subprocess で TypeScript でもないので
規則上 `in-page` を名乗れず、`sandboxed` で走る——**第三者とまったく同じ立場**である。
Python が自分の URI 空間（`banto://hello-py/greeting/{name}`）を持ち、
ホストが MCP 越しに読み、モジュール自身の面が描く。本物のブラウザで測った。

**閉じ込めを、閉じ込められた側から見せている**——面が「banto の cookie は
見えない（触ると SecurityError）」と自分で表示する。安全は主張ではなく、観測できる。

**繋いだモジュールを閉じる道が無い**（規則8 の記録）。ホストは起動時に
subprocess のモジュールへ繋ぐが、止めるときに切らない。プロセスが終われば
一緒に終わるので実害は出ていないが、**畳む手順が無いことは書いておく**。

**決着**：決定20 を見よ。

同じトークンを引く——引かない面は、そこだけ別の製品に見える。

## 判断した：Managed Agents は使わない（2026-08-20）

**理由は設計ではなく前提条件。Managed Agents は Claude API の課金対象で、
banto はそこに課金しない。**

出所は2つ：

- Managed Agents の要件——「To get started, you need: **1. A Claude API key** …
  3. Access to Claude Managed Agents (**enabled by default for all API accounts**)」
- Anthropic ヘルプセンター——「A paid Claude subscription enhances your chat experience
  but **doesn't include access to the Claude API or Console**」

Claude のサブスクからは到達できない。**一方、決定1 の Claude Agent SDK は
サブスクで動く**（Phase 0 で実際に動かして確認済み）。この非対称が、
決定1「ランタイムは Agent SDK 一本」を裏から支えている。

**したがって決定10 は自前のまま。** Factory の耐久ワークフローは banto が持つ
——ただし教訓18 のとおり、これには **durable execution** という名前がある。
自分で考えるのは配分と粒度だけで、機構は既知の答えに乗る。

**覆すとき**：API アカウントを持つことになったら、この判断は変わりうる。そのときの
検証の題と手順は `docs/notes/2026-08-20-managed-agents-self-hosted.md` にそのまま
走らせられる形で残してある（下調べは済んでいて、決め手は
「self_hosted で grader が採点対象をどう見るか」の1点だけ）。以下は当時の検討の記録。

- 検証の題は1点だった：**`self_hosted` 環境で Outcomes（rubric で採点→修正→再採点）が
  決定10 の受け入れを置き換えられるか**
- Banto はローカルの git リポジトリで作業するので `self_hosted` 一択。この判断は変わらない
  （下の下調べのあとも）。**ただし前提は2026-08-20 に当たり直した**
  （`docs/notes/2026-08-20-managed-agents-self-hosted.md`）：
  - Memory Stores は**対応済みになった**（ADR の「未対応」は古い）。ただし banto は
    記憶ストアを作らないと決めている（要件 R7）ので、使わない
  - 環境変数資格情報は**いまも未対応**
  - **`file` と `github_repository` の resource は 400 で拒否される**（ADR に書いていなかった）。
    banto の worker はローカルの作業ツリーの上で動くので、mount してもらう必要が無い
  - 残るのは Outcomes / threads / Deployments / Skills
- 線が引けるなら **会話＝Agent SDK ／ Factory＝Managed Agents**。
  ロックインの単位が分かれ、低レイテンシの会話と投げっぱなしの自律作業に、それぞれ合う

### 決定22. GUI を作り直す。サイドバー＋会話パネル＋層で重なる作業パネル（2026-08-22）

**出所**：PO の指示（2026-08-22）。「いまの GUI は全部一度捨てて、`13-tsuzukima-kai.html`
（v2 の意匠見本、複数案を統合した最終案）の UX で作ってほしい。ただし部品は自作しすぎず、
定評あるライブラリを積極的に使う。用語は見本のものをそのまま持ち込まず、初見のエンジニアが
分かる一般名にする」。

**決定21（意匠トークンの一本化）は仕組みとして正しかったが、値が違う家だった。**
決定21は v2 の washi（和紙）の値を引いていたが、PO が指したのは別の意匠見本
（`ideal.css`、和紙でも符牒でもない「第三の家」）だった。**仕組み**（`theme/tokens.css`
1枚から Tailwind へ橋渡しする構造）はそのまま活かし、**値**だけを見本のものに差し替えた。

#### 構えを変えた

前：会話は「開いた分だけ横に並ぶ列」（`apps/web/src/App.tsx` の `MAX_OPEN=3`）。
**列は本質的にスケールしない**——4本目を開こうとすると、いちばん古いものを黙って閉じていた。

後：**サイドバー＋層で重なる会話パネル。**

- **サイドバー**：受信箱（判断待ちの件数）・プロジェクト（頭文字＋通知の点）・
  開いているもの（点、状態で色分け）・履歴／設定／明暗
- **会話パネル**：1本を開く。フォークを開くと、その会話に**入れ替わる**
  （開いた元は消えない——頭の「戻る」でいつでも戻れる。同時に2本の会話パネルを
  横へ並べて重ねる見た目は、**今回は作っていない**——実際に作ったのは、層で重なるのは
  「作業パネルが開いたときの会話パネル」だけである。プロトタイプの絵が示す
  「フォークが元の上に紙で重なる」見た目そのものは、まだ無い。作るなら別途、
  という位置づけで正直に書いておく）
- **作業パネル**：モジュールの GUI・決まったこと（base）は、会話パネルの右側に
  さらに層で重ねて全幅で開く。開くと会話パネルは「話しかけるための帯」に縮む
  （`react-resizable-panels` で幅を可変にした）
- **判断待ちは常設欄を持たない**（要件 A6・E10）。会話の最後尾にそのまま出る
  ——それが最新の発言なら、放っておいても一番下にある。遡ったときだけ、
  下端の浮き玉（`JumpToBottom`）が朱色に変わって件数を言う（要件 A7 と同じ「滞留」の考え）
- **受信箱・履歴・設定はダイアログ**（Radix Dialog）。常設のタブではなく、
  押したときだけ被さる

#### 用語を見本から一般名に置き換えた（規則11）

見本は「幹・枝・面・器・レール・続き間・抱えているもの・畳んで回収」という独自の言葉を
使っていたが、**これは見本用の言葉であって banto の用語ではない**。CLAUDE.md 自身が
「前の実装は独自の日本語を内部用語に多用して失敗した」と書いている、まさにその失敗の形。
PO の指示で、初見のエンジニアが読んで分かる一般名に置き換えた：

| 見本の言葉 | banto での呼び名 | 理由 |
|---|---|---|
| 幹 | （呼ばない。ただのスレッド） | v3 は元々 `thread`/`fork` の語彙を持つ（`ThreadSummary`・`thread.forked`） |
| 枝 | フォーク | 同上 |
| 面 | 作業パネル | VSCode 等で誰でも知っている語 |
| レール | サイドバー | 最も一般的な語 |
| 抱えているもの | 開いているもの | そのままの意味 |
| あなたの番／askBlock | 判断待ち | 既存の要件文言（A6）と揃える |
| 器（vessel） | （今回は作らない） | 下記バックログ |

#### 定評あるライブラリを積極的に使った

手組みを避け、Radix（既存の Select/Tabs/ScrollArea に続けて）と
`react-resizable-panels` を追加した：

| 用途 | ライブラリ | 手組みだったら要ったもの |
|---|---|---|
| 受信箱・履歴・設定のダイアログ | `@radix-ui/react-dialog` | フォーカストラップ・Escape・スクロールロック・背景クリック |
| サイドバーのホバー札 | `@radix-ui/react-tooltip` | キーボードでも出せる遅延ホバー |
| 「開いているもの」の一覧 | `@radix-ui/react-popover` | 外側クリックで閉じる判定 |
| 会話パネルの帯の幅をつまんで変える | `react-resizable-panels` | pointerdown/move/up のドラッグ処理 |

**動き（enter/exit のフェード・スライド）は新しい依存を足さなかった**——Tailwind v4
（`@tailwindcss/vite`、JS config 無し）は `@theme` の `--animate-*` と `@keyframes` を
ネイティブに持っており、JS プラグイン（`tailwindcss-animate` 等）を足す理由が無かった
（規則10）。

#### v3 の実データに無いものは作らなかった（規則2・8）

見本は見本用のデータ（架空のプロジェクト・記憶・ADR 草案・職人一覧）を持っていたが、
**v3 の実データに対応が無いものは作文しなかった**：

- **フォークを畳んで幹に回収（結論つき）**：`merge` の API が無い。フォークは
  「閉じて元へ戻る」だけができる
- **器（tool の戻り値を構造化したカード）**：host は tool 呼び出しをイベント化していない。
  唯一データがある `reference.recorded`（AI が指したもの）だけ「作業パネルを開くカード」

### 決定24. フォークを閉じて親に畳む機構を作る（2026-08-22）

**出所**：PO の指摘（2026-08-22）。「フォークが増えすぎてわけわからないので、
たためるようにしてほしい」。決定22のバックログに記録していた「フォークをマージして

**畳むのは「決まったこと」（`ownBase`）だけ**。会話の全文を要約したり、新たに AI を

そのまま残る。「開いているもの」の一覧から外れるだけで、技術的には再開できる——ただし
畳むボタンは一度使うと出なくなるので、通常の操作ではもう一度畳めない（再探索したい

requirements.md のバックログに記録した。

「◂ 親のタイトル から」という行を題の**上**に色付きで出す（`PanelHeader` に `eyebrow`
を追加）。サイドバーでは、スレッドは四角＋タイトルの頭文字（v2 の「プロジェクト」ボタン
と同じ見た目を転用）、フォークは縁取り付きの丸い点にして、開かなくても一目で分かる
ようにした。実装前に v2 の実際のコード（`packages/banto-web` の `trunkRoom`/`branchRoom`）
を読み、`.from` 行（親からの継承を題の上に出す）と、開いている一覧が枝だけを対象に
していたことを確認してから作った。

### 決定25. 作業パネルの重なりは `react-resizable-panels` に `style={{overflow:'visible'}}` を渡して作る（2026-08-22）

**出所**：PO の指摘（2026-08-22）。「プロトタイプは画面で上にかぶさるようにきれいな
表示になっているが、こちらはできていない」。

最初、`Panel`/`Group` が既定で `overflow: hidden`/`auto` を強制していることだけを見て
「`className` では上書きできない」と早合点し、影を `PanelSeparator` 側に描く回り道をした
（濃さの調整が粗く、影が別区画に見えるとさらに指摘を受けた）。ライブラリのコンパイル済み
ソースを読み直すと、`style` prop は消費側のものが既定値の**後に**展開される
（`{ ..., overflow: "auto", ...(消費側の style) }`）——`className` では負けるが、
`style={{ overflow: 'visible' }}` なら勝つ。これで見本（`13-tsuzukima-kai.html` の
`.work`）が実際に使っている値（`margin-left: -10px`／`box-shadow: -24px 0 52px …`）を
そのまま持ち込めるようになった。

**教訓（規則12 の実例）**：「上書きできない」という結論を、ドキュメントの一文
（`className` に触れた TypeScript の doc comment）だけで確定させず、実際に試す
（`style` prop も別の経路として在ることを、コンパイル済みソースの該当行まで読んで
確かめる）べきだった。

### 決定26. 幹（ルート）は常に居る。フォークは開いた元の横に紙が重なる——room-stack（2026-08-22）

**出所**：PO の指摘（2026-08-22）。「基本的な UI 的にはやりたいことはほぼ
`13-tsuzukima-kai.html` で完成している」——プロトタイプの実際の状態遷移
（`render()`／クリック委譲）を読み、そのまま model に落とし込んだ。

決定22 の時点では「1本の会話パネルを開き、フォークは開いた元を置き換える」だった。
プロトタイプの実装は違う——**幹は消えず、フォークはその横に紙が1枚重なって並ぶ**
（`branch`/`work` の2状態と、それぞれが「どちらの会話から開かれたか」を覚える
`workFrom` で決まる3段の重なり）。

- **状態は `rootThreadId` と `forkThreadId` の2本**（`activeThreadId` 1本をやめた）。
  フォークを開くと、その `forkedFrom.threadId` を `rootThreadId` として一緒に立てる
- **作業パネルが無いとき**：`rootThreadId` は常に全幅で描く。`forkThreadId` があれば、
  その横に（`margin-left:-10px`／控えめな影 `--elev-branch-cascade`、決定25と同じ機構で）
  紙が1枚重なって並ぶ——素の `flex` 行なので `overflow` の制約が無い
- **作業パネルがあるとき**：開いた側（幹かフォークか）だけが帯（`slim`）に縮み、
  作業パネルが全幅で隣に開く。**開かなかった側は消えない**——幹から開いたときは
  フォークが表示から外れ（削除ではない）、フォークから開いたときは幹が
  背表紙（新規 `Spine.tsx`、44px・矢印＋頭文字）に畳まれる。背表紙を押すと
  両方閉じて幹だけの表示に戻る
- **作業パネルは ESC・会話側のクリック（ボタン等を除く）・閉じる(X、左端に移動)の
  どれでも閉じる**（PO指摘 2026-08-22）。ESC は作業パネルだけを対象にした——
  フォークを畳む操作は明示のボタン（背表紙・戻る）に残した
- **サイドバーの「開いているもの」の点は、フォークだけ現在の幹に属するものに絞った**
  （見本の `mine()` がプロジェクトで絞るのと同じ考え——プロジェクトが無い v3 では
  幹がその代わりを持つ）

**踏んだ罠**：`handleFork`/`handleMerge`/`handleCreate` の中で、`refetch()` の直後に
（当時の）`openThread(newId)` を呼んでいたら**何も起きなかった**——`openThread` は
`threads` 配列から `find` する実装だが、この関数閉包が捕まえている `threads` は
`refetch()` を待っても更新されない（React の状態はその後の再描画で初めて新しくなる。
非同期関数の中の `await` はそれを待たない）。**API の返答から素性が直接分かっている
場面では `threads` の再取得を待たず、状態を直接組み立てる**——新しいスレッドは常に
ルート、新しいフォークの親は forkThreadId として渡した引数、畳んだ後の戻り先は
常にいまの `rootThreadId`。

### 決定28. base の訂正は無効化で行う。上書きしない（PO裁定 2026-08-22）

**出所**：`append_base`（決定27）の実機確認で、テスト用の事実を誤って実在の
スレッドへ記録してしまい、その場しのぎで訂正の追記を積んだ（`base.appended` を
上書きできないので、上に足すしかなかった）。PO の指摘：**base は追記のみで
単調増加するので、訂正のたびに足していくと閾値の予算を静かに食いつぶす**
——事後対応も、上書きではなく無効化で行うべきだった。

**event sourcing の tombstone（無効化）パターンをそのまま使う**（規則12）。
削除ではない——`base.appended` はログに残ったまま、新しいイベント
`base.invalidated { threadId, baseVersion }` を積むだけ。`base.reactivated` で
取り消せる（無効化↔有効化を何度でも切り替えられる）。

**無効化した行は、閾値の予算（`baseCharacters`）から実際に外れる。** ここが
今回の本題への直接の答え——訂正を追記で行うと、間違えた原文＋訂正文の両方が
居座り続けるが、無効化はその場で予算を空ける。

**自分のスレッドが自分で追記した行だけを対象にできる。** 継承した行（fork 元の
もの）は、fork 元のスレッドでしか無効化できない——`append_base` が自分のスレッド
にしか書けないのと同じ理由（要件 D4）。親の行を無効化すると、**それを継承した
既存のフォーク全部からも消える**——フォークは写しを持たず、`effectiveBaseEntries`
が毎回親を辿って解くので、これは追加の実装をせずに自然に成り立つ（規則3）。

**fork の継承境界は版号（`baseVersion`）で判定する。配列の長さでは判定しない。**
無効化しても配列からは取り除かない（`BaseEntry.invalidated` を立てるだけ）
——長さで判定すると、親の途中の行を無効化した瞬間に、既存フォークの継承境界が
ずれる。これは実装前に気づいた罠で、`fold.test.ts` に専用の試験がある。

**口は3つ（人・AI・GUI）とも同じゲート（`invalidateBase`/`reactivateBase`）を通る**
——`POST /api/base/invalidate`、`invalidate_base`/`reactivate_base` tool、
`BasePanel` の切り替えボタンのどれも `packages/core/src/base.ts` の同じ関数を
呼ぶ（決定4と同じ「迂回できる場所に置くと迂回される」という考え）。

**あわせて GUI 側に3つ足した**（PO裁定 2026-08-22、まとめて実装）：
1. **既定では有効な行だけを表示**。チェックボックスで無効化済みも呼び出せる
2. **検索**（画面側の文字列一致のみ。サーバ側の検索 API は無い）
3. **ページング**（画面側のみ、1ページ20行）。**サーバ側のページング API は
   意図的に作っていない**——base は文字数の上限（既定2万文字）で頭打ちなので、
   実際の行数は有限で小さい。無い機能を測る試験は書けないので、要らないと
   判断した根拠をここに書く（規則7・8）

### 決定29. セキュリティモデルは「監督の有無 × 可逆性/影響範囲」の2軸で決める。1インスタンスで複数リポジトリを扱えるようにする（2026-08-23）

**出所**：PO との対話（2026-08-23）。「1つのインスタンスで複数プロジェクトを並行に
扱いたい」という要望から、スレッドのライフサイクル・実行パス・セキュリティモデルの
議論に発展した。設計をサブエージェントに大きな視点でレビューさせたところ、
提案していた「監督があれば広くて良い」という単純規則だけでは塞げない穴が
複数見つかり（下記）、その指摘を踏まえて2軸モデルに直した。

**2軸**：

1. **監督の有無**——人がその場にいて、毎ターン見ている・止められるか
2. **可逆性／影響がbantoの外に出るか**——読み取りやローカルの変更のように後から
   直せるか、push・外部送信・課金のように取り返しがつかない、またはbanto外に
   効くか

|  | 可逆・banto内で完結 | 不可逆／banto外に影響 |
|---|---|---|
| **監督あり（会話）** | 緩くてよい | 見ているだけでは不十分。判断待ちキューで一旦止める |
| **監督なし（Factory）** | 構造で縛る（人の注意力に頼らない） | 既定で禁止。許可は個別の設計判断として開ける |

「監督の有無」だけを軸にする案は、会話中のプロンプトインジェクション
（読み取り範囲を広げると、リポジトリ内の仕込まれた指示が隣のリポジトリの秘密に
届きうる）や、Factoryの既定実装が実は無隔離だった、という既存の穴を見逃していた。
2軸目（可逆性／影響範囲）を足すことで、どちらも扱える形にした。

**やったこと**：

1. **読み取りは広く、書き込みは狭く**（穴A対応）。`modules/fs` の `FileSystemCore` に
   `writeRoot`（そのスレッドが向いているリポジトリ）を追加。読み取り・一覧は
   今までどおり `root` 全体を見られるが、`write` だけは `writeRoot` の内側に
   ハードに縛る。`writeRoot` はスレッドが宣言した `workspaceRoot`
   （`ThreadCreated.workspaceRoot`、フォークは `effectiveWorkspaceRoot` で根まで
   遡って継承）から `apps/host/src/server.ts` の `/api/prompt` が解いて渡す。
   `fs` モジュールは `conversationModule` と同じ「呼び手が対象を渡す」形の
   ファクトリ関数になった（`fsModule(root, writeRoot)`）。境界チェック
   （`resolveInside`）は fs・repo・env-process・env-docker の4箇所の重複を
   `@banto/module-kit` に統合した（規則3）。

2. **Factory の既定を `env-docker` に変更**（穴B対応）。`env-process`
   （ホストと同じ権限で任意コマンドを実行する、無隔離の実装）が既定だったのを、
   隔離される `env-docker` に変えた。`env-process` を使うには運用者が
   `--env env-process` と明示する。

3. **`env-docker` に既定でネットワーク制限**（穴C対応）。当初 `--network none`
   を試したが、**ホストからコンテナへの到達性（`address`、プレビュー用）まで
   壊れることを実測で確認した**（コンテナにIPが付かない）。代わりに
   `--internal` なブリッジ（`banto-internal`、無ければ`create()`が自動で作る）を
   既定にした——実測で、ホスト↔コンテナは届く（`address`が生きる）が、
   コンテナ→外部インターネットは塞がることを確認済み
   （`modules/env-docker/src/core.test.ts` に実docker試験）。運用者が
   `BANTO_DOCKER_NETWORK` で明示的に緩められる。

4. **`repo`/`env-process`/`env-docker` をRunごとにパラメータ化**（穴E対応）。
   以前は `buildFactory` が `process.env['BANTO_REPO_ROOT']` 等にグローバル書き込み
   していたため、複数リポジトリを並行では扱えなかった。3モジュールとも
   `fsModule` と同じファクトリ関数の形（例：`repoModule(root)`）に変え、
   `buildFactory` が直接引数で渡す形にした。

5. **`FactoryPool`（`apps/host/src/index.ts`）で複数リポジトリに対応**。
   `--repo` は今後「広い親（複数リポジトリの根）」にもなれる。`/api/runs` が
   `repo`（相対パス、省くと `'.'`）を指定すると、そのリポジトリ向けの
   `Factory` を**要求されて初めて**組み立て、以後は使い回す（先回りして
   全リポジトリには繋がない）。`repo` を省く今までどおりの単一リポジトリ運用は
   無変更で動く。境界は `resolveInside` で確かめる——広い root の外を指しても
   広がらない。

6. **`env-script`（リポジトリが自前の環境を宣言できる、既存だが未配線だった
   モジュール）をホストに配線**。監督なし×banto外に影響しうる操作なので、
   2つの門は維持した——①`buildFactory` に渡した `repoRoot` だけが
   `allowedRepos` に入る（リポジトリの中身だけでは有効化されない）、
   ②スクリプトの中身は承認台帳（`foldApprovals`/`ledgerOf`、既存の
   `decision.requested`/`decision.resolved` の仕組みをそのまま使う）を
   通るまで実行されない。実際に `--env env-script` で起動し、本物のプロセスで
   `/api/runs` が通ることを確認済み。

7. **スレッド作成に `workspaceRoot` を追加**（利便のための宣言、ハードな壁では
   ない）。`packages/core` の `ThreadCreated` イベントに任意フィールドとして追加。
   `apps/web` の空状態（まだ会話が無いとき）に対象リポジトリの入力欄を追加し、
   会話パネルの頭に表示する。

**決定23を上書きする**。決定23は「`BANTO_FS_ROOT`／`BANTO_REPO_ROOT`は
1インスタンス=1作業範囲」「実開発ではプロジェクトが変われば banto の
インスタンス自体を分けるのが自然」としていたが、これは PO の「1つのインスタンスで
複数プロジェクトを並行に扱いたい」という要望と正面から矛盾する。当時の理由は
実装コスト（複数プロジェクトを横断的に扱う仕組みが無い）であって、セキュリティ上の
理由ではなかった——今回、上記1〜6でその仕組みを作ったので、決定23の
「インスタンスを分けるのが自然」という結論を撤回する。**Channel（プロジェクト分け）を
UIから外したこと自体（決定23の本題）は変えない**——複数プロジェクトの扱いは
`workspaceRoot`／`FactoryPool` の側で持ち、UIのプロジェクト行を復活させる話ではない。

**あえて作らなかったもの**：`fs` をスレッドごとに複数インスタンス化して読み取りも
ハード隔離する案は見送った。`banto://fs/...` というURIの仕組み自体を変える必要が
あり（どのリポジトリのファイルかをURIが持てない）、複雑さに見合う実害が今の
脅威モデル（単一の信頼ユーザー・人が同席するチャット）には無いと判断した
（規則12）。

**バックログに積んだもの**（今回はやらない）：
- Runイベントがどのリポジトリを対象にしたか、という情報をイベントスキーマに
  持たせていない。`/api/state` の `runs` 一覧にリポジトリ名が出ない
- スレッド作成の `workspaceRoot` 入力は自由記述のテキスト欄のみ。
  リポジトリを一覧から選べるブラウザ的なUIは作っていない
- 本番デプロイ（`~/.banto-v3/env`）の `BANTO_FS_ROOT` を実際に広げる作業は、
  どのディレクトリまで許すかが運用者の判断そのものなので、この変更には含めない
  （コード側は既にどんなディレクトリでも動く）

### 決定30. スレッドに作成・削除を持たせる。baseを「共有base」（全スレッド共通）と
「スレッドローカルのbase」の二段階にする（2026-08-23）

**出所**：PO の提案（2026-08-23）。「スレッドの作成削除の機能を持たせたい。baseが
スレッドに紐づくのであれば、スレッドを消すときに残すべきものがないか、残すなら
どこに残すかを考えたい」。

**v2の「帳場」を調べたが、再利用できなかった**（規則1：自己申告を信頼しない）。
PO は「v2にも帳場という常設スレッドがあった。それを一般名にして共有baseの置き場に
できないか」と提案したが、実際に `main` の `packages/banto-host/src/threads.ts` を
読んだところ、帳場は「共通base」とは**構造的に逆**だった——役割は「宛先不明の
知らせの吹き溜まり（lost-and-found）」で、しかも「記憶は幹ごとに分かれる」設計
（PO裁定2026-08-10）により**他の幹とは記憶を共有しない**。加えて実際に3つの
問題を抱えていた：宛先不明の通知が誤って流れ込む事故（`work/inbox/incident/
inc-0051`・`inc-0052`）、**帳場は「畳めない」設計のため会話が伸び続けて
詰まるという未解決の構造問題**（`inc-0068`、status: open）、番頭自身が帳場を
「banto開発用の特別な幹」と取り違える事故（`threads.ts:581`）。

**再利用したのは「常設のスレッドを1本持つ」という形だけ**で、失敗の核心
（実際に会話が積もり続けて畳めない）は再現しない設計にした——共有baseスレッドは
**会話をしない**。AIとも人ともチャットのやり取りをせず、`base` だけを持つ器
なので、帳場を壊した「畳めない会話」がそもそも発生しない。

**共有baseは固定id（`SHARED_BASE_THREAD_ID = 'shared-base'`）で、名前検索を
挟まない**。`ensureSharedBaseThread` が無ければ作る（`ensureChannel` と同じ
「無ければ作る」の形。規則12）。既存の `base.appended`／`invalidateBase`／
`reactivateBase`／`appendBase` のゲートをそのまま使い、新しいイベント型は
足していない（規則3）——新しいのは `effectiveBaseEntries` の解きかただけ。

**共有baseは凍結しない。fork継承とはここが決定的に違う。** fork継承は
「切った時点の版まで」で凍結する（要件R4）が、共有baseは**後から足しても
既存の全会話にすぐ効く**——一般的に成り立つ事実は、後から分かっても
遡って全部に届いてほしいため。実装は `effectiveBaseEntries` を2段に分けた：
fork継承と自分の追記だけを解く `ownAndInheritedBaseEntries`（旧ロジックそのまま、
再帰もこちらを呼ぶ）と、その手前に共有baseの**いまの** `ownBase` を毎回足す
公開版 `effectiveBaseEntries`。共有baseの `baseVersion` とfork継承境界の
`baseVersion` は意味する対象が違う（前者はそのスレッド自身、後者はfork元）ので、
**同じ版号空間で比較しないよう、2段に分けたこと自体が正しさの根拠**——`fold.test.ts`
に、親のbaseVersionと共有baseのbaseVersionが数字として重複するケースの専用試験がある。

**AIは会話中に共有baseへ直接書ける**（`append_shared_base` tool）。**最初は
「削除時の抽出だけで足りる」と考えたが、PO に「AIが会話中に入れるケースは
無いか、批判的にレビューして」と指摘され、考え直した**——PO自身に関する
情報（好み・制約）は言われた瞬間から一般的に有用で、削除まで待つと
（多くのスレッドは削除されないので）一般化されないまま埋もれる。この番頭
自身が持つ記憶の仕組み（気づいた瞬間に書く、user/feedback/project/reference
の4種）と同じ形に揃えた（規則12）。

一方で批判的レビューで見つけた懸念には対応した：
1. **他スレッドのデータへ書ける経路になる**（要件D4の建前に触れる）——
   `threadId` を引数にせず、共有baseの固定idを閉じ込めた別ツールにすることで、
   「任意のスレッドを指定させない」という実質は破っていない
2. **帳場と同じ吹き溜まりになる懸念**——共有baseは既存の文字数上限ゲート
   （要件R8）にそのまま乗るので、帳場のような無制限の増大にはならない。
   SYSTEM_PROMPTに「不明なら scoped な `append_base` を使う」という指針を明記
3. **プライバシー的な越境**——AIは共有baseの**追記だけ**でき、無効化・訂正は
   人のみ（`BasePanel`）に残した。AIの書き込みミスは人が消せる、片方向の安全弁

**共有baseはサイドバーの固定部には置かない**（PO指摘：「大事なサイドバーの
固定部をとるほどの機能ではない」）。会話をしないので「開いているもの」にも
出さない。既存の「設定」ダイアログに区画を1つ足し、既存の `BasePanel` を
共有baseスレッドid固定で開くだけにした（新規コンポーネントを増やさない。規則3）。

**スレッド削除もトゥームストーン**（`thread.deleted`、`base.invalidated`・
`thread.merged` と同じ形）。ログからは消えない——「開いているもの」「履歴」
どちらからも外れるだけ。**未マージのフォークは自動でマージしてから削除する**
（PO裁定）。削除の直前に、そのスレッド自身の（無効化されていない）base行を
見せ、共有baseへ持ち出す行を人が選べる——**既定はすべて未選択**（AIの書き込みと
同じ「不明ならローカルのまま」の考え）。

**削除は「畳む」ではなく「削除する」と呼ぶ**——PO の指摘（「そもそも畳むという
語彙が適切かな？v2に引きずられていないかな」）を受けて、`main` を
`git grep` で実際に確認した。「畳む」は v2 のADR・提案書（`adr-0022-branch-
outcome-does-not-flow-away.md`・`2026-08-18-thread-watchdog-and-auto-fold.md`
等）で、まさにこの「枝を閉じる」概念に多用されていた語だった。しかも**v3の
意匠見直し計画（決定22の元になった検討）自体が、この語をv2の言い回しと
名指しして「マージして閉じる」に置き換える決定を既にしていた**——にもかかわらず
決定24のタイトル・内部コメントは「畳む」に戻ってしまっていた（ボタン文言
「マージして閉じる」とイベント名 `thread.merged` は素の語彙のまま保たれていた）。
この決定30の文章では「畳む」ではなく「マージして閉じる」「削除する」で統一し、
決定24側の内部コメントの言葉遣いも合わせて直す機会があれば直す
（今回は本題ではないので、決定24自体の文言修正はしていない——規則7）。

**実装中に見つけて直したバグ**：会話が1本も無い状態（例：唯一のスレッドを
削除した直後）で「共有baseを開く」を押すと、`rootThread === null` の判定が
`work !== null` より先に評価され、空状態（「まだ会話がありません」）が
作業パネルより優先されて**共有baseが開けなかった**。ui-smoke試験
（削除→共有baseを開く、を実際のブラウザで通す試験）が無ければ気づけなかった
——型検査・単体試験はどちらも緑のまま通り抜けていた。`rootThread === null &&
work !== null` の場合を先に分岐して、作業パネル単独表示を追加して直した。

### 決定31. フォークからのフォークを禁止する。共有base由来の行に専用の印を付ける（2026-08-23）

**出所**：本番稼働中のPOからの実機フィードバック（2026-08-23）。「共有baseは読むとき
個別スレッドのbaseの一部のように見える」「`http://banto.tjstkm.net`を開くと謎に
forkが開いた状態になる」の2点。

**謎のfork表示は、実際に本番データに残っていたフォークのフォークが原因だった**
（規則1：コードを読んで確認、推測で済ませない）。`App.tsx`の「幹の解決」処理が
`thread.forkedFrom.threadId`を**1階層だけ**遡って「幹」にしていたため、遡った先
自体がフォークだった場合、幹側のパネルにまでフォークの表示（分岐元へのリンク）が
出てしまっていた。同じ処理が自動オープンとサイドバークリックの両方にあった。

副産物として、`POST /api/threads/fork`のタイトル生成ロジック
（`親の題.replace(/ から分岐$/, '')`で既に付いている接尾辞を剥がしてから
付け直す、実測2026-08-22の対症療法）も、**フォークのフォークだと親と全く同じ
題名になる**ことが分かった——これが「2つのパネルが同じ題名」に見えた理由。

**PO裁定**：フォークからのフォークはそもそも想定していないので禁止する。

**やったこと**：
1. `POST /api/threads/fork`が、対象スレッドが既にフォーク（`forkedFrom !== null`）
   なら400で断る。**フロント（フォークボタンを幹にしか出さない）と両方**で断る
   ——フロントだけだと直接APIを叩けば素通りする（規則1と同じ考え）
2. タイトルの接尾辞剥がしロジックは、フォークからのフォークが作れなくなった
   ことで到達しなくなったので削除し、単純に`${親の題} から分岐`にした
3. **既存データに残ってしまった入れ子**（新規には作れないが、既に存在するもの）
   でも表示は壊れないよう、幹の解決を`trueRootId`——`forkedFrom`が無くなるまで
   遡る——に直した（防御的修正。フロントだけの話で、イベントの形は変えていない）
4. `ConversationPanel`の`parentTitle`（フォークの題の上に出す「◂ ○○ から」）も、
   常に幹の題ではなく**フォークの直接の親**の題を引くよう直した——入れ子でも
   正しいラベルになる

**共有baseの見分けやすさ**：`EffectiveBaseEntry`の`own`（自分の行か）はフロントの
型に無く、`ownerThreadId`も同様に欠けていた——バックエンドは送っていたのに
フロントが捨てていた。両方をフロントの`BaseEntry`型に足し、`BasePanel`で
`ownerThreadId === sharedBaseThreadId`のときだけ、fork継承のGitForkアイコンとは
別に「🌐 共有」の印を出すようにした。`sharedBaseThreadId`は`App.tsx`→
`WorkPanel`→`BasePanel`とバケツリレーで通す（既存の`/api/state`の
`sharedBaseThreadId`をそのまま使う。決定30と同じ、新しい機構を足さない）。

**追記（同日、追加のPOフィードバック）**：上記だけでは直らなかった。
「フォークからのフォークを禁止」は**新規作成**を止めるだけで、**未マージの
既存フォーク**（特に孫以降）は残ったまま——親フォークをマージしても孫フォーク
自身は片付かない。「一番新しいスレッドを自動で開く」がフォークも候補に
入れていたため、開き直すたびに毎回その孫フォークが「最新」として出てきて
しまっていた。**自動オープンの対象を幹（`forkedFrom === null`）だけに絞った**
——フォークは、幹を開いてから明示的にクリックしたときだけ表示される。
併せて、フォークのパネルから削除ボタンも外した（PO指摘：「マージして閉じる」
と役割が重複する。削除は幹だけでよい）。

### 決定32. スレッド作成の場所を、モジュールが候補として提案できるようにする（2026-08-24）

**出所**：PO の提案（2026-08-24）。「スレッドの作成については場所を指定する
必要がある。その候補をModuleが提案できるようにしたい——Git管理のModuleでClone
した場所をスレッドのbaseにする、のようなことが簡単にできるといい」。

**決定16の役割（Capability）パターンをそのまま使う**（規則12）——新しい機構は
作らない。`repo`が`provides: ['environment']`のような形で役割を名乗り、Factory
が実装を知らずに役割だけで頼む、あの形をそのまま流用した。新しい役割
`workspace-suggestions`を定義し、`repo`モジュールがまず1つの実装として名乗る
（`provides: ['repo', 'workspace-suggestions']`）——**将来cloneする専用モジュール
が増えても、hostは1文字も変えずに済む**（Factory側の役割の使い方と同じ利点）。

**今回作ったのは`repo`が候補地を列挙する分だけ**。「cloneしてくる」機能自体は
まだどこにも無いので、そこまでは作らない（規則7）——`repo.list_candidates`は
rootの直下を見て`.git`があるディレクトリを返すだけ（1階層のみ、`workspaceRoot`
が広いrootからの相対パス1段で表される形と揃える）。

**候補の形はPO裁定で決めた**：`path`・`label`に加えて`lastModified`
（最終更新日時）と、**そのスレッド固有ではなくhost側で突き合わせて**付ける
`inUse`（既にどれかのスレッドがこの場所を使っているか）。`inUse`をモジュール側
ではなくhostが付けるのは、モジュールはスレッドの存在を知らないため
（`repo`にthreadの知識を持たせると境界が滲む。規則3と同じ考え）。

**集約は`/api/state`と別の口**（`GET /api/workspace-candidates`）。**必要なとき
だけ**（PO裁定）——スレッド作成の空状態を出したときの1回だけフロントが呼ぶ。
毎回のポーリングに含めると、候補を出すモジュール全部への問い合わせが常時
発生することになる。

**AI向けの`modules`とは別の場所に持たせた**（`ServerOptions.
workspaceSuggestionModules`）——ここに繋いだモジュールは会話には一切出ない。
候補を出す道具（`list_candidates`）は人向けの機能であって、AIが会話中に
呼ぶ理由が無いツール定義を見せてトークンを使わせないため。

**画面側は、自由入力の欄はそのまま残し、候補は押すと入力欄に入るボタンの
一覧として添えた。** 新しいUIライブラリは増やしていない（規則10）——native の
`<datalist>`も検討したが、`lastModified`・`inUse`を添えて出したいという裁定
だったので、素の押せるリストのほうが単純に作れた。
