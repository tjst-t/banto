# ADR-0022: 継ぎ目を引き直す — ループを抽象化せず、資産の側でモデル非依存を守る

> status: **proposed**（2026-08-20 起草）。PO は ①モデル非依存の撤回 ②Slack モデルの自作UI
> ③既存実装のゼロベース再構成（部品としての再利用は可）の3点を裁定済み。

## 文脈

### 症状

「pi をハーネスにしていたところへ Claude Agent SDK を統合しようとして、うまくいかず、
トークンを浪費し、Claude の性能を活かせていない」（PO・2026-08-20）。

### 診断1：継ぎ目をエージェントループに置いたこと

`BantoHarness`（ADR-0020 決定88・89）は pi と Claude Agent SDK の**共通部分＝最小公約数**しか
表現できない。実際に起きたことは引き継ぎ書に記録がある。

> 契約の言葉が同じでも、意味が同じとは限らない。`prompt(): Promise<void>` は型としては
> 両方満たすが、片方は「積んだ」で片方は「終わった」だった。

同種の破れが繰り返し出た——`resume` の取り違え（新しい会話が黙る）、`opus` と `opus[1m]` が
**別のモデル**であること、`supportedModels()` が「勧める一覧」であって「使える名前の全部」では
ないこと。**差し替え可能にしたのに、差し替えるたびに壊れる。**

エージェントループは、ベンダ間で差がいちばん大きく、いちばん速く変わる部分である。そこに
継ぎ目を置いた結果、差分を吸収するコードが増え続けた（ADR-0020・ADR-0021、task-0102〜0111、
inc-0058・inc-0062）。

### 診断2：ランタイムが持つ能力を自前で作り直したこと

| 自前実装 | ランタイム側の同等物 |
|---|---|
| `ChapterKeeper`（章立て） | compaction |
| `worker.delegate` の `tools` 絞り込み | subagent の tool allowlist |
| SKILL 3層（決定26） | Skills（progressive disclosure） |
| 記憶の抽出と注入（決定28） | memory ツール＋ファイル |
| モデル台帳4箇所 | 役 → モデル 1箇所 |

二重化した分だけ、両方を整合させる仕事が発生した。実機の journal に
`職人の既定モデル: opencode-go/deepseek-v4-flash（standard）` と出ながら実際は opus で
走っていた——「1行に2つの嘘」は二重管理の症状であって、実装の不注意ではない。

### 診断3：トークンの浪費の実体は「文脈が 1M 窓の上限まで伸びること」（2026-08-20 実測）

**起草時の初版は「キャッシュがほぼ効いていない」と推定していた。実測したところ外れていた。**
以下は推定ではなく計測値である（`~/.claude/projects` のトランスクリプト 1,059 セッション・
88,711 ターン。LLM は呼んでいない）。

**キャッシュは効いている。**

```
キャッシュ読み  14,878,227,752   (97.9%)
キャッシュ書き     325,563,595
未キャッシュ           717,889
```

97.9% は良い値であり、ここに直すところは無い。決定28 の妥協（記憶をシステムプロンプトに
入れるためキャッシュが壊れる）も、実害としては現れていなかった。

**効いていないのは圧縮のほうだった。**

```
1ターンあたりの文脈サイズ   p50  90,949   p90 465,712   p99 839,320   max 999,622
                          平均 171,406
うち固定プレフィックス      p50  31,312   p90  43,487     ← システム＋道具56本＋SKILL
200k 超を運んでいるターン   25.4%
```

`max 999,622` は **1M 窓の上限に張り付いている**ということである。長いセッションの文脈推移を
1ターンずつ並べると（単位:千トークン）：

```
33 99 131 166 201 231 267 312 341 368 425 481 510 537 562 583 614 638 662 693 725 747 770 803 832 859 891 913
```

**1,210 ターンかけて 33K から 913K へ単調に増えており、大きく下がった回数は 0。** 上位5セッションで
0〜2 回。**自動の章立て（圧縮）がほぼ発火していない。**

これは inc-0062（「バックエンドを替えると `ChapterKeeper` の購読が古いハーネスに残り、自動の
章立てが働かない」）および task-0308（「窓・トークン数が引けなくても保険で章を畳めるようにする」）
と一致する。**自前の章立てが黙って止まっていた**、というのが実体である。

浪費の構造はこうなる——キャッシュ読みは 0.1× に割り引かれているが、**900K の文脈を数百ターン
読み直せば、割り引いても効く**。1セッションで 826M トークン（1,857ターン）という記録がある。
「Claude の Max 枠を banto が食い潰す」（2026-08-17、残り 2%）はこれで説明がつく。

**したがって梃子は「キャッシュ衛生」ではなく「文脈の長さ」である。** 決定110 はこの計測に
合わせて書き直してある。

> **記録として**：この ADR の初版は、キャッシュを測る前にキャッシュを犯人だと書いていた。
> I1（自己申告を信頼しない）は**自分の推論にも掛かる**——ADR-0013 で番頭が同じ誤りをしている
> （「構造逆転で工場は失効した」を観測から推論した飛躍）。二度目である。

### PO 裁定（2026-08-20）

1. **モデル非依存（`CLAUDE.md` Tech Stack）は降ろす。**
2. UI は **Slack のモデルを借りた自作 Web/PWA**。本物の Slack は使わない。
3. **ゼロベースで再構成する。** 既存実装は部品として持ち込んでよいが、土台としては使わない。
   外形的な仕様（これまで検証で確かめた振る舞い）は活用する。

## 決定

### 105. ループは Claude Agent SDK 一本にする。抽象化しない（2026-08-20、PO裁定）

- `BantoHarness` / `RuntimeDriver` / `harness-backends` / `PiRpcDriver` / `llm-registry` /
  `model-roles`（`ModelLedger`）/ クオータ・フォールバック（`swapHarness`）を**すべて廃止する**。
- 番頭も職人も Claude Agent SDK 上で動く。職人は subagent。
- **`CLAUDE.md` の「LLMプロバイダ層はプラガブル＝モデル非依存」は撤回する。** ADR-0020 決定88・89
  （`BantoHarness` 契約と二実装）、決定93（`RuntimeDriver` は関所）、ADR-0021 決定99（供給と役の
  分離）は、いずれも二実装を前提とした構造なので同時に失効する。
- pi は**職人ランタイムとしても使わない**。`@earendil-works/pi-*` への依存を落とす。

**不採用**：「ループの抽象化は残したまま Agent SDK 側の実装だけ直す」。同じ形の破れが
7回出ており（`prompt()` の意味・`resume`・モデル名・`ChapterKeeper` の購読残り 等）、
8回目が出ないと考える根拠がない。

### 106. モデル非依存は「資産の側」で守る（2026-08-20、PO裁定）

ロックインの代償を、移植可能な資産で相殺する。移植可能な資産は4つだけと定義する。

| 資産 | 形 | 移植性 |
|---|---|---|
| モジュール | **MCP サーバ** | 他のクライアント（Claude Code / Cursor 等）からも同じものが使える |
| 手順 | **SKILL.md**（agentskills.io） | 形式が標準 |
| 記録 | **自前の append-only イベントログ** | 完全に自分のもの。真実はここに1つ（D3） |
| 画面 | **React コンポーネント** | ランタイムに触れない |

将来ハーネスを替えるときに作り直すのは Runner（決定109）だけで、規模は数百行に収まる。
**「ループを抽象化して資産を守る」は、コストが逆だった**——資産は最初からベンダ中立で、
中立にならないのはループだけである。

### 107. 会話の構造：Channel / Thread / Fork（2026-08-20、PO裁定）

Slack のモデルと、エージェントランタイムのセッションを一致させる。

| Slack | Banto | 実体 |
|---|---|---|
| Channel | プロジェクト | 1リポジトリ（＋その worktree 群） |
| Thread | 会話 | 1 セッション |
| 返信ツリーの枝 | 平行試行 | 親の履歴を引き継いだ**分岐スレッド** |

- **分岐（fork）は複製ではない。** `thread.created` イベントが `parentThreadId` と
  `forkFromEventId` を持ち、分岐スレッドは親の当該地点までを**論理的に引き継ぐ**。
- **分岐の最大の利点はキャッシュの共有**である。プレフィックスが親と共通なので、同じ文脈からの
  2本目・3本目の試行が安く立つ。平行開発の単価を下げる機構がここに来る。
- 現行の「会話52本フラット」は、平行開発をモデル化したはずが平行に並んだだけだった。枝にすると
  「どの決定から派生したか」が構造で表せる＝認知負荷が下がる（vision の当初の狙い）。

### 108. モジュールは MCP サーバ。自前のレジストリ／HTTP面／Tool 定義を捨てる（2026-08-20、PO裁定）

決定25・27 の「接続情報・Tool・GUI・SKILL を1単位で登録する」は維持する。**実現手段だけ差し替える。**

```ts
export interface BantoModule {
  id: string                       // "git" / "factory" / "vault"
  mcp: { command: string, args?: string[] } | { url: string }
  gui?: { entry: string; views: CanvasView[] }   // React。決定12・17 のまま
  skills?: string                  // SKILL.md ディレクトリ（決定26 の3層は維持）
  settings?: JSONSchema            // 設定画面の区画（決定41 のまま）
}
```

帰結：

- **決定9 のドット記法と決定22 の論理名↔wire名変換は不要になる。** MCP サーバ名がそのまま
  名前空間になる。この層を丸ごと削る。
- **未決のまま残っていた「モジュール HTTP 面の認証」が解消する。** MCP のトランスポートと
  認証に乗る。自前の無認証 HTTP 面（Worker Pool の報告経路・Environment Pool の sops 経路）を
  作らない。
- **道具をスレッド単位で出し入れできる。** Financial Planner のスレッドに `factory` の道具は
  見えない。決定27 の「Banto をブローカーにしない」も維持される——モジュール間呼び出しは、
  呼ぶ側が MCP クライアントを持てばよく、Banto は経路に入らない。

### 109. Runner：ベンダに触れる唯一の面（2026-08-20、番頭裁定）

```ts
interface Runner {
  run(input: {
    threadId: ThreadId
    systemPrompt: string        // スレッド生存中は読み取り専用
    mcpServers: McpServerSpec[] // そのスレッドに紐づくモジュールの分だけ
    skills: string[]
    model: ModelId              // スレッドに紐づく。変更＝新スレッド
    resumeFrom?: { threadId: ThreadId; eventId: EventId }  // 分岐
    prompt: Content
  }): AsyncIterable<Event>
}
```

Agent SDK の呼び出しはこのファイル群の中だけに閉じる。ここ以外にベンダ固有の型・語彙を
出さない（D5 の Surface 原則の延長）。

### 110. 梃子は文脈の長さである。短く保つことを機構にする（2026-08-20、番頭裁定・実測に基づく）

診断3 の計測により、直すべきはキャッシュ衛生ではなく**文脈の長さ**と確定した。効きの大きい順に置く。

1. **会話を伸ばさない。第一の手段は分岐（決定107）である。**
   1,857 ターン・1M 窓の1本より、小さな共有プレフィックスから枝分かれした短い枝の束のほうが、
   体験としても費用としても良い。**決定107 は UI の話であると同時に、費用の話でもある**
   ——枝は親のプレフィックスをキャッシュ共有したまま、自分は短いまま終わる。
2. **圧縮はランタイムに任せ、効いていることを計測する。** `ChapterKeeper` を廃止する。
   自前の章立ては**黙って止まっていた**（inc-0062・診断3）。自前で持つと、止まったことに
   気づく仕組みまで自前で要る。
3. **古い tool result を落とす**（context editing）。長い作業ほど、前半のツール出力は
   もう読まれない。
4. **1M 窓を既定にしない。** 窓が大きいことは「伸ばしてよい」ではない。窓は保険であって既定値ではない。
5. **システムプロンプトは凍結。道具はスレッドに紐づくモジュールの分だけ。**
   固定プレフィックスは実測 p50 31K / p90 43K。全体に占める比は小さいが**全ターンに乗る**ので、
   削る価値はある（道具は提示56本／在庫85本。増えたら tool search の `defer_loading`）。
   記憶の注入は (a) `messages[]` への `{"role":"system"}` 追記（Opus 5 / 4.8 対応・beta ヘッダ不要・
   キャッシュを壊さない）、または (b) memory ツール＋ファイル。
   → **決定28 の「注入は次のセッション開始時に限る」という妥協は撤回する。**
6. **走行中にモデルを替えない。** キャッシュはモデル単位。安いモデルは subagent に回す。
7. **毎ターン「文脈サイズ」と「圧縮が発火した回数」をイベントに記録し、閾値を超えたら
   incident を積む。** 記録すべき第一の指標は `cache_read_input_tokens` ではなく
   **文脈サイズの伸び**である。**単調に増え続けているなら機構が壊れている**（P6）。
   inc-0062 は1か月近く誰にも気づかれなかった——気づく仕組みが無かったからである。

### 111. 状態の置き場を1つに畳む（2026-08-20、番頭裁定）

現行は台帳が散っている——`llm-registry.json` / `model-roles.json` / `worker-pool/settings.json` /
`kobo-settings.json` / `threads/index.json` / `place-grants.json` / `spawn-ledger` /
Kobo の event log / `env-ledger`。D3（真実は一箇所）を運用で守り切れていない。

```
<data>/
  events/      # append-only JSONL（日付ローテート）。真実はここだけ
  blobs/       # 添付・スクリーンショット・成果物（content-addressed）
  config.json  # 人が編集するもの（役ごとのモデル・モジュール登録・場所）
  secrets/     # vault モジュールの持ち物（sops）
```

- **導出できる値は保存しない。** スレッド一覧も Run の状態も、起動時に events を畳んでメモリに
  載せる。`threads/index.json` のような写しを持たない。
- **どこまで読んだかを保存しない。** 起動のたびに 0 から読み直す（task-0060 で採った形が正しい。
  「Kobo が落ちている間に終わった職人も拾える」）。
- 版印（`schemaVersion`）はイベントの型に持たせ、**読めない版に当たったら止まる**（ADR-0021 で
  得た「黙って別のモデルで走るのが一番困る」を継承）。

### 112. Factory は小さな耐久ワークフロー。統治デーモンではない（2026-08-20、PO裁定）

PO が説明した Factory は「worktree 作成 → 実装 → テスト → main へマージ」。現行 Kobo は
そこに健康状態 taxonomy・3段レビュー・TTL 超過検出・独自帳簿・spawn 台帳・監査ロール・
rework 昇格が乗った 2,293 行のデーモンであり、**やりたいことより1桁大きい。**

```
Run:  queued → running → review → merging → done | failed
```

- 各 step は**冪等な handler**。落ちたらその step から再開する。run log は決定111 のイベントログの一部。
- 実行は subagent（tool allowlist 付き）。`worker.delegate_toolkit` と砦（`worker-guard.ts`）は
  不要になる——allowlist はランタイムの機能。
- **マージ前の承認は Thread に届く**（`decision.requested` イベント）＝ Slack の返信ツリーに
  「判断待ち」として出る。決定58 の `origin` の発想はそのまま生きる。
- Factory は **Channel に1つ**。プロジェクト＝Channel なので「Factory を作る」＝その Channel に
  工場を紐づける、という体験になる。

### 113. 既存実装の扱い：土台にしない。部品として救出する（2026-08-20、PO裁定）

**持ち込むもの**（振る舞いが検証済みで、ベンダに依存しないもの）：

| 出所 | 部品 | 理由 |
|---|---|---|
| Kobo | マージキュー、依存ゲート | 実 LLM の e2e で通しの実績がある |
| Kobo | `task-frontmatter` 検証、work/ のスキーマ | 外形仕様として有効 |
| Environment Pool | docker / process ドライバ、sops、`workdir` 契約（決定34d） | env モジュールの中身になる |
| repo-manager | ghq / gwq からの導出（**独自台帳を持たない**設計） | 決定111 と整合 |
| browser | CDP 転送、`chromium-launcher` の env 注入口（task-0319） | browser モジュールの中身 |
| web tools | SSRF ガード（`[::ffff:...]` の穴を塞いだもの） | 同じ穴を二度掘らない |
| 場所（places） | `file.write` の範囲チェック・`.git/` とデータ置き場の保護（決定37・38） | fs モジュールの砦 |
| prompt assets | `BANTO_SKILLS_DIR` による追跡下ファイルからの隔離（task-0323） | |
| UI プロトタイプ | 十二次改訂までの体験（タブ・履歴・設定・受け口・モバイル） | **外形仕様として全面的に活用する** |

**捨てるもの**：

`BantoHarness` / `RuntimeDriver` / `harness-backends` / `PiRpcDriver` / `llm-registry` /
`model-roles` / クオータ・フォールバック / `swapHarness` / `ChapterKeeper` /
Tool 名の論理名↔wire名変換（決定22）/ `worker-guard` / `spawn-ledger` / 職人の等級と
リソースベース並行制御 / Kobo の健康状態 taxonomy・3段レビュー・監査ロール /
自前モジュールレジストリの HTTP 面。

### 114. UI：ライブラリに寄せる（2026-08-20、番頭裁定）

決定12（React に統一）は維持。実装をライブラリに寄せる。

| 用途 | 採用 | 理由 |
|---|---|---|
| チャット | **assistant-ui** | ストリーミング・tool call の描画・添付・生成UI。`ExternalStoreRuntime` で**決定111 のイベントログを真実として繋げる** |
| 基盤 | shadcn/ui + Radix + Tailwind | assistant-ui の前提。モバイル対応（決定21）もここで担保 |
| キャンバスのタブ | Radix Tabs | タブ一本化（§5）なら十分 |
| ターミナル | xterm.js | |
| DIFF | `@git-diff-view/react` または Monaco diff | |
| ファイル木 | react-arborist | |
| Markdown | streamdown（ストリーミング中の未完コードブロックを壊さない） | |
| 状態 | TanStack Query + Zustand | |
| PWA | vite-plugin-pwa | 「どこからでも同じように」（PO要件） |

**不採用**：Vercel AI SDK の `useChat`。トランスポートも所有しようとするため、Runner が
返すイベント（tool 実行・subagent・承認待ち）と二重管理になる。assistant-ui の Runtime だけ使う。

**根拠（D6：依存追加の理由）**：タブの罫線・オーバーフロー・モバイルの入力欄隠れに
**十二次の改訂**を費やした領域である。自作を続ける費用が、依存を1つ増やす費用を上回っている。

### 115. パッケージ構成（2026-08-20、番頭裁定）

```
apps/
  web/                 React PWA（assistant-ui）
  host/                Banto Core：HTTP + WS、Runner、モジュール解決
packages/
  core/                ドメイン型、イベントログ、Thread/Channel/Fork
  runner/              Agent SDK 呼び出し（唯一のベンダ接触面。決定109）
  module-kit/          モジュール作者向け（MCP サーバ + GUI + skills + settings の宣言）
  ui-kit/              React 共有部品（shadcn ベース。モバイル前提）
modules/
  fs/ git/ shell/ browser/ env/ publish/ vault/ backlog/ factory/
```

`modules/*` はそれぞれ独立プロセスの MCP サーバ＋React GUI＋SKILL ディレクトリ。
