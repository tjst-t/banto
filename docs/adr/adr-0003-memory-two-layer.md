# ADR-0003: 記憶（Memory）の二層モデル

## 文脈

全体像設計プロトタイプ（ADR-0002）で、POがAIと話す面が複数（Planning / Review / Consult / Backlog / Terminal）に分散し、各会話の文脈が分断される問題が顕在化した。POは「散らばった会話面に、**共通の記憶を持つ一人のAI**が向き合う」形を望む。これは spec-ui 第二原理／D8「操作と文脈の記憶はシステムが持つ、POの頭は判断だけに使う」の実装機構にあたる。記憶を全プロジェクト横断で共有するか、プロジェクト別に持つかが論点だった。

## 決定

記憶を**二層**で持つ。

1. **あなた（人）の記憶＝全プロジェクト横断・共有**：好み・進め方・常設の指示など“人”についての記憶。どの面・どのプロジェクトでも効く。
2. **プロジェクトの記憶＝各リポジトリに閉じる・横断させない**：決定・規約・ドメインなど“そのプロジェクト”の記憶。契約層（ADR/spec）と地続き。統治の単位はプロジェクトなので混ぜない（spec-multi-project §1）。

各会話面は **①あなたの記憶 ＋ ②そのプロジェクトの記憶 ＋ その場の文脈** を合成する。記憶は**競合する隠れ状態にしない**：イベントログ（originRef, D8）を真実とし、記憶はそこから**蒸留した導出＋PO編集可**とする（D3）。中身は可視・編集可能とし、PO主権・透明性を担保する。UIでは独立メニュー（Records › Memory）として扱う。

## 帰結

- (+) 「継続した一人のAI」に見えつつ、プロジェクト知識は混ざらない（統治単位＝プロジェクトを保つ）
- (+) D8「文脈の記憶はシステムが持つ」の実装機構が定まる。会話冒頭の復帰リキャップはこの記憶の部分表示
- (+) 記憶が真実でなく導出のため、イベントログとの二重管理・drift を避けられる（D3）
- (−) 何を記憶化するかの蒸留規則・鮮度管理は別途設計が要る（POと追って詰める。本ADRは二層の骨格と真実の所在のみ固定）
- (−) 横断共有する「人の記憶」に機微情報が入りうる。可視・編集可で担保するが運用注意
- spec-ui に本モデルを追記する（P3）。方針変更はこのADRの supersede を要する
