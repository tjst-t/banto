# ADR-0003: 記憶（Memory）の二層モデル

## 文脈

全体像設計プロトタイプ（ADR-0002）で、POがAIと話す面が複数（Planning / Review / Consult / Backlog / Terminal）に分散し、各会話の文脈が分断される問題が顕在化した。POは「散らばった会話面に、**共通の記憶を持つ一人のAI**が向き合う」形を望む。これは spec-ui 第二原理／D8「操作と文脈の記憶はシステムが持つ、POの頭は判断だけに使う」の実装機構にあたる。記憶を全プロジェクト横断で共有するか、プロジェクト別に持つかが論点だった。

## 決定

記憶を**二層**で持つ。

1. **あなた（人）の記憶＝全プロジェクト横断・共有**：好み・進め方・常設の指示など“人”についての記憶。どの面・どのプロジェクトでも効く。
2. **プロジェクトの記憶＝そのプロジェクトに閉じる・横断させない**：決定・規約・ドメインなど“そのプロジェクト”の記憶。契約層（ADR/spec）と地続き。統治の単位はプロジェクトなので混ぜない（spec-multi-project §1）。**区画の単位は「幹」**（→ 追補 2026-08-10）。

各会話面は **①あなたの記憶 ＋ ②そのプロジェクトの記憶 ＋ その場の文脈** を合成する。記憶は**競合する隠れ状態にしない**：イベントログ（originRef, D8）を真実とし、記憶はそこから**蒸留した導出＋PO編集可**とする（D3）。中身は可視・編集可能とし、PO主権・透明性を担保する。UIでは独立メニュー（Records › Memory）として扱う。

## 帰結

- (+) 「継続した一人のAI」に見えつつ、プロジェクト知識は混ざらない（統治単位＝プロジェクトを保つ）
- (+) D8「文脈の記憶はシステムが持つ」の実装機構が定まる。会話冒頭の復帰リキャップはこの記憶の部分表示
- (+) 記憶が真実でなく導出のため、イベントログとの二重管理・drift を避けられる（D3）
- (−) 何を記憶化するかの蒸留規則・鮮度管理は別途設計が要る（POと追って詰める。本ADRは二層の骨格と真実の所在のみ固定）
- (−) 横断共有する「人の記憶」に機微情報が入りうる。可視・編集可で担保するが運用注意
- spec-ui に本モデルを追記する（P3）。方針変更はこのADRの supersede を要する

## 追補 2026-08-10：第二層の区画は「場所」ではなく「幹」

**PO裁定。** 第二層をリポジトリ（場所）で分けていたが、区画の単位を**幹**（ADR-0017 決定77
の会話の幹）へ移す。

### なぜ

場所に結びつけると、**プロジェクトとして扱いたいものの多くが記憶を持てない**。

- 複数のリポジトリにまたがる仕事（banto と loamium を並べて直す、等）は、どの場所にも属さない
- **まだリポジトリの無い相談**——構想段階の話は、場所ができるまで記憶を持てない
- 逆に、同じリポジトリで別々の仕事をしているとき、記憶が1つに混ざる

一方 PO裁定 2026-08-09 で**幹＝プロジェクトの単位**と決まっている。区画をそこへ合わせると、
「幹を分ける」と「記憶を分ける」が同じ判断になり、番頭が持つ判定が1つで済む。

**場所は「どこに書けるか」、幹は「何についての仕事か」**——役割が違うものを兼ねさせない。

### 決めたこと

- 第二層の区画は**幹**。置き場は `<data>/trunks/<幹のID>/memory.jsonl`
- **枝は親の幹と同じ区画**（ADR-0017 決定77 の深さ1段がそのまま効く）。枝で調べたことは
  枝を畳んだ後も仕事の記憶として残る
- 会話に注入されるのは**人の記憶＋その幹の記憶だけ**。他の幹の記憶は載らない
- ただし**探すのは幹をまたげる**（`memory.search({ acrossTrunks: true })`）。
  注入を絞る理由は予算であって秘匿ではない——「前に別の仕事で似た話をした」を思い出せないと、
  分けた代償のほうが大きい。持ってくると決めたら、いまの幹へ改めて保存する（書き直して入れる）
- 幹を終うとき、**持って出る記憶は番頭が選ぶ**（`thread.close_trunk` の `carry`）。
  選ばれた文は人の記憶（横断する層）へ上がる。これが第二層→第一層の唯一の経路

### 帰結

- (+) リポジトリの無い仕事・リポジトリをまたぐ仕事も記憶を持てる
- (+) 幹を分ける判断と記憶を分ける判断が1つになる（番頭が持つ規則が減る）
- (+) 場所の別名畳み込み（PO裁定 2026-08-05）が要らなくなった——ワークツリーごとに
  記憶が分かれる問題は、区画が場所でなくなった時点で消える
- (−) **場所で分けていた頃の記憶は自動では移らない。** どの幹のものかは中身を読まないと
  決まらず、推測で混ぜたら分けた意味が消えるため。起動時に件数と置き場を名指しして
  知らせる（I2）ので、要るものは読んで入れ直す
- (−) 幹が増えるほど「どこで覚えたか」を番頭が忘れうる。`acrossTrunks` がその受け皿
