# ADR-0017: 会話は**幹1本と枝**。番頭は**中核の器**に Tool の戻り値を載せ、**作業する面だけ**が間になる

> status: **accepted**（2026-08-09。PO 裁定）。**ADR-0015 決定73 の画面側を差し替える**
> （取次そのものは無傷）。決定番号は 76（ADR-0016）の続きから採る。
>
> **訂正（2026-08-13・PO指示）**: 決定77 の「幹と枝の間を通るのは2行だけ」「枝には送れない」は
> **決定105〜108 で覆した**。幹と枝は、枝が生きている間も対話する。決定77 の本文は記録として
> そのまま残す（D3：既に書いたものは書き換えない）ので、**読むときは決定105〜108 が優先**。

## 文脈

案3「座敷」（会話が本体・キャンバスは差し出し物）は **2026-08-05 の裁定⑤「主従は後で」で
未決のまま残っていた**。PO 提起（2026-08-09）——

> bantoのUIだけど、いまキャンパスとチャットを横並びにやっているけど、これが本当にいいのか
> ちょっと悩んでいる。（中略）プロジェクト単位では会話は一つのラインになっていて、人間が
> 認識しないところで、内部でセッションの切り替えと引継ぎをしている。そして必要に応じて
> 分岐していく（中略）Slackのスレッド的なUIを応用するのはどうかな。ただSlackでは分岐した
> スレッドが埋没する問題がある

見本を 11 枚組んで比べた（`prototype/redesign/`）。**同じ場面を描かせて並べた**
（`scene.js`）ので、違いは構造だけになっている。

### 半分は既に在った

「内部でセッションを切り替えて引き継ぐ」は **ADR-0010 決定47(b) で実装済み**だった
（`chapters.ts` / `handoffs.ts`）。文脈が閾値に達したら番頭がターン境界で章を閉じ、
引き継ぎ資料を書き、次の章へは見出しと参照だけを渡す。**足りなかったのは機構ではなく、
会話の単位が「並列のタブ」のままだったこと**である。

### Slack の埋没を分解すると、2つはこの店では起きない

| 埋没の原因 | banto では |
|---|---|
| 枝が**場所**であって**用件**でない（畳む条件が無い） | 未解決。決定77 で閉じる |
| 枝の持ち主が**人間**。思い出さないと進まない | **起きない**。持ち主は番頭（D10）、番頭は忘れない（D11） |
| 結論が枝に閉じ、幹に**還らない** | 未解決。決定77 で閉じる |
| 未処理を集める**1本の口が無い** | **起きない**。取次1本（ADR-0015 決定73） |

**Slack の埋没は UI の問題ではなく「枝に持ち主と出口が無い」問題だった。**

### 数えたこと

| 何を | 実測 |
|---|---|
| 3か月ぶんの幹（`06-suji.html`） | **81 行**。「決めたことだけ」に絞ると **24 行**——画面2枚に収まる |
| 枝を 23 本に増やしたとき | 「あなたの番 3」「止まっている 1」は破綻しない。**壊れるのは「動いている 16」** |
| ファイル閲覧を列に入れる | 一覧 288px ＋ コード欄。**400px の列には入らない** |
| 器を会話に埋めたとき | 差分・職人の手元・記憶・推移が**列を食わない**。列が生えるのは幅が要る作業だけ |

## 決定

### 決定77: 会話はプロジェクトごとに**幹1本**。枝は**還す条件**を持って生まれ、畳むと**結論1行**が幹に還る

- **幹はプロジェクトに1本で、永続。畳まない。** 会話のタブは作らない
- **枝は「還す条件」を持って生まれる。** 何が決まれば幹に還るかを書けないものは枝にしない
  （幹で話す）。ここが Slack との分岐点そのもの
- **枝は番頭の判断でも、PO の指示でも開く**（PO裁定 2026-08-09）。番頭は「継続的な議論・
  調査になる」と見たら自分で開いてよく、PO が明示したときも開く。**開いた理由を札に必ず書く**
  ——書けないなら枝にしない、が歯止めになる
- **幹に載るのは、開いた1行と還った1行だけ。** 枝の中身（職人のおしゃべり・調査・往復）は
  幹に流さない。これで幹は**プロジェクトの意思決定の帯**として端から端まで読める
- **幹は追記のみ**（D3）。ただし**枝の札は「その枝を指す参照」であって写しではない**ので、
  状態表示は生きている。記録は書き換わらない
- **深さは1段。枝の中に枝を作らない。** 埋没は深さに対して指数的に効く。枝が別の枝を要する
  なら、畳んで幹に還してから開き直す
- **枝の出口は「結論」であって「実装」ではない。** incident を起票し task を積んだ時点で畳む
  ——実装の寿命まで開いておくと、結局 Slack になる。**保留も結論の一種**として
  「保留：理由」で畳み、開き直せるようにする

**埋没しないための不変条件（試験にできる形）：**

> 開いている枝は、必ず **①幹の札 ②横断の通知 ③レールの点**（決定79）のどれかに出ている。
> **どこにも出ていない枝は作れない。**

`spec-ui` §2 の「現れる場所のない操作は追加できない」と同じ形である。加えて、
**黙って止まった枝は機構の異常として扱い**（P6・ADR-0016）、滞留を検出したら取次へ積む。
忘れられた枝を人の記憶に頼らせない。

**却下した案：Slack 式の右パネルのスレッド。** 埋没の原因①③をそのまま持ち込む。
**却下した案：会話のタブ。** 置き場の記憶を要求する（D7 違反）。並列に並べた時点で
「どれが本筋か」が消える。

### 決定78: 器は**中核が持つ有限の語彙**。モジュールは GUI 部品を作らず、形を合わせる

番頭が画面を組む（`11-zen.html`）と、**同じ話が毎回違う見た目になる**。
`spec-canvas-ui` の第一原理（POから見ればどれも番頭が出した面でひと続き）が崩れる。
だから：

- **器は中核が有限の語彙として持ち、番頭は選ぶだけ。生成UIではなく選択UI**
- **モジュールは器を作らない。** `spec-canvas-ui` §10「モジュールごとの CSS を足さない。
  足りない語彙は §5 に追加して全モジュールで共有する」の延長
- 語彙は **13 種**：行の一覧 / 鍵と値 / 表 / 差分 / 選択肢 / 数の札 / 目盛 / 推移 /
  経過 / 画像 / 文書 / 引用 / 面への口（一覧は `prototype/redesign/12-utsuwa.html`）
- **どの器も「畳んだ姿」（狭いときの1行）を持つ。** 判定はコンテナクエリ
  （`spec-canvas-ui` §3 と同じ規約）——ビューポートではなく**会話の帯の幅**で決まるので、
  細い帯でもモバイルでも同じものが効く。器を1つ足すコストが2倍になるのは**歯止めとして
  望ましい**
- **どの器も「いつの」を出す**（決定81(c)）
- `state` は **5役だけ**（`run` / `turn` / `stop` / `warn` / `done`）。モジュールに独自の
  状態名を持ち込ませない——持ち込むと色の意味が崩れる
- **膳は小さい。** ツール戻り値は 4000 文字で切り詰められる（`TOOL_PAYLOAD_MAX_CHARS`）ので、
  **この線は規約ではなく機構が引く**。切ったことは隠さない（I1）

**作らない器**（理由を残す。書かないと同じ議論が戻る）：

| 作らない | なぜ | 代わりに |
|---|---|---|
| 棒グラフ | 膳に載る本数（2〜5本）なら表のほうが速く正確 | 表／面 |
| 円グラフ | 角度は読み違える | 目盛／表 |
| 散布図・箱ひげ | 見比べる作業は膳の大きさを超える | 面 |
| ツリー・グラフ図 | 依存は番頭が言葉で言えるなら言うべき | 本文／面 |
| カンバン | 面の仕事。眺めるものが会話に居座る | 面 |
| マークダウンの全部描画 | 器が小さなブラウザになる | 文書＋面 |
| 自由な図・画像の生成 | **選択UIが生成UIに戻る**。前提が崩れる | —— |

判定は1つに畳める：**「見比べる作業」は面、「判断に要る事実」は膳。**
グラフのうち推移（`spark`）だけを残したのは、これが見比べる器ではなく
**1つの事実（向き）を言う器**だから（P6 が要求する計測は、率だけでなく向きで意味が変わる）。

### 決定79: **読む面は器、作業する面は間**。作業する面でも会話は細い帯として残す

器を入れると、面が2種類に割れる。

| | 何が要るか | どこに出すか |
|---|---|---|
| **読む面**（差分の抜粋・記憶・職人の手元） | 事実が数行 | **器として会話の中に**。列を食わない |
| **作業する面**（ファイル閲覧・Git・検証環境） | 探す・移動する・比べる。**幅** | **間**（列）として開く |

- **作業する面は、手前を背表紙に畳んで全幅を使う。** 400px の列に押し込まない
- **ただし「いま居た会話」は細い帯（既定 344px）として残す。** 面を見ながら
  「これ何？」と訊けないのは、番頭が主体の店として本末転倒（PO指摘 2026-08-09）。
  **主役が何かで幅を配る**——会話が主役なら会話が広く、作業が主役なら会話は細くてよい。
  そこで読むのではなく、**話しかけるための幅**だから
- **帯の幅はつまんで変えられる**（260〜620px）。主役がその時の作業で変わるので決め打ちにしない
- **面はどこから開いたかを覚える。** 幹から開いたら枝を閉じ、枝から開いたら枝を左に残す。
  畳んだ面を開き直すと**そのときの組み合わせが復元される**
- **探す面と読む面を分ける。** `file.browser`（探す・移動する）と `file.viewer`（1つを読む）は
  目的が違うので別種にする——決定17 が「シェルと職人ビューアは目的が違うので別コンポーネント」
  としたのと同じ理屈
- **幹・枝・面は重なりで表す。** 幹は地、枝はその上の紙、面はさらに上。広い画面で横に
  並んでいても関係は重なりのままで、**狭い画面の重ねと同じ模型**になる
- **狭い画面（760px 以下）は重ねる。** 幹が地、枝と面は下から上がる紙、上端に幹が覗く

**却下した案：面をモーダルで覆う。** 戻り道が見えない。背表紙なら経路が残る。

### 決定80: 判断待ちは**常設しない**。会話の流れに立て、遡ったときだけ↓に朱を載せる

**ADR-0015 決定73 の画面側を差し替える。** 決定73 が入力欄の直上を選んだ理由は2つあった：

1. **気づけること** → **横断の通知が既に担っている**（決定73 自身が作った口）。二重
2. **判断待ちを持ったまま話し続けないこと** → **遡ったときだけの問題**

番頭が判断を求めたなら、それは**会話の最新の発言**なので、放っておいても一番下にある。
だから `spec-chat-ui` §3.2 の**既にある↓ボタンに朱を載せる**だけで足りる。

- 判断は**会話の流れの中に立つ**（朱の札）。固定の帯は置かない
- **最下部から離れたときだけ**、↓ボタンが朱になり「判断待ち N」と言う
- **読みと入力の間に常設はひとつも無くなる**
- **帰属が自明になる**——「この会話の下にある」以外の意味を持ちようがない。
  固定の帯は、通知と同じ言葉・同じ色で、幹と枝に2つ同時に出るため
  **どこの話か読み取れなかった**（PO指摘 2026-08-09）

**決定73 の他の部分は無傷**：判断を求めるものは取次1つ・押されたことはホストがその場で
効かせる（`InboxEffect`）・効かせられなければ畳まない・`effect` は画面へ配らない。

### 決定81: 器の運用

#### (a) どの器で描くかは**番頭が都度指定する**

- モジュールは素のデータを返すだけで、**器のことを知らない**。同じ戻り値でも文脈によって
  出したい器は変わり（環境の一覧を「行の一覧」で出すか「数の札」で出すか）、
  **モジュールは文脈を知らない**（D5：Surface に判断を持たせない）
- **データは再送させない。** 番頭は「どのツール結果を・どの器で・どこを」だけを言い、
  実体はホストが**退避済みの結果**（決定47(a) の `artifacts/`）から引く
- **副作用：Tool を1つ新設する**（`canvas.show`）。番頭が器を選んで出す唯一の口

**却下した案：モジュールが戻り値に `utsuwa` を付ける。** 楽だが、モジュールに画面の都合が
漏れ、文脈による出し分けができない。
**却下した案：モジュールが既定を申告し番頭が上書き。** どちらが効いたか分からなくなる。

#### (b) 膳＝器1つ。並べたいときは続けて出す

まとまりを表現する＝レイアウトを組ませることなので、「番頭は選ぶが作らない」が崩れる。
**入れ子は許さない**（許した瞬間に生成UIへ戻る）。足りないと分かったら、
**上限3・入れ子なし**の配列を後から足せる。

#### (c) 器は**凍る**。どの器も「いつの」を出す

面と器は二重管理ではない。**種類が違う。**

| | 何か | 変わるか |
|---|---|---|
| **器** | そのときそう見えた**記録**。会話の一部 | **凍る**（幹は追記のみ・D3） |
| **面** | **いまの状態**。自分で `endpoint` から取る（決定25） | 生きる |
| **枝の札** | その枝を指す**参照** | 生きる |

だから器には**「いつの」を必ず出す**。出さないと、古い写しなのか いまの状態なのかが読めない。
いまを知りたければ `open`（面への口）で面へ行く道がある。

#### (d) 描けない戻り値は**会話に出し、番頭にも返す**

- **どのモジュールの・どの Tool の・どの器で・何が足りないか**まで書く。直せるのは登録した
  人なので、出所が分かる形で（I2）
- **番頭にも同じものが返る**ので言い直せる（別の器にする・面へ送る）
- **会話は止めない**——回復可能なので I2 の「回復不能なら failed にして止まる」には当たらない
- **黙って素の JSON を出さない**（壊れた見た目が既定になる）。素の値は畳んで置く
- 大きすぎるものは切って「N 件のうち先頭のみ」と書く（I1・`spec-chat-ui` §6.3 と揃える）

### 決定105〜108: **幹と枝は対話できる**（決定77 の訂正・PO指示 2026-08-13）

> **決定77 のうち「幹と枝の間を通るのは2行だけ」「枝には送れない」は、ここで覆る。**
> 上の決定77 の本文はそのまま残す（記録なので書き換えない・D3）。以後は**この4つが優先**する。

**なぜ覆すか。** 決定77 は Slack の埋没を分解して「幹に載るのは開いた1行と還った1行だけ」に
絞った。埋没は実際に防げたが、**運用してみると別の壊れ方が出た**（PO判断 2026-08-13）:

1. 枝の中で何が起きているか**幹から見えない**。「枝で見ています」と言ったきり、
   止まっているのか進んでいるのかも分からない（滞留の検出は3日後・`BRANCH_STALE_DAYS`）
2. **開いたあとの枝へ話しかけられない**。`thread.open` の `message` が最初で最後なので、
   前提が変わっても方針が変わっても、枝が畳むまで待つしかない
3. **枝から幹へ相談できない**。畳むまで黙るか、**結論を捏造して畳む**かの二択になる
   ——決定77 が嫌った「実装の寿命まで開いておく」の裏返しで、こちらは「決まってないのに畳む」

**譲らないもの（決定77 から引き継ぐ縛り）：**

- **幹は端から端まで読める帯**。行が増えても**1行は1行のまま**——詳細は幹に流さない
- **幹は追記のみ**（D3）。既存の行は書き換わらない
- **深さは1段**。枝の中に枝は開けない。枝から枝へも渡せない（幹を通す）
- **幹は畳めない**
- **幹をまたがない**。他の幹の枝は読めないし、渡せない（記憶が分かれる単位は幹・ADR-0003 追補）

#### 決定105: **幹から枝の中身を読める**（`thread.read`）

- **生きている枝も、畳んだ枝も読める。** 畳んだ枝の中身は消えていない（決定30c と同じ扱い）
- **全文は返さない。** 既定は末尾20件、`offset` / `limit` で辿る。1行ずつも切り詰める。
  それでも大きければ**既存の退避に載る**（決定47a）——栞になり `artifact.read` で引ける
- **読めるのはこの幹とその枝だけ。** 隣の幹の中身は読めない（用があるなら `thread.send`）
- 頭書きに状態・還す条件・開いた理由・結論・詳細を出す。「もう畳んだのか」で読み方が変わる

#### 決定106: **開いたあとの枝へ言伝を渡せる**（`thread.steer`）

- **決定77 の「枝には送れない」は、親の幹からに限って覆る。** 隣の幹からは相変わらず
  渡せない——それは差配ではなく割り込みで、決定77 の理由（1つの問いに閉じている）がそのまま効く
- 経路は `thread.open` の `message` と同じ（知らせとして届き、枝のターンが回る）
- **枝から枝へは渡せない**（深さ1段が横に破れる）。幹へ還してから幹に渡してもらう

#### 決定107: **枝から幹へ、畳む前に相談できる**（`thread.consult`）

- **問い（`question`）か報告（`report`）かを書く。** 返事が要るかどうかが分かれ目で、
  読み分けられないと、問いが黙殺されるか報告に返事を書かされるかのどちらかになる
- **幹には札が立つ**（知らせにしない）。枝の札・還った1行と**同じ列**に並べる
  ——知らせに混ぜると職人の報告や環境の知らせに紛れ、読み返したときに辿れない。
  埋没しない不変条件（決定77）はこれで保たれる
- **枝は畳まれない。** 待つ間に進められることは進めてよい。返事は `thread.steer` で返る

#### 決定108: **畳むときは詳細も渡せる。ただし幹へは流さない**（`thread.merge`）

- `investigated`（調べたこと）／`decided`（決めたこと）／`remaining`（残ったこと）を足せる
- **詳細は枝に残る。** 幹に積まれるのは**結論1行のまま**で、「詳細が在る」ことだけを出す
  （`hasDetail`）。読むのは枝を開いてから（`thread.read`・画面では「詳しい経緯をひらく」）
- **一覧が読めなくなる作りにしない**、が決定77 から引き継ぐ縛りそのもの

**往復は機構で止める（P4）。** `thread.steer` / `thread.consult` は向きのある組ごとに
10分で10通まで（幹どうしの `thread.send` は5通のまま）。親子の往復は仕事そのものなので
緩くするが、両側とも番頭なので**頼むだけでは止まらない**。

**却下した案：`thread.send` を枝にも通す。** 1本で済むが、**隣の幹からの割り込み**と
**親からの差配**が同じ口になる。前者は決定77 が明示的に禁じたもので、区別が消える。

## 却下した案（全体）

- **案7「伺い」／案8「帳面」**（会話を主面から降ろし、裁きの列か台帳を主役にする）。
  原理からは筋が通る（「POの仕事は裁くこと」）が、**会話が中心という前提を崩す**ので
  PO 裁定で外した。ただし案7 の「番頭が自分で決めたことの控え」（D9 が働いている証拠を
  見せる）は拾う価値があり、未決事項に残す
- **案11「膳」の全面採用**（固定のレイアウトを持たず、番頭が毎ターン画面を組む）。
  予測可能性と一望性を失い、番頭の判断力に全部を賭けることになる。**器の考え方だけを採り**、
  骨格は案9「続き間」に置いた
- **符牒（全面等幅・キー駆動）と和紙（明朝・紙の質感）**。意匠は第三の家を採る
  （`prototype/redesign/ideal.css`）。ただし**「朱＝あなたの番、面を塗ってよい唯一の色」は
  引き継ぐ**——判断待ちが常に画面でいちばん強い、という規則は意匠が変わっても動かさない
