# ADR-0011: LLM・モデル管理は Banto 中核が持つ（モジュールにしない）

> status: **accepted**（2026-08-03。PO 裁定）。ADR-0004 の実装配置を定める。
> ADR-0010 決定25・27 のモジュール境界と、決定41（設定画面は項目の宣言だけを受け取る）に例外を1つ加える。

## 文脈

ADR-0004 で「使えるLLMは全体設定、モデルはセッション/タスクごとに動的選定」と決めた。その実装として `LlmCatalog`（banto-core）と `llm-registry` モジュール（banto-host）を作り、Tool・設定・キャンバスGUI を1単位で登録した——決定25 のモジュールの形に素直に乗せたつもりだった。

その後、tier と制約による解決・キーの優先順・tier ごとの判断基準を画面に出す段になって、2つの食い違いが表に出た。

**1. 設定画面に本体を出せない。** 決定41 により、モジュールが設定画面に渡せるのは項目の宣言（`SettingField[]`：`text / number / boolean / select / list`）だけで、GUI は渡せない。LLM 管理の中身——モデルごとの tier 選択と役割トグルを持つ繰り返し行、tier ごとの自由記述、順序を持つキーの行、条件を選ぶたびに解決先が変わる確認——はこの語彙で表せない。結果として設定画面には既定3項目しか出ず、残りはキャンバスへ逃がすことになった。PO の想定は「これは banto のコア機能なので設定画面に出る」であり、実装と食い違っていた。

**2. 依存の向きがモジュールになっていない。** `bin.ts` の構築順が実態を示している。

```
llmCatalog = new LlmCatalog({...})        ← モジュールレジストリより前
createModuleRegistry([...])
  createLlmRegistryModule({ catalog })    ← 既にある物を受け取るだけ
llmCatalog.resolveHostDefault()           ← 番頭のセッションを組み立てるのに使う
```

番頭のセッションを作るのにカタログが要るため、モジュールが存在するより前に構築される。**中核がカタログに依存し、モジュールが中核に依存している。** モジュールは Tool と GUI を被せる薄い層でしかない。

なお ADR-0010 決定26・27 で中核自身のドメインとされているのは `canvas.*` / `memory.*` / `skill.*` で、いずれも「それが無いと番頭が番頭でなくなる」ものである。モジュールは番頭が**獲得する**能力（Kobo・Worker Pool・Environment Pool）で、Kobo 無しでも番頭は職人に委譲できる（決定23）。モデルは獲得する能力ではなく、番頭が乗っている土台である——番頭は LLM セッションそのものだからである。

## 決定

### 42. LLM・モデル管理は中核のドメインとする（2026-08-03、PO裁定）

- **`llm.*` を `canvas.*` / `memory.*` / `skill.*` と同格の中核ドメインとする。** `llm-registry` モジュールは廃止し、Tool は `createLlmTools(catalog)` として `bin.ts` が中核の Tool 群と一緒に組む（`createCanvasTools` と同じ形）。番頭は常に `llm.*` を持つ。
- **設定は中核の区画に戻す。** `createCoreSettingsSections` が「場所」「接続と公開」と並べて LLM の区画を出す。ADR-0004 の実装過程で中核から外してモジュールへ移したが、これを戻す。
- **`LlmCatalog` は banto-core に置いたまま。** CLAUDE.md「LLMプロバイダ層はプラガブル＝モデル非依存。banto-core に I/F、アダプタで差し替える」の通りで、変更しない。プロバイダの差し替え可能性はカタログの seam が担い、管理面をモジュールにする必要はない。
- **中核も HTTP の Tool 面を持つ。** モジュールが `<baseUrl>/tools/<name>` を持つのと同じ規約で、中核は `/api/core/tools/<name>` を持つ。これまで中核由来のキャンバスGUIは到達先が空文字で、実質モジュールでなければ GUI がデータを取れなかった。この穴を塞ぐ。

### 43. 設定画面が専用の面を持てるのは中核の区画だけ（2026-08-03、PO裁定）

- 決定41（モジュールは項目の宣言だけを出す。GUI は渡さない）は**モジュールに対してそのまま維持する**。守りたいのは「モジュールが増えても設定画面が変わらない」ことであり、その狙いは変わらない。
- **中核の区画に限り、設定画面が専用の描画を持ってよい。** 中核は固定の小さな既知集合（場所／接続と公開／LLM）で、設定画面は `createCoreSettingsSections` を通じて既に中核の存在を知っている。モジュールに逃げ道を配ると全モジュールが使い始めるが、中核の区画にだけ許すならその波及は起きない。
- 却下した案：`ModuleSettingsSpec` に `view?: string`（描くコンポーネント名）を足し、どのモジュールも宣言できるようにする。渡すのは文字列1つなので決定41 の字面は保てるが、**逃げ道を全モジュールに配ることになり、決定41 が守ろうとした「書式がばらばらになる」がそのまま起きる**。
- 却下した案：項目の語彙を増やす（table 型・行内コントロール型）。汎用のフォーム言語を作ることになり、決定41 の前提「設定は名前と型と今の値でほぼ尽きる」自体が崩れる。割に合わない。

### 44. モジュールは起動時に動く処理を持てる（2026-08-04、PO裁定）

- `BantoModule` に `init?(ctx)` を足す。ホストはレジストリが揃ってから、**待ち受ける前に**登録順で一度だけ呼ぶ。
- 目的は、モジュールが「起動のたびにやること」を自分で持てるようにすること。**中核が個々のモジュールの都合を知らずに済む**（決定27：Banto をブローカーにしない）。
- 最初の利用者は Worker Pool の職人の復帰。これは中核（`bin.ts`）に直接書かれていたが、「職人がどう畳まれ、どう起き直るか」は Worker Pool の都合であって番頭核が知る話ではない（inc-0019）。
- 例外は握りつぶさない。ただし1つのモジュールの失敗でホスト全体は落とさず、ログに出して次へ進む——設定の区画を1つ読めないときと同じ扱い（I2）。
- `ctx` はいまログだけ。増やすときに中核の都合（Kobo の参照など）を渡さないこと。渡した瞬間にモジュールが中核へ依存し、差し替え可能性が失われる。

### 45. pi の設定ファイルは banto が書く（2026-08-04、PO要望）

- ここまで `~/.pi/agent/models.json` と `auth.json` は**読むだけ**で、banto が書くのは
  オーバーレイ（`llm-registry.json`）だけだった。プロバイダとキーを画面から足せるようにするため、
  **この2ファイルも banto が書く**ことにする。`llm.add_provider` / `llm.remove_provider` /
  `llm.set_key` / `llm.remove_key` / `llm.fetch_models` が書き手。
- **pi 本体は無改造のまま**（CLAUDE.md）。触るのは設定ファイルであって pi のコードではない。
  外で pi を触っても壊れないよう、既存の記述は残したまま足し引きする（丸ごと書き直さない）。
- 守ること：
  - **手で入れた設定を壊さない。** 既にあるプロバイダは上書きしない。取り込んだモデルは
    足すだけで、既存の `input`（画像可否）や `contextWindow` は据え置く。
  - **黙って消さない。** プロバイダ側から消えたモデルはこちらでは消さず、名前を返して人に決めさせる。
    → **決定46 で改めた**（自動で消し、消したものを名前で挙げる）。「黙って」の部分だけが要点だった。
  - **壊れた JSON は上書きしない。** 読めないファイルはエラーにして止める（I2）。
  - **キーは書けるが読めない。** `auth.json` は 0600 のまま保ち、一覧には名前と状態しか出さない。
- **1プロバイダ1鍵のまま**。複数鍵は `auth.json` のデータモデル変更（D1）で、別に決める。
- モデルの自動取得は OpenAI 互換の `GET {baseUrl}/models`。**返るのは基本 ID だけ**で、画像を
  読めるかは分からないため、新しく足すものは `text` のみと名乗る（読めないものを読めると
  偽らない・I1）。→ 画像可否と文脈長の埋め方は**決定46 で足した**（組み込み定義と公開台帳）。

### 46. 文脈長は公開台帳から引き、消えたモデルは自動で消す（2026-08-04、PO裁定）

- **文脈長を空のままにしない。** ハーネス（pi）は文脈長が無いモデルを `contextWindow ?? 0`
  として扱い、`shouldCompact` が `tokens > 0 - reserve` で**常に真**になる。結果、
  あふれる代わりに**毎ターン自動要約が走る**（会話が毎回まとめ直され、遅くなり、話が削られる）。
  実測で確認した。
- 埋める順序は **①プロバイダの `/models`（どのモデルがあるか）→ ②ハーネスの組み込み定義
  （画像可否）→ ③公開台帳 models.dev（文脈長）**。推測値は置かない——不明だった41件が
  models.dev で41件とも埋まったので、当てずっぽうを持つ理由が無い。
  - models.dev の `attachment` は画像かファイル全般か判別できないため、**画像可否は取らない**（I1）。
  - 取りに行くのは取り込みを押したときだけ。届かなくても取り込みは続ける（I2）。
- それでも埋まらないものは**「長さ不明」と画面に出す**。選べば毎ターン要約が走るので、
  選ぶ前に見えている必要がある。
- **プロバイダ側から消えたモデルは、こちらからも消す**（決定45 の「消さない」を改める）。
  残しても選べるだけで、選べば必ず失敗する。消したものは名前を挙げるので「黙って消す」にはならない。
- **消えたモデルを指していた既定は、警告しつつ選び直す**（同じプロバイダ → 同じ tier →
  残っているもの、の順）。指したまま放置すると番頭が起動も会話もできなくなる。
  何を何に付け替えたかは必ず出す（黙って別のモデルに変えない・I1）。
- **文脈のまとめ直し（compaction）は会話に残す。** ハーネスの `compaction_end` を知らせ行に
  変換する。実際に古いやり取りが要約へ置き換わるので、黙って進めると「番頭が急に
  前の話を忘れた」としか見えない。中断は出さず、失敗は出す。

### 138. モデルは「列挙」ではなく「採用と検索」で扱う（2026-08-04、PO裁定）

（旧・決定47。2026-08-16 に決定番号の一意化のため 138 へ移した（task-0159・imp-0073）。
ADR-0010 の決定47「文脈の管理をコンパクションから退避と章立てへ移す」とは**別物**。
2026-08-16 より前に書かれた文書の「ADR-0011 決定47」は、この決定138 を指している。）

- **前提が変わった。** 決定42〜46 は「モデルは10件程度」を暗黙の前提にしていた。OpenRouter は
  **337モデル**（models.dev 調べ）あり、1モデル＝1行に7個の操作を並べる設定画面では
  約2,400個の操作が1画面に出る。チャットのモデル選択にも337件が並ぶ。成り立たない。
- **`hostUsable` / `workerUsable` の既定を false に反転する（＝採用したものだけ使える）。**
  「全部使ってよい、要らないものを個別に落とす」は10件なら成り立つが、337件では成り立たない。
  - **移行時は、そのとき載っているモデルを全部採用済みにする**（`adoptionMigratedAt`）。
    いま使えているものを黙って使えなくしない。以後に取り込んだものは採用されない。
  - 既定・第一候補が消えて**採用済みの代わりが1つも無いときだけ**、採用していないものを
    採用した上で選ぶ。動かない番頭より、線引きを1つ広げるほうがまし（変更は必ず報告する）。
- **`llm.list` は全件を返さない。** 既定は採用中のみ・50件（上限200）。`query`（空白区切りで
  全語一致）・`provider`・`vision`・`free`・`minContext`・`sort`（名前/文脈長/価格）で絞る。
  返すときは**総数と返した件数の両方**を出す（切ったことを隠さない・I1）。
- **設定画面は「採用中」＋「探して採用」の2段。** tier と役割の割り当ては採用中にだけ出す
  ——337件に tier を割り当てたい人はいない。
- **価格を取り込む**（models.dev / 組み込み定義の `cost`）。337件から選ぶ実際の軸は
  「能力・文脈長・価格」で、価格が無いと選べない。無料判定も「鍵が要らない」という粗い
  推定から、**価格が 0 かどうか**に変える。
- **消えたモデルの報告は段階的に。** 採用していないものの増減は一々報告しない
  （プロバイダは日常的に出し入れする）。**採用していたものが消えたときだけ強く警告**する。

### 追補: 設定の枠組みを2段にする（2026-08-10、PO要望）

決定41 は「モジュールは GUI を渡さず、項目の宣言だけを渡す」。決定43 はその例外として
中核の区画にだけ `view`（描き先の宣言）を許した。**職人の設定でこの線が持たなくなった**
——バックエンド（pi / Claude Code / 将来の Codex）の一覧・使えるか・入切・既定・等級ごとの
モデルが絡み合い、平たい項目の並びでは「切ってあるバックエンドのモデルが選べるように見える」
「どのバックエンドのモデルか分からない」が避けられない。

枠組みを2段にする（どちらも設定画面が描く。モジュールが React を持ち込むわけではない）:

1. **宣言（既定）**——`fields`。**関数でも書けるようにした**ので、選択肢がそのつど変わる
   区画（採用済みのモデル・使えるバックエンド）も宣言のままでよい。工場の役割設定はこちら
2. **描き先の宣言（例外）**——`view`。**モジュールにも開く**。一覧とその中の状態を同時に
   見せる類だけ。職人の区画（`WorkerSettings`）が最初の利用者

**値のやりとりはどちらも設定画面の口のまま**（`settings.describe` / `settings.update`）。
GUI を宣言しても、モジュールが独自の口を生やすことはしない——番頭に渡らないはずの操作が
別の面から漏れるのを防ぐため、区画に渡すのは「いまの値」と「保存する関数」だけ。

あわせて**職人の既定は「LLM・モデル」から「職人」へ移した**。あちらが持つのは素材と採用
（プロバイダ・鍵・モデル・職人に使わせてよいか）まで。等級ごとのモデルをあちらに置くと、
**登録に載らないバックエンド（Claude Code）のモデルを並べられず**、pi のモデルだけが特別扱いに
なる。移した先では、どのバックエンドのモデルも同じ1つの表に並ぶ。

## 帰結

- **中核が太る。** 中核は降りられないので、増やす判断は本来慎重であるべき。ここでは「番頭がそれ無しに起動できない」を基準に採り、モデル管理はそれに当たると判断した。今後この基準を満たさないものを中核に入れない。
- **モジュールの4点セット（接続情報・Tool・GUI・SKILL）を1単位で登録する利点は失う。** 中核ドメインは Tool を `bin.ts` で組み、GUI は中核のビューとしてカタログに登録する形になる。決定36 で「そのどれも持たないものをモジュールと呼ぶと枠が緩む」としたのと逆向きに、**中核が持つべきものをモジュールと呼ぶと境界が緩む**という整理になる。
- **GUI は設定画面だけに出す。キャンバスには出さない**（2026-08-03、PO裁定）。起票時は「番頭が会話中に見せられるよう両方に出す」としていたが、これは設定であって会話の材料ではない、という判断で撤回した。番頭が会話中にモデルの状態を語る必要があるときは `llm.list` の結果を述べればよく、GUI を出す必要はない。
  - コンポーネント（`LlmRegistryViewer`）は UI 側のレジストリに載ったままで、設定画面が決定43 の `view` 宣言から名前で引く。キャンバスのカタログには登録しない。
- ADR-0010 の決定一覧（決定41 まで）に決定42・43 を追加する。CLAUDE.md のモジュール例示から `llm-registry` を外す。
- Worker Pool は「必須の組み込みモジュール」（決定23・27c）のままとする。必須かどうかではなく**中核がそれ無しに起動できないか**が基準であり、番頭は職人を起こさずに動ける。
