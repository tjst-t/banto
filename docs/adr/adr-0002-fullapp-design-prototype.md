# ADR-0002: 全体像（フルアプリ）設計プロトタイプの導入

## 文脈

S30a8fd（POコックピットv1）のプロトタイプPOレビューで、「レビュー1画面しかなく開発の全流れ・アプリ全体像が像を結ばない」というフィードバックが繰り返し出た。原因は、bantoのPO操作面がGUI（キュー/ボード/バックログ）と会話面（検討/レビューのpiセッション）に分かれ、v1プロトタイプがその一部（キュー/カード/tmux）しか描いていなかったこと。VISIONの中核主張「POの一日を会話2枚＋キュー1本に圧縮し、残りはAIが回す」が成立するかは、全PO面を通して見ないと判断できない。実装コードを書く前に、この操作モデルとVISIONの妥当性を最も安く検証する手段が要る。

## 決定

全PO面をクリック可能な静的モックで網羅する「全体像（フルアプリ）設計プロトタイプ」を、現Sprint S30a8fd とはスコープを分離した独立工程として導入する（ROADMAP: S6cfce9、execution_order 上は S30a8fd の直後・残り実装Sprintの前に front-load）。既存の `prototype/app.html`（サイドバー統合シェル＋フローティング解説レイヤー）を土台に、未着手のPO面（レビュー会話・バックログ編集・改善ループのレビュー＝月次diff承認・共有ブラウザペイン・通知/設定・マルチプロジェクト横断 ほか）を追加して一巡させる。

位置づけは**非拘束の設計リファレンス**とする。設計の真実は `docs/spec/` のままであり、プロトタイプは正典化しない（公開IF・データモデルを固定しない＝D1を発火させない／Specとの矛盾検知＝P3の対象にしない）。忠実度はモック（ハードコードデータ）に留め、判断駆動でピクセル磨きに逃げない。成果は後続の実装Sprint（S24ddde 以降）の実装基準・レビュー観点として参照する。

## 帰結

- (+) daemon/GUI実装前に操作モデルとVISIONの妥当性を最小コストで検証でき、手戻りを前倒しで潰せる
- (+) 全PO面が1つのクリック可能な参照になり、後続Sprintの実装が像を共有した状態で始められる
- (+) 保留中のVISION見直し論点（操作モデルが期待と合うか）を、実装前の安いタイミングで判定できる
- (−) 静的モックはSpec進化に対し陳腐化しうる。非拘束と明示し、乖離時はSpecを真実として従う（プロトタイプを追随更新するか破棄する）
- (−) S30a8fdのv1配信とは別に工数が要る。スコープ分離を守りv1の意味を薄めない（P1）
- 方針変更（例: 拘束的な仕様の真実に格上げ）はこのADRのsupersedeを要する
