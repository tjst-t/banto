# ADR-0007: Git / Provider の秘密情報は sops（age）で管理

## 文脈

プロジェクト取り込み（clone / push）の Git 認証（GitHub / GitLab、マルチアカウント）と、Provider（実行環境）の認証を banto が扱う必要がある。秘密情報の保存方式は不可逆な選択（D1、データモデル）であり、勝手に決めずADRで固定する。spec-environment §4 は既に環境 credentials を「sops 管理・参照名のみ・daemon が復号して環境変数で渡す」と規定済みで、Git 認証・マルチアカウントも同じ要件を持つ。

## 決定

Git ホスト（マルチアカウント）および Provider の秘密情報は **sops（age 鍵）** で暗号化管理する。

- **値のみ暗号化し、ファイル構造は平文**にする＝ git diff でどのキーが変わったかをレビューでき、暗号文はコミットしても安全
- 復号鍵（age 秘密鍵）は**ホスト（daemon）のみが保持**し、リポジトリには入れない
- **daemon が使用時に復号し、対象プロセス（git / ドライバ）の環境変数として直接渡す。エージェントのコンテキスト・ツール結果には一度も出さない**（spec-environment §4）

対抗案の評価：OS キーチェーン＝ヘッドレスな自宅 Ubuntu VM で扱いにくく git 管理外／独自暗号化ファイル＝車輪の再発明／Vault 等の秘密管理基盤＝PO 一人には過剰。

## 帰結

- (+) 秘密管理機構が1つに統一される（環境も Git も sops）。仕組みを複数作らない（D3/D4 の精神）
- (+) 暗号化済みファイルを git 管理でき、構造変更がレビュー可能。age 鍵1つでヘッドレス運用が完結する
- (+) 秘密がエージェントに漏れない（I1「ずるは不可能にする」の土台）
- (−) age 秘密鍵の管理・バックアップ・ローテーション運用が必要（鍵を失うと復号不能）
- 方針変更はこのADRの supersede を要する
