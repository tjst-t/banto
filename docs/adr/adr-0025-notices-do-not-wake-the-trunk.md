# ADR-0025: 知らせは**幹のターンを起こさない**。用件ごとの枝で受ける

> status: **accepted**（2026-08-15。PO 裁定。訂正を2度反映した最終形）。
> 決定番号は **120〜126**。当時 ADR-0026「道具からの一本の入口」が名乗っていた 119
> （現・決定133「弁は watcher ではなく『積む口』に付ける」）の続きとして採ったもので、
> **これが決定番号の衝突そのものの原因**——並走した枝がそれぞれ別の ADR を「直前」と
> みなして採番した。2026-08-16 に ADR-0026 側を 127〜137 へ振り直し（task-0159・imp-0073）、
> 以後は `docs/adr/**` を走査した**最大 +1** から採る。本 ADR の番号は動かしていない。
> **ADR-0010 決定29 を改訂する**——(a)〜(c) はそのまま。改めるのは (d) の
> 「番頭は会話に出す」の**宛先**だけ。

## 文脈

PO の訴え（2026-08-15、幹「電卓開発」にて）：

> 知らせへの対応は自動でやってほしいから札にするは無し。一方で知らせが来た時も
> ユーザへの対応はしてほしい。だから、知らせへの対応は枝でやるほうがいいと考えている。
> ……やってると私が会話できないので、枝でやってほしいということ。

**目標は「幹は常に入力を受けられる」かつ「知らせへの対応は止めない」。** 手段は
対応の場所を幹から枝へ移すことであって、対応をやめることではない。

### 何が起きていたか（実測・2026-08-15）

決定29 は職人の報告を**起動元の会話へ配る**と決めた。起動元が幹なら幹へ配られ、
**知らせ1件につき幹のターンが1本**回る。番頭が答えている間、幹は塞がる——PO は
自分の幹に話しかけられない。ここに Kobo の進捗・env の知らせ・system の再起動通知が
重なる。帳場に届いた知らせは、文字量の **76% が職人の報告**だった。

稼働ホストの台帳（`/var/lib/banto/turns.jsonl`、T1 で導入）から、改修前の幹の姿：

| 出所 | 幹のターン | busy |
|---|---|---|
| `kobo` | 2本 | 53秒・96秒 |
| `worker` | 1本 | 85秒 |
| `system` | 2本 | 1.3秒・1.4秒 |

`po` / `thread`（会話そのもの）を除いた**知らせ由来の幹のターンが 5本**。1本が
1〜2分塞ぐので、幹はその間ずっと返事をしない。

## 決定

### 決定120: 知らせは**幹のターンを起こさない**（決定29d の宛先の改訂）

知らせ（職人の報告・質問／Kobo の進捗／env／system）が幹へ配られようとしたら、
**幹ではなく枝へ配る**。決定29 の (a) 事実と主張を分ける・(b) 質問はまず起動元が受ける・
(c) イベントログ＋購読、は**変えない**。改めるのは「番頭は会話に出す」の会話が
**どれか**だけである。

**逃がすのは「幹へ配られようとしている知らせ」だけ。** 宛先が既に枝ならそのまま配る
（枝の中で委譲した報告が枝へ返るのは、もともと正しい形）。

### 決定121: 枝の立ち方は**2通りだけ**。常設の受け皿は設計に存在しない

| | 鍵 | 配り先 | 閉じるとき |
|---|---|---|---|
| ① | **割り出せる**（`taskId` / 職人の `sessionId` / `envId`） | その鍵の枝。開いていなければ**機構が立てる** | **鍵が終端に達したら**（職人 closed・タスク closed/merged・環境 teardown） |
| ② | **割り出せない**（system の通知など） | **その知らせ1件のための枝**を立てる | **捌いたら**。次の鍵無しの知らせは、また別の新しい枝 |

**常設の枝・受け皿・溜め place は作らない**（PO 訂正 ×2）。常設が悪い理由は三重：
(1) 文脈が積み上がり、**古い文脈を抱えたまま新しい知らせに対応する** (2) 章立て・
自動コンパクションと二重に畳む (3) 無関係な件が1本に混ざる。

②が1件で閉じてよい理由は、**鍵が割り出せない＝続きが来ても同じ枝に結びつけようが
ない＝その1件で終わる用件**だから。

①を知らせ1件ごとに閉じてはならない理由は、質問に答えて即閉じると**次の完了報告が
「自分の答えを知らない枝」に入る**から。

### 決定122: 畳むのは番頭。機構は「畳んでよい」と分かる印を添えるところまで

閉じる条件は決まっているが、**機構は勝手に畳まない**——`thread.merge` は結論を要求する
道具であり、機構が畳めば**結論を捏造する**ことになる。機構がやるのは、終端に達した
知らせに印を添えることだけ。

### 決定123: PO の発話と他の幹からの言伝は**幹のまま**

`thread.send`（出所 `thread`）と PO の発話は**知らせではなく会話そのもの**なので、
幹で受ける。幹から会話を取り上げるのがこの ADR の目的ではない。

### 決定124: 枝の本数で `thread.open` を**断らない**

用件ごとに枝を立てる以上、上限で断ると**弾かれた知らせが行き場を失う**。上限は
促す／警告する側に寄せる（画面の `HOLD_SHOWN=6` と揃える）。入り口で断るのは、
促しの効き目を測ってからでよい（決定126）。

### 決定125: **道具の呼び出しの続き**は知らせではない——呼んだ会話へ返す

`system.restart` の一言のように、**番頭自身が呼んだ道具の結果として返ってくるもの**は
知らせの経路に載せない。知らせとして扱うと、自分の道具の返事が別の枝へ飛ぶ。
呼んだ会話（幹でも枝でも）へそのまま返す。

### 決定126: 効き目は**台帳で測る**（言い分ではなく数字で）

`turns.jsonl` に1ターン1行（`threadId` / `threadKind` / `source` / `durationMs` /
`ok`）を残し、`npm run turn-report` で日ごとに読む。判定に使うのは
**「`threadKind: "trunk"` の行に `worker` / `kobo` / `env` / `system` が出ていないか」**。

幹で手を動かしたときの促し（T4）も同じ台帳で数える——`nudges`（`delegate` / `browse`）と
`browseNudgeAt`。**`nudgedTurns.browse` と `afterBrowseNudge.turns` の比**が「促されたのに
幹で続けた割合」で、断る側へ寄せるかどうかの根拠になる。項目の無い古い行は 0 として
数える（無いものを「促した」に化けさせない・I1）。

## 認めた割り切り

1. **「幹での委譲を断っても幹のターンは減らない」。** 断られた番頭はその場で枝を開いて
   やり直すので、むしろ1本増える。減るのは「報告が幹へ来る」分——PO が幹で「やって」と
   言い、番頭が「枝を開いた」と返す1往復は**会話そのもの**なので消さない。
2. **文脈は継がない。** 用件の枝に要るのは幹の会話履歴ではなく、`kobo.task` /
   `worker.events` で引ける事実。だからセッションの fork は要らない（記憶は `trunkId`
   で共有される）。
3. **T4 は促しであって禁止ではない。** 一発で終わる確認まで枝にすると往復が増える。
   効き目が足りなければ断る側へ寄せる——その判断は決定126 の数字が出てからにする。

## まだ確かめていないこと

- **`env` の知らせが `envId` の枝へ入ること**の実地確認。稼働ホストの台帳には
  `source: "env"` の行がまだ1本も無い（期限切れ待ち）。**出ていないものを「枝へ入った」
  とは読まない**（I1）。
- T4（`efdb9cdf` / `6d0990d0`）は**まだ稼働ホストに載っていない**。載せた後の台帳で
  促しの数を見る。
