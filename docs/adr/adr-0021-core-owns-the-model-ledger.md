# ADR-0021: **モデルの台帳は核が持つ。**バックエンドは供給元になる

> status: **proposed**（2026-08-13）。ADR-0020 決定88（層を分ける）・決定98d
> （バックエンドが名乗る）の続き。決定番号は 98 の続きから採る。
> **ADR-0004（使えるLLMは全体設定）の「全体設定」が何を指すかを改訂する。**

## 決めたいこと

PO の問い（2026-08-13）:

> 職人や番頭の設定画面を独立させたのに、LLMモデルのところに番頭や職人の既定を
> 設定できるのは二重管理になってない？
>
> いま、バックエンドを核から切り離して差し替え可能とした。となると、設定画面の作りも
> 抜本的に変わるべきなのかも。**いまある LLM モデルはそもそも pi coding agent の
> バックエンドの仕組み**で、Claude Code のバックエンドの仕組みは別にあり、それぞれが
> どんなプロバイダ・どんなモデルを提供するかを核に提示し、それに対して番頭・職人で
> 何を使えるようにするか、何を既定で使うかを決める——というのが正しい形では？

**その通りである。** 以下は、いまそうなっていないことの測定と、正しい形の定義。

## 文脈：継ぎ目が1つ手前にある

`LlmCatalog`（`llm-registry.json`）は **pi バックエンドの台帳**である。プロバイダの登録・
鍵・`models.json` の取り込み・文脈長の手入力——どれも pi 固有の関心事。ところがそれが
**核のモデル台帳の位置**に置かれている。そこから3つの症状が出る。

### 症状1: 採用の旗を Claude に立てられない（コードが自分で書いている）

```ts
// llm-registry.ts setRole()
// 採用（policy）は **pi のモデルにだけ**立てる。Claude Code のモデルは
// LLM 登録（models.json 由来）に載らないので、採用の旗を立てる先が無い
```

### 症状2: 「バックエンド横断のモデル一覧」が3箇所に別実装

| 場所 | 何を集めているか |
|---|---|
| `pool.ts selectableModels()` | 工房のランタイムが名乗るモデル ＋ LLM 登録の採用済み |
| `bin.ts harnessBackends` | 番頭のハーネスが名乗るモデル（決定98d で作ったばかり） |
| `LlmRegistryViewer` | **LLM 登録だけ**——横断していない |

同じ問い（「いま選べるモデルは何か」）に3つの実装が別々に答えている。

### 症状3: 二重管理が実データで食い違い、片方が黙って負けている（実測 2026-08-13）

`pool.ts:782` は `input.model ?? 工房の assignedModel(tier)` の順で解くので、
**工房が勝つ**。LLM 登録の `roles["worker.*"]` は工房の割り当てが空のときしか読まれない。

| 等級 | 実際に走る（工房・勝つ） | LLM 画面が見せている（負ける） |
|---|---|---|
| reasoning | `opus`（Claude Code） | `opencode-go/kimi-k3` |
| standard | `sonnet` | `opencode-go/deepseek-v4-flash` |
| fast | `haiku` | `opencode-go/mimo-v2.5` |

**LLM 画面で「職人の通常」を選び直しても、職人は何も変わらない。**

加えて番頭側：`llm.set_role` には `backend` の引数が無く、`setRole` は役の欄を丸ごと
置き換えるので、**LLM 画面から選ぶと backend が落ちて pi に戻る**（実測）。

```
設定画面で選んだ後 : {"backend":"claude-agent-sdk","provider":"claude","model":"opus"}
LLM画面で選び直した後: {"provider":"opencode-go","model":"deepseek-v4-flash"}
```

**症状1〜3 は別々の不具合ではない。** どれも「pi の台帳を核の台帳として使っている」ことの
現れである。

### なぜこうなったか（記録として）

`pool.ts` に理由が書いてある——「Claude のモデルは『LLM・モデル』の画面に並べられず、
職人の既定をひとつの表で見られない」（PO要望 2026-08-10）。**当時は正しい判断だった。**
決定98d でバックエンドが自分のモデルを名乗るようになり、その前提は消えている。

## 決定

### 決定99: **供給**と**役の決定**を分ける。継ぎ目はここ

```
供給（誰が何を出せるか）              役の決定（誰が何を使うか）
────────────────────────         ────────────────────────
pi バックエンド                       番頭：既定1つ ＋ 採用
  └ プロバイダ登録・鍵・取り込み       職人：等級ごとに既定 ＋ 採用
    ・文脈長・等級
Claude Code バックエンド
  └ 聞けば返る（決定98d）
```

- **供給はバックエンドの持ち物。** そのバックエンドに固有の管理（鍵・到達先・取り込み）は
  そこにしか無いし、そこにしか要らない
- **役の決定は核の持ち物。** 「番頭が何を使うか」「職人の等級に何を当てるか」は
  バックエンドを跨ぐ問い——`opus` を pi 経由で呼ぶか Claude Code 経由で呼ぶかまで含めて
  1つの答えになる（決定95a）
- **提示は導出**（D3）。核はモデルの一覧を保存しない。供給元に聞いて組む

**ADR-0004 の「使えるLLMは全体設定」は、この分け方に読み替える**——「全体設定」が
指していたのは役の決定であって、プロバイダの登録ではない。

### 決定100: 供給の名乗りは **層ごと**にある（1つに畳まない）

ADR-0020 決定88 の2層がそのまま効く。

| 層 | 供給の名乗り | 実装 |
|---|---|---|
| 番頭（会話） | `BantoHarness` の実装 | `HarnessBackendDescriptor`（決定98d・実装済み） |
| 職人（プロセス） | `RuntimeDriver` の登録 | `RuntimeRegistration.models()`（実装済み） |

**同じ名前のモデルが両方に出るのは正しい。** 番頭の pi ハーネスと職人の pi ドライバは
別物で、片方だけ使える構成がありうる（例：職人だけ Claude Code に寄せる＝いまの実機）。

**pi のプロバイダ登録（`llm-registry.json`）は、両方の層が読む共有の供給元**である。
これは既にそうなっている（`ensureLoaded` の注記：「同じオーバーレイを複数のプロセスが
読む——番頭ホストが画面から書き、職人の工房が読む」）。

### 決定101: 役の決定は**1つの台帳**に集約する。`roles["worker.*"]` と工房の `tierAssignments` を統合

**書き先はここ1つ**：

```ts
// 役 → 使ってよい集合（採用）と、既定の1つ
interface RoleBinding {
  default?: ModelRef;              // backend/provider/model（決定98c：3成分のまま）
  adopted: ModelRef[];             // 空＝既定だけ使う
}
type Roles = Record<"steward" | "worker.reasoning" | "worker.standard" | "worker.fast", RoleBinding>;
```

- **採用（policy）は役ごとに持つ。** いまの `hostUsable`/`workerUsable` → `policy`
  （決定98b）は「モデルの属性」として持っていたが、これは**役の決定**である。
  役の側に置けば Claude のモデルにも旗が立つ（症状1が消える）
- **等級（tier）は役の一部。** `worker.<tier>` が役の名前そのものなので、工房が
  `tierAssignments` を別に持つ理由が無くなる

#### ブローカーにはならない（決定27 との関係を確かめた）

懸念は「工房が役の決定を引くために Banto へ依存する＝決定27 が避けた依存の逆転」だが、
**工房は台帳のファイルを直接読んでいる**（`LlmCatalog` を工房のプロセスが開く。task-0066）。
Banto が落ちていても読める。したがって集約しても Banto は経路に入らない。

**ただし前提が1つある**：台帳が同一ホストのファイルであること。工房を別ホストへ出す日が
来たら、この前提は崩れる——そのときは「核が押す（変更時に工房へ写しを配る）」へ移す。
**いま先回りしない**（P1）。

### 決定102: 画面は「供給の面」と「役の面」に割り直す

| 面 | 何を出すか | いまどこにあるか |
|---|---|---|
| **バックエンド（供給）** | 一覧・入切・状態。各バックエンドが自分の面を宣言する | 工房の `WorkerSettings` に一部 |
| ├ pi の面 | プロバイダ登録・鍵・取り込み・文脈長・等級 | **いまの「LLM・モデル」画面**（`LlmRegistryViewer`） |
| └ Claude Code の面 | 認証の状態だけ（ほぼ空） | 無い |
| **役（核）** | 番頭・職人の等級ごとに、採用と既定を決める1枚 | 3箇所に分散（下記） |

**いまの「LLM・モデル」画面は、実体が pi バックエンドの面である。** 役割の割り当て
（番頭の Select・「番頭」チップ・「職人の◯◯」チップ）はそこから外し、役の面へ移す。

これは**決定96（設定画面は3段＋ポリシー）と同じ形**である。決定96 の「2. プロバイダと
資格情報」＝供給の面、「3. 役割へ割り当て」＋「4. ポリシー」＝役の面。いまは 2 と 3 が
pi 専用の面に混ざっているのが問題だった、と読み替えられる。

### 決定103: `ModelRef` は3成分のまま（決定98c を引き継ぐ）

役の台帳の鍵も `backend/provider/model`。**`backend` を落とす経路を作らない**
——`llm.set_role` に `backend` を足す（いま引数が無いのが症状3の後半）。

## 移行（実機の実数・2026-08-13）

| 移すもの | 件数 | 移行先 |
|---|---|---|
| `models[*].policy`（pi のモデルの採用） | 87件（うち host 30・worker 26） | 役ごとの `adopted` |
| `roles`（番頭1 ＋ 職人3） | 4件 | 新しい役の台帳 |
| 工房の `tierAssignments` | 3件 | 同上。**食い違っているので、どちらを正とするか要裁定** |

**食い違いの扱いが唯一の判断点**：実機では工房（Claude の opus/sonnet/haiku）が
実際に走っている。**走っているほうを正とする**のが安全（黙って職人のモデルが変わらない）。

## 段取り

1. **役の台帳を核に作り、書き手を1本にする**（`llm.set_role` に `backend`）。
   工房は新しい台帳を読む。**画面は据え置き**——挙動が変わらないことを試験で押さえる
2. **工房の `tierAssignments` を廃す**。ここで症状3（食い違い）が消える
3. **画面を割り直す**（供給の面／役の面）。ここで初めて見た目が変わる

**1と2を分けるのは、職人の起こし方が壊れると工場が止まるから。** 常に動く工房を
手元に残したまま進む（ADR-0020 の段取りと同じ考え方）。

## 未決

1. **採用（`adopted`）を役ごとに持つと、337件あるプロバイダで役の数だけ選び直すことになる。**
   「供給の側で一度採用し、役の側で絞る」の二段にするか、役ごとに一本化するか
2. **工房を別ホストへ出す日の台帳の配り方**（決定101 の前提が崩れたとき）。いまは決めない
3. **バックエンドが設定面を宣言する仕組み。** モジュールの `ModuleSettingsSpec` に相乗りするか、
   バックエンド用の枠を作るか（バックエンドはモジュールではない）
