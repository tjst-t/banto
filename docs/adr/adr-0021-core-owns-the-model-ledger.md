# ADR-0021: **モデルの台帳は核が持つ。**バックエンドは供給元になる

> status: **proposed**（2026-08-13。**レビュー反映の第二版**）。ADR-0020 決定88（層を分ける）・
> 決定98d（バックエンドが名乗る）の続き。決定番号は 98 の続きから採る。
> **ADR-0004 の「使えるLLMは全体設定」が何を指すかを改訂し、ADR-0020 決定98e
> （職人の既定等級は工房が持つ）を部分的に反転する。**

## 決めたいこと

PO の問い（2026-08-13）:

> 職人や番頭の設定画面を独立させたのに、LLMモデルのところに番頭や職人の既定を
> 設定できるのは二重管理になってない？
>
> いま、バックエンドを核から切り離して差し替え可能とした。となると、設定画面の作りも
> 抜本的に変わるべきなのかも。**いまある LLM モデルはそもそも pi coding agent の
> バックエンドの仕組み**で、Claude Code のバックエンドの仕組みは別にあり、それぞれが
> どんなプロバイダ・どんなモデルを提供するかを核に提示し、それに対して番頭・職人で
> 何を使えるようにするか、何を既定で使うかを決める——というのが正しい形では？

**その通りである。** 以下は、いまそうなっていないことの測定と、正しい形の定義。

## 文脈：継ぎ目が1つ手前にある

`LlmCatalog`（`llm-registry.json`）は **pi バックエンドの台帳**である。プロバイダの登録・
鍵・`models.json` の取り込み・文脈長の手入力——どれも pi 固有の関心事。ところがそれが
**核のモデル台帳の位置**に置かれている。そこから症状が出る。

### 症状1: 採用の旗を Claude に立てられない（コードが自分で書いている）

```ts
// llm-registry.ts setRole()
// 採用（policy）は **pi のモデルにだけ**立てる。Claude Code のモデルは
// LLM 登録（models.json 由来）に載らないので、採用の旗を立てる先が無い
```

同じ形の `backend === undefined || backend === "pi"` が**3箇所**にある
（`llm-registry.ts:579` / `:840` / `:1352`・`:1369`）。**同じ if が3つ出てきたのは、
型が間違っている合図。**

### 症状2: 「何が選べるか」に答える実装が **5箇所**

| 場所 | 何を集めているか |
|---|---|
| `pool.ts:588-614` `selectableModels()` | 工房のランタイムの名乗り ＋ LLM 登録の採用済み |
| `bin.ts:826-833` `harnessBackends` | 番頭のハーネスの名乗り（決定98d） |
| `LlmRegistryViewer.tsx:373,424` | **LLM 登録だけ**——横断していない |
| `llm.resolve`（`llm-tools.ts:248-291`） | LLM 登録の `roles["worker.*"]`。**番頭に渡る4本の1つ** |
| 工房の起動ログ（`worker-pool/bin.ts:121,220`） | 同上 |

後ろ2つは**画面が嘘をつくより悪い**——番頭の判断そのものが誤情報の上に乗る。実機の
journal に出ている行がその証拠で、**1行に2つの嘘**がある:

```
[worker-pool] 職人の既定モデル: opencode-go/deepseek-v4-flash（standard）
   実際は defaultTier: reasoning ／ tierAssignments.reasoning: opus
```

### 症状3: 職人のモデルを決める層が **3つ**あり、実データで食い違っている（実測 2026-08-13）

**（第一版の訂正）** 初版は「工房が勝ち、LLM 画面が負ける」と2者で書いたが、**誤り**。
実際の優先順位は3段で、**稼働機で最も多い経路（Kobo 起点）では Kobo が勝つ**。

| 段 | 持ち主 | 実機の値 | いつ効くか |
|---|---|---|---|
| 1 | **Kobo** `roleAssignments`（`kobo-settings.json`） | executor / rework / audit **すべて `opus`** | Kobo が起こす職人（＝工場の主経路） |
| 2 | **工房** `tierAssignments`（`worker-pool/settings.json`） | reasoning `opus` / standard `sonnet` / fast `haiku` | **番頭起点で、番頭が `model` を名指ししなかったとき**だけ |
| 3 | **LLM 登録** `roles["worker.*"]` | opencode-go の kimi-k3 / deepseek-v4-flash / mimo-v2.5 | 段2が空のときだけ。しかも空なら `planModel` が `defaultBackend`（実機 `claude-agent-sdk`）へ落ちるので、**実機では原理的に到達しない** |

根拠：`daemon.ts:1706-1722`（`...(assigned.model ? { model: assigned.model } : {})`）→
`pool.ts:781-782`（`input.model ?? assignedModel(tier)`）→ `pool.ts:694-695`（`defaultBackend`）。

**LLM 画面で「職人の通常」を選び直しても、職人は何も変わらない。**

### 症状4: 番頭の束縛は入口ごとに書く形が違う

`llm.set_role` には `backend` の引数が無く（`llm-tools.ts:353-359`）、`setRole` は役の欄を
丸ごと置き換える（`llm-registry.ts:583`）。**LLM 画面から選ぶと backend が落ちて pi に戻る**（実測）。

```
設定画面で選んだ後 : {"backend":"claude-agent-sdk","provider":"claude","model":"opus"}
LLM画面で選び直した後: {"provider":"opencode-go","model":"deepseek-v4-flash"}
```

**症状1〜4 は別々の不具合ではない。** どれも「pi の台帳を核の台帳として使っている」ことの現れ。

### なぜこうなったか（記録として）

`pool.ts` に理由が書いてある——「Claude のモデルは『LLM・モデル』の画面に並べられず、
職人の既定をひとつの表で見られない」（PO要望 2026-08-10）。**当時は正しい判断だった。**
決定98d でバックエンドが自分のモデルを名乗るようになり、その前提は消えている。

## 決定

### 決定99: **供給**と**役の決定**を分ける。継ぎ目はここ

```
供給（誰が何を出せるか）              役の決定（誰が何を使うか）
────────────────────────         ────────────────────────
pi バックエンド                       番頭：既定1つ ＋ 採用
  └ プロバイダ登録・鍵・取り込み       職人の等級：等級ごとに既定 ＋ 採用
    ・文脈長・等級（モデルの属性）
Claude Code バックエンド
  └ 聞けば返る（決定98d）
```

- **供給はバックエンドの持ち物。** そのバックエンドに固有の管理（鍵・到達先・取り込み）は
  そこにしか無いし、そこにしか要らない
- **役の決定は核の持ち物。** ただし**適用範囲は下記99a に限る**
- **提示は導出**（D3）。核はモデルの一覧を保存しない。供給元に聞いて組む

**ADR-0004 の「使えるLLMは全体設定」は、この分け方に読み替える**——「全体設定」が
指していたのは役の決定であって、プロバイダの登録ではない。

#### 決定99a: **既定は核が持ち、呼び出し側のモジュールが上書きできる**（PO裁定 2026-08-13）

> 職人のデフォルトは任意のモジュールから呼ぶものとして規定は作っておく一方で、
> 呼び出す側のモジュールで規定を上書きはできるようにしておく。実装やレビューなど、
> 用途ごとに好きなモデルを持てるようにするのは正しい。

つまり**2段**である。

| 段 | 持ち主 | 何を答えるか |
|---|---|---|
| 既定 | **核** | 「誰も指定しなかったら、その等級の職人は何で走るか」 |
| 上書き | **呼び出し側のモジュール** | 「この用途では、この役は何で走るか」（Kobo の `executor` / `rework` / `audit`） |

**これは例外ではなく一般則である。** 初版は Kobo を「決定27 の壁の向こうにある特例」として
書いたが、正しくは**どのモジュールも自分の用途ごとの役を持ってよい**——ただしその決定は
そのモジュールが持ち、核へは寄せない。核が答えるのは「指定が無いとき」だけ。

機構としては既にそうなっている（`daemon.ts:1706-1722` が `model` を渡し、
`pool.ts:781-782` の `input.model ??` がそれを優先する）。**この形を正典として明文化する。**

したがって核の役の台帳が持つのは `steward` と `worker.<tier>` まで。Kobo の
`roleAssignments` は移さない——寄せると **Kobo が Banto へ依存する**（決定27(b)(c) が
不採用にした依存の逆転）。Kobo は選択肢の照合を工房へ聞いており（`kobo-settings.ts:59-67`）、
Banto は経路に入っていない。**この向きを壊さない。**

Kobo の `executor` / `rework` / `audit`（`kobo-settings.ts:26-42`）は **Kobo が持つ**
（PO裁定 2026-08-10）。核へ寄せると **Kobo が Banto へ依存する**——決定27(b)(c) が
不採用にした依存の逆転そのもの。Kobo は選択肢の照合を工房へ聞いており
（`kobo-settings.ts:59-67`）、Banto は経路に入っていない。**この向きを壊さない。**

したがって「役の決定は核が持つ」は**全部ではない**。核が持つのは
「番頭が何を使うか」と「職人の等級に何を当てるか」まで。

### 決定100: 供給の名乗りは **層ごと**にある（1つに畳まない）

ADR-0020 決定88 の2層がそのまま効く。

| 層 | 供給の名乗り | 実装 |
|---|---|---|
| 番頭（会話） | `BantoHarness` の実装 | `HarnessBackendDescriptor`（`harness-backends.ts:40-49`・実装済み） |
| 職人（プロセス） | `RuntimeDriver` の登録 | `RuntimeRegistration.models()`（`backends.ts:44-45`・実装済み） |

**同じ名前のモデルが両方に出るのは正しい。** 番頭の pi ハーネスと職人の pi ドライバは
別物で、片方だけ使える構成がありうる（実機がまさにそれ）。

**pi のプロバイダ登録（`llm-registry.json`）は、両方の層が読む共有の供給元**である
（`ensureLoaded` の注記・`worker-pool/bin.ts:114-118`）。

#### 決定100a: **バックエンドの id 空間を契約で揃える**

（レビュー指摘）いま番頭層は `pi` / `claude-agent-sdk`（`harness-backends.ts:80,186`）、
職人層は `pi-rpc` / `claude-agent-sdk`（`pool.ts:320`・`naming.ts:14`）で、橋渡しは
工房の中の `RUNTIME_ALIASES`（`pool.ts:288-294`）だけ。**核は知らない。**

役の台帳が両層の束縛を1つの表に入れる以上、**id は契約で共有する**（正準 id を core に置き、
各層はエイリアスを持ってよい）。揃えないと、3つ目のバックエンドが層ごとに違う id で
登録された瞬間に、保存された台帳が片方の層で解決できなくなる。

### 決定101: 役の決定は**1つの台帳**に集約する（範囲は99a）

```ts
interface RoleBinding {
  default?: ModelRef;              // backend/provider/model（決定98c：3成分のまま）
  adopted?: ModelRef[];            // 未指定＝既定だけ使う
  constraints?: ModelConstraints;  // 決定101b
}
```

- **採用（policy）は役ごとに持つ。** いまの `policy`（決定98b）は「モデルの属性」として
  持っていたが、これは**役の決定**である。役の側に置けば Claude のモデルにも旗が立つ
- **等級（tier）は役の名前の一部。** `worker.<tier>` が役名そのもの。工房が
  `tierAssignments` を別に持つ理由が無くなる ＝ **ADR-0020 決定98e の「職人の既定等級は
  工房が持つ」を反転する**（決定99a：既定は核、上書きは呼び出し側）

#### 決定101a: 台帳は**別ファイル**に置き、**版印を持つ**

（レビュー指摘）`llm-registry.json` に同居させると、決定99/102 が「pi の面」と呼んだ
入れ物に核の台帳が混ざり、分離が保存層で成立しない。**`roles.json`（仮）に分ける。**

**版印（`schemaVersion`）を必ず持つ。** 番頭ホストと工房は**別サービスで再起動が独立**し、
工房は mtime で**走行中に読み直す**（`llm-registry.ts:893-899`）。版印が無いと、
古い版のコードが新しい形のファイルを読み、**黙って別のモデルで走る**——
`resolveForWorker` は `pick.provider` が引けないと候補の先頭へ落ち（`:815-819`）、
`pi-rpc-driver.ts:256-259` は起動時の写しへ落ちる。**どちらもエラーにならない**（I2 違反）。

**読み手は版が違えば止まる。** 併せて**再起動順を段取りに書く**（下記）。

#### 決定101b: 制約（`ModelConstraints`）の置き場は**役**

（レビュー指摘）`vision` / `local` / `free` は供給側のモデル属性だが、
**「この役はローカルのみ」という条件は役の決定**である（ADR-0004 が明示的に狙っている）。
`adopted` で代用すると「制約は決して緩めない」（`llm-registry.ts` I2）が
「採用集合に無い＝落ちる」に化け、`droppedPick` / `usedFallbackTier` の説明が意味を失う。

#### 決定101c: 役の欄は**部分更新**にする

（レビュー指摘）症状4 の原因は `backend` 固有ではなく、`setRole` が**役の欄を全置換する**
こと（`llm-registry.ts:583`）。`RoleBinding` にすると同じ形で「既定を変えたら採用集合が
消える」が起きる。**書き口を部分更新にし、`roles` へ書く7経路すべてをそこへ通す**
（`llm.set_role` / `core-settings` / `bin.ts` の移行 / `repairDefaults` / `migrateRoles` /
`migrateWorkerDefault` / `migrateOnce`。うち `backend` を運ぶのは2つだけ）。

#### 決定101d: 工房は**読むだけ**を機構で担保する

（レビュー指摘）`saveOverlay` は全文上書きで、工房も migration 経路から書きうる。
役の台帳を同じ機構に載せるなら、工房側の口を読み取り専用にする（いまは慣習）。

#### ブローカーにはならない（範囲99a に限れば）

工房は台帳のファイルを直接読んでおり（`worker-pool/bin.ts:114-118`）、Banto が落ちていても
読める。**ただし前提が2つある**：

1. **同一ホストのファイルであること。** 工房を別ホストへ出す日は「核が押す」へ移す。
   いま先回りしない（P1）
2. **書きと検証は逆向き。** 「職人の等級に当てられるモデル」の照合は工房が持つ
   （`pool.ts:666-673` が `selectableModels()` と突き合わせる）。役の面を核へ移すと、
   核は `worker.models` を HTTP で聞くことになる＝**工房が落ちている間は役の面が編集できない**。
   Kobo の設定画面が既に同じ性質を持っている（届かなければ自由入力に落ちる・
   `kobo-settings.ts:62-66`）ので、**同じ逃げ道を採る**

### 決定102: 画面は「供給の面」と「役の面」に割り直す

| 面 | 何を出すか | いまどこにあるか |
|---|---|---|
| **バックエンド（供給）** | 一覧・入切・状態 | 工房の `WorkerSettings` に一部 |
| ├ pi の面 | プロバイダ登録・鍵・取り込み・文脈長・等級 | **いまの「LLM・モデル」画面** |
| └ Claude Code の面 | 認証の状態だけ（ほぼ空） | 無い |
| **役（核）** | 番頭・職人の等級ごとに、採用と既定を決める1枚 | **3箇所に分散**（`LlmRegistryViewer.tsx:420` の番頭 Select ／ `:745` の番頭チップ ／ `:759` の職人の等級チップ） |

**いまの「LLM・モデル」画面は、実体が pi バックエンドの面である。** 役割の割り当ては
そこから外し、役の面へ移す。

これは**決定96（設定画面は3段＋ポリシー）と同じ形**である。決定96 の「2. プロバイダと
資格情報」＝供給の面、「3. 役割へ割り当て」＋「4. ポリシー」＝役の面。

#### 決定102a: バックエンドの面は既存の区画機構に乗せる。ただし**項目で書ける範囲**に限る

（レビュー指摘）`sections()` は毎回組み直される（`settings-module.ts:82-100`）ので、
バックエンド1つにつき1区画を核が並べるのは追加の枠なしにできる。**ただし専用ビュー
（`view`）は banto-web の静的レジストリ（`views/registry.tsx:85-106`）でしか解決できない**
——「各バックエンドが自分の面を持ち込む」を真に動的にするのは決定43 の枠を超える別 ADR。

当面は**項目（`fields`）で書ける面に限る**。Claude Code の面は「認証の状態だけ」なので
これで足りる。**区画 id には接頭辞の規約を決める**（`backend:pi` 等。`settings.update` は
id で引くため・`settings-module.ts:171-176`）。

### 決定103: `ModelRef` は3成分のまま（決定98c を引き継ぐ）

役の台帳の鍵も `backend/provider/model`。**`backend` を落とす経路を作らない**
（一般形は決定101c）。

## 移行（実機の実数・2026-08-13）

| 移すもの | 件数 | 移行先 |
|---|---|---|
| pi の採用（`models[*].policy` の**旗**） | **32モデル・56旗**（host 30／worker 26）。overlay のエントリ数87 とは別（`migrateAdoption` が全件にキーを付けるため） | 役ごとの `adopted` |
| `roles`（番頭1 ＋ 職人3） | 4件 | 新しい役の台帳 |
| 工房 `tierAssignments` | 3件 | 同上。**食い違っているので要裁定** |
| Kobo `roleAssignments` | 3件（すべて `opus`） | **移さない**（決定99a：上書きは呼び出し側） |
| 工房 `defaultTier` | 1件（`reasoning`） | 核（決定99a：既定は核） |
| 工房 `defaultBackend` | 1件（`claude-agent-sdk`） | 工房に残す（供給の入切） |

**食い違いの扱い**：実機では Kobo（`opus`）が実際に走っている。**走っているほうを正とする**
のが安全（黙って職人のモデルが変わらない）。

## 段取り

| 段 | 中身 | 完了条件 |
|---|---|---|
| **1a** | 役の台帳を別ファイルに作る（版印つき）。`roles` の形を移し、書き口を部分更新1本に。`llm.set_role` に `backend`。**`policy` は据え置き** | `npm test` 全通過＝**挙動が変わらない** |
| **1b** | `policy` → 役ごとの `adopted`。役を知らない読み手3つ（`llm.list` の `adopted` 既定・`fetch_models` の消失警告・「探して採用」の `scope:"host"` 固定）の意味を決める | 同上 |
| **2** | 工房の `tierAssignments` を廃す。`llm.resolve` と工房の起動ログの誤答を同時に直す | 症状2・3が消える |
| **3** | 画面を割り直す（供給の面／役の面） | 見た目が変わる |

**再起動順**：台帳を書く側（番頭ホスト）を**後**に上げる。工房を先に新しい版へ上げ、
古い形しか読めない版が新しいファイルに出会う窓を作らない。**版印が食い違ったら
読み手は止まる**（黙って別のモデルで走らせない・I2）。

**1a と 1b を分けるのは**、`policy` の読み手が5箇所あり、同じ段で動かすと
「挙動が変わらない」を試験で押さえられなくなるため。

## 未決

1. **採用を二段にするか、役ごと一本か。** 337件あるプロバイダで役の数だけ選び直す体験の
   問題に加えて、**役を知らない読み手が3つある**（`llm.list` を含む）。「採用されている
   モデルは何か」を役抜きで問われたとき、4役の和を取るのか、既定の役に落とすのか
2. ~~工房の `defaultTier` / `defaultBackend` の持ち主~~ → **決定99a で決まった**（既定は核）。
   `defaultTier`（「等級の指定が無いときどの等級か」）は既定なので核へ移す。
   `defaultBackend` は**供給の入切**（どのランタイムを使うか）なので工房に残す
   ——切ってあるバックエンドを核が指せてしまうと、選ばせてから落ちる（I2）
3. **tier のフォールバックの向き。** `resolveForWorker:809-810` は
   `[要求した等級, ...MODEL_TIERS の残り]` の順に見る。`MODEL_TIERS` は
   `["reasoning","standard","fast"]` なので、**`fast` を要求して候補が無いと、次に見るのは
   `reasoning`**——安いつもりが一番高いモデルに落ちる。いまも起きうる。
   採用が役ごとになると、これは「`worker.fast` の要求を `worker.reasoning` の採用集合で
   満たす」ことになる
4. **工房を別ホストへ出す日の台帳の配り方**（決定101 の前提1が崩れたとき）
5. **バックエンドの面を真に動的にするか**（決定102a・決定43 の枠を超える）
