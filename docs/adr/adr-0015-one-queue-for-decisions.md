# ADR-0015: POの判断を求めるものは**取次1つ**。押されたことはその場で効き、番頭が先へ進む

> status: **accepted**（2026-08-09。PO 裁定）。**ADR-0010 決定38(c)(e) の画面側を差し替える。**
> 決定番号は 72（ADR-0014）の続きから採る。

## 文脈

PO の報告（2026-08-09）：

> いま、bantoからの通知がいまいち整理しきれていません。特にbantoのフォルダのアクセス許可が
> 微妙で、基本通知に出てこないよね。あれは既存の通知の枠組みにそろえてほしい。
> （中略）また、アクセス許可とかユーザが判断したら、そのままbantoにその旨通知が言って、
> 自動で先に行くようにしてほしい。
> キャンバスの書き込み許可と、設定の場所(Place)の設定はかぶっている。これは設定側に
> 寄せてほしい。また、全レポジトリで共通の許可（略）をできるようにしてほしい。
> とにかく、全体的にユーザのアクションを求めるアーキテクチャを共通にしてほしい。

### 何が起きていたか（実測）

**受け口は既に1つあった**（取次・spec-design §7）。外れていたのは書き込み許可だけで、
外れ方が3段になっていた：

| | 実際の挙動 | 症状 |
|---|---|---|
| 積む | `place.request_write` は帳簿に書くだけ | 番頭が `canvas.open` で面を出さない限り、POは頼まれたことに気づけない |
| 効かせる | 取次の答えは記録するだけ | 承認は**番頭が呼べない口**（決定29e・38c）なので、誰も呼ばない |
| 知らせる | `broadcast({type:"notice"})` | 画面には出るが**番頭のセッションには入らない**。ターンも回らない |

3段目が一番たちが悪い。`server.notify()` は「記録して配ってターンを回す」のに、
取次の答えだけが `broadcast` を直に呼んでいた——**POから見ると「押したのに進まない」**。

そして書き込み許可の面（`place.permissions`）と設定の「場所」は、同じことを2つの入口で
決められる状態だった。**場所と、そこで書ける範囲は同じ1つの設定**である。

## 決定

### 決定73: 判断を求めるものは取次1つ。**押されたことはホストがその場で効かせる**

- モジュールは自前の「判断を求める画面」を持たない。`inbox.post` へ積む
- 選択肢は**押されたらホストが呼ぶ口**を持てる（`InboxEffect = {module, tool, args}`）。
  呼ぶ先は普通 `internalTools`——番頭には渡していない口を、POが押したときだけ呼ぶ。
  **番頭が自分で押せないことは変わらない**（決定29e・38c は無傷）
- **効かせられなければ畳まない。** 「許した」と記録が残るのに書けないままが最悪
- 答えは `server.notify()` で入れる。記録に残り、**ターンが回る**（＝自動で先に行く）
- 押されたときに何を呼ぶかは**画面へ配らない**（`InboxItemView` は `effect` を落とす）。
  配ると画面から任意の口を叩けることになり、機構で分けた意味が無くなる（I1）
- **判断待ちは、見ているところにも出す。** 面の中と、**会話の入力欄のすぐ上**（固定）。
  流れの中に差し込むと、遡ったとき判断待ちを持ったまま話し続けられてしまう
- 一通は**どこへ飛べるか**を持つ（会話／面／設定）。取次の札からその件の会話へ戻れる
- 同じ用件で札を積み増さないための合印（`key`）を持つ。未解決の同じ合印があれば積まない

**却下した案：番頭に承認の口を渡し、POの答えを解釈させる。** 決定38b の自己昇格が
成立する。「約束させるのではなく、不可能にする」（I1）を崩さない。

### 決定74: 書き込み許可に**全ての場所で効く範囲**を持てる

- `PlaceGrantStore.globalWritable()` を場所ごとの許可に**重ねる**。順序は判定に効かない
- 効く先は**登録された全ての場所**（PO裁定）。リポジトリだけに絞ると「効く場所と効かない
  場所」をPOが覚えることになる
- 足すのではなく**置き換え**（空にできる）。決定38e の `revoke` と同じ理由
- 口は `place.set_global_write`（internalTools）。番頭は自分では広げられない

**なぜ要るか**：無いと、番頭が新しいリポジトリに触るたび同じ承認を繰り返す。それは
**POが中身を読まずに押す習慣**をつくる——決定38e が避けたかったことそのもの。

### 決定75: 書き込み許可は**設定へ寄せる**。キャンバスの面は持たない

- `place.permissions`（キャンバスの面）を廃し、中核の設定区画「場所と書き込み許可」に統合
  （決定43 の枠。項目の宣言では表せないので `view: "PlaceSettings"` を宣言する）
- 1画面に出るもの：保留中の要求／全場所共通の許可／場所ごとの実効範囲と**その出どころ**
  （設定・承認・共通）／場所そのものの足し引き／判断の履歴
- 取次の一通は `opens.settings` を持てる。**開くのは画面**——設定は会話に被さる面で、
  キャンバスのタブではないのでホストからは動かせない
- 中核の設定区画にも `endpointOf` を渡す（決定27 のレジストリ方式）。中核の区画でも
  モジュールの口が要ることがある——場所の許可は workspace が持っている

## 帰結

- 「POの判断待ちはどこにあるか」の答えが1つになった。モジュールが増えても増えない
- 番頭のSKILL から `canvas.open({kind:"place.permissions"})` の手順が消えた——
  頼めば札が立ち、答えが返ってくる
- **ADR-0010 決定38(c)(e) の「番頭が canvas.open で承認の面を出す」は撤回**。
  決定38 の本体（既定は読み取り専用・番頭は頼めるだけ・帳簿は番頭が書けない場所）は無傷
- 効果の実行は「モジュールの帳簿から引いて呼ぶ」ので、Banto はブローカーにならない（決定27）
