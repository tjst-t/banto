# 前の実装で得た教訓

> 2026-08-20 第一版。前の実装（2026-07-23 〜 08-20、4週間、11万行）から、**実装に依存しない
> ものだけ**を持ち込んだ。「前にこうだったから」は理由にしない。実装固有の記録は `main` の
> `work/`（incident 66件・improvement 86件）と `docs/notes/handoff.md` に残っている。
>
> **これは第一版で、私が直接読んだ範囲から書いた。** `work/` の全件を畳み直すのは別途。

## 確かめかた

**1. 偽の実装で試すと、本物の制約が出ない。**
偽ドライバのテストが全通過なのに、本物に差し替えると壊れていた、が短期間に3回起きた。
偽物が本物の制約を持っていない箇所は、**偽物を本物に寄せる**。

**2. ガードのテストが空振りしていないか確かめる。**
「弾かれること」だけを見るテストは、**ガードを外しても通ってしまう**書き方をしやすい。
ガード無しでは本当に通ってしまうことを、一度実行して確かめる。

**3.「単体では通る」も「全部回したら落ちた」も、そのままでは根拠にならない。**
誰の変更で落ちたのかを分離して初めて言える。作業ツリーを他と共有していると、
**他人の失敗を自分のものとして数える**。

**4. 件数で確かめる。**
「動いた」では、落ちた欄に気づけない。移行なら前後の件数を数える。

**5. 自分の推論にも 1 が掛かる。**
「この仕組みはもう使われていない」（3週間触られていないという観測から、意図を推論した飛躍）と、
「トークン浪費はキャッシュミス」（測る前に犯人を決めた）で、**同じ誤りを2回やった**。
どちらも測ったら外れていた。

## 契約と境界

**6. 契約の言葉が同じでも、意味が同じとは限らない。**
`prompt(): Promise<void>` は型としては両方満たすが、片方は「積んだ」で片方は「終わった」だった。
呼ぶ側がどちらの意味に掛けているかを見ないと、境界は嘘をつく。

**7.「誰が勝つか」は、上から順に読まないと分からない。**
2者だと思って測ると、実際に支配している層を見落とす。設定が3層あるとき、
いちばん上が常に埋まっていれば、下の2層は一度も読まれない。

**8. 手で書いた一覧は、書いた瞬間から古くなる。**
モデル名の表を手で持っていたら、実際に問い合わせた一覧と食い違っていた。聞けるものは聞く。

**9. 導出できる値を保存すると、いつか食い違う。**
台帳が4箇所に散った結果、ログが「A で走っています」と言いながら実際は B で走っていた。
**画面が嘘をつくより、機構が嘘をつくほうが悪い**——AI の判断が誤情報の上に乗る。

## 壊れかた

**10.「起きなかったこと」は自動では見つからない。**
自動の文脈圧縮が止まっていたが、**何も失敗しなかったので1か月近く誰も気づかなかった**。
エラーも例外も出ない。ただ起きるべきことが起きなかった。
期待を明示したときだけ検知できる。

**11. 観測は、観測される機構の外側に置く。**
10 が見つからなかったのは、止まった機構と同じ場所に観測が住んでいたから。
実際、外から測ったら（トランスクリプトを畳んだら）**壊れたまま測れた**。

**12. 間欠は、機構が壊れている合図。**
待ちを延ばす・リトライを足す・「まれに落ちる」で先へ進む、のどれもしない。
「既存の不安定さ」は分類であって根拠ではない。根拠は計測（何回中何回落ちるか）。

**13. 例外にならない失敗がいちばん危ない。**
指定が黙って無視される・既定値に落ちる、は誰にも気づかれない。断るなら理由を値で返す。

## 作業のしかた

**14. `git add -A` を使わない。**
共有ツリーでは、他の誰かの未コミット作業を何度も巻き込んだ。ファイルを明示して積む。

**15. worktree の `node_modules` を丸ごと symlink しない。**
自分のパッケージが本体を向き、**自分の変更を読まずに試験が回る**。

**16. 実プロセスで確かめる。**
モジュールの境界は、型が通っても実プロセスで壊れる。とくに最初の1回は本物で叩く。

## 規模について

**17. 4週間で 11万行書けた。**
だから「大きいから捨てられない」は、たいてい成り立たない。捨てる判断のコストは、
思っているより低い。**惜しいのは行数ではなく、行数が証明した外形仕様のほう。**

## 発明の予算

**18. 名前がある問題に、設計の時間を使わない。**
前の実装の失敗の多くは「すでに解かれている問題を、名前を知らないまま解こうとした」形だった
——真実の一元化、外からの監視、名前空間、レジストリ、core とアダプタの分離。
逆に、本当に価値があった判断（会話の構造で平行開発を表す、分岐がプレフィックスを共有する
ので平行試行が安くなる、通知は発生ではなく滞留で鳴らす）は、どの文献にも無かった。
**作る前に一度だけ問う——「これには名前があるか」。**

前の実装で実際に起きた形：

| 起きたこと | 名前 |
|---|---|
| 真実が4箇所に散って食い違った | single source of truth |
| 観測を、観測対象の内側に置いた | 監視は外から（dead man's switch） |
| Tool 名の論理名↔wire 名の変換層を作った | 名前空間で済む |
| モジュール間が O(N²) に結合しかけた | レジストリ |
| core と面が二重実装になりかけた | ports & adapters |

これから当たるものの、名前だけ。**読み込む必要はない**——既知の答えに素早く乗るための一覧：

| 作るもの | 名前 |
|---|---|
| 追記のみのログ＋畳み込みで状態を作る | event sourcing（**CQRS までは採らない**。ログと fold だけでいい） |
| 冪等な step、落ちたら途中から再開 | durable execution（**Temporal の概念だけ。Temporal 自体は要らない**） |
| core ＋2つのアダプタ | ports & adapters / hexagonal |
| 「自分を待っているもの」の一覧 | コードではなく製品を見る（Linear の Inbox、GitHub の notifications。**Slack は反面教師**——発生で鳴らして読めなくなっている） |
| MCP | 仕様書を直接読む。短い |

規則10（依存を足す前に標準ライブラリと既存資産を見る）はライブラリの話。
これは機構・設計パターンの話で、別のもの。

**19. CLI が黙って上書きするように見えても、まず CLI 自身の逃げ道を探す。**
`npx shadcn add` は既存ファイルへの上書きが既定で `false`（実測、`shadcn add --help`）
——黙って壊す設計ではない。実際に `button.tsx`／`index.css` が上書きされたのは、
非対話環境（サブエージェント）で確認プロンプトを `-y`/`--overwrite` で素通りさせた
ときだった。**壊れた原因は CLI ではなく、確認を飛ばした側にあった。**

CLI 自身が非対話利用向けの安全な手順をすでに持っていた：

```
npx shadcn@latest add <component> --dry-run      # 何が上書きされるかを先に見る
npx shadcn@latest add <component> --diff <file>  # 上書き対象それぞれの差分を見る
npx shadcn@latest add <component> --overwrite    # 見てから、要るものだけ許可する
```

**「有名なツールが不用意に人の変更を壊す」と感じたら、まず `--help` を読む。**
エージェント自身が非対話で安全に使うための逃げ道は、作者側もたいてい先に用意している
（規則12 と同じ形——ここでは設計パターンではなく CLI の使い方の話）。
