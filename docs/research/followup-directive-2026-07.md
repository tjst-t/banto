# Banto フォローアップ作業 — 実行指示書（調査資料付き）

この文書はBantoリポジトリ上でClaude Codeに実行させるための指示書である。目的は、(1) 外部オーケストレータ調査（本文書の付録A）の成果を仕様に反映し、(2) v1b候補のタスク定義ドラフトを用意し、(3) 永続データの形に関わる前提を確認することである。

**前提**: 最初のマイルストーン「セッション実行」(daemonコア基盤・契約層とスケジューラ・セッション実行)が完了していること。以降のスプリント(監査・マージ機構、POコックピットv1等)が着手前のこのタイミングで実行するのが最適である——Phase 1の監査対象(イベントログ・spawn台帳・スキーマ)が完成直後で、まだ上物が建っていないため。進行中・未着手スプリントのスコープをこの作業で変更・拡張しないこと。ただしPhase 2で仕様に追記する `ready` クエリと通知イベントについては、「POコックピットv1のスコープに含めるか、v1bに回すか」をPhase 4の完了報告でPOに問うこと(勝手にどちらとも決めない)。

**進め方の原則**(principles準拠):
- 仕様(docs/spec/)への追記はコミットとして行い、POレビューを受ける。黙って実装に反映しない
- 各タスクの scope 外のファイルに触らない。触る必要が生じたら作業を止めてPOに報告する
- 判断に迷う点は勝手に決めず、選択肢を提示してPOに問う(D1)

作業は以下のPhase順に行う。各Phase完了時にコミットを分けること。

## Phase 1: 前提確認(永続データの形。欠けがあればフィールド追加のみ)

以下4点を実装とスキーマに対して目視確認し、結果を `docs/research/v1a-data-shape-audit.md` にまとめる。**機能は実装しない**。欠けている場合はフィールド/構造の追加のみ行い、値の生成は既存コードが自然に書ける範囲に留める。

1. **イベントログ**: 各イベントに (a) プロジェクトタグ、(b) タイムスタンプ、(c) 起点参照(引き金となったPO入力またはイベントのID)のフィールドがあるか。cが無い場合はoptionalフィールドとして追加(既存イベントの遡及埋めは不要)
2. **セッションJSONL**: 実行者・監査等のセッションログが破棄されず、spawn台帳からタスクID→セッションファイルパスを辿れるか
3. **ID名前空間**: タスクIDが `<project>/<id>` 形式で解決可能か。採番がツール/daemon経由に一元化されているか
4. **タスクスキーマ**: `scope.paths` と `refs` フィールドが存在するか

各項目について「OK / フィールド追加した / 構造的問題あり(POに報告)」のいずれかを記録する。「構造的問題あり」の場合はこのPhaseで直さず、問題の説明と選択肢を書いてPOの判断を待つ。

## Phase 2: 仕様書への反映

付録Aの項目A〜Gを各仕様書に追記する。仕様書は `docs/spec/` 配下にある(ファイル名が異なる場合は内容から特定する)。既存の記述と矛盾しないよう、追記位置は各仕様の構成に合わせて調整してよいが、**内容は以下の通りとする**:

### daemon-core仕様
- **[A] ready クエリ**: 「`ready`(依存駆動ゲートを通過し着手可能なタスクの一覧)をdaemon APIの一級クエリとする。検討エージェントの分解判断、ボードのNext表示、spawnスケジューラは同一のこのクエリを参照する」
- **[F] マージキュー将来拡張**(§マージ機構に1段落): 「将来、ゲート実行時間がボトルネック化した場合の既定の進化先はBors型バッチ処理とする: 複数の承認済みタスクを束ねて一括検証し、グリーンなら一括マージ、レッドなら二分探索で失敗タスクを隔離する。v1は直列1件ずつでよい」
- **[G] OTLP注記**(§イベントログのロールアップ付近): 「ロールアップのエクスポート形式はOTLP互換とし、既製の可視化基盤(Grafana等)を利用可能にする。v1では不要、ロールアップ実装時に形式を寄せる」
- **[D] 健康状態taxonomy**(§spawn管理・照合付近、v1.x マーカー付き): 「照合ループはエージェント健康状態を導出する: `working` / `stalled`(進捗低下) / `no-progress`(一定期間無進捗) / `zombie`(セッション死亡) / `idle`。判定はイベント間隔とdiff変化から機械的に行う。介入動詞として `nudge`(注意喚起メッセージ注入)と `handoff`(新セッションへのコンテキスト再注入)をdaemon APIに持つ」
- **[E] ask_predecessor**(status_reporter付近、v1.x マーカー付き): 「status_reporterの姉妹機能として `ask_predecessor` を提供する: 対象タスクの先行セッション(escalate元・conflict元・handoff前)のJSONLログを注入した短命SDKセッションに一問一答させる。呼び出し元は実行者・レビューセッション・PO」
- **[C] 通知イベント**(API節): 「daemonはアテンションカード生成イベントを通知チャネル(層B設定: ntfy等のプッシュ通知)に送出する。通知文はD8に従い経緯1行を含む。対象はカード生成のみ(blocking発生、レビュー待ち、failed、評価カード、定期レビュー)」

### schemas仕様
- **[B] discovered-from規約**(taskとimprovementの節): 「エージェントの作業中に生成されるドキュメント(escalateタスク、incident、friction、design-request)は、`refs` の先頭に発見元タスクIDを必ず含める。生成ツールが自動で付与し、手動生成時は検証で警告する」
- **未決事項に追加**: 「オフライン・daemon不在時のID採番の扱い(必要になればハッシュサフィックス方式)」

### ui仕様
- **[C] 通知の節を追加**: 「アテンションカードの生成をプッシュ通知(携帯到達可能なチャネル)で通知する。通知文は『経緯1行＋カード種別』とし、通知からカードへ直接遷移できること。通知対象・チャネル・静穏時間は層B設定」
- **[D] エージェント画面に健康フィルタ**(v1.x マーカー付き): 「健康状態(stalled/no-progress/zombie)での絞り込みビューを持ち、nudge / handoff を操作として提示する(D7に従いボタンで)」

### 反映しないことの記録
- 付録Aの不採用4件(LLMオーケストレータ、ワークフローエンジン、SQL DB化、フェデレーション)は仕様に追記しない。判断理由は付録Aに記載済みのため、必要ならADRドラフト「外部調査に基づく不採用判断の記録」を1本起こしてPOの承認に回す(起こすか否かはPOに確認する)

## Phase 3: v1b候補のタスク定義ドラフト作成

以下3件のタスク定義ドラフトを作成する(enqueueはせず、draft状態で `work/tasks/` に置き、POレビューに回す)。スキーマは schemas仕様に従い、`refs` にこの指示書と調査文書のIDを含める:

1. **task: ready クエリのAPI/CLI実装**(A)— 受け入れ条件: 依存グラフ・スコープ重複・quotaを反映した一覧が返る / CLIとboardが同一クエリを使う
2. **task: discovered-from自動付与**(B)— 受け入れ条件: /escalate・/incident・report_friction・request_design が発見元taskIDをrefs先頭に自動付与する / 検証ツールが欠落を警告する
3. **task: プッシュ通知**(C)— 受け入れ条件: カード生成でntfy(または層B設定のチャネル)に通知が届く / 通知文に経緯1行が含まれる / 静穏時間設定が効く

D(健康taxonomy)とE(ask_predecessor)はタスク化せず、Laterの候補として調査文書へのポインタをroadmapに1行ずつ追記するに留める。

## Phase 4: 完了報告

以下を含む完了報告を作成しPOに提示する:
- Phase 1の監査結果サマリ(OK / 追加 / 要判断 の件数と、要判断項目の選択肢)
- Phase 2で変更した仕様ファイルとコミット一覧
- `ready` クエリ・通知の「POコックピットv1に含めるか、v1bに回すか」の問い(選択肢と推奨を添えて)
- Phase 3のドラフト3件の所在
- 作業中に発見した仕様と実装の矛盾・欠落(あれば incident としてimprovement-inboxに積む。無ければ「無し」と明記)

## 禁止事項

- 完了済みスプリントの実装コードの機能変更・リファクタリング(Phase 1のフィールド追加を除く)
- 仕様追記を超えた新機能の実装(Phase 3はドラフト作成まで)
- vision / principles の変更(変更が必要と考えた場合はADRドラフトの提案に留める)
