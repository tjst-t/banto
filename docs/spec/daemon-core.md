# Spec: Koboコア

オーケストレータ本体（**Kobo**）の状態モデル、イベントログ、実行制御、マージ機構、稼働形態の仕様。

> **語彙 — Kobo の旧称は daemon** 【2026-07-27・[ADR-0009](../adr/adr-0009-agent-primary-inversion.md) accepted。**この定義が正典**】
>
> **Kobo（工房）＝開発ワークフローの決定論的統治**。イベントソーシング・ステートマシン・ゲート・spawn 執行を担う。`docs/spec/` 全体でこの語を使う。旧称 `daemon` は 2026-07-27 に語彙を統一した。
>
> **ファイル名 `daemon-core.md` とドキュメントID `spec-daemon-core` は据え置く。** ID の張り替えは `refs` を持つ全ドキュメント（spec 4本・ADR・`ROADMAP.json`・`work/` 配下のタスク）へ波及する一方、いつ実施しても結果が同じ**可逆**な作業だからである（D1）。参照は `spec-daemon-core` のまま書くこと。
>
> 4層の中での位置：PO（主人）／**番頭**（記憶あり・PO 代理・差配）／**Kobo**（決定的統治基盤）／**職人**（memoryless worker）。番頭と Kobo の関係は「体験・差配の軸では番頭が主、執行の軸では Kobo が主」——**番頭でも帳簿はごまかせない**（[vision](../vision.md)）。**Kobo と番頭核は完全分離し、Kobo 側から番頭の記憶を直接読む手段は持たない**——番頭が Kobo の状態を必要とするときは、Tool/SKILL 経由の公開クエリ（本仕様 §6）を呼ぶ（ADR-0009 決定①）。

原則：Koboは**決定的なコード**であり、制御ループにLLMを置かない（→ D2）。LLMが必要な判断（分解・要約・診断・分類）はSDK単発セッションをスポットで呼ぶ。

## 1. タスクのステートマシン

```
draft → queued → ready → planning → implementing → auditing
  → review-ready → in-review → approved → merging → merged
  → evaluating → closed
```

横断遷移：
- **paused**：blocking設計依頼の発生時（→ 解決で元の状態へ復帰）
- **failed**：回復不能エラー（→ I2。黙って続行せず止まって台帳に残す）。**ここは行き止まりではない**（→ §1.1）
- **superseded**：escalateによる置換
- **closed（工場の外で決着）**：中身が別の経路で入った・もう要らなくなった・番頭が直接片づけた。**failed とは別物**（→ §1.2）
- **quarantine保留**：検疫マーク領域への新規spawn時の保留勧告（→ spec-improvement-loop §8）

規則：
- `queued → ready`：依存駆動ゲートを通過したもののみ（→ spec-multi-project §3。依存グラフ、スコープ重複×未レビュー祖先、物理quota。数値WIPは存在しない）
- `auditing → merging`：マージポリシーが auto のタスクは in-review を経ずに直行（→ spec-improvement-loop §7）
- `merged → evaluating`：hypothesis を持つタスクのみ。horizon経過後に評価カードを生成
- かんばんの Now / Next / Later はこの状態の集約ビューであり、独立した状態ではない

### 1.0 契約の改訂（ADR-0014・決定69〜72）

**積んだあとの契約は凍結しない。** もとの裁定（決定64）は「訂正は新しいタスクを積み、元を `superseded` にする」だったが、**間違いが直せないので運用が「新しいタスクを立てる」に逃げ、経緯が別 id に分かれて追跡性がむしろ落ちた**（実機の loamium task-0004 → 0005）。凍結が守ろうとしたものを、凍結が壊していた。

代わりに3つを守る：

1. **黙って起きない**——ファイルを書き換えただけでは反映されない（watcher は読み飛ばす）。`kobo.amend` を呼んだときだけ取り込む
2. **記録に残る**——`task_contract_amended` に変更前後・誰が・なぜ、そして**改訂後の契約そのもの**が載る（D3：状態はイベントから作り直せること）
3. **依存するものが差し戻る**——基準が動いたら監査は無効になり `implementing` へ戻る

| 変えたもの | 監査 | 状態 |
|---|---|---|
| `acceptance[].verify` **だけ** | **有効のまま** | 動かさない。マージ前ゲートは元々毎回回る |
| `acceptance[].text` / 条件の増減 / `scope.paths` | **無効** | `implementing` へ戻す |
| `title` / `body` | 影響なし | 動かさない |

**`verify` は「何をもって完了とするか」ではなく「どう確かめるか」。** 基準が正しいまま確かめ方だけ壊れていることがある（実機：基準は「UI の型チェックが通る」で正しく、`verify` に環境の用意 `npm ci` が焼き込まれていた）。ここを区別するのが改訂の主目的。

**緩める方向は PO だけ。** 番頭が通せるのは「検証コマンドの訂正・スコープからパスを取り除く・受け入れ条件を増やす」。PO が要るのは「スコープに新しいパスを足す・基準を変える・条件を消す」。**glob の広い／狭いは文字列では解けない**ので、いまの一覧に無い文字列が増えたら意味に関わらず PO に上げる（間違えてよいのは「厳しすぎる」側）。

**`amend` と `supersede` の使い分け**：**同じ依頼のままなら `amend`**（契約を直して経緯を1本に保つ）、**依頼そのものが別物になったなら `supersede`**（新しいタスクを積み、元を `superseded` にする）。決定64 の改訂で訂正の既定は `amend` に移ったが、`supersede` が要る場面は残る——依頼が入れ替わったのに同じ id に上書きすると、**何を頼まれていたのかが帳簿から消える**。

### 1.1 failed から戻す（task-0081・PO 要望 2026-08-08）

**落ちたタスクを切り直させない。** 落ちるたびに新しいタスクを立てる運用だと、同じ依頼が `task-0004` → `task-0005` → … と別 id に分かれ、**何度目の挑戦なのかが帳簿から読めない**（実機の loamium で実際にそうなった）。番頭が理由を見て、直して、**同じタスクのまま**最後まで通せるようにする。

```
failed → implementing   （rework：中身の問題。職人が直す）
failed → approved       （reverify：検証環境の問題。中身は触らずゲートを回し直す）
failed → closed         （abandon：どうしようもないものを、落ちたまま畳む）
```

契約の改訂による差し戻しも**後ろへ戻る道**として持つ（→ §1.0）：

```
approved / in-review / review-ready → implementing
auditing → planning
```

**前へ飛ぶ道は増やしていない。** 番頭は進められるが飛ばせない（決定62c）。

- **どちらへ戻すかは番頭が選ぶ**（`kobo.reopen` の `mode`）。落ちた理由で変わるものなので、機械が推さない
- **選ぶ前に理由が読める**こと。`kobo.task` は落ちているタスクについて、ゲートの不通過理由に加えて**検証ログの末尾**まで返す——「`verify_failed:a4(exit=1)`」から分かるのは番号だけで、何が起きたかはログにしか無い
- **`reverify` は承認まで行った実績があり、かつそのあと監査を無効にする改訂が無いときだけ**（I2・→ §1.0）。監査を飛ばしてマージ待ちに置けてしまうと、番頭の取り違えで未監査のものがマージされる
- **`rework` では落ちた理由を職人に渡す**。渡さないと同じ失敗を繰り返す
- **`abandon` しても記録は消えない**。経緯には落ちたことも畳んだ理由も残る。畳むと既定の一覧（→ §6）から外れ、「まだ見る必要がある」ふりをしなくなる
- **`abandon` は `failed` 専用ではない**（PO 裁定 2026-08-14）。上の `failed → closed` は元からある道だが、実運用で宙に浮くのは `queued` / `paused` / `review-ready` の方だった——実機の工場に14本が凍り、畳む手段が無かった。そこで `fail()` / `supersede()` と同じ**横断の遷移**にしてある：**`closed` / `superseded` 以外のどの状態からでも畳める**。「もう畳んである」ものを断るのは、二重に畳んだ記録を積み上げないため（I2）。**失敗ではなく工場の外で決着したものは `kobo.settle`**（→ §1.2）
- **戻した回数は帳簿から導出する**（`state_transitioned` の `from: failed` を数える）。新しいイベント種は増やさない。同じところで落ち続けているかが分かるので、P6（同じ試験に2回パッチを当てて定着しなかったら根本原因分析）がここで機械的に判定できるようになる

**`failed` が「終端」なのは「二度と落ちない」の意味**であって「二度と動かない」ではない。`fail()` / `supersede()` は終端状態には効かないままにする（落ちたものをもう一度落とさない）。

### 1.2 工場の外で決着したものを畳む（realign 第2便・imp-0019）

この口を足した当初、**`abandon`（§1.1）は `failed` にしか効かなかった。** だが実際に降ろせなくて困ったのは落ちたタスクではなく、**`queued` / `paused` / `review-ready` のまま中身が別の経路で main に入ったもの**だった。工場を止めていた間に番頭が職人へ直接投げて片づけたタスク群がそれで、**判定を帳簿へ書き戻す手段が無く**、improvement 文書（`work/inbox/improvement/imp-0019`）が代わりの記録になっていた。

**その穴は塞がった**——PO 裁定 2026-08-14 で `abandon` は `closed` / `superseded` 以外のどの状態からでも畳めるようになり（→ §1.1）、畳める範囲は下の表とほぼ重なる。**それでも口は分けたままにする。違いは範囲ではなく帳簿に何を書くかである**——`settle` は「失敗ではない・工場の外で決着した」、`abandon` は「諦めた」。1つにまとめると**「どれだけ捨てたか」と「どれだけ工場の外で片付いたか」が混ざって数えられなくなる**（統治を測るための区別。PO 裁定 2026-08-14）。

```
draft / queued / ready / planning / implementing / auditing
  / review-ready / in-review / approved / paused  →  closed
```

- **`failed` を経由しない。** 失敗ではないので `task_failed` を積まない。経緯が「落ちた」と読めてしまうと、あとから成否を数えたときに嘘になる
- **理由が必ず残る。** `task_settled_outside` に分類（`landed_elsewhere` / `no_longer_needed` / `handled_directly`）と根拠の自由文、そして**どこで止まっていたか**（`settled_from`）が載る。分類を3つに絞ってあるのは、降ろされ方の内訳を数えられるようにするため
- **記録は消えない。** それまでの遷移も職人の起動も帳簿に残る。消えるのは「まだ見る必要がある」というふりだけ（既定の一覧から外れる。→ §6）
- **専用の口を通ったものだけが閉じる。** `X:closed` を通常の遷移表に10本足すのではなく `settleOutside()` を1本置く——どこからでも `closed` へ飛べる機械にしないため。理由と一緒でなければ閉じられない
- **`merging` と `failed` は対象外。** `merging` は着地の最中で、横から閉じるとマージキューが自分の対象を失う（降ろす口は `supersede`）。`failed` は `abandon` の領分で、「失敗ではない」と言うためのこの口と混ぜない
- **断るときは行き先を言う。** 「`failed` からは畳めません」で終わらせず「落ちたまま諦めるなら `kobo.abandon`」まで返す——道具が断るだけだと、番頭は同じ口をもう一度叩く
- **選ぶ基準は状態ではなく理由。** `abandon` と範囲が重なる以上、「どの状態か」では選べない。**畳む理由が「外で決着した（失敗ではない）」なら `kobo.settle`、「諦める」なら `kobo.abandon`**——この一文を両方の口の説明に置く（載せないと番頭は範囲で選ぼうとして迷う）

## 2. イベントソーシング

実行時状態はmutableなDBに持たず、**追記専用のイベントログを真実とし、状態はリプレイで導出する**（→ D3：ファイルは意図、イベントログは実行時状態）。

採用理由（設計配当）：
- クラッシュ回復と自己更新時のKobo引き継ぎが「ログを読み直す」に統一される
- シャドー実行（候補Koboに同一ログを与えて判断差分を検証）が自然に成立する（→ 自動更新パイプライン）
- D8の起点参照（判断要求→POの入力）がイベントIDで機械的に張れる

### 2.1 ログの内容（何を入れないかが本体）

- 記録するのは**オーケストレーションイベントのみ**：状態遷移、spawn/exit、ゲート判定、承認・却下、環境provision/teardown、POの操作、カード生成、**滞留の判定**（→ §5）、**工場の外での決着**（→ §1.2）。1イベント数百バイト規模
- **セッショントランスクリプトは記録しない**。piが持つセッションJSONLへの参照（ファイルパス）のみを持つ
- 全イベントにプロジェクトタグを付与（→ spec-multi-project §1）

**イベント種を増やすのは後方互換な追加に限る**（番頭決定 2026-08-14）。D1/D9 が縛っているのは**形式を変える**こと——既存の読み手が読めなくなる、過去の記録が意味を失う——であって、種や項目の**追加**は古いイベントを1つも壊さない。既存イベントに項目を足すときも**任意項目**にし、この項目より前に書かれた帳簿を読めなくしない。読み手（`StateStore` / `deriveQueue`）は知らない項目を無視する作りである。形式そのものの変更（契約と試行の分離など）はこの限りではなく、D1 に戻る。

### 2.2 構造：グローバル1本＋時間セグメント

- ログは**Koboに1本**（タスク別に分割しない）。キュー順序・quota・照合・依存ゲートはタスク横断の状態であり、分割すると全体順序の再構成問題を生むため
- セグメント化：`events/2026-07.jsonl` のように分割し、追記は常にアクティブセグメント1本のみ
- タスク別ビュー（カードの経緯表示等）はインデックスで導出する

### 2.3 ログのライフサイクル（肥大化の有界性）

ディスク使用量は「スナップショット＋アクティブセグメント＋保持期間分のアーカイブ」で**有界**であること。無限に育つファイルを持たない。

1. **ローテーション**：アクティブセグメントは月次または上限サイズのどちらか早い方で切る（閾値は層B）
2. **スナップショット**：セグメント切替時に導出済み状態＋イベント位置をダンプ。リプレイは常に「最新スナップショット＋アクティブセグメント」のみで、起動コストはログ全長と無関係に一定
3. **ロールアップ**：ケイデンス集計時、閉じたセグメントから統計値（escaped defects、パッチ効率等の時系列）を別ファイルへ抽出。改善ループの長期材料はロールアップ側が担う。ロールアップのエクスポート形式はOTLP互換とし、既製の可視化基盤（Grafana等）を利用可能にする。v1では不要、ロールアップ実装時に形式を寄せる（→ research-orchestrator-survey G）
4. **アーカイブ／削除**：ロールアップ済みセグメントはzstd圧縮でアーカイブし、保持期間（層B。例：生ログ1年、ロールアップ無期限）経過後に削除。**例外：openなタスクが参照するイベントを含むセグメントは削除対象から除外する**

### 2.4 証拠に「何に対して」を刻む（realign 第2便・段1）

判定を積むだけでは足りない。**何に対しての判定なのかが一緒に残っていないと、その判定がまだ有効かを後から計算できない。**

| イベント | 刻むもの | 何に答えるか |
|---|---|---|
| `audit_verdict` | `contractVersion` | どの契約に対して監査したか |
| `audit_verdict` | `checklistVersion` | どの基準で監査したか |
| `merge_gate_evaluated` | `environmentDigest` | どの環境で検査したか |
| `merge_gate_evaluated` | `baseCommit` | どのコミットの上で検査したか |

- **契約の版は新しく持たない。** 契約を定めた最後のイベント（`task_created`、または直近の `task_contract_amended`）の `eventId` をそのまま使う。版は既に §1.0 の仕組みが表しており、別に数えると二重管理になって食い違う（D3）。突き合わせは「いまの帳簿から導いた版と、判定に刻まれた版が同じか」で済む
  - これが無かったので、基準が動いたことを**状態を `implementing` へ巻き戻す**という形でしか表せなかった（§1.0）。刻まれていれば「その判定は古い」と言うだけで済む
- **基準と環境の版は「中身の指紋」**（短いハッシュ）。どちらも版番号を持たないもの（`skills/audit-checklist.md` と `meta/environments.yaml` のプロファイル）なので、番号を別に振ると**書き換えても上げ忘れる**。環境はプロファイル**名**では足りない——同じ名前のまま土台のイメージや `setup` が変われば、同じ差分でも結果は変わりうる
  - 環境の指紋を作るのは**環境の持ち主**（Environment Pool が `env.provision` の返りに載せる）。Kobo は受け取って刻むだけで、環境の中身を読まない（決定60a）
- **分からないものは埋めない。** `git rev-parse` が解決できない・環境を立てていない・プールが指紋を返さない——どの場合も**項目ごと落とす**。ref 名や推測で埋めると、読む側は SHA だと思って比較し、常に一致しないか常に一致するかのどちらかになる。**証拠が静かに嘘になる**（I2）
- **刻む前に、その中身が届いていることを確かめる。** 監査チェックリストは pi 拡張の `before_agent_start` だけで渡していたため、`extensionPaths` を読まない Claude Agent SDK の監査人には**一度も届いていなかった**——実運用の監査人はほぼ全てその経路である。届いていない基準の指紋を刻むのは証拠ではなく嘘なので、**Kobo が指示文に載せて渡す**（経路に依らず届く唯一の道）

> **刻みの無い判定は自動着地させない**【2026-08-14・番頭決定】
>
> この項目より前に積まれた判定には、上の4つが付いていない。**混在するので、扱いを決めておく必要がある。**
>
> **証拠が無いものは自動で着地させない**——`review.policy` の既定を反転したあと（第3便）も、`contractVersion` / `checklistVersion` を持たない `audit_verdict` は、今までどおり人（番頭または PO）の承認を通す。刻みを要求した意味は「証拠のあるものだけを機械に通させる」ことであって、証拠が無いものを黙って通すなら要求した意味がなくなる。
>
> 決めたのは**番頭**（PO 判断を要さないと判断した細部。利用体験は変わらず、緩い側へ倒れないため）。異論があれば言ってください。

### 2.5 `review.policy` の既定は自動着地。ただし証拠の揃ったものだけ（realign 第3便）

**既定は `auto`**【2026-08-14・PO 裁定：4案から「刻みあり＋検査ありだけ自動で着地させる」】。反転前は `banto`（監査を通ったものを番頭が一次受けする）だった。

**`auto` は「人を通さなくてよい」という宣言でしかなく、通してよい根拠は別に要る。** 自動で着地するのは次が**両方**揃ったものだけで、どちらかを欠けば `banto` へ落として人（番頭または PO）の承認を通す：

| 見るもの | どこで見るか | 実装 |
|---|---|---|
| `contractVersion` / `checklistVersion` の刻み | 監査の判定と同じ時点 | `autoLandBlockers` |
| 契約が `acceptance[].verify` を1本以上持つこと | 同上 | `autoLandBlockers` |
| `baseCommit` / `environmentDigest` の刻み | **マージ前ゲート** | `gateEvidenceBlockers` |

- **刻みは2か所に分かれて出る。** `baseCommit` / `environmentDigest` は §2.4 のとおりゲートの**出力**で、監査の分岐の時点にはまだ存在しない（ゲートが回るのは `merging` に入ったあと）。だから前者2つは分岐の**入力**、後者2つは**ゲートの成立条件**として扱う——状態機械を作り替えてゲートを前倒しするより影響が小さい【2026-08-14・番頭決定】
- **検査を要求するのは、ゲートが契約の書いた `verify` を回すだけだから。** 1本も無ければ「何も確かめずに passed」になる。実測で帳簿の契約72本中50本がこれだった。人が見るならその目が検査の代わりになるが、機械だけで通すならならない
- **ゲート側の厳しさは auto 経路にだけ効かせる**（`landedWithoutHumanApproval` が `auditing → merging` か `approved → merging` かを帳簿から導く）。人が見ているものと機械だけで通すものを同じ基準にすると、**既存の緑が理由なく落ちる**。この非対称は意図であって漏れではない
- **落とした理由は書き切る**（I2）。遷移の `reason` に `auto_land_unmarked:*` / `auto_land_no_verify` が入り、判断待ちの札にもそのまま載る（→ spec-ui §3）
- **旧称 `manual` は既定に依らず `banto` へ写す。** 既定への fall-through で表していると、反転した瞬間に「人が見る」と書いたタスクが黙って機械通過になる（帳簿に13本あった）
- **厳しい側の上書きは必ず勝つ。** `governance: true` と `review.po_required_paths` はこの既定より手前で効く（→ ADR-0013 決定57・66）

**後戻りは層B設定1つ**：`meta/config.yaml` の `review.default_policy`（`auto` / `banto` / `po`）。Kobo は毎回このファイルを読み直すので、ビルドも再起動も要らずに次の判定から戻せる。戻したあとに残るのは**既に着地したマージだけ**で、それは帳簿の `audit_passed:auto` から数えられる。

> **反転が効き始めるのは Kobo を再起動してからである。** 刻みを付ける実装（§2.4）は 2026-08-14 時点で稼働中の Kobo に入っておらず、帳簿の `audit_verdict` 23本は**1本も刻みを持たない**。つまり再起動までは自動着地率は 0% で、再起動後に監査を通ったものから条件を満たし始める。

## 3. spawn管理と回復

> **失効（2026-08-06・ADR-0013 決定60、task-0060 で実装）。** 職人の台帳・生存確認・回復は
> **Worker Pool が持つ**（検証環境は Environment Pool）。Kobo は `worker.*` を呼ぶ側になり、
> spawn 台帳も照合ループも持たない——二重に持つと真実が割れる（D3・inc-0027）。
> Kobo 再起動時に職人を畳むこともしない（決定63）。落ちている間の出来事は
> `worker.events`（`afterEventId`）で追いつく。以下は改訂までの記録として残す。

- **spawn台帳**（永続化）：起動した子プロセス（pid、タスクID、セッションパス、worktree）を登録。Kobo再起動時は台帳から孤児を引き取り再接続する（→ 自動更新の前提条件）
- **照合ループ**：spawn台帳・環境台帳と実態（プロセス、ドライバ `list`）を定期突合し、差分をケイデンス議題に載せる（→ spec-environment §5）
- **健康状態taxonomy（v1.x）**：照合ループはエージェント健康状態を導出する：`working` / `stalled`（進捗低下）/ `no-progress`（一定期間無進捗）/ `zombie`（セッション死亡）/ `idle`。判定はイベント間隔とdiff変化から機械的に行う。介入動詞として `nudge`（注意喚起メッセージ注入）と `handoff`（新セッションへのコンテキスト再注入）をKobo APIに持つ（→ research-orchestrator-survey D）

## 3.5 セッションランタイムとモデルルーティング

### ランタイムドライバ
セッション起動は**ランタイムドライバ契約**（spawn / メッセージ注入 / イベント購読 / kill）で抽象化する：
- `pi-rpc`：参照実装（headless pi、RPCモード）
- `claude-agent-sdk`：サブスクリプション課金枠で回すためのドライバ。**注**：サブスク経由の可否・課金条件（プラン枠かextra usageか）はAnthropicのポリシーに依存し変動する（2026年前半に2度変更あり。piのOAuth認証は現在extra usage従量課金）。ドライバ隔離はこの変動をconfig1行の影響範囲に局所化するための設計である
- **PO と対話する主体は番頭であり、番頭のハーネスはプラガブル**とする 【2026-07-27・ADR-0009 改訂】。Kobo・WorkerAgent（本節の職人）との結合は**Tool／SKILL の公開 I/F のみ**を介し、ハーネス実装の詳細に依存しない。**第一実装は pi coding agent**（本節のランタイムドライバ契約に従う職人セッションのドライバとしても、番頭が呼び出すハーネスとしても使う）。将来別ハーネスへの置き換えを前提とする——番頭が特定ハーネスの資産に固定される決定はしない
- 可搬性の構造保証：ツール定義・Kobo APIクライアント・プロンプト資産読込は**ランタイム中立の共通ライブラリ（banto-core）**に置き、各ランタイムのアダプタは薄い皮（ツール登録とフック接続のみ）に留める。実行者のツールは中身がすべてKobo API呼び出しであり、判断ロジックをアダプタに置かない（→ D5）
- スコープ執行の最終防衛はランタイム非依存にする：`scope.paths` 違反はマージ前ゲートでKoboがdiffを機械検査して拒否する（→ I1）。セッション内フックは早期警告に格下げし、統治をランタイムの規律差に依存させない
- ランタイム間の品質差の検出：E2Eシナリオはドライバごとに実行し、テレメトリ（監査通過率・/fix回数等）にランタイム軸を持たせてロールアップする。差はケイデンスで評価し、割に合わないドライバの撤退はconfig変更のみで行える

### モデルtier（層B）
コードとタスクはモデル名を知らず、**tier**（`reasoning` / `standard` / `fast`）のみを参照する。

> **ルーティング表の置き場が変わった（2026-08-06・ADR-0013 決定60a、task-0060 で実装）。**
> tier からモデルへの解決は **Worker Pool（と番頭核の `LlmCatalog`）が持つ**。Kobo は
> tier の文字列を渡すだけで、モデル名も provider も鍵も知らない——公開の口を通らない経路が
> 1本でもあると、その口の変更が黙って Kobo を壊す。以下の `meta/config.yaml` の表は
> 改訂までの記録（ADR-0011 決定42 で `LlmCatalog` に一本化済み）。

```yaml
models:
  reasoning: { runtime: claude-agent-sdk, model: ... }   # まずサブスク枠
  standard:  { runtime: pi-rpc, provider: zen, model: ... }
  fast:      { runtime: pi-rpc, provider: vllm-local, model: ... }
  fallbacks: { reasoning: reasoning-api, fast: standard }
providers:
  vllm-local: { endpoint: "http://...", max_concurrent: 4 }
  subscription: { window_budget: ... }    # 時間窓予算
```

- 既定の割当は役割×kindの決定的マッピング（監査・診断・検討=reasoning、feature=standard以上、batch/fix・要約・分類=fast）。検討エージェントはenqueue時にタスク単位で `model_tier` を上書きできる
- プロバイダ同時実行上限・サブスクの時間窓予算は物理quotaとして台帳管理し、枯渇時はfallbackに退避する（→ spec-multi-project §3の3番目の実行停止理由）
- モデルの入替・格下げ実験は層B変更として仮説付き改善に乗せる（→ spec-improvement-loop §5）

### ask_predecessor（v1.x）

status_reporterの姉妹機能として `ask_predecessor` を提供する：対象タスクの先行セッション（escalate元・conflict元・handoff前）のJSONLログを注入した短命SDKセッションに一問一答させる。呼び出し元は実行者・レビューセッション・PO（→ research-orchestrator-survey E）。

### 失敗駆動の昇格（非対称規則)
- **昇格は機械**：監査2回不通過、または同一acceptanceで/fix回数が閾値超過→ 一段上のtierでrespawn（イベント記録）
- **格下げは人間**：tier別テレメトリ（監査通過率・/fix回数・escalate率。ロールアップに含める）を根拠に、ケイデンスで判断する。安いモデルへの過剰最適化による静かな品質劣化を防ぐ

## 4. マージ機構

### 4.1 直列マージキュー
- approvedタスクは**マージキューで直列処理**する：先頭タスクをメインラインへrebase → マージ前ゲート（Kobo自身がテスト実行。→ I1）→ マージ。メインラインは常にグリーンを保つ
- 緩い並行マージは行わない。ゲートの意味（メインの健全性保証）は直列化によってのみ成立する
- **検証は検証環境の中でだけ回す**（PO裁定 2026-08-07・task-0075）。Kobo はホストで
  検証コマンドを走らせない——ホストの状態（入っている道具・空いているポート）が検証結果に
  混ざるため。実際に混ざった（inc-0032）：Kobo が 3000番に居座っていたせいで、受け持つ
  プロジェクトのテストが1件**永久に落ちていた**
  - **§3 の「Kobo自身がテスト実行」は「Kobo が Environment Pool に回させる」と読む。**
    守るべき不変条件は「Kobo」という固有名詞ではなく、**依頼者（職人）ではない信頼された
    第三者が回して結果を記録すること**（I1）——spec-environment §3 が 2026-07-30 に
    済ませた読み替えと同じ
  - プロファイルは層B設定（`meta/config.yaml` の `verify.profile`・既定 `test`）。
    **受け持たせるリポジトリには必ず1つ要る**
  - **届かないならゲートは通さない**（`verify_env_unavailable:<profile>`）。ホストへ落とす道を
    残すと、いちばん静かに壊れる形（「たまたま通った」）に戻る。
    **`verify_failed` とは別の言葉にする**——環境の不備をテストの失敗として読ませない（I2）
  - 立てるのは**1タスクにつき1回**（受け入れ条件ごとではない）。畳むのは finally（I3）
- **検証コマンドの制限時間は層B設定**（`meta/config.yaml` の `limits.verify_timeout_minutes`。
  既定10分・上限60分。task-0071）。数字は spec-environment §5.1 と揃える——同じ問い
  （テスト一式を何分待つか）に2つの答えを作らない。**上限があるのは直列だから**で、
  長い1本が後ろを全部止める
- **時間切れは「判断」ではなく「事故」**として扱い、**上限まで延ばして1回やり直す**。
  テストが落ちた（exit≠0 かつ≠124）ものはやり直さない——それは検証が出した判定であって、
  二度走らせても同じことを二度言われるだけ。上限まで駄目なら
  `verify_timeout:<ac>(N分待っても終わらず・延長済み）` として止め、**`verify_failed` とは
  区別する**（`exit=124` のままだと「テストが落ちた」と読める）
  - **既定は 60 秒だった**（2026-08-07 に発覚）。しかも daemon から一度も渡されておらず
    設定する術が無かった。検証環境側は同じ問題を 2026-08-01 に裁定済みで、ゲート側だけ
    取り残されていた——**同じ穴を2度掘っている**（inc-0030）
- **ゲートの結果には「何に対して通ったのか」を刻む**（realign 第2便・段1）。`merge_gate_evaluated` に
  `baseCommit`（`base` を解決した SHA）と `environmentDigest`（立てた検証環境の中身の指紋）。
  `passed` は「**この土台の上で・この環境でなら**通る」という主張でしかなく、それを言えない証拠で
  人の承認なしに着地させるのは危険だからである（→ §2.4）
- **将来拡張**：将来、ゲート実行時間がボトルネック化した場合の既定の進化先はBors型バッチ処理とする：複数の承認済みタスクを束ねて一括検証し、グリーンなら一括マージ、レッドなら二分探索で失敗タスクを隔離する。v1は直列1件ずつでよい（→ research-orchestrator-survey F）

### 4.2 コンフリクトの自動解消
- rebase失敗時、Koboは**解消タスクを自動起票**しエージェントに解かせる。解消結果も監査＋マージ前ゲートを通す（特別扱いしない）
- 解消の品質はテストで保証する。コンフリクト解消の失敗事例は再現E2Eシナリオとして追加する（→ spec-improvement-loop §4）
- 解消タスクが失敗した場合はfailedとしてアテンションキューへ

## 5. 定期処理（スケジューラ）

Koboのtickが担う定期処理の一覧（改訂 2026-08-07・ADR-0013 決定60）：

- 依存駆動ゲートの再評価（レビュー通過・マージによる ready 昇格）
- **自動着手**：ready のタスクに職人を1人つける（物理quota の範囲で）
- **職人に起きたことの引き取り**：`worker.events` を `afterEventId` で追い、終了・畳みを
  自分の帳簿へ写す。**Kobo が落ちている間の出来事も取りこぼさない**
- 直列マージキュー（rebase → マージ前ゲート → fast-forward）
- コンフリクト解消タスクの結果確認（解消 → 元タスクを merging へ戻す／失敗 → 連鎖失敗）
- **滞留の見張り**（`dwell-watch`。realign 第2便・下記）
- スナップショット・ローテーション・ロールアップ
- タスク定義watcher（`work/` の変更検知 → enqueue取り込み。不正形式の拒否。
  **取り込み済みの書き換えは反映せず、そのことを記録する**——決定64）
- ケイデンス／メタケイデンス／評価カードの合成キューアイテム生成 **（未実装）**

**Kobo が持たなくなったもの**（決定60。持ち主が回す）：

| 定期処理 | いまの持ち主 |
|---|---|
| TTL執行・quota確認・照合（環境） | Environment Pool |
| 照合（spawn＝職人の生存確認） | Worker Pool |

二重に持つと真実が割れる（D3）。実際、Kobo と各Poolが同じ台帳を別々に開いていた
時期があり、**Kobo の tick は番頭が立てたものを対象外にしていた**（inc-0027）。

### 5.1 滞留の見張り（realign 第2便・rethink C-3 第1手）

**状態は「いつからその状態なのか」を答えられなかった。** だから何日詰まっていても誰も気づかない——実測で 19.2h / 28.6h / 16.8h の滞留があり、そのうち task-0100 の 19.2 時間は「`gate_evaluated.blockedBy` が 18 時間変わらなかった」というだけの事実だったのに、それを言える機構が無かった。**閾値を超えた `blockedBy` の不変は、機構が壊れている合図**（P6）そのもので、機械が言える。

- **時間は保存しない**（D3）。滞在時間は「最後の `state_transitioned` からいままで」で、帳簿が既に持っている。写しを作ると、状態を動かす経路すべてで更新し忘れが起き、静かに古い数字が出る
- 閾値を超えたら **`task_stalled` を1回だけ積む**。載るのは判定の事実と、**そのときの実測値・そのときの閾値**（あとから閾値を変えても、当時の判断が読める）、そして待っている相手（`blockedBy`）
- **同じ状態のあいだ再発火しない。** 判定は「最後の `state_transitioned` より後に `task_stalled` があるか」だけ——**鳴らした印を手元に持たない**。持つと再起動で消え、起動のたびに溜まっている分が全部鳴り直す
- **知らせは束ねる。** 番頭へ返すとき、同じ宛先の滞留は1通にまとめる（→ spec-ui §3）。1件1通で流すと溜まっていた分がそのまま通数になり、**実測で35件が35回届いた**——そうなると読まれなくなり、知らせないのと同じになる
- **見張るのは、止まったときに手の打てる状態だけ。** 閾値を持たない状態（`ready` / `merging` など通り過ぎるだけのもの）では鳴らさない
- 閾値は**状態ごとの層B設定**（`meta/config.yaml` の `limits.dwell_warn_minutes`）。書かなかった状態は既定に落ちる：

```yaml
review:
  default_policy: banto    # policy を書かなかったタスクの既定（→ §2.5）。
                           # 省略時は Kobo の既定＝ auto。これが反転の後戻りの口
limits:
  dwell_warn_minutes:      # 既定 — queued 120 / implementing 90 / review-ready 240
    queued: 120            #        failed 60 / paused 240（単位は分）
    review-ready: 480
```

職人が動いている状態（`implementing`）は短く、人の判断を待つ状態（`review-ready` / `paused`）は長く取る。`failed` が短いのは、落ちたまま置かれるのがいちばん見落とされるため。

## 6. API

Kobo は**2つの口**を持つ（改訂 2026-08-07・ADR-0013 決定58・60）。どちらも同じ Daemon を
見ており、片方が状態を持つことはない（D5：Surfaceにロジックを持たせない）。

### 6.1 モジュールの口（`{baseUrl}/tools/{名前}`）— 番頭と UI が使う

決定27b の呼び出し規約に乗る。**契約は Tool で、体系を2つ持たない**（決定9）。
既定の到達先は `/api/kobo`。

| Tool | 何をするか | 番頭に見える |
|---|---|---|
| `kobo.enqueue` | タスク定義ファイルを積む。`origin`（積んだスレッド）と `originRef`（経緯）つき | ○ |
| `kobo.list` / `kobo.task` | 一覧と、1件の**いまと経緯**（解決済みのレビュー段・触れる環境・滞在時間つき） | ○ |
| `kobo.projects` | 受け持っているプロジェクト | ○ |
| `kobo.approve` | レビューを通す。**`po` と判定されたものは通せない**（決定57） | ○ |
| `kobo.send_back` | レビュー待ちを**実装へ差し戻す**（通さない方の判断）。契約は変えない | ○ |
| `kobo.reopen` | **落ちたものを同じタスクのまま動かし直す**（`rework` / `reverify`。→ §1.1） | ○ |
| `kobo.amend` | 積んだあとの契約を**訂正する**。緩める方向は PO だけ（→ §1.0） | ○ |
| `kobo.supersede` | タスクを**別のタスクで置き換える**（→ §1.0 の使い分け） | ○ |
| `kobo.abandon` | **諦めて畳む**（どの状態からでも。→ §1.1） | ○ |
| `kobo.settle` | **工場の外で決着したものを畳む**（失敗ではない。→ §1.2） | ○ |
| `kobo.set_watch` / `kobo.set_merge_queue` | watcher・マージキューを**止める**（工場が壊れたときの制御の口） | ○ |
| `kobo.unregister_project` | プロジェクトの**受け持ちを外す** | ○ |
| `kobo.register_project` | プロジェクトを受け持つ | — |
| `kobo.events` | 起きたことを `afterEventId` で追う。**宛先（origin）を添えて返す** | — |

**「番頭に見える」は在庫にあるかとは別の問いである。** 在庫の正典は `packages/banto-daemon/src/kobo-tools.ts`、番頭に見えるものの正典は `packages/banto-host/src/presented-tools.ts`——**後者に載せなければ、在庫にあってもモデルには存在しない**（決定82）。実際、`abandon` / `supersede` / `amend` は在庫にありながら提示されておらず、機構が「`kobo.abandon` で畳んでください」と案内し続ける一方で番頭の手にその道具が無い、という状態が続いた（inc-0063）。

`—` の2本は**意図的に提示していない**：`register_project` は受け持ちを増やす操作で番頭の判断だけでは決めない。`kobo.events` は番頭ホストの知らせの層（`kobo-notice.ts`）が直に呼ぶ口で、モデルが読むのは `kobo.list` / `kobo.task` の方。

**UI は Kobo へ直接は届かない**（§7 のとおり 127.0.0.1 にしか出ていない）。番頭ホストが
自分の面に `/api/kobo/tools/*` を生やして中継する。

### 6.2 REST（`/api/v1/*`）— CLI と職人の拡張が使う

- `GET /api/v1/ready`：**着手できる仕事**を返す一級クエリ。`kobo ready` CLI・番頭の
  `kobo.list`・自動着手の tick は**同じ導出**を見る（→ D3。判定を2箇所で数えない）
- 状態遷移・監査判定（`report_phase` / `report_done` / `audit_report`）は職人の pi 拡張が叩く
- WebSocket でイベントを購読できる

### 6.3 通知

**Kobo は PO へ直接積まない**（決定58）。判断待ちは `kobo.events` を番頭ホストが引き、
**積んだスレッドの会話へ**返る。番頭が捌けないものだけを番頭が取次（`inbox.post`）へ上げる。
プッシュ通知（ntfy 等）は取次から出す——通知系を2つ作らない（決定29b）。

## 7. 稼働形態

- **サーバ集中型**：自宅サーバのVM（Ubuntu）上で systemd サービスとして常時稼働。
  worktree・セッション・環境接続もサーバ側に置き、PO は Web GUI でどこからでも接続する
  （**tmux は使わない**——職人を覗くのはセッションビューア。決定18・59）
- **待ち受けは既定で 127.0.0.1**（改訂 2026-08-07・決定40・task-0061）。この口は認証を
  持たず、状態遷移も監査判定も受ける。広げるのは `BANTO_DAEMON_BIND` の明示だけで、
  そのとき起動ログに警告が出る。外から使うなら前段（Caddy 等）で守る
- **worktree は `gwq` の配下**に作る（決定60・a6）。番頭と PO が場所として中を読める
- ユニットの分かれ方（決定19・61）：

  | ユニット | 何を持つか |
  |---|---|
  | `banto.service` | 番頭ホスト（会話・記憶・取次・キャンバス） |
  | `banto-daemon.service` | **Kobo**（この spec） |
  | `banto-worker-pool.service` | 職人の台帳とセッション |
  | `banto-environment-pool.service` | 検証環境の台帳と sops の鍵 |

  **4つとも常駐する**（2026-08-07・task-0066）。番頭ホストは工房も検証環境も自分の中に
  作らず、**両方の利用者**になった——Kobo も番頭も、それぞれ直に叩く（決定27：Banto を
  ブローカーにしない）。台帳は置き場ごとに1つで、番頭と Kobo が同じものを見る（決定29c）。
  ブラウザは 127.0.0.1 のサービスへ届かないので、**UI の経路だけ**番頭ホストが中継する
- 常時稼働が前提の機能：自動着手、マージキュー、（Pool 側の）TTL執行・照合
- **リリースの世代管理**：`releases/<version>/` を並べ `current` シンボリックリンクを
  切替える方式。ロールバック＝リンクの張り戻し
