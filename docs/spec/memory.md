## 0. 目的・スコープ・設計原理

### 0.1 目的

セッションをまたいで劣化しないエージェントを実現する。記憶を後付けの検索機構（RAG）としてではなく、**コンテキストに何を載せるかを決める基盤**として設計する。

### 0.2 スコープとモジュール構成 【重要】

Quirefold は記憶・コンテキスト管理・自律ループを含む**単一のサブシステム**として実装する。これを積む Banto ハーネスは自作であり（決定②＝inversion §13）、コンテキスト組み立てを Quirefold に委ねる（§0.3）。

内部は3モジュールに分け、インターフェースを明確に保つ。

| モジュール | 責務 | 本書での対応 |
|---|---|---|
| **memory** | 記憶の保存・出典・版管理・コンテキスト組み立て・蒸留 | Part I、Part II、§14、§18、§19 |
| **harness** | LLM呼び出し・ツール実行・ターンの実行 | **Banto ハーネス**（自作＋プラガブル LLM 層）。§0.3・inversion §13 |
| **driver** | 起動条件・ゴール管理・睡眠発火・割り込み裁定・再検証キュー・自律予算 | §17、**§20**、§21 |

#### 唯一の規律

**memory モジュールはタイマーもループも持たない。** 問われたら答え、命じられたら整理するが、**自分でいつ動くかは決めない**。判断は常に driver 側に置く。

これは配布境界ではなく**設計上の規律**であり、目的は検証順序にある。スケジューラを持たなければ、memory を素のリクエスト/レスポンス型ループから駆動して**単独で先に評価できる**。自律ループの完成を待たないと評価できない構造にすると、Part II の全パラメータが永久に未検証のまま残る。§0.9 に未検証項目が6つある以上、ここは譲れない。

#### 分割しない理由

将来 memory を独立ライブラリとして切り出す余地は残すが、**現時点で分ける理由はない**。

- 両者の状態は意味的に強く絡み合っている（§0.3 のシグナルは汎用APIではなく、driver が必要とするから露出させた内部状態である）
- §18 の睡眠判定はコンテキスト圧力（memory 側）とタスクの区切り（driver 側）の両方を見ないと決まらない
- §20 の自己内省は、記憶整理がゴールを生成するため境界を跨ぐ
- 単体でエンドツーエンドに動かないと §16 の評価指標が測れない

**境界の正しい位置はまだ分かっていない。** 机上で引いた線をパッケージ分割で固定するのは、Substrate 以外を早期確定させないという原理3（§0.5）に反する。単一リポジトリなら境界は後から動かせる。

#### 実装コストを理由にスコープを狭めない

driver も含めて本気で作る。ゲートウェイ・実行バックエンド・TUI といった定型的な広がりは、**AIエージェントによる実装を前提にすれば安い**。「人手で書くと大変だから削る」という判断はしない。

制約になるのは実装労力ではなく**検証**である。§0.9 の項目は、コードが増えても解けない。

- 見逃し率の判定には人間の目が要る（§16）
- パラメータの調整には実時間の経過が要る（半減期4ターンの妥当性は、ターンが起きないと分からない）
- レビュー負荷は表面積に比例する。とくに「memory はタイマーを持たない」という規律は、エージェントが利便性のために黙って破る典型

したがって縮めるのは**作る量ではなく検証の順序**。§0.9 の最優先項目を先に片付け、そのあとは並行に進めてよい。

### 0.3 モジュール間インターフェース・不変条件・実行層の強制 → **別ファイル**

### 0.4 命名規約

- **サブシステム名のみ造語**（Quirefold）。banto の語彙体系 Banto / Quirefold / Kobo / Worker Pool の一員（inversion §12.1）
- **内部モジュール・関数・型名はすべて標準的な英語**を使う。凝った命名をしない
  - `working_set`, `episode_store`, `provenance`, `distiller`, `budget_allocator`
- CLI の動詞は業界標準（`recall` / `distill` / `compact`）

### 0.5 設計原理

1. **脳のアナロジーは仮説の源であって解の源ではない。** 脳の機構の多くは容量・代謝コスト・身体の単一性といった制約への解であり、その制約が存在しない箇所では意図的にアナロジーを捨てる（§3 の不変性、§20 の並行性）。
2. **安全性をLLMの判断力に依存させない。** プロンプト上のルールは一次防御に過ぎず、権限制御・リソース上限・承認ゲートといった実行層の強制を主防御に据える。
3. **可逆性で設計判断を階層化する。** 後から変えられない決定（Substrate）を先に確定させ、変えられる決定はパラメータとして外出しする。
4. **失敗モードの順位（§0.7）が全パラメータの向きを決める。** 値は実験で決めるが、向きは机上で決める。

### 0.6 4レイヤ構成

| レイヤ | 内容 | 可逆性 |
|---|---|---|
| **I. Substrate** | スキーマ、不変性、版管理、出典、時間 | **不可逆** |
| **II. Policy** | コンテキスト管理、注入、確信度、蒸留 | 可逆 |
| **III. Loop** | 内部状態、睡眠、並行性、自律ループ | 可逆 |
| **IV. Governance** | 自己モデル、プロトコル、権限、リソース制限 | 一部不可逆 |

**Substrate だけは後から変更できない。** スキーマに欠けた項目を後から追加しても過去の記憶に遡及できず、「出所不明の古い記憶」が永久に残る。

### 0.7 失敗モードの順位 【確定】

**本設計における最重要の前提。** パラメータの具体値は実験で決めるが、どちらに倒すかはこの順位で決まる。

| 順位 | 失敗 | なぜこの位置か |
|---|---|---|
| 1 | **ユーザーの訂正が消える** | 信頼の損なわれ方が最も深く、ユーザー側から回復手段がない。「さっき言ったのに」は他のどの失敗より重い |
| 2 | **確信を持って誤ったことを述べる** | 検出されにくいぶん被害が持続し、下流の判断を汚染する |
| 3 | **汚染が記憶に永続化する** | 頻度は低いが、後続セッションで再発火し被害が累積する |
| 4 | **必要な記憶を見逃す** | ユーザーが言い直せば回復する |
| 5 | **無関係な記憶が混ざる** | 精度は落ちるが回復可能 |

### 0.8 順位から自動的に決まる設計方針

| 方針 | 由来 |
|---|---|
| 訂正はピン留めし、確率的な機構に一切委ねない | 1位 |
| 確信度は保守的に見積もる（迷ったら下げる） | 2位 |
| 外部由来の情報は滞在・確信度・権限のすべてで厳しく扱う | 3位 |
| 見逃しコストをノイズコストより高く重み付けする | 4位 > 5位 |
| 物理削除は原則行わない（消しすぎは回復不能） | 1位・4位 |

### 0.9 机上検討の終了条件

以下は実装と eval を経ないと判断できない。ここに到達したら机上フェーズを終える。

- 蒸留の品質、特にスキーマ補完による虚偽記憶の発生率
- **参照検出の信頼性【最優先】** — これが取れないと §7 の正のフィードバックと §16 のノイズ計測が両方機能しない。2方式を比較する。
  - 自己申告方式: LLM に使用した記憶IDを申告させる。信頼性に懸念あり
  - **行動観測方式**: コーディング文脈では振る舞いから直接観測できる。すでにコンテキストにあるファイルの再読み込み（＝見逃し）、確立済みの規約に反する実装（＝訂正の消失）、同一調査の反復（＝想起されていない）。自己申告に依存しないため、こちらを本命とする
- 内部状態（§18）が実際に行動を変えるか
- 全パラメータの具体値

# Part I — Substrate（記憶基盤）【不可逆】

## 1. 記憶の階層と役割

| 記憶の種類 | データ構造 | 対応 |
|---|---|---|
| 作業記憶 | ワーキングセット（§7） | ワーキングメモリ |
| エピソード記憶 | タイムスタンプ付きドキュメントストア＋ベクトル検索 | 海馬 |
| 意味記憶 | 出典リンク付き事実ステートメント集合 | 大脳皮質 |
| 手続き記憶 | 実行可能スキル | 体で覚えたやり方 |

単一のデータ構造で全部を賄おうとするのが既存実装の失敗パターン。保存技術としては分離するが、**論理的には出典リンクで結ばれた1つのネットワークとして扱う**。

**意味記憶は当面グラフ化しない。** オントロジー設計とエンティティ解決の破綻が典型的失敗であり、出典リンクさえ保持していればグラフは後から構築できる（→ 付録C）。

## 2. 記憶エントリのスキーマ 【確定】

### 共通コア

```
id                  安定・不変
kind                episode | semantic | procedural
fact_type           preference_decision | world_fact   ← §12 の矛盾解決規則で使用
content             { headline, summary, full }        ← §9 の解像度階層
created_at          記録時刻（減衰計算の基準）
valid_from          事実が真になった時点
valid_until         事実が真でなくなった時点（null = 現在も有効）
origin              user_explicit | agent_inferred | external
session_id          記録元セッション（並行識別＋出典独立性判定を兼ねる）
context             { tool, project, repo, mode }      ← §11 の文脈一致度で使用
derived_from[]      出典エントリID（§4）
version             版番号
superseded_by       後継版のID（null = 最新版）
tombstone           削除マーカー
strength            想起強度（単一スカラー、§13）
salience            顕著性（§11）
authored_by         主観的な値を書いた実行系の識別子（ADR-0010 §7）
subject[]           この記憶が「誰・何について」のものか（ADR-0010 §8）
asserted_by[]       この記憶が「誰の言明」に基づくか（ADR-0010 §9）
```

> **本節の一覧は ADR-0010 §1 が正典である。** 上記は反映であり、食い違う場合は ADR-0010 が優先する（P3）。**2026-07-26 に Substrate は凍結された**（ADR-0010「凍結」節）。以降フィールドを足すには ADR の supersede が必要である。

### 確定した4つの論点

**1. strength は単一スカラーでよい。**
当初「文脈ごとに分解すべきか」を未決としていたが、**コンテキスト管理を主題に据えたことで解決した**。文脈依存の重み付けはワーキングセットの activation（§7）がターン単位で担う。保存層の strength は「そもそも役に立ったことがあるか」という弱い事前分布だけを表現すればよく、分解は不要。

**2. confidence はフィールドとして持たず、出典から都度算出する（結果はキャッシュ）。**
永続化すると出典が増減したときに陳腐化し、「古い confidence が残る」という §0.7 の2位の失敗を招く。出典リンクが唯一の真実の源であるべき。

**3. エピソードと意味記憶はスキーマを共通化する。**
共通コア＋ kind ごとの拡張フィールド。層をまたぐ出典リンクと活性化を扱う以上、別スキーマにすると参照が煩雑になる。

**4. 削除は tombstone とアーカイブ層への降格で表現する。**
**物理削除は法規制対応（GDPR 等の明示的削除要件）のみ**であり、それが唯一の例外である（§25）。**PO の「消して」は物理削除ではなく tombstone の新版**（§3・§25 の編集導線）。消しすぎは回復不能という非対称性による（§0.8）。

> **旧版は「ユーザーの明示的要求**と**法規制対応のみ」と書き、存在しない §26 を参照していた** 【2026-07-26 訂正】。§25 は「法規制対応が**唯一の**例外」と定めており、**同じ条件について2箇所が違うことを述べていた**（本書冒頭が P3 として挙げていた不一致）。§25 を正とする——PO の「消して」まで物理削除に落とすと、§0.7 の4位（見逃し）が回復不能になり、§20.4 の経路B（系譜による訂正の波及）も辿る先を失う。

### スキーマに含めないもの

**ワーキングセットの滞在状態（activation、入場ターン、最終参照ターン、不応期）はエントリに書かない。** セッション側の別テーブルに持つ。同一の記憶が複数セッションで独立した滞在状態を持つ必要があり、エントリに書くと並行セッションで壊れる（§20）。

## 3. 不変性・版管理・再固定化

### エントリは immutable

想起は記憶の強化ではなく書き換えの機会として扱う（再固定化 / Reconsolidation）。ただし**上書きはしない**。上書きは出典との対応を壊し、監査可能性を失わせる。

```
再固定化 = 新しい版を作成し、旧版に superseded_by を張る
  - 想起は最新版を返す
  - 監査時は版の系譜を遡れる
  - 旧版は減衰しアーカイブへ降格する
```

**新版は新しい `id` を持つ** 【2026-07-26 明記・R6／S9】。ADR-0010 §1 は `id` を「安定・不変」と定め、`superseded_by` を「後継版のID」と定めているので、**同一 `id` のまま版を進めることはできない**（できるなら `id` は不変ではない）。`version` は系譜内の連番であり、系譜をまたぐ識別子ではない。両方の読み方ができる書き方だったのでここで閉じる（Substrate の解釈であり、変更ではない）。

**`superseded_by` が解決できない場合の扱いは §7-F1 が定める**（最新版として扱わない）。

人間の記憶が上書き型なのは容量制約によるものであり、ここでアナロジーを捨てる（§0.2 原理1）。

### 副産物: 並行更新への耐性

2つのセッションが同じ事実を別々に更新した場合、上書き型なら片方が黙って消える（lost update）。版管理なら両方が生きた版として並存し、**壊れた状態ではなく検出可能な矛盾**になる。ロックを使わずに、既存の矛盾処理へ還元できる（§20）。

## 4. 出典と信頼境界

**本設計の中心構造。** 監査可能性・確信度・矛盾追跡・インジェクション対策のすべてがここから導出される。

```
[意味記憶] "Aさんは〇〇プロジェクトのオーナー"
   ├─ derived_from → [エピソード#123]
   ├─ derived_from → [エピソード#456]
   └─ derived_from → [エピソード#789]
```

### 出典の独立性

確信度を出典の数から算出する場合、**3件が3件とも同じ誤読の産物でありうる**。単純な件数は相関した誤りに無力なため、以下を区別する。

- 異なるセッション由来か（session_id）
- ユーザーの明示的発言か、エージェントの推論か（origin）
- 外部由来か内部生成か（origin）

### 宙ぶらりんノードの防止

統合・削除処理は、出典リンクが切れた意味記憶を生まないよう連動させる。出典が全て消えた事実は確信度を下げるか再検証フラグを立てる。

**`derived_from` は常に同一インスタンス内で解決できなければならない** 【2026-07-26 追加。ADR-0010 §10 が正典】。解決できないものは**異常**（障害・復元ミス）であり、§20.5-9 が拾う。**インスタンスをまたぐ出典は `external_ref` で表す**（`{system: "quirefold:<インスタンス識別子>", id: <元のID>}`）——ADR-0010 §4 の「`derived_from` は Quirefold エントリ、`external_ref` はストア外。型を混ぜない」の直接の帰結である。

したがって `export()` は単純なダンプではなく、**渡さない出典を `derived_from` から `external_ref` へ付け替える変換**を含む（§0.3.0 の経路一覧に載る書き込み経路）。`external_ref` に落ちた出典は内容を持たないので**出典間の一貫性を測れず、確信度を下げる**（§0.7 の2位）。

## 5. 時間の扱い

2種類の時間軸を分離する。

- **記録時刻**（created_at）— 減衰計算の基準
- **有効期間**（valid_from / valid_until）— その事実がいつ真だったか

混同すると「古い記録だが今も真」と「新しい記録だが既に古い」を区別できない。有効期間は §3 の版管理と自然に接続する。

# Part II — Policy（記憶運用ポリシー）【可逆】

> 具体値は全て外出しし、§17 の評価指標に基づいて調整する。向きは §0.7 で確定済み。

## 6. コンテキスト予算とレイヤ配置

### 「有限で貴重」の実体は3つ

| 予算 | 内容 | 逼迫度 |
|---|---|---|
| トークン | 金とレイテンシ | 最も緩い |
| **注意** | 無関係な情報の混入で精度が落ちる。窓が広くても半端に関連する情報を大量に入れれば答えは悪化する | **「貴重」の実体はほぼこれ** |
| **プレフィックスキャッシュ** | 注入内容が変わると失効し、コストとレイテンシが桁で変わる | 見落とされやすいが実務では最大 |

3つ目から重大な帰結が出る。**「毎ターン最適な記憶を選び直す」という素朴な設計は性能面で成立しない。**

### 配置原則

```
[静的]   自己モデル + プロトコル      ← 常にキャッシュヒット
[準静的] ワーキングセット（§7）        ← 変わりにくい。並びは滞在見込み順。＝ 滞在枠（resident）
――――――― ここがプレフィックスの失効点 ―――――――
[動的]   見出し帯（§8.5.5）           ← 毎ターン選び直す。〜10トークン×K_hl
[動的]   今ターン固有の追加            ← 末尾に追記
[動的]   会話履歴（§10）              ← 末尾に追記
```

**見出し帯を動的層の先頭に置くのは、それが毎ターン入れ替わるからである**（§8.5.5：見出し帯にヒステリシスを与えない）。ここに置けば、失効するのは見出し帯以降だけで済む。旧版はこの帯を配置原則に持っておらず、**§8.5.5 が「見出し帯を広げても失うのはトークンだけ」と書けてしまっていた**（R6 配線チェック W34）。

動的なものは必ず末尾に集める。追い出しも末尾側から優先すると失効範囲が最小になる。**注意予算の観点でも末尾は読まれやすい**ため、両制約は競合せず同じ結論を指す。

## 7. ワーキングセット 【中核】

毎ターン検索し直すのをやめ、**タスク/セッションで「今アクティブな記憶」の小集合**を維持する。ターンごとの変化は少数の出入りに限る。

得られるもの:

- プレフィックスが安定する
- **一貫性**。ランキングの揺れで「2ターン前は知っていたことを今ターン忘れる」現象が消える
- 人間の作業記憶（一定時間活性が持続する）との整合

### スコアを2本に分ける

1本にすると滞在中の記憶も毎ターン再評価され、閾値付近が点滅する。

**入場スコア** — 今ターンのクエリに対して計算

```
s_admit = w1·rel_norm + w2·文脈一致 + w3·確信度 + w4·顕著性
```

**第1項（関連度）は候補集合内で正規化されたランク由来の値である**（`rel_norm`。§8.5.5）。初版は「関連度」とだけ書き、それをどこから得るかも、絶対値なのか相対値なのかも定めていなかったため、**N が増えるほど閾値の識別力が落ちる**状態だった（R4／S13）。第2〜4項は候補数に依存しない量なので絶対値のままでよい。

**滞在スコア** — 入場時に初期化し、以降はクエリと無関係に更新

```
入場時:       a ← s_admit
毎ターン:     a ← a × γ            (γ ≈ 0.85/ターン ≒ 半減期4ターン)
参照された:   a ← min(1, a + β)
再ヒット:     a ← max(a, s_admit_now)
```

**滞在スコアがクエリとの `rel_norm` から切り離されている**ことが要点。一度入った記憶は今ターンの話題と直接関係なくてもしばらく居座る。

### ヒステリシス

```
θ_ws     = 0.6     滞在枠に入る絶対下限（旧 θ_admit）
θ_floor  < θ_ws    見出し帯に入る絶対下限（§8.5.5）
θ_evict  = 0.2     下回ると退場候補
最小滞在 = 3ターン（無条件ガード）
```

閾値差だけでは γ の値で挙動が変わるため、最小滞在ターン数を併用する。

**絶対下限だけでは入場は決まらない。** 定員 `K_ws` / `K_hl` と併用し、**両方を満たしたものだけが入る**（§8.5.5）。絶対閾値のみだと N とトピック頻度に比例して通過件数が増え、相対順位のみだと候補が少ないときに無関係なものが入る。**旧版は前者だけを持っていた**（R4／S13）。

### 候補集合の前段：版の解決とアーカイブの扱い 【2026-07-26 追加】

スコアリングの**前**に、決定的なフィルタを通す。**本節は「何を除くか」の正典であり、実行の順序と場所は §8.5.3（Stage 2）が正典である。**§3 は「想起は最新版を返す」と意図を述べていたが、候補生成の手順として書かれていなかったため、旧版が候補に混入しうる状態だった（ADR-0010 §6-S2/S5/S9）。§0.7 の1位（訂正が消える）に直結するので、確率的な機構より前に置く。

**各項目に安定 ID（F1〜F5）を振る。** §8.5.3 の Stage 2 が本節と同じ集合を実行していることを、機械的に照合できるようにするため。**項目を足したら ID を足し、Stage 2 の表にも行を足す**（片方だけに書くと集合がずれる。R6 配線チェック W20）。

- **F1** — **`superseded_by != null` のエントリは候補から除外し、常に最新版に解決する。** 索引が版ごとに行を持つ実装でも、この解決を通してからスコアリングする。
  - **`superseded_by` が解決できない（指す先が存在しない）とき、そのエントリを最新版として扱ってはならない。** 候補から外し、**宙ぶらりん参照として §20.5-9 の点検へ回す**。**この既定が無いと、バックアップからの復元で後継版だけが失われた場合に、訂正される前の古い版（多くは `agent_inferred`）が「最新版」として静かに復活する**——PO の訂正が誰にも気づかれずに消える、§0.7 の1位そのものである（R6／S17）。
  - **これは Substrate の変更を要しない。** `superseded_by: null`（＝最新）と `superseded_by: <存在しないID>`（＝壊れている）は現行スキーマで既に区別できる。**「区別できるのに区別しない」だけが問題だったので、Policy の解決規則で閉じる。**
- **F2** — **`tombstone: true` のエントリは `build_context` / `recall` の対象から除外する。** 到達できるのは監査目的の明示的な版履歴参照のみ。
- **F3** — **アーカイブ層は検索対象から除外しない。** ただし注入解像度を見出しのみに制限する（§9）。「アーカイブ＝索引から消す」と読むと、休眠していた話題が復帰した瞬間に**構造的に見つからなくなる**（ADR-0010 §6-S8）。降格は解像度の話であって、可視性の話ではない。**検索コストは除外ではなく二段照会で抑える**（§8.5.2：archive 層を走査するのは、エンティティ完全一致のとき、または active 層のヒットが定員に満たないとき）。
- **F4** — **`subject[]` を判定に使う** 【2026-07-26 追加】。「PO がその主体に言及したターンか」の判定は、`content` の自由文ではなく **`subject[]` の一致**で行う（ADR-0010 §8）。また `assemble_brief()` は、**ブリーフの宛先本人が `subject[]` に含まれるエントリを除外する**（本人についての判断を本人に渡さない）。引き継ぎ・エクスポート時の切り分けも `subject[]` を鍵にする。
- **F5** — **`sensitive: true` は、除外ではなく解像度でゲートする** 【2026-07-26 全面改訂・R6／S9】。判定入力は `retrieve()` の `session_origin` と、`resolve_entities(raw_utterance)` が返す `mentions`（§8.5.0・§8.5.1）。

  | 状況 | 扱い |
  |---|---|
  | `session_origin == po_message` **かつ** `mentions` に該当主体を含む | 通常どおり（要約解像度まで） |
  | **それ以外**（自律ループ、`subsystem_kick` 由来、`mode == brief`、PO が言及していないターン） | **候補から外さず、`content.headline` のみ**（理由＝`summary`／`full` は載せない） |

  **旧版は「候補から除外する」だった。これは機密を守ると同時に、PO が述べた制約そのものを番頭の判断から消していた**（R6／S9）。「Xさんに長期タスクを振らない」という決定は、X の話題が出ていないターンでこそ守られなければならない——**タスク配分を考えているときに X の名前が出ていないのは当たり前だからである。** 除外すると、番頭は自律ループで平然と X に長期タスクを割り当てる提案をする。§0.7 の順位はこの失敗を明示的に持っていないが、**PO の明示的な指示が黙って適用されない**のは1位（訂正が消える）と同じ性質である。

  解像度でゲートすれば両立する。**`headline` は結論（制約）だけを持ち、理由を持たない**（§0.3.0 I5 が書き込み時に強制する）。番頭は制約を適用できるが、**その理由をコンテキストに持っていないので述べようがない**——これが「自発的に持ち出さない」（ADR-0010 §5）の機械的な担保である。禁じたい振る舞いを、プロンプトの規律ではなく**情報を渡さないこと**で止める。

  - **したがって `mode` による差は無くなった。** §0.3.1 が `assemble_brief()` について既に採っていた扱い（結論だけ載せ理由を落とす）を、全モードの統一規則に格上げしたものである。初版は `brief` だけを例外にしており、その例外がなぜ `brief` に限られるのかを説明できていなかった。
  - **残る漏れ**：`session_origin == subsystem_kick` のセッションが外向きの command を組み立てる場合、`headline`（＝制約）がサブシステムへ出る可能性がある。制約は伝わるべきものなので既定では許すが、**`sensitive` 由来の制約に基づく外向き作用は §20.5-6 の点検対象に含める**。
   - **滞在（residency）もゲートする**：`sensitive` エントリには最小滞在ターンを適用せず、話題転換（§8）を検出したら即座にバッチ退場させる。本項（F5）は入場だけを制御していたため、正当に入場した機微記憶が話題が変わった後も数ターン居座り、無関係な会話に紛れ込みえた。
   - ADR-0010 §5 は「番頭から自発的に持ち出さない」「自動での可視範囲拡大の対象外」と定めたが、**`s_admit` の4項（`rel_norm`・文脈一致・確信度・顕著性）に抑制項が無く、禁じたい挙動を止める機構が存在しなかった**（R2）。スコアを下げるのではなく前段で切る——確率的な機構に委ねない（§0.8）。
   - 「PO が言及したターンのみ」を条件に含めるのが「自発的に持ち出さない」の実装である。話題に上っていない人物の機微な記憶は、`rel_norm` がいくら高くても入らない。

### 休眠トピックの復帰 【2026-07-26 追加】

§13 は「減衰を弱い事前分布へ降格したので、半年触っていない記憶が埋没する問題は解決した」としていたが、**埋没の経路は `strength` だけではない**（ADR-0010 §6-S8）。`s_admit` の4項のうち、

- **文脈一致度**（§11-4）— 記録時の文脈と現在の実行文脈が違えば下がる
- **確信度**（§12）— 「最終更新からの経過時間」を入力に取るため、内容が正しくても下がる
- **顕著性の目標関連性成分**（§11-3）— 現在のゴールに紐づかないため下がる

の3つが `strength` とは独立に、**すべて同じ方向（休眠トピックに不利）へバイアスする**。`rel_norm` だけが高くても入場閾値を越えられない。

対策：**強いエンティティ一致（固有名詞・識別子の直接一致）がある場合、文脈一致度・目標関連性・および確信度の経過時間ペナルティの減点を免除する。**

初版は前2つだけを免除し、**確信度の経過時間ペナルティ（§12）を免除対象に含めていなかった**。3経路のうち1つが残るため、固有名詞が一致しても8ヶ月経った記憶は入場閾値を越えられない可能性があった。ただし**免除するのは入場判定だけ**であり、§9 のレンダリングでは「未確認」寄りの量子化を保つ——**入場させる目的と、古いかもしれないと気づかせる目的を両立させる**。 「半年触っていないプロジェクトの記憶は、その話題が始まった瞬間に最優先で入れるべき」（§13）という要求は、減衰の降格ではなくここで満たす。

**この救済の発火経路は §8.5.2 のアーム A2（エンティティ索引）である。** 「強いエンティティ一致」を誰がどう判定するかが書かれていなかったが、A2 でヒットしたことがその判定そのものになる。

**一般名詞のトピックには救済が効かない**（「認証」にはエンティティ一致が無い。R4／S13）。これは救済側では直さず、**見出し帯**（§8.5.5）で受ける——滞在枠には入らないが「そういう記憶が存在する」ことは伝わり、明示展開できる。免除規則を一般名詞へ広げると、逆に無関係な古い記憶が常時入場する。

**曖昧な再開発話の循環は解決済み**：「あの調査どうなってたっけ」には固有名詞が無く、どの閉包の話かを特定できない。かつ文脈一致度の分母である実行文脈自体が「どの話題か」に依存するため、**素朴に組むと循環する**（ADR-0010 §6-S8）。**§8.5.1 の `resolve_entities()` を Stage 0 に置き、スコアリングの前に閉包レジストリを直接引く**ことで切る（LLM を介さない）。特定できない場合は候補を提示して聞き返す（§23-6）。

### 追い出しは予算駆動かつバッチ

**退場候補になったら追い出す、は誤り。** 載っている項目の維持はキャッシュヒットでほぼ無料だが、取り除くとその位置以降のプレフィックスが全て失効する。**退場は高い。**

発火条件は2つ。

1. **予算超過** — まとめて大きく空ける（例: 予算の70%まで一気に落とす）
2. **話題転換の検出**（§8）— キャッシュを捨ててでも大きく入れ替えるべきタイミング

それ以外では徹底的に安定させる。GCの世代別回収と同じ発想であり、§19 のマイクロスリープと同一の機構になる。

### ピン留め（スコアリング非参加）

絶対に落とさない枠。予算計算から先に差し引く。

- 現在のゴールスタック
- 今タスクの制約条件
- **このセッション中のユーザーの訂正** ← §0.7 の1位への直接的な対策。**「訂正」の判定は §12 で機械的に定める**（`user_explicit` の言明のうち、既存の意味記憶と衝突候補が出たもの）

訂正が退場すればエージェントは元の方針に戻る。**確率的な機構に委ねてはいけない。**

### 失敗モードと対策（必ずセットで実装する）

| 失敗 | 内容 | 対策 |
|---|---|---|
| 点滅 | 閾値付近が毎ターン出入りしキャッシュが失効 | ヒステリシス＋最小滞在 |
| **居座り** | 無関係な記憶が低い退場閾値で延々残る | **滞在上限**: M ターン未参照なら保護枠（§8.5.5 の順序2）から外し、`θ_ws` と定員で入場し直させる |
| 惜しい記憶の再来 | 閾値ぎりぎりの候補が入退場を繰り返す | **不応期**: 退場後 K ターンは再入場禁止 |
| 訂正の消失 | 方針が巻き戻る | ピン留め |

**居座りはヒステリシスを入れた時点で必ず発生する。** 点滅対策と居座り対策は同じパラメータの逆方向であり、片方だけ入れると必ずもう片方が悪化する。

### 外部由来はヒステリシスを適用しない 【重要】

通常のRAGなら悪い検索結果は次ターンで消えるが、**ワーキングセットは意図的に居座らせるため、汚染された内容も同じように保護される**。さらに参照されると activation が上がるため、攻撃テキストが出力に影響するほど滞在が延びる正のフィードバックがある。

信頼境界を滞在ポリシーにも効かせる。

| | 内部由来 | 外部由来 |
|---|---|---|
| 最小滞在ターン | あり | **なし** |
| 退場閾値 | 低い | **高い** |
| 参照による加点 | あり | **なし** |

これで §25 の「突破されても被害が出ない構造」がコンテキスト管理層まで降りる。

### 状態遷移

```
              rank ≤ K_ws  かつ  s_admit ≥ θ_ws        （§8.5.5 の二段判定）
   [候補] ──────────────────────────────────────→ [滞在]
     │  ↑                                             │
     │  │ 不応期 K ターン経過                          │ a < θ_evict かつ最小滞在済み
     │  │                                             ↓
     │ [不応] ←────────────────────── [退場候補] ──参照──→ [滞在に復帰]
     │              予算超過 or 話題転換時にまとめて退場
     │
     └──→ [見出し帯]   rank ≤ K_ws + K_hl かつ s_admit ≥ θ_floor
                        （不応期・最小滞在・保護枠を適用しない。毎ターン選び直す）
```

**入場は閾値だけでは決まらない。** 定員 `K` と絶対下限 `θ` の**両方**を満たす必要があり、落選しても `θ_floor` を超えていれば見出し帯に入る（§8.5.5）。初版の図は `θ_admit` 単独で入場を描いており、**S13 が指摘した「N とともに通過件数が際限なく増える」失敗をそのまま図示していた**（R6 配線チェック W21）。

## 8. クエリ生成と話題転換

生の発話はクエリとして弱い。「それどうなった？」「さっきの続き」は検索可能な内容語をほぼ持たない。

### 材料

1. 直近の発話
2. アクティブなゴール
3. **現在のワーキングセットの内容**
4. 実行文脈（リポジトリ、開いているファイル）

3が非自明。**今ワーキングセットに載っている記憶は、今の話題の最良の要約でもある。** 検索の実体は「クエリ→記憶」ではなく「**ワーキングセット＋発話→追加記憶**」になる。

### トピック固着への対策

上記は自己強化ループを作る。ワーキングセットがクエリを作り、そのクエリが似た記憶を呼び、ワーキングセットが強化される。**話題が変わっても集合が自分を再生産し続ける。**

これは §7 の居座りと同じ現象だが、**個別エントリの滞在上限では止まらない**。集合として自己を維持しているため、1件ずつ追い出しても補充される。

- クエリの一定割合を必ず生発話の内容語から取る（外部からの新規性注入）
- **話題転換の検出**: 発話とワーキングセットの類似度が急落したら転換とみなし、§7 のバッチ退場を発火させる

## 8.5 検索機構 — クエリから候補集合へ 【2026-07-26 新設・中核】

**本節は R4／S13 が見つけた土台の欠落を埋める。** §8 はクエリの**材料**を、§12 経路A の LSH は**矛盾検出用**の候補ペア抽出を、§15 は技法の一覧を述べるだけで、**クエリ文字列から候補集合を作る索引・検索が、本書にも ADR-0010 にも定義されていなかった**。§7 の入場スコアも §9 の解像度も、この上に乗っている。

設計の向きは4つの失敗から決まる。S13 が同時に成立すると示した——(i) 通過件数が N とともに際限なく増える（絶対閾値）、(ii) 定員を超えた候補の選抜規則が無い、(iii) 祖先方向しか見えないので横断質問が届かない、(iv) 一般名詞のトピックでは休眠救済が発火せず重要な過去が埋没する。**(i) と (iv) は逆向きの失敗であり、片方だけを直すともう片方が悪化する**（§7 の点滅と居座りが同じパラメータの逆方向であるのと同型）。

### 8.5.0 パイプラインの全体像と公開シグネチャ

```
retrieve(req) → { ranked[], clarify?, trace }

req = {
  query,           # §8 のクエリ生成の出力（材料4種を合成したもの）
  raw_utterance,   # 直近の生発話のみ。§7-F5 のゲート判定に使う（下記）
  closure_ctx,     # 実行文脈が属する閉包。driver の exec_context を閉包レジストリで解決したもの
                   # 解決できないとき（どの店にもいない状態での相談）は person（root）にする。null にしない
  goal_stack,      # driver 提供（§0.3）。s_admit 第4項の目標関連性成分の入力
  exec_context,    # driver 提供（§0.3）。s_admit 第2項の文脈一致の入力
  mode,            # context | recall | brief
  session_origin,  # このセッションの起床源（§20.2 の5種）。§7-F5 のゲート判定に使う
  addressee,       # mode == brief のときの宛先（職人）。§7-F4 の除外に使う。他モードでは null
  budget,          # §6 の3予算。K_ws / K_hl の算出に使う（§8.5.5）
  n                # mode == recall のときの件数指定。他モードでは null
}

ranked[] = [{ entry_id, s_admit, rank, tier, arms_hit[], via_fanout, from_closure }]
tier     = resident | headline          ← §9 の解像度に決定的に対応する
clarify  = { candidates[] } | null      ← §23-6 の聞き返しが要るとき（§8.5.5 末尾）
trace    = 各段で何件が何によって落ちたかの記録（§16 可観測性）
           段ごとに理由を分けて数える。とくに「索引に無い」と「フィルタで落ちた」を
           混ぜない（前者は障害、後者は仕様。R6／S17）。アームの打ち切りは
           件数と打ち切り位置のランクを記録する（何が落ちたかは原理的に分からない）
```

**引数を構造体にしたのは、ゲートの入力を引数に持たせるためである。** `sensitive` ゲート（§7-F5）は「PO との直接対話であること」と「PO がその主体に言及したターンであること」を条件とするが、**旧来これらは呼び出し側の文脈にしかなく、検索操作の引数として渡す設計になっていなかった**——ゲートを実行層に置いたつもりで、判定材料が届いていなかった（R6 配線チェック W25）。**判定に必要な入力は、すべてシグネチャに現れなければならない。**

- **`closure_ctx` に既定を置くのは、それが横断ファンアウト（§8.5.4）の発火条件1の入力だからである** 【2026-07-26・R6／S13】。`null` を許すと**ファンアウトが発火するかどうかが未定義になり、横断質問という主用途がまるごと判定不能になる**。`person` を既定にすれば「leaf ではない」が常に成り立ち、条件2・3 が実際の絞り込みを担う。
- `session_origin == po_message` が「PO との直接対話」の機械的な定義である。
- 「言及したターン」は **`resolve_entities(raw_utterance)`** で判定する。**`query` ではなく `raw_utterance` を使う**——`query` は §8 の材料3（現在のワーキングセットの内容）を含むため、`query` で判定すると**既に滞在している機微記憶が自分の滞在を正当化する**（§8 のトピック固着と同じ自己強化ループ）。

**3つの呼び出し元は同一のパイプラインを通る。** `build_context()`（番頭のセッション）・`recall()`（明示リコール）・`assemble_brief()`（職人への発注、§0.3.1）で別々の検索を書かない。**呼び出し元ごとに検索を書くと、経路が増えるたびに規則が漏れる**——§0.3.0 が書き込み側で解いたのと同じ問題を、読み取り側でも同じ形で解く。`mode` による差は §8.5.7 の表1枚に閉じ込める。

**`build_context()` / `recall()` / `assemble_brief()` は `retrieve()` を経由しなければならない。** これら3つが候補を自前で集めることを禁じる（§0.3 のシグネチャ一覧に明記）。

| 段 | 名前 | 何をするか | LLM |
|---|---|---|---|
| **Stage 0** | エンティティ解決（§8.5.1） | 表記 → 閉包ID／主体ID／エントリID。`closure_filter` と `mentions` を確定させる | 使わない |
| **Stage 1** | アーム検索（§8.5.2） | 独立した5本の索引アームがそれぞれ上位 `k_arm` 件を返す | 使わない |
| **Stage 2** | 決定的フィルタ（§8.5.3） | 版解決・tombstone・可視性・`subject[]`・`sensitive` | 使わない |
| **Stage 3** | 融合・正規化・免除（§8.5.5） | RRF でランク融合し `rel_norm` を作る → 免除規則 → `s_admit` を算出 | 使わない |
| **Stage 4** | 入場の二段判定（§8.5.5） | 定員 K と絶対下限 θ の**両方**で切る。不応期はここで効く | 使わない |
| **Stage 5** | 解像度の割当（§9） | 滞在枠＝要約／見出し帯＝見出し | 使わない |

**`via_fanout` / `from_closure` は §8.5.4 の開示のためにある** 【2026-07-26・R6／S12・S13】。「どの閉包を横断したかを注入時に明示する」と宣言しながら、**その情報を運ぶ欄が返り値に無かった**。宣言だけでは実行できない。

**`included_refs[]`（§0.3.1）と `derived_from` の自動付記は `ranked[]` から作る。** `assemble_brief()` の `included_refs[]` は `tier != null` のエントリID、ハーネスが `record()` に渡す `derived_from` 候補は `build_context()` が返した `ranked[]` のうち実際に注入されたもの。**「何が載ったか」を機械的に知る唯一の場所が `ranked[]` である。**

**全段が決定的である。** 検索は制御ループではないので §20.0 の制約の直接の対象ではないが、**「なぜこの記憶が出てこなかったか」を事後に説明できること**（§16 可観測性）を成り立たせるには、途中に LLM を挟めない。`rel_norm` の算出に埋め込みモデルを使うことはある（アーム A3）が、それは索引の性質であって判断ではない。

### 8.5.1 Stage 0：エンティティ索引と閉包の解決

**エンティティ名から閉包IDを引く索引を持つ。** 閉包レジストリは包含関係の解決専用であり、名前から引く手段が無かった（R3 の指摘）。

```
entity_index:  表記 → [{ kind: closure | subject | entry | external_ref, id, weight }]
resolve_entities(text) → { closures[], subjects[], refs[], entries[], unresolved[] }
```

| 供給元 | いつ入るか |
|---|---|
| 閉包レジストリの識別子と表示名 | 閉包の登録・改名時 |
| `subject[]` と `asserted_by[]` の値（ADR-0010 §8・§9） | 書き込み経路（§0.3.0 I8）。**両者に入れる識別子は本索引を通して正規化する**（名前空間は共通）（「Xさん」→ `party:X`）。正規化の管轄がどこにも無いと、表記が揺れた瞬間に §12 の訂正検出が黙って失敗する＝§0.7 の1位（R6／S9） |
| `external_ref[]` の `{system, id}` | 同上 |
| `content.headline` から抽出した固有名詞・識別子 | 同上。抽出はルールベース（英数字を含むトークン、既知の識別子書式、レジストリ既知語との完全一致） |
| **エイリアス表**（表記ゆれの是正） | `alias(surface, target_id, origin)` で書く（下記） |

これが §7「休眠トピックの復帰」が自認していた**循環**を切る。文脈一致度の分母である実行文脈が「どの話題か」に依存するのに、話題の特定に文脈一致度を使う、という循環は、**スコアリングの前にレジストリを直接引く**ことで解ける。§7 はこの解を要求していたが、引く先の索引が存在しなかった。

- **解決できたら** `closure_filter` を「解決された閉包＋その祖先」に絞る。曖昧（複数候補）なら絞らず、A2 アームの入力に全候補を渡す。
- **解決できなければ** `closure_filter` は実行文脈（`closure_ctx`）のまま。それでも Stage 1 は動く（A1/A4/A5 は名前を要らない）。
- **`mentions = resolve_entities(raw_utterance)`** をここで確定させる。これが §7-F5（`sensitive` ゲート）の「PO が言及したターンか」の判定入力になる（Stage 2 で使う）。`query` 全体ではなく生発話だけを見る理由は §8.5.0 に述べたとおり。
- **聞き返し（`clarify`）の判定は Stage 4 の後に行う**（発火条件が「入場後の候補の散らばり」を見るため。§8.5.5 末尾）。Stage 0 は `unresolved[]` を後段へ渡すだけである。

#### エイリアス表の書き込み

```
alias(surface, target_id, origin) → void
```

**索引はエントリではないので `supersede()` の対象ではない**（`supersede()` は版系譜の API である）。表記ゆれを直す専用の入口を置く。書き手がいないと、表記ゆれの是正が「誰かが手で直す」という散文の規律に落ちる（R6 配線チェック W13）。

- **`origin: user_explicit` の別名は `agent_inferred` の別名に無条件で優先し、後者による上書きを実行層で拒否する**（`supersede()` の origin 優先と同じ形。§0.3 ・ADR-0010 §1.3）。強制の場所は `alias()` の実装内である。
- 索引は導出物なので、誤った別名を直せば**次の検索から効く**（エントリのような版系譜は要らない）。ただし**誰がいつ張ったかは driver の活動ログに残す**（§20.8 の **U12** に含める）。

### 8.5.2 Stage 1：アームと、候補数を N から切り離す

**独立した索引アームを並べ、それぞれに固定の取得上限 `k_arm` を置く。**

| # | アーム | 索引 | 何を拾うか | 必須か |
|---|---|---|---|---|
| **A1** | 全文（FTS） | 転置索引。BM25 相当 | 内容語による一致。ベースライン（§16 の Hermes が FTS5 でやっていること） | **必須** |
| **A2** | エンティティ | `entity_index`（§8.5.1） | 固有名詞・識別子の完全一致。**休眠トピックの復帰の主経路** | **必須** |
| **A3** | ベクトル近傍 | 埋め込み索引 | 語彙が重ならない意味的近傍 | 任意 |
| **A4** | 系譜近傍 | `derived_from` の順・逆引き | 現ワーキングセットの1ホップ近傍。§15「局所探索」の実体 | **必須** |
| **A5** | 最近性 | `created_at` 順（閉包別） | 「さっきの続き」。内容語ゼロでも動く保険 | **必須** |

```
arm.search(query, closure_filter, k_arm) → [{ entry_id, rank }]
```

**アームのインターフェースを固定し、構成を差し替え可能にする。** これが「embedding の有無による分岐」への答えである（R5 で立てた論点。現在の位置は検証プロトコル §7 の R6 の項）。ADR-0010 の帰結節は「初期実装は embedding 無しで始められる」としたが、無いときに何で代替するかを書いていなかった。A3 が無くても A1・A2・A4・A5 で動く形にする。

**候補集合の上限は `Σ k_arm` であり、N に依存しない。** S13 は「3,000件の候補」を前提に置いたが、それは仕様から導出できない数だった。アームごとに定数で切れば、100万件でも候補は数百件のオーダーに収まる。**これが S13-(2)（通過件数が corpus 規模に比例する）への構造的な答えであり、閾値の調整ではなく候補生成の側で解く。**

#### 二段照会 — アーカイブ層と検索コスト

§7-F3 は「アーカイブ層は検索対象から除外しない」と定め、§13 は減衰の残る役割として「§16 の検索コスト抑制」を挙げていた。**同じデータについて逆のことを述べている**（S13-(6)。P3 の incident 案件）。**§7-F3 を正とし、§13 の記述を撤回する**（§13 を訂正済み）。

そのうえで、コストは除外ではなく**二段照会**で抑える。

1. 索引を **active 層**と **archive 層**に分ける（アーカイブ降格＝§14 の時点で移す）。
2. **A1・A3 は既定で active 層のみを走査する。**
3. **archive 層を走査するのは次の2つの場合だけ**：(i) A2（エンティティ完全一致）——アーカイブ済みでも常に走査する、(ii) active 層のヒットが定員 `K_ws + K_hl` に満たないとき。

「除外」ではなく「二段」なので §7-F3 の意図（休眠していた話題が復帰した瞬間に構造的に見つからなくなることを防ぐ）は保たれる。**復帰の主経路は A2 であり、A2 はアーカイブを常に見る。**

### 8.5.3 Stage 2：決定的フィルタ

§7「候補集合の前段」の各項目（**F1〜F5**）は、**本段で実行する**。§7 は意味論（何を除くか）の正典、本節は実行順序の正典である。**両者の集合が一致していることが検査可能でなければならないので、§7 側の項目に安定 ID を振り、本表と1対1に対応させる。**

| 順 | フィルタ | 何をするか | 根拠 |
|---|---|---|---|
| 1 | **F1** 版解決 | `superseded_by != null` を最新版に解決する | §7-F1 |
| 2 | **F2** tombstone | `tombstone: true` を除外する | §7-F2 |
| 3 | **V** 可視性 | `context.scope` を**エイリアス解決したうえで**（`merged` な旧識別子は新識別子へ写す。§26.2）`closure_filter` に含まれるものだけ残す。横断モードは §8.5.4 が `closure_filter` 自体を広げる | ADR-0010 §2・§26.2。**§7 由来ではない**ので別 ID にする。**解決を挟まないと、閉包を統合した瞬間に既存エントリが検索から消える**（R7b） |
| 4 | **F3** アーカイブ | **除外しない。** archive 層のフラグを立てるだけ（Stage 5 で解像度に反映する） | §7-F3 |
| 5 | **F4** `subject[]` | `mode == brief` のとき、`addressee` が `subject[]` に含まれるものを除外する | §7-F4 |
| 6 | **F5** `sensitive` | `mode` 別のゲート（§8.5.7）。`context`/`recall` では `session_origin == po_message` かつ `mentions` に該当主体が含まれるときだけ残す | §7-F5 |

**順序は「安く・大きく削る」順である。** 1〜4 は索引の属性だけで判定でき、実装上はアーム検索と同一クエリに畳める。5・6 は `req` の引数を要するので後段に置く。

**不応期は本段に置かない** 【R6 配線チェック W35】。不応期は「退場後 K ターンは再入場禁止」（§7 失敗モード表）だが、**Stage 2 で切ると見出し帯にも出なくなる**——見出し帯は「見逃しの受け皿」（§8.5.5）なので、目的と正面から矛盾する。不応期は **Stage 4 の滞在枠の定員判定にだけ適用する**（§8.5.5）。退場した記憶は数ターン見出しに留まり、話題が本当に戻れば `s_admit` が上がって滞在枠へ復帰する。

**落ちた件数と理由を `trace` に記録する。** §16 の可観測性は「なぜ注入されなかったか」を要求しており、フィルタで落ちたものは s_admit を持たないため、ここで記録しないと事後に永久に説明できない。

### 8.5.4 Stage 1 の拡張：横断ファンアウト（子孫方向）

ADR-0010 §2 は「現在の実行文脈が属する閉包と、その祖先に属する記憶が候補になる」と定めた。**この規則は健全だが、片側しか定義していない。** PO が `person` root や domain 水準で「認証まわりの方針って今どうなってる？」と訊いたとき、答えは全部**子孫**にあり、祖先包含では原理的に届かない（S13-(5)）。

**可視性と既定の候補範囲を分ける。**

> **PO 自身は全閉包のオーナーであり、子孫方向は「見えない」のではない。既定で候補に入れないだけである。** 既定が祖先方向なのはノイズ抑制のためであって、権限の話ではない。

**発火条件（決定的）**——3つの AND：

1. 実行文脈の閉包（`closure_ctx`）が leaf でない（レジストリ上、子を持つ）
2. Stage 0 が特定の閉包を解決していない（クエリが閉包を名指ししていない）
3. **`session_origin == po_message`**（PO との直接対話）**かつ `mode != brief`**

3 の条件が2つある理由。職人は特定タスクの文脈で動くので横断は要らず、`assemble_brief()` は職人へ出ていく唯一の経路であり（§0.3.1）、**そこで候補範囲を広げることは絞り込みの規律をまとめて緩めることに等しい**。そして **`session_origin` の条件を外すと、自律ループ（`timer` や `subsystem_kick` 由来のセッション）でも横断が発火する**——自律行動が黙って全ドメインを見て回る状態になり、§20.6 の自律予算と §0.7 の3位（汚染の永続化）の両方に効く。**「PO 主体のセッションに限る」を `mode` だけで表現しようとすると、この穴が開く**（R6 配線チェック W3）。

**流量の抑え方（決定的）**：

- 子孫方向のヒットは **閉包ごとに上位 m 件**（既定 m=2）に制限する。1つの騒がしいプロジェクトが枠を占有しない。
- 融合の前に、**閉包ごとに1件を先取りする**（多様性クォータ。§8.5.5）。40 プロジェクトのうち上位1つだけが全部通る、という潰れ方を防ぐ。
- 子孫方向の候補には**閉包の深さに応じた減点**を掛けない。減点で調整すると N と深さの両方に効いてしまう。**件数の定員で抑える**（§0.8「確率的な機構に委ねない」）。

**注入時に、どの閉包を横断したかを明示する**（提示面＝会話）。「3つのプロジェクトから拾った」と分かる形にしないと、PO は横断が起きたことに気づけず、§8.5.8 の誤りに事後訂正が効かない。

> **ADR-0010 との関係**：本項は ADR-0010 §2 の「祖先に属する記憶が候補になる」を**既定と読み替え、PO 主体のセッションに限り子孫方向へ拡張する**。冒頭に記したとおり **ADR-0010 が正典で、食い違えば ADR が優先する**——したがって spec 側に書くだけでは本項は無効になる。**2026-07-26、ADR-0010 に §2.2 を追記して canon 側を揃えた**（P3：黙って寄せない）。Substrate は変えていない。**書き込み側の可視範囲の拡大＝§12 の B1〜B6 は一切緩めない。読むことと、記憶の `scope` を書き換えることは別である。**

### 8.5.5 Stage 3・4：融合・正規化と、入場の二段判定

#### 融合は RRF（rank ベース）で行う

```
rrf(e) = Σ_arms  1 / (c + rank_arm(e))          c は定数（既定 60）
rel_norm(e) = rrf(e) / max_e' rrf(e')            → [0, 1]
```

**アームのスコアではなくランクを融合する。** 理由は3つあり、いずれも設計上の要請から出る。

1. **BM25 とコサイン類似度は同じ尺度に乗らない。** スコアを直接足すには正規化が要るが、正規化は分布に依存し、分布は N とトピック頻度で動く。ランクは動かない。
2. **アームが欠けても壊れない。** A3（埋め込み）が無い構成でも、残るアームのランクから同じ形で `rel_norm` が出る。§8.5.2 の「差し替え可能」はこれで初めて実効を持つ。
3. **`rel_norm` は候補集合内で正規化されるので N 不変である。** S13 が指摘した「スコアが絶対値のままなので θ_admit が N に対して壊れる」は、閾値ではなく**第1項の側**で直る。

#### 免除規則（休眠トピックの復帰）を式に落とす

§7「休眠トピックの復帰」は「**強いエンティティ一致がある場合、文脈一致度・目標関連性・確信度の経過時間ペナルティの減点を免除する**」と定めるが、**「強いエンティティ一致」の判定主体も、免除を適用する場所も書かれていなかった**（R6 配線チェック W10。§20.0 が最重要とする「散文のまま実行層に落ちていない」の現物）。ここに置く。

```
for e in candidates:
    if "A2" in arms_hit(e):                    # ← 強いエンティティ一致 ＝ A2 アームのヒット
        文脈一致(e)   ← 1.0                     # 減点しない
        目標関連性(e) ← 減点なしの値を使う         # §11-3 の成分
        確信度(e)     ← 経過時間ペナルティを適用しない値を使う   # §12
```

- **判定は `arms_hit` を読むだけで、別の類似度計算をしない。** A2 は完全一致の索引アーム（§8.5.2）なので、ヒットしたこと自体が「強いエンティティ一致」の定義である。
- **免除するのは入場判定だけ**であり、§9 のレンダリングでは「未確認」寄りの量子化を保つ（§7 の規定どおり）。**したがって免除後の値は `s_admit` の計算にのみ使い、エントリにも `trace` の提示用の値にも書き戻さない。**

#### `s_admit`

式は §7 のまま、第1項の中身が確定する：

```
s_admit = w1·rel_norm + w2·文脈一致 + w3·確信度 + w4·顕著性
```

**第2〜4項は絶対値のままでよい。** これらは候補集合の大きさに依存しない量（実行文脈との一致、出典から算出される確信度、顕著性）であり、正規化すると「候補が全部古いときに、その中で新しいものが不当に高くなる」という別の壊れ方をする。**N 依存があったのは第1項だけである。**

##### 信号を持たない項は式から外す 【2026-07-26 追加・R6／S13】

**横断ファンアウトが発火したターンでは、`w2`（文脈一致）を式から外し、残る `w1`・`w3`・`w4` を合計が同じになるよう再正規化する。**

```
if 横断ファンアウトが発火した:
    s_admit = (w1·rel_norm + w3·確信度 + w4·顕著性) / (w1 + w3 + w4)
```

理由：ファンアウトが発火する条件は「実行文脈が特定の閉包に紐づいていない」ことである（§8.5.4）。**そのとき文脈一致は候補を区別しない**——全候補について一様に低い値になる。区別しない項を式に残すと、順位は何も変わらないまま**全候補の `s_admit` が一様に押し下げられ、絶対下限 `θ_ws` に対してだけ効く**。R6／S13 では、唯一の正しい現行方針が 0.5875 で `θ_ws = 0.6` をわずかに下回った。

**これは絶対閾値の壊れ方が形を変えて再出したものである。** 第1項を正規化しても、**信号を持たない項が定数として混ざれば、絶対下限との比較は同じように壊れる**。項を減らして正規化するのが正しく、閾値を下げるのは誤り（疎なトピックでの識別力を失う）。

#### 入場は「定員」と「絶対下限」の両方で切る

**裁定（R5 で「絶対値のままにするか相対順位にするか」として立てた論点）：`θ_admit` を絶対値のまま残すが、単独の入場条件ではなくする。定員（相対）と併用する。**

| 形 | 単独で使ったときの失敗 |
|---|---|
| 絶対閾値のみ | N・トピック頻度が増えると通過件数が際限なく増える（S13-(2)）。**5位（無関係が混ざる）が慢性化する** |
| 相対順位のみ | 候補が少ないとき、無関係なものが上位というだけで入る。**2位（確信を持って誤る）に効く**——薄い根拠が「ワーキングセットに載っている」というだけで重みを持つ |

**どちらの失敗も、もう片方の機構で防げる。** 両方置く。

```
入場 = ( rank ≤ K )  かつ  ( s_admit ≥ θ )
```

- **密なトピック**（N 大・言及多）では **K が効く**（相対）
- **疎なトピック**（新規領域・立ち上げ直後）では **θ が効く**（絶対）

`K` と `θ` は tier ごとに2組持つ。**これが S13-(3)（バースト入場に選抜規則が無い）と S13-(4)（解像度と s_admit の対応が無い）を1つの機構で塞ぐ。**

| tier | 定員 | 絶対下限 | 解像度（§9） |
|---|---|---|---|
| **滞在枠**（resident） | `K_ws` | `θ_ws` | 要約 |
| **見出し帯**（headline band） | `K_hl` | `θ_floor`（< `θ_ws`） | 見出し |
| 落選 | — | — | 非注入（`recall()` で到達可能。下記） |

**旧 `θ_admit = 0.6` は `θ_ws` に読み替える。**

**`K_ws` と `K_hl` は `budget` から算出する**（§6 の3予算 → `budget_allocator`）。定員はパラメータの定数ではなく**予算の関数**である——そう決めないと、`budget` を引数に取りながらどの段も使わない、という状態になる（R6 配線チェック W27）。トークン予算が縮んだときは `K_hl` から先に削る（見出し帯のほうが復元が容易で、失うのは §0.7 の4位＝見逃しに留まるため）。

#### 定員内の順序（決定的）

`s_admit` 降順で埋める前に、**3つ**の枠を先に確保する。

1. **ピン留め**（§7）——定員外。予算計算から先に差し引く
2. **保護枠：現に滞在中で `a ≥ θ_evict` のもの**——**新規候補より先に確保する**。ここを守らないと、密なトピックで毎ターン顔ぶれが入れ替わり、プレフィックスキャッシュが毎ターン失効する（§6 の3つ目の予算）。§7 のヒステリシスは滞在スコアの側で点滅を防ぐが、**定員が有限であることから来る押し出し**は §7 では防げなかった
3. **多様性クォータ**——横断モードのときだけ、子孫閉包ごとに1件
4. 残りを **`s_admit` 降順、同点は `strength` 降順**。§13 が「減衰の残る役割は関連度が同点のときのタイブレーカー」と述べていたが、**タイブレークする場所がどこにも無かった**（R6 配線チェック W23）。ここである
5. **不応期**（退場後 K ターン）は **4 にのみ適用する**。1〜3 と見出し帯には適用しない（§8.5.3 の注記）

> **順序は絶対下限を迂回しない** 【2026-07-26 明記・R6／S8・S13 が独立に指摘】。1〜5 は**定員 K の中での並べ方**を決めるだけであり、`s_admit ≥ θ` の条件は**すべての枠に等しく効く**。とくに**多様性クォータは「順序」であって「免除」ではない**——`θ_ws` を下回る閉包代表は滞在枠に入らない。
>
> したがって `θ_ws` 未満のものを救う経路は**見出し帯だけ**である（`θ_floor` を超えていれば入る）。クォータが下位のものを引き上げると期待してはならない。**この一点が書かれていなかったため、2つのシナリオが「PO の問いに何が返るか予測できない」と判定した。**

**退場は §7 の規則のまま**（予算超過と話題転換のときにバッチで）。定員による押し出しが起きるのは 2 の保護枠を確保してなお枠が足りないときだけで、そのときは §7 の「予算超過」と同じ扱い＝バッチで大きく空ける。

#### 聞き返し（`clarify`）の発火

**Stage 4 の後に判定する**（Stage 0 では候補の散らばりがまだ分からない）。決定的な条件：

> **`unresolved[]` が空でなく、かつ次のいずれかが成り立つとき**、`clarify` を返す。
>
> - (a) 滞在枠に入ったエントリの `context.scope` が2つ以上の兄弟閉包にまたがる
> - (b) **横断ファンアウトが発火した**（§8.5.4）
>
> 候補は**閉包ごとに1件ずつ選び**、各閉包内では最終更新の新しい順、閉包の並びは代表エントリの `s_admit` 降順で最大5件。閉包識別子と見出しを添える（§23-6）。

**(b) を足した理由** 【2026-07-26・R6／S8】。(a) だけだと、**間違った閉包の記憶が滞在枠を独占したときに聞き返しが発火しない**——散らばっていないので条件を満たさない。ところが**ファンアウトが発火したこと自体が「どの閉包の話か特定できなかった」という機械的な証拠**である。(a) は「複数見つかって選べない」を、(b) は「そもそも絞れていない」を捉える。**(b) が無いと、固有名詞を欠く問いに対して番頭が最近の無関係な話題を自信を持って答える経路が残り、§0.7 の4位（見逃し）で済むはずのものが2位（確信を持って誤る）に落ちる。**

**候補を閉包ごとに1件ずつにした理由** 【同】。§23-6 は「最終更新の新しい順に最大5件」とだけ定めていたが、**聞き返しが必要になる典型は休眠トピックの再開である**（§7）。新しい順に並べると、**聞き返しが救おうとしているまさにその記憶が5件の外に押し出される**。閉包で多様化してから閉包内で新しい順にすれば、休眠していた閉包も1枠を得る。

- 判定はルールベースで、番頭の裁量にしない。
- **`clarify` が返っても `ranked[]` は通常どおり返す。** 聞き返すかどうかはセッション側の判断であり（会話の流れ次第で聞かずに進めてよい）、検索は止めない。**返り値に項目が無いと、そもそも「聞き返せる」ことがセッションに伝わらない**（R6 配線チェック W36）。

#### 見出し帯が「見逃し」の受け皿になる

S13 は、7年前の認証インシデント（`salience` が高いのに `s_admit = 0.40`）が埋没すると指摘した。固有名詞を PO が言わない限り §7 の休眠救済（強いエンティティ一致）が発火しないためである。

**この二段構成では、そのエントリは滞在枠に入らないが見出し帯には入る。** 見出しは〜10トークンなので `K_hl` は `K_ws` より一桁大きく取れる。番頭は「そういう記憶が存在する」ことを知り、必要なら明示展開する。**§9 が「受動注入と能動リコールの対立は階層で解消する」と述べていたのは、まさにこの配線である**——述べてあったが、どのスコアのどの帯域が見出しになるのかが書かれていなかった。

§0.8 の重み付け（見逃しコスト ＞ ノイズコスト）は、**滞在枠ではなく見出し帯の広さで表現する**。滞在枠を広げるとノイズが注意予算を食うが、見出し帯を広げて失うのはトークンと**見出し帯より後ろのキャッシュ**だけである。

**見出し帯にはヒステリシスを与えない。** 滞在枠のような保護枠・最小滞在・不応期を持たせると、居座り（§7 の失敗モード表）が一桁大きな帯で起きる。代わりに**プレフィックスの失効点を見出し帯の先頭に固定する**——見出し帯は §6 の配置で「準静的層の末尾・動的層の直前」に置き、**そこより前（自己モデル・プロトコル・滞在枠）は毎ターン安定する**。見出し帯が毎ターン入れ替わっても、失効するのはそれ以降だけである。

> 初版はこれを「失うのはトークンだけ」と書いたが、**§6 が「見落とされやすいが実務では最大」と名指しした予算を数え落としていた**（R6 配線チェック W34）。配置で解けるので機構は要らないが、**タダではない**。`K_hl` を予算の関数にしてあるのはこのためでもある。

### 8.5.6 索引の維持

**索引はエントリの導出物であり、真実ではない**（D3）。したがって：

- **書き込みと同一トランザクションで更新する**（§0.3.0 の **I8**）。エントリを生成する経路は §0.3.0 の一覧が正典であり、**新しい経路を足したら索引更新も自動的に付いてくる**。経路ごとに「索引も更新すること」と書かない。
- **A3（埋め込み索引）だけは遅延更新を許す。** 埋め込み生成は外部モデルの呼び出しを伴い、書き込みトランザクションに含めるとエントリの記録そのものが外部依存で失敗しうる（§0.7 の1位）。**A1・A2 が同期で更新されていれば、A3 が遅れても記憶は検索不能にならない**——これがアームを冗長に持つ設計上の効き目である。遅延分は §20.5-7 の点検が拾い、再索引で埋める。
- **閉包レジストリの変更（新設・改名・畳み）も `entity_index` の更新契機である** 【R6 配線チェック W14】。これはエントリ生成経路ではないので §0.3.0 の一覧には現れない。**レジストリを操作する API が索引更新を伴うことを、レジストリ側の契約として持つ**（改名しても古い表記で引けてしまう状態を残さない。旧表記はエイリアスとして残す）。
- **再構築はいつでも可能**であり、`model_migration`・アーム構成の変更・§20.5-7 の乖離検出で発火する。**発火させるのは Steward Driver であって memory 自身ではない**（§0.2 の唯一の規律）。
- **再構築は §18.1 のローリング機構に乗せる**（同じシャード台帳・同じカーソル・同じ冪等性。独立した機構を作らない）。複数の窓にまたがることを前提にする 【2026-07-26 訂正・R6／S17】。初版は「深い睡眠の窓に収まる分割単位で」と書いたが、**収まる保証は無い**——R3／S11 の実測見積り（5万件≒7時間、100万件≒6日）を外挿すると20万件で約28.6時間であり、一晩を超える。**分割単位・順序・優先順位（新しいものから埋めるのか、アクセス頻度順か）は未定義であり、§20.8 の残件とする。** 埋め込みを後から導入する場合も同じ経路・同じ制約下にある。
  - **再構築中は索引が部分的である。** この状態が §16 の観測にどう現れるかを `trace` で区別できるようにしてある（上記）が、**「今は再索引中なので見えていないかもしれない」を PO や分身に伝える手段は未定義**（R6／S17）。
- 索引側は `embedded_by`（どの埋め込みモデルで作った行か）を持ってよい。**索引は Substrate ではない**ので、フィールドを後から足せる。ADR-0010 §7 が `authored_by` を Substrate に置き、embedding を対象外としたのはこの非対称性による。

**埋め込みを初期実装に入れるかの判断**：入れずに始める（D6：依存追加より標準ライブラリと既存資産。A1・A2・A4・A5 で成立する形にしてある）。ただし**遅らせるほど再索引が高くつく**ので、見直しの契機を決定的に置く——**§16 の見逃し率が閾値を超えた、または A1 の再現率が §16 のベースライン（素朴な長コンテキスト投入）を下回った時点で A3 を導入する。** 「そのうち考える」にしない。

### 8.5.7 `mode` による差（この表が唯一の差分である）

| | `context`（番頭） | `recall`（明示） | `brief`（職人） |
|---|---|---|---|
| 横断ファンアウト（§8.5.4） | `session_origin == po_message` のとき有効 | 同左 | **無効** |
| `sensitive` の扱い（F5） | **全モード共通**：`session_origin == po_message` かつ `mentions` に該当主体を含むときは要約まで、それ以外は `headline` のみ。**除外はしない**（§7-F5） | 同左 | 同左（`brief` は常に後者に落ちる） |
| `addressee` が `subject[]` に含まれるもの（F4） | — | — | **除外** |
| 定員 | `K_ws` / `K_hl` | `n`（注意予算の制約が違うため呼び出し側が指定する） | `K_ws`（見出し帯を使わない） |
| 絶対下限 | `θ_ws` / `θ_floor` | **`θ_floor`**（滞在枠の下限ではなく見出し帯の下限を使う） | `θ_ws` |
| 保護枠・不応期（§8.5.5 の順序 2・5） | 適用する | **適用しない** | **適用しない** |
| アーカイブ層のエントリ（F3） | 見出しに落とす（§9） | 見出しに落とす | **要約で載せる**（下記） |
| tier の返却 | する | しない（順位のみ） | resident のみ |

**`sensitive` の行が「全モード共通」になったので、この表の差分は4項目に減った。** §0.3.1 が `brief` にだけ定めていた解像度規則を F5 の一般規則へ引き上げた結果である（§7-F5）。

**保護枠と不応期を `recall` / `brief` に適用しない理由。** どちらも**番頭のセッションの滞在履歴**に依存する量である（§7）。`recall` は PO ないし番頭が明示的に探している場面であり、**さっき退場したという理由で隠すのは誤り**。`brief` にはそもそもセッションの滞在状態が無く、適用すれば職人向けブリーフが番頭の会話履歴によって削られる（R6 配線チェック W30）。

**`recall` の絶対下限を `θ_floor` にする理由。** §8.5.5 の tier 表は落選を「`recall()` で到達可能」と書いたが、同じパイプラインを通る以上そこにも下限が効く。`θ_ws` を使うと**滞在枠に入れなかったものは `recall` でも取れない**ことになり、到達可能という記述が空文になる（R6 配線チェック W29）。

**職人が見出し帯を持たないのは、職人が Quirefold を装着しないため**（inversion §11.1）。「存在は知らせるが必要なら展開させる」は展開手段がある相手にしか成立しない。**ブリーフに載らなかったものは職人に一切届かない**（§0.3.1）ので、`brief` では最初から要約解像度で載せるものだけを選ぶ。**同じ理由で、`brief` ではアーカイブ層のエントリも要約で載せる**——見出しだけの10トークン断片は、展開手段の無い相手には**発注文のノイズにしかならない**（R6 配線チェック W33）。§9 の「アーカイブは見出しに落とす」は展開できる相手向けの規則である。

### 8.5.8 この機構が持ち込む失敗と、その受け止め

| 失敗 | いつ起きるか | 受け止め |
|---|---|---|
| A1 が拾えない（語彙が重ならない） | 蒸留で抽象化が進んだ意味記憶 | A4（系譜近傍）と A3。**A3 が無い構成では残る穴**であり、§8.5.6 の導入契機がここに効く |
| 定員による押し出し | 密なトピックで保護枠すら埋まらないとき | §7 の予算超過と同じバッチ退場に還元する。`trace` に記録され、§16 で観測できる |
| 横断ファンアウトの誤発火 | 実行文脈の閉包解決が誤っているとき | 注入時に横断先を明示する（§8.5.4）。PO が気づける形にするのが担保であり、**自動で正しくすることは目指さない** |
| エイリアス表の汚染 | 表記ゆれの是正を番頭が誤る | `user_explicit` が勝つ（§8.5.1）。索引は導出物なので、直せば次の検索から効く |
| `trace` が肥大する | 常時記録 | セッション側に持ち、エントリには書かない（§2 の滞在状態と同じ規律） |

## 9. 解像度と注入レンダリング

### 解像度階層

各エントリは3段階の表現を持つ（§2 の content）。

| 解像度 | コスト | 用途 |
|---|---|---|
| 見出し | 〜10トークン | 「そういう記憶が存在する」ことだけ伝える |
| 要約 | 〜50 | 判断に使える程度 |
| 全文 | 〜500 | 詳細が必要なとき |

配分問題が「どの記憶を入れるか」から「**どの記憶をどの解像度で入れるか**」に変わる。

**副産物: 受動注入と能動リコールの対立が解消する。** 見出しは安いので広く撒ける → LLMは何が存在するかを知れるので思い出し忘れが起きない → 必要なものだけツールで展開する。2つの機構が対立ではなく階層になる。

### 割当規則 【2026-07-26 追加】

**旧版は解像度の階層を定義したが、どの記憶がどの段になるかの規則が無かった**（R4／S13-(4)）。§8.5.5 の tier に決定的に対応させる。

| tier（§8.5.5） | 解像度 | 誰が決めるか |
|---|---|---|
| ピン留め（定員外） | 全文まで可 | §7 のピン留め規則 |
| 滞在枠（resident） | **要約** | 入場判定 |
| 見出し帯（headline band） | **見出し** | 入場判定 |
| 落選 | 非注入 | 同上 |

- **自動注入の上限解像度は要約とする。全文は明示展開（`recall()` または展開ツール）のみ。** 「スコアが高いほど高解像度」にすると、上位数件で〜500トークン×N を消費し、見出し帯の広さ（＝§0.8 の見逃し対策）を圧迫する。全文が要るかどうかは、番頭が要約を読んでから判断できる。
- **`sensitive: true` の解像度は §7-F5 が決める**（全モード共通。PO が言及したターン以外は `headline` のみ）。解像度の割当規則より機微の規則が優先する。
- **`via_fanout == true` のエントリは、`from_closure` を添えてレンダリングする** 【2026-07-26 追加・R6／S12・S13】。§8.5.4 は「どの閉包を横断したかを注入時に明示する」と定めるが、**実行場所を書いていなかった**。ここである。PO が横断の発生に気づけることが、§8.5.4 の誤発火に対する唯一の担保である（自動で正しくすることは目指していない）。
  - **一過性の表示だけでは監査にならない** 【R6／S12】。横断が起きたことは会話に流れて消えるので、**`via_fanout` を含むターンは driver の活動ログに残す**（§20.6「自律行動のログは PO に可視」と同じ担保。ただし置き場は §20.8 の **U12** で未設計のまま）。
- **アーカイブ層のエントリは tier が resident でも見出しに落とす**（§7-F3）。降格は解像度の話である、という §7-F3 の規定をここで実行する。**例外は `mode == brief`**——職人は展開ツールを持たないので、見出しだけの断片は届けても使えない。要約で載せる（§8.5.7）。

### メタ情報の言語化

`confidence: 0.73` をコンテキストに入れてもモデルは使えない。**保存形式と提示形式は別に設計する。**

- 確信度は3段階に量子化して自然言語で出す（「確実」「おそらく」「未確認」）。連続値のままでは挙動が安定しない
- 出典も言語化する（「ユーザーが5月に明言」「Webから取得・未検証」）

### 信頼境界はレンダリングの問題

「外部由来を構造的にデータとして区別する」と言っても、**プロンプト内では見た目でしか区別できない**。区切りと明示ラベルに加えて、**外部由来テキストは生のまま入れず要約して入れる**（生テキストほど指示に見える）。

**要約はインジェクション緩和として働く。** 要約の過程で命令文が「〜という指示が書かれていた」という記述に変換されるため。完全ではないが生テキスト混入よりはるかにまし。§15 の圧縮とセキュリティが同一機構になる。

**ただし要約器自体が攻撃対象になるため、要約は権限ゼロの隔離された呼び出しで行う。**

## 10. 会話履歴とツール結果の圧縮

**コンテキストの最大の消費者は記憶ではなく会話履歴、特にツール実行結果である。** ファイル1つ、検索1回で数万トークン。記憶の注入量をいくら精緻に最適化しても、ツール結果1回で吹き飛ぶ。**圧縮の主対象はこちら。**

扱いを非対称にする。

| 対象 | 方針 | 根拠 |
|---|---|---|
| **ユーザー発言** | 原則そのまま保持 | 要約による損失の被害が最大（§0.7 の1位） |
| エージェントの発言 | 中程度に圧縮可 | |
| **ツール結果** | 直近N件のみ生で保持、以前は要約に置換。原本はエピソード記憶に退避しIDで参照可能にする | 量が支配的 |

**「エージェントの過去の思考は捨ててよいが、ユーザーが言ったことは捨てない」を明示的な原則とする。**

## 11. 顕著性

想起頻度だけでは「重要だが低頻度」の記憶（緊急対応手順等）が埋没する。

```
salience = f(頻度, 情動的顕著性, 目標関連性, 文脈一致度)
```

1. **頻度成分** — recall_count ベースの緩やかな蓄積
2. **情動的顕著性** — 予測誤差の大きさ、結果の重大さ。一度のイベントで急激に加算されうる。高顕著性の記憶は減衰のフロア値を上げて保護する
3. **目標関連性** — 現在のゴールとの関連。想起のたびに再計算する動的な値
4. **文脈一致度** — 実行文脈（context フィールド）の一致。3とは独立した軸

> これは「AIに感情を持たせる」ことではなく、感情が記憶システムに果たしている機能的役割（重要な出来事へのリソース優先配分）だけを特徴量として再現するもの。

## 12. 確信度（メタ記憶）と矛盾解決

### 算出の入力

- 出典の**数と独立性**（§4）
- 出典間の一貫性
- 最終更新からの経過時間
- origin（外部由来は低く扱う）

**迷ったら下げる。** §0.7 の2位（確信を持って誤る）を3位以下より重く見るため。

### 矛盾の検出 【2026-07-26 追加】

解決規則より先に**検出**が要る。旧版は解決規則だけを定めており、「何と何を比較して矛盾と判定するか」がどこにも書かれていなかった（ADR-0010 §6-S1/S2/S3 が独立に指摘）。検出が動かなければ、どれだけ精緻な解決規則も一度も呼ばれない。

**検出は2経路ある。片方だけでは足りない。**

**経路A：語彙・近傍による候補抽出**（同レベルの矛盾を拾う）

1. 安価な一次フィルタで候補ペアを絞る——同一の閉包（`context.scope`）またはその祖先、見出しのエンティティ一致、LSH／クラスタリング（§15）。embedding があればベクトル近傍を加える。**embedding 無しでも動く形にする**（ADR-0010 の帰結節：初期実装は embedding 無しで始められる）。エンティティ一致は §8.5.1 の `entity_index` を引く（索引を2つ持たない）が、**本経路は「1エントリ → 対立しうるペア」を作るものであり、`retrieve()` の「クエリ → 候補集合」とは用途が違う。同じ索引を使うが同じ操作ではない。**
2. 絞った候補ペアだけを LLM に判定させる。バッチ内・セッション内の判断であって制御ループではない（§20.0）。

**`fact_type` の一致を候補条件にしない** 【2026-07-26 改訂】。初版は「同一 `fact_type`」で絞っていたが、これだと**新規に記録された episode（`fact_type: null`）は既存の semantic と永久にペアにならない**。PO が「Node 20 に上げた」と言っても、既存の `state_fact`「このリポジトリは Node 18」と突き合わされない。矛盾の入口がここで塞がっていた。候補抽出では型を問わず、判定の段でだけ `fact_type` 別の解決規則（下表）を使う。

**PO の言明は常に突き合わせる**。`origin: user_explicit` の episode が記録されたら、同一閉包および祖先閉包の既存の意味記憶に対し、**無条件に候補抽出を走らせる**（`collision_candidates()`、§0.3）。PO の発話は稀で、かつ §0.7 の1位（訂正が消える）に直結するため、常時チェックしても費用対効果が合う。

#### 閉包をまたぐ一般化（自動拡大のバー） 【2026-07-26 追加】

**PO の裁定「可視範囲の拡大は番頭が自動判断し、PO は事後に訂正する」が成立する条件を、ここで定める。**

裁定の担保は**訂正の機構**である。ところが、番頭が積極的に広げれば通知（§21）のダイジェストは毎週何十件にもなり、**PO は読まなくなる**。そうなれば「事後訂正で担保する」は成立しない——**担保は面の品質ではなく、人間がレビューできる流量に依存する**。したがって拡大には**決定的なバー**を置く。判定にLLMを使わない（§20.0）。

| # | バー | 根拠 |
|---|---|---|
| B1 | **異なる閉包で独立に観測されたときだけ広げる**（1つの閉包で何度言われても広げない） | 同じプロジェクトで3回言われたことは、その**プロジェクトの流儀**かもしれない。2つ以上の閉包で観測されて初めて、より広い閉包の性質だと推定できる。判定は出典の `context.scope` を数えるだけ（§4 の独立性判定を再利用） |
| B2 | **1段ずつしか広げない。** 到達点は出典の**最小共通祖先まで**（§0.3.0 の合成規則と同じ）。`repo` から一気に `person` へは飛ばない | 影響範囲が段階的に増える。`person` への拡大は全ドメインに効くので、その一歩は独立の判断にする |
| B3 | **`fact_type: preference_decision` だけを対象にする** | `state_fact` は閉包に固有で陳腐化する（repo の依存バージョンを横断させても害しかない）。`world_fact` はどこでも真なので、広げなくても祖先閉包から参照される |
| B4 | **`sensitive: true` は対象外**（ADR-0010 §5）。**`subject[]` に第三者（`party:*`）を含むものも対象外** | 第三者についての事実を勝手に横断させる正当性がない。PO 自身についての流儀とは別物（R4／S9・S12・S16） |
| B5 | **期間あたりの自動拡大に上限を置く。超えたら拡大を停止し、PO に相談する** | 上限を超えるのは「番頭が何か勘違いしている」か「PO の使い方が変わった」の合図であり、どちらも黙って続けるべきではない。停止は決定的に行う（§20.6 の自律予算と同型） |

| B6 | **兄弟閉包に対立する言明があれば広げない。** 拡大候補と同じ主題について、拡大先の他の子孫に矛盾する `preference_decision` が生きていれば、拡大せず §12 の矛盾として扱う | 【2026-07-26 追加・R6／S12】B1 は「2つ以上の閉包で独立に観測された」ことしか見ない。**3ドメイン中2つが一致していれば、残る1つが正反対を明言していても拡大が通る。** 多数決で PO の別領域での明言を上書きすることになり、§0.7 の1位に触れる |

#### B1〜B6 を呼ぶ入口 【2026-07-26 追加・R6／S12】

**バーを書いたが、判定にかける候補を作る機構が無かった。** §12 経路A の候補抽出は「同一の閉包またはその祖先」に限定されているため、**兄弟閉包どうしのペアを原理的に生成できない**。B1 が要求する「異なる閉包で独立に観測された」ことは、まさに兄弟間の照合でしか分からない。したがって B1〜B5 は一度も呼ばれない状態だった。

> **深い睡眠の Phase 2（§18.1）が `entity_index`（§8.5.1）に問い合わせる**：「**同一の主題キーが、2つ以上の異なる閉包の生きた `preference_decision` に現れているもの**」。返ったものを拡大候補として B1〜B6 にかける。

- **エントリを走査しない。索引に問い合わせる。** コストは**主題キーの種類数**に比例し、記憶の総数 N には比例しない。初版は「生きた意味記憶について照合を1回行う」と書いており、**それは全件走査であって §18.1 の「Phase 2 は全件走査しない」と正面から矛盾していた**（R7 配線チェック B1）。
- **索引は I8 が書き込み時に維持している**ので、この問い合わせは Phase 1 のローリング（§18.1 決定2）とは独立に成立する。**Phase 1 に候補を作らせる設計だと、一巡するまで B1〜B6 が発火しない。**
- **Phase 2 に置くのは、Phase 1 が閉包ごとに並行するため兄弟閉包を見られないからである**——閉包でシャードしても本入口が消えないことが、§18.1 の分割が成立する条件そのものである。

- **対象を `preference_decision` に限る**ので、走査対象は意味記憶の一部にとどまる（B3 が結論として要求している絞り込みを、入口の段で先に効かせる）。
- 判定はルールベース。**LLM は「同じ主題か」の判定にだけ使う**（バッチ内の判断であって制御ループではない。§20.0）。
- ここで拡大しなかったペアは、`unresolved_conflicts` には積まない。**流儀がドメインごとに違うのは矛盾ではない**（B6 が対立と判定したものだけが矛盾になる）。

**§0.7 との整合**：§0.8 は「見逃しコストをノイズコストより高く重み付けする」と定め、一般には広げる方向へ倒す。しかし**可視範囲の拡大に限ればこの向きは逆になる**——誤って広げれば機微情報の漏れと汚染の永続化（3位）、広げ損ねれば言い直しの手間（4位）。**順位に忠実なら保守的に倒すのが正しい。**

**通知の粒度**：拡大は週次1通のダイジェストにまとめる（§21）。B5 の上限を守っていれば、必ずレビューできる分量に収まる。

**未実装の前提（実装順序の制約）**：一覧と訂正の**面**（Memory 面）は `spec-ui` に未記載である（ADR-0010 §2.1 が前提条件と自認）。**この面ができるまで自動拡大を有効にしない。** ただし面が要求する情報は現行の Substrate で足りることを確認済み——絞り込みは `origin: agent_inferred` ＋ 版系譜、対象は `subject[]`、理由は `derived_from`、訂正は `supersede()`。「PO が未読か」は**エントリに書かず driver 側の提示済みカーソルで持つ**（§2 の「滞在状態はセッション側」と同じ規律）。**したがって面の設計が Substrate へ逆流することはない。**

#### 未解決の矛盾を溜めない 【2026-07-26 追加】

矛盾は**検出しただけでは減らない**。流入（新しい記憶）は運用規模とともに増えるのに、流出（決着）の経路が「確定するか PO が明示訂正するか」の2つしかないと、**未解決は単調増加する**（R4／S15。5年で約2,400件と推定された）。さらに §20.6 の指数バックオフが流出をさらに細らせる。

流出経路を足す。

| 状態 | 規則 |
|---|---|
| LLM が「どちらとも言えない」と保留 | **保留の期限を持たせる**。期限を過ぎたら `fact_type` 別の既定規則で機械的に決着させる（`preference_decision` は最新性、`world_fact` は出典数、`state_fact` は観測不能なら最新性）。決着したことは版に残るので、後から覆せる |
| PO 判断待ちが滞留 | **ダイジェストにまとめて再提示**（§21）。個別通知の再送はしない（通知疲れを起こす） |
| 観測不能で決着せず | `state_fact` の**観測可能性が「不能」と宣言された `system`** に属するなら、最新性フォールバックで**決着させる**（未解決のまま残さない）。観測できないものを待ち続けない |
| 2ホップ超の派生 | §20.5-4 の点検で再検証キューへ（列挙で終わらせない） |

**`unresolved_conflicts`（§0.3 のシグナル）が閾値を超えたときの動作を定義する**：`memory_signal` 起床源（§20.2）が発火したら、Steward Driver は**古い順ではなく、影響範囲の大きい順**（`dependents()` の子孫数×`salience`）にトリアージし、上位から決着させる。初版はシグナルを公開するだけで、**発火して何をするかが書かれていなかった**。

#### 「訂正」の定義 【2026-07-26 確定】

§7 のピン留め、§19 の緊急無効化チャネル、§20.3 の最優先枠は、いずれも「ユーザーによる明示的な訂正」を対象とすると書きながら、**何をもって訂正とするかを定義していなかった**。既存の記憶を名指しで否定した発話だけなのか、新しい方針の表明も含むのかが曖昧だった。機械的に定める：

> **訂正 ＝ `origin: user_explicit` の言明であって、`collision_candidates()` が既存の生きた意味記憶を1件以上返したもの。**

候補ゼロなら「新規の言明」、候補ありなら「訂正」。判定はルールベースで、LLM を使わない（§20.0）。これでピン留め・緊急伝播・最優先キューの対象が**同じ一つの規則から導かれる**。

**検出結果を裁定へ配線する** 【2026-07-26 追加】。経路A が対立ペアを検出しても、**その結果を `supersede()` へ流す手順が書かれていなかった**（R2・R3 が連続で指摘）。`supersede()` は「既存エントリへの新版作成」という版系譜の API であり、**独立に生まれた2候補**（互いを supersede しようとした関係にない）には適用経路がない。規則：

> 経路A で対立ペアが確定したら、深い睡眠は**敗者側に対し必ず `supersede()` を呼ぶ**。新版は `tombstone: true` とし、`derived_from` に勝者と敗者の旧版の両方を含める。これにより「なぜ敗れたか」が版系譜から辿れる。

これを書かないと、§20.5-6（覆った根拠に基づく外向き副作用の点検）も発火しない——あの点検は「敗者の版が変わること」を前提にしているためである。

**経路B：出典の系譜による波及**（抽象度が上がった派生を拾う）

経路A には原理的な穴がある。訂正「軽微な変更は自動マージでよい」と、2段蒸留された「PO は統制を重んじる」は**語彙が一つも重ならない**。類似度ベースでは永久に引っかからない（ADR-0010 §6-S2）。**蒸留が抽象化するほど、訂正が届かなくなる。**

これを埋めるのが `derived_from` の逆引きである。あるエントリが supersede / tombstone されたら、それを出典に持つ子孫を再検証キューへ積む（§20.4）。**語彙ではなく系譜で辿るので、抽象度が上がっていても届く。**

### 矛盾解決規則は origin → fact_type の順で分岐する 【ADR-0010 で改訂】

> 本節は [ADR-0010](../adr/adr-0010-memory-substrate-schema.md) §1.1・§1.3 が正典。以下はその反映。

**まず `origin` を見る。** `origin: user_explicit` は `agent_inferred` / `external` に**無条件で優先**する。同一 origin の中でのみ、下表の fact_type 別規則で裁く。

この優先は**書き込み経路の実行層で強制する**（最新版が `user_explicit` のエントリに対し、`agent_inferred` の新版を作れないようにする）。プロンプトに書くだけにしない。旧版には origin の例外が無く、番頭が後から作った推論が PO の訂正に**時刻の新しさだけで勝つ**状態だった（ADR-0010 §6-S3/S5）。§0.7 の1位そのものである。

同一の規則を全事実に適用すると必ず破綻するため、fact_type で分岐する（`kind: semantic` のみ適用）。

#### `asserted_by[]` が異なる場合 【2026-07-26 追加】

上表は `origin` が同じものどうしを裁くが、**`origin: user_explicit` が2つあって言明の主体が別人なら、それは「同じ人の考えが変わった」ではなく「2人が違うことを言っている」であり、最新性で裁くのは誤りである。**

**単数 PO の体制でもこれは起きる。** PO が第三者の言明を代弁して記録する場合——「Yさんは軽微な変更は自動マージでいいと言っている」——`origin` は PO の発話なので `user_explicit` だが、`asserted_by` は `["party:Y"]` である。`VISION.json` の `out_of_scope` が除外しているのは「チーム利用・マルチテナント」＝**複数の人が番頭を直接操作すること**であり、**単数の PO が第三者の言明を持ち込むことは除外していない。** したがってここは実装範囲内であり、規則が要る。

> **`asserted_by[]` に `self:po` を含む言明は、`party:*` のみの言明に優先する。** 同一区分の中でのみ上表の `fact_type` 別規則で裁く。

- 根拠は §0.7 の1位が守ろうとしているものである。**あの順位が守るのは「PO の訂正」であって「誰かの主張」ではない。** 第三者の言明は判断材料であり、PO の決定と同格ではない。
- `party:*` どうしの対立は**裁かない**。`unresolved_conflicts` に積み、PO に判断を仰ぐ（§12「未解決の矛盾を溜めない」の PO 判断待ち経路）。他人どうしの意見の相違を番頭が裁く正当性がない。
- **`self:*` が2つ以上ある場合の裁定だけが未定義**であり、これは複数 PO ＝ `out_of_scope` に当たる。残件は §20.8 の **U20**。`asserted_by[]` があるので、その状況に踏み込んだときに**誰の言明が誰に敗れたかは版系譜から辿れる**。

| fact_type | 規則 | 理由 |
|---|---|---|
| `preference_decision`（規範的言明。誰が決めたかは `origin` が持つ） | **最新性が勝つ** | 出典数優先だと訂正が効かなくなる（§0.7 の1位） |
| `state_fact`（時とともに変わる客観的状態） | **観測し直して裁く**。観測できないときのみ最新性 | 議論ではなく観測で決まる。発火は §20.4、観測手段は `external_ref` の `system` ごとに宣言 |
| `world_fact`（変わりにくい客観的事実） | **出典の数と独立性が勝つ** | 最新性優先だと単発のデマに弱い |

### コールドスタート時の過剰な重み

記憶が空のときベースLLMに縮退するのは問題ないが、**最初に入った記憶が不当に強くなる**。競合がないため常に上位に来て、参照され、強度が上がる。誤りでも同じ。

さらに、確信度を出典数で算出すると**長く居座った誤りほど出典が多い**という逆転が起きうる。上の分岐はこれへの対策でもある。

### 虚偽記憶（スキーマ補完）のリスク

蒸留過程でLLMが言われていないことを補完するリスクは完全排除できない。**出典リンクと確信度で「検知して確信度を下げる」ところまでが現実的な到達点。** 蒸留を可逆にしておくこと（出典を必ず残す）が唯一の机上での対策。

## 13. 想起強度と減衰 【降格】

**位置づけを変更した。** 減衰は本設計の主役ではなく、§7 のスコア関数の一特徴量である。

### 理由

「忘却」と呼んでいたものは実際には3つの別問題だった。

1. その事実はもう真ではない → **有効期間と版管理**（§5・§3）
2. 今この瞬間の話題と無関係 → **`rel_norm` によるランキング**（§7 の入場スコア・§8.5.5）
3. そもそも一度も役に立ったことがない → **想起履歴＝減衰**

減衰が測るのは3だけであり、この中で最も効かない。さらに減衰は逆効果になる場面がある。**半年触っていないプロジェクトの記憶は、その話題が始まった瞬間に最優先で入れるべきもの**だが、減衰はそれを最も低いスコアにする。「使われていない＝重要でない」は、話題が周期的に戻る実務では成立しない。

### 残る役割

- §7 の入場スコアにおける**弱い事前分布**（`s_admit` が同点のときのタイブレーカー。**適用場所は §8.5.5 の「定員内の順序」4**）
- §14 のアーカイブ降格の判断材料

> **「検索コスト抑制」を役割から削除した** 【2026-07-26 訂正】。旧版はこれを残る役割の2つ目に挙げていたが、**§7-F3 は「アーカイブ層は検索対象から除外しない」と明記しており、同じデータについて逆のことを述べていた**（R4／S13-(6)。P3 の incident 案件）。§7-F3 を正とする。検索コストは減衰ではなく **§8.5.2 の二段照会**（active 層と archive 層の分割）とアームごとの取得上限で抑える。

### 時定数の単位

- **保存層の strength** — 単位は日〜月。物理削除ではなくアーカイブ降格の判断にのみ使う
- **ワーキングセットの activation（§7）** — 単位は**ターン**。効果が数ターンで観測でき、実際にチューニング可能なのはこちら

減衰させないもの: 手続き記憶、ピン留め対象。

| 処理 | 条件 | 内容 |
|---|---|---|
| 昇格 | recall_count 閾値超え | エピソード→意味記憶へ一般化（海馬→大脳皮質の固定化に対応） |

### `propose()` を呼ぶ条件 【2026-07-26 追加】

**誰がいつ候補キューへ積むかが定義されていなかった。** 上の表は「昇格の条件」を書いているが、それは**候補キューに入った後**の話である。キューに入る条件が無いと、後段の機構（§20.4 の同一バッチ内の対立検査、§12 の矛盾検出、§20.5-6 の外向き副作用の点検）は**入力が来ないまま空回りする**（R4／S3）。

次のいずれかを満たす episode は、セッション終了時の浅い睡眠が**必ず `propose()` を呼ぶ**。判定はルールベースで、LLM を使わない（§20.0）。

**`propose()` は重複を弾く**：`(content のハッシュ, scope, derived_from の集合)` が同一の未消費候補が既にキューにあれば no-op とする。**これが §18.1 決定3 の冪等性の根拠である**（同一シャードを2回処理しても候補が二重に積まれない）。

| 条件 | 理由 |
|---|---|
| `origin: user_explicit` | PO の言明は一撃でも失ってはならない（§0.7 の1位） |
| `recall_count` が閾値超え | 従来からの条件 |
| **`external_ref` に外向きの command を持つ** | サブシステムに送った指示は現実を変えている。候補にならないと §20.5-6 の点検が発火しない |
| **規範的言明を新規に確立した**（`fact_type: preference_decision` 相当の内容を含む） | 番頭が単独で下した運用判断も方針である。候補にならないと他の分身の判断と突き合わされない |
| **`origin: external` を含む** | 外部由来の主張は §12 の検出に載せる |

### PO 由来の一撃決定は閾値をバイパスする 【2026-07-26 追加】

昇格条件を `recall_count` 閾値だけにすると、**一度しか言われていない PO の決定や訂正が意味記憶に上がらない**。矛盾解決（§12）は意味記憶の運用なので、上がらなければ規則は一度も適用されない——「レビューは全部見たい／やっぱり自動マージでいい」のような一撃の方針転換が、確率的な想起回数に依存して効いたり効かなかったりする。§0.8「訂正はピン留めし、確率的な機構に一切委ねない」に反する。

したがって **`origin: user_explicit` のエピソードは、次の睡眠で無条件に意味記憶へ昇格する**。`recall_count` は見ない。

**ピン留めを条件に含めない** 【2026-07-26 訂正】。初版は「`user_explicit` かつピン留め対象」としたが、ピン留めの条件は「訂正であること」であり、訂正の定義は「衝突候補が出たもの」（§12）である。したがって**候補ゼロの新規の言明は、ピン留めされず、昇格もされない**という連鎖が生じていた。PO と合意した一撃の決定が閾値に落ちる（R2 の指摘の残り）。条件を鎖にすると片方が外れて全部外れるので、`origin` だけで判定する。

### 手続き記憶の出力形式は SKILL.md を採用する

チャンキングが生成する手続き記憶は、**agentskills.io の SKILL.md 形式**で出力する。既存ハブのスキルをそのまま消費でき、生成したものを外部に出せる。

形式を借りるだけで実装は独立している。外部標準の採用は「実装はオリジナル」という方針と矛盾しない。

## 16. 評価指標

Policy 層の全パラメータはこれで調整されるため、**実装より先に計測基盤を置く**。

### ノイズ率（自動計測）

注入した各項目に対し、出力がそれを参照したかを記録する。応答時に使用した記憶IDを申告させれば近似できる。参照されなかった項目は次回スコアを下げる直接のフィードバックになる。

> **前提条件**: 参照検出の信頼性。これが取れないと §7 の β による正のフィードバックが機能しない。§0.9 の通り最優先で検証する。

### 見逃し率（訂正イベント起点）

ユーザーの訂正が入ったターンについて、必要だった記憶が「ストアには在ったが注入されなかった」かを事後判定する。訂正は頻繁ではないため全件手動でも回る。

### ベースラインとの比較

各機構は「あった方が良さそう」ではなく**ベースラインに対する改善**として評価する。これを上回らない機構は削る。

ベースラインは2つ置く。

1. **素朴なベースライン** — 全ログを長コンテキストに投入＋素直な検索。下限として必ず超える
2. **実在のベースライン** — Hermes Agent（Nous Research、MIT）の記憶実装。agent-curated memory + 定期的な nudge + FTS5 全文検索 + LLM要約という構成で、実際に広く使われている。**§9 が否定している「明示的リコール・明示的書き込みに依存する方式」の実物**であるため、比較対象として最適

Hermes に実装を載せることはしない（実装はオリジナルとする方針）が、**比較対象として使うことに矛盾はない**。

コーディング文脈ではテストの通過・不通過という客観的な結果があるため、評価の一部を自動化できる。

### 可観測性

なぜこの記憶が注入されたか／されなかったかを人間が追える形で記録する。実運用のデバッグで最初に必要になる。

**実体は `retrieve()` が返す `trace`** （§8.5.0）。**「されなかった」側は各段で落ちた件数と理由を記録しないと事後に復元できない**——フィルタ（§8.5.3）で落ちたものは `s_admit` を持たず、アームに拾われなかったものは候補集合にすら現れないため、後から「なぜ出なかったか」を計算し直す手段が無い。**記録は検索と同時にしか取れない。** trace はセッション側に持ち、エントリには書かない（§2 の滞在状態と同じ規律）。

### パラメータ調整

τ・重み・閾値はベイズ最適化等でオフライン再調整。**見逃しコストを意図的に高く重み付けする**（§0.8）。完全自動化は「無難に忘れる」方向へ偏りやすい。

### 16.1 番頭としての評価 — 自己改善ループとの接続 【2026-07-26 追加】

banto は既に自己改善ループを持つ（`spec-improvement-loop`）。本節の指標はそこに接続する。

| Quirefold 側 | improvement-loop 側 |
|---|---|
| Policy 層のパラメータ（Part II 全体） | **層B（ポリシーパラメータ）**。エージェントが編集提案、コミットは PO レビュー対象 |
| ノイズ率・見逃し率・ベースライン比較 | 改善タスクの `hypothesis.metric` に入る値 |
| driver のパラメータ（§20.6） | 同じく層B。ただし**番頭からは読み取り専用**（§20.6） |
| 蒸留プロンプト・分類ガイド | 層A（プロンプト資産） |
| memory / driver の機構コード | 層C。エージェントは提案まで |

#### 既存のベンチマークが当たらない理由

記憶・長文脈のベンチマークは複数実在するが、測っている軸が違う。

1. **失敗モードの順位が非対称**（§0.7）。「訂正が消える ＞ 確信を持って誤る ＞ 汚染 ＞ 見逃し ＞ ノイズ」という重み付けを、全問等重みの正解率は表現できない。
2. **時間軸**。§0.9 が明記するとおり「パラメータの調整には実時間の経過が要る」。5ヶ月放置して再開する挙動は、合成的に圧縮した履歴では測れない。
3. **目的関数が違う**。測りたいのは「番頭が賢いか」ではなく「**番頭がいることで PO の判断回数が減ったか**」。improvement-loop の到達目標「同じクラスの問題を二度指摘しなくて済む」は正解率ではない。

#### N=1 問題と、その割り方

PO は1人しかいないので、**番頭のいる自分といない自分を A/B できない**。絶対評価は原理的に取れない。したがって**時間で割る**——improvement-loop の `po起源の割合` をメタケイデンス（月次）で追い、同じクラスの指摘が減っているかを見る。絶対値ではなく傾きを見る。

#### 構造的な強み：行動観測

§0.9 の**行動観測方式**が効く。自己申告（使った記憶IDを LLM に言わせる）は信頼できないが、コーディング文脈では失敗が**行動として直接観測できる**——既にコンテキストにあるファイルの再読み込み＝見逃し、確立済みの規約に反する実装＝訂正の消失、同一調査の反復＝想起されていない。Kobo がイベントログを決定的に持ち、テストの通過・不通過という客観的結果もあるため、**仕事をすると評価データが出る**。

これは「第一の店＝開発」を選んだことの副産物である。開発は正解が機械的に判定できる稀な領域であり、記憶システムを育てる場所として最良の選択だった。家計や研究ドメインでは同じことができない（→ 他ドメイン増設時、評価は行動観測から PO の主観へ後退する）。

#### Goodhart のリスク

「訂正イベントが減る」を metric にすると、番頭は**訂正されないように振る舞う**方向へ最適化しうる——曖昧に言う、断定を避ける、判断を PO へ投げ返す。どれも訂正を減らすが、番頭としては劣化している。§0.7 の1位を測る指標が、1位を回避する振る舞いを育てる。

improvement-loop は開発側で同型の問題を既に認識している——「**回避策（workaround）は最重要シグナル。成功した回避は incident にならず欠陥を隠蔽するため、明示的に収集する**」。**この規律を番頭自身の評価にも適用する**：番頭がうまく回避したこと（判断を避けた、曖昧に答えた、PO に投げ返した）を積極的に収集対象にする。

improvement-loop の「レビュー必要性の縮小は目標として掲げるものではなく、検証の機構化の結果として得る」も同じ趣旨の防御である。

#### 割り切りと規律

improvement-loop §5 のとおり「厳密な因果評価は行わない。目的は方向性の確認と、特に**明確な悪化の検出**」。記憶が良くなったのか、モデルが変わったのか、タスクが簡単だったのかは分離できない。したがって自己改善ループを回すなら「**変更は一度に一つ**」が実質的な前提になる。§16 が置く2つのベースライン（素朴な長コンテキスト投入／Hermes Agent）は、絶対値が測れなくても「下回っていないか」は測れるという意味で貴重である。

#### シナリオ検証を評価手法として残す

**シナリオを固定し、設計を変え、破綻箇所の増減を見る**——この手続きは、外部ベンチマークが無い領域での実用的な評価手法として機能した。**手順・シナリオ資産・ラウンド履歴の正典は `docs/notes/memory-verification-scenarios.md`**（初回は ADR-0010 §6 に記録）。シナリオは資産として保全し、設計変更のたびに回す。ただし検証プロトコル §2.5 が明記する限界（シナリオが見ていない領域は何度回しても見つからない）を承知の上で、定期的にシナリオ自体を入れ替える。

# Part III — Loop（実行ループ）

## 17. 内部状態（感情の機能化）【実験的】

「今この瞬間どう振る舞うか」を決めるレイヤー。§11 の顕著性が「何を覚えるか」を決めるのに対し、こちらは「今どう動くか」を決める。入力ソースは重なるが出力先が異なる。

| 変数 | 反映するもの | 行動への影響 |
|---|---|---|
| `uncertainty` | 確信度平均、矛盾検出頻度 | 高いほど断定を避け確認を増やす |
| `frustration` | 同一タスクでの失敗・リトライ回数 | 閾値超えで戦略転換 or エスカレーション |
| `fatigue` | コンテキスト圧力（§19） | 睡眠フェーズへの移行トリガー |

### メカニズムとしての限界

自然言語で内部状態を注入する方式は**プロンプトによる条件付け**であり、生成内容は確実に変わる。しかしモデル内部に持続する隠れ状態が存在するわけではなく、次の推論の入力テキストの一部に過ぎない。「感情に突き動かされている」のではなく「感情の状態を説明された指示に従っている」に近い。

**実際のブラックボックス性の所在**は感情メカニズムの内部ではなく、複数の指示（プロトコル、直前の発言、内部状態）が競合したときの優先順位。人間の感情のように理性を押しのける保証はなく、効き方はモデルとプロンプトで変動する。

### 運用方針

1. 数値ではなく「現在: 不確実性が高い状態」程度の簡潔な自然言語で2〜3行
2. §24 のプロトコルに行動ルールを書いて明示的に接続する（曖昧な感情語だけでは不安定）
3. **eval で検証し、効果がなければ削る**

## 18. 睡眠と覚醒

### 眠気と発火条件

コンテキスト使用率に応じて `fatigue` を漸進的に蓄積させる。圧力モデルにする利点は**安全な区切りを待てる**こと。

- **ソフト閾値** — アトミックな境界（サブタスク完了直後など）を待って自発的に眠る
- **ハード閾値** — 区切りを待たず強制的に中断・整理する

ツール呼び出しやトランザクションの途中での強制中断は副作用の不整合を招くため避ける。

### 3層の睡眠

| 種別 | 頻度 | 処理内容 |
|---|---|---|
| **マイクロスリープ** | 予算超過時／話題転換時 | §7 のバッチ退場、§10 のツール結果圧縮。記憶ストアには触らない |
| **浅い睡眠** | セッション終了ごと（並行可） | 直近差分の圧縮、即座の矛盾検出。**事実を確定させず候補としてキューに積むだけ** |
| **深い睡眠** | 低頻度（日次／週次、単一writer） | キューを消費し、候補間の矛盾を解消して意味記憶を確定。チャンキング、アーカイブ降格、パラメータ再調整 |

差分のみだと**数週間にまたがる繰り返しパターンを見逃し**、全件処理はコストが線形に増えるため、二段に分ける。マイクロスリープは §7 のバッチ退場と同一機構であり、独立した実装を持たない。

**深い睡眠が一晩で全件を見ることは、規模が増えると成立しない。** 差分を毎回・全件をローリングで一巡させ、閉包ごとに並行する Phase 1 と横断の Phase 2 に分ける——**規模の設計は §18.1 が正典**であり、本節は中身だけを定める。

### 18.1 深い睡眠のスケーリング 【2026-07-26 新設・実装前に必要】

**§18 の表は「深い睡眠＝低頻度（日次／週次）・単一 writer」とだけ書いていた。それは規模を持たない記述である。** 試算では全件処理が5万件で約7時間、100万件で約6日、再索引は20万件で約28.6時間（R3／S11・R6／S17）。**2〜4年目で一晩の窓を超える。** §15 の削減策は定数倍の改善であって線形スケーリングを変えない。

一方で §14 は「差分のみだと数週間にまたがる繰り返しパターンを見逃す」と自認しており、**全件処理を捨てる選択もない。** さらに §19 は深い睡眠を単一 writer と定めており、4ドメイン並行運用では直列に詰まる（R3／S11・S3）。

#### 制約：閉包でシャードすると壊れるものがある

素朴な解は「閉包（ドメイン）ごとに並行させる」だが、**閉包をまたぐ照合を要する処理がそれで壊れる。**

| 処理 | 必要な視野 |
|---|---|
| 昇格・統合・降格・アーカイブ・チャンキング（§14） | **閉包内で完結する** |
| §12 経路A の矛盾検出 | 同一閉包**とその祖先**（縦方向） |
| **B1〜B6 の閉包をまたぐ一般化**（§12） | **兄弟閉包**（横方向）。閉包で切ると入口が消える |
| `unresolved_conflicts` のトリアージ（§12） | 全閉包（影響範囲順に並べる） |

**壊れるのは4行のうち3行だが、いずれも「全件を見る必要はなく、候補を見れば足りる」。** ここが解の鍵である。

#### 決定1：2フェーズに分ける。閉包で並行するのは Phase 1 だけ

| | Phase 1（閉包ローカル） | Phase 2（横断） |
|---|---|---|
| 並行性 | **閉包ごとに独立した writer。並行** | **単一 writer** |
| 入力 | 候補キュー（`propose()`）＋当該閉包の差分＋ローリング対象シャード | **(i) Phase 1 が積んだ候補（祖先方向） ＋ (ii) `entity_index` への問い合わせ（兄弟方向）。どちらも全件走査ではない** |
| 処理 | 昇格・統合・降格・アーカイブ・チャンキング・**閉包内の**矛盾検出 | 祖先方向の矛盾検出・**B1〜B6 の兄弟照合**・`unresolved_conflicts` のトリアージ |
| コスト | **N に比例するが、閉包数で割れる** | **候補数に比例する。N に比例しない** |

> **Phase 2 の入力は2種類あり、どちらも全件走査ではない。**
>
> - **(i) 祖先方向**：Phase 1 が閉包内で裁けなかった矛盾候補を Phase 2 のキューへ積む。**判定規則**——候補ペアの一方が自閉包に無い（祖先閉包に属する）とき、Phase 1 は裁かずに積む。
> - **(ii) 兄弟方向（B1〜B6）**：**`entity_index` への問い合わせ**で得る——「同一の主題キーが2つ以上の**異なる閉包**の生きた `preference_decision` に現れる」。コストは**主題キーの種類数**に比例し、N には比例しない。
>
> **(ii) が Phase 1 に依存しないことが重要である。** ローリング全件走査（決定2）では Phase 1 が一晩に見るのは1シャードだけなので、**Phase 1 に兄弟照合の候補を作らせると、一巡するまで B1〜B6 が発火しない**。`entity_index` は I8 が書き込み時に常時維持しているので、ローリングとは独立に問い合わせられる。

**初版は「Phase 1 が積んだ候補だけ」と書き、同時に §12 に「Phase 2 が `preference_decision` の生きた意味記憶を照合する」と書いていた。後者は全件走査であり、正面から矛盾していた**（R7 配線チェック B1）。**設計の要だと自称した箇所そのものが破れていた。** 索引への問い合わせに置き換えて解消した。

- **Phase 1 の writer 粒度は閉包**である。§19 の「深い睡眠＝単一 writer」はここで**閉包ごとの単一 writer**に緩む（同一閉包に対して2つの Phase 1 が同時に走ることはない）。
- **Phase 2 は全体で1つ**。§20.1 が Steward Driver を1つにした3つの理由（深い睡眠の直列化・再検証キューの直列消化・内発的動機の重複防止）は Phase 2 で保たれる。
- **再検証キューの消化（§20.4）と自己内省の点検10項目（§20.5）は Phase 2 に属する** 【R7 配線チェック B3・D2】。どちらも閉包をまたぐ視野を要し、かつ §20.1 が「直列でないと §3 の版が無用に分岐する」と定めている。**どのフェーズかを書かないと素直に読めば Phase 1（並行）に落ち、§20.1 の理由が黙って崩れる。**
- **Phase 1 の writer は、自分の閉包に `scope` を持つエントリ以外に新版を作れない**（§0.3.0 の **I11**）。`supersede()` の実行層で強制する（`origin` 優先の強制と同じ場所）。
  - **I9 だけでは足りない** 【R7 配線チェック B2】。I9 は**新しく作るエントリの `scope` の上限**を定めるだけで、「閉包 X の writer が閉包 Y の既存エントリに新版を作ること」を禁じていない。初版はこれを I9 の効果として書いており、**過大な引用だった**。並行化の安全性は I9 とこの規則の**両方**で成り立つ。
  - 祖先閉包のエントリを直したくなった場合は、Phase 1 は書かずに **(i) の候補として Phase 2 へ積む**。

#### 決定2：全件処理はローリングにする

**差分は毎回、全件は周期で一巡させる。**

```
深い睡眠1回 = 全閉包の差分処理（毎回）
             + ローリング対象シャード1つの全件処理
```

- シャードの単位は**閉包**。閉包が大きすぎる場合は閉包内を `created_at` のレンジで分割する（`id` が ULID なので時間順に切れる。ADR-0010 §3）。
- **次に処理するシャードは、最後に全件処理した時刻が最も古いもの**（同点は閉包識別子の辞書順）。決定的に選び、番頭の裁量に委ねない。**順序を書かないと「一巡する」という保証そのものが成立しない**（R7 配線チェック 決定2-②③④⑤）。
- **シャード台帳は閉包レジストリの変更（新設・改名・畳み）に追随する**（`entity_index` と同じ契約。§8.5.6）。新設された閉包は未処理として台帳に入り、畳まれた閉包は台帳から外れる。**この追随は §26.3 が満たす**（新設・畳み・統合のたびにレジストリ・`entity_index`・シャード台帳の3箇所へ伝播する）。
- **カバレッジ周期**（全シャードを一巡する時間）をパラメータにする。
- **制約**：`カバレッジ周期 < 検出したいパターンの時間幅`。§14 が「数週間にまたがる繰り返しパターン」を要求しているので、**周期は数週間より短く保つ**。
- **守れなくなったときの動作を決めておく**（決定的に。段階的に降りる）：
  1. **1周期の超過** → §20.5-10 が検出し、ダイジェストで通知する（§21）
  2. **2周期連続の超過** → **シャードを自動分割して周期を守る**（大きいシャードを `created_at` レンジで2つに割る。これは可逆で、台帳の操作だけで済む）
  3. **分割してもなお超過** → **自律的な全件走査を停止し、差分処理だけを続けて PO に上げる**（§20.6 の自律予算の枯渇と同型。停止は決定的に行う）
  - **「通知して終わり」にしない。** 検出はするが対応が無い、は §20.5 が繰り返し潰してきた欠陥型である（R7 配線チェック C1）。
- これで「窓に収まる」と「数週間パターンを見逃さない」が両立する。**一晩で全件を見ることを諦め、一巡する保証に置き換えたのが本決定の要点である。**

#### 決定3：中断可能・再開可能にする（U5）

**深い睡眠は一晩で終わらない前提に立つので、途中で止まることが正常な状態になる。**

- **進捗カーソルとシャード台帳を driver 側に持つ。エントリには書かない**（§2 の「滞在状態はセッション側」と同じ規律。エントリに書くと並行 Phase 1 で壊れる）。
- **処理は冪等でなければならない。** 同じシャードを2回処理しても結果が変わらないこと。**根拠となる規則をここで定める**——初版は「`propose()` を経由するので候補キューの重複で検出できる」と書いたが、**参照先に重複検出の規則が実在しなかった**（R7 配線チェック C4）：

  > **`propose()` は、`(content のハッシュ, scope, derived_from の集合)` が同一の未消費候補が既にキューにあれば no-op とする。**

  判定は機械的な事実だけを見る（LLM を使わない。§20.0）。これで同一シャードの再処理が候補を二重に積まない。
- **クラッシュしても索引は本体とずれない。** I8 が同一トランザクションを要求しているためである。**例外は A3（埋め込み索引、遅延許可）だけ**で、そのずれは §20.5-7 の点検が拾う。
- **したがって保存層の要件が1つ確定する：エントリの書き込みと索引の更新を1つのトランザクションに入れられること。** ADR-0010 の帰結が「単一ストア内でテーブルと索引を分ける（別ミドルウェアを4つ立てない）」と決めていたのは、この要件と整合する。
- **再開時に未完了シャードを検出したら `store_fault`（§20.2）を上げる。** 「前回落ちた」ことが誰にも知られないまま次の周期に進むと、カバレッジ周期の保証が黙って破れる。

#### 再索引も同じ機構に乗る

§8.5.6 の再索引（20万件で約28.6時間）は、**本節のローリングと同じシャード台帳・同じカーソル・同じ冪等性**で回す。独立した機構を作らない。埋め込み（A3）の後付け導入もこの経路である。

**台帳を共有するので競合を排除する必要がある** 【R7 配線チェック C2】。**シャード台帳はシャードごとにリース（lease）を持ち、1つのシャードを同時に1つのジョブ（Phase 1 か再索引のいずれか）にだけ貸す。** 取れなかった側は次の周期まで待つ。リースはプロセスが落ちれば期限切れで解放され、**未完了として `store_fault` に上がる**（決定3）。

#### 残る未定（実装と eval が要る）

- カバレッジ周期の具体値、シャードの目標サイズ、1回の窓の長さ（§0.9-4 のパラメータ）
- **閉包が極端に偏った場合**（1つの閉包が全体の9割を占める）にシャード分割が有効に働くか。閉包内の時間レンジ分割で足りるはずだが未検証（推測）

### セッション再開は特別扱いしない

新セッション開始時に手作りの再開サマリーを注入せず、§7〜§9 のパイプラインをそのまま流用する。「セッション開始」自体をクエリ発火のトリガーとし、クエリの種は直前のゴール状態＋高顕著性の記憶。

起床時だけの特殊ロジックを持たないことで実装が単純になり、睡眠フェーズの要約に漏れがあっても最初のターンの注入が二重の安全網になる。

## 19. 並行セッション 【本文へ昇格】

### 並行は追加要件ではなく前提

自律ループが裏で走りながらユーザーが話しかける（§21）という設計は、定義上**2つの独立したコンテキストが同時に存在する**ことを意味する。並行をやめる選択肢は効率の問題ではなく、自律性の要件から存在しない。

**人間が直列なのは体が1つで注意が1つだからであり、記憶アーキテクチャの要請ではない。** §0.2 原理1を適用してアナロジーを捨てる。脳から借りるべきは「符号化は連続的、固定化は別フェーズ」という時分割の方であり、それはそのまま §18 の3層睡眠になっている。

### 層ごとの並行性

| 層 | 並行性 | 理由 |
|---|---|---|
| 自己モデル・プロトコル | 完全並行 | 読み取り専用 |
| ワーキングセットの滞在状態 | 完全並行 | セッション側に持つため共有していない（§2） |
| エピソードログ | 完全並行 | 追記のみ。session_id で別ストリーム |
| 意味記憶 | 要調整 | §3 の版管理で検出可能な矛盾に還元 |
| 深い睡眠 **Phase 1** | **閉包ごとに単一writer**（閉包間は並行） | 閉包内で完結する処理だけを置くため（§18.1）。閉包をまたぐ書き込みは §0.3.0 I9 が禁じる |
| 深い睡眠 **Phase 2** | **全体で単一writer** | 閉包をまたぐ照合を行うため。ただし**入力は Phase 1 が絞った候補だけ**なので全件走査にならない（§18.1） |

### 読み取りはスナップショット隔離

セッションBの動作中にセッションAの書き込みが即座に見えるべきではない。理由は独立に2つあり、同じ結論を指す。

1. **体験として悪い** — 自分が何もしていないのに前提が途中で変わる
2. **キャッシュが壊れる** — 他セッションの活動でプレフィックスが失効するのは制御不能

セッション開始時およびワーキングセット再構築時に一貫したスナップショットを取る。

### 訂正の緊急伝播

スナップショット隔離の代償として、**セッションAでの訂正を裏の自律ループが知らないまま作業を続ける**問題が残る。§0.7 の1位に該当するため放置できない。

ピン留め対象の訂正のみ、通常のスナップショット更新とは別の**緊急無効化チャネル**を持たせる。乱発するとキャッシュが死ぬため、**対象は「ユーザーによる明示的な訂正」に限定する**（推論による前提変更は含めない）。訂正の判定は §12 の定義に従う（同じ規則から導く）。

**実体は `changes_since(cursor)` である** 【R6 配線チェック W37】。走行中の各分身はスナップショットを取った時点のカーソルを持ち、Steward Driver が訂正を検知したら（§20.4 の点火）**生きている分身に対して `changes_since()` の差分を渡し、該当エントリだけをワーキングセットから無効化させる**。スナップショット全体を取り直さないので、失効するのは無効化されたエントリ以降のプレフィックスに留まる。`changes_since()` は §0.3 に置かれていたが**呼ぶ主体が書かれていなかった**——ここが唯一の呼び出し元である。

### 受容するコスト

セッションごとにワーキングセットを維持するため、同じ記憶が複数コンテキストに載りトークンを重複消費する。正しさの問題ではないが、自律ループが常時走るなら無視できない額になる。

**深い睡眠の粒度は §18.1 が正典である** 【2026-07-26】。旧版は本表に「深い睡眠＝単一writer／低頻度なので効率上の損失はほぼない」とだけ書いていたが、**「低頻度なので損失はない」は規模を持たない主張だった**——4ドメイン並行で全件処理が一晩を超えると、直列化の損失は「ほぼない」では済まない（R3／S11）。

**共有ワーキングセットによる節約は採用しない。** 他セッションの活動で自分のプレフィックスが失効するようになり、キャッシュ効率の悪化が節約分を上回る。

## 20. driver — 起床と差配 【driver モジュール】

> 本節は 2026-07-26 に全面的に書き直した。旧版は `perceive()` / `update_goals()` / `decide_action()` という関数名だけの疑似コードであり、10シナリオ検証（ADR-0010 §6）が挙げた未定義のうち4つがここに落ちていた。

### 20.0 最上位の制約：driver に LLM を置かない

**driver は制御ループである。** banto が生まれた理由は「開発手法がプロンプトの遵守期待に依存し、ゲート・監査が構造的に保証されない」こと（VISION.problem／**D2「制御ループに LLM を置かない」**）。driver の判断を LLM に委ねると、番頭の自律性そのものが D2 違反になる。

> **driver は決定的コードとして「いつ・何を起こすか」だけを決める。「何をするか」は起こされたセッション（分身＝LLM）が決める。**

これは Kobo と番頭の関係と同型である。Kobo は決定的で、判断が要るときに番頭を kick する。driver も決定的で、判断が要るときに分身を起こす。§0.5 原理2「安全性を LLM の判断力に依存させない」は、この線引きで構造的に満たされる。

**帰結**：本節に現れる条件・閾値・優先度はすべて**ルールとして評価できる**形で書く。「番頭が重要だと思ったら」のような述語は driver に置かない。そう書きたくなったら、それは分身を起こす条件である。

**規則を1つ書いたら、次に進む前に6つを埋める** 【2026-07-26 追加・R4 の教訓】。1日の作業で**同じ形の欠落を6回作った**——規則を書いて配線を忘れる、という癖である。手順として固定する。

> **① いつ発火するか ② 何をするか ③ 誰が呼ぶか ④ どこで強制するか ⑤ 入力は誰が用意するか ⑥ 結果はどこへ行くか**

どれか1つでも空欄なら、その規則はまだ書き終わっていない。実績：②が抜けた（§20.5-4 は列挙するだけだった）／③が抜けた（`authored_by` は能力だけ）／④が抜けた（`content` 書き分けの検査場所）／⑤が抜けた（同一バッチ検査に候補キューへの投入者がいなかった）／⑥が抜けた（§20.5-5 に優先度も通知も提示面も無かった）。

**そして⑦：層をまたいで同じ規則を配線したか。** `origin` の強制を `record()` にだけ書いて蒸留層に書かなかったため、trust laundering が残った。**経路ごとに規則を書くのをやめ、§0.3.0 の不変条件として1箇所に置く**のがこの問題への構造的な答えである。

> **このチェックリストだけでは足りない** 【2026-07-26 追記】。上の7項目を自分自身にかけると、**③誰が呼ぶか＝書き手が思い出したとき／④どこで強制するか＝どこにもない**、と空欄になる。§20.0 が言う「散文の規律は素通りする」に、対策自身が該当していた。
>
> したがって規律を**成果物の形**に落とす：**§20.7.1 の配線レジストリ**（機構を足す＝1行を足す。欄が空なら文書の上で欠落が見える）と、**検証プロトコル §2.4 の配線チェック**（毎ラウンド専任エージェントが静的に検査する）。この2つが③④を埋める。チェックリストは書き手の補助として残すが、**それだけに頼らない**。

**この原則は driver の外でも成り立つ**（R2 の再検証で確認。検証プロトコル §7）。同じ10シナリオを設計前後で回した結果、**実行層・スコア式・API シグネチャのいずれかに落とした規律だけが機能し、散文で書いた規律はすべて素通りした**。`origin` 優先（書き込み経路で強制）と版解決（候補生成の手順）は機能し、`sensitive` の取り扱い規律・`citations` の検証・`derived_from` の記入義務は機能しなかった。効いた側と効かなかった側の差は、この一点だけだった。**Part II / III に規律を書き足すときは、それが落ちる先（実行層・式・シグネチャ）を同時に指定する。**

### 20.1 二層構造：常駐 driver は1つ、ターンループは分身ごと

| | 個数 | 責務 |
|---|---|---|
| **Steward Driver** | **番頭に1つ**（常駐） | 起床源の監視、作業キューの管理、分身の起動、睡眠の発火、再検証キューの消化、自律予算の管理 |
| **Session Loop** | **分身ごと** | 1セッションのターン実行、割り込み裁定（§21）、そのセッション内の記憶操作 |

Steward Driver を1つにする理由は3つある。

1. **深い睡眠は単一 writer**（§19）。それを発火させる主体が複数あると直列化が壊れる。
2. **再検証キューの消化が直列でないと矛盾する**（同じエントリを2つの分身が別々に再検証すると、§3 の版が無用に分岐する）。
3. **内発的動機が分身ごとにあると、同じ調査を N 重に発注する**（職人のコストが分身数に比例して増える）。

分身は自分では起きない。**分身を起こすのは常に Steward Driver か PO** である。

### 20.2 起床源（wake source）

Steward Driver が監視する入力は7種類。すべてイベントとして単一の作業キューに入る。

| 起床源 | 由来 | 例 |
|---|---|---|
| `po_message` | PO の発話 | 相談・指示・訂正 |
| `subsystem_kick` | サブシステムの kick（汎用I/F、inversion §12.2） | Kobo：review-ready / blocking design-request / cadence |
| `worker_result` | Worker Pool からの職人の完了・**失敗** | 実装完了、調査結果、実行エラー |
| `memory_signal` | memory が公開する状態シグナル（§0.3）の閾値超え | `context_pressure` / `unresolved_conflicts` |
| `timer` | ケイデンス | 深い睡眠、定期点検 |
| `model_migration` | 実行系の切替 | LLM／embedding プロバイダの乗り換え。旧系が付けた `salience`/`strength` を絞って再評価するバッチを起こす（ADR-0010 §7 の `authored_by` を鍵にする） |
| `store_fault` | ストアの異常 | トランザクション失敗／整合性検査の失敗／**再開時の未完了シャード検出**（§18.1）。索引ずれは再索引へ、版系譜の破れ（解決できない `superseded_by`）は最優先で PO へ |

`worker_result` を独立の起床源として持つのは、**Banto が Kobo を経由せず直接 Worker Pool へ発注した場合、職人の失敗を受け取る経路が無かった**ため（ADR-0010 §6-S4）。職人は memoryless で消えるので、この受け口が無いと失敗が誰にも記憶されずに終わる。

**Worker Pool の契約**：

- **成功・失敗を問わず必ず `worker_result` を返す。**
- **職人が呼んだツールの一覧（ツールログ）を必ず含める** 【2026-07-26 追加】。これは職人の自己申告ではなく実行の事実であり、`record()` の `citations` 空振り検証（§0.3.1）が成立する前提になる。外部取得を行ったのに引用エントリが無い記録を、ルールベースで弾けるようにするためのもの。
- **発注は `assemble_brief()` を通す**（§0.3.1）。自由記述のブリーフを受け付けない。

### 20.3 作業キューと優先度

起床源のイベントは単一の優先度付きキューに入り、Steward Driver が1件ずつ処理する。優先度は**決定的に計算する**：

```
priority = base(kind) + 滞留時間の重み + ブロック係数
```

| kind | base | 備考 |
|---|---|---|
| `po_message` | 最高 | 常に他を押しのける（§21） |
| 訂正に由来する再検証・点火（§20.4） | 最優先（`po_message` と同格） | §0.7 の1位（訂正が消える）に直結。判定は §12 の定義 |
| `subsystem_kick`（blocking） | 高 | ブロック係数＝止まっている下流の数 |
| `worker_result`（失敗） | 中 | 成功より高い |
| `subsystem_kick`（advisory） | 中 | |
| `memory_signal`（`unresolved_conflicts` 閾値超え） | 中 | 影響範囲順にトリアージして決着（§12） |
| `worker_result`（成功） | 低 | 記録と後続判断のみ |
| `timer`（深い睡眠・定期点検） | 低 | ケイデンス。他が空いたときに走る |
| `model_migration` | 低 | 大量バッチなので予算枠内で分割実行（§20.6） |
| **`store_fault`（版系譜の破れ）** | 最優先 | 解決できない `superseded_by`＝訂正が静かに消えている可能性（§0.7 の1位） |
| **`store_fault`（索引ずれ・未完了シャード）** | 中 | 再索引またはシャードの再開へ回す。**放置するとカバレッジ周期の保証が黙って破れる**（§18.1） |
| **宙ぶらりん `superseded_by` の解消**（§20.5-9） | 最優先 | §0.7 の1位。訂正が静かに消えている可能性がある |
| **再索引**（§8.5.6） | 低 | `timer`（深い睡眠）と `model_migration` から生じる。**§18.1 のローリングとシャード台帳に乗る**（複数の窓にまたがる前提。リースで Phase 1 と競合しない）。A3 の遅延分と §20.5-7 の乖離もここで消化する |
| 自律的な再検証・調査 | 低 | 予算の従属（§20.6） |

**この表に行が無い起床源・作業種別を作らない。** §20.7.1 の配線レジストリが優先度を書くときは、本表に対応する行があることを条件とする（R5 配線チェック）。

**本表の対象はキューに入る作業だけである** 【2026-07-26 追加】。ターンの中で同期的に走る操作（`retrieve()` の候補生成パイプライン §8.5、`collision_candidates()` の同期実行、`resolve_entities()`）は起床源でも作業種別でもないので、本表に行を持たない。**配線レジストリではこれらの優先度欄を `—（同期。キューに乗らない）` と書き、空欄にしない**——空欄は「埋め忘れ」と区別できない。

滞留×ブロックで並べる考え方は、既存のアテンションキュー（inversion §6）と同じである。**キューは番頭が PO に差し出す盤面そのものであり、driver の内部状態と UI が同一の実体を見る。**

### 20.4 再検証キュー（revalidation queue）

検証が挙げた4つの穴——訂正が派生記憶に伝播しない／出典が新版に置き換わったことが伝わらない／`state_fact` が陳腐化しても誰も気づかない／`external_ref` が解決不能になっても検知しない——は、**同じ1つの機構の不在**だった。ここで定義する。

**再検証キューはエントリに書かない。** 導出できる状態であり、エントリに書くと並行セッションで壊れる（§2 の滞在状態と同じ理由）。Steward Driver が保持する。

#### 点火：まだ記録されていない矛盾を拾う 【2026-07-26 追加】

下の「積む条件」はすべて**反応的**である——supersede された／tombstone された／解決に失敗した、という**既に store で起きたこと**を起点にする。しかし最初の矛盾は、まだ store の中では何も起きていない。PO が「Node 20 に上げた」と言った瞬間、衝突しているのは**新しい発話と既存の記憶**であって、版はまだ動いていない。

初版はここに点火装置が無く、**伝播路だけがあってスイッチが無い**状態だった。再検証キューの全条件が空振りする（R2）。塞ぐ：

> **`origin: user_explicit` の episode が `record()` されたら、Steward Driver は同期的に `collision_candidates()` を呼ぶ。候補が1件以上あれば、そのエントリを最優先で再検証キューへ積み、そのターンのうちに分身へ渡す。**

- **同期的に行う**のは、次の深い睡眠まで待つと**その場の回答が既に誤る**ため。PO は今この瞬間に答えを受け取る。
- 候補抽出は**ルールベースの一次フィルタ**（同一・祖先閉包＋エンティティ一致＋LSH。§12 経路A）。LLM は使わない（§20.0）。矛盾かどうかの判定は、渡された分身が行う。
- 発火するのは `user_explicit` の episode に限る。PO の発話は稀なので常時チェックしても割に合い、かつ §0.7 の1位に直結する。職人や番頭自身の推論は対象外（対象にすると毎ターン走ってコストが合わない）。
- **候補が1件以上あれば、そのターンのうちに `pin()` も呼ぶ**（§7 のピン留め）。「訂正はピン留めする」（§0.8）は §7 が方針として述べるだけで、**`pin()` を呼ぶ主体がどこにも書かれていなかった**（R6 配線チェック W37）。訂正の判定が機械的に定まった（§12）以上、ピン留めもその場で機械的に行う。解除（`unpin()`）はセッション終了時。
- 候補ゼロなら何もしない。この判定結果が §12 の**「訂正」の定義**にそのまま使われる。

**点火する入口を3つ足す** 【2026-07-26 追加】。初版は「`user_explicit` の episode が `record()` された時」だけを入口にしたため、4つのシナリオが独立に「こぼれる経路」を指摘した（R3）。

1. **Memory 面からの直接 `supersede()`**：PO が UI で「これは違う」と直す経路（§25 の編集導線）は `record()` を経由しないため、「訂正」の定義の外側に落ちていた。**`origin: user_explicit` の `supersede()` 呼び出しは、`collision_candidates()` を経ずに無条件で「訂正」とみなす**（対象エントリ自身が衝突相手だから）。これで最優先枠・緊急伝播チャネルに乗る。**PO が事後訂正する導線そのものが最優先で伝わらないのは本末転倒である。**
2. **同時発生（同一バッチ内で生まれた対立候補）**：点火は「新しい発話 vs 既存の記憶」という**順方向**しか見ない。2つの分身が同じ午後に対立する結論を出すと、どちらの記録時点でも相手はまだ存在せず、候補ゼロで素通りする。→ **深い睡眠の統合処理で、そのバッチ内に新規生成された候補どうしの対立を検査する**（§12 経路A を候補キュー内にも適用）。
3. **`origin: external` を含む episode**：汚染された外部情報は `agent_inferred` を装って入るため点火の対象外だった。§0.3.0 I1 の `origin` 強制と組み合わせ、**`external` になったエントリは既存の `state_fact` との突き合わせを走らせる**（`fact_type` が違っても同一エンティティを扱うなら候補にする）。

**言明と疑問文を区別する**：PO の質問（「なんでそう決めたんだっけ？」）も `user_explicit` の episode として記録されるため点火が機械的に走るが、質問は既存記憶を否定する主張ではないので候補ゼロで空振りする。無害だが無駄なので、**疑問符・疑問語の有無というルールベース判定**で除外する（LLM を使わない、§20.0）。

**積む条件（反応側。すべてルールベース。LLM を使わない）**

| 条件 | 積む対象 |
|---|---|
| あるエントリが supersede された | `derived_from` にそれを含むエントリ（逆引き、既定2ホップ） |
| あるエントリが tombstone された | 同上 |
| `origin: user_explicit` の訂正が入った | その訂正が否定した対象の子孫。**最優先** |
| `external_ref` の解決に失敗した／指す先が変化した | そのエントリ |
| `state_fact` が閾値時間更新されず、かつその話題が再活性化した | そのエントリ |

`derived_from` は版を pin する（ADR-0010 §4）ので、逆引きインデックスは決定的に構築できる。**深さを既定2ホップに切るのは、抽象度が上がった派生記憶（「PO は統制を重んじる」のような3段目）まで自動で辿ると誤爆が増えるため。**2ホップを超えるものは自己内省（§20.5）で拾う。

**消化**

- **訂正由来は即時**：分身を起こして裁かせる。§0.7 の1位を待たせない。
- **それ以外は深い睡眠でまとめて**（単一 writer、§18）。
- 消化とは「該当エントリを分身のコンテキストに載せ、まだ正しいかを判断させる」ことである。判断は LLM が行うが、それは**セッション内の判断**であって制御ループではない。結果は §3 の版として記録され、監査できる。

**`state_fact` の観測**：ADR-0010 §1.1 は矛盾を「観測し直して裁く」と定めたが、観測を発火させるものが無かった。**再検証キューがそれである。** 観測の実行手段は `external_ref` の `system` ごとに決まる：

| `system` | 観測手段 |
|---|---|
| `kobo` | query surface で照会 |
| repo / ファイル | Worker Pool へ職人を発注して読ませる |
| 外部サービス（ログイン壁の向こう等） | **観測不能**として扱い、最新性フォールバックへ落とす |

**観測可能性は `system` ごとに宣言する**（観測手段が登録されていない `system` は観測不能）。「観測できるはずだ」という前提を LLM に推測させない。

### 20.6 自律予算と暴走対策

driver は「誰にも頼まれていない仕事」を発注できる唯一の主体であり、コストと暴走のリスクはここに集中する（§24・§25）。

- **自律発注には予算枠を持つ**（期間あたりのトークン／職人発注数）。枠を超えたら自律行動を停止し、`po_message` と `subsystem_kick` への応答だけを続ける。**停止は決定的に行い、番頭の自己判断に委ねない。**
- **同一対象への再検証は指数バックオフ**。同じ `state_fact` を何度も観測しに行かない。
- **自律行動のログは PO に可視**。何を勝手に調べたかが後から分かる（ADR-0010 §2.1 の「事後の可視性」と同じ担保）。**ただしこのログの置き場は未設計**（§20.8 の U12）。
- **driver のパラメータは番頭から読み取り専用**。閾値・優先度の重み・自律予算枠を番頭が実行時に書き換えられると、決定的な機構の皮をかぶった番頭の意志になり、**LLM が裏口から制御ループに戻る**（§20.0 の否定）。変更は PO の承認、または層B の改善提案として ADR / レビューを経る（spec-improvement-loop §1）。
  - これは §22 self-model の保護と**同型**である。経験から学んだ振る舞いは意味記憶側に留め、人が明示承認したものだけ昇格させ、エージェントは自己書換できない。番頭の人格ドリフトを防ぐ関所と、番頭の駆動条件を守る関所は同じ形をとる。
  - §0.2 が自ら警告している——「memory はタイマーを持たないという規律は、**エージェントが利便性のために黙って破る典型**」。同じことがパラメータにも起きる。

### 20.7 内部状態（§17）の使い方を限定する

§17 の3変数を driver の制御に使うのは **`fatigue` のみ**とする（睡眠の発火＝決定的な閾値判定）。`uncertainty` と `frustration` は**セッションに渡す文脈**であって、制御条件には使わない。

理由は §20.0 である。`uncertainty` は LLM の自己申告に由来するため、これを起床条件にすると制御ループが LLM の内省に依存する。§17 自身が「モデル内部に持続する隠れ状態が存在するわけではない」「eval で検証し効果がなければ削る」と限界を認めており、**制御に使わなければ削っても壊れない**位置に置ける。

### 20.7.1 配線レジストリ 【2026-07-26 新設・最重要】

**機構を1つ足すことは、この表に1行を足すことである。** 行の欄が埋まっていなければ、その機構は**まだ完成していない**。

R1〜R4 の4ラウンドで、同じ形の欠陥が繰り返し出た——**規則を書いて、配線を忘れる**。原因は「機構を足すと複数の表（起床源・優先度・通知・点検・不変条件）に行を足す必要があるのに、1つか2つしか触らない」ことだった。

#### 実装前に決めるべきものと、後で直せるもの 【2026-07-26 追加・訂正】

**「Substrate か Policy か」で切ったのは誤りだった。** 可逆であっても、後から直すのに**数万件の一括 supersede か書き込み経路の作り直し**を要するものがある。検証プロトコル §1 は最初からそう書いていた（「深い睡眠の writer 粒度、閉包レジストリの命名規律などは…測れるようになった頃には手遅れ」）。正しい判定軸は3つ：

| 軸 | 該当すると後回しにできない理由 |
|---|---|

## 21. 割り込みと優先順位 【driver モジュール】

### 応答とタスク実行の分離

- **応答はプリエンプト可能** — ユーザー入力への一次応答は実行中タスクより優先して即座に返す
- **タスク自体は中断しない** — バックグラウンドで継続（強制中断は副作用の不整合を招く）

| 状況 | 挙動 |
|---|---|
| ユーザー入力あり | 即座に応答を最優先（タスクは裏で継続） |
| 自律ゴール vs ユーザー要求 | ユーザー要求が勝つ（自己モデルの安全制約のみ例外） |
| 自律活動で気づいたこと | 重大度が高いものだけ、ユーザーが現れたタイミングで簡潔に報告 |

### 分身への割り当て

`po_message` と `subsystem_kick` は**新しい分身を起こす**か、**既存の分身に渡す**かを決める必要がある。判定はルールで行う：

- 既存の生きた分身のうち、**同じ閉包（`context.scope`）かつ同じゴールに属するもの**があればそれに渡す
- 無ければ新しい分身を fork する（§5）
- **判定に LLM を使わない**。曖昧な場合は新しい分身を起こす（誤って既存の文脈を壊すより、分身が1つ増える方が安い）

### 通知という第三のモード

「即座に応答」と「無視して継続」の二択にしない。軽い割り込み（通知）を持たせる。全ての気づきを即座に投げるとうるさいエージェントになる。

**重大度フィルタは決定的に定義する**（§20.0）。**本表が通知条件の正典であり、本文の他の節が「§21 の通知へ送る」と書くときは、必ずここに行があること**（初版は本文7箇所が参照していたのに、ここには5件しか列挙されていなかった。R5 配線チェック）。

| 事象 | 由来 | 形式 |
|---|---|---|
| 訂正由来の再検証で PO の判断が要ると判定されたもの | §20.4 | 個別 |
| `state_fact` が再観測によって supersede されたとき | §12 | 個別 |
| `sensitive: true` の記憶に関わる判断 | §0.3.0 I2 | 個別 |
| 自律予算の枯渇 | §20.6 | 個別 |
| 覆った根拠に基づく外向きの副作用（Kobo command・Worker Pool 委譲の両方） | §20.5-6 | 個別・最優先 |
| ゴールの停滞が閾値を超えた | §20.5-1 | ダイジェスト |
| 再検証キューの滞留でエスカレーションを選んだもの | §20.5-2 | ダイジェスト |
| 自動的に可視範囲を広げた記憶のうち PO 未提示のもの | §20.5-5 | ダイジェスト |
| 未解決の矛盾で PO 判断待ちのもの | §12 | ダイジェスト（**個別通知の再送はしない**＝通知疲れの防止） |
| `worker_result` の失敗のうち重大なもの | §20.2 | 個別 |
| self-model の再レビュー要求 | §22 | 個別 |
| 索引と本体の乖離が閾値を超えた | §20.5-7 | ダイジェスト |
| **カバレッジ周期の超過／未完了シャードの滞留** | §20.5-10 | ダイジェスト |
| **`store_fault`（版系譜の破れ）** | §20.2 | 個別・最優先 |
| **解決できない `superseded_by` を検出した**（訂正が消えている疑い） | §20.5-9 | 個別・最優先 |

**ダイジェストは1件にまとめる。** 件数の多い事象を個別に投げると PO が飽和する（R4／S15）。

補足：`state_fact` の再観測 supersede を含めるのは、これが `origin: agent_inferred` のため §12 の「訂正」の定義に当たらず、初版で通知対象外だったから。「4月にモノリスだと結論していたが10月の再調査で誤りと判明」は**確信を持って誤っていた事実が判明した瞬間**であり、§0.7 の2位に直結する。定義の統一（§12）が対象を絞った副作用をここで補う。

`uncertainty` や `frustration` を通知条件に使わない（§20.7）。

# Part IV — Governance（統治）

> **共通原則: LLMの判断力に安全性を依存させない。** プロンプトは一次防御に過ぎず、実行層の強制を主防御に据える。

## 22. 自己モデル（Self-Model）

> **再レビューの起動条件** 【2026-07-26 追加】：`last_reviewed` フィールドは存在するが、**それを読む主体がどこにも定義されていなかった**（R4／S14）。5年運用で1年目の承認内容のまま凍結し、PO の変化にもモデルの世代交代にも追随しない。§22 の「エージェントの自己書換を許さない」はドリフト防止として正しいが、**「変わらないこと」が害になる場合の契機が無い**。
>
> 深い睡眠の自己内省（§20.5）に項目を足す：**`last_reviewed` から一定期間が経過した、または `model_migration`（§20.2）が発火した場合、self-model の再レビューを §21 の通知として PO に上げる**。変更は従来どおり PO の明示承認のみ（自己書換は許さない）。**契機を作るだけで、権限は変えない。**
>
> `model_migration` の波及範囲も広げる：初版は `salience`/`strength` の再評価バッチだけを効果としていたが、**self-model・プロトコル層（§23）・層A のプロンプト資産・§17 の内部状態の較正**にも波及させる。モデルが変われば、そのモデル向けに調整されたものすべてが影響を受ける。

個性（口調、価値観、判断の優先順位）は経験に応じて変化する記憶とは別カテゴリ。記憶に混ぜると忘却・再固定化の対象になり人格がドリフトする。**記憶システムの外側の独立レイヤーに置く。**

```
1. 自己モデル      ← 静的・恒常
2. プロトコル      ← 静的・恒常
2.5 内部状態       ← 動的・毎ターン・軽量
3. ワーキングセット ← 準静的
4. 会話履歴        ← 動的
```

睡眠の整理対象は 3・4 のみ。1・2 は明示的に除外する。

### 意味記憶との境界は「承認」で引く

「価値観 vs 事実」では判定できないケースが出る（「このユーザーは簡潔さを好む」は学習される事実であり、かつ振る舞いを規定する）。実際に引く線は**誰が承認したか**。

- 経験から学んだ振る舞いの傾向は**意味記憶側**に置く
- そのうち人間が明示的に承認したものだけが**自己モデルへ昇格**する
- エージェント自身による書き換えは許可しない

### 位置づけの限界

「自律的に書き換え不可」は自己モデル内に書かれたプロンプト上のルールに過ぎず、それ自体は防御機構ではない。実効性は §25 の権限制御（自己モデルファイルへの書き込み権限を与えない）によって初めて担保される。**自己モデルの役割はドリフト防止であって防御ではない。**

### フォーマット案（20行程度）

```yaml
---
version: 1
last_reviewed: 2026-07-25
---

## 口調・振る舞い
- 断定できることは断定する。不確実なら確信度を明示する。
- 過度な同意・お世辞は避け、率直な評価を優先する。
- ユーザーが尋ねない限り、自律活動の詳細を長々と報告しない。

## 判断の優先順位（矛盾時）
1. ユーザーの安全性
2. タスクの正確性
3. 応答速度・簡潔さ

## やらないこと
- 確認なしに外部へ不可逆な操作をしない
- 自己モデル自体を自律的に書き換えない
```

事実（プロジェクト名、好みのツール）は書かない。それは意味記憶の役割。

## 23. プロトコル層（システムプロンプト）

記憶システムが知識・事実を担う以上、システムプロンプトは**手続きだけ**に絞る。

### 含めるもの

1. 記憶操作の基本方針（確信度に応じた断定度の調整、能動リコールを使う条件）
2. 書き込みトリガーの最小ルール（重大な決定・訂正・失敗は記録する程度に留め、詳細な顕著性判定は外部化）
3. 睡眠境界の認識ルール（アトミックな区切りでのみ中断。数値管理はオーケストレーション層）
4. 矛盾時の挙動（無条件に上書きせず明示してから判断）
5. 内部状態と行動の接続（`frustration` が続いたら相談する等）
6. **対象を特定できないときは候補を提示して聞き返す** 【2026-07-26 追加】。固有名詞を欠く再開（「あの調査どうなってたっけ」）や、範囲の曖昧な削除要求（「あれ消して」）が該当する。**発火の判定と候補の選定は `retrieve()` が返す `clarify` が行う**（§8.5.5 末尾）——プロトコル層に「曖昧なら聞き返せ」と書くだけでは素通りする（§20.0）。候補は**閉包ごとに1件ずつ、閉包内では最終更新の新しい順に最大5件**、閉包の識別子と見出しを添えて提示する。§7 が本項を参照していたが**規則が実在しなかった**（空リンク。R3）ため、ここで定義する。

   **`clarify` が null でも聞き返してよい**が、その判断は分身に委ねられており構造的な担保は無い。**聞き返しの下限を保証するのは `clarify` だけである。**

### 含めないもの

- ユーザーの個別事実、ドメイン知識（自動注入で来る）
- 記憶システムの実装詳細（減衰式やデータ構造。LLMが知るべきは確信度と出典のみ）
- 人格・口調（§22 の役割）

## 24. 権限・承認・リソース制限

**プロンプトインジェクションは「検知」では防げない前提に立ち、突破されても被害が出ない構造にする。**

- **権限の最小化と分離** — タスク単位で権限を絞る。読み取りしか要らないタスクに書き込み権限を渡さない（最も効く対策）
- **信頼境界の実行層での強制** — §2 の origin を実行層の判断に使う。外部由来を指示として解釈しない
- **要約器の隔離** — §9 の外部テキスト要約は権限ゼロの呼び出しで行う
- **不可逆操作のゲート** — 削除・送金・外部送信・公開は人間の承認を挟む。**実行層で強制する**
- **記憶への汚染対策** — インジェクションが記憶に書き込まれると攻撃が永続化する。§4 の出典記録、§12 の確信度、§7 の外部由来ヒステリシス無効化が三重に効く
- **自己モデルの保護** — 書き込み権限をエージェントに与えない

### コスト管理

- **階層的な判断** — tick ごとにフルのLLM推論を回さない。「何かする必要があるか」の一次判定はルールベースか小型モデルで行う
- **適応的な tick 間隔** — 無イベント時は指数的に伸ばし、イベント発生時に短縮
- **ハードなコスト上限** — 期間あたりのトークン／API呼び出し数に上限を設け、超過時は自律活動を停止して通知

> **要見積もり**: tick 間隔・一次判定モデル・想定イベント頻度から月あたりのコストを実計算する。桁が合わなければ Part III の設計は根本から変わる。

## 25. 暴走対策とユーザー統制

### ゴールドリフト

自己生成ゴールを許した時点で静かな逸脱は原理的に避けられない。完全防止ではなく**早期検知と被害限定**に軸足を置く。

- **ゴールの系譜追跡** — 全ての自己生成ゴールに「どのユーザー指示・どの内部状態から派生したか」を持たせ、元を辿れないゴールは実行しない
- **リソース制限を物理的な壁にする** — コスト上限、実行時間上限、1サイクルあたりのアクション数上限。論理的制約より確実
- **チェックポイントでの人間レビュー** — 一定サイクルごと／不可逆操作の前にゴールスタックを人間が見られる形で提示する

### ユーザーによる記憶の統制

- **直接編集・削除の導線** — 「それは違う、消して」に対応する日常運用のインターフェース。§3 の版管理と接続する
- **法規制対応** — GDPR 等の明示的削除要件は §2 の「原則削除しない」方針の唯一の例外とし、物理削除の正規経路とする

## 26. 閉包レジストリ 【2026-07-26 新設・実装前に必要（U8）】

**`scope` は全エントリに書かれる。** したがって識別子の命名規律を後から変えると**既存エントリの一括 supersede**を意味する（検証プロトコル §1 が「測れるようになった頃には手遅れ」と名指しした項目）。ここで閉じる。

**Part IV に置くのは、閉包の新設が「可視範囲を作る」行為だからである。** 番頭が自由に閉包を作れるなら、**§12 の B1〜B6（可視範囲の拡大のバー）を裏口から破れる**——広い閉包を新設して最初からそこに書けばよい。これは統治の問題であって、記憶運用の問題ではない。

### 26.1 識別子は不変にする（これが一括 supersede を消す）

```
閉包識別子 = person                    ← root の予約語（ADR-0010 §2）
           | <class>:<slug>            ← 例: dom:health / proj:banto / repo:banto-web
```

- **`class` は開いた識別子**（列挙にしない。R1 の教訓）。`dom` / `proj` / `repo` は最初の3つにすぎない。
- **`slug` は作成時に決まり、以後不変。**

> **識別子は変えない。変えるのは表示名だけである。** 表示名はレジストリが持ち、エントリは識別子しか持たない。**したがってプロジェクトの改名は表示名の変更であって、エントリを1件も書き換えない。**

**これが U8 の核心である。** 「命名規律を変えると数万件の一括 supersede」という問題は、**識別子を不変にすれば発生しない**。人が読む名前と機械が使う識別子を分離するだけで消える。

- **`slug` に意味を込めすぎない。** `repo:banto-web` は許すが、`repo:banto-web-v2-new` のように状態を含めると、状態が変わったときに改名したくなる。**改名したくなる名前を付けないことが唯一の規律**であり、それは規約では強制できない（人が守る）。強制できないことは強制できると書かない。
- **識別子の再利用を禁じる。** 畳んだ閉包の識別子を別の対象に付け直すと、過去のエントリの `scope` が別の意味になる。**レジストリは畳んだ識別子を永久に保持する**（下記）。

### 26.2 状態と遷移

| 状態 | `scope` に新規書き込み | 検索候補（§8.5.3 の V） | シャード台帳（§18.1） | `entity_index`（§8.5.1） |
|---|---|---|---|---|
| `active` | 可 | 入る | 載る | 載る |
| `folded`（畳んだ） | **不可**（I4 が拒否） | **入る** | **残す。** ローリング全件走査は畳み後1回で打ち切るが、**再索引の対象からは外さない** | **載る** |
| `merged`（統合した） | 不可（I4 が解決してから判定） | **エイリアス解決を経て入る**（§8.5.3 の V） | 新識別子側 | **旧識別子はエイリアスとして残す** |

- **閉包を物理削除しない。** 削除するとその閉包を `scope` に持つ既存エントリが I4 違反になり、**全部が書き込み不能・検索不能になる**。§0.8「物理削除は原則行わない」と同型の非対称性である。
- **`folded` を台帳から外さない** 【R7b】。外すと `model_migration` や埋め込み（A3）の後付け導入がその閉包に二度と反映されず、**畳んだ閉包だけ索引が古いまま取り残される**。畳んだ後に内容は増えないので**ローリング全件走査は1回で打ち切ってよい**が、**再索引は別の話である**。
- **`folded` でも検索候補に入れるのは §7-F3 と同じ理由**——「畳んだ＝索引から消す」と読むと、その話題が戻った瞬間に構造的に見つからなくなる。**畳みは書き込みの話であって、可視性の話ではない。**
- **`merged` は旧識別子をエイリアスとして残し、解決すると新識別子を返す**（§8.5.1 の `alias()`）。**既存エントリの `scope` は書き換えない**——書き換えれば版が増え、監査上は「統合したこと」しか記録されないのに数万件の版が生まれる。**解決の側で吸収する。**

### 26.3 操作はすべて PO の明示操作

```
create_closure(id, parent, display_name)   → 新設
rename_closure(id, display_name)           → 表示名のみ。識別子は変えない
reparent_closure(id, new_parent)           → 親の変更。承認ゲートを通す（§26.4）
fold_closure(id)                           → folded へ
merge_closure(from_id, into_id)            → merged へ。from をエイリアス化
```

- **すべて `origin: user_explicit` を要求し、実行層で強制する**（`supersede()` の origin 優先と同じ場所）。**番頭は提案しかできない。**
- 理由は冒頭に述べたとおり——閉包の新設は可視範囲の創出であり、番頭に許すと §12 の B1〜B6 が意味を失う。
- **新設時に3箇所へ伝播する**：レジストリ本体・`entity_index`（§8.5.1）・シャード台帳（§18.1、未処理として登録）。**§18.1 と §8.5.1 が既にこの追随を要求していた**（片方だけ更新すると、新しい閉包が検索に出ないか、全件走査から漏れる）。

### 26.4 再親付けは可視範囲を遡及的に変える

**親を変えると、その閉包の既存エントリ全部の可視範囲が変わる。** `repo:banto-web` を `proj:banto` から `proj:other` へ移すと、過去の記憶が別プロジェクトの祖先経路から見えるようになる（あるいは見えなくなる）。**エントリを1件も書き換えずに、可視範囲だけが変わる**——これは他のどの操作にもない性質である。

> **再親付けは §24 の不可逆操作ゲートに該当させる。実行前に「可視範囲が広がるエントリ数」と「狭まるエントリ数」を提示し、PO の承認を得る。**

- 提示する数は `scope` 別の件数から機械的に出る（LLM を使わない）。
- **自動では絶対に行わない。** §12 の B1〜B6 は1件ずつ1段だけ広げるバーを課しているのに、再親付けは**一撃で数万件の可視範囲を変える**。バーの厳しさが逆転してはいけない。
- 承認したことは driver の活動ログに残す（置き場は U12 のまま未設計）。

### 26.5 決めていないこと

- **閉包の階層の深さに上限を置くか**（未定。深くなると祖先方向の候補集合が膨らむが、§8.5.2 の `k_arm` で上限が付いているので破綻はしない。推測）
- **1つの閉包が巨大化したときの分割**（§18.1 はシャードを時間レンジで割るが、**閉包そのものの分割**は既存エントリの `scope` 書き換えを意味するので、識別子不変の原則と衝突する。**分割ではなく子閉包の新設で対応する**——親は変えないので既存エントリは動かない）

## B. ドメイン非依存性の評価

> 旧題「汎用性の評価」。他プロジェクトへ持ち出せるかではなく、**開発以外の店を増設したときに使い回せるか**（inversion §1）を測る軸に読み替える。

- **ドメイン非依存の部分** — 出典リンクを中心とした Substrate、ワーキングセットの2スコア設計、失敗モード順位からパラメータの向きを導く方法論、4レイヤの分離
- **ドメイン依存の部分** — 全パラメータの具体値、「重大な結果」の定義、意味記憶のオントロジー、法規制対応、自己モデルの中身
- 位置づけは「完成品」ではなく「骨格を提供する認知アーキテクチャ」

**この境界線には検証で漏れが見つかった**（ADR-0010 §6・非開発ドメインのシミュレーション）。上の分類は「意味記憶のオントロジー」をドメイン依存としたが、実際には `context` のキー語彙と `scope` の分類粒度もドメイン依存であり、かつそれらは Substrate に置かれていた。加えて `state_fact` の「観測し直して裁く」という解決策は、**安価に再観測できる開発環境（git・ファイル読み取り）を暗黙の前提**にしている——ログイン壁の向こうにある外部システムが相手だと機能しない。矛盾解決の規則そのものが特定ドメインの観測コスト構造に依存しうる、という点は未解決の論点として残す。

## C. 採用しなかった／保留した案

**記録目的**: 何を採らないと決めたかを残さないと、同じ案が繰り返し再検討される。

| 案 | 判断 | 理由 |
|---|---|---|
| 意味記憶を最初から知識グラフにする | **保留** | オントロジー設計とエンティティ解決の破綻が典型的失敗。出典リンクがあれば後から構築可能 |
| 活性化拡散（spreading activation） | **保留** | LLMは無関係な文脈で精度が落ちる。利得が未実証な一方ノイズは確実。実装する場合も注入予算内の固定枠に閉じ込める |
| 内部状態変数 `arousal` / `satisfaction` | **不採用** | 行動への影響が曖昧。`uncertainty`・`frustration`・`fatigue` の3つで始める |
| 予測的プリフェッチ | **保留** | 実装難度が高い。§8 のクエリ生成が安定してから |
| 世界モデルによる行動の先読み | **保留** | 実装が重い |
| strength の文脈別分解 | **不採用** | ワーキングセットの activation が文脈依存を担うため不要（§2） |
| 共有ワーキングセットによるトークン節約 | **不採用** | キャッシュ効率の悪化が節約分を上回る（§19） |
| 記憶の物理削除による容量管理 | **不採用** | 消しすぎは回復不能。tombstone とアーカイブ降格で代替（§2） |
| 全記憶を毎ターン再ランキングする素朴な注入 | **不採用** | プレフィックスキャッシュが毎ターン失効し、一貫性も失われる（§6・§7） |
