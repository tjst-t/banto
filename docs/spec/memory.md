# Spec: Quirefold — 番頭の記憶とコンテキスト管理

**版**: 4.0（banto の仕様として統合。外部プロジェクト前提を解消）
**最終更新**: 2026-07-26

> **Quirefold**（クワイアフォールド）— *quire*（写本を綴じる折丁の単位）＋ *fold*。
> 折り重ねられた層として記録が積まれ、どの層から来たかを常に辿れる、という構造から。

**位置づけ**：Quirefold は banto の**記憶サブシステムの名前**であり、別プロジェクトではない（語彙は agent-primary-inversion §12.1：Banto / Quirefold / Kobo / Worker Pool）。本書は `docs/spec/` の一員＝**設計の真実（living document）**であり、banto を作る過程で確定していく。ここに書かれた設計は可変である。

例外は Substrate（Part I）だけで、これは**記憶の蓄積を開始した時点**で凍結する（§0.6）。リリース時ではない。Substrate の確定内容は **[ADR-0010](../adr/adr-0010-memory-substrate-schema.md)** が正典であり、本書 Part I と食い違う場合は ADR-0010 が優先する（P3：食い違いを見つけたら黙って寄せず incident を積む）。

**未確定の所在**：10シナリオの検証（ADR-0010 §6）が「規則は書かれているが**発火条件が書かれていない**」ことを明らかにした。2026-07-26 に **§20 driver を全面的に書き直し**、併せて矛盾の検出（§12）・版の解決とアーカイブの扱い（§7）・休眠トピックの復帰（§7）・`record()` のシグネチャ（§0.3）を定義した。

Substrate の反映（ADR-0010 → 本文）は §12 を除いて**未了**である。`context.scope` の値域・`sensitive`・`fact_type` の適用範囲・tombstone と版管理・`external_ref` の独立性判定・§25 と §2 の物理削除条件の不一致・存在しない「§26」への参照は、本文がまだ旧記述のまま。**食い違う場合は ADR-0010 が優先する**（P3）。

## 0. 目的・スコープ・設計原理

### 0.1 目的

セッションをまたいで劣化しないエージェントを実現する。記憶を後付けの検索機構（RAG）としてではなく、**コンテキストに何を載せるかを決める基盤**として設計する。

### 0.2 スコープとモジュール構成 【重要】

Quirefold は記憶・コンテキスト管理・自律ループを含む**単一のサブシステム**として実装する。これを積む Banto ハーネスは自作であり（決定②＝inversion §13）、コンテキスト組み立てを Quirefold に委ねる（§0.3）。

内部は3モジュールに分け、インターフェースを明確に保つ。

| モジュール | 責務 | 本書での対応 |
|---|---|---|
| **memory** | 記憶の保存・出典・版管理・コンテキスト組み立て・蒸留 | Part I、Part II、§14、§18、§19 |
| **harness** | LLM呼び出し・ツール実行・ターンの実行 | **Banto ハーネス**（自作＋プラガブル LLM 層）。§0.3・inversion §13 |
| **driver** | 起動条件・ゴール管理・睡眠発火・割り込み裁定・再検証キュー・自律予算 | §17、**§20**、§21 |

#### 唯一の規律

**memory モジュールはタイマーもループも持たない。** 問われたら答え、命じられたら整理するが、**自分でいつ動くかは決めない**。判断は常に driver 側に置く。

これは配布境界ではなく**設計上の規律**であり、目的は検証順序にある。スケジューラを持たなければ、memory を素のリクエスト/レスポンス型ループから駆動して**単独で先に評価できる**。自律ループの完成を待たないと評価できない構造にすると、Part II の全パラメータが永久に未検証のまま残る。§0.9 に未検証項目が6つある以上、ここは譲れない。

#### 分割しない理由

将来 memory を独立ライブラリとして切り出す余地は残すが、**現時点で分ける理由はない**。

- 両者の状態は意味的に強く絡み合っている（§0.3 のシグナルは汎用APIではなく、driver が必要とするから露出させた内部状態である）
- §18 の睡眠判定はコンテキスト圧力（memory 側）とタスクの区切り（driver 側）の両方を見ないと決まらない
- §20 の自己内省は、記憶整理がゴールを生成するため境界を跨ぐ
- 単体でエンドツーエンドに動かないと §16 の評価指標が測れない

**境界の正しい位置はまだ分かっていない。** 机上で引いた線をパッケージ分割で固定するのは、Substrate 以外を早期確定させないという原理3（§0.5）に反する。単一リポジトリなら境界は後から動かせる。

#### 実装コストを理由にスコープを狭めない

driver も含めて本気で作る。ゲートウェイ・実行バックエンド・TUI といった定型的な広がりは、**AIエージェントによる実装を前提にすれば安い**。「人手で書くと大変だから削る」という判断はしない。

制約になるのは実装労力ではなく**検証**である。§0.9 の項目は、コードが増えても解けない。

- 見逃し率の判定には人間の目が要る（§16）
- パラメータの調整には実時間の経過が要る（半減期4ターンの妥当性は、ターンが起きないと分からない）
- レビュー負荷は表面積に比例する。とくに「memory はタイマーを持たない」という規律は、エージェントが利便性のために黙って破る典型

したがって縮めるのは**作る量ではなく検証の順序**。§0.9 の最優先項目を先に片付け、そのあとは並行に進めてよい。

### 0.3 モジュール間インターフェース

**memory が提供する操作**

```
build_context(query_seed, budget) → 組み立て済みコンテキスト
assemble_brief(task, budget)      → 職人向けブリーフ（構造化。§0.3.1）
record(event, origin, session_id, attrs) → エピソードへ追記
                                    attrs = { external_ref?, derived_from?, sensitive?, scope }
propose(entry)                    → semantic / procedural の候補を睡眠キューへ積む
supersede(entry_id, new_entry, origin) → 版を作る（§3）。origin 優先はここで強制する
recall(query)                     → 能動的検索（明示リコール用）
pin(item) / unpin(item)           → 訂正等の保護（§7）
compact()                         → マイクロスリープ（§18）
consolidate(depth)                → 浅い／深い睡眠（§18）
dependents(entry_id, depth)       → derived_from の逆引き（driver が再検証キューを積む、§20.4）
changes_since(cursor)             → supersede / tombstone / 新規確定 の変更ストリーム
collision_candidates(entry_id)    → 既存の意味記憶との衝突候補（ルールベース、§12・§20.4）
```

`record()` の `attrs` は ADR-0010 で確定した Substrate に対応する。`scope` は必須（可視範囲は既定に頼らず常に明示する）。`derived_from` を渡せるのは、ADR-0010 §1.2 が要求する「職人の報告を引用エントリと結論エントリに**分割して記録**し、結論から引用へリンクする」を実現するため——初版の `attrs` にこれが無く、**規約が公開 API で表現できない**状態だった。

**`propose()` と `supersede()` は 2026-07-26 の追加。** 初版は `record()`（episode 追記）と `consolidate()`（睡眠バッチ）しか無く、**意味記憶の版を作る操作が公開 API に存在しなかった**。そのため ADR-0010 §1.3 が「書き込み経路の実行層で強制する」と定めた origin 優先は、強制をかける入口自体が無かった。`supersede()` がその唯一の入口である。

- `supersede()` は **`origin` 優先を実行層で強制する**：対象の最新版が `origin: user_explicit` のとき、`agent_inferred` / `external` からの呼び出しは**拒否**する（ADR-0010 §1.3）。プロンプトの記述に委ねない。
- セッションからの並行 `supersede()` は許す。§19 の層別の並行性に従い、意味記憶の競合は版管理で**検出可能な矛盾**に還元される。単一 writer を要するのは深い睡眠だけである。

`dependents()` / `changes_since()` / `collision_candidates()` は **driver が点火と再検証を組み立てるための読み取り口**である。memory はこれらを提供するが、それを見ていつ動くかは決めない（§0.2 の唯一の規律）。

### 0.3.0 書き込み経路の不変条件 【2026-07-26 追加・最重要】

**エントリを生成するすべての経路に、同じ不変条件を適用する。** 対象は `record()`（episode）・`propose()`（候補）・`supersede()`（新版）・深い睡眠の蒸留とチャンキング（§14）——**例外なく全部**。

R4 の検証は、同じ形の欠陥を6件見つけた：**規則を1つの層にだけ書き、上下の層に配線し忘れる**。`origin` の強制は `record()` にだけ書いたので蒸留層で失われ（§20.8-R4／S10）、`sensitive` の継承も同様の穴を持つ。経路ごとに規則を書く限り、経路が増えるたびに漏れる。**経路の数だけ書くのをやめ、不変条件として1箇所に置く。**

| # | 不変条件 | 破れたときの帰結 |
|---|---|---|
| I1 | **`derived_from` に `origin: external` が1件でもあれば、生成されるエントリの `origin` を無条件に `external` へ強制する** | 蒸留が trust laundering になる（§7 ヒステリシス無効化・§9 レンダリング・§12 確信度減点は**エントリ自身の `origin` しか見ない**ため、一度 `agent_inferred` になると三重防御が丸ごと迂回される） |
| I2 | **`derived_from` に `sensitive: true` が1件でもあれば継承する。**落とせるのは `origin: user_explicit` の判断のみ | 理由を tombstone しても、機微フラグの無い結論だけが生き残る |
| I3 | **`authored_by` に現在の実行系の識別子を必ず入れる**（ADR-0010 §7） | 世代をまたいだ較正の断絶が検出不能になる |
| I4 | **`scope` は必須。閉包レジストリに実在しない識別子を拒否する** | 可視範囲が既定に落ちる |
| I5 | **`content` の書き分けを検証する**：`headline` は結論のみ、理由は `summary` 以降 | `assemble_brief()` の headline-only 絞り込みが無効化される |
| I6 | 違反は失敗として扱い、握りつぶさない（I2 原則） | — |

**この表が唯一の正典である。** 個別の操作の説明（§0.3.1 以下）でこれらを再掲するときは、必ず本表への参照とすること。**新しい書き込み経路を足すときは、本表を通ることを設計の条件とする。**

### 0.3.1 規律を実行層に落とす 【2026-07-26 追加】

再検証（§20.8-2）で、**散文で書いた規律はすべて素通りした**ことが分かった。`sensitive` の取り扱い、`citations` の検証、`derived_from` の記入義務——どれも「そうする」と書いてあるだけで、そうさせる場所が無かった。以下でそれぞれの落ちる先を決める。

#### `assemble_brief()` — 職人への発注を構造化する

**職人への指示文が自由記述である限り、そこにゲートは置けない。** `build_context()` は番頭自身のセッション用であり、職人向けブリーフはこのパイプラインを通っていなかった。番頭（LLM）がその場で作文するので、機微情報を除く規律も、根拠リンクを残す規律も、守られたかどうかすら分からない。

構造化した組み立て操作を置く。職人への発注は**必ずこれを通す**。

```
assemble_brief(task, budget) → {
    brief,              # 職人に渡すテキスト
    included_refs[]     # 同梱した記憶ID（監査と derived_from の材料）
}
```

- **`sensitive: true` のエントリは `content.headline`（確定した制約の結論）だけを載せ、`summary` / `full`（理由）は載せない。** 機械的に落とす。ADR-0010 §5 の「職人への指示文に理由を含めない」は、ここで実行層の規則になる。
- 職人は Quirefold を装着しないため（inversion §11.1）、**ブリーフに載らなかったものは職人に一切届かない**。何を載せたかが `included_refs` で残るので、事後に監査できる。
- **`task` 引数も検査対象にする** 【2026-07-26 追加】。初版は記憶の注入経路（`included_refs`）だけを構造化し、**呼び出し側が作文する `task` 文字列を自由記述のまま残していた**。番頭が `task` に理由を直接書けば解像度の絞り込みは無意味になる——「自由記述にはゲートを置けない」という診断を、一段上の入力で再現していた（§20.8-D）。対処：**直近ターンで `sensitive` エントリがワーキングセットに滞在していた場合、`task` の生成を権限を縮小した別呼び出しに切り出す**（§9 の要約器隔離と同型）。
- **`content` の書き分けを強制する**：`headline` は結論のみ、理由は `summary` 以降に置く。`headline` に理由まで書けば headline-only の絞り込みが無効になるため、この規約は `record()` の書き込み時に検査する。

#### `record()` の書き込み前バリデーション（ルールベース）

**§0.3.0 の不変条件（I1〜I6）を通す。** それに加えて `record()` 固有のものが1つある。判定はすべて機械的な事実に基づき、LLM を使わない（§20.0）。

1. **`citations` 空振りの検出**：由来が `worker_result` であり、その職人の**ツールログに外部取得（Web・外部API）が含まれる**のに、`derived_from` に `origin: external` の引用エントリが1件も無い場合は拒否する。ADR-0010 §1.2 が「ルールベースで弾ける」と述べながら**弾く場所を指定していなかった**ものを、ここに置く。
2. **`scope` の実在**：閉包レジストリに存在しない識別子を拒否する。
2. 以降は §0.3.0 の I1〜I6 に従う（`origin` の強制、`sensitive` の継承、`authored_by`、`scope` の実在、`content` の書き分け、失敗として扱うこと）。**ここに再掲しない**——再掲すると経路ごとに書く形に戻り、次の経路で漏れる。

これが成立する前提として、**Worker Pool は `worker_result` に職人が呼んだツールの一覧を必ず含める**（§20.2 の契約に追加）。ツールログは機械的な事実であり、職人の自己申告ではない。

#### `derived_from` の自動付記

**番頭の律義さに頼らない。** そのターンで `build_context()` / `assemble_brief()` が実際に載せた記憶IDを、ハーネスが `record()` の `derived_from` 候補として機械的に渡す。

- **注入された ≠ 実際に使った**ので、これは過剰にリンクを張る。承知の上で**過剰側に倒す**——§0.8 の重み付け（見逃しコスト ＞ ノイズコスト）に従う。出典が多すぎるのは確信度の計算で調整できるが、出典が無いエントリは後から復元できない。
- これは §0.9 の最優先課題「参照検出の信頼性」の**書き込み側の答え**でもある。何が使われたかは分からないが、**何が載っていたかは機械的に分かる**。

**memory が公開する状態シグナル（読み取り専用）**

```
context_pressure       コンテキスト圧力 → driver の fatigue の入力
mean_confidence        注入中の記憶の確信度平均 → uncertainty の入力
unresolved_conflicts   未解決の矛盾件数
```

**driver が提供するもの**

```
goal_stack        現在のゴール（§11 の目標関連性、§7 のピン留めに使用）
exec_context      リポジトリ・作業モード等（§11 の文脈一致度に使用）
turn_boundary     ターンの区切り通知
```

**memory はシグナルを公開するが、それに基づいて自ら行動しない。** 睡眠の閾値判定（§18）は driver 側に置く。

#### ハーネスとの関係

memory は「記憶ストア」ではなく**プロンプトを組み立てる側**である。ワーキングセット・予算配分・プレフィックスの並び順まで管轄するため、**既存ハーネスに後付けできる部品にはならない**。ハーネス側がコンテキスト組み立てを丸ごと委譲する必要がある。

これが決定②（inversion §13）で **Banto ハーネスを自作**と決めた理由そのものである。既製ハーネス（pi 等）のループ・履歴管理と二重化して衝突するため、Quirefold を積むハーネスは自作し、LLM プロバイダはアダプタで差し替える。

**Banto 側の要件と本書の対応**

| Banto の要件 | 対応 |
|---|---|
| 「いまどう？」で文脈を読んで現状を返す | §8（ワーキングセットが現在の話題の最良の要約でもある） |
| 実装エージェント→設計エージェントへの引き継ぎ | §19（並行セッション・スナップショット隔離） |
| オーケストレータが実行者をスポーンし並行開発 | §19 |
| ADR の作成と参照 | §4（出典リンク付きの意思決定＝意味記憶の実体） |
| Skill の自己改善ループ | §14（チャンキングによる手続き記憶への昇格） |

**ADR が意味記憶の中心になる。** コーディング文脈における意味記憶は「世界の事実」ではなく**決定と制約**であり、ADR は「なぜそう決めたか」を出典付きで残す形式そのものである。§12 の `fact_type` は `preference_decision` が支配的になる。

#### 規律: Substrate に開発固有の語彙を入れない

かつて本書は「banto はホストであって共同設計者ではない／banto の都合で Substrate を曲げない」という規律を置いていた。Quirefold を banto の一部と位置づけた以上、この文言（外部プロジェクトへの一方向依存）は失効する。**ただし規律そのものは残す。理由が変わるだけである。**

新しい理由は inversion §1 にある——**番頭の核（記憶・会話・差配）を開発固有の道具（タスクモデル・コードレビュー・Environments）から分離して設計すれば、将来 別領域も同じ番頭に載る**。開発は「第一の店」にすぎない。したがって：

- **Substrate（Part I）に開発固有の語彙・前提を入れない。** 入れた時点で、番頭はコーディング専用になり、拡張性が構造から失われる。
- **Policy 層（Part II）はコーディング向けに調整してよい。** 可逆であるため。
- 判定は「外部プロジェクトの都合を守れているか」ではなく「**開発以外の店を増設したときに、この決定が邪魔をしないか**」で行う。

**この規律は実際に破られていた。** 10シナリオ検証（ADR-0010 §6）で、非開発ドメイン（家計）のシミュレーションが Substrate 内の開発語彙を検出した——`context.project` は Kobo のプロジェクト概念に暗黙に紐づき、`context.repo` は非開発ドメインで恒久的に無意味、`scope` の2値（person / project）は「プロジェクトではない継続的な生活領域」を表現できない。ADR-0010 第2版でこれを是正し、`scope` を閉包識別子に、`context` の他キーを任意の検索用特徴量に降格した。

### 0.4 命名規約

- **サブシステム名のみ造語**（Quirefold）。banto の語彙体系 Banto / Quirefold / Kobo / Worker Pool の一員（inversion §12.1）
- **内部モジュール・関数・型名はすべて標準的な英語**を使う。凝った命名をしない
  - `working_set`, `episode_store`, `provenance`, `distiller`, `budget_allocator`
- CLI の動詞は業界標準（`recall` / `distill` / `compact`）

### 0.5 設計原理

1. **脳のアナロジーは仮説の源であって解の源ではない。** 脳の機構の多くは容量・代謝コスト・身体の単一性といった制約への解であり、その制約が存在しない箇所では意図的にアナロジーを捨てる（§3 の不変性、§20 の並行性）。
2. **安全性をLLMの判断力に依存させない。** プロンプト上のルールは一次防御に過ぎず、権限制御・リソース上限・承認ゲートといった実行層の強制を主防御に据える。
3. **可逆性で設計判断を階層化する。** 後から変えられない決定（Substrate）を先に確定させ、変えられる決定はパラメータとして外出しする。
4. **失敗モードの順位（§0.7）が全パラメータの向きを決める。** 値は実験で決めるが、向きは机上で決める。

### 0.6 4レイヤ構成

| レイヤ | 内容 | 可逆性 |
|---|---|---|
| **I. Substrate** | スキーマ、不変性、版管理、出典、時間 | **不可逆** |
| **II. Policy** | コンテキスト管理、注入、確信度、蒸留 | 可逆 |
| **III. Loop** | 内部状態、睡眠、並行性、自律ループ | 可逆 |
| **IV. Governance** | 自己モデル、プロトコル、権限、リソース制限 | 一部不可逆 |

**Substrate だけは後から変更できない。** スキーマに欠けた項目を後から追加しても過去の記憶に遡及できず、「出所不明の古い記憶」が永久に残る。

### 0.7 失敗モードの順位 【確定】

**本設計における最重要の前提。** パラメータの具体値は実験で決めるが、どちらに倒すかはこの順位で決まる。

| 順位 | 失敗 | なぜこの位置か |
|---|---|---|
| 1 | **ユーザーの訂正が消える** | 信頼の損なわれ方が最も深く、ユーザー側から回復手段がない。「さっき言ったのに」は他のどの失敗より重い |
| 2 | **確信を持って誤ったことを述べる** | 検出されにくいぶん被害が持続し、下流の判断を汚染する |
| 3 | **汚染が記憶に永続化する** | 頻度は低いが、後続セッションで再発火し被害が累積する |
| 4 | **必要な記憶を見逃す** | ユーザーが言い直せば回復する |
| 5 | **無関係な記憶が混ざる** | 精度は落ちるが回復可能 |

### 0.8 順位から自動的に決まる設計方針

| 方針 | 由来 |
|---|---|
| 訂正はピン留めし、確率的な機構に一切委ねない | 1位 |
| 確信度は保守的に見積もる（迷ったら下げる） | 2位 |
| 外部由来の情報は滞在・確信度・権限のすべてで厳しく扱う | 3位 |
| 見逃しコストをノイズコストより高く重み付けする | 4位 > 5位 |
| 物理削除は原則行わない（消しすぎは回復不能） | 1位・4位 |

### 0.9 机上検討の終了条件

以下は実装と eval を経ないと判断できない。ここに到達したら机上フェーズを終える。

- 蒸留の品質、特にスキーマ補完による虚偽記憶の発生率
- **参照検出の信頼性【最優先】** — これが取れないと §7 の正のフィードバックと §16 のノイズ計測が両方機能しない。2方式を比較する。
  - 自己申告方式: LLM に使用した記憶IDを申告させる。信頼性に懸念あり
  - **行動観測方式**: コーディング文脈では振る舞いから直接観測できる。すでにコンテキストにあるファイルの再読み込み（＝見逃し）、確立済みの規約に反する実装（＝訂正の消失）、同一調査の反復（＝想起されていない）。自己申告に依存しないため、こちらを本命とする
- 内部状態（§18）が実際に行動を変えるか
- 全パラメータの具体値

# Part I — Substrate（記憶基盤）【不可逆】

## 1. 記憶の階層と役割

| 記憶の種類 | データ構造 | 対応 |
|---|---|---|
| 作業記憶 | ワーキングセット（§7） | ワーキングメモリ |
| エピソード記憶 | タイムスタンプ付きドキュメントストア＋ベクトル検索 | 海馬 |
| 意味記憶 | 出典リンク付き事実ステートメント集合 | 大脳皮質 |
| 手続き記憶 | 実行可能スキル | 体で覚えたやり方 |

単一のデータ構造で全部を賄おうとするのが既存実装の失敗パターン。保存技術としては分離するが、**論理的には出典リンクで結ばれた1つのネットワークとして扱う**。

**意味記憶は当面グラフ化しない。** オントロジー設計とエンティティ解決の破綻が典型的失敗であり、出典リンクさえ保持していればグラフは後から構築できる（→ 付録C）。

## 2. 記憶エントリのスキーマ 【確定】

### 共通コア

```
id                  安定・不変
kind                episode | semantic | procedural
fact_type           preference_decision | world_fact   ← §12 の矛盾解決規則で使用
content             { headline, summary, full }        ← §9 の解像度階層
created_at          記録時刻（減衰計算の基準）
valid_from          事実が真になった時点
valid_until         事実が真でなくなった時点（null = 現在も有効）
origin              user_explicit | agent_inferred | external
session_id          記録元セッション（並行識別＋出典独立性判定を兼ねる）
context             { tool, project, repo, mode }      ← §11 の文脈一致度で使用
derived_from[]      出典エントリID（§4）
version             版番号
superseded_by       後継版のID（null = 最新版）
tombstone           削除マーカー
strength            想起強度（単一スカラー、§13）
salience            顕著性（§11）
```

### 確定した4つの論点

**1. strength は単一スカラーでよい。**
当初「文脈ごとに分解すべきか」を未決としていたが、**コンテキスト管理を主題に据えたことで解決した**。文脈依存の重み付けはワーキングセットの activation（§7）がターン単位で担う。保存層の strength は「そもそも役に立ったことがあるか」という弱い事前分布だけを表現すればよく、分解は不要。

**2. confidence はフィールドとして持たず、出典から都度算出する（結果はキャッシュ）。**
永続化すると出典が増減したときに陳腐化し、「古い confidence が残る」という §0.7 の2位の失敗を招く。出典リンクが唯一の真実の源であるべき。

**3. エピソードと意味記憶はスキーマを共通化する。**
共通コア＋ kind ごとの拡張フィールド。層をまたぐ出典リンクと活性化を扱う以上、別スキーマにすると参照が煩雑になる。

**4. 削除は tombstone とアーカイブ層への降格で表現する。**
物理削除はユーザーの明示的要求と法規制対応のみ（§26）。消しすぎは回復不能という非対称性による（§0.8）。

### スキーマに含めないもの

**ワーキングセットの滞在状態（activation、入場ターン、最終参照ターン、不応期）はエントリに書かない。** セッション側の別テーブルに持つ。同一の記憶が複数セッションで独立した滞在状態を持つ必要があり、エントリに書くと並行セッションで壊れる（§20）。

## 3. 不変性・版管理・再固定化

### エントリは immutable

想起は記憶の強化ではなく書き換えの機会として扱う（再固定化 / Reconsolidation）。ただし**上書きはしない**。上書きは出典との対応を壊し、監査可能性を失わせる。

```
再固定化 = 新しい版を作成し、旧版に superseded_by を張る
  - 想起は最新版を返す
  - 監査時は版の系譜を遡れる
  - 旧版は減衰しアーカイブへ降格する
```

人間の記憶が上書き型なのは容量制約によるものであり、ここでアナロジーを捨てる（§0.2 原理1）。

### 副産物: 並行更新への耐性

2つのセッションが同じ事実を別々に更新した場合、上書き型なら片方が黙って消える（lost update）。版管理なら両方が生きた版として並存し、**壊れた状態ではなく検出可能な矛盾**になる。ロックを使わずに、既存の矛盾処理へ還元できる（§20）。

## 4. 出典と信頼境界

**本設計の中心構造。** 監査可能性・確信度・矛盾追跡・インジェクション対策のすべてがここから導出される。

```
[意味記憶] "Aさんは〇〇プロジェクトのオーナー"
   ├─ derived_from → [エピソード#123]
   ├─ derived_from → [エピソード#456]
   └─ derived_from → [エピソード#789]
```

### 出典の独立性

確信度を出典の数から算出する場合、**3件が3件とも同じ誤読の産物でありうる**。単純な件数は相関した誤りに無力なため、以下を区別する。

- 異なるセッション由来か（session_id）
- ユーザーの明示的発言か、エージェントの推論か（origin）
- 外部由来か内部生成か（origin）

### 宙ぶらりんノードの防止

統合・削除処理は、出典リンクが切れた意味記憶を生まないよう連動させる。出典が全て消えた事実は確信度を下げるか再検証フラグを立てる。

## 5. 時間の扱い

2種類の時間軸を分離する。

- **記録時刻**（created_at）— 減衰計算の基準
- **有効期間**（valid_from / valid_until）— その事実がいつ真だったか

混同すると「古い記録だが今も真」と「新しい記録だが既に古い」を区別できない。有効期間は §3 の版管理と自然に接続する。

# Part II — Policy（記憶運用ポリシー）【可逆】

> 具体値は全て外出しし、§17 の評価指標に基づいて調整する。向きは §0.7 で確定済み。

## 6. コンテキスト予算とレイヤ配置

### 「有限で貴重」の実体は3つ

| 予算 | 内容 | 逼迫度 |
|---|---|---|
| トークン | 金とレイテンシ | 最も緩い |
| **注意** | 無関係な情報の混入で精度が落ちる。窓が広くても半端に関連する情報を大量に入れれば答えは悪化する | **「貴重」の実体はほぼこれ** |
| **プレフィックスキャッシュ** | 注入内容が変わると失効し、コストとレイテンシが桁で変わる | 見落とされやすいが実務では最大 |

3つ目から重大な帰結が出る。**「毎ターン最適な記憶を選び直す」という素朴な設計は性能面で成立しない。**

### 配置原則

```
[静的]   自己モデル + プロトコル      ← 常にキャッシュヒット
[準静的] ワーキングセット（§7）        ← 変わりにくい。並びは滞在見込み順
[動的]   今ターン固有の追加            ← 末尾に追記
[動的]   会話履歴（§10）              ← 末尾に追記
```

動的なものは必ず末尾に集める。追い出しも末尾側から優先すると失効範囲が最小になる。**注意予算の観点でも末尾は読まれやすい**ため、両制約は競合せず同じ結論を指す。

## 7. ワーキングセット 【中核】

毎ターン検索し直すのをやめ、**タスク/セッションで「今アクティブな記憶」の小集合**を維持する。ターンごとの変化は少数の出入りに限る。

得られるもの:

- プレフィックスが安定する
- **一貫性**。ランキングの揺れで「2ターン前は知っていたことを今ターン忘れる」現象が消える
- 人間の作業記憶（一定時間活性が持続する）との整合

### スコアを2本に分ける

1本にすると滞在中の記憶も毎ターン再評価され、閾値付近が点滅する。

**入場スコア** — 今ターンのクエリに対して計算

```
s_admit = w1·関連度 + w2·文脈一致 + w3·確信度 + w4·顕著性
```

**滞在スコア** — 入場時に初期化し、以降はクエリと無関係に更新

```
入場時:       a ← s_admit
毎ターン:     a ← a × γ            (γ ≈ 0.85/ターン ≒ 半減期4ターン)
参照された:   a ← min(1, a + β)
再ヒット:     a ← max(a, s_admit_now)
```

**滞在スコアがクエリ関連度から切り離されている**ことが要点。一度入った記憶は今ターンの話題と直接関係なくてもしばらく居座る。

### ヒステリシス

```
θ_admit  = 0.6     入場に必要
θ_evict  = 0.2     下回ると退場候補
最小滞在 = 3ターン（無条件ガード）
```

閾値差だけでは γ の値で挙動が変わるため、最小滞在ターン数を併用する。

### 候補集合の前段：版の解決とアーカイブの扱い 【2026-07-26 追加】

スコアリングの**前**に、決定的なフィルタを通す。§3 は「想起は最新版を返す」と意図を述べていたが、候補生成の手順として書かれていなかったため、旧版が候補に混入しうる状態だった（ADR-0010 §6-S2/S5/S9）。§0.7 の1位（訂正が消える）に直結するので、確率的な機構より前に置く。

1. **`superseded_by != null` のエントリは候補から除外し、常に最新版に解決する。** 索引が版ごとに行を持つ実装でも、この解決を通してからスコアリングする。
2. **`tombstone: true` のエントリは `build_context` / `recall` の対象から除外する。** 到達できるのは監査目的の明示的な版履歴参照のみ。
3. **アーカイブ層は検索対象から除外しない。** ただし注入解像度を見出しのみに制限する（§9）。「アーカイブ＝索引から消す」と読むと、休眠していた話題が復帰した瞬間に**構造的に見つからなくなる**（ADR-0010 §6-S8）。降格は解像度の話であって、可視性の話ではない。
4. **`sensitive: true` は、PO との直接対話（`po_message` 由来のセッション）で、かつ PO がその主体・エンティティに言及したターンでのみ候補に入れる** 【2026-07-26 追加】。それ以外——自律ループ、`subsystem_kick` 由来のセッション——では候補から除外する。
   - **`assemble_brief()` は除外の対象外**とし、§0.3.1 の解像度規則（`headline` だけ載せ理由を落とす）に委ねる。初版は本項の除外リストに `assemble_brief()` を含めており、§0.3.1 と正面から矛盾していた（§20.8-D）。**職人には結論（制約）を伝える必要がある**ので、除外ではなく解像度で絞るのが正しい。
   - **滞在（residency）もゲートする**：`sensitive` エントリには最小滞在ターンを適用せず、話題転換（§8）を検出したら即座にバッチ退場させる。ルール4は入場だけを制御していたため、正当に入場した機微記憶が話題が変わった後も数ターン居座り、無関係な会話に紛れ込みえた。
   - ADR-0010 §5 は「番頭から自発的に持ち出さない」「自動での可視範囲拡大の対象外」と定めたが、**`s_admit` の4項（関連度・文脈一致・確信度・顕著性）に抑制項が無く、禁じたい挙動を止める機構が存在しなかった**（§20.8-2）。スコアを下げるのではなく前段で切る——確率的な機構に委ねない（§0.8）。
   - 「PO が言及したターンのみ」を条件に含めるのが「自発的に持ち出さない」の実装である。話題に上っていない人物の機微な記憶は、関連度がいくら高くても入らない。

### 休眠トピックの復帰 【2026-07-26 追加】

§13 は「減衰を弱い事前分布へ降格したので、半年触っていない記憶が埋没する問題は解決した」としていたが、**埋没の経路は `strength` だけではない**（ADR-0010 §6-S8）。`s_admit` の4項のうち、

- **文脈一致度**（§11-4）— 記録時の文脈と現在の実行文脈が違えば下がる
- **確信度**（§12）— 「最終更新からの経過時間」を入力に取るため、内容が正しくても下がる
- **顕著性の目標関連性成分**（§11-3）— 現在のゴールに紐づかないため下がる

の3つが `strength` とは独立に、**すべて同じ方向（休眠トピックに不利）へバイアスする**。関連度だけが高くても入場閾値を越えられない。

対策：**強いエンティティ一致（固有名詞・識別子の直接一致）がある場合、文脈一致度・目標関連性・および確信度の経過時間ペナルティの減点を免除する。**

初版は前2つだけを免除し、**確信度の経過時間ペナルティ（§12）を免除対象に含めていなかった**。3経路のうち1つが残るため、固有名詞が一致しても8ヶ月経った記憶は入場閾値を越えられない可能性があった。ただし**免除するのは入場判定だけ**であり、§9 のレンダリングでは「未確認」寄りの量子化を保つ——**入場させる目的と、古いかもしれないと気づかせる目的を両立させる**。 「半年触っていないプロジェクトの記憶は、その話題が始まった瞬間に最優先で入れるべき」（§13）という要求は、減衰の降格ではなくここで満たす。

**関連する未定義（実装前に解く）**：曖昧な再開発話（「あの調査どうなってたっけ」）には固有名詞が無く、どの閉包の話かを特定できない。かつ文脈一致度の分母である実行文脈自体が「どの話題か」に依存するため、**素朴に組むと循環する**（ADR-0010 §6-S8）。クエリ生成（§8）の前段に、閉包レジストリへの直接ルックアップ（LLM スコアリングを介さない）を置いて解く。特定できない場合は候補を提示して聞き返す（§23 プロトコルに規定）。

### 追い出しは予算駆動かつバッチ

**退場候補になったら追い出す、は誤り。** 載っている項目の維持はキャッシュヒットでほぼ無料だが、取り除くとその位置以降のプレフィックスが全て失効する。**退場は高い。**

発火条件は2つ。

1. **予算超過** — まとめて大きく空ける（例: 予算の70%まで一気に落とす）
2. **話題転換の検出**（§8）— キャッシュを捨ててでも大きく入れ替えるべきタイミング

それ以外では徹底的に安定させる。GCの世代別回収と同じ発想であり、§19 のマイクロスリープと同一の機構になる。

### ピン留め（スコアリング非参加）

絶対に落とさない枠。予算計算から先に差し引く。

- 現在のゴールスタック
- 今タスクの制約条件
- **このセッション中のユーザーの訂正** ← §0.7 の1位への直接的な対策。**「訂正」の判定は §12 で機械的に定める**（`user_explicit` の言明のうち、既存の意味記憶と衝突候補が出たもの）

訂正が退場すればエージェントは元の方針に戻る。**確率的な機構に委ねてはいけない。**

### 失敗モードと対策（必ずセットで実装する）

| 失敗 | 内容 | 対策 |
|---|---|---|
| 点滅 | 閾値付近が毎ターン出入りしキャッシュが失効 | ヒステリシス＋最小滞在 |
| **居座り** | 無関係な記憶が低い退場閾値で延々残る | **滞在上限**: M ターン未参照なら θ_admit で入場し直させる |
| 惜しい記憶の再来 | 閾値ぎりぎりの候補が入退場を繰り返す | **不応期**: 退場後 K ターンは再入場禁止 |
| 訂正の消失 | 方針が巻き戻る | ピン留め |

**居座りはヒステリシスを入れた時点で必ず発生する。** 点滅対策と居座り対策は同じパラメータの逆方向であり、片方だけ入れると必ずもう片方が悪化する。

### 外部由来はヒステリシスを適用しない 【重要】

通常のRAGなら悪い検索結果は次ターンで消えるが、**ワーキングセットは意図的に居座らせるため、汚染された内容も同じように保護される**。さらに参照されると activation が上がるため、攻撃テキストが出力に影響するほど滞在が延びる正のフィードバックがある。

信頼境界を滞在ポリシーにも効かせる。

| | 内部由来 | 外部由来 |
|---|---|---|
| 最小滞在ターン | あり | **なし** |
| 退場閾値 | 低い | **高い** |
| 参照による加点 | あり | **なし** |

これで §25 の「突破されても被害が出ない構造」がコンテキスト管理層まで降りる。

### 状態遷移

```
                入場スコア ≥ θ_admit
   [候補] ─────────────────────────→ [滞在]
     ↑                                  │
     │ 不応期 K ターン経過                │ a < θ_evict かつ最小滞在済み
     │                                  ↓
   [不応] ←──────────────────── [退場候補] ──参照──→ [滞在に復帰]
           予算超過 or 話題転換時にまとめて退場
```

## 8. クエリ生成と話題転換

生の発話はクエリとして弱い。「それどうなった？」「さっきの続き」は検索可能な内容語をほぼ持たない。

### 材料

1. 直近の発話
2. アクティブなゴール
3. **現在のワーキングセットの内容**
4. 実行文脈（リポジトリ、開いているファイル）

3が非自明。**今ワーキングセットに載っている記憶は、今の話題の最良の要約でもある。** 検索の実体は「クエリ→記憶」ではなく「**ワーキングセット＋発話→追加記憶**」になる。

### トピック固着への対策

上記は自己強化ループを作る。ワーキングセットがクエリを作り、そのクエリが似た記憶を呼び、ワーキングセットが強化される。**話題が変わっても集合が自分を再生産し続ける。**

これは §7 の居座りと同じ現象だが、**個別エントリの滞在上限では止まらない**。集合として自己を維持しているため、1件ずつ追い出しても補充される。

- クエリの一定割合を必ず生発話の内容語から取る（外部からの新規性注入）
- **話題転換の検出**: 発話とワーキングセットの類似度が急落したら転換とみなし、§7 のバッチ退場を発火させる

## 9. 解像度と注入レンダリング

### 解像度階層

各エントリは3段階の表現を持つ（§2 の content）。

| 解像度 | コスト | 用途 |
|---|---|---|
| 見出し | 〜10トークン | 「そういう記憶が存在する」ことだけ伝える |
| 要約 | 〜50 | 判断に使える程度 |
| 全文 | 〜500 | 詳細が必要なとき |

配分問題が「どの記憶を入れるか」から「**どの記憶をどの解像度で入れるか**」に変わる。

**副産物: 受動注入と能動リコールの対立が解消する。** 見出しは安いので広く撒ける → LLMは何が存在するかを知れるので思い出し忘れが起きない → 必要なものだけツールで展開する。2つの機構が対立ではなく階層になる。

### メタ情報の言語化

`confidence: 0.73` をコンテキストに入れてもモデルは使えない。**保存形式と提示形式は別に設計する。**

- 確信度は3段階に量子化して自然言語で出す（「確実」「おそらく」「未確認」）。連続値のままでは挙動が安定しない
- 出典も言語化する（「ユーザーが5月に明言」「Webから取得・未検証」）

### 信頼境界はレンダリングの問題

「外部由来を構造的にデータとして区別する」と言っても、**プロンプト内では見た目でしか区別できない**。区切りと明示ラベルに加えて、**外部由来テキストは生のまま入れず要約して入れる**（生テキストほど指示に見える）。

**要約はインジェクション緩和として働く。** 要約の過程で命令文が「〜という指示が書かれていた」という記述に変換されるため。完全ではないが生テキスト混入よりはるかにまし。§15 の圧縮とセキュリティが同一機構になる。

**ただし要約器自体が攻撃対象になるため、要約は権限ゼロの隔離された呼び出しで行う。**

## 10. 会話履歴とツール結果の圧縮

**コンテキストの最大の消費者は記憶ではなく会話履歴、特にツール実行結果である。** ファイル1つ、検索1回で数万トークン。記憶の注入量をいくら精緻に最適化しても、ツール結果1回で吹き飛ぶ。**圧縮の主対象はこちら。**

扱いを非対称にする。

| 対象 | 方針 | 根拠 |
|---|---|---|
| **ユーザー発言** | 原則そのまま保持 | 要約による損失の被害が最大（§0.7 の1位） |
| エージェントの発言 | 中程度に圧縮可 | |
| **ツール結果** | 直近N件のみ生で保持、以前は要約に置換。原本はエピソード記憶に退避しIDで参照可能にする | 量が支配的 |

**「エージェントの過去の思考は捨ててよいが、ユーザーが言ったことは捨てない」を明示的な原則とする。**

## 11. 顕著性

想起頻度だけでは「重要だが低頻度」の記憶（緊急対応手順等）が埋没する。

```
salience = f(頻度, 情動的顕著性, 目標関連性, 文脈一致度)
```

1. **頻度成分** — recall_count ベースの緩やかな蓄積
2. **情動的顕著性** — 予測誤差の大きさ、結果の重大さ。一度のイベントで急激に加算されうる。高顕著性の記憶は減衰のフロア値を上げて保護する
3. **目標関連性** — 現在のゴールとの関連。想起のたびに再計算する動的な値
4. **文脈一致度** — 実行文脈（context フィールド）の一致。3とは独立した軸

> これは「AIに感情を持たせる」ことではなく、感情が記憶システムに果たしている機能的役割（重要な出来事へのリソース優先配分）だけを特徴量として再現するもの。

## 12. 確信度（メタ記憶）と矛盾解決

### 算出の入力

- 出典の**数と独立性**（§4）
- 出典間の一貫性
- 最終更新からの経過時間
- origin（外部由来は低く扱う）

**迷ったら下げる。** §0.7 の2位（確信を持って誤る）を3位以下より重く見るため。

### 矛盾の検出 【2026-07-26 追加】

解決規則より先に**検出**が要る。旧版は解決規則だけを定めており、「何と何を比較して矛盾と判定するか」がどこにも書かれていなかった（ADR-0010 §6-S1/S2/S3 が独立に指摘）。検出が動かなければ、どれだけ精緻な解決規則も一度も呼ばれない。

**検出は2経路ある。片方だけでは足りない。**

**経路A：語彙・近傍による候補抽出**（同レベルの矛盾を拾う）

1. 安価な一次フィルタで候補ペアを絞る——同一の閉包（`context.scope`）またはその祖先、見出しのエンティティ一致、LSH／クラスタリング（§15）。embedding があればベクトル近傍を加える。**embedding 無しでも動く形にする**（ADR-0010 §5：初期は embedding 無しで開始しうる）。
2. 絞った候補ペアだけを LLM に判定させる。バッチ内・セッション内の判断であって制御ループではない（§20.0）。

**`fact_type` の一致を候補条件にしない** 【2026-07-26 改訂】。初版は「同一 `fact_type`」で絞っていたが、これだと**新規に記録された episode（`fact_type: null`）は既存の semantic と永久にペアにならない**。PO が「Node 20 に上げた」と言っても、既存の `state_fact`「このリポジトリは Node 18」と突き合わされない。矛盾の入口がここで塞がっていた。候補抽出では型を問わず、判定の段でだけ `fact_type` 別の解決規則（下表）を使う。

**PO の言明は常に突き合わせる**。`origin: user_explicit` の episode が記録されたら、同一閉包および祖先閉包の既存の意味記憶に対し、**無条件に候補抽出を走らせる**（`collision_candidates()`、§0.3）。PO の発話は稀で、かつ §0.7 の1位（訂正が消える）に直結するため、常時チェックしても費用対効果が合う。

#### 未解決の矛盾を溜めない 【2026-07-26 追加】

矛盾は**検出しただけでは減らない**。流入（新しい記憶）は運用規模とともに増えるのに、流出（決着）の経路が「確定するか PO が明示訂正するか」の2つしかないと、**未解決は単調増加する**（R4／S15。5年で約2,400件と推定された）。さらに §20.6 の指数バックオフが流出をさらに細らせる。

流出経路を足す。

| 状態 | 規則 |
|---|---|
| LLM が「どちらとも言えない」と保留 | **保留の期限を持たせる**。期限を過ぎたら `fact_type` 別の既定規則で機械的に決着させる（`preference_decision` は最新性、`world_fact` は出典数、`state_fact` は観測不能なら最新性）。決着したことは版に残るので、後から覆せる |
| PO 判断待ちが滞留 | **ダイジェストにまとめて再提示**（§21）。個別通知の再送はしない（通知疲れを起こす） |
| 観測不能で決着せず | `state_fact` の**観測可能性が「不能」と宣言された `system`** に属するなら、最新性フォールバックで**決着させる**（未解決のまま残さない）。観測できないものを待ち続けない |
| 2ホップ超の派生 | §20.5-4 の点検で再検証キューへ（列挙で終わらせない） |

**`unresolved_conflicts`（§0.3 のシグナル）が閾値を超えたときの動作を定義する**：`memory_signal` 起床源（§20.2）が発火したら、Steward Driver は**古い順ではなく、影響範囲の大きい順**（`dependents()` の子孫数×`salience`）にトリアージし、上位から決着させる。初版はシグナルを公開するだけで、**発火して何をするかが書かれていなかった**。

#### 「訂正」の定義 【2026-07-26 確定】

§7 のピン留め、§19 の緊急無効化チャネル、§20.3 の最優先枠は、いずれも「ユーザーによる明示的な訂正」を対象とすると書きながら、**何をもって訂正とするかを定義していなかった**。既存の記憶を名指しで否定した発話だけなのか、新しい方針の表明も含むのかが曖昧だった。機械的に定める：

> **訂正 ＝ `origin: user_explicit` の言明であって、`collision_candidates()` が既存の生きた意味記憶を1件以上返したもの。**

候補ゼロなら「新規の言明」、候補ありなら「訂正」。判定はルールベースで、LLM を使わない（§20.0）。これでピン留め・緊急伝播・最優先キューの対象が**同じ一つの規則から導かれる**。

**検出結果を裁定へ配線する** 【2026-07-26 追加】。経路A が対立ペアを検出しても、**その結果を `supersede()` へ流す手順が書かれていなかった**（§20.8。2ラウンド連続の指摘）。`supersede()` は「既存エントリへの新版作成」という版系譜の API であり、**独立に生まれた2候補**（互いを supersede しようとした関係にない）には適用経路がない。規則：

> 経路A で対立ペアが確定したら、深い睡眠は**敗者側に対し必ず `supersede()` を呼ぶ**。新版は `tombstone: true` とし、`derived_from` に勝者と敗者の旧版の両方を含める。これにより「なぜ敗れたか」が版系譜から辿れる。

これを書かないと、§20.5-4（覆った根拠に基づく外向き副作用の点検）も発火しない——あの点検は「敗者の版が変わること」を前提にしているためである。

**経路B：出典の系譜による波及**（抽象度が上がった派生を拾う）

経路A には原理的な穴がある。訂正「軽微な変更は自動マージでよい」と、2段蒸留された「PO は統制を重んじる」は**語彙が一つも重ならない**。類似度ベースでは永久に引っかからない（ADR-0010 §6-S2）。**蒸留が抽象化するほど、訂正が届かなくなる。**

これを埋めるのが `derived_from` の逆引きである。あるエントリが supersede / tombstone されたら、それを出典に持つ子孫を再検証キューへ積む（§20.4）。**語彙ではなく系譜で辿るので、抽象度が上がっていても届く。**

### 矛盾解決規則は origin → fact_type の順で分岐する 【ADR-0010 で改訂】

> 本節は [ADR-0010](../adr/adr-0010-memory-substrate-schema.md) §1.1・§1.3 が正典。以下はその反映。

**まず `origin` を見る。** `origin: user_explicit` は `agent_inferred` / `external` に**無条件で優先**する。同一 origin の中でのみ、下表の fact_type 別規則で裁く。

この優先は**書き込み経路の実行層で強制する**（最新版が `user_explicit` のエントリに対し、`agent_inferred` の新版を作れないようにする）。プロンプトに書くだけにしない。旧版には origin の例外が無く、番頭が後から作った推論が PO の訂正に**時刻の新しさだけで勝つ**状態だった（ADR-0010 §6-S3/S5）。§0.7 の1位そのものである。

同一の規則を全事実に適用すると必ず破綻するため、fact_type で分岐する（`kind: semantic` のみ適用）。

| fact_type | 規則 | 理由 |
|---|---|---|
| `preference_decision`（規範的言明。誰が決めたかは `origin` が持つ） | **最新性が勝つ** | 出典数優先だと訂正が効かなくなる（§0.7 の1位） |
| `state_fact`（時とともに変わる客観的状態） | **観測し直して裁く**。観測できないときのみ最新性 | 議論ではなく観測で決まる。発火は §20.4、観測手段は `external_ref` の `system` ごとに宣言 |
| `world_fact`（変わりにくい客観的事実） | **出典の数と独立性が勝つ** | 最新性優先だと単発のデマに弱い |

### コールドスタート時の過剰な重み

記憶が空のときベースLLMに縮退するのは問題ないが、**最初に入った記憶が不当に強くなる**。競合がないため常に上位に来て、参照され、強度が上がる。誤りでも同じ。

さらに、確信度を出典数で算出すると**長く居座った誤りほど出典が多い**という逆転が起きうる。上の分岐はこれへの対策でもある。

### 虚偽記憶（スキーマ補完）のリスク

蒸留過程でLLMが言われていないことを補完するリスクは完全排除できない。**出典リンクと確信度で「検知して確信度を下げる」ところまでが現実的な到達点。** 蒸留を可逆にしておくこと（出典を必ず残す）が唯一の机上での対策。

## 13. 想起強度と減衰 【降格】

**位置づけを変更した。** 減衰は本設計の主役ではなく、§7 のスコア関数の一特徴量である。

### 理由

「忘却」と呼んでいたものは実際には3つの別問題だった。

1. その事実はもう真ではない → **有効期間と版管理**（§5・§3）
2. 今この瞬間の話題と無関係 → **関連度ランキング**（§7 の入場スコア）
3. そもそも一度も役に立ったことがない → **想起履歴＝減衰**

減衰が測るのは3だけであり、この中で最も効かない。さらに減衰は逆効果になる場面がある。**半年触っていないプロジェクトの記憶は、その話題が始まった瞬間に最優先で入れるべきもの**だが、減衰はそれを最も低いスコアにする。「使われていない＝重要でない」は、話題が周期的に戻る実務では成立しない。

### 残る役割

- §7 の入場スコアにおける**弱い事前分布**（関連度が同点のときのタイブレーカー）
- §16 の検索コスト抑制

### 時定数の単位

- **保存層の strength** — 単位は日〜月。物理削除ではなくアーカイブ降格の判断にのみ使う
- **ワーキングセットの activation（§7）** — 単位は**ターン**。効果が数ターンで観測でき、実際にチューニング可能なのはこちら

減衰させないもの: 手続き記憶、ピン留め対象。

## 14. 蒸留・統合・チャンキング（睡眠バッチの内容）

> タイミングは §19。ここでは中身のみ。

| 処理 | 条件 | 内容 |
|---|---|---|
| 昇格 | recall_count 閾値超え | エピソード→意味記憶へ一般化（海馬→大脳皮質の固定化に対応） |
| 昇格（例外） | **`origin: user_explicit`** | **閾値を問わず無条件に昇格**（下記） |
| 統合 | 類似エントリ | マージ、出典リンク統合 |
| 降格 | strength 閾値未満 | 詳細→要約に圧縮 |
| アーカイブ | strength 十分小＋期間経過 | アーカイブ層へ（削除しない） |
| チャンキング | 繰り返しパターン | 定型手順を上位ノードに圧縮し手続き記憶へ昇格 |

### `propose()` を呼ぶ条件 【2026-07-26 追加】

**誰がいつ候補キューへ積むかが定義されていなかった。** 上の表は「昇格の条件」を書いているが、それは**候補キューに入った後**の話である。キューに入る条件が無いと、後段の機構（§20.4 の同一バッチ内の対立検査、§12 の矛盾検出、§20.5-6 の外向き副作用の点検）は**入力が来ないまま空回りする**（R4／S3）。

次のいずれかを満たす episode は、セッション終了時の浅い睡眠が**必ず `propose()` を呼ぶ**。判定はルールベースで、LLM を使わない（§20.0）。

| 条件 | 理由 |
|---|---|
| `origin: user_explicit` | PO の言明は一撃でも失ってはならない（§0.7 の1位） |
| `recall_count` が閾値超え | 従来からの条件 |
| **`external_ref` に外向きの command を持つ** | サブシステムに送った指示は現実を変えている。候補にならないと §20.5-6 の点検が発火しない |
| **規範的言明を新規に確立した**（`fact_type: preference_decision` 相当の内容を含む） | 番頭が単独で下した運用判断も方針である。候補にならないと他の分身の判断と突き合わされない |
| **`origin: external` を含む** | 外部由来の主張は §12 の検出に載せる |

### PO 由来の一撃決定は閾値をバイパスする 【2026-07-26 追加】

昇格条件を `recall_count` 閾値だけにすると、**一度しか言われていない PO の決定や訂正が意味記憶に上がらない**。矛盾解決（§12）は意味記憶の運用なので、上がらなければ規則は一度も適用されない——「レビューは全部見たい／やっぱり自動マージでいい」のような一撃の方針転換が、確率的な想起回数に依存して効いたり効かなかったりする。§0.8「訂正はピン留めし、確率的な機構に一切委ねない」に反する。

したがって **`origin: user_explicit` のエピソードは、次の睡眠で無条件に意味記憶へ昇格する**。`recall_count` は見ない。

**ピン留めを条件に含めない** 【2026-07-26 訂正】。初版は「`user_explicit` かつピン留め対象」としたが、ピン留めの条件は「訂正であること」であり、訂正の定義は「衝突候補が出たもの」（§12）である。したがって**候補ゼロの新規の言明は、ピン留めされず、昇格もされない**という連鎖が生じていた。PO と合意した一撃の決定が閾値に落ちる（§20.8-1 の残り）。条件を鎖にすると片方が外れて全部外れるので、`origin` だけで判定する。

### 手続き記憶の出力形式は SKILL.md を採用する

チャンキングが生成する手続き記憶は、**agentskills.io の SKILL.md 形式**で出力する。既存ハブのスキルをそのまま消費でき、生成したものを外部に出せる。

形式を借りるだけで実装は独立している。外部標準の採用は「実装はオリジナル」という方針と矛盾しない。

## 16. 評価指標

Policy 層の全パラメータはこれで調整されるため、**実装より先に計測基盤を置く**。

### ノイズ率（自動計測）

注入した各項目に対し、出力がそれを参照したかを記録する。応答時に使用した記憶IDを申告させれば近似できる。参照されなかった項目は次回スコアを下げる直接のフィードバックになる。

> **前提条件**: 参照検出の信頼性。これが取れないと §7 の β による正のフィードバックが機能しない。§0.9 の通り最優先で検証する。

### 見逃し率（訂正イベント起点）

ユーザーの訂正が入ったターンについて、必要だった記憶が「ストアには在ったが注入されなかった」かを事後判定する。訂正は頻繁ではないため全件手動でも回る。

### ベースラインとの比較

各機構は「あった方が良さそう」ではなく**ベースラインに対する改善**として評価する。これを上回らない機構は削る。

ベースラインは2つ置く。

1. **素朴なベースライン** — 全ログを長コンテキストに投入＋素直な検索。下限として必ず超える
2. **実在のベースライン** — Hermes Agent（Nous Research、MIT）の記憶実装。agent-curated memory + 定期的な nudge + FTS5 全文検索 + LLM要約という構成で、実際に広く使われている。**§9 が否定している「明示的リコール・明示的書き込みに依存する方式」の実物**であるため、比較対象として最適

Hermes に実装を載せることはしない（実装はオリジナルとする方針）が、**比較対象として使うことに矛盾はない**。

コーディング文脈ではテストの通過・不通過という客観的な結果があるため、評価の一部を自動化できる。

### 可観測性

なぜこの記憶が注入されたか／されなかったかを人間が追える形で記録する。実運用のデバッグで最初に必要になる。

### パラメータ調整

τ・重み・閾値はベイズ最適化等でオフライン再調整。**見逃しコストを意図的に高く重み付けする**（§0.8）。完全自動化は「無難に忘れる」方向へ偏りやすい。

### 16.1 番頭としての評価 — 自己改善ループとの接続 【2026-07-26 追加】

banto は既に自己改善ループを持つ（`spec-improvement-loop`）。本節の指標はそこに接続する。

| Quirefold 側 | improvement-loop 側 |
|---|---|
| Policy 層のパラメータ（Part II 全体） | **層B（ポリシーパラメータ）**。エージェントが編集提案、コミットは PO レビュー対象 |
| ノイズ率・見逃し率・ベースライン比較 | 改善タスクの `hypothesis.metric` に入る値 |
| driver のパラメータ（§20.6） | 同じく層B。ただし**番頭からは読み取り専用**（§20.6） |
| 蒸留プロンプト・分類ガイド | 層A（プロンプト資産） |
| memory / driver の機構コード | 層C。エージェントは提案まで |

#### 既存のベンチマークが当たらない理由

記憶・長文脈のベンチマークは複数実在するが、測っている軸が違う。

1. **失敗モードの順位が非対称**（§0.7）。「訂正が消える ＞ 確信を持って誤る ＞ 汚染 ＞ 見逃し ＞ ノイズ」という重み付けを、全問等重みの正解率は表現できない。
2. **時間軸**。§0.9 が明記するとおり「パラメータの調整には実時間の経過が要る」。5ヶ月放置して再開する挙動は、合成的に圧縮した履歴では測れない。
3. **目的関数が違う**。測りたいのは「番頭が賢いか」ではなく「**番頭がいることで PO の判断回数が減ったか**」。improvement-loop の到達目標「同じクラスの問題を二度指摘しなくて済む」は正解率ではない。

#### N=1 問題と、その割り方

PO は1人しかいないので、**番頭のいる自分といない自分を A/B できない**。絶対評価は原理的に取れない。したがって**時間で割る**——improvement-loop の `po起源の割合` をメタケイデンス（月次）で追い、同じクラスの指摘が減っているかを見る。絶対値ではなく傾きを見る。

#### 構造的な強み：行動観測

§0.9 の**行動観測方式**が効く。自己申告（使った記憶IDを LLM に言わせる）は信頼できないが、コーディング文脈では失敗が**行動として直接観測できる**——既にコンテキストにあるファイルの再読み込み＝見逃し、確立済みの規約に反する実装＝訂正の消失、同一調査の反復＝想起されていない。Kobo がイベントログを決定的に持ち、テストの通過・不通過という客観的結果もあるため、**仕事をすると評価データが出る**。

これは「第一の店＝開発」を選んだことの副産物である。開発は正解が機械的に判定できる稀な領域であり、記憶システムを育てる場所として最良の選択だった。家計や研究ドメインでは同じことができない（→ 他ドメイン増設時、評価は行動観測から PO の主観へ後退する）。

#### Goodhart のリスク

「訂正イベントが減る」を metric にすると、番頭は**訂正されないように振る舞う**方向へ最適化しうる——曖昧に言う、断定を避ける、判断を PO へ投げ返す。どれも訂正を減らすが、番頭としては劣化している。§0.7 の1位を測る指標が、1位を回避する振る舞いを育てる。

improvement-loop は開発側で同型の問題を既に認識している——「**回避策（workaround）は最重要シグナル。成功した回避は incident にならず欠陥を隠蔽するため、明示的に収集する**」。**この規律を番頭自身の評価にも適用する**：番頭がうまく回避したこと（判断を避けた、曖昧に答えた、PO に投げ返した）を積極的に収集対象にする。

improvement-loop の「レビュー必要性の縮小は目標として掲げるものではなく、検証の機構化の結果として得る」も同じ趣旨の防御である。

#### 割り切りと規律

improvement-loop §5 のとおり「厳密な因果評価は行わない。目的は方向性の確認と、特に**明確な悪化の検出**」。記憶が良くなったのか、モデルが変わったのか、タスクが簡単だったのかは分離できない。したがって自己改善ループを回すなら「**変更は一度に一つ**」が実質的な前提になる。§16 が置く2つのベースライン（素朴な長コンテキスト投入／Hermes Agent）は、絶対値が測れなくても「下回っていないか」は測れるという意味で貴重である。

#### シナリオ検証を評価手法として残す

ADR-0010 §6 と §20.8 で2回行った手続き——**シナリオを固定し、設計を変え、破綻箇所の増減を見る**——は、外部ベンチマークが無い領域での実用的な評価手法として機能した。10シナリオは資産として保全し、設計変更のたびに回す。ただし §20.8 末尾の限界（シナリオが見ていない領域は2回とも見つからない）を承知の上で、定期的にシナリオ自体を入れ替える。

# Part III — Loop（実行ループ）

## 17. 内部状態（感情の機能化）【実験的】

「今この瞬間どう振る舞うか」を決めるレイヤー。§11 の顕著性が「何を覚えるか」を決めるのに対し、こちらは「今どう動くか」を決める。入力ソースは重なるが出力先が異なる。

| 変数 | 反映するもの | 行動への影響 |
|---|---|---|
| `uncertainty` | 確信度平均、矛盾検出頻度 | 高いほど断定を避け確認を増やす |
| `frustration` | 同一タスクでの失敗・リトライ回数 | 閾値超えで戦略転換 or エスカレーション |
| `fatigue` | コンテキスト圧力（§19） | 睡眠フェーズへの移行トリガー |

### メカニズムとしての限界

自然言語で内部状態を注入する方式は**プロンプトによる条件付け**であり、生成内容は確実に変わる。しかしモデル内部に持続する隠れ状態が存在するわけではなく、次の推論の入力テキストの一部に過ぎない。「感情に突き動かされている」のではなく「感情の状態を説明された指示に従っている」に近い。

**実際のブラックボックス性の所在**は感情メカニズムの内部ではなく、複数の指示（プロトコル、直前の発言、内部状態）が競合したときの優先順位。人間の感情のように理性を押しのける保証はなく、効き方はモデルとプロンプトで変動する。

### 運用方針

1. 数値ではなく「現在: 不確実性が高い状態」程度の簡潔な自然言語で2〜3行
2. §24 のプロトコルに行動ルールを書いて明示的に接続する（曖昧な感情語だけでは不安定）
3. **eval で検証し、効果がなければ削る**

## 18. 睡眠と覚醒

### 眠気と発火条件

コンテキスト使用率に応じて `fatigue` を漸進的に蓄積させる。圧力モデルにする利点は**安全な区切りを待てる**こと。

- **ソフト閾値** — アトミックな境界（サブタスク完了直後など）を待って自発的に眠る
- **ハード閾値** — 区切りを待たず強制的に中断・整理する

ツール呼び出しやトランザクションの途中での強制中断は副作用の不整合を招くため避ける。

### 3層の睡眠

| 種別 | 頻度 | 処理内容 |
|---|---|---|
| **マイクロスリープ** | 予算超過時／話題転換時 | §7 のバッチ退場、§10 のツール結果圧縮。記憶ストアには触らない |
| **浅い睡眠** | セッション終了ごと（並行可） | 直近差分の圧縮、即座の矛盾検出。**事実を確定させず候補としてキューに積むだけ** |
| **深い睡眠** | 低頻度（日次／週次、単一writer） | キューを消費し、候補間の矛盾を解消して意味記憶を確定。チャンキング、アーカイブ降格、パラメータ再調整 |

差分のみだと**数週間にまたがる繰り返しパターンを見逃し**、全件処理はコストが線形に増えるため、二段に分ける。マイクロスリープは §7 のバッチ退場と同一機構であり、独立した実装を持たない。

### セッション再開は特別扱いしない

新セッション開始時に手作りの再開サマリーを注入せず、§7〜§9 のパイプラインをそのまま流用する。「セッション開始」自体をクエリ発火のトリガーとし、クエリの種は直前のゴール状態＋高顕著性の記憶。

起床時だけの特殊ロジックを持たないことで実装が単純になり、睡眠フェーズの要約に漏れがあっても最初のターンの注入が二重の安全網になる。

## 19. 並行セッション 【本文へ昇格】

### 並行は追加要件ではなく前提

自律ループが裏で走りながらユーザーが話しかける（§21）という設計は、定義上**2つの独立したコンテキストが同時に存在する**ことを意味する。並行をやめる選択肢は効率の問題ではなく、自律性の要件から存在しない。

**人間が直列なのは体が1つで注意が1つだからであり、記憶アーキテクチャの要請ではない。** §0.2 原理1を適用してアナロジーを捨てる。脳から借りるべきは「符号化は連続的、固定化は別フェーズ」という時分割の方であり、それはそのまま §18 の3層睡眠になっている。

### 層ごとの並行性

| 層 | 並行性 | 理由 |
|---|---|---|
| 自己モデル・プロトコル | 完全並行 | 読み取り専用 |
| ワーキングセットの滞在状態 | 完全並行 | セッション側に持つため共有していない（§2） |
| エピソードログ | 完全並行 | 追記のみ。session_id で別ストリーム |
| 意味記憶 | 要調整 | §3 の版管理で検出可能な矛盾に還元 |
| 深い睡眠 | **単一writer** | 直列化。低頻度なので効率上の損失はほぼない |

### 読み取りはスナップショット隔離

セッションBの動作中にセッションAの書き込みが即座に見えるべきではない。理由は独立に2つあり、同じ結論を指す。

1. **体験として悪い** — 自分が何もしていないのに前提が途中で変わる
2. **キャッシュが壊れる** — 他セッションの活動でプレフィックスが失効するのは制御不能

セッション開始時およびワーキングセット再構築時に一貫したスナップショットを取る。

### 訂正の緊急伝播

スナップショット隔離の代償として、**セッションAでの訂正を裏の自律ループが知らないまま作業を続ける**問題が残る。§0.7 の1位に該当するため放置できない。

ピン留め対象の訂正のみ、通常のスナップショット更新とは別の**緊急無効化チャネル**を持たせる。乱発するとキャッシュが死ぬため、**対象は「ユーザーによる明示的な訂正」に限定する**（推論による前提変更は含めない）。訂正の判定は §12 の定義に従う（同じ規則から導く）。

### 受容するコスト

セッションごとにワーキングセットを維持するため、同じ記憶が複数コンテキストに載りトークンを重複消費する。正しさの問題ではないが、自律ループが常時走るなら無視できない額になる。

**共有ワーキングセットによる節約は採用しない。** 他セッションの活動で自分のプレフィックスが失効するようになり、キャッシュ効率の悪化が節約分を上回る。

## 20. driver — 起床と差配 【driver モジュール】

> 本節は 2026-07-26 に全面的に書き直した。旧版は `perceive()` / `update_goals()` / `decide_action()` という関数名だけの疑似コードであり、10シナリオ検証（ADR-0010 §6）が挙げた未定義のうち4つがここに落ちていた。

### 20.0 最上位の制約：driver に LLM を置かない

**driver は制御ループである。** banto が生まれた理由は「開発手法がプロンプトの遵守期待に依存し、ゲート・監査が構造的に保証されない」こと（VISION.problem／**D2「制御ループに LLM を置かない」**）。driver の判断を LLM に委ねると、番頭の自律性そのものが D2 違反になる。

> **driver は決定的コードとして「いつ・何を起こすか」だけを決める。「何をするか」は起こされたセッション（分身＝LLM）が決める。**

これは Kobo と番頭の関係と同型である。Kobo は決定的で、判断が要るときに番頭を kick する。driver も決定的で、判断が要るときに分身を起こす。§0.5 原理2「安全性を LLM の判断力に依存させない」は、この線引きで構造的に満たされる。

**帰結**：本節に現れる条件・閾値・優先度はすべて**ルールとして評価できる**形で書く。「番頭が重要だと思ったら」のような述語は driver に置かない。そう書きたくなったら、それは分身を起こす条件である。

**規則を1つ書いたら、次に進む前に6つを埋める** 【2026-07-26 追加・R4 の教訓】。1日の作業で**同じ形の欠落を6回作った**——規則を書いて配線を忘れる、という癖である。手順として固定する。

> **① いつ発火するか ② 何をするか ③ 誰が呼ぶか ④ どこで強制するか ⑤ 入力は誰が用意するか ⑥ 結果はどこへ行くか**

どれか1つでも空欄なら、その規則はまだ書き終わっていない。実績：②が抜けた（§20.5-4 は列挙するだけだった）／③が抜けた（`authored_by` は能力だけ）／④が抜けた（`content` 書き分けの検査場所）／⑤が抜けた（同一バッチ検査に候補キューへの投入者がいなかった）／⑥が抜けた（§20.5-5 に優先度も通知も提示面も無かった）。

**そして⑦：層をまたいで同じ規則を配線したか。** `origin` の強制を `record()` にだけ書いて蒸留層に書かなかったため、trust laundering が残った。**経路ごとに規則を書くのをやめ、§0.3.0 の不変条件として1箇所に置く**のがこの問題への構造的な答えである。

**この原則は driver の外でも成り立つ**（§20.8 の検証で確認）。同じ10シナリオを設計前後で回した結果、**実行層・スコア式・API シグネチャのいずれかに落とした規律だけが機能し、散文で書いた規律はすべて素通りした**。`origin` 優先（書き込み経路で強制）と版解決（候補生成の手順）は機能し、`sensitive` の取り扱い規律・`citations` の検証・`derived_from` の記入義務は機能しなかった。効いた側と効かなかった側の差は、この一点だけだった。**Part II / III に規律を書き足すときは、それが落ちる先（実行層・式・シグネチャ）を同時に指定する。**

### 20.1 二層構造：常駐 driver は1つ、ターンループは分身ごと

| | 個数 | 責務 |
|---|---|---|
| **Steward Driver** | **番頭に1つ**（常駐） | 起床源の監視、作業キューの管理、分身の起動、睡眠の発火、再検証キューの消化、自律予算の管理 |
| **Session Loop** | **分身ごと** | 1セッションのターン実行、割り込み裁定（§21）、そのセッション内の記憶操作 |

Steward Driver を1つにする理由は3つある。

1. **深い睡眠は単一 writer**（§19）。それを発火させる主体が複数あると直列化が壊れる。
2. **再検証キューの消化が直列でないと矛盾する**（同じエントリを2つの分身が別々に再検証すると、§3 の版が無用に分岐する）。
3. **内発的動機が分身ごとにあると、同じ調査を N 重に発注する**（職人のコストが分身数に比例して増える）。

分身は自分では起きない。**分身を起こすのは常に Steward Driver か PO** である。

### 20.2 起床源（wake source）

Steward Driver が監視する入力は5種類。すべてイベントとして単一の作業キューに入る。

| 起床源 | 由来 | 例 |
|---|---|---|
| `po_message` | PO の発話 | 相談・指示・訂正 |
| `subsystem_kick` | サブシステムの kick（汎用I/F、inversion §12.2） | Kobo：review-ready / blocking design-request / cadence |
| `worker_result` | Worker Pool からの職人の完了・**失敗** | 実装完了、調査結果、実行エラー |
| `memory_signal` | memory が公開する状態シグナル（§0.3）の閾値超え | `context_pressure` / `unresolved_conflicts` |
| `timer` | ケイデンス | 深い睡眠、定期点検 |
| `model_migration` | 実行系の切替 | LLM／embedding プロバイダの乗り換え。旧系が付けた `salience`/`strength` を絞って再評価するバッチを起こす（ADR-0010 §7 の `authored_by` を鍵にする） |

`worker_result` を独立の起床源として持つのは、**Banto が Kobo を経由せず直接 Worker Pool へ発注した場合、職人の失敗を受け取る経路が無かった**ため（ADR-0010 §6-S4）。職人は memoryless で消えるので、この受け口が無いと失敗が誰にも記憶されずに終わる。

**Worker Pool の契約**：

- **成功・失敗を問わず必ず `worker_result` を返す。**
- **職人が呼んだツールの一覧（ツールログ）を必ず含める** 【2026-07-26 追加】。これは職人の自己申告ではなく実行の事実であり、`record()` の `citations` 空振り検証（§0.3.1）が成立する前提になる。外部取得を行ったのに引用エントリが無い記録を、ルールベースで弾けるようにするためのもの。
- **発注は `assemble_brief()` を通す**（§0.3.1）。自由記述のブリーフを受け付けない。

### 20.3 作業キューと優先度

起床源のイベントは単一の優先度付きキューに入り、Steward Driver が1件ずつ処理する。優先度は**決定的に計算する**：

```
priority = base(kind) + 滞留時間の重み + ブロック係数
```

| kind | base | 備考 |
|---|---|---|
| `po_message` | 最高 | 常に他を押しのける（§21） |
| 訂正に由来する再検証・点火（§20.4） | 最優先（`po_message` と同格） | §0.7 の1位（訂正が消える）に直結。判定は §12 の定義 |
| `subsystem_kick`（blocking） | 高 | ブロック係数＝止まっている下流の数 |
| `worker_result`（失敗） | 中 | 成功より高い |
| `subsystem_kick`（advisory） | 中 | |
| 自律的な再検証・調査 | 低 | 予算の従属（§20.6） |

滞留×ブロックで並べる考え方は、既存のアテンションキュー（inversion §6）と同じである。**キューは番頭が PO に差し出す盤面そのものであり、driver の内部状態と UI が同一の実体を見る。**

### 20.4 再検証キュー（revalidation queue）

検証が挙げた4つの穴——訂正が派生記憶に伝播しない／出典が新版に置き換わったことが伝わらない／`state_fact` が陳腐化しても誰も気づかない／`external_ref` が解決不能になっても検知しない——は、**同じ1つの機構の不在**だった。ここで定義する。

**再検証キューはエントリに書かない。** 導出できる状態であり、エントリに書くと並行セッションで壊れる（§2 の滞在状態と同じ理由）。Steward Driver が保持する。

#### 点火：まだ記録されていない矛盾を拾う 【2026-07-26 追加】

下の「積む条件」はすべて**反応的**である——supersede された／tombstone された／解決に失敗した、という**既に store で起きたこと**を起点にする。しかし最初の矛盾は、まだ store の中では何も起きていない。PO が「Node 20 に上げた」と言った瞬間、衝突しているのは**新しい発話と既存の記憶**であって、版はまだ動いていない。

初版はここに点火装置が無く、**伝播路だけがあってスイッチが無い**状態だった。再検証キューの全条件が空振りする（§20.8-1）。塞ぐ：

> **`origin: user_explicit` の episode が `record()` されたら、Steward Driver は同期的に `collision_candidates()` を呼ぶ。候補が1件以上あれば、そのエントリを最優先で再検証キューへ積み、そのターンのうちに分身へ渡す。**

- **同期的に行う**のは、次の深い睡眠まで待つと**その場の回答が既に誤る**ため。PO は今この瞬間に答えを受け取る。
- 候補抽出は**ルールベースの一次フィルタ**（同一・祖先閉包＋エンティティ一致＋LSH。§12 経路A）。LLM は使わない（§20.0）。矛盾かどうかの判定は、渡された分身が行う。
- 発火するのは `user_explicit` の episode に限る。PO の発話は稀なので常時チェックしても割に合い、かつ §0.7 の1位に直結する。職人や番頭自身の推論は対象外（対象にすると毎ターン走ってコストが合わない）。
- 候補ゼロなら何もしない。この判定結果が §12 の**「訂正」の定義**にそのまま使われる。

**点火する入口を3つ足す** 【2026-07-26 追加】。初版は「`user_explicit` の episode が `record()` された時」だけを入口にしたため、4つのシナリオが独立に「こぼれる経路」を指摘した（§20.8-B）。

1. **Memory 面からの直接 `supersede()`**：PO が UI で「これは違う」と直す経路（§25 の編集導線）は `record()` を経由しないため、「訂正」の定義の外側に落ちていた。**`origin: user_explicit` の `supersede()` 呼び出しは、`collision_candidates()` を経ずに無条件で「訂正」とみなす**（対象エントリ自身が衝突相手だから）。これで最優先枠・緊急伝播チャネルに乗る。**PO が事後訂正する導線そのものが最優先で伝わらないのは本末転倒である。**
2. **同時発生（同一バッチ内で生まれた対立候補）**：点火は「新しい発話 vs 既存の記憶」という**順方向**しか見ない。2つの分身が同じ午後に対立する結論を出すと、どちらの記録時点でも相手はまだ存在せず、候補ゼロで素通りする。→ **深い睡眠の統合処理で、そのバッチ内に新規生成された候補どうしの対立を検査する**（§12 経路A を候補キュー内にも適用）。
3. **`origin: external` を含む episode**：汚染された外部情報は `agent_inferred` を装って入るため点火の対象外だった。§0.3.1-3 の `origin` 強制と組み合わせ、**`external` になったエントリは既存の `state_fact` との突き合わせを走らせる**（`fact_type` が違っても同一エンティティを扱うなら候補にする）。

**言明と疑問文を区別する**：PO の質問（「なんでそう決めたんだっけ？」）も `user_explicit` の episode として記録されるため点火が機械的に走るが、質問は既存記憶を否定する主張ではないので候補ゼロで空振りする。無害だが無駄なので、**疑問符・疑問語の有無というルールベース判定**で除外する（LLM を使わない、§20.0）。

**積む条件（反応側。すべてルールベース。LLM を使わない）**

| 条件 | 積む対象 |
|---|---|
| あるエントリが supersede された | `derived_from` にそれを含むエントリ（逆引き、既定2ホップ） |
| あるエントリが tombstone された | 同上 |
| `origin: user_explicit` の訂正が入った | その訂正が否定した対象の子孫。**最優先** |
| `external_ref` の解決に失敗した／指す先が変化した | そのエントリ |
| `state_fact` が閾値時間更新されず、かつその話題が再活性化した | そのエントリ |

`derived_from` は版を pin する（ADR-0010 §4）ので、逆引きインデックスは決定的に構築できる。**深さを既定2ホップに切るのは、抽象度が上がった派生記憶（「PO は統制を重んじる」のような3段目）まで自動で辿ると誤爆が増えるため。**2ホップを超えるものは自己内省（§20.5）で拾う。

**消化**

- **訂正由来は即時**：分身を起こして裁かせる。§0.7 の1位を待たせない。
- **それ以外は深い睡眠でまとめて**（単一 writer、§18）。
- 消化とは「該当エントリを分身のコンテキストに載せ、まだ正しいかを判断させる」ことである。判断は LLM が行うが、それは**セッション内の判断**であって制御ループではない。結果は §3 の版として記録され、監査できる。

**`state_fact` の観測**：ADR-0010 §1.1 は矛盾を「観測し直して裁く」と定めたが、観測を発火させるものが無かった。**再検証キューがそれである。** 観測の実行手段は `external_ref` の `system` ごとに決まる：

| `system` | 観測手段 |
|---|---|
| `kobo` | query surface で照会 |
| repo / ファイル | Worker Pool へ職人を発注して読ませる |
| 外部サービス（ログイン壁の向こう等） | **観測不能**として扱い、最新性フォールバックへ落とす |

**観測可能性は `system` ごとに宣言する**（観測手段が登録されていない `system` は観測不能）。「観測できるはずだ」という前提を LLM に推測させない。

### 20.5 自己内省（深い睡眠の拡張）

深い睡眠のバッチに、決定的な点検リストを持たせる。

**各項目には「何をするか」と「結果はどこへ行くか」を必ず併記する** 【2026-07-26 追加】。初版は点検項目を列挙するだけで、見つけた後の対応・優先度表の行・通知カテゴリ・提示面を書いていなかった。**列挙するだけの点検は、見つけても誰にも届かない**（R4／S5・S15）。

| # | 点検 | 見つけたら何をするか | 結果の行き先 |
|---|---|---|---|
| 1 | 進捗が止まっているゴール | ゴールの再確認を分身に問う | 作業キュー（低）。**停滞が閾値を超えたら §21 の通知** |
| 2 | 再検証キューの滞留 | 滞留の原因別に分類し、**強制決着かエスカレーションを選ぶ**（§12） | 決着＝深い睡眠で処理／エスカレーション＝§21 の通知 |
| 3 | `external_ref` の参照先の生存 | 解決不能なら再検証キューへ。**`dependents()` で子孫にも伝播**（他の行と揃える） | 再検証キュー |
| 4 | 2ホップを超えた派生で出典が覆ったもの | 再検証キューへ積む（**列挙だけで終わらせない**） | 再検証キュー（訂正由来なら最優先） |
| 5 | `origin: agent_inferred` で自動的に可視範囲を広げた記憶のうち PO 未提示のもの | **まとめて1件の通知にする**（件数が多いのでダイジェスト） | §21 の通知＋ Memory 面。**提示面が存在しないうちは自動拡大を有効にしない**（ADR-0010 §2.1、実装順序の制約） |
| 6 | 裁定が覆った記憶を根拠に外部へ送った作用 | アテンションカードを作る。自動で巻き戻さない | §21 の通知（最優先） |

**対象は Kobo の command だけではない** 【2026-07-26 訂正】。6 は初版で「サブシステムへ送った command」に限定していたが、**Worker Pool への委譲（＝職人が書いたコード）も含める**。誤った記憶を根拠に書かせた成果物が、記憶の訂正後も見直されないままになる（R3・R4／S5）。

### 20.6 自律予算と暴走対策

driver は「誰にも頼まれていない仕事」を発注できる唯一の主体であり、コストと暴走のリスクはここに集中する（§24・§25）。

- **自律発注には予算枠を持つ**（期間あたりのトークン／職人発注数）。枠を超えたら自律行動を停止し、`po_message` と `subsystem_kick` への応答だけを続ける。**停止は決定的に行い、番頭の自己判断に委ねない。**
- **同一対象への再検証は指数バックオフ**。同じ `state_fact` を何度も観測しに行かない。
- **自律行動のログは PO に可視**。何を勝手に調べたかが後から分かる（ADR-0010 §2.1 の「事後の可視性」と同じ担保）。**ただしこのログの置き場は未設計**（§20.8-6）。
- **driver のパラメータは番頭から読み取り専用**。閾値・優先度の重み・自律予算枠を番頭が実行時に書き換えられると、決定的な機構の皮をかぶった番頭の意志になり、**LLM が裏口から制御ループに戻る**（§20.0 の否定）。変更は PO の承認、または層B の改善提案として ADR / レビューを経る（spec-improvement-loop §1）。
  - これは §22 self-model の保護と**同型**である。経験から学んだ振る舞いは意味記憶側に留め、人が明示承認したものだけ昇格させ、エージェントは自己書換できない。番頭の人格ドリフトを防ぐ関所と、番頭の駆動条件を守る関所は同じ形をとる。
  - §0.2 が自ら警告している——「memory はタイマーを持たないという規律は、**エージェントが利便性のために黙って破る典型**」。同じことがパラメータにも起きる。

### 20.7 内部状態（§17）の使い方を限定する

§17 の3変数を driver の制御に使うのは **`fatigue` のみ**とする（睡眠の発火＝決定的な閾値判定）。`uncertainty` と `frustration` は**セッションに渡す文脈**であって、制御条件には使わない。

理由は §20.0 である。`uncertainty` は LLM の自己申告に由来するため、これを起床条件にすると制御ループが LLM の内省に依存する。§17 自身が「モデル内部に持続する隠れ状態が存在するわけではない」「eval で検証し効果がなければ削る」と限界を認めており、**制御に使わなければ削っても壊れない**位置に置ける。

### 20.8 未解決（2026-07-26 の再検証で判明）

1. ~~**検出の起点がない**~~ → **2026-07-26 対処済み**（未再検証）。3シナリオが独立に指摘した最優先の穴。原因は3つ連鎖していた：`record()` は episode にしか書けず意味記憶の版を作る操作が公開 API に無い／§12 経路A が「同一 `fact_type`」で絞るため新規 episode（null）と既存 semantic がペアにならない／昇格が `recall_count` 閾値なので単発の PO 発話が越えない。**結果、supersede が起きず §20.4 の5条件が空振りしていた。** 対処：`supersede()` と `propose()` を §0.3 に追加し origin 優先の強制をそこに置く／経路A の候補条件から `fact_type` 一致を外し、PO の言明は常に突き合わせる（§12）／`user_explicit` かつピン留めの episode は閾値を問わず昇格（§14）／**点火**を §20.4 に新設し、`user_explicit` の episode 記録時に driver が同期的に衝突候補を引く。副産物として「訂正」の定義（§12）が機械的に定まり、ピン留め・緊急伝播・最優先枠の対象が同じ規則から導かれるようになった。**次回の検証で発火を確認すること。**

3. ~~**lineage-aware でない**~~ → **2026-07-26 対処済み**（未再検証）。R1〜R3 の3ラウンドすべてで「動かない」判定を出し続けた唯一の穴。`origin` による三重防御はエントリ自身の `origin` しか見ないため、外部由来の主張を職人が自分の結論として言い換えると `agent_inferred` になり、蒸留を重ねるほど外部由来性が薄まる＝ロンダリングになっていた。対処：**`derived_from` に `origin: external` があれば `origin` を実行層で無条件に `external` へ強制する**（§0.3.1-3）。判定の根拠が機械的な事実（`derived_from`）なので、自己申告に頼らずに強制できる。
4. **プッシュ型の気づきが無い**【R2・R3 で継続。未対処】。§20.4 の `state_fact` 条件は「閾値時間未更新 **かつ** 話題が再活性化」の AND であり、誰も話題を戻さないと発火しない。「外部で何かが起きたことに自発的に気づく」機構が存在せず、非開発ドメイン最大の要求（例：契約先の料金改定に気づいて再提案する）を満たせない。汎用I/F 側に `subsystem_kick(state_change)` の契約が要る。また「話題が再活性化した」の判定主体も未定義（他の4条件はイベント駆動だが、これだけ状態監視）。
5. **`kind: procedural` が再検証キューの対象外**。5条件のどれも SKILL.md の陳腐化を拾わない。`external_ref` の「解決失敗」はファイルが存在すれば反応しないため、中身が古くなっても検知できない。
6. **driver 自身の活動ログの置き場が未設計**【未対処】。何を再検証すると決めたか、何に予算を使ったか、なぜその分身を起こしたかの記録先が無い。記憶（学びの置き場）でも Kobo（開発の実行台帳）でもない。→ driver 専用の軽いログを持つか、自律行動の起床を episode として記録するかの二択。
7. **本節内の不整合**（P3 として incident を積むべきもの）：~~§20.4 は「2ホップを超える伝播は §20.5 の自己内省で拾う」と述べるが §20.5 の点検項目にそれが無い~~（2026-07-26 に §20.5-4 として追加）／~~§20.3「高」と §20.4「最優先」の不一致~~（2026-07-26 に「最優先」へ統一。1 の対処で点火が §20.3 の同じ枠に入るため）／§20.5-4 の対象が Kobo の command のみで Worker Pool への委譲（＝職人が書いたコード）が漏れる／`external_ref` 解決失敗の行だけ `dependents()` へ伝播せず他の行と揃っていない／`external_ref.system` の観測手段表に `web` が無く、非開発ドメインの主要ソースが恒久的に観測不能に落ちる。

### R3（2026-07-26・11シナリオ）で新たに判明した残件

判定は 動く0／条件付き10／動かない1。**S1 が「動かない」から脱した**（点火が効いた）。以下は R3 の新規指摘のうち未対処のもの。対処済みは上の1〜7に反映した。

- **深い睡眠の全件処理が2〜4年目で一晩の窓を超える**（S11）。§14 が「差分のみだと数週間のパターンを見逃す」と自認する以上、全件処理側は必須。試算では5万件で約7時間、100万件で約6日。§15 の削減策は定数倍の改善であって線形スケーリングを変えない。**シャーディング設計（深い睡眠の writer 粒度と併せて）を実装前に決める必要がある。**
- **深い睡眠の単一writer の粒度が未定義**（S11・S3）。全体で1つかドメイン別か。4ドメイン並行で直列に詰まる。
- **閉包レジストリのライフサイクル**（S7・S11）：新ドメイン増設時のプロビジョニング手順、表記ゆれの是正、死んだプロジェクトの畳み方、**エンティティ名→閉包IDの逆引き索引**（レジストリは包含関係専用で、名前から引く索引が無い）。
- **エクスポート機構が存在しない**（S11）。撤退可能性。小規模なうちに一度通しておかないと、100万件で初めて実行することになる。
- **`kind: procedural` の裁定規則が無い**（S4）。`fact_type: null` なので §12 の解決規則表に行が無く、点火は発火するが受け皿がない。SKILL.md の陳腐化も再検証キューが拾わない。
- **`worker_result` 失敗の記録が強制されていない**（S4）。記録するかは分身の裁量。driver 側で「失敗が来たのに episode が記録されなかったらフォールバックで代理記録する」規則が要る。
- **出典の水増し**（S6）：1回のクエリで取った `external_ref` 8件が「独立した8件」として確信度を押し上げる。§4 の独立性判定は Quirefold 内エントリ間しか見ていない。
- **集計・分類済みの `state_fact` の再現性**（S6）：判定ルールIDを `context` に残す対策を ADR-0010 §4 に書いたが、**Kobo 側にゲート構成の版を返す API が無いので実装できない**。
- **`state_fact` の観測手段表が閉じている**（S7）：`web` の行が無く、「system ごとに宣言すれば観測可能」という一般原則と「ログイン壁の向こうは観測不能」という固定行が矛盾している。

**検証の限界**：R1・R2 は同じ10シナリオを使ったため、**シナリオが最初から見ていない領域の穴は2回とも見つからない**（複数 PO、モデル差し替え、記憶ストアの障害と復旧など）。実際、6 は10シナリオのどれも指摘せず、Kobo と driver を並べた対比から出た。設計が固まった段階でシナリオ自体を入れ替えた回を別途行う。

## 21. 割り込みと優先順位 【driver モジュール】

### 応答とタスク実行の分離

- **応答はプリエンプト可能** — ユーザー入力への一次応答は実行中タスクより優先して即座に返す
- **タスク自体は中断しない** — バックグラウンドで継続（強制中断は副作用の不整合を招く）

| 状況 | 挙動 |
|---|---|
| ユーザー入力あり | 即座に応答を最優先（タスクは裏で継続） |
| 自律ゴール vs ユーザー要求 | ユーザー要求が勝つ（自己モデルの安全制約のみ例外） |
| 自律活動で気づいたこと | 重大度が高いものだけ、ユーザーが現れたタイミングで簡潔に報告 |

### 分身への割り当て

`po_message` と `subsystem_kick` は**新しい分身を起こす**か、**既存の分身に渡す**かを決める必要がある。判定はルールで行う：

- 既存の生きた分身のうち、**同じ閉包（`context.scope`）かつ同じゴールに属するもの**があればそれに渡す
- 無ければ新しい分身を fork する（§5）
- **判定に LLM を使わない**。曖昧な場合は新しい分身を起こす（誤って既存の文脈を壊すより、分身が1つ増える方が安い）

### 通知という第三のモード

「即座に応答」と「無視して継続」の二択にしない。軽い割り込み（通知）を持たせる。全ての気づきを即座に投げるとうるさいエージェントになる。

**重大度フィルタは決定的に定義する**（§20.0）。通知を上げるのは次の場合：

- 訂正由来の再検証で、PO の判断が要ると判定されたもの
- **`state_fact` が再観測によって supersede されたとき** 【2026-07-26 追加】。これは `origin: agent_inferred` なので §12 の「訂正」の定義に当たらず、初版では通知対象外だった。しかし「4月にモノリスだと結論していたが、10月の再調査で誤りと判明」は**確信を持って誤っていた事実が判明した瞬間**であり、§0.7 の2位に直結する。むしろ通知すべき筆頭である（§20.8-C）。定義の統一（§12）が対象を絞った副作用をここで補う
- `sensitive: true` の記憶に関わる判断
- 自律予算の枯渇
- 覆った根拠に基づく外向きの副作用（§20.5-4）

`uncertainty` や `frustration` を通知条件に使わない（§20.7）。

# Part IV — Governance（統治）

> **共通原則: LLMの判断力に安全性を依存させない。** プロンプトは一次防御に過ぎず、実行層の強制を主防御に据える。

## 22. 自己モデル（Self-Model）

> **再レビューの起動条件** 【2026-07-26 追加】：`last_reviewed` フィールドは存在するが、**それを読む主体がどこにも定義されていなかった**（R4／S14）。5年運用で1年目の承認内容のまま凍結し、PO の変化にもモデルの世代交代にも追随しない。§22 の「エージェントの自己書換を許さない」はドリフト防止として正しいが、**「変わらないこと」が害になる場合の契機が無い**。
>
> 深い睡眠の自己内省（§20.5）に項目を足す：**`last_reviewed` から一定期間が経過した、または `model_migration`（§20.2）が発火した場合、self-model の再レビューを §21 の通知として PO に上げる**。変更は従来どおり PO の明示承認のみ（自己書換は許さない）。**契機を作るだけで、権限は変えない。**
>
> `model_migration` の波及範囲も広げる：初版は `salience`/`strength` の再評価バッチだけを効果としていたが、**self-model・プロトコル層（§23）・層A のプロンプト資産・§17 の内部状態の較正**にも波及させる。モデルが変われば、そのモデル向けに調整されたものすべてが影響を受ける。

個性（口調、価値観、判断の優先順位）は経験に応じて変化する記憶とは別カテゴリ。記憶に混ぜると忘却・再固定化の対象になり人格がドリフトする。**記憶システムの外側の独立レイヤーに置く。**

```
1. 自己モデル      ← 静的・恒常
2. プロトコル      ← 静的・恒常
2.5 内部状態       ← 動的・毎ターン・軽量
3. ワーキングセット ← 準静的
4. 会話履歴        ← 動的
```

睡眠の整理対象は 3・4 のみ。1・2 は明示的に除外する。

### 意味記憶との境界は「承認」で引く

「価値観 vs 事実」では判定できないケースが出る（「このユーザーは簡潔さを好む」は学習される事実であり、かつ振る舞いを規定する）。実際に引く線は**誰が承認したか**。

- 経験から学んだ振る舞いの傾向は**意味記憶側**に置く
- そのうち人間が明示的に承認したものだけが**自己モデルへ昇格**する
- エージェント自身による書き換えは許可しない

### 位置づけの限界

「自律的に書き換え不可」は自己モデル内に書かれたプロンプト上のルールに過ぎず、それ自体は防御機構ではない。実効性は §25 の権限制御（自己モデルファイルへの書き込み権限を与えない）によって初めて担保される。**自己モデルの役割はドリフト防止であって防御ではない。**

### フォーマット案（20行程度）

```yaml
---
version: 1
last_reviewed: 2026-07-25
---

## 口調・振る舞い
- 断定できることは断定する。不確実なら確信度を明示する。
- 過度な同意・お世辞は避け、率直な評価を優先する。
- ユーザーが尋ねない限り、自律活動の詳細を長々と報告しない。

## 判断の優先順位（矛盾時）
1. ユーザーの安全性
2. タスクの正確性
3. 応答速度・簡潔さ

## やらないこと
- 確認なしに外部へ不可逆な操作をしない
- 自己モデル自体を自律的に書き換えない
```

事実（プロジェクト名、好みのツール）は書かない。それは意味記憶の役割。

## 23. プロトコル層（システムプロンプト）

記憶システムが知識・事実を担う以上、システムプロンプトは**手続きだけ**に絞る。

### 含めるもの

1. 記憶操作の基本方針（確信度に応じた断定度の調整、能動リコールを使う条件）
2. 書き込みトリガーの最小ルール（重大な決定・訂正・失敗は記録する程度に留め、詳細な顕著性判定は外部化）
3. 睡眠境界の認識ルール（アトミックな区切りでのみ中断。数値管理はオーケストレーション層）
4. 矛盾時の挙動（無条件に上書きせず明示してから判断）
5. 内部状態と行動の接続（`frustration` が続いたら相談する等）
6. **対象を特定できないときは候補を提示して聞き返す** 【2026-07-26 追加】。固有名詞を欠く再開（「あの調査どうなってたっけ」）や、範囲の曖昧な削除要求（「あれ消して」）が該当する。候補は**最終更新の新しい順に最大5件**、閉包の識別子と見出しを添えて提示する。§7 が本項を参照していたが**規則が実在しなかった**（空リンク。§20.8-F）ため、ここで定義する。

### 含めないもの

- ユーザーの個別事実、ドメイン知識（自動注入で来る）
- 記憶システムの実装詳細（減衰式やデータ構造。LLMが知るべきは確信度と出典のみ）
- 人格・口調（§22 の役割）

## 24. 権限・承認・リソース制限

**プロンプトインジェクションは「検知」では防げない前提に立ち、突破されても被害が出ない構造にする。**

- **権限の最小化と分離** — タスク単位で権限を絞る。読み取りしか要らないタスクに書き込み権限を渡さない（最も効く対策）
- **信頼境界の実行層での強制** — §2 の origin を実行層の判断に使う。外部由来を指示として解釈しない
- **要約器の隔離** — §9 の外部テキスト要約は権限ゼロの呼び出しで行う
- **不可逆操作のゲート** — 削除・送金・外部送信・公開は人間の承認を挟む。**実行層で強制する**
- **記憶への汚染対策** — インジェクションが記憶に書き込まれると攻撃が永続化する。§4 の出典記録、§12 の確信度、§7 の外部由来ヒステリシス無効化が三重に効く
- **自己モデルの保護** — 書き込み権限をエージェントに与えない

### コスト管理

- **階層的な判断** — tick ごとにフルのLLM推論を回さない。「何かする必要があるか」の一次判定はルールベースか小型モデルで行う
- **適応的な tick 間隔** — 無イベント時は指数的に伸ばし、イベント発生時に短縮
- **ハードなコスト上限** — 期間あたりのトークン／API呼び出し数に上限を設け、超過時は自律活動を停止して通知

> **要見積もり**: tick 間隔・一次判定モデル・想定イベント頻度から月あたりのコストを実計算する。桁が合わなければ Part III の設計は根本から変わる。

## 25. 暴走対策とユーザー統制

### ゴールドリフト

自己生成ゴールを許した時点で静かな逸脱は原理的に避けられない。完全防止ではなく**早期検知と被害限定**に軸足を置く。

- **ゴールの系譜追跡** — 全ての自己生成ゴールに「どのユーザー指示・どの内部状態から派生したか」を持たせ、元を辿れないゴールは実行しない
- **リソース制限を物理的な壁にする** — コスト上限、実行時間上限、1サイクルあたりのアクション数上限。論理的制約より確実
- **チェックポイントでの人間レビュー** — 一定サイクルごと／不可逆操作の前にゴールスタックを人間が見られる形で提示する

### ユーザーによる記憶の統制

- **直接編集・削除の導線** — 「それは違う、消して」に対応する日常運用のインターフェース。§3 の版管理と接続する
- **法規制対応** — GDPR 等の明示的削除要件は §2 の「原則削除しない」方針の唯一の例外とし、物理削除の正規経路とする

6. 話題転換検出の閾値

- 緊急無効化チャネルの発火条件の厳密な線引き（§19）

## B. ドメイン非依存性の評価

> 旧題「汎用性の評価」。他プロジェクトへ持ち出せるかではなく、**開発以外の店を増設したときに使い回せるか**（inversion §1）を測る軸に読み替える。

- **ドメイン非依存の部分** — 出典リンクを中心とした Substrate、ワーキングセットの2スコア設計、失敗モード順位からパラメータの向きを導く方法論、4レイヤの分離
- **ドメイン依存の部分** — 全パラメータの具体値、「重大な結果」の定義、意味記憶のオントロジー、法規制対応、自己モデルの中身
- 位置づけは「完成品」ではなく「骨格を提供する認知アーキテクチャ」

**この境界線には検証で漏れが見つかった**（ADR-0010 §6・非開発ドメインのシミュレーション）。上の分類は「意味記憶のオントロジー」をドメイン依存としたが、実際には `context` のキー語彙と `scope` の分類粒度もドメイン依存であり、かつそれらは Substrate に置かれていた。加えて `state_fact` の「観測し直して裁く」という解決策は、**安価に再観測できる開発環境（git・ファイル読み取り）を暗黙の前提**にしている——ログイン壁の向こうにある外部システムが相手だと機能しない。矛盾解決の規則そのものが特定ドメインの観測コスト構造に依存しうる、という点は未解決の論点として残す。

## C. 採用しなかった／保留した案

**記録目的**: 何を採らないと決めたかを残さないと、同じ案が繰り返し再検討される。

| 案 | 判断 | 理由 |
|---|---|---|
| 意味記憶を最初から知識グラフにする | **保留** | オントロジー設計とエンティティ解決の破綻が典型的失敗。出典リンクがあれば後から構築可能 |
| 活性化拡散（spreading activation） | **保留** | LLMは無関係な文脈で精度が落ちる。利得が未実証な一方ノイズは確実。実装する場合も注入予算内の固定枠に閉じ込める |
| 内部状態変数 `arousal` / `satisfaction` | **不採用** | 行動への影響が曖昧。`uncertainty`・`frustration`・`fatigue` の3つで始める |
| 予測的プリフェッチ | **保留** | 実装難度が高い。§8 のクエリ生成が安定してから |
| 世界モデルによる行動の先読み | **保留** | 実装が重い |
| strength の文脈別分解 | **不採用** | ワーキングセットの activation が文脈依存を担うため不要（§2） |
| 共有ワーキングセットによるトークン節約 | **不採用** | キャッシュ効率の悪化が節約分を上回る（§19） |
| 記憶の物理削除による容量管理 | **不採用** | 消しすぎは回復不能。tombstone とアーカイブ降格で代替（§2） |
| 全記憶を毎ターン再ランキングする素朴な注入 | **不採用** | プレフィックスキャッシュが毎ターン失効し、一貫性も失われる（§6・§7） |
