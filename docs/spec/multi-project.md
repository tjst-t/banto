# Spec: マルチプロジェクト（単一窓口での並行開発）

複数リポジトリの並行開発を、一人のPOの単一窓口（1本の会話・1本の取次）に集約する仕組み。

設計原理：**ボトルネックはPOの時間と注意力のみであり、実行は希少資源ではない**。したがって、POの判断待ちは全プロジェクトで一元化し、実行はプロジェクト間・プロジェクト内とも依存が無い限り無制限に並行させる。

> **改訂 2026-08-07**（ADR-0009・ADR-0013 決定58・60・61）。単一窓口は Kobo ではなく**番頭**に
> なった（構造逆転）。判断待ちは Kobo 独自のキューではなく取次へ、台帳は Kobo ではなく
> 各Poolへ移っている。未実装のものには **（未実装）** と印を付けてある——
> 書いてあることを実装済みと読ませないため（P3）。

## 1. 責務の配置

### グローバル（横断で1つ）

改訂 2026-08-07（ADR-0013 決定58・60・61）。**「グローバル」＝「Koboに1つ」ではなくなった。**
判断待ちは番頭の取次へ、台帳は作った者（各Pool）へ移っている。

| 横断で1つのもの | どこが持つか |
|---|---|
| **判断待ちの列** | **番頭の取次**（`inbox.*`）。Kobo 独自のアテンションキューは作らない（決定58・inc-0025）。出所（Kobo・職人・検証環境・外の道具）を問わず同じ口へ積む |
| **職人の台帳** | **Worker Pool**（置き場ごとに1つ） |
| **環境台帳・quota** | **Environment Pool**（置き場ごとに1つ）。物理資源は共有なので、置き場を分けない（→ spec-environment §5） |
| **イベントログ** | Kobo。全イベントにプロジェクトタグを付与 |
| **ケイデンス/メタケイデンスのスケジューリング** | Kobo（**未実装**。→ spec-daemon-core §5） |

**台帳を Kobo に置かないのが要点。** 番頭は Kobo 無しでも職人を起こし環境を立てられる
（決定23・32c）ので、Kobo 側に台帳を持つと**同じものが2箇所で開かれる**——実際にそうなり、
Kobo の tick が番頭の立てたものを対象外にしていた（inc-0027）。持ち主は作った者に一本化し、
Kobo は写しを見て判定する（決定60）。**プロジェクトを跨いでも台帳は1つ**で、
projectTag は台帳の中の絞り込みであって置き場の分割ではない。

### プロジェクトごと（リポジトリに閉じる）
- **契約層のすべて**：vision / principles / roadmap / spec / ADR / タスク定義 / inbox / environments.yaml / skills。**統治の単位はプロジェクトであり、混ぜない**
- **Next / Laterの中身と順序**

### 対話セッションは横断してよい（ADR-0010 決定36）

かつてここには「**検討エージェント**：プロジェクトのworktreeで起動する対話セッション。横断させない」と書かれていた。ADR-0009 の構造逆転で対話の主体は番頭になり、番頭は複数プロジェクトを扱うため、この記述は成り立たなくなった（決定36i の改訂）。

**横断させないことで守ろうとしていた不変条件は2つある。どちらも別の手段で保たれる。**

1. **セッションが触れるファイルが、そのプロジェクトの外へ出ないこと。**
   → 対話の単位ではなく**場所（Place）の登録と範囲チェック**で保つ（決定36c・g）。番頭が触れるのは登録された場所の中だけで、判定はシンボリックリンクを解決した後に行う。書き込みはさらに、場所ごとにPOが明示的に許した範囲だけに限られる（決定38）。会話が1本か複数本かは、この判定に一切影響しない。
2. **どのプロジェクトの話をしているかが取り違えられないこと。**
   → 場所を**呼び出しごとに引数で明示**することで保つ（決定36f）。番頭に「いまどのプロジェクトか」という隠れ状態を持たせない。場所の名前がTool呼び出しとして画面に出るため、取り違えは長い絶対パスに埋もれる従来より**見えやすい**。

すなわち、守っていたのは*会話の境界*ではなく*作用の境界*であり、後者は会話の分割より直接的な手段で保証できる。POが1本の会話で「loamium の様子は？」「ついでに banto の docs を見て」と言えることは、単一窓口（本specの前提）とむしろ整合する。

**統治の単位がプロジェクトであることは変わらない。** 契約層は混ぜず、イベントログのプロジェクトタグもID空間（§2）もそのまま効く。変わったのは対話セッションが1プロジェクトに閉じるかどうかだけである。

番頭の**記憶**が跨ぐかは決着した（ADR-0003 追補 2026-08-10）。**人の記憶は跨ぐ／その仕事の記憶は跨がない**の二層は変わらず、**区画の単位が場所から「幹」へ移った**。幹＝プロジェクトの単位（PO裁定 2026-08-09）なので統治の単位とはずれないが、リポジトリと1対1ではない——複数のリポジトリにまたがる仕事も、まだリポジトリの無い相談も、幹1本として1つの区画を持つ。

### 共有資産（プロダクト既定＋プロジェクト差分）
Extension Pack、監査チェックリスト等の層A資産、および層B既定値は**プロダクト側の既定**とし、プロジェクトはオーバーライドのみを持つ。1プロジェクトでの改善が全プロジェクトに波及する（改善はまず既定側への提案として扱い、プロジェクト固有事情のみ差分に置く）。

## 2. ID空間と名前空間

- Koboは**プロジェクトレジストリ**を持つ（実装済み）。登録項目は `id` / `repoPath` /
  `profile` / `registeredAt` の4つだけ
- **登録する口は Tool**（`kobo.register_project`）。番頭も PO も同じ口を通る（決定25）
  ——REST（`POST /api/v1/projects`）は CLI と職人のために残っているが、番頭は任意の HTTP を
  叩く道具を持たないので、**手順書に REST を書くと実行できない**（2026-08-07 の PO報告）
- グローバルな参照は `<project>/<id>` 形式（例：`loamium/task-0042`）。リポジトリ内の相互参照は従来どおり `task-0042`
- イベントログ・台帳・環境リソース命名（taskIDプレフィックス）はすべてプロジェクト名を含む

## 3. 実行制御：数値WIPは持たない

実行を止めてよい理由は機械的に判定できる3つのみとし、**POの帯域を理由に実行を絞らない**：

1. **依存関係**：タスク定義の依存グラフ上、前段の成果が必要
2. **前提の未確定（実質依存）**：マージベースにレビュー未通過の祖先を持ち、かつ**スコープ（scope paths）が重なる**場合、spawnを保留する。escalateで前提が覆ると積んだ分が腐るため。スコープが重ならなければ並行してよい
3. **物理資源**：環境quota、APIコスト上限

プロジェクト間は定義上スコープが重ならないため、常に全並行。「プロジェクト間の優先配分」という概念は存在しない。

## 4. POの注意力の保護（実行制御の代わりに）

- **上流＝流入制御**：ローリング分解が実質のスロットル。Nextに積む量（＝レビュー可能な量）は検討セッションでPOが決める。蛇口は計画段階にある
- **下流＝順序制御**：全プロジェクトのレビュー待ちは**1本の取次**に並び、POが上から潰す（決定58）。プロジェクト優先度とは配分アルゴリズムではなく、この列のソート規則（手動並べ替え＋滞留日数）である
  - **一次受けは番頭**（決定57）。Kobo の判断待ちはまず番頭の会話へ返り、番頭が捌けないもの
    （PO必須の面・統治コード・本物のトレードオフ）だけが取次へ上がる。取次に並ぶ量は
    「レビュー待ちの総数」ではなく「**番頭が捌けなかった数**」——ここが実行制御の代わりに効く
- **可視化**：滞留日数と「このタスクの上に積まれている未spawnタスク数（ブロック影響度）」を表示（**未実装**）。注意力が最も効く場所へ自然に誘導する
- レビュー待ち行列の増加そのものは害ではない。害はレビュー品質の劣化であり、その根本対策は行列の制限ではなく検証の機構化によるレビュー必要性の縮小である（→ spec-improvement-loop §7）

## 5. 横断的な自己改善

- improvementの集計はプロジェクト別に加え**クラス別の横断集計**を行う。「同型incidentが複数プロジェクトで発生」は、プロダクト既定（共有資産）側の欠陥シグナルとして扱う
- メタケイデンスの成熟度メトリクス（origin比率等）は横断で算出する

## 6. UI

改訂 2026-08-07（→ spec-ui §1）。

- **取次**：横断1本（決定58）。判断待ちはここへ集まる
- **ボード**（`kobo.board`・実装済み）：Kobo のステートマシンのビューア。受け持ちの切替を持ち、
  受け持ちが空のときは**空の画面が登録を促す**（`kobo.register_project`）。**閲覧専用**
- **レビュー面**（`kobo.review`・実装済み）：判断待ちの1件を決める面
- バックログGUI：プロジェクト切替＋「横断Nextビュー」（**未実装**。いまはタスク定義ファイルを
  番頭が `file.write` で書く）

## 7. 実装戦略

**設計は初日から、実装は1プロジェクトから**。

- 初日から入れる（後付けが高い）：ID名前空間、プロジェクトレジストリ、イベントログのプロジェクトタグ
- 2つ目のプロジェクトを載せる日まで作らない：横断ビュー、横断集計、共有資産のオーバーライド機構
