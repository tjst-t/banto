## なぜ分離したか

`spec-memory` §0 は「目的・スコープ・設計原理」という見出しの下に **285行**を抱え、うち **174行（61%）が §0.3 系＝API・不変条件・実行層の規則**だった。これは目的でもスコープでも原理でもなく、**文書中で最も参照される規範そのもの**である。とくに §0.3.0（書き込み経路の不変条件 I1〜I11）は、全ての書き込み経路が通ることを要求される唯一の関所でありながら、「はじめに」の中に埋まっていた。

**結合の向きが一方向であることが、ここを切ってよい根拠である。** 契約層は全体から参照されるが、自分からはほとんど参照しない。逆に §7↔§8.5↔§9（ワーキングセット・検索・解像度）や §12↔§20.4（矛盾検出・再検証）は相互参照が密で、切ると壊れる。

### 0.3 モジュール間インターフェース

**memory が提供する操作**

```
build_context(query_seed, budget) → 組み立て済みコンテキスト
assemble_brief(task, budget)      → 職人向けブリーフ（構造化。§0.3.1）
record(event, origin, session_id, attrs) → エピソードへ追記
                                    attrs = { scope, asserted_by, subject,
                                              external_ref?, derived_from?, sensitive? }
propose(entry)                    → semantic / procedural の候補を睡眠キューへ積む
supersede(entry_id, new_entry, origin) → 版を作る（§3）。origin 優先はここで強制する
recall(query, n)                  → 能動的検索（明示リコール用）。件数は呼び出し側が指定する（§8.5.7）
retrieve(req)                     → { ranked[], clarify?, trace }
                                    候補生成の唯一の入口（§8.5）。上の3つの組み立て操作は
                                    **必ずこれを通す**。自前で候補を集めることを禁じる
resolve_entities(text)            → 表記 → 閉包ID／主体ID／エントリID（§8.5.1）
alias(surface, target_id, origin) → エイリアス表への書き込み（§8.5.1）。origin 優先はここで強制する
reindex(target, arm)              → 索引の再構築。target = 閉包識別子 | all、arm = A1|A2|A3|A4|A5|all
                                    呼ぶのは Steward Driver のみ（§20.7.1「索引の再構築」の行）

export(selector)                  → エクスポート成果物を作る（§24 の承認ゲートを通す）。渡す集合の
                                    derived_from 閉包を計算し、閉包の外を指す参照を external_ref へ
                                    書き換える（ADR-0010 §10）。**ストアを書き換えない**
import_entries(artifact, scope_map) → 受け取り側へ取り込む。**これがエントリを生成する経路**（下記の一覧）
                                    scope_map は閉包識別子の写像。PO が決める（§26.3 と同じ理由）

create_closure(id, parent, display_name)  ┐
rename_closure(id, display_name)          │ 閉包レジストリの操作（§26.3）。
reparent_closure(id, new_parent)          │ すべて origin: user_explicit を要求し、
fold_closure(id)                          │ レジストリ・entity_index・シャード台帳の
merge_closure(from_id, into_id)           ┘ 3箇所へ伝播する。番頭は提案のみ
pin(item) / unpin(item)           → 訂正等の保護（§7）
compact()                         → マイクロスリープ（§18）
consolidate(depth)                → 浅い／深い睡眠（§18）
dependents(entry_id, depth)       → derived_from の逆引き（driver が再検証キューを積む、§20.4）
changes_since(cursor)             → supersede / tombstone / 新規確定 の変更ストリーム
collision_candidates(entry_id)    → 既存の意味記憶との衝突候補（ルールベース、§12・§20.4）
```

`record()` の `attrs` は ADR-0010 で確定した Substrate に対応する。`scope` は必須（可視範囲は既定に頼らず常に明示する）。**`asserted_by` と `subject` も必須である** 【2026-07-26 追加・R6c】——I7 と I10 が「必ず埋める」と要求しているのに、**初版の `attrs` にはどちらも無く、渡す経路が存在しなかった**。不変条件を書いて入力口を作り忘れる、という §20.0 の典型例である。`derived_from` を渡せるのは、ADR-0010 §1.2 が要求する「職人の報告を引用エントリと結論エントリに**分割して記録**し、結論から引用へリンクする」を実現するため——初版の `attrs` にこれが無く、**規約が公開 API で表現できない**状態だった。

**`propose()` と `supersede()` は 2026-07-26 の追加。** 初版は `record()`（episode 追記）と `consolidate()`（睡眠バッチ）しか無く、**意味記憶の版を作る操作が公開 API に存在しなかった**。そのため ADR-0010 §1.3 が「書き込み経路の実行層で強制する」と定めた origin 優先は、強制をかける入口自体が無かった。`supersede()` がその唯一の入口である。

- `supersede()` は **`origin` 優先を実行層で強制する**：対象の最新版が `origin: user_explicit` のとき、`agent_inferred` / `external` からの呼び出しは**拒否**する（ADR-0010 §1.3）。プロンプトの記述に委ねない。
- セッションからの並行 `supersede()` は許す。§19 の層別の並行性に従い、意味記憶の競合は版管理で**検出可能な矛盾**に還元される。単一 writer を要するのは深い睡眠だけである。

`dependents()` / `changes_since()` / `collision_candidates()` は **driver が点火と再検証を組み立てるための読み取り口**である。memory はこれらを提供するが、それを見ていつ動くかは決めない（§0.2 の唯一の規律）。

**memory が公開する状態シグナル（読み取り専用）**

```
context_pressure       コンテキスト圧力 → driver の fatigue の入力
mean_confidence        注入中の記憶の確信度平均 → uncertainty の入力
unresolved_conflicts   未解決の矛盾件数
```

**driver が提供するもの**

```
goal_stack        現在のゴール（§11 の目標関連性、§7 のピン留めに使用）
exec_context      リポジトリ・作業モード等（§11 の文脈一致度に使用）
turn_boundary     ターンの区切り通知
```

**memory はシグナルを公開するが、それに基づいて自ら行動しない。** 睡眠の閾値判定（§18）は driver 側に置く。

### 0.3.0 書き込み経路の不変条件 【2026-07-26 追加・最重要】

**エントリを生成するすべての経路に、同じ不変条件（I1〜I11）を適用する。** 対象は `record()`（episode）・`propose()`（候補）・`supersede()`（新版）・深い睡眠の蒸留とチャンキング（§14）——**例外なく全部**。

R4 の検証は、同じ形の欠陥を6件見つけた：**規則を1つの層にだけ書き、上下の層に配線し忘れる**。`origin` の強制は `record()` にだけ書いたので蒸留層で失われ（R4／S10）、`sensitive` の継承も同様の穴を持つ。経路ごとに規則を書く限り、経路が増えるたびに漏れる。**経路の数だけ書くのをやめ、不変条件として1箇所に置く。**

| # | 不変条件 | 破れたときの帰結 |
|---|---|---|
| I1 | **`derived_from` に `origin: external` が1件でもあれば、生成されるエントリの `origin` を無条件に `external` へ強制する** | 蒸留が trust laundering になる（§7 ヒステリシス無効化・§9 レンダリング・§12 確信度減点は**エントリ自身の `origin` しか見ない**ため、一度 `agent_inferred` になると三重防御が丸ごと迂回される） |
| I2 | **`derived_from` に `sensitive: true` が1件でもあれば継承する。**落とせるのは `origin: user_explicit` の判断のみ | 理由を tombstone しても、機微フラグの無い結論だけが生き残る |
| I3 | **`authored_by` に現在の実行系の識別子を必ず入れる**（ADR-0010 §7） | 世代をまたいだ較正の断絶が検出不能になる |
| I4 | **`scope` は必須。閉包レジストリに実在しない識別子を拒否する。** さらに**状態が `active` でない閉包（`folded`／`merged`）への新規書き込みを拒否する**（§26.2）。`merged` はエイリアス解決で新識別子へ写してから判定する | 可視範囲が既定に落ちる。畳んだ閉包に書き足せると、畳んだこと自体が意味を失う |
| I5 | **`content` の書き分けを検証する**：`headline` は結論のみ、理由は `summary` 以降 | `assemble_brief()` の headline-only 絞り込みが無効化される |
| I6 | 違反は失敗として扱い、握りつぶさない（I2 原則） | — |
| I7 | **`subject[]` を必ず埋める**（ADR-0010 §8）。`derived_from` を持つ場合は既定で和集合を継承する | 「誰についての記憶か」が自由文にしか無いと、可視範囲・機微性・引き継ぎの3つがすべて解釈に落ちる（R4／S9・S12・S16） |
| I8 | **索引を同一トランザクションで更新する**（§8.5.6）。対象は **A1・A2・A4・A5 の索引と `entity_index`**（`subject[]`・`external_ref`・`headline` 抽出語・`scope`）。**A3（埋め込み索引）だけは遅延更新を許す**（下記） | 書き込めたが検索に出ない記憶が生まれる。エントリは存在するのに `retrieve()` が返さないため、**見逃しが「記憶していない」と区別できなくなる**（§16 の見逃し率が測れない） |
| I9 | **`scope` は `derived_from` の閉包の最小共通祖先を超えられない。** 超える `scope` を設定するには §12 の B1〜B6 を通し、通らなければ最小共通祖先に留める。`derived_from` が空のエントリは、そのセッションの `closure_ctx` を超えられない | **可視範囲の拡大が、B1〜B5 の管轄外の経路から無審査で起きる**（R6／S12）。B1〜B5 は深い睡眠の蒸留だけを見ており、`person` 水準のセッションで番頭が複数ドメインの材料から結論を書くと、**一度の `record()` で `scope: person` を獲得して恒久化する**。§8.5.4 の横断ファンアウトはこの経路を実際に到達可能にするので、放置できない |
| I10 | **`asserted_by[]` を必ず埋める**（ADR-0010 §9）。値は `entity_index`（§8.5.1）で正規化する。**人格主体を指す名前空間（`self:*` / `party:*`）のみを許し、それ以外（`repo:*`・`proj:*`・`dom:*` 等）を拒否する。** `derived_from` を持つ場合は和集合を継承。持たない一次エントリの既定は `origin` から決まる：`user_explicit` → 発話者（単数 PO 体制では `self:po`）／`agent_inferred` → `self:banto`／`external` → `external_ref` の `system` を `party:` 名前空間へ写した識別子（不明なら `party:unknown`） | **`origin` が「誰の言明か」を保持していない。** `origin: user_explicit` が2人以上を指しうる体制では、**一方の言明が他方の方針を上書きしても、上書きされた側が誰だったか記録が残らない**（R6／S18）。`session_id` は「どのセッションか」、`authored_by` は「どの実行系が書いたか」、`subject[]` は「誰**について**か」であり、いずれも代用にならない |
| I11 | **深い睡眠 Phase 1 の writer は、自分の閉包に `scope` を持つエントリ以外に新版を作れない**（§18.1 決定1）。`supersede()` の実行層で強制する | 閉包ごとに並行する Phase 1 が互いのエントリに新版を作ると、§3 の版が無用に分岐する。**I9 は新規エントリの `scope` の上限を定めるだけで、これを禁じていない**（R7／B2） |

#### 派生エントリのフィールド合成規則

**蒸留・昇格・統合が新しいエントリを作るとき、各フィールドを誰がどう決めるかが未定義だった。** R1・R3・R4 で繰り返し指摘された（例：出典の `origin` が `user_explicit`×2 と `agent_inferred`×1 で混在するとき、生成物の `origin` は何か）。I1〜I11 は継承の向きを決めるが、**継承では決まらないフィールド**が残る。ここで埋める。

| フィールド | 合成規則 |
|---|---|
| `origin` | I1 が最優先（`external` があれば `external`）。次に **`user_explicit` が1件でもあれば `user_explicit`**。どちらも無ければ `agent_inferred`。§0.8「迷ったら下げる」とは逆に見えるが、`origin` は信頼度ではなく**出所**であり、PO の言明を含む以上それは残す |
| `sensitive` | I2（1件でもあれば継承） |
| `subject[]` | I7（和集合） |
| `authored_by` | I3（**継承しない**。合成した実行系を入れる。出典の世代は `derived_from` を辿れば分かる） |
| `asserted_by[]` | I10（**和集合**）。`authored_by` と逆であることに注意——`authored_by` は「誰が書いたか」なので合成時に置き換わるが、`asserted_by` は「誰の言明に基づくか」なので**失うと復元できない**。スカラーにしなかったのはこのため（複数主体の言明を1件に畳むとき、その場で不可逆に捨てることになる） |
| `scope` | **出典の閉包の最小共通祖先**。ただし異なるドメインの出典から `person` へ上がる場合は §12 の「閉包をまたぐ一般化」の規則に従う（既定では上げない） |
| `fact_type` | 出典が同一なら継承。混在する場合は**生成しない**（分割して別エントリにする）。混合言明を1エントリに畳むと、状態の部分が陳腐化の検証に乗らない（R4／S9） |
| `strength` | **継承しない。** 新規エントリの既定値から始める。`strength` は想起履歴の要約であり（§13）、派生物にはまだ履歴が無い |
| `salience` | 合成した実行系が付ける。ただし**出典の最大値を上限とする**（蒸留を重ねるだけで顕著性が上がる経路を塞ぐ）。世代の別は `authored_by`（I3）で分かる |
| `valid_from` | 出典の最も古い `valid_from`。`created_at` は合成時刻 |
| `valid_until` | null（新しい版が作られたときに埋める。§3） |

#### 対象経路の一覧（これが検査可能性の要）

**表を作っただけでは足りない。「どの経路が表を通るか」を列挙しないと、経路側に書き忘れる。** 初版は `record()` にだけ「§0.3.0 を通す」と書き、`propose()`・`supersede()`・蒸留には書かなかった——**不変条件表そのものが、防ごうとした欠陥を一段上で再現していた**（R5 配線チェック）。

| 経路 | 節 | I1〜I11 を通すか |
|---|---|---|
| `record()` | §0.3.1 | **通す** |
| `propose()` | §0.3・§14 | **通す** |
| `supersede()` | §0.3・§3 | **通す** |
| 深い睡眠の蒸留・昇格・統合 | §14 | **通す**（生成物は `propose()` を経由すること） |
| チャンキング（手続き記憶の生成） | §14 | **通す** |
| tombstone の新版作成 | §3 | **通す** |
| **`import_entries()`（取り込み）** | §4・ADR-0010 §10 | **通す。ただし I3・I10 は継承する**（下記の例外） |
| 閉包レジストリの操作（`entity_index`・シャード台帳への伝播） | §26.3 | **I8 のみ**（エントリを生成しないため他は非該当） |

**`export()` は本一覧に載らない。** エクスポートは成果物を作る操作でストアを書き換えないため、エントリを生成する経路ではない。**書き込みが起きるのは受け取り側の `import_entries()` である。**

**`import_entries()` の例外（唯一の例外。ここ以外に例外を作らない）** 【2026-07-26・R7b】：

| 不変条件 | 取り込み時の扱い | 理由 |
|---|---|---|
| **I3**（`authored_by` に現在の実行系を入れる） | **継承する**（元の値を保つ） | 移送は新しい著者を作らない。現在の実行系を入れると、**そのエントリの `salience`/`strength` を実際に付けたモデルが分からなくなり、`authored_by` を Substrate に置いた唯一の目的が消える**（ADR-0010 §7） |
| **I10**（`asserted_by[]`） | **継承する** | 誰の言明かは移送で変わらない（ADR-0010 §10 の受け取り側の表） |
| I4（`scope` の実在） | **`scope_map` で写してから判定する** | 受け取り側に同じ閉包識別子が無ければ I4 違反になる |
| I1・I2・I5・I7・I8・I9 | 通常どおり | — |

**初版は `export()` を「I1〜I11 を通す」と書いており、ADR-0010 §10 の「`authored_by`・`asserted_by` はそのまま」と正面から矛盾していた**（R7b）。書き込みが起きる主体を取り違えたことと、例外を書かなかったことの2つの誤りが重なっていた。

**規律**：エントリを生成する操作を新設したら、**この一覧に行を足す**。一覧に無い操作は仕様違反とみなす（検証プロトコル §2.4 の検査項目2）。個別の操作の節では**再掲せず本表を参照する**——再掲すると経路ごとに書く形へ戻る。

**この表が唯一の正典である。**

### 0.3.1 規律を実行層に落とす 【2026-07-26 追加】

再検証（R2）で、**散文で書いた規律はすべて素通りした**ことが分かった。`sensitive` の取り扱い、`citations` の検証、`derived_from` の記入義務——どれも「そうする」と書いてあるだけで、そうさせる場所が無かった。以下でそれぞれの落ちる先を決める。

#### `assemble_brief()` — 職人への発注を構造化する

**職人への指示文が自由記述である限り、そこにゲートは置けない。** `build_context()` は番頭自身のセッション用であり、職人向けブリーフはこのパイプラインを通っていなかった。番頭（LLM）がその場で作文するので、機微情報を除く規律も、根拠リンクを残す規律も、守られたかどうかすら分からない。

構造化した組み立て操作を置く。職人への発注は**必ずこれを通す**。

```
assemble_brief(task, budget) → {
    brief,              # 職人に渡すテキスト
    included_refs[]     # 同梱した記憶ID（監査と derived_from の材料）
}
```

- **`sensitive: true` のエントリは `content.headline`（確定した制約の結論）だけを載せ、`summary` / `full`（理由）は載せない。** 機械的に落とす。ADR-0010 §5 の「職人への指示文に理由を含めない」は、ここで実行層の規則になる。
- 職人は Quirefold を装着しないため（inversion §11.1）、**ブリーフに載らなかったものは職人に一切届かない**。何を載せたかが `included_refs` で残るので、事後に監査できる。
- **`task` 引数も検査対象にする** 【2026-07-26 追加】。初版は記憶の注入経路（`included_refs`）だけを構造化し、**呼び出し側が作文する `task` 文字列を自由記述のまま残していた**。番頭が `task` に理由を直接書けば解像度の絞り込みは無意味になる——「自由記述にはゲートを置けない」という診断を、一段上の入力で再現していた（R3）。対処：**呼び出し元セッション（＝ブリーフを作っている番頭自身のセッション）の直近ターンで `sensitive` エントリが滞在枠に載っていた場合、`task` の生成を権限を縮小した別呼び出しに切り出す**（§9 の要約器隔離と同型）。

**判定対象を呼び出し元セッションに明記した** 【2026-07-26・R6／S9】。初版は「ワーキングセットに滞在していた場合」とだけ書いていたが、`assemble_brief()` の候補パイプラインと `build_context()` のワーキングセットは**別の状態である**（§8.5.7）。どちらを見るのかが書かれていないと、ブリーフ側を見る読み方では**発火条件が構造的に成立せず、規則が死ぬ**。見るべきは番頭自身のセッションの滞在状態である——理由を `task` に書いてしまう主体はそちらだからである。
- **`content` の書き分けを強制する**：`headline` は結論のみ、理由は `summary` 以降に置く。`headline` に理由まで書けば headline-only の絞り込みが無効になるため、この規約は `record()` の書き込み時に検査する。

#### `record()` の書き込み前バリデーション（ルールベース）

**§0.3.0 の不変条件（I1〜I11）を通す。** それに加えて `record()` 固有のものが1つある。判定はすべて機械的な事実に基づき、LLM を使わない（§20.0）。

1. **`citations` 空振りの検出**：由来が `worker_result` であり、その職人の**ツールログに外部取得（Web・外部API）が含まれる**のに、`derived_from` に `origin: external` の引用エントリが1件も無い場合は拒否する。ADR-0010 §1.2 が「ルールベースで弾ける」と述べながら**弾く場所を指定していなかった**ものを、ここに置く。

これ以外は §0.3.0 の I1〜I11 に従う。**ここに再掲しない**——再掲すると経路ごとに書く形に戻り、次の経路で漏れる。初版は `scope` の実在検査（I4）を番号付きで再掲しており、**「再掲しない」と書いた行の直上で自ら再掲していた**（R6 配線チェック W19）。

これが成立する前提として、**Worker Pool は `worker_result` に職人が呼んだツールの一覧を必ず含める**（§20.2 の契約に追加）。ツールログは機械的な事実であり、職人の自己申告ではない。

#### `derived_from` の自動付記

**番頭の律義さに頼らない。** そのターンで `build_context()` / `assemble_brief()` が実際に載せた記憶IDを、ハーネスが `record()` の `derived_from` 候補として機械的に渡す。

- **注入された ≠ 実際に使った**ので、これは過剰にリンクを張る。承知の上で**過剰側に倒す**——§0.8 の重み付け（見逃しコスト ＞ ノイズコスト）に従う。出典が多すぎるのは確信度の計算で調整できるが、出典が無いエントリは後から復元できない。
- これは §0.9 の最優先課題「参照検出の信頼性」の**書き込み側の答え**でもある。何が使われたかは分からないが、**何が載っていたかは機械的に分かる**。

### 0.3.2 ハーネスとの関係

memory は「記憶ストア」ではなく**プロンプトを組み立てる側**である。ワーキングセット・予算配分・プレフィックスの並び順まで管轄するため、**既存ハーネスに後付けできる部品にはならない**。ハーネス側がコンテキスト組み立てを丸ごと委譲する必要がある。

これが決定②（inversion §13）で **Banto ハーネスを自作**と決めた理由そのものである。既製ハーネス（pi 等）のループ・履歴管理と二重化して衝突するため、Quirefold を積むハーネスは自作し、LLM プロバイダはアダプタで差し替える。

**Banto 側の要件と本書の対応**

| Banto の要件 | 対応 |
|---|---|
| 「いまどう？」で文脈を読んで現状を返す | §8（ワーキングセットが現在の話題の最良の要約でもある） |
| 実装エージェント→設計エージェントへの引き継ぎ | §19（並行セッション・スナップショット隔離） |
| オーケストレータが実行者をスポーンし並行開発 | §19 |
| ADR の作成と参照 | §4（出典リンク付きの意思決定＝意味記憶の実体） |
| Skill の自己改善ループ | §14（チャンキングによる手続き記憶への昇格） |

**ADR が意味記憶の中心になる。** コーディング文脈における意味記憶は「世界の事実」ではなく**決定と制約**であり、ADR は「なぜそう決めたか」を出典付きで残す形式そのものである。§12 の `fact_type` は `preference_decision` が支配的になる。

### 0.3.3 規律: Substrate に開発固有の語彙を入れない

かつて本書は「banto はホストであって共同設計者ではない／banto の都合で Substrate を曲げない」という規律を置いていた。Quirefold を banto の一部と位置づけた以上、この文言（外部プロジェクトへの一方向依存）は失効する。**ただし規律そのものは残す。理由が変わるだけである。**

新しい理由は inversion §1 にある——**番頭の核（記憶・会話・差配）を開発固有の道具（タスクモデル・コードレビュー・Environments）から分離して設計すれば、将来 別領域も同じ番頭に載る**。開発は「第一の店」にすぎない。したがって：

- **Substrate（Part I）に開発固有の語彙・前提を入れない。** 入れた時点で、番頭はコーディング専用になり、拡張性が構造から失われる。
- **Policy 層（Part II）はコーディング向けに調整してよい。** 可逆であるため。
- 判定は「外部プロジェクトの都合を守れているか」ではなく「**開発以外の店を増設したときに、この決定が邪魔をしないか**」で行う。

**この規律は実際に破られていた。** 10シナリオ検証（ADR-0010 §6）で、非開発ドメイン（家計）のシミュレーションが Substrate 内の開発語彙を検出した——`context.project` は Kobo のプロジェクト概念に暗黙に紐づき、`context.repo` は非開発ドメインで恒久的に無意味、`scope` の2値（person / project）は「プロジェクトではない継続的な生活領域」を表現できない。ADR-0010 第2版でこれを是正し、`scope` を閉包識別子に、`context` の他キーを任意の検索用特徴量に降格した。
