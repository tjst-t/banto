# Spec: UI（POコックピット）

POの操作面全体（Web GUI・CLI・会話の対話規約）の仕様。

> **tmux は使わない**（改訂 2026-08-07・ADR-0013 決定59）。当初は「POは tmux アタッチで
> エージェントの進行を目視する」と書いていたが、**面はブラウザに一本化した**——職人を覗くのは
> セッションビューア、検証環境は公開URL。以下に残る「tmux」の語は会話の再開の話（§4）で、
> **番頭との会話そのもの**を指す。

第一原理：**「いま自分の判断を待っているものは何か」**。UIはPOの注意力（レビュー帯域）の配分装置として設計する。第二原理として、**POの頭は判断だけに使う。操作の記憶と文脈の記憶はシステムが持つ**（→ D7, D8）。

## 1. 画面構成

改訂 2026-08-09（ADR-0017 決定77・79・80）。**主役は会話**——PO は番頭と話して店を
動かし、面は番頭が差し出すか、PO が自分で開く（決定17）。

### 1.1 骨格：レールと続き間

```
レール    横断の通知 ／ 幹 ／ 抱えているものの点 ／ 履歴・設定・明暗   （狭いと上端の帯）
続き間    [背表紙] 幹（地）→ 枝（その上の紙）→ 作業する面（さらに上）
```

**幹・枝・面は重なりで表す。** 広い画面で横に並んでいても関係は重なりのままで、
狭い画面（760px 以下）の重ねと同じ模型になる——狭いときは幹が地、枝と面は下から上がる紙で、
上端に幹が覗く。

- **会話はプロジェクトごとに幹1本。永続で、畳めない。会話のタブは作らない**（決定77）
- **枝は「還す条件」を持って生まれる。** 何が決まれば幹に還るかを書けないものは枝にしない
  （幹で話す）。**番頭の判断でも PO の指示でも開き、開いた理由を札に必ず書く**
- **幹に載るのは、開いた1行と還った1行だけ。** 枝の中身は幹に流さない——これで幹は
  プロジェクトの意思決定の帯として端から端まで読める
- **深さは1段。** 枝の中に枝を作らない。枝が別の枝を要するなら、畳んで幹へ還してから開き直す
- **埋没しない不変条件**：開いている枝は必ず **①幹の札 ②横断の通知 ③レールの点** の
  どれかに出ている。**どこにも出ていない枝は作れない**（§2 の「現れる場所のない操作は
  追加できない」と同じ形）。加えて、**黙って止まった枝は機構の異常として扱い**（P6）、
  滞留を検出したら取次へ積む
- **作業する面を開くと、いま居た会話は細い帯（既定 344px・260〜620px）として残る**
  （決定79）。そこで読むのではなく、**話しかけるための幅**。幅はつまんで変えられる
- **面はどこから開いたかを覚える**——面は会話ごとのキャンバスに載る（決定2）ので、
  幹から開けば枝は視界から外れ、枝から開けば枝が細い帯として左に残る

### 1.2 面の一覧

1. **取次**（レールの受け口）：**判断待ちの列はここ1本**。Kobo 独自のアテンションキューは
   作らない（決定58）——出所（Kobo・職人・検証環境・番頭自身・外の道具）を問わず、
   POに用があるものは同じ口へ積まれる。**常に見えているのはレールのボタンと数字だけ**で、
   開くまで画面を取らない。一通は §3 の三部構成（経緯／起きたこと／求める判断）
   - **判断待ちは会話にも出るが、常設しない**（決定80）。番頭が判断を求めたなら、それは
     会話の最新の発言なので、放っておいても一番下にある。**遡ったときだけ**↓ボタンが
     朱になり「判断待ち N」と言う。**読みと入力の間に常設はひとつも無い**
2. **ボード**（`kobo.board`）：Kobo のステートマシンをそのまま描くビューア。列（待ち／
   着手できる／動いている／判断待ち／マージ／止まっている／終わった）は**状態の集約**で
   あって独立した状態ではない（→ spec-daemon-core §1）。UI側に独自状態を持たせない（D3・D5）。
   **閲覧専用**——承認は3のレビュー面で行う（一覧から押せると、経緯を読まずに通せてしまう）
3. **レビュー面**（`kobo.review`）：判断待ちの1件を決めるための面。経緯・変更の範囲・
   受け入れ基準・監査の判定が揃い、**触れる環境があれば開ける**（決定59）。
   `po` と機械的に判定されたものは**通すボタンが出ない**（決定57）
4. **ドリルダウン**：職人ビューア（`worker.viewer`）でセッションの中身を覗く。
   **tmux は使わない**（決定18・59）——プロセスに割り込まず、セッションJSONLの末尾を読む
5. **バックログ編集**：タスク定義ファイルの編集。**番頭が書く**（`file.write`）のが既定で、
   独自DBは持たない。積むのは `kobo.enqueue`
6. **共有ブラウザペイン**（v1.x）：レビュー環境の Chromium を CDP 画像転送で表示。
   いまは検証環境の公開URLをブラウザ面で開く形（決定59）で足りている

**v1 の範囲**：取次・ボード・レビュー面・職人ビューア（いずれも実装済み）。
健康状態での絞り込みと nudge / handoff は v1.x（→ spec-daemon-core §3）。

### 1.3 器：Tool の戻り値は会話の中に埋まる

**読む面は器、作業する面は間**（決定79）。事実が数行で足りるもの（差分の抜粋・記憶・
職人の手元）は**器として会話の中に**出し、列を食わない。列が生えるのは
「探す・移動する・比べる」＝**幅が要る作業**のときだけ。

判定は1つに畳める：**「見比べる作業」は面、「判断に要る事実」は膳。**
器の語彙と規約は `spec-canvas-ui` §11。

## 2. 文脈アクション面（D7の実装）

コマンドは機械の契約（エージェント⇔Kobo間の語彙）であり、**人間の入口は文脈が提示する選択肢**とする。人間がコマンド名・skill名を記憶する必要がある設計を禁止する。

提示面は3つ。**すべての操作はいずれかの面に現れなければならず、現れる場所のない操作は追加できない**（動詞増殖へのブレーキを兼ねる）：

1. **カードのボタン**：カード種別ごとに有効なアクションをボタン化（レビュー待ち→「レビュー開始」、評価カード→「keep / tune / revert」、ケイデンス議題→「承認／差し戻し／後で」等）
2. **セッション内の番号付き選択肢**：判断の分岐点で、エージェントが選択肢を番号付きで提示する（各役割のシステムプロンプト規約＝層A）。POは番号または自由文で応答する
3. **セッションフッター**：Extensionが現フェーズの有効操作を常時表示する

### 選択肢はショートカットであり、入力形式ではない
- 選択肢の提示中も、自由な会話（質問・相談・選択肢外の指示）を常に受け付ける
- 相談への回答後、エージェントは選択肢を**再掲して分岐点に戻る**。相談の結果に応じて選択肢を再構成してよい
- GUIの全判断ポイントに「相談する」を常設する：押すと当該カードのコンテキスト（タスク定義・差分・評価データ等）を注入したセッションが開き、会話後に判断へ戻れる。**どの判断ポイントからもワンアクションで会話に降りられる**

### skillの文脈起動
skillは人間が名前で召喚するものではなく、フェーズ・タスク種別・ファイル種別からエージェントが自動で引く。人間側にskillの語彙の記憶を要求した時点で設計違反とみなす。

## 3. カードの解剖学（D8の実装）

すべての判断要求（カード・通知）は次の3部構成を必須とする。**画面を遡らずカード単体で判断できること**：

| 部 | 内容 |
|---|---|
| **経緯** | 起点となったPOの指示の引用（発言時刻・発生場所へのリンク付き） |
| **起きたこと** | その後の経過の要約（実行・判明した事実） |
| **求める判断** | 問いと選択肢（ボタンまたは番号付き） |

- 実装規約:Koboのイベントには「起点となったPOの入力への参照」を必ず紐付ける。会話・操作はすべてイベントログを通るため、参照は機械的に解決できる
- 経緯の引用が存在しないカード（システム起点のもの：ケイデンス、照合検出等）は、起点を「生成規則」として明示する（例：「TTL超過検出により生成」）

### 3.1 同じ理由の知らせは束ねる（realign 第2便）

**通数が増えると読まれなくなり、知らせないのと同じになる。** 実測で、同種の知らせ35件が35回届いた事例がある。

- **同じ理由・同じ宛先の知らせは1通にまとめる。** 中身は消さず、1通の中に並べる（長く止まっているものが上）。最初の適用先は滞留の知らせ（`task_stalled`。→ spec-daemon-core §5.1）
- **束ねてよいのは「同じことが並んでいるだけ」のもの**に限る。「止まった」「落ちた」は1件ずつ理由が違うので1通ずつのまま——束ねると3部構成が書けなくなる
- **束ねた知らせにも3部構成を守る。** 「求める判断」には、**降ろす道を含めて**次の手を名指しする（`kobo.reopen` / `kobo.approve` / `kobo.send_back` / `kobo.settle`）
- 機構の側で**同じ状態のあいだ一度しか鳴らない**なら、そのことを文面に書く。読み手が「鳴り続けているのか、一度きりなのか」を区別できないと、待てばよいのかを判断できない

## 4. セッション復帰リキャップ（D8の実装）

会話（Web GUI のスレッド）で、POの前回入力から一定時間（層Bパラメータ、既定10分）経過後の
再開時、番頭が自動でリキャップを挿入する：

```
── 42分ぶりです。あなたの最後の指示:「…」／その後: 修正2件完了、1件が判断待ち ──
```

- 中断検出は時刻差のみの機械処理。要約はstatus_reporter（安価モデル）を流用する

## 5. CLI

- CLIはGUIと同一のKobo APIのクライアント。GUIで可能な判断系操作のサブセットを提供する
- CLIにおいてもD7を適用する：引数を記憶させず、対話的選択（現在有効な対象の列挙から選ぶ）を既定とする

## 6. 通知

アテンションカードの生成をプッシュ通知（携帯到達可能なチャネル。ntfy等）で通知する。アテンションキューは「開けば分かる」が「開くきっかけ」を通知が担う（→ research-orchestrator-survey C）。

- 通知文は「経緯1行＋カード種別」とし（→ D8）、通知からカードへ直接遷移できること
- 通知対象はカード生成イベントのみ（blocking発生、レビュー待ち、failed、評価カード、定期レビュー）
- 通知対象・チャネル・静穏時間は層B設定（`meta/config.yaml`）

## 7. 未決事項

- カードのソート規則の重み（滞留日数×ブロック影響度）の初期値
- リキャップ閾値の既定値の妥当性
- 共有ブラウザペインの要素指差し（DOM参照送信）機能の仕様（v2以降）
