# Spec: 自己改善ループ（Improvement Loop）

システム自身の欠陥・改善点を発見し、仮説付きで改善を実装し、効果を評価して定着または差し戻す仕組み。claude-skillsの「Skillの見直し自体もSkillに入れる」思想の構造化版。

到達目標：POは「最後のセンサー」として残るが、**同じクラスの問題を二度指摘しなくて済む**状態を維持する。レビュー必要性の縮小は目標として掲げるものではなく、検証の機構化の結果として得る（→ §7）。

> **改訂 2026-08-07**（ADR-0009・ADR-0013、task-0067）。**このループはまだほとんど回っていない。**
> 層A/B/Cの配置と処方の原則（§1・§4）と、統治コードのレビュー強制（§4・§7）は入ったが、
> **入口の道具（`report_friction`）・集計・ケイデンス・仮説の評価はどれも未実装**で、
> いまは番頭が手で incident を積んでいる。未実装のものには **（未実装）** と印を付けた
> ——設計意図と実態を混ぜないため（P3）。

## 1. 改善対象の3層

| 層 | 対象 | 変更方法 |
|---|---|---|
| **A** | プロンプト資産（システムプロンプト、監査チェックリスト、classify判定プロンプト、skills） | エージェントが直接編集提案。コミット＝POレビュー対象 |
| **B** | ポリシーパラメータ（閾値、ケイデンス間隔、マージポリシー、スコープ規則、費用の上限、レビューの判定表。`meta/config.yaml`） | 同上 |
| **C** | 機構コード（Kobo、Extension Pack、ドライバ） | エージェントは提案まで。タスク化して正規フロー（実装→監査→POレビュー→自動更新パイプライン） |

原則：機構は「実施の保証」だけを担い、判断基準は層A/Bに置く（→ D2）。層Cは壊れると止まり、層A/Bは壊れると静かに劣化する——この性質差を配置判断の基準とする。

## 2. 発見（入口）：3つの起源

すべてのincident/improvementは `origin: system | po | agent` を持つ。

### system起源（テレメトリからの自動検出）
Koboが構造化ログ（監査指摘、escalate勧告と却下、force類の操作、/fix回数、reopen、escaped defects、テスト結果）から機械的に検出する。

### po起源（POの指摘）— 二重処理の規約
POが構造的問題を指摘した場合、**必ず2件として処理する**：
1. 指摘された問題自体への対処
2. **センサー欠落incident**：「なぜシステムはこれを自分で検知できなかったか」。検知に必要なテレメトリ・統計・議題生成をタスク化する

po起源の割合はループの成熟度メトリクスであり、メタケイデンス（→ §6）で追跡する。目標は指摘ゼロではなく、各クラスの指摘を一回きりにすること。

### agent起源（エージェント自身の発見）
- **`report_friction` ツール**（全役割に常設）：不自然な回避、タスク定義に無く推測した情報、繰り返しの無駄、などを1行で積む **（未実装）**
- **タスク後振り返り**（実行者、完了時に3問）：何に詰まったか／何を回避したか／仕組みに何が欠けていたか **（未実装）**
- **回避策（workaround）は最重要シグナル**：成功した回避はincidentにならず欠陥を隠蔽するため、明示的に収集する（→ P7）
- ノイズ対策：ケイデンス議題に載せるのは**パターン（同型N件）のみ**。単発は蓄積に留める

**いまの実態（2026-08-07・P3）**：道具は無く、**番頭が `work/inbox/incident/` へ手で積んでいる**
（inc-0019〜0029）。積まれてはいるので入口が塞がっているわけではないが、**積むかどうかが
番頭の判断に依っている**——`report_friction` が狙っていたのは「気づいた瞬間に、判断を挟まず
1行で置ける」ことなので、そこは埋まっていない。集計（§3）も手作業。

## 3. 蓄積と集計

- 置き場：`work/inbox/improvement/`（frontmatter: id, origin, class, refs, status, resolution）
- ケイデンスごとにKoboが集計し、同型パターン・件数・傾向を議題として合成カードに載せる。1件ずつではなくパターンで扱う

## 4. 処方の原則

- 誤解・知識不足が原因 → 層A/Bで修正
- 虚偽報告・手抜き・迂回が原因 → **層Cへ昇格**（自己申告を信じない機構化。→ I1, P4）。incidentの再発はプロンプト層から機構層への一方向の昇格として扱い、使うほど「騙せない部分」を増やす
- 層C改善はマージ前に**再現E2Eシナリオの追加**を必須とする（検証スイートをループと共に育てる）
- 統治コードに触るタスクは `governance: true`：バッチ混載禁止、レビュー省略対象外、UIで強調表示
  - **実装済み**（決定57・66）。`governance: true`、または `meta/config.yaml` の判定表が
    PO必須と定めた面に触るタスクは、**レビューの段が `po` に解決され、番頭には通すボタンが
    出ない**。判定表を読めない側（番頭ホスト）に推測させず、Kobo が解決済みの段を返す

## 5. 仮説駆動の評価（出口）

**すべての改善タスクはenqueue時に仮説を宣言する**：

```yaml
hypothesis:
  expect: "テスト検証まわりの同型incidentが減る"
  metric: incident.count[class=test-skip]   # Koboが計測できる値。測定不能なら none
  horizon: 21d
```

- Koboはマージ時にベースラインを記録し、horizon経過後に**評価カード**を合成キューアイテムとして生成 **（未実装）**
- 評価セッション（SDK単発）が前後比較＋期間中のfriction/escaped defectsから `keep / tune / revert` を勧告。判断はPO（実績によりautoクラス化可） **（未実装）**

- 結果は改善ファイルのstatusに書き戻す。**revert済み改善は履歴として照合対象になり**、類似提案のenqueue時に「同案revert済（理由付き）」として弾く
- 割り切り：厳密な因果評価は行わない。目的は「方向性の確認」と特に「**明確な悪化の検出**」。不明ならkeep
- `metric: none` を許容し、horizon後に主観1問で評価する（形式の強制で改善の流量を殺さない）
- revertコスト：層A/B＝git revert即時、層C＝通常タスク＋Nix世代ロールバック

**いまの実態（2026-08-07・P3）**：入っているのは**分岐の片側だけ**。`merge-queue.ts` は
`hypothesis` を持たないタスクを `merged → closed` へ自動で送るが、**持つタスクは `merged` に
置いたまま**にする（`evaluating` へは誰も動かさない。状態機械の表に
`merged:evaluating` / `evaluating:closed` は在るが、呼ぶ側が無い）。

つまり**仮説を宣言したタスクは `merged` で止まる**。仮説を書かなければ流れは詰まらないので、
**評価側（カード生成・評価セッション）を作るまでは `hypothesis` を宣言しない**方がよい。

## 6. 周期構造：ケイデンスとメタケイデンス

| | 周期 | 議題 |
|---|---|---|
| **ケイデンス** | 2〜3日（パラメータ） | 未承認ADR、勧告却下ログ集計、improvementパターン、Epic分解残、評価カード |
| **メタケイデンス** | 月次程度（パラメータ） | **ループ自身の健康**：origin別比率、機構化までの平均日数、escaped defects傾向、resolution無しクローズ、改善流量。内省セッション（トランスクリプト標本・却下ログ・正規フロー外のPO介入から構造的盲点を探索）の結果 |

いずれも合成キューアイテムとして**取次**に載る（決定58。別の儀式を作らない）。
**どちらも未実装**（→ spec-daemon-core §5）。Kobo の tick に登録されているのは
ゲート再評価・自動着手・職人イベントの引き取り・マージキュー・コンフリクト確認・
ローテーションだけで、合成カードを作る仕事は無い。

- 改善タスクはNextに固定枠（既定：5タスクに1つ、層Bパラメータ）。「手が空いたら」にしない

**「環境の孤児・teardown失敗」はここから外した**（task-0067）。ケイデンスを待たず、
Environment Pool が出来事として積み、番頭が `env.events` を引いて**その場で会話へ返す**
——外に残ったものは費用（I3）なので、2〜3日に一度の議題では遅い。

## 7. 自律性の段階拡大（レビュー必要性の縮小）

レビューを減らせるのは、**検証の機構化がそれを肩代わりした範囲だけ**。エージェントの印象的な品質向上を根拠にしない。

### マージポリシー（層B）
タスクのリスククラス×実績でマージ経路を分ける：

- **auto**：監査＋テストグリーンで自動マージ。事後ダイジェスト通知のみ
- **sampled**：自動マージ＋N%を無作為事後レビュー。ドリフト検出のためautoクラスにも薄く維持する
- **mandatory**：事前レビュー必須（`governance: true`、新規設計領域、GUI/UX）

昇格・降格はケイデンスで判断する。制御信号は**escaped defects**（自動マージ後にユースケースQAで発見された不具合）。増加したクラスは自動で降格候補として議題に載る。

### レビュー単位の移動
タスク差分の事前レビューが縮小する代わりに、**Epic受け入れセッション**を一級フェーズとする：構成タスク全マージ後、staging環境で動くものをユースケースで通す。POの関与は仕様対話・GUIレビュー・ユースケースQAに収斂させる。

### 設計判断の自律化
可逆な設計判断はエージェントが決定しADRドラフトに記録（ケイデンスで事後承認）。不可逆・vision抵触のみ対話に上げる。D1の「不可逆」の定義を実績に応じて狭めていく。

## 8. 第3階：アーキテクチャ見直し

個別incident処理では掴めない構造劣化（パッチを積んでも品質が上がらないパターン）を扱う。

### 検出（決定的コード、ケイデンスごとに算出）
- **ホットスポット**：同一ファイル群が多数タスクで反復変更されている
- **再発集中**：同一スコープのescaped defects・reopenの集中
- **パッチ効率劣化**：受け入れ条件あたりのdiff量・/fix回数・escalate率の時系列悪化
- **修正の不定着**：層A改善後も同型incidentが再発（最強のシグナル）

### 診断（アーキテクトレビューア、SDK単発）
統計＋コード構造＋関連ADR・Specを入力し、原因仮説を**既存ADRのsupersede提案＋リファクタリングEpicドラフト**の形式で出力する（新しい文書種は作らない）。

### 判断と検疫
- アーキテクチャ変更は常にmandatory。判断はケイデンスでPOが行う
- 診断が出た領域には**検疫（quarantine）マーク**：該当スコープへの新規パッチタスクのspawn時に保留勧告を出す（禁止ではなく勧告。→ 判断主権）。判断前にパッチの積み増しを止める
- 診断の的中/外れも評価対象とし、検出閾値・診断プロンプトを改善ループで育てる
- 発火規則：同一スコープで修正が2回定着しなかったら、3回目のパッチ前に根本原因分析を要求（→ P6。reopen計数によりKoboが勧告を機械発火）

## 9. 追加されるprinciples（採択時にprinciples.mdへ）

- **P6.** 同一スコープで修正が2回定着しなかったら、3回目のパッチを書く前に根本原因分析をincidentとして積む。パッチの繰り返しは症状であり、進捗ではない
- **P7.** 不自然な回避策を取ったら、成功しても report_friction する。回避の成功は仕組みの欠陥の隠蔽である
