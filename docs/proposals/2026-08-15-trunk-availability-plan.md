# 幹を待ち状態に保つ — 実装計画（形A＋受け皿）

- 日付: 2026-08-15
- 前段: `docs/proposals/2026-08-15-trunk-availability.md`（実測と機構の調査。**案II「知らせを札にする」は PO 方針により却下**）
- 調査: 職人 inv-trunk-idle-a / inv-trunk-idle-b / inv-notice-to-branch
- 渡し先: banto開発(thread-61)

## 0. PO の方針（確定）

> 知らせへの対応は自動でやってほしいから札にするは無し。一方で知らせが来た時もユーザへの対応はしてほしい。だから、知らせへの対応は枝でやるほうがいいと考えている。例えば banto開発は電卓開発の枝といまアクティブに会話している。あれはいい。ただ、やってると私が会話できないので、枝でやってほしいということ。

したがって目標は **「幹は常に入力を受けられる」かつ「知らせへの対応は止めない」**。手段は**対応の場所を幹から枝へ移すこと**であって、対応をやめることではない。

## 1. 採る形

**形A（発生源で分ける）を主、形B（機構が枝を開く）を受け皿にだけ限定適用する。**

形Aが軽いのは、**機構が既に「報告は delegate した会話へ届く」性質を持っている**から（`origin=banto:<threadId>` → worker-notice.ts:362、Kobo も同様に origins を引く → kobo-notice.ts:157-159/174/376）。**枝の中で委譲すれば、報告は枝へ届き幹には来ない。** 帳場の知らせは文字量の76%が職人の報告なので、これだけで大半が消える。

一方、**対応すべき枝を持ちようがない知らせ**が残る：

| 出所 | 枝へ届くか | 対処 |
|---|---|---|
| 職人の報告・質問 | 枝から delegate すれば**届く** | 形A（規律＋ガード） |
| Kobo | 枝から enqueue すれば**届く**。引けなければ幹 | 形A＋逃がし先を受け皿へ |
| env | **届かない**（threadId の引数が無い・env-notice.ts:31/73） | 受け皿の枝（必須） |
| system（再起動等） | 届かない（宛先なし） | 受け皿の枝 |
| 他の幹の thread.send | 幹宛て（それが正しい） | そのまま幹へ |

## 2. 認めた割り切り

**「幹での委譲を断っても幹のターンは減らない」。** 断られた番頭はその場で枝を開いて開き直すので、**むしろ1本増える**（調査の指摘）。減るのは「報告が幹へ来る」分。

これは受け入れる。**PO が幹で「やって」と言い、番頭が「枝を開いた」と返す1往復は会話そのもの**であって、消すべき雑音ではない。消したいのは、そのあと延々と続く職人の報告・工場の進捗・環境の知らせで幹が塞がることの方。

## 3. 実装（タスクの粒と順序）

### T1. 幹のターンを計測できるようにする【最初にやる】
いまは `turn_start`/`turn_end` が WS へ broadcast されるだけでどこにも残らず（server.ts:816/827/1419）、永続する会話記録の TranscriptEntry には**時刻の欄が無い**（protocol.ts:571-587。`at` を持つのは `branch_result` だけ）。**先行調査は SDK セッションファイルの timestamp を突き合わせて測るしかなかった。**

`deliverToThread`（server.ts:812-831）と PO 発話の経路に記録を1つ足し、「スレッドごとのターン本数・所要・出所」を残す。**これが無いと以降の受け入れ基準を数字で書けない**ので最初に置く。

- 受け入れ基準: 幹の1日あたりターン本数・busy 合計・出所別内訳が、後から機械的に取り出せる

### T2. 畳んだ枝への配達を塞ぐ【穴・T5 の前提】
畳んだ枝にも知らせが配られ、畳んだ枝のターンが回る。`resolve` が畳んだスレッドも返すのは意図的（threads.ts:1420-1424、決定35b）なので**resolve は触らず**、`deliverToThread` の resolve 直後（server.ts:791-802）で判定する。ここは worker/kobo/env/system と `nudge` が**全部通る唯一の関所**。

回し先は **`reopen`（枝を開き直す）** を採る（threads.ts:1408。決定68 が本来これを意図していると kobo-notice.ts:161 のコメントにある）。捨てるのは I2 に反し、親の幹へ回すのは今回の狙いに逆行する。

- 受け入れ基準: 畳んだ枝へ知らせが来たら枝が開き直り、**幹のターンは回らない**／知らせは失われない

### T3. 受け皿の枝を用意する
env・system・宛先を引けなかった Kobo/worker の知らせの配達先を、帳場ではなく**受け皿の枝**にする。`ThreadRegistry.open` はホスト内部から呼べる（server.ts:1121-1134 / bin.ts:1637 が前例）ので機構が開ける。**開いただけでは番頭は動かない**——動き出すのは `notify`（→ deliverToThread → ターン1本）なので、「open してから、その枝へ notify」で成立する。

論点（PO 判断）: **常設1本**にするか、**知らせのたびに開いて畳む**か。常設は畳む手間が無い代わりに文脈が伸び続ける（章立てで畳まれる）。都度は畳む設計が要る。

- 受け入れ基準: env・system の知らせで**幹のターンが0本**になる／知らせは受け皿で読める・見落とせない

### T4. 委譲は枝で（ガード）
幹で `worker.delegate` / `kobo.enqueue` を呼んだら、直し方を添えて断る。threadFactory が `identity`（kind: trunk|branch）と threadId を持つ**同じクロージャの中で Tool を1本ずつ包んでいる**ので書ける（bin.ts:1069-1076 / 1159-1207）。断る包み方の前例は worker-guard.ts:32-54、**警告に留める**前例は withTierUnassignedNotice（bin.ts:1176）。

論点（PO 判断）: いきなり**断る**か、まず**警告**から始めるか。一発で終わる小さな委譲まで枝になる副作用があるので、警告から入って様子を見るのが安全。

- 受け入れ基準: 幹で委譲しようとすると「先に枝を開け」と直し方つきで返る／枝の中では通る

### T5. 枝の生存管理（上限と促し）
枝は**上限なし・自動で畳まれない**（3日放置で取次に札が出るだけ・threads.ts:1490）。枝を主戦場にするなら必須。

- 上限は `open()` の parentTrunk 確定直後（threads.ts:921-934）に置く。数える式は既存（closeTrunk と同じ `list({state:"open",kind:"branch"}).filter(parentId===…)`）。
- **上限は画面に出る数と合わせる**——Web UI は枝をレールに**先頭6本だけ**出し、残りは「+N」（App.tsx:73 `HOLD_SHOWN = 6`）。**PO の目に入る数＝管理できる数**なので 6 を推す。
- 超えたら `thread.open` を断り「先に畳め」と言う。
- 機構が畳む口: `merge` は結論が空だと投げる（threads.ts:1074-1075）ので、自動で畳むなら定型の結論文を渡すか別メソッドを足す。

論点（PO 判断）: 上限をいくつにするか（6 を推す）。

- 受け入れ基準: 上限に達した状態で `thread.open` が断られる／開いている枝の数が画面と一致する

### T6. fork で枝を開くコストを下げる【段階2・任意】
`forkSession(sessionId, {upToMessageId?})`（Agent SDK・実物確認済み）／pi の `forkFrom` で、幹の文脈を引き継ぐ枝を作る。instruction を書き切らなくてよくなる（PO 案2）。artifact ストアを幹単位に寄せる（bin.ts:1088）と観測 ID もそのまま解決する。

**必須ではない**（枝は instruction を書けば開ける）。トークン代と引き換えなので、T1〜T5 が効いたあとで判断する。

## 4. 想定される副作用と、その手当

| 副作用 | 手当 |
|---|---|
| 枝が同時に何本も回る（**会話をまたぐ直列化は無い**・枝5本は5本同時。上限・絞りは見つからなかった） | T5 の上限で抑える。API のレート制限時の挙動は未調査 |
| 枝10本で画面が溢れる（レール6＋「+4」、幹の本文に札10行） | T5 の上限を画面の 6 に合わせる |
| 枝の結論が静かすぎて埋もれる（`merge` は幹のターンを回さず札1件） | 未読（`marksUnread`）で足りるか運用で見る。PO の判断が要るものは従来どおり取次へ |
| 幹と枝が同じ職人・環境を二重に触る（`worker.steer`/`worker.list` に検査が無く、env はスレッドに紐づかない） | 別建て。枝を主戦場にすると踏む確率は上がる |
| `thread.consult` は幹のターンを回す（10分に10回） | 枝が増えると幹が埋まる新しい経路。運用で見て、多いようなら回数を絞る |

3. **T5 の枝の上限をいくつにするか**（画面と揃えて 6 を推す）
