## 0. PO の方針（確定）

> 知らせへの対応は自動でやってほしいから札にするは無し。一方で知らせが来た時もユーザへの対応はしてほしい。だから、知らせへの対応は枝でやるほうがいいと考えている。例えば banto開発は電卓開発の枝といまアクティブに会話している。あれはいい。ただ、やってると私が会話できないので、枝でやってほしいということ。

目標は **「幹は常に入力を受けられる」かつ「知らせへの対応は止めない」**。手段は**対応の場所を幹から枝へ移すこと**であって、対応をやめることではない。

### 0-1. 受け皿という概念は無い（2026-08-15・PO 訂正 ×2）

初版の「受け皿は常設1本」も、その次の「鍵が引けない知らせの落ち先だけ常設でよい」も、**どちらも取り下げ**。

> 知らせのたびに新規で枝を作るのだから、常設の落ち先という概念自体が要らない。

**常設の枝・受け皿・溜め place は設計に存在しない。** 常設が悪い理由は三重だった：(1) 文脈が積み上がり、**古い文脈を抱えたまま新しい知らせに対応する**ことになる (2) 章立て・自動コンパクションと二重に畳む (3) 無関係な件が1本に混ざる。

**枝の立ち方は2通りだけ。**

| | 鍵 | 配り先 | 閉じるとき |
|---|---|---|---|
| ① | **割り出せる**（`taskId` / 職人の `sessionId` / `envId`） | その鍵の枝。開いていなければ機構が立てる | **鍵が終端に達したら**（職人 closed・タスク closed/merged・環境 teardown） |
| ② | **割り出せない**（system の再起動通知など） | **その知らせ1件のための枝を立てる** | **捌いたら**。次の鍵無しの知らせは、また別の新しい枝 |

②が「1件で閉じてよい」理由：**鍵が割り出せない＝続きが来ても同じ枝に結びつけようがない＝その1件で終わる用件**だから。一度きりの知らせ（env の期限切れ・孤児検出・system）と同じ扱いで足りる。

①で「知らせ1件ごとに閉じてはいけない」理由：質問に答えて即閉じると、**次の完了報告が「自分の答えを知らない枝」に入る**。

### 0-2. 逃がす対象と、幹に残すもの

**逃がすのは「幹へ配られようとしている知らせ」だけ。**

- 宛先が**枝**ならそのまま配る（枝の中で委譲した報告が枝へ返るのは、既に正しい形）。
- **他の幹からの言伝（`thread.send`・出所 `thread`）と PO の発話は幹のまま。** これは知らせではなく会話そのもの。

### 0-3. 枝の数で断らない

**`thread.open` を枝の本数で断ってはならない**（PO 名指し）。用件ごとに枝を立てる以上、上限で断ると**弾かれた知らせが行き場を失う**。上限は促す／警告する側に寄せる（T5）。

### 0-4. 機構は勝手に畳まない

閉じる条件は決まっているが、**畳むのは番頭**。機構が畳むと結論を捏造することになる（`merge` は結論が空だと投げる）。機構は**終端の知らせに「畳んでよい」と分かる印を添える**ところまで。

## 1. 採る形

**形A（発生源で分ける）を主、形B（機構が枝を開く）を用件ごとの枝に適用する。**

形Aが軽いのは、**機構が既に「報告は delegate した会話へ届く」性質を持っている**から（`origin=banto:<threadId>` → worker-notice.ts:362、Kobo も同様に origins を引く → kobo-notice.ts:157-159/174/376）。**枝の中で委譲すれば、報告は枝へ届き幹には来ない。** 帳場の知らせは文字量の76%が職人の報告なので、これだけで大半が消える。

残るのは、**幹へ落ちる知らせ**：

| 出所 | いまの落ち先 | T3 後の落ち先 |
|---|---|---|
| 職人の報告・質問 | origin の会話（幹で委譲すれば幹） | 鍵 `sessionId` の枝 |
| Kobo | origins の会話。引けなければ幹 | 鍵 `taskId` の枝 |
| env | **必ず幹**（threadId の引数が無い・env-notice.ts:31/73） | 鍵 `envId` の枝（取れるか要確認） |
| system（再起動等） | 必ず幹（宛先なし） | **その1件だけの枝** |
| 他の幹の `thread.send` | 幹 | **幹のまま**（会話だから） |

## 2. 認めた割り切り

**「幹での委譲を断っても幹のターンは減らない」。** 断られた番頭はその場で枝を開いて開き直すので、**むしろ1本増える**。減るのは「報告が幹へ来る」分。

これは受け入れる。**PO が幹で「やって」と言い、番頭が「枝を開いた」と返す1往復は会話そのもの**。消したいのは、そのあと延々と続く職人の報告・工場の進捗・環境の知らせで幹が塞がることの方。

## 3. 実装（タスクの粒と順序）

**T1 計測 → T2 畳んだ枝への配達を塞ぐ → T3 用件ごとの枝 → T4 委譲ガード（警告から）→ T5 促し**。T6（fork）は**不要**として落とした。

### T1. 幹のターンを計測できるようにする 【着地済み `cd670922`】
`turn_start`/`turn_end` は WS へ broadcast されるだけでどこにも残らず、TranscriptEntry に時刻の欄も無かった（protocol.ts:571-587）。追記専用の JSONL 台帳を1本足した。

- 実装: `packages/banto-host/src/turn-log.ts`（1ターン＝1行：at / threadId / threadKind / parentId / source / durationMs / ok / errorMessage）、集計 CLI `turn-report.ts`（`npm run turn-report`、`--since` / `--thread` / `--json`）
- 置き場: `<BANTO_DATA_DIR>/turns.jsonl`。稼働ホストは **`/var/lib/banto/turns.jsonl`**
- 出所の値: `worker` / `kobo` / `env` / `system` / `thread` / 取次の回答元 id ＋ 今回足した `po` / `nudge`
- 書けなくてもターンは壊さない（console.error に出すだけ）／壊れた行があっても台帳ごと落とさない
- **検証**: docker の test プロファイルで `npm run typecheck && npm test` exit 0（2218件・fail 0）。稼働ホストで実際に1行目を確認

### T2. 畳んだ枝への配達を塞ぐ 【着地済み `8751a925`】
畳んだ宛先へ知らせが届いたら、**宛先を開き直してから配る**。`deliverToThread` の `poFloor` 直後（列の中）に `reopenClosedTarget` を1本。`resolve` は触っていない（決定35b）。

- 捨てない（I2）／親の幹へ回さない／`state !== "closed"` で即 return なので既存経路は不変・2件目以降で印が積み上がらない
- **畳んだ幹も本人を開き直す**（印の文言だけ分ける）。幹には還す親が無く、ほかへ逃がすと必ず**帳場のターンが回る**——それは塞ぎたいものそのもの
- **検証**: 新規8件（出所5種＋nudge が同じ関所で塞がること、T1 台帳で幹の行0・枝の行2）。呼び出しを外すと8件中6件が落ちることも確認済み。docker で全量 exit 0（2226件・fail 0）

### T3. 用件ごとの枝へ配る 【実装中】
0-1〜0-4 のとおり。詰めるべき点：

1. **鍵の割り出し** — env が `envId` を持って通知しているか（env-notice.ts:31/73）。取れなければ鍵無し扱い（②）に倒す。
2. **鍵→枝の対応をどこに持つか** — 再起動をまたいで残ること。title の文字列一致で探すのは禁止（改名で壊れる）。
3. **機構が枝を立てる経路** — `ThreadRegistry.open` の内部呼び出し（前例 server.ts:1121-1134 / bin.ts:1637）。幹に札が1行立つのは可、**幹のターンを回すのは不可**。
4. **終端の印** — 判定できる出所だけでよい（できないものを判定したふりをしない・I1）。
5. **見え方** — 用件枝が5〜10本開いたときの `thread.list` とレール（App.tsx `HOLD_SHOWN = 6`）を実際に見る。

- 受け入れ基準: env・system の知らせで**幹のターンが0本**（T1 の台帳で示す）／知らせは用件枝で読める・見落とせない／同じ鍵の2件目は同じ枝／鍵無しの2件は別々の枝／畳んだ用件枝に遅れて来た知らせは T2 で開き直る

### T4. 委譲は枝で（ガード・**警告から**）
幹で `worker.delegate` / `kobo.enqueue` を呼んだら、直し方を添えて**警告する**（断らない）。threadFactory が `identity`（kind: trunk|branch）と threadId を持つ**同じクロージャの中で Tool を1本ずつ包んでいる**（bin.ts:1069-1076 / 1159-1207）。断る前例は worker-guard.ts:32-54、**警告に留める**前例は withTierUnassignedNotice（bin.ts:1176）。

- 受け入れ基準: 幹で委譲すると「先に枝を開け」と直し方つきの警告が返る／処理そのものは通る

### T5. 枝の生存管理（**促しのみ・弾かない**）
枝は上限なし・自動で畳まれない（3日放置で取次に札・threads.ts:1490）。**`thread.open` は断らない**（0-3）。

- 開いている枝が増えたら**番頭へ「畳め」と促す**（数える式は closeTrunk と同じ）
- 目安は画面に出る数と揃える（`HOLD_SHOWN = 6`）。**閾値であって上限ではない**
- 用件枝は鍵の終端／1件で閉じるので原理的に溜まらない。促しの主対象は**番頭が手で開く議論の枝**

### T6. fork — **不要（落とす）**
用件の枝に要るのは**幹の会話履歴ではなく、その用件の事実**（kobo.task / worker.events / 契約から道具で引ける）。記憶は元々 trunkId 共有。

## 4. 想定される副作用と、その手当

| 副作用 | 手当 |
|---|---|
| 枝が同時に何本も回る（会話をまたぐ直列化は無い） | 用件枝は閉じるので溜まらない。促し(T5)で見る。API のレート制限時の挙動は未調査 |
| 用件枝が10本で画面が溢れる（レール6＋「+4」） | T3 の詰め⑤で実際に見る。**弾かない** |
| 枝の結論が静かすぎて埋もれる（`merge` は幹のターンを回さず札1件） | 未読（`marksUnread`）で足りるか運用で見る。PO の判断が要るものは取次へ |
| 閉じた鍵に遅れて知らせが届く | **T2 で塞いだ**（開き直して配る） |
| T2 と T3 が往復する（畳む→開き直す→畳む） | 閉じる条件を**鍵の終端**に固定する。「1件捌いたら畳む」にすると必ず踏む |
| `kobo-notice.ts:155-166` の「畳まれていたら既定の宛先へ逃がす」フォールバック | T2 で事実上デッド。**残っている限り帳場のターンを起こす経路**なので T3 で始末する |
| `thread.consult` は幹のターンを回す | 枝が増えると幹が埋まる新しい経路。多いようなら回数を絞る |

## 5. PO 判断（決着済み）

1. **T4 のガードは「断る」か「警告」か** → **警告から**
2. **受け皿は常設か都度か** → **常設は無い**。鍵があれば鍵の枝、無ければその1件だけの枝
3. **T5 の枝の上限** → **弾かない**。6 は促しの閾値
4. **T6（fork）** → **不要**
