# 提案: Kobo の見直し — POのイメージ・現物・番頭の誤読の DIFF と、あるべき配線

**日付**: 2026-08-06
**立場**: 番頭の調査と提案（PO 裁定を仰ぐ）
**発端**: PO の提起——「Kobo を配線したいが、作りかけで方向をピボットし、元々 Kobo に入れる予定だったものを別モジュールへ切り出している。Kobo のコンセプトから今の banto になじむのか含めて見直してほしい」
**改訂**: 初版（同日）は「工場（自動パイプライン）は構造逆転で失効した」と判断して縮小案を推したが、**これは番頭の誤読だった**。PO のイメージは工場そのものである。初版の推奨は取り下げ、本版で DIFF を取り直した。誤読の経緯は §4 に残す（P3：黙って書き換えない）。

---

## 0. 結論（先に）

1. **PO のイメージ（＝タスクを積めば Kobo が職人を使って自動でさばき、状態遷移で完了まで運ぶ）は、実装として7割方すでに存在する。** `tests/e2e/pipeline-merge.e2e.spec.ts` が実 pi・実 LLM で「タスク投入 → 取り込み → ready → 自動着手 → 実装 → 実監査 → マージキュー → main へマージ」を通しで検証している。**動いていないのではなく、番頭・画面・他モジュールに繋がっていない。**

2. **足りないのは工場の中身ではなく、工場の入口・出口・配管である。** ①番頭から積む口（`kobo.*` はゼロ本）、②POへ判断を出す口（取次に積まれない）、③見る面（GUI はゼロ）、④職人と検証環境を各モジュールへ寄せること（台帳が2つずつある）、⑤作った worktree が場所として見えないこと。

3. **切り出しは正しかったが、2段階の2段目が止まっている。** Worker Pool・Environment Pool は「まず切り出し、後で Kobo をサービス利用へ」の2段階で進める決め（決定23・32a）だったが、2段目（task-0024・task-0046）が未着手のまま。そのため Kobo は自前の台帳・自前の pi 起動を持ったままで、**Kobo が起こした職人は番頭からも画面からも見えない**。

4. **したがって「作り直し」ではなく「配線と寄せ直し」が要る。** 状態機械・依存ゲート・監査の差配・マージキュー・マージ前ゲートは残す（PO のイメージの本体）。捨てるのは Kobo 自前の職人台帳・環境台帳・tmux・独自の受け口であって、統治ではない。

## 3. DIFF ①：POのイメージ（A） vs 現物（B）

**本体は在る。無いのは繋ぎである。** 埋めるべき差は10項目。

| # | 差 | いま何が起きるか | 効く規則 |
|---|---|---|---|
| **1** | **番頭 → Kobo の口が無い**（`kobo.*` Tool は0本。`ready` クエリも未実装） | 番頭は Kobo にタスクを積めない。積むにはファイルを書くしかなく、状態照会の手段も無い | 決定1・task-0001 |
| **2** | **Kobo → PO の口が無い** | レビュー待ち・failed・blocking が取次に積まれない。人間レビューは API 直叩き相当 | `spec-design` §7 |
| **3** | **画面が無い**（Kobo の GUI コンポーネントは0個） | ボードもレビュー面も無い。状態遷移が見えない | 決定12・49 |
| **4** | **職人が Worker Pool 経由でない**（`SpawnLedger` が daemon と worker-pool の両方にある） | Kobo の職人は `worker.list` にも職人ビューアにも出ない。番頭から覗けない・止められない | D3・決定29c・task-0024 |
| **5** | **検証環境が Environment Pool 経由でない**（`EnvLedger` と TTL 執行が両方にある） | 環境の真実が2つ。消し忘れの責任が割れる（外部VMコストは one-way な副作用） | D3・決定32e・task-0046 |
| **6** | **worktree が場所（Place）にならない** | 実装中の中身を番頭も PO も読めない。`file.read` も届かない | 決定36 |
| **7** | **モデル方針が `LlmCatalog` の外**（`BANTO_PI_PROVIDER`/`BANTO_PI_MODEL` 固定。tier ルーティングは spec のみ） | 「ひたすら積む」と費用が env 変数2つに支配される。tier による昇格・格下げが効かない | ADR-0011 決定42 |
| **8** | **待ち受けが `0.0.0.0` で無認証** | 決定40 で番頭側を 127.0.0.1 に閉じた隣に、無認証の口が開く | 決定40 |
| **9** | **`evaluating` 以降が未実装** | 「完了まで持っていく」の尻尾（評価カード・ケイデンス・改善ループ）が無い | `spec-improvement-loop` |
| **10** | **`bin: "banto"` が二重**（banto-cli＝Koboのクライアント／banto-host＝番頭） | `npm link` で後勝ち。どちらが起動するか環境依存 | — |

加えて、配線の前に**決めないと二重になるもの**が1つある。

- **タスクの `status` の持ち主。** watcher は `status: queued` のファイルだけを取り込み、**ファイルには絶対に書き戻さない**（D3。`no-writeback.spec.ts` が見張る）。一方 2026-08-01 の PO 裁定Aで「Kobo 統合までは番頭が実装と照合して `done` に更新する」暫定運用になっている。**配線＝この暫定運用の終端**である。

## 4. DIFF ②：POのイメージ（A） vs 番頭の初版提案（C）

初版（C）は「工場を畳み、関所（マージゲート）だけ残す」を推した。**主軸で誤っている。** A は工場そのものであり、C が畳もうとした watcher・auto-spawn・13状態・依存ゲート・監査の差配・タスクの所有は、すべて A の本体である。

**なぜ誤ったか（記録として残す）**：番頭は「Kobo が3週間触られていない」「番頭ホストだけが育っている」「番頭が手でタスクを回している」という**観測から意図を推論した**。実際には「配線されていないだけで、中身は e2e まで通っていた」。観測は正しく、推論が誤り。**動いていないものを見て『前提が失効した』と読むのは、番頭がやってはいけない飛躍だった**（I1 の精神：自己申告と同じく、自分の推論も裏を取る）。

**C から生き残るもの**（A の下でも有効、むしろ A では緊急度が上がる）：

- 二重台帳の解消（差 4・5）——A では Kobo が実際に走るので、「配線したら二重になる」ではなく「配線の前提条件」になる
- POへの出口を取次に一本化（差 2）——Kobo 独自のアテンションキューを作らない
- 待ち受けと認証（差 8）
- 「横（登録機構と GUI）を全部やる前に、縦を1本通す」という順序の考え方

## 5. あるべき論

### 5.1 分界の原則（3つ）

1. **「何を作るか」は番頭、「どう回すか」は Kobo。**
   番頭は PO と話してタスクを起票し、Kobo に積み、状態を読んで PO に取り次ぐ。Kobo は積まれたものを決定的に回す。**番頭は状態を進められるが、飛ばせない**——`approve` は操作として存在してよいが、マージ前ゲートは誰にも飛ばせない（vision「番頭でも帳簿はごまかせない」）。

2. **意図はファイル、状態はイベントログ。**
   タスク定義ファイルは「何をしてほしいか」だけを持ち、**`status` はイベントログが唯一の持ち主**にする。2026-08-01 の暫定運用（番頭が `done` を書く）は、配線と同時に終える。

3. **能力は一箇所。Kobo はその利用者になる。**
   職人＝Worker Pool、検証環境＝Environment Pool、作業場所＝repo-manager、POへの口＝取次、画面＝banto のキャンバスと意匠、モデル＝`LlmCatalog`。**Kobo が自分で持つのは統治だけ**（状態機械・ゲート・キュー・帳簿・監査の差配）。

### 5.2 但し書き：番頭も職人を起こしてよい。線引きを明文化する

決定23 のとおり番頭は Kobo 無しでも職人へ委譲できる。二重差配にしないための線引きを、いま決めておく：

> **main に着地する変更を伴う仕事は Kobo のタスクにする。調査・下読み・その場の確認は番頭が直に職人へ。**

この線があれば「番頭が直に起こした職人が勝手にコミットしていた」が起きない（職人の worktree も Kobo のタスク由来のものだけが main へ向かう）。

### 5.3 具体的に決めておく必要のある設計点（配線で必ずぶつかる）

- **取次の三部構成を Kobo が満たせるか。** 取次の一通は「経緯（起点となったPOの指示）／起きたこと／求める判断」が必須（`spec-ui` §3・`spec-design` §7）。Kobo は**起点を持っていない**——タスクを積んだのは番頭なので、**起票時に「起点となったPOの発言への参照」を番頭が Kobo へ渡す**必要がある（D8 の起点参照をモジュール跨ぎで繋ぐ）。これを設計に入れないと、レビュー待ちの札が「起きたこと」しか書けない。
- **レビュー待ちの粒度。** 1タスク1通か、溜まったら束ねて1通か。「ひたすら積む」運用では前者だと取次が溢れる。**束ねて1通・中で個別に捌ける**形が要る。
- **同時実行数とモデル tier が費用を決める。** 既定は同時5・モデルは env 変数固定。差7（`LlmCatalog` へ寄せる）とセットで、**上限は能力側が持ち超過は黙って丸めず拒否**（決定34f と同じ形）にする。
- **worktree を `gwq` 配下に作る。** そうすれば repo-manager が場所として返し、番頭も PO も中を読める（差6）。Kobo 独自の worktree 置き場を持たない。

## 6. 実装順（あるべき順序と、その理由）

### Phase 0 — 前提を1つ決める（コードなし）
タスクの `status` の持ち主を確定する（§5.1-2）。ここが割れたまま配線すると、以降すべての段で二重になる。

### Phase 1 — 縦に1本通す（体験が最初に出る）
- Kobo をモジュール登録（接続情報＋`kobo.*` Tool：`enqueue` / `ready` / `list` / `get` / `transition`）
- 番頭が会話からタスクを積める。積むときに**起点の参照**を渡す（§5.3）
- Kobo の判断待ち（レビュー待ち・failed・blocking）を**取次へ積む**
- **画面はまだ作らない。** 取次と会話だけで「積む → 勝手に回る → 判断だけ来る」が成立する

> 画面より取次を先にするのは、取次が既にあり、判断待ちの唯一の口と決まっているから（`spec-design` §7・PO裁定 2026-08-05④）。

### Phase 2 — 能力を一箇所にする（実運用に入る前に）
- task-0024：Kobo が Worker Pool をサービス利用する。自前の `SpawnLedger`・`PiRpcDriver` 直呼び・tmux を捨てる
- worktree を repo-manager（`gwq`）経由にし、**場所として見えるようにする**
- これで職人ビューア（決定18）が Kobo のタスクにもそのまま効く＝ドリルダウンが無料で手に入る

> 二重台帳は「実運用に入ってから剥がす」と高い。**回し始める前に潰す。**

### Phase 3 — 面を作る
- ボード（Kobo の状態機械をそのまま描くビューア。独自状態を持たない）
- レビュー面（DIFF＋承認／差し戻し）
- いずれも banto の意匠（`spec-design`）とキャンバスのカタログ規約（決定17）に従う

### Phase 4 — 検証環境
- task-0046：Environment Pool をサービス利用（台帳・TTL の一元化）
- レビュー用 dev サーバの公開（決定39）

### Phase 5 — 尻尾を育てる
- `merged → evaluating`、評価カード、ケイデンス、改善ループ（`spec-improvement-loop`）

**あわせて随時**：差7（モデルを `LlmCatalog` へ）、差8（127.0.0.1）、差10（`bin` 衝突）。

## 7. PO に上げる判断（D9）

1. **タスクの `status` の持ち主**——ファイルから外し、Kobo（イベントログ）を唯一の持ち主にしてよいか。＝2026-08-01 の暫定運用（番頭が `done` を書く）を配線と同時に終える
2. **番頭と Kobo の線引き**——「main に着地する変更を伴う仕事は Kobo のタスク、調査は番頭が直に」でよいか
3. **順序**——Phase 1（取次まで）を先にし、**画面（ボード・レビュー面）は Phase 3 に回してよいか**。「積めば回る」を先に体感できる代わりに、しばらく盤面は見えない
4. **費用の上限**——同時実行数とモデル tier の上限を Kobo（能力側）が持ち、超過は拒否する形でよいか
