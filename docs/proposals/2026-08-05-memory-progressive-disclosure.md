# 提案: コンパクションに代わる「外部ファイル＋段階的開示」の記憶・文脈管理

**日付**: 2026-08-05
**立場**: 番頭の提案（PO 裁定待ち）。調査メモ: `docs/proposals/2026-08-05-context-memory-survey.md`（職人調査・2026-08-05）。

## 要旨

- PO の仮説（会話の中でコンテキストをクリアしつつ、文脈を外部ファイルに置き、段階的開示で引き継ぐ）は、**業界の複数実装が既に取っている方向と一致**しており、新奇ではない。最も近い先例は Claude Code の auto memory（MEMORY.md 索引＋トピックファイル）と Hermes Agent の三層メモリ
- banto は既に **SKILL で段階的開示を実装済み**（一覧だけ常時・本体は skill.read）。これを記憶と「進行中の文脈」へ拡張するのが本提案の正体
- 方針: **要約（コンパクション）に頼らない。** 外部ファイルに書き出し、索引だけ常時見せ、詳細は検索・参照で引く。会話全文は検索可能な形で残し、コンパクションで失われる情報を無くす
- 実装は4フェーズ。**第一着手は task-0056（会話の引き継ぎ）**——設計合意済み・未実装のものを先に動かし、その上に検索と自動トリガーを積む

---

## 1. 背景と論点

PO の提起（2026-08-05）:

- コンパクション（Claude・pi の、会話を LLM 要約で置き換える方式）は「要約で情報を失う」ためイマイチ。別の解決策を探したい
- banto は**セッション間で記憶を共有したい**（現状は memory.jsonl の全件注入のみ）
- 思案中: 会話の中でコンテキストをクリアしつつ、文脈を外部ファイルに置いて、**段階的開示**として引き継ぐ

## 2. 現状の整理

### 2.1 実装済み

| 層 | 中身 | 実装 | 注入方式 |
|---|---|---|---|
| 第一層 | 永続記憶（fact / preference / habit） | `JsonlMemoryStore`（memory.jsonl、追記のみ・supersedes で訂正） | **セッション開始時に全件**システムプロンプトへ注入（`renderMemoryForPrompt`） |
| 第二層 | 手続き記憶（SKILL） | `skills.ts`・`skill-tools.ts` | **一覧（名前・説明）だけ常時**、本体は `skill.read` でオンデマンド（段階的開示の実装例） |

### 2.2 未実装（draft のまま）

- **第三層（エピソディック記憶）**: FTS5全文検索によるセッション横断検索（task-0007 で「SQLite 実装へ差し替える想定」と明記、着手時再検討）
- **記憶の自動抽出**（task-0022）: 会話の区切りで背後のLLMが記憶すべきことを抽出。決定28で設計済みだが未実装
- **SKILL学習層**（task-0017）: 番頭の学びの置き場。未実装
- **会話の引き継ぎ**（task-0056 / epic-0012）: 新規会話ボタンでの handoff 資料生成。**2026-08-02 設計合意済み**だが未実装

### 2.3 コンパクションの実態

- pi の自動コンパクションが有効。文脈があふれると古い会話が LLM 要約に置き換わる
- `server.ts` は `compaction_end` を notice として画面に出すだけ（「まとめ直しました。番頭が細部を覚えていないときは前提をもう一度伝えてください」）
- **要約は会話の外に保存されない**——セッションを越えて引き継がれず、検索もできない。PO の「いまいち」はこの構造に由来
- トランスクリプト（会話の記録）は ThreadStore が保存するが、これは画面表示用で、番頭の文脈には入らないし検索もできない

### 2.4 セッション間共有の現状

- memory.jsonl はホスト再起動・スレッドを越えて共有される（D11）が、入るのは「覚えておくべき好み・習慣・事実」だけ
- **進行中の文脈**（いま何をしていて、どこまで進み、次に何をするか）は共有されない。これが task-0056 の射程

## 3. サーベイの要点（詳細は調査メモ参照）

| 方式 | 何を覚えるか | どこに置くか | いつ注入するか | 検索 | コンパクションとの関係 |
|---|---|---|---|---|---|
| **Hermes 三層** | 耐久的事実 / SKILL / 会話全文 | MEMORY.md・skills/・SQLite+FTS5 | 事実は常時、SKILLは一覧常時+本体オンデマンド、会話は検索時 | FTS5（CJK対応） | 圧縮しても**soft-archive で検索可能に残す**。「要約で潰す」代わりに「検索で取り出す」 |
| **MemGPT/Letta** | メモリブロック（persona/human）/ 会話DB / 文書DB | ブロックは毎ステップ注入、archival/recall は検索時 | 自己管理（エージェントが退避判断） | ベクトル+関数呼び出し | **要約より検索が勝つ**（DMR評価 92.5% vs 32.1%） |
| **Claude Code** | CLAUDE.md（指示）/ auto memory（学習） | 平文Markdown、**MEMORY.md 索引＋トピックファイル** | 索引の先頭200行/25KBを毎セッション、詳細はオンデマンド | ファイル読み（検索エンジンではない） | コンパクション後も**ファイルから再注入**される。ファイルに書けば残る |
| **ChatGPT/Claude.ai** | 永続ファクト / 最近会話要約 | サーバ側DB | **全件注入**（33件程度なら機能） | 検索しない（要約リストの範囲内） | 要約（Claude.ai 逐次自動要約）は損失あり。全件注入のスケール限界の実例 |
| **段階的開示** | メタデータ→本体→リソースの3層ロード | microsoft/agent-skills 等 | 索引（50-100トークン/件）常時、詳細は活性化時 | — | 「コンテキスト窓は有限、知識ベースは無限」への標準解 |
| **ハンドオフ方式** | ゴール・現在地・決定・未決・次の一手 | 外部ファイル（HANDOFF.md 等） | セッション境界・**コンテキスト枯渇トリガー** | — | **決定論的書き出し**——要約の損失がない。書き忘れ・陳腐化が弱点 |

**要点**: PO の仮説は Claude Code auto memory（外部ファイル＋索引＋オンデマンド）と Hermes 三層（検索可能な会話保存）の合成に最も近い。banto は既に SKILL で段階的開示を実装しており、踏み台が揃っている。

## 4. 提案

### 4.1 4層モデルに整理し、「常時注入 or オンデマンド」を明示する

| 層 | 中身 | 現状 | 提案 |
|---|---|---|---|
| L1 永続記憶 | fact / preference / habit | 全件注入 | **件数が少ないうちは全件注入のまま**。索引が膨らんだら「索引（1行1エントリ）常時＋詳細は memory.recall（検索）で引く」へ（Claude Code 式。閾値は論点3） |
| L2 手続き記憶 | SKILL | 一覧常時＋skill.read（段階的開示） | **現状維持**（既に正しい形） |
| L3 エピソディック記憶 | 会話の記録（トランスクリプト） | 保存のみ・検索不可 | **全文検索を実装**（第3フェーズ）。コンパクションで失われる情報の受け皿。「前に直した」「前回のやり方で」を検索で引く |
| L4 進行中の文脈 | スレッドの handoff 資料 | 未実装 | **task-0056 を実装**（第1フェーズ）。新規会話ボタンで handoff 資料を生成し、最小限の引き継ぎ＋参照を下書きで渡す |

### 4.2 コンパクションを「最後の手段」に格下げする

- pi の自動コンパクションは、**無効化または閾値を大幅に上げる**（設定で制御可能。`settings.json` の `compaction` 節、SDK モードでの渡し方は実装時に確認）
- 主経路を「**handoff 資料の書き出し＋スレッド切替**」にする:
  1. 会話が長くなったら（PO が新規会話ボタンを押す、または後述の自動トリガー）、現在地を handoff 資料として外部ファイルに書き出す
  2. 新しいスレッドで、handoff 資料の要約＋参照を下書きとして受け取って続ける
  3. 古い会話はトランスクリプトとして残り（必要なら L3 検索で引ける）、**情報は失われない**
- コンパクションがどうしても働く場合も、**要約は会話の外（L4 handoff 資料）に書き出してから**行う——Claude Code の「ファイルに書けばコンパクションを生き残る」と同じ保証を banto でも持つ

### 4.3 段階的開示の本格化（SKILL の実績を記憶に拡張）

- セッション開始時のシステムプロンプトには:
  - L1: 記憶の**一覧**（現行どおり。増えたら索引に縮小）
  - L2: SKILL の一覧（現行どおり）
  - L4: 進行中の文脈の**索引**（「◯◯の続きから」＋トピック／決まったこと／次の一手＋handoff 資料への参照。task-0056 の下書きと同じ形をセッション開始時にも）
- 詳細（handoff 資料全文・過去の会話・記憶の詳細）は `file.read` / `memory.recall` で引く
- これにより「コンテキストをクリアしても、番頭はどこに何があるかを知っている」状態を作る

### 4.4 実装の優先順位（フェーズ）

| フェーズ | 内容 | 根拠 |
|---|---|---|
| **P1** | **task-0056（会話の引き継ぎ）を実装** | 設計合意済み。ユーザー起点の文脈クリアが先に動く。L4 の土台 |
| **P2** | 記憶ビューアの完成（task-0023 の削除・出所可視化）＋ 記憶の自動抽出（task-0022） | 決定28で設計済み。L1 の質を上げる |
| **P3** | **トランスクリプト全文検索（L3 最小版）** | 「コンパクションで失われない」の保証。実装は SQLite+FTS5（Node 22.5+ の node:sqlite、または既存依存で賄える範囲から） |
| **P4** | 自動トリガー（`session_before_compact` フックで、コンパクションの代わりに handoff 資料を書き出してからクリア） | コンパクション格下げの自動化。pi の SDK モードでフックが使えるかは実装時に確認 |

P1 と P3 は独立に進められる。P2 は P1 と並行可。

## 5. 論点（PO 裁定待ち）

1. **クリアした会話をどこまで残すか**
   - A案: トランスクリプト＋handoff 資料だけ（検索なし。実装が軽い）
   - B案: さらに全文検索（L3）まで作る（Hermes 式。「損失なく検索可能」は唯一これ）
   - 推奨: B を視野に入れつつ P1 を先に。P3 で検索を足す
2. **自動クリアのトリガーを入れるか**
   - A案: まず手動のみ（新規会話ボタン。task-0056 のスコープどおり）
   - B案: 文脈があふれそうになったら自動で handoff を書き出して新スレッドへ
   - 推奨: A から始め、コンパクションの実績（何トークンで発動するか）を見て B を判断
3. **L1 記憶の常時注入の上限**
   - 現行は全件注入。何件（何行）まで全件注入し、超えたら索引＋オンデマンドへ移行するか
   - 推奨: 現状の件数では問題ないので、閾値は「索引が視認できる規模（目安 20〜30 件）」とし、実装は移行時
4. **handoff 資料の生成タイミングとコスト**
   - task-0056 の設計合意どおり「新規会話ボタンで自動生成（LLM 1回）」で良いか。短会話はスキップ（合意済み）

## 6. 不採用とした選択肢

- **MemGPT 式の自己管理（エージェントが関数でメモリをページング）**: 毎ターンのオーバーヘッドとモデルの関数呼び出し品質への依存が大きく、banto では「ファイル読み」で十分（調査メモ §7.2 も同旨）。自前検索 API・heartbeat ループは過剰設計
- **要約を主経路にしたまま改善する**: PO の不満（情報喪失）の根本を変えないため不採用
- **記憶の全件注入を維持したままにする**: ChatGPT の実例（33件で破綻）が示すスケール限界がある。ただし件数が少ないうちは現行のまま（論点3）
