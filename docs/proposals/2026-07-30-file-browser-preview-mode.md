# file.browser にプレビューモードを追加する提案

## 現状

`file.browser`（`packages/banto-web/src/views/FileBrowser.tsx`）は現在、ファイル内容をすべて生テキストとして表示している。以下の問題がある：

- **Markdown ファイル（.md）が生ソースのまま表示される**。見出しは `# タイトル` としか見えず、読み手は頭の中でレンダリングを補完する必要がある。画面が縦に長くなりがち（長文の Markdown を読むのに際限なくスクロールが必要）
- **図（PlantUML / Mermaid）はコードブロックとしてしか見えない**。図の形状を理解するのに頭の中でパースが必要
- **コードの色分けが無い**。ファイルの種別（.ts, .py, .rs 等）に関わらず白黒の等幅フォントで表示され、可読性が低い
- **画像ファイル（.png, .jpg 等）は表示できない**。バイナリ扱いとなり「表示できません」のメッセージが出る
- **CSV/TSV が生テキストのまま**。列構造が目視でしか追えず、表としての一覧性が無い
- **diff/patch ファイルに行単位の色分けが無い**。何が増えて何が減ったかが一目で分からない

## 提案

ファイルの内容部（右ペインの `.fb-preview`）に **preview/source の表示モード切替**を導入する。デフォルトは **preview モード**（レンダリング表示）とし、右上のトグルスイッチで生テキスト（source モード）に切り替えられるようにする。

### プレビュー対象のファイル種別

| 種別 | 拡張子 | プレビュー内容 |
|---|---|---|
| Markdown | `.md` | レンダリングHTML（見出し・リスト・リンク・テーブル・画像埋め込み・引用・コードブロック） |
| 図（PlantUML） | `.puml`, `.plantuml` | PlantUML を SVG 画像にレンダリング |
| 図（Mermaid） | `.mmd`, `.mermaid` | Mermaid を SVG にクライアントサイドレンダリング |
| 図（draw.io） | `.drawio`, `.dio` | diagrams.net viewer を iframe で埋め込み |
| ソースコード | `.ts`, `.js`, `.py`, `.rs`, `.go`, `.java`, `.c`, `.h`, `.cpp`, `.hpp`, `.css`, `.scss`, `.json`, `.yaml`, `.yml`, `.xml`, `.sh`, `.toml`, `.rb`, `.php`, `.swift`, `.kt`, `.dart` | シンタックスハイライト（テーマ切替対応が望ましい） |
| 画像 | `.png`, `.jpg`, `.jpeg`, `.gif`, `.svg`, `.webp` | `<img>` タグで画像そのものを表示 |
| データ可視化 | `.csv`, `.tsv` | テーブル表示（ヘッダ行の強調・列揃え） |
| diff | `.diff`, `.patch` | 行単位の色付き差分表示（unified モード: 追加行を緑、削除行を赤、ハンクヘッダを青）。side-by-side モードで左右並列表示も可能 |

### 種別判定のロジック

拡張子で判定する。`file.browser` は既にファイル名を持っているので、`path` の末尾から拡張子を切り出し上記マップで判定する。該当しない拡張子（または拡張子無し）は source モード固定としプレビューは提供しない（現在の生テキスト表示）。

### UI/UX

#### トグルの配置

ファイル内容部のヘッダ行（`.fb-preview-head`）の右端に、preview / source を切り替えるトグルを配置する。

```
┌──────────────────────────────────────────────┐
│ src/views/FileBrowser.tsx    [⛅ preview │ ☰ source]  [☐ 折り返し] │
│                                                │
│  (レンダリング結果または生テキスト)             │
└──────────────────────────────────────────────┘
```

- **トグルのデザイン**: セグメント切り替え（タブ状）か、バイナリスイッチ（ON/OFF）。
  現時点では**セグメント型**（`preview` | `source` の2ボタン）を推す。理由：
  - どちらのモードかが一目で分かる
  - マウスクリック1回で切り替わる
  - タブキー＋Enter でも操作可能

- **デフォルト**: preview モード（レンダリング表示）
- **source モード**: 現在の生テキスト表示と同じ。ただし可能ならシンタックスハイライトも適用する（コード種別の場合）

#### スクロール位置の維持

モード切替時にスクロール位置を維持する。preview → source → preview の往復で同じ位置に戻るのが望ましい。ただしレンダリング結果と生テキストで行数が異なるため、完全一致は難しい。少なくとも**切替前のスクロール位置に対応する割合位置**に復元する（例：50%スクロールしていたら切替後も50%の位置）。

#### 状態の保持

- トグルの状態は**コンポーネントのローカル state** で持つ（URLパラメータやグローバルステートに保存はしない）。ファイルを切り替えたりタブを閉じるとリセットされて構わない
- ただし「デフォルトは preview」という挙動は固定

#### ソースモードの折り返しトグル（右上チェックボックス）

source モードで、長い行を**画面端で折り返すかどうか**を、ヘッダ行（`.fb-preview-head`）の右端のチェックボックスで切り替えられるようにする。

````
┌────────────────────────────────────────────────┐
│ src/views/FileBrowser.tsx  [⛅ preview │ ☰ source] [☐ 折り返し] │
│                                                  │
│  (レンダリング結果または生テキスト)               │
└────────────────────────────────────────────────┘
````

- **配置**: `.fb-preview-head` の右端。preview/source トグルの右隣に「☐ 折り返し」チェックボックスを置く
- **動作**:
  - チェック ON: `.fb-code` に `white-space: pre-wrap; overflow-wrap: anywhere` を適用し、画面端で折り返す（長いトークン・URL でも折り返す）
  - チェック OFF: 現状のまま（`white-space: pre; overflow-x: auto` の横スクロール表示）
  - 行番号（`.fb-lineno`）は `white-space: pre` のままにして折り返さない
- **表示条件**: source モードのときのみ表示する。preview モードでは非表示（レンダリング結果の折り返しは表示側のレイアウトに任せる）
- **デフォルト**: チェック OFF（現状の挙動を維持。コードは折り返さず横スクロールが既定）。長い行を読むときだけ ON にする。※既定を ON にして読みやすさ優先にする案もあるが、行番号と横スクロールの現状を変えない OFF を推す
- **状態の保持**: preview/source トグルと同じくコンポーネントのローカル state で持つ（ファイル切替・タブを閉じるとリセットされて構わない）
- **実装**: `.fb-code` にクラス（例: `is-wrap`）を付与して CSS で切り替える。CodeBody へ `wrap` props を追加する想定
- **行番号・行強調との関係**: 折り返し ON でも行番号は論理行（`\n` 区切り）に対応し、行強調（`from`/`to`）も論理行基準で動く。折り返しは表示だけの問題なので既存機能に影響しない

#### Diff 表示モードトグル（unified / side-by-side）

diff ファイル（`.diff`, `.patch`）の preview モードでは、さらに unified / side-by-side の表示モードを切り替えられるトグルを追加する。

```
┌────────────────────────────────────────────────────────┐
│ foo.diff                    [⛅ preview │ ☰ source]  [≡ unified │ ▯ side-by-side] │
│                                                          │
│  (差分表示)                                               │
└──────────────────────────────────────────────────────────┘
```

- **デフォルトは unified**（行単位の色分け表示。CSS クラス `gv-add`/`gv-del`/`gv-hunk` を流用）
- **side-by-side モード**: 左パネルに削除行（旧ファイル）、右パネルに追加行（新ファイル）を並べて表示。対応する行が無い場合は空行で埋める
- **diff ファイル限定**: side-by-side 表示は `.diff` / `.patch` ファイルにのみ有効。Markdown やソースコード等の他の種別では diff トグル自体を非表示にする
- **トグルの表示条件**:
  - preview モードかつ diff ファイルのときのみ diff トグルを表示する
  - source モードでは diff トグルをグレーアウトまたは非表示にする（生テキストに side-by-side は意味が無い）
- スクロール位置の維持については preview/source トグルと同様の扱い

### 技術検討

#### 1. Markdown レンダリング — 既存依存で対応可能（追加不要）

**既存**: `react-markdown` ^10.1.0 ＋ `remark-gfm` ^4.0.1（`packages/banto-web/package.json` に既に記載）

`react-markdown` で Markdown を React 要素にレンダリングし、`remark-gfm` でテーブル・取り消し線・タスクリスト等の GFM 拡張に対応する。これらは既に依存に入っているため**新たな依存追加は不要**（D6）。

CSS は既存の `.markdown` クラスのスタイル（`styles.css`）を流用する。

#### 2. Mermaid レンダリング — 依存追加が必要

**既存**: 該当するライブラリ無し

**提案**: `mermaid`（`mermaid.js`）を依存に追加する。

- **理由**: Markdown 内の Mermaid コードブロックおよび `.mmd` / `.mermaid` ファイルのプレビューに対応する唯一の実績あるクライアントサイドレンダラ。PlantUML とは異なりサーバ不要で SVG を生成できる
- **方式**: 
  - Markdown 内の Mermaid コードブロック（```mermaid）は `react-markdown` の `components.code` でフックし、`mermaid.run()` または `mermaid.render()` で SVG に変換して埋め込む
  - `.mmd` / `.mermaid` ファイルのプレビューはファイル内容を直接 `mermaid.render()` に渡す
- **バンドルサイズ**: mermaid.js は約 700KB（minified）と大きいが、動的インポート（`import("mermaid")`）で遅延読み込みすれば初回ロードに影響しない

#### 3. PlantUML レンダリング — 依存追加が必要（軽量）

**既存**: 該当するライブラリ無し

**提案**: `plantuml-encoder` を依存に追加する。

- **理由**: PlantUML はサーバサイドレンダリングが一般的だが、banto は自宅 VM で稼働するとは限らない（第一実装は pi coding agent on VS Code）。オフラインでもプレビューできるよう、`plantuml-encoder` で URL エンコードした上で `https://www.plantuml.com/plantuml/svg/{encoded}` の画像として埋め込む（オンラインサーバに依存するトレードオフは「技術検討 補足 B」で議論）
- **代替案**: Banto の Kobo 側に PlantUML レンダラを立てる（サーバサイド）。ただし Kobo の完成を待つことになり、番頭が先に動く方針（D10）に反する
- **注意**: PlantUML オンラインサーバは外部依存であり、ネットワークが切れた環境では機能しない。将来 Kobo に render 機能が入った時点で差し替える想定をコードに残す（アダプタパターン or 設定切替）

#### 4. draw.io レンダリング — 追加依存不要（iframe 埋め込み）

**既存**: 必要なし

**方式**: diagrams.net の公式 viewer を iframe で埋め込む。

- `.drawio` / `.dio` ファイルは中身が XML（MxGraph 形式）。テキストファイルとして `file.read` で内容を取得できる
- 取得した XML を URI エンコードし、`https://viewer.diagrams.net/` のクエリパラメータとして埋め込む
  - URL 例: `https://viewer.diagrams.net/?embed=1&ui=min&spin=1&svg=1&load=data:application/xml,{エンコード済みXML}`
  - パラメータの意味:
    - `embed=1`: 埋め込みモード（ヘッダ類を非表示）
    - `ui=min`: 最小 UI（ツールバーをコンパクトに）
    - `spin=1`: ローディングアニメーション表示
    - `svg=1`: SVG 出力（ベクター品質）
- **ネットワーク依存**: diagrams.net viewer は CDN 上の OSS であり、自ホストも可能（https://github.com/jgraph/draw-image-export を参照）。将来 Kobo VM に置けばオフラインでも使える
- **代替案**: Kroki.io 経由のレンダリング（draw.io に対応している）。ただし要外部依存で viewer 直使いと変わらない
- **非推奨**: mxgraph ライブラリを直接バンドルする（ライブラリサイズが大きく、React との統合も面倒）。iframe 分離の方が安全
- **セキュリティ**: viewer.diagrams.net は sandbox 属性付き iframe で埋め込むことを前提とした設計。`allow-scripts` は必要だが `allow-same-origin` は外す

#### 5. シンタックスハイライト — 依存追加が必要

**既存**: 該当するライブラリ無し

**提案**: `shiki` または `highlight.js` のいずれか。以下比較：

| 軸 | Shiki | highlight.js |
|---|---|---|
| 方式 | ビルド時にテーマをバンドル or 動的読み込み | ランタイムにハイライト |
| バンドルサイズ | テーマ込みで大きいが、動的インポート可 | コア 20KB＋言語パック（動的読み込み可） |
| 言語数 | 190+（TextMate 文法） | 190+（独自文法） |
| 品質 | VS Code と同じパーサ（onsiguri/TextMate） | 独自パーサ。概ね正確だが VS Code より劣る場合あり |
| React 対応 | `@shikijs/rehype` / `@shikijs/react` | `highlight.js` を useEffect で適用 |
| テーマ切替 | 豊富（VS Code テーマそのまま） | 多数あるが Shiki より少ない |

**推奨**: `shiki`（`@shikijs/rehype` ＋ 動的インポートで軽量化）

- **理由**: 
  - レンダリング品質が VS Code と同等（同一パーサ）
  - `rehype` プラグインとして `react-markdown` のコードブロックに直接適用できる
  - テーマ切替が容易（`github-light` / `github-dark` 等）
  - Markdown 内のコードブロックと、ソースコードファイルのプレビューの両方で同じエンジンを使い回せる
- **トレードオフ**: 初回ハイライトが highlight.js よりやや遅い。ただし動的インポートで分割すれば体感への影響は小さい

#### 6. 画像プレビュー — 追加依存不要

単純な `<img>` タグで表示する。追加依存不要。

**注意点**:
- `file.read` が返す content は文字列（テキストファイルが前提）。画像ファイルは `binary: true` で返ってくるため、現状の取得方法では src に当てられる URL が無い
- `file.read` から返る content がバイナリファイルの場合は `undefined` になる（現在の実装を確認）。画像プレビューを実現するには **画像ファイルの内容を base64 エンコードして data URL として渡す拡張**、または **画像ファイル専用のエンドポイント（`file.read_binary` 等）** が必要
- もしくはエンドポイントが静的ファイルをホストしている場合、`{endpoint}/raw/{path}` のような URL を組み立てて `<img src>` に直接指定する方法もある（エンドポイントの実装に依存）

→ **画像プレビューは file.browser のフロントエンド変更だけでは完結せず、モジュール（workspace）側の API 拡張が必要**。本提案では画像プレビューを要件として記載するが、**実装はモジュール側の整備と合わせて行う**ことを明記する。

#### 7. CSV/TSV テーブル表示 — Papa Parse または自前パース

選択肢：
- **Papa Parse**（`papaparse`）：高機能。ヘッダ行検出、列型推論、エスケープ処理が正確。バンドルサイズ約 20KB
- **自前パース**: 簡易的なもの（行分割 → カンマ/タブ split → テーブルレンダリング）なら数十行で書ける。ただし引用符で囲まれたカンマや改行を含むセルに対応できない

**推奨**: `papaparse` を依存に追加する。理由は正確性（エスケープ処理）。ただし数百行以下の小規模ファイルが想定されるなら自前パースでも十分かもしれない——実装時の判断に委ねる。

#### 8. diff/patch の色付き表示 — 追加依存不要

##### unified モード（デフォルト）

行頭の文字（`+` / `-` / `@@`）で判定し、CSS クラスを割り振る。既に GitViewer の `gv-diff` スタイル（`gv-add` / `gv-del` / `gv-hunk`）が流用できるため、新たな依存は不要。

```
.gv-add { color: #7fb069; }
.gv-del { color: #d97b6c; }
.gv-hunk { color: #7a9cc6; }
```

##### side-by-side モード

`.diff` / `.patch` ファイルを開いたとき、preview モード内で unified 表示と side-by-side 表示を切り替えられるようにする。

- **表示形式**: 左パネルに削除行（旧ファイル）、右パネルに追加行（新ファイル）を並べて配置する
  - 行頭が `-` の行は左パネルに表示し、右パネルは空行（薄いグレー）
  - 行頭が `+` の行は右パネルに表示し、左パネルは空行
  - 行頭が ` ` （スペース、共通行）は両方に表示
  - ハンクヘッダ（`@@` 行）は両方のパネルにまたがって表示
- **行番号**: 左右それぞれに表示する（左: 旧ファイルの行番号、右: 新ファイルの行番号）。ハンクヘッダから抽出した行番号オフセットを使う
- **パース方法**: クライアントサイドで行ごとに走査し、ハンクヘッダを解析して左右の行番号を追跡する。依存ライブラリ不要
- **UI**: side-by-side モードでは `.fb-preview` 内のレイアウトが 2カラムになる。CSS Grid または flexbox で実現する
- **diff ファイル限定**: side-by-side 表示は `.diff` / `.patch` ファイルにのみ有効。他の種別ではトグル自体を非表示にする
- **巨大ファイルの制限**: side-by-side は左右2倍の横幅を使うため、1000行を超える diff では unified 表示にフォールバックする（または警告を表示する）

|------|------|--------|
| Markdown → HTML | `react-markdown` ＋ `remark-gfm` | 不要（既存） |
| draw.io 表示 | diagrams.net viewer iframe | 不要（iframe 埋め込み） |
| diff 色分け | CSS クラス（既存の `gv-add` etc.） | 不要（既存のスタイル流用） |

#### 補足 B: 依存追加の理由（D6 判断）

| 追加候補 | 追加理由 |
|----------|----------|
| `mermaid` | Mermaid 図をクライアントサイドで SVG レンダリングする唯一の実績あるライブラリ。Markdown 内のコードブロックと `.mmd` ファイルの両方に対応できる |
| `plantuml-encoder` | PlantUML ソースを URL エンコードして画像として埋め込むための軽量エンコーダ。サーバサイドレンダラを自前で立てるより低コスト |
| `shiki`（`@shikijs/rehype`） | VS Code と同じパーサによる高品質シンタックスハイライト。Markdown 内コードブロックとソースコードファイルの両方に同一エンジンを使い回せる。テーマ切替が容易 |
| `papaparse` | CSV の正確なパース（引用符内カンマ・改行セル対応）。自前パースではエスケープ処理が不完全になる |
| _`mermaid` (draw.io とは別)_ | Mermaid 図の SVG レンダリング。draw.io とは異なる図形式のため別途必要 |

**追加しないもの**: `highlight.js`（shiki で代替可）、`remark-parse` 等の低レベルパーサ（react-markdown が内包）、`rehype-*` 系（shiki の rehype プラグインで足りるものはそれを使う）

### 実装上の注意点

#### a. ファイル種別判定の場所

preview モードにするかどうかは **フロントエンド側（FileBrowser.tsx）** で拡張子から判定する。エンドポイントからヒント（MIME type 等）が返ってくるわけではないので、拡張子リストを定数として持つ。

#### b. コードブロックのシンタックスハイライトと Markdown の二重適用防止

`.md` ファイルの場合：
1. `react-markdown` でレンダリング
2. レンダリング結果内のコードブロック（```ts 等）には `shiki`（`rehype` プラグイン）でシンタックスハイライト
3. コードブロック内の Mermaid (```mermaid）は上記より先に mermaid レンダラが処理する

適用順: `react-markdown` → `components.code` で mermaid 検出 → mermaid でなければ `shiki` がハイライト

#### c. 巨大ファイルの扱い

プレビューモードでも、現在の `maxLines` 制限は引き続き適用する。特に Mermaid/PlantUML のレンダリングは内容が大きくなくても SVG 生成に時間がかかる場合があるため、ファイル全体の行数が 2000 行を超える場合は preview を無効にして source モードを強制する（または「大きいファイルのためプレビューを無効にしました」と表示する）。

#### d. モジュール側 API の拡張が必要なケース

- **画像プレビュー**: `file.read` がバイナリファイルの内容を base64 で返すか、別のバイナリ取得エンドポイントが必要
- **SVG の直接表示**: `.svg` ファイルはテキストとして読めるが、`<img src>` にそのまま渡すには content を data URL に変換する必要がある（`data:image/svg+xml;base64,...`）

これらの拡張は本提案の対象外だが、プレビュー機能の完成には必要なので「関連タスク」として記録する。

### 現在の実装との整合性

- `FileBrowser.tsx` の既存機能（ディレクトリ一覧・ファイル選択・行番号表示・行強調スクロール）は維持する
- preview モードでは行番号は表示しない（レンダリング結果に行番号は意味が無い）
- source モードは現在の `CodeBody` をそのまま使うが、可能ならシンタックスハイライトを追加する
- 行強調（`from` / `to` パラメータによる自動スクロール）は source モードでのみ有効。preview モードでは強調すべき行が特定できないため無視する
- source モードの折り返しは右上の「☐ 折り返し」チェックボックスで切り替える（既定は折り返さない＝現状維持）

### PlantUML：既定では描かない。描画先を設定したときだけ使う（2026-07-31、PO裁定）

提案は `plantuml.com` の URL に図を載せる形を既定にしていた。これは**リポジトリの中身を
第三者のサーバへ送る**ことになるので、既定にはしない——banto が扱うのは PO の未公開の
設計・仕様であり、提案が注意点に挙げた「ネットワークが切れると動かない」より、
**切れていない環境で送られてしまう**方が問題である。

**PO裁定：描画先を設定したときだけ使えるようにする。** 設定しなければプレビューは出ない
（source 表示のまま、「描画先が未設定です」と示す）。

- 設定値は**描画サーバの URL** 1つ。どこを指すかは PO が選ぶ
  - **自前（既定として推奨）**：`plantuml/plantuml-server` の Docker イメージを手元で立て、
    `http://localhost:8080` を指す。公式イメージで、pull 数 5,100万・2026-06 更新の現役
  - **公式サイト**：`https://www.plantuml.com/plantuml` を指す。**図の中身が外部へ出る**ことを
    承知のうえで選ぶ
- **既定値は空**。設定しない限り一切送信しない。「気づいたら外に出ていた」を作らない
- `plantuml-encoder`（1.4.0、依存なし）は URL の組み立てに使う。これ自体は通信しない

#### 純 JS / WASM で描く道は無い（調査済み・2026-07-31）

npm を一通り当たったが、PlantUML のレンダラを JS へ移植したパッケージは存在しない。

| パッケージ | 実態 |
|---|---|
| `plantuml-encoder` | 外部サーバ用の URL を作るだけ。**描画しない** |
| `plantuml-parser` | 構文解析だけ |
| `node-plantuml` / `plantuml-pipe` | **Java の jar を子プロセスで回す**ラッパー |

レンダラ本体が Java 実装のため、「TypeScript だけで完結」はできない。Java を同梱する案は
D6（依存を増やさない）に対して重すぎるので採らない——**サーバを立てるか外部を使うかを
PO が選ぶ**、という上の形が現実的な着地になる。

### draw.io：外部送信は要らなかった（`@maxgraph/core`）

提案は `viewer.diagrams.net` へ XML を載せる iframe 方式を採り、その理由として

|---|---|---|
| 最新 | 4.2.2（2020-10-28） | **0.24.0（2026-07-08）** |
