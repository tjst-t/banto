# 幹を「いつでも入力を受けられる待ち状態」に保つ

- 日付: 2026-08-15
- 出所: PO からの設計相談（「職人・他の幹からの通知でバンバン埋まって幹で会話ができない」「幹が情報過多で入力できないのがしんどい」）
- 調査: 職人 inv-trunk-idle-a（通知の注入経路・ターン競合・実時間の実測）／inv-trunk-idle-b（枝の起動・文脈引き継ぎ・幹枝の可視性）
- 位置づけ: 提案。実装は banto開発(thread-61)へ渡す

## 1. 結論

**推す順序は I → II → III。PO が挙げた案の順番とは逆になる。**

| # | 案 | 効く所 | 実装の重さ | 独立に出せるか |
|---|---|---|---|---|
| I | 走行中でも入力を受ける（UI の門番を外す） | 「入力できない」体感そのもの（実働時間の 33%） | 小 | 出せる |
| II | 知らせは札にし、ターンを起こすものを選ぶ | busy 時間の 44%、文脈消費、相槌ターン | 中 | 出せる |
| III | 仕事を枝へ逃がす（種類で判定・文脈は fork で引き継ぐ） | 職人の作業が幹で走ること（本丸） | 大 | I・II の後 |

**理由**: 「入力できない」の直接原因は Web UI の門番であって機構の制約ではない。サーバは走行中の入力を既に受けられる。次に効くのは知らせの選別で、実測では知らせ由来ターンの 35% が「道具ゼロ・200字未満の相槌」で終わっている——幹のターンを回す価値がそもそも無い。枝へ逃がす案は最も本質的だが、最も重く、枝の管理という新しい負債を作る。

## 2. 実測でわかったこと（推測ではない）

### 2.1 何が幹のターンを起こしているか

知らせは出所を問わず `server.notify()` → `deliverToThread()` を通り、**1件につき幹のターンを1本起こす**（server.ts:765/802）。「ログに積むだけでは足りない、気づかせるのが目的」という設計判断がコメントに明記されている（決定29）。

| 出所 | 経路 | ターン |
|---|---|---|
| PO のチャット | WS `prompt` → `promptEvenWhileBusy` 直呼び（server.ts:1420） | 起こす |
| 職人 | worker-notice.ts が 1.5 秒ポーリング → notify | 1件ごとに1本 |
| Kobo | kobo-notice.ts が 5 秒ポーリング → notify | 1件ごとに1本 |
| 環境 env | env-notice.ts が 30 秒ポーリング → notify（宛先なし） | 起こす |
| 他の幹 thread.send | handOff → notify | 起こす |
| 枝→幹 thread.consult | 札を記録 ＋ `nudge` | 起こす |
| 枝の畳み thread.merge | 札1件を記録するだけ | **起こさない** |

宛先を持たない知らせ（env・system・親を引けなかったもの）は `resolve(undefined)` → `trunk()` で**全部「帳場」に落ちる**（threads.ts:1425）。帳場が特に重いのは構造的な理由がある。

### 2.2 PO の入力はどこで止まっているか

- **サーバは受けられる。** `promptEvenWhileBusy()`（server.ts:733）が「まず送り、busy なら `streamingBehavior:"steer"` で積み直す」。Agent SDK 側は `PromptQueue` という生きた行列で、走行中の `query()` へそのまま差し込まれる。
- **止めているのは Web UI。** `Room.tsx:620` の `submit()` が `if ((text.length === 0 && …) || busy) return;` で**黙って捨てる**。`busy` は `turn_start` で立ち、**職人の知らせで始まったターンでも立つ**。送信ボタンは中断ボタンに化ける。

### 2.3 どれだけ塞がっているか（帳場・直近24時間）

SDK セッションファイルの timestamp から実測（thread の JSONL には時刻が無いため）。

- ターン **98本 / busy 合計 165分**、実働 500分のうち **33% が busy**
- 1ターンの長さ: 中央値 **61秒** / p90 176秒 / 最大 17分。30秒超 77%、60秒超 50%
- 内訳: PO 発話 51本（89分）／**知らせ 44本（72分＝busy の 44%）**
- busy ブロックの隙間: 中央値 148秒だが、**下位25%は1秒以下**。知らせが連続すると入力窓が実質ゼロになる

体感の主因は総量より**分布**。1件 49秒でも 4〜8連続すれば数分間ずっと塞がる。

### 2.4 知らせ由来のターンは何をしているか（全履歴）

| 起点 | n | 道具0件 | 道具0件かつ200字未満 |
|---|---|---|---|
| po | 107 | 12% | 8% |
| notice 全体 | 297 | 42% | **35%** |
| notice:worker | 104 | 20% | 10% |
| notice:kobo | 118 | 51% | **46%** |
| notice:env | 53 | 64% | **57%** |

**kobo・env の知らせは半分が相槌で終わる。職人の報告だけは違う**（中央値で道具2件・909字動いている）。ここが「札にしてよいもの」と「働くもの」の境目。

### 2.5 文脈の消費

知らせは `harness.prompt()` を通る＝**セッションの user メッセージとして累積し、章を畳むまで消えない**。帳場の知らせは文字量の **76% が職人の報告**（中央値 2032 字）。1章あたり中央値 5件・13,099字。章畳みは失敗しうる（実際に2回、`stopReason: length` で失敗し「文脈はそのまま伸び続けます」と記録されている）。

### 2.6 調査で見つかった穴（この相談とは別に直す価値がある）

1. **畳んだ枝へ知らせが配られ、畳んだ枝のターンが回る。** `resolve` は畳んだスレッドも返し（threads.ts:1420）、`deliverToThread` は state を見ない。ハーネスも生きたまま（`dispose()` はサーバ終了時のみ）。枝へ逃がす設計を採るなら必ず塞ぐ。
2. **abort 直後に知らせを取りこぼす疑い。** `abort` は `thread.notices` の列に触らないので、中断してもすぐ次の知らせが走り出して再び busy になる。加えて、解放された `.then` が `start()` の `finally` より先に `prompt()` を呼ぶと、閉じられる直前の `PromptQueue` へ push されて消えうる（マイクロタスク順序次第・要検証）。
3. **幹と枝が同じ職人・同じ環境を二重に触れる。** `worker.steer` / `worker.list` にスレッドの検査が無く、env はスレッドに紐づかない。
4. **Agent SDK バックエンドで自動コンパクションを止めていない。** pi 側は `setAutoCompactionEnabled(false)` を呼ぶが、`claude-agent-harness.ts` に相当する設定が無い。banto の章立てと二重に畳んでいる可能性（要確認）。
5. **番頭は自分の threadId を知らない**（bin.ts:1152）。

## 3. PO の3案の判定

| PO の案 | 判定 | 根拠 |
|---|---|---|
| 1. ターン終わりに1分以上かかる処理は即座に枝へ | **そのままでは実装できない** | 機構は時間を測っていない（turn-budget.ts は道具の呼び出し回数のみ・60/100/120 で警告と遮断）。掛かる時間は事前に判らず、**動き出したターンを事後に枝へ移す手段も無い**。判定は着手前にやるしかない → **閾値ではなく種類で決める**しかない |
| 2. 幹のコンテキストを引き継いで分岐する枝 | **できる（思ったより安い）** | Agent SDK に `forkSession(sessionId, {upToMessageId?})` が公式にある（transcript を複製し UUID を振り直す）。pi にも `forkFrom` / `createBranchedSession`。**banto が使っていないだけ**。observation（artifact）は `dataDir/artifacts/<threadId>` をスレッドごとに採番しているので、枝のストアを幹の trunkId へ向ければ（bin.ts:1088）`a-0007` はそのまま解決する。system prompt は毎 run 渡し直しで履歴に残らないので identity の差し替えで足りる。記憶は元々 trunkId 共有 |
| 3. 幹か枝かが判るツール | **もうある** | システムプロンプトに「You are in the branch「…」, off the trunk「…」」「You cannot open a branch from here」が生成されて入る（bin.ts:444-491）。`thread.list` にも「＊いまのこの会話」。**残る不便は「自分の threadId を知らない」ことだけ**で、これは別の小さい修正 |

## 4. 設計案

### 案 I — 幹は常に受け付ける（門番を外す）

**やること**
- `Room.tsx` の busy ガードを外し、走行中も送信できるようにする。送信と中断を**併存**させる。
- 割り込みの意味論を決めて UI に出す: 「いまの作業に足す」（= steer で融合）／「止めて話す」（= abort してから新しいターン）。
- **PO の発話を知らせの列より優先する**。いまは abort しても `thread.notices` の残りがすぐ走り出して再び塞がる。
- 上記 2.6-2 の取りこぼしを検証して塞ぐ。

**壊れる所**: 走行中に送ると現状は「走っているターンに融合」する（割り込んで先に答えるのではない）。PO の期待とずれると混乱するので、UI の文言で明示が要る。abort 中断は履歴に `Claude Code process aborted by user` の system 通知として残り、`tool_end` の来なかった道具が `running` のまま残る（次回起動時に `failed` へ確定）。

**受け入れ基準の骨**
- ターン走行中に送信したメッセージが捨てられない（現状は黙って捨てる）
- abort 後、列に残った知らせより PO の発話が先に処理される
- 走行中に送った知らせ／発話が `PromptQueue` の入れ替えで消えない（2.6-2 の再現テスト）

### 案 II — 知らせは札、ターンを起こすものを選ぶ

**やること**: `notify` の「記録＋配信」と「ターンを回す」を分離する。**部品は既にある**——`thread.consult` が実例で、`ThreadRegistry.consult` が札を記録し `nudge` が別途ターンを回している。`nudge` を呼ばなければ札だけが出る。UI 側の未読（`marksUnread` → `unreadThreadIds`）もそのまま使える。

知らせを3階級に分ける:

| 階級 | 対象 | 挙動 |
|---|---|---|
| 札だけ | Kobo の進捗、env、system | 記録＋配信のみ。ターンを回さない。UI が未読で光る |
| 束ねて1ターン | 職人の報告 | 一定の窓でまとめるか、PO の次の発話の先頭に束ねて渡す |
| 即ターン | 職人の**質問**（待ちが発生する）、判断が要るもの | 従来どおり。あるいは取次（inbox）へ |

**効果**: busy の 44% を占める知らせのうち、相槌で終わる分（kobo 46%・env 57%）が丸ごと消える。文脈消費（章あたり 13,099字）も束ねる分だけ減る。

**壊れる所**: 決定29「ログに積むだけでは足りない」と**正面から対立する**ので ADR の改訂が要る。職人が質問して待っているのに番頭が気づかない事故が起きうる（→ 質問だけは即ターンで守る）。「宛先なしの知らせが全部帳場へ落ちる」構造（threads.ts:1425）も併せて見直したい。

**受け入れ基準の骨**
- Kobo の進捗・env の知らせで幹のターンが 0 本になる
- 札は履歴と UI に残り、未読が付く（消えない・見落とせない）
- 職人の質問は従来どおり即ターンで届く
- 束ねた報告は次の1ターンで全件渡る（間引かれない）

### 案 III — 仕事を枝へ逃がす（PO 案1・2の実装できる形）

**やること**
- **判定は種類**: 職人へ委譲する仕事・調査・複数往復が要る検討は、**着手前に**枝を開く。時間では判定しない（測れないし移せない）。
- **枝を開くコストを下げる**: `forkSession` / `forkFrom` で幹の文脈を引き継ぐ枝を作れるようにする。instruction を書き切らなくてよくなる（PO 案2）。artifact ストアを幹単位に寄せる（bin.ts:1088）。
- **畳む側**: (1) 畳んだ枝への配達を止める（2.6-1）(2) 還す条件が満たされた枝を促す仕掛け——いまは3日放置で取次に札が出るだけ（threads.ts:1490、`BRANCH_STALE_DAYS`）(3) 開いている枝の**上限**（超えたら開けない・畳めと言う）。

**この案が自動的に効く点**: 職人の報告の宛先は `origin=banto:<threadId>` から引かれ、**delegate した会話そのものへ届く**（worker-notice.ts:362）。枝で委譲すれば報告は枝へ行き、幹には来ない。そして `thread.merge` は**幹のターンを回さない**（札1件だけ）ので、**枝を畳んでも幹は埋まらない**。ここは既に良い設計になっている。

**壊れる所・コスト**
- fork は文脈を丸ごと複製するので枝が最初から大きい文脈を抱える（章の閾値 0.6 にすぐ当たる＝トークン代が増える）。`upToMessageId` で切る運用が要る。
- 枝が増える。誰がいつ畳むのか——上限と促しが無いと放置される（いま上限なし・自動畳みなし）。
- 幹と枝が同じ職人・環境を二重に触る危険（2.6-3）。
- `thread.consult` は幹のターンを回す（10分に10回まで）。枝が増えると consult で幹が埋まる新しい経路ができる。

**受け入れ基準の骨**
- 幹から fork した枝が、親の会話の内容を前提に応答できる（instruction を書かなくても続きが通じる）
- 枝から親の観測 ID（`a-0007`）が解決できる
- 畳んだ枝へ知らせが配られない／畳んだ枝のターンが回らない
- 開いている枝が上限に達したら新しい枝を開けない（畳めと言われる）

## 5. 対立軸への答え

**(a) 幹を守る vs (b) 幹を軽くする** → **(a) が先。ただし最後は両方要る。**
busy 時間の 44% が知らせで、そのうち相当量が相槌。これは「幹に届く価値」を主張できない純粋な無駄で、消せば消しただけ効く。(b) が効くのは職人の報告（＝実際に働いている分）だけで、実装が重く枝の管理という負債が付く。**通知は「幹に届くこと」自体に価値があるので、消すのではなく札にして、対応は枝がやる**という分け方が正しい——これは (a) と (b) の合流点で、案 II と案 III は排他ではない。

**閾値 vs 種類** → **種類。** 時間を測る口が無く（turn-budget.ts は回数のみ）、事前に判らず、事後に移せない（fork はセッション単位で、走行中のターンを移す口ではない）。「1分以上」は原理的に実装できない。

**枝の増殖** → `thread.merge` が幹のターンを回さないので「還すときにまた幹が埋まる」は起きない（札1行のみ）。危ないのは `consult`（ターンを回す・10分に10回）と、畳まれない枝。畳む側の設計を案 III に含めた。
