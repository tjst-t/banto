# worker.list にページネーションを追加する提案

## 現状

現在 worker.list には `projectTag` と `includeClosed` の2パラメータしかなく、ページネーション機構が無い。長期運用で close 済み worker が蓄積すると一覧が膨大になり、使いにくくなる。

## 提案する追加パラメータ

### A. limit / offset 方式

| パラメータ | 型      | 既定値 | 説明         |
|------------|---------|--------|--------------|
| `limit`    | number  | 20     | 最大取得件数 |
| `offset`   | number  | 0      | スキップ件数 |

古典的なOFFSET/LIMIT方式。実装が単純で、任意のページへ直接移動できる。ただし、大きな offset になるとデータベース側の走査コストが増加する。

### B. cursor / after / limit 方式

| パラメータ | 型       | 既定値 | 説明                         |
|------------|----------|--------|------------------------------|
| `after`    | string   | 未指定 | 前回の最後の worker ID（カーソル） |
| `limit`    | number   | 20     | 最大取得件数                 |

カーソルベース方式。最初のリクエストでは `after` を省略し、レスポンスに次回用のカーソル（最後の worker ID）を返す。大量データでも安定した性能を保てるが、任意ページへのジャンプができない。

## 備考

あわせて「全体の総件数」を返すかどうかも検討が必要。

- 総件数を毎回計算すると、大規模データ時にパフォーマンス負荷が増える。
- オプション扱い（例: `includeTotal: boolean`）にするか、別エンドポイントで提供することが望ましい。
