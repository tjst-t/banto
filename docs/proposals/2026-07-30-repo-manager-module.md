# repo-manager モジュール提案

## 現状

### 閲覧専用の `git.*` ツール

現在 workspace モジュール（`packages/banto-host/src/modules/workspace.ts`）が提供する `git.*` ツールはすべて**閲覧専用**である。決定24 で「Git 閲覧系を基本GUIセットに追加するが、変更操作（stage / commit / branch作成等）は持たない」と明示されており、実装もそれに従っている。

| ツール | 機能 | 読み取り | 書き込み |
|--------|------|----------|----------|
| `git.status` | 作業ツリーの状態 | ✅ | ❌ |
| `git.diff` | 差分表示 | ✅ | ❌ |
| `git.log` | コミット履歴 | ✅ | ❌ |
| `git.branches` | ブランチ一覧 | ✅ | ❌ |
| `git.show` | コミット詳細 | ✅ | ❌ |
| `git.blame` | 各行の由来 | ✅ | ❌ |

### 閲覧専用の `file.*` ツール

同じ workspace モジュールの `file.*` ツールも閲覧専用である（file.list / file.read / file.stat / file.find / file.grep）。ファイルの作成・編集は職人に委譲する設計（D10）。

### 問題

- **リポジトリのクローン、ブランチ作成/切替、コミット、プッシュ/プル等の操作ができない**。番頭が「この変更をコミットして」「新しいブランチを切って」と指示しても、自分で実行できず職人に委譲するしかない。
- **複数のリポジトリやワークツリーを管理する仕組みが無い**。1つのワークスペース内に複数の Git リポジトリが存在しうるが、現在の `git.*` ツールは `repoRoot` に固定された1リポジトリだけを扱う。
- **ワークツリー（`git worktree`）の管理ができない**。複数のブランチを同時に作業できるワークツリー機能が全く使えていない。
- **Kobo のマージキュー・マージゲート（ADR-0009）は日常的なGit操作をカバーしない**。Kobo は CI 通過後のマージやゲート判断を担うが、番頭の日常的な操作（ブランチ切替、コミット、プッシュ等）は対象外である。

## 提案

**repo-manager モジュール**（仮称）を新設する。これは既存の `git.*` を変更せず、`repo.*` 名前空間で読み取りも含めた包括的なリポジトリ操作ツールを提供するモジュールである。

### `git.*` との関係

- `git.*`（閲覧専用）— **変更しない。現状のまま維持する。** 決定24 は引き続き遵守する
- `repo.*`（管理・操作）— 新モジュール。読み取り（リモート一覧等）から書き込み（コミット・プッシュ等）までを含む

`git.*` は workspace モジュールのまま据え置き、`repo.*` は新しい repo-manager モジュールが提供する。ツールの重複（例：`git.branches` と `repo.branch.list`）は許容する——前者は workspace モジュール（基本GUIセット）の一部としての「閲覧専用」、後者は repo-manager モジュールの一部としての「操作を含む」で役割が異なる。番頭は状況に応じて使い分ける。

## モジュール構成（ADR-0010 4点セット）

| 要素 | 内容 |
|------|------|
| 接続情報 | 管理下のリポジトリ一覧（設定で指定、または番頭が動的に追加）。既定は workspace のルート。絶対パスまたは workspaceRoot からの相対パスのいずれかを許容するかは設計上の考慮点（後述） |
| 番頭へのTool | `repo.*` 名前空間の各種操作ツール（下記一覧） |
| キャンバスGUI | `repo.manager` — リポジトリ管理ダッシュボード（下記に詳細） |
| SKILL | 「リポジトリ操作の基本手順」「変更のコミットフロー」等。ただし `repo.*` ツール自体が単発操作なので、SKILL は複数ツールを組み合わせた手順（例：「feature ブランチでの作業フロー」）を想定 |

### 提供するTool

#### リポジトリ管理

| Tool | パラメータ | 説明 |
|------|-----------|------|
| `repo.clone` | `url`（必須）、`dir`（任意） | リポジトリをクローンする。`dir` 省略時はリポジトリ名から自動決定 |
| `repo.init` | `dir`（必須） | 新規リポジトリを初期化する |
| `repo.remote.list` | `repoPath`（任意） | リモート一覧を返す |
| `repo.remote.add` | `repoPath`（任意）、`name`、`url` | リモートを追加する |
| `repo.remote.remove` | `repoPath`（任意）、`name` | リモートを削除する |

#### ブランチ操作

| Tool | パラメータ | 説明 |
|------|-----------|------|
| `repo.branch.list` | `repoPath`（任意） | ブランチ一覧（ローカル＋リモート追跡）を返す |
| `repo.branch.create` | `repoPath`（任意）、`name`（必須）、`base`（任意） | ブランチを作成する。`base` 省略時は現在のHEADから |
| `repo.branch.switch` | `repoPath`（任意）、`name`（必須） | ブランチを切り替える（git checkout / git switch） |
| `repo.branch.delete` | `repoPath`（任意）、`name`（必須）、`force`（任意） | ブランチを削除する |
| `repo.branch.merge` | `repoPath`（任意）、`from`（必須）、`into`（任意） | ブランチをマージする。`into` 省略時は現在のブランチへ |

#### コミット操作

| Tool | パラメータ | 説明 |
|------|-----------|------|
| `repo.stage` | `repoPath`（任意）、`files`（必須） | ファイルをステージする |
| `repo.unstage` | `repoPath`（任意）、`files`（必須） | ファイルをアンステージする |
| `repo.commit` | `repoPath`（任意）、`message`（必須） | コミットする。`--allow-empty` は意図的に禁止（空コミットが必要なら職人へ） |
| `repo.push` | `repoPath`（任意）、`remote`（任意）、`branch`（任意） | プッシュする。各種パラメータ省略時は upstream 設定に従う |
| `repo.pull` | `repoPath`（任意）、`remote`（任意）、`branch`（任意） | プルする。各種パラメータ省略時は upstream 設定に従う |

#### ワークツリー管理

| Tool | パラメータ | 説明 |
|------|-----------|------|
| `repo.worktree.list` | `repoPath`（任意） | ワークツリー一覧を返す |
| `repo.worktree.add` | `repoPath`（任意）、`path`（必須）、`branch`（任意） | ワークツリーを追加する。`branch` 省略時は現在のブランチから |
| `repo.worktree.remove` | `repoPath`（任意）、`path`（必須） | ワークツリーを削除する |

#### タグ操作（任意）

| Tool | パラメータ | 説明 |
|------|-----------|------|
| `repo.tag.list` | `repoPath`（任意） | タグ一覧を返す |
| `repo.tag.create` | `repoPath`（任意）、`name`（必須）、`ref`（任意） | タグを作成する。`ref` 省略時は HEAD |

### 提供するGUI

**repo.manager** — リポジトリ管理ダッシュボード（キャンバスGUI、kind: `repo.manager`）

以下の情報と操作を1画面にまとめて表示する。

#### ヘッダ部
- 管理下のリポジトリ一覧（プルダウンまたはタブで切替）
- 各リポジトリのパス・状態（clean / dirty）・現在のブランチ

#### ステータス部
- `git status --short` 相当の変更ファイル一覧（追加・変更・削除・未追跡）
- ファイル単位のチェックボックス → stage / unstage 操作

#### ブランチ管理部
- ローカルブランチ一覧（現在のブランチを強調表示）
- リモート追跡ブランチ一覧
- ブランチ作成（名前入力＋作成ボタン）
- ブランチ切替（一覧から選択＋切替ボタン）
- ブランチ削除（削除ボタン＋確認ダイアログ）
- ブランチマージ（from と into の選択＋マージボタン＋確認ダイアログ）

#### コミット部
- コミットメッセージ入力エリア
- コミット実行ボタン（未ステージのファイルがある場合は警告表示）
- プッシュボタン（プッシュ先の remote/branch 指定＋実行）
- プルボタン

#### リモート管理部
- リモート一覧表示
- リモート追加（名前＋URL の入力フォーム）
- リモート削除（確認付き）

#### ワークツリー部
- 現在のワークツリー一覧
- ワークツリー追加（パス＋ブランチの入力）
- ワークツリー削除（確認付き）

#### 操作確認ダイアログ

次の操作には確認ダイアログを必須とする：
- ブランチの削除（未マージの場合は特に警告）
- ブランチのマージ（競合の可能性を通知）
- プッシュ（リモートへの副作用があるため）
- プル（ローカルの変更が上書きされる可能性を通知）
- ワークツリーの削除

確認ダイアログは「はい / いいえ」の2択とし、「今後この確認をスキップする」のような永続的設定は設けない（D9：確認を省く判断は番頭自身が行うべきであり、GUIの都合で迂回させない）。

#### 表示状態の保持
- 現在選択中のリポジトリ・ブランチ等はコンポーネントのローカル state で持つ
- キャンバスに開き直したときにリセットされて構わない（永続化しない）
- ただし「最後に開いたリポジトリ」をセッション起点で記憶できる余地は残す（設計時検討）

## 既存ツールとの関係・役割分担

### `git.*` との棲み分け（決定24 の再確認）

決定24 は「基本GUIセットに Git 閲覧系を追加する。閲覧専用とし、変更操作は持たない。番頭の役割は『見て判断する』ことであり、リポジトリを変更する作業は職人へ委譲する（D10）」と定めている。この方針は**維持する**——`git.*` はこのまま閲覧専用であり続ける。

`repo.*` は `git.*` とは**別の名前空間・別のモジュール**である。決定24 の制約は `git.*` に対するものであり、`repo.*` はこの制約を受けない。閲覧専用ツールと管理操作ツールが併存する形になる。

**重複の許容**：`git.branches`（閲覧専用）と `repo.branch.list`（管理用）は同じ情報を返す可能性がある。これは設計上の重複ではなく、用途の違いに基づく：
- `git.branches` → 番頭が「今どうなっているか」を素早く確認するための閲覧専用。workspace モジュールの一部
- `repo.branch.list` → repo-manager が管理するリポジトリのブランチ一覧。GUI や後続の操作（switch / delete 等）のためのデータ取得

### Kobo との役割分担

Kobo にはマージキュー・マージゲート（ADR-0009）がある。repo-manager が提供する `repo.branch.merge` は**あくまでローカルでのブランチマージ**であり、CI を通過した PR の自動マージ等とは責務が異なる。

| 操作 | repo-manager | Kobo マージキュー |
|------|-------------|-------------------|
| ローカルブランチのマージ | ✅ | ❌ |
| CI 通過後のマージ | ❌ | ✅ |
| ゲート判断（マージ可否） | ❌ | ✅ |
| コンフリクト解決 | ❌（職人へ委譲） | ❌（職人へ委譲） |

### 職人との役割分担（D10 の維持）

「複雑なGit操作は職人に任せる」という方針（D10）は維持する。repo-manager は**番頭自身が日常的な操作**を素早く行うための道具であり、以下は引き続き職人に委譲する：

- **複雑なマージコンフリクトの解決** — repo-manager は `repo.branch.merge` を提供するが、コンフリクトが発生した場合は「コンフリクトが発生した」と報告し、解決は職人に委譲する
- **大規模なリファクタリングに伴う Git 操作** — 多数のファイルを跨ぐ staging や interactive rebase 等
- **Git hooks や CI との連携が必要な操作**
- **Git LFS / submodule の操作**

つまり repo-manager は「素早くコミットしてプッシュしたい」「ちょっとブランチを切り替えたい」という**番頭の日常業務を効率化する**ものであり、「複雑なGitワークフローを代行する」ものではない。

### workspace モジュールとの関係

workspace モジュール（`packages/banto-host/src/modules/workspace.ts`）はファイル閲覧と Git 閲覧を提供する組み込みモジュールである。repo-manager モジュールはこれとは**別の独立したモジュール**とする。両者は同じ `git` CLI を内部で使う可能性があるが、モジュールとしては独立して登録される。

**内部実装の共通化**：`git` CLI の実行ラッパー（`git()` 関数、`execFile` の promisify 等）は現状 `git-tools.ts` に閉じており、repo-manager も同様のラッパーを持つことになる。これを共通ユーティリティとして banto-core または banto-host の共有モジュールに抽出できるかは検討に値する。ただし決定27b（モジュール間呼び出しはレジストリ＋直接）の趣旨から、単なる実装の共通化（関数の切り出し）とモジュール間のサービス呼び出しは区別する——前者は許容される共有ライブラリの範囲内である。

## 設計上の考慮点

### 1. セキュリティ — `repoPath` の制限

`repo.*` ツールは Git リポジトリに対して破壊的操作（コミット・プッシュ・ブランチ削除等）を行う。`repoPath` パラメータの制限方針について2つの案がある。

#### 案A: workspaceRoot 内に制限（推奨）

- `repoPath` は workspaceRoot からの相対パスまたは workspaceRoot のサブパスに制限する
- workspaceRoot 外のパスは拒否する
- **メリット**: 番頭が誤って重要な外部リポジトリを破壊するリスクを軽減する。既存の `file.*` / `git.*` と同じ制約範囲
- **デメリット**: 明示的に別の場所にあるリポジトリ（例：`~/oss-projects/some-lib`）を管理したい場合に使えない
- **安全側に倒す**: 最初は workspaceRoot 内に制限し、必要に応じて後で拡張する

#### 案B: 任意のパスを許可

- 任意の絶対パス・相対パスを受け付ける
- **メリット**: 柔軟性が高い。複数のワークスペースを跨いだリポジトリ管理が可能
- **デメリット**: システムの重要なリポジトリ（`/etc` 以下等）を誤操作するリスクがある
- 緩和策: `/etc` や `/usr` 等のシステムパスを拒否するブロックリストを併用する

**本提案は案A（workspaceRoot 内に制限）を推す。** 理由：
- 既存の `git.*` / `file.*` との一貫性（同じ workspaceRoot の制約下で動いている）
- D1（不可逆な選択）に抵触する操作（`repo.push` でリモートにプッシュ等）を踏み間違えるリスクを減らせる
- 最初は制限して、必要に応じて拡張する方向が安全

### 2. 副作用の可逆性と D1・D9

`repo.*` ツールの中には外部に累積する副作用を持つものがある。

| ツール | 副作用 | 可逆性 | D1/D9 判断 |
|--------|--------|--------|------------|
| `repo.commit` | ローカルリポジトリの履歴に追記 | 可逆（git reset / revert） | D9 範囲内 |
| `repo.push` | リモートリポジトリに履歴を公開 | **不可逆**（公開後は撤回困難） | **D1 に抵触しうる** |
| `repo.branch.delete` | ブランチの削除 | 可逆（gc 前なら reflog から復元可） | D9 範囲内 |
| `repo.branch.merge` | マージコミットの作成 | 可逆（reset / revert） | D9 範囲内 |
| `repo.remote.add/remove` | リモート設定の変更 | 可逆（再追加/削除） | D9 範囲内 |

**D1 判断**: `repo.push` によるリモートへのプッシュは、一度公開したコミットの撤回が困難なため、不可逆な選択（D1）に該当する。番頭がこれを自由に呼べる条件を明文化する必要がある。

**提案する条件**:
1. **pre-release では制限なし** — 番頭は自由にプッシュできる。壊してもよい（CLAUDE.md D9）
2. **確認ダイアログ必須** — GUI から操作する場合、プッシュ前に「リモート `{name}` の `{branch}` にプッシュします。よろしいですか？」の確認を入れる。Tool 直接呼び出しの場合は、番頭が自覚的に行うものとして確認は省く（Tool の description に「この操作はリモートリポジトリに不可逆な変更を加える」と明記）
3. **累積する副作用が外部に及ぶ場合、PO 判断が必要なこともある** — 具体的には「公開パッケージのリリースタグを push する」「本番ブランチへ直接 push する」等。これらは判断基準として「利用体験を変え、かつ本物のトレードオフか」（D9）で番頭が判断し、不可逆と判断したら escalate する

### 3. Kobo 非依存

repo-manager は Kobo が無くても動くべきである（決定23 の精神）。ローカルの `git` コマンドだけで全ての操作が完結するようにする。Kobo のマージキュー・マージゲートに依存した操作（例：「CI が通ったらマージ」）は repo-manager の範囲外とする。

これは既存の `git-tools.ts` の設計方針（Kobo にも Worker Pool にも依存しない）をそのまま踏襲する。

### 4. 複数リポジトリの管理

1つのワークスペースに複数の Git リポジトリが存在しうる（monorepo 以外の構成、サブモジュール、独立したプロジェクトの混在等）。repo-manager は以下のレベルで複数リポジトリを管理する。

#### 管理対象の検出

- モジュール初期化時に workspaceRoot 以下の Git リポジトリをスキャンする（`.git` ディレクトリの存在)
- 手動でリポジトリを追加・削除できる（`repo.add` / `repo.remove` 相当の内部管理操作）
- 設定ファイルで明示的に管理対象を指定できる（既定は workspaceRoot）

#### 各Toolの `repoPath` パラメータ

- ほとんどの Tool は `repoPath`（任意）パラメータを持つ
- `repoPath` 省略時は workspaceRoot（のGitリポジトリ）を対象とする
- workspaceRoot が Git リポジトリでない場合、`repoPath` の指定は必須とする

#### GUI での扱い

repo.manager のヘッダ部で管理下のリポジトリをプルダウンまたはタブで切り替えられるようにする。複数リポジトリを同時に表示する必要はない（タブ方式に統一：決定5・決定8）。

### 5. 既存の `git.*` との内部実装の共通化

repo-manager も内部で `git` CLI を呼び出す（`execFile`）。`git-tools.ts` には既に `git()` 関数（引数配列で git を呼ぶラッパー）がある。repo-manager 側でも同じ関数を必要とする。

**選択肢**:

1. **`git-tools.ts` の `git()` 関数をエクスポートして再利用する** — 簡単だが、`git-tools.ts` は workspace モジュールの内部実装の一部であり、モジュール間の依存関係が暗黙的になる
2. **共通ユーティリティ（`banto-host` 内の `git-utils.ts` 等）に抽出する** — `git()` 関数を独立したファイルに切り出し、workspace モジュールと repo-manager モジュールの両方から参照する。ツール名の決定22（同じ `git` CLI を使う）にも沿う
3. **各モジュールが独自に持つ** — 重複が発生するが、モジュール間の暗黙の依存を防げる

**本提案は案2（共通ユーティリティへの抽出）を推す。** 理由：10行程度のラッパーを2箇所に書くのは保守性を損なう（出力上限の変更やエラーハンドリングの改善が片方だけになる）。ただし抽出範囲は `git()` 関数と `bounded()` 関数に限定し、ツール定義（`defineNamespacedTool` を使った各Toolの定義）までは共通化しない——各モジュールが独自の判断でツールを定義する権利を残すため。

### 6. エラーハンドリング

Git 操作のエラーには以下の種類がある。I2（エラーを握りつぶさない）に従い、適切に区別して報告する。

| エラー種別 | 例 | 対応 |
|-----------|-----|------|
| リポジトリ不在 | `fatal: not a git repository` | 明確なエラーメッセージ + repoPath が正しいか確認を促す |
| 操作拒否 | `fatal: refusing to merge unrelated histories` | stderr をそのまま添えて失敗させる |
| コンフリクト | `Automatic merge failed; fix conflicts` | 「コンフリクトが発生しました。解決は職人に委譲してください」と報告 |
| 認証失敗 | `Permission denied (publickey)` | 認証情報が未設定であることを報告。ssh-agent や credentials の設定は職人の責務 |
| ネットワーク | `Could not read from remote repository` | ネットワーク到達性の問題を報告 |

### 7. GUI のモバイル対応

決定8（モバイル対応を最初から前提とする）に従い、repo.manager もモバイル対応を前提に設計する。

- リポジトリ一覧 → プルダウンセレクタ（タブは画面幅を取るため）
- 複数セクション（ステータス・ブランチ・コミット等） → 縦スクロールで順に並べる
- 確認ダイアログ → 画面中央のモーダル（決定5 のタブ方式と一貫性を保つ）
- 操作ボタン → 十分なタップターゲットサイズ（44px 以上）を確保

複雑な操作（マージ元の選択とマージ先の選択等）はモバイルでも使いやすいフォームにする。

### 8. `git.*` の未来（将来的な統合の可能性）

本提案では `git.*`（workspace モジュール）と `repo.*`（repo-manager モジュール）を別モジュールとして維持することを前提としている。しかし中長期的には以下の議論がありうる：

- **`git.*` を repo-manager モジュールに統合する** — 閲覧も操作も同じモジュールが持つ方が一貫性がある。ただし決定24 の「閲覧専用」の制約は維持したまま（閲覧ツールとしての `git.*` は repo-manager の一部分として残す）
- **統合しない** — 閲覧（workspace モジュールの `git.*`）と操作（repo-manager モジュールの `repo.*`）は別々のモジュールとして独立させる。workspace モジュールが提供する基本GUIセットとしての位置づけと、repo-manager の管理ツールとしての位置づけを分離したままにする

**本提案は統合しない立場を取る。** 理由：
- 決定24 は workspace モジュールの `git.*` を「基本GUIセット」として定義しており、基本GUIセットをモジュール間で分散させると整合性が取りにくい
- `git.*` を repo-manager に移すと、workspace モジュールからファイル閲覧以外のGit関連がすべて抜けることになり、モジュールの責務が曖昧になる
- 番頭が「見るだけ」の目的で使うツールと「操作する」目的で使うツールが別名前空間にあることで、意思決定の明確さが増す（見るだけなら `git.*`、操作するなら `repo.*`）

この判断は将来の PO 裁定で覆しうる。提案の当初は分離して出し、実際の使用感を見て統合を検討するのが安全。

## 実装時の注意点

### a. `git` CLI の依存

既存の `git-tools.ts` と同様、`node:child_process` の `execFile` を使い、シェルを介さず引数配列で git を呼び出す（注入の余地を作らない）。D6 の範囲内。

### b. 出力上限

`git-tools.ts` は `MAX_OUTPUT_BYTES = 200_000` の上限を持つ。repo-manager も同様の上限を設けるが、操作系ツール（`repo.commit` 等）の成功メッセージは短いので上限の影響は少ない。`repo.branch.list` や `repo.log` 相当の出力が多いツールには適用する。

### c. Git 2.x への依存

`git branch` ではなく `git switch` / `git restore` を使う等、Git 2.23+ のコマンドを積極的に使う。`git checkout` は多機能で混乱を招くため、ブランチ切替には `git switch`、ファイル復元には `git restore` を使う。ただしエラーメッセージでユーザーに伝えるときは汎用的な表現にする。

### d. `repo.*` のTool名とSKILL名の衝突回避

SKILL名ではドットが使えない（決定26 の注意）ため、repo-manager のSKILLは `repo-clone` / `repo-branch-workflow` のようなハイフン区切りにする。Tool名は `repo.branch.create` のようなドット記法（決定9・決定22）。

### e. 内部状態（管理下のリポジトリ一覧）

管理下のリポジトリ一覧は以下のいずれかで管理する：
- 設定ファイル（YAML）に静的に記述
- モジュール初期化時に workspaceRoot 以下をスキャン
- メモリ上の状態として保持（番頭が動的に追加/削除）

永続化が必要かどうかは実装時の判断に委ねる。提案としては「設定ファイル＋スキャンによる自動検出」の組み合わせを推す（D3：導出できる値は保存しない。workspaceRoot 以下の Git リポジトリはスキャンで導出できる）。

### f. `repo.push` の認証

Git リモートへの認証（SSH鍵・credential helper・personal access token 等）は repo-manager の範囲外とする。認証情報の管理は Environment Pool（決定32e）または OS の credential helper に委ねる。repo-manager は認証情報を一切保持せず、OS の git 設定（`credential.helper`・`core.sshCommand` 等）に従う。
