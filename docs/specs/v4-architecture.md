## banto とは何か

**人に伴走し、人の助けとなるソフトウェア。** 第一の領域はソフトウェア開発
（`docs/vision.md`）。**1人で使う**ことを前提にしている。

人は banto と会話し、banto は**その人の代わりに手を動かす**——ファイルを読み書きし、
コマンドを走らせ、サブエージェントに仕事を任せ、詰まったら人に聞く。
仕事は**同じ話題が続くかぎり残り**、そこで決まったことを覚えている。

### 何が独自なのか——2つだけ

banto の独自性は**この2つに絞られている**。それ以外は既にあるものを使う。

**① Project / Thread というモデル**（§1.1・§2.2）

仕事の入れ物（**Project**）があり、その中に主の会話（**Base Thread**）と、
枝分かれした会話（**Fork Thread**）がある。Project は**決まったこと（Memory）**を
持ち、Thread はそれを共有する。

**「次に AI へ何を渡すか」を決めるのは、この層だけ**——会話を畳む・やり直す・
枝を作る・繋ぐ道具を変える・別の会話に頼む。**全部が同じ1つの決定の現れ**であって、
別々の機構ではない（§2.2）。

**② 機能はすべて MCP のインターフェースの向こうにある**（§1・§5）

ファイルも、コマンドも、サブエージェントも、**Module** として MCP で繋がる。
**Module は banto のコードに一切依存しない**——他の MCP ホストでもそのまま動く。
core が持つのは「**MCP のインターフェースの向こう側に置けないもの**」だけである。

### 作らないもの

**既に名前がついている問題は、既知の答えを使う**（規則12）。banto が発明しない：

| | 使うもの |
|---|---|
| Canvas の表示 | MCP Apps（`ui://`） |
| AI がその場で作る UI | A2UI |
| 人に聞く | MCP の Elicitation |
| 覚え書きの形式 | Agent Skills（`SKILL.md`） |
| Module の配布・接続 | `server.json` / `mcp.json` |
| 会話の器 | assistant-ui |
| 履歴の持ち方 | event sourcing |
| 閉じ込め | Landlock |
| 返信の無限往復を防ぐ | RFC 3834 |

### この文書の読み方

- **決まったことしか書いていない。** 未決は §10 に分けてある
- **§10 に無く、ここにも無いものは、まだ存在しない**
- Module の一覧は `docs/specs/v4-modules.md`
- なぜそう決めたか・却下した案は `docs/notes/`

## 0. 前提

**v3 を捨てて v4 を作ることは決定**（2026-08-29、ユーザー）。

**v3 から拾うのは知見だけ**（§9）。コードは持ってこない。「v3 の実装がこう
なっている」は、v4 がどうあるべきかの根拠にならない——v3 は「Module の境界を MCP
で区切る」という原理が固まる前に書かれたものだから。CLAUDE.md が `main` に対して
置いている姿勢（「部品として引くのはよいが、土台にはしない」）を、v3 にも適用する。

**生きているもの**：`docs/requirements.md`（要件）と `docs/lessons.md`（教訓）。

**`docs/adr/adr-0001-architecture.md` は生きていない**（2026-08-29、ユーザー）。
**参考にすることはあっても、アーキテクチャの決定はゼロから実施する。**
理由は v3 のコードを捨てるのと同じ——あの決定群は「Module の境界を MCP で区切る」
という原理が固まる前に積み上がったもので、v3 の実装と一体で育っている。
「決定N がこう言っている」を v4 の根拠にしない。

したがって**この仕様書が、v4 のアーキテクチャ決定の唯一の置き場**である。
旧 ADR から引き継ぎたい決定があるなら、**ここで改めて決め直して、ここに書く**
（同じ結論になってもよいが、そのときも根拠は旧 ADR ではなく、いま示せる理由）。

## 1. 箱は2つ——core と Module

| | 定義 | 契約 |
|---|---|---|
| **core** | Module 以外の部分。すべての土台 | — |
| **Module** | 機能を提供する、**完全に独立したコード** | **MCP** |

**Module は banto のコードに一切依存しなくてよい。** MCP の JSON-RPC も
MCP Apps の postMessage ハンドシェイクも、依存ゼロで素で書ける程度のものである
——**「TypeScript でないモジュールが1本、実際に動いている」は Phase 1 の完了条件**
（要件C6）。

**「共有ライブラリ」は第3の箱ではない。** TypeScript で Module を書く人が楽を
するための道具は作ってよいが、それは `zod` や `@modelcontextprotocol/sdk` と
同じ **npm 依存**であって、アーキテクチャの分類ではない。「このライブラリは
core か Module か」という問いは立てない。

**banto が出荷する Module も、プロセスは in-process でよい。** 契約（MCP か否か）と
プロセス境界（in-process か subprocess か）と、コードの依存関係は、**独立した3つの軸**。
in-process であることは、core のコードに依存する理由にならない。

### 1.1 用語

**入れ物と会話を別の語で呼ぶ。** 1語に両方を担わせると、枝分かれを説明するたびに
どちらの意味かを言い足すことになる。

| 語 | 何か |
|---|---|
| **Project** | **入れ物。** 同じ仕事が続くかぎり残る単位 |
| **Base Thread** | Project にただ1つある、主の会話 |
| **Fork Thread** | Base Thread から枝分かれした会話。0個以上 |
| **Memory** | Project の「決まったこと」。毎ターン system prompt に入る |
| **Global Memory** | **banto 全体で覚えておくこと**（人の名前など）。Project をまたいで効く。毎ターン system prompt に入る（決定・2026-09-05、§2.2） |

**単に「Memory」と書いたら Project の Memory を指す。** 全体のほうは必ず
`Global Memory` と書く。

**「Global」を選ぶ理由**（決定・2026-09-05）：`Instance Memory` を最初に採ったが、
**「全体の記憶」に読めない**（instance は設定の階層を指す語であって、記憶の広がりを
言う語ではない）。`global` ↔ `project` は一般的な対で、初見のエンジニアが範囲を
そのまま想像できる（規則11）。**設定の語彙（「instance 既定 → Project 上書き」、
§2.10）はそのまま**——あちらは階層の話で、こちらは記憶の範囲の話。

- **Project は、1つの Base Thread と 0個以上の Fork Thread を持つ。**
- **Thread** は「1本の会話」を指す語として使う（Base か Fork かのどちらか）。
  入れ物の意味では使わない
- Fork は「同じ Project で別の話題を並行して進める」ためのもの。
  「同じ話題のまま積もった分を整理する」のは Fork ではなく、Base Thread を
  畳む操作（§2.2）

**「Project」を選ぶ理由**：入れ物のほうは「同一プロジェクトが続くかぎり残る」という
性質で説明されてきた。名前を実態に合わせる（規則11：初見のエンジニアが機能を
想像できる語）。「Thread」を入れ物に使うと、プログラミングの thread（実行の筋）と
も紛れる。

**「Memory」を選ぶ理由**：**この機構には既に名前がある**（規則12）——Claude Code が
`CLAUDE.md` を「project memory」と呼んでいるものと、置き場も役割も同じ（毎ターン
system prompt に入る、人と AI が明示的に積む、決まったこと）。`base` は banto の
独自の言葉より、初見のエンジニアが機能を想像できる語を選ぶ（規則11）。**`Base Thread` の
「Base」との衝突も同時に消える。**

**「Trunk / Branch」は採らない**：banto はソフトウェア開発の道具で、**`branch` と
`merge` は git に取られている**（要件に「ブランチ」が8箇所、いずれも git の意味。
`repo` の役割は worktree を切って merge・rebase する）。会話の Branch を足すと
「このブランチをマージして」が git のことか会話のことか読めなくなる。
**`Fork` は空いている**——banto はリポジトリを fork しない（worktree を切る）ので、
git 語彙とぶつからない。加えて `Trunk`/`Branch` にすると名前から `Thread` が消え、
「Project の下にある Thread たち」という階層が読めなくなる。

## 2. core の内訳

### 2.1 Event Store

唯一の真実。起きたこと全部を**追記だけ**で記録し、書き換え・削除はしない。
「いまの状態」はキャッシュせず、履歴を畳み込んで（`fold`）その場で作る（規則3）。

- **名前は `Event Store`。** 「ログ」は「捨ててよい・
  巡回削除される・診断用の副産物」という含みを持つが、これは失えば banto の全部が
  消えるもの。event sourcing の確立した呼び名に合わせる（規則12）
- **`State`（`fold()` の結果）は `State` のまま。** Event Store が State を
  直接持つわけではないので `StateStore` とは呼ばない——そう呼ぶと「`get()` すれば
  今の状態が返る」と誤解させ、規則3 が名前から消える
- **「畳んだ状態を安く得る」設計を最初から含める。** 後付けが難しい部類
  （読み込み経路・fold 関数の形・購読の仕組み全部に関わる）。これも名前がある
  問題——event sourcing の read model / projection
- 規則3 との整合線：**いつでも捨てて0から再計算でき、再計算結果と必ず一致する**
  ものはキャッシュであって写しではない

#### read model の方式を決めた（item 4、決定・2026-08-30、実測 `poc/01-item4-event-store-read-model/`）

**潰した問題は速度ではなく API の形。** v3 の失敗（§9）は「読み取り API が全件配列を
返すので、状態が欲しい全員が全件 fold するしかない——畳み直しが25箇所、1ハンドラの
中で5回」。実測は3本の arm（`read(): Event[]` ＋ 自由な fold ／ `state()` ＋ 増分適用 ／
それにスナップショットを足したもの）を、同一の `fold`/`apply` で比較した。

**決めたこと：**

- **インターフェースは3つ。** `append(event): Promise<Cursor>` ／ `state(): State`（同期・O(1)）／
  `subscribe(listener): () => void`——**購読者に届くのは更新後の `State` であって
  イベントだけではない**（イベントだけを配ると、購読者側で fold し直す形が戻り、
  v3 の失敗が購読経路から再発する）。全件を順に読む必要があるものには
  `readFrom(cursor): AsyncIterable<...>` を出す。**配列は返さない**
- **`read(): Event[]` は落とす。** 構造で決まる——`state()`/`subscribe` 経由なら
  1リクエストあたりの全件 fold 回数は常に0（実測で確認）。`read(): Event[]` を
  経由する形は、呼ぶたびに1回、v3 の失敗をそのまま再現する
- **State は追記時の増分適用で保つ。写しではない**——規則3 との整合は
  「派生物を全部消してから再計算した結果と、増分で保った State が必ず一致する」を
  プロパティ試験で機械的に保証する（別プロセスでの再開・並行 append・`at` の逆行・
  torn な最終レコード・毒入り snapshot を含めて確認済み）。**この試験の形は
  本実装に必ず入れる**
- **State は素の JSON で表せるものに限る**（Map・Set・クラス実体を持たない）
  ——そうでないとスナップショットの一致を機械で確かめられない
- **並びは追記順（記録の位置）で決まる。`at` では決まらない**（`at` を逆行させた
  イベント列でも規則3 が壊れないことを確認済み）
- **スナップショットを採る。** cold start の実測が決め手——1M件・1GBのログで、
  スナップショット無し（毎回全件 fold）は **3.46〜4.47秒**、スナップショット
  ありは **27ms**。**スナップショット無しでは実用にならない**
- **スナップショットの起動時検証は軽量に限る（`foldVersion` と `cursor` の整合
  だけ）。ハッシュによる改竄検出（`coveredBytesHash`・`integrityHash`）は
  `verifyIntegrity()` という別の・明示的に呼ぶ・遅くてよい操作に分離する。**
  実測で判明したトレードオフ——ハッシュ検証を起動時の必須チェックにすると、
  ログの `[0, cursor)` を読むコスト（1M件で3.4秒）がそのままスナップショットの
  効果を食い潰す。**軽量な起動では、スナップショット自身の `state` フィールドが
  改竄されているケースを検出できない**（version・cursor は正しいまま state だけ
  書き換えられた場合）。この制約は隠さず、この文書に残す
- **スナップショットは temp + rename + fsync(dir) で原子的に書く。いつ消してもよい**
  （消しても state 自体は変わらない——規則3 のプロパティ試験で確認済み）
- **追記形式は JSON Lines**（1レコード = `JSON.stringify(event) + '\n'`）。
  **`\n` で終わっていない最終レコードは「無い」とみなす**（crash-torn の回復）。
  次の `append` の前に切り詰める。**黙って捨てず、切り詰めたことを記録する**（規則2）
- **fsync は追記ごと。** append は fsync が終わってから解決し、購読者への通知も
  その後——crash で消える状態を画面や購読者に見せない。実測では append
  （fsync込み）の p95 が1ms未満で、購読者への通知遅延も同程度
- **位置は不透明な `Cursor`（`{ seq, byteOffset }` 相当）。バイト位置をインターフェースの外に
  出さない**——ファイル分割・アーカイブ（§2.9・§10 item 5）を先に閉じないため
- **`append` はプロセス内で直列化する。** 実測で判明した必要性——直列化しない
  実装で並行 append（200件、`Promise.allSettled`）を実際に走らせたところ、
  追記用の fd キャッシュがレースし fd がリークした。直列化キューを1本挟むだけで
  解消する
- **0からの再計算にかかる時間：1M件で約4秒。**「いつでも捨てて再計算できる」は
  実用的に成り立つが、**無料ではない**——この秒数は明記しておく
- **常駐メモリは、Project 全体で1つの `State` のままで十分だった**（実測：
  1M件で GC後 53.7MB、閾値256MBに対して大きく余裕）。**keyed projection
  （Project 単位などで分割する形）は、この規模では要らない。** 必要になったら
  同じ枠組み（named・versioned・rebuildable なプロジェクション）で足せる

#### 保管そのものの上限を決めた（item 5、決定・2026-08-30）

上の read model の話（読み取りを安く保つ）とは別の軸——**追記のみで減らないので、
長く使うほどディスクは伸びる**という問題。

- **削除は採らない。** Event Store という名前を選んだ理由自体が「ログは捨てて
  よい・巡回削除される、という含みを持つが、これは失えば banto の全部が消える
  もの」だった（§2.1 冒頭）。**保管上限に達したら古い区間を消す、という設計は
  この前提と正面から矛盾する**ので除外する
- **セグメント分割を採る。** 1ファイルが際限なく伸び続けるのではなく、一定の
  サイズ（あるいは件数）で新しいセグメントファイルに切り替える。**`Cursor` を
  不透明にしておいた設計（`{ seq, byteOffset }` 相当、上記）がそのまま活きる**
  ——将来 `Cursor` の内部表現を「どのセグメントの何バイト目か」に広げても、
  インターフェースの外にバイト位置を出していないので、Cursor を使う側のコードは変わらない。
  具体的な分割の閾値は実装時に決める
- **古いセグメントは、必要なら外部ストレージへ移送できる。** 移送は「アーカイブ」
  であって「削除」ではない——fold は移送先のセグメントも読みに行くので、
  読み取り速度が落ちることはあっても、内容は失わない
- **いまは実用上困らないと判断し、閾値や移送の詳細設計はここで打ち切る**
  （規則7——まだ困っていないことに設計コストを使わない、v3 の教訓と同じ判断）。
  実測の目安：v3 本番7日で888イベント・324KB（§9）。`tool.result` を含めても
  年間で数GB規模に収まる見込みで、1人で使う前提（`vision.md`）のローカル
  ディスクでは当面問題にならない

### 2.2 Project / Thread（Memory を含む）

「仕事の入れ物とは何か、会話とは何か、枝分かれとは何か」の定義そのもの（§1.1）。
Thread は「Memory ＋ それ以降のメッセージ」なので、**Memory はこの定義の一部**。

**この項目の仕事は「次に Runner へ何を渡すか」を決めて保持すること。** 以下は
すべて**同じ1つの決定の現れ**であって、別々の機構ではない：

| 操作 | Runner に渡すもの |
|---|---|
| 会話を畳む（同じ Thread のまま整理する） | resume-point 無し |
| やり直す | 過去の resume-point |
| Fork Thread を立てる／その中で分岐する | 引き継いだ resume-point ＋ **最初のターンで `forkSession`**（下記）。SDK の枝分かれで**キャッシュを引き継げる**——実測 §8 |
| Fork Thread の Memory を親の最新版に置き換える（item 6、下記） | 変更後の Memory（マージではなく置き換え） |
| 接続する Module 集合を変える | 変更後の Module 集合 |
| 効かせる Skill 集合を変える（§5.6） | 変更後の Skill 集合 |
| サブエージェントに頼む（§4.1） | Subagent Module 呼び出し——**新しい Thread は core 側に作らない**（§4.1 訂正、2026-08-31）。core が受け取るのは実行結果の転記のみ |
| 別の Thread へメッセージを送る（§4.2） | 宛先 Thread に user 役のメッセージを積んで走らせる |
| **既定モデル・既定 reasoning effort をこの Project で上書きする**（決定・2026-09-01） | 以後の**新規** Thread 作成時の初期値（走行中の Thread には効かない） |
| **使う資格情報の割り当てを変える**（§2.8） | 以後の新規会話が使う資格情報 |
| **セキュリティ境界の根を変える**（`docs/specs/v4-security.md`） | 以後の新規会話に効く構成 |

**Runner に「畳む機能」「やり直し機能」「分岐機能」を別々に作らない。**

#### 設定のカスケード（決定・2026-09-01）

上の3行が典型だが、**runtime config（§2.6）は既定で全項目が Project 単位に
上書き可能**とする。個別に「この項目は Project で上書きさせない」としたい
ものが出てきたら、**ブラックリストで塞ぐ**——既定は「開いている」側にする
（新しい項目を足すたびに「Project で上書きできるか」を都度判断させない）。

**カスケードは3段**：**instance 既定 → Project 上書き（あれば） → Thread が
作成時点の実効値を確定**。Thread が確定した後は §3 の規律（走行中の枝の
先頭は変えない）のとおり、その Thread の中では変わらない——変更は次に
作る Thread から効く。

**Memory は Project が持ち、その Project の Thread が共有する**（`Project Memory`）。
Fork Thread は枝分かれした時点の Memory を引き継ぐ。

#### Fork Thread と親 Memory の食い違いを決めた（item 6、決定・2026-08-30）

**Fork Thread は分岐した時点の Memory を固定的に持ち続ける——これは維持する。**
親の Memory が後から伸びても自動では反映しない。git の branch が、切った後に
main が進んでも自動では追随しないのと同じメンタルモデルで、意図した動作である
（§2.9）。

**運用上の扱いとして、明示的な「親の Memory を取り込む」操作を足す。** 新しい
機構は要らない——§2.2 冒頭の表（次に Runner へ何を渡すか）に並ぶ操作の一種
として、「Fork Thread が使う Memory のスナップショットを、分岐時点のものから
親の最新のものへ**置き換える**」を追加するだけ。**マージではなく置き換え**
——Fork Thread 側の Memory の独自差分（あれば）との衝突解決は考えない、
単純に親の最新版に揃える。**自動では取り込まない**（§3 の規律「黙って変えない」
——キャッシュ境界を切る変更は明示的にだけ）。

**走行中の枝の先頭は変えない。** これは §3 のキャッシュ規律から出る制約——
すでに走っている枝の system prompt が途中で変わると、そこから後ろのキャッシュが
崩れる。**変更は次のキャッシュ境界から効く。**

#### Memory の書き換えと上限を決めた（item 3、決定・2026-08-30）

- **物理的な書き換え・削除はしない。訂正は無効化イベントの追記で行う。**
  Event Store は追記のみ（規則3・§2.1）なので、Memory の「訂正」もその規律の
  外に出ない——元の行を消すのではなく、`memory.invalidated` 相当のイベントを
  追記し、fold 結果（AI に見える Memory の中身）からその行を除外する。
  これは banto の発明ではなく、規則3から機械的に導かれる帰結
- **大きさを計測し、閾値を超えたら追記を拒否する**（要件 G5「際限なく膨らませない」）。
  **自動要約は採らない**——LLM による要約は「決まったこと」の意味を静かに
  歪めるリスクがあり、規則1（自己申告を信頼しない）・G2（持ち越すのは決まった
  ことだけ、経過は入れない）の精神に反する。「伸ばすに任せる」も G5 に反するため
  除外。Skill と同じ progressive disclosure も、Memory は「常に効くべき決まった
  こと」なので部分読み込みは意味が変わり、不適
- **拒否されたら判断待ちとして人に上げる。** 新しい機構は要らない——§2.4 の
  Elicitation 経由の判断待ちがそのまま使える。選択肢は「古い行を無効化する」
  「別の Project を始める」等を Elicitation の enum で提示する
- 近い先例：Claude Code の project memory（`CLAUDE.md`）は自由に編集でき上限で
  拒否しないが、banto は Project 単位で長期間使われる前提が強く、G5 の要件も
  明示されているため、そのまま踏襲しない

#### Fork Thread の最初のターンで、セッションを分岐させる（決定・2026-09-05）

**引き継いだ resume-point を、そのまま resume してはいけない。** SDK の `resume` は
**同じセッションの続き**なので、Base と Fork が同じセッションを共有し、
**両方の会話が1本に混ざる**（実測・2026-09-05——Fork で話した内容が Base 側の
文脈に出てきて、AI が「直前のターンは Fork でした」と答える状態になっていた）。

**Fork Thread の最初のターンだけ、Runner に `forkSession` を渡す**（SDK のオプション。
「resume したセッションを続けず、新しい session id へ分岐する」）。分岐後に返ってきた
session id がその Thread のものになり、2ターン目以降は普通の `resume` に戻る。

- **判断の材料は「その resume-point が自分のものか」**（`ownsSession`）。Fork は
  作られた時点では**親から借りている**だけなので false。Runner が返した session id を
  受け取った時点で true になる——**Event Store から導出**する（写しを持たない、規則3）
- **「やり直す」（過去の resume-point を明示して Fork）も同じ扱い**。借り物である
  ことに変わりはない
- **畳む**と resume-point 自体を捨てる（新規セッション）ので、この判断は要らない
- §8 の実測「`forkSession` で枝分かれ——新しい `session_id` になるが**キャッシュは
  引き継ぐ**、元の枝もそのまま続けられる」が、この決定の根拠

**2つの Thread が同じ resume-point を指している状態は、不変条件の破れ**である
（会話が1本に混ざる）。この決定より前のデータには実際に存在するので、
**ターンを走らせる時に検知して、その場で枝を分ける**——黙って壊れたまま
続けない（規則2）。

#### 走行中に増えた Memory は、メッセージで届ける（決定・2026-09-05）

**Memory の持ち主は Project**（§1.1）。同じ Project の Thread が共有する。

**system prompt に入る Memory は、Thread 作成時（畳んだときは畳んだ時点）に
確定する**——§3 の規律「走行中の枝の先頭は変えない」がそのまま効く。

**その後に別の Thread で増えた分は、次のターンの user メッセージに添えて届ける**
（§2.3）。system prompt を書き換えないので**キャッシュは崩れない**。無効化
（`memory.invalidated`）も同じ経路で「この決定は取り消された」と届ける。

- **同じ差分を毎ターン繰り返さない。** メッセージ列は追記なので、一度届けば
  会話に残る。どこまで届けたかは Event Store から fold できる（規則3）
- **Fork Thread のスナップショットの決定（item 6）は変えない。** 届けるのは
  「親の Thread でこう決まった」という**知らせ**であって、Fork が持つ Memory の
  置き換えではない。取り込みは明示操作のまま——item 6 の意図（キャッシュ境界を
  切る変更は明示的にだけ）は、メッセージで届ける限り損なわれない
- **出所を添える**（どの Thread で決まったか）。Fork の側は「別の枝で決まったこと」
  として読める必要がある

#### Global Memory（決定・2026-09-05）

**banto 全体で覚えておくことを置く場所を作る。** 人の名前・呼ばれ方・Project に
紐づかない共通の好み。**Project Memory と同じ規律をそのまま使う**——新しい機構は
作らない：

- 追記のみ。訂正は無効化イベントの追記（item 3 と同じ）
- 大きさの上限を超えたら追記を拒否し、判断待ちとして人に上げる（G5、item 3 と同じ）
- **走行中は変えない**（Thread 作成時に確定）。増えた分は Project Memory と同じく
  メッセージで届ける
- system prompt での位置は Project の文脈より**前**（§2.3）——全 Project で同一
  なので、キャッシュの前方一致が **Project をまたいで**効く

**まだ決めていない**：AI 自身が Global Memory に書けるようにするか
（`remember_decision` は Project 向け）。**Phase 0 では人が書くだけ**にする——
AI が「人の名前」を勝手に書き換える経路を、観測の仕組みが揃う前に開けない。

### 2.3 Runner

Claude Agent SDK に触れる**唯一のインターフェース**。ベンダ固有の型・語彙をこの層の外に出さない。

- **呼ばれるたびに使い捨ての、状態を持たない実行係。** 渡された入力
  （system prompt 材料・接続する Module 集合・resume-point）で1回実行するだけ
- **resume-point がどこから来たかを一切知らない・気にしない。** 畳む・やり直す・
  分岐・Module 追加削除のどれに由来するかは Project / Thread 側の話
- **モデルB を採る**：1ターン＝1回の `query()` 呼び出し、`resume` で継続。
  常時起動の streaming session（モデルA）は採らない——host 再起動に弱く、
  大量の長期生存 Project と相性が悪い（アイドルな Project に常駐コストが積み上がる）。
  **性能実測で確認済み**（2026-08-30、§8）——1ターンの固定費はプロセス起動の
  約2.4秒が支配的で、**Module を毎ターン繋ぎ直す費用は付随的**（subprocess 8本で
  +0.45秒）。**本決まり。**
- **「1本に保つ」は規律であって、パッケージ境界が保証するものではない。**
  `@anthropic-ai/claude-agent-sdk` を import してよい場所を1つに限る仕掛け
  （依存関係の lint 等）を置く

#### 割り込みのために、入力を開いたまま保つ（実測 2026-08-30）

**Base Thread に割り込みは要る**（§8）。実測の結果、**成立するが条件が付く**：

- **`prompt` を非同期の並びにし、そのターンの間ずっと開いたままにする。**
  1つ流して閉じると `interrupt()` は
  **「Query closed before response received」で失敗し、処理は完走してしまった**
  （36.7秒、成功扱い）
- 開いたまま保つと **`interrupt()` は成功し、6.6秒で止まった**
- **`close()` も効く**（8.0秒で停止）

**つまり Runner は「文字列を1つ渡して終わり」ではない。** 1ターンの間だけ
入力の並びを開いておく——**セッションを永続させるモデルAとは別物**で、
モデルB（§2.3）のままで割り込みが手に入る。

**止めたターンは「エラー」として返る**（下記、実測）。

**入力を開いたままにする必要があるのは `interrupt()` だけではない**——
**すべての制御要求**（`close()`・`rewindFiles()`・使用量の照会など）が同じ条件を
持つ。閉じた状態で呼ぶと **「Query closed before response received」** で失敗する
（実測 2026-08-30。ここで2回踏んだ）。**Runner の契約に最初から入れておく。**

#### ファイル編集の巻き戻しは `resume` をまたぐ（実測 2026-08-30）

`enableFileCheckpointing` を有効にすれば、**別の呼び出しで `resume` してから
過去の発言まで巻き戻せる**（`canRewind: true`、ファイルは実際に戻った）。

**ただし巻き戻し先の識別子が、ストリームから取れない。** 流れてくる `user` の
メッセージは**すべて tool の結果**で、**人の発言そのものは流れてこない**
——巻き戻しはその uuid を要求する。

**取れるのは CLI がディスクに書く転写ファイルからだけ**である
（`~/.claude/projects/<cwd をエンコードしたもの>/<セッション>.jsonl`）。

> **これは重い依存である**（規則8）。**banto が CLI のディスク上の形式に依存する**
> ことになり、その形式は banto の契約ではない。
> **巻き戻しを実装するなら、この依存を1箇所に閉じて、形式が変わったら
> 気づけるようにする**（読めなければ黙って諦めず、はっきり断る——規則2）。

#### 止めたターンの記録（実測 2026-08-30）

`interrupt()` で止めると、結果は **`error_during_execution` かつ `is_error: true`**
で返り、**そこまでの出力は結果に載らない**（`output_tokens: 0`）。

**したがって banto は、流れてきた分を自分で記録しておく必要がある**
——結果メッセージを待って組み立てる作りだと、**止めた瞬間に何も残らない**（規則2）。
**止めたことは「失敗」ではなく「人が止めた」として区別して記録する。**

#### システムプロンプトは core が全文を組み立てる（決定・2026-09-05）

**`claude_code` プリセットを使わない。** core が全文を組み立てて `systemPrompt` に
渡す。プリセット＋追記（`append`）では次の3つが解けない：

- **無い tool の使い方が書いてある。** banto は組み込み tool を `WebSearch` /
  `WebFetch` だけに絞っている（Shell への経路は Landlock で絞った Shell Module
  経由だけ、`docs/specs/v4-security.md`）のに、プリセットは Bash / Read / Edit /
  TodoWrite / Task 等の使い方を語り続ける。**仕様と実態の食い違い**（規則8）で、
  追記では打ち消せない——本文が勝つ
- **SDK 側の記憶が文脈に入る。** 実 daemon で `Memory files: 155 tokens` を観測
  （2026-09-05）。banto の Memory（§2.2）と**真実が二箇所**になる（規則3）
- **人格が「CLI のコーディングエージェント」になる。** banto 中核は領域の意味を
  知らない（vision「4. 開発は最初の領域にすぎない」）

**system prompt に入れるのは2層だけ。順序は固定。**

| | 何を書くか | いつ変わるか | キャッシュ |
|---|---|---|---|
| **1. 骨格** | **banto という場の説明**（Project / Thread / Fork / Memory / Module / 判断待ちが何か）と、**伴走の作法**（人に聞くときは Elicitation、決まったことは Memory に残す、出力の作法） | banto のバージョンが上がったときだけ | **静的**（境界より前） |
| **2. Global Memory**（§2.2） | banto 全体で覚えていること（人の名前など） | 人が編集したとき。**走行中の Thread には効かない** | **静的**（境界より前）——全 Project で同一なので **Project をまたいで**前方一致する |
| **3. Project の文脈** | Project 名・root、Memory、人が書く Project 固有の指示 | **Thread 作成時に確定**し、その Thread の中では変わらない（§2.2 の設定のカスケードと同じ扱い） | 境界より後。ただし走行中は不変 |

`systemPrompt` は**配列**で渡し、2 と 3 の間に `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` を
置く——**骨格と Global Memory は全 Project・全 Thread で前方一致する**
（§3 のキャッシュ規律）。

#### ターンごとに変わるものは system prompt に入れず、そのターンに添える（決定・2026-09-05）

**system prompt に入れてよいのは、その Thread の中で変わらないものだけ。** 変わる
ものは**その回の user メッセージに添える**——メッセージ列は追記なので、何を添えても
前方一致は壊れない。理由は2つとも §3 から出る：

- **走行中の枝の先頭を変えないため。** system prompt はメッセージ列より前にあるので、
  1バイト変われば**そこから後ろのキャッシュが全部崩れる**
- **Fork のキャッシュ継承を捨てないため。** Fork Thread は親の resume-point を
  引き継いでキャッシュも引き継げる（§8 実測）。system prompt に「これは Fork」と
  書けば分岐した瞬間に親と先頭が変わり、**引き継げるはずのキャッシュを自分で捨てる**

**手法自体は SDK も採っている**——`excludeDynamicSections` は cwd・git status 等を
system prompt から剥がして**最初の user メッセージとして入れ直す**（SDK の型定義に
明記）。banto は同じことを自前でやる。

**添えるのはこの4つ。同じ1つの機構で扱う**（別々の仕掛けを作らない）：

| 添えるもの | どう書くか | なぜ system prompt に置けないか |
|---|---|---|
| **このターンの開始時刻** | **「今日は〜」と断定しない。「このターンの開始時刻」として渡す**——長いターンなら終わるころには過去になっている（規則8 の精神）。いまの時刻が要る作業は、そのとき tool で取り直す | **日をまたぐだけで変わる。** 置いた瞬間、日付が変わるたびに走行中の Thread のキャッシュが崩れる |
| **いまいる Thread** | Base か Fork か。Fork ならどこから分岐したか | Fork した瞬間に親と先頭が変わり、キャッシュ継承を捨てる（上記） |
| **Thread が始まってから増えた／無効化された Memory**（§2.2） | 出所（どの Thread で決まったか）を添える。**一度届けたら繰り返さない** | 走行中の枝の先頭は変えない（§3） |
| **判断待ちの状況**（§2.4.1） | いま何を人に聞いていて、何が返ってきたか | ターンの途中でも変わる |

**添える内容は Event Store の真実ではない。** 人の発言そのものは人が書いた文字列で
あり、添え物は banto がその時点の状態から**導出したもの**（規則3）。記録するのは
人の発言、渡すのは人の発言＋導出、という分担にする。

**骨格は領域不可知。** ソフトウェア開発固有の作法は骨格に書かない。それは
Module の tool description と層3（Project 指示）に置く。vision の
「第一の領域はソフトウェア開発」は**標準で繋がる Module の選び方**の話であって、
中核の人格の話ではない。

**語彙は骨格が定義する。** Project / Thread / Fork / Memory / Module / 判断待ちは
一般語だが banto 固有の意味を持つ（§1.1・§2.2）——定義しなければモデルは一般的な
意味で受け取る。**出所は §1.1・§2.2 であり、骨格はそれをモデルに向けて言い直した
もの**（§1.1 を変えたら骨格も直す）。

**個々の tool のことは骨格に書かない**（規則3）。どんな tool があるかは
`tools/list` の description が真実で、system prompt に写しを持てばいつか食い違う。
**有効な組み込み tool の一覧も骨格に列挙しない**——`WebSearch` / `WebFetch` を
許しているのは Runner の設定であって、骨格に書けば真実が2箇所になる
（設定を変えた瞬間に骨格が嘘になる）。骨格が言うのは**構造**だけ：

- **環境に触れる操作（ファイル・シェル等）は、繋がっている Module の tool を
  通してしか行えない**——組み込みの Bash / Read / Edit は無効にしてある
- **いま見えている tool の一覧が、できることの全部**。無い道具を使ったつもりで
  話を進めない

列挙が要ると分かったら、層2で **Runner の設定から導出して**渡す
——写しではなく導出なら真実は一箇所のまま。

**Claude Code のプロンプトは参考にするが、本文は持ち込まない。** 借りるのは構造と
結論（簡潔さ・スコープの規律・過剰な自己修正の説明を避ける等）だけ。写しを置くと
**根拠が banto の外に出る**——前の実装に対する姿勢（CLAUDE.md）と同じ。

**環境情報は自前で組む必要がある。** `systemPrompt` に文字列／配列を渡すと
SDK の動的セクション（cwd・git status 等）は一切付かない（`excludeDynamicSections`
は文字列のとき無効、と SDK の型定義に明記）。**これは失うのではなく、banto の
語彙と置き場で書き直す**——Thread の中で変わらないもの（Project root）は層2、
変わるもの（時刻・Base か Fork か）はターンに添える。

**完了の判定は計測**（規則1・Phase 0 の完了条件と同じ考え方）。
`getContextUsage()` が返す `systemPromptSections`（名前とトークン）で置換の前後を
実測し、**`Memory files` が 0 になること**を確認する。

### 2.4 受信箱——人のところに来るもの

**2種類が入る。性質が違うので、区別して扱う。**

| | **判断待ち** | **レビュー待ち** |
|---|---|---|
| 何を求めるか | **答え** | **確認** |
| AI の状態 | **止まっている。答えないと進めない** | **止まっていない。もう終わっている** |
| 応答 | `accept` / `decline` / `cancel`（Elicitation発）／ Thread に普通に返信する（AI 自身の発話発） | 見た／取り込んだ／差し戻した |
| 溜めてよいか | **よくない**——進行が止まっている | **よい** |

**入れ物は1つにする。** 人から見れば「自分のところに来ているもの」であり、
分けると2箇所を見に行くことになる。**種類で区別し、判断待ちを先に出す**
——止まっているものが先。

#### 判定の軸を一般化した（決定・2026-08-31）

**どちらの種類も、Elicitation や Subagent のような特定の機構に紐づく話ではない。**
判定基準は2つの独立した軸に分解できる：

1. **AI が止まっているか**（判断待ち／レビュー待ち）——先に進むのに人の入力が
   要るかどうか。**発生源を問わない**——Module の Elicitation でも、AI が
   会話の中で自発的に聞いて（選択肢の提示を含む）止まっただけでも、同じ
   「判断待ち」。逆に、AI が単に会話を最後までやり切って終わった（判断は
   不要、ただ見てもらえばいい）なら、Module が関わっていなくても「レビュー
   待ち」——**「進行が止まっているかどうか」が本当の判定基準であって、
   「Module が関わっているかどうか」ではない**
2. **その事実がどこで起きたか**——**Base/Fork Thread 自身の中**（人が直接
   会話しているそのもの。AI の地の文で聞いたか、tool 呼び出し中の
   Elicitation として聞いたかは問わない——どちらも同じ Thread の同じ
   ターンの中の出来事）か、**Module が管理する非同期の実行**
   （Subagent・Factory。§4.1 の訂正により、これらの実行は core が管理する
   普通の Thread ではなく Module の持ち物であり、完了は Module から core への
   能動的な転記でしか伝わらない）か

**開いたときの行き先（action）は、この2軸で決まる**（新しい機構ではない
——既存の概念の組み合わせ）：

| | **Base/Fork Thread 自身の中で起きた** | **Module が管理する非同期の実行** |
|---|---|---|
| **判断待ち** | 行き先＝**そのThreadを開いて返信する**（AIの地の文）、または**インラインフォーム**（Elicitation。Subagent自身がElicitationを使う場合も、他のModuleと同じこの経路に載る——特別扱いしない） | （Elicitationとして上と同じ経路に収束する。Subagent固有の別経路は無い） |
| **レビュー待ち** | 行き先＝**そのThreadを開く**（見るだけ。純粋にタスクが完了して終わった） | 行き先＝**Module の Canvas**（`fullscreen`。Subagentの完了報告・Factory/Moduleの完了、どちらもModuleが持つ詳細画面） |

#### レビュー待ち

並行で仕事を走らせるなら、**終わった順に人のところへ積まれる場所**が要る
（サーベイで確認：Cursor・Vibe Kanban・Conductor が揃って持っている。
**並行実行に必ず付いてくる需要**だから）。

- **「終わった」と決めるのは、Base/Fork Thread 自身の完了（core が直接知る）か、
  Module 側の報告（Factory 的なものが run の完了を、Subagent Module が
  実行結果の転記を届ける、§4.1）のどちらか**。**core は「積むインターフェース」と「型」を
  持つだけ**——判断待ちとまったく同じ構造
- **Module 発のレビューの中身は Canvas で見る**（`docs/specs/v4-frontend.md` §6.2）。差分・テスト結果・
  動いている URL ——**全部 Module が持つ**。**core は待ちの一覧だけを持ち、
  開いたら Module の Canvas が出る**。**差分ビューアを core に作らない**
  （Repo Module の Canvas になる）

### 2.4.1 判断待ち

**以下は Elicitation 発の判断待ちに絞った節。** AI が会話の中で自発的に聞いて
止まる（選択肢の提示を含む）ケースは、Elicitation のような専用プロトコルを
持たない——単に、そのThreadを開いて普通に返信すれば答えたことになる。
特別な設計は不要（§2.4「判定の軸を一般化した」）。

- **「人への問いが立った／解けた」は Event Store の一級の事実**である。
  core の外枠（受信箱）がこれを特別扱いして描くには、core が最初からその型を
  知っている必要があるため。**Elicitation を採ると決めた以上、形はそちらに合わせる**
  （下記）。**記録するタイミングと中身は決定済み**（item 13、2026-08-30、下記の
  「後で答える」の実現方式）——`onElicitation` が呼ばれた時点で
  `serverName` / `message` / `mode` / `requestedSchema` または `url` を
  Event Store に記録する。**イベント型の正確なスキーマ（フィールド名の確定）は
  未決のまま残る**（実装時に詰める）
- **受信箱の UI（バッジ・件数・一覧）は core が持つ。** MCP Apps の見せ方
  （inline / fullscreen）は「どの tool 呼び出しから来たか」に紐づくが、受信箱が
  要求するのは**「どの Thread の会話でもない、常にそこにある入れ物」**
  ——Project 単位の MCP 接続の外側にあるので、Module の器では原理的に作れない

#### 「人に聞く」は Elicitation に乗せる（自前で作らない）

**MCP には完成した機構がある**（2026-08-29 確認）。banto が独自の「判断を立てる
tool」を発明しない（規則12）：

- サーバが `Server.elicitInput()` を呼ぶ → クライアント（Runner）が
  `onElicitation` コールバックを呼ぶ → **同じ呼び出しの中で** `accept` /
  `decline` / `cancel` のいずれかを返す。`elicitInput()` の呼び出しは
  **そのリクエストの中で完結する同期的なもの**——
  `@modelcontextprotocol/sdk@1.30.0` に`inputResponses` / `InputRequiredResult`
  のような非同期継続の型は存在しない（grep 0件）。実験的な **Tasks**
  （`ClientCapabilities.tasks.requests.elicitation.create`）も仕様上は
  存在するが、**Claude Code CLI 2.1.237 は advertise しない**（実測、
  `poc/step0-host-mcp-client/`）
- **応答は3値**：`accept`（答えた）/ `decline`（明示的に断った）/
  `cancel`（黙って閉じた）。**「断る」と「閉じる」を分けている**
  ——自前で作ると落としがちな区別なので、そのまま使う
- `mode: "form"` の `requestedSchema` は**フラットな primitive のみ**
  （string / number / boolean / enum。単一選択・複数選択、`default` 付き）。
  要件の「判断は選択肢を出せる。ただし答えは選択肢に閉じない」は、
  enum ＋ 自由記述の欄で表せる
- **`mode: "url"` が別にある**：鍵・トークン・決済のような機微情報は
  **form で聞いてはならない（MUST NOT）／URL モードを使う（MUST）**。
  この境界は仕様が引いており、banto はそれに従う

  > **実測（2026-08-30）：Claude Code CLI は `elicitation.url` の capability も
  > advertise しない**（`{"elicitation":{"form":{}},"roots":{"listChanged":true}}`
  > のみ）。§2.8 の「サブスクへのログインは shell を走らせ、URL を
  > `mode: "url"` で見せる」の前提は、**この CLI 単体では成立しない**——
  > 別の経路（banto の host が自前で URL を提示する等）が要る。**まだ設計して
  > いない。§10 に追加**（下記）

**banto が足すのは「後で答える」だけ。** Elicitation は「いま走っている呼び出しの
中で人に聞く」機構で、**人が数時間後に答える前提を持っていない**（仕様は
「クライアントは再試行/中止の手段を人に与えるべき」までしか言わない）。
banto の受信箱は、この待ちを**イベントとして寝かせて、後から解決できるようにする
層**である。**問いの形（`mode` / `message` / `requestedSchema` / `url`）と
答えの3値（`accept` / `decline` / `cancel`）は Elicitation のものをそのまま使う**
——イベント型はそれを包むだけにして、banto 独自の問いの形を作らない。

#### 「後で答える」の実現方式を決めた（item 13、決定・2026-08-30、実測 `poc/02-item13-parked-elicitation/`）

**Elicitation プロトコル自体の継続では実現できないことが実測で確定した。**
`Query.close()`（host・Runner の接続を閉じる）を呼ぶと、pending 中の
`elicitInput()` は**即座に** `{"action":"cancel"}` として強制解決される
（66ms）。つまり **host（banto）を落として上げ直すと、その時点の elicitation
は自動的に「黙って閉じた」ものとして処理され、続きは無い。** §2.4.1 が未決として
残していた2つの選択肢——「呼び出し自体を保留する」か「`requestState` を
Event Store に持つ」か——のうち、**前者は実装として成立しないことが実測で
分かった。**

**したがって「後で答える」は次の形にする：**

1. **`onElicitation` が呼ばれた時点で、その内容（`serverName` / `message` /
   `mode` / `requestedSchema` または `url`）を Event Store に即座に記録する**
   ——これが §2.4.1 の「人への問いが立った」という一級の事実
2. **その場の `elicitInput()` 呼び出し自体はタイムアウトに委ねる**
   （実測：Module 側が指定した秒数で `MCP error -32001: Request timed out` が
   返る。既定は60秒、§2.3）。**`onElicitation` から `decline` や `cancel` を
   即座に返さない**——タイムアウトに任せることで、Module 側の
   「再試行/中止の手段を人に与えるべき（SHOULD）」という仕様の要求を、
   Module 自身の実装に委ねたまま壊さない
3. **人が受信箱から後で答えたら、その回答は元の Elicitation の応答としてではなく、
   次のターンへの新しい入力として渡す**（§2.2「次に Runner へ何を渡すか」の
   一種）。tool 呼び出し自体は既にタイムアウトで終わっているので、
   Elicitation の枠の外——普通の会話ターンとして扱う

**帰結：同じ問いが2箇所に出る問題（§2.4.1）は、設計の選択ではなく構造から来る。**
Elicitation の応答（`accept`/`decline`/`cancel`）は、その tool 呼び出しの
生存期間の中でしか意味を持てない。受信箱に表示される「問い」と、会話の中の
tool part に一瞬だけ現れる「Elicitation」は、**プロトコル上不可避に別物**
——後者は静かにタイムアウトし、前者（Event Store に記録された事実）だけが
実際の「待ち」として生き続ける。

**仕様が課している UI 要件**（MUST/SHOULD。作り込みではなく要求）：
どのサーバが聞いているかを明示する・断る/取り消す手段を明確に出す・
form は送る前に人が見て直せる・URL は遷移前にドメインを見せて同意を取る。

#### タイムアウトは banto の制御外（決定・2026-08-31）

**タイムアウト秒数を banto 側で調整することはできない。** `elicitInput()` は
**Server（＝MCP Module）側のメソッド**で、タイムアウトは Module の実装が
`RequestOptions.timeout` に何を渡すか（渡さなければ SDK 既定の60秒）で決まる
（`poc/02-item13-parked-elicitation/module.mjs` で確認）。banto は client 側で
`onElicitation` コールバックを実装するだけで、そこにタイムアウトを指定する
引数は無い（Agent SDK の型定義 `OnElicitation` でも確認済み）。

**banto（client）側にもタイムアウト検知の手段はある。** `onElicitation` の
第2引数 `options` には `signal: AbortSignal` が渡っており、Module 側が
タイムアウトすると発火する——生の MCP SDK（`shared/protocol.js`）を読むと、
リクエスト側（Module）がタイムアウトしたとき `notifications/cancelled` を
相手（banto）に送り、受け取った側はこれを対応する `AbortController.abort()`
に変換する実装になっている。

**実測（2026-08-31）で signal が実際に abort することを確認した：**

```
[sdk] onElicitation 受信 at 6370ms. signal.aborted=false
[sdk] result subtype=success elapsed=17301ms sawAbort=false   ← 会話のターンはここで終わる
[sdk] signal aborted at 17839ms. reason={}                     ← abort はこの後に届く
```

**ただし signal の到着は、会話に tool 呼び出しの結果（エラー）が反映されるより
遅い**（n=1、傾向として安定かは未確認）。つまり検知手段はあるが、**受信箱の
状態切り替えをリアルタイムに揃えたいなら、`signal` の abort よりも、
tool 呼び出し自体の結果（成功/エラー）が会話ストリームに現れるタイミングを
見るほうが早くて確実**——banto はこれを他の理由（tool part の描画）で
既に監視しているので、追加の監視経路を増やさずに済む。out-of-band 完了通知
（`notifications/elicitation/complete`）は Tasks capability 前提で
Claude Code CLI が advertise しないため使えない（item 27 と同根の制約）ままだが、
上記の代替があるので支障は無い。

**帰結：受信箱の判断待ちは3状態を出し分ける（決定・2026-08-31）：**

| 状態 | 意味 | 遷移の検知 |
|---|---|---|
| **生きている** | まだ Module のタイムアウトを迎えていない。受信箱・ライブカードのどちらから答えても、**元の tool 呼び出しを直接解決できる**（banto は手元に残る Promise をそのまま resolve すればよい——「次のターンへの新規入力」に頼らなくてよい） | 初期状態（`onElicitation` 発火時） |
| **解決済み** | 人が（ライブカード／受信箱のどちらかから）答えた | banto 自身がその場で resolve した瞬間に分かる（自明） |
| **タイムアウト済み** | 誰も答えないまま Module 側の期限が過ぎた。ここで答えても元の処理は再開できず、**次のターンへの新規入力として渡る**（この場合のみ、その旨の説明を表示） | tool 呼び出しの結果（エラー）が会話ストリームに現れたタイミングで判定。`signal` の abort は補助的な確認に使える |

**「生きている」間だけ、受信箱から答えても実際に元の呼び出しを解決できる。**

**ただし Phase 0 の実装では、答える口は Thread 側のカード1箇所に置く**
（決定・2026-09-06）。受信箱は「どこで止まっているか」の一覧に徹し、行から
その Thread へ送るだけにする——同じ操作口を2つ持つと、片方だけ直した／片方だけ
壊れた、が起きる（規則3）。**受信箱に答える口を置かないぶん、Thread を開けば
必ずカードがある**ことが要件になる：走行中でなくても（リロード後・別 Project から
戻った後でも）、host 側で生きている判断待ちは会話の画面に描き直す
（`restoredJudgmentMessages`）。
この前提が崩れると「受信箱には出ているのに誰も答えられない」が起きる
——実際に 2026-09-06 に起きた（`docs/notes/2026-09-06-judgment-after-reload-and-home-redirect.md`）。

**答えても元の呼び出しに届かないものには、答える口を出さない**（決定・2026-09-06、
規則13）。いまの実装では Elicitation 由来の判断待ちがこれにあたる——記録は
するが `canUseTool` のような解決先を持たないので、答えても Module 側の
タイムアウトを待つことになる。カードにはその旨を書き、フォームは出さない。

実装（`components/banto/inbox/elicitation-form.tsx` 等）は3状態を反映する形に
書き直す。状態切り替えの具体的な配線（tool_use_id で Event Store のレコードと
tool 呼び出し結果を紐づける詳細）は本実装で詰める（§10 に残す）。

#### 受信箱は Event Store の射影である

**判断待ちの状態（生きている／解決済み／タイムアウト済み）を、フラグとして
Event Store に書き換えながら持つのではなく、追記されたイベントを畳んで
導出する。** 規則3（真実は一箇所。導出できる値を保存しない）と、§2.1 で
既に決めた read model の方式（「State は追記時の増分適用で保つ。写しではない」）
をそのまま適用しただけで、新しい決定ではない——§2.4.1 が最初から
「人への問いが立った／解けた」を Event Store の一級の事実と呼んでいたことの
具体化。

イベントは3種——**`ElicitationAsked`**（`onElicitation` 発火時に記録。既存の
決定）・**`ElicitationAnswered`**（人が答えた。ライブ経由か受信箱経由かは
payload の詳細で、状態としては同じ「解決済み」）・**`ElicitationTimedOut`**
（tool 呼び出し結果の到着で判定して記録）。ある問いの現在状態は、この3種を
`elicitationId` で畳んだ結果——`Asked` のみなら生きている、`Answered` があれば
解決済み、`TimedOut` があれば（`Answered` が無ければ）タイムアウト済み。
受信箱 UI が読むのはこの畳んだ結果であって、UI 側で別に状態を持たない。

#### 設計意図とのズレ（確認・2026-08-31）

**MCP Elicitation は、そもそも banto が使いたい「数時間後でもいい判断待ち」を
想定して設計されていない。** 仕様原文（modelcontextprotocol.io、2025-06-18版）を
確認した：

> "Elicitation in MCP allows servers to implement interactive workflows by
> enabling user input requests to occur **nested** inside other MCP server
> features."

例示も "Please provide your GitHub username" 程度の即答を想定したものしかなく、
メッセージフロー図も往復が一続きの同期処理として描かれている。**タイムアウトへの
言及は仕様書に一切無い**——60秒は Elicitation 専用の設計値ではなく、SDK が
全リクエスト共通でかけている汎用 RPC タイムアウト。むしろ示唆的なのは
cancel（黙って閉じた）への仕様のガイダンス——「Handle dismissal (e.g., **prompt
again later**)」——**「同じ呼び出しを寝かせて再開する」という発想自体が仕様の
想定に無く、聞き直すのはサーバの仕事**とされている。item 13 の決定
（タイムアウトさせて次のターンへの入力として渡す）は、この想定のズレを
解消したのではなく、**正直に受け入れた**もの。

**この帰結として、判断待ちの2つの経路は信頼度が異なる：**

- **承認ゲート**（`docs/specs/v4-frontend.md` §6.4、banto 自身が tool を呼ぶ**前**に持つ機構）経由のものは、
  実際の MCP 呼び出しがまだ発生していないので Elicitation の同期前提を踏まない。
  何時間放置しても状態は banto 側にそのまま残り、承認されて初めて呼び出す
  ——**確実に後から答えられる**
- **Module 自身が tool 実行の**途中**で `elicitInput()` を呼ぶもの**は、上記の
  制約をそのまま受ける——**答えても元の処理が直接再開するわけではなく、
  AI がそれを見て自分で処理を再試行することに委ねる、ベストエフォート**
- **「確実に後から答えられる判断待ち」にしたいものは、Module の Elicitation では
  なく banto の承認ゲートに寄せるべき**——Module 作者への設計ガイダンスとして
  将来書く価値がある（未着手）

**一方、item 13 の設計自体は業界標準パターンと一致していることも確認した。**
Devin・GitHub Copilot のバックグラウンドエージェント・Cursor Background Agents
等、非同期の人間確認を製品化しているものは共通して「待ち」を RPC の生存期間ではなく
オーケストレーション層（エージェントの永続セッション状態）に置く。resume も
「同じ呼び出しの再開」ではなく「蓄積した文脈＋人の回答を持った新しい実行」——
banto の Event Store ＋「次のターンへの新規入力として渡す」はこのパターンと同形。

### 2.5 host（配線・解決層）

「誰が何の役割を満たすか」を1箇所で解決して接続する層。2種類の配線を両方含む：

- **(a) AI 向け**：**Runner に渡す入力を組み立てる**——そのターン繋ぐ Module 集合と、
  **効かせる Skill（§5.7）**の両方。どちらも「候補は Module が持ち、どれを使うかは
  Project / Thread が決め（§2.2）、Runner が食える形にするのは host」という
  同じ構図
- **(b) Module 同士**：役割ごとの呼び出しインターフェースを解決して配る

**host は自分の MCP クライアントを持つ**（実測 2026-08-30、`poc/step0-host-mcp-client/`、
`docs/notes/2026-08-30-poc.md`）。Runner（Claude Agent SDK）の `Query` は
MCP 接続の**状態と制御**（`mcpServerStatus` / `setMcpServers` / `toggleMcpServer` /
`reconnectMcpServer`）しか持たず、`resources/list` や `_meta` を読むインターフェースが無い。
一方 §5.4・§5.7・`docs/specs/v4-frontend.md` §6.2 は host が Module の `_meta` を読み、`SKILL.md` を資源として
取ることを前提にしている——**この前提を満たすには、host が
`@modelcontextprotocol/sdk` の `Client` を自前で持つしかない**（実測で `_meta` が
`Tool._meta` / `Resource._meta` としてそのまま届くことを確認済み）。

**stdio Module では、Runner が直接 spawn する接続と host が張る接続を両方
持たせると、別プロセスになる。** stdio は1プロセスにつき1本の stdin/stdout
しか持てないため（実測：2つの接続で `process.pid` が異なった）。**この問題は
Runner を実 Module に直接繋がせないことで解消した**——下記「Runner は実 Module
に直接繋がない」を参照（決定・2026-09-02、PoCで実証）。

> **Skill の配線は Module にはできない。** Module は自分の Skill を配れるが、
> **Runner を知らないし、他の Module の Skill も知らない**。「どの Skill を、
> どの形で Runner に渡すか」を解決できるのは、全部を見ている host だけ。
> Module 集合の組み立てとまったく同じ理由で、**ここは core に要る**。

**この解決は自動でなければならない。** Module が宣言する依存（役割名・使う tool 名・
使われる自分の tool 名）を読んで、役割→実装の対応を host が組み立てる。
**人が host のコードに「この Module はこの役割」と手で書く箇所があってはいけない**
——そこがあると、Module を足すたびに core を直すことになり、「Module 化した」と
言えない。

決まっている細部：

- **同じ役割を複数の Module が名乗ってよい。** 自動解決が作るのは「役割→1つの
  勝者」ではなく**「役割→{名前: 呼び出しインターフェース} の辞書」**。本当の衝突は「同じ名前を
  2つの Module が名乗ること」だけで、それは普通の名前衝突として弾く
- **役割が満たされないときの扱いは、`required`（上記 `dependsOn`）で分かれる**
  （決定・2026-09-02、要件C11とここの「起動を止めない」の食い違いを解消）。
  **「起動を止めない」のは banto host 自身の話**——host は依存の充足状況に
  関わらず必ず起動する。一方、**依存している Module 側は `required` に従う**：
  - `required: false`（任意）：Module は起動する。「無ければどの tool が
    断るか」を依存宣言から導いて、使う tool だけがはっきり断る
  - `required: true`（必須）で満たされない：**その Module 自体がマウントされ
    ない**（要件C11「必須が満たされなければ起動せず」）。Module 一覧には
    「無効——理由：role `vault` を満たす実装が無い」のように理由付きで出す。
    banto host 自身の起動は止まらない——止まらないのは host、止まるのは
    その Module だけ、という2階層に分けて初めて両方の文言が両立する
- **解決のタイミング**：(a) は Project / Thread が明示的に決めるたび。
  (b) は banto 起動時、または接続 Module 集合が変わったとき（Project 単位ではない）
- **Project ごとの違い（作業対象のパス等）は「どの Module を使うか」ではなく
  「その呼び出しに何を渡すか」という引数の差で吸収する**

**制約**：既定値を持たせない（§9 の「既定値は忘れられる」）。**「人が書く場所が
host のコードに無い」ことと「誰も選んでいない接続が黙って起きる」ことは別**で、
後者は避ける。両立案は §10（未決）。

#### role 依存の解決は Module の仕事——banto が渡すのはリストだけ（決定・2026-09-02）

**「あるロールに複数の実装があるとき、どれを使うか」を banto が代わりに
決める仕組みは持たない。** 理由：

- **選び方は Module ごとに全く違う。** Vault のように「値は動かさず、固定の
  接続を人が選んでおく」ものもあれば、**Subagent のように「候補一覧を見て、
  仕事の中身に応じて AI がその場で選ぶ」もの**もある。banto が「型はこれ」と
  決め打ちすると、当てはまらない Module が必ず出る
- **Module の独立性（§1）と矛盾する。** 依存先の選び方という Module 固有の
  ロジックに banto core が口を出すのは、境界を越えている

**banto がやることは1つだけ：role → 実装の一覧を、依存している Module に渡す。**
選び方（固定で決めておくか、AI が呼び出しごとに動的に選ぶか、その中間か）は
**その Module 自身の設定 Canvas（`ui://<id>/config`、`docs/specs/v4-frontend.md` §6.2）の仕事**——banto の
Configuration（§2.6）は「その役割を instance 全体として有効にするか」までしか
持たない。

副作用：
- **Project 単位の「使う Vault 接続」の上書きは banto から無くなる。** 選ぶのは
  Vault に依存する Module（Repo・Shell 等）自身——それぞれの `ui://<id>/config`
  の中で選ぶ
- **Module 自身の設定 Canvas が Project ごとに中身を変えたいとき**——banto は
  Module のプロセスを Project に紐づけていない（§10 未決事項の注記、
  2026-08-30）ので、Module は「今どの Project のために描いているか」を
  自分では知りようがない。**banto は `ui://<id>/config` を埋め込むとき、
  現在の Project の識別子を渡す**（詳細は `docs/specs/v4-frontend.md` §6.2「設定 Canvas への Project の文脈」）。
  対応するかどうかは Module 次第——対応しない Module は今まで通り instance
  全体で1枚の設定を出すだけでよい（§2.5 冒頭「役割が満たされないときは
  その機能が使えないでよい」と同じ扱い）

#### Module 間の呼び出し——host が中継する（決定・2026-09-02）

要件 C10「Module は他の Module の tool／resource／prompt を呼べる」は、
**host が中継する**形にする（tool だけでなく resource・prompt も同じ形で
対応する）。

**Module 同士が直接つながる形（呼び出し前に core へ許可だけ求め、許可後は
実データを Module 同士が直接やり取りする）は採らない。** 理由は2つ：

- **Module 同士が直接つながる transport が要る。** stdio は1プロセスにつき
  stdin/stdout が1本しかない（§2.5 実測済み）ので、宛先ごとに別のインターフェース
  （Unix domain socket 等）を Module に持たせる設計が要った
- **許可を経ずに直結されることを防ぐ検証が要る。** 「core に先に聞く」という
  行儀のよい Module の前提に乗るだけでは、なりすまし直結を防げず、
  許可トークンの発行・検証という新しい設計項目が残っていた

**中継にすると、この2つとも要らなくなる。** Module はみな host という
**同じ1箇所**にしか繋がないので、宛先ごとの transport も、なりすまし対策も
構造的に発生しない。

**仕組み：**

- **host は自分自身の MCP のインターフェース（C13）に、Module 間呼び出し用の中継 tool を持つ。**
  `tools/call` / `resources/read` / `prompts/get` それぞれに対応する薄い転送インターフェース
  ——呼び出し元 Module は「宛先 Module・呼びたい名前・引数」を渡すだけでよい
- **host は権限を確認する。** 呼び出し元が宣言した依存（§2.5「role依存の解決」）
  に照らして許可されているかを見る。**承認は「呼び出し元・宛先・tool/resource/prompt」
  の組み合わせごとに1回でよい**——以降は同じ Project 内で自動許可。旧案の
  この部分の考え方（Claude Code 自身の許可プロンプトと同じ形）は変わらず引き継ぐ
- **host は Event Store に記録するが、メタデータだけ。** 呼び出し元・宛先・種別
  （tool/resource/prompt）・名前・成否・時刻を記録する。**引数のうち、値そのもの
  ではなく「何を指しているかの識別子」（例：Vault の alias 名）は記録してよい**
  ——秘密の値そのもの・戻り値の実データは記録しない。この線引きの具体例は
  `docs/specs/v4-modules.md` §2.1（Vault）を参照。これが監査（`docs/specs/v4-frontend.md` §6.0）の要求を
  満たす部分
- **host は宛先 Module へ実際の JSON-RPC を転送し、結果をそのまま呼び出し元へ
  返す。実データは host のプロセスメモリを一過性に通過するだけ**——**ディスクにも
  Event Store にも、Canvas のような画面にも出さない**
- **core が落ちている間は、この中継がリトライで待たされるだけでよい。**
  完全に落ちていれば他の経路（Runner 呼び出し等）もすべて止まっているはずで、
  ここだけ特別な耐障害機構を持たせる理由が無い

**Module 側がこの中継 tool にどう到達するか（決定・2026-09-03）**：MCP は
サーバ（Module）がクライアント（host）の tool を呼ぶ手段を持たない。
Module 側が host に対する**別の client 接続**を自分で張る必要がある。

- **host は localhost 限定の Streamable HTTP MCP エンドポイントを持つ。**
  Module プロセスには `BANTO_HOST_MCP_URL`（例：`http://127.0.0.1:<port>/relay`）
  と、**プロセスごとに発行する bearer token**（`BANTO_HOST_MCP_TOKEN`）を
  起動時の環境変数として渡す。host はこのトークンで「どの Module・どの
  Project からの呼び出しか」を特定する——上記の許可確認（呼び出し元・宛先の
  組み合わせ）はこの識別が無いと成立しない
- **Unix domain socket は採らない。** `docs/specs/v4-security.md` が
  「特殊ファイルシステム（ソケット等）は Landlock で明示的に制限できない」
  と明記しており、Landlock 配下の Shell/FileSystem からの到達性が未測定
  のため。TCP の localhost 接続は Landlock ABI4 で制御対象になることが
  既に実測済み（`docs/specs/v4-security.md`）——枯れた経路を選ぶ
- **トークンはプロセス起動のたびに発行し直す。** 使い回さない（規則2と
  同じ精神——黙って緩めない）

**Vault の例との整合**：D3 が守るのは「鍵そのものが AI の文脈に出ない」こと。
下記の ssh-agent の例が守るのは「秘密鍵は Vault のプロセスから一度も出ない」
こと（ソケットパスしか外に出ない）。**どちらも、host を一過性に通過するだけの
中継とは矛盾しない**——AI の文脈にも、ディスクにも出ないままである。

**将来の課題として残す：直結への分離。** 中継が host の性能上のボトルネックに
なる、あるいは大容量データ（バイナリ添付等）の中継が問題になる、といった
**実測ベースの理由が出てきたら**、旧案（control-plane / data-plane 分離・直結）
に戻す道はある。ただしそのときは、上で消えた2つの論点（transport・なりすまし
対策）を合わせて片づける必要がある。**いまはまだ困っていないので、設計コストは
使わない**（規則7）。

#### Runner は実 Module に直接繋がない——代理サーバ方式（決定・2026-09-02、`poc/05-module-relay-topology/` で実証）

上の「Module はみな host という同じ1箇所にしか繋がない」は、**それ自体が
自動的に成り立つ前提ではなく、Runner の配線をこの形にして初めて真になる
結論**だった。Runner（Claude Agent SDK）に実 Module の `mcpServers` 設定を
そのまま渡すと、Runner は自分で実プロセスに spawn ・接続してしまい、host が
別途持つ接続と合わせて**同じ Module に2本の接続**ができる——stdio では
別プロセスになり（上記）、状態を持つ Module では2つの実行環境が食い違い、
Vault のような鍵を持つ Module では秘密鍵やソケットが2組できて D3/D5 の
保証が構造ではなく偶然になる。

**採る配線**：

1. **host が実 Module への接続を1本だけ持つ**（`@modelcontextprotocol/sdk` の
   `Client`）。Runner には実 Module の `mcpServers` を直接渡さない
2. **host は `@modelcontextprotocol/sdk` の低レベル `Server` で代理サーバを
   組む**（決定・2026-09-02、`poc/06-resource-prompt-relay/`）。
   `createSdkMcpServer`（Claude Agent SDK の高レベルラッパー）は tool しか
   受け付けないため使わない——低レベル `Server` なら `tools/list`・
   `resources/list`・`resources/read` のハンドラを自分で実装でき、実 Module
   から受け取った `tools/list` の結果をそのまま返せる（**JSON Schema → zod
   変換も不要**）。**代理サーバと Runner の間は、localhost 限定の実 HTTP
   （`StreamableHTTPServerTransport`）で繋ぐ**（決定・2026-09-03、本実装での
   実測で訂正——経緯は下記「実装上の留保」）。`mcpServers` に渡す設定は
   `{type: 'http', url}` で、host は §2.5「Module 間の呼び出し」の
   `/relay` エンドポイントとは別に、Runner 向けの `/agent-relay/<module名>`
   エンドポイントをもう1つ持つ
3. 代理サーバは実 Module の `tools/list`/`resources/list` のうち **`agent`
   可視性のものだけ**を、hostの実接続へ転送するハンドラとして登録する
4. **Runner に渡す `mcpServers` は、この代理サーバを指す**

**効果（3回中3回、間欠なく再現）**：

- **実 Module のプロセスは1つだけになる。** 対照実験（Runner に実 Module を
  直結）ではプロセスが3つ（host 1 ＋ Agent SDK 側 2）できた——**「2重起動」は
  避けられない制約ではなく、配線の選択の結果だった**
- **`module`/`admin` 可視性の tool は Runner の tool 一覧に一切現れない。**
  `docs/specs/v4-modules.md` §2.1 の可視性は「フィルタで隠す」のではなく
  「代理サーバに最初から登録しない＝存在しない」で実現する。§9 に持ち込んだ
  v3 の知見（SDK 組み込みの資源系 tool は見せない設定でも見えたまま）は
  `allowedTools` のような**フィルタ経路の話**であり、`createSdkMcpServer` に
  登録しない経路にはそもそも掛からない
- **承認ゲート（`docs/specs/v4-frontend.md` §6.0・`docs/specs/v4-frontend.md` §6.4、`canUseTool`）は代理サーバの tool でもそのまま
  正しく呼ばれる。** 新しい機構は要らない
- **resource も代理できる。** Runner（Claude Code の実行系）は resource を
  直接読まず、`ListMcpResourcesTool`/`ReadMcpResourceTool` という**組み込み
  tool 経由**で `resources/list`/`resources/read` を呼ぶ——これは要件C14
  「AI は指すだけ」の`resource_link`パターンとは別の経路で、AI が能動的に
  resource を読みにいく場合（`vault://aliases`等）に使われる。**banto が
  同種の汎用 tool を自作する必要はない**（Claude Code 側が既に持っている）
- **prompt は Runner に届かない。** 代理サーバが `prompts` capability を
  申告しても、Runner（`query()`）側は `prompts/list` を一度も呼ばない——
  MCP の prompt は人が選ぶスラッシュコマンドの領域であり、Runner の会話には
  露出しない、という実測の結論。**§2.5 の Module 間中継（`prompts/get` の
  転送）は host 自身の Client が呼ぶので、これとは別で影響を受けない**

**resource には tool と違う非対称がある（重要）**：

- **tool は「登録しない＝存在しない」で守れるが、resource はそうならない。**
  `ReadMcpResourceTool` は URI を直接指定できるため、`resources/list` に
  載せなかった `module`/`admin` 可視性の resource でも、URI さえ知っていれば
  `resources/read` で読めてしまう（実測で確認：`vault://internal/audit` を
  一覧から外しても、直接指定で読めた）。**可視性の判定は `resources/read`
  ハンドラの中でも行う必要がある**——一覧から外すだけでは D3 を守れない
- **`canUseTool`（`docs/specs/v4-frontend.md` §6.0・`docs/specs/v4-frontend.md` §6.4 の承認ゲート）は resource 読み取りでは一度も
  呼ばれない。** resource アクセスの統制は代理サーバの `resources/read`
  ハンドラの中で完結させるしかなく、既存の承認ゲート機構には乗らない
- **`_meta` はそのままモデルへ渡る。** `dev.banto/visibility` のような
  banto 拡張キーが tool_result / resource 経由でモデルの文脈に露出する
  ——代理サーバは転送時にこれを剥がす

**実装上の留保（訂正の経緯、規則1・規則8）**：当初は手順2を `{type: 'sdk',
instance}`（低レベル `Server` を高レベル `McpServer` の型に嘘のキャストで
渡す、Agent SDK の内部実装が `connect()` しか呼ばないという非公開の実装詳細に
依存する形）で実装していた。**本実装（Phase 1、Vault の `requestAlias` を
実際に呼ぶ検証）で、この形では Elicitation が機能しないことを実測した**——
`{type: 'sdk', instance}` で接続する Agent SDK 内部のブリッジは、MCP の
`initialize` ハンドシェイクで `elicitation` capability を宣言しない。
そのため代理サーバの `elicitInput()` は常に
`"Client does not support form elicitation"` で失敗する。**Module 起点の
Elicitation（Vault の `requestAlias` 等）は §2.4「人に聞くは Elicitation に
乗せる」の前提そのものなので、これは受け入れられない。**

切り分けとして、同じ `elicitInput()` 呼び出しを実 stdio 接続・実 HTTP 接続
それぞれに繋ぎ直して検証したところ、**どちらも `onElicitation` が正しく
発火した**——`instance` 形式固有の問題であり、代理サーバのロジック自体の
問題ではないと確認できた。HTTP を採った理由は、§2.5 の Module→host 中継
（`/relay`、`HostRelayEndpoint`）で同じ `StreamableHTTPServerTransport` の
実装パターンをすでに持っており、Runner→host 方向にもう1エンドポイント
増やすだけで済む（stdio 案は Module ごとに追加のプロセスが要る）ため。

この訂正により、型キャストの嘘（`sdk-shim.ts`・`asSdkServerConfig`）は
不要になった——実 HTTP 接続なので、Agent SDK 側は正規の MCP クライアントとして
`elicitation` capability を含めて正しくハンドシェイクする。**起動時に
`mcp_servers` の接続状態を検査し、代理サーバが `connected` にならなければ
起動を拒否する健全性検査（health.ts）は変わらず維持する**——理由は型キャストの
崩れではなく、単純にネットワーク越しの接続が実際に確立したかを確認するため
（既存の Landlock ABI 検査と同じ形、`docs/specs/v4-security.md`「ABI 版が
足りなければ断る」）。

##### 具体例：Repo が Vault から ssh-agent のソケットを得る（`docs/requirements.md` D5 の具体化）

1. host が `vault` 役割を解決し、**満たす実装の一覧**（例：組み込みローカル・
   HashiCorp Vault）をこの Project にマウントする——**どれを使うかは host が
   決めない**（下記「role 依存の解決は Module の仕事」）
2. Repo も同じ Project にマウントされる。**Repo 自身の設定**（D5「どのリポジトリに
   どの身元を使うかの割り当て表」、Repo 自身の `ui://<id>/config` の中）に
   「identityA → Vault 接続 X・パス `github/identityA`」と書かれている——
   **「どれを使うか」は Vault ではなく呼び出し元 Module が持つ**
3. AI が push の tool を呼ぶ
4. Repo が host の中継 tool 経由で「Vault の `startSshAgent` を呼びたい」と渡す（上記。`docs/specs/v4-modules.md` §2.1 B節）
5. host が権限を確認し、Event Store にメタデータを記録してから、Vault へ転送する
6. Vault は自分のプロセス内で ssh-agent を立て、**ソケットパスだけ**を返す。
   host はこれを Repo へそのまま返す（記録も保持もしない）。**秘密鍵そのものは
   Vault のプロセスの外に一切出ない**——AI の文脈にも、呼び出し元 Repo の文脈にも
   出ない（D3 よりさらに一段強い）

##### 具体例：Shell に秘密情報を渡す——alias 方式（決定・2026-09-01）

Shell は AI が書いたコマンド文字列をそのまま実行するので、**値をコマンド
文字列に混ぜたら、その時点で AI の文脈にも tool 呼び出しの記録にも値が
写ってしまう**（`docs/specs/v4-frontend.md` §6.0：tool の入力は人に見せるべき）。

- **Vault は Project 単位で「名前付き参照（alias）」を持てる。** 例：
  `github-token` という名前が、内部では `接続X / github/identityA/token` を指す
- **AI に見えるのは alias の一覧（存在と名前）だけ。値は一切見せない。**
  D3 が禁じているのは「鍵そのもの」であって「鍵の存在」ではない
- **Shell の tool 呼び出しは、コマンド文字列と別に「使う alias の一覧」を持つ**
  （例：`command: "curl -H \"Authorization: Bearer $GITHUB_TOKEN\" ..."`,
  `envSecrets: {GITHUB_TOKEN: "github-token"}`）。AI が書くのはコマンド文字列の
  中の**環境変数名**だけ
- **実行直前、Shell が host の中継経由で（上記の許可を経て）Vault に alias を
  解決してもらい、返ってきた値を spawn する子プロセスの環境変数テーブルに
  直接注入する。**
  コマンド文字列にも argv にも値を書かないので、`ps` にも tool 呼び出しの
  記録にも値は出ない
- **承認ゲートで人に見せるのは、コマンド文字列＋使われる alias の一覧。値は
  出さない。** 「知らない alias が使われようとしていたら拒否できる」状態は保てる
- **ファイルとして必要な秘密**（`.npmrc`・`kubeconfig` 等）も同じ原則——Shell が
  実行直前に Landlock された根の中へ一時ファイルとして書き出し、実行後に消す。
  AI が書くコマンドは「ファイルが既にそこにある」前提で動くだけでよい

> **この機構が機能するには、Shell からネットワークへ出られる必要がある。**
> `docs/specs/v4-security.md` で未決のまま残していた「shell からネットワークに出られてよいか」が、
> この用途（秘密情報を使って外部 API を叩く）でそのまま刺さる。単純に塞ぐと、
> alias 方式そのものの使いどころが無くなる。

### 2.6 Configuration

Module を抜きにした、core 自体の設定。**Module 一覧や Project 単位の設定より
先に**存在すべきもの——「core の上に何を載せるか」ではなく「core そのものが
どう組み立つか」の話だから。

- **層1：bootstrap config**——データディレクトリの場所・待受ポート・認証の合言葉。
  Event Store を開くより先に要るので、その中には書けない。**プロセスの環境変数
  ではなく、ちゃんとした1つのファイル**（§9：起動の仕方が動いているプロセスの
  環境変数にしか無いと、落として上げ直したときに失われる）
- **層2：runtime config**——新規 Project の既定モデル・既定 reasoning effort・
  Memory の上限文字数など、走行中に変えられるもの。**別の設定ストアを作らず、
  Event Store 自体のイベント型として載せる**（規則3。「いつ何が変わったか」の
  履歴も無料で付いてくる）
- **runtime config は既定で全項目が Project 単位に上書き可能**（決定・
  2026-09-01、§2.2「設定のカスケード」）。上書きさせたくない項目は個別に
  ブラックリストで塞ぐ——既定は「開いている」側にする

**層1の形式・置き場を決めた**（item 18、決定・2026-08-30）：

- **置き場は XDG Base Directory 仕様に従う**（規則12——発明しない）。
  bootstrap config は `$XDG_CONFIG_HOME/banto/config.json`
  （`$XDG_CONFIG_HOME` 未設定なら既定の `~/.config/banto/config.json`）
- **形式は素の JSON。** TOML/YAML はコメントを書けて読みやすいが、
  Node 標準ライブラリにパーサーが無い（規則10——依存を足す前に標準ライブラリを
  見る）。bootstrap config は項目数が少なく（データディレクトリの場所・
  待受ポート・認証の合言葉）、コメントの必要性がその依存を正当化しない
- **bootstrap ファイルは、それが指すデータディレクトリの中に置かない。**
  §9 の事故（起動の仕方が動いているプロセスの環境変数にしか無く、落として
  上げ直したら作業範囲を見失った）を、**置き場を分離する**ことで構造的に防ぐ。
  データディレクトリの既定は `$XDG_DATA_HOME/banto`（既定
  `~/.local/share/banto`）で、`config.json` の `dataDir` キーで上書きできる
- **起動時に、`dataDir` が `config.json` 自身を含むディレクトリと重なって
  いないかを検査する。** 重なっていたら起動を拒否する（規則2——黙って別の
  経路へ落ちない）
- **`BANTO_CONFIG_PATH` 環境変数で `config.json` 自体の場所を上書きできる。**
  §9 の教訓とは矛盾しない——**環境変数が「唯一の真実の置き場」になっていない**
  （ファイルが唯一の真実で、環境変数は「そのファイルをどこから探すか」を
  教えるだけ。環境変数が失われても、既定の XDG パスに戻るだけで済む）

> **§2.7 セキュリティ境界は `docs/specs/v4-security.md` に分離した**（2026-09-02）。

### 2.8 資格情報と使用量

**複数の資格情報を登録して使い分ける**（方向・2026-08-29）——サブスクの OAuth も
API トークンも複数持てるようにし、**それぞれの消費量を見て、それぞれに上限を置き、
達したら別のものへ移る。**

**1人で使う前提は変わらない**（`vision.md`）。これは組織の予算管理ではなく、
**手元にある複数の枠を使い切るための機構**である。

#### 既存の枠に収まる。新しい箱を作らない

| | どこが持つか |
|---|---|
| 資格情報そのもの（鍵） | **Vault**（`docs/specs/v4-modules.md` §2——**必須 Module に格上げ**、下記） |
| **どの資格情報でこのターンを走らせるか** | **host**（§2.5(a)——Runner に渡す入力を組み立てる側） |
| 消費した量 | **Event Store から導出する**（規則3。ターンごとの使用量はすでにイベントとして残る） |

**モデルB（§2.3）だからこれができる。** 1ターン＝1回の呼び出しで使い捨てるので、
**ターンごとに違う資格情報を渡せる**。常駐セッション（モデルA）だと、途中で
差し替えるインターフェースが要る。**モデルB を採った判断がここで効く。**

#### Vault は必須 Module にする（決定・2026-09-01）

`docs/specs/v4-modules.md` は当初 Vault を「作りたい Module（必須ではない）」に
置いていたが、**§2.8 の複数資格情報の使い分けは banto の中核機能として決定済み
であり、Vault が無いインストールは成立しない。** 「必ず作る Module」に移す
（`docs/specs/v4-modules.md` §2）。

- **役割としての構造（複数バックエンド）は維持する。** `vault` は他の役割
  （§2.5）と同じ枠組みに乗る——HashiCorp Vault・OS のキーチェーン・banto 組み込み
  実装などが同じ役割を名乗ってよい
- **banto はローカルで秘密情報を管理するデフォルトバックエンドを同梱する——
  実装は SOPS を使う（決定・2026-09-02）。** 追加のインストール・設定なしに
  動く——これで「banto 起動直後、Module 集合を解決する前に資格情報が要る」
  という鶏卵問題が消える。起動直後から `vault` 役割の候補が必ず1つ存在する。
  SOPS 自身の復号鍵（age/PGP のローカル鍵ファイル等）は banto がファイルとして
  直接持つ——これは alias 解決の対象ではない、**唯一、本当に特別な1点**
  （下記「mcpServers への秘密情報の注入」参照）
- **「同梱」は「core と同じプロセスで動く」という意味ではない。** `docs/requirements.md`
  C8b の表がすでに「鍵を持つものは subprocess」と定めている——core のバグが
  直接鍵のメモリを覗ける状態は避ける。**組み込みバックエンドも、実行は core とは
  別プロセスのまま**、ただし利用者が個別にインストール・起動する手間は無い
- **他バックエンドを追加したときは、中身を移行できる**操作を持つ。**移行は秘密
  情報を直接動かす操作なので、人専用とする**（AI には露出しない——§2.10「変更
  主体」の軸のとおり）

#### Vault 接続のアドレス（決定・2026-09-01）

**アドレスは2段**：**接続識別子（banto が採番、§5.2 と同じ原則）＋ 接続内部の
秘密のパス（実装依存の名前空間。banto は統一しない——Module の独立性、§1）。**

**「どの Vault 接続を使うか」を banto が instance 既定・Project 上書きとして
持つ仕組みは無い**——**§2.5「role 依存の解決は Module の仕事」に統合**した。
banto が持つのは role→実装の一覧を渡すことだけで、Vault について特別な
カスケードは持たない。「どれを使うか」は、それを使う Module 自身が
`docs/requirements.md` D5「どのリポジトリにどの身元を使うかの割り当て表は
Repo が持つ」のとおり自分の設定 Canvas で持つ。Vault は「識別子を渡されたら対応する
秘密を使わせる」だけに徹し、「どれを使うべきか」の判断はしない。

**Module 間の呼び出しの具体形（Repo→Vault の ssh-agent、Shell への alias 経由
の注入）は §2.5「Module 間の呼び出し——host が中継する」にまとめた。**

#### 上限は % で置く。SDK から取れる（2026-08-29、型定義で確認）

Claude Agent SDK は **`/usage` の構造化データを返すインターフェース**を持っている。
**サブスク枠の消費率が % で取れる**ので、「断られてから気づく」ではなく
**先回りして切り替えられる**：

| 取れるもの | 中身 |
|---|---|
| `subscription_type` | `pro` / `max` / `team` / `enterprise`、API キー等では `null` |
| `rate_limits_available` | **API キー・Bedrock・Vertex では `false`**（枠の概念が無い） |
| `rate_limits.five_hour` | **`utilization`（0〜100）** と **`resets_at`（ISO 8601）** |
| `rate_limits.seven_day` | 同上 |
| `rate_limits.seven_day_opus` / `seven_day_sonnet` / `model_scoped[]` | **モデル別の週次の窓** |
| `rate_limits.extra_usage` | 追加利用枠（`monthly_limit` / `used_credits` / `utilization`） |
| `session.total_cost_usd` | そのセッションの費用 |

**決まること：**

- **上限は % で置く。** ユーザーが窓ごとに閾値を決め、超えたら次の資格情報へ移る
- **窓は1つではない。** 5時間・7日・モデル別が別々に動くので、**どれか1つでも
  閾値を超えたら移る**——「5時間窓は空いているが7日窓が尽きた」が普通に起きる
- **`resets_at` があるので、外した資格情報を戻せる。** 枯渇したものを永久に外すのでは
  なく、**リセット時刻を過ぎたら候補に戻す**
- **API キーは別建て。** `rate_limits_available` が `false` なので、
  **`session.total_cost_usd` の積算**で見る

> **この API は不安定だと明記されている**（規則1・規則8）。型定義に
> 「**EXPERIMENTAL：予告なく変更・削除されうる。まだ依存するな。安定化したときに
> メソッド名は変わる**」とある。**採るが、依存を1箇所に閉じる**——Runner が
> ベンダの語彙を外に出さないのと同じ扱い（§2.3）にして、名前が変わったときに
> 直す場所を1つにする。

**枠が尽きて断られた場合も、黙って切り替えない**——**断られたことをイベントとして
残してから移る**（規則2）。**黙って切り替わると、なぜ費用の出方が変わったのかが
後から分からなくなる。**

> **副産物**：同じ SDK に `getContextUsage()` があり、**文脈窓の内訳**
> （system prompt・tools・messages・MCP tools・memory files 別のトークン数）を
> 返す。**要件 F2「文脈サイズと圧縮の発火回数を数値で返す」（Phase 0 の完了条件）に
> そのまま使える。**

#### サブスクへのログインは shell を走らせる（方向・2026-08-29）

対話的なログインコマンドを走らせて認証させる。**専用の認証画面を作らない。**

**ただし Shell Module（`docs/specs/v4-security.md`）では実行できない。** Shell は Project の根に
Landlock で閉じ込められており、**資格情報の保存先は根の外**にある。
**資格情報の登録は、閉じ込めない別の実行経路**として持つ必要がある
——**Shell Module の穴にしない。** これは明示的な例外であり、
**そこを通せるのは「資格情報を登録する」という1つの用途だけ**にする。

**画面との繋ぎには新しい機構が要らない。** ログインコマンドはブラウザで開く URL を
出すので、**その URL を Elicitation の `mode: "url"` で人に見せる**（§2.4）
——仕様が「機微情報は URL モードで」と定めている、まさにその用途。

#### 代償：切り替えるとキャッシュは全損する（実測 2026-08-30）

**別アカウントの資格情報で同じ会話を測った：**

| | cache_read | cache_create | 費用 |
|---|---|---|---|
| A で resume（基準） | 24,835 | 58 | $0.0085 |
| **B へ切り替えて resume** | **0** | **25,540** | **$0.154** |
| **A へ戻して resume** | 24,893 | 88 | $0.0105 |

**キャッシュはアカウント単位**で、切り替えた回は**約15倍**になった。
§9 の「トークンの 98.5% がキャッシュ読み」がそのまま裏返る。

**ただし A へ戻すとキャッシュは戻った**——アカウントごとに別々のキャッシュが
保たれている。**`resets_at` を過ぎたら候補に戻す**という設計（上記）は、
この点で理にかなっている。行き来しても、それぞれの温まりは失われない。

#### 切り替え方——設定ディレクトリごと替えない。資格情報だけ差し替える

**設定ディレクトリを変えて `resume` すると `No conversation found` で失敗する**
（実測）。認証の拒否ではなく、**セッションの転写が設定ディレクトリの中にある**
から（`<設定ディレクトリ>/projects/<cwd>/<セッション>.jsonl`）。

**しかし転写を複写する必要はない**——**キャッシュは資格情報（アカウント）に
紐づいており、設定ディレクトリには紐づいていない**ことを実測で確かめた：

| | cache_read | cache_create |
|---|---|---|
| 別の設定ディレクトリ ＋ **同じ資格情報** | **21,177**（ほぼ復帰） | 4,767 |
| 同じ設定ディレクトリ ＋ **別の資格情報** | **0**（全損） | 25,540 |

**したがって、設定ディレクトリは1つに保ち、その中の資格情報だけを差し替える。**
そうすれば転写はそのまま見つかり、**CLI のディスク配置に依存する必要が無くなる**
（§2.3 の巻き戻しでは依存が残るが、資格情報の切り替えでは不要）。

#### したがって切り替えの粒度は「会話の途中」ではない

転写の問題は上で消えたが、**キャッシュ全損は消えない**（アカウントに紐づくため）。
**1つの会話の途中で移すと、その会話の費用が約15倍になる。**

**割り当ては Project 単位に寄せる**——この Project は A、別の Project は B。
**枠が尽きたときに移すのは、次の会話から。**

§3 の規律に **資格情報も加える**：**モデルと同じく、走っている会話の途中で
変えない。**

#### OAuth の登録は Elicitation の URL モードに乗る

サブスクの OAuth を登録する画面は、**新しく作らない**——MCP の Elicitation は
**`mode: "url"`** を持ち、仕様が「鍵・トークン・決済のような機微情報は
form で聞いてはならない（MUST NOT）／URL モードを使う（MUST）」と定めている
（§2.4）。**第三者の認可フローを URL モードで回す形は、仕様が想定している用途
そのもの**である。

> **前提が崩れた**（実測 2026-08-30、§2.4）：**Claude Code CLI 2.1.237 は
> `elicitation.url` capability を advertise しない。** この CLI 経由では
> `mode: "url"` の elicitation がそもそも成立しない可能性が高い。**代替の経路
> （banto の host が Elicitation を介さず直接 URL を提示する等）を設計する
> 必要がある——未着手。§10 に追加。**

### 2.9 記憶の全体像——どこに何が残るか

banto が「覚えているもの」は**6つ**あり、層が違う。ここに一覧を置く
（各項目の詳細は参照先）。

| | 何を覚えるか | 誰が持つか | 範囲 | **文脈に入るか** |
|---|---|---|---|---|
| **Event Store**（§2.1） | **起きたこと全部** | banto | banto 全体 | **入らない** |
| **Global Memory**（§2.2） | 人の名前など、Project に紐づかないこと | banto | **banto 全体** | **常に全部** |
| **Memory**（§2.2） | この Project の決まったこと | banto | **Project** | **常に全部** |
| **Skill**（§5.6） | Project をまたぐやり方 | Module が配る | **効かせた範囲** | **名前と説明だけ常に。本体は合致したとき** |
| **会話**（resume-point、§2.2） | いままでのやり取り | **SDK 側** | **Thread** | **入る**（セッションとして） |
| **繋がっているもの**（§2.2） | どの Module / Skill が有効か | banto | Project | tool 定義として入る |

**文脈に入るのは5つ。Event Store だけが入らない**——あれは真実の保管庫であって、
モデルに読ませるものではない。

#### 忘れ方がそれぞれ違う

| | どう減るか |
|---|---|
| **Event Store** | **減らない。** 追記のみで書き換えも削除もしない。**保管上限は削除ではなくセグメント分割＋アーカイブ**（item 5、§2.1） |
| **Global Memory** | **Memory と同じ**（無効化イベントの追記、上限超えは追記拒否＋判断待ち、§2.2） |
| **Memory** | **無効化イベントの追記。上限超えは追記拒否＋判断待ち**（item 3、§2.2） |
| **Skill** | **効かせるのをやめる**／引退させる（§5.7）。中身は Module 側に残る |
| **会話** | **畳む**（同じ Thread のまま resume-point を捨てる、§2.2）／SDK の自動コンパクション（§3） |
| **繋がっているもの** | 外す（§2.2 の決定） |

#### 決まっていること

- **Event Store が唯一の真実**。他は全部そこから導出できるか、外（Module・SDK）にある
- **この5つの外にあるものを文脈に入れない**（§2.3、決定・2026-09-05）——
  `claude_code` プリセットが読む SDK 側の記憶（auto-memory・`CLAUDE.md`）は
  banto の記憶ではない。**入っていたら不具合**で、`getContextUsage()` の
  `Memory files` が 0 でないことで気づける
- **Memory は Project、Skill は Project をまたぐ**（§5.6）
- **Fork Thread は枝分かれした時点の Memory を引き継ぐ**（§2.2）
- **走行中の枝の先頭は変えない**（§3 のキャッシュ規律）
- **学習したことをどちらに書くかは、人に選ばせる**（§5.6）

#### まだ決まっていないこと

**`references/` の重さが見えていない。** Skill の本体は5,000トークン以下が推奨
だが、`references/` は**それとは別に**必要時に読み込まれる。`docs/specs/v4-frontend.md` §6-9 の内訳表示で
見えるようにする必要がある。

### 2.10 設定の分類（決定・2026-09-01）

**「設定」は banto のあちこちに散らばっているが、種類は3つの軸で説明できる。**
Module の設定 Canvas（`docs/specs/v4-frontend.md` §6.2）だけを「設定」だと思うと、core 自身の設定（§2.6）や
資格情報（§2.8）が置き場を持てない——ここでその全体像を1箇所にまとめる。
（画面上の配置は `docs/specs/v4-frontend.md` §6.1、この節は**保存・反映の構造**）

#### 軸1：所有者

| 所有者 | 何が入るか |
|---|---|
| **core（instance）** | 層1 bootstrap／層2 runtime config の**既定値**（§2.6）、役割の有効/無効（`docs/specs/v4-frontend.md` §6.1 階層1） |
| **Project** | Module 集合・Skill 集合（§2.2）、**runtime config の Project 単位の上書き**（§2.2「設定のカスケード」）、資格情報の割り当て・セキュリティ境界の根（`docs/specs/v4-security.md`・§2.8） |
| **Module** | **banto は値を持たない。** Module 自身が tool で読み書きする（`docs/specs/v4-frontend.md` §6.2 で決定済み）。**role に複数の実装があるとき、どれを使うかも含む**——Vault 接続の選択はここに属する（§2.5「role 依存の解決は Module の仕事」、2026-09-02 訂正） |

Project の列は、§2.2 冒頭の表（「次に Runner へ何を渡すか」）に並ぶ**同じ性質の
操作**——新しい概念ではなく、その表の一部として扱う。

#### 軸2：秘密性

- **平文で見せてよい値**（既定モデル、Memory 上限など）——階層1・2 の画面に
  そのまま出す
- **見せてはいけない値**（資格情報の鍵）——**所有者としては core／Project だが、
  Vault という別の保管庫にあり、設定画面からは「登録する・選ぶ」操作しか
  できない。値そのものは表示しない。** 所有者軸だけでは扱いきれない、
  独立した性質として扱う（`docs/specs/v4-security.md`・§2.8・Vault の詳細）

#### 軸3：変更主体

**独立した保存・表示の仕組みは持たない。** 「人だけが変えてよいか、AI も
tool 経由で提案してよいか」は、**その変更操作を AI に露出する tool として
与えるかどうか**という設計判断に還元される：

- **AI に与える** → その変更は tool 呼び出しになり、**`docs/specs/v4-frontend.md` §6.0 の承認ゲートが
  そのまま掛かる**（新しい承認 UI は要らない——直前に作った
  `unstable_humanToolNames` + `addResult` の機構がそのまま使える）
- **与えない** → 人しか UI から触れない

これで **item 20（Project 単位の Module 変更を AI 自身も起票できるか）は
解決した：Yes、tool として露出してよい。ただし通常の tool 呼び出しと同じく
承認ゲートを通る。**

#### UI 固有の状態は「設定」の対象外とする

パネル幅・サイドバー開閉・下書き等は banto の Configuration が扱う対象では
ない——**「振る舞いを変える値」ではない**ので、複製してサーバに送る理由が
無い（規則3）。ブラウザの `localStorage` に任せ、banto の設定体系からは
意識的に外す。ただし「下書き」は失うと実害があるので、性質としては
「Thread の状態」（会話の一部）として扱うべきで、この節の対象外（別の
未決事項）。

## 3. キャッシュ規律

プロンプトキャッシュは前方一致——同じ system prompt・同じ tool 一覧・同じモデルに
新しい発言だけが継ぎ足されていれば、続きの部分だけ課金・処理される。

**Runner が毎ターン組み立て直すのは「コードが状態を持たない」という意味であって、
中身が毎回変わるという意味ではない。** 中身を安定させるのは Project / Thread の規律：

1. **走行中の枝の Memory は変わらない**——先頭部分が1バイトも変わらないこと。
   変更を許すかどうかとは別の話で、**変わるとしても次のキャッシュ境界から**（§2.2）
2. **モデルは Project の間ずっと固定**——変更＝新しい Project
2b. **資格情報は走行中に変えない**（§2.8）——**キャッシュはアカウント単位だと
   実測済み**。切り替えると全損する（同じ会話で費用が約15倍）。
   **割り当ては Project 単位に寄せる**
3. **接続する Module 集合は「黙って変えない」**——tool 定義も system prompt と
   同じくキャッシュ対象。ターンごとに勝手に変わると、**変わったぶんだけ作り直しが
   起きる**（総崩れではない。下の実測）

> **これは banto 固有の工夫ではなく、仕様が意図している性質である**（2026-08-29
> 確認）。tools 仕様いわく：サーバは tool を**決定的な順序**で返すべき（SHOULD）
> ——「クライアントが tool 一覧を確実にキャッシュでき、**tool がモデルの文脈に
> 入るときの LLM プロンプトキャッシュのヒット率が上がる**」から。
> `tools/list` の応答は `ttlMs` / `cacheScope` も持つ。**順序が不安定な Module は
> それだけでキャッシュを壊す**ので、banto 側でも順序を安定させて渡す。

**3 は「固定」ではない。** Project / Thread が明示的に決めて変えるのは**許される、
というより必須**（Project は同じ仕事が続く限り残るので、使える Module が
後から増える・要らなくなるのは通常運転）。

> **Module の tool は「窓の外」に置かれる**（実測 2026-08-30）。tool 定義を
> 増やしても**モデルの文脈には入らない**（`deferred`）：
>
> | tool 数 | cache_read | cache_create | MCP tools の扱い |
> |---|---|---|---|
> | 0 | 24,835 | 0 | 2,940（**窓外**） |
> | 8 | 21,177 | 3,770 | 4,025（**窓外**） |
> | 40 | 21,177 | 4,218 | 8,368（**窓外**） |
> | 120 | 21,177 | **5,338** | 19,300（**窓外**） |
>
> **`cache_read` は一定**——**要件 Phase 1 の完了条件「ツールを足してもキャッシュが
> 落ちない」は満たせる。** tool 120個でも増えたのはキャッシュ生成の 1,568 だけ。
>
> **ここに Skill との非対称がある**——**Skill は窓の中に入り、Module の tool は
> 窓の外にいる**（§5.7）。「Module を増やすと文脈を食う」は成り立たない。

> **実測で分かったこと（2026-08-30）——Module 集合の変更も想定より安い。**
> 同じセッションを `resume` しながら Module 集合を変えて4ターン測った：
>
> | | cache_read | cache_create | 費用 |
> |---|---|---|---|
> | 新規（tool 1個の Module ×1） | 21,177 | 3,680 | $0.0285 |
> | resume（同じ集合） | 24,857 | 48 | $0.0078 |
> | **resume（Module を1つ足す）** | 24,905 | **344** | $0.0096 |
> | **resume（足した Module を外す）** | 25,249 | **336** | $0.0097 |
>
> **キャッシュは総崩れしない。** 変更時に作り直されたのは 340 トークン前後で、
> `cache_read` は伸び続けた。**「変える瞬間にキャッシュ境界を切る」という理解は
> 強すぎた**——正しくは**変わったぶんだけ作り直す**。
> ただし tool 定義が大きい Module ではこの差分も大きくなる
> （上の実測は tool 1個の極小 Module）。
>
> **したがって「黙って変えない」の理由は費用ではなく、追跡可能性である**
> ——何がいつ変わったかが分からないと、挙動の変化を説明できない。

**文脈が膨らんだときの手当ては、いま2つ決まっている**：

| | 誰が決めるか |
|---|---|
| SDK 自身の自動コンパクション | SDK/CLI が自分の予算で判断。banto は指示せず、観測して記録するだけ（規則4） |
| 会話だけを畳んで同じ Thread として続ける | 人（か AI）が能動的に選ぶ。Project / Thread の決定（§2.2） |

**Memory が膨らんだときの扱いは未決**（§2.2・§10）。持っていたが、**それを引き継ぐかどうかも含めて決め直す。**

## 4. 会話を走らせるもの

### 4.1 サブエージェント（worker）と backend

**Base/Fork Thread の会話を走らせることは core（Project / Thread ＋ Runner）である。
サブエージェントの実行はそうではない**——**サブエージェントの実行は core が
管理する普通の Thread ではなく、それを管理する Module（Subagent Module）の
持ち物**（決定・2026-08-31、§10 item 8）。

- **worker（Subagent）Module は「どの backend で走らせるか選ぶ」だけの薄い層。**
  ただし Thread の作成は core 側に残らない——**サブエージェントの実行は
  Subagent Module の持ち物であり、core が管理する Project 直下の Base/Fork Thread
  の並びには現れない**
- **backend Module が担うのは、ベンダの差だけ**——「このプロンプトを投げて、
  結果をこの形で返す」というインターフェース。**Agent SDK 自身が持つ Subagent/Task 機構を使うか、
  Claude Code CLI 自身の Subagent 機構を使うかは、Subagent Module の内部実装の
  選択にすぎない。** Main/Fork Thread 側から見た呼び出し方は同じでなければならない
  ——backend の違いを外に漏らさないという原則をここでも一貫させる
- **core が受け取るのは実行結果の転記だけ**——サブエージェントの会話そのものが
  Base/Fork Thread の並びに漏れてくることは無い

**根拠**：Module 境界の原則（§1、Module は独立したコード）に照らすと、
サブエージェントの実行を core が「普通の Thread」として管理してしまうと、
core が Subagent の内部を知っている必要が生まれ、境界が崩れる。**core が知って
よいのは「依頼した」という事実と、「結果がこう返ってきた」という転記だけ**
——器（channel と thread の作成）は Subagent Module 側に残り、**core に渡るのは
転記される結果だけ**。転記される型は Base Thread のものとまったく同じで、
**サブエージェント固有の事実は1つも無い**。特権を持つ理由が無い。

**backend Module のインタフェースの具体形は未決**（§10）。ただし、Claude 系
以外の実装が core の前提とどこまで噛み合うかを実測した（`opencode-ai`、
`poc/03-item1-backend-interface/`、2026-08-30）：

| core が前提にしていること | opencode（実測） |
|---|---|
| 完了前の差分 streaming | 未対応と判断（プロセス実行中は出力されず、終了時にまとまって出る） |
| ターン途中の割り込み（§2.3） | 未対応（`SIGINT` を送ると出力が空のまま終了。`interrupt()` 相当の明示的な API は CLI に無い） |
| session id での resume（§2.3） | 対応。プロンプトキャッシュも引き継がれた |
| ターンごとの usage（§2.8） | 対応。トークン内訳・キャッシュ・費用が揃っている |
| tool 呼び出しの可視性 | 対応、詳細（tool名・input・output が全部載る） |
| elicitation | **非対応、明示的エラー**（`"Client does not support form elicitation."`——沈黙ではなく、はっきり断る） |
| 文脈の内訳（`getContextUsage()` 相当） | 未対応と判断（見当たらなかった） |

**帰結：backend Module のインタフェースは、この7項目それぞれを
オプショナルな能力として扱い、無いものは「無い」という明示的な値を返す形に
する**（規則2・教訓13——「たぶん動く」で埋めない）。streaming と割り込みと
文脈内訳は、Claude 系だけが提供できる能力として設計する。**インタフェースの
正確な型定義（TypeScript 的な形）はここでは詰めていない**——実測で分かったのは
「何が可能か」の材料であって、答えそのものではない。設計自体は引き続き未決
（§10）。

### 4.2 Thread 間のメッセージ

Thread の AI が、**別の Thread の AI にメッセージを送れる**（要件：Thread 間の
AI 間メッセージング）。例：インフラ管理の Project と、アプリ開発の Project が
やり取りする。

**別の Thread の中身は読まない。** 見えるのは**宛先の一覧**（id・題・状態）だけで、
そこへメッセージを送る。会話の中身を覗くインターフェースは作らない。

#### 新しい機構は要らない

**§2.2 の「次に Runner へ何を渡すか」の一種**である——宛先 Thread に
`user` 役のメッセージを積んで、そのターンを走らせるだけ。§4.1 のサブエージェントと
同じ土台に乗る。違うのは相手の立場だけ：

| | サブエージェント（§4.1） | Thread 間メッセージ（§4.2） |
|---|---|---|
| 相手 | **新しく作る** Thread | **既にある** Thread |
| 寿命 | その仕事のあいだ | 相手は独立に生き続ける |
| 返事 | 呼び出しの戻り値として返る | **返すかどうかは相手が決める** |

#### ループ防止には名前がある（規則12）

「A→B に送ったら B の返事がまた A に送り返って止まらない」は、**メールが
20年前に解いた問題**である——**RFC 3834**（Recommendations for Automatic
Responses to Electronic Mail）。設計を自分で考えず、そこの答えを写す。

RFC 3834 の核：

- **`Auto-Submitted` ヘッダ**が「そのメッセージは人が書いたのか、機械が出したのか」を
  示す
- **`Auto-Submitted` が `no` 以外の値を持つメッセージには、自動応答してはならない
  （SHOULD NOT）**
- 加えて、**送り主あたり・期間あたりの回数を制限する**（メールでは典型的に1日1回）



**banto に写すときの違い**：メールの「自動応答するな」をそのまま適用すると、
**意図した往復（依頼して答えをもらう）まで止まる**。区別するために3つ揃える：

1. **人か機械かの印**（`Auto-Submitted` 相当）——AI が送ったメッセージには印を付ける
2. **ホップ数**——1つの発端から何回中継したかを運び、上限を超えたら止める
   （IP の TTL、メールの `Received` を数える手法と同じ）
3. **速度制限**——同じ相手への連続送信に上限を置く

この3つはメールが実際に併用している組み合わせであり、**どれか1つでは足りない**
（印だけでは意図した往復を止めてしまい、ホップ数だけでは往復の暴走を止められない）。

#### A2A は使わない（が、境界の外では使う余地がある）

**A2A（Agent2Agent）** は「**不透明なエージェント同士が、システムや組織をまたいで
互いを発見し、仕事を委譲する**」ための protocol——Agent Card（能力を公開する
JSON）、Task のライフサイクル（submitted / working / completed / failed /
canceled）、認証を持つ。

**banto の Thread 間は、その境界の内側にある**：

- 相手は同じ banto インスタンスの Thread。**発見が要らない**（Event Store に全部ある）
- **認証が要らない**（同じインスタンスの中）
- **不透明でない**——banto は両方の Thread を持っている
- Agent Card に当たるもの（題・状態）は、**すでに Event Store から導出できる**

**将来 banto の外のエージェントと話すなら A2A**——そのときは §5.1 と同じ姿勢
（配布・接続の標準は発明しない）を採る。**それは境界を越える話であって、
ここではない。**

#### まだ決めていない

- **宛先の粒度**——要件の例（インフラ管理とアプリ開発）は、§1.1 の用語では
  **別々の Project** に当たる。ただし同じ Project の Fork Thread へ送りたい場面も
  ありうるので、**宛先は Thread 単位**にしておけば両方を覆える。確定は未決
- 送るインターフェース（core が直接持つ MCP のインターフェースか、薄い Module か）
- **届いたメッセージが画面でどう見えるか**——**人の発言に見えてはいけない**
  。上の「人か機械かの印」を画面側でも使う

## 5. Module と Skill の契約

### 5.1 パッケージングとマウント

**banto は配布形式を発明しない**（規則12）。MCP には既に**公式のレジストリと
`server.json`** がある（2026-08-29 確認）：

- `server.json` が「この MCP サーバは何で、どう手に入れて、どう起動するか」を書く
  ——`packages`（npm・PyPI・NuGet・Docker/OCI 等、registry type ＋ identifier ＋
  version ＋ transport）と `remotes`（HTTP エンドポイント）。両方書いてよい
- 公開は `mcp-publisher`、取得は公式レジストリの REST API

**したがって banto への「マウント」は、他の MCP クライアントがやっていることと
同じ**——`server.json` が示す形で起動するか、`remotes` の URL に繋ぐ。banto 独自の
パッケージ形式・独自のインストーラを作らない。

**クライアント側の設定形式にも標準化の動きがある**——`server.json` が「配布」の
仕様なのに対し、**`mcp.json`（SEP-2633）が「クライアントがどう繋ぐか」の仕様**。
提案の動機がそのまま現状の問題を言っている：クライアントごとにファイル名も形式
（JSON / JSONC / TOML）もトップレベルのキー（`servers` / `mcpServers`）も
秘密の埋め込み方も違う。

> **状態は「提案中」**（PR #2633、2026-04）。**確定ではない**ので、banto は
> **`mcpServers` 形（Claude Code・VS Code 等の事実上の共通形）に寄せつつ、
> 仕様が固まったら合わせる**。独自形式を作らない。

**マウントの記録は Event Store に置く**（item 9 の一部、決定・2026-08-30）。
bootstrap config（層1、§2.6）ではない——**層1 は「Event Store を開くより前に
要るもの」に限る**と決めた時点で、Module 一覧はそこに入らない（Module が無くても
banto は起動する）。Event Store に置く利点は2つ：**Module を足す・外すのは
走行中の操作なので、その履歴が規則3のまま自然に残る**こと、そして
**「どこに置くか」と「誰が書き込めるか」は別の軸**であること——
`module.mounted` / `module.unmounted` のようなイベント型として記録しても、
**そのイベントを追記する tool を AI に公開しなければ、任意コード実行の権限は
AI に渡らない**。`subprocess` の起動コマンドは任意コード実行そのものだが、
**item 20（§2.10、決定・2026-09-01）により、AI に公開してよい——ただし
tool 呼び出しとして承認ゲート（`docs/specs/v4-frontend.md` §6.0）を必ず通り、人が起動コマンドの中身を
見てから許可する。** イベント型の具体的な中身は item 4（Event Store の
read model）が決まってから詰める。

**決定（2026-09-06、Phase 1）——受け入れる起動の形は1種類だけ。**

**「このプログラムを、この引数で、この環境変数で起動する」**。これだけ。
パッケージ名からの解決・自動インストール・レジストリからの取得は**入れない**（規則10）
——いま要るのは「もうそこにあるものを起動する」ことだけで、それ以上は必要になってから
足せばよい。この1種類で **TypeScript でない Module（Python・Ruby・Go）も同じ書き方で載る**
——実際、Python の Module を宣言1本で繋いで AI が tool を呼べることを実測した
（2026-09-06、`docs/notes/2026-09-06-module-declaration.md`）。

宣言に書ける差し込み語は、**host が起動時に確定させる値だけ**
（node の実行ファイル・banto の置き場・データ置き場・中継の URL と合言葉・Project の根）。
知らない語が書かれていたら**起動する前に落とす**（規則2——黙って空文字で起動しない）。
Project の根は、`scope: "project"` の Module だけが使える。

#### Module の発見元は3つ（決定・2026-09-02、`server.json`／`mcpServers` 規約に
乗せ直して訂正）

**banto 自身が Module を探すための一覧（マーケットプレイス UI）は持たない。**
発見は既にある場所に任せ、banto は「見つけた後、繋ぐ」だけを担う——規則12
（既存のエコシステムに寄生する）と、規則7（スコープ外に触らない）の両方から
出てくる帰結。

**前回（2026-09-02 前半）は発見元を4つに分けたが、実在する規約を確認した
うえで3つに整理し直した**（WebSearch で確認：`server.json` は
`modelcontextprotocol/registry` が定める公式スキーマで `packages`／`remotes`／
`_meta`（逆 DNS 名前空間のカスタムメタデータ）を持つ。`mcpServers` は
Claude Desktop・Claude Code・Cursor 等が共通して使う実質標準の設定形式で
`command`/`args`/`env`（stdio）または `url`/`headers`（remote）を持つ）。
**banto は両方とも自分で発明せず、そのまま乗る：**

| 発見元 | 何をするか | 使う場面 |
|---|---|---|
| **公式レジストリからインストール**（`registry.modelcontextprotocol.io`） | REST API で検索し、見つけた `server.json` を `mcpServers` エントリに変換して保存 | 一般に公開されている MCP サーバーを探す |
| **`server.json` を指定してインストール** | リモート URL で指定、または手元の `server.json` ファイルをアップロード——**どちらも同じ「`server.json` を読む」処理**。banto 自身の Module も含め、GitHub 上の `server.json` を URL で指すだけで取り込める | 公式レジストリに出ていない Module（社内限定・個人用・banto 固有の `_meta` 拡張前提のものを含む）。**新しい配布形式は作らない**——Claude Code の `/plugin marketplace add` が独自リポジトリ形式を要求するのとは違い、banto は既存の `server.json` 1枚で足りる |
| **`mcpServers` 規約を直接記入** | `server.json` すら無い場合の最終手段——`command`/`args`/`env` または `url`/`headers` を人が直接書く | どちらの規約にも乗っていない、ごく単純な stdio/remote サーバー |

**instance 単位の Module 管理 UI（item 14、§10）は、この3つを切り替える
だけの薄い画面でよい**——banto 自身が検索・カタログ・レビューを持つ
「ストア」を作る必要が無くなった。**installed の管理も同じ規約に乗る**：
banto が保持する「instance が知っている実装」の実体は、内部的には
`mcpServers` 形式の集合——実装を1件足す・消すは、このオブジェクトへの
追加・削除でしかない。

**将来の TODO（今は作らない、規則7）**：banto 専用モジュールが増えたら、
「GitHub 上の `server.json` の URL 一覧」だけを中身に持つ banto 専用の
カタログリポジトリを作ってもよい——ただしこれは上の3つ目「`server.json` を
URL 指定」の**利用者向けショートカット**（どの URL を打てばいいか探す手間を
減らすだけ）であって、新しい発見元にはならない。

#### role・依存の宣言は `server.json` の `_meta` に乗せ、接続時に自己申告と
突き合わせる（決定・2026-09-02）

§2.5 で「role は Module 自身が宣言する」と決めたが、**どこに書き、いつ
読むか**を詰める。`_meta` は `server.json` にも MCP の `InitializeResult`
にも存在する拡張点（2026-09-02 確認：逆 DNS 名前空間、`modelcontextprotocol`/
`mcp` を第2ラベルに使う接頭辞は予約済みなので `dev.banto/module` のような
banto 独自の接頭辞を使う——§5.4 で決めた「banto の逆 DNS 接頭辞を `_meta`
キーに使う」と同じ規則）。**この1つの `_meta` キーを、静的・動的の両方の
置き場として使う：**

1. **静的宣言**：`server.json`（→ `mcpServers` エントリに変換して保存する
   ときも一緒にコピーする）の `_meta["dev.banto/module"]` に「自分が満たす
   role」「依存している role」を書く。host は Module を spawn/接続する**前**に
   これを読み、役割解決の初期候補を作れる（毎回全 Module を起動して確かめる
   必要が無い）。**形**（決定・2026-09-02、要件 C11 との整合、下記）：
   ```json
   {
     "satisfies": ["shell"],
     "dependsOn": [
       { "role": "vault", "required": true },
       { "role": "notifications", "required": false }
     ]
   }
   ```
   `dependsOn` の各項目は `required: true`（無いと Module 自体が動けない）か
   `required: false`（無くても動けるが、使う一部の tool が断る）かを持つ——
   要件 C11「必須が満たされなければ起動せず、任意が満たされないときは、
   それを使うツールだけが理由つきで断る」の「必須／任意」はこのフィールドで
   表現する
2. **動的自己申告**：Module を実際に spawn/接続し、`initialize` 応答の
   `_meta["dev.banto/module"]`（同じキー）を受け取る
3. **突き合わせ**：静的宣言と動的自己申告が**食い違ったら、動的（実際に
   繋いだ結果）を正として `mcpServers` 側の記録を更新する**

**これは規則1「自己申告を信頼しない」と矛盾しない。** 静的宣言は「Module が
過去に自己申告した値のキャッシュ」でしかなく、**信頼して使うのではなく、
接続するたびに実物（動的自己申告）と照合して食い違いを検出・修正する**——
検証してから使う、という規則1の姿勢そのもの。新しい機構ではなく、
「宣言的な設定＋実行時のヘルスチェックで乖離を直す」という一般的な形
（例：Kubernetes が spec と実際の状態を継続的に照合するのと同じ構図）。

**これで item 2「host の自動役割解決の設計」（§10）は解決した**——候補の
列挙は `mcpServers` の `_meta` から自動、実行時に自己申告で正す。「候補が
2つ以上あるときどれを使うか」は、§2.5「role 依存の解決は Module の仕事」
（2026-09-02）の決定どおり、host ではなく依存する Module 自身が選ぶ。

**ただし `scope`／`isolation`／`handlesSecrets`／`confinement` の4フィールドは、
この突き合わせルールをそのまま適用してはいけない**（決定・2026-09-03）。
他のフィールド（`satisfies`/`dependsOn`）は接続後のルーティングにしか
影響しないので「動的な値で記録を更新するだけ」でよいが、この4つは
**spawn の仕方そのもの**を左右する——読み取った時点で、すでにその形で
spawn してしまっている。例えば `confinement`（Landlock で閉じ込めるか）が
静的宣言と食い違って発覚しても、その時点で Project 間共有のプロセスに
なっているかもしれない。

**したがってこの4フィールドで食い違いを検出したら：**

1. **その接続を切る**（読み違えたまま動かし続けない）
2. **動的自己申告の値に基づいて正しい形で再 spawn する**（例：`confinement`
   がある = Project 単位のプロセスに、無い = instance 単位のプロセスに、
   というように配線をやり直す）
3. **食い違いを Event Store に記録する**
4. **同じ Module で2回続けて食い違ったら、遮断する**（自動修復を無限に
   繰り返さない——規則6「間欠的に落ちるものはリトライを足さない」と同じ形）

#### mcpServers への秘密情報の注入は、Vault の alias 方式が使える（必須ではない）
（決定・2026-09-02 改訂）

`mcpServers` の `env`（stdio）・`headers`（remote、`${VAR}` 構文）に書く値が
秘密情報のとき、§2.5「alias 方式」を使える——**AI に見えるのは alias 名だけ、
値は Module を spawn/接続する直前に host が Vault から解決して直接注入する**
（Shell への注入と同じ経路・同じ理由）。

**ただし alias 方式は必須ではない。** `env` に値を直接書く（例：ローカル開発中の
使い捨てトークン）ことも妨げない——banto は「書ける形」を1つに絞らない。
**alias は「値を人が見なくて済む・AI に渡さなくて済む」ための手段であって、
mcpServers の書式そのものを変えるものではない**（`"env": {"API_KEY": "$my-alias"}`
のように、値の文字列が `$` で始まる alias 名か、直接の値かの違いでしかない）。

> **alias の表記は場面によって2通りあり、これは意図した違いである**（決定・
> 2026-09-02、整合性の確認）。`envSecrets`/`secretFiles`（Shell、
> `docs/specs/v4-modules.md` §2.3）は alias 名を**裸のまま**書く
> （`{ENV名: alias名}`）——`command` 文字列とは別の引数なので、値との
> 混同が起きず、`$` で区別する必要が無い。一方この節の `mcpServers` の
> `env` は、**1つの同じフィールドに alias 参照と直接値が両方入りうる**ため、
> `$` 前置で区別する必要がある。**どちらも「同じ alias 方式」の別の
> 適用場面であって、表記の不統一ではない**——フィールドが値専用か
> 値/参照兼用かで、区別の要否が変わるだけ。

**「Vault 自身の起動は例外」だった扱いを撤回し、SOPS デフォルトバックエンドに
一本化する（決定・2026-09-02）。** 従来は「Vault 自身のバックエンドが必要とする
秘密情報は alias 方式では解決できない（鶏卵問題）」として、banto 組み込み
バックエンドの暗号化ストアという**別枠の仕組み**を用意していた。これを
やめ、次の形にする：

1. **SOPS デフォルトバックエンドは、`vault` 役割の中で唯一「起動に外部の
   秘密情報を必要としない」実装**——復号鍵はローカルのファイル（age/PGP鍵）
   としてbanto自身が直接持ち、alias解決を経ない。これが鶏卵問題を構造的に
   断ち切る唯一の場所（§2.8で述べた通り）
2. **他のバックエンド（HashiCorp Vault・Infisical 等）を追加するとき、
   その接続に要る秘密情報（APIトークン等）は、SOPSデフォルトバックエンドに
   ——他の秘密情報とまったく同じように——alias として登録する。**
   Infisical バックエンドの設定 Canvas（`ui://<id>/config`）は、この alias を
   参照してInfisical自身に接続する
3. **帰結：「Vaultの起動は特別」という例外が要らなくなった。** 特別なのは
   SOPSデフォルトバックエンド1つだけで、そこから先（Infisicalを含む、
   他のどのバックエンドも）は、他のModuleが秘密情報を使うのとまったく同じ
   alias方式に乗る——Vaultだからといって特別扱いする箇所が、SOPSの
   復号鍵という1点まで縮んだ

### 5.2 名前空間は banto が採番する

**`server.json` や `serverInfo` の `name` を識別に使わない。** 仕様が明記している
（2026-08-29 確認）：

> tool 名の一意性は**1つのサーバの中でのみ**保証される。複数サーバの tool を
> 束ねるクライアントは**衝突しうる**ので、**サーバ識別子を接頭辞に付けるなどの
> 曖昧さ解消を実装すべき（SHOULD）**。**サーバ `name`（`serverInfo` 由来）は
> サーバ間で一意である保証がなく、曖昧さ解消に依存すべきでない（SHOULD NOT）**

したがって **banto が Module 識別子を自分で採番し、それを tool の接頭辞にする**。
自己申告の名前を信じない（規則1と同じ姿勢）。

tool 名の制約も仕様にある：1〜128字、`A-Za-z0-9_-.`、大文字小文字を区別。
**接頭辞を付けたあとの長さがこの上限に収まること**を確かめる。

### 5.3 tool の性質は `annotations` で分かるが、信じてよいとは限らない

仕様は tool に `annotations` を定義している（`ToolAnnotations`、2026-08-29 に
schema で確認）：

| フィールド | 意味 | 既定 |
|---|---|---|
| `title` | 人に見せる名前 | — |
| `readOnlyHint` | true なら環境を変更しない | `false` |
| `destructiveHint` | true なら破壊的な更新をしうる（`readOnlyHint == false` のときだけ意味を持つ） | **`true`** |
| `idempotentHint` | true なら同じ引数で繰り返しても追加の効果が無い | `false` |
| `openWorldHint` | true なら外部の「開いた世界」と関わる（web 検索は true、メモは false） | `true` |

**既定が安全側に倒れている**——何も宣言しない tool は「破壊的で、外の世界に触る」
とみなされる。banto の「既定値は忘れられる」（§9）と同じ設計思想なので、そのまま使う。

**ただし仕様は釘を刺している**：

> 信頼できるサーバから来たものでない限り、クライアントは tool の annotations を
> **信用してはならない（MUST）**

つまり `readOnlyHint: true` を根拠に確認を省いてはいけない。**annotations は
「人に見せる材料」と「既定をきつくする材料」に使い、緩める根拠には使わない。**

### 5.4 banto の拡張は `_meta` に載せる。別のマニフェストを作らない

設定 Canvas（`docs/specs/v4-frontend.md` §6.2）や launcher（`docs/specs/v4-frontend.md` §6.2）は **MCP の仕様に無い banto の拡張**である。
これを「banto 用マニフェストファイル」として別に持たせると、**Module が banto
専用になり、「完全に独立したコード」（§1）が崩れる。**

**仕様には拡張を載せる正式な場所がある**——`_meta` のベンダ接頭辞（2026-08-29 確認）：

- キー名は「接頭辞（省略可）＋名前」。接頭辞は**逆 DNS 記法のラベルをドットで
  繋いでスラッシュで閉じる**（例 `com.example/`）
- **第2ラベルが `modelcontextprotocol` または `mcp` の接頭辞は MCP 予約**
  （`io.modelcontextprotocol/`・`dev.mcp/`・`com.mcp.tools/` 等）。
  banto の接頭辞は第2ラベルがそれ以外なので、規則どおりに取れる
- 仕様いわく「third-party extensions use their own vendor prefix」

**決定**：banto の拡張は、**banto の逆 DNS 接頭辞を付けた `_meta` キー**として
資源・tool に載せる。**Module 側に banto 専用のファイルは要らない**——
`resources/list` に出てくる資源の `_meta` を banto が読むだけ。

この形の利点：**同じ Module が他の MCP ホストでもそのまま動く**。banto の拡張は
知らないホストからは単に無視される `_meta` にすぎない。

**接頭辞の文字列は `dev.banto` に決めた**（決定・2026-09-02）。banto は
ドメインを所有していないが、`_meta` の逆 DNS 記法は実際に DNS 解決できる
必要はなく、**名前空間の衝突を避けるための記法**でしかない（仕様上も
「third-party extensions use their own vendor prefix」としか要求していない）。
`dev.banto/module`・`dev.banto/visibility` は既にモック・今回のPoCで一貫して
使われており（`mock/lib/mock/settings.ts` 等）、これを正式な決定にするだけ——
新しい文字列は選ばない。

> **§5.5 は欠番。** Module 同士の呼び出しは §2.5「Module 間の呼び出し——host
> が中継する」にまとめてある（旧稿の経緯は
> `docs/notes/2026-09-02-module-relay.md`）。

### 5.6 Skill——Module が配り、core が効かせる

**Skill には確立した形式がある**（規則12）——**Agent Skills**（`agentskills.io`、
2025-12-18 に公開標準化。Agentic AI Foundation が管理）。2026-06 時点で約40の
製品が対応。**banto は形式を発明しない。**

- `SKILL.md`：YAML frontmatter に **`name` と `description` の2つだけが必須**、
  あとは Markdown の本文
- 任意のディレクトリ：`scripts/`（実行するコード）・`references/`（必要になったら
  読む長い資料）・`assets/`（雛形）
- **progressive disclosure が3段**：起動時は**名前と説明だけ**（1スキルおよそ
  100トークン）→ task が合致したら **`SKILL.md` の本文**（5,000トークン以下を推奨）
  → 必要なときだけ `references/`

#### Skill は「能力」ではなく「文脈」である

**この一点が core / Module の分かれ目を決める。** progressive disclosure の第1段
——名前と説明——は、**起動時からモデルの文脈に入る**。tool 定義とまったく同じ位置で、
**§3 のキャッシュ規律がそのまま掛かる**。

したがって扱いは Module 集合と同じ：

| | 誰の仕事か |
|---|---|
| **どの Skill をこの Project に効かせるか** | **core**（§2.2 の決定の一種。**黙って変えない、明示的にだけ変える**——変える瞬間にキャッシュ境界が切れる） |
| **Skill の中身を配る・保管する・探す** | **Module でよい** |

**§2.5（host が候補を解決し、Project がそのうちどれを繋ぐか選ぶ）と同じ補完関係**
であり、`docs/specs/v4-frontend.md` §6.2（Module が中身を持ち、core が置き場を決める）とも同じ形。

#### 配り方——普通の MCP 資源に載せる

**外部の Skill も自作の Skill も、Module が MCP の資源として配れる**
（`resources/list` / `resources/read`）。`SKILL.md` は移植可能な1ファイルなので、
新しい運び方は要らない。**どの資源が Skill かの印は `_meta`**（§5.4。config・
launcher と同じ1つの仕組みを使う）。

> **`skill://index.json` は標準ではない**（2026-08-29 確認）。MCP サーバから
> Skill を配る方式（`skill://index.json` の索引、`skill-md` / `archive` の2形式）を
> 実装している処理系があるが、**`agentskills.io` の仕様が定義しているのは
> ファイル形式だけ**で、MCP 配布は含まれていない。**特定実装の慣習に乗らない**
> ——普通の資源＋`_meta` で足りる。標準化されたら乗り換える。

#### 学習——引き金は2つ、インターフェースは1つ

**Skill を書くインターフェースは §5.7 の「自作／AI が書いた Skill」と同じ1つ**である。
違うのは**誰が引き金を引くか**だけ。**インターフェースを分けない**——後から引き金を足すのが安くなる。

| | 引き金 | 優先度 |
|---|---|---|
| **人が起点**（Devin 型） | **会話の中で人が訂正し、その学びを Skill に書き戻す** | **先に作る** |
| **AI が起点**（Hermes 型） | 複雑な仕事を終えたとき、失敗から回復したときに、AI が自分で書く | **低い** |

**人が起点の形が先である。** サーベイで確認した Devin の使い方——
「同じ playbook で複数並行に走らせ、**詰まったところを人がチャットで直し、
その学びを playbook に書き戻す**」——は、**自律的な書き換えを必要としない**。
`update_skill` のインターフェースがあれば、人が「いまの学びを Skill に足して」と言うだけで成立する。

**AI が起点の形を足すときも、Hermes Agent のやり方を写す**（自分で考えない）。
インターフェースは同じなので、引き金の条件を足すだけになる。

#### 学習したことを Memory と Skill のどちらに書くか

§5.6 で区別は決めた（**Memory はこの Project の決まったこと、Skill は Project を
またぐやり方**）が、**実際に「いま学んだこと」が来たときにどちらへ書くかは、
毎回の判断**になる。**AI が黙って決めると混ざる。**

**Elicitation の enum で人に選ばせる**（§2.4）——「この学びをどこに残すか：
この Project の Memory ／ 再利用する Skill ／ 残さない」。**新しい機構は要らない。**

> **Devin が同じ区別を持っている**ことがサーベイで分かっている——「繰り返す
> 一行ルールは **Knowledge**、手順は **playbook**」。**別の製品が独立に同じ線を
> 引いている**ので、区別そのものは筋がよいと考えてよい。

**すでに決まっていることから出る制約は1つだけ**：**効かせる Skill 集合の変更は
明示的な決定である**（上表・§3）。Skill が書かれた瞬間に黙って次のターンの文脈が
変わる形にはしない——**キャッシュ境界が切れるから**であって、内容を審査するためでは
ない。書くこと自体は妨げない。

なお Skill の作成・更新・引退が Event Store に残るのは、**Skill に固有の規律では
なく、banto では起きたことが全部イベントとして残るから**（§2.1）。

> **どこまで自動にするかは決めていない**（§10）——「書くのも効かせるのも AI に
> 任せる」から「書くのは AI、効かせるのは人が承認」まで幅がある。
> **ユーザーの希望は自己学習そのもの**（「HermesAgent のように自己学習できると
> 素晴らしい」）なので、既定を「人の承認が要る」に寄せる根拠は、いまのところ無い。

#### Memory と Skill を混同しない

どちらも「文脈に入る、AI が書ける知識」なので、区別を決めておく：

| | Memory（§2.2） | Skill（§5.6） |
|---|---|---|
| 範囲 | **その Project 限定** | **Project をまたいで再利用** |
| 文脈への入り方 | **常に全部入る** | **名前と説明だけ入り、必要なときに本体** |
| 中身 | この仕事で決まったこと | やり方・手順 |

### 5.7 Skill の入手・作成・管理

#### 入手の経路を1本に保つ——Skill を入れる＝Module をマウントする

§5.6 の「Module が配り、core が効かせる」を例外なく通すと、**Skill を入れる行為は
Skill を配る Module をマウントすること**（§5.1）になる。**banto に2つ目の配布機構を
作らない。**

**既存実装も同じ形をしている**（規則12。2026-08-29 確認）——Claude Code は
**plugin という束**を単位にし、**その中に skills も MCP サーバも hooks も入る**
（`/plugin marketplace add <owner>/<repo>` でカタログを足し、`/plugin install` で
束ごと入れる）。banto の Module は MCP サーバなので、**Module が Skill も配れば
plugin と同じ役割を果たす**——束ねる単位を2つ作る必要がない。

#### 入り口は3つ、経路は1つ

| 入り口 | どう入るか |
|---|---|
| **外部の Skill（Module が配っている）** | **その Module をマウントするだけ。** Skill は資源として配られる。**真実は配り手側にあり、banto はそれを取りに行く**（下記「実体化」参照）。更新は配り手側で起きる |
| **外部の Skill（ファイルだけで配られている）** | **banto のローカル Skill Module が取り込む。** `SKILL.md` は移植可能な1ファイルなので取り込める。**現実にはこれが主要な経路**（下記） |
| **自作／AI が書いた Skill** | **同じローカル Skill Module に書く** |

> **「ファイルだけ」が例外ではなく多数派である**（2026-08-29 に実態を確認）。
> `anthropics/skills`（公式）も `awesome-agent-skills` 系の一覧が指す先も
> **git リポジトリの中のフォルダ**で、MCP サーバではない。索引サイト（SkillsMP 等、
> 公開 `SKILL.md` を GitHub から集めて検索可能にする独立の企画）にも
> **公式の CLI や自動導入の仕組みが無く、ZIP を落とす形**。
> **取り込み口は脇道ではなく、主要な入り口として設計する。**

#### 取り込み口が対応する形

実態を見ると、**出所の形は実質2つ**に落ちる：

| 形 | 例 |
|---|---|
| **git リポジトリの、あるパス**（`owner/repo` ＋ サブディレクトリ ＋ 任意の ref） | `anthropics/skills`、`awesome-*` の一覧が指す先の大半 |
| **圧縮ファイル、または手元のフォルダ** | 索引サイトからの ZIP、自分で書いたもの |

**一覧サイト（`awesome-*`）は「発見の手段」であって取得元ではない。** 実体は
結局 git リポジトリなので、**一覧ごとに専用の取り込み口を作らない**
——リンクを辿った先が上の2つのどちらかになる。

決めること：

- **取り込む単位は1つの Skill（フォルダ）。** リポジトリ丸ごとではない
  （`anthropics/skills` は複数の Skill を含む）。まとめて取り込む口があってもよいが、
  単位はフォルダ
- **出所を必ず記録する**——どこから・いつ・どの ref。**更新に追随するために要る**
  （元が動いたかを判定できないと、取り込んだ写しが黙って古くなる）
- 取り込んだあとは**自作 Skill と同じ扱い**（ローカル Skill Module が配る）

#### 外部 Skill は「他人が書いた、文脈に常駐する指示文」である

**tool より扱いが難しいところがある**、と自覚して設計する：

- tool は**呼ばないと効かない**が、**Skill は効かせた時点で説明が毎ターン文脈に入り、
  活性化すると本文がまるごと入る**
- **`scripts/` に実行コードを同梱できる**（Agent Skills の仕様、§5.6）
- 索引サイトが集めているのは**公開 GitHub 上の他人のファイル**である

**どう扱うかは未決**（§10）。選択肢の幅：取り込みを人の明示的な行為に限るか／
AI にも開くか、`scripts/` を含む Skill を別扱いするか、出所をどこまで見せるか。
**ここは根拠を出して選ぶ話であって、既定を決め打ちしない。**

**core から見ると3つとも同じ**——「ある Module が配っている Skill」。
`skills` は §2.5 の**役割**であり、**複数の Module が名乗ってよい**（辞書として
共存する）。banto 自身が持つローカル Skill Module は、そのうちの1実装にすぎない。

#### 名前空間は Module 識別子をそのまま使う

新しい規則を作らない。tool と同じく、Skill も **banto が採番した Module 識別子**で
修飾する（§5.2）。Claude Code も plugin 名で namespace している——**同じ問題に
同じ答え**。

#### 「入っている」と「効いている」を分ける

**これは利便性の話ではなく、progressive disclosure から出る必然である。**
効いている Skill は**名前と説明が起動時からモデルの文脈に入る**（1つおよそ
100トークン）。したがって：

- **効いている Skill の数が、そのまま毎ターンのトークンを食う。** 100個効かせれば
  毎ターン約1万トークン。**「全部効かせる」は成立しない**
- **効く・効かないの変更はキャッシュ境界を切る**（§3。tool 集合の変更と同じ位置）

> **実測（2026-08-30）——「効いている数がそのまま食う」は本当だった**：
>
> | | Skills の行 | cache_read |
> |---|---|---|
> | 指定なし（既定） | **1,949** | 25,168 |
> | `skills: 'all'` | 1,949 | 25,168 |
> | **`skills: []`** | **（消える）** | 21,177 ＋ 作り直し 1,862 |
>
> **そして既定が危ない。何も指定しないと全部載る**（`'all'` と同じ）。
> **`settingSources: []`（分離モード）にしても Skill は載ったまま**だった。
> **banto は毎回明示的に指定する**——指定を忘れると、ディスク上の Skill が
> 黙って文脈に入る（§9「既定値は忘れられる」そのもの）。
>
> **Module の tool とは効き方が違う**（§3）——**Skill は窓の中、tool は窓の外**。

決まること：

- **「入っている（マウント済み）」と「効いている（文脈に入る）」は別の状態**として
  持つ。Claude Code も disable と uninstall を分けている
- **画面は、効いている Skill の数とそれが食っているトークン量を見せる**
  ——見えないものは際限なく増える
- **切り替えはまとめてできる形にする。** 1つずつ切り替えて毎回キャッシュ境界を
  切ると高くつく

#### 実体化——Skill を Runner に渡す配線は core が持つ

Module は Skill を **MCP 資源として**配る。Runner（＝Claude Agent SDK）が Skill を
どう受け取るかは別の話で、**ファイルとして置くことを要求する可能性がある**
（未確認、下記）。

**その差を埋める配線は Module にはできない**——Module は Runner を知らず、他の
Module の Skill も知らない。**全部を見ている host だけが解決できる**（§2.5(a)）。
Module 集合の組み立てとまったく同じ理由で、**ここは core に要る。**

**実体化した `SKILL.md` は「写し」ではなく「キャッシュ」として扱う。** §2.1 で
引いた境界線をそのまま使う——**いつでも捨てて取り直せ、取り直した結果が必ず一致する**
なら、規則3 は破れていない。守る条件は3つ：

1. **実体化したものを真実として扱わない。** 真実は配り手（Module）側にある
2. **`notifications/resources/list_changed` で捨てる。** 元が変わったら作り直す
3. **人が編集できる場所に置かない。** 置いた瞬間、そこが第二の真実になる
   ——自作 Skill も**ローカル Skill Module が真実**であって、実体化ディレクトリ
   ではない

> **実測で確定した**（2026-08-30）：**メモリ上の値では渡せない。名前の配列で渡し、
> 中身はディスクから発見される。** したがってこの節の実体化層は**必要**である。

#### 効かせる粒度は2つ

Skill は **Project をまたいで再利用するもの**（§5.6 の Memory との対比）。
だから自然に2つの粒度が出る：

- **banto 全体の既定**——どの Project でも効く
- **Project ごと**——この Project でだけ効かせる／外す

（`docs/specs/v4-frontend.md` §6.1 の設定画面が2階層なのと同じ形になるが、**根拠は別**である——こちらは
Skill が Project をまたぐという性質そのものから出ている）

#### まだ決めていない

> **実体化は必須だと確定した**（実測 2026-08-30）。SDK が受け取るのは
> **Skill の名前の配列**（`string[]` または `'all'`）で、**中身は渡せない**
> ——Skill は**ディスク上から発見される**。したがって
> **Module から取った `SKILL.md` を banto が実体化する層が要る**（§5.7）。
>
> **さらに重要**：この指定は**文脈フィルタであってサンドボックスではない**。
> 仕様の言葉で「外した Skill はモデルの一覧から隠れ Skill tool から拒否されるが、
> **ファイルはディスクに残り `Read`/`Bash` から届く**」。
> つまり**「効かせていない Skill も、AI は読めてしまう」**
> ——§5.7 の「入っている／効いている」の区別は**文脈の話であって、
> 到達可能性の話ではない**。到達も止めたいなら、`docs/specs/v4-security.md` の境界の側で止める。
- **外部 Skill の扱い**（上の「他人が書いた、文脈に常駐する指示文」）——取り込みを
  人の明示的な行為に限るか／AI にも開くか、`scripts/` を含む Skill を別扱いするか、
  出所をどこまで見せるか
- 取り込み口の具体形（git の指定の書き方、ref の既定、更新の検出方法）
- **AI が「この Skill を効かせてほしい」と言えるか**——progressive disclosure で
  モデルが選ぶのは**活性化**（説明を見て本体を読む）であって、効く候補に入れるか
  どうかではない。後者を AI に開くかは別の判断
- 更新——Module が配る Skill が更新されたとき（`notifications/resources/list_changed`
  で気づける）と、取り込んだ写しの追随
- 効く・効かないの記録先（§2.6 のどちらの層か。Project ごとの分は Event Store が
  自然に見えるが未確定）
- 自己学習をどこまで自動にするか（§5.6）
- Skill の探索を Command Palette（`docs/specs/v4-frontend.md` §6.3）に出すか

> **§6 フロントエンド側の core は `docs/specs/v4-frontend.md` に分離した**（2026-09-02）。

| **A-8** | キャッシュはアカウント単位か | **アカウント単位。切り替えた回は cache_read が 0 に落ち、費用が約15倍**（$0.0085 → $0.154）。**ただし戻せば温まりも戻る**（§2.8） |
| **A-9** | サブスクの残量を知る手段があるか | **実際に値が返った**（`five_hour.utilization: 5` / `seven_day.utilization: 19` と各 `resets_at`）。**型定義より多くの欄が返る**（`limit_dollars`・`spend`・`model_scoped` 等）ので、**型に無いものに依存しない** |

#### 追加で測ったもの（2026-08-30）

| | 結果 |
|---|---|
| **Module の tool を増やしたときの文脈とキャッシュ** | **tool 定義は窓の外（`deferred`）**。120個でも `cache_read` は一定、増えたのはキャッシュ生成 1,568 のみ。**要件 Phase 1 の完了条件を満たせる**（§3） |
| **Skill の実コストと絞り込み** | 効いている Skill が **1,949 トークン**を常時占める。`skills: []` で消える。**指定しないと全部載る**（§5.7） |
| **Landlock を実際に掛ける** | 閉じ込め成立。**資格情報も守れた**。`execve` をまたいで継承。ただし**実行に必要なものを許可しないと shell が起動しない**（`docs/specs/v4-security.md`） |
| **`forkSession` で枝分かれ** | **新しい `session_id` になるが、キャッシュは引き継ぐ**（枝分かれ直後の `cache_read` 22,832 / 作り直し 84）。**元の枝もそのまま続けられる**——両方の枝が温まったまま並存する |

#### system prompt を自前に置き換えた前後（2026-09-05）

同じ内訳（`getContextUsage()` の `categories`）で比べた。Module 構成は同じ
（MCP tools 1,003 で一致）。

| | `claude_code` プリセット＋追記 | **core が組み立てた全文** |
|---|---|---|
| System prompt | 3,515 | **2,605** |
| System tools | 902 | 902 |
| MCP tools | 1,003 | 1,003 |
| **Memory files** | **155** | **カテゴリごと消えた（0）** |

**`Memory files` は banto の Memory ではない**——プリセットが読み込む SDK 側の
記憶（auto-memory・`CLAUDE.md`）だった。これが消えたことが、この置き換えで
一番効いた点（真実が二箇所だった、規則3）。

**同時に、AI から見えるものが実態と揃った**（実機で確認）：ツールを挙げさせると
Bash・Read・Edit・TodoWrite・Task を挙げなくなり、実在する tool
（WebSearch / WebFetch / MCP の各 tool）だけを挙げる。**Memory も初めて
system prompt に入った**——それまで記録はされていたが AI に渡っていなかった
（§2.2 の食い違い、2026-09-05 に発見・修正）。

**B が モデルB を採用してよいかの分かれ目だった**（§2.3）——**実測で通った**
（2026-08-30）。1ターンの固定費は**プロセス起動の約2.4秒が支配的**で、
**Module を繋ぐ費用は付随的**（subprocess 8本でも +0.45秒、1本あたり約16ms）。
**「毎ターン繋ぎ直すのは高い」という懸念は当たらなかった。**
§2.3 の「性能実測が済むまでは仮」は外れ、**モデルB は本決まり**とする。

**Base Thread に割り込みは要る**——人がリアルタイムで待っている同期対話に、
「即座に止まらない」を持ち込まない。ふつうのチャット AI に「止める」が無いのは
おかしい。A-2/A-3 はこれを実現できるかの確認。

### 5.4-a Module 宣言の上書きは「差分」で持つ（決定・2026-09-07）

**既定を写さない。変えたところだけを持つ。**

以前は Project ごとに宣言の一覧を**丸ごと写して**いた。すると既定を改良しても
写しを持つ Project には届かず、「そこだけ動かない」が起きる——実際に起きた

**やり方は VS Code に倣う**（規則12）：既定はプログラムが持ち、設定には
**変えた項目だけ**が入る。合成規則も VS Code と同じ

| 項目 | 規則 |
|---|---|
| `launch.command`（文字列） | 置換 |
| `launch.args`（配列） | 置換 |
| `launch.env`（オブジェクト） | **キー単位でマージ** |

| 既定に無い `name` | まるごと新しい Module として足す |
| `enabled: false` | その Module を**外す**（VS Code に無い、banto が足す） |

- **置き場の鍵は `moduleOverlays`。** 古い `modules`（丸ごとの写し）は
  **読むだけ**——形が同じでも意味が違う（差分の「書いていない」＝既定のまま、
  写しの「載っていない」＝外した）ので、**同じ鍵に混ぜない**
- **host が必ず用意する値は宣言に置かない**（`BANTO_MODULE_DATA_DIR` 等）。
  VS Code のポリシー設定と同じ扱い——誰にも上書きさせず、実行時に渡す
- 画面を作るときは、**変えた項目に印**＋**「既定に戻す」**を出す
  （VS Code の色の帯と歯車と同じ）
