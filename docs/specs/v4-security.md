## 1. セキュリティ境界

**core で詰める**と決まっている——Module ごとに境界を決めない理由は次節のとおり。
以下は 2026-08-29 時点で出発点として置いた事実（§2）から始まり、Landlock を
実際に検証して固めた決定（§3〜§9）までをまとめる。

### なぜ Module ごとではなく core なのか

アーキ仕様 §2.5 は「Project ごとの違い（作業対象のパス等）は**その呼び出しに何を渡すか**で
吸収する」と決めている。**しかし引数で根を渡すことは、強制ではない。**

- **渡した根を Module が守る保証はどこにも無い。** Module は「完全に独立したコード」
  （アーキ仕様 §1）であり、第三者が書いたものでありうる
- **「渡した」は依頼であって境界ではない**
- Module ごとに境界を決めると、**Module の数だけ食い違いが生まれる**

### 出発点となる事実

**① 既定値に落ちた瞬間に破れる**（アーキ仕様 §9 の知見）——作業範囲の根が cwd に落ち、
**試験を走らせただけで本物のリモートに `git push` が到達した**。境界の設計は
「既定値を持たない」から始める。

**② FileSystem と Shell は、強制できる層が違う**（`docs/specs/v4-modules.md` §3）：

- **FileSystem** は自分が開くファイルを自分で決められるので、**アプリ層で強制できる**
  ——ただし正しくやるのは難しい（`..`・シンボリックリンク・ハードリンク・
  検査と使用の間の競合）。**既知の脆弱性の型なので、既知の答えを使う**（規則12）
- **Shell は任意のプロセスを起こせるので、アプリ層では強制できない。**
  起こされたプロセスは banto の検査を通らない。**OS の閉じ込めか、隔離された
  実行環境が要る**

**この2つを同じ扱いにすると、片方だけ守られた状態になる。**

**③ 画面にも境界がある**（`docs/specs/v4-frontend.md` の Canvas の節）——Module の Canvas は二重 iframe で隔離する。
`allow-same-origin` を含めた瞬間にサンドボックスは破れる。**プロセスで信用して
いないものを、画面で信用しない。**

### Shell の閉じ込めは Landlock で行う（決定・2026-08-29、Linux）

アプリ層で shell のコマンド文字列を検査する形は採らない——**起こされたプロセスは
banto の検査を通らない**ので、原理的に守れない。**OS の機構に任せる。**

**Landlock を採る。** 決め手は3つ（2026-08-29 に kernel の仕様を確認）：

1. **非特権で使える。** `no_new_privs` を立てれば root は要らない。
   **banto は人が自分の機械で動かすもの**なので、AppArmor / SELinux のように
   **プロファイルの読み込みに root が要る**機構は、入れる手間が重すぎる
2. **子プロセスに継承され、`execve()` をまたいで残り、外せない。**
   「一度 landlock されたスレッドは、制限を**追加**できるだけで**解除できない**」
   ——**shell が何を起こしても効き続ける**。shell に必要な性質そのもの
3. **ファイルシステムの読み書きを Project の根に閉じられる**（ABI 1 から）

### 実際に掛けて確かめた（2026-08-30）

**設計どおり動く。** 非特権のまま、あるディレクトリだけを許して閉じ込めた：

| 試したこと | 結果 |
|---|---|
| 許可した範囲の読み書き | **できる** |
| 許可外のディレクトリ | **拒否** |
| **`~/.claude/.credentials.json`** | **拒否**——**資格情報を守れる**（アーキ仕様 §2.8） |
| `/bin/ls` の実行 | **できる**（実行に必要なものを許可すれば） |
| `execve` した子プロセス | **制限が効いたまま**（継承を確認） |

**実務上の落とし穴が2つ見つかった：**

1. **「Project の根だけ許す」では shell が動かない。** Landlock は**実行**も
   権限として扱うので、`/usr`・`/lib`・`/bin` 等を**読み取り＋実行**で許さないと
   **`/bin/ls` すら起動できない**（最初の試行はこれで失敗した）。
   **許可リストは Project の根だけでは済まない。**
2. **ルールはディレクトリ単位。** 個別のファイルを足そうとしたら
   `EINVAL` で拒否された。**`/etc` を許すと `/etc/passwd` も読める**
   ——**粒度をどこに置くかは設計事項**（アーキ仕様 §10）。

### 許可リストの組み方——粒度を決めた（決定・2026-09-02、`poc/07-landlock-allowlist-from-path/`）

**固定リスト（`/usr`・`/lib`・`/lib64`・`/bin` 等）は環境によって壊れる。**
このマシンでは `/usr/local/bin` が `/usr` の部分木なので固定リストでも
node/npm/git は動いたが、**PATH がホームディレクトリ配下・`/opt`・`/snap`
（nvm・asdf・Homebrew・snap 等）を指す環境では実行ファイルにたどり着けず、
固定リストは壊れる**（実測で再現済み）。

**採る方式**：許可リストを起動時の `PATH` から動的に組む。

- `PATH` の各ディレクトリを `EXECUTE | READ_FILE | READ_DIR` で許可する
- **`PATH` のディレクトリだけでは足りない**——`npm` のように symlink の
  実体が別ディレクトリ（`node_modules/npm/bin/npm-cli.js` 等）にあるコマンドは、
  依存するパッケージ木ごと読む。**`.../bin` の兄弟ディレクトリ
  （`lib`/`lib64`/`libexec`/`share`）も合わせて許可する**——実測した中で
  「全部動く」を満たす最も狭い形だった（親ディレクトリ全体を許す形は固定
  リストと同じ広さに戻ってしまう）
- **動的リンカが使うパス**（`ld.so.conf` 由来）も読み取りで追加する
- **`/dev` は書き込みも要る**——`git` が `/dev/null` を `O_RDWR` で開くため、
  読み取りだけの許可では `git` が動かない（実測で発見）
- `/etc` は読み取りで許可し、Project の根だけ読み書きで許可する
- **`/proc` は許可しない**（決定・2026-09-10、実測）——下記

**`/proc` を許可リストから外す**（決定・2026-09-10、`relay-proc-allowlist`）：

**理由**——許すと、AI の書いたコマンドが**親（Module）の `/proc/<pid>/environ` を
読める**。`BANTO_HOST_MCP_TOKEN` は「どの Module からの呼び出しか」の識別そのもの
なので、子プロセスに env を渡さないようにしても（下記「子プロセスの env 継承」）
ここから漏れる。**実測**：`/proc` あり＝子から親の environ の秘密が読めた、
なし＝`Permission denied`。

**代償も測った**（同日、Landlock 下の実コマンドで）：

| | `/proc` あり | `/proc` なし |
|---|---|---|
| `nproc`／Node の `availableParallelism()`／`totalmem()` | 動く | **動く**（sysconf 経由） |
| `npm`・`git`・`python3`・`curl`・ファイル操作 | 動く | **動く** |
| `df` | 動く | 値は出る（警告つき） |
| `ps`・`free`・`uptime` | 動く | **使えない** |
| Node の**古い** `os.cpus()` | 4 | **0 を返す**（`availableParallelism()` は正しい） |

使えなくなるのは「自分の機械の様子を見る道具」。**他プロセスの一覧は banto の
境界の外側**の話なので、見せないほうが設計と揃う——`ps` が要る用途が出てきたら、
そのときに Environment（`docs/specs/v4-modules.md` §4）側で考える。

**残るトレードオフ（機構では消せない）**：許可した `.../bin` の**中**に
機微なファイルを置かれると読めてしまう（`.../lib` を足すとその中も同様）。
Landlock ABI 4 にファイル単位の除外は無いため、**「PATH に含めるディレクトリに
資格情報を置かない」という運用上の前提に依存する**——特に `~/.local/bin`・
`~/bin`・`node_modules/.bin` のような、人が自由にファイルを置けるディレクトリが
危ない。機構的な保証ではなく運用上の前提であることを、ドキュメントに明記する
（実装時の TODO）。

**書き出す前に、機械的な検査を必ず通す**（決定・2026-09-02、配線・2026-09-10、
**対象を改訂・2026-09-11**）：ルールセットは書き出す直前に `assertRulesetIsSafe` を
通し、**banto のデータ置き場・設定の置き場の祖先を許可するもの／資格情報ファイルを
含むディレクトリを許可するもの／`/`・home を許可するもの**を拒否する。
**拒否＝その Module は起動しない**（弱いまま閉じ込めたことにしない、規則2）。
会話は止めず、理由は受信箱のお知らせに1件出る（アーキ仕様 §5.4-0）。

#### 人が根を選ぶための窓（追加・2026-09-11）

`GET /api/fs/directories` は、**フォルダの名前だけ**を返す（ファイル名も中身も
返さない）。これは **AI の道具ではなく、人が Root を選ぶための窓**——合言葉を
持っている人＝その機械の持ち主にしか見えない。閉じ込め（Landlock）は Module に
掛かるもので、この口とは層が違う。

#### 根は、あとから変えられる（決定・2026-09-11、ユーザー要望）

Project 設定の「一般」から Root を直せる（`docs/specs/v4-frontend.md` §6.17）。
**根は閉じ込めの範囲そのもの**なので、変えたら host は**その Project の Module を
落とす**——古い根のまま動いているものを残さない。次に要るときに、新しい根で立つ。

#### **人が選んだ根は、検査の対象外**（決定・2026-09-11、ユーザー）

**広い根（home 等）を選ぶこと自体は止めない。** 以前は「Project の根に home を
指定すると、閉じ込める Module は起動しない」としていたが、**やめた**
——home を根にして AI にいろいろやらせたい、という使い方を banto が禁じる
理由が無い（ユーザー決定）。

**代わりに、選ぶ前に見せる**（規則2 の別の守り方）：

| どこで | 何を出すか |
|---|---|
| **新しい Project を作るとき**（Base パスを打っている最中） | 「この根では閉じ込めが効きません」＋**そこに何が入るか** |
| **その Project の Module を選ぶ画面** | 同じ警告（閉じ込める Module を使う場所だから） |

- 「広いか」の判断は **host が持つ**（`GET /api/config/root-scope`）——画面が
  home の場所を推測しない（規則3）。判断は**パスの形ではなく中身**で決める：
  その根が **banto の設定・banto の記録・Claude の資格情報を含むか**
- **検査そのものは残る。** 捕まえたいのは「導出が静かに広がった」場合
  （PATH の realpath の親が紛れ込む等、poc/07）——**人が選んだ根だけが免除される**
- **残るリスクを、そのまま書いておく**：home を根にすると、AI のシェルは
  `~/.config/banto/config.json`（banto の合言葉）・`~/.local/share/banto`（全 Project の
  会話と Memory）・`~/.claude/.credentials.json`（Claude の資格情報）を読める。
  **Landlock は「許可」しか書けない**ので、根を許可した時点で中身は分けられない
  ——そこだけ外す仕組み（根の直下を1つずつ許可する）は**作らないと決めた**
  （2026-09-11、ユーザー——「問題になるまでは、全部アクセス可能にしておこう」）。
  必要になったらそこから作る
- **banto のデータ置き場を、Module に読める場所（開発時はモノレポの根）の
  下に置かない。** E2E がここに当たったので、E2E のデータ置き場をリポジトリの
  外へ移した（`banto/e2e/config.ts`）

**残る未決**：
- **起動時にどの `PATH` を確定として使うか。** `PATH` は環境変数なので、
  AI や子プロセスが書き換えた後の値を許可リスト生成に使うと、許可リスト
  自体が汚染されうる——banto が Module 起動前に確定させた値を使うべきで、
  実行時に動的に読み直さない、という実装上の注意点として残す

### Landlock が縛らないもの（把握して設計する）

**「Landlock を入れたから安全」にはならない。** 仕様が明示している範囲外：

| | 扱い |
|---|---|
| **リソース（CPU・メモリ・プロセス数）** | **Landlock は一切関知しない。** fork bomb は止まらない——**cgroup が別に要る。Phase 1 では作らない**（決定・2026-09-02）——Phase 1 の目的は Vault/Shell/FileSystem の契約確定であり、リソース制限は後回しにする。**黙って忘れない**（規則2）ための明示的な未決事項として、`docs/specs/v4-modules.md` §5 に残す |
| **メタデータ操作**（`chmod` `chown` `stat` `utime` `fcntl` `access` 等） | 対象外。根の外のファイルの**存在は確かめられる** |
| **`mount()` / `pivot_root()`** | 対象外（ファイルシステムの構成変更） |
| **既存の fd** | 渡した `stdin`/`stdout`/`stderr` 経由の ioctl |
| **特殊ファイルシステム**（パイプ・ソケット・nsfs） | 明示的に制限できない |

**ネットワークは ABI 版に依存する**——TCP の bind/connect は **ABI 4 以降**、
UDP は **ABI 10 以降**。それ以前のカーネルでは**素通り**する。

> **実測（2026-08-30、kernel 6.8）：ABI は 4**。TCP は縛れるが **UDP は縛れない**。
> LSM も有効（`lockdown,capability,landlock,yama,apparmor`）。
> **どの環境でどこまで守れるかは、動かしてみないと分からない**
> ——だから下の「足りなければ断る」が要る。
**shell からネットワークに出られるかは、既定で許可する**（決定・2026-09-02）。
`npm install`・`git fetch`、および アーキ仕様 §2.5「alias 方式」（秘密情報を使って外部
API を叩く）がそのまま動く必要があるため。**ホスト単位の許可リストは持たない**
——banto は1人で使う前提（`vision.md`）であり、過剰な制限は開発体験を損なう
（要件と同じ判断軸）。ABI 4 以降なら TCP の bind/connect は Landlock で縛れる
ので、**塞ぎたくなったときの技術的な足場（ホスト単位の許可リスト）は後から
足せる**——いまは「全許可」を既定にするだけで、機構自体は用意しておく。

### ABI 版が足りなければ断る（規則2）

**カーネルの版によって守れる範囲が変わる**ので、**黙って弱くならないようにする**：

- **実行時に Landlock の ABI 版を確認する**
- **要求する版に満たなければ、shell を走らせずに断る**——「守れていないが動く」
  という状態を作らない（規則2：黙って別の経路へ落ちない）

これは アーキ仕様 §9 の「既定値は忘れられる」と同じ形の危険である——**古い環境で静かに
弱くなる**のを、構造で防ぐ。

### 他の機構との関係

- **seccomp** は必須にしない。システムコールを絞るのは開発用の shell では
  壊す側に働きやすい。要ると分かってから足す
- **コンテナ**は `Environment`（`docs/specs/v4-modules.md` §4）の側の道具。
  **Shell とは用途が違う**（同 §2.1）
- **Linux 限定である。** 他の OS で動かすなら別の機構が要る——そのとき
  「同じ境界」をどう保つかは未検討（下記）

**Shell は自分で閉じ込める。** `Environment` の中でだけ走らせる形は採らない
——**Shell と Environment は用途も契約の形も違う別 Module** だから
（`docs/specs/v4-modules.md` §2.1：Shell は1回で終わり状態を持たない、
Environment は状態を持ち識別子で参照する）。

**閉じ込めの機構は共有ライブラリにする。** Shell も Environment も同じものを使えば、
Module を分けても実装は重複しない（アーキ仕様 §1——共有ライブラリは第3の箱ではなく npm 依存）。

> **未確認**（規則1）：Landlock・seccomp・AppArmor はいずれも **Linux 限定**。
> コンテナは可搬。banto を他の OS でも動かすなら、**閉じ込めの機構が OS ごとに
> 変わる**——その場合に「同じ境界」をどう保つかは未検討。

**FileSystem 側と境界を一致させる。** shell をコンテナに閉じ込めても、
FileSystem Module がアプリ層で別の根を見ていたら、**片方だけ守られた状態**に
戻る（`docs/specs/v4-modules.md` §3）。**根は1箇所で決め、両方に同じものを効かせる。**

### FileSystem も同じ Landlock で閉じ込める（決定・2026-09-02）

**FileSystem 側の強制方法は、Shell と同じ Landlock に決めた。** アプリ層で
パス検査を正しくやる（`..`・シンボリックリンク・ハードリンク・検査と使用の間の
競合を全部塞ぐ）という道は採らない——Node の `fs` には `openat2`
（`RESOLVE_BENEATH`/`RESOLVE_NO_SYMLINKS`）のような、この種の脆弱性の型を
まとめて塞ぐ口が無く、アプリ層で正しくやるのは規則12の「既知の答え」に
当てはまらない（Node 向けの既知の答えが無い）。

**Landlock は「execve をまたぐ子プロセスの制限」だけでなく、「呼び出した
プロセス自身のファイル操作の制限」としてもそのまま使える**——`restrict_self`
（`landlock_restrict_self()`）は、それを呼んだプロセス自身に即座に効く
（`poc/00-prior-2026-08-30/landlock.py` の「閉じ込め後（親）」の実測がまさに
これで、execve を挟まず同一プロセス内で読み書きが拒否されることを確認済み）。
FileSystem Module のプロセス自身が `fs.readFile`/`fs.writeFile` を呼ぶだけなので、
Shell のように子プロセスへ execve する必要すら無く、**Shell より単純なケース**。

**帰結**：
- **FileSystem Module の `isolation` は `subprocess` にする。** 現在モックが
  `banto.fs` を `in-process` としているのは訂正が要る（`in-process` では
  banto 本体のプロセスに Landlock を掛けることになり、Event Store 等
  banto 自身のファイルアクセスまで一緒に縛られてしまうため、構造的に
  Landlock を適用できない）
- **根は1箇所で決め、Shell と FileSystem の両方に同じ Landlock ルールセットを
  効かせる。** 「片方だけ守られた状態」（`docs/specs/v4-modules.md` §3）が
  構造的に起きなくなる
- **新しい PoC は不要。** 上記の実測が既にこのケースをカバーしている

### Project の根は Module 起動時に確定させる——Shell/FileSystem は Project 単位でプロセスを分ける（決定・2026-09-03）

**Landlock は不可逆で、後から許可を広げられない。** `landlock_restrict_self()`
は呼ぶたびに制限を**足す**方向にしか効かない（`poc/00-prior-2026-08-30/`で
確認済み）——一度あるディレクトリに縛ったプロセスに、後から別のディレクトリの
許可を追加することはできない。**したがって Project の根は、Shell/FileSystem
Module プロセスの起動時（Landlock を掛ける前）に確定していなければならない。**

これはアーキ仕様 §2.5「Project ごとの違いは、どの Module を使うかではなく、
その呼び出しに何を渡すかという引数の差で吸収する」という一般原則と
**正面から衝突する**——tool 呼び出しごとに違う Project の根を渡す形は、
Landlock を掛けた後のプロセスでは実現できない。

**採る形（この2つの Module に限った、一般原則への例外）**：

- **Shell・FileSystem は、Project 単位でプロセスを分ける。** host は、
  ある Project で初めて Shell/FileSystem が要る Thread が動いたときに、
  **その Project の根を渡してプロセスを spawn する**（`mcpServers` の
  stdio 起動設定——`args`/`env`——に Project の根を積む。具体的なキー名は
  実装時に決める）。Module は起動直後、渡された根に対して Landlock を掛ける
- **同じ Project の複数 Thread は、同じプロセスを共有してよい**（根が同じ
  なので問題にならない）。**別の Project とはプロセスを共有しない**
- **プロセスの寿命は Project に紐づく**（Project が畳まれる／終了するまで、
  または一定時間使われなければ回収してよい）——**Thread・会話には紐づかない**、
  という従来の指針（アーキ仕様 §10 item 9「ライフサイクル」：
  「Module プロセスの寿命を Project に紐づけない」）と矛盾するように見えるが、
  **元の指針が言っていたのは「個々の会話・Thread単位で作り直さない」ことで、
  Project 単位で分けることまでは禁じていない**——2段の粒度として整理し直す
- **他の Module（Vault 等）はこの制約を持たない。** Landlock を掛けない
  Module は、これまでどおり banto 全体で共有される単一プロセスでよい。
  **この例外は Shell・FileSystem に限る**——両方とも Landlock で閉じ込める
  と決めた Module だから

### host の中継・可視性の層も、同じ境界である——中継が縛らないもの（2026-09-10）

この文書はここまで Shell/FileSystem の OS 閉じ込めを扱ってきたが、**アーキ仕様 §2.5 の
host 層（代理サーバ・Module 間中継・bearer token・可視性・画面からの tool 呼び出し）は、
banto が自作した機構であり、MCP にも Landlock にも守られない独自の境界面**である。
「機能はすべて MCP の向こう」と決めた帰結として MCP に無いものを自作した場所なので、
穴もここに集まる（実例：`docs/notes/2026-09-09-repo-review.md`）。

上の「Landlock が縛らないもの」と同じ形で、**MCP のインターフェースに乗らない経路**を
列挙しておく（把握して設計する）：

| 経路 | 何が境界を越えるか | 状態 |
|---|---|---|
| **子プロセスの env 継承** | Module に渡した `BANTO_HOST_MCP_TOKEN` が、Module の spawn する子（＝AI の書いたコマンド）へそのまま継承される。トークンは「どの Module からの呼び出しか」の識別そのものなので、漏れれば AI がその Module の身元で中継を呼べる | **決定（2026-09-10）：Module は子プロセスに `BANTO_*` を渡してはならない。** §2.5 の「プロセスごとに発行」の意図（プロセス＝身元）から、子はその身元ではない。**実装済み（2026-09-10、Shell の `runCommand`）**——`docs/specs/v4-modules.md` §2.3「子プロセスの環境変数」。残る漏れ口は下段の `/proc` |
| **`/proc`** | Landlock 許可リストが `/proc` の読み取りを許すと、AI のコマンドが**親（Module）の `environ`** からトークンを読める | **決定・実装済み（2026-09-10）：許可しない。** 実測で「あり＝読める／なし＝拒否」を確認。代償（`ps`・`free`・`uptime`・`os.cpus()`）は上記の表 |
| **画面 API（`ui-tool-call`）** | authToken だけで `module` 可視の tool（`resolveAlias` 等）も呼べ、秘密の値がブラウザに返る。可視性の強制が frontend 頼み | **実装済み（2026-09-10）**——host が API 境界で可視性を検査する。`agent`・`admin` のみ許可、`module` 可視性は拒否。**その Module が名乗っていない tool 名も拒否**（fail closed）。3つの口（Thread／Project／instance）すべてで同じ検査を通す。「自分の Module か」の照合を host に持たせる形（Canvas ごとのトークン）は将来の強化 |
| **Project をまたぐ秘密の参照** | ある Project の会話から、別の Project に紐付いた秘密を引けてしまう。**以前は引けた**——`scope` はただの札で、`resolveAlias` は呼び出し元を見ていなかった（画面は制約を示しているのに実装は制約していない、規則13） | **決定・実装済み（2026-09-13）**——**使える範囲は置き場（グループ）が決める。** その Project に紐付いたグループ＋共通グループだけ。判定の根拠は **host が刻んだ呼び出し元**（`_meta["dev.banto/caller"]`）で、**Module の自己申告ではない**。**刻印が無ければ値を渡さない**（fail closed）。使えない alias は**名前も見せない**——`vault://aliases` と `lookupAlias` の両方で絞り、**横断する窓口も絞る**。**backend の `listAliases` も刻印で絞る**（訂正・2026-09-15、レビューで発覚——ここは以前「人の管理面なので全部返す」としていたが、この口は `valueFree` なので**初回承認すら出ず**、`dependsOn: [{role:"vault"}]` を宣言した任意の Module が承認ゼロで全 Project の目録を読めていた。窓口で絞っても、窓口以外の呼び出し元には効かない——**判定は材料が在る場所で行う**）。**刻印が無ければ空ではなく断る**（「無い」と「決められない」を混ぜない） |
| **値を返さない中継** | 窓口が金庫を横断して**一覧を組む**ような、値が1バイトも通らない呼び出し。**毎回聞くと、AI が目録を読むたびに人が止められる**（しかも resource の読み取りは進捗を送れず60秒で切れる） | **決定・実装済み（2026-09-12）**——**`_meta["dev.banto/valueFree"]: true` を名乗った tool だけ、初回の承認を聞かない。** 根拠は `relayListTargets` と同じ（返るのは名前だけ）。**無指定は「値を返す」扱い**（fail closed——名乗らないだけですり抜けられては逆になる）。緩むのは **tool 単位**で、同じ Module の `resolveAlias` は今までどおり毎回聞く。監査には `reason: "値を返さない口"` として残る |
| **画面を出所とする中継** | 人が Module の画面で押した操作が、その Module の依存先を呼ぶ（vault-directory → Vault）。**全部聞くと管理画面が開いた瞬間から止まり、全部通すと悪意ある Module が自分の画面から他 Module の秘密を持ち出せる** | **決定・実装済み（2026-09-12）**——**宛先が `admin` 可視性のときだけ聞かない。** `module` 可視性（値を返す部品間専用の口）は出所が画面でも聞く。出所は台帳で引き（推測しない）、**1つでも AI のターン由来が混ざればターン扱い**（緩いほうへ倒さない）。聞かなくても監査には `reason: "人が画面で行った管理操作"` として残る。`docs/specs/v4-frontend.md`「Module 間中継の承認」 |
| **初回承認ゲート・監査** | 設計は決定済み（アーキ仕様 §2.5：初回のみ承認・メタデータを Event Store に記録） | **実装済み（2026-09-10）**——初回は会話と受信箱に判断待ちが出て、許可すると `relay.grant_created`、呼び出しは成否込みで `relay.call_recorded` に残る。`bypassPermissions` でも出る。**残っているのは待っている間の進捗送出だけ**（`docs/specs/v4-frontend.md`「Module 間中継の承認」の注） |
| **`admin` 可視性の tool を Module から呼ぶ** | `admin` は「AI に見せない」と「人の画面からならゲートを飛ばす」の2つしか意味しておらず、**host の中継は可視性で拒否していない**。つまり Module は承認1回で `setGroupBinding` を呼べ、**`resolveAlias` の制限判定そのものを書き換えられた**——制限を守る側が、制限を書き換えられる形になっていた | **決定・実装済み（2026-09-15）**——**台帳と紐付けを変える口は、人の刻印（`{admin: true}`）があるときだけ通す**（`createAlias` / `generateSecret` は Project からも通す——秘密を預ける行為は制限を広げないため）。可視性は「見せるかどうか」の話で、「呼べるかどうか」は**呼ばれた側が刻印で判断する** |
| **`valueFree` の申告方向** | `valueFree` は**戻り値**が無いことの宣言だが、呼び出しには**引数**があり、引数は宛先へ流れる。悪意ある Module が `valueFree` を名乗る tool を1本持てば、**そこへの呼び出しは承認なしで通り、承認済みの `resolveAlias` で得た値を積んで持ち出す出口になる**。「無指定は値を返す扱い」は呼び出し側の fail closed だが、**宛先の申告を信じる方向は fail open** | **決定・実装済み（2026-09-15）**——**`valueFree` を信じるのは同梱 Module だけ**。第三者の申告は読むが、承認は今までどおり聞く。外から Module を入れられるようにする前に決める、としていた行の決着 |
| **外から繋いだ Module が閉じ込め無しで走る** | 閉じ込めは `scope:"project"` でしか宣言できない（根が Project の根）ので、**`scope:"instance"` の第三者 Module は構造上まったく閉じ込められない**——`~/.claude/.credentials.json`・中継の合言葉・全 Project の会話を素で読める。しかも**「`${projectRoot}` を書かない」という一番楽な道**がそこへ落ちる | **決定・実装済み（2026-09-15）**——**`origin !== "bundled"` かつ閉じ込め無しなら起動を断る**（受信箱に理由が1件）。帰結として**いまは外から繋いだ instance の Module を立てられない**——閉じ込めを instance へ広げるまでは、外から繋げるのは Project ごとの Module だけ。**楽な道が危ない結果に落ちてはいけない** |
| **役割のなりすまし** | `satisfies` は自己申告で、spawn の形を左右する4項目のような厳格さが掛かっていない。第三者が `vault-directory` を名乗れれば**AI と Shell が話す窓口になりうる**（alias 名を全部観測し、値を取りに行く先を自分の実装へ向けられる）。`shell` を名乗れば閉じ込めの緩い profile を得られた | **決定・実装済み（2026-09-15）**——**骨格の役割（`shell`・`filesystem`・`vault`・`vault-directory`）は同梱だけが名乗れる**。閉じ込めの広さ（`profile`）は `satisfies` から推さず**宣言が持つ**。束ね役は **instance 全体で1本**（`SINGLETON_ROLES`）——2本目は読み込みで止める |
| **承認を名前で引くこと** | 中継の許可は `projectId␠呼び出し元␠宛先␠種別␠tool 名` で引く。**登録を消して、後日別のサーバを同じ名前で繋ぐと、前の承認がそのまま効く**——改名は安全側（聞き直し）に倒れるのに、削除→再利用は危険側に倒れていた | **決定・実装済み（2026-09-15）**——**外から繋いだ宛先は、起動するコードの印（`codeId`）にも縛る**。同梱は対象外（コードが既定と一致していることが `bundled` の条件なので入れ替わらない）＝既存の承認はそのまま生きる |
| **Module が machine の外へデータを出す** | 表の他の行はすべて**subprocess が前提**で、「Module が外へ出す」経路の行が無かった。リモート MCP（`url`+`headers`）を受け入れると、AI がそのツールを呼ぶたび**引数（会話由来の内容を含む）が相手の URL へ出ていく**。閉じ込めは効かない。戻り値で AI を誘導して別 Module からさらに持ち出させることもできる。`headers` に秘密を入れれば**秘密が毎回外へ送られる** | **未決（2026-09-15 記録）**——リモート MCP は**まだ実装しない**。入れるときの最低線として検討中：リモートは敏感な役割を満たせない／繋ぐときに「これは machine 外へデータを送ります」を人が明示承認／リモートの tool を `agent` 可視の既定に自動で載せない |
| **Elicitation の宛先** | 共有接続のハンドラ上書きにより、並行ターン中は別ターンへ質問が届きうる | 実装待ち（`docs/tasks.json`） |
| **トークン・セッション・プロセスの回収** | revoke・回収の経路が無く増える一方。寿命の設計は決定済み（本書「Project の根は Module 起動時に確定させる」・アーキ仕様 §10 item 9） | 実装待ち（`docs/tasks.json`） |

Canvas の sandbox（`docs/specs/v4-frontend.md` §6.2）はこの表に**入れない**——
CSP の fail closed を確認済み（2026-09-09 レビュー）で、既に守られている外周。

### 詰めるときの論点

- ~~FileSystem 側の強制方法~~ → **決定（2026-09-02、上記）**
- Project の根を誰が決め、誰が保持するか
- 第三者の Module に `in-process` を開くか（アーキ仕様 §10）
- 鍵をどこに置くか（Vault、`docs/specs/v4-modules.md` §2）
- ~~Module 間直接呼び出しの許可トークンを発行・検証するか~~ → **解消**（2026-09-02）
  ——アーキ仕様 §2.5「Module 間の呼び出し」を host 中継方式に変更したことで、Module 同士が
  直結すること自体が無くなり、なりすまし対策の必要も消えた。中継方式が将来
  性能上の理由で直結に戻ることがあれば、この論点も一緒に復活する
- 外部 Skill が持ち込む `scripts/`（アーキ仕様 §5.7）
- **TLS を割る代理を入れるか**（`docs/specs/v4-modules.md` §4.1）——入れると
  **通る資格情報を全部平文で読める**。banto は Vault と複数のサブスク資格情報を
  持つ（アーキ仕様 §2.8）ので、**banto 自身の通信を通さない分離**が要る。
  なお**ブラウザの通信を見るだけなら代理は要らない**（CDP が復号済みで返す）
