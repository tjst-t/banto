## 1. セキュリティ境界

**core で詰める**と決まっている——Module ごとに境界を決めない理由は次節のとおり。
以下は出発点として置いた事実から始まり、閉じ込めの決定（**Project ごとのシステムコンテナ**、
2026-09-25）、コンテナの中の細部（§2）、host の中継・可視性の層（§3）をまとめる。

### なぜ Module ごとではなく core なのか

アーキ仕様 §2.5 は「Project ごとの違い（作業対象のパス等）は**その呼び出しに何を渡すか**で
吸収する」と決めている。**しかし引数で根を渡すことは、強制ではない。**

- **渡した根を Module が守る保証はどこにも無い。** Module は「完全に独立したコード」
  （アーキ仕様 §1）であり、第三者が書いたものでありうる
- **「渡した」は依頼であって境界ではない**
- Module ごとに境界を決めると、**Module の数だけ食い違いが生まれる**

### 出発点となる事実

**① 既定値に落ちた瞬間に破れる**（アーキ仕様 §9 の知見）——作業範囲の根が cwd に落ち、
**試験を走らせただけで本物のリモートに `git push` が到達した**。境界の設計は
「既定値を持たない」から始める。

**② FileSystem と Shell は、強制できる層が違う**（`docs/specs/v4-modules.md` §3）：

- **FileSystem** は自分が開くファイルを自分で決められるので、**アプリ層で強制できる**
  ——ただし正しくやるのは難しい（`..`・シンボリックリンク・ハードリンク・
  検査と使用の間の競合）。**既知の脆弱性の型なので、既知の答えを使う**（規則12）
- **Shell は任意のプロセスを起こせるので、アプリ層では強制できない。**
  起こされたプロセスは banto の検査を通らない。**OS の閉じ込めか、隔離された
  実行環境が要る**

**この2つを同じ扱いにすると、片方だけ守られた状態になる。**

**③ 画面にも境界がある**（`docs/specs/v4-frontend.md` の Canvas の節）——Module の Canvas は二重 iframe で隔離する。
`allow-same-origin` を含めた瞬間にサンドボックスは破れる。**プロセスで信用して
いないものを、画面で信用しない。**

### 閉じ込めは Project ごとのシステムコンテナで行う（決定・2026-09-25、ユーザー）

**仕切りは2つだけにする**：

| 箱 | 中身 | 決め方 |
|---|---|---|
| **banto 本体（ホスト）** | core・会話の本体（Runner）・Claude のログイン・Vault・設定・banto 全体の同梱 Module | **AI に渡してはいけないものだけ** |
| **Project のコンテナ** | Project のファイル・Project の Module（Shell・FileSystem・Subagent・外から足したもの）・AI のコマンド・サブエージェント・入れた道具 | **それ以外の Project のもの全部** |
| **banto 全体用のコンテナ（1台）** | 外から足した banto 全体の Module（第三者のコード） | **banto 本体で動くのは banto 自身のコードだけ**（決定・2026-09-25、ユーザー） |

**Landlock はやめた**（2026-09-25 に移し終えた）。
理由（実測、`docs/notes/2026-09-25-dev-environment.md`・`poc/09-project-container/`）：

- **root になれないので、道具を足せない**（`apt install` ができない）——「開発ごとに道具を入れる」と合わない
- **許可リストに道具ごとの穴が出続ける**——gcc の下請け（`/usr/libexec`）・ヘッダ（`/usr/include`）に届かず
  `cargo build`・`cc` が止まった。言語ごとに置き場が違う
- **抜け道があった**——Landlock（kernel 6.8・ABI 4）は名前付きの UNIX ソケットへの接続を縛らない。
  閉じ込めの中から docker.sock の API に届き（docker グループ＝root 相当）、`systemd-run --user` で
  閉じ込めの外にコマンドを走らせて `~/.claude` の資格情報を開けた
- 仕組みを1つにできる（Landlock とコンテナの2つを持たない）

**コンテナは「中にマウントしたものしか存在しない」世界を足し算で組む**。中は root で自由に道具を入れられ、
Docker の口・ユーザーの systemd・人のホーム・banto の秘密は、**そもそも中に無い**。

**会話の本体（Runner）は外に置く**：コンテナは AI が root で何でもできる場所なので、**中に置いたものは全部
AI が読めるものとして扱う**。本物の Claude ログインは中に置けない。会話の本体は自分ではコマンドを実行しない
（組み込みの Bash 等は切ってあり、実行は必ず Project の Module を通る——アーキ仕様 §2.5）ので、外で困らない。

**機構：Incus のシステムコンテナ**（Docker ではなく）：

- 中の root が**ホストでは一般ユーザー**（既定で user namespace。Docker は既定でホストの root と同じ）
- 入れた道具が機械と同じく**残る**。systemd がそのまま使える。**中で Docker を動かせる**。同じ操作で VM に上げられる
- **Incus**（LXD ではなく）：普通の apt パッケージ（snap の自動更新・閉じ込めが無い）・多くのディストリビューションの
  イメージが使える・コミュニティ運営で Apache 2.0。**6.0 LTS の 6.0.6 以降**（Zabbly の `lts-6.0`）が要る——
  Ubuntu 24.04 の 6.0.0 では中の Docker が AppArmor に止められる（runc の CVE-2025-52881 の修正との衝突。
  上流 PR #2624 で直った）
- **Linux 限定**（Landlock も Linux 限定だった）

**コンテナの作り方**（PoC 09 で確かめた形）：

- **Project ごとに1台**。host（core）が作り・起こし・止める——**Project の Module を起こす場所**だから
  （Module の起動を持つのは host。アーキ仕様 §2.5・§5.4-0）
- **Project の根を同じ絶対パスでマウント**する——Shell と FileSystem が同じ場所を同じ名前で指す
  （「根は1箇所で決め、両方に同じものを効かせる」が構造で成り立つ）。**マウントは同時に来た分を
  まとめて1回で足す**（REST の PATCH。装置の表に差分として混ざる——実測・2026-09-26）
- **中から host に届くアドレスは、ブリッジ（host 自身のインターフェース）から読む**（決定・2026-09-26）
  ——中の既定の経路を待つと、起こした直後は DHCP が済むまで約 0.4 秒待たされる。ブリッジが host に
  見えない形のネットワークのときだけ、中の経路を待つ
- **ファイルの持ち主を揃える**：中の uid 1000 ＝ホストの uid 1000（`raw.idmap`）。中の root はホストでは一般ユーザー
- **権限を絞った使い方**：banto を動かすユーザーは `incus` グループ（`incus-admin` ではない）——**banto 自身が
  root 相当にならない**。Incus の `incus-user` がユーザーごとの制限つきの区画を作る（見せられるホストのフォルダは
  ホームの下だけ・proxy デバイス禁止・`raw.lxc` 等の低い層は禁止）
- **入れ子（中で Docker）は、要る Project だけに許す**——許したコンテナでは Incus が `/proc`・`/sys` の保護規則を外す
  （入れ子を許せばコンテナは自分で `/proc`・`/sys` を付け直せるので、その保護はもともと効かない、という上流の判断）。
  許していないコンテナには残る（実測）。**Project の設定「中で Docker を使う」**（既定は切。設定のキーは
  `container.nesting`、Project ごと）。切り替えるとその Project の Module を落とし、次に使うときにコンテナへ効かせる
  （コンテナを起こし直す）
- **止めるのを待ちすぎない**：上限を決めて、超えたら強制停止する（`incus restart` が5分以上返らなかったことが1回あった）
- **資源の上限を付ける**（決定・2026-10-02、ユーザー。2026-09-30 に Project のコンテナの中のフル E2E が入れ子のコンテナを
  約50台立て、host の負荷 320・incusd が詰まり Module が全部止まった再発防止）。入れ子のコンテナも親の枠に入るので、
  暴走はその Project の中で止まる。**既定値は固定の数値にせず、コンテナを用意するときにその host の資源から計算する**
  （いろんな host に入れるため。`defaultContainerLimits`）：メモリ＝host の全メモリから 2GiB を host に残した残り
  （最低 1GiB）、CPU＝コア数から1を引いた分を時間で切る上限（`limits.cpu.allowance`、最低1コア）、プロセス数＝8192。
  banto 全体用のコンテナも同じ。動いているコンテナにもそのまま効く（起こし直さない）。Subagent とその子（Claude Code 等）は
  Project のコンテナの中で動くので、その Project の枠に入る。
  **上書き**（2026-10-02）：banto 全体の設定「コンテナ」で、host に残すメモリ・残す CPU・1台あたりのプロセス数を変えられる
  （鍵 `container.limits.hostReserveMemoryMiB`・`hostReserveCpus`・`processes`、instance 既定）。Project の設定の
  「コンテナ」で、その Project のメモリ・CPU・プロセス数を**banto 全体の上限より下げることだけ**できる（鍵
  `container.limits.project.*`、Project 上書き。上げた値は上限で止まる——上げられると host を守る上限が外れる）。
  保存すると動いているコンテナにも起こし直さずに効く。
  **全 Project の合計の上限は Incus では掛けない**（2026-10-02 に実測）：Incus の区画の `limits.memory` は各コンテナに
  **書いた上限の合計**を数えるだけで、使っている量ではない——1台の上限が host のほぼ全部なので、区画に合計を付けると
  2台目が作れない。しかも区画の設定は権限を絞った banto からは変えられない（`Certificate is restricted`）。
  コンテナの cgroup は Incus がルートの直下（`/lxc.payload.<区画>_<名前>`）に作るので、systemd の枠にも入れられない。
  代わりに **host の側を守る**：`system.slice` の CPUWeight を上げると、コンテナが CPU を取り合っても host のサービスが
  先に回る（入れ子の環境で、競合時の取り分が約47%→約81%になるのを実測）。手順は `docs/runbooks/host-resource-protection.md`
  （host で人が一度行う）
- **置き場は banto 専用の btrfs（`banto`）**（決定・2026-09-25、実測）：写しを共有するので2台目からは 0.2 秒で作れ、
  3台とイメージで 627MB（`dir` は毎回 3.4 秒・1台 602MB 丸写し。E2E は Project ごとに1台作る）

**外から足した banto 全体の Module は、banto 全体用のコンテナ（1台）で動かす**（決定・2026-09-25、ユーザー）。
Project の根は見せない。どの Module がどこで動くかの一覧は §2。

**中に入れないもの**：Docker の口・ユーザーの systemd の口・人のホーム・`~/.claude`・banto の設定と記録・Vault の中身。
**外から入るもの**：Project の根・banto の Module のコード（読み取り専用）・人が選んだ設定の写し（`.gitconfig` 等、下の
「専用のホーム」と同じ）・人が承認した秘密（`envSecrets` 等で、その回のコマンドに）。

**中から来たものは「その Project の AI」と同じに扱う**（帰結）：

- 中では AI が root なので、同じコンテナの Module の中継の合言葉も AI が読める——**Module の名乗りで信用を
  分けられない**。中継の承認はいま「Project・呼び出し元・宛先・種別・名前」の単位（alias は入らない）で、
  なりすましで**一度許した道具からどの鍵でも引き出せる**。→ **コンテナから値を返す口を呼ぶときは、鍵の名前ごとに
  人に聞く**（§3 の表）
- **Claude のログインの中継は host に置く**——本物の資格情報を中に入れない。**core が1本だけ常設し、Project の
  コンテナの環境に住所とその Project 用の合言葉を入れておく**（改訂・2026-09-27、ユーザー。以前は banto 全体の
  `subagent-settings` が1回ごとに開け閉め——**実装はまだその形**。§2「banto 本体の Claude ログインは、中継で
  共有する」）。**待ち受けは Project のネットワークの host 側のアドレス**——127.0.0.1 はコンテナから届かず、
  proxy デバイスは制限つきの区画で使えない（実測）
- **Module が呼ぶ host の中継**（`BANTO_HOST_MCP_URL`）も同じ理由で、Project のネットワークの host 側のアドレスで
  待ち受ける（合言葉は今までどおり）

**ネットワーク**：中から外へは既定で出られる（npm・git・apt。§2「コンテナが縛らないもの」）。**Docker が入っているホストでは、
Docker が転送を既定で止めるので、Incus のブリッジの許可を足す**（Docker の起動のたびに `DOCKER-USER` へ
`incusbr+` の許可を足す systemd の drop-in——このホストには入れてある）。**ホストで 0.0.0.0 に待ち受けているもの
（banto の API など）には中から届く**——LAN から届くのと同じ範囲で、banto の API は合言葉が要る。

**ホストの前提**（入れる手順は本実装で書く）：Incus 6.0.6 以降・banto を動かすユーザーが `incus` グループ
（**`sg incus` ではなくグループを引き直して起動する**——`sg` は主グループを変え、作るファイルのグループが中に対応しない）・
`/etc/subuid`・`/etc/subgid` に `root:<uid>:1`（ホストの uid をコンテナに対応させるため）・btrfs の置き場 `banto`・
Docker が居れば上の drop-in。確かめる口：`node packages/container/dist/doctor.js`。

**まだ決まっていないこと**（アーキ仕様 §10 にも載せる）：

- **ホームの外の Project の根**（制限つきの区画はホームの下しかマウントできない。いまはコンテナを作るところで
  Incus に断られ、その Project の Module が繋がらない——理由は受信箱に出る。E2E は根をホームの下に作る）
- 道具の定義を再現できる形で持つか（`devcontainer.json` 等）、コンテナの状態に任せるか
- 中から host のサービスへ届く範囲を絞るか・資源の上限（Incus の `limits.*`。§2 の「cgroup が別に要る」の答えの候補）
- **Project の実行場所に VM を選べるようにするか**（追加・2026-09-27）——ハイパーバイザー・カーネル・
  host のネットワークに触るアプリは、カーネルを共有するコンテナでは原理的に開発できない。案：Project の設定で
  「コンテナ／VM」を選ぶ（Environment Module の復活ではなく、「どこで動かすか」を担う Project のコンテナを
  広げる）。Incus の VM も `incus exec` と disk デバイスが使えるので、Module の起こし方はほぼそのままの見込み。
  この機械はそれ自体が VM だが AMD の `svm` と `kvm_amd` の `nested=1` が見える（確認済み）。
  **制限つき区画で VM を作れるか・VM の中の `/dev/kvm`・VM へのフォルダの持ち主・コンテナに `/dev/kvm` を
  渡せるかは未測**——`poc/10-project-vm/probe.sh`（host で実行する）
- **AI に host や banto 自身を変えさせたいときの形**（追加・2026-09-27）——守るものは「host で動くものは
  必ず人の確認を通り、その確認画面を AI が偽れない」こと。案は3つの型：① banto 自身の設定は、AI が提案し
  banto が自分の画面で中身を見せて人が押す（`import_skill` と同じ形）。② 決まった host 操作（反映・公開・
  再起動）は、型のある tool を host 側の Module に置き、人が承認する（Publish がこの形——承認は会話の中の画面、2026-09-28）。③ 型にできない
  操作（アプリを入れる等）は AI が用意まで、実行は人——banto の画面に**人だけが使える host の端末**を置き、
  AI の下書きをそこに出す。**作らないもの**：host で任意のコマンドを打てる tool に承認を付ける形（人は
  読み切れず承認が素通りになる）・一時的に AI に host の権限を渡す非常口

## 2. コンテナの中の細部（2026-09-25 に Landlock から移した）

**Landlock の時の決定のうち、コンテナでも効くものをここに残す。** Landlock そのものの話（許可リストの組み方・
`/proc` の扱い・ABI の版・ドメイン）は、コンテナへ移したときに消した——経緯は
`docs/notes/2026-09-25-dev-environment.md`。

### どの Module がどこで動くか（決定・2026-09-25）

| Module | 動く場所 |
|---|---|
| Project の Module（`scope: "project"`——Shell・FileSystem・Subagent・外から足したもの） | **その Project のコンテナ** |
| 外から足した banto 全体の Module | **banto 全体用のコンテナ（1台）** |
| 同梱の banto 全体の Module（Vault・窓口・設定の画面・Skill など） | **banto 本体** |
| URL に繋ぐ形 | こちらにプロセスが無い（§3「Module が machine の外へデータを出す」） |

**置き場所は宣言の `scope` と `origin` から host が導く**（`modulePlacement`）。宣言の `confinement` は置き場所を
決めない——Landlock の時の項目で、いまは読むだけの印（名前の付け直しは `docs/tasks.json`）。**外から足した
起動する形は、宣言に何が書いてあっても必ずコンテナで動く**——閉じ込めを宣言が名乗る形をやめた。

**起こし方**：host が `incus exec` でコンテナの中に Module を起こす（stdio はそのまま繋がる）。中の uid・gid は
ホストで banto を動かしているユーザーと同じ。**host の環境変数は渡さない**——渡すのは Module の置き場（`HOME`）・
host の中継の住所と合言葉・宣言の `env` だけ。

**中に見せるもの**：Project の根（同じ絶対パス）・banto のコード（読み取り専用、同じ絶対パス）・その Module の
置き場・registry から取ってきた配布物（読み取り専用）。**node はホストと同じ版を土台のイメージに入れる**
（土台はホストの node の版・入れる道具の一覧から印を作り、変わったら作り直す）。

**稼働中の banto は、開発用とは別の clone から動かす**（決定・2026-09-27、ユーザー）。置き場は
`~/.local/share/banto-release`、`release` ブランチを動かす。手順は `docs/runbooks/release.md`。

- **理由**：banto のコードの置き場は「稼働中の banto 自身のリポジトリ」（`cli.ts` の `monorepoRoot`）である。
  banto で banto を開発する Project では、**その置き場が Project の根の中に入る**。すると
  ① 読み取り専用のマウントの上に、読み書きできる根のマウントが重なって読み取り専用が効かない
  （実測、2026-09-27。`/proc/self/mountinfo` で、`…/banto/banto` の ro の後に親の rw が乗っていた）。
  ② **閉じ込めの抜け道になる**——Vault など banto 本体で動く Module も同じコードを読むので、中の AI が
  書き換えたコードが、次の再起動で人の確認を経ずに host の権限で動く。③ build しただけで稼働中の
  画面が壊れる（ルートの build が稼働中の画面の `.next` を上書きする）
- **重なりの順番を直すだけでは解けない**——読み取り専用が上に来れば、その Project で banto を編集できなくなる。
  置き場を分ければ重なり自体が無くなり、「反映する」が人の見える操作になる
- **ワークツリーではなく clone**：ワークツリーは開発用の `.git` を共有し、その `.git` は Project の根の中にある
  ——`.git/hooks` や `.git/config` を中の AI が書き換えると、人が host で git を打ったときに動く。
  **clone の取り込み元は GitHub**。開発用のリポジトリをローカルのパスで fetch しない（相手側のリポジトリで
  git が動く）
- **置き場はデータ置き場（`~/.local/share/banto`）の外**——データの退避や消去にコードを巻き込まないため
- **残る穴**（未決）：人が host で**開発用の**リポジトリに git を打つと、その `.git/hooks`・`core.hooksPath`・
  `core.fsmonitor` などが動く。これは今回の切り替えとは別にもとからある。手順書では打つ前に確かめる手順を入れた
- **切り替え後も古い読み取り専用のマウントが残った**（実測、2026-09-27）：新しい置き場は ro で見え書き込みも
  断られたが、コンテナを起こし直さないままだと `…/ghq/…/banto/banto` の ro が mountinfo に残っていた。根の
  マウントに隠れていて外す処理が空振りしたと推測（未確認。`poc/10-project-vm/probe.sh` の 0c で host 側の
  デバイス一覧を見る）。隠れているので実害は無い見込み

**中で `sudo` が使える**（パスワード無し）。中の AI は root になれる前提で設計している（§1「中から来たものは
その Project の AI と同じに扱う」）ので、塞いでも守れるものは増えず、道具を入れる手段だけが減る。

**前提が欠けていれば、コンテナで動く Module を起こさずに断る**（規則2）。host は起動時に前提（§1「ホストの前提」）を
確かめ、足りないものを名指しして直し方を添える。Module を起こすときにも同じ理由で断る——閉じ込め無しに落ちない。

### 根と Project の関係

**Project の根は Module の起動時に確定させる——Shell・FileSystem・Subagent は Project 単位でプロセスを分ける**
（決定・2026-09-03、理由を改訂・2026-09-25）。根はコンテナにマウントするもので、コンテナは Project ごとに1台。
tool 呼び出しごとに違う根を渡す形（アーキ仕様 §2.5 の一般原則）は採れない——**この2つの Module に限った例外**：

- **同じ Project の複数 Thread は、同じプロセスを共有してよい。別の Project とは共有しない**
- **プロセスの寿命は Project に紐づく**（Thread・会話には紐づかない）。**Project を畳むとコンテナも止める**
  （消さない——入れた道具は残る）
- **FileSystem も同じコンテナで動く**——Shell と FileSystem が同じ根を同じ名前で見る。「片方だけ守られた状態」
  （`docs/specs/v4-modules.md` §3）が構造で起きない。FileSystem の `isolation` は `subprocess`

**根は、あとから変えられる**（決定・2026-09-11、ユーザー要望）。Project 設定の「一般」から Root を直せる
（`docs/specs/v4-frontend.md` §6.17）。**根は閉じ込めの範囲そのもの**なので、変えたら host は**その Project の
Module を落とす**。次に要るときに、コンテナの根を付け替えて新しい根で立つ。

**人が根を選ぶための窓**（追加・2026-09-11）：`GET /api/fs/directories` は**フォルダの名前だけ**を返す
（ファイル名も中身も返さない）。AI の道具ではなく、人が Root を選ぶための窓——合言葉を持っている人＝その機械の
持ち主にしか見えない。閉じ込めはコンテナで、この口とは層が違う。

**広い根（home 等）を選ぶこと自体は止めない**（決定・2026-09-11、ユーザー）——home を根にして AI にいろいろ
やらせたい、という使い方を banto が禁じる理由が無い。**代わりに、選ぶ前に見せる**（規則2 の別の守り方）：

| どこで | 何を出すか |
|---|---|
| **新しい Project を作るとき**（Base パスを打っている最中） | 「このフォルダでは、サンドボックスがほぼ機能しません」＋**そこに何が入るか** |
| **その Project の Module を選ぶ画面** | 同じ警告 |

- 「広いか」の判断は **host が持つ**（`GET /api/config/root-scope`）——画面が home の場所を推測しない（規則3）。
  判断は**パスの形ではなく中身**で決める：その根が **banto の設定・banto の記録・Claude の資格情報を含むか**
- **残るリスクを、そのまま書いておく**：home を根にすると、home がまるごとコンテナに見え、AI のシェルは
  `~/.config/banto/config.json`（banto の合言葉）・`~/.local/share/banto`（全 Project の会話と Memory）・
  `~/.claude/.credentials.json`（Claude の資格情報）を読める。**マウントは根ごと**なので中身は分けられない
  ——そこだけ外す仕組みは**作らないと決めた**（2026-09-11、ユーザー——「問題になるまでは、全部アクセス
  可能にしておこう」）
- **banto のデータ置き場を、コンテナに見せる場所の下に置かない**——banto のコード（開発時はモノレポの根）は
  中に見えるので、その下に置き場があると Module が banto 自身の Event Store を読める。E2E のデータ置き場は
  リポジトリの外（`banto/e2e/config.ts`）
- **E2E は claude CLI の置き場（`~/.claude`）にも書かない**（決定・2026-09-16）。Runner が起こす CLI は
  **cwd ごとにプロジェクトを作って会話を記録する**ので、spec が毎回違う作業ディレクトリを作ると**人の
  `~/.claude/projects` が実行のたびに増える**（11日で 4198 件溜まった）。`CLAUDE_CONFIG_DIR` を実行ごとの
  置き場に向ける——**書いてから片づけるのではなく、書かない**。**資格情報だけは
  `CLAUDE_SECURESTORAGE_CONFIG_DIR` で本物（`~/.claude`）を指す**——写しを持たせると、CLI がトークンを更新
  したときに人の側が取り残される（規則3）。経緯は `docs/notes/2026-09-16-e2e-claude-config-isolation.md`

### Shell のコマンドには、専用のホームを渡す（決定・2026-09-23、ユーザー）

**人のホームは見せない**（コンテナにそもそも無い）。**Dev Containers と同じ形にする**（規則12）：

- **Project ごとに書けるホーム**を Shell の Module の置き場の中に用意し、コマンドの `HOME`（と XDG の置き場）に
  する。npm・pip などのキャッシュもここに書ける
- **人が選んだ設定だけを写す**（banto 全体の設定「Shell のホーム」。既定は `~/.gitconfig` と `~/.config/git`）。
  写すのは host（コンテナの外）。Shell が起きるときと、人が一覧を変えたとき（立っている Shell にも写し直す
  ——コマンドは毎回新しく起こすので次のコマンドから効く）
- **資格情報は写さない。** git の設定からは `credential.*`（取り出し役）と `include`（写していないファイルを
  指す）を git 自身で外し、人のホームを指す値は Shell のホームへ向け直す。資格情報の置き場（`.ssh`・`.gnupg`・
  `.config/gh`・`.npmrc`・banto 自身の設定と置き場 など）は一覧に足せない。**資格情報は Vault から渡す**
  （`sshIdentity`・`envSecrets`）
- `shell` は同梱だけが名乗れる役割なので、**第三者の Module に人の git の設定は渡らない**
- **コンテナに無いものを指して失敗したら、そう言う。** 失敗したコマンドの `No such file or directory` が
  Project と Shell のホームの外（人のホームの下）を指していたら、結果に `confinementNote` を添える（人にも AI にも、
  「自分の端末では動くのに」の理由が分かる）

### サブエージェントは Project のコンテナの中で走る（決定・2026-09-24、改訂・2026-09-25）

Subagent Module（アーキ仕様 §4.1）は Project の Module なので、**Module ごと Project のコンテナの中で起き、
エージェント（Claude Code・OpenCode など）も中で走る**。エージェントは自分の tool（シェル・ファイル操作）を持つ
ので、**エージェントのプロセスそのものが「AI の書いたコマンドを走らせるもの」**——Shell と同じ扱いになる。

- エージェントに渡す環境変数は一覧で絞る（`PATH`・`LANG` など）。host が Module に渡した `BANTO_*`
  （中継の合言葉を含む）も、人の環境の秘密も、エージェントには渡さない。ただし中では AI が root なので、
  **同じコンテナの Module の env は読めるものとして扱う**（§1 の帰結。守りは中継の側——§3）
- 人の `~/.claude`・`~/.config` は中に無い。エージェントには専用のホームを渡す（Shell と同じ形）

**渡した資格情報は、そのサブエージェントのシェルから読める**（実測、`poc/08-subagent-acp/`）。Claude Code の
Bash は env からトークンを消しているが、エージェント本体の `/proc/<pid>/environ` から読める。OpenCode はシェルの
env にもそのまま渡す。**→ サブエージェントに渡すのは、サブエージェントに読まれてよいものだけ。** 資格情報は
ファイルに写さず env で渡す（アーキ仕様 §4.1）。

**banto 本体の Claude ログインは、中継で共有する——トークンは渡さない**（決定・2026-09-24、ユーザー）。
access token は会話の履歴・claude.ai のコネクタ（人の Gmail・Drive など）・ファイルの送り込みまで触れる権限を
持ち、寿命は約8時間、しかも**同じ置き場に refresh token がある**（回るぶん access token より危ない）。
**資格情報を足す中継**（サンドボックスの外で認証を差し込む、既知の形——規則12）にする：

- **中継は core が1本だけ常設する**（改訂・2026-09-27、ユーザー。検討は
  `docs/notes/2026-09-27-claude-login-relay-alternatives.md` の案A）。core の HTTP サーバの1つの口
  （コンテナからすでに届いている host 中継 `/relay` の隣）。新しいポートも Module のプロセスも増やさない。
  **持ち主が core なのは**、中継の寿命がコンテナと同じで、コンテナを起こし止めるのが core だから。中継は AI の
  tool ではなく境界の機構で、host 中継 `/relay` と同じ層（「機能は MCP の向こう」の原則の対象外）
  - ~~中継は banto 全体の `subagent-settings` が持ち、Subagent Module が1回ごとに開いてもらって閉じる（閉じ忘れは
    12時間で閉じる）~~（2026-09-25 の決定。**実装はまだこの形**——移行は `docs/tasks.json` の `claude-login-relay-owner`）。
    寿命が「1回の仕事」で必要な単位（Project）より短く、呼び出し口（サブエージェント・Shell・Service・E2E）が
    増えるたびに開け閉めの配線と寿命の規則が増えるため改めた
- **合言葉は Project ごとに1つで、固定**（改訂・2026-09-27、ユーザー——当初は「コンテナを起こすたびに
  発行し直す」だったが、Service のサービスはコンテナの起動で systemd が勝手に起こすので、古い合言葉を持ったまま
  起きて 401 になる——Fable のレビューで判明）。**替えるのは Project 設定の「Claude のログインを使わせる」を
  切って入れ直したとき**（切った時点で無効になり、入れ直すと新しいものが出る）。合言葉は host 側に持ち、値を
  記録には残さない。**1回ごとに分けない理由**：中では AI が root なので、コマンド1回に渡した合言葉も
  同じコンテナの別のプロセスから読める——実際の境界はコンテナで、粒度をそこに合わせる（§1「中から
  来たものはその Project の AI と同じに扱う」）
- **コンテナの環境に常に入れる**：`ANTHROPIC_BASE_URL`（中継の住所）・`CLAUDE_CODE_OAUTH_TOKEN`（合言葉）・
  `CLAUDE_CODE_SUBSCRIPTION_TYPE`・`CLAUDE_CODE_RATE_LIMIT_TIER`。**入れ方は core が `incus exec` で Module を
  起こすときの env**（いま `BANTO_HOST_ADDRESS` を渡している経路。新しい機構を増やさない）。Shell の子は
  `buildChildEnv` がそのまま通し、サブエージェントは渡す変数の一覧に4つを足し、Service は systemd の定義に写す。
  Incus の `environment.*`（人が `incus exec` で入っても通る）は、欲しくなったときに足す
- **Claude Code の認証の形は今のまま**：合言葉は `CLAUDE_CODE_OAUTH_TOKEN` で渡す。公式の gateway の作法
  （`ANTHROPIC_AUTH_TOKEN`・`apiKeyHelper`）に替えると、サブスクのログインではなく API キー扱いになる（公式
  ドキュメント「Subscriptions and gateways」、2026-09-27 に確認）。中継は `anthropic-beta` 見出しを触らず転送する
- 合言葉が違えば 401。シェルから読めても、**その Project のコンテナが起きている間、その中継を通して推論を
  呼べる**以上のことはできない（本物のトークンを持ち出せない）
- **送り元をその Project のコンテナのアドレスに縛る**（方針。2026-09-27）——漏れた合言葉が他から効かないように。
  **入れる前に測る**：同じブリッジの別のコンテナから届くか・コンテナの IP が寿命の途中で変わることがあるか
- **通すのは `/v1/messages`（と `/v1/messages/count_tokens`）だけ**（それ以外は 403）。実測で Claude Code が
  中継に投げたのはこれだけ
- **人の確認は Project の設定のスイッチにする**（決定・2026-09-27、ユーザー）：「この Project に Claude の
  ログインを使わせる」、**既定はオン**。その Project の会話の本体（Runner）はすでに同じログインで動いており、
  中の AI はその Project の AI と同じ扱い。オフなら中継はその Project の合言葉を断り、環境からも外す（次に起こす
  ときに効く）。**1回ごとの承認は出さない**——同日の「承認画面に『Claude のログインを使う』と出す」は
  取り消し。中で root の AI が同じコンテナの合言葉を読める以上、本当の柵にはなっていなかった。代わりに
  **枠の消費を人が見られること**（下の観測）を柵にする。banto 全体の「サブエージェント」設定にある「本体の
  ログインを使う」の表示は、この Project 設定に移す
- **観測**：中継は Project ごとに要求の回数・最終時刻・直近の 401 を持ち、Project 設定に出す。Event Store には
  要求ごとには残さない（多すぎる）。**本体のログインが切れたら受信箱に1件**出す（今は失敗の後に推測している）
- **本物は毎回、本体の置き場から読み直す**——更新（refresh）は本体の CLI の仕事のまま。中継は更新しない
  （refresh token に触れない。二者が同時に更新すると回る鍵の取り合いになる）
- 実測（`poc/08-subagent-acp/proxy-probe.mjs`、結合試験）：本物の access token も refresh token も、
  エージェントの環境に入らない。契約の種類の問い合わせだけは中継を通らず直接出る（合言葉では通らない）
  ——代わりに**契約の種類と上限の段**（`subscriptionType`・`rateLimitTier`。資格情報ファイルに並ぶが
  **秘密ではない**）を env で渡し、既定を本体と揃える（アーキ仕様 §4.1）

### コンテナが縛らないもの（把握して設計する）

| | 扱い |
|---|---|
| **資源（CPU・メモリ・プロセス数）** | **まだ上限を掛けていない。** Incus の `limits.*` で掛けられる（§1「まだ決まっていないこと」）。Phase 1 の目的は Vault/Shell/FileSystem の契約確定で、資源の制限は後回し（決定・2026-09-02）。**黙って忘れない**（規則2）ための明示的な未決事項として、`docs/specs/v4-modules.md` §5 にも残す |
| **ネットワーク** | **中から外へは既定で出られる**（決定・2026-09-02）。`npm install`・`git fetch`、アーキ仕様 §2.5「alias 方式」（秘密を使って外部 API を叩く）がそのまま動く必要がある。**ホスト単位の許可リストは持たない**——banto は1人で使う前提（`vision.md`）。**ホストで 0.0.0.0 に待ち受けているものには中から届く**（§1「ネットワーク」） |
| **同じコンテナの中どうし** | 分けない。中では AI が root なので、Module の env・合言葉・ファイルはすべて AI が読めるものとして扱う（§1）。守りは中継の側（§3「コンテナの中から値を返す口を呼ぶ」） |

## 3. host の中継・可視性の層——中継が縛らないもの（2026-09-10）

§1・§2 はコンテナによる閉じ込めを扱ってきたが、**アーキ仕様 §2.5 の
host 層（代理サーバ・Module 間中継・bearer token・可視性・画面からの tool 呼び出し）は、
banto が自作した機構であり、MCP にもコンテナにも守られない独自の境界面**である。
「機能はすべて MCP の向こう」と決めた帰結として MCP に無いものを自作した場所なので、
穴もここに集まる（実例：`docs/notes/2026-09-09-repo-review.md`）。

§2 の「コンテナが縛らないもの」と同じ形で、**MCP のインターフェースに乗らない経路**を
列挙しておく（把握して設計する）：

| 経路 | 何が境界を越えるか | 状態 |
|---|---|---|
| **子プロセスの env 継承** | Module に渡した `BANTO_HOST_MCP_TOKEN` が、Module の spawn する子（＝AI の書いたコマンド）へそのまま継承される。トークンは「どの Module からの呼び出しか」の識別そのものなので、漏れれば AI がその Module の身元で中継を呼べる | **決定（2026-09-10）：Module は子プロセスに `BANTO_*` を渡してはならない。** §2.5 の「プロセスごとに発行」の意図（プロセス＝身元）から、子はその身元ではない。**実装済み（2026-09-10、Shell の `runCommand`）**——`docs/specs/v4-modules.md` §2.3「子プロセスの環境変数」。**コンテナの中では、この守りは効かない**（中の AI は root なので、同じコンテナの Module の env も読める）——§1 の帰結として、**中継の側で守る**（下の「コンテナの中から値を返す口を呼ぶ」） |
| **`/proc`** | AI のコマンドが**親（Module）の `environ`** からトークンを読める | Landlock の時は `/proc` を許可しないことで塞いでいた（2026-09-10）。**コンテナの中では塞がない**（中の AI は root で、`/proc` を読めないと動かない道具も多い）——§1 の帰結として、**中継の側で守る**（下の「コンテナの中から値を返す口を呼ぶ」） |
| **画面 API（`ui-tool-call`）** | authToken だけで `module` 可視の tool（`resolveAlias` 等）も呼べ、秘密の値がブラウザに返る。可視性の強制が frontend 頼み | **実装済み（2026-09-10）**——host が API 境界で可視性を検査する。`agent`・`admin` のみ許可、`module` 可視性は拒否。**その Module が名乗っていない tool 名も拒否**（fail closed）。3つの口（Thread／Project／instance）すべてで同じ検査を通す。「自分の Module か」の照合を host に持たせる形（Canvas ごとのトークン）は将来の強化 |

### 画面は HTTPS でしか動かさない（決定・2026-10-03、ユーザー）

http（ブラウザの言う「安全でない文脈」。localhost は除く）で開かれた画面は、使わせずに「HTTPS で開いてください」と
出す（`components/banto/shell/connect-gate.tsx`）。名前で開いていれば同じ名前・同じ場所の https へのリンクを出し、
IP アドレスなら名前で開くよう書く。

- **理由**：(1) ブラウザは安全でない文脈で一部の機能（`crypto.randomUUID`・クリップボード等）を出さず、携帯から
  送信ごと落ちた（a029ea1a で送信そのものは直した）。(2) 合言葉が平文で流れる。(3) http と https は別のオリジンなので、
  覚えた合言葉が別々になる（2026-09-18 に踏んだ）
- **合言葉は http では読みも覚えもしない**（`getBackendConfig()` が null を返す）——門より先に走る読み込みが URL の
  `bantoToken` を http の側に覚えてしまうため（E2E で実測）。URL の合言葉は https へのリンクにそのまま運ぶ
- localhost・127.0.0.1 は安全な文脈なので止まらない（開発・E2E）
- **入口の側（host で人が行う）**：前に置いた Caddy の http のサイトを https への転送にする。画面の 4175・host の 4737 を
  LAN へ直に出しているなら、待ち受けを 127.0.0.1 に絞ると http で届く道そのものが無くなる（未実施）
- E2E：`e2e/specs/insecure-context.spec.ts`

### 人のログイン（決定・2026-10-03、ユーザー。未実装）

長く使う合言葉（`bantoToken`）を画面で持ち回るのをやめ、**端末ごとのセッション**にする。1人で使う前提で、
アカウント・ユーザー名は持たない（ログインできる人＝持ち主）。

**なぜ**：(1) 新しい端末ごとに長いトークンを手で運ぶ必要があり、運ぶ途中で漏れる（2026-10-03、QR で運んだ値が
AI の文脈に入った）。(2) トークンが画面の JavaScript から読める localStorage にある。(3) 1本しか無いので、
1台だけ締め出せない（替えると全端末で入れ直し）。

#### 決まったこと（結果）

- **パスワードは置かない**（ユーザー——管理が面倒）。入り方は次の3つだけ：
  1. **パスキー**（WebAuthn）。端末の指紋・顔・パスコードなど、端末が本人と認めれば入れる
  2. **端末を追加**：入っている端末の設定画面で押すと、**QR とリンクの両方**（中身は同じ、リンクにはコピーの
     ボタン）を出す。**有効 10 分・1回だけ使える**。使われたら、出した側の画面に「端末が入りました」と出す
  3. **host のコマンドが出すログインのリンク**（1回だけ・10 分）。まっさらなとき・パスキーを全部なくしたときの
     戻り道。**host に入れる人＝持ち主**を最後の頼りにする
- **いまの利用者の切り替え**（Fable のレビュー高1を受けて改めた）：トークンをセッションに引き換える口は作らない——
  あると、機械のトークンを持つ者がいつまでも人として入れる（パスキーの登録・端末の締め出しまで）。**最初の1回は host で
  `banto login-link` を打って入り**、設定画面でパスキーを登録する。**切り替えのときに機械のトークンを作り直す**（漏れた値を
  無効にする。2026-10-03 に値が AI の文脈に入っている）。画面の localStorage に残ったトークンは、画面が見つけ次第消す
- 設定画面に**「ログイン中の端末」**の一覧（入った方法・最後に使った時刻・おおよその端末名）と、
  1台ずつ締め出す操作、パスキーの一覧と消す操作を持つ
- **セッションの期限は 30 日で、使っている間は延びる**（ユーザー——手間を増やしたくない）。30 日使わなかった端末は
  入り直す
- **今のトークン（`authToken`）は機械の口として残す**——E2E・`restart-when-idle.mjs`。画面は持たない
- **Publish で公開したものの前にも、このログインを効かせる**（2026-09-28 の「当面は認証を置かない」を改める）。
  人から見れば「banto にログインしていれば、公開したものもそのまま開ける」。下の「公開したものの前の認証」
- **公開先のドメインは今の `*.banto.tjstkm.net` のまま**（ユーザー）。banto の子でないドメインへ移せば公開先から
  パスキーのプロンプトも出せなくなるが、DNS・証明書の追加と URL の変更が要る。下の直しで残るのはそのプロンプトだけ

#### 方式（ユーザー「結果が変わらなければ方式は任せる」。Fable のレビュー（2026-10-03）を受けて改めた）

**前提の事実**：画面は `https://banto.tjstkm.net`（Caddy → 画面 4175・`/api` は host 4737。画面と API は同じオリジン）。
Canvas の sandbox は `sandbox.banto.tjstkm.net`（iframe は親に postMessage するだけで、API を呼ぶのは親の画面）。
公開したものは `*.banto.tjstkm.net`（publish-caddy、中身はコンテナの中で **AI が作って動かすもの**）。これらは
**同じサイト**（登録可能ドメイン `tjstkm.net`）なので、**SameSite は公開先・sandbox からの要求を止めない**。公開先は
敵になりうるものとして設計する。host の API は `0.0.0.0:4737` で待ち受け、コンテナからも届く——**認証の要らない口は
すべてコンテナの AI から叩ける**前提で作る。WebSocket は core にも画面にも無い（2026-10-03 確認）。

- **画面の公式のオリジン**：既にある config の `publicUrl`（OAuth の戻り先に使っている）をそのまま使い、オリジンの形で
  あることを確かめる。別の項目は足さない。パスキーの RP ID・Origin の検め・リンクの組み立てに使う
- **API の基点は画面のオリジンに固定する**：`publicUrl` のある運用では、画面は `window.location.origin` の `/api` だけを
  呼ぶ。URL の `bantoHost` は **localhost・127.0.0.1 でだけ読む**（開発で画面と host のポートが違うとき）——本番で読むと、
  公開先のページが `?bantoHost=<自分>` へ飛ばして画面の接続先をすり替えられる（レビュー高2、今のコードの穴）。
  **画面は `bantoToken` を読まない**（Bearer で話す様式を画面から消す。開発・E2E もログインのリンクで入る）
- **セッションの Cookie**：`__Host-banto-session`（`__Host-` で Domain 無し・Path=/・Secure を強制——兄弟のサブドメイン
  からの上書き（Cookie tossing）を防ぐ）。HttpOnly・Secure・SameSite=Lax。値はランダム 256 bit で、**host はハッシュ
  （SHA-256）だけを持つ**。30 日の滑走（使えば延びる）。絶対上限は置かない（ユーザー「手間を増やしたくない」）
- **API の認証は2本**：`Authorization: Bearer <authToken>`（機械）か、セッションの Cookie（人）
  - **Cookie で来た要求は、独自のヘッダ `X-Banto-Client: 1` が無ければ断る**——独自のヘッダ付きの要求は別のオリジンから
    preflight 無しに出せず、CORS は画面のオリジンにしか許さないので、兄弟のサブドメインからの `<img>`・フォーム・遷移・
    no-cors fetch がまとめて落ちる。`Origin` があれば画面のオリジンとの一致も見る。Origin・Sec-Fetch-Site・Referer を
    重ねて見る形は採らない（古い Safari は Sec-Fetch を送らず、Referer は消えうる——レビュー中3）
  - **CORS**：`access-control-allow-origin: *` をやめる。本番は同じオリジンなので CORS は要らない。開発（画面と host の
    ポートが違う）でだけ画面のオリジンに `allow-credentials: true` で許す
- **画面を iframe に入れさせない**：画面に `Content-Security-Policy: frame-ancestors 'none'` と
  `Cross-Origin-Opener-Policy: same-origin` を付ける（同じサイトの iframe には Lax の Cookie が付くので、公開先が
  ログイン済みの画面を透明に重ねて承認や「端末を追加」を押させられる——レビュー中7）。sandbox の口は別なので影響しない
- **パスキー**：RP ID は `banto.tjstkm.net`。**守りは検証時の origin の一致**（clientDataJSON の origin を画面のオリジン
  1つに固定）——RP ID の子（公開先・sandbox）は同じパスキーのプロンプトを出させられるので、RP ID では守れない
  （レビュー中4）。userVerification は required。公開鍵・credential id・署名回数だけを持ち、署名回数が増えないことを
  複製とは見ない（同期型のパスキーは常に 0）。登録はセッションのあるときだけ。ライブラリは `@simplewebauthn/server`（予定）
- **大事な操作は直前のパスキーを求める**（step-up、ユーザー）：端末を追加・パスキーの追加と削除・端末の締め出しは、その場で
  パスキーを通してから。本人の確かめ方は端末に任せる（指紋・顔・パスコードのどれでもよい）——画面に XSS が1つあれば、HttpOnly でも「端末を追加」を呼んで札を外へ送れるため（レビュー中6）。
  パスキーがまだ1つも無いとき（切り替え直後）は求めない
- **1回だけの札**（端末を追加・host のリンク）：ランダム 256 bit、host はハッシュと期限（10 分）だけ。URL は
  `https://banto.tjstkm.net/login#code=<札>`——**札はフラグメントに置く**（アクセスログ・Referer に残らない）。画面が
  フラグメントを読み、`POST /api/auth/redeem` で引き換えて URL から消す。出した側には `/api/events` で「使われた」
  （端末名）を届ける。http から https への案内（connect-gate）はフラグメントも運ぶ
- **host のコマンド**：`banto login-link`（cli.ts）。host の設定とデータ置き場を読める人だけが打てる
- **認証の要らない口**（redeem・パスキーの開始・publish-check・callback）は数と寿命に上限を置く（コンテナからも叩けるため）
- **締め出し**：セッションを消せば、その端末の次の要求から 401。`/api/events` の流れも切る
- **ログインしていない画面**：門（ConnectGate）が「パスキーで入る」と「ほかの端末から追加」の案内を出す。
  トークンを打つ欄は消す
- **機械の合言葉**：起動ログにトークンを出さない（今は `cli.ts` が毎回出し、journald に残っている）。コンテナには今も
  渡しておらず（渡す env の一覧に無い）、これからも渡さない
- **E2E**：`e2e/start-core.ts` が書く config に、その回の画面のオリジン（`http://127.0.0.1:<port>`）を `publicUrl` として
  入れ、**画面には `banto login-link` と同じ口で出したリンクで入る**——Cookie・独自ヘッダ・札の引き換えの経路を毎回通す
  （localhost は http でも Secure・`__Host-` の Cookie を受ける）。パスキーは Playwright の仮想認証器で通す。
  API を直に叩く試験は今までどおり Bearer

#### 公開したものの前の認証

oauth2-proxy と同じ形。**banto のセッションの Cookie は公開先へ届かない**（`__Host-` で `banto.tjstkm.net` だけ）。

1. publish-caddy のルートを subroute にし、先頭で `/.banto-auth/*` を host に回す。それ以外は、host の確かめ口
   （`GET /api/auth/publish-check`）へ `reverse_proxy` の `rewrite`＋`handle_response`（Caddyfile の `forward_auth` を
   JSON に落とした形）で問い、2xx なら次へ。元のメソッドと URI は `X-Forwarded-Method`・`X-Forwarded-Uri` で渡す
2. 確かめ口は、**その公開先の名前にだけ効く通行証**の Cookie（`__Host-banto-pass`、その公開先のホストだけに置く）を見る。
   公開先は Caddy の付ける `X-Forwarded-Host` で知る——**4737 に直に来た要求（LAN・コンテナ）では使わない**（Caddy を
   通ったことが分かる形で受ける。形は実装で決める）。通っていれば 200。無い・古いとき、画面の遷移
   （`Sec-Fetch-Mode: navigate`）なら `https://banto.tjstkm.net/api/auth/publish-start?rd=<公開先の URL>` へ 302、
   それ以外（fetch 等）は 401
3. **公開先どうしの横取りを断る**：確かめ口は `Sec-Fetch-Site` が `same-origin`・`none` 以外なら断る——別の公開先の
   ページから A へ要求を出すと、Lax の通行証が付いて A のサービスを人の名義で動かせるため（レビュー中5）
4. `publish-start` は banto のセッションを確かめ（無ければログインの画面を経て **`publish-start` に戻る**——画面は自分で
   飛ばさない）、`rd` を URL として読み、`https:` かつホストが**今公開中のホスト名のどれか**であるときだけ、1回だけ・1分の
   札を付けて `https://<公開先>/.banto-auth/callback?code=<札>&rd=<元のパス>` へ戻す。渡すのはパスだけで、先頭は `/`
   1文字（`//`・`/\` は断る——レビュー中8）
5. host は札を引き換え、その公開先だけの通行証を Set-Cookie して元のパスへ戻す
6. **通過したあと、Caddy は通行証の Cookie を要求から外してからサービスへ渡す**（`headers` の Cookie の正規表現の
   置き換え）。**応答の側でも、サービスが返す `__Host-banto-pass` の Set-Cookie を落とす**——サービスは自分のホストなので
   通行証を書き換え・消せる（レビュー中9）。`/.banto-auth/` のパスはサービスへ渡さない

- 通行証は banto のセッションに結びつける——セッションを締め出せば、その端末の通行証も次の要求から効かない。
  公開をやめれば、その公開先の通行証も効かない。期限はセッションと同じ
- 承認の画面の認証の選択に「banto のログイン」を足し、**既定にする**。「無し」「Basic 認証」は残す
- **前提**：host の Caddy が `handle_response`・`headers` の正規表現の置き換えを持つ版であること（2.5 以降）。
  host の Caddy は v2.11.4（2026-09-28 に確認、v4-modules.md の Publish）なので足りる
