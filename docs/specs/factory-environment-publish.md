# 仕様：Factory / Environment / 公開

> **状態：ADR-0001 決定16 として記録済み**（2026-08-21）。ADR は決定と理由を、
> ここは形を持つ。**同じことを2箇所に書かない**（規則3）ので、食い違ったらこちらが誤り。
> 要件 B1〜B7・C5・C10・C11・D1・D2・D4・A6・F4 に対応する。
> **草案時点の未決5点は §8 で解いた。残っている1点もそこにある。**

---

## 0. なぜ3つを一度に書くか

Factory の一本の流れが、そのまま Environment と公開の呼び出し順になっている。

```
依頼 → worktree を作る（Repo）→ 環境を立てる（Environment）→ 実装 →
       テストを走らせる（Environment.exec）→〔人が見るなら公開〕→
       main へマージ（Repo）→ 環境を畳む（Environment.destroy）
```

3つを別々に決めると、この接ぎ目——**誰が worktree を持つか / テストはどこで走るか /
公開したものは何を指しているか**——が抜ける。要件 B2 が「ワークツリー作成→実装→
テスト→マージ」と一続きに書かれているのは、そういう意味だと解釈した。

## 1. 全体の姿

```
                     ┌──────────────────────────────┐
   依頼 ──────────►  │  Factory（耐久ワークフロー）   │
                     │  段を進める。冪等。再開する      │
                     └───┬───────┬───────────┬──────┘
                         │       │           │
                  capability   capability  capability
                    "repo"    "environment"  "publish"
                         │       │           │
              ┌──────────┘   ┌───┴────┐   ┌──┴──────┐
              │              │        │   │         │
            Repo         process   docker  none   cloudflared
         （worktree）     script   devpod   caddy   tailscale
                         proxmox …          …
```

- **Factory は git を知らない。** worktree は Repo に頼む（ADR 決定5 で既決）
- **Factory は環境の種類を知らない。** capability で頼む
- **環境は公開の手段を知らない。** `host:port` を返すところまでが仕事

## 2. Environment

### 2.1 口

```
capability: "environment"

create(spec)            → handle          環境を1つ立てる
exec(handle, command)   → 出力 / 終了コード  環境の中で走らせる
address(handle, port)   → host:port       中の port へ届く宛先を返す
destroy(handle)                           畳む
```

`handle` は**不透明な文字列。banto は解釈しない**（`thread.session` と同じ扱い）。
ただし**ログに載せるときは `environmentHandle` と名乗る**——`thread.session` の
`sessionHandle` と同じ理由で、**鍵になる項目は名前だけで一意**でなければならない（§8-1）。

`spec` の中身は実装ごとに違うので、**banto は素通しする**。docker なら image 名、
process なら作業ディレクトリ、script なら何も見ずにスクリプトへ渡す。ここを
banto 側で型づけると、型が実装の共通部分に縮み、providers を足せなくなる。

### 2.2 到達性の規則（これが要）

> **環境は、`address` が返す宛先が banto ホストから届くことを保証する。**
> 届かないなら、トンネルを張るのは環境の側の仕事。

これを書かないと、公開モジュールが「Proxmox のときはこう、AWS のときはこう」と
環境の事情を知る羽目になり、**組み合わせの数（N×M）だけ実装が要る**ことになる。
規則を1本置くと、代償は環境の種類の数（N）だけで済む。**払う場所を選ぶ判断**である。

| 実装 | `address` の中身 |
|---|---|
| process | `127.0.0.1:N`（何もしない） |
| docker | `-p` で割り当てたホスト側の port |
| VM（Proxmox / AWS / SSH） | VM の IP。届かなければ**環境実装が SSH トンネルを張る** |

### 2.3 実装は provider として差し替える

これは名前のついた形である（規則12）——Kubernetes の CRI、Terraform の provider、
そして **DevPod の provider**。DevPod の契約は実際にこうなっている（実物を確認）：

```yaml
exec:
  init: …    command: …    create: …    delete: …
  start: …   stop: …       status: …
```

中身はただのコマンド行で、Go を書く必要はない。**この形をほぼそのまま借りる。**

### 2.4 リポジトリのスクリプトが実装になる場合

`env-script` という汎用アダプタを1つ持つ。これが `environment` capability を満たし、
各動詞を宣言されたスクリプトへ委譲する。**リポジトリは MCP サーバを書かなくてよい。**

```jsonc
// リポジトリ側
{ "environment": { "kind": "script",
    "create":  "script/env-create",
    "exec":    "script/env-exec",
    "address": "script/env-address",
    "destroy": "script/env-destroy" } }
```

線は **argv 入力・stdout 出力・終了コード**。発明しない。
**非ゼロで終わったら止まる。黙って既定へ落ちない**（規則2）。

先例：CNB buildpack（`bin/detect` / `bin/build`）、CNI プラグイン、
GitHub の "Scripts to Rule Them All"（`script/bootstrap` / `script/server`）。

これは機能であると同時に**口の検査**である。**4本のシェルスクリプトで満たせない口は、
大きすぎる口。** だから後付けの拡張ではなく、早い段階で書く（§7）。

#### 安全上、ここで2つ決める必要がある

**① 隔離を作るコードは、その隔離の中では走れない。**
`env-create` は banto ホスト上で banto の権限で走る。つまり**リポジトリを取り込むことが
コード実行を許すことになる。**
→ **リポジトリの中身だけで有効化されない。**「このリポジトリは自前の環境を持ってよい」を
運用者が banto 側の設定で明示的に許す。

**② AI がそのスクリプトを書き換えられる。**
エージェントはそのリポジトリで作業するので、`script/env-create` を書き換えれば
**自分を閉じ込めている箱の作り手を書き換えられる。**
→ **環境スクリプトの変更は判断待ちに立てる**（要件 A6 の既存のキューを使う。新機構を作らない）。
人が承認するまでは**前に承認された版**を使う。承認の単位は内容のハッシュ。

### 2.5 devcontainer.json は契約にしない（実測）

仕様を読んだ結果：**`image` / `build.dockerfile` / `dockerComposeFile` のいずれか1つが必須**で、
「非コンテナ環境（素のプロセスやベア VM）を対象にする手段は無い」と明記されている。

DevPod ですらここを越えていない——devcontainer.json が無ければ**自動生成してでも**用意する。
つまり AWS も Proxmox も「Docker を動かす場所」を作っているだけで、
**プロバイダが一番揃っている既存製品でも「コンテナを使わない」は環境として存在しない。**

したがって：

> **devcontainer.json は、コンテナ系 provider の入力形式。banto の契約ではない。**

対応する価値はある（既存リポジトリがそのまま乗る）が、それは docker provider の中の話。

なお、**あのコンテナ限定の仕様にすら `forwardPorts` がある。** 環境を定義すると port の話が
必ず付いてくる、という傍証として採る。ただし届くのはローカルマシンまでで、
公開 URL の概念は仕様に無い——だから §3 は自分で決める。

## 3. 公開（Publish）

### 3.1 口

```
capability: "publish"

publish(host:port, name?) → URL
unpublish(name)
```

**環境を知らない。** 受け取るのは `host:port` だけ。

| 実装 | 中身 |
|---|---|
| `none` | 受け取った `host:port` をそのまま返す |
| `caddy` | 経路を書いて `https://<name>.example.com` |
| `cloudflared` | トンネルを掘って URL |
| `tailscale` / `ngrok` | 同様 |

> **`publish` という語を、port の割り当てに使わない。** docker の `-p` は
> 慣用的に「publish」と呼ばれるが、ここでは **capability の名前**である。
> port の話は「割り当て」と呼ぶ（ADR 決定7 の名前づけ 2）。

### 3.2 なぜ環境から割るか

全部を環境に入れると **N×M**（環境の種類 × 公開手段）になる。process にも docker にも
Proxmox にも cloudflared 対応を書くことになる。

割る位置は「**それは環境にしか答えられないか**」で決まる。
`address` は環境にしか答えられない。`publish` は答えられる。だから境目はそこ。
**N＋M になり、新しい公開手段を足すのに環境実装を1つも触らない。**

要件 C5 が最初から公開を別モジュールに割っていたのは、この形だったと解釈した。

## 4. capability（役割）による依存

いまの契約は依存を**実装の名前**で書く形になっている：

```ts
{ module: 'env-docker', tools: [...] }   // ← 実装を名指ししている
```

これでは Factory が「環境をくれ」と言えない。**差し替え可能にしたいのに、
契約が差し替えを許していない。** 役割で書けるようにする：

```ts
// 実装側：この役割を満たすと宣言する
readonly provides?: readonly Capability[];         // 'environment' | 'publish' | …

// 依存側：実装ではなく役割を要求する
{ capability: 'environment', tools: ['create','exec','address','destroy'], usedBy: ['verify'] }
```

**役割の実体はツール名の集合である。** ここが効くところで、既存の `resolve()` は
すでに**本物の `tools/list` と突き合わせて `required-tool-missing` を出す**機構を持っている。
つまり「この実装は environment を名乗ってよいか」を**自己申告ではなく実測で確かめられる**（規則1）。
**役割に名前を付けるだけで、検証機構はもう在る。**

どの実装を使うかは設定で選ぶ（§6）。**候補が1つでも、自動で選ばない**——
黙って選ばれた既定は、忘れられる（C8c と同じ理由）。

## 5. Factory

要件 B1〜B7、ADR 決定10。

### 5.1 Run とは何か

> **Run は Thread を1つ持つ。**

実装をするのはエージェントなので、Run には会話が要る。banto にはすでに Thread があり、
base・fork・セッション再開（`thread.session`）を持っている。**新しい会話の器を作らない。**

- **依頼は Thread の base に入る。** 要件 R3 の表に「依頼・制約」が base に入るものとして
  そのまま書いてある
- B5（落ちた地点から再開）のうち、**会話の再開は既存の機構でそのまま効く**
- 失敗した Run から fork して人が引き取る、が自然にできる（要件 A3）

### 5.2 段

```
queued → worktree → environment → implement → test → 〔review〕→ merge → teardown → done
                                                                            └→ failed
```

| 段 | やること | 頼む先 |
|---|---|---|
| `worktree` | ブランチと作業ツリーを作る | Repo |
| `environment` | 環境を立てる | capability `environment` |
| `implement` | サブエージェントが実装し、コミットする | Runner |
| `test` | テストを走らせる | `environment.exec` |
| `review` | **既定では通過。** 待つ設定のときだけ判断待ちに立つ（B4） | A6 のキュー |
| `merge` | main へ入れる | Repo（§5.4 の順序づけに従う） |
| `teardown` | 環境を畳む | `environment.destroy` |

公開は段ではなく、**`review` で待つときに使う任意の枝**とする——動いているものを人が
見たい場合だけ `publish` を呼ぶ。常に公開すると、待たない既定（B4）で誰も見ない URL が生える。

### 5.3 再開（B5）——済みかどうかは現物を見て決める

耐久ワークフローの核。名前のついた問題である（durable execution）。

banto での解き方は、規則3 から素直に出る：

> **「その段は済んだ」というフラグを保存しない。世界を見て判定する。**

| 段 | 済みの判定 |
|---|---|
| `worktree` | そのブランチと作業ツリーが在る |
| `environment` | `address` が返る |
| `implement` | ブランチに新しい commit が在る |
| `test` | ← **観測できない**（下記） |
| `merge` | main がそのブランチを含む（`git merge-base --is-ancestor`） |
| `teardown` | 環境が無い |

git を使う段は、ほぼ全部が観測可能になる。**フラグを持たないので、フラグと現実がずれない。**

**`test` だけは導出できない。** 再実行しないと分からないので、これは**記録してよい事実**である
（`thread.session` と同じ理由——導出できないものは規則3 の対象外）。ただし、

> **テスト結果は commit の sha で鍵をつける。** sha が変われば無効。

こうすると、保存した値が現物から自己無効化される。**古い結果が生き残る経路が無い。**

### 5.4 順序づけと衝突（B7）——マージだけ直列にする

これも名前がある：**merge queue**（bors-ng、GitHub merge queue、Zuul の gating）。

- **`implement` と `test` は並行。`merge` だけ1本の列に入れる**
- マージが衝突したら、**main の先端に載せ直して `test` からやり直す**
  （`implement` からではない——実装は済んでいる）
- 載せ直しても通らなければ **`failed` にして判断待ちに立てる**（A6）。
  **列を止めない**——要件 B の受け入れが「1つ失敗させても他の2つは進む」なので、
  失敗した Run が後続を塞いではいけない

### 5.5 失敗の扱い

- `failed` になった Run は、**環境を畳まない**。人が中を見られる状態で残す
- ただし放っておくと資源が漏れるので、**畳む期限を設定で持つ**。
  **公開も同じ期限に乗せる**——タイマーを2つ持つと、いつか片方だけが残る
- 失敗は判断待ちに立つ（A6）。**発生では鳴らさない。滞留したら鳴る**（A7）

### 5.6 並行数

**Factory は同時実行数の上限を設定で持つ。** WorkerPool モジュールは Phase 3 なので、
Phase 2 では Factory 内で数える。

上限の根拠は F4 で測る。**F4 は「線形を超えたら違反」ではなく「どこで曲がるか」を
測る検証項目である**（ADR 決定15）——枝が長く伸びれば共有プレフィックスの割合は
減るので、線形に近づくのは自然な挙動。**曲がる点が分かれば、それがこの上限になる。**

### 5.7 ツールの許可（D4）

Run のサブエージェントに渡すのは、**その Factory に紐づいたモジュールのツールだけ**。
既定で何も通らない現在の実装（`allowedToolNames`）がそのまま効く。

## 5.8 語の使い分け（Factory を書く前に決めておく）

ログはイベントの型を跨いで読まれるので、Factory が語を持ち込む前に決める
（ADR 決定7 の名前づけ）。

| 語 | Factory では | なぜ |
|---|---|---|
| **base** | **使わない。`targetBranch` と呼ぶ**（既定は `main`） | `base` は会話の base（要件 G）。git の base branch と重なる |
| **queue** | 判断待ちは `pendingDecisions`、マージの列は `mergeQueue` | 素の `queue` は、A6 のキューと merge queue のどちらにも読める |
| **status** | Run の状態も `status` | 「どうなっているか」は1語に寄せる |
| **run / runId** | Factory の Run。**空けてある** | 問い合わせは `query` / `queryId`（§8-1） |
| **handle** | 環境のものは `environmentHandle` | セッションのものは `sessionHandle` |

## 6. 設定

どこに何を置くか。**同じことを2箇所に書かない**（規則3）。

| 置き場 | 何を | 理由 |
|---|---|---|
| **リポジトリ**（`.banto/` 等） | どういう環境が要るか（`environment.kind` とスクリプトの場所）、テストの走らせ方 | プロジェクトについて恒久的に真なこと（要件 R7） |
| **banto の設定** | どの provider を使うか、公開手段、並行数、`review` で待つか、**そのリポジトリに自前環境を許すか**（§2.4①） | 運用者の判断。リポジトリに書かせてはいけないもの |

**「自前環境を許すか」がリポジトリ側に無いのが要点。** リポジトリの中身が
自分の権限を決められてはならない。

## 7. 実装順

| | 中身 | 得るもの | 状態 |
|---|---|---|---|
| 0 | capability 依存（module-kit） | Factory が「環境をくれ」と言えるようになる | **済**（2026-08-21） |
| 1 | **`process` ＋ `none`** | Factory が動き出す。**安全上の判断が要らない** | **済**（2026-08-21） |
| 2 | **`env-script`** | 口が argv 4本で表せるかの検査。§2.4 の①②を**ここで**決める | |
| 3 | **`docker`** | 2つ目の実装。口が本当に差し替え可能かの証明 | |

**`process` の `destroy` は何も消さない。** 消すものが無いからではなく、
**消してよいものが無いから**である——worktree の持ち主は Repo（決定5）。
ここで消せると、Factory が Repo に頼まずに worktree を消せてしまう。
同じ理由で `create` もディレクトリを作らない（在ることを確かめるだけ）。

**`none` は公開したふりをしない。** 返す URL に「届く範囲」を必ず添える
——URL だけ返すと外から開けると誤解され、**「動いているはずなのに開けない」**という
一番たちの悪い壊れ方になる。

**安全の判断を最初の一歩に載せない**ので、Phase 2 が止まらない。
そして **1つ目の実装では口の正しさは分からない。2つ目を足したときに分かる**ので、
1つ目は一番安いものにして早く2つ目へ行く。

## 8. 草案時点の未決——どう解いたか

**5点とも解いて ADR-0001 決定16 に記録した。** 経緯を残すのは、後から読む人が
「なぜこの形なのか」を辿れるようにするため。

### 1. `run` という語が2つの意味を持っている → **改名済み（版2）**

`run.step` / `runId` はいま **Runner の1回の `query()`** を指しているが、Factory の Run は
別物である。**`Dependency.tools` が2つの名前空間を背負っていた失敗と同じ形**（教訓6）で、
あのときは3本目のモジュールを書くまで露見しなかった。今度は書く前に気づいている。

→ **`query.step` / `queryId` に改めた**（2026-08-21）。`LOG_VERSION` は 2 で、
1 を読む道は `packages/core/src/migrate.ts`。あわせて `thread.session.handle` を
`sessionHandle` に（環境モジュールも handle を返すため）、`step` を削除した
（常に `'query'` で情報を持たず、Factory の「段」と重なる）。

**基準は「鍵になるか」。** 型を見ずに読まれる鍵は名前だけで一意でなければならない。
型の中に閉じた値（`state` など）は、イベントの型が分かれば意味も決まる。

### 2. 環境は Run ごとか、Factory ごとか → **Run ごと**

B3 が並行を要求するので、Factory ごとに共有すると並行する Run が互いを汚す。
立ち上げ費用が Run の数だけ掛かるのが代償だが、**最初の provider は `process` なので
ほぼ掛からない**。費用が問題になるのは docker 以降で、そのときには実測がある。

失敗した Run の環境は畳まない（§5.5）。畳む期限は設定で持ち、**公開も同じ期限に乗せる。**

### 3. `status` / `start` / `stop` を口に入れるか → **いまは入れない（唯一の持ち越し）**

DevPod は持っているので、検証用環境が長生きするなら要るはずである。しかし
**いま足すと使わない動詞が増える。** `env-script` を書いた時点で足りなければ露見するので、
そこで判断する。**これが唯一の持ち越しで、引き金は「`env-script` を書き終えたとき」。**

### 4. `test` の走らせ方を誰が決めるか → **リポジトリ（`script/test`）**

§6 のとおり「プロジェクトについて恒久的に真なこと」なのでリポジトリ側。
**Factory はコマンドを組み立てない**——組み立てると Factory がプロジェクトの事情を知る。

### 5. 公開の名前空間 → **Factory が Run ごとに振り、`teardown` で `unpublish`**

`caddy` は永続的な経路を書くので畳み忘れが残りうる。失敗して環境を残す場合は
公開も残す（見るために残しているので）。**期限は環境と同じものを使う**——
タイマーを2つ持つと、いつか片方だけが残る。
