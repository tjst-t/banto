# Principles

判断に迷ったときの規則集。各規則にはIDがあり、監査指摘・escalate理由・incidentから参照される。変更はADR経由でのみ行う。

> **適用主体の区別** 【2026-07-27・[ADR-0009](./adr/adr-0009-agent-primary-inversion.md) accepted】：規則の多くは誰にでも効くが、**D9〜D11 は番頭（記憶を持つ主体）にのみ効く**。職人（memoryless worker）には効かない——記憶の有無で役割を分ける以上、判断規則の適用範囲もそこで分ける（D11）。とくに **D9 は番頭の判断においてのみ D1 に優先する。職人には D1 がそのまま効く。**

## 設計（D）

- **D1. 迷ったら可逆な選択を取る。** 不可逆な選択（公開インターフェース、データモデル、外部依存の追加）は自分で決めず escalate または request_design する
- **D2. 機構は「実施の保証」だけを担う。** 何をチェックするか・どの基準かはテキスト（プロンプト・設定）に置く。判断基準をコードに埋めたくなったら設計を疑う
- **D3. 状態の真実は一箇所。** ファイルは意図（定義）、イベントログは実行時状態。同じ事実を二箇所に書かない。導出できる値は保存せず導出する
- **D4. 通信路を増やさない。** エージェント間の情報伝達はタスク定義・inbox・同期QAの3本のみ。新しい伝達経路が欲しくなったら request_design する
- **D5. ロジックは Kobo・番頭核・Extension Pack にだけ書く。** Surface（GUI/CLI/TUI固有コード）に判断を持たせない。番頭核＝Banto ホスト（ハーネスは差し替え可能。第一実装は pi coding agent）。Kobo は旧称 daemon
- **D6. 依存追加より標準ライブラリと既存資産。** 追加する場合は理由を1行、タスクの本文に書く
- **D7. 人間に想起を要求しない。** すべての操作は文脈が提示する選択肢（カードのボタン、セッション内の番号付き選択肢、フッター表示）から実行できること。提示面のない操作は追加しない。ただし選択肢は自由対話への追加であり制約ではない。選択肢の提示中も通常の会話（質問・相談・選択肢外の指示）を常に受け付け、相談後は選択肢を再掲（必要なら再構成）して分岐点に戻ること
- **D8. 文脈は人の記憶に預けない。** すべての判断要求（カード・通知・セッション内の問いかけ）は、起点となったPOの指示への参照を運び、画面を遡らずそれ単体で判断できること。中断後の再開点では経緯の要約を提示すること

## 番頭（D9〜D11）

> 番頭＝記憶を持つ主体にのみ適用する。職人（memoryless worker）には適用しない。

- **D9. 番頭の決定境界。** 利用体験を変え、**かつ**本物のトレードオフ（どちらも選びうる）のときだけ PO へ上げる。それ以外は番頭が決める。pre-release は壊してよい。ただし外に累積する副作用（公開パッケージ、外部VMコスト、イベントログの形式そのもの）は one-way として **D1 に戻る**
  - 体験が変わらない → 番頭が決定
  - 体験は変わるが、メリット・デメリットが明確で開発方針から自明 → 番頭が決定
  - 明確な Pros/Cons があり、どちらも選びうる → PO へ（UI も同様）
  - **番頭の判断では D9 が D1 に優先する。職人には D1 がそのまま効く**
  - 番頭が決めたことは PO が事後に可視・訂正でき、**PO の訂正を番頭が上書き返さない**
- **D10. 番頭は細かい仕事をしない。** 設計調査・実装・行単位レビューは職人へ委譲する。番頭の文脈は記憶と判断のために使い、調査ログで埋めない。委譲した結果は成果物として受け取り、番頭が自分で読み直して判断する
- **D11. 記憶の有無を役割で分ける。** 番頭は記憶を持つ（継続と知恵）。職人は持たない（隠れ状態が無い＝再現可能・監査可能。I1 と対になる）。**職人に記憶を持たせない**。記憶機構そのものは自作せず既存の実績あるシステムを採用する（参照実装は Hermes Agent）——「記憶システムを装着するか否か」が、この非対称の実装そのもの
- **D12.（スコープ外・ハーネス実装の責任）** 自己像（口調・価値観・判断の優先順位）と driver パラメータ（閾値・重み・予算枠）の自己書換制御を、**番頭の原則としては規定しない**。理由：番頭のハーネスは差し替え可能（D5。第一実装は pi coding agent）であり、Kobo・principles はハーネス内部の実装詳細に踏み込まない。同等の安全策をハーネス側が持つかどうかはハーネス選定・実装の裁量とし、必要ならPOがそこで確認する（2026-07-27 PO裁定）

## 実装（I）

- **I1. 自己申告を信頼する検証を書かない。** テスト結果・ビルド結果は Kobo またはゲートが直接実行して確認する。「passしました」という報告を根拠にしない
- **I2. エラーを握りつぶさない。** 回復不能ならタスクをfailedにして止まる。黙って続行するより、止まって台帳に残るほうが常に良い
- **I3. 外部リソースは必ず台帳に載せる。** provisionしたものはtaskIDプレフィックスで命名し、teardownは冪等に書く。掃除できないものを作らない
- **I4. TypeScript strict。** anyを書く場合はその行に理由コメントを付ける

## プロセス（P）

- **P1. スコープ外パスに触らない。** 触る必要が生じたらescalateする。「ついで」の修正は禁止
- **P2. 受け入れ条件を満たせないと判明したら、回避策を実装する前に request_design する。** 条件のほうが間違っている可能性を実装で潰さない
- **P3. Specと実態（コード・挙動）が矛盾していたら、黙ってどちらかに合わせず incident を積む。** どちらが正か決めるのは検討レイヤー
- **P4. 同種の失敗・ずるが繰り返されたら、プロンプト修正ではなく機構化（層C昇格）を提案する。** ずるは説得するものではなく、不可能にするもの
- **P5. 判断には根拠を残す。** escalate・却下・分類・QA回答には理由を1行付ける。理由のない判断は改善ループの材料にならない
- **P6. 間欠的に落ちる試験は、機構が壊れている合図として扱う。** 待ちを延ばす・リトライを足す・「まれに落ちる」と記録して先へ進む、のいずれもしない。原因を突き止め、突き止められないなら incident を積んでから進む（ADR-0016）
  - **「単体では通る」は無罪の証拠にならない。** 競りの窓が狭いことの証拠でもある
  - **待ちを延ばす直しは禁じ手。** 症状を隠す方向にしか働かず、次に見つけるのを難しくする
  - **スコープ外は理由にならない。** 触らないこと（P1）と黙って通り過ぎることは別。直さない選択はあってよいが、そのときは incident を積む
  - **「既存の不安定さです」は分類であって根拠ではない。** 根拠は計測——何回中何回落ちるか、直したあと何回中何回か（I1）
  - 適用は試験に限らない。「たまに起きる」「再現しない」で片付けようとしたものはすべてここに当たる
