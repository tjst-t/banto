# Principles

判断に迷ったときの規則集。各規則にはIDがあり、監査指摘・escalate理由・incidentから参照される。変更はADR経由でのみ行う。

## 設計（D）

- **D1. 迷ったら可逆な選択を取る。** 不可逆な選択（公開インターフェース、データモデル、外部依存の追加）は自分で決めず escalate または request_design する
- **D2. 機構は「実施の保証」だけを担う。** 何をチェックするか・どの基準かはテキスト（プロンプト・設定）に置く。判断基準をコードに埋めたくなったら設計を疑う
- **D3. 状態の真実は一箇所。** ファイルは意図（定義）、イベントログは実行時状態。同じ事実を二箇所に書かない。導出できる値は保存せず導出する
- **D4. 通信路を増やさない。** エージェント間の情報伝達はタスク定義・inbox・同期QAの3本のみ。新しい伝達経路が欲しくなったら request_design する
- **D5. ロジックはdaemonとExtension Packにだけ書く。** Surface（GUI/CLI/TUI固有コード）に判断を持たせない
- **D6. 依存追加より標準ライブラリと既存資産。** 追加する場合は理由を1行、タスクの本文に書く
- **D7. 人間に想起を要求しない。** すべての操作は文脈が提示する選択肢（カードのボタン、セッション内の番号付き選択肢、フッター表示）から実行できること。提示面のない操作は追加しない。ただし選択肢は自由対話への追加であり制約ではない。選択肢の提示中も通常の会話（質問・相談・選択肢外の指示）を常に受け付け、相談後は選択肢を再掲（必要なら再構成）して分岐点に戻ること
- **D8. 文脈は人の記憶に預けない。** すべての判断要求（カード・通知・セッション内の問いかけ）は、起点となったPOの指示への参照を運び、画面を遡らずそれ単体で判断できること。中断後の再開点では経緯の要約を提示すること

## 実装（I）

- **I1. 自己申告を信頼する検証を書かない。** テスト結果・ビルド結果はdaemonまたはゲートが直接実行して確認する。「passしました」という報告を根拠にしない
- **I2. エラーを握りつぶさない。** 回復不能ならタスクをfailedにして止まる。黙って続行するより、止まって台帳に残るほうが常に良い
- **I3. 外部リソースは必ず台帳に載せる。** provisionしたものはtaskIDプレフィックスで命名し、teardownは冪等に書く。掃除できないものを作らない
- **I4. TypeScript strict。** anyを書く場合はその行に理由コメントを付ける

## プロセス（P）

- **P1. スコープ外パスに触らない。** 触る必要が生じたらescalateする。「ついで」の修正は禁止
- **P2. 受け入れ条件を満たせないと判明したら、回避策を実装する前に request_design する。** 条件のほうが間違っている可能性を実装で潰さない
- **P3. Specと実態（コード・挙動）が矛盾していたら、黙ってどちらかに合わせず incident を積む。** どちらが正か決めるのは検討レイヤー
- **P4. 同種の失敗・ずるが繰り返されたら、プロンプト修正ではなく機構化（層C昇格）を提案する。** ずるは説得するものではなく、不可能にするもの
- **P5. 判断には根拠を残す。** escalate・却下・分類・QA回答には理由を1行付ける。理由のない判断は改善ループの材料にならない
