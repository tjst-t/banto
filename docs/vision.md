# Vision — Banto（番頭）

## 目的

一人のプロダクトオーナーが、AIエージェントのチームを率いて開発するための統治環境。名の由来は商家の番頭——店の切り盛り一切を担い、大事な判断だけを主人に上げる役。claude-skillsで実践してきた開発手法——タスク定義、フェーズゲート、自己監査、自己改善——を、プロンプトの遵守期待ではなく機械的構造として実装し、POの一日を「会話2枚（検討・レビュー）と判断キュー1本」に圧縮する。

## 非目的（Non-goals）

- 汎用のtmux/worktreeマネージャにはしない。それはPalmux2の領分であり、本プロダクトはガバナンスレイヤーに徹する
- チーム利用・マルチテナントは対象外。PO一人の道具として設計する
- pi本体の改造・フォーク・代替TUIは作らない。piは無改造のランタイムとして扱う
- JIRA的なプロジェクト管理ツールにはしない。階層はEpic→Taskの2段まで、Epicに状態管理を持たせない
- 汎用CI/クラウド管理基盤にはしない。評価環境はライフサイクル動詞の契約だけを定義し、実装はプロジェクトに委ねる
- インナーループ（編集・テスト・修正の回し）の品質でClaude Code等と競わない

## 価値の優先順位（衝突したときはこの順で決める）

1. **POの判断主権** — 最終判断は常に人間。エージェントは勧告・提案までとし、判断を代行しない
2. **ガバナンスの確実性** — ゲート・分類・監査が「必ず行われる」ことを構造で保証する。黙って迂回できる経路を作らない
3. **POのレビュー帯域の保護** — 希少資源はPOの注意力。タスクサイズ・WIP・UIはすべてこの帯域の配分装置として設計する
4. **エージェントの自律性** — 上位3つを侵さない範囲で、エージェントが自力で決着できる範囲を最大化する
5. **実行スループット** — 並列度や速度は最後。帯域と統治を犠牲にした高速化はしない

## 成功の姿

朝、検討セッションでinboxを片付けてタスクを2つ積む。日中は別の仕事をし、昼に「btw、どう？」と聞くだけ。夕方、アテンションキューを上から潰す——レビューで十数回の/fixを回し、1件escalateし、ADRドラフトを1本積んで終える。spawn・監査・環境の後始末を自分でやった記憶がない。そして月に一度、システムが自分の失敗パターンから自分の規則と機構を改善した形跡を、diffで確認して承認している。
