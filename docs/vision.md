# Banto — 何のためのものか

> 2026-08-20 起草。**ユーザーの説明（2026-08-20）だけを一次資料とし、既存実装・既存 ADR・既存 spec は
> 参照していない。** 旧 `docs/vision.md` とは独立に書かれている。

## ひとことで

**人に伴走し、人の助けとなるソフトウェア。** 第一の領域はソフトウェア開発。

## 解こうとしている問題

Vibe Coding で平行開発をすると、人の側が破綻する。

平行には2種類ある。**複数のプロジェクトを同時に持つこと**と、**1つのプロジェクトの中で複数の
作業や会話を同時に走らせること**。どちらも生産性のためにやるのに、どちらも人の頭の中に
「いま何がどこまで進んでいるか」を積み上げていく。**平行度を上げるほど、それを追う仕事が増える。**

**Banto の目的は平行開発そのものではなく、平行開発をしても人の認知負荷が上がらないようにすること。**
平行にできることは手段であって、目的ではない。

> この区別は運用上きわめて重要である。「ブランチを増やす機構」だけを作ると、増えたブランチを追う仕事が
> 人に返ってきて、**目的に対して逆に働く**。機構を足すときは毎回この問いに戻る——
> 「これは人が覚えておかなければならないことを、増やすのか、減らすのか」。

## 中心にある主張

### 1. 会話の構造で、平行を表す

複数プロジェクトと、プロジェクト内の平行を、**同じ1つの形**で表す。Slack のモデルを借りる
——プロジェクトが並び、その中に会話が並び、会話は返信ツリーとして分岐する。

分岐は「同じ話の続き」ではなく、**同じ文脈から出た別の試み**を表す。どの決定から派生したかが
構造として残るので、人は「いまどこにいるか」を思い出さなくてよい。

### 2. めんどくさいことは、モジュールに任せる

開発に必要なものは Banto が標準で持つ——検証環境、外部公開、サブエージェント、秘匿情報、
ブラウザ、バックログ、ファイル、Git。**各プロジェクトは Banto Way に従うだけで、
これらを自分で用意しなくてよい。**

モジュールは **AI からも人からも使える**。同じものを見て、同じものを触る。AI が開いた画面を
人が続きから触れるし、人が見ている画面について AI に相談できる。

### 3. 形式的なワークフローで、実装を回す

「ワークツリーを作る → 実装する → テストする → main にマージする」は、毎回同じ形をしている。
**Factory を作れば、あとは自動で走る。** 人は依頼と、本当に判断が要る地点だけを見る。

### 4. 開発は最初の領域にすぎない

モジュールは拡張できる。Financial Planner でも、音楽生成でも、好きなものを作って Banto から
使える。**Banto 中核は、領域の意味を知らない。**

### 5. どこからでも、同じように

Web アプリ／PWA。端末を選ばない。狭い画面でも使える。

## 成功の判定

- 5つのプロジェクトを同時に持っていても、**「いま自分を待っているもの」が1画面で分かる**
- 同じ依頼から3つの実装を試して比べることが、億劫でない
- Factory に投げた仕事について、人が思い出しておくことが何も無い
- 新しい領域のモジュールを足すときに、Banto 中核を書き換えない
- 平行度を上げても、費用が線形以上に増えない

## この文書が言っていないこと

意図的に書いていない。実装で決める。

- 中の作りかた（どのランタイム、どの言語、どんな通信）
- 何と呼ぶか（役割の名前・比喩・語彙）
- 何人で使うか（現状は ユーザー1人が前提。多人数は要件に入っていない）
