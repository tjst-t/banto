## 確かめた欠陥（重い順）

### 1. 修飾名は Shell 経路で解決できない（見えているのに繋がっていない）

`vault://aliases` は「一覧に出る名前が、そのまま使える名前」と約束し、既定の外の
秘密を `vault-infisical:npm-token` の形で出す。しかし Shell は `lookupAlias` の
答えから **implementation しか読まず**（`shell/src/host-relay-client.ts:61-75`）、
`resolveAlias` には **AI が書いた文字列をそのまま**渡す（`run-command.ts:103`）。
backend の `findAlias` は素の名前しか知らないので `not found`。

窓口自身が `vault-directory/src/server.ts:577` に
「`name` は backend での本当の名前——その先の `resolveAlias` は素の名前で
呼ぶ必要がある」と書いているのに、Shell がそれを捨てている。

**確かめた**（コードを追った）。**試験は無い**——修飾名を envSecrets に通す E2E が
存在しない空白地帯。規則13 の破れが主経路に在る。

### 2. 未設定の Vault が1本あると、AI は目録を一切読めない

`vault://aliases` は failures が1件でもあれば throw
（`vault-directory/src/server.ts:955`）。`vault-infisical` は既定の宣言に入って
おり、**未設定でも立つ**（そう直したのは 09-13）。つまり**素のインストールでは、
AI は一覧を読むたびに必ず失敗する**——vault-local に使える秘密が在っても。

しかも `requestAlias` は failures を無視して通るので、
「requestAlias は通るのに一覧は読めない」というちぐはぐを AI に見せる。

「無い」と「読めていない」を混ぜない（規則2）は正しいが、その帰結として
**読める側まで封鎖する**のは行き過ぎ。しかもエラーが指す先（設定画面）は
admin の領分で、AI には直しようが無い——**直せるのは人だけなので、
この failure は AI ではなく受信箱へ向けるのが筋**。

**確かめた**（コードを追った）。E2E では Infisical が環境変数で設定済みなので、
この経路は試験に掛かっていない。

### 3. `listAliases` は承認ゼロで全 Project の目録を返す

`listAliases` は `admin` 可視性だが **`valueFree: true`** を持つ。
そして host の中継は、**可視性による拒否をしていない**
（`host-relay-endpoint.ts:289-310`——`admin` が効くのは「canvas 由来なら
ゲートを飛ばす」と「AI に見せない」の2つだけ）。

したがって `dependsOn: [{role: "vault"}]` を宣言した任意の Module が、
**初回承認すら出さずに**全 Project の alias 名・note・グループ・紐付きを読める。
「使えない alias は名前も見せない」は**窓口の中だけの努力**で、
backend の生の口が素通りする。

`setGroupBinding`（admin）も同様に module から呼べる——こちらはゲートを通るので
人の承認1回が要るが、**通れば以後、自 Project を他 Project のグループに
紐付けられる**。つまり `resolveAlias` の制限判定そのものを書き換えられる。

**確かめた**（`vault-kit/src/server.ts:389-398, 420-428` と中継の判定順）。

### 4. 削除も「別の秘密を消す」——直したのと同じ穴が隣に残っている

窓口の `deleteAlias` は `{implementation, name}` しか受けず
（`vault-directory/src/server.ts:395`）、管理画面もそれしか送らない
（`manage-app.ts:730`）。同名が同一 Vault の2つの置き場に在るのは
**正しい状態**と決めたのに、削除は backend の既定解決に落ちる
——**一覧で選んだ行と別の秘密が消える**。

09-14 に `migrateAlias` で直したのと**同じ穴**。1箇所だけ直していた。

加えて backend の `deleteAlias` は、**見つからなくても `deleted <name>` を返す**
（`vault-kit/src/server.ts:742-749`）。`moved: false` で直したのと同型の
「何もしていないのに動いたと言う」。

**確かめた**（コードを追った）。

### 5. 「コピーする」は一度も動いたことがない

公開鍵の「コピーする」は `void navigator.clipboard?.writeText(...)`
（`manage-app.ts:664`・`request-app.ts:244`）。**sandbox iframe には
permissions policy でクリップボードが渡っていない**（外側・内側とも `allow` 属性
が無く、内側へ渡す口は在るのに誰も渡していない）。

**実ブラウザで測った**（使い捨ての E2E プローブ。人のクリックと同じ条件で）：

```
NotAllowedError / The Clipboard API has been blocked because of
a permissions policy applied to the current document.
```

`void` で投げっぱなしなので失敗は消え、成功の合図も無い。
**人は押して、何も起きず、コピーされたと思い込む。**
規則2（握りつぶさない）と規則13（見えているものは繋がっている）の両方に掛かる。
E2E も「押して例外が出ない」しか見ていない——規則14 で書いたばかりの穴と同じ形。

### 6. キャンセルした秘密鍵が画面に残る

新規登録ダイアログを開くとき `new-value` と `new-note` はクリアするが、
**`new-value-multiline` はしていない**（`manage-app.ts:545-555`）。
秘密鍵を貼って「やめる」を押すと DOM に残り、**次に開くと前回の秘密鍵が見える**。

このファイルの冒頭は「値は…この画面のどこにも残らない」と宣言している。
**確かめた**（コードを追った。1行で塞がる）。

### 8. Project の既定グループ名が UUID のまま人に出る

## 設計としての提案（まだ決めていない）

### A. 正準参照を1つ定める

`vault-local:group/name` のような、三つ組をそのまま表す形。
**すべての口がこれを受け、解決関数は kit に1つ**。素の名前は入口の糖衣に限定し、
受け取ったら即、正準形に正規化してから運ぶ。

- 既知の形（規則12）：HashiCorp Vault の mount+path、1Password の
  `op://vault/item/field`、External Secrets Operator の `{store, key}`
- 副次効果：仕様が認めている「既定を変えると名前が変わる（過去の参照が切れる）」も、
  正準形は不変なので Memory や過去ログの参照が生き残る
- `:` と `/` を alias 名から予約する必要がある（いまグループ名だけ検査していて、
  alias 名は無検査）

**これが入れば、上の 1・4 は構造的に再発しなくなる**——いまは同じ穴を
口の数だけ手で塞いでいる。

### B. 絞り込みを backend の1箇所に寄せる

`listAliases` を刻印で絞る（`{admin:true}`＝全部、`{project}`＝使えるものだけ、
刻印なし＝拒否）。変異系（delete/update/migrate/setGroupBinding/setSharedGroup）は
`{admin: true}` 限定にする。

これは**既に自分で決めた原則の適用漏れ**——「判定は、材料が在る場所で行う」。
窓口で絞っている限り、窓口以外の呼び出し元には効かない。

### C. `valueFree` は宛先の自己申告で、引数方向を見ていない

`valueFree` は**戻り値**の話だが、呼び出しには**引数**があり、引数は宛先へ流れる。
悪意ある Module が valueFree を名乗る tool を1本持てば、
**そこへの呼び出しは承認なしで通り、秘密を積んで持ち出す出口になる**。
「無指定は値を返す扱い」は呼び出し側の fail closed だが、
**宛先の申告を信じる方向は fail open**。

緩和案：valueFree の効力を**同梱 Module に限る**。第三者 Module の valueFree は
宣言として読むが承認は聞く。少なくとも `v4-security.md` の表に1行要る。

### D. 文脈の伝搬を「在籍台帳」から「相関子」へ

`ModuleCallTracker.projectFor` は、instance 単位の Module（窓口）に
**複数 Project のターンが同時に掛かると `undefined`** を返す
（`module-calls.ts:93-98`）→ 刻印が付かず fail closed で断られる。
方向は正しいが、**正常な並行利用が間欠エラーになる**——規則6 が
「間欠は機構が壊れている合図」と言うものを、機構が構造として内蔵している。

これは **context propagation** という名前のある問題（規則12）。既知の解は
「アンビエントな台帳」ではなく「呼び出しに相関子を運ばせる」。host が外側の
呼び出しごとに使い捨てトークンを発行して `_meta` で渡し、Module は中継時に
エコーし、host はトークンで台帳を引く。**トークンは host 発行なので詐称できず**、
「同じ Module 名の in-flight 集合」という曖昧さが定義から消える。

> 09-15 に記録した `vault-request-inline` の間欠（5回中1回）と同じ土壌の
> 可能性がある。**断定はしない**——次に落ちたとき、これを疑う先の1つとして見る。

### E. 窓口を「全部読んで絞るビュー」から「点の問い合わせ」へ

窓口のほぼ全操作が `crossAliases()`＝全 Vault の全列挙。Shell が秘密を1個使う
たびに全列挙が走る。`setProjectPlacement(migrate:true)` は移すごとに再列挙。
09-13 に「O(フォルダ数)」と記録したが、**列挙してから絞る形そのもの**が原因で、
フォルダ掃除では消えない。

backend に `lookupAlias(name)` を生やし、窓口はそれを扇形に投げる。
**DNS はゾーン転送ではなくクエリで引く**——窓口を DNS に例えた以上、そこまで倣う。
副次効果として B のメタデータ漏れも減る（backend は聞かれたことにしか答えない）。

### F. Infisical の「乗り」は半分

「グループ＝root 直下のフォルダ、1階層のみ」の帰結として、
**root 直下に直接置かれた秘密と、入れ子フォルダの中の秘密は存在しないことになる**
（`infisical-alias-store.ts:54-61`）。09-13 の「backend に既にある秘密は本体」
という決定が、フラット運用・入れ子運用の人には半分しか成立していない。
せめて**見えていない秘密が在りうることを管理画面で言う**（規則2）。

（未確認——コードの引用は読んだが、実データでは測っていない）

### G. `markUsed` が読みのたびに共有ストアへ書く

`resolveAlias` のたびに `markUsed` が走り、Infisical では**全フォルダ走査＋
`secretComment` 更新**（`infisical-alias-store.ts:110-114`）。
複数ホストで競合し、Infisical 側のバージョン・監査履歴を汚し、レイテンシを積む。

`lastUsedAt` は**観測データ**であり、「共有すべき真実」かは再考の余地がある
（規則4 の親戚——観測を、観測される機構の置き場に混ぜている）。

**確かめた**（呼び元 `vault-kit/src/server.ts:595`）。

## 人の UI/UX（設計の話と分けて）

### 概念の数についての結論

「グループ」「置き場」「使える範囲」「Vault 実装」の4概念は多いが、
**既定の中では3つ（名前・種別・この Project か共通か）まで隠せており、
隠し方は正しい**。減らす余地が残るのは見せる側ではなく**漏れる側**
——UUID グループ（8）、保存先セレクトの重複、backend 列の常時表示。
そこを締めれば「グループ」を人が目にするのは**既定の外に自分で出たときだけ**になる。

### 保存先セレクトが重複し、重複を選ぶと嘘を出す

`fillPlacementChoices` は「この Project」「共通」の後に**全 Vault × 全グループ**を
平坦に並べるので、既定のグループが再登場する。しかも重複側（`at:` 形式）を選ぶと
「→ 既定の置き場ではないので `vault-local:名前` のように頭に付けて引きます」と
出るが、**それが実際には既定グループなら素の名前で引ける**——画面が嘘をつく。
（未確認・レビューの指摘）

### unbound を UI で作れるのに、直す道が UI に無い

置き場変更で「移さない」を選ぶと秘密は unbound になる。事前警告は出る（良い）が、
その後**その行を移す・紐付け直す操作が画面に無い**。人にできるのは削除だけ。
「使えなくなります」と警告した先が行き止まりでは、警告の意味が半分。
行の操作に「移す…」を足せばよい（`migrateAlias` は既に在る）。

### 語彙が画面ごとに割れている（規則11）

| 概念 | 管理 Canvas | 入力欄 | 設定画面 |
|---|---|---|---|
| 預けるもの | **alias**（alias 一覧・alias を新規登録） | **秘密**（秘密を登録） | 秘密 |
| 保管する実装 | 見出しは「**実装**」／列とフィルタは「**backend**」／ダイアログは「**Vault**」 | Vault | Vault |
| 共通範囲 | 保存先は「**共通**」／範囲列は「**どこからでも**」 | 共通 | 共通 |
| 自由記述 | 「用途（**note**）」 | — | — |

とくに **`alias` は directory 設計の内部語**。会話で「秘密を登録」した人が、
管理画面の「alias 一覧」を同じものだと分かる保証が無い。
**人の画面は「秘密」と「名前」で通し、`alias` は仕様書とコードの語に留める**
のが規則11 に沿う。実装名は「Vault」に統一。
削除ダイアログの「解決できなくなる」も内部語（resolve）——「使えなくなります」でよい。

### 会話の入力欄に「断る」が無く、次の一手も書いていない

カードは「登録する」しか無い。**AI の要求を断る意思表示の口が無く**、人は無視する
しかない——答の出ないフォームが会話に残り続ける。
また登録完了後、「AI は次の返信からこの名前を使えます」のような**引き継ぎの一文が
無い**。`requestAlias` は即返る設計なので、**人が登録した事実を AI がいつ知るのかが
人には見えない**。

関連して AI 側：`requestAlias` の戻り値は「人が入れるまで待ってください」と言うが、
**ターンの途中で「待つ」手段を AI は持たない**。几帳面な AI は `vault://aliases` を
ポーリングし始める。正解は「ターンを終え、人の次の発言後に確かめる」だが、
どこにも書いていない。

### 置き場変更：不可能と分かっているのにボタンが押せる

`preview()` が衝突や「他の Project も使っているので一緒には移せません」を出しても、
**「変える」は有効なまま**。押してからエラーになる。
また sharedWith の文言は「移せません」で止まっていて、**では押すとどうなるのか**が
読めない——この画面の他の部分は全部、帰結まで書いているのに。

### そのほか

- 管理 Canvas から**共通の置き場への道標が無い**（設定画面には逆方向の案内があるのに）。
  「共通＝設定、Project＝Canvas」は**設計者の軸**（値が動くか）で、人の軸
  （「保存先を変えたい」）では同じ問い
- 空状態が「登録されている alias はまだありません」だけで、
  **この場所が何のためにあるかを言わない**
- グループを「作る」後に、作ったグループが自動選択されない
- 種別フィルタが実在しない種別まで並べる／backend が1本でも backend 列が出る

## 壊してはいけないもの（3体が揃って評価した）

- **値の面と名前の面の分離**（`resolveAlias` は caller→host→backend 直行、
  窓口はメタデータのみ）。DNS の resolver/authoritative 分離に対応する既知の形
- **グループが唯一の真実、`scope` は導出値**。09-13 の導出化で食い違いが定義上消えた
- **caller を host が刻む**（自己申告を排除）。読み経路の fail-closed は実測で本物
- **「値は AI に渡らない」を画面の言葉で毎回言う**。人が判断すべきことが、その場で読める
- **導出値をその場に出す**（保存先を選ぶと「→ この Project からだけ使えます」）。
  真実を聞き、結果を見せる順序
- **変える前に帰結を出す**（`planProjectPlacement`）
- **失敗を「無い」に化けさせない**（読めなかった backend を名指しで出す）
- **繋がってから保存する**（Infisical）
- **tool の説明文が「AI への教育」として設計されている**——`envSecrets` の
  「値ではなく alias 名を書く」、`requestAlias` の「まず一覧を見て、無いときだけ呼ぶ」。
  system prompt に頼らず tool 定義に置いたのは正しい（そこしか確実に届かない）
- **AI に金庫を選ばせない**（窓口1本・実装名の秘匿）
- **公開鍵を agent に開けた判断**——「この鍵を GitHub に登録して」が成立する
- **`handlesSecrets: true` なら全 tool に明示 visibility を要求してマウント拒否**
  ——宣言漏れを起動失敗として可視化する形は、他のサブシステムにも輸出する価値がある

## 設計レビューの結論（窓口という層は正当か）

**正当。** 「AI に金庫を選ばせない」「値の面と名前の面の分離」は、
ESO の ClusterSecretStore や DNS に対応物のある本物の問題で、
backend が2本になった実測（選ぶ先が毎回変わる）という根拠もある。
**層が1枚多いのではない。**

ただし2点：
1. いまの窓口は resolver ではなく「**全部読んでから絞るビュー**」で、
   層の薄さがまだ本物でない（提案 E）
2. `agentFacing` と REQUEST_APP を kit が backend にも配る形は、窓口一本化後の
   **死に道**を残している。「他ホストで単体動作」で説明は付くが、
   **AI 向け契約が2形あることは仕様に明記した方がよい**

**名前解決モデル**（素＝Project ＞ 共通既定、他は修飾名）は、shadowing の根拠
（本当の包含関係）が明確で筋が良い。破綻するのは
(a) 修飾名が三つ組を表せない点、(b)「既定変更で名前が変わる」点
——**どちらも正準参照（提案 A）で糖衣層に閉じ込められる**。

**既定グループ名に `projectId` を使う設計**は「UUID は衝突しない」前提だが、
Project の複製・データ移行で **projectId ごと複製される**経路ができた瞬間、
「人の意図でだけ共有が起きる」が破れる。前提として仕様に1行残す価値がある。
