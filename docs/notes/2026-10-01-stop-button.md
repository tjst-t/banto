# 停止ボタンが効かない／押したら入力に戻したい（2026-10-01）

仕様は `docs/specs/v4-frontend.md` §6.31。ここは経緯と実測。

## 報告（ユーザー）

> プロンプトを入れて、あ、しまった、間違った！ 修正したい！ と思って停止ボタンを押してもなかなか反応しません。
> 押したその瞬間止まってほしい。また、AI が何も出力していない間は、停止ボタンを押したときは、確定前、つまり
> 入力したプロンプトを編集中の状態に戻してほしい。

## 原因（コードで確かめた）

1. **画面は、host から次のイベントが届くまで止まらなかった。** 停止ボタンは assistant-ui の `cancelRun()` を
   呼ぶだけで、ランタイム（`@assistant-ui/core` の `local-thread-runtime-core.js`）は adapter の `run()` が次を
   `yield` したときに初めて「止めた」を描く。banto の adapter は `abortSignal` を見ておらず、SSE の次のイベントを
   待っていた。AI が考えている間（何も出していない間）は次が来ないので、押しても何も起きない。
2. **host のターンは止まらなかった。** 停止ボタンは「この画面が読むのをやめる」だけで、host にはターンを止める
   口が無かった（`POST /messages` の接続が切れても host は最後まで走らせる——画面を閉じても走り続けるため）。
   止めたつもりでも AI は最後まで走り、次に送った発言は前のターンの後ろに並んで待たされた。

## 実装で踏んだこと

- **止める要求が遅かった。** 最初の作りでは、ターンを始める前の下ごしらえ（Module を起こす・画面つき tool の
  一覧・モデルの一覧＝CLI を起こす）が終わるまで待っていて、HTTP の試験で 0.5〜1.1 秒かかった（ターン本体は
  4ms で止まっていた）。下ごしらえも止める合図と競わせて 5ms。
- **assistant-ui の中断の見分け。** `cancelRun()`（停止ボタン・入力欄の Escape）は `AbortError(detach=false)`、
  面を外す `detach()` は `AbortError(detach=true)`、run を重ねて始めるときは理由なしで止める。host を止めるのは
  1つ目だけ。banto 自身が会話を組み直す前に呼ぶ `cancelRun()` は `cancelRunQuietly` で見分ける。
- **Memory の「届けた」の記録を遅らせた。** `system/init` で記録していると、取り消して AI の文脈から切り落とした
  差分が二度と届かなくなる。AI の最初の返事で記録する。

## SDK の実測（サブエージェント、2026-10-01）

認証が子プロセスに通らず、モデルの返事そのものは見られていない（どのターンも「Not logged in」の合成応答で終わる）。
鎖の形は実測：

- 送った発言は、モデルの応答より前に `type=user` の行として jsonl に書かれる（parentUuid は前のターンの
  assistant の uuid）。→ 取り消すには切って resume する必要がある
- `resumeSessionAt` に前のターンの assistant の uuid を渡すと、エラーにならず、session_id は**元と同じ**まま、
  新しい発言はその uuid の直後から**同じファイルの中で枝分かれ**する（取り消した発言の行は飛ばされる）。
- `abortController.abort()` から for-await が終わるまで 408ms（画面は待たない。host は最大 3 秒まで待つ）。
- **まだ確かめていない**：本物のモデルの返事に、取り消した発言が出てこないこと（鎖の形からはそうなるはず）。
