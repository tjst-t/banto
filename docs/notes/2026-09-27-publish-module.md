# 2026-09-27 Publish の窓口と Caddy の実装を作ったときの検討

決まったことは `docs/specs/v4-modules.md` §4.3 と `docs/specs/v4-security.md` §3。ここは**なぜそうしたか・却下した案**。

## 窓口をどこで動かすか

- **案A：窓口を Project ごと（コンテナの中）にする**——Service と同じ Project なので中継の制限に当たらず、`listServices` を
  素直に呼べる。**却下**：承認の画面を出すコードがコンテナの中で動くことになり、中で root の AI がそのプロセスを
  書き換えられる（ptrace 等）。`v4-security.md` §1 が「その確認画面を AI が偽れない」ことを守るものとして挙げている。
  さらに、中の AI は同じコンテナの Module の中継の合言葉を読めるので、窓口の名で実装の `publishRoute` を直接呼べる
  ——中継の承認は初回だけで、「公開するたびに」にならない
- **案B（採用）：窓口も実装も banto 全体（banto 本体）**。代わりに、banto 全体の Module が Project ごとの Service を
  呼べない、に当たる。→ 中継の制限を「その Project のための呼び出しを処理している間は、その Project の Module を
  呼べる」に広げた。どの Project のためかは host の台帳（`callerFor`）が決め、Module は選べない。**広げたのは
  core の境界なので、ユーザーの確認待ち**として仕様に印を付けた

## 承認をどの仕組みに乗せるか

「新しい承認の仕組みを発明しない」（ユーザー決定）ので、既にあるものから選んだ：

| 仕組み | 使えるか |
|---|---|
| tool 呼び出しの承認（`canUseTool`） | `permissionMode` が `auto`（既定）や `bypassPermissions` だと聞かれない。出せるのは tool 名と引数だけで、「どこまで届くか」や実装の設定項目の入力欄を出せない |
| 中継の承認ゲート | 初回だけ（組み合わせごとに覚える）。「公開するたびに」にならない |
| Module からの elicitation | host に答えの届け先が無い（答えても Module に届かない——`apps/frontend/lib/backend/adapter.ts` の `answerable: false`） |
| **tool の画面（`import_skill` の形）** | **採用**。AI は頼むところまで、人が画面で押したときだけ実行。画面は banto 本体で動く窓口が出すので AI は偽れない。設定の入力欄も出せる |

押した後の結果は、返信用の札（`relayDeliverToThread`）で呼び出し元の Thread に届ける——AI が URL を知るため。

**食い違いが1つ残る**：`v4-security.md` §1 の②は「受信箱で承認する（Publish がこの形）」と書いているが、`import_skill` の
形は受信箱に出ない。ユーザーに上げた（規則8）。

## 「人が押した」をどこで確かめるか

窓口の `approve_publish` だけで確かめると、窓口以外の呼び出し元（将来の第三者 Module）が実装の `publishRoute` を
直接呼べる。**実装の側でも人の刻印（`{admin: true}`）を確かめる**ことにした。host は画面からの呼び出しにしか
この刻印を付けないので、AI のターンからは（窓口がどう呼ばれても）道が張れない。Vault の「紐付けを変える口は人の
刻印があるときだけ」と同じ線。

残る穴：`publish` を依存に宣言した第三者 Module の**画面**から人が何かを押すと、その間の中継には人の刻印が付く。
柵は中継の初回承認だけ。仕様の未決に置いた。

## 「待ち受けている」を信じてよいか

Service の `listening` はコンテナの中の `ss -ltnH` で、**127.0.0.1 だけで待っているものも数える**（Vite の既定がこれ）。
Caddy は host にいるので、そういうものには届かない。窓口は Service の `listening` で断り（ユーザー決定）、加えて実装が
道を張る前に **host から TCP で繋いでみる**。どちらか片方では足りない：前者だけだと届かない URL ができ、後者だけだと
「Service の登録から選ぶ」が守れない。

## アドレスの解決

- **案：コンテナの中の窓口が自分のアドレスを申告する**——却下。中の AI が別の Project のコンテナのアドレスを名乗れ、
  Caddy が他人のコンテナへ中継してしまう
- **案：Incus の DNS（`<名前>.incus`）を Caddy の行き先に書く**——Caddy が引くたびに最新になるので追随は要らない。
  却下：host のリゾルバが Incus のブリッジの dnsmasq を見ているかは環境しだいで、確かめられない
- **案：固定のアドレスをコンテナに割り当てる**——制限つきの区画で NIC の設定を変えられるか未確認。見送り
- **採用：core が Incus に毎回聞く口（`relayProjectAddress`）＋実装の突き合わせ（15 秒ごと）**。止まったコンテナの
  行き先は 503 に替える——前のアドレスを残すと、DHCP でそれを受け取った別の Project のコンテナに届く

## Caddy に触る形

- **Caddyfile を書き換えて読み込み直す**——却下。人の設定ファイルを banto が書き換えることになり、書き換えてよい範囲が
  分からない（host の Caddy は見えていない）
- **admin API で `@id` 付きのルートを足す（採用）**。まとめた `*.<ドメイン>` のルートより先に当たるよう先頭に差し込む。
  Caddyfile から読み込み直すと消えうるので、マスターを持って突き合わせで戻す（Service の systemd と同じ関係）。
  `@id` に持ち主（置き場）の印を入れる——E2E の banto と人の banto が同じ Caddy を使っても、互いの余りとして消さない

## 認証

- Caddy の `http_basic` が受けるのは bcrypt。Node の標準に bcrypt が無いので `bcryptjs`（依存なし・型同梱）を足した。
  強さは 10——Caddy は**リクエストごとに**照合する（開発サーバはページごとに数十のリクエストを出す）ので、`caddy
  hash-password` の既定の 14 は重い。`hash_cache` も付けた（Caddy の版によっては知らない項目で断られる——未確認）
- **「banto の合言葉で守る」は作らなかった**：banto の画面の合言葉は localStorage にあり Cookie ではないので、
  サブドメインへのブラウザの遷移に載らない。`forward_auth` で見るには banto にログインの口（合言葉→親ドメインの
  Cookie）が要る。繋がっていない選択肢を画面に出さない（規則13）ので、設定項目から外した

## 試験

- 偽の Caddy は admin API を **HTTP で**真似る（`PUT` の配列への差し込み・`PATCH`・`DELETE`・`/id/`）——本物の口
  （`HttpCaddyAdmin`）をそのまま通すため。本物の Caddy の検め（知らない項目で断る等）は真似ていない
- 壊して落ちることを確かめた箇所は、コミットの報告に列挙した
