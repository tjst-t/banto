## 1. やったこと（原因 → 直し方）

### 1.1 Vault の資源一覧がクラウドに行っていた【前回 A】

`vault-kit` の `resources/list` が alias を1つずつ資源として並べていたので、**資源の一覧を作るたびに
金庫に問い合わせていた**。host は設定画面・Skill 一覧・Command Palette・新しい会話の最初のターンの前に
全 Module の資源一覧を取るので、Infisical の N+1（1.4〜3.0 秒）を人のほぼすべての操作が待っていた。

- **alias ごとの資源は `resources/templates/list` に移した**（`vault://aliases/{name}`）。仕様の表記が
  もともとテンプレートの書き方で、`v4-modules.md` の別の節も「パラメータ付きの資源は templates/list」と
  決めていた。FileSystem の `file:///{path}` と同じ形。host の可視性の検査はテンプレートの前方一致を
  既に持っていた（`relay/visibility.ts`）。**読み方は変わらない**
- **Infisical の一覧は再帰1回に**（`listSecrets({ recursive: true, viewSecretValue: false })`）。
  直下のフォルダの秘密だけを数える（以前と同じ 34 件——直す前後で一覧が同じことを本番の接続で確かめた）。
  **値を取らない**のは副産物（以前は一覧のたびに全部の値が手元に届いていた）
- host の設定 Canvas・入口の一覧は、Module を**並べて**聞くようにした（以前は直列で合計を待った）。
  失敗の扱いは変えない（1本でも失敗したら理由つきで失敗）。答えない1本で永久に止まらないよう上限を付けた

**採らなかった案**：

- **Infisical の一覧を Module の中でキャッシュする**——`infisical-alias-store.ts` は「別のホストと同じ
  金庫を共有するので写しを持たない、毎回聞く」と決めている。キャッシュはこの決定に反する。
  テンプレートへ移したので、資源一覧のためにキャッシュが要る理由が無くなった
- **host で資源一覧をキャッシュし、`list_changed` で捨てる**——host と Module の契約が1つ増える。
  上の直しで遅さが消えたので要らない

**残ること**：Vault の管理画面・サブエージェントの設定・「Vault の置き場」は alias の一覧そのものを
見せるので、Infisical への往復1回（0.2〜0.9 秒、クラウドまでの距離）は残る。削るなら「毎回聞く」の決定を
見直すことになる（人の判断）。

### 1.2 会話の記録が使用量の履歴で膨らんでいた【前回 B】

- `GET /api/threads/:id` は文脈使用量を**最新の1件だけ**返す（画面はメーターの最新値しか読まない）。
  記録（`usage.recorded`）は変えていない
- Project を開くときは**開いている Thread だけ**取る。閉じた Fork は履歴で要約（件数・最初と最後の発言）
  しか見せず、全文はその会話を開いた面が取る
- ホーム（`/`）から最初の Project へ飛ぶときは、**飛ぶ前から**その Project の会話を取り始める
  （URL が変わって Project の画面が組み上がるまで約 0.4 秒、何も取っていなかった）。Project の画面は
  同じ取得を分け合う

**いったん入れて外したもの**：閉じた Fork に `?fork=` で直接来たとき、中身を取りに行く部品を
`thread-panel.tsx` に足した。ところが**足した試験は、その部品を外しても通った**——会話の面は開かれた時点で
`latest-state.ts`（同じ日に入った「最新の状況を出す」仕組み）が記録を取りに行くので、中身の無い会話も
そちらで揃っていた。**同じことの二重持ち**（規則3）なので外した。試験は「閉じた Fork に直接来ても会話が
出る」ことを守るものとして残し、`latest-state.ts` の取得を止めると落ちることを確かめた（規則1）。

### 1.3 ターンの固定費【前回 C】

- **答えが揃った時点でターンを終える**（`runner/adapter.ts`）。入力を閉じてから CLI のプロセスが終わるまで
  約 0.75 秒、その間に届くものは無い（SDK 単体で2回測って確かめた）
- 前回のノートの「決める必要があること」だった2つはこう決めた：
  - **次のターンが前の CLI の後片づけと重ならないように**：同じセッションを `resume` するターン（同じ
    Thread の続き・Fork の最初のターン）は、前の CLI が終わるのを待ってから起こす（`turn-runner.ts` の
    `cliExits`、鍵はセッション id）。続けてすぐ送った試しでは 0.47〜0.64 秒待った——人が次を打つ間に
    終わるので、ふつうは待たない
  - **終わり際に CLI が失敗したら**：答えはもう記録にあるので、host のログに書く。受信箱には出さない
    ——人がすることが無い。次の `resume` が壊れていれば、そちらが理由つきで落ちる
- **モデルの一覧は、期限が切れても前のものをすぐ返し、裏で取り直す**（stale-while-revalidate）。
  host の起動時にも一度取っておく（起動直後の最初のターンが 0.61 秒待っていた）

**触らなかったもの**：CLI の起動と MCP の初期化（約 0.9 秒）は「1ターン＝1 `query()`」（アーキ仕様
§2.3 モデルB）の費用。`getContextUsage()` の約 0.3 秒は F2 の要件。

### 1.4 設定画面の二重取得と待ち【前回 3.5】

- 設定 Canvas の一覧は、部品ごとに取っていたので**開くたびに2回**取っていた。控えを部品の外に1つ置き、
  同時の要求は1本にまとめ、前に取ったものはすぐ出して裏で取り直す
- 「広すぎる根」の警告の判定が、打っている途中の連打よけの 250 ms 待ちを**開いた最初の1回にも**掛けていた
- 会話の中の Canvas がそれぞれサンドボックスの住所を取っていた（host が起きている間は変わらない）。
  ページの中で1回にした。画面の HTML は同時に同じものを欲しがった分だけまとめる（終わったものは覚えない
  ——Module を入れ替えたら次に開いたとき新しい画面が出る）

### 1.5 新しい Project を開くとき（今回はじめて測った）

新しい Project では Module を起こす前にコンテナを作る。`incus` の CLI を十数回直列に呼んでいた。

| 区間（検証用 host） | 直す前 | 直した後 |
|---|---|---|
| 中から host への経路を待つ（DHCP） | 0.48 秒 | 0.04 秒（ブリッジから読む） |
| マウント | 1つ 0.1 秒 × 本数（直列） | 同時に来た分を PATCH 1回（約 0.16 秒） |
| コードと根のマウント（作るとき） | 2回 | PATCH 1回 |

- **経路はブリッジから読む**：ブリッジは host 自身のインターフェースなので、コンテナの NIC が繋がる
  ネットワーク名（`expanded_devices`）で host のインターフェースを引けば、DHCP を待たずに同じ値が出る。
  引けない形（ブリッジでないネットワーク）だけ、今までどおり中の経路を待つ
- **マウントは PATCH で束ねる**：`incus config device add` は1回に1つ。REST の PATCH は装置の表に差分として
  混ざる（既存の装置は残る——捨てるコンテナで確かめた）。束ごと断られたら1つずつ足し直して、悪い1つだけを
  落とす（束ねる前は1つずつ失敗していた）
- Shell はホームの写しを作ってからマウントを頼んでいたので、他の Module の束に乗り遅れていた。先に頼む順に
- 画面は Project を**作った時点で** Module の用意を頼み、Project の画面を開いたときは会話の取得と並べて頼む
  （以前は会話を取り終えてから頼んでいた）

**残ること**（1.5〜1.75 秒）：コンテナを起こす（約 0.9 秒：init・start・中で node を確かめる）と、
Module の node の起動と MCP の接続（約 0.5 秒）。削るなら**コンテナを先回りして作り置く**仕組みが要る
（Project の id で名前が決まり、根のマウントも Project ごとなので、名前の付け替えを含めて設計が要る）。
起票した。

## 2. 観測を機構の外に置いた（前回 3.8、規則4）

次に「遅い」と言われたとき、プローブを書かずに `~/banto-host.log` を grep すれば済むようにした。

- **500 ms を越えた `/api/*` の要求を1行書く**（`[host] 遅い要求: POST /api/projects/…/modules/prepare 200 1560ms`）。
  流しっぱなしの口（SSE）と、Module・Runner からの中継は数えない
- **Module が繋がった行に内訳を添える**（`filesystem connected …（1400ms：コンテナ 783ms・マウント 127ms・
  起動と接続 476ms・申告と可視性の確認 13ms）`）
- 画面側の物差し `banto/e2e/latency-probe.mjs`：初回表示・Project を順に開く・設定画面の各節を開く、を
  「押してから通信が落ち着くまで」で測り、遅い要求を並べる（`WATCH_FRONT=1` で Next.js 側の要求も出す）
