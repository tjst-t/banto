# 流れている吹き出しと記録で、文のつなぎ方を揃える（2026-09-26）

`tasks.json` の `live-text-join-differs-from-record`（同日、最新の状況を出す作業の途中で気づいて起票）。
ユーザー指示「直しておいて」。決めたことは `docs/specs/v4-frontend.md` §6.8。

## 何が違っていたか

SDK は AI の文を**ブロックごとに別の assistant メッセージ**で届ける。

| | つなぎ方 | Markdown での見え方 |
|---|---|---|
| 流れている吹き出し（`PartsAccumulator.appendText`） | 前も文なら**そのまま貼り合わせ** | 「…です。次の文…」がくっつく |
| 記録（`extractAssistantText`、リロード後はここから組み直す） | 改行1つ（`\n`） | 同じ段落（改行は空白になる） |

同じターンが、流れているときとリロード後で違って見えていた。E2E（`assistant-text-blocks.spec.ts`）を先に
書き、直す前の画面で流れている吹き出しが「最初の段落です。2つ目の段落です。」と貼り合わさることを確かめた。

## どちらに寄せるかを、測って決めた

起票のときに「本物のモデルで文だけのメッセージが続く場合を測ってから決める」と書いていた。本物の CLI の
会話の記録（`~/.claude/projects/*/*.jsonl`、298 会話）を数えた：

- 文ブロック 約 8,400、tool_use 約 25,000、thinking 約 12,900
- **道具を挟まずに文が文に続くのは 9 件だけ**（間に thinking だけを挟むものを含む）
- 9 件はどれも**別の応答**（割り込んだ入力への返事）か、**CLI が出す合成文**
  （「…asked for.」の直後に「API Error: Response stalled mid-stream…」、「API Error: 529 Overloaded…」）

→ **別々に届く文は、別々の発言**。貼り合わせると「…です。API Error: …」がくっついて読めない。
改行1つでも Markdown では同じ段落に混ざる。**どちらも段落で区切る**（`\n\n`）に揃えた。

道具を挟んだ前後の文（「調べます。」→ tool →「分かりました。」）も、記録では改行1つで同じ段落に混ざって
いた——流れているときは間に tool のカードが入るので分かれて見える。段落で区切れば、記録から組み直しても
別の段落になる。

## 直し方

- 画面：`PartsAccumulator.addTextBlock`——SDK の文ブロックはこれで足す。前も文なら `\n\n` でつなぐ
  （エラー・「この発言は送っていません」の追記は従来どおり `appendText`、元から `\n\n` 始まり）
- host：`extractAssistantText` を `\n\n` でつなぐ
- **これまでの記録（改行1つ）は書き換えない**（Event Store は追記だけ）。直した後のターンから揃う

## フル E2E で出た間欠（同じ日に直した）

段落を揃える直しのあとのフル E2E で `turn-lifecycle-abandoned` が1回落ち、繰り返すと**10回に3〜4回**
落ちた（同じ日に入れた「最新の状況を出す」の側の問題で、段落の直しとは関係なかった）。落ち方は2つ：

1. **送った発言が消える**（入力欄は空、host に届かない）。受信箱から復元した判断待ちのカード
   （`restoredJudgmentMessages`）が、受信箱が変わるたびに会話の鍵を変えて**会話を作り直していた**。
   人が Enter を押してから host に送り出すまでの間にそれが当たると、送った発言ごと会話が作り直される。
   判断待ちは流し直しの中で必ず出るので、**受信箱から描き足す道をやめた**（同じカードを描く道を1つに）。
   あわせて「会話が送っている・流している間は組み直さない」（`registerRuntimeBusy`）と、「描き始めの
   合図は、組み直した版の会話だけが取る」（`takeFollowToStart` の `build`）を入れた。前者の穴は、
   復元の道が無くても、他所のターンの終わりと送信が重なれば同じことが起きうるので塞いだ。
   後者は、フル E2E の最初の1回の落ち方（戻っても何も出ない）の説明になる
2. **走っている最中の Enter**（打った文字は残る——消えてはいない）。観測を入れて捕まえた：試験は
   「送るボタンが見える」で待っていたが、判断待ちに答えた直後の一瞬はまだ「判断待ち」の形で送るボタンが
   出ていて、その直後に走り出す。試験の待ちを「host の記録に返事が入った」（成功したときにだけ現れる
   もの——規則14）に直した

直したあと、`turn-lifecycle-abandoned` と `judgment-after-reload` を交互に12回ずつ回して **24回とも通った**。

観測を入れると落ちにくくなった（この spec だけを20回回して20回とも通った）——交互に回したときにだけ
捕まった。**間欠は、落ちる形の組み合わせで回して数える**。

さらにフル E2E で、黙って止まった接続の試験（`turn-reattach`）が1回落ちた——上の「会話が走っている間は
組み直さない」守りが自分を止めていた。流れが切れたと分かった瞬間は、まだ会話の run の後片づけの途中で
「走っている」ので、最新を出す道が引き返し、次のきっかけ（知らせの繋ぎ直し）が先に来てしまった回は
二度と来なかった。**引き返したら印を残し、会話が走り終えた瞬間にやり直す**（`onRuntimeIdle`——会話の
状態の変化で動く。ポーリングはしない）。直したあと、その場面を7回回して7回とも通り、フル E2E も
140 件通った。
