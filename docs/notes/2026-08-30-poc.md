## 計画段階で見つかった、仕様と実態の食い違い（規則8）

計画を書く前の下調べで、`@anthropic-ai/claude-agent-sdk@0.3.237` と
`@modelcontextprotocol/sdk@1.30.0` の型定義を自分で読んで確認した（規則1——
サブエージェントの報告も鵜呑みにせず、型定義を自分で grep し直した）。

**F1. §2.4 が確定事項として書いている MRTR が、出荷されている MCP SDK に無い。**
仕様（v4-architecture.md §2.4）は「`InputRequiredResult` に `elicitation/create` を
入れて返し、同じ呼び出しを `inputResponses` 付きで再送する（MRTR）」と書いているが、
`@modelcontextprotocol/sdk@1.30.0` 全体に `grep -rn "inputResponses\|InputRequiredResult"`
を掛けて **0件**。出荷されているのは実験的な **Tasks**
（`TaskStatus = "working"|"input_required"|"completed"|"failed"|"cancelled"`、
`ClientCapabilities.tasks.requests.elicitation.create`）。

**F2. host が MCP を話す口が、Agent SDK の `Query` に無い。**
`Query` インタフェースの全メンバを列挙すると、あるのは `mcpServerStatus` /
`setMcpServers` / `toggleMcpServer` / `reconnectMcpServer`（接続の**状態と制御**）
だけで、`callTool` / `mcpMessage` / `listResources` に相当するものは無い。
一方 §5.4・§5.7・§6.2 は「host が `resources/list` を読み、`_meta` を見て、
`SKILL.md` を資源として取る」前提で書かれている。

副産物：`DEFAULT_REQUEST_TIMEOUT_MSEC = 60000` を確認。「MCP の既定タイムアウトは
60秒」は v4 でも効く知見として残る。

## Step 0 実測（2026-08-30、`poc/step0-host-mcp-client/`）

F1・F2 を実機で確かめた。実 stdio Module（`module.mjs`、`@modelcontextprotocol/sdk`
の `Server` を素で使う、banto のコードに依存しない第三者 Module の代わり）を1本立て、
2つの経路から接続した。

### 実測1：Claude Code CLI が Module に advertise する capabilities

`run-claude-sdk.mjs`（Agent SDK の `query()` 経由、CLI 実体は `claude-code@2.1.237`）
が `module.mjs` に initialize したときの `clientCapabilities`：

```
{"elicitation":{"form":{}},"roots":{"listChanged":true}}
```

**`tasks` フィールドが無い。** MCP の `ClientCapabilitiesSchema` は
`tasks.requests.elicitation.create` を型として持つが、Claude Code CLI
2.1.237 はこれを advertise しない。**Tasks 経由で「後で答える」を実現する
選択肢は、この CLI では最初から成立しない**（§10-13 の実験B で使う前提が
1つ消えた——規則12「名前がある機構を使う」を試す前に、その名前の機構自体が
出荷されていないと分かった）。

**加えて `elicitation.url` も無い**（`form` のみ）。仕様が「鍵・トークン・決済は
`mode: "url"` を使う（MUST）」と定めている（§2.4）にもかかわらず、
**この CLI は url モードの capability 自体を advertise していない**。
§2.8「サブスクへのログインは shell を走らせ、URL を Elicitation の
`mode: "url"` で見せる」の前提も、ここで揺らぐ。**§10 に追加**
（下記「更新」参照）。

### 実測2：`_meta` は host 自前クライアントに届くか

`run-own-client.mjs`（`@modelcontextprotocol/sdk` の `Client` を直接使う、
banto の host を模したコード）で同じ Module に接続すると：

```json
{"name":"ping","description":"poc 疎通確認","inputSchema":{...},
 "_meta":{"jp.banto.poc/kind":"diagnostic"}}
```

**`Tool._meta` / `Resource._meta` はそのまま届く。** v3 の実測「`_meta` は
`PostToolUse` フックの `tool_response` に含まれない」（§9）とは別経路
——**フック経路の否定は、host 自前クライアント経路には及ばない**。
F2 は実証された：**host は自分の MCP クライアントを持たなければ `_meta` を読めない。**

### 実測3：2つの経路は同じプロセスに繋がるか

`run-both.mjs` で SDK 側接続と host 自前接続を同時に張り、`module.mjs` 側で
`process.pid` をログさせた：

```
[module pid=2198194] clientVersion={"name":"banto-host-poc",...}
[module pid=2198242] clientVersion={"name":"claude-code",...}
```

**pid が異なる。2本の接続は、2つの別プロセスになる。** stdio Module は
1プロセスにつき1本の stdin/stdout しか持てないため、「SDK が読む口」と
「host が読む口」を両方 stdio で持とうとすると、**同じ Module の起動が2回
必要になる。**

これは `docs/specs/v4-modules.md` §2.1 の「Environment は状態を持ち、
識別子で参照する」と正面から衝突しうる——**状態を持つ Module を stdio で
2重起動すると、2つのプロセスが別々の内部状態を持つ。** ステートレスな
Module（FileSystem・Shell・Skill 配布など、大半）では実害が無いが、
**状態を持つ Module では「AI が呼んだ側」と「host が `_meta` を読みに行った側」
で状態が食い違いうる。**

## 決めたこと

- **host は自分の MCP クライアントを持つ。** Agent SDK の `Query` には
  `resources/list` 相当の口が無いので、他に道が無い（実証済み・F2）
- **§2.4 の MRTR 記述は書き直す。** 出荷されている機構は Tasks ではなく
  （advertise されない）、実質は `onElicitation` コールバックのみ。詳細は
  実験B（item 13、Step 4）で確定させる
- **状態を持つ Module を stdio で提供する場合、host 経路と SDK 経路の
  2重起動が起きることを Module 契約に明記する。** 対処（プロセス外に状態を
  外部化する／将来 host が中継するブリッジを作る）は、item 9（Module 契約の
  ライフサイクル）の設計時に詰める。**ここでは PoC の範囲を超えるので
  §10 に事実として書き足すに留める**（規則7——スコープ外に踏み込まない）

## Step 2（item 9 の一部「マウントの記録先」、設計のみ）

18 が「層1（bootstrap config）は Event Store を開くより前に要るものに限る」と
決めたことがそのまま効いた——Module 一覧はその条件を満たさない（Module 無しでも
banto は起動する）ので、**残る選択肢は Event Store しかなかった。**

唯一の懸念だった「subprocess の起動コマンドは任意コード実行なので AI に触れる
場所に置けない」は、**「どこに置くか」と「誰が書き込めるか」を混同していた**
だけだと気づいた——Event Store 上のイベント型として記録しても、そのイベントを
追記する tool を AI に公開しなければ権限は渡らない。「AI に開くか」は独立した
決定（item 20）として残し、ここでは置き場だけを決めた。

item 9 の他のサブ項目（package type・`_meta` 接頭辞・第三者の信頼境界・
tool 選別・ライフサイクル）はまだ未決なので、item 9 全体は引き続き C 群に残る
——今回打ち消したのはマウント記録先の1点のみ。

## Step 3（item 4、実験A：Event Store read model、`poc/01-item4-event-store-read-model/`）

計画どおり、規則3 のプロパティ試験をベンチより先に書いた。書いた直後の実行で
2つの実装バグを実際に見つけた——「先に試験を書く」規律がそのまま効いた例：

1. **毒入り snapshot の (iii)（中身だけ改竄）が最初は検出できなかった。**
   `coveredBytesHash` は「ログの範囲」のハッシュで、snapshot ファイル自身の
   `state` フィールドとは無関係だった——ハッシュを持たせただけでは
   「snapshot 自身の内部整合性」は守れていなかった。`integrityHash`
   （`coveredBytesHash` と `state` を合わせてハッシュ）を追加して直した
2. **並行 append（10件）は最初「たまたま通っていた」だけだった。** 200件に
   増やしたら、直列化していない実装で `shared/jsonl.mjs` の fd キャッシュが
   実際にレースし、fd がリークすることを確認した
   （`Warning: Closing file descriptor N on garbage collection` が大量発生）。
   直列化キュー（`shared/queue.mjs`）を1本挟んで解消した

cold start の実測でも1つ、設計を訂正する発見があった——**`coveredBytesHash` を
起動時の必須検証にすると、検証コスト（O(n)）がスナップショットの短縮効果を
そのまま食い潰す**（1M件・1GBで3.4秒）。起動時チェックを軽量（version・cursor
のみ）にし、ハッシュ検証を `verifyIntegrity()`（オプトイン、遅くてよい）に
分離した。**この分離の結果、軽量な起動では snapshot の `state` 改竄を検出
できない**という制約が残る——これは隠さず仕様に書いた（§2.1）。

Gate 判定・規模別の数値は `poc/01-item4-event-store-read-model/README.md` に
まとめてある。node:sqlite との比較（物差し）は、ボトルネックが自作コード側
（ハッシュ検証）だと特定できた時点で必要性が下がったため省略した——「測らな
かった」という事実自体は隠さない。keyed projection（Arm D）も、Arm C（単一
State）だけで常駐メモリの閾値を大きく下回ったため実装しなかった。

§2.1・§10（C 群・§10.1②・§10.2）を更新。次は item 13（実験B、判断待ちを
寝かせられるか）。

## Step 4（item 13、実験B：判断待ちを寝かせられるか、`poc/02-item13-parked-elicitation/`）

4つの問いを実測した：

1. **タイムアウトで切れるか** — Module 側が指定した秒数（5秒で試験）で
   `MCP error -32001: Request timed out` が返る。既定60秒（型定義で確認済み・
   Step 0）も同じ機構で効くはず
2. **`onElicitation` が `null` を返したとき** — 型定義の警告どおり fail-closed。
   帯域外応答を送らずに `null` を返すと、何も送られず Module 側のタイムアウト
   まで pending のまま
3. **host（banto）を落として上げ直したあとに答えられるか** — **答えられない。**
   `Query.close()` を呼ぶと、pending 中の `elicitInput()` は即座に
   `{"action":"cancel"}` として強制解決された（66ms）。これが核心の発見——
   §2.4.1 が未決として残していた「呼び出し自体を保留する」という選択肢は、
   **実装として成立しない**ことが実測で確定した
4. **Tasks 経路** — Step 0 で「advertise されない」ことが確定済みなので実測は省略

合否はサーバ側（Module のログ）で見た——クライアント側の静けさ（例外が出ない）は
「寝かせられた」ことの証拠にならない（教訓13）。

決定：**`requestState` を Event Store に持つ**（`onElicitation` が呼ばれた時点で
問いの内容を記録し、呼び出し自体はタイムアウトに委ね、人の回答は次のターンへの
新しい入力として渡す）。「同じ問いが2箇所に出る問題」も、設計の選択ではなく
プロトコル上不可避な構造だと分かった——tool 呼び出しの中の Elicitation は
静かにタイムアウトし、受信箱（Event Store の記録）だけが実際の「待ち」として残る。

**副産物の食い違い**：Claude Code CLI が `elicitation.url` capability も
advertise しないと Step 0 で分かっていたが、これは §2.8 の OAuth ログイン
UI の前提（Elicitation の URL モードに乗せる）を崩す。item 13 のスコープでは
なくスコープ外なので、新しい未決事項として `item 27` を切り出した（規則7）。

§2.4・§2.4.1・§2.8・§10（item 13 打ち消し・item 27 新設・C 群・§10.1②・
§10.2）を更新。Phase 0 に要る未決は3件（3・5・6）まで減った。次は item 1
（backend Module インタフェース、ユーザー指示による実測）。

## Step 5（item 1、backend Module インタフェース、`poc/03-item1-backend-interface/`）

このマシンに Claude 以外の Agent CLI が1本も無かったので、`opencode-ai`
（npm、TypeScript製、Claude Agent SDK を一切使わない独立実装）を新規に入れた。
OpenRouter の認証情報は既にあったがクレジット不足で使えず（実測：
`AI_APICallError: Insufficient credits`）、opencode 自身がホストする無料枠
（`opencode/mimo-v2.5-free`）で実測した。

core が前提にしている7項目の可否：**streaming（未対応）・割り込み（未対応、
SIGINT で出力ごと消える）・resume（対応、キャッシュも引き継ぐ）・
usage/cost/cache（対応）・tool 可視性（対応、詳細）・elicitation（非対応、
明示的エラー "Client does not support form elicitation."）・文脈内訳
（未対応）**。elicitation は Step 4 で使った Module（`poc/02-item13-.../
module.mjs`）をそのまま MCP として繋いで確認した——沈黙ではなく Module 側の
ログにはっきりエラーが返っていた（教訓13の逆の実例）。

これで「§10.2 の観測の材料 済」が Claude backend 限定の事実であって core
全体の事実ではないことが分かった——Phase 0 は Claude backend 前提で進めれば
条件を満たせるが、この限定を仕様に書かないと後から誤読される。

§4.1・§10（item1・§10.2）を更新。**item1 自体は「決定」ではなく「実測で材料が
揃った」状態のまま残す**——インタフェースの正確な型定義はまだ設計していない。
Phase 0 の臨界パス（4・13・18・9の一部）とユーザー指示の item1、これで今回の
PoC セッションの到達目標を終える。
