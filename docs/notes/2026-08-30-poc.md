## 計画段階で見つかった、仕様と実態の食い違い（規則8）

計画を書く前の下調べで、`@anthropic-ai/claude-agent-sdk@0.3.237` と
`@modelcontextprotocol/sdk@1.30.0` の型定義を自分で読んで確認した（規則1——
サブエージェントの報告も鵜呑みにせず、型定義を自分で grep し直した）。

**F1. §2.4 が確定事項として書いている MRTR が、出荷されている MCP SDK に無い。**
仕様（v4-architecture.md §2.4）は「`InputRequiredResult` に `elicitation/create` を
入れて返し、同じ呼び出しを `inputResponses` 付きで再送する（MRTR）」と書いているが、
`@modelcontextprotocol/sdk@1.30.0` 全体に `grep -rn "inputResponses\|InputRequiredResult"`
を掛けて **0件**。出荷されているのは実験的な **Tasks**
（`TaskStatus = "working"|"input_required"|"completed"|"failed"|"cancelled"`、
`ClientCapabilities.tasks.requests.elicitation.create`）。

**F2. host が MCP を話す口が、Agent SDK の `Query` に無い。**
`Query` インタフェースの全メンバを列挙すると、あるのは `mcpServerStatus` /
`setMcpServers` / `toggleMcpServer` / `reconnectMcpServer`（接続の**状態と制御**）
だけで、`callTool` / `mcpMessage` / `listResources` に相当するものは無い。
一方 §5.4・§5.7・§6.2 は「host が `resources/list` を読み、`_meta` を見て、
`SKILL.md` を資源として取る」前提で書かれている。

副産物：`DEFAULT_REQUEST_TIMEOUT_MSEC = 60000` を確認。「MCP の既定タイムアウトは
60秒」は v4 でも効く知見として残る。

## Step 0 実測（2026-08-30、`poc/step0-host-mcp-client/`）

F1・F2 を実機で確かめた。実 stdio Module（`module.mjs`、`@modelcontextprotocol/sdk`
の `Server` を素で使う、banto のコードに依存しない第三者 Module の代わり）を1本立て、
2つの経路から接続した。

### 実測1：Claude Code CLI が Module に advertise する capabilities

`run-claude-sdk.mjs`（Agent SDK の `query()` 経由、CLI 実体は `claude-code@2.1.237`）
が `module.mjs` に initialize したときの `clientCapabilities`：

```
{"elicitation":{"form":{}},"roots":{"listChanged":true}}
```

**`tasks` フィールドが無い。** MCP の `ClientCapabilitiesSchema` は
`tasks.requests.elicitation.create` を型として持つが、Claude Code CLI
2.1.237 はこれを advertise しない。**Tasks 経由で「後で答える」を実現する
選択肢は、この CLI では最初から成立しない**（§10-13 の実験B で使う前提が
1つ消えた——規則12「名前がある機構を使う」を試す前に、その名前の機構自体が
出荷されていないと分かった）。

**加えて `elicitation.url` も無い**（`form` のみ）。仕様が「鍵・トークン・決済は
`mode: "url"` を使う（MUST）」と定めている（§2.4）にもかかわらず、
**この CLI は url モードの capability 自体を advertise していない**。
§2.8「サブスクへのログインは shell を走らせ、URL を Elicitation の
`mode: "url"` で見せる」の前提も、ここで揺らぐ。**§10 に追加**
（下記「更新」参照）。

### 実測2：`_meta` は host 自前クライアントに届くか

`run-own-client.mjs`（`@modelcontextprotocol/sdk` の `Client` を直接使う、
banto の host を模したコード）で同じ Module に接続すると：

```json
{"name":"ping","description":"poc 疎通確認","inputSchema":{...},
 "_meta":{"jp.banto.poc/kind":"diagnostic"}}
```

**`Tool._meta` / `Resource._meta` はそのまま届く。** v3 の実測「`_meta` は
`PostToolUse` フックの `tool_response` に含まれない」（§9）とは別経路
——**フック経路の否定は、host 自前クライアント経路には及ばない**。
F2 は実証された：**host は自分の MCP クライアントを持たなければ `_meta` を読めない。**

### 実測3：2つの経路は同じプロセスに繋がるか

`run-both.mjs` で SDK 側接続と host 自前接続を同時に張り、`module.mjs` 側で
`process.pid` をログさせた：

```
[module pid=2198194] clientVersion={"name":"banto-host-poc",...}
[module pid=2198242] clientVersion={"name":"claude-code",...}
```

**pid が異なる。2本の接続は、2つの別プロセスになる。** stdio Module は
1プロセスにつき1本の stdin/stdout しか持てないため、「SDK が読む口」と
「host が読む口」を両方 stdio で持とうとすると、**同じ Module の起動が2回
必要になる。**

これは `docs/specs/v4-modules.md` §2.1 の「Environment は状態を持ち、
識別子で参照する」と正面から衝突しうる——**状態を持つ Module を stdio で
2重起動すると、2つのプロセスが別々の内部状態を持つ。** ステートレスな
Module（FileSystem・Shell・Skill 配布など、大半）では実害が無いが、
**状態を持つ Module では「AI が呼んだ側」と「host が `_meta` を読みに行った側」
で状態が食い違いうる。**

## 決めたこと

- **host は自分の MCP クライアントを持つ。** Agent SDK の `Query` には
  `resources/list` 相当の口が無いので、他に道が無い（実証済み・F2）
- **§2.4 の MRTR 記述は書き直す。** 出荷されている機構は Tasks ではなく
  （advertise されない）、実質は `onElicitation` コールバックのみ。詳細は
  実験B（item 13、Step 4）で確定させる
- **状態を持つ Module を stdio で提供する場合、host 経路と SDK 経路の
  2重起動が起きることを Module 契約に明記する。** 対処（プロセス外に状態を
  外部化する／将来 host が中継するブリッジを作る）は、item 9（Module 契約の
  ライフサイクル）の設計時に詰める。**ここでは PoC の範囲を超えるので
  §10 に事実として書き足すに留める**（規則7——スコープ外に踏み込まない）
