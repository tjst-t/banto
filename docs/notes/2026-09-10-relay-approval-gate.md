# 2026-09-10 Module 間中継の承認ゲートと監査——「どの会話で聞くか」をどう決めたか

`docs/tasks.json` の `relay-approval-gate-and-audit`。設計（アーキ仕様 §2.5・
`docs/specs/v4-frontend.md`「Module 間中継の承認」）は 2026-09-02〜03 に決まっていて、
実装だけが無かった。**書いてみて初めて詰まったのは1点だけ**——承認をどの会話に
出すか。

## 詰まった点：中継の接続は Thread を知らない

Module→host の中継（`/relay`）は**プロセスごとの bearer token** で識別する。
これは「どの Module・どの Project か」を答えるが、「どのターンの仕事か」は答えない。
一方、承認カードを出す先は会話（＋受信箱）で、Thread が要る。

考えた案：

- **却下：Module に自己申告させる**（中継の引数に threadId を足す）——申告できる
  なら詐称できる。可視性を「フィルタで隠す」でなく「最初から存在しない」にした
  §10 item 9 と同じ理由で採らない。
- **却下：Thread 無しの判断待ちにする**（Project 単位のカードを受信箱にだけ出す）
  ——受信箱の行き先は「その Thread を開く」で、答える口は Thread 側のカード1箇所
  （§2.4.1、決定・2026-09-06）。Thread を持たない判断待ちは、**答える場所が無い**。
- **採った：host 自身が渡した Thread を使う。** Runner 向けの接続
  （`/agent-relay/<名前>`）は host が Thread ごとに張っているので、そこに
  `x-banto-thread-id` を付ける。代理サーバは tool ハンドラが動いている間だけ
  「この Module はこのターンの仕事をしている」と台帳（`relay/module-calls.ts`）に
  持ち、中継が来たらそれを引く。**推測はしない**——走行中の呼び出しが無い／
  同じ Module を複数のターンが同時に使っている、のどちらも「決められない」として
  **通さない**（規則2）。

  画面からの tool 呼び出し（`/api/threads/:id/ui-tool-call`）も同じ台帳に置いた
  ——Canvas の中の操作が内部で中継を使っても、承認はその会話に出る。
  Project 単位・instance 単位の口（設定画面・ランチャー）は Thread が無いので、
  そこから始まる中継は未承認だと通らない。**そのときエラーは黙らせず返す。**

## 決めた細かいこと

- **拒否は覚えない。** 覚えると「気が変わった」を戻す口が要る。次に同じ呼び出しが
  来たらもう一度聞く（閉じたまま待つ側に倒す）。
- **判断待ちに引数を載せない。** 判断待ちは Event Store に積まれる。載せるのは
  宛名（呼び出し元・宛先・種別・名前）まで——§2.5 の「値そのものは記録しない」を、
  カードの中身にもそのまま適用する。
- **人が遅れても答えは無駄にしない。** 外側の tool 呼び出しが MCP の既定60秒で
  先に諦めても、host は答えを待ち続ける。許可されれば記録に残り、AI がやり直せば
  通る。§2.4.1「後で答える」と同じ形。
- **同じ組み合わせの2本目は1本目に相乗りさせる。** カードを増やさない。

## 積み残し（規則8——黙って寄せない）

仕様（`v4-frontend.md`「Module 間中継の承認」の 2.）は「待っている間、代理サーバが
`notifications/progress` を定期送出してタイムアウトを更新する」と決めているが、
**これは入れていない**。いまは60秒で外側が失敗する（承認自体は残る）。
Shell の長時間コマンド対策と同じ経路なので、`docs/tasks.json` の
`shell-progress-keepalive` に寄せた。仕様側にも注記を書いた。

## ついでに直った／触ったところ

- `turn-runner` の SSE ループを、**SDK の続きとターン外の判断待ちのどちらが先に
  来ても流せる**形にした（`http/turn-events.ts`）。仕様が「host 自身の中継ロジックも
  判断待ちの発生源になれる」と言っていたのに、SSE には SDK 由来しか流せなかった。
- 中継トークンの identity に「宣言の名前・プロセスの名前・Project」を持たせた
  （以前は連結名1つだけで、承認の粒度に使えなかった）。

## 測った結果

- 単体6件（初回だけ聞く・2回目は聞かない・拒否・宛先の失敗も記録・ターンを
  特定できないときは通さない・並行ターンで決められないときは通さない・
  再起動後も承認が残る）
- E2E 1件（実ブラウザ・実モデル）：`bypassPermissions` でもカードが出る／
  カードに呼び出し元と宛先が見える／**値は見えない**／許可すると
  `got=<秘密の値>` が会話に出る／2回目は聞かれない／Event Store の記録が
  期待どおり。**ゲートを外すとこの試験が落ちることを確かめた**（規則1）
- E2E 26件・単体155件・typecheck 通過
