  （tool・中継の承認は入れない）。歯止めはホップ 10（およそ5往復）
- 今の作りで確かめたこと：Module→host の中継には host 自身が受ける口（relayRaiseNotice・relayDeliverToThread、host-relay-endpoint.ts）があり、
  relayEmitEvent はその並びに足せる。Service は落ちたことを unit の起動役（log-wrapper.ts）が exit.json に書くが、Module は listServices の
  ときに読むだけで見張っていない——出口の箱へ書くのは起動役にする。Project の Module は使われないと止められる作りは見当たらなかった
  （道具用のコンテナの Module だけ使うとき起こす、startsOnDemand）

## Fable のレビュー（1回目・2026-10-16）とユーザーの答え

結論は「条件つきで進めてよい」。前提が崩れていた3つ：(1) 呼び出しの印は呼び出し中しか引けず（module-calls.ts）、後から起きる出来事に
輪の止め方が効かない→始まりの印を持ち越す causedBy＋終わった呼び出しも引ける写し＋同じ自動化・同じ出来事の回数の歯止め。(2) send_message
で届く答えは #312 の「従わない」前置きが付く→判断役専用の answer_decision（元の選択肢だけ）と書き手の種類 decision。ユーザー「AI に判断
させていい。AI が分からなければ改めて人に出す」。(3) スリープ中は出来事が出ない→ユーザー「案1：待たれている Module は止めない」。
ほか：判断役が先に答えたらカードを替える、判断役の会話は承認を必ず聞く、readExternal、受信箱と同じ条件で出す、速さで断らずまとめる、
重複落としは消えない置き場、待つ自動化が無いのも受け取り済み、service.gave-up は外す、段1の4か所の一般化。外から繋いだ Module は
Fable の勧めでユーザー「最初は同梱だけ」。
