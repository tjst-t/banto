# Vault の Tool 層を仕様まで揃え、窓口（vault-directory）を作った（2026-09-12）

> **改名（同日・夕方）**：`vault-ui` → **`vault-directory`**。この文書の
> 「VaultUI」は全部これを指す。理由は下の「窓口になった」の節。

決まったことは `docs/specs/v4-modules.md` §2.1・`v4-architecture.md` §2.5・
`v4-frontend.md`・`v4-security.md` に書いた。ここには**なぜそうしたか**と、
**却下した案**を残す。

## 何を直したのか——まず、はっきりさせた

「Tool の実装が不十分で、バックエンドがどうなっているか謎」という状態だったので、
先に仕分けた。

**バックエンドは謎ではなく、むしろ一番できていた。** 実体は `SopsBackend`
（SOPS + age）1本。仕様 §2.1 D の8メソッドは全部実装済みで、OS 面の4つの穴も
2026-09-10 に塞いであり、実 `sops`/`age`/`ssh-keygen`/`ssh-agent` を叩く統合試験が
通る。足りないのは `@banto/vault-kit`（共通ライブラリ）だけ。

**穴だったのは Tool 層。** 仕様の A/B/C と実装を突き合わせて出てきたもの：

- `vault://aliases`（一覧の resource）が **`resources/list` に載っていなかった**
  ——読み取りハンドラは前から通っていたので、「動いている」ように見えていた。
  AI は URI を知らないと辿り着けないので、**A節の入口が実質存在しなかった**
- `requestAlias` が **Elicitation の答えを `.catch()` で捨てて**いた。人が断っても
  常に `REQUEST-ACCEPTED` を返すので、AI は「頼んでおいた」と思って次へ進む
- `createAlias` の**グループが `"user-secrets"` 決め打ち**。仕様で決めてある
  「Project ↔ backend グループの紐付け」が丸ごと無かった
- `scope: "project"` を受け取るのに **`projectId` を持っていなかった**
  ——「Project のもの」とは言えても、どの Project かが分からない
- `updateAlias` が無い（`AliasRegistry.update()` は**呼び出し元ゼロの死にコード**
  だった）。`note` の編集も対象の付け替えもできない
- `verify` の比較が `===`（タイミング安全でない）
- `generateKeypair` が `kind` 引数を**黙って無視**（仕様は `ssh`|`gpg`、実装は ssh 固定）

**やらなかったこと**（範囲の判断）：`migrateTo`（具体形が未設計）、gpg 鍵、
`expiresAt` の設定経路、Event Store 由来の呼び出し履歴の閲覧、`vault-kit` の抽出。

### バイナリの alias は「半分だけ直す」をやめた

`kind: "file"` でバイナリを持つ道は、いま**そもそも存在しない**
（`createAlias` は文字列しか受け取らない）ので、黙って壊れている状態ではない。
通すには vault・core の中継・Shell の3層（中継クライアントは
`content[0].text` しか運ばない）を変える必要があり、今回の目的から遠い。
**中途半端に通す道を作ると、後から base64 が書かれたファイルが出てくる**ので、
作らずに記録に留めた。

## VaultUI——仕様と実装が食い違っていた（規則8）

仕様 §2.1 C節はこう書いていた：

> VaultUI の Canvas から**直接**、host 中継経由で Vault backend の `admin` tool を
> 呼ぶ。VaultUI 自身のバックエンドはこの経路に一切登場しないので
> `handlesSecrets: false`・`in-process` のままでよい。

**この経路は実装に無い。** `module-canvas.tsx` に
「**呼び先は画面が選べない**——この Canvas がどの Module のものかで決まる」
（決定・2026-09-07）と書いてあり、Canvas は自分の Module の tool しか呼べない。

さらに、素直な迂回（VaultUI のバックエンドが `relayCallTool` で vault を呼ぶ）は
**承認ゲートで構造的に必ず止まる**。`approval-gate.ts` は「どのターンからの
呼び出しか」を `moduleCalls.threadFor()` で引くが、**画面の操作は AI のターンでは
ない**ので `kind: "none"` → 「決められないなら通さない」で拒否される。
仕様が「未決」と書いていた**`admin` tool への承認ゲートの循環**は、
UX の冗長さではなく**ハードブロック**だった。

### 採った案：VaultUI のバックエンドが中継する＋出所を台帳に持つ

- Canvas → 自分の Module（VaultUI）→ host 中継 → vault。使うのは**既にある機構だけ**
- host は `ui-tool-call` の間だけ「この Module はいま**人の画面の操作**を
  実行中」と台帳（`ModuleCallTracker`）に置く。承認の宛先はその Project の
  **Base Thread**（2026-09-07 に決めた場所と同じ。答える場所を増やさない）
- **値は VaultUI のプロセスを通過する**ので、仕様の記述を訂正して
  `handlesSecrets: true`・`isolation: "subprocess"` にした。要件 C8c の
  「扱う」の定義（Module 自身のバックエンドコードが平文を変数・引数として
  受け取ること）に、この経路は当てはまる——当てはまるなら名乗る

### 却下した案：Canvas が呼び先を選べるようにする

仕様どおりの形にはなるが、

- MCP Apps の `tools/call` に**呼び先を載せる場所が無い**ので、規約を発明する
  ことになる（規則12——名前のあるものを使う、の逆）
- 2026-09-07 の「呼び先は画面が選べない」を覆すので、どの Canvas も依存先の
  tool に手が届くようになる。境界が広がる

### 却下した案：VaultUI をやめて vault の config Canvas を厚くする

経路の問題は消えるが、`vault` は**複数の実装が名乗れる役割**なので、
横断管理をどれか1つの backend の画面に入れると、2本目を足したときに
作り直しになる。いまは backend が1本なので横断の実利はゼロだが、
**形を先に正しくしておく**ほうが安い。

## 承認ゲートの循環——ここで決着させた

実測で分かったのは、**開いた瞬間の読み取り（`listAliases`）からゲートに掛かる**
ということ。人は管理画面を開いたのに、画面は無言で止まり、答えは別の会話に出る。
聞いている内容は「あなたがいま開いた画面が、その画面の目的どおり動いてよいか」
でしかない。

**決定：出所が人の画面で、宛先の tool が `admin` 可視性なら、承認を求めない。**

- 根拠は 2026-09-07 の「画面が自分の Module を呼ぶときは承認を求めない
  ——その画面を開いたのは人」の延長。中継の1ホップは**同じ人の操作の続き**であって、
  別の意思ではない
- **緩めるのは `admin` だけ。** `module` 可視性（Vault の `resolveAlias` のような、
  値を返す部品間専用の口）は、出所が画面でも今までどおり聞く。
  さもないと、**悪意ある Module が自分の画面から admin tool を1つ生やし、
  その中で他 Module の秘密を引いてブラウザへ返す道**が、人に一度も見られずに開く
  （2026-09-10 の `v4-security.md` で塞いだ穴と同じ形）
- **聞かないが、記録はする。** Event Store の監査には
  `reason: "人が画面で行った管理操作"` として残る

却下した案：**画面起点なら中継を全部素通し。** 上の `module` 経由の持ち出しが
塞げない。「人が開いた画面」と「その画面の Module が信用できる」は別のこと。

## ついでに直った／足したもの

- **`relayListTargets`**（アーキ仕様 §2.5「role→実装の一覧は host が渡す」の実体）。
  これが無かったので、依存する Module は宛先の名前を決め打ちするしかなかった。
  **Shell はいまも `vaultModuleName ?? "vault"` と書いたまま**（今回の範囲外——
  触ると Shell の承認・閉じ込めの試験まで巻き込む）。VaultUI が先に使い、
  Shell は 2本目の vault 実装を足すときに移す
- **Project の Canvas の呼び出しも台帳に載るようにした。** Thread の Canvas は
  前から載っていたが、Project の Canvas は載っていなかった。
  **instance（banto 全体の設定）の口も同じく漏れていた**——こちらは実機で
  `generateSecret` を叩いて初めて出た（試験は Project の口しか通っていなかった）。
  instance には載せるべき Thread が無いので、**出所だけ**を記録する形にした
- **画面からの tool 呼び出しのタイムアウトを10分にした。** 中で人に聞くことが
  あるのに MCP の既定（60秒）のままだと、人が答える前に切れて、
  「画面にだけ失敗が出て、次に押すと通る」という分かりにくい形になる
- **`hostContext` に「いまどこで開かれているか」（Project の id と名前）を足した。**
  これが無いと、対象を選ぶ画面は人に UUID を打たせることになる。
  MCP Apps の `McpUiHostContext` は追加の項目を認めている（index signature、
  "for forward compatibility"）ので、新しい受け渡しの道を作らずに済んだ。
  **渡すのは開かれた場所だけ**——Project の一覧を全部渡すと、どの Canvas にも
  人の Project 名が全部見える
- **`aliases.json` の書き込みを tmp→rename ＋直列化にした。** 途中で落ちると
  中途半端な JSON が残り、**値は backend にあるのに、それを指す名前を丸ごと失う**

## いま残っている限界（記録）

- **VaultUI が名前で扱えるのは「いま開いている Project」だけ。** 他の Project の
  alias は id の先頭8文字で出る。Project の一覧を Canvas に渡さないと決めたため
  ——必要になったら、`projects` のような役割を足して依存で解決する
- **`migrateTo`（バックエンド間の移行）は未実装・未設計のまま**
- **`@banto/vault-kit` は作らなかった。** backend が1本しか無い状態で共通化すると、
  抜き出す境界を `SopsBackend` 1本から推測することになる。2本目を足すときに
  実際の差分を見て切る
- **バイナリの alias は通らない**（上記）

## 窓口になった——`vault-ui` → `vault-directory`（同日・夕方）

2本目の backend（`vault-infisical`）を既定に入れたら、
`docs/notes/2026-09-12-second-vault-backend.md` が予告した4つの割れ目が
その日のうちに実物として出た。**それを見ながら窓口を設計する**というのが選択だった。

### なぜ改名したか

`vault-ui` は**画面の Module**という名前だった。実際にやることが
「名前から在りかを引き、横断して見せる」に変わったので、名前が仕事と
合わなくなった。**`directory`（電話帳・ディレクトリサービス）**は
やっていることそのもので、初見のエンジニアが機能を想像できる（規則11）。
DNS と同じ形——**名前を引く場所と、値を取りに行く場所は別**。

### 面を3段に分けた——AI に金庫を選ばせない

割れ目①②は、どちらも「**AI に選択肢を2つ見せている**」という同じ形だった。
AI は `vault` と `vault-infisical` のどちらに預けるべきか判断する材料を持たない
——実際、E2E を走らせるたびに選ぶ先が変わった。

直し方は「AI に選ばせる材料を足す」ではなく、**選ばせない**：

```
AI が見るもの        requestAlias（窓口の1本だけ）／vault://aliases（横断した目録）
Module 間            lookupAlias（名前 → 在りか。値は返さない）
人の画面             listVaults・createAlias・generateSecret・…（窓口が横断）
```

`vault-kit` に **`agentFacing`** という1個の旗を足し、backend 側の
`requestAlias` と `vault://aliases` を `agent` から **`module` へ降格**した。
**可視性を消すのではなく降ろす**——backend 同士や窓口からは今までどおり呼べる。

横断した目録から **`implementation` を落として**いるのも同じ理由。
AI に金庫の名前を見せれば、いつか選ばせることになる。

### 値は窓口を通らない（control plane と data plane を分ける）

窓口が `resolveAlias` を代理すると、**全ての秘密が窓口のプロセスを毎回通る**
——覗ける面が1つ増え、ホップも1つ増える。なので窓口が返すのは**在りかだけ**：

```
Shell → lookupAlias("npm-token") → vault-directory   「vault-infisical にあります」
Shell → resolveAlias("npm-token") → vault-infisical   値はここから直接
```

DNS が名前を返してデータは返さないのと同じ。人の画面（`createAlias` 等）は
別で、そこは**値が窓口を通る**——だから窓口は `handlesSecrets: true` のままで、
`isolation: "subprocess"` から降ろしていない。

### 割れ目③（Shell の決め打ち）を閉じた

Shell は `deps.vaultModuleName ?? "vault"` と書いていたので、
**Infisical に預けた秘密には構造的に届かなかった**。`lookupAlias` を通す形に変えた。

- **引けなかったら止まる。** 既定の金庫へ落とすと、**別の金庫の同名を開ける**（規則2）
- **1回の `runCommand` の中だけ覚える。** `envSecrets` と `secretFiles` に
  同じ alias が出ることがあるので2度は引かないが、**跨いでは持たない**
  ——別のホストが預け先を変えたとき、古い在りかを見せることになる（規則3）
- **フルスタック試験の金庫の名前を `vault-keychain` にした**（`vault` ではなく）。
  決め打ちに戻った瞬間、ここが落ちる（規則1——試験が構造を押さえる）

### 名前は一意でなければならない

名前から在りかを引く以上、**同じ名前が2つの金庫にあると決められない**。
`createAlias` は他の金庫に同名があれば断り、`lookupAlias` は
0件でも2件でも通さない。**「たぶんこっち」で開けない**。

### 途中で出た、本物の穴——入れ子の中継が通らなかった

Shell を `lookupAlias` 経由にした瞬間、E2E がこう落ちた：

```
alias "e2e-relay-..." はどの Vault にもありません
```

**名前が無いのではなかった。** `lookupAlias` が横断に失敗した理由を
握りつぶしていて（規則2）、それを直したら真因が出た：

```
vault-directory から vault の listAliases への中継は許可されていません：
どのターンからの呼び出しか特定できません（走行中の tool 呼び出しがありません）
```

承認ゲートは「どの会話に聞くか」を台帳から引くが、**host は宛先を呼ぶ間、
宛先に在籍を立てていなかった**。1段の中継しか存在しなかったので、
今まで誰も踏んでいない。**2段目を作った私の変更が、初めて踏んだ**。

直し方は「宛先にも在籍を立て、外側の Thread と出所を継ぐ」（アーキ仕様 §2.5）。
**機構を外すと新しい単体試験が `{ kind: 'none' }` で落ちる**ことまで確かめた（規則1）。

### その先で出た、もっと大きいもの——目録が「空」に化けた

入れ子を通したら、次はこうなった：**AI が `vault://aliases` を読むと、
alias が1つも無いように見える**。

窓口は目録を出すために金庫を横断する（`listAliases`）。これは `admin` の
tool なので、**AI のターンから呼ぶと承認ゲートに掛かる**。ところが
**resource の読み取りは進捗を送れない**ので、人が60秒以内に押さなければ
MCP が切れる。そして切れた結果は、窓口の中で**失敗が落ちて空の一覧**になっていた。

つまり「配線が承認待ちで止まっている」が「まだ何も登録されていません」に
化けていた。**規則2 の同じ間違いを、今日3回した**（`lookupAlias`・
`vault://aliases`・そして最初の `crossAliases`）。いずれも
**「無い」と「読めていない」を混ぜた**もの。

#### 決めたこと：ゲートが守るのは値であって、名前ではない

（決定・2026-09-12、ユーザー選択。仕様は `v4-architecture.md` §2.5・
`v4-security.md`）

`_meta["dev.banto/valueFree"]: true` を名乗った tool は初回の承認を聞かない。
根拠は既にあった——**`relayListTargets` を承認も監査も通していない**のは、
返るのが名前と role だけだから。一覧も同じ性質である。

- **無指定は「値を返す」扱い**（fail closed）。逆にすると、第三者の Module は
  **名乗らないだけで承認をすり抜けられる**
- **緩むのは tool 単位**——`vault` の `listAliases` が緩んでも `resolveAlias` は
  今までどおり毎回聞く。単体試験でそこを押さえた
- 監査には `reason: "値を返さない口"` として残る

却下した案：**いまの挙動（毎回聞く）を正とする。** 人が押せば通るが、
**resource の読み取りには進捗の口が無い**ので、60秒を過ぎると落ちる。
「押せば通る」が成立していない。

却下した案：**窓口→backend だけ特例にする。** 実装は最小だが、
*どの Module のどの呼び出しが緩いか*が配線の名前に埋まって、
読んでも分からなくなる。**名乗らせるほうが、後から見て分かる。**

ここで2つ学んだ：

- **握りつぶしは、別の事実に化ける。**「どこにもありません」と「片方が
  読めていません」は違う話で、混ぜると**設定の壊れが「そんな名前は無い」に
  見える**。`lookupAlias` は失敗した backend を名指しで返すようにした
- **承認は経路の段数だけ出る。** 初回のターンで4枚（在りか／横断×2／値）。
  これは緩めない——「窓口が金庫を一覧してよいか」は「Shell が値を取ってよいか」
  とは別の問い。ただし**人の手数としては重い**ので、role 単位の許可など、
  粒度の見直しは別途

### 残っているもの

- **設定していない環境のノイズ**——Infisical の資格情報が無いと、受信箱に
  「繋げませんでした」が毎回1件出る。「設定が無ければ既定から外れる」形が要る
- `vault-infisical` は設定 Canvas を持たない（横断管理は窓口がやる）ので、
  資格情報の入れ方は env のみ

## 鍵ペアが通らなかった（2026-09-13、ユーザー報告）

「SSH Key Pair の生成がうまくいかない」「Secret なのか SSH 鍵ペアなのかで
選べるオプションは変わるべきなのに全然変わらない」「対象が HOME or Instance
って何？」——**3つの指摘は、4つの別々の原因だった**。全部まとめて「鍵が作れない」
に見えていたのが、切り分けを遅らせた。

### ① `hidden` が1つも効いていなかった

```css
.field { display: grid; }   /* ← [hidden] の display:none より強い */
```

`[hidden]` はブラウザ既定のスタイルなので、**クラスで `display` を指定した
瞬間に負ける**。JS は正しく `hidden` を立てていたのに、画面は何も隠れない。

- 「Vault の中で作る」を選んでも**値の入力欄が残る**
- 鍵ペアなのに**「作る強さ 32 バイト」**が出る（鍵の強さは鍵の種類が決めるのに）
- **公開鍵の欄が最初から見えている**——だから「出たけど空」になった

`[hidden] { display: none !important; }` を全ての規則より先に置いた。
**CSS で hidden を殺していないか**は、`display` を書くたびに効く話なので、
ここに書き残す。

### ② 種類ごとの違いが3箇所に散っていた

`applyAsked` と `applySource` と送信時に `if (kind === "ssh-identity")` が
別々にあり、**増やすたびに揃わなくなる形**だった。表1枚（`KINDS`）に集めた
——何を聞くかは種類が決める、が1箇所で読める。

ついでに出てきたのが**秘密鍵を1行の `input` で受けていた**こと。
`-----BEGIN OPENSSH PRIVATE KEY-----` は複数行なので、貼っても改行が落ちて
**読めない鍵が登録される**。`kind` が複数行かどうかを持つようにした。

### ③ 窓口が backend の返事を包んでいた

窓口の `generateSecret` が `{ ok: true, created: {...} }` で返していた。
**同じ入力欄が窓口にも backend にも繋がる**（kit が配る1枚）ので、
返しの形が違うと片方でしか読めない。実際、管理画面（`result.created.publicKey`）
では出て、**会話の中の入力欄（`result.publicKey`）では空**だった。
窓口は backend の返事をそのまま返す形にした（規則3）。

### ④ alias 名が公開鍵の断片になっていた（データが壊れていた）

いちばん重い。`github-ssh` として作った鍵が、一覧に
**`AAAAC3NzaC1lZDI1`** という名前で出ていた。

`InfisicalAliasStore` は「`name` は置き場から導けるので注記に書かない」
（規則3のつもり）としていたが、**その前提が成り立たない**——秘密鍵の置き場を
決めるのは `generateKeypair`（`ssh/<公開鍵の先頭16文字>`）であって、
alias 名ではない。**導出できると思い込んでいたものが、導出できなかった。**

注記に `name` を書くようにした。古い注記（`name` 無し）は置き場から読む形で
そのまま見せる——**推測で直さない**（規則2）。本物の Infisical に対する
統合試験で押さえた。

### 学び

**規則3「導出できる値を保存しない」は、導出できるときだけ成り立つ。**
「導ける」と書いたときは、**導けなくなる経路が本当に無いか**を数える。
ここでは「置き場を決めるのが誰か」が2通りあった（kit と backend）。

## 「対象」列から出てきた、もっと大きい話（2026-09-13）

ユーザーの一言は「この対象ってどういう意味だっけ」だった。調べたら
**その列は意味が半分しか無かった**。

### 分かったこと

1. **`scope` は何も制限していなかった。** `resolveAlias` は呼び出し元を
   見ていない。`listAliases` も `vault://aliases` も絞っていない。
   実測：**どの Project にも属さない接続**から窓口の目録を読んだら、
   `scope: "project"` の秘密が普通に出た
2. **`scope` が効いていたのは「どのグループに置くか」だけ。** しかも
   鍵ペアは `scope` を無視して `ssh-identities` に置くので、そこすら食い違う
3. **共通グループだけ紐付けが無かった**（`const INSTANCE_GROUP = "instance"`）。
   Project 側は人が紐付けるのに、共通側は名前が固定。つまり**同じ backend を
   指した2台目の banto が現れると、人が何も割り当てていないのに共有される**
   ——仕様が唯一避けたかった「自動的に共有が起きる」形が、ここにだけ残っていた

### 決めたこと：グループを唯一の真実にする

（仕様は `v4-modules.md` §2.1・`v4-architecture.md` §2.5・`v4-security.md`）

```
居るグループが 共通グループ            → どの Project からでも
居るグループが Project に紐付いている  → その Project（複数可）
どちらでもない                        → 誰も使えない（unbound）
```

`scope`/`projectId` を alias に保存するのをやめた。**二重管理をやめたら、
食い違いが定義上ありえなくなる**（規則3）。

派生して決まったこと：

- **置き場を決めるのは呼び出し側**。`generateKeypair(kind, path)` にして、
  backend が勝手な場所を選べなくした。**先日の「alias 名が公開鍵に化けた」
  不具合と同じ根**（置き場を決める主体が2つあった）が、ここで消えた
- **`updateAlias` で使える範囲を変えられない。** 以前は `scope` を付け替え
  られたが、**値は元のグループに残ったまま**で表示だけが変わる嘘だった
- **共通グループも紐付けにする**（`setSharedGroup`）。backend ごとに1つ

### 制限の効かせ方：host が刻む

**Module に自己申告させない。** host が中継のたびに
`_meta["dev.banto/caller"]` を刻む（`{project}` か `{admin: true}`）。

実装で触ったのは**4行だけ**——AI の代理（tool 呼び出し・resource 読み取り）と
Module 間中継（同じ2つ）。**どれも入れ子の中継を通したときに触った場所と同じ**で、
台帳（`ModuleCallTracker`）に projectId を1つ足すだけで済んだ。

- **刻印が無ければ値を渡さない**（fail closed）。既定を「全部使える」にすると、
  名乗らないだけで制限をすり抜けられる
- **窓口も絞る。** backend の `listAliases` は人の管理面なので全部返す
  ——窓口がそれをそのまま AI に渡したら、backend 側の制限は素通りだった。
  **横断して見せるのが窓口の仕事なら、絞るのも窓口の仕事**（ここは実装中に
  気づいた穴で、試験を書くまで見えていなかった）

### 互換性のために確かめたこと

- `_meta` は MCP が拡張のために用意している場所で、**知らない Module は無視する**
  （`dev.banto/visibility` と同じ）。tool の引数スキーマは変えていない
- `resolveAlias` を呼んでいるのは **Shell 1つだけ**（数えた）。**Shell は無改修**
  ——刻むのは host なので

### 残っている限界

- **`ssh-identities` に居る既存の鍵は `unbound` になる**（＝誰も使えない）。
  人の画面には出るので移せるが、**移す道具（`migrateTo`）はまだ無い**ので
  作り直しになる。実機には0件だった

## 同じ不具合が、もう1枚の画面で出た（2026-09-13）

「fullscreen の Vault 管理画面で作ろうとすると、ssh key pair なのに
うまく選択肢が出てない」——**前日に直したはずのもの**が、別の画面で生きていた。

原因は2つとも同じ形：

1. **CSS がまた `hidden` を殺していた。** `manage-app.ts` にも
   `.field { display: grid }` があり、`[hidden]` に勝つ。**同じ書き方の画面が
   2枚あるので、同じ罠が2回ある**
2. **種別ごとの規則を2箇所に直書きしていた。** 入力欄（`request-app.ts`）で
   直した表が、管理画面には無い

**直したのは症状ではなく、2箇所あることのほう**：規則を `vault-kit/kind-rules.ts`
の1枚にして、両画面が**同じ JS 断片を埋め込む**形にした。

**そして「1箇所であること」を機械で押さえた**——両画面の HTML に
`const ALIAS_KIND_RULES =` と `kindRule(` が入っていること、`[hidden]` を
効かせる CSS があること。直書きに戻したら落ちる。

### 学び

**「同じものが2枚ある」を見つけたら、片方を直す前に数える。**
今回は「画面が2枚」に気づかないまま1枚だけ直し、ユーザーにもう一度
同じ報告をさせてしまった。`grep` で `.field {` を引けば2箇所出ていた
——規則15 の1番（契約を変える前に、壊れる先を grep で列挙する）は、
**直すときにも同じだけ効く**。

## 公開鍵を、人にも AI にも出せるようにした（2026-09-13）

「ssh の公開鍵は gui で表示とコピーができるようにして。あと公開鍵は ai に
見せてもいいはず。その口は作らない？」——どちらもそのとおりだった。

**公開鍵は `generateSecret` の戻りに1回出るだけ**で、画面を閉じたら二度と
見られなかった。相手方（GitHub 等）に登録するためのものなのに、である。

### 決めたこと

- **保存しない。** 秘密鍵から `ssh-keygen -y` で導く（規則3——導出できる値を
  持たない。規則12——名前のある解を使う）。平文の鍵は 0700 の一時ディレクトリに
  だけ置き、`finally` で消す（`loadIntoAgent` と同じ手当て）
- **backend の `getPublicKey` は `module` ＋ `valueFree`。** 秘密鍵は通らない
  ので、中継の初回承認は聞かない
- **窓口の `getPublicKey` は `agent`。** AI が読めないと「この鍵を GitHub に
  登録して」と頼めず、鍵を作った意味が薄い。**使える範囲の判定は他の口と揃える**
- **画面は一覧の行から開ける。** 鍵のときだけ「公開鍵」ボタンが出る

### 途中で出た、刻印の抜け（記録）

管理画面から公開鍵を読もうとしたら **「どの Vault にもありません」** になった。
原因は **画面 API だけ `_meta` を刻んでいなかった**こと。

前日に「刻む場所は4つ」と数えたが、それは**中継と AI の代理だけ**だった。
**画面 API は host が Module と直接話すので、中継を通らない**——数え落とし。
`listAliases` は呼び出し元を見ないので動いていて、**呼び出し元を見る口を
足した瞬間に初めて露見した**。

受け手が fail closed で止まったのは正しい挙動で、**間違っていたのは
「経路を数えたつもり」のほう**。規則15 の1番（壊れる先を grep で列挙）を、
**経路の数え上げにも使う**——`client.callTool(` を grep すれば5箇所出ていた。
