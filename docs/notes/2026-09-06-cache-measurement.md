# キャッシュは落ちるのか——本実装で測った（Phase 1）

2026-09-06。`docs/tasks.json` の `phase1-cache-measurement`。
Phase 1 の完了条件「**ツールを足してもキャッシュが落ちない（数値で確認）**」。

## なぜ測るか

banto の設計は「Module をいくらでも足せる」が前提。もし **Module（tool）を足すたびに
キャッシュが落ちて全部読み直しになる**なら、その前提が崩れる。

8月30日に PoC で測ってはいた（tool 0/8/40/120 で使い回しが一定）が、**捨てる前提の
コードでの数字**。いまの banto は system prompt を自分で組み立て、毎ターン
その回だけの情報を添え、Memory を届けている——**「毎ターン何かを添える」は
キャッシュにとって一番危ない形**なので、本実装で測り直した。

## 測る前に：数字を記録していなかった

キャッシュの内訳（使い回し＝`cache_read`／覚え直し＝`cache_creation`）は
Runner の応答に来ているのに**捨てていた**。文脈サイズ（`contextUsage`）は
「どれだけ積んだか」であって「いくらで読めたか」ではない。
`usage.recorded` に `apiUsage` として**そのまま**残すようにした（決定・2026-09-06）。
計測のためだけでなく、あとから「あのターンはなぜ高かったのか」を追える記録になる。

|---|---|---|---|

## 分かったこと

### 1. Module を足してもキャッシュは落ちない（完了条件を満たす）

**B-1**：使い回し 3,331 を保ったまま、覚え直しは 875。普通のターンの覚え直しが
114 なので、**新しい道具の定義を覚え直したぶんは 760 程度**。次のターン（B-2）は
すぐ通常（115）に戻る。**全部読み直し（使い回し 0）にはならない。**

### 2. 「3,331」は固定部分の大きさ

B-1 と C-2 に同じ 3,331 が出る。これは **system prompt ＋ 道具の定義**という、
会話に依らない先頭部分。会話が伸びるとその上に積み上がり（3,859→4,206→4,321）、
Clear すると会話部分だけが落ちて、また固定部分から始まる。

### 3. Clear は思ったより安い

**C-2**：Clear した直後でも使い回し 3,331。**キャッシュは会話（セッション）ではなく
中身に紐づく**ので、新しいセッションでも先頭が同じなら効く。
「畳むと全部読み直し」ではない。

### 4. 走行中の Memory / Global Memory 追加は、キャッシュを壊さない

**C-1・D-1** とも落ちていない。Memory は仕様どおり**ターンに添えて**届けているので
先頭が変わらない（§2.3）。Global Memory は system prompt に入るが、
**resume 中のセッションでは反映されない**——だから落ちない。

### 5. 落ちる操作は実在する（測定の感度の確認）

**E-1：使い回し 0、覚え直し 3,827。** Global Memory を足したあと Clear して
新しいセッションを始めると、**先頭が変わるので全部覚え直し**になる。
「落ちない」ばかり並べても測定が壊れている可能性を排除できない（規則1）ので、
**実際に落ちる筋書きを1つ通した**。これで上の「落ちなかった」に意味が出る。

## 副産物：Global Memory は走行中の会話に届かない

D-1 と E-1 の差から分かったこと——**resume 中のセッションでは system prompt が
固定されており、後から Global Memory を足しても、その Thread の会話には届かない**
（次に Clear するか、新しい Thread を始めたときに初めて効く）。

Project の Memory は「確定より後に増えた分はターンに添えて届ける」という仕組みが
あるが（§2.3）、**Global Memory には同じ仕組みが無い**。
`docs/tasks.json` の `global-memory-mid-thread-delivery` として起票した。
