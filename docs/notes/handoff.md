## 決定: Kobo独立プロセス vs Bantoへのプラグイン組み込み（2026-07-28、PO裁定）

**Koboを独立ソフトウェア（別プロセス、HTTP API＋WebSocket）のまま維持し、Bantoへの組み込み（in-process plugin化）はしない。** 番頭の推奨をPOが承認して確定（ADR-0010 §6に反映済み）。

- 既にKoboは実装済み・331テスト通過。プラグイン化は主にデプロイ形態の変更で、機能的な必要に迫られたものではない。
- Worker Pool（pi職人）は既に別プロセスであり、Koboへは元々ネットワーク越しにアクセスする必要がある。番頭だけをin-process化しても、職人・GUI/CLI向けのHTTP/WS面は結局残さざるを得ず、「番頭だけ特別な内部経路を持つ」という一貫性のない状態になる（ADR-0010 §1が既に「番頭はKobo状態をTool経由の公開クエリでしか読めない」と規定しており、in-process化はこれと整合しない）。
- Koboが独立GUI・APIを持つことで、PO直操作と番頭経由操作が同じAPIを共有できる（ADR-0010 §2の前提）。in-process化するとこの独立性が失われる。
- Koboの systemd常駐によるライフサイクル独立性（番頭・ハーネスの再起動やクラッシュから統治状態が守られる）は、ハーネス差し替え可能性（ADR-0010 §3）とも相性が良い。プラグイン化するとKoboの寿命が特定ハーネスプロセスに縛られる。

**「プラグイン的に感じられる部分」**は、キャンバスのGUIプラグインカタログ（ADR-0010 §5・banto-shellプロトタイプで実装済み）で既に達成できている——Koboの個別GUI要素（キュー・ボード）をカタログエントリとして番頭が呼び出す、という体験上の統合感は、Koboのコアエンジン自体をin-process化しなくても得られる。

**PO条件付き承認（2026-07-28）：デプロイ・運用は一体的な体験にすること。** 独立プロセスであることが利用者（PO）の手間として露出してはならない——単一のインストール/起動手順、Kobo起動状態のBanto側からの可視化（Settings › Kobo接続で先取り済み）、バージョン整合性チェック等。**具体的な実現方法は未決**（単一systemdユニットで両方管理するか、Banto起動時にKoboの存在確認〜起動まで面倒を見るか等）。ADR-0010 §未決事項に追記済み。実装フェーズで検討する。

## UIプロトタイプ 五次改訂（2026-07-28、PO五次フィードバック）: 下部欠け不具合の真因修正・タブの見た目刷新

- **チャット下部が隠れる不具合の真因を特定・修正**: `--topbar-h`（画面の残り高さを計算する基準）が`.shell-topbar`だけを実測しており、その上にある`.proto-strip`（プロトタイプ注記バナー）の高さを引き忘れていた。バナー分（約30px）だけ`.shell-body`の計算上の高さが実際より高くなり、`body{overflow:hidden}`によって下端（ちょうどチャット入力欄の高さ分）が切れていた——1周目の`100vh`→`100dvh`→実測値という修正はすべてこの見落としを直しておらず、無意味だった。

  - 選択中のタブは上端にアクセントカラーの細いバーを表示。
  - **キャンバスタブの「見苦しさ」の実体**: 選択中タブの背景色と、その下のコンテンツ領域の背景色が違う色（`--surface`と`--bg`）になっており、タブが浮いて見えていた。コンテンツ領域の背景をタブと揃えて解消。

## UIプロトタイプ 六次改訂（2026-07-28、PO六次フィードバック）: モバイルヘッダの破綻・タブの横スクロール廃止

PO報告のスクリーンショット（モバイル幅）で、5次改訂のモバイルヘッダ（2行折返し）が破綻していることが判明——セッションタブが異常に巨大化、「＋新しいセッション」ボタンが謎の点線円に、キャンバスタブ列にOSネイティブのスクロールバー（矢印付き）が出て「グチャグチャ」な見た目になっていた。

POの指示: (1) 会話タブ（セッションタブ）の見た目をもっと整える、(2) モバイルではタブ列を出さず素直にドロップダウンメニューにする、(3) キャンバスタブ・セッションタブとも、横スクロールはやめて「収まらない分だけ▾で選べる」方式に統一する。

- **横スクロールを全廃し、「収まらない分だけ▾に収納」する共通ロジックを実装**: `computeOverflow()`（実測して収まる分だけ表示、はみ出す分を`display:none`にして返す）を新設。セッションタブ・キャンバスタブの両方に適用。
  - **▾は「収まらないときだけ」出る**（PO指定どおり）。空いていれば▾自体が非表示になる。

## UIプロトタイプ 十一次改訂（2026-07-28、PO十一次フィードバック）: タブは選択対象と「くっついている」必要がある

POからYahoo News／SmartNewsのタブUIを参照例に提示された指摘: 隙間を消しただけでは不十分——**アクティブなタブは、それが制御するコンテンツ領域と地続き（同色・境界線なし）でなければならない**。隙間（十次改訂で対処）と、境界線そのもの（今回）は別の問題だった。

- **原因**: `.canvas-head`自身が`border-bottom: 1px solid var(--line)`を持っており、タブ側の「アクティブタブが罫線を隠す」演出（`.canvas-tabstrip`の2px罫線を消す仕組み）とは別に、ヘッダ全幅にわたる1pxの境界線がそのまま残っていた。すきまはなくなっても、線一本挟まっている限り「くっついて」は見えない。
- **修正**: `.canvas-head`の`border-bottom`を削除。ヘッダの背景（`--surface`）とコンテンツ上端（`.canvas-tab-content`も`--surface`）が完全に同色になり、アクティブなタブの下端から中身まで、遮るものなく地続きになった。タブ以外の領域（カタログボタン側）に境界線がなくなった副作用は、参照例（タブ専用のバー）と違いカタログボタンが同じ行に同居しているための妥協点として許容。
- 実機確認済み（palmux-browser、デスクトップ幅）。アクティブタブとコンテンツの接続・空状態（GUI未オープン時）の見え方の両方を確認。

## UIプロトタイプ 十二次改訂（2026-07-28、PO十二次フィードバック）: 空状態でも太い線が残っていた

十一次改訂の確認は不十分だった——空状態のスクリーンショットで薄い線に見えたものを「問題なし」と流してしまったが、POが拡大した実際のスクリーンショットでは明確に太い線として残っていた（I1: 自己申告に頼らず直接確認する、を徹底できていなかった）。

- **原因**: `#canvasTabstrip`はヘッダ内に常設された要素で、GUIが1つも開いていない空状態でも常にDOMに存在する。`.canvas-tabstrip`の`border-bottom: 2px solid var(--line-strong)`（タブが罫線の上に乗るための基準線）は、中身が空（`innerHTML=''`）のときも関係なく描画され続けていた——「タブが罫線を隠す」演出は、そもそも罫線を出す条件を「タブがあるとき」に絞れていなかった。
- **修正**: `.canvas-tabstrip:not(:empty) { border-bottom: ... }` とし、タブが1つも無い（要素が空）ときは罫線自体を出さないようにした。CSSの`:empty`疑似クラスだけで判定でき、JS側の変更は不要。
- 実機確認済み（palmux-browser、デスクトップ幅）。空状態で線が完全に消えたこと、GUIを開いたときに基準線とアクティブタブの地続き表現が変わらず機能することの両方をあらためて確認。

### 追ったら、既定が 60 秒だった

`loamium/task-0002` の `verify_failed:a3(exit=124)`。`a3` の verify は文字通り **`npm test`**
（vitest 1939件）。そして **`verifyTimeoutMs` は daemon から一度も渡されておらず、常に既定の
60 秒**だった——設定する術も無かった。

**同じ問いは既に裁定済みだった。** 検証環境側は 2026-08-01 に「既定30秒では `npm test` が
途中で切れていた」として既定10分・上限60分に直している（spec-environment §5.1）。
**ゲート側だけ取り残されていた**——同じ穴を2度掘っている。

### 直したこと

1. **層B設定**（`meta/config.yaml` の `limits.verify_timeout_minutes`）。既定10分・上限60分
   ——**数字は spec-environment と揃えた**（同じ問いに2つの答えを作らない）。
   上限超えは黙って丸めず断る
2. **時間切れは上限まで延ばして1回やり直す**。task-0070 の監査の事故と同じ形で、
   **事故はやり直し、判断はやり直さない**：

   | 落ち方 | 扱い |
   |---|---|
   | `exit 124`（時間切れ） | **事故**。上限まで延ばして1回やり直す |
   | `exit ≠ 0, ≠ 124`（テストが落ちた） | **判断**。やり直さない |

   **倍ではなく上限まで一気に延ばす**（最初は倍にしていた）。やり直しは1回きりなので、
   倍にしてまた足りなければ時間を使って何も分からない。上限まで出したうえで駄目なら
   「**この検証は許された範囲では終わらない**」という確かな答えになる——それが番頭に
   渡したい signal。副産物として、テストが時間に対して頑健になった
3. **理由を `verify_timeout:a1(20分待っても終わらず・延長済み）` に**。`verify_failed` と
   混ぜない——`exit=124` のままだと「テストが落ちた」と読める
4. **知らせが止まり方ごとに手を変える**。「直して積み直すか畳むか」だけだと、時間切れの
   ときに**落ちてもいないテストを直そうとする**。時間切れ／監査の事故／スコープ違反で分けた
