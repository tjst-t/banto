## 決定: Kobo独立プロセス vs Bantoへのプラグイン組み込み（2026-07-28、PO裁定）

**Koboを独立ソフトウェア（別プロセス、HTTP API＋WebSocket）のまま維持し、Bantoへの組み込み（in-process plugin化）はしない。** 番頭の推奨をPOが承認して確定（ADR-0010 §6に反映済み）。

- 既にKoboは実装済み・331テスト通過。プラグイン化は主にデプロイ形態の変更で、機能的な必要に迫られたものではない。
- Worker Pool（pi職人）は既に別プロセスであり、Koboへは元々ネットワーク越しにアクセスする必要がある。番頭だけをin-process化しても、職人・GUI/CLI向けのHTTP/WS面は結局残さざるを得ず、「番頭だけ特別な内部経路を持つ」という一貫性のない状態になる（ADR-0010 §1が既に「番頭はKobo状態をTool経由の公開クエリでしか読めない」と規定しており、in-process化はこれと整合しない）。
- Koboが独立GUI・APIを持つことで、PO直操作と番頭経由操作が同じAPIを共有できる（ADR-0010 §2の前提）。in-process化するとこの独立性が失われる。
- Koboの systemd常駐によるライフサイクル独立性（番頭・ハーネスの再起動やクラッシュから統治状態が守られる）は、ハーネス差し替え可能性（ADR-0010 §3）とも相性が良い。プラグイン化するとKoboの寿命が特定ハーネスプロセスに縛られる。

**「プラグイン的に感じられる部分」**は、キャンバスのGUIプラグインカタログ（ADR-0010 §5・banto-shellプロトタイプで実装済み）で既に達成できている——Koboの個別GUI要素（キュー・ボード）をカタログエントリとして番頭が呼び出す、という体験上の統合感は、Koboのコアエンジン自体をin-process化しなくても得られる。

**PO条件付き承認（2026-07-28）：デプロイ・運用は一体的な体験にすること。** 独立プロセスであることが利用者（PO）の手間として露出してはならない——単一のインストール/起動手順、Kobo起動状態のBanto側からの可視化（Settings › Kobo接続で先取り済み）、バージョン整合性チェック等。**具体的な実現方法は未決**（単一systemdユニットで両方管理するか、Banto起動時にKoboの存在確認〜起動まで面倒を見るか等）。ADR-0010 §未決事項に追記済み。実装フェーズで検討する。

## UIプロトタイプ 五次改訂（2026-07-28、PO五次フィードバック）: 下部欠け不具合の真因修正・タブの見た目刷新

- **チャット下部が隠れる不具合の真因を特定・修正**: `--topbar-h`（画面の残り高さを計算する基準）が`.shell-topbar`だけを実測しており、その上にある`.proto-strip`（プロトタイプ注記バナー）の高さを引き忘れていた。バナー分（約30px）だけ`.shell-body`の計算上の高さが実際より高くなり、`body{overflow:hidden}`によって下端（ちょうどチャット入力欄の高さ分）が切れていた——1周目の`100vh`→`100dvh`→実測値という修正はすべてこの見落としを直しておらず、無意味だった。

  - 選択中のタブは上端にアクセントカラーの細いバーを表示。
  - **キャンバスタブの「見苦しさ」の実体**: 選択中タブの背景色と、その下のコンテンツ領域の背景色が違う色（`--surface`と`--bg`）になっており、タブが浮いて見えていた。コンテンツ領域の背景をタブと揃えて解消。

## UIプロトタイプ 六次改訂（2026-07-28、PO六次フィードバック）: モバイルヘッダの破綻・タブの横スクロール廃止

PO報告のスクリーンショット（モバイル幅）で、5次改訂のモバイルヘッダ（2行折返し）が破綻していることが判明——セッションタブが異常に巨大化、「＋新しいセッション」ボタンが謎の点線円に、キャンバスタブ列にOSネイティブのスクロールバー（矢印付き）が出て「グチャグチャ」な見た目になっていた。

POの指示: (1) 会話タブ（セッションタブ）の見た目をもっと整える、(2) モバイルではタブ列を出さず素直にドロップダウンメニューにする、(3) キャンバスタブ・セッションタブとも、横スクロールはやめて「収まらない分だけ▾で選べる」方式に統一する。

- **横スクロールを全廃し、「収まらない分だけ▾に収納」する共通ロジックを実装**: `computeOverflow()`（実測して収まる分だけ表示、はみ出す分を`display:none`にして返す）を新設。セッションタブ・キャンバスタブの両方に適用。
  - **▾は「収まらないときだけ」出る**（PO指定どおり）。空いていれば▾自体が非表示になる。

## UIプロトタイプ 十一次改訂（2026-07-28、PO十一次フィードバック）: タブは選択対象と「くっついている」必要がある

POからYahoo News／SmartNewsのタブUIを参照例に提示された指摘: 隙間を消しただけでは不十分——**アクティブなタブは、それが制御するコンテンツ領域と地続き（同色・境界線なし）でなければならない**。隙間（十次改訂で対処）と、境界線そのもの（今回）は別の問題だった。

- **原因**: `.canvas-head`自身が`border-bottom: 1px solid var(--line)`を持っており、タブ側の「アクティブタブが罫線を隠す」演出（`.canvas-tabstrip`の2px罫線を消す仕組み）とは別に、ヘッダ全幅にわたる1pxの境界線がそのまま残っていた。すきまはなくなっても、線一本挟まっている限り「くっついて」は見えない。
- **修正**: `.canvas-head`の`border-bottom`を削除。ヘッダの背景（`--surface`）とコンテンツ上端（`.canvas-tab-content`も`--surface`）が完全に同色になり、アクティブなタブの下端から中身まで、遮るものなく地続きになった。タブ以外の領域（カタログボタン側）に境界線がなくなった副作用は、参照例（タブ専用のバー）と違いカタログボタンが同じ行に同居しているための妥協点として許容。
- 実機確認済み（palmux-browser、デスクトップ幅）。アクティブタブとコンテンツの接続・空状態（GUI未オープン時）の見え方の両方を確認。

## UIプロトタイプ 十二次改訂（2026-07-28、PO十二次フィードバック）: 空状態でも太い線が残っていた

十一次改訂の確認は不十分だった——空状態のスクリーンショットで薄い線に見えたものを「問題なし」と流してしまったが、POが拡大した実際のスクリーンショットでは明確に太い線として残っていた（I1: 自己申告に頼らず直接確認する、を徹底できていなかった）。

- **原因**: `#canvasTabstrip`はヘッダ内に常設された要素で、GUIが1つも開いていない空状態でも常にDOMに存在する。`.canvas-tabstrip`の`border-bottom: 2px solid var(--line-strong)`（タブが罫線の上に乗るための基準線）は、中身が空（`innerHTML=''`）のときも関係なく描画され続けていた——「タブが罫線を隠す」演出は、そもそも罫線を出す条件を「タブがあるとき」に絞れていなかった。
- **修正**: `.canvas-tabstrip:not(:empty) { border-bottom: ... }` とし、タブが1つも無い（要素が空）ときは罫線自体を出さないようにした。CSSの`:empty`疑似クラスだけで判定でき、JS側の変更は不要。
- 実機確認済み（palmux-browser、デスクトップ幅）。空状態で線が完全に消えたこと、GUIを開いたときに基準線とアクティブタブの地続き表現が変わらず機能することの両方をあらためて確認。

## セッション更新（2026-08-07、「まれに落ちる試験」は機構の壊れだった・task-0072 / inc-0031）

### 何が起きていたか

職人を起こすのは非同期で、`closeWorkerFor` と `worker.delegate_toolkit` の HTTP 往復を挟む。
その間にタスクが先へ進む（あるいは終端に着く）と、**出来上がった職人を誰も畳まない**

実際の形：2回目の監査不通過でタスクが `failed` になったあと、1回目の不通過で頼んでいた
rework の職人が**遅れて生まれ**、工房の安全弁（既定15分）まで走り続けていた。

```

残っている: ["capture-task-double-fail-1:rework-1786096500516-614089"]
```

**20秒待っても畳まれない**——遅いのではなく、誰も畳まないから。

### なぜ「テストが遅い」と読まれ続けたか（inc-0031）

混んでいるときだけ出るので、単体では通る。それを「テストの都合」の証拠として読み、
**待ち時間を延ばす直しが2回入っていた**（テスト内のコメントがそれを残している）。
待ちを延ばすほど頻度が下がり、余計に機構の問題に見えなくなる。

**まれに落ちる試験は、機構が壊れている合図として扱う**のが正しかった。P6（同一スコープで

`keepWorkerIfStillWanted`：職人が出来上がった直後に**帳簿を読み直し**、その役目を要る状態

その場で畳んで、帳簿には載せずに戻る。

- **帳簿に載せない**のは誰も使っていない職人だから。工房のログには残るので事実は失われない

**画面の骨格が変わった。** 会話のタブは無くなり、**プロジェクトごとに幹1本**（永続・
畳めない）と、**還す条件を持って生まれる枝**になった。詳細は
`docs/adr/adr-0017-trunk-branch-and-utsuwa.md` と `work/tasks/task-0088-…md`。

読み始めるならこの順：`spec-ui` §1（骨格）→ `spec-canvas-ui` §11・§12（読む面と作業する面／
器の語彙）→ `spec-chat-ui` §1・§2.1。

手を入れるときに効くこと：

- **`ThreadRegistry` は幹1本と枝の帳簿になった。** `open(spec)` は `ThreadSpec`
  （trunk / branch）を取り、`merge(id, conclusion)` で畳む。`close()` と `new_session` は無い
- **深さ1段は型（親の欄が無い）と実行時（枝からの枝を拒む）の2つで縛ってある。**

- 器の畳み判定は `.talk` のコンテナクエリ。ビューポートではないので、細い帯でも
  モバイルでも同じものが効く


## 記憶の区画は幹になった（2026-08-10・ADR-0003 追補）

**第二層（プロジェクトの記憶）を、場所（リポジトリ）から幹へ移した。** 理由と決めたことは
`docs/adr/adr-0003-memory-two-layer.md` の「追補 2026-08-10」。

手を入れるときに効くこと：

- 置き場は `<data>/trunks/<幹のID>/memory.jsonl`（`bin.ts` の `trunkMemoryPath`）。
  `<data>/projects/<場所>/memory.jsonl` は**もう読まない**——起動時に件数を名指しして
  知らせるだけ（`warnStrandedPlaceMemory`）
- 会話へ何を注入するかは `ThreadIdentity.trunkId` で決まる。**幹なら自分・枝なら親**なので、
  枝で覚えたことは畳んだ後も仕事に残る
- `memory.save` の `trunk` は**省略が既定**（`defaultTrunkId`）。番頭は常に1本の幹に居るので、
  毎回どの幹かを書かせない。知らない幹を名指ししたら断る（I2）
- **探すときだけ幹をまたげる**：`memory.search({ acrossTrunks: true })`。畳んだ幹も対象
  （終わった仕事の記憶こそ横断で効く）
- 場所の別名畳み込み（`resolveProjects` / `projectIdFor`）は bin.ts から外した。
  区画が場所でなくなったので、ワークツリーごとに記憶が分かれる問題が消えたため。
  banto-core 側の関数は残っている（場所の同一性判定としてはまだ意味がある）

**残っている論点：自動抽出の宛先。** 章の境界で走る記憶の自動抽出（決定28）は、いまも
**人の記憶へだけ**入る。区画が幹になったので宛先の幹は分かるようになったが、抽出器は
「人についての長生きする事実」を出す前提で書かれていて、差分（`MemoryDelta`）が区画を
持たない。仕事に固有の話が横断層へ入りうる状態は残っている——直すなら抽出器の出力形式
（`ADD <kind> <本文>`）に区画を足すところから。

## 番頭が黙っていた本当の理由（2026-08-13・task-0104・決定97）

**「再起動のたびに番頭だけが全部忘れる」を直しに行って、もっと広い穴が出た。**
`roles.steward` は既に `claude-agent-sdk` なので、**新しく開く会話は全部その形で黙る**
状態だった——起票時に見えていたのは症状の半分。

### 一番効いたこと

**症状が同じでも原因は2つあった。** `resume` の取り違え（新規に実在しない札を渡す）と
札の保存漏れ（再起動で忘れる）は、**どちらも「番頭が黙る」**という同じ見え方になる。
翻訳が `result` を一様に「ターンの終わり」として扱っていたので、
`error_during_execution` が**本文の無いターン**にしか見えなかった。

> **エラーで終わったターンを黙って通さない。** 出口を一様に扱うと、原因の違う故障が
> 同じ見え方に潰れる（inc-0038 の「git のエラーがテストの失敗に化ける」と同じ形）。

### 手を入れるときに効くこと

- **`BantoHarness` に3つ増えた**（いずれも任意・決定97）：`resumeToken()` /
  `contextWindow()` / `dispose()`。復元は**手続きではなく札**——生きているハーネスへ
  後から文脈を差し込む口は作らない
- **札の置き場は索引の `backendSessionId`**（`StoredThread`）。pi の `sessionFile` と
  並ぶが別物で、**同じ会話が両方を持つ**（バックエンドを往復するため）
- **新規は `sessionId`、復元は `resume`。両立しない**（SDK の型注釈が明記）。
  実在しない札の `resume` は `error_during_execution`
- **ハーネスを作り直すたびに前のものを畳む。** `PromptQueue` は「空になっても終わらせない」
  ので、放すだけでは終わらない。**実測：ハーネス1本＝子プロセス1本**（3本立てて 2→5、
  畳んで 5→2）。札は引き継ぐので、**モデルを替えても文脈は続く**
- **走行中の畳みには世代を持たせる。** 古いループの `finally` が新しい `run` を消す。
  併せて `query()` が終わったら**待ち行列も作り直す**——死んだ生成器に resolver が
  残っていて、次の発話がそこへ渡って消える
- **章の閾値はハーネスの文脈長で測る**（`result.modelUsage[*].contextWindow`。実測 200,000）。
  自前の表を持たない（D3）

### 試験の書き方（同じ形が使える）

**`query()` を差し替えられるようにした**（`spawnQuery`）。世代・待ち行列・立て直しは
「翻訳だけを流し込む」試験では**1件も落ちない**——`PiHarness` が pi のセッションを
受け取るのと同じで、起こす手続きを外から渡す。**直しを1つずつ戻して落ちることを
6か所すべてで確認した**。

### inc-0058（間欠する試験）を直した

**待ちが切れていたのではない。待ちが早く満たされすぎていた。** 接続時に
**会話の本数だけ** `model_state` が配られるのに、試験は1本目だけを待って配列を空に
していたので、遅れて届いた初期値を「変更の反響」と取り違えていた。
`waitFor` に述語を足して**探しているものを名指しで待つ**形にした。
起票時の見当（`FakeSession` の sessionId 共有／ポートの取り合い）は**両方とも外れ**。

### 実機で確かめる過程で7つめが出た

**Claude 側だけ `prompt()` がターンを待たずに返っていた。** サーバは `prompt()` の解決を
もって `turn_end` を配る（pi は待って返る）ので、**返事が来る前に画面が「終わった」に
なる**。これが直るまで受け入れ自体が観測できないので併せて直した。

> **契約の言葉が同じでも、意味が同じとは限らない。** `prompt(): Promise<void>` は
> 型としては両方満たすが、片方は「積んだ」で片方は「終わった」だった。
> 呼ぶ側（サーバ）がどちらの意味に掛けているかを見ないと、seam は嘘をつく。

### 実機の確かめ方（そのまま使える）

**PO の会話を汚さずに済む。** 別ポート・別データ置き場で番頭ホストを1本立て、
Kobo・工房・検証環境の URL を**空いていない番号へ向けて切り離す**（向けないと
本物の Kobo の知らせを拾い、番頭が実際に動き出す——一度やってしまった）。

```
BANTO_DATA_DIR=<tmp> BANTO_KOBO_URL=http://127.0.0.1:4999/... \
BANTO_WORKER_POOL_URL=http://127.0.0.1:4998/... BANTO_ENV_POOL_URL=http://127.0.0.1:4997/... \
node --import tsx packages/banto-host/src/bin.ts serve --port 4199
```

`<tmp>/llm-registry.json` に `roles.steward` だけ書けば、そのバックエンドで新しい幹が立つ。
WS へ `{"type":"prompt","text":"..."}` を投げ、`text_delta` を拾って `turn_end` で締める。

### 残っているもの

- **inc-0062**：バックエンドを替えると `ChapterKeeper` の購読が古いハーネスに残り、
  自動の章立てが働かない（手で区切る口は効く）
- サブスクリプションの消費は**未計測**のまま（今回の実測は haiku での機構確認だけ）

## 概念を畳み切った（2026-08-13・ADR-0020 決定98・task-0102）

決定94 の残り6点。**「使われていない」と「死んでいる」の見分けが、ここでも効いた。**

### 手を入れるときに効くこと

- **採用は `policy` 1つ**（`hostUsable`/`workerUsable` は消えた）。書き先は `allowUse` に
  集約してある——欄が2つあった頃は、片方だけ書く経路が増えるたびに食い違った
- **`LlmDefaults.workerTier` は無い。** 職人の既定等級は工房（`backends.defaultTier`）が持つ
- **バックエンドは自分を名乗る**（`harness-backends.ts`）。`supports(ref)` が
  **`NotSupported` を値で返す**ので、断る理由に「次にどうすればよいか」を書ける
  ——「採用してください」（pi）と「経路を替えてください」（Claude 専用）は直し方が違う
- **モデルの一覧は聞く。** `query().supportedModels()` は **LLM を呼ばずに約1秒**で返る。
  **待たない**（写しを返し、裏で聞き直す）。**聞けなくても空にしない**（I2）
- **番頭の `llm.*` は4本**（`list` / `resolve` / `check_key` / `reload`＝読みと診断）。
  **HTTP 面は17本のまま**——設定画面の到達先なので、絞ると 404 になる

### 聞いてみたら、手書きの表は既に古かった

`CLAUDE_KNOWN_MODELS` は `opus` / `sonnet` / `haiku` の3行だったが、実際に聞くと
`default` / `opus[1m]` / `claude-fable-5[1m]` / `sonnet` / `haiku`。
**手で書いた一覧は、書いた瞬間から古くなる。**

### 途中で見つかった穴

**設定画面の選択肢は起動時に凍っていた。** 区画（`ModuleSettingsSpec`）は起動時に1回だけ
組まれるので、`options` を配列で持つと、モデルを採用しても出てこない。`get options()` に
した。**問い合わせを入れる前提**でもある（答えは1秒後に返るので、凍っていたら意味がない）。

### 確かめ方（この形が効いた）

- **移行は実データの写しで測る。** `/var/lib/banto/llm-registry.json` を temp へ写して
  読ませ、`host=true` 30件 → `policy⊃host` 30件、`worker=true` 26件 → 26件、
  併記の `contextWindow` も落ちないことを数えた。**件数で確かめる**——「動いた」では
  落ちた欄に気づけない
- **聞くために立てたセッションも畳む。** 子プロセスの数を前後で数えて 2→2 を確認
  （task-0104 と同じ罠。`supportedModels()` のためだけに `query()` を立てている）

## 二重管理を畳んだ（2026-08-13・ADR-0021 accepted・task-0106〜0109）

**PO の問い**「職人や番頭の設定画面を独立させたのに、LLM モデルのところで既定も設定できるのは
二重管理では？」から、継ぎ目を1つ手前へ動かした。**供給（誰が何を出せるか）と役の決定
（誰が何を使うか）を分ける。**

### 手を入れるときに効くこと

- **役の台帳は `<data>/model-roles.json`**（`ModelLedger`）。`llm-registry.json` は
  **pi バックエンドの供給**の台帳に戻った
- **版印（`schemaVersion`）を持つ。** 番頭ホストと工房は別サービスで再起動が独立するので、
  版が違えば**読み手は止まる**——黙って別のモデルで走るのが一番困る
- **役へ書くのは `updateRole` の部分更新1本**（全置換が `backend` 落ちの原因だった）
- **採用は母集団1つ**（`adopted`）。役の `only` は任意で、未指定＝母集団ぜんぶ。
  役の面で選べば採用も立つので、**画面に二度手間は出ない**
- **既定は核、上書きは呼び出し側**（決定99a）。Kobo の `executor`/`rework`/`audit` は
  Kobo が持つ——寄せると決定27 の依存逆転に触る
- **等級は落ちない**（決定104）。`MODEL_TIERS` の並びのせいで `fast` → `reasoning` に
  落ちていた（安いつもりが一番高いモデル）
- 画面は**役の面1枚**（番頭＋職人の等級）と**供給の面**（pi の登録・鍵・取り込み・採用）。
  工房の画面と LLM 画面からは割り当てが消え、書こうとすると**行き先を言って断る**

### 入れ替えで踏んだ穴（どれも「窓」で出る）

1. **同じミリ秒に2回書くと読み手が取りこぼす。** 台帳は数KBなので**毎回読む**
2. **読み取り専用の台帳で移行が落ちる／台帳がまだ無いと役が空になる。** 移行は書き手だけ、
   台帳が無いうちは従来の場所を読む。**デプロイは工房 → 番頭ホストの順**
3. **画面が「いま選べるもの」を出すと、いま効いているものが消える。** 実機の番頭は
   `claude/opus` だが、バックエンドに聞いた一覧には `opus[1m]` しか無く、
   **開いただけで別のモデルが選ばれているように見えた**。一覧に無い現在値は先頭に足す。
   **さらに根っこ**：`supportedModels()` は「勧める一覧」であって「使える名前の全部」では

4. **写しは起動時に温める。** 冷えたまま最初に開くと職人の欄が空になる
