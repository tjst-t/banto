## 2. 現在のフェーズ

**実装フェーズ。机上で決めるべきものは残っていない**（§27 の判定軸で全件確認済み）。

Substrate は **2026-07-26 に凍結**（ADR-0010 `accepted`）。**収束したからではない**——検証プロトコル §3 の3条件は未達のまま、「Substrate の残件だけ潰して固め、残りは実装しながら直す」と PO が裁定した。範囲と受け入れたリスクは ADR-0010「凍結」節が正典。

> **注意：実装前に決めた5件は、どれも配線チェックしか通っていない。シナリオ検証は一度も回していない。**

## 3. PO の判断待ち

**ADR-0009（番頭主体への構造逆転）の `status: proposed` が `spec-schemas` §3 の enum（`draft`/`accepted`/`superseded`）に無い。**

ADR-0010 は `accepted`、ADR-0003 は `superseded` へ移行済みで、**ADR-0009 だけが宙に浮いている**。内容の裁定（逆転を正式に受け入れるか）を伴うので番頭が決めず、PO に上げる。

## 4. 崩すと同じ穴を作る規律

詳細は検証プロトコル §6.4。ここには**特に効いたものだけ**を置く。

- **実行層・スコア式・API シグネチャに落ちた規律だけが機能する。** 散文で書いたものは4ラウンド全部素通りした。**知っていても防げない**——前セッションでは、この規律を引用しながら書いた新設節の中で同じ日に2回破った
- **機構を足すときは `spec-memory` §20.7.1 の配線レジストリに行を足してから本文を書く。** 逆順にすると必ず欄が空く（R5・R6 で二度実証）
- **設計を変えたら配線チェックを1体走らせる**（§2.4、ログは `verification-log/`）。前セッションでは5回走らせ、**毎回自分の主張を壊された**。とくに「設計の要」と自称した箇所こそ壊れる
- **一方の側を直すと反対側に穴が開く。** 横断ファンアウト（読み）が無審査の `scope` 拡大（書き）を到達可能にした。「緩めない」と宣言しただけでは緩む
- **可逆/不可逆は「後回しにできるか」の軸ではない。** 正しい軸は (a) 全エントリに書き込まれるか (b) 識別子の命名・粒度か (c) 保存層・書き込み経路の形を決めるか
- **同じことを2箇所に書かない**（D3）。矛盾を見つけたら黙って寄せず incident を積む（P3）
