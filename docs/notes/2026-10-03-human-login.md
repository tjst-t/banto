# 2026-10-03 人のログイン（パスキー・端末を追加・公開先の通行証）

仕様は `docs/specs/v4-security.md`「人のログイン」、画面は `docs/specs/v4-frontend.md` §6.24。ここは経緯と、
却下した案・実装で方式を変えたところ。

## きっかけ

携帯で banto を開くのに、長い合言葉（`authToken`）を手で運ぶ必要があった。QR にして運んだところ、確かめる途中で
値が AI の文脈に入った（Playwright の失敗のメッセージに URL がそのまま入っていた）。ユーザー：「Token での認証は
ちょっと辛くなってきた。1ユーザだけど、ログインの仕組みを考えられないか」。

## 決まったこと（ユーザー）

- パスワードは置かない（管理が面倒）。入り方はパスキー・端末を追加（QR とリンク、10分・1回）・host のコマンドのリンク
- セッションは 30 日で、使っていれば延びる（「手間は増やしたくない」。一度「30分」と書いたのは打ち間違い）
- Publish で公開したものの前にも効かせる（2026-09-28 の「当面は認証を置かない」を改める）
- 方式は「結果が変わらなければ任せる」。まとめたら Fable にレビューさせる

## Fable のレビューで変えたこと

- **高1**：トークンをセッションに引き換える口（最初の案の「いまのブラウザはトークンを見せて引き換える」）は作らない
  ——あると機械の合言葉を持つ者がいつまでも人として入れる。最初の1回も host のリンクで入り、合言葉を作り直す
- **高2**：URL の `bantoHost` を本番で読むと、公開先のページが画面の接続先をすり替えられた（今のコードの穴）。
  localhost でだけ読む
- **中3**：Origin・Sec-Fetch-Site・Referer を重ねて見る案をやめ、独自のヘッダ `X-Banto-Client: 1` を必須にした
- **中4**：パスキーの守りは RP ID ではなく検証時の origin の一致（RP ID の子＝公開先もプロンプトは出せる）
- **中5〜9**：公開先どうしの横取り（Sec-Fetch-Site）・本人確認（step-up）・iframe に入れさせない・戻り先の検め・
  サービスが返す通行証の Set-Cookie を落とす
- 公開先のドメインを banto の子でない名前に移す案（中4・5・7 が軽くなる）は、DNS と証明書と URL の変更が要るので
  採らなかった（ユーザー）

## 実装で方式を変えたところ（結果は同じ）

- **host のコマンドは `banto login-link`（cli.ts）ではなく `node scripts/login-link.mjs`**。cli.ts は起動すると
  サーバを立てる作りで、サブコマンドを持っていない。`restart-when-idle.mjs` と同じく scripts に置いた。札は API では
  作らず、データ置き場のファイルにする（API で作れると、機械の合言葉で人として入れる＝高1 と同じ穴）
- **リンクは `/login#code=` ではなく `/#banto-login=`**。どの場所でも門が読むので、専用のページを作らなかった
- **画面のオリジンに `uiOrigin` を足した**。仕様は「既にある `publicUrl` を使い、別の項目は足さない」だったが、
  `publicUrl` は API の住所（OAuth の戻り先 `<publicUrl>/api/oauth/callback`）で、開発・E2E では画面と違うポートに
  いる。省略時は `publicUrl` のオリジンなので、本番は書かなくてよい（写しにはならない）
- **公開先の戻り先は「今公開中の名前」ではなく「banto の画面の名前の下」で確かめる**。公開の一覧は publish の Module
  が持ち、core は知らない。代わりに札と通行証を公開先の名前に結びつけた——よその名前に札が渡っても、手に入るのはその
  名前の通行証だけ。同じ理由で「Caddy を通ったことが分かる形」も要らなかった（`X-Forwarded-Host` を偽っても、
  偽った名前のものを持っていない）
- **通行証はプロセスメモリではなく HMAC の署名つきの値**（鍵はデータ置き場）。host を起こし直すたびに公開先の
  fetch が 401 になるのを避けた
- **署名回数はライブラリに 0 を渡す**。仕様は「増えないことを複製とは見ない」で、`@simplewebauthn/server` は
  「前より大きいか」を必ず検める。同じパスキーを2つの端末で使う試験で実際に断られた（`Response counter value 2
  was lower than expected 2`）
- **公開先の確かめ口で、画面の遷移は `same-site` でも通す**。banto の一覧から公開先のリンクを押すのは `same-site`
  の遷移で、それを断ると公開先が開けない
- **E2E のブラウザは localhost で開く**。WebAuthn は IP アドレスを RP ID に取れない（127.0.0.1 では
  「This is an invalid domain」、実測）。Cookie は名前ごとでポートを問わないので、画面と core のポートが違っても付く

## 確かめたこと

- core の単体試験（`packages/core/src/auth/service.test.ts` 16本）：リンクの札は1回・10分・ファイルも消える／
  独自のヘッダ・Origin の検め／CORS は画面のオリジンだけ／Bearer では人の扱いを変えられない／30日の滑走と再起動後／
  端末を追加と知らせ／締め出しで 401 と流れの切断／ログアウト／パスキーの登録・入る・別オリジンの拒否・同期した
  パスキー・challenge の使い回し拒否／step-up／公開先の確かめ口・publish-start・戻り道・名前の結びつけ・戻り先の検め。
  ソフトの認証器（`soft-authenticator.ts`）で WebAuthn の応答を作る
- E2E（`connect-gate.spec.ts` 6本、Chromium の仮想認証器）
- 本物の Caddy v2.11.4 をコンテナで立てたプローブ（使い捨て）で 14 項目：未ログインは banto へ回る／ログイン後は
  元の場所へ戻って開ける／サービスに通行証も banto のセッションも届かない／サービスが通行証を書き換えられない／
  サービス自身の Cookie は届く／同じ公開先の fetch は通る／別の公開先のページからの要求はサービスに届かない／
  通行証の無い fetch は 401／締め出したら開けない
