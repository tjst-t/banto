# 別のサーバへのコードの送り込みを速く・見えるようにする（Backlog #269）

2026-10-12。決まったことは `docs/specs/v4-security.md` §1「向こうに置くもの」。ここは測った数字と、選ばなかった案。

## きっかけ

qemu-bmc を banto-dev-vm へ移した直後、最初のターンが banto のコード（約 850MB）を送り終わるまで約4分、tool を1つも
呼べずに止まって見えた（毎秒約5MB）。人は「AI が応答しなくなった」と受け取った。

## 測ったもの

相手：E2E の SSH の相手と同じイメージのコンテナ（4コア）に、incus の `limits.ingress=40Mbit` で線を絞った
（`head -c 50MB /dev/urandom | ssh … cat` で 50MB が 10.7 秒＝毎秒約 4.7MB——実機の毎秒約5MB に近い）。
新しい形は本物の `RemoteSshRuntime.syncCode` を、自分で張った ControlMaster の上で回して測った（送る→向こうで照合→切り替え）。

| | 送る中身（縮める前） | 線に流れた量 | 送るのにかかった時間 |
|---|---|---|---|
| 前（tar を縮めずに・node は cat） | 852MB（tar 728MB＋node 124MB） | 852MB | 199 秒（tar 172 秒＋node 27 秒） |
| 今・向こうに zstd がある | 809MB（tar 685MB＋node 124MB） | 270MB | 61 秒 |
| 今・向こうに zstd が無い（gzip） | 809MB | 316MB | 69〜75 秒 |

照合（向こうで sha256sum）と切り替えに、さらに 3〜10 秒。E2E（`remote-code-transfer.spec.ts`、gzip）の host の記録：
「808.6MB を gzip で 316.0MB に縮めて・69137ms」。

送る中身の内訳（縮める前、大きい順）：Claude の CLI（`@anthropic-ai/claude-agent-sdk-linux-x64`）223MB、opencode が2つ
（`opencode-linux-x64` と `-baseline`、各 185MB。`opencode-ai/bin/opencode.exe` は baseline へのハードリンクで、tar は
2件目から中身を持たない）、node 124MB。型定義・ソースマップ・ワークスペースの試験を外して 43MB 減った（728→685MB）。

縮め方（host の 1 コア、tar 728MB を相手に）：

| | 縮めた大きさ | 時間 |
|---|---|---|
| gzip 段1（コマンド） | 276MB | 13.1 秒 |
| gzip 段6（コマンド） | 247MB | — |
| zstd 段1（node の zlib） | 262MB | 4.2 秒 |
| zstd 段3（node の zlib） | 234MB | 5.3 秒 |
| zstd 段6（node の zlib） | 218MB | 14.8 秒 |

zstd 段3 は毎秒 130MB 強で縮められ、回線（毎秒数 MB〜LAN の毎秒 100MB）より速いので回線を待たせない。gzip 段1 は
毎秒約 55MB——LAN では縮めずに送るのと同じくらいだが、遅い回線では効く。

## 選ばなかった案

- **opencode の使わないほうの版（`opencode-linux-x64`、185MB）を外す**：今の host では `opencode.exe` が baseline へのハード
  リンクで、もう一方は読まれない。ただ「どちらが使われるか」は opencode の postinstall が host で決めることで、依存の宣言
  からは分からない。パッケージの名前で特別扱いを書くことになるので、やめた（外したときの減り方は測っていない）
- **zstd の段を上げる**（段6 で 218MB）：縮めるのに 15 秒かかり、LAN では縮めずに送るより遅くなる
- **送る中身をパッケージの `files` で絞る**：外から入れた依存は npm が `files` に従って置いたものなので、もう絞られている。
  残っているのはほぼ実行ファイル（Claude の CLI・opencode・node）
- **向こうに zstd を入れさせる（前提の確かめに足す）**：root の準備を増やすほどではない（gzip でも 199 秒が 75 秒になる）。
  あれば使う

## 時間切れに当たらないか

- **ターン**：ターンそのものに時間切れは無い。Module を起こす（`runtime.prepare`）にも時間切れは無く、MCP の初期化は
  `prepare` が返ってから（送り終えて照合したあと）始まるので、その時間切れに送り込みの待ちは入らない（`cli.ts` の
  Module を繋ぐところ）
- **送り込み**：前は tar に 600 秒・node に 300 秒の時間切れがあり、毎秒約 1.2MB を切る回線では送り終わる前に切れた（tar 728MB を 600 秒）。
  全体の時間ではなく「120 秒のあいだ1バイトも進まない」で止めるようにした
- **照合**：向こうの sha256sum（約 800MB）に 180 秒の時間切れ。実測 3〜10 秒

## E2E で踏んだもの

最初の形では、バイトを送り終えたところで「送っています」を消していた。E2E は消えた直後に向こうの版を見て「無い」と
落ちた——向こうではまだ照合している最中だった。そのあと試験の片づけがコンテナを消し、host には「SSH の接続が途中で
閉じました」が残り、一見すると接続が切られたように見えた（実際は試験の片づけ）。**消えたら使える**という意味にする
ため、照合と切り替えが終わるまで出し続けるようにした。

## レビューで直したもの：止める道で core が落ちる・永久に待つ

指摘（2026-10-12）：送り込みを途中で止める道（120 秒の停滞で ssh を止める・登録を外す・接続が切れる）が tar の段で
起きると、`sendTree` が「tar の終わりを待ってから ssh の結果を見る」順だったため、

- ssh が死ぬと縮める流れが外れて tar の出力が止まり、tar は書き出しで塞がったまま終わらない→ tar の終わりを待つ側
  （Module を起こす `prepare`、つまり最初のターン）が永久に返らない
- 先に失敗した ssh の結果は誰にも受けられず、unhandledRejection で core ごと落ちる（node 24 の既定。core にその受け手は無い）

元の形も tar を待って塞がる形ではあったが、失敗の順番が入れ替わって落ちる道が新しく加わっていた。

直し方：

- `sendTree` は ssh の結果をすぐ受けて持っておき、tar の終わりと先に来たほうを見る。ssh が先に失敗したら tar を止めて
  （`SIGKILL`）、終わったのを見てから ssh の理由で失敗する
- `sendStream` は ssh が失敗したら流れの上流（数える・縮める・元の流れ）を閉じる
- 登録を外したとき（`closeRuntime`）は、用意している途中の接続（先に送っている最中）も閉じる——前は張り終えた接続しか
  見ておらず、先に送っている最中に外しても止まらなかった
- 送れなかったときは画面の行を消さず、「送れませんでした」と理由に変えて残す（黙って消えると終わったように見える）。
  Module を起こすのが失敗したことは今までどおり受信箱に出る（会話にお知らせを混ぜない、は前からの決定）

確かめ：単体（`remote-ssh.test.ts`）で偽の ssh（標準入力を読まずに居座る・途中で 255 で終わる・親が消えたら終わる）を
相手に、3つの道とも理由つきで返ること・tar が残らないこと・受けられていない失敗が無いことを見た。**元の順に戻すと3件中
2件が落ちる**（停滞・外した。停滞では ssh の失敗が受けられずに出る）。E2E（`remote-code-transfer.spec.ts`）では、送っている
途中で向こうの sshd のこのユーザーの接続を落とし、会話とサイドバーの行が「送れませんでした」と理由（SSH の接続が途中で
閉じました）に変わること、次に Module を起こそうとしたときに送り直して最後まで届くことを見た（host の記録に
unhandled の類は無く、tar も残っていない）。

## レビューで直したもの：繋いでいる途中で登録を外すと、外した名前で接続が残る

指摘（2026-10-12）：`closeRuntime` は「用意している途中（`settingUp`）」と「張り終えた（`connections`）」しか見ない。
`connect` が `settingUp` に入るのは、前提の確かめ・親の接続（Allocated port）を待ったあと。その数秒に登録を外されても
何も閉じず、`connect` は完走して接続を残した。さらに同じ名前で別の host を登録し直すと、先に送る（`warmUp`）も
Project の `ensureConnection` も残った接続（外した旧 host）を使い、そこで Module が起きた。登録したら先に送る形を
足したことで、Project が無いまま接続が張られうるようになり、新しくできた道（前は Project が使っている間は外せなかった）。

直し方：名前ごとに「登録を外した回数」を持つ。`connect` は始めたときの回数を覚え、`settingUp` に入った直後（コードを
送る前）と、繋ぎ終えて `connections` に入れる直前に比べ、変わっていれば親の接続を閉じて「外されたので、繋ぐのを
やめました」で失敗する。繋ぎを1本にまとめる鍵にも回数を含め、登録し直したあとの繋ぎが外す前の繋ぎに相乗りしない。

確かめ：単体（`remote-ssh.test.ts`）で、偽の `withConnection`（門が開くまで待つ＝前提の確かめ・親の接続を待つ間）の
最中に外し、同じ名前で登録し直して先に送る。前の繋ぎは閉じて失敗し、残るのは登録し直した host の接続だけ。
回数の比べと鍵の回数を抜くと、この試験は落ちる（2本目の繋ぎが始まらない＝前の繋ぎに相乗りする）。

## main に載せ直したあとの E2E で踏んだもの：接続が切れた理由が「ssh の終了コード 255」だけになる

#270 と重なる4ファイルを解いて main に載せ直したあと、`remote-code-transfer.spec.ts` が1回落ちた：向こうの sshd を落とした
とき、会話の行の理由が「SSH の接続が途中で閉じました」ではなく「コードを送れませんでした（ssh の終了コード 255）」だった。
載せ直しのせいではない。接続が切れると、多重化した上の ssh（255 で終わる）と親の接続のどちらが先に終わって見えるかは
決まらず、前の回は親が先、この回は上の ssh が先だった。上の ssh を先に見ると親はまだ生きて見えるので、「途中で閉じた」と
分からず、人には何が起きたか分からない文になる。

直し方：多重化した ssh が 255 で終わり、親がまだ生きて見えるときは、親が閉じるかを 2 秒だけ見てから理由を決める
（`mustRun`）。試験は待ちを延ばしたのではなく、製品が理由を決める前に見る——試験の側は前と同じ文を待つ。
単体（`remote-ssh.test.ts`）に「上の ssh が先に 255 で終わり、親はそのあと閉じる」を足した。この待ちを抜くと落ちる。
