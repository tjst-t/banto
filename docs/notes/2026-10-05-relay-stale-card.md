# 2026-10-05 中継の承認のカードが畳まれずに残る・後ろの書き込みが60秒で切れる

決まったことは `docs/specs/v4-frontend.md`「Module 間中継の承認」（改訂・2026-10-05）と
`docs/specs/v4-architecture.md` §2.5「出所は呼び出し単位で継ぐ」。ここは経緯・測ったこと・却下した案。

## 症状（本番、2026-10-05）

Backlog の書き込みの tool（createItem・updateItem 等）は、backlog ブランチへのコミットのあと push を待つ
（中継 → Repositories の `push_branch`）。初回は中継の承認で人に聞く。

1. 承認を待つ間、AI の Backlog の呼び出しが60秒で `MCP error -32001: Request timed out` になる（書き込み自体は済む）
2. 04:17、別の Thread（Fork）で Backlog の書き込みから出た承認のカードが、聞いた呼び出しが終わっても畳まれず受信箱に残った
3. 同じ組み合わせ（grantKey）の承認は1枚目に相乗りするので、以後の書き込みは新しいカードを出さず、取り残されたカードを待ち続けた
4. そのカードは出た会話の中でしか答えられない（今回は直していない。ユーザーに別途聞く）

## 測ったこと

本番のログ・Event Store は今回の作業環境からは読めなかった。以下はすべて手元で再現して測った。

### Runner（同梱の Claude Code 2.1.281）の MCP クライアント

実物の CLI を、偽の Anthropic API（`ANTHROPIC_BASE_URL` に立てた、tool_use を1つ返すだけのサーバ）と、
返事を遅らせるだけの MCP サーバ（HTTP）に繋いで測った。モデルは使っていない。

| 試したこと | 結果 |
|---|---|
| 75秒黙って返す | 待って受け取った（**60秒の上限は無い**） |
| 75秒・130秒、10秒ごとに進捗 | 待って受け取った |
| 330秒黙る | **300秒で諦めた**（`sent no response or progress for 300s; aborting`）。**サーバには取り消しが来なかった**——ハンドラは最後まで走った |
| 330秒、10秒ごとに進捗 | 331秒で受け取った（**進捗で延びる**） |
| 呼び出しの途中で CLI に SIGTERM／SIGKILL | **どちらも取り消しもセッションの終わり（DELETE）も来ない**。サーバのハンドラは最後まで走った |

CLI を読むと、上限は2つ：全体（既定は約28時間、進捗では延びない）と、無音（http は5分、進捗で延びる。
`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`）。無音で諦めるときは `Promise.race` で抜けるだけで、SDK の要求は取り消さない。
v4-architecture.md §4（Subagent）の「無音が続くと切る（http 5分）が、進捗で延びる」と一致した。

### host（実物の Backlog・中継・承認・台帳・代理サーバを1つのプロセスで繋いだプローブ）

上限を3秒に縮め、Runner の代わりに SDK の Client を代理サーバに繋いだ。

- **A：1本目が承認を待つ間に、別のターンから2本目の書き込み** → 2本目が上限で `MCP error -32001: Request timed out`。
  Backlog は「取ってくる・書く」を1本ずつの列に並べ、「送る」も1本ずつ並べる。2本目は1本目の承認待ちの**後ろで**黙って待つが、
  台帳の「人を待っている」は1本目にしか付いていないので、host の上限（`agent-proxy.ts`、既定60秒）が2本目を切った。
  **症状1の 60秒・-32001 はこれ**（文言も host の見張りのものと同じ）。切れたあとも Backlog の中では2本目の仕事が続き、
  終わった呼び出しの印で中継を呼んだ——台帳は「終わった印なら接続の全部」に戻していたので、**1本目の呼び出しを借りて**
  通っていた（許可済みでなければ、1本目の会話にカードを出していた）
- **B：承認を待つ呼び出しを Runner が取り消す** → カードは畳まれ、次の呼び出しでまた聞いた（2026-10-04 の直しどおり）
- **C：1本目が承認待ち・2本目が後ろで待つ中、1本目の Runner が去る** → 直す前は2本目が切れ、加えて Backlog の
  `hostRelayCall` が「断られた」返事で**共有の接続ごと繋ぎ直した**ため、同じ接続で承認を待っていた別の中継まで切れ、
  host にはその承認のカードだけが残った

### 実ブラウザ（E2E、`backlog.spec.ts`）

- 承認のカードが出ている間は、画面に「止める」ボタンが出ない（カードが答えを待っている間、ターンは走っていない扱い）。
  **人がターンを止めてカードを残す、という道は実際には無い**
- 偽の Runner に「返事も進捗も4秒来なければ、取り消さずに去る」（本物の300秒の縮小）をさせると、直す前は**カードが受信箱に
  残り続けた**（症状2の再現）。直したあとは畳まれ、次のターンで新しいカードが出た

## 原因

- **確かめた**：症状1は host 自身の上限。Module の中で人を待つ呼び出しの後ろに並んだ呼び出しを、人待ちと見ていなかった
- **確かめた**：host は Runner が去ったことを知る経路を持っていなかった。Runner が無音で諦めたとき・プロセスごと終わったとき、
  取り消しは来ず、AI の代理サーバの呼び出し・台帳の在籍・承認の判断待ち・`holdForHuman` が全部残る——カードは畳まれず
  （症状2）、同じ組み合わせの次の呼び出しはそこに相乗りする（症状3）
- **確かめた**：台帳が「終わった呼び出しの印」を接続の全部に戻していたので、去った呼び出しの続きの仕事が、別のターンの
  呼び出しを借りてカードを出し、その呼び出しを人待ちにできた
- **確かめた**：Backlog の `hostRelayCall` が、断られただけで共有の接続を切り、並んで待っていた別の中継を巻き込んでいた
- **推測のまま**：04:17 の Fork でカードが残った直接の経路。ログを読めていない。「止める」が出ないので人が止めたのではなく、
  Runner が300秒の無音で諦めた（Backlog は承認の進捗を外へ流し直していなかった）か、上の「借りた」経路のどちらかと考えている
- Backlog は中継に呼び出しの印（`dev.banto/callId`）を**返していた**（疑いの1つは外れ）

## 直したもの

- **host が Runner へ進捗を送る**（`agent-proxy.ts`）。人を待っている間、10秒ごと（`APPROVAL_PROGRESS_INTERVAL_MS`）。
  待っている間は host 自身の上限も数え直す——数え直さないと、待ち終えた瞬間に、待つ前から数えていた分で切れる（プローブ C で実際に起きた）
- **同じ Module のどれかが人を待っている間は、上限を数えない**（`ModuleCallTracker.isModuleWaitingOnHuman`）
- **Runner が返事を受け取れなくなったら止める**（`agent-relay-endpoint.ts` → `AgentProxy.abortCalls`）。POST の応答の流れが、
  返事を書き終える前に閉じたら、その POST の tools/call を止める。止めると Module にも取り消しが届き、台帳から外れ、承認は畳まれる
- **終わった呼び出しの印は何も指さない**（`ModuleCallTracker.entriesOf`）
- **相乗りした先が「聞いた呼び出しの終わり」で畳まれたら、続いている呼び出しは聞き直す**（`approval-gate.ts`）
- **Backlog の `hostRelayCall` は、接続が壊れたときだけ繋ぎ直す**（host が返事として返した失敗では切らない）
- 偽の Runner（`e2e/fake-runner.ts`）：止められたら取り消しを送らずに接続を切る（本物と同じ去り方）。`giveUpToolAfterMs` で
  本物の無音の諦め方を再現できる

## なぜ「host が進捗を送る」か（Module に送らせない）

- 人を待っていることを知っているのは host（承認のゲート）。Module は「中継の返事がまだ来ない」しか知らない
- Module に流し直させる形（2026-09-10 の Shell）は、流し直さない Module で切れる——2026-10-04 の publish-directory、
  今回の Backlog（`onprogress: () => undefined`）がまさにそれ。直すべき Module が増え続ける
- 列に並んだ後ろの呼び出しは、Module が流し直しても進捗が来ない（中継を呼んでいるのは前の呼び出し）。Module の単位で
  人待ちを見られるのは host だけ
- 既にある手当て（host → Module への承認待ちの進捗、`host-relay-endpoint.ts`）と同じ間隔・同じ文言を使う。新しい機構は足していない

## 却下した案

- **push を書き込みの後ろに回して遅らせる**：ユーザーが採らないと決めた（push はなるべくすぐ）
- **`push_branch` を承認なしで通す**：ユーザーが採らないと決めた
- **Backlog の列から「取ってくる」を外し、人待ちが列を塞がないようにする**：Backlog の中だけの直しで、ほかの Module が
  同じ形（中で並べる）を持てば同じことが起きる。host の見方を直すほうが根に近い
- **ターンが終わったら、その Thread の代理サーバのセッションを全部閉じる**：応答の流れが閉じたのを見るほうが、ターンの
  終わり方（終わった・止めた・CLI が落ちた・通信が切れた）を問わずに効く。セッションの片づけとしては別に意味があるが、今回は入れていない

## 残したこと（直していない）

- **ターンが先に終わると、畳んだカードは画面の上で答えられるように見えたまま**。畳んだことは走っているターンの流れにしか
  流さないので、終わったターンのカードには届かない。開き直すと消える（中継のカードは走っているターンにしか描かれない）。
  押すと、もう決着した判断待ちに答えることになる
- **カードが答えを待っている間、「止める」ボタンが出ない**——人がそのターンを止められない
- **Module → host の中継の側も、呼び出し元の Module が去ったことに気づかない**（`host-relay-endpoint.ts`）。今回は Backlog が
  無駄に接続を切らなくしただけ。Module のプロセスが落ちれば外側の呼び出しが終わって畳まれるので、残り続けはしない
- 症状4（カードは出た会話の中でしか答えられない）——ユーザーに別途聞く
