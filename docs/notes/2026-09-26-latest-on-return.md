# 戻ってきたら、最新の状況をそのまま出す（2026-09-26）

ユーザー指摘：「AI の応答に時間がかかる時にタブを閉じて開き直したり、更新したり、別アプリに移り、戻ったとき
シンプルに最新の状況を出してくれればいいだけなんだけど、今はそうなっていないね」。画面には
「このターンは走っています（別の画面で始まったものに繋ぎ直しました）／いま動いているもの：
mcp__subagent__runSubagent／まだ出力はありません」という帯が出ていた。

決めたことは `docs/specs/v4-frontend.md` §6.8。ここは測ったこと・踏んだこと・却下した案。

## 直す前に測ったこと

E2E（`turn-reattach.spec.ts`）を新しい振る舞いで先に書き、直す前の画面で回した：

| 場面 | 直す前 |
|---|---|
| 走行中にリロード | 本文に AI の発言が出ない（帯だけ） |
| 走行中に接続が切れる（別アプリへ移る） | 吹き出しに「[1] エラー: network error」が出たまま止まる。host ではターンが最後まで終わっているのに、画面は変わらない |
| 別の画面・API で始まったターン | 開いている画面に出ない |
| 判断待ちに答えたあと開き直す | カードが出ない |

**ブラウザの「オフライン」切り替え（Playwright の `setOffline`）では、張ってある接続は切れなかった**
——最初はこれで接続断を試したら、直す前の画面でも通ってしまった（再現になっていない）。
画面と host の間に TCP の中継を挟み、そこで接続を切る（`cut`）・切らずに止める（`freeze`）形にした。

## 原因

1. **描き方が2つあった**。自分で送ったターンは本文に流れるが、それ以外（リロード・他所で始まった）は
   帯に要約して出していた。同じターンが、見る画面によって違う形に見える
2. **流れが切れたら、それきり**。自分の送信の流れが切れると `エラー: …` を書いて run を終え、
   そのあと最新を取りに行く道が無かった。帯の側も「開いたとき」と `turn.started` でしか繋がない
3. **`turn.started` が早すぎた**。host の知らせは順番の鍵を取った時点で出るが、流し直しの口
   （`GET …/stream`）が「走っている」と答えるのは、Module を起こし終えて走り始めてから（数秒、
   コンテナが初めて起きる回はもっと）。画面はその隙間に聞いて `idle` を受け取り、見逃していた。
   リロードがこの隙間に当たっても同じ
4. **判断待ちの答えは、ターンの流れに載っていなかった**。流し直すと、答え済みの判断が未回答に見えうる

## 直し方

- 帯をやめ、**最新を出す道を1つに**した（`lib/backend/latest-state.ts`）：記録から組み直す → まだ走って
  いれば流し直してもらい、**自分で送ったターンと同じランタイムの run として**描く
  （assistant-ui の `startRun`。adapter の run は「同じターンの続きを読む」経路をそのまま使う）
- 流れが切れたら、エラーではなく `disconnected` として扱い、上の道で組み直す
- host はどの SSE にも15秒ごとに空行、画面は45秒なにも届かなければ切れたとみなす
- 流し直しの口は、鍵を取ってから走り始めるまでの間は待つ（`TurnEventBus.whenBegun`）
- 判断待ちの答えを、ターンの外から中への口（side）で流す（`answered`）——自分の送信の流れにも、
  流し直しにも同じものが届く

## 却下した案

| 案 | 却下した理由 |
|---|---|
| 帯を残し、中身を増やす（tool のカードも帯に出す） | 同じものを2つの描き方で持つことになる（規則3）。人から見て「いつもと違うもの」が出るのは変わらない |
| 戻ってきたら毎回、記録から組み直す | 流れを最後まで読んだ会話まで組み直すと、流れていた tool のカードが消える（記録は文と画面つき tool しか持たない）。最後まで読んだ会話は組み直さず、どこまで見せているかを覚えるだけにした |
| ポーリング（数秒ごとに記録を取る） | 受信箱で踏んだ——再描画が assistant-ui のランタイムを壊した。出来事と「戻ってきた」で動く |
| `turn.started` を host が走り始めた時点に遅らせる | 知らせを出す場所（順番の鍵）と、走り始める場所（turn-runner）が別。流し直しの口の側で待てば、リロードが隙間に当たった場合も同じ直しで済む |
| 見切る時間を短くする（15秒等） | tool が長く走る間、ターンは何も出さない。空行（15秒ごと）の3倍にした |

## 踏んだこと

- **流し直しの試験で、答え済みの判断のカードが「見えない」と落ちた**——畳まれた「2 tool calls」の中に
  入っていた（答えを待っているものだけが開いて出る）。未回答として出ているのではなかったので、製品は
  変えず、試験で畳みを開いて中身を見るようにした。答えの扱いを外すと「答えた判断に、また答える口が
  出ている」で落ちることも確かめた
- **`turn-lifecycle-abandoned` が落ちた**——答えた直後、まだ走っている間に Enter を押していた。乗った流れ
  も自分の送信と同じく「走っている間は止めるボタン」なので送られない（以前は帯だったので送れて、host が
  順番待ちさせていた）。試験を「送るボタンに戻ってから送る」に直した。人が見る形（止めるボタン→送る
  ボタン）と同じ
- 単体試験で、`begin` の直後に同じ手番で `end` まで呼んでいたため、待っていた側が再開する前にターンが
  消えていた。本物のターンは走り始めてから中身を出すまでに必ず手番をまたぐので、試験を実物の順序に合わせた
  （スナップショットを再開後に取る実装のほうが、その間の出来事を取りこぼさない）
- **フル E2E で `project-thread-fork` が落ちた**（Fork の入口が出ない）。最後まで読んだ会話に記録の写しだけ
  書き込んでいたため——会話の中の目印は、組み立てたときの記録の番号（`real-<seq>`）で置き場所を探すので、
  写しだけ新しくなると、いまの会話に無い番号を探す。写しは組み直すときにだけ書き換え、「どこまで見せて
  いるか」は別に覚える形に直した
