# コードブロックが途中で止まる不具合と、応答性の実測（2026-09-07）

## 1. `ui-codeblock-cjk`——犯人は memo 化だった

### 症状
AI の返事の**コードブロックの中身だけ**が途中で止まる。止まる位置は毎回違う。
E2E `shell-confinement` がフルスイートで**約3回に1回**これで落ちていた
（単体では再現しない）。

### 外した仮説（記録として残す——同じ道を二度通らないため）

1. **「日本語が表示されない」** ……止まる位置が毎回違うので、文字種の問題ではない。
   最初の報告でそう見えたのは、日本語が先頭にあったから
2. **「typewriter（`useSmooth`）が requestAnimationFrame で止まる」** ……
   裏に回ったタブでは rAF が止まる、という筋書きを立てたが、**headless Chromium では
   裏のページでも rAF は 60fps で回り続ける**ことを実測（`before:3 after:123 delta:120`）。
   落ちた瞬間の画面でも rAF は 60〜61 フレーム/秒で生きていた
3. **「SSE がターンの途中で終わっていて、短いまま確定している」** ……
   `data-status="complete"` から一度はこれを疑ったが、**ランタイムは全文を持っていた**
   （下の実測）。配送は正常

### 決め手になった実測

落ちた瞬間に、次の3つを**同時に**取れるようにして再現させた
（`e2e/specs/shell-confinement.spec.ts` の `captureFreezeEvidence`）：

```
[HOST]  assistant: "コマンドは成功し（終了コード 0）、出力は次のとおりです。\n\n```\n中は読める1788793037422\n```\n\n標準エラー出力は空でした。"
[PART]  len=72 status=complete tail="37422\n```\n\n標準エラー出力は空でした。"
[CODE]  shown=4 text="中は読\n"
[DOM]   status=complete text="コマンドは成功し（終了コード 0）、出力は次のとおりです。\nCopy中は読\n\n標準エラー出力は空でした。"
[rAF]   1秒間のフレーム数 = 60
```

- **host にも、ランタイムにも全文がある**（`[PART] len=72 status=complete`）
- **コードブロックを描く component だけが4文字で止まっている**（`[CODE] shown=4`）
- **その後ろの段落は正しく描けている**——部分木だけが取り残されている

### 原因

`@assistant-ui/react-markdown` の `unstable_memoizeMarkdownComponents` が付ける比較は
**`node`（markdown の構文木）しか見ない**（`memoization.js` の `memoCompareNodes`）。
段落や見出しは中身が `node` に入っているのでこれで足りる。

ところが**コードブロックの中身は `node` ではなく props で渡ってくる**——
同ライブラリの `CodeOverride` が
`<Pre><Code node={node}>{code}</Code></Pre>` の形に組み替えるため、
中身は `children`（文字列）として届く。比較はそれを見ないので、
**中身が増えても「変わっていない」と判定され、最初に届いた分のまま二度と
描き直されなかった**。

**1度に全文が届いた回は正しく出る**ので、約3回に1回という間欠に見えていた。
フルスイートでだけ落ちたのは、負荷が高いほど chunk が細かく分かれるため。

### 直し方

`apps/frontend/components/assistant-ui/elements/markdown-text.tsx` で、
**コードブロックを描く3つ（`pre` / `code` / `CodeHeader`）だけ memo 化から外した**。
段落・見出し等はこれまでどおり memo 化する（ストリーミング中の再描画を抑える
効果はそのまま）。

**テストは緩めていない**（規則6）。完了条件は「フルスイートを5回続けて回して
`shell-confinement` が一度も落ちないこと」。

## 2. 応答性の実測（サブエージェント2本＋自分で裏取り）

「全体的に応答性が悪い」という指摘を、推測でなく数値にした。

### バックエンド（host）は犯人ではなかった

稼働中の host の**実データ**（イベント344件・1.2MB）での実測：

| 測ったもの | 中央値 |
|---|---|
| `GET /api/projects` | 0.7 ms |
| `GET /api/threads/:id`（259KB 返す） | 3.9 ms |
| `GET /api/ui-config` | 0.4 ms |

サブエージェントが出した「起動12秒」「thread 取得142ms」は
**イベントを3.2万件まで合成した条件**の値で、いまの実データはその1/100。
**そのままでは効かない**——ただし伸び方（O(n²) の replay）は将来の話として残る。

実データでも効いていたのは1つだけ：

- **Module の起動が直列**。Project で最初に Module に触れる操作（＝最初のターン）が
  中央値1.5秒・最悪2.2秒。`dependsOn` は中継の宛先を決めるためのもので
  起動の前後関係ではないので、**同時に起こす**ようにした
  （`cli.ts` の3箇所）。同時起動で新しく生まれる「宣言の直しの読み書き競合」は
  1本に直列化して塞いだ
- ついでに、イベントログを **seq だけ見て読み飛ばす**ようにした
  （スナップショットがあっても各 store が全行を `JSON.parse` してから捨てていた）

### フロントエンドが体感の主因

実ブラウザ（Playwright）での実測、いずれも**開発モード（`next dev`）**の数値：

| 測ったもの | 中央値 | 最悪 |
|---|---|---|
| 初回表示・操作可能まで | 5.8 s | 6.4 s |
| 初回表示中の long task 合計 | 3.4 s | 3.6 s |
| リロード（キャッシュ温）・操作可能まで | 3.7 s | 4.2 s |
| Project 切り替え | 1.8 s | 2.9 s |
| Fork（履歴）を開く | 2.6 s | 3.3 s |
| 設定を開く | 0.6 s | 1.1 s |
| Command Palette を開く | 0.8 s | 1.0 s |

- Project 切り替えと Fork はネットワーク呼び出しゼロ——**純粋に JS の実行時間**
- 初回に、**開いていない Project の Thread 一覧まで全部取りに行っている**
  （fetch だけで 1.94MB）。同一セッション内で行き来しても追加取得は0件なので、
  「何度も取り直している」のではなく「要らないものまで先取りしている」
- **`useSmooth` が毎フレーム markdown を再パースしている**という仮説は、
  実測では支持されなかった（1766字の応答で DOM 更新は8回、long task 合計888ms、
  壁時計34.5秒に対して CPU は約7%）

**まだ切り分けられていない一番大きいもの**：上の数値は全部 `next dev`（未 minify の
JS 4.6MB・React の dev ビルド）で測っている。**本番ビルドで測り直すまで、
「dev だから遅い分」と「本番でも遅い分」は分けられない**。

### 本番ビルドで測り直した（2026-09-07、決着）

同じ物差し（同じスクリプト・同じ機械・静かな状態、各5回）で dev と本番ビルドを並べた。
「操作可能まで」は**行き先が決まって composer が出るまで**（`helpers.ts` の `openApp` と同じ待ち方）。

| 測ったもの | `next dev` | 本番ビルド | 差 |
|---|---|---|---|
| 初回表示・操作可能まで（中央値） | 2.39 s | **0.97 s** | −59% |
| リロード・操作可能まで | 1.42 s | **0.49 s** | −65% |
| long task 合計 | 1.11 s | **0.34 s** | −69% |
| 転送量 | 2.8 MB | **1.53 MB** | −45% |
| Project 切り替え | 0.13 s | 0.21 s | **+0.08 s（悪化）** |

- **体感の主因は開発モードだった。** サブエージェントが出した「初回5.8秒」は、
  dev＋同時に E2E が走っている状態の値で、静かな dev だけなら 2.39 秒
- **稼働中の 4175 を本番ビルドに切り替えた**（ユーザー判断・2026-09-07——
  「同じポートで再起動すれば Caddy の変更も要らない」）。
  **画面を直したら `npm run build` してから起動し直す**必要がある。
  E2E も同じ 4175 を使うので、**直したらビルドしてから回す**（`e2e/config.ts` に明記）
- Project 切り替えだけ本番のほうが遅い。`/p/[projectId]` が「都度サーバ描画」
  （ビルド出力の `ƒ`）なので、切り替えのたびにサーバへ取りに行くためと**推測**
  ——まだ測っていない。次に触るときの手がかりとして残す

## 3. `global-memory-mid-thread-delivery`——起票が古かった（2026-09-07）

起票（2026-09-06）は「Global Memory には、Project Memory のような『確定より後に
増えた分をターンに添える』仕組みが**無い**」としていた。いまのコードは違う：
`http/turn-runner.ts` が `splitMemory(globalMemory.list(), memoryBaselineSeq,
memoryDeliveredSeq)` を通し、**Project Memory と同じ1つの規律**でターンに添えている
（`project-thread/memory-split.ts`——「同じ規則を2箇所に書かない」）。

**読んで「直っている」と決めず、完了条件をそのまま測った**（規則1）：

- 1ターン会話して **resume-point が立っている**（＝system prompt が固定される状況）
  ことを確かめてから、
- **後から** Global Memory に一意な合言葉を足し、
- 次のターンで **AI がその合言葉を答える**ことを確認した
- あわせて `memoryDeliveredSeq` が進むこと（＝差分として届けた記録が残り、
  毎ターン同じものを繰り返さない）も見た

→ **直す変更は無し。回帰テストだけ残した**（`e2e/specs/global-memory-mid-thread.spec.ts`）。
同じ疑いが起きたときに、また一から測り直さないため。

**教訓**：起票の「why」は書いた時点の観測であって、いまの実装の説明ではない。
**着手前に、その前提がまだ生きているかを測る**——このセッションでは
「Module はターンを始める瞬間に起動する」でも同じ食い違いを踏んだ（規則8）。

## 4. 起動時の先取り fetch を止めた（`perf-bootstrap-overfetch`、2026-09-07）

**実測（直す前）**：起動時の API 転送 **2.88MB のうち 2.875MB（99.9%）**が
`GET /api/projects/:id/threads`。開いてもいない Project の**全会話**を受け取っていた。

原因は一覧の返し方。`ThreadState` をそのまま返していたので、会話の中身
（messages/markers/usage）も、走行の事情（resume-point・捨てたセッション・
文脈使用量の内訳）も一緒に出ていた。**一覧は目次に徹する**形に変えた
——id・種類・状態・分岐位置・件数・最初と最後の発言だけ。中身は開いた Project の
分だけ `/api/threads/:id` から取る（同じものを2つの口から返さない、規則3）。

| 測ったもの | 前 | 後 |
|---|---|---|
| Thread 一覧の転送 | 2,875 KB | **17.9 KB**（−99.4%） |
| API 転送合計 | 2,878 KB | **403 KB**（残りは開いた Project の中身） |
| 操作可能まで（中央値） | 1.42 s | **1.03 s** |

> 「操作可能まで」の意味が少し厳しくなっている：**会話の中身が届くまで待つ**
> ようになったので、以前より正直な数字になった（途中の計測では 0.63〜0.88 秒と
> 出たが、それは中身が入る前に「出た」と数えていた）。

**途中で踏んだ2つ**（どちらも「後から届く」を甘く見ていた）：

1. **中身は、一覧の登録より先に届くと捨てられる。** `updateRealThreadData` は
   既に登録された Thread しか触らない——直接 `/p/<id>` を開くと、一覧の読み込み
   （hydrate）と中身の取得が競走して、負けたほうが消えていた。
   **hydrate を待ってから取り込む**（進行中のものは使い回されるので二重には取らない）
2. **後から届いた中身は、会話に入らない。** `useLocalRuntime` は
   `initialMessages` を**作るときにしか読まない**ので、空で組み立ててしまうと
   もう入らない。**中身が揃うまで会話を組み立てない**（0件の Thread は `[]` を
   持つので「まだ来ていない」と区別がつく）

**E2E も直した**：`fork-session` が resume-point を**一覧から**読んでいた
——一覧が目次になった以上、走行の事情は1件ずつの記録から取る。
`global-memory` は、私が足した「走行中に Global Memory を届ける」試験と
**同じ置き場を共有**していて、走る順（worker 2本）で「まだ無い」が壊れた
——順番に意味があるものは同じファイルに置いた（規則6）。
