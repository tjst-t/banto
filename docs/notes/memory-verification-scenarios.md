# 記憶システム 検証プロトコル と シナリオ資産

> **これは手順書である。** コンテキストが切れても、この文書だけで検証を再開・継続できることを目的とする。
> **対象**：Quirefold（`spec-memory`）＋ ADR-0010（Substrate の正典）。
> **なぜ必要か**：外部ベンチマークがこの領域を測れない（→ `spec-memory` §16.1）。シナリオを固定して設計を変え、破綻箇所の増減を見る、という手続きが代替の評価手法として機能している。

---

## 1. 何をどこまで机上で決めるか

**混同しないこと。**

| 机上で**決まらない**（実装と eval が要る） | 机上で**決まる**（設計で閉じる） |
|---|---|
| 参照検出の信頼性（§0.9 最優先） | スキーマの形、フィールドの意味論 |
| 蒸留の品質、虚偽記憶の発生率 | 規則の発火条件・適用範囲・優先順位 |
| 全パラメータの具体値（γ・β・θ_admit 等） | API の境界と、どこに強制を置くか |
| 内部状態が実際に行動を変えるか | 継承・伝播・失効の規則 |

**構造上の欠陥は机上で潰す。** 理由は「後工程が楽になる」より強い——**実装後には直せないものが混じる**からである。

- **Substrate は記憶の蓄積開始時点で凍結する**（ADR-0010）。後から足したフィールドは過去の記憶に遡及できない。**文字通り今しか直せない。**
- 深い睡眠の writer 粒度、閉包レジストリの命名規律などは、変更が書き込み経路の作り直しや数万件の一括 supersede を意味する。
- これらは「測れるようになった頃には手遅れ」な類である。

## 2. 回し方

### 2.1 手順

1. 設計を変える（修正を spec / ADR に適用する）
2. シナリオを選ぶ（§3 のカタログから。**新しい軸を足すことを優先する**、理由は 2.4）
3. サブエージェントを並列で走らせる（Sonnet 級。1シナリオ1体）
4. 各体が**自分で報告をファイルに書く**（§4）
5. 結果を突き合わせ、消えた穴・残った穴・新しく出た穴の3つに分ける
6. `spec-memory` §20.8 の残件一覧を更新し、修正を適用して 1 に戻る

### 2.2 プロンプトの規律（これを崩すと結果が濁る）

- **シナリオ文は固定する。** 読ませる仕様だけ差し替える。そうしないとラウンド間の比較ができない
- **前回の指摘は渡さない。** 渡すと「それを確認するだけ」になり、新しい穴を探さなくなる
- **代わりに「新しく足した機構がこのシナリオで実際に発火するか」を明示的に検査させる**
- 報告フォーマットを固定する（§4）
- 規律を明記する：好意的に解釈しない／実行できない箇所は「実行できない」と書く／書いていないことを補って正当化しない（書いていなければ「未定義」）／節番号を必ず添える／推測は「推測」と明示する

### 2.3 各体に必ず埋めさせるもの

抽象的な「動きそう」を禁じるため、具体値を要求する。

- 作られるエントリの共通コア各フィールドに**実際の値**（id / kind / fact_type / origin / session_id / context{scope,…} / derived_from / external_ref / sensitive / valid_* / version / superseded_by / tombstone）
- 何が検索・注入されるか（§7 の候補集合の前段・入場スコア、§9 の解像度）
- 矛盾の検出・解決・蒸留・睡眠の挙動（§12 / §14 / §18 / §19）
- **driver（§20）が何をするか**：起床源、優先度、点火（§20.4）、再検証キュー
- PO と職人にそれぞれ何が見えるか

### 2.4 軸を増やす > 回数を増やす

**同じシナリオ群での反復は収穫が逓減する。** 実績：R1 は「機構の不在」を、R2 は「機構はあるが点火しない」を、R3 は「境界のずれ」を見つけた——1ラウンドごとに指摘が細かくなっている。

一方、**S11（長期運用）を1本足しただけで、既存10本が3ラウンド・のべ30回で一度も出さなかった Substrate 判定の穴を発見した**。軸が違うと見えるものが違う。

したがって、新ラウンドは「新しい軸のシナリオ」＋「直した箇所を突く既存シナリオ（リグレッション）」の組み合わせで構成する。全件を毎回回す必要はない。

## 3. 終了条件

これを決めないと永遠に回せる。

> **新しい軸のシナリオを回して、(a) Substrate 判定の指摘がゼロ、(b) Policy/Loop の指摘が §20.8 の既知一覧に収まる——この2つが2ラウンド続いたら、構造上の収束とみなして実装フェーズへ移る。**

**「動く」が全シナリオで揃うことを条件にしない。** 3ラウンドで「動く」判定はゼロであり、この基準では永久に終わらない。`条件付きで動く` の**中身が既知に収まること**を条件にする。

収束後に残る未確定は §0.9 の6項目（実装と eval が要るもの）に限られるはずであり、そこからは行動観測（§0.9）と自己改善ループ（`spec-improvement-loop`、対応は `spec-memory` §16.1）で測る。

## 4. ログの残し方

**各サブエージェントは、報告を自分で以下のパスに書き出す**（プロンプトで指示する）。

```
docs/notes/verification-log/r<ラウンド番号>-<シナリオID>.md
```

例：`docs/notes/verification-log/r4-s12.md`

これにより、コンテキストが切れてもログが残る。ラウンドごとの要約（判定表・消えた穴・残った穴・新規）は §6 の履歴に追記する。

## 6. ラウンド履歴

各ラウンドの判定と主要な発見。詳細は `verification-log/` を参照。

### R1（2026-07-26）— Substrate 初版の検証。10シナリオ

判定：動く 0／条件付き 7／実質動かない 1／動かない 2。

**構造的診断**：Quirefold は**規則を書いているが発火条件を書いていない**。§12 は矛盾の裁き方を定めるが検出を定めず、§13 は減衰を定めるが再浮上を定めず、§4 は出典の全消滅のみ定める。原因は §0.2「memory はタイマーを持たない＝判断は driver 側」の帰結で、**判断を全部移した driver（§20・§21）が2節しかない**こと。10体中9体が「Substrate 変更不要、欠けているのは Policy/Loop の配線」と判定。

**教訓**：Substrate で**閉じた列挙は破れ、開いた識別子は破れなかった**。`fact_type` は5シナリオが別カテゴリで破り、`scope` 2値は非開発ドメインが破った。一方 `external_ref.system`（列挙にしない）は汎用性を保つと評価された。→ ADR-0010 第2版で `scope` を閉包識別子へ、`context` を任意特徴量へ。

### R2（2026-07-26）— driver 設計後

判定：動く 0／条件付き 8／動かない 2。

**穴の性質が「機構が存在しない」から「機構はあるが点火しない・網羅が甘い」へ移った。**

解消：訂正の派生記憶への伝播（R1 で3体が指摘）／`superseded`・`tombstone` の候補除外（3体）／`origin` を無視した最新性（2体）／職人の失敗の受け口／アーカイブ層の可視性／`record()` の `external_ref`。

**最大の学び**：効いた機構と効かなかった機構の差は「**実行層・スコア式・API シグネチャに落としたかどうか**」の一点だけ。散文で書いた規律（`sensitive` の扱い・`citations` 検証・`derived_from` の記入義務）は全て素通りした。→ §20.0 の補足に記載。

### R3（2026-07-26）— 点火（①）と実行層への落とし込み（②）の後。S11 追加で11本

判定：動く 0／条件付き 10／動かない 1（S10）。**S1 が「動かない」から脱した。**

発火確認：点火（S1・S2・S4・S5・S7・S9）／版解決（全）／`origin` 優先の実行層強制（S1・S3・S5）／経路B（S2・S5・S9）／`record()` の citations バリデーション（S8・S10）／`worker_result`（S4）。

**S11 が、既存10本が3ラウンドで一度も出さなかった Substrate 判定を発見**（`salience`/`strength` にモデル出所がない）。→ §2.4 の根拠。

残った穴（詳細は §20.8）：`origin` が自己申告のまま（S10、3ラウンド連続で「動かない」）／点火の入口が狭い（4シナリオが独立指摘）／「訂正」の定義を統一した副作用（3シナリオ）／`sensitive` が伝播しない・規則が矛盾（S9）／深い睡眠の全件処理は2〜4年目で破綻（S11）。

**自分で作った負債**：同日に書いた §7ルール4 と §0.3.1 が `assemble_brief()` での `sensitive` の扱いで正面から矛盾／§7 が §23 を参照するが該当規則が存在しない（空リンク）／§20.4 が「2ホップ超は §20.5 で拾う」と書くが §20.5 に項目がない。

### R4（2026-07-26）— 長期・多トピック軸5本＋リグレッション4本

判定：動かない 6（S3・S5・S14・S15・S16、および S10 継続）／条件付き 3（S9・S12・S13）。S3・S5 は**機構が届かない理由が精密に判明したための降格**であり、診断としては前進。

**新しい軸が大量の未発見を出した。** S12〜S16 の5本中3本が「動かない」。既存10本を3ラウンド回して得られなかった種類の指摘であり、§2.4（軸を増やす > 回数を増やす）を裏付けた。

**最も重い発見（S13）**：**クエリ文字列から候補集合を作る索引・検索機構が、どこにも定義されていない。** §8 はクエリの材料を、§12 経路A の LSH は矛盾検出用を、§15 は技法一覧を述べるだけで、`build_context()` の候補生成に配線されていない。R1〜R3 が見つけた「発火条件の欠落」よりさらに手前、**検索の土台の欠落**。候補3,000件→θ超過150〜300件に対し実効容量は数十〜数百件で、**5〜10倍の超過に対する選抜規則も無い**。スコアは絶対値で正規化されていないため、θ_admit は N に対して壊れる。

**Substrate 判定2件**（どちらも蓄積開始前しか直せない）：`subject[]`（3シナリオが独立に収束）／インスタンスをまたぐ `derived_from` のセマンティクス。

**6件すべてに共通する原因**：修正が「1つの層」でだけ行われ、上下の層に同じ規則が配線されていない。→ §20.0 に6項目チェックリスト＋⑦（層をまたぐ配線）を追加し、`spec-memory` §0.3.0 に**書き込み経路の不変条件**を新設して構造的に解決した。

**PO へ上げた件**：ADR-0010 §2.1 の裁定（自動横断＋事後訂正）が依存する Memory 面が、3ラウンド連続で「存在しない」と指摘されている。§20.5-5 の結果の行き先として「提示面が存在しないうちは自動拡大を有効にしない」を実装順序の制約として明記した。
