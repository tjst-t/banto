# 記憶システム 検証プロトコル と シナリオ資産

> **これは手順書である。** コンテキストが切れても、この文書だけで検証を再開・継続できることを目的とする。
> **対象**：Quirefold（`spec-memory`）＋ ADR-0010（Substrate の正典）。
> **なぜ必要か**：外部ベンチマークがこの領域を測れない（→ `spec-memory` §16.1）。シナリオを固定して設計を変え、破綻箇所の増減を見る、という手続きが代替の評価手法として機能している。

---

## 1. 何をどこまで机上で決めるか

**混同しないこと。**

| 机上で**決まらない**（実装と eval が要る） | 机上で**決まる**（設計で閉じる） |
|---|---|
| 参照検出の信頼性（§0.9 最優先） | スキーマの形、フィールドの意味論 |
| 蒸留の品質、虚偽記憶の発生率 | 規則の発火条件・適用範囲・優先順位 |
| 全パラメータの具体値（γ・β・θ_ws・K_ws 等） | API の境界と、どこに強制を置くか |
| 内部状態が実際に行動を変えるか | 継承・伝播・失効の規則 |

**構造上の欠陥は机上で潰す。** 理由は「後工程が楽になる」より強い——**実装後には直せないものが混じる**からである。

- **Substrate は記憶の蓄積開始時点で凍結する**（ADR-0010）。後から足したフィールドは過去の記憶に遡及できない。**文字通り今しか直せない。**
- 深い睡眠の writer 粒度、閉包レジストリの命名規律などは、変更が書き込み経路の作り直しや数万件の一括 supersede を意味する。
- これらは「測れるようになった頃には手遅れ」な類である。

## 2. 回し方

### 2.1 手順

1. 設計を変える（修正を spec / ADR に適用する）
2. シナリオを選ぶ（**§5** のカタログから。**新しい軸を足すことを優先する**、理由は **§2.5**）
3. サブエージェントを並列で走らせる（Sonnet 級。1シナリオ1体）
4. 各体が**自分で報告をファイルに書く**（§4）
5. 結果を突き合わせ、消えた穴・残った穴・新しく出た穴の3つに分ける
6. `spec-memory` §20.8 の残件一覧を更新し、修正を適用して 1 に戻る

### 2.2 プロンプトの規律（これを崩すと結果が濁る）

- **シナリオ文は固定する。** 読ませる仕様だけ差し替える。そうしないとラウンド間の比較ができない
- **前回の指摘は渡さない。** 渡すと「それを確認するだけ」になり、新しい穴を探さなくなる
- **代わりに「新しく足した機構がこのシナリオで実際に発火するか」を明示的に検査させる**
- 報告フォーマットを固定する（§4）
- 規律を明記する：好意的に解釈しない／実行できない箇所は「実行できない」と書く／書いていないことを補って正当化しない（書いていなければ「未定義」）／節番号を必ず添える／推測は「推測」と明示する

### 2.3 各体に必ず埋めさせるもの

抽象的な「動きそう」を禁じるため、具体値を要求する。

- 作られるエントリの共通コア各フィールドに**実際の値**（id / kind / fact_type / origin / session_id / context{scope,…} / derived_from / external_ref / sensitive / valid_* / version / superseded_by / tombstone）
- 何が検索・注入されるか（§7 の候補集合の前段・入場スコア、§9 の解像度）
- 矛盾の検出・解決・蒸留・睡眠の挙動（§12 / §14 / §18 / §19）
- **driver（§20）が何をするか**：起床源、優先度、点火（§20.4）、再検証キュー
- PO と職人にそれぞれ何が見えるか

### 2.4 配線チェック（毎ラウンド必須・シナリオとは別枠）

**シナリオ検証は「振る舞い」を試す。配線チェックは「文書の整合」を静的に検査する。** 別物なので必ず両方走らせる。

R1〜R4 で最も繰り返された欠陥は「**規則を書いて配線を忘れる**」だった。対策として §20.0 にチェックリストを書いたが、**チェックリスト自身が散文の規律であり、誰が呼ぶか・どこで強制するかが空欄**だった。同じ病気に対策が罹っている。したがって規律ではなく**手順**にする——毎ラウンド、専任のエージェントを1体走らせる。

**このエージェントの仕事**（シミュレーションはしない）：

1. `spec-memory` §20.7.1 の**配線レジストリ**の各行について、各欄が**本文で実際に定義されているか**を確認する（表に書いてあるだけで本文に無いものを見つける）
2. **レジストリに登録されていない機構**を本文から探す（未登録＝配線が保証されていない）
3. **宙ぶらりんの参照**：「§X に規定」と書いてあるが §X にその規則が無いもの
4. **能力はあるが呼び出し元が無いもの**（例：フィールドを足したが読む主体がいない）
5. **検出はするが対応が無いもの**（例：点検リストが列挙するだけ）
6. **層をまたいで配線されていないもの**（例：`record()` にだけ書いて `propose()`/`supersede()` に無い規則）
7. **相互に矛盾する2つの記述**

出力は「箇所・種別（1〜7）・該当節・修正案」の表。ログは `verification-log/r<N>-wiring.md`。

**この検査で見つかったものは、シナリオ検証の結果とは別に集計する。** 収束条件（§3）には「配線チェックの指摘がゼロ」を含める。

### 2.5 軸を増やす > 回数を増やす

**同じシナリオ群での反復は収穫が逓減する。** 実績：R1 は「機構の不在」を、R2 は「機構はあるが点火しない」を、R3 は「境界のずれ」を見つけた——1ラウンドごとに指摘が細かくなっている。

一方、**S11（長期運用）を1本足しただけで、既存10本が3ラウンド・のべ30回で一度も出さなかった Substrate 判定の穴を発見した**。軸が違うと見えるものが違う。

したがって、新ラウンドは「**配線チェック1体**」＋「新しい軸のシナリオ」＋「直した箇所を突く既存シナリオ（リグレッション）」の組み合わせで構成する。全件を毎回回す必要はない。

**この手法の限界を明記しておく**（旧 `spec-memory` §20.8 末尾より移設）。R1・R2 は同じ10シナリオを使ったため、**シナリオが最初から見ていない領域の穴は2回とも見つからない**（複数 PO、モデル差し替え、記憶ストアの障害と復旧など）。実際、driver 自身の活動ログの不在（現 §20.8 の U12）は10シナリオのどれも指摘せず、Kobo と driver を並べた対比から出た。**シナリオ検証は「置いた鏡に映るものしか映さない」。** 鏡を増やすこと（§2.5）と、シナリオ以外の見方（配線チェック §2.4、層どうしの対比）を併用することでしか埋まらない。

## 3. 終了条件

これを決めないと永遠に回せる。

> **新しい軸のシナリオを回して、(a) Substrate 判定の指摘がゼロ、(b) Policy/Loop の指摘が §20.8 の既知一覧に収まる、(c) 配線チェック（§2.4）の指摘がゼロ——この3つが2ラウンド続いたら、構造上の収束とみなして実装フェーズへ移る。**

**「動く」が全シナリオで揃うことを条件にしない。** 3ラウンドで「動く」判定はゼロであり、この基準では永久に終わらない。`条件付きで動く` の**中身が既知に収まること**を条件にする。

収束後に残る未確定は §0.9 の6項目（実装と eval が要るもの）に限られるはずであり、そこからは行動観測（§0.9）と自己改善ループ（`spec-improvement-loop`、対応は `spec-memory` §16.1）で測る。

> **この条件は満たされないまま、2026-07-26 に PO が Substrate を凍結して実装へ移った** 【追記】。R6 時点で3条件とも未達であり、**新しい軸を足すたびに新規指摘が出続けて、条件が満たされる見込みが立たなかった**（§6.0）。
>
> **条件を下げたのではない。** 適用範囲を狭めた——**Substrate（不可逆）については「残る Substrate 判定を潰す」を終了条件に置き換え**、Policy/Loop（可逆）は行動観測と自己改善ループへ委ねた。§1 の表「机上で決まる／決まらない」の線引きは、**実際には「机上で決めないと手遅れになる／ならない」の線引きだった**——後者は実装しながら直せる。この読み替えが本プロトコルの最大の学びである。

## 4. ログの残し方

**各サブエージェントは、報告を自分で以下のパスに書き出す**（プロンプトで指示する）。

```
docs/notes/verification-log/r<ラウンド番号>-<シナリオID>.md
```

例：`docs/notes/verification-log/r4-s12.md`

これにより、コンテキストが切れてもログが残る。ラウンドごとの要約（判定表・消えた穴・残った穴・新規）は **§7 のラウンド履歴**に追記し、次の一手は §6 を書き換える。

## 6. 現在地と次の一手 【ここから読めば再開できる】

**最終更新：2026-07-26（R6 終了時点）。** ブランチ `explore/agent-primary`。

### 6.0 Substrate は凍結された 【2026-07-26】

**PO 裁定：`asserted_by[]` を追加し、Substrate を凍結して実装に入る。**

- R6／S18 が指摘した「`origin: user_explicit` に誰の言明かが無い」（旧 U1）に対し、**`asserted_by[]`**（開いた識別子の配列）を追加した。ADR-0010 §9・不変条件 I10。**記録だけ残し、多人数運用の振る舞いは実装しない**（VISION の `out_of_scope`）。
- **`person` の予約語問題（U2）は足さずに凍結した。** 多人数機能と不可分で安価な保険にならないため。踏み込むなら ADR-0010 の supersede が必要。
- ADR-0010 は `status: accepted`。**凍結の範囲と、凍結によって受け入れたリスクは ADR-0010 の「凍結」節が正典。**

**凍結の理由は「収束したから」ではない。** §3 の条件は R6 時点で3条件とも未達であり、**新軸を足すたびに新規指摘が出続けて条件が満たされる見込みが立たなかった**。PO の判断は「Substrate の残件だけ潰して固め、残りは実装しながら直す」である。

**したがって §3 の収束条件は、Substrate については役目を終えた。** Policy/Loop については、以後は机上検証ではなく **§0.9 の行動観測と `spec-improvement-loop`** で測る（`spec-memory` §16.1）。**この文書の役割は「実装前に構造を固める手続き」から「設計変更時のリグレッション資産」へ変わる。**

### 6.1 次にやること（実装フェーズ）

**実装前に決めるべきものは全部決めた**（2026-07-26）。判定軸と根拠は `spec-memory` §20.8「実装前に決めるべきものと、後で直せるもの」。

| 項目 | 決着先 |

| **U4・U5** 深い睡眠と再索引のスケーリング | `spec-memory` §18.1 |

**残るのは実装である。** 未解決は `spec-memory` §20.8 の U6・U7・U9〜U20（すべて可逆。既存エントリを書き換えずに直せる）と、§0.9 のパラメータ（実装と eval が要る）。

**ただし全件が「未再検証」である。** 上の6件はいずれも配線チェックを通したが、**シナリオ検証は一度も回していない**。§18.1・§26 を突くシナリオ（S17 の再走、S11 の長期運用、S16 の引き継ぎ）は、実装が動き出してから**リグレッションとして**回すのが順序として正しい——机上でこれ以上回しても、R6 で確認したとおり新軸が新規指摘を出し続けるだけである。

### 6.2 決着済み（触り直さないこと）

- **自動横断の担保**（2026-07-26）— 論点は「UI をいつ書くか」ではなく**流量**だった。§12 の B1〜B6 が決定的なバーを置き、面（Memory 面）ができるまで自動拡大を有効にしない、という実装順序の制約で閉じた。
- **検索機構**（R6）— `spec-memory` §8.5。候補生成・選抜・θ の形・横断・エンティティ逆引きの5点すべて決着。**θ は絶対値のまま残し、定員（相対）と併用する**という形に落ちた。
- **深い睡眠のスケーリング**（§18.1）— 2フェーズ＋ローリング全件走査。**閉包でシャードしても B1〜B6 が壊れないのは、兄弟方向の入口を `entity_index` への問い合わせにしたから**。
- **閉包レジストリ**（§26）— **識別子を不変にし、改名を表示名の変更に限る。** これで「命名規律の変更＝数万件の一括 supersede」が構造的に発生しない。
- **インスタンスをまたぐ出典**（ADR-0010 §10）— `derived_from` はストア内で必ず解決でき、またぐものは `external_ref`。ADR §4 の「型を混ぜない」の適用で決まった。

- **どのラウンドが何を見つけ、何をどう直したか** → 本ノート §7
- **次に何をするか** → 本ノート §6.1

**Substrate は 2026-07-26 に凍結した**（§6.0）。U 番号のうち Substrate に触れるのは次の2つだけで、**どちらも「凍結時に受け入れたリスク」として ADR-0010 の凍結節に明記されている**——**U2**（`person` が非パラメータの予約語。踏み込むなら ADR の supersede が必要）と **U3**（インスタンスをまたぐ `derived_from` の意味論。未定義のまま凍結）。残り18件は可逆。

### 6.4 この作業で学んだ規律（繰り返さないために）

- **実行層・スコア式・API シグネチャに落ちた規律だけが機能する。** 散文で書いたものは全て素通りした（R2 の最大の学び、§20.0 に記載）。**R6 では、この規律を知ったうえで書いた新設節の中で、同じ日に2回破った**——判定材料がシグネチャに無いゲート、適用場所の無い免除規則。**知っていても防げない。検査で拾うしかない。**
- **規則を書いたら【①いつ発火 ②何をする ③誰が呼ぶ ④どこで強制 ⑤入力は誰が用意 ⑥結果はどこへ行く ⑦層をまたいで配線したか】を埋める**（§20.0）
- **ただしチェックリスト自体は散文なので、それだけに頼らない。** 配線レジストリ（§20.7.1）＋毎ラウンドの配線チェック（§2.4）が③④を埋める
- **同じ病気が3つの形で出る**：規則はあるが発火条件がない／発火条件はあるが対応がない／能力はあるが呼び出し元がない。全部「部品を足して繋ぐのを忘れる」
- **配線レジストリは新規機構に偏る。** R6 の配線チェックは、既存の中核（I1〜I8・話題転換の検出・睡眠の発火・`propose()` の呼び出し）が**一度も登録されていない**ことを見つけた。**新設のたびに足すだけでは、古い機構が永久に未登録のまま残る。** 一度棚卸しをした（R6）が、これは定期的に要る
- **一方の側を直すと反対側に穴が開くことがある。** R6 の横断ファンアウト（読み）は、`person` 水準セッションを実用的にすることで、無審査の `scope` 拡大（書き）を到達可能にした。**「書き込み側は緩めない」と宣言しただけでは緩む。** 変更を入れたら、逆側の層で何が到達可能になったかを問う
- **無情報な項は絶対閾値を壊す。** 関連度を正規化しても、候補を区別しない項が定数として式に残れば、全体が一様に下がって絶対下限にだけ効く（R6／S13）。**正規化すべきは項ごとに判断する**
- **軸を増やす > 回数を増やす**（§2.5）。R6 は新軸2本のうち2本が「動かない」で、既存4本には無い種類の指摘を出した
- **閉じた列挙は破れ、開いた識別子は破れなかった**（R1 の教訓）

### R1（2026-07-26）— Substrate 初版の検証。10シナリオ

判定：動く 0／条件付き 7／実質動かない 1／動かない 2。

**構造的診断**：Quirefold は**規則を書いているが発火条件を書いていない**。§12 は矛盾の裁き方を定めるが検出を定めず、§13 は減衰を定めるが再浮上を定めず、§4 は出典の全消滅のみ定める。原因は §0.2「memory はタイマーを持たない＝判断は driver 側」の帰結で、**判断を全部移した driver（§20・§21）が2節しかない**こと。10体中9体が「Substrate 変更不要、欠けているのは Policy/Loop の配線」と判定。
