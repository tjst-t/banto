# 記憶システム検証シナリオ（10本）

> **用途**：Quirefold（`spec-memory`）の設計を変えたら、この10本を回して破綻箇所の増減を見る。外部ベンチマークが当たらない領域（→ spec-memory §16.1）での実用的な評価手法として、2026-07-26 に2回実施し機能した。
> **回し方**：シナリオ文は固定。読ませる仕様だけ差し替える。**前回の指摘は渡さない**（渡すとそれを確認するだけになり、新しい穴を探さなくなる）。代わりに「新しく足した機構がこのシナリオで実際に発火するか」を明示的に検査させる。
> **実施記録**：1回目＝ADR-0010 §6（Substrate 初版の検証）／2回目＝spec-memory §20.8（driver 設計後）。いずれも Sonnet 級のサブエージェント10体を並列実行。

## 共通の設問

各シナリオをターン単位で具体的にシミュレートさせる。抽象的な評価を禁じ、以下を必ず埋めさせる。

- 作られるエントリの共通コア各フィールドに**実際の値**（id / kind / fact_type / origin / session_id / context{scope,…} / derived_from / external_ref / sensitive / valid_* / version / superseded_by / tombstone）
- 何が検索・注入されるか（§7 の候補集合の前段・入場スコア・滞在スコア、§9 の解像度）
- 矛盾の検出・解決・蒸留・睡眠の挙動（§12 / §14 / §18 / §19）
- driver（§20）が何をするか：起床源、優先度、再検証キューに積まれるか
- PO と職人にそれぞれ何が見えるか

報告は「動くこと／破綻・穴（各項目に **Substrate か Policy/Loop か**の判定を付す）／最小の修正案／判定（動く・条件付きで動く・動かない）」。

**規律**：好意的に解釈しない。実行できない箇所は「実行できない」と書く。書いていないことを補って正当化しない（書いていなければ「未定義」）。節番号を必ず添える。推測は「推測」と明示する。

## 2回目で確かめられたこと

- **解消**：訂正の派生記憶への伝播（1回目に3体が指摘）／`superseded`・`tombstone` の候補除外（3体）／`origin` を無視した最新性（2体）／職人の失敗の受け口／アーカイブ層の可視性／`record()` の `external_ref`
- **残存**：spec-memory §20.8 に一覧
- **最大の学び**：効いた機構と効かなかった機構の差は「**実行層・スコア式・API シグネチャに落としたかどうか**」の一点だけだった（§20.0 の補足）

## この手法の限界

**2回とも同じ10本を使ったため、シナリオが最初から見ていない領域の穴は2回とも見つからない。** 実際、「driver 自身の活動ログの置き場が無い」（§20.8-6）は10本のどれも指摘せず、Kobo と driver を並べた対比から出た。カバーできていない領域の候補：

- 複数 PO／権限の異なる利用者
- LLM プロバイダやモデルの差し替え（決定②のプラガブル層）
- 記憶ストアの障害・復旧・マイグレーション
- 記憶が数十万件に達したときの性能とコスト
- 番頭自身の自己改善（層A/B の変更が記憶に与える影響）

設計が固まった段階で、**シナリオ自体を入れ替えた回**を別途行う。
