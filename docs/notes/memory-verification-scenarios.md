# 記憶システム検証シナリオ（10本）

> **用途**：Quirefold（`spec-memory`）の設計を変えたら、この10本を回して破綻箇所の増減を見る。外部ベンチマークが当たらない領域（→ spec-memory §16.1）での実用的な評価手法として、2026-07-26 に2回実施し機能した。
> **回し方**：シナリオ文は固定。読ませる仕様だけ差し替える。**前回の指摘は渡さない**（渡すとそれを確認するだけになり、新しい穴を探さなくなる）。代わりに「新しく足した機構がこのシナリオで実際に発火するか」を明示的に検査させる。
> **実施記録**：1回目＝ADR-0010 §6（Substrate 初版の検証）／2回目＝spec-memory §20.8（driver 設計後）。いずれも Sonnet 級のサブエージェント10体を並列実行。

## 共通の設問

各シナリオをターン単位で具体的にシミュレートさせる。抽象的な評価を禁じ、以下を必ず埋めさせる。

- 作られるエントリの共通コア各フィールドに**実際の値**（id / kind / fact_type / origin / session_id / context{scope,…} / derived_from / external_ref / sensitive / valid_* / version / superseded_by / tombstone）
- 何が検索・注入されるか（§7 の候補集合の前段・入場スコア・滞在スコア、§9 の解像度）
- 矛盾の検出・解決・蒸留・睡眠の挙動（§12 / §14 / §18 / §19）
- driver（§20）が何をするか：起床源、優先度、再検証キューに積まれるか
- PO と職人にそれぞれ何が見えるか

報告は「動くこと／破綻・穴（各項目に **Substrate か Policy/Loop か**の判定を付す）／最小の修正案／判定（動く・条件付きで動く・動かない）」。

**規律**：好意的に解釈しない。実行できない箇所は「実行できない」と書く。書いていないことを補って正当化しない（書いていなければ「未定義」）。節番号を必ず添える。推測は「推測」と明示する。

**S11 の年表**（シミュレートさせる筋）

- **1〜2年目**：banto 開発。順調に運用。記憶が数万件に達する
- **2年目**：家計ドメインを増設。**3年目**：健康、執筆と続き、Kobo を含めて4ドメインが常時稼働
- **3年目**：LLM プロバイダを乗り換える（決定②のプラガブル層。Anthropic → ローカルモデル）。**embedding モデルも変わり、索引を再生成する**
- **4年目**：banto プロジェクト自体が一区切りついて休止。1年後に復活する
- **5年目**：**PO の役割が変わる**。自分でコードを書かなくなり、判断の粒度が上がる。5年前の `preference_decision`（「`any` は理由コメント必須」等）の多くが、もう本人の関心事ではない
- **5〜10年目**：記憶が100万件規模。自己改善ループ（`spec-improvement-loop`）が5年分の層A/B変更と revert 履歴を積み上げている

**特にこの11本目で問うこと**

1. **蓄積に耐えるか** — 深い睡眠は一晩で終わるか。§14 は「差分のみだと数週間のパターンを見逃し、全件処理はコストが線形に増える」と自認している。100万件でこの二段構えは成立するか。§15 のコスト削減策で足りるか
2. **世代交代の較正** — `confidence` / `salience` / `strength` は**モデルに依存して付いた値**である。プロバイダを乗り換えると、旧モデルが付けた値と新モデルの値が同じスケールで混在する。§16 の指標も断絶する。**この較正について設計は何か言っているか**
3. **Substrate が足りないと分かったとき** — 5年運用して初めて「このフィールドが要る」と判明したら何ができるか。ADR-0010 は「凍結点は蓄積開始時点」と定めた。移行スクリプト＋再蒸留のコストと、過去の記憶に遡及できない範囲を具体的に見積もれるか
4. **閉包レジストリの肥大** — 4ドメイン × 数十プロジェクト × リポジトリ階層で、閉包木は何段・何ノードになるか。`scope` の包含解決は現実的なコストで回るか。死んだプロジェクトの閉包はどう畳むか
5. **古い `preference_decision` の失効** — 5年前の PO の選好に `valid_until` は誰も付けていない。`preference_decision` は「最新性が勝つ」が、**競合する新しい言明が無ければ古いものが勝ち続ける**。PO の変化にどう追随するか
6. **自己改善ループの堆積** — 5年分の層A/B の変更と revert 履歴。`meta/config.yaml` が誰にも理解できない状態にならないか。improvement-loop のメタケイデンス（ループ自身の健康）はこれを検知できるか
7. **番頭の一貫性 vs PO の変化** — §22 self-model は人の明示承認でしか変わらない。5年で PO は変わるが self-model は承認された時点で止まる。ゴールドリフト（§25）の長期版として、**「変わらないこと」が害になる**場合をどう扱うか
8. **撤退可能性** — やめたくなったとき、記憶を取り出せるか。SKILL.md はファイルなので出せるが、意味記憶の出典グラフごと外に出す手段はあるか

## 2回目で確かめられたこと

- **解消**：訂正の派生記憶への伝播（1回目に3体が指摘）／`superseded`・`tombstone` の候補除外（3体）／`origin` を無視した最新性（2体）／職人の失敗の受け口／アーカイブ層の可視性／`record()` の `external_ref`
- **残存**：spec-memory §20.8 に一覧
- **最大の学び**：効いた機構と効かなかった機構の差は「**実行層・スコア式・API シグネチャに落としたかどうか**」の一点だけだった（§20.0 の補足）

## この手法の限界

**2回とも同じ10本を使ったため、シナリオが最初から見ていない領域の穴は2回とも見つからない。** 実際、「driver 自身の活動ログの置き場が無い」（§20.8-6）は10本のどれも指摘せず、Kobo と driver を並べた対比から出た。カバーできていない領域の候補：

- 複数 PO／権限の異なる利用者
- LLM プロバイダやモデルの差し替え（決定②のプラガブル層）
- 記憶ストアの障害・復旧・マイグレーション
- 記憶が数十万件に達したときの性能とコスト
- 番頭自身の自己改善（層A/B の変更が記憶に与える影響）

設計が固まった段階で、**シナリオ自体を入れ替えた回**を別途行う。

**2026-07-26 に S11（長期運用）を追加**。上の候補のうち「モデル差し替え」「数十万件規模」「番頭自身の自己改善が記憶に与える影響」を1本に束ねた。残る未カバーは**複数 PO／権限の異なる利用者**と**記憶ストアの障害・復旧**。前者は現行 VISION が「一人の PO」を前提としているため優先度が低い。後者は実装フェーズで扱う。
