# 2026-09-02 FileSystem Module の設計検討

`docs/specs/v4-modules.md` §2.2 として決定した内容の経緯。決めた結論だけを
仕様に書き、検討の過程・却下した案はここに残す。

## 出発点

FileSystem は v4-modules.md §2 で「ファイルを読む・書く」の一行しか無く、
tool/resource の中身が未設計だった。Vault（§2.1）と同じ粒度まで詰めてから
モックに進む、という順で検討した。

## 1. tool の語彙

ゼロから設計せず、MCP 公式の filesystem リファレンス実装の tool 名・引数の
形をそのまま採用した（規則12）。独自の語彙を発明するコストも、他実装との
差異による混乱も避けられる。

## 2. 承認ゲート——「ストームになるのでは」という懸念

**検討の発端**：`writeFile`/`deleteFile` に、Vault の B節のような独自の承認
スキームを作るべきか、という問い。ユーザーから「承認ストームになると嫌」
という懸念が出た。

**却下した案**：FileSystem 用に「初回のみ確認、以降は自動」のような独自ポリシーを
新規設計する。

**採った案**：何もしない。この問題への対処は既にアーキ仕様 §6.0（2026-08-31）で
Agent SDK に委ねると決定済み——`canUseTool` フック＋`permissionMode`の`'auto'`
（モデル分類器が許可/拒否を自動判定し、人に上げるのは本当に必要なものだけ）。
FileSystem は Vault の B/C節のような Module 間中継tool ではなく、Runner が
直接呼ぶ`agent`可視性の tool なので、素直にこの一般機構の対象になる。
**新しく設計することが「決定」だった**（規則12）。

## 3. resource——Command Palette 統合は新しい設計か

**検討の発端**：ユーザーから「Command Paletteへの資源の組み込みをここで
新規に検討するのか」という確認が出た。

**確認した内容**：これは FileSystem 固有の新しい統合ではなく、アーキ仕様
§6.3で確定している一般則（`resources/templates/list` + `completion/complete`
に、数えきれない資源を持つ Module はすべて乗る）がそのまま適用されるだけ。
実際、モックの `mock/lib/mock/palette.ts` には `MOCK_FILES` という名前で
この形の足場が2026-09-02より前から既にあった（`banto.fs の資源
（completion 相当）` というsubtitleつき）。**検討済みの一般原則を、
FileSystem に個別適用する場面で「新規の検討が要る」と早合点しかけた**、
という経緯。§6.3を読み返して解消した。

## 4. Canvas プレビュー——非テキスト対応と拡張性

**要望**：`readFile`は画像・PDF・Markdown・HTML等、テキスト以外もできる限り
対応したい。対応形式は後から簡単に増やせるようにしたい。

**設計**：
- tool 結果の型は MCP の content block（`text`/`image`/`resource`）にそのまま
  乗せる——新しい型を作らない。画像は`image`で返すことで、**モデルがそのまま
  見られる**という副産物がある
- Canvas 側のレンダリングは、拡張子/MIME→レンダラーの**内部対応表**として
  FileSystem Module 自身の実装に閉じる。契約（tool/resourceの形）には現れない
  ので、対応形式を増やしても core・他 Module に影響しない

これにより「対応ファイルを増やす」ことと「Module の契約を変える」ことが
分離された——増やすたびに仕様を変える必要が無い。

## 5. モックUI——ファイルブラウザの2ペイン化・ダウンロード/アップロード

launcher が開くファイルブラウザ（fullscreen）を、VSCode のエクスプローラを
参考にした2ペイン（左：フォルダツリー、右：選択中ファイルの中身）に作り替えた。
ここで「ダウンロード／アップロードは新しい tool が要るか」という論点が
出たが、**要らないと判断した**——Vault の C節（backend 自身の`ui://<id>/config`
が自分の tool を呼ぶだけ）と同じ形で、ブラウザ UI 自身が`readFile`/`writeFile`
を内部的に呼べば足りる。複数選択のZIPダウンロードも launcher 側（Module実装）
の仕事であって、AI向けの新しいtool（例えば`downloadZip`のようなもの）は
増やさない。

**モックでは実際のZIP生成をしていない**——`jszip`等の新規依存を、UIの
決定に不要なもの（バイト列の正しさ）のために足す理由が無いため（規則10）。
選択→ボタン→トースト、という操作の流れだけを再現し、単一ファイルの
ダウンロードはテキスト系ファイルに限り実際にBlobダウンロードさせて
（標準Web APIのみ、新規依存なし）手触りを持たせた。
