## #212 ターンが先に終わると、畳んだカードが答えられるように見えたまま

- 原因：会話のカードが答えを知る道は、ターンの流れ（`answered`）だけだった。host がカードを畳むのは聞いた呼び出しが
  終わったとき（ターンが先に終わっている）なので、届け先の流れがもう無い
- 直し：host の受信箱に「判断待ちに答えが付いた」の聞き手（`InboxStore.onJudgmentAnswered`）を置き、ターンをまたぐ知らせ
  `judgment.answered` を流す（`/api/events`）。画面は受け取った答えを覚え（`lib/backend/judgment-answers.ts`）、カードは
  それでも答え済みになる。答えの言葉は流れの `answered` と同じ関数（`inbox/answer-text.ts`）
- 却下：受信箱を取り直して「開いた一覧に無ければ答え済み」と見る——出したばかりの判断待ちが一覧に載る前に見ると、
  答えていないのに答え済みに見える。答えの言葉も分からない
- 見た目は新しく足していない：答えたカードと同じ「回答：…」

## #213 カードが出ている間、止めるボタンが出ない

- 原因：assistant-ui は判断待ち（requires-action）の間を「走っていない」と数え、停止ボタン（`ComposerPrimitive.Cancel`）を
  出さず、押せなくもする。だが実 Thread の run はカードを出したあとも host の流れを読み続けていて、ランタイムの
  `cancelRun` はその間も止める合図を届けられる（assistant-ui の `cancelRun` は状態を見ずに abort する——読んで確かめた）
- 直し：run が流れを読み続けている間だけ「人を待っている」を立て（`useRealRunAwaitingHuman`）、そのとき送るボタンの位置に
  同じ見た目の停止ボタンを出す。押すと `cancelRun`——停止ボタンと同じ止め方（`stopOnHost`）
- 台本の会話（モック）は requires-action で run を終えるので立たない——押しても何も起きないボタンを出さない（規則13）
- **止めると、中継のカードは「答え済み」ではなく会話から消える**。止めたターンは記録から組み直す（§6.31「ここで止めました」）
  が、中継のカードは記録に載らない——止めたターンの tool のカードも一緒に消える。受信箱からも消える（host が畳む）。
  答え済みのまま残すには中継のカードを記録に載せる必要があり、今回はしていない（ユーザーに上げる）

## #214 受信箱から中継の承認に答えられない

- 原因：受信箱は「Thread を開くだけ」と決めていた（§2.4.1、2026-09-06——操作口を2つ持たない）。中継のカードは走っている
  ターンの流れにしか描かれないので、会話で見失うと答える手段が無かった
- host 側は前から答えられた：`/api/inbox/:id/answer` は中継の承認の待ちも解く（ゲートが同じ登録簿に待ちを置いている）
- 直し：受信箱の判断待ちの行のうち `source: "relay"` のものに、会話のカードと同じ部品（`ElicitationFormView`）で選択肢を出す。
  送る道も会話のカードと同じ（`answerRealJudgment`、`sendRealAnswer` から切り出した）。会話のカードは、ターンの流れの
  `answered` と `judgment.answered` で答え済みになる
- 2つの口の食い違いは、部品と送る道を1つにすることで抑える（規則3 の懸念への答え）
- 中継の承認だけにした：指示の範囲。tool の承認（canUseTool）も host 側は同じ口で答えられるが、今回は出していない
