# 起こし直しをまたいで続ける——今の作りと実測（2026-10-04）

Backlog のストーリー resume-across-restart の検討。Fork「起こし直しをまたいで続ける」。

## 今の作り（コードを読んで分かったこと。起こし直しの実地では未確認）

- **途中だったターン**：人の発言（と積んだ届いたもの）は記録に残る。AI の返事は記録されず、resume-point も更新されない
  （`turn-runner.ts`——resume-point と返事はターンの最後に1回だけ書く）。「ターンが始まった」は Event Store に残らない
  （`ThreadTurns` はメモリだけ）ので、起き直した host は走っていたターンがあったことを知らない。新しい会話の最初の
  ターンは session id（`system/init` で分かる）も残らない
- **返事待ちの札**（runInBackground のサブエージェント等）：起動時に `deliverLostReply` が「途中で終わりました」を
  届け、AI が起きる（`cli.ts`）
- **判断待ち**：起動時に `expireOrphanedJudgments` が期限切れにする
- **Subagent**：走っている仕事の記録（`RunLog.running`）はメモリだけ。終わったものだけ `runs.jsonl`。ACP の `session/load`
  で続きから頼む口（`sessionId`）はもうある
- **起こす仕組み**：起動後に `deliveries.resumeAll()` が、届いていて起こしていない Thread のターンを回す。ここに
  「途中で切れました」を届ければ続きのターンを始められる
- **Factory の仕様の前提**（v4-modules.md §4.5「記録と再開」）：「Factory が起き直しても Subagent は走り続けている」。
  host を起こし直すと両方止まるので、この前提は host の起こし直しでは成り立たない

## 実測（2026-10-04、プローブ `.worktrees/resume-probe/banto/probes/`。偽の Anthropic API で、本物のモデルは使っていない）

本物のモデルを使わなかった理由：サブエージェントの Bash には `CLAUDE_CODE_OAUTH_TOKEN` が渡らない（CLI が外す）。
API に送られた要求の中身（＝モデルが見るもの）を記録した。

### Agent SDK（query、0.3.281＝CLI 2.1.281。banto core と同じ版）

## 実装の最初の確かめ（resume-restart-measure、2026-10-05）

### M4. host が止まったとき、コンテナの中の Module とその子は止まるか

プローブ `banto/probes/m4-incus-exec.mjs`。この Project のコンテナの中の Incus に使い捨てのコンテナ（rs-probe）を立て、
banto と同じ形（`incus exec <名前> -- /bin/sh -c "exec node …"`、stdio は pipe、tty なし）で「Module」を起こした。
Module は子を2つ持つ（同じプロセスグループの `sleep 600` と、別グループの `sleep 600`）。呼び出し元の `incus` クライアントを
止めて中を数えた。

| 呼び出し元への信号 | Module（node） | 同じグループの子 | 別グループの子 |
|---|---|---|---|
| SIGTERM | 2秒以内に止まった | **残った**（10秒後も） | **残った** |
| SIGKILL | 2秒以内に止まった | **残った** | **残った** |

- **Module は host と一緒に止まる**（仕様の見込みどおり）。Module は起き直した host が起こし直す
- **Module が起こしたコマンドは止まらずに残る**（親を失って動き続ける）。Shell の `runCommand` の長いコマンドは、起こし直したあとも
  コンテナの中で走り続け、結果はどこにも返らない。続きの AI が同じコマンドを流し直すと二重に走る
- → 「結果は分かりません。確かめてから進めてください」の文面は正しい。加えて「まだ動いているかもしれない」ことを書く。
  残ったコマンドを Module が起き直したときに片づけるか（Shell が起こしたプロセスを覚えておいて止める）は別に決める

### M1〜M3（2026-10-05、プローブ `banto/probes/m-sdk.mjs`・`m3-host.mjs`・`m3.mjs`。偽の API、SDK 0.3.281）

**前提の訂正**：`rewindTo`（`resumeSessionAt`）は「次のターン以降も渡し続ける」のではない——`thread.resume_point_updated`
のたびに消える（`fold.ts`）。巻き戻したターンが最後まで行けば次からは付かない。**起こし直しで切れたときだけ残り、次の
ターンでもう一度渡される**。

**M1：巻き戻したあと、`resumeSessionAt` 無しで resume したとき CLI はどの鎖から続けるか**

| ケース | 次のターンの要求に入った発言 |
|---|---|
| 巻き戻したターン3が完了 | TURN1・TURN3（新しい鎖） |
| ターン3を SIGKILL | TURN1・**TURN2**（取り消した古い鎖が戻る） |
| ターン3をプロセス木の全部に SIGTERM | TURN1・TURN3（新しい鎖、CLI が終わり際に書く） |
| 同じ `resumeSessionAt` を渡す（SIGKILL・SIGTERM とも） | TURN1 だけ（ターン2もターン3も入らない） |
| SIGKILL のあと `getSessionMessages` の鎖の最後の uuid を渡す | 失敗「No message found with message.uuid of: …」 |

CLI はターンの終わりに書く `last-prompt`（`leafUuid`）の行で鎖を選んでいる（その行を消すと古い鎖に戻った）。SIGKILL では
書かれない。`getSessionMessages` は新しい鎖を返し、CLI は古い鎖を選ぶ——**SDK の読む口と CLI の選び方が食い違う**。
→ **切れたターンが巻き戻しの上にあったら、`resumeSessionAt` を保ったまま続ける**（今の作りのまま）。そのとき切れたターンの
人の発言と途中の作業は CLI から消えるので、**続きの文に切れたターンの人の発言（と届いたもの）を入れ直す**

**M2：記録の無い最初のターン**

- `system/init` 直後の SIGKILL で記録ファイルは10回中10回できない
- resume すると `system/init` は来ず `result`（`subtype: error_during_execution`・`num_turns: 0`・`errors: ["No conversation found with session ID: …"]`）
  のあと例外。使っていない id と同じ形
- **走らせる前に `getSessionInfo(id)` が `undefined` かで記録の有無が分かる**（文言に頼らない）
- 記録が無ければ、同じ `options.sessionId` を渡して resume 無しで走らせ直せる。記録が有るのに同じ `sessionId` で新しく走らせると
  「Session ID … is already in use」（result 無しで exit 1）
→ **最初のターンは banto が session id を先に決めて `options.sessionId` で渡す**（`system/init` を待たずに記録できる）。
起き直したら `getSessionInfo` で記録の有無を見て、無ければ同じ id で走らせ直し、有れば resume

**M3：host（親）が止まったとき**

- host に SIGTERM（host は保存して `process.exit(0)`。SDK は exit で起こした CLI に SIGTERM）：bash・sleep は 250ms 以内に消え、CLI は
  2〜2.5秒孤児で生きて記録に `tool_result(is_error):"Exit code 137"` を書いた（resume すると AI はそれを見る）
- host に SIGKILL（落ちたとき）：CLI・bash・sleep が全部生き残り、孤児の CLI は tool を最後までやって **API にもう1回要求を出し**
  返事を記録に書いた（約2分）
→ 落ちたあとに孤児の CLI が同じ記録に書き続けうる。**systemd が cgroup ごと刈る（`KillMode=control-group`）ことを前提にし、
起き直したときにそれを確かめる**（設定は host で確認待ち）。banto の Runner は組み込みの Bash を使わない（tool は Module 経由）
ので、Bash の子の形は banto とは違う

## 実装の1つめ：ターンの進み具合を残す（resume-turn-events、2026-10-05）

仕様 §2.5「1. Thread のターンを続ける」のうち、`turn.started`・`turn.session_known`・`turn.ended` を書くこと、
切れたターンを見分けること（`findInterruptedTurns`）、新しい会話の session id を host が先に決めること。続ける処理は次。

実装で決めたこと（仕様の該当の箇条に反映）：

- **`turn.started` は発言を積むより先**：あとにすると「このターンで積んだ発言」が seq から引けない（直前の
  user の並びを推すことになる）。先に書いて発言の前に落ちた場合は、発言の無い切れたターンになる——人の発言は
  HTTP の要求の中にしか無かったので、どちらでも失われる。届いたものは待ち行列に残っているので、`resumeAll` が起こす
- **始めた時刻は出来事の ts**：payload に同じ時刻をもう1つ持たない（規則3）
- **`turn.session_known` は毎ターン書く**（resume のターンでは resume-point と同じ id）：`system/init` まで行ったか
  の印にもなる。1ターン1件
- **閉じて開き直した Thread**：閉じた時点で走っていたターンは続けない（印は消えない）
- **終わりは `runThreadTurn` の finally で1回**：done→completed、stopped→stopped、それ以外（error・例外・呼び出し
  側が読むのをやめた）→failed。書けなければログに残す（起き直したら切れたターンに見える）

試験で確かめたこと：偽の Runner が `system/init` のあと返らない（＝host がそこで止まった）状態から、開き直した
store で1件。`system/init` の前に止まっても先に決めた id で1件。resume-point を書いたあと（返事の記録）で止まったら
0件。開き直したあと Clear したら0件。実装の該当行を1つずつ壊して（17か所）、どれも試験が落ちることを見た。

気づいたこと（未決）：

- 偽の Runner でしか通していない。banto の host から本物の SDK に `options.sessionId` を渡して走らせたことはまだ無い
  （`system/init` がその id を名乗ること・記録ファイルがその名前になることは、ここでは確かめていない）
- 1ターンにつき Event Store の書き込みが3件増える（started・session_known・ended）

## Fable のレビューを受けた直し（2026-10-05）

1. **何も積まずに切れたターン**：`InterruptedTurn.stackedMessages`（`startedSeq` より後ろの user の発言の数）を足した。
   0 なら続けない——AI にはまだ何も渡っておらず、届いたものは待ち行列に残っていて `resumeAll` が起こす。人の発言は
   HTTP の要求の中にしか無かったので、どちらにしても残っていない（続けても空のターンになる）
2. **人が止めた直後に落ちる窓**：止めると決めた時点（`abortTurn.abort()` の前）で `turn.ended("stopped")` を書く。
   印の出来事を足すより単純なので、終わりを前に出した。書いたら finally では書かない（二重にしない）。書けなかったら
   CLI は止め、finally がもう一度書こうとする
3. **Clear の防御の穴**（前からある）：新しい会話の最初のターン・Fork の最初のターンを走行中に Clear すると、
   resume-point に自分の会話が無い（新しい会話は undefined、Fork は親から借りた id）ので、Clear が捨てる側に入るのは
   それだけ。終わりに来た resume-point の更新（新しい会話・分けた会話の id）がそのまま入り、Clear を取り消していた。
   Clear のとき最後のターンの `assignedSessionId`・`knownSessionId` も捨てた側に入れる
4. **Fork の最初のターンも session id を先に決める**：下の実測 F1 で SDK が受けることを確かめた
5. 小さいもの：画面に出す走り始めた時刻を `turn.started` の ts にそろえた（`TurnEventBus.setStartedAt`。`begin` は
   始まりを書くより前に呼ぶので、時刻はあとから直す）／`turn.started` が resume-point・巻き戻しの位置を写して持つ理由
   （続けるには始めたときの値が要る。Thread の値は終わり・Clear・取り消しで変わる）を型に書いた／Fork の最初の
   ターンかは `ownsSession === false` から分かることを型に書いた
6. 試験の穴：健全性検査の中断・例外・呼び出し側が読むのをやめたターンが failed になること、Fork が親の
   `lastTurn` を引き継がないこと

壊して落ちるかは、上の直しの該当行を12か所壊して見た。最初の版では3か所（発言の数に AI の発言も数える・走り始めた
時刻をそろえない・既定の終わり方を completed にする）で試験が落ちなかったので、試験を直してから全部落ちることを見た。

### F1：`forkSession` と一緒に `sessionId` を渡したら（2026-10-05、`banto/probes/m-sdk.mjs F1`。偽の API、SDK 0.3.281＝CLI 2.1.281）

| ケース | 結果 |
|---|---|
| 新しい会話に `sessionId: A` | `system/init` の id＝A、記録は `A.jsonl` |
| `resume: A`・`forkSession`・`sessionId: F` | `system/init` の id＝F、記録は `F.jsonl`。A の記録は1行も変わらない。最初の要求に TURN1（親の発言）が入る＝親の会話を引き継ぐ |
| `resume: F`（`sessionId` 無し） | `system/init` の id＝F、要求に TURN1・TURN2・TURN3 |
| `resume: A`・`forkSession`・`sessionId: G` を `system/init` で即 SIGKILL（5回） | 5回とも `G.jsonl` が**ある**が、中身は `mode`・`atis-latch` の2行だけ。`getSessionInfo(G)` は5回とも `undefined` |
| そのあと同じ `sessionId: G` で分け直す | 失敗「Session ID … is already in use」（exit 1、result 無し） |
| そのあと G を resume | 失敗「No conversation found with session ID: …」（`error_during_execution`） |
| そのあと新しい `sessionId: H` で分け直す | 成功。要求に TURN1・新しい発言 |
| `resume`（`forkSession` 無し）に `sessionId` | CLI が断る「--session-id can only be used with --continue or --resume if --fork-session is also specified」（adapter の試験で、断る行を外して見た） |

→ Fork の最初のターンでも先に決めた id で会話が分かれる。ただし**会話を書く前に切れた Fork は、新しい会話（M2：記録
ファイルができない）と違って中身の無い記録が残る**ので、同じ id では走らせ直せない。`getSessionInfo` が `undefined` を
返すところは同じなので、続ける処理は「記録が無い」を見たら、Fork の最初のターンなら新しい id で分け直す必要がある

## 実装の2つめ：書き終えた発言ごとに記録する（resume-message-by-message、2026-10-05）

仕様 §2.5「書き終えた発言ごとに記録する」の項。決めたことは仕様に反映した。ここは理由と、選ばなかった案。

### 吹き出しの単位：1ターンの AI の発言は1つ（fold でまとめる）

- Event Store には SDK の assistant のメッセージごとに `message.appended` を1件書き、fold が同じターンの分を会話の1件に
  まとめる。**まとめる場所を fold にした理由**：「ターンの最後の AI の記録」を1件として読んでいるところが多い——受信箱の
  「ターンが終わりました」の要約（`cli.ts` の `turnEndSummary`、会話の最後の1件の頭）・一覧の件数と最後の発言
  （`toThreadSummary`）・Fork が親の会話を写すこと・画面の組み直し（`realMessagesToInitial`、1件＝1吹き出し）・最新の
  20 件だけ描く（§6.29、件数）。会話の1件をターンごとに保てば、どれも変えずに済む
- 選ばなかった案：記録は発言ごとの件数のまま返し、画面で連続する AI の発言を1つの吹き出しにまとめる。要約・件数・
  「この Fork を開く」の件数などをすべて直す必要があり、画面と host で「1件」の意味が食い違う
- まとめる条件は「最後のターンの始まり（`lastTurn.startedSeq`）より後ろで、直前の1件も AI の発言」。この仕組みより前の
  記録（`turn.started` が無い）ではまとめない——前は AI の発言が続くことが無かったので同じ結果
- 走っている途中に Clear すると、そのターンのそのあとの発言も Clear の横線より前の吹き出しに入る（前はターンの最後に
  書いたので横線の後ろに出ていた）。Clear が切り離すのはそのターンの会話なので、横線より前のほうが合っている

### 書く単位

- 文は発言が届いた時点。画面つきの呼び出しは結果（次の user の tool_result）が来た時点で、文の無い1件として書く
  ——文まで結果を待たせると、承認待ちの間（人が答えるまで）文が記録に落ちない
- 結果が来ないまま終わった（done・失敗・止めた）呼び出しは最後に結果無しで書く（前も結果無しで残していた）
- 書いてから画面に流す（`await` してから `yield`）。1発言ごとに fsync を待つ——1ターンで発言が多いと（tool を30回呼ぶ
  ターンで 30〜60 件）、流れが fsync の分だけ遅れる。測っていない

### 「ここから Fork」が壊れる穴（洗い出しで見つけた）

前は resume-point → 返事 の順に書いていたので、返事の seq より前にそのターンの resume-point の履歴（`resumePoints`）が
あった。発言ごとに書くと返事が resume-point より前になり、**新しい会話の最初のターン**（Clear のあと・Fork の最初の
ターンも）の返事から分けると「その時点ではまだ会話が無い」と判定され、まっさらな会話で始まっていた（続きのターンは
同じ会話なので見た目は変わらない——履歴は会話が変わったときだけ積む）。履歴の seq をそのターンの始まりの seq にした

### 流し直しの境界

- 走っているターンに乗った画面は、記録から組み直したうえで、そのターンを最初から流し直してもらう。記録にもう入った
  発言がそのまま描かれると2回出る
- 選んだ形：`attached` にターンの始まりの seq を載せ、画面がそのターンの AI の1件を記録から外す。流し直しはそのまま
  全部流す——判断待ち・答えは記録に入らず流し直しにしかないので、流し直しの側を削ると並びが崩れる
- 選ばなかった案：流し直しを「記録に入っていない分だけ」にする。画面は乗ってから記録を取る（取りこぼさないため）ので、
  乗った時点の境界と記録を取った時点の境界がずれ、その間に入った発言が二重か欠けになる。吹き出しも記録の分と流れる
  分の2つに割れる
- 始まりを記録する前（Skill を決めている間）に乗られたら、境界が決まるまで `attached` を待たせる。待つ間に終わった
  ターンを取りこぼさないよう、知らせを受けたその場で途中経過を取り、続きを溜める（単体の試験は記録と終わりを同じ手番で
  書くので、溜めないと必ず `idle` になった）
- 画面が外すのは「始まりより後ろで人の発言の次の AI の1件」。乗ったターンが取り消されて次のターンが返事を書くまでの
  間に記録を取ると次のターンの返事を外してしまうので、記録の `lastTurn` が後ろにあればその始まりより前に限る

### 試験の待ちの前提が変わった

「記録の AI の件数が増えた」は、もうターンの終わりの合図ではない（最初の発言で増える）。E2E の多くがこれを待ちに
使っている。turn-reattach は host に聞く形（`GET …/stream` が `idle`）に直した。ほかの spec の洗い出しは下の「残したこと」。

## 実装の3つめ：起き直したら切れたターンを続ける（resume-thread-turn、2026-10-05）

仕様 §2.5「1. Thread のターンを続ける」の「起き直したら」「上限」と、Fable の指摘（続きを人の発言にしない・切れた
吹き出しから Fork するとまっさらになる）。決めた形は仕様に書いた。ここは理由と選ばなかった案。

### 続きを「届いたもの」で起こし、続きの指示を届いたものに載せた

- 続きは送り手 `banto` の届いたもの（§4.2 の口）。人の発言にすると、画面に人の吹き出しが出る・止めたときの取り消し
  （§6.31）が機械の文を入力欄へ戻す・`findRewindBeforePrompt` の目印が狂う（Fable）
- 続ける会話・`attempt`・会話の始まりは、その届いたものの `continues` に載せた。**選ばなかった案**：起動時に host が
  続きの指示をメモリに持ち、ターンを直接起こす——起こす前にもう一度落ちると失われ、起こす経路が `resumeAll` と2本に
  なる。記録に載せれば、続きを起こす前に落ちても次の起動で `resumeAll` が拾う
- 待ち行列の先頭に並べる（fold が `continues` 付きを先頭へ）。速度の上限には数えない（人のターンを続けるだけ）。
  ホップは切れたターンのもの（積んだ届いたもののホップの最大）

### 切れたターンの終わり方は failed

続けたものも続けないものも、見たら `turn.ended`（failed）を書く。新しい終わり方（「切れた」）を足す案もあったが、頼みの
形に揃えた。続きに引き継いだかは、次のターンの `continuesTurnId` から辿れる。

### 「続ける」の口はお知らせのボタン

判断待ち（選択肢つき）にする案は使えなかった：判断待ちのカードは走っているターンの流れの中でしか描かれない（受信箱は
Thread を開くだけ）・起動のたびに期限切れにされる・答えは許可/拒否の形。お知らせは記録に残り、行にもうボタン
（「確認した」）がある——「続ける」を1つ足した。押した続きも `attempt` を数え続ける（0 に戻さない）：押したあとまた
切れたら、また聞く。**訂正**（2026-10-05）：押したら 0 に戻す（人の判断）——下の直し。

**上限の読み方**：頼みの「続けたターンがまた切れたら1回だけ続け直し、続けて2回切れたら」は、仕様の「続けて2回切れたら
自動で続けるのをやめ」に合わせ、**最初に切れたら1回続け、その続きもまた切れたら（2回目の切れで）やめる**と読んだ
（`RESUME_CUT_LIMIT = 2`）。2回目の切れでもう1回続けるつもりなら 3 にする。
**訂正**（2026-10-05、ユーザーとの合意）：合意は「切れた→自動で続ける→それも切れた→もう一度だけ続ける→それも切れた
（続けて2回）→やめる」で、上の読みは1回少なかった。3 にした（下の「Fable のレビューを受けた直し（resume-thread-turn）」）。

### 文面

- 時刻は切れたターンを始めた時刻。切れた時刻は分からない（最後に書いた出来事の時刻をターンごとには持っていない）
- 入れ直す条件に「鎖に発言の文が見つからない（届いたか分からない）」も入れた——AI が同じ発言を2回見ることはあっても、
  届いていないまま続けるよりよい。続いている会話で、CLI が発言を書く前（`turn.started` と CLI の書き込みの間）に切れた
  ときがこれ
- 実行中だった呼び出しは「鎖の最後の人の側の発言より後ろ」に限った——前のターンの止めた呼び出しを拾わない
- 承認を待っていた呼び出しは、その Thread の判断待ちのうち切れたターンを始めてから期限切れになったもの。起動時に期限
  切れにするのが先（`expireOrphanedJudgments` は `resumeInterruptedTurns` より前）

### 切れた吹き出しから Fork（Fable の指摘3）

続きのターンが書く resume-point の履歴を、切れたターンの会話の始まり（`continuesFromSeq`、続きの続きなら最初に切れた
ターン）に置く。新しい会話の最初のターンが切れたとき、切れた吹き出しの seq より後ろにしか履歴が無く、そこから分けると
まっさらな会話になっていた。間に Clear があれば置かない（Clear より前の発言から分けて、Clear のあとの会話にならない
ように）。履歴は seq の順に並べ直す。

### 見つけた穴：走っている続きを Clear

試験の作り（届いたもので起こす口を起動の片づけより先に用意してしまった）のせいで、続きのターンが走っている途中に Clear
する形を偶然踏んだ。続きが新しい会話の最初のターンの会話（Thread の resume-point に無い）を続けているとき、`system/init`
の前に Clear すると、Clear が捨てる側に入れるもの（Thread の resume-point・最後のターンの先に決めた id・名乗った id）が
どれも無く、終わりの resume-point の更新が Clear を取り消していた。Clear は最後のターンを始めたときの resume-point も
捨てるようにした。試験の作りは直した（`listen()` で口を用意する——cli.ts と同じ順）。

### E2E：自前の host

E2E の core は全 spec が共有し、Playwright の webServer と片づけ役が持っているので止められない。spec の中で自前の
host（`e2e/own-host.ts`、別の置き場・待ち受け）を起こし、画面を `?bantoHost=` でそちらへ向ける。踏んだもの：

- 置き場を E2E の TMPDIR の下に作ると、Incus の Module のマウントが「file name too long」（マウントの道を1つのファイル
  名で持つ、255 字まで）。/tmp にすると「Disk source path … not allowed」（人の Incus の project は
  `restricted.devices.disk.paths: /home/ubuntu` だけ）。passwd のホームの下の短い道（`~/.cache/bo-*`）にした
- 偽の Runner は印のあとを全部 JSON として読んでいた——入れ直した発言の後ろに続きの文があると読めない。印のあとの1行
  だけを読むようにした（`fakeTurn` は改行の無い JSON を書く）
- この環境では会話の記録（CLI）が無いので、E2E が通るのは「記録が無い→同じ id で最初から・発言を入れ直す」道。
  記録があるときの道は単体（偽の読み口）で見た

### M5. systemd の止め方（2026-10-05）

稼働中の host の設定（人が host で確認）：`banto-host.service` は `KillMode=mixed`・`TimeoutStopUSec=1min 30s`。

同じ設定の試験用の unit を、この Project のコンテナの中の systemd で確かめた（`systemd-run -p KillMode=mixed -p Restart=on-failure`、
主のプロセスは node で、SIGTERM で `process.exit(0)` し、子に同じグループ・別グループの `sleep` を持つ）：

| 止め方 | 子（同じグループ・別グループ） |
|---|---|
| `systemctl stop`（主に SIGTERM → 主が終わる） | 3秒以内に両方消えた |
| 主を `kill -9`（落ちた）→ `Restart=on-failure` で起こし直し | 起こし直す前（2秒後）に両方消えていた。起こし直したあとは新しい子だけ |

→ **主（host）が終わると、cgroup に残ったもの（Runner の CLI・その子・Module を起こした `incus exec` のクライアント）は systemd が
刈る**。M3 の「落ちたあと孤児の CLI が同じ記録に書き続ける」は、今の unit では起きない。人の起こし直しでも CLI は SIGTERM を
受けて終わり際に書く前に刈られうるので、記録は SIGKILL と同じ形（`last-prompt` 無し）になりうる——巻き戻しの位置を保って続ける
今の作りで足りる。コンテナの中の Module の子は cgroup の外なので残る（M4）。

## Fable のレビューを受けた直し（resume-thread-turn、2026-10-05）

決めた形は仕様 §2.5「1. Thread のターンを続ける」（形・上限）に書いた。ここは理由と、選ばなかった案と、確かめたこと。

### 0. 上限は 3

ユーザーとの合意は「切れた→続ける→また切れた→もう一度だけ続ける→また切れた→やめる」。`RESUME_CUT_LIMIT = 3`
（切れたターンの `attempt`＋1 が 3 に達したらやめる）。

### 1. 上限で止めた Thread を、別の届いたものが起こしていた（高）

起動の順は「Module の札 → 切れたターン → 待ち受け → `resumeAll`」。札の「途中で終わりました」は届いたものとして積まれ、
`resumeAll` がそれをふつうのターンとして起こしていた。結果：最後のターンが変わるので「続ける」が 409、そのターンは
`attempt` 0 で始まるので上限が効かない、切れた会話は引き継がない（新しい会話の最初のターンが切れていたら黙って捨てる）。

決めた形（ユーザーとの合意）：
- 自動で続けるのをやめた Thread は、お知らせが開いている間、届いたものを起こさずに留める（`ThreadDeliveries` の
  `hold`。cli.ts が `resumeHoldReason` を渡す）
- 次に始まるターン（「続ける」・人が送った）が切れた会話を引き継ぐ。人が送ったら `attempt` 0、「続ける」も 0、
  引き継いだターンがお知らせを片づける

**どう引き継がせるか——続きを待ち行列に積んで留める**（選んだ案）：上限に達しても続きの届いたものは今までどおり作って
積み、起こさないだけ。人が送ったターンは今までどおり待ち行列のものを全部積むので、何も足さずに続きを引き継ぐ（会話・
並び・ホップは続きが持っている）。「続ける」は積んである続きを `attempt` 0 で出し直して起こす。留めの条件は「開いている
お知らせがあり、**その続きがまだ待ち行列にある**」——続きを誰かが積めば（人が送った）・捨てれば（Clear）お知らせが
残っていても留めは外れる（留めっぱなしにならない）。

選ばなかった案：
- 上限で何も積まず、人が送ったときに host が続きを組んで足す。送るたびに CLI の記録を読む（`planContinuation`）口が
  人のターンの途中に要り、続きを作る経路が2本になる。続きを積む前に切れた続き（下の 3）は結局待ち行列に残るので、
  出し直し（置き換え）の口はどちらにしても要る
- 留めを続きの届いたものに印で持つ（お知らせと切り離す）。「確認した」で外れない形になるが、合意は「お知らせが開いて
  いる間」なのでそちらにした

**出し直しは同じ届いたもの（同じ id）を置き換える**：「続ける」と、人が送ったターンが同時に動いたとき、人のターンが
古い続きを読んだあと出し直しが入っても、積んだときに同じ id で待ち行列から外れる（id を変えると、新しい続きが残って
もう一度走る）。出し直す前に積まれていたら何もしない。

**Clear・閉じたら待ち行列の続きを捨てる**：続きを留めておくようになったので、人が「何度も切れるから Clear してやり直そう」
としたあと、次に送ったターンが畳んだ会話の続きの文（入れ直した発言も）を新しい会話に積むようになる。捨てる。前は
起動の片づけから `resumeAll` までの間だけの話で、試験は「Clear のあと続きは今の会話で走る」を見ていた——その試験は
「捨てる・次に送ったターンは新しい会話」に直した。

**見つけた穴：続きの続きが切れた会話を捨てていた**（前の実装からある）：新しい会話の最初のターンが記録を書いてから
切れ、その続き（`resume: 自分の会話`）もまた切れると、次の続きは `session` を持たず Thread の resume-point（無い）で
走り、新しい会話になっていた——続きのターンは `turn.started` の resume-point に続けた会話を持つので「続いている会話」と
読まれ、Thread の resume-point と違うことを見ていなかった。上限が 2 のときは「続ける」を押したときだけ踏み、3 にすると
自動で踏む。続けたターンの resume-point が Thread のものと違えばそれを続ける（`resume`）ようにした。
**訂正**（2026-10-05、引き継いだ担当）：上の読みは筋が違っていた。続きのターンが `system/init` のあとで切れたなら、
名乗った id（`turn.sessionId`）で前から続けられていた。踏むのは **`system/init` の前に切れた**とき——`sessionId` が
無く「記録が無い」と読まれ、`session` を持たない（新しい会話・Fork は親から分け直す）。直しを入れた場所
（`ownsSession` が true の枝）は、Thread が自分の会話を持つ＝resume-point が Thread のものなので届かず、壊しても試験が
落ちなかった（下の追記）。「切れたターンの resume-point が Thread のものと違う」を枝の前で見る形に直した

### 2. 「続ける」の同時押し（中）

host：お知らせの id ごとに「いま続けている」を持ち、走っている間の2つめは 409「いま続けています」。順は「出し直す →
お知らせを片づける → 起こす」——片づけてから出し直しに失敗すると、続きが上限の `attempt` のまま留めが外れる。片づけに
失敗したら（続きはもう `attempt` 0）、押し直せば同じことをやり直す。画面：返事が来るまでボタンを押せない（ref で
確かめる——描き直す前の2回目の押下も止める）。

### 3. 続きを人のターンが引き継ぐとき（中）

- `cause` は human、`attempt` は 0、ホップは 0（`lastTurnOf` は人のターンなら 0。前は積んだ届いたもののホップの最大を
  取っていて、人のターンの鍵の値（0）と食い違っていた）
- **頼みの前提と違ったこと（報告）**：頼みは「取り消し（§6.31）のとき、一緒に積んだ続きの届いたものは待ち行列に戻る
  （既存の届いたものと同じ扱い）ことを確かめる」。今の規則（v4-frontend.md §6.31）は「届いたものも一緒に積んだターン
  は取り消さない——止めるだけ」で、届いたものが待ち行列に戻る道は無い（戻るのは、積む前に止めたとき——そもそも
  待ち行列から出ていない）。続きを引き継いだ人のターンも同じく**取り消さない**：人の発言も続きも記録に残り、
  「（ここで止めました）」が付く。規則を変えずに、そうなることを試験で確かめた。変えるなら §6.31 ごと決め直す
- 止めたとき切れた会話を失う穴：続きが Thread の resume-point に無い会話（新しい会話の最初のターンが書いた会話）を
  続けていて、`system/init` の前に止めると、止めたあとの resume-point の更新（名乗った id で書く）が無く、次のターンが
  新しい会話になっていた。名乗った id が無ければ続けた会話を書く
- 狭い穴（続きを積む前に切れた続き）：`stackedMessages` が 0 でも、そのターンが続きを引き継いだターン

### 印：Module の申告に1項目足す

`dev.banto/module` の `resumesAfterRestart: true`（`parseModuleMeta` が読む）。選んだ理由：host が**起こす前に**宣言で分かる

読む既存の流儀に乗る。選ばなかった案：MCP の capabilities（`experimental`）に載せる——起こして initialize するまで分からない。
tool の `_meta` に印を付ける——印は仕事ごとではなく Module ごとの約束で、問いの口を持つかどうかと同じ。

### 問い：決まった名前の tool

`resumeAfterRestart`（`@banto/module-contract` の `RESUME_AFTER_RESTART_TOOL`）。visibility は admin（AI には見せない）。
host だけが呼ぶ可視性は無いので admin にした——人の画面（ui-tool-call）からも呼べてしまう。Subagent は札の指紋が合う記録
だけを続けるので、知らない札では何も起きない（懸念に残す）。1接続に1回、その接続に渡した札を全部まとめて渡す。

### 起動の順番：名乗った Module の札がある Thread だけ、待ち受けのあと

頼みの順（判断待ちの期限切れ → 札の判定 → 切れたターン → 待ち受け → resumeAll）のうち、**名乗った Module に問うのは
待ち受けのあと**にした。理由：
- **Module が host に届く口（中継）が待ち受けと同じ所にある**。続けると答えた Subagent は、まず中継で資格情報を受け取り
  （Vault・本体の Claude ログイン）、終われば札で届ける——待ち受けの前はどちらも繋がらない
- Project のコンテナを起こすのに数秒〜十数秒かかる（E2E で コンテナ 4.5 秒・Module の起動と接続 1.8 秒）。その間、画面も開けない

二重に扱わないために、**名乗った Module の札を持つ Thread は判定が終わるまで留める**：届いたもので起こさない（`hold`）・
人が送ったターンも判定を待ってから始める（`awaitRestartRecovery`）・その Thread の切れたターンは判定のあとに片づける。
名乗らない Module の札・ほかの Thread は今までどおり待ち受けの前に片づける。
選ばなかった案：
- 全部を待ち受けの前に問う（頼みのとおり）：上の理由で、Module が中継に届くまで待つ口を Module 側に作ることになる。
  画面も開けない時間が延びる
- 待ち受けのあとに全部（名乗らない Module の札・切れたターンも）：留める Thread が増える。名乗らない Module は起こさないので
  速く、前に置いても困らない

札は**問う前に**同じ印で覚え直す（`ReplyHandles.restore`、使えるのは1回）——続けると答えた Module がすぐ終わって届けても
受けられる。続けないと答えた・答えない・起こせない（120 秒まで）なら `deliverLostReply` が片づける。問っている間に Module が
止まった（`onclose` がもう「途中で終わりました」を届けた）なら、答えが「続ける」でも数えない。

### 観測：続けると答えた時刻

`reply.kept`（Event Store）→ 返事待ちの `keptAt` → 画面のバックグラウンドの一覧に「起こし直しのあと続けています
（<何分前>から）」。何分で人に知らせる（受信箱に出す）かは決めていない——いまは人が一覧を開いて見る形。

### Subagent

- 記録は1件1ファイル（`running/<id>.json`、一時ファイル→rename）。走っている仕事が並ぶので、1ファイルを書き換え合わない
- **札は指紋（sha256 の頭 32 字）だけ書く**。札は届けるための推測できない印で、続けるときは host が問いで渡す
- **頼んだ文は全文書く**（仕様の挙げた「頼んだ文の頭」より多い）：load できないものを同じ頼みでやり直すのに要る。終わった
  仕事の記録（`runs.jsonl`）も全文を持っているので、置き場に新しく残すものは増えていない
- envSecrets は alias の名前を書く（値ではない）——続けるときに受け取り直す
- 「まだ何も進んでいない」は記録で見る（会話の id が無い・tool も返答も無い）。load の失敗の文言に頼らない
  （`session/load` の失敗は `SessionLoadError` で見分けるが、やり直すかは記録で決める）。続きから頼んだ仕事（sessionId を
  渡した）は、load できなくても最初からはやらない——前の会話を失う
- 実行中だった tool は記録の「呼んで、終わりが来ていない」最後の1つ（`tool_call_update` の completed・failed で外す）
- 届けられなかった結果は記録に残し、次に問われたら走らせ直さずに届ける
- 偽のエージェント：頼まれた文を頼まれた時点で会話に残す形にした（本物の CLI と同じ）。`[then-slow N]`（続けたときに遅くする）・

## Fable のレビューを受けた直し（resume-module-contract・resume-subagent、2026-10-05）

### main の取り込み

`git rebase main`。テキストの衝突は無かった。意味の上でぶつかったのは Module 宛ての返事（1ecc4ab1）：
- 起動時に `moduleReplies.loseAll`（前の走行の Module 宛ての返事待ちを全部「途中で終わりました」）——札の判定

### 2. 残ったエージェント——確かめた

own-host の E2E と同じ形のプローブ（コミットしない）で、偽のエージェントの待たない仕事が tool の途中のところで host を
SIGKILL し、ホストの `ps` でコンテナの中のプロセスを数えた。偽のエージェントに `[child N]`（子を1つ起こす。claude-agent-acp
が CLI を子で起こすのと同じ形）を足して、子も数えた。

| | SIGKILL の前 | 3 秒後 | 15 秒後 | 30 秒後 |
|---|---|---|---|---|
| Module（subagent/dist/server.js） | 居る | 居ない | 居ない | 居ない |
| エージェント（fake-agent.js） | 居る | **居る** | **居る** | **居る** |
| エージェントの子（fake-agent-child） | 居る | **居る** | **居る** | **居る** |

- **残った**。エージェントは親（Module）を失って、ACP の管が切れても自分の仕事（`[slow 90]`）を続けた。子も残った
- エージェントと子のプロセスグループは Module と同じ（incusd のもの）で、グループごと止める手が使えなかった
- 偽のエージェントは管が切れても終わらない作り。本物の claude-agent-acp が管が切れたら終わるかは確かめていない——終わっても、
  子の CLI が残る形は同じなので、どちらでも止める

直した形：エージェントを**自分のプロセスグループで**起こし（`detached`）、pid（コンテナの中の番号）と開始時刻（`/proc/<pid>/stat`
の starttime）を走っている記録に残す。続ける前・続けないと決めたとき、グループが残っていれば SIGTERM → 5 秒で SIGKILL →
居なくなったのを確かめてから `session/load`。止まらなければ続けずに失敗を届ける。pid の使い回しは、グループの頭の開始時刻が
記録と違えば止めない（頭が居なくて子だけ残っているなら、グループの id はまだ使われている途中なので別のプロセスに渡って
いない——止める）。ふだん止めるとき（`cancelRun`・終わったあと）もグループごと止めるようにした（子を残さない）。

E2E（`subagent-resume-restart.spec.ts`）に足した：SIGKILL の2秒後に前の走行のエージェントが**まだ居る**こと（試験の前提）、
続けている間に居るエージェントは続けた1本だけ・前の走行の子も居ないこと。記録の pid はコンテナの中の番号でホストの `ps`
とは違う（最初に書いた試験がそこで落ちた）——E2E はホストから見た番号で数える。

### 1. 期限を過ぎたあとの問い

外側の `Promise.race` は答えを捨てるだけで、内側（コンテナを起こす・`callTool`）は走り続けていた。期限（120 秒）を
`AbortController` にし、起こす所（`connect`）と問い（`ask`、MCP の `callTool` の `signal`）の両方に渡す。**問いを送る直前に**
期限と札の状態を見る（済んだ札は載せない）。Subagent は host が問いを取り消したら続けない（記録とエージェントを片づける）。
Module 側のこの確かめは単体で再現できていない（取り消しが届く時刻を決められない）——host 側で送らない・取り消すことを
試験した。

### 3. Module 宛ての札（決定）

Factory が中継で頼んだ Subagent の仕事が起こし直しで必ず失われるのは困る、というユーザーの決定。Module 宛ての返事待ち
（`module-replies.json`）も、頼んだ先が名乗っていれば同じ問いに乗せる（`thread` の代わりに `caller: { module, projectId? }`）。
返事待ちの行に `projectId` を足した（宣言を引き、Project の Module を起こすのに要る。前からある行には無い——Project の
Module なら起こす Project が分からず、「途中で終わりました」（理由つき）になる）。Subagent は Thread の印の無い記録（中継で頼まれた仕事）を `caller` で問われたときだけ続ける。

### 4〜9

- 4：問いは host だけ。Module は呼び元の印（`caller`・`thread`・`callId`）が付いた問いを断り、host も画面の口と中継で断る

  無い）も退ける

## Fable のレビューを受けた直し（resume-light-update-wait、2026-10-05）

決めた形は仕様 §2.5「いま動いているもの」（止める間は断る・待たないものに残る例外）・「起こし直しをまたいで続ける」の
続きの文と「2.」の Module 宛ての札・§2.5 の呼び出しの印（elicitation にも返せる）、v4-frontend.md §6.34、手順書 B-3、
install.sh に書いた。ここは理由と確かめたこと。

### 1. 待つものが無いと見てから止まるまでの窓

- **断る場所は台帳**（`ModuleCallTracker.stopAccepting`）に印を持たせ、入口3つで見る：AI の tool 呼び出し（`agent-proxy`
  ——投げずに `isError` の結果で返す。投げると Runner が自分の言葉に包み、AI に「起き直したあとにもう一度」が届かない）・
  画面の3つの `…/ui-tool-call`（503）・中継。`beginCall` で投げる案は却下——入口ごとに返し方（結果・HTTP・中継のエラー）が
  違い、host 自身の呼び出し（秘密の解決）まで巻き込む
- **実行中の呼び出しの中の中継は通す**：通さないと、待っている呼び出しそのものが失敗する（中継で Vault を引く
  Subagent 等）。判定は「呼び元の呼び出し（印があればその1件、無ければその接続のどれか）が走っているか」——印の無い
  Module は接続単位なので、終わった呼び出しの後の仕事の中継も、同じ接続で別の呼び出しが走っていれば通る（緩いほう）
- **読み取り（resource）は断らない**：副作用が無く、短い。台帳には載るので待たれる
- **待つのは人を待っていない呼び出しだけ**、上限 60 秒（`STOP_DRAIN_LIMIT_MS`）。systemd の止める上限は banto-host では
  既定の 90 秒（稼働中の unit で `TimeoutStopUSec=1min 30s` を確かめた）。install.sh の unit に `TimeoutStopSec=90s` を
  明記した（`setup-update.sh` は unit の中身を変えない）。2回目の信号は待たない
- **断った呼び出しの続きの文**：会話の記録の tool の結果に `RESTARTING_REFUSAL` の文があるものを「起こし直し中のため断った
  呼び出し」と書く（結果があるので実行中には数えない）。E2E の偽の Runner は会話の記録を作らないので、ここは単体だけ

### 2. 質問の印の精度

- Module が問いの `_meta` に `dev.banto/callId` を返せば、その1件の会話に出し、その1件だけ人待ちにする（会話を決めるのも
  その1件——以前は接続の全部で決め、別の会話の呼び出しが並んでいると断っていた）。返さなければ、問いを出す会話の呼び出し
  だけ。**同梱の Module に elicitation を使うものは無い**（Vault も使っていない——grep で確かめた）ので、返させる先は無かった
- 同じ会話で同じ Module を並べて呼び、印を返さない Module が質問すると、質問していないほうも人待ちに見える（残る例外）

### 3〜6

- 3：上限に達するターン（`attempt`＋1 ≥ 3）は理由つきで待つ。`attempt` は Thread の最後のターン（終わりがまだ無い）から
- 4：判断待ちに**別の欄** `withinToolCallId` を足した。`toolCallId` に入れる案は却下——画面がカードを tool 呼び出しに
  結びつける欄で、承認の答えの口（`pendingApprovals`）とも混ざる。台帳が AI の呼び出しごとに Runner の tool_use の id
  （`claudecode/toolUseId`）を持ち、中継の宛先へ継ぐ。承認は聞いた呼び出し（`callerCallId`）から、質問は「質問の間に印を
  立てた呼び出しのうち、その会話で1つに決まるもの」から。決まらなければ付けず、今までどおり実行中だった呼び出しとして書く
- 5：呼び元が名乗っていない Module 宛ての札は待つ・問わない。**Factory はまだ名乗っていないので、Factory が中継で頼んだ
  Subagent の仕事は Factory が名乗るまで起こし直しで失われる**（前の決定「必ず失われないように」は、Factory が名乗って

- 6：簡単なほう——仕様に「Fork の予約は失われ、AI が頼み直す」（待たないものに残る例外）。続きの文には前から
  「このターンで頼んだ Fork は立っていません」が出る

## 実装の5つめ：Factory を起こし直しの約束に乗せる（resume-factory、2026-10-07）

決めた形は仕様（v4-modules.md §4.5「記録と再開」・「実装」の「起こし直し」、アーキ仕様 §2.5「2.」の「Factory」）に書いた。
ここは確かめたことと、見つけた穴と、選ばなかった案。

### 始めに分かったこと

Factory は factory-runtime（2026-10-06）の時点で、もう「続けられる」と名乗り（目録の `resumesAfterRestart: true`）、問いの口
（`resumeAfterRestart`）を持っていた。仕様の「2. は Subagent まで、Factory は未」「Factory はまだ名乗っていない」は、その前に
書いたまま古くなっていた。足りなかったのは、名乗ったうえで起こし直しを端から端まで通した確かめ。

### E2E で確かめたこと（`e2e/specs/factory-resume-restart.spec.ts`、自前の host）

本物の Subagent・Backlog・Factory を Project のコンテナで動かし、エージェントだけ偽物。タスクの本文は
`[child 300] [slow 600] [then-slow 8] [then-commit resumed.txt]`——実装役は子を起こして 600 秒の tool を始め、続けたとき
（同じ会話の次の頼み）は 8 秒の tool のあとコミットする。実装役の仕事が tool の途中（走っている記録の `toolsInFlight` が
`sleep 600`）のところで host を SIGKILL し、2 秒後に起こし直す。

| 確かめ | 結果 |
|---|---|
| 落とす前 | Thread の返事待ちは factory の1件。host の `module-replies.json` に Factory 宛ての返事待ち（記録の返事の印と同じ）。Backlog は in-progress。エージェント1本とその子 |
| 落ちた直後 | 前の走行のエージェントはコンテナの中で走り続けている（試験の前提） |
| 起き直した host の問い | ログ「前の走行の返事待ち（factory・Thread …）→ 続けると答えた」「前の走行の返事待ち（subagent・呼び元 factory）→ 続けると答えた」。Thread の札は「続けています」（`keptAt`） |
| 続けている間 | 前の走行のエージェントとその子は居ない。居るのは続けた1本だけ |
| 返事 | Factory の受け口に**同じ返事の印**で届いた（`final: true`・`lost: false`・`resumedAfterRestart: true`・「受け取った：banto を起こし直したため、作業が途中で切れました。切れたとき実行中だった tool：sleep 600…」）。走っている記録は消えた |
| 流し直し | 段の記録で、どの番号も「始めた」は1回。段の並びは 始める→in-progress→worktree→実装→agent:implementer→commits-ahead→テスト→test→レビュー→agent:reviewer→マージ→rebase→test→fast-forward→done→cleanup。サブエージェントに頼んだのは2回（実装役1・レビュー役1）で、1回目の返事の印は落とす前と同じ。失敗した段は無い |
| 最後まで | main に `fake: resumed.txt` のコミットとファイル。Backlog は done。worktree とブランチは消えた。実行は done・`notifyErrors` は空 |
| 頼んだ Thread | 届いたのは「Factory の実行が終わりました（取り込み 1／1 件）」の1件だけ（「途中で終わりました」「止まりました」は無い）。AI がそれで起きてターンを終え、返事待ちは空 |

1回目で通った（55 秒）。偽のエージェントは「レビュー役」の頼みにもタスクの本文が入るので、`[slow]`・`[child]` を実装役にだけ
効かせるようにした（`[commit]` と同じ扱い）——レビュー役が 600 秒待たないように。

### 見つけた穴（読んで見つけ、単体で再現してから直した）

E2E の形（実装役の途中で落とす）では表に出ない。どちらも Factory の札がメモリにしか無いことから来る。

1. **問いより先に終わった実行の最後の知らせが捨てられ、Thread に「途中で終わりました」が届く**。Factory は起きるとすぐ記録から
   流し直す。host が Factory を起こしてから問いを送るまでの間に、流し直しが知らせる段まで進むと（記録の最後の段だけ残っていた
   ——たとえば done を書いたあと cleanup の前に落ちた）、札がまだ無いので「知らせる先がありません」で知らせを捨て、`finishedAt`
   を書く。そのあと問われると「終わっていない Factory の実行がありません」と答え、host は頼んだ Thread に「途中で終わりました」を
   届ける——仕事は済んで main に入ったのに。単体（`server.test.ts` の1本目）で、直す前は `resume: false` で落ちた。
   **直し**：流し直した実行（札の指紋があるもの）の知らせは問いまで待たせる（上限 150 秒、host の問いの上限 120 秒より少し長く）。
   問われたら、終わった実行でも待たせた知らせがあれば「続ける」と答え、答えを返したあと（`setImmediate`）届ける。上限を越えたら
   今までどおり `notifyErrors` に残す（Factory だけが起き直した——host は問わない）。
   選ばなかった案：札をファイルに書く——札は平文で書かない（§4.2、Subagent の走っている記録と同じ）。host が Factory を問うのを
   先にする——起こしたプロセスは問いの前に走り出すので、順番では閉じない。
2. **止まって人を待っていた1件が、流し直しで「止まりました」を届け直す**。流し直しで答えの無い問い（`ask`）に戻ると、もう一度
   知らせていた。直す前は札がまだ無いので `notifyErrors` に「知らせる先がありません（…止まりました）」が残るだけだったが、1. の
   直しで問いまで待つようになると、覚え直した札（最後の1回だけ）で同じ「止まりました」を届け直し、最後の知らせの分を使い切る。
   **直し**：知らせが届いたことを止まった印に残し（`stopped.notified`）、流し直しで同じ理由の問いに戻ったときは届け直さない。
   **届いていなければ届ける**（届ける途中で落ちた等）——「流し直しでは届けない」だけにすると、届く前に落ちたとき Thread が
   止まったことを知らないまま待ち続ける。流し直しの間は段の印が status を running に戻すので、status ではなく止まった印の
   理由で見る。host が届けたあと記録に `notified` を書く前に落ちたら、届け直す（二重に届く。残した）

E2E は Factory と core を写し（`_mut-src`）で壊して別の出力先（`_mut-dist`）に組み、目録の Factory をそこへ向けた core を

写しで組んだもの（none）は通ることを先に見た。単体は Factory の `_mut-dist` の試験を回した。

### 残したこと・懸念

- **Factory の Thread への札が無いと、起こし直しのあと Factory が立たない**（読んだ限り。確かめていない）：host が Factory を起こす
  のは、Factory に頼んだ Thread への札を問うため。その札を使い切った（止まる回数が多い）・24時間の期限が切れたあとに落ちると、
  host は Subagent には問うが Factory は起こさず、Subagent の返事は `module-replies.json` に残ったまま、Factory の実行も止まったまま
  （次に誰かが Factory を使うまで）。アーキ仕様 §4.2「Module 宛ての返事」の「まだ決めていない」（残った返事があれば立ち上げるか）
  と同じ問いなので、そこに註を足した。決めていない
- 起こし直したあとに止まった1件は、覚え直した札（最後の1回）を「止まりました」で使い切る。そのあとの最後の知らせは answerFactory の
  呼び出しの札を引き継いで届く（前からの作り）
- Factory だけが落ちて起き直したとき（host は動いたまま）、host は頼んだ Thread に「途中で終わりました」を届け、Factory は記録から
  黙って続ける（札が無いので知らせは `notifyErrors` に残る）。この変更の前からの形で、範囲外
- Subagent は問いの `caller.module` と記録の頼んだ Module（`requestedByModule`）を照らしていない（札の指紋で結びついているので
  別の Module の仕事を続けることは無い）
- 新しい会話の最初のターンで切れた形は、本物のモデルでは通していない（アーキ仕様 §2.5「まだ確かめていないこと」に書いた）
