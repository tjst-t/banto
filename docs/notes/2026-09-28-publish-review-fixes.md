# Publish と Service の Fable レビューを受けて直したこと（2026-09-28）

直す対象はユーザーが決めた（2026-09-28）。決まったことは `docs/specs/v4-architecture.md` §2.5「出所は呼び出し単位で継ぐ」・
`docs/specs/v4-security.md` §3「Project をまたぐ Module の呼び出し」・`docs/specs/v4-modules.md` §4.2・§4.3。
ここには、なぜその形にしたかと、選ばなかった案を残す。

## 1. 入口の画面から押した呼び出しで、窓口が Service を呼べない

- 原因：画面 API（`/api/{threads,projects}/…/ui-tool-call`）が台帳に Project を置いていなかった。中継は「banto 全体の
  Module は、その Project のための呼び出しの中でだけ Project の Module を呼べる」ので、人の画面からは必ず断られていた。
  窓口は Service の宛先が0本だと黙って空にしていたので、画面は「公開できるサーバが無い」ように見えた
- 試験がこれを隠していた：窓口の試験の偽の中継は「人の刻印なら Service が見える」と仮定し、しかも刻印を窓口全体で1つ持っていた。
  **偽物は host の規則をそのまま真似るように書き直した**（呼び出しごとに台帳を持ち、印が無ければ合わせる）

### 刻印の形

画面から Project を置くと、中継の刻印の組み立て（Project が分かれば `{project}`）が人の印を消す——publish-caddy は
「`admin` のときだけ道を張る」ので、人の承認が断られる。人の印を保ったまま Project を伝える形を選んだ。

- **案：`{admin: true, project: "<id>"}`**——却下。受け手はどれも `"admin" in stamp`／`"project" in stamp` で刻印を見分けて
  いる。vault-kit の `findAlias`（名前から置き場を決める）は `"project" in caller` を先に見るので、併記するとそこでは人の刻印が
  Project の刻印として扱われる（人の管理面なのに、その Project の置き場を優先して引く）。今の受け手が無事でも、第三者の受け手が
  `"project" in` を先に書けば同じことが起きる——意味の違うものに同じ名前を付けない
- **案：Project の画面からも `{project}` にして、publish-caddy は別の方法で人を見分ける**——却下。人の印は Vault の紐付けを
  変える口なども見ている。画面の呼び出しだけ意味が変わると、そちらが黙って断るようになる
- **採用：`{admin: true, forProject: "<id>"}`**。今までの受け手には `{admin: true}` にしか見えない（`callerOf` も
  `admin` を先に読む）。Project の Module の画面からの中継は今までどおり `{project}`——Project に縛られた Module に、
  人の画面だからといって全体を見せる向きに変えない
- 注：vault-directory の `createAlias` には `forProject` という**引数**がある。刻印の中の名前とは場所が違うのでぶつからないが、
  読む人は混同しうる

## 2. AI のターンと人の画面が同時に窓口を通ると、人の承認が断られる

- 原因：台帳は接続ごとに走っている呼び出しを全部合わせ、ターンが1つでも混ざればターンと答える（緩いほうへ倒さない）。
  窓口は banto 全体で1接続なので、pA の AI が publishService を処理している最中に人が「公開する」を押すと、
  approve → publishRoute の中継がターンの刻印（`{project}`）になっていた
- 1 と同じ根（出所を接続で持っている）なので一緒に設計した

### 選んだ形：呼び出しの印を host が渡し、Module が中継に返す

- 名前のある解き方：分散トレースの文脈の受け渡し（W3C Trace Context の `traceparent`——呼ばれた側が印を受け取り、下流へ
  添える）。banto の中にも同じ形がある：返信用の札（`dev.banto/replyTo`、host が `_meta` で渡し Module が中継で返す）
- **案：窓口を Project ごとに1本立てる**——却下。承認の画面を出すコードは banto 本体で動かす（`v4-security.md` §1）ので
  コンテナには置けず、banto 本体で Project の数だけプロセスを立てることになる。公開の実装（Caddy）も banto 全体で1本
- **案：Module の側で AsyncLocalStorage を使って印を自動で運ぶ**——Module の中の実装の話で、host との約束（`_meta` に返す）は
  変わらない。窓口は中継の口を明示的に受け渡す形（`Scoped`）にした——試験の偽の中継が印を受け取れる形のほうが確かめやすい
- **案：第三者の Module が返した印も信じる**——却下。印があると同じ接続で同時に走っている呼び出しのうち1件を選べるので、
  第三者は AI のターンの仕事を人の画面の印で中継でき、`admin` の口の承認を飛ばせる（試験で確かめた）。`valueFree` を同梱だけ
  信じるのと同じ線にした
- 印は推測できないもの（以前の台帳の連番ではない）——同じ接続の別の呼び出しの印を当て推量で名乗れないように
- 承認ゲートが承認カードを出す会話も、印があればその1件で決める（2つのターンが同じ Module を使っていても決まる）
- **まだ印を返していないもの**：vault-directory。2つの Project の Shell が同時に秘密を引くと窓口→Vault の2段目で Project が
  決まらない形が残る（コードを読んで判明、実機では未観測）。スコープ外なので `docs/tasks.json` の `vault-directory-call-id` に置いた

## 3. アドレスが一時的に引けないだけで全公開が 503、中継が切れると戻らない

- `containerAddress` の断りを型で分けた（`ContainerAddressUnavailable`＝無い・他人・止まっている・アドレスがまだ無い）。
  それ以外（Incus が答えない・時間切れ・読めない）は「確かめられない」
- **動いているがアドレスがまだ無い（DHCP 待ち）は「確かに届かない」側に入れた**——前のアドレスは別のコンテナに配られうるので、
  前の行き先に残すほうが危ない
- 中継は確かに届かないときに値（`{unavailable}`）、確かめられないときに失敗で返す。**案：両方とも失敗にして文言で分ける**——却下
  （文言で分岐すると、文言を直したときに黙って挙動が変わる）
- publish-caddy は確かめられないときに Caddy の道に触らず `address-unknown` とする。道がそもそも無い（Caddyfile の読み直しで
  消えた）ときも足さない——正しい行き先が分からないまま足すより、次の突き合わせを待つ
- 中継の口（publish-caddy・publish-directory・Service の小さな口）は、中継に届かなかった（HTTP の段で落ちた・接続が閉じた・
  時間切れ）ときだけ作り直す。host の口が理由つきで断ったもの（JSON-RPC のエラー）では作り直さない——作り直しても同じで、
  host 側のセッションが増えるだけ（Service の口は簡単のため失敗なら作り直す）

## 4. 公開中の Service が removeService されたら公開もやめる（案A、ユーザー決定）

- **案：窓口／publish-caddy の突き合わせで「登録が無くなった公開」を見つける**——却下。publish-caddy の突き合わせは 15 秒ごとに
  走るが、そのときは「その Project のための呼び出し」の中ではないので Service を呼べない。窓口が Project の文脈で呼ばれたとき
  （一覧・入口の画面）に見る形だと遅れて気づくだけで、**消して同じ名前で登録し直す（本当に危ない形）は名前が戻っているので
  見つけられない**。登録ごとの印を公開に持たせれば見つけられるが、公開の記録（実装が持つ）に Service の登録の印を運ぶ口が要る
- **採用：Service の `removeService` が、登録を消す前に窓口の `serviceRemoved` を中継で呼ぶ**。Project の Module から banto 全体の
  Module は中継で呼べる。窓口は値を返さないと名乗るので初回の承認は出ない（窓口→実装の `unpublishRoute` は今までどおり初回だけ
  会話で聞く——AI の `unpublishService` と同じ）
- **やめられなければ登録を消さない**。**案：消してから知らせ、失敗は返事に書くだけ**——却下。その失敗の後に同じ名前で登録し直すと、
  直したかった形がそのまま起きる
- 承認待ちの頼みも取り下げる：人が画面で見て承認するのは「web:3000」という名前だけで、中身は見ていない。登録し直した後の中身を
  前の頼みの承認で出さない
- 「やめた」ことを窓口が24時間覚える（`withdrawn.json`）。窓口は公開の一覧を持たない（規則3）が、やめた出来事はどの実装にも
  残らないので、ここにしか置き場が無い。会話への届けは `removeService` の返事（やめた URL が入る）で足りるとした——頼んだ AI の
  会話にそのまま出る。公開を頼んだ会話の札は公開した時点で使い終わっている
- **既存の Service は宣言に窓口への依存が無い**（宣言は入れた時点の目録の写し。中継は宣言の依存でしか宛先を許さない）ので、
  入れ直すまで知らせが届かない。宣言を目録に合わせて直す仕組みは今は無い
- 知っている穴：serviceRemoved の中の窓口→実装の中継が初回の承認で止まっている間、host→窓口の呼び出しは進捗を受けないので
  60 秒で切れうる（入れ子の承認の進捗送出がまだ無い、`v4-security.md` §3 の「初回承認ゲート・監査」の行）。切れたら
  removeService は理由つきで断られ、登録は残る（黙って消えない）

## 5. 細かいもの

- 窓口が「Service の Module が無い」と「どの Project か決められない」を取り違えていた——中継の宛先の一覧の返事に、どの Project の
  ための呼び出しとして一覧を作ったか（`dev.banto/onBehalfOf`）を添え、それで分けた。**案：窓口が自分で Project を推す**——
  却下（中継が見せなかった理由は中継しか知らない）
- approve：記録してから会話に届ける。publishRoute は通ったのに返事が落ちたら、実装の一覧にその公開があれば公開したと確定させる。
  **案：「もう公開しています」の文言を見て確定させる**——却下（別の実装の文言に依存する）。一覧に同じ（サービス, ポート）が
  あれば、それが前からあったものでも「公開している」は事実なので確定させてよい、とした
