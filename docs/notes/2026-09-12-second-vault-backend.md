# 2本目の Vault（Infisical）を作り、`vault-kit` を切り出した（2026-09-12）

決まったことは `docs/specs/v4-modules.md` §2.1 に書いた。ここには**実物を作って
初めて分かったこと**と、なぜその順番にしたかを残す。

## なぜこの順番だったか

Fable のアーキテクチャ検討（`2026-09-12-vault-architecture.md` 参照）は
「窓口（facade）の移動は**2本目の backend が実在してから**」と結論した。
理由は CLAUDE.md の2つの文が同じことを言っているから：

- 「契約は先に決め、中身は後」
- 「backend が1本しか無い状態で共通化すると、抜き出す境界を推測することになる」

**決めることと抽出することを分けろ**、という指示である。そこへユーザーから
「もう Infisical で2本目を作ってほしい」と来たので、**推測する理由が消えた**。

## 実物を作って出てきた差分（推測では出なかったもの）

### ① `createGroup` が冪等でない

SOPS は `mkdir -p` なので何度呼んでも平気。**Infisical の `folders.create` は
既にあると 400 で落ちる**。呼び出し側（kit）は alias を作るたびに `createGroup`
を呼ぶ設計なので、ここが冪等でないと**2つ目の alias が作れない**。

`VaultBackend` の契約に「冪等であること」と**書いていなかった**——SOPS の
都合が暗黙の前提になっていた。Infisical 側で飲み込み、仕様にも明記した。
**「既にある」以外の失敗は通す**（規則2——握りつぶさない）。

### ② メタデータの置き場は backend が選ぶべきだった

いちばん大きい発見。

alias のメタデータ（kind・scope・projectId・note・lastUsedAt）は、これまで
**Module 側のローカルファイル**（`aliases.json`）にあった。SOPS ならそれでよい
——仕様 D節も「組み込み（SOPS）はメタデータの持ち方自体を banto が決められる」
と書いている。

ところが**仕様 §2.1 は「複数台のホストが同じ backend（同じ Infisical
アカウント等）を共有できるようにする」ことを、Infisical を名指しで決めている**。
メタデータがローカルにあると、**2台目のホストからは値はあるのに名前も種別も
用途も分からない**——共有が半分しか成立しない。規則13 の親戚（繋がっている
ように見えて、繋がっているのは値だけ）。

**Infisical には秘密ごとの注記（`secretComment`）があり、値を読まずに一覧で
取れる**ことを実測で確認した（仕様 D節「メタデータは値と分離して持つ。値を
復号・解錠せずに読める必要がある」をそのまま満たす）。なので Infisical 実装は
**メタデータを Infisical 自身の中に置く**。

- **別の台帳ファイルを持たない**（規則3）。alias を消せばメタデータも消える
- **写しを手元に持たない**——共有が眼目なので、毎回聞く。手元に貯めると、
  別のホストが変えたときに古いものを見せる
- **banto が付けた注記の無い秘密は alias として数えない**（規則2）。Infisical は
  banto 以外からも書ける。「たぶん secret だろう」で拾うと、人が別の用途で
  置いた秘密まで一覧に混ざる

この差を受けて、`AliasStore` を**差し替え可能・非同期**にした。遠くにある
置き場は同期では読めない（`get`/`list` が `Promise` になった）。

### ③ 秘密鍵は Infisical では作れない

Infisical に鍵ペア生成の口は無い。`ssh-keygen` で作って**秘密鍵を秘密として
預ける**。`privateKeyRef` は不透明な参照なので、`VaultBackend` の契約
（「backend によっては秘密鍵が一度もプロセスに出てこない」）は壊れていない
——Infisical の場合は出てくる、というだけ。平文の鍵は `finally` でも残さない。

## `@banto/vault-kit` の境界（実物2本から切った）

```
kit が持つ（共通）              各 backend が書く
─────────────────────────      ─────────────────────
A/B/C の tool・resource 配線     VaultBackend（D節の8メソッド）
alias の台帳の契約（AliasStore）  AliasStore の実装（置き場を選ぶ）
会話の中の入力欄（MCP App）      設定 Canvas（持たなくてよい）
Project ↔ グループの紐付け
```

- **`vault`**：SopsBackend ＋ `LocalFileAliasStore` ＋ 設定 Canvas
- **`vault-infisical`**：InfisicalBackend ＋ `InfisicalAliasStore`（設定 Canvas 無し
  ——横断管理は VaultUI がやるので、薄い画面をもう1枚増やす理由が無い）

**会話の中の入力欄の URI は Module ごとに分けた**（`ui://banto-vault/request` と
`ui://banto-vault-infisical/request`）。2本並んだとき、どちらの画面かが URI から
分かる必要がある。

却下した案：**複製する。** 600行を2つ持つと、窓口の設計に進んだとき直す対象が
2倍になる。仕様も最初から「共通ロジックは npm ライブラリで共有し、Module 間の
MCP 契約にはしない」と言っていた（Module を分けると値が余分な1ホップを通る）。

## 資格情報の置き場——金庫を開ける鍵は金庫に入らない

Infisical の Machine Identity（clientId/clientSecret）は **Infisical には
入れられない**。組み込み Vault の `identity.txt`（age の秘密鍵）と
**まったく同じ category**——仕様が「alias 解決の対象ではない、唯一、本当に
特別な1点」と呼んでいるもの。

**宣言（`DEFAULT_MODULE_DECLARATIONS`）には書かない。** 宣言は Event Store に
残るので、書くと**秘密が記録に残る**。host の環境変数を子がそのまま継ぐ
（`cli.ts` が `...process.env` を渡す）ので、置き場は運用側になる。

却下した案：**差し込み語 `${env:…}` を足す。** 宣言の語彙を増やすことになるうえ、
結局 env を読むだけなので、継承で足りる（規則12——機構を増やさない）。

## 開発用の Infisical

`packages/modules/vault-infisical/dev/`（docker compose ＋ README）。
**行き先は Infisical Cloud**（確認・2026-09-12、ユーザー）——ここで立てるのは
開発と試験の相手であって運用先ではない。**backend のコードは自前ホスト固有の
前提を持たない**（違いは `siteUrl` と資格情報だけ）。

試験を自前ホストにしたのは、組み込み Vault の試験が実 `sops`/`age` を叩いて
いるのと同じ形にするため（規則1）。外のネットワークとアカウントに依存しないので
間欠の原因が増えず（規則6）、試験で作った秘密が人の本番に残らない。

### 途中で踏んだもの（記録）

- **存在しないイメージタグをでっち上げた**（`v0.132.2-postgres`）。Docker Hub を
  見て実在する `v0.165.10` に直した。**版は固定する**——`latest` だと、ある日
  勝手に変わって試験が落ちた理由が分からなくなる
- **bootstrap は1回きり**なのに、返ってきたトークンを画面で切り詰めて表示して
  取り損ねた。中身が空のうちに積み直した。`dev/README.md` に「必ず保存する」と書いた
- bootstrap のメールは**ドメインが必要**（`@localhost` は 422）
- **統合試験のパスを間違えて、8件が黙って skip された**。skip の理由は出して
  あったので気づけたが、**「黙って緑」に一番近い形**だった（規則1）

## いま起きていること——4つの割れ目が日常に出た

既定に入れた（ユーザー選択——「割れ目を日常で規定事実にする」）。実機で
`vault` と `vault-infisical` が同時に立ち、VaultUI の横断一覧に
`implementation` つきで両方が出ることを確認した。

ここから先は、Fable の検討が予告していたとおりになる：

1. **AI に `requestAlias` が2つ並ぶ**（`mcp__vault__` と `mcp__vault-infisical__`）
2. **AI から見える `vault://aliases` が2つに割れる**
3. **Shell は `"vault"` を決め打ちしている**ので、Infisical 側の alias に届かない
4. **会話の中の入力欄が2枚ある**

**これを見ながら窓口（`vault-directory`）を設計する**というのが、今日の選択。

### 実際に E2E で出た（予告が実物になった）

既定に入れて全 E2E を回したら4件落ち、**3つの性質に分かれた**：

- **私のリグレッション**（1件）——kit へ移すとき、設定 Canvas の表示名を
  `moduleName` で上書きしてしまい「Vault」が「vault」になっていた。
  表示名は Module が決めるものなので、`configApp.name` として渡す形に直した
- **設定していない環境のノイズ**（2件）——資格情報が無いと `vault-infisical` が
  繋がらず、受信箱に「繋げませんでした」が毎回1件出る。**割れ目ではなくノイズ**。
  E2E には開発用の資格情報を渡す形にした（無ければ警告して繋がない）。
  **運用でも同じことが起きる**——Infisical を設定していない人には毎回お知らせが
  出る。窓口を入れるときに「設定が無ければ既定から外れる」形を考える必要がある
- **本物の割れ目**（1件）——`project-modules` の「要るものを外すと警告が出る」が
  落ちた。`vault` を外しても **`vault-infisical` が同じ役割を満たす**ので、
  警告が出ないのが**正しい新挙動**。試験のほうを直した（役割を満たすものが
  全部消えて初めて「動きません」と言う）。**名前ではなく役割で見ている**ことが
  試験で押さえられた形

さらに `vault-request-inline` が**単独では通るのに全体では落ちた**——
**AI がどちらの Vault を選ぶか毎回変わる**。これが割れ目①の実物。試験は
「どちらであれ入力欄が出て、実 Vault に届くか」を横断一覧で確かめる形に変えた
——**問題を隠さず、機構は見る**。AI 向けの指示も「`vault://aliases` を**全部**
読んで」と書かざるを得なくなり、割れ目②が文面に現れている。

## 4つの割れ目のその後（同日・夕方）

**①②③は窓口（`vault-directory`）で閉じた**——経緯は
`docs/notes/2026-09-12-vault-directory.md` の末尾。要点だけ：

| 割れ目 | どう閉じたか |
|---|---|
| ① `requestAlias` が2つ並ぶ | backend 側を `module` へ降格。**AI に見せるのは窓口の1本だけ** |
| ② `vault://aliases` が2つに割れる | 窓口が横断して1本にまとめる。`implementation` は**落とす** |
| ③ Shell が `"vault"` 決め打ち | `lookupAlias` で在りかを引いてから、その金庫を直接呼ぶ |
| ④ 入力欄が2枚 | ①と同じ——窓口の1枚だけが `agent` に見える |

**④の「backend ごとに URI を分けた」判断は、結果として無駄にならなかった**
——`module` 可視性のまま残っているので、窓口を経由しない直接操作では今も使える。

**残っているのは「設定していない環境のノイズ」だけ**（上記）。これは割れ目ではなく、
既定の組み方の問題。
