# Shell と Vault を、初めて画面から確かめた（Phase 1）

2026-09-06。`docs/tasks.json` の `phase1-modules-verified-in-browser`。

3本の Module のうち **FileSystem だけ**が画面から通しで確かめられていた
（承認・拒否の E2E）。**Shell と Vault は一度も画面から触られていなかった**
——この2つは「壊れても静かな」機構を持つので、見ないまま Phase 1 を閉じない（規則1）。

## この2つが「静かに壊れる」理由

- **Shell の閉じ込め**：普通の作業は Project の中で完結するので、壊れていても
  **全部成功してしまう**。壊れているのは「外に出られてしまう」ときだけ分かる
- **Vault の可視性**：AI に「実際の値を取る道具」が見えていても、AI が呼ばない限り
  画面は正常に見える

だから今回の確認は「やったらできた」ではなく **「やってもできない」** を見る。

## 追加した回帰テスト（毎回の E2E で回る）

### `shell-confinement.spec.ts`——両側から見る

- **Project の中**：`cat <root>/inside.txt` → 承認して**中身が出る**（Shell が動いている）
- **Project の外**：許可リストに無い一時ディレクトリのファイルを `cat` →
  **その中身が画面にも host の記録にも出ない**

片側だけでは証明にならない（中も外も失敗するなら、閉じ込めではなく Shell が
壊れているだけ）。**`/etc` や PATH の下は読み取りが許されている**ので、
外の証明にはそこを使わない（v4-security.md の許可リストの組み方）。

### `vault-visibility.spec.ts`——AI が繋がる経路そのものに問い合わせる

AI の言葉づかい（「その道具は持っていません」）に頼らず、**host の中継に
`tools/list` を投げて**、Runner に見えているものと同じ一覧を取る。

- `requestAlias`（申請）は**見えている**——Vault が動いていることの確認
- `resolveAlias`・`startSshAgent`・`generateKeypair`・`verify`（module 限定）は**見えない**
- `createAlias`・`deleteAlias` 等（admin 限定）も**見えない**
- Module 自身の申告（host だけが読む資源）も漏れていない

Module は**ターンで初めて起動する**ので、1ターン走らせてから見る。

## 「通った」だけで終わらせない——壊したら落ちることを両方で確認した

**Shell**：閉じ込め**無し**で同じ Module を起動し、同じコマンドを実行したら
**外のファイルが読めた**（`exitCode: 0`、中身が返る）。
＝ E2E で読めなかったのは閉じ込めのおかげ。

**Vault**：中継の可視性フィルタを一時的に外したら、
`resolveAlias が AI から見えている（module 限定のはず）` で**落ちた**。
＝ このテストは実際にフィルタを見ている。

## 測った結果

**core 単体 74件・E2E 13 spec 全通過**（約1.4分）。
