## Vault の議論

**きっかけ**：`docs/specs/v4-modules.md` は Vault を「作りたい Module
（必須ではない）」に置いていたが、§2.8 の複数資格情報の使い分けは
banto の中核機能として既に決定済み——**矛盾に気づいた**。加えて
「banto 起動直後、資格情報が要るのに Module 集合の解決がまだ済んでいない」
という鶏卵問題があった。

**出た案と選んだ理由**：

- 「Vault を core に完全に統合する」案も出たが、**複数バックエンドという
  構造は失いたくない**というユーザーの判断で却下。役割（`vault`）としての
  枠組みは維持し、**組み込みのローカルバックエンドを同梱する**ことで
  鶏卵問題を解いた（Module としての独立性と、ゼロ設定起動を両立）
- 「同梱」を「core と同じプロセス」と誤解しないよう明示——
  `docs/requirements.md` C8b の「鍵を持つものは subprocess」は崩さない

**Module 間直接呼び出し（C10）の監査**：「データはコアを通さないが、
呼び出し自体はコアを経由しないと発動できないようにできないか」という
ユーザーの提案から、**control-plane / data-plane 分離**という名前のある形
（規則12）に落とした。メタデータだけの許可要求は core を通し監査・承認
ゲートを掛け、実データは直接。許可は呼び出しの組み合わせごとに初回のみ
確認（Claude Code 自身の許可プロンプトと同じ形）。

**明示的に先送りしたもの**：**許可トークンの発行・検証**。「Core に先に
聞く」という行儀のよい Module の前提に今は乗るだけで、悪意ある／バグの
ある Module が negotiation をすっ飛ばして直接呼ぶことを防ぐ仕組みは無い。
ユーザーの判断で「トークン発行・検証は TODO 化、まずは後者（検証なし）で
進める」と明示的に決めた——セキュリティ境界の設計（§2.7、まだ着手前）に
持ち越す。`docs/specs/v4-architecture.md` §2.7「詰めるときの論点」に追記済み。

**alias 方式**：Shell に秘密情報を渡す具体例を考える過程で出てきた。
値をコマンド文字列に混ぜると AI の文脈・tool 呼び出しの記録の両方に
写ってしまうため、**名前（alias）だけを AI に見せ、値は実行直前に
Shell が Vault から取って子プロセスの環境変数テーブルに直接注入する**
という形にした。副産物として、**§2.7 で保留していた「shell からネット
ワークに出てよいか」が、この用途で具体的に刺さる**と分かった——まだ
決めていないが、放置すると alias 方式自体の使いどころが無くなる。
