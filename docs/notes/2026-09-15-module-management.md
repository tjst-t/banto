# Module をどう管理するか——問題の整理（2026-09-15）

ユーザー提起「Module について、ちょっとちゃんと考えてみよう。結構考えることが多い」。
きっかけは「`vault-infisical` をもう1本立てて Infisical Cloud に繋ぎたい」で、
そこから**これは Vault の話ではなく Module 管理の話**だと分かった。

**このノートは整理と提案であって、決定ではない。** 決めたことは `docs/specs/` へ。

## いま在るもの（コードを読んで確かめた）

| 在る | 実体 |
|---|---|
| 宣言（起動の仕方＋meta） | `DEFAULT_MODULE_DECLARATIONS` ＋ Event Store の差分（overlay） |
| 差分の重ね方 | VS Code 方式。**既定に無い名前は「新しい Module」として足せる**（`overlay.ts:88-97`）——つまり**足す土台は既にある** |
| Project ごとに使う／使わない | `setProjectModuleSelection` ＋ `/api/projects/:id/modules`（GUI あり） |
| 立っているか・理由 | `moduleStatusForProject` が `connected` と `error` を返す。失敗は受信箱にも出る |
| 使える状態か | `readiness()`（2026-09-13。未設定でも立ち、値を触る口だけ断る） |
| role → 実装の一覧 | `relayListTargets`（呼ぶ側が選ぶ。決め打ちを避けるため） |
| 起動の形 | **1種類だけ**——「このプログラムを、この引数で、この環境変数で」（§5.1、2026-09-06） |
| 自己申告 | 任意。名乗らない Module は宣言だけで起動する（`selfreport.ts`） |

| 無い | 何が困るか |
|---|---|
| **宣言を足す／消す口**（API も GUI も） | コードか Event Store の直書きしかない。§10 item 14 (a) が未着手 |
| **instance 層の有効/無効** | Project ごとの選択はあるが、banto 全体で止める口が無い |
| **リモート MCP**（`url` + `headers`） | 起動の形が command/args/env だけ。`server.json` の `remotes` に乗れない |
| **同じ role を何本まで見せてよいかの規律** | 呼ぶ側が名前を決め打ちしている（Shell は `"vault-directory"` を直書き） |
| **宣言に秘密を書けない問題の答え** | 一般の MCP は `env` に API キーを直に書くのが普通。宣言は Event Store に残る |

## 用語を3つに分ける（提案）

いま**宣言1つが「実装」と「その1本」を兼ねている**。だから
「もう1本 Infisical」がコードの改変になる。分ける：

| 層 | 何を言うか | 例 |
|---|---|---|
| **実装** | 何を起動できるか（プログラム・引数の型） | 同梱の `vault-infisical`／外から取り込んだ `server.json` |
| **登録** | その実装の、**名前つきの1本**。自分のデータ置き場と設定を持つ | `vault-infisical`（自前ホスト）と `vault-infisical-cloud` |
| **有効化** | どこで使うか | banto 全体で止める／Project ごとに AI へ見せる |

**導出されるもの**（人が設定しない・規則3）：

- **起動できるか**——これは**測るもの**。`npx` は実行時に取りに行くし、ファイルは
  消えていることもある。「インストール済み」という状態を持つと、いつか実態と食い違う
  （規則1・規則3）。**「試す」を押して実際に起動してみる**のが答えで、
  持ってよいのは「最後に試したときの結果」だけ
- **立っているか**——遅延起動なので、要るときに立つ。人が起動ボタンを押す設計にしない
- **使える状態か**（`readiness`）——立っているが未設定、がある（Infisical）

**人に見せる状態は3つ**：`使える` ／ `立っているが未設定`（設定画面へ）／
`繋がらない`（理由と「試す」）。

## 新しく要る規律：同じ role は、AI に見える面で1本だけ

ユーザーの「複数立てられるものと一つだけのものがある」は、**実装の性質ではなく
role の性質から導ける**：

- `vault-infisical` を何本立ててもよいのは、**A 面（AI に見せる口）を持たない**から
  （`agentFacing: false` で `module` 可視性に降格している）
- `vault-directory` が1本なのは、**AI に見せる窓口そのもの**だから。2本あると
  AI に `requestAlias` が2つ並び、**選ぶ材料が無い**——2026-09-12 に実測した
  「走らせるたびに選ぶ先が変わる」がそのまま戻る

したがって規律はこう書ける：

> **AI に見える面では、同じ role を名乗る Module は1本まで。**
> 複数持ちたいなら、**束ねる窓口を立てて、窓口だけを AI に見せる**（Vault の形）。
> Module 間（`dependsOn`）では何本でもよい——`relayListTargets` で呼ぶ側が選ぶ。

**導出できるので、宣言に「1本だけ」と書かせない**（規則3）。繋ぐときに host が
検査して、2本目を**理由つきで断る**。あわせて、**呼ぶ側の決め打ちをやめる**
——Shell の `"vault-directory"` 直書きは、この規律があれば
「role `vault-directory` を名乗る唯一の1本」に書き換えられる。

## 有効化の軸は2つある（ユーザーの一覧に無かったもの）

「繋ぐ／繋がない」は**1つではない**：

1. **登録を有効にするか**（banto 全体）——止めたいとき。プロセスも立たない
2. **その Project の AI に見せるか**（Project ごと）——いまの Module 画面

**2つが要る理由**：`vault-directory` は Shell の依存なので、**誰も AI に見せて
いなくても立つ必要がある**。「どの Project でも見せない＝立てない」にすると、
依存で要求されている Module が落ちる。逆に「全部立てる」にすると、止めたいときに
止められない。

**プロセスが立つかは導出**：登録が有効で、かつ（どこかの Project が見せる ∪
誰かが `dependsOn` で要求する）なら立つ。人はこれを設定しない。

## 一般の MCP サーバを繋ぐ——3つの壁

§5.1 は既に「`server.json` か `mcpServers` に乗る。独自形式を作らない」と決めている。
その上で、いまの実装との差は3つ。

### 壁1：秘密を宣言に書けない

`mcpServers` の慣習は `env: { "GITHUB_TOKEN": "ghp_..." }`。ところが banto の
**宣言は Event Store に残る**（§5.1）ので、**そのまま書くと秘密が記録に残る**
——`vault-infisical` の資格情報を宣言に書かないと決めたのと同じ理由。

**提案：`env` の値に Vault の名前を書けるようにする。**

```
env: { GITHUB_TOKEN: "${secret:github-token}" }
```

起動の直前に host が Vault から引いて差し込む。既に差し込み語の仕組み
（`${moduleDataDir}` など）があり、**知らない語は起動前に落とす**規律もある
（規則2）ので、そこに1語足すだけ。今日直した Vault の三つ組・刻印がそのまま効く
（**どの Project のために起動する Module か**が分かっているので、
使ってよい秘密かを判定できる）。

> これは「人が手で貼り付けた API キーが Event Store に残る」という、
> **一般 MCP を受け入れた瞬間に踏む穴**。先に塞いでおく価値が高い。

### 壁2：リモート（`url` + `headers`）は起動の形に乗らない

「起動の形は1種類だけ」（2026-09-06）は**起動するもの**の話で、
リモートは**起動しない**。§5.1 は `remotes` を認めているので方向は矛盾しないが、
**形が2つになる**ことは明示的に決め直す必要がある（規則8——黙って増やさない）。

あわせて考えること：リモートには**閉じ込めが効かない**（Landlock は自分のプロセス
にしか掛からない）。**中で何が動くか分からない**という点では subprocess の
第三者 Module と同じだが、「どこへ出ていくか」が見えない分だけ性質が違う。

### 壁3：名乗らない Module の meta を誰が決めるか

一般の MCP サーバは `dev.banto/module` を名乗らない（当然）。そのとき
**`scope`（Project ごとか instance か）・`isolation`・`confinement`・
`handlesSecrets` を誰が決めるか**。

- `scope`：**人が選ぶしかない**。Project の根が要るサーバ（git・filesystem 系）は
  `project`、要らないもの（天気・検索）は `instance`。既定は？
- `handlesSecrets: false` なら tool ごとの可視性は不要で、全部 AI に見える
  ——一般の MCP サーバはそれでよい
- `confinement`：第三者コードなので**閉じ込めたい**が、何を許せばいいかは
  サーバによる。既定を厳しくすると動かないサーバが出る

## 決めないといけないこと（私の推しつき）

| # | 問い | 推し |
|---|---|---|
| 1 | 「実装」を独立した概念として持つか | **持たない**。当面は「登録」だけにして、GUI の「同じものをもう1本」は宣言の複製。ただし**どこから来たかの印**（`server.json` の identifier 等）は残して、後から実装の層を足せるようにする（規則10——必要になってから） |
| 2 | 有効化の軸 | **2つ**（登録の有効/無効・Project ごとに見せるか）。プロセスが立つかは導出 |
| 3 | 同じ role を何本まで | **AI に見える面では1本**。host が繋ぐときに検査して断る。呼ぶ側の名前決め打ちをやめる |
| 4 | 秘密の渡し方 | **`${secret:name}`** を差し込み語に足す。宣言に平文を書かせない |
| 5 | リモート MCP | **起動の形を2つにする**（起動する／繋ぐだけ）と明示的に決め直す |
| 6 | 「起動できるか」 | **測る**。状態として持たない。GUI に「試す」 |
| 7 | 消したときのデータ | **消さない**が既定（`moduleDataDir` もその Module が Vault に置いた秘密も）。「まとめて消す」は別操作・別の確認 |
| 8 | 名前を変えられるか | **変えられるが、承認はやり直しになる**（実測済み——中継の許可は名前で引く）。画面でそう言う |

## まだ整理しきれていないと感じるところ

- **Project ごとに「同じ実装の別の1本」を使い分けたいか。** 例：Project A は
  自前 Infisical、Project B は Cloud。いまの形（登録は instance、Project は
  見せる/見せないだけ）でも**置き場の紐付け**で実現できるが、
  「この Project ではこちらの登録を使う」という直接の表現は無い
- **`dependsOn` の解決を人が上書きしたいか。** いまは呼ぶ側が選ぶ。
  「この Project の Shell は、こちらの Vault を使う」を人が決めたい場面はあるか
- **同梱 Module の更新と、複製した登録の関係。** 同梱は差し込み語（`${monorepoRoot}`）
  なので複製も一緒に上がる。外部 MCP の version は登録ごとに散る
- **Landlock の profile を人がどう選ぶか**（§10 item 19 と重なる）
