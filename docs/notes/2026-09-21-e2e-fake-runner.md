# E2E から実 LLM を外した（2026-09-21）

## なぜ

フル E2E で `vault-request-inline` が**間欠的に落ちていた**。測ると、完走5回中2回。
単独では7回とも緑。落ち方はいつも同じで、**AI にターンを回して tool を呼ばせ、
入力欄が出るのを 180 秒待つ**ところの時間切れ。

ユーザーの問い：「そもそも回帰テストに実 LLM を使うのはおかしくて、モックで
やるべきでは？」

## 判断：実 LLM を使う E2E spec は1本も要らない

AI のターンに依存していた spec は22本。頼んでいる内容は**2種類しかなかった**：

- **「この言葉を返して」** — `「いちばん目」とだけ返して` 等。見たいのは Fork・
  文脈使用量・畳む／開く・再接続・高さで、**AI の文は目印にすぎない**
- **「この tool を呼んで」** — `listDirectory で…` 等。見たいのは承認カード・
  受信箱・Canvas・中継ゲート・閉じ込めで、**AI は tool_use を1つ出す引き金**

どちらも対象は **banto 自身の振る舞い**。モデルが何を選ぶかは検証対象ではなく、
むしろ邪魔をしていた——`vault-request-inline` のコメント自身が
「走らせるたびに選ぶ先が変わる」と書いている。

**本物の SDK と喋れているかだけは別**だが、その居場所は既に在った
（`packages/core/src/runner/adapter.smoketest.mjs`）。E2E が22本がかりで
引き直す必要は無い。**`npm run check:agent-sdk` の口を足した**——それまで
手で叩く前提で、「コミット前に何を回すか」にも入っていなかった。

## 作ったもの

**差し替え口**（`cli.ts`）。`AppDeps.runTurn` は元から在り単体試験が使っていた。
本番の経路が渡していないだけなので、**env（`BANTO_FAKE_RUNNER`）が指すときだけ**
流し込む。本番では効かない。**指していて読めなければ理由を言って起動を止める**（規則2）。

**偽 Runner**（`e2e/fake-runner.ts`）。**偽物にするのは AI だけで、その先は全部本物**
——tool は実際に MCP の口へ繋いで呼ぶ。そうしないと承認カードも受信箱も Canvas も
動かず、試験の意味が消える。

spec は**プロンプトの末尾に印**を書いて指示する（`fakeTurn({...})`）。印より前は
人が読む文のまま残すので、**画面の見た目は今までどおり**で、決まり方だけが決定的になる。

### 踏んだ設計上の判断

**承認を求めるかどうかを固定にしなかった。** 本物は `permissionMode` が `auto` なら
求めず `default` なら求める。固定にすると**どのモードでゲートが効くかという検証が
消える**——実際 `vault-request-inline` は承認を扱っておらず、固定なら永久に待っていた。

**承認は「呼ぶ」だけでなく「流す」。** banto が判断待ちを立てるのは、コールバックでは
なく**流れてきた `approval_requested` を見たとき**。呼ぶだけで待つと、受け手に
イベントが届かないまま両方が止まる。

**tool の結果を発言として返す。** 本物のモデルは結果を読んで一言添える。
省くと記録に残る assistant の発言が空になり、「答えたあとの続きが画面に入る」類の
試験が通らない。

**Global Memory は「届いたか」を直接見る形にした。** 以前は「モデルが合言葉を
覚えていて答えてくれること」に賭けていた。偽物は**banto が実際に送った文脈**を
返せるので、そちらを見る——モデルの機嫌に依存しない、**より強い**検査になった。
同じ理由で `vault://aliases` も、読めた中身をそのまま発言に載せる形にした
（値が漏れていれば spec が捕まえる）。

## 効果（実測）

| spec | 実 LLM | 偽 Runner |
|---|---|---|
| `inbox` | 1分11秒（落ちる） | **4.2秒** |
| `judgment-deny` | 1分11秒（落ちる） | **4.1秒** |
| `judgment-after-reload` | 2分6秒（落ちる） | **6.4秒** |
| `shell-confinement` | 3分6秒（落ちる） | **3.5秒** |
| `vault-request-inline` | 23〜35秒・フルでは5回中2回落ちる | **12.7〜13.3秒、5回とも緑** |
| 前半38本 | 8.1分 | **1.9〜3.8分** |

## 偽物が掘り出した、本物の不具合

**速さが落ちると隠れていた競合が出る。** モデルの遅さが覆いになっていた。

1. **承認の答えが画面に残らない**（`judgment-answer-render-race`）。画面は host に
   答えを送るのを待ってから記録へ書き戻すが、**その待ちの間にターンが完走すると
   SSE が先に閉じる**。偽 Runner 側に 500ms の間を入れて回避しているが、
   **画面側の競合はそのまま**
2. **Canvas が開かない／中身が来ない**（`fullscreen-canvas-order-fragility`）。
   `module-canvas-inline` の「フルスクリーン」と `frontend-interaction` の「Canvas の橋」は、
   **単独なら数秒で通るのに、同じ worker で別の Canvas を開いた後だと落ちる**。
   `toolDelayMs` で間を入れても直らなかったので**戻した**——待ちで隠すのは筋が悪い（規則6）

どちらもタスクに起票した。**2本は落ちたまま残している**——緑にするために
待ちを足すことはしない。

## 残り

- 100本中 **98本が緑**。落ちているのは上記2本（原因は同じ系統と思われる）
- `banto-memory` はプロセス内の SDK サーバで HTTP ではないため、偽 Runner から
  同じ手では呼べない。いまは `sayContext` で「届いたか」を見る形で足りている
