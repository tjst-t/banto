# 長い会話・Fork で画面がもっさりする（2026-09-29）

ユーザー指摘「体感が全体的にもっさり遅い。使うのがしんどい」→「長いセッションでも全ログを画面に
保持している。長いセッションを Fork すると Fork 画面でも全ログが出る。これが重い原因では？」。
前回の遅さのレビュー（`2026-09-25-latency-review.md`）は通信だけを見ていて、**描く量は測っていなかった**。

## 1. 測り方

- `banto/e2e/heavy-thread-probe.mjs`：host の記録の大きさ（Project・Thread ごとの発言数と応答の大きさ）と、
  一番重い Project を実際に開いて「落ち着くまでの時間・DOM の数・long task・1文字ごとの反応・Fork を開く時間」
- `banto/e2e/heavy-thread-profile.mjs`：その間の CPU プロファイル（関数ごとの self time）
- 合言葉は Vault の `banto-token` を `PROBE_TOKEN` に渡す（`BANTO_` で始まる名前は envSecrets に使えない）。
  `PROBE_CPU=4` で CPU を 4 倍遅くする（ノート PC・携帯の見込み）。読むだけで、発言・変更はしない

## 2. 実測（稼働中の banto、「Banto開発」Project）

host の記録：Base 193 件。開いている Fork 5 本はどれも親の約 180 件を写して持つ（1 本 250 KB 前後）。
取るのは 1 本 10 ms 前後——**通信は遅くない**。

| 操作 | CPU ×1 | CPU ×4 |
|---|---|---|
| Project を開いて落ち着くまで（193 件） | 3.0 s、long task 1.2 s（最長 0.69 s） | 8.9 s、long task 6.8 s（最長 3.1 s） |
| Fork を開く（Base と並んで 375 件、DOM 1.1 万） | 1.3〜2.2 s | 5.5〜9.6 s（最長 2.9 s 固まる） |
| 1 文字ごとの反応 | 中央 16 ms | 中央 88 ms・最大 232 ms |

Fork を開いたときのプロファイル（CPU ×4、忙しかった合計 5.6 s）：

- **1.4 s**：Radix の `Presence` の `getAnimationName`（`getComputedStyle(...).animationName`）——発言ごとの部品が
  見た目を問い合わせ、そのたびに 1 万個の DOM のスタイルを計算し直す
- **1.2 s**：assistant-ui の Viewport の自動スクロール——`MutationObserver`（subtree・attributes・characterData）と
  `ResizeObserver` のたびに `scrollHeight` を読み、レイアウトを強制する
- 文字を打つとき：入力欄の状態の変化が、描いている全発言の `useAuiState` の購読者に配られる（`notifySubscribers`・`get`）

**どれも描いている発言の数に比例する。** 個々を削るより、描く数を減らすのが効く。

## 3. 決めたこと（ユーザー、2026-09-29）

- 会話は**最新の 20 件だけ**描き、上端の「それより前を表示」で 20 件ずつ足す。スクロールで自動に足す形は採らない
  （2026-09-10 に「上へ辿ると位置がずれる」問題を直した経緯）
- **Fork の画面では、分ける前の親の会話は最後の 1 件だけ**出す
- host が Fork に親の記録を写す仕組み（`project-thread/fold.ts`）は変えない——通信は遅くない

却下：最初に描く数は多め（40 件）を提案したが、ユーザーが少なめを選んだ。
Fork の親の分は「窓で自然に軽くなる（直前の親のやり取りが少し見える）」を提案したが、最後の 1 件だけにした。

## 4. 作り

- `components/banto/thread/message-window.tsx`：ランタイムには全件を持たせたまま、**描くのを窓の中だけ**にする
  （記録の流し込み・走っているターンには触れない）。窓の始まりは**発言の id で覚える**——件数で覚えると返事が
  増えるたびに窓が下へずれ、上を読んでいる人の足元が消える。足したときは一番下からの距離を保って見ていた場所を
  動かさない。読んでいた場所へ戻す（`RememberScrollPosition`）ときは、その発言が窓に入るところから始める
- `components/banto/thread/thread-panel.tsx`：Fork の画面に渡す発言を「親の最後の 1 件＋Fork 自身の分」に絞る。
  親の分の横線（Clear 等）も出さない。親の会話に置く「この Fork を開く」の件数は Fork 自身の分だけを数える
  （以前は写した分も数え、分けたばかりでも「180 件のやり取り」と出ていた）

## 5. 直した後（2026-09-30、同じ条件で前後を続けて測った）

直した画面は別の置き場でビルドして 4197 で起こし、API は稼働中の host を使った（`PROBE_API`）。

| 操作 | 前 CPU ×1 | 後 CPU ×1 | 前 CPU ×4 | 後 CPU ×4 |
|---|---|---|---|---|
| Project を開いて落ち着くまで | 3.4 s（long task 1.6 s） | 2.2 s（0.4 s） | 9.7 s（7.4 s、最長 3.1 s） | 4.7 s（2.6 s、最長 0.8 s） |
| DOM の数 | 6,200 | 820 | | |
| Fork を開く | 1.4〜2.3 s | 0.73〜0.76 s | 5.3〜9.1 s | 0.84〜1.4 s |
| Fork を開いた後の DOM | 11,600 | 1,200〜1,450 | | |
| 1 文字ごとの反応 | 中央 16 ms | 中央 16 ms | 中央 72 ms・最大 192 ms | 中央 40 ms・最大 56 ms |

振る舞い（`heavy-thread-behavior.mjs`）：ボタンで 20→40 件、見ていた発言の位置は 68px→68px（最初は
一番下からの距離で1回だけ合わせていて 109px ずれた——足した発言の高さが数フレーム遅れて揃うため。
見ていた発言を目印に 30 フレーム合わせ続ける形に直した）。Fork は親の最後の 1 件＋自身の 14 件で 15 件。
入口の件数は「14 件のやり取り」（以前は親の分を含め 180 件超）。

E2E はこのコンテナからは流せない（global-setup が Incus に繋げない）。
ビルドの失敗（`next/font/google queries have exactly one entry`）は、置き場を空にして作り直したら消えた
——落ちては起こし直されたサービスが残した壊れたキャッシュだったと見ている（確かめてはいない）。
