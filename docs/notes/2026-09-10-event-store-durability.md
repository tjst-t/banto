# 2026-09-10 Event Store：追記ごとの fsync と、書きかけの行の切り詰め

`docs/tasks.json` の `event-store-durability`。アーキ仕様 §2.1 は前から
「fsync は追記ごと」「`\n` で終わらない最終レコードは切り詰めてから追記し、
切り詰めを記録する」と決めていたが、実装は `appendFile` 1行だった。

**放っておくと何が起きるか**：書きかけの行が1本残ると、次回以降の起動で
`JSON.parse` が毎回その行で失敗する。**host が二度と立ち上がらない**、という壊れ方。

## やったこと

- **起動時に切り詰める。** ファイルの最後が `\n` でなければ、後ろから 64KB ずつ
  遡って最後の `\n` を探し、そこまでに切り詰める（**ファイル全体は読まない**
  ——1GB のログでも起動を遅くしない）。1行も完結していなければ空にする
- **切り詰めたことを記録する。** `event_store.torn_line_truncated` を1件積む。
  中身は残さない（秘密が混ざりうる）——**落としたバイト数と、どこまで残ったか**だけ
- **追記ごとに fsync。** `append` は fsync が終わってから解決する
- **スナップショットも確定させる。** tmp に書く → fsync → rename → **ディレクトリを
  fsync**。rename 自体が確定していないと、crash 後に「空のスナップショットだけが残る」
  ことがある

## 却下した案：追記用の fd を持ち回す

最初はそう書いた（開きっぱなしの `FileHandle`）。やめた理由は2つ：

- Node が「GC で fd を閉じた」と警告を出し、**将来は例外になる**と明言している
  ——`close()` を誰がいつ呼ぶかという寿命の問題を、Event Store が抱えることになる
- **速くならない。** 実測（300回、200字のイベント）：

  | 形 | p50 | p95 |
  |---|---|---|
  | `appendFile`（fsync 無し・旧実装） | 0.090ms | 0.145ms |
  | open+write+fsync+close（採用） | 0.839ms | 1.021ms |
  | fd を持ち回す + fsync | 0.798ms | 0.963ms |

  **代金のほぼ全部が fsync**で、追記ごとの open/close は 0.06ms 程度。
  仕様の「p95 1ms 未満」に対して本実装は 1.02ms——同じ桁で、機械が違うぶんの差。
  この 0.06ms のために寿命の問題を抱えない。

## 測った結果

- 単体3件を追加：手で作った半端な行の切り詰め／1行も完結していないログ／
  **実際に SIGKILL された子プロセス**が残した半端な行からの回復
  （「書いている途中で落ちた」を机上で作らない——規則1）。
  いずれも、切り詰めの記録が1件残り、その後の `append` が正しい seq で続く
- 単体120件・E2E 27件・typecheck 通過
