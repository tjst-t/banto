### 1.4 PO が「認証の方針って結局どうなってる？」と聞いたときの経路

1. **`build_context(query_seed, budget)`** が呼ばれる。§8 のクエリ生成：直近発話「認証の方針」＋アクティブゴールなし＋ワーキングセット（この話題は今スレッド開始のため空に近い）＋実行文脈（`proj:banto`）。
2. **候補集合の前段**（§7）：`superseded_by != null` を除外、`tombstone: true` を除外。**A・B とも `superseded_by: null` かつ `tombstone: false` なので、両方とも候補に残る。** これは「未解決」の定義そのもの——deep sleep が確定判定に至らなかった以上、`supersede()` は一度も呼ばれておらず、版解決フィルタが引っかける旧版が存在しない。
3. **入場スコア**：両方とも見出しに「認証」を含みエンティティ一致。休眠トピック復帰の免除規則（§7）が働くかどうかに関わらず、両方が θ_admit=0.6 を素直に超えると考えられる。**両方がワーキングセットに入場する。**
4. **確信度算出**（§12）：入力は「出典の数と独立性」「出典間の一貫性」「経過時間」「origin」。**この4入力のいずれにも「他に競合する未解決エントリが存在する」という項目がない。** A・B はそれぞれ独立に、相手の存在を知らないまま確信度を計算される。
   - A：origin=user_explicit（高評価要因）だが単一出典（自分の発言のみ）、経過時間は約3年（時間減衰でマイナス）。§7 の休眠免除は**入場判定にのみ適用**され、§9 のレンダリングでは「未確認寄りの量子化を保つ」と明記されている（§7「休眠トピックの復帰」）。したがって A は PO 自身の明示決定であっても「おそらく」寄りに量子化されうる。
   - B：origin=agent_inferred（低評価要因）、出典2件だが独立性は実質薄い、経過時間は約1年3ヶ月（Aより新しいため時間減衰は相対的に軽い）。
   - 両者が同程度の「おそらく」判定になりうる——**PO の明示決定と、裏取り未完了の蒸留結果が、レンダリング上ほぼ同格に見える。**
5. **注入レンダリング**（§9）：A・B ともに要約解像度で本文に入る。「これは別のエントリと矛盾している」という構造的マーカーは**注入経路のどこにも存在しない**。矛盾の存在を知っているのは Steward Driver が保持する再検証キュー（§20.4）だけであり、`build_context()` の読み取り経路はこのキューを参照しない（`collision_candidates()` は書き込み時の点火・自己内省の点検に使われるのであって、通常の recall/build_context のパスには組み込まれていない）。
6. **番頭（LLM）の応答**：コンテキストに矛盾する2つの headline が並ぶ状態で、番頭が実際に何を答えるかは**LLM がその場でこの矛盾に気づくかどうかに依存する**。気づけば「2023年はKeycloak、2024年に(未確認の)SAML移行の報告があり、どちらが現行か確信が持てません」といった muted な回答になりうる。だが、それは構造的保証ではなく確率的な振る舞いであり、§0.5 原理2「安全性をLLMの判断力に依存させない」に反する経路である。**もしトークン予算の都合でBだけが残り、Aが末尾側で先に追い出された場合**（§6 動的末尾追い出し、§7 予算駆動の追い出し）、番頭は「SAML SSOに移行しました」と**確信を持って誤った**、あるいは少なくとも PO の生きた明示決定を無言で無視した回答を返しうる。これは §0.7 の2位（確信を持って誤る）・1位（訂正が消える）に直結するが、それを防ぐ専用のガードは見当たらない。

## 2. 動くこと

- **版解決フィルタ自体は健全**：既に確定的に supersede/tombstone されたエントリは正しく除外される（§7 ルール1-2）。汚染は「未解決」のケースに限られる。
- **origin優先の書き込み時強制**（§0.3.1-3、ADR-0010 §1.3）は機能する：`agent_inferred` の版が `user_explicit` を黙って上書きすることはできない。エントリAが理由なく消えることはない。
- **検出経路（経路A・経路B）自体は候補ペアを生成できる**：`fact_type` 一致を候補条件から外した改訂（§12）により、episode（B相当の新規記録）と既存 semantic（A）の突き合わせが空振りしない。「どちらとも言えない」「PO判断が必要」という区分自体は生成される——問題は生成後にある。
- **`worker_result` の失敗・成功が必ず返る契約**（§20.2）と `citations` 空振り検証（§0.3.1）により、Bの出典（職人報告）に外部由来の主張が紛れ込んでいれば、そこは機械的に弾かれる防御は機能する。
- **自己内省（§20.5-4）は2ホップ超の派生矛盾を実際に列挙する**：2026-07-26 の追加により、少なくとも「見つける」ことはできる。
- **通知トリガーのカテゴリ列挙自体は妥当**（§21）：訂正由来の判断要求・`state_fact` 再観測による supersede・機微情報・予算枯渇・外向き副作用の巻き戻し、という5カテゴリは筋が通っている。

## 4. 単調増加の判定

**増え続ける構造になっている。増加を止める規則が欠落している。**

流入（新規未解決の発生）と流出（解決・除去）を比較する。

- **流入**：(i) `origin: user_explicit` の episode が record される度に `collision_candidates()` が同期的に走り（§20.4 点火）、候補が出れば「訂正」として最優先キューへ積まれる——PO の発話は稀だが5年間累積すれば相応の件数になる。(ii) 深い睡眠バッチ内の新規対立候補（同時発生、§20.4 の点火入口2）。(iii) `state_fact` の再活性化。(iv) 2ホップ超の派生矛盾（§20.5-4）。事業・プロジェクト数が増えるほど流入は増える方向にしかならない。
- **流出**：唯一の明記された解消経路は、深い睡眠が「対立ペアを**確定**」させて敗者に `supersede()` を呼ぶケース（§12）と、PO が明示的に訂正・編集する（§25）ケースの2つのみ。**「確定できなかった」場合の第三の出口（強制決着・確信度の恒久的減衰による実質無害化・期限付きアーカイブ）が定義されていない。**
- **流出を細らせる副作用まである**：§20.6 の指数バックオフは、決着困難な対象ほど再チェック頻度を下げる。これは負荷対策としては合理的だが、**「決着できない項目はチェックされなくなり、チェックされないのでますます決着しない」という負のフィードバックを止める規則が無い。**
- **PO のキャパシティは有限で一定**（シナリオ前提「PO が処理しきれず放置された」）が、流入は運用規模とともに増加しうる。流入 ≥ 流出が続く限り、キューは queueing theory の意味で発散する。

したがって `unresolved_conflicts` は**定常状態に落ち着く保証がなく、設計上は単調増加しうる構造**である。欠落している規則は具体的に3つ：

1. **エスカレーション/強制決着規則**：N回連続で「どちらとも言えない」と判定された対立に対する、確信度の恒久的引き下げ・アーカイブ降格・PO への強制エスカレーションのいずれかを定める規則（§12・§20.4 のいずれにも無い）。
2. **`memory_signal`（`unresolved_conflicts`閾値超え）の発火後アクション**：定義されていない（§20.2）。少なくとも「トリアージバッチを起こす」「PO向けダイジェスト通知を1本にまとめる」等のアクションが必要。
3. **通知のボリューム制御**：レート制限・ダイジェスト化の規則が無い（§21）。これが無いと「PO が処理しきれない」という前提そのものが解消されず、流出側のもう一つの経路（PO の明示訂正）も細る。

## 5. 最小の修正案

1. **§12 の確信度算出に「対抗仮説の存在」を第5の入力として明記する。** `collision_candidates()` が現在も候補を返すエントリ（＝supersede されていない対立が存在する）については、確信度を上限キャップする（例：量子化を強制的に「未確認」段に固定する）規則を、実行層の式として追加する。散文の注意書きでは§20.8の教訓通り機能しない。
2. **§7 の版解決フィルタに第4の規則を足す**：`collision_candidates()` が現在有効な対立ペアを返すエントリ集合は、両方を通常のスコアリング候補に流す代わりに、**「未解決の対立あり」という明示メタ情報を付けて注入する**特殊経路を通す（例：`build_context()` が対立ペアを検出したら、通常の headline/summary の代わりに「A: …（PO明言・2023）／B: …（未確認・2024、要確認）」という対比形式でレンダリングする）。これにより LLM の気づきに依存せず構造的に矛盾を提示できる。
3. **`memory_signal` の発火アクションを §20.2 に明記する**：例えば「`unresolved_conflicts` が閾値を超えたら、Steward Driver は次の深い睡眠バッチに『長期未決着の矛盾に対する強制トリアージ』ジョブを追加し、結果を1本のダイジェスト通知にまとめる」。`model_migration` の書き方に揃える。
4. **エスカレーション規則を §20.4 の「消化」に追加する**：「同一の対立ペアが3回連続の深い睡眠で『どちらとも言えない』と判定された場合、確信度を機械的に最下段へ固定し、アーカイブ層へ降格し、PO への通知を1件（ダイジェスト）に集約する」といった、決定的に評価できる終了条件を置く。
5. **§21 に通知のボリューム制御を追加する**：同一カテゴリの通知が閾値件数/期間を超えたら個別通知を停止し、日次または週次の1本のダイジェストへ切り替える規則。
6. **`state_fact` の観測不能フォールバックが `supersede()` を呼ぶか否かを明記する**（§20.4）。呼ぶなら「観測不能な対象は事実上常に最新性で決着する」という設計選択を明示し、呼ばないなら上記4のエスカレーション規則の対象に含める。

---

## 6. 判定

**動かない** — 検出経路（経路A/B・点火）は機能するが、未解決の矛盾を認識した後の確信度反映・トリアージ・`memory_signal`の発火アクション・通知のボリューム制御・強制決着のいずれも定義されておらず、`unresolved_conflicts` は構造上単調増加し、PO の質問に対して番頭が矛盾する2つの生きたエントリを区別なく注入し確信を持って誤りうる状態を防ぐ機構が存在しない。
