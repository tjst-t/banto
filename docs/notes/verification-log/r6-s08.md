### 1.2 ターン1（固有名詞なし）：「あの調査どうなってたっけ」

**PO の実行文脈**：5ヶ月間触っていないため、`exec_context` は特定プロジェクトに紐づかない。`closure_ctx = "person"`（root）と仮定する（推測）。root は葉ではない（子閉包を持つ）。

#### Stage 0（§8.5.1）

`resolve_entities("あの調査どうなってたっけ")` を実行する。

- 「あの調査」は指示語＋一般名詞であり、`entity_index` の供給元（閉包レジストリの識別子・`subject[]` の値・`external_ref`・`content.headline` から抽出した固有名詞/識別子・エイリアス表）のどれとも一致しない。「調査」は英数字を含むトークンでも既知の識別子書式でもなく、レジストリ既知語との完全一致もしない（§8.5.1 の抽出規則）。
- **結果**：`closures=[]`, `subjects=[]`, `refs=[]`, `entries=[]`, `unresolved=["あの調査"]`。
- **`mentions = resolve_entities(raw_utterance)`** も同じ結果（機微ゲート §7-F5 の判定に使うが、本シナリオに機微記憶は無いので影響しない）。
- `closure_filter` は解決できなかったため実行文脈のまま＝ `person`（root）に留まる。

#### Stage 1（§8.5.2）とファンアウト（§8.5.4）

**横断ファンアウトの3条件（AND）を判定する**：

1. `closure_ctx`（= `person`）が葉でない → **真**
2. Stage 0 が特定の閉包を解決していない → **真**（`unresolved` が非空）
3. `session_origin == po_message` かつ `mode != brief` → **真**（PO との直接対話）

**3条件すべて成立 → 横断ファンアウトが発火する。** `proj:logi-switch` / `proj:web-app` / `dom:health` の3閉包それぞれから上位 `m=2`（既定）件が候補に入りうる状態になる。

各アームの挙動（推測込み。`query` には §8 の材料4種＝直近発話・ゴール・現在のワーキングセット・実行文脈が合成される。ワーキングセットはセッション開始時、直前のゴール状態＋高顕著性の記憶から種を作る＝§18。直前セッションは `dom:health` だったと仮定する＝推測）：

| アーム | 挙動 |
|---|---|
| **A1（FTS）** | クエリの内容語は実質「調査」のみ。**E1（"物流会社B切替**調査**"）にも E3（"競合**調査**"）にも同じ語でヒットしうる**。E1 はアーカイブ層のため既定では走査されないが、active 層のヒットが定員（`K_ws+K_hl`）に満たなければ§8.5.2 の二段照会条件(ii)が成立し archive も走査される——本シナリオでは「調査」がヒットする active 層のエントリが少ない（E3 のみと仮定）ため、**条件(ii)が成立し E1 も拾われると仮定する（推測）** |
| **A2（エンティティ）** | Stage 0 が何も解決していないため**検索する対象がない。ヒット0件。** |
| **A3（ベクトル近傍）** | 初期実装は embedding 無しで開始する、という ADR-0010 帰結節の既定に従い、**本シナリオでも未導入と仮定する（推測）**。したがってアーム自体が構成に存在しない |
| **A4（系譜近傍）** | ワーキングセットの1ホップ近傍＝直前セッション（`dom:health` と仮定）の隣接ノード。**E4 周辺のみヒットし、`proj:logi-switch` 側には届かない** |
| **A5（最近性・閉包別）** | `closure_filter` がファンアウトで3閉包に広がっているため、**各閉包内での最新順**が効く。`proj:logi-switch` 内での最新は E1（次点 E2）。`proj:web-app` は E3、`dom:health` は E4 |

**候補集合**：{E1, E2, E3, E4}（`arms_hit`: E1=[A1,A5], E2=[A5], E3=[A1,A5], E4=[A4,A5]）。

#### Stage 2（§8.5.3）

F1/F2（版解決・tombstone）：該当なし。V（可視性）：ファンアウトにより4件とも可視。F3（アーカイブ）：E1 にフラグが立つ（除外はしない）。F4（`subject[]`）：`mode=context` のため不適用。F5（`sensitive`）：4件とも `sensitive:false` のため不適用。**4件とも Stage 3 へ進む。**

#### Stage 3（§8.5.5）：融合・免除・`s_admit`

**免除規則（§7「休眠トピックの復帰」・§8.5.5）は `arms_hit` に `"A2"` が含まれるエントリにのみ適用される。** 本ターンでは A2 が0件のため、**E1 にも E2 にも免除は適用されない。** 文脈一致度・目標関連性・確信度の経過時間ペナルティは、すべて素点のまま計算される。

`s_admit = w1·rel_norm + w2·文脈一致 + w3·確信度 + w4·顕著性` を、重み `w1=0.4, w2=0.2, w3=0.2, w4=0.2`（**推測**。合計1.0）で計算する。RRF 定数 `c=60`（本文既定）。`rel_norm` は候補集合内で正規化するため、本来は各アームのランクから計算するが、ここでは最終値を直接示す（**推測**、ランク計算の詳細を §1.4 に別掲）。

| エントリ | rel_norm | 文脈一致 | 確信度 | 顕著性 | `s_admit` | 判定 |
|---|---|---|---|---|---|---|
| **E1**（アーカイブ・logi-switch） | 0.55 | 0.10（免除なし） | 0.30（経過時間ペナルティ適用） | 0.40 | **0.38** | `θ_floor(0.35) ≤ 0.38 < θ_ws(0.6)` → **見出し帯** |
| **E2**（logi-switch の決定） | 0.45 | 0.10 | 0.25（免除なし） | 0.50 | **0.35** | ちょうど `θ_floor` 境界 → **見出し帯（ぎりぎり）** |
| **E3**（web-app・直近） | 0.60 | 0.50 | 0.80（新しい・ペナルティなし） | 0.50 | **0.60** | `θ_ws(0.6)` にちょうど到達 → **滞在枠** |
| **E4**（health・直近） | 0.65 | 0.50 | 0.85 | 0.30 | **0.59** | `θ_ws` 未達 → **見出し帯** |

（`θ_ws=0.6`、`θ_floor=0.35`：いずれも**推測**。`θ_ws` のみ本文の既定値と一致。`K_ws`・`K_hl` は十分大きく、この4件は全て定員内に収まると仮定する）

#### Stage 4（§8.5.5）：入場の二段判定と多様性クォータ — **未定義に突き当たる**

**「定員内の順序」は 1.ピン留め 2.保護枠 3.多様性クォータ（横断モードのときだけ、子孫閉包ごとに1件） 4. `s_admit` 降順 の順で滞在枠を埋めると定める。** 本ターンは横断ファンアウトが発火しているため3が適用対象になる——`proj:logi-switch` / `proj:web-app` / `dom:health` それぞれに1枠を**先取り**する規定である。

**ここで本文に書かれていない分岐が生じる**：多様性クォータで先取りされる1枠が、**`θ_ws` の絶対下限を免除して確保されるのか、免除せず単に「その閉包の中で最高スコアの候補が rank 上位に来る」ことだけを保証するのか**が書かれていない（§7 は「絶対下限だけでは入場は決まらない。定員と併用する」と述べるが、これは通常の `s_admit` 降順の話であり、多様性クォータという第三の経路が `θ_ws` とどう関係するかには触れていない）。

- **読みA（クォータが `θ_ws` を免除する）**：`proj:logi-switch` の最高スコア E1（0.38）が**滞在枠に1件確保される**。ただし E1 は archive フラグを持つため、§9 により**滞在枠に入っても見出し解像度でレンダリングされる**（後述）。
- **読みB（クォータは rank だけを保証し `θ_ws` は免除しない）**：E1（0.38）は `θ_ws` 未達のため滞在枠に入れない。`proj:logi-switch` はどの読みでも滞在枠に**代表を送れない**。

**本シナリオでは判定できない。** どちらの読みを採るかで、次の聞き返し判定（§1.3）の結果が変わる。

#### 1.3 聞き返し（`clarify`）の判定 — **条件が判定できない**

条件は「`unresolved[]` が空でなく、かつ滞在枠に入ったエントリの `context.scope` が2つ以上の兄弟閉包にまたがるとき」。

- `unresolved[]` は非空（"あの調査"）→ 第1条件は**満たす**。
- 第2条件は Stage 4 の分岐に依存する。
  - **読みA**（クォータが `θ_ws` を免除）：滞在枠 = {E1(logi-switch), E3(web-app)}。**2閉包にまたがる → `clarify` が発火する。**
  - **読みB**（免除しない）：滞在枠 = {E3(web-app)} のみ。**1閉包しかない → `clarify` は発火しない。**

**判定：条件が判定できない（未定義に依存）。** 発火する場合、候補は「最終更新の新しい順に最大5件」（§23-6）。E1〜E4 を作成日時降順で並べると **E4(07-25) > E3(07-20) > E2(02-25) > E1(02-20)** となり、5件の枠に全て収まるため見かけ上は logi-switch も候補リストに載る。しかし**候補の生成元がどの集合か（滞在枠のみか、`ranked[]` 全体か）が §8.5.5 にも §23-6 にも書かれていない**——読みBのように logi-switch が滞在枠に一切残らない場合、候補リストの元が「滞在枠のみ」なら E1/E2 はそもそも候補に上らない。この点も**未定義**。

#### 1.4 `clarify` が発火しない場合にターン1で実際に起きること — 本シナリオの核心

読みBの下では `clarify` は発火しない。この場合、番頭は `ranked[]`（滞在枠={E3}、見出し帯={E1,E2,E4}）を受け取り、自分の判断で応答を組み立てる。

**滞在枠に入っているのは E3（"競合調査：機能ギャップ大"）ただ1件であり、`s_admit` 上は全候補中トップ（0.60）である。** クエリの内容語「調査」は E3 のヘッドラインにも含まれる。§23 のプロトコル層は「対象を特定できないときは候補を提示して聞き返す」と定めるが、**この規律は `retrieve()` の `clarify` フィールドに支えられていない限り散文の指示に過ぎない**（§20.0 が自ら警告する失敗形式そのもの）。`clarify` が null で返ってきた場合、番頭が自発的に「特定できていない」と判断する保証はどこにも実行層に無い。

**結果として起きうるのは、「あの調査」を E3（直近の競合調査）だと取り違え、確信を持ってそちらについて答えてしまうことである。** これは §0.7 の失敗順位で**2位「確信を持って誤ったことを述べる」**に該当し、4位（見逃し。PO が言い直せば回復する）よりも重い失敗である。本来 PO が聞きたかった `proj:logi-switch` の調査は、見出し帯に E1・E2 として存在してはいるが（滞在枠に入らなかっただけで検索不能ではない＝§7-F3 の意図どおり)、**番頭が別の話題に確信を持って回答してしまえば、見出し帯の存在は使われないまま終わる。**

読みA（クォータが `θ_ws` を免除）の場合は `clarify` が発火し、E1〜E4 が候補として提示される可能性があるが、それも**未定義の解釈に依存した偶然の救済**であり、設計として保証されたものではない。

### 1.2 ターン2（固有名詞あり）：「ああ、物流会社Bの調査ね」

#### Stage 0（§8.5.1）

`resolve_entities("ああ、物流会社Bの調査ね")` を実行する。「物流会社B」は `subject[]`（E1・E2 双方が `party:LogiCorpB` を含む）およびヘッドライン抽出語（E1 の "物流会社B切替調査"）と一致するため、**解決に成功する**。

- `closures = ["proj:logi-switch"]`
- `subjects = ["party:LogiCorpB"]`
- `unresolved = []`

`closure_filter` は「解決された閉包＋その祖先」＝ `{proj:logi-switch, person}` に**絞られる**（§8.5.1）。

#### 横断ファンアウトの再判定（§8.5.4）

## 3. 動くこと

- **固有名詞が与えられた瞬間の復帰経路は仕様どおり機能する**（ターン2）。`resolve_entities()` → A2 ヒット → §7/§8.5.5 免除規則 → `s_admit` が `θ_ws` を超える、という連鎖は §7・§8.5.1・§8.5.5 の記述と矛盾なく追跡できた。
- **アーカイブのレンダリング上限（§9 F3）は tier 判定と独立に効く。** E1 が `s_admit` 上は滞在枠相当でも、見出し解像度に強制的に落ちる。免除規則（入場判定用）とレンダリング規則（表示用）が別レイヤーで独立に機能しているという §7 末尾の設計意図（「入場させる目的と、古いかもしれないと気づかせる目的を両立させる」）は、この2件の分離によって実際に成立している。
- **閉包解決の成功が横断ファンアウトを自動的に止める。** ターン1で発火していたファンアウトが、ターン2で閉包が特定された瞬間に条件2の不成立によって止まる。これにより無関係な `proj:web-app`／`dom:health` がターン2の候補から構造的に排除される——ターン1の「取り違えリスク」がターン2では原理的に発生しない。
- **`clarify` の第1条件（`unresolved[]` 非空）は確定的に判定できる。** ターン2でこれが偽になることにより、`clarify` 不発火は未定義に依存せず断言できる。
- **二段照会の条件(i)（A2完全一致は常にアーカイブを走査する）はターン2で確実に成立し、アーカイブ層に落ちていた E1 を実際に候補へ引き上げる。** §7-F3 の「アーカイブ＝検索不能ではない」という設計意図は、この一点に限れば正しく機能している。

## 4. 破綻・穴

### 穴1：ターン1で「確信を持って誤る」リスクが放置される（最重要）

- **(a) いつ起きるか**：ターン1、Stage 3〜4（`s_admit` 計算後、`clarify` が発火しない読みBの経路）。
- **(b) 何が起きるか**：内容語「調査」がクエリと E3（直近・別プロジェクトの"競合調査"）の両方にヒットし、E3 だけが唯一 `θ_ws` を単独で超える。番頭が `clarify` に頼らずそのまま応答を組み立てた場合、「あの調査」を E3 だと取り違え、確信を持って別の話題に答えてしまいうる。これは §0.7 の**2位**（確信を持って誤る）に該当し、4位（見逃し。言い直せば回復可能）より重い失敗である。仕様が「一般名詞のトピックには救済が効かない。見出し帯で受ける」（§7）と自認する範囲を超え、**見出し帯で受けた記憶が実際に使われる保証がない**ことまでは書かれていない。
- **(c) 節番号**：§0.7（失敗順位）／§7「休眠トピックの復帰」末尾／§8.5.2（A1）／§8.5.5（`s_admit`・`clarify`）／§23 プロトコル層6項。
- **(d) Substrate か Policy/Loop か**：**Policy**（`s_admit` の算出式・アーム構成・`clarify` の発火条件の設計問題）。Substrate 変更は不要。

### 穴2：多様性クォータと `θ_ws` 絶対下限の関係が未定義

- **(a)** ターン1、Stage 4「定員内の順序」の3（多様性クォータ）適用時。
- **(b)** 横断ファンアウトで得た子孫閉包ごとの1枠が、`θ_ws` の絶対下限を免除して確保されるのか、免除せず単に rank 上の優先権だけを与えるのかが本文に書かれていない。この一点だけで、ターン1の `clarify` 発火可否（穴3）と、そもそも `proj:logi-switch` の記憶が滞在枠に一切現れるか（穴1の深刻度）が変わる。
- **(c)** §8.5.5「定員内の順序」（多様性クォータの行）／§7「絶対下限だけでは入場は決まらない。定員と併用する」。
- **(d)** **Policy**。

### 穴3：`clarify` の候補生成元と並び順が、救済対象を構造的に不利にする

- **(a)** `clarify` が発火する場合（穴2の読みA）に、候補リストを作る段階。
- **(b)** §23-6 は候補を「最終更新の新しい順に最大5件」と定める。これは §7・§13 が繰り返し警告してきた「休眠トピックは新しさで測ると必ず負ける」という同じバイアスを、**救済策であるはずの `clarify` の候補選定自体に持ち込んでいる**。本シナリオでは5件の枠に収まったため実害が出なかったが、候補数が5件を超える運用規模（数千〜数万エントリ）では、直近の無関係な活動が5枠を埋め、8ヶ月前の調査は候補にすら現れない可能性が高い。加えて、候補の生成元が「滞在枠のみ」か「`ranked[]` 全体」かが書かれていない（本文にも §23-6 にも無い）。
- **(c)** §8.5.5 末尾（`clarify` の発火）／§23-6。
- **(d)** **Policy**。

### 穴4：§23-6「聞き返す」規律が `clarify` フィールドに構造的に支えられていない

- **(a)** ターン1、`clarify` が null で返ってきた場合（穴2の読みB）。
- **(b)** §23 は「対象を特定できないときは候補を提示して聞き返す」とプロトコル層（システムプロンプト）に書く。しかし §20.0 は「散文で書いた規律はすべて素通りした」ことを自ら10シナリオ検証で確認し、実行層・式・シグネチャに落ちたものだけが機能すると総括している。`retrieve()` の `clarify` フィールドが null であれば、番頭が自発的に「特定できていない」と判断して聞き返す保証は実行層のどこにも無い——**§20.0 自身が警告した失敗形式が、その§20.0 と同じ文書の §23 で再現している**。
- **(c)** §23 プロトコル層6項／§20.0。
- **(d)** **Policy**（プロンプト層の規律が実行層の裏付けを欠く）。

### 穴5：アーカイブ降格の閾値が未定義であるため、シナリオの前提そのものが検証不能

- **(a)** シナリオ構築時点（§0）。
- **(b)** 「5ヶ月不活性」で E1・E2 がアーカイブ層に落ちているかどうかは、§14 の「strength 十分小＋期間経過」という記述だけでは決まらない。本検証では E1=アーカイブ済み・E2=未降格という**推測**を置いたが、逆の仮定（両方アーカイブ済み、あるいは両方未降格）を置いても仕様上は反証できない。これは付録 A.1-4「全パラメータの具体値」が未決であることの直接の帰結であり、**「休眠と再開」という本シナリオの核心的な問いが、閾値未定のままでは机上検証の対象になりきらない**ことを意味する。
- **(c)** §14／§13／付録 A.1-4。
- **(d)** **Policy**（パラメータ未決）。

## 5. 最小の修正案

1. **穴1・穴4 への対処**：`clarify` の第2条件に「または、`unresolved[]` が非空 **かつ** 滞在枠1位の候補の `arms_hit` に `A2` が含まれない（＝強いエンティティ一致に基づかない）」を OR で追加する。これにより、内容語だけで単独トップに立った候補（本シナリオの E3）に対して無条件に確信させず、聞き返しを強制できる。§23-6 の散文規律を実行層の条件に落とし込む最小の変更。

## 6. 判定

**ターン1（固有名詞なし）は「あの調査」を安定して特定できない。** `resolve_entities()` は明確に空振りし（発火するが解決しない）、横断ファンアウトと A5（閉包別最近性）により `proj:logi-switch` の記憶は候補集合には入るものの、免除規則（§7・§8.5.5）が A2 ヒットを前提とするため一切効かず、`s_admit` は絶対下限付近に沈む。ここで聞き返し（`clarify`）が発火するかどうかは、多様性クォータと `θ_ws` の関係という**本文未定義の一点**に依存し、**判定できない**。未定義を最も不利な側（クォータが `θ_ws` を免除しない）に倒して読むと、`clarify` は発火せず、番頭は直近・無関係な別プロジェクトの「調査」を唯一の滞在枠候補として確信を持って答えてしまうリスクが構造的に残る——これは仕様が最も重く位置づける失敗（§0.7 の2位）であり、4位の「見逃し」で済むはずの発話が2位に格上げされて着地しうる。

**ターン2（固有名詞あり）は仕様どおりに機能する。** `resolve_entities()` が閉包を解決し、横断ファンアウトが自動的に止まり、A2 ヒットが §7 の免除規則を起動し、休眠していた決定（E2）は要約解像度で滞在枠に入る。アーカイブ層の生ログ（E1）は入場条件を満たしても §9 のレンダリング上限（見出しのみ）に正しく抑えられる。この経路に関しては、10シナリオ検証（ADR-0010 §6-S8）が「解決済み」とした主張は本シナリオでも再現し、支持される。

**総括**：本設計は「固有名詞さえ出れば直る」設計であり、それ自体は §7・§8.5.1 の意図どおりに機能する。しかし**その前段（固有名詞が出るまでの1ターン目）の挙動は、本文が「見出し帯で受ける」とだけ述べて済ませており、実際には見出し帯止まりで無害に終わるのか、それとも別の候補への確信的な誤答に転ぶのかを、§8.5.5 の未定義箇所（多様性クォータと絶対下限の関係）が決めてしまっている。** これは「動かない」ではなく「条件が判定できない」がもっとも正確な判定であり、その未定義自体が本設計にとって §0.7 の2位に直結する実害を持ちうる、という点を穴1〜4として記録する。
