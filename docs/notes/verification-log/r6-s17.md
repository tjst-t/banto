# R6 / S17【新軸】：記憶ストアの障害・索引喪失・復旧・マイグレーション

**対象**: `docs/spec/memory.md`（版4.0、2026-07-26）／[ADR-0010](../../adr/adr-0010-memory-substrate-schema.md)（Substrate 正典）
**検証者**: サブエージェント（敵対的シミュレーション）
**規律**: 好意的に解釈しない。実行できない箇所は「実行できない」と書く。書いていないことを補って正当化しない。節番号を必ず添える。推測は「推測」と明示する。「新しい軸なので未定義が多いのは当然」と割り引かない。

> **前提の確認**：この軸（記憶ストアの障害・復旧・マイグレーション）は §20.8 末尾が自ら「シナリオが最初から見ていない領域」の例として名指ししている（"記憶ストアの障害と復旧" は10シナリオのどれも扱っていない）。したがって本ラウンドで見つかる未定義は「検証漏れ」ではなく「一度も検証されたことがない領域の一次検証」である。

## 1. シミュレーション本体

### 1.1 (1) 部分障害

深い睡眠バッチ（§18）が `propose()` → 蒸留 → `supersede()`/新規 semantic 確定を行っている最中にプロセスが落ちる。**エントリ本体（ストアの行）は書けたが、索引側（A1 の直近3日分、`entity_index` の一部）が失われた。**

これは §0.3.0 **I8**「索引を同一トランザクションで更新する（対象は A1・A2・A4・A5 と `entity_index`）」への違反そのものである。I8 の文言どおりに実装されていれば、エントリ本体の書き込みと索引更新は不可分（同一トランザクション）であり、「本体は生きているが索引だけ消える」状態は原理的に起きないはずである。**起きたという時点で、I8 が要求する原子性を実際に担保する機構（単一ストア内のACIDトランザクションか、複数ストアにまたがる場合の分散コミットか）がどこにも規定されていない**ことが露呈する。A1（全文索引）は「転置索引。BM25相当」（§8.5.2）と書かれるのみで、エントリ本体と同じ物理ストアに同居する保証はない。§16 が比較対象に挙げる Hermes Agent は「FTS5」という具体的技術を明記するが、Quirefold 自身の索引の物理配置（同一DBか別ミドルウェアか）は本文に記述がない。**したがって「同一トランザクションで更新する」は規範（あるべき姿）として書かれているだけで、クラッシュ耐性のある実装保証は未定義**——I8 自体は規定があるが、それを成立させる実装機構が欠落している。

- **A1（全文）**：索引が失われているため候補を返さない。
- **A2（エンティティ）**：仮に索引が生きていたとしても、そもそも「認証」は一般名詞であり `entity_index` の抽出規則（§8.5.1「英数字を含むトークン、既知の識別子書式、レジストリ既知語との完全一致」）に当てはまらない。§7「休眠トピックの復帰」自身が「一般名詞のトピックには救済が効かない（『認証』にはエンティティ一致が無い。R4／S13）」と明記しており、**このエントリは索引が無傷でも A2 では拾えない**。
- **A4（系譜近傍）**：現在のワーキングセットに `derived_from` で1ホップ以内の記憶が滞在していなければヒットしない。翌朝の新しいセッションであれば通常ワーキングセットは空に近く、期待できない。
- **A5（最近性、閉包別）**：`created_at` 順は索引が失われていないため機能しうる。`proj:banto` が活発な閉包であれば、3日前のエントリは `k_arm` 件の中に残っているとは限らない（`k_arm` の値は §A.1 の未確定パラメータ）。**ここだけが唯一の生存経路であり、しかも運任せである。**

**s_admit の試算（(2) の指示どおり4項に分けて数値化。tier 判定まで行う。パラメータは全て推測と明記）**

推測する重み：`w1=0.4, w2=0.2, w3=0.2, w4=0.2`（合計1、根拠なし、純粋な仮置き）。RRF 定数 `c=60`（§8.5.5 に明記された既定値、これは推測ではない）。`θ_ws=0.6`（§7 に明記、推測ではない）。`θ_floor=0.35`（未確定パラメータにつき推測）。

*ケースα：A5 だけが拾った場合*（現実的な最悪未満のケース）

- A5 での順位を rank=4 と仮定（推測）。他アームは0件。
  `rrf(e) = 1/(60+4) = 0.015625`
- 比較用に、索引が健全なら A1 rank=1・A2 rank=2 で拾えていたはずの同エントリの rrf を仮に計算すると
  `rrf_intact = 1/61 + 1/62 ≈ 0.0164 + 0.0161 = 0.0325`
- 候補集合内の最大 rrf（強くヒットする別エントリを想定）を `max_rrf = 0.049`（推測）とすると
  - 索引喪失時：`rel_norm(e) = 0.015625 / 0.049 ≈ 0.319`
  - 索引健全時：`rel_norm(e) = 0.0325 / 0.049 ≈ 0.663`
- 文脈一致度：現在の実行文脈が `proj:banto` 自身 → `0.9`（推測）
- 確信度：出典2件・単一セッション由来（独立性弱、§4）・経過時間ペナルティなし（直近）→ `0.75`（推測）
- 顕著性：格納値 `salience=0.62` をそのまま使用（推測。§11 のゴール関連性補正は未定義のため適用しない）

```
索引喪失時： s_admit = 0.4×0.319 + 0.2×0.9 + 0.2×0.75 + 0.2×0.62
           = 0.1276 + 0.18 + 0.15 + 0.124
           = 0.582   → θ_ws(0.6) 未満。θ_floor(0.35) は超過。
           → tier = headline（見出し帯のみ。要約は出ない）

索引健全時： s_admit = 0.4×0.663 + 0.2×0.9 + 0.2×0.75 + 0.2×0.62
           = 0.2652 + 0.18 + 0.15 + 0.124
           = 0.719   → θ_ws(0.6) を明確に超過。
           → tier = resident（要約が滞在枠に入る）
```

**索引喪失は tier を resident（要約つき）から headline（見出しのみ、〜10トークン）へ落とす**、というのがケースαの結論。番頭は「そういう記憶が存在する」ことだけ知り、明示展開すれば追い付ける——ただし PO の質問に対してその場で答えを組み立てる文脈では、見出し帯止まりの記憶を能動的に展開する判断が要る（それ自体は §9 の設計どおり機能している）。

*ケースβ：A5 でも拾えなかった場合*（`proj:banto` が活発で、3日前のエントリが `k_arm` 圏外に押し出された）

- 全アーム0件 → `rrf(e)=0` → `ranked[]` に一切現れない → `s_admit` は計算されず、tier は「落選」ですらなく **候補にすら入らない**。番頭にとってこのエントリは「存在しない」のと区別がつかない。

**「記憶が無い」と「索引に無い」の区別可否**：§0.3.0 I8 の帰結欄自身が「見逃しが『記憶していない』と区別できなくなる（§16の見逃し率が測れない）」と明記しており、**設計者自身がこの区別が失われることを認めている**。しかし `retrieve()` の戻り値（`ranked[]` / `clarify` / `trace`）のどこにも「索引の健全性が疑わしい」旨のフラグは無い（§8.5.0 のシグネチャに存在しない）。したがって**番頭は区別できない**。番頭が答える内容は、ケースαなら「見出し帯にある記憶を見つけて展開する」（正しく答えられる可能性が残る）、ケースβなら「そのような決定は記憶にない」と断定するか、「わからない」と保留するかのどちらかになるが、**どちらを選ぶべきかを導く規定がない**（§0.7・§9 いずれにも「索引欠落の疑いがあるときは断定を避ける」という規則は無い）。§17 の `uncertainty` は確信度平均・矛盾検出頻度からしか計算されず、索引の健全性を入力に取らない。

### 1.3 (3) 検知

いつ・どう・誰が気づくか。

- **§20.2 の起床源6種**（`po_message` / `subsystem_kick` / `worker_result` / `memory_signal` / `timer` / `model_migration`）のいずれにも「ストレージ・索引のインフラ障害」に対応するものが無い。`memory_signal` は `context_pressure` / `unresolved_conflicts` の閾値超えのみを対象とし（§0.3 のシグナル一覧に索引健全性は含まれない）、索引欠落はこの経路でも拾えない。
- 唯一の検知経路は **§20.5 の点検7「索引と本体の乖離（本体件数 vs 索引件数、未索引エントリ、A3 の遅延分、`entity_index` の解決不能率）」**であり、**深い睡眠のバッチの中でのみ**走る。
- 深い睡眠は「低頻度（日次／週次、単一writer）」（§18）としか書かれておらず、**具体的な周期は §A.1「全パラメータの具体値」の未解決事項に含まれ確定していない**。
- さらに重大な点：**点検7自体が、クラッシュを起こしたその深い睡眠バッチの一部として実行される想定になっている**（§20.5 の点検リストは「深い睡眠のバッチに、決定的な点検リストを持たせる」と書かれ、バッチ内の1ステップである）。プロセスがクラッシュして中断した回のバッチでは、点検7を含む後続ステップも実行されなかった可能性が高い。**したがって検知は「クラッシュを起こした当日」ではなく、少なくとも次回の深い睡眠まで持ち越される。**
- 点検7が乖離を検出しても、通知は「閾値超えでダイジェスト」（§20.5 の表・§21 の通知表）であり、**閾値の値もダイジェストの配信周期も未確定**（§A.1 参照）。

**検知までの時間**：最短でも「次回の深い睡眠1回分」（日次なら約24時間、週次なら約7日、この選択自体が未確定）。加えてダイジェストの閾値・周期が未定のため、**上限は事実上無制限になりうる**。§0.7 の1〜2位級の実害（PO の意思決定情報が見えなくなる）に対して、検知の優先度は §20.5 の表で「低」、通知も「閾値超えでダイジェスト」——**実害の重大度と検知経路の優先度が釣り合っていない**。

### 1.4 (4) 復旧

再索引が20万件規模でどう走るか。

§8.5.6「再構築は深い睡眠の窓に収まる分割単位で漸進的に行う。全件を一晩で処理する前提を置かない」——**これは「収まらないことがある」ことを設計側が自認する記述**である。分割の単位（チャンクサイズ、優先順位づけ＝どの閉包・エントリから先に処理するか、1回の深い睡眠でどこまで進めるかのアルゴリズム）を**誰が決めるかは書かれていない**。§20.3 の「再索引」行も「窓に収まる分割単位で実行する」と同じ言い回しを繰り返すのみで、実行主体（Steward Driver がどう分割を決定するアルゴリズムを持つのか）は未定義。

**20万件の所要時間試算**（§20.8 の R3 検証が残した実測値を利用。以下は既存の見積りの外挿であり、それ自体を含め「推測」）：

> §20.8「R3」に既存の試算がある：**5万件で約7時間、100万件で約6日（144時間）**。

この2点から実効スループットを逆算すると、5万件/7時間 ≈ 7,143件/時、100万件/144時間 ≈ 6,944件/時と、**ほぼ線形**（§15 の削減策は定数倍改善であって線形スケーリングを変えない、という記述と整合する）。この線形近似を20万件に外挿すると：

```
20万件 ÷ 約7,000件/時 ≈ 28.6時間 ≈ 1.2日
```

深い睡眠の1回の窓の長さ自体は本文に明記が無いため、**仮に1晩＝6〜8時間と推測**すると、28.6時間の処理には**最低でも4〜5夜分の窓が連続で必要**になる。深い睡眠は単一writer（§19）であり、複数の分割ジョブを並行して走らせることはできない（§8.5.6 も「分割単位で漸進的に」＝逐次処理を前提とする）。**したがって20万件の再索引は単一夜の窓には収まらない。試算上は数日にまたがる。**

なお上記の R3 の数値は「深い睡眠の全件処理（蒸留バッチ）」の所要時間であり、A1/A2/entity_index の再構築や A3 の埋め込み生成とはコスト構造が異なる可能性がある（LLM 判定を伴う蒸留と、機械的な転置索引再構築や外部埋め込みAPI呼び出しでは単位コストが違う）。**この差分を補正する係数は仕様のどこにも無く、上記試算は「同種の処理として近似できる」という追加の仮定に依存する（明記して推測とする）。**

**再索引中に PO が話しかけたら何が起きるか**：`po_message` の優先度は「最高」（§20.3）であり、応答はプリエンプト可能（§21「応答とタスク実行の分離」）。したがって PO のセッションは即座に処理され、再索引ジョブ（優先度=低）はバックグラウンドで継続する。**問題はその瞬間の `retrieve()` が何を見るかである。** §19「並行セッション」は意味記憶の並行性を「要調整（§3の版管理で検出可能な矛盾に還元）」、読み取りを「スナップショット隔離」と定めるが、これは**エントリ本体の書き込み競合**についての規定であり、**索引の再構築中の読み取り一貫性**については §19 のどの行にも対応がない（並行性の表に「索引」という行自体が存在しない）。再索引がクロージャ単位・アーム単位で漸進的に進む以上、ある瞬間には「一部のクロージャ・一部のアームは再構築済み、残りは未処理」という混在状態が必ず生じるが、この混在状態下で RRF 融合がどう振る舞うべきかの規定は無い。**未定義。**

- 候補集合内の最大 rrf を、別の強くヒットするエントリ（A1・A2 双方で上位）から `max_rrf = 0.05`（推測）とする。
  `rel_norm(②) = 0.03154 / 0.05 = 0.631`
  `rel_norm(③) = 0.01515 / 0.05 = 0.303`
- 文脈一致度（両者とも `repo:banto/payments` が実行文脈）：`1.0`（推測、同一）
- 確信度（両者とも単一由来・経過時間同程度）：`0.5`（推測、同一）
- 顕著性（格納値をそのまま使用）：`0.5`（推測、同一）

```
② s_admit = 0.4×0.631 + 0.2×1.0 + 0.2×0.5 + 0.2×0.5
          = 0.2524 + 0.2 + 0.1 + 0.1 = 0.6524   → θ_ws(0.6) 超過 → tier = resident

③ s_admit = 0.4×0.303 + 0.2×1.0 + 0.2×0.5 + 0.2×0.5
          = 0.1212 + 0.2 + 0.1 + 0.1 = 0.5212   → θ_ws(0.6) 未満、θ_floor(0.35) 超過 → tier = headline
```

**内容的にほぼ同義な2件が、A3 への埋め込み処理の進捗タイミングだけで tier が resident（要約つき）と headline（見出しのみ）に分かれる。** これは「一部のエントリだけが A3 索引に載っている状態」が RRF 融合そのものを破壊するわけではない（§8.5.5 の主張どおり、アームが欠けても `rel_norm` は同じ形で算出され続ける＝**壊れない**）が、**移行期間中は A3 未処理のエントリが構造的に不利になる**ことを数値で確認できる。これは §8.5.6 が定める「A3 導入の見直し契機」（見逃し率・再現率の閾値）とは別問題であり、**移行の"最中"に生じる一時的な不公平を補償する仕組みは仕様のどこにも無い**（§12「コールドスタート時の過剰な重み」は初期状態の話であり、移行期の不均一とは別の論点として扱われている）。

### 1.6 (6) より重い障害：本体の部分喪失とバックアップ復元

エントリ本体そのものが一部失われ、より古いバックアップから復元した結果、**2種類の宙ぶらり参照**が生じる。

**具体エントリ④（`derived_from` が存在しないIDを指す）**

```

kind          : semantic
fact_type     : preference_decision
content       : { headline: "障害復旧は自動フェイルオーバーを許可する",
                   summary: "…", full: "…" }

                                                    バックアップのスナップショット時点には存在しないため復元されず、
                                                    このIDはストア内のどこにも存在しない

```

**この寸断を誰が検出するか**を §4「宙ぶらりんノードの防止」と §20.5 の点検表・§20.4 の積む条件表で追う。

- §4：「統合・削除処理は、出典リンクが切れた意味記憶を生まないよう連動させる。出典が全て消えた事実は確信度を下げるか再検証フラグを立てる。」——これは**自システムの統合・削除処理が能動的に出典を消すケース**を前提にした規定であり、**バックアップ復元という外部イベントによって事後的に宙ぶらりが生じるケース**は範囲外。
- ADR-0010 §4：「出典の最新版が supersede された／tombstone されたエントリを再検証キューへ積む規則が要る」——これも `supersede()`/`tombstone()` という**システム内の版イベント**を起点にした規則であり、「そもそも参照先IDがストアに存在しない」（削除されたのでなく、復元されなかった）ケースは対象外。
- §20.4「積む条件」表の5条件（supersede された／tombstone された／`user_explicit` の訂正／`external_ref` 解決失敗／`state_fact` 未更新＋再活性化）の**どれにも該当しない**——`derived_from` が指す先が存在しないことを直接検出する条件が無い。
- §20.5 の点検表8項目のうち、参照の生存確認を行うのは**点検3「`external_ref` の参照先の生存」だけ**であり、これは `external_ref`（ストア外）を対象とし `derived_from`（ストア内）は対象外。**`derived_from` の参照整合性をチェックする点検項目は存在しない。**

**結論：誰も検出しない。仕様上、このエントリの `derived_from` は永久に壊れたままになりうる。** これは「未定義」ではなく「検出経路が構造的に存在しない」という、より強い意味での穴である。

**具体エントリ④'（`superseded_by` が存在しないIDを指す＝より深刻）**

同じ障害はもう一箇所で異なる形で牙をむく。PO が過去に一度訂正した意思決定が、復元によって**訂正前の状態に巻き戻る**可能性である。

```
               headline: "デプロイはCI基準を満たせば自動承認に変更"、
               derived_from: [旧版ID, 訂正発話のepisode ID]
```

**§8.5.3 Stage 2 の F1「`superseded_by != null` のエントリは候補から除外し、常に最新版に解決する」を、`superseded_by` が指す先が存在しないときにどう実行するかが書かれていない。** 挙動として論理的にありうるのは次の3通りだが、仕様はどれを取るか指定していない。

1. 解決に失敗したら旧版自体も候補から除外する（＝この決定についての記憶が完全に消える。§0.7 の4位）
2. 解決に失敗したら旧版を「最新版扱い」にフォールバックする（＝**PO が明示的に訂正した内容が消え、訂正前の古い方針が「現在の方針」として復活する**。§0.7 の**1位**そのもの、しかも `origin: agent_inferred` の版が `user_explicit` の訂正を実質的に上書きする形になり、ADR-0010 §1.3 の origin 優先強制は「新版を作る場面」でのみ効き、この「新版が消えて旧版が residual に残る」場面には**適用対象外**）
3. 例外として拒否・failed にする（I6 の精神に近いが、I6 は書き込み経路の検証であり、読み取り時の版解決失敗を failed にするとは書かれていない）

**規律「好意的に解釈しない」に従い、2番目（訂正前の古い方針が黙って復活する）が起こらないという保証は仕様のどこにも書かれていない。** かつ、上記の④と同じ理由で、この破損自体を検出する経路も存在しない（`superseded_by` の参照整合性も §20.4・§20.5 のどちらの表にも対象として現れない）。**これは本シナリオ全体で最も重大な発見である**：§0.7 が最優先に置く「ユーザーの訂正が消える」失敗が、書き込み経路（I1〜I8・origin優先の実行層強制）では防がれているのに、**バックアップ復元という書き込み経路を経由しない事象からは無防備に発生しうる**。

**PO・職人に何が見えるか（(6) 全体）**：PO には④・④' のどちらについても通知が一切発生しない（検出機構が無いため §21 の通知表のどの行にも載らない）。④' のケース2（旧版復活）が実際に起きた場合、PO には「以前訂正したはずの方針が、何の説明もなく元に戻っている」ように見える——しかもこれは番頭が「確信を持って」述べる形になりうる（旧版が正規の resident エントリとして注入されるため）。職人は `assemble_brief()` 経由でしか記憶を受け取らないため、この巻き戻りが発生した状態で発注されたブリーフには**訂正前の古い方針が「現在の結論」として headline に載る**可能性があり、職人はそれを疑う手段を持たない（memoryless、§0.3.1）。

## 3. 動くこと

- **A4・A5 アームによる縮退動作**：A1・entity_index が壊れても、A4（系譜近傍）・A5（最近性）が生きていれば完全な喪失にはならない場合がある（1.2 ケースα）。これは §8.5.6 が意図した「A1・A2 が同期更新されていれば A3 が遅れても検索不能にならない」という冗長設計の副産物であり、設計されていない偶然の耐性として機能する。ただし A2 はそもそも一般名詞トピックに効かないため（§7 が自認）、実質的な保険は A5 一本に近い。
- **RRF融合はアーム欠落そのものには頑健**（§8.5.5 の明記どおり）。一部エントリのみ A3 に載っている状態でも計算自体は破綻しない（1.5 の試算どおり、両エントリとも `rel_norm` は算出でき、tier 判定まで機械的に進む）。「壊れる」のではなく「系統的に不利になる」という形で影響が出る。
- **見逃し率の一部は事後計測できる**（§16、訂正イベント起点）。PO が後から気づいて訂正すれば、(2) のような欠落は統計上補足されうる経路がある。
- **`po_message` の最優先プリエンプト**（§20.3・§21）は、再索引中であっても PO の応答を待たせない形で機能する。障害・移行の裏でも対話体験そのものは壊れない。
- **`model_migration` は起床源として存在し**（§20.2）、A3導入時のトリガーには対応する行がある。「再評価バッチをどう起こすか」という入口自体は用意されている。

## 5. 最小の修正案

**筆頭（蓄積開始前にしか直せない可能性があるもの）**

- **`derived_from` / `superseded_by` の版解決失敗時の挙動を、Substrate の意味論として今のうちに確定する。** 現行の共通コア（ADR-0010 §1）は「参照先が存在する」ことを暗黙の前提にスキーマ・アルゴリズム（F1）を組んでおり、「存在しないIDを指す」ケースの扱いが version/superseded_by/tombstone の意味論のどこにも書かれていない。これは新規フィールドの追加ではなく**既存フィールドの意味論の欠落**なので、Substrate 変更として扱うべきか Policy 側の実行層規則として扱うべきかの判定自体をまず PO 裁定に上げる必要がある——後から「実は Substrate 側の前提だった」と気づいても、蓄積済みの過去のエントリには遡及できない。**最低限、「解決不能な参照は`unresolved`として扱い、絶対にフォールバックで『存在するかのように』扱わない」という原則だけは、蓄積開始前に固定しておく価値がある**（フォールバック先の実装は Policy で調整できても、「フォールバックしてはいけない」という向きは §0.7 の1位に直結するため後から変えにくい）。

**Policy/Loop 側（現行の枠組みのまま追加できるもの）**

1. **索引健全性シグナルを `retrieve()` の戻り値に追加する**（`trace` の一部、または新規フィールド）。「このクロージャ・この期間の索引は再構築待ち／健全性未確認」という粒度でよい。これがあれば番頭は §0.7 の2位（断定して誤る）を避け、4位（見逃しとして保留する）側に倒せる。
2. **§20.4 の「積む条件」表に行を1本足す**：「`derived_from`／`superseded_by` の参照先が存在しない」→ 積む対象「そのエントリ自身、最優先」。これは既存の表形式・既存の再検証キュー機構をそのまま流用でき、新しい機構を要らない（配線レジストリ§20.7.1に1行足すだけで済む設計になっている）。
3. **§20.5 の点検表に「参照整合性」の項目を足す**（点検3の対象を`external_ref`から`derived_from`/`superseded_by`にも広げる、または新規の点検9として追加）。バックアップ復元やデータ移行のような「システム外イベント」を深い睡眠の起床源に明示的に含める（`timer`の一種として「復旧後の整合性チェック」を義務づける）。
4. **索引障害を起床源として明示する**（§20.2 に7つ目の種別、例：`store_integrity` を追加するか、`memory_signal` の対象シグナルに索引健全性を含める）。現状「深い睡眠の点検を待つしかない」という単線の検知経路を、少なくとも「プロセス再起動時に軽量な整合性チェックを走らせる」程度の同期的トリガーで補強できる。
5. **A3移行期の不公平に対する緩和策を明記する**：未処理エントリに対して暫定的に「A2/A4/A5のみでの`rel_norm`計算に小さな補正項を与える」か、逆に「見出し帯の定員 `K_hl` を移行期間中だけ広げる」等、§8.5.6の「見直しの契機」とは別に「移行期間中の扱い」を一文足す。
6. **再索引の分割単位・優先順位の決定規則を明文化する**（例：「アクティブなクロージャから優先」「1回の深い睡眠あたりの上限件数を予算関数として定義」）。§20.3「再索引」行に、§8.5.5の`K_ws`/`K_hl`同様「予算の関数」として算出する規則を足す。

## 6. 判定

**この軸（記憶ストアの障害・索引喪失・復旧・マイグレーション）は、これまでの10シナリオ・R1〜R6のいずれからも検証されたことがない、文字通りの死角だった**（§20.8 末尾が自ら認めている）。結果として、検査した10論点のうち **規定ありと言えるものは実質2件のみ**（RRFのアーム欠落耐性＝壊れない、`po_message`最優先プリエンプト）で、**未定義7件、矛盾1件**という判定になった。

とりわけ深刻なのは (6) の `superseded_by` 宙ぶらりケースである。書き込み経路（`record()`/`supersede()`/蒸留、I1〜I8・origin優先の実行層強制）に対しては §0.3.0・ADR-0010 §1.3 が「訂正は消えない」ことを何重にも担保しているのに、**バックアップ復元という書き込み経路を経由しない事象**に対しては、同じ失敗（PO の訂正が黙って消え、訂正前の古い方針が復活する）を防ぐ機構が一切存在しない。これは §0.7 が最上位に置く失敗モードに対して、**防御が「通常の書き込み経路」にしか張られておらず、復旧・移行という非通常経路には及んでいない**ことを意味する。これまでのラウンド（R1〜R6）が繰り返し見つけてきた「規則を1つの層にだけ書き、配線を忘れる」という同じ形の欠陥（§0.3.0 冒頭が自認する病）が、今回は「層」ではなく「経路の種類（通常運用 vs 障害復旧）」という新しい軸で再現している。

索引の健全性についても、Substrate（エントリ本体）と Policy（索引・スコアリング）の分離という設計の基本方針（D3：導出できる値は保存しない）自体は正しいが、**その分離ゆえに「本体は無事だが索引だけ壊れる」という中間状態が構造的に発生しうるにもかかわらず、その中間状態を検知・通知・区別する機構が一段薄い**。§8.5.6の「索引はエントリの導出物であり真実ではない」という位置づけは、保存の正しさ（再構築可能性）については真だが、応答の正しさ（PO が今この瞬間に正しい答えを得られるか）については何も保証しない——この2つを同一の文で扱ってしまっていることが、(2) で仕様自身の矛盾として露呈した。

**総合判定：この軸は「未定義が多いのは新しい軸だから当然」では済まされない。** とくに #8（`superseded_by`宙ぶらりによる訂正の巻き戻り）は、§0.7の設計原理そのものに対する例外であり、次のラウンドで最優先に埋めるべき筆頭候補として引き継ぐ。
