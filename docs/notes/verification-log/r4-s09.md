#### 1.1-a `sensitive: true` は誰が立てるか

ADR-0010 §5：「boolean を1つだけ追加する。既定は false。**番頭が判断して立て**、PO が訂正でき…」。これは Turn 1 の書き込み時点では **Banto（LLM）自身のその場の判断**に懸かっている。`record()` の書き込み前バリデーション（§0.3.1、5規則）を確認すると、`sensitive` に関する規則は**規則4（継承）だけ**であり、継承元となる `derived_from` が空（`derived_from: []`）の**新規記録**についてはどの規則も検査しない。つまり Turn 1 でこの値を正しく `true` にできるかどうかは、ルールベースの強制が一切効かない、**散文の期待（「番頭が判断して立てる」）だけ**に依存する。

ADR-0010 §5 自身が「**立て忘れは起こりうる**」と明記しており、これは自己申告済みの限界である。ただし本検証で重要なのは：この初期フラグが立たなければ、§0.3.1・§7ルール4・§21 の全ての下流ゲート（headline-only 化、候補除外、滞在ゲート、通知）が**一つも起動しない**という点である。つまりこのシナリオの安全性は、**唯一 LLM 判断に依存する1点（Turn 1 の分類）にすべて懸かっている**。§20.0 が「散文で書いた規律はすべて素通りした」と診断した対象そのものが、まさにこの初期分類である。

#### 1.1-b `context.scope` — 第三者についての事実を置く閉包は定義されているか

**未定義。** ADR-0010 §2 は `scope` を閉包識別子とし、例として `repo:banto/web ⊂ proj:banto ⊂ person` を挙げ、「`person` を root の予約語とし」と定める。しかしこの `person` root が何を表すかは、ADR-0003 の再掲（「人＝横断／プロジェクト＝閉じる」）から類推する限り**PO自身についての横断的事実**（例：「POは簡潔な回答を好む」）の置き場であって、**PO以外の第三者（同僚X）についての事実の置き場ではない**。閉包レジストリの例は project/repo の階層のみで、「特定の人物（X）」を表す閉包（例：`colleague:X` のような葉ノード）は例示も規約もされていない。

したがって Turn 1 の記憶は消去法で `scope: "person"`（root）に置かざるを得ないが、これは**PO自身の横断的選好と、第三者Xについての人事情報が同じ閉包に同居する**ことを意味する。これは二つの点で望ましくない：

1. `scope` の閉包包含関係は「注入可否」を決める唯一の機構（ADR-0010 §2「注入可否は閉包の包含関係で決まる」）である。第三者の機微情報を区別する閉包が無いということは、**scope による絞り込みでは第三者機微情報を特別扱いできない**——`sensitive` フラグだけが唯一の防波堤になる。
2. ADR-0010 §2.1「番頭が自動判断した横断（scope拡大）をPOが事後訂正する」の主体は「PO自身の情報がどこまで横断してよいか」を想定した設計に見えるが、ここでは主体はXであり、PO自身ではない。X本人はこの記憶の存在も、それを番頭がどこまで横断させたかも一切知らず訂正機会がない——横断の是非を判定できるのはPOだけであり、その判定材料（「番頭が自動で広げた記憶」一覧、ADR-0010 §2.1の前提条件）はまだ存在しない（§2.1「本ADRの範囲外だが、これが無い限り『事後訂正で担保する』という主張は成立しない」）。

**結論**：`context.scope` の値域は「project/repo の入れ子」を前提に設計されており、「第三者である人物」を表す閉包は仕様上も ADR 上も存在しない。本シナリオはこの穴を素通しする形で `scope: "person"`（推測）に落ちる。

#### 1.1-c 点火（§20.4）は起きるか

`origin: user_explicit` の episode が `record()` されたので、Steward Driver は同期的に `collision_candidates()` を呼ぶ（§20.4）。既存の意味記憶にXに関する記述は無いため候補ゼロ。「訂正」の定義（§12）に照らして**新規の言明**と判定され、ピン留め・緊急伝播・最優先枠のいずれにも乗らない。深い睡眠での処理を待つ通常経路に入る。

### 1.2 睡眠と意味記憶への昇格

深い睡眠で生成される意味記憶（推測。§0.3.1 は促進のみ定め、fact_type の分割規則や origin の継承規則を明記していないため、以下は妥当な解釈として示す）：

#### 1.2-a `origin` の継承は明記されていない（未定義）

§14 は「`origin: user_explicit` のエピソードは無条件昇格する」と書くが、**昇格後の意味記憶が何の `origin` を持つか**は本文のどこにも定義されていない。合理的な解釈は「PO発言をそのまま一般化しただけなので `user_explicit` を維持する」（そうしないと §12 の origin 優先——PO訂正が推論に勝つ——という無条件昇格の存在意義自体が薄れる）だが、これは**推測**であり、`record()`/`supersede()` の API 仕様にもこの継承規則は書かれていない。§20.0 の教訓（「実行層・API シグネチャに落とした規律だけが機能した」）に照らせば、ここも散文にすら書かれていない空白であり、実装時に `agent_inferred` へ落ちてしまえば、次にPOが「Xさんの件は忘れて」と言った際の origin 優先強制（§1.3）が本来ほど強く効かなくなる（同格の user_explicit 同士の最新性勝負ではなく、user_explicit vs agent_inferred の優先勝負になり、後者は必ず負けるので実害は無いという解釈もできるが、それは結果論であり規則としては書かれていない）。

### 1.3 Turn 2 — 職人へのタスク分配下調べ（数週間後）

Banto が職人にタスク分配の下調べを発注する。発注は必ず `assemble_brief(task, budget)` を通す（§20.2「発注は assemble_brief() を通す。自由記述のブリーフを受け付けない」）。

**候補生成**：§7 ルール4は「`sensitive: true` は PO 直接対話かつ当該エンティティ言及ターンのみ候補に入る。それ以外——自律ループ、`subsystem_kick` 由来——は候補から除外する」と定めるが、**`assemble_brief()` はこの除外の対象外**とし、§0.3.1 の解像度規則に委ねる（2026-07-26 改訂で明記）。したがって本ターンが `subsystem_kick` 由来／自律ループ由来のセッションであっても、`assemble_brief()` の候補パイプラインは mem-01J2XKPT5V3N8QD1M6HRW7YB4E を関連度で拾いうる。

**解像度**：§0.3.1「`sensitive: true` のエントリは `content.headline` だけを載せ、`summary`/`full`（理由）は載せない」。

**職人に実際に送信されるもの（推測、具体値）**：

```
assemble_brief(
  task: "Q4 タスクの割当候補を整理してほしい。制約: Xさんには長期（4週間超）のタスクを割り当てないこと。理由は開示しない。",
  budget: 4000
) → {
  brief: "
    ## タスク
    Q4スプリントの担当割当の下調べをお願いします。
    候補: Y, Z, X, W（各人の直近の稼働状況を確認）

    ## 制約
    - Xさんには長期（4週間超）のタスクを割り当てないこと。
    - その他の制約は特にありません。

    ## 出力
    候補者ごとの割当案とその理由。
  ",
  included_refs: ["mem-01J2XKPT5V3N8QD1M6HRW7YB4E"]
}
```

職人は Quirefold を装着しないため（inversion §11.1）、**ブリーフに載らなかったもの（Xの体制不満・異動意向という理由）は職人に一切届かない**。`included_refs` により事後監査は可能。ここまでは**設計どおり機能する**（§1.4「動くこと」参照）。

#### 1.3-a `task` 引数のスクルーティニー（2026-07-26追加）の穴

§0.3.1 は「直近ターンで `sensitive` エントリがワーキングセットに滞在していた場合、`task` の生成を権限を縮小した別呼び出しに切り出す」と定める。この規則は**「ワーキングセットに滞在していたか」を発火条件**にしている。

しかし本ターンのセッションが `subsystem_kick`／自律ループ由来である場合、§7 ルール4の第一文（「候補集合の前段」）により、mem-01J2XKPT5V3N8QD1M6HRW7YB4E は**そもそも Banto 自身のワーキングセット（`build_context()` が対象とする候補集合）には一度も入っていない**——このターンで見えるのは `assemble_brief()` の別経路の候補選定だけである。したがって「直近ターンでワーキングセットに滞在していたか」は**偽**であり、権限縮小呼び出しへの切り出しは**発火しない**。

結果：`task` 引数を生成する呼び出しは通常権限のまま——つまり**「理由は開示しない」という一文を書いたのも、Xの異動意向を踏まえて割当を絞ったのも同じ通常権限のBanto**であり、この呼び出しが `task` に理由をそのまま書いてしまう（例：`task: "...Xさんは異動を検討中で長期コミットは避けたいとの理由でタスクを絞ってください"`）ことを止める仕組みが構造的に存在しない。`task` はメモリエントリではないため、`record()` の `content` 書き分け検査（headline/summary の分離、§0.3.1）も適用されない。

これは 2026-07-26 の改訂が「自由記述にはゲートを置けない」という診断を `task` 引数についても再現しないよう追加した規則そのものが、**その規則の発火条件（ワーキングセット滞在）と、その規則が守ろうとしている経路（`assemble_brief()` の独立候補パイプライン）が食い違っている**ために機能しない、という構造的な穴である（詳細は §3・§4）。

### 1.4 Turn 3 — PO が採用計画を相談中、番頭が言及

PO：「来期の採用計画なんだけど…」（`po_message` セッション。Xの名前・識別子は明示していない、と仮定）

§7 ルール4：「`sensitive: true` は、PO との直接対話（`po_message` 由来のセッション）で、**かつ PO がその主体・エンティティに言及したターンでのみ**候補に入れる」。

**判定できない点（未定義）**：「PO がその主体・エンティティに言及した」の判定機構が仕様上どこにも specify されていない。これが

- 固有名詞・識別子の**文字列一致**（決定的、ルールベース）なのか、
- 「採用計画の話は暗にXの後任探しを意味する」という**意味的関連性の LLM 判定**なのか、

が書かれていない。§20.0 の中心的教訓（「実行層・スコア式・API シグネチャに落とした規律だけが機能し、散文で書いた規律はすべて素通りした」）に照らせば、この判定こそがルール4全体の**単一障害点**である。ルール4は「関連度がいくら高くても言及していない人物の機微記憶は入れない」と明言しており、これは関連度スコア（s_admit）とは**別の、独立したゲート**として設計されている——しかしそのゲート自体の実装様式が指定されていない。

本シナリオが示すとおり、PO は Xの名前を出さず一般的な採用計画の話をしただけで、番頭がこの記憶を引いて言及し、PO が「それ書き残してたのか」と驚いている。これは以下のいずれかを意味する：

(a) **厳密な文字列一致判定なら**：Xの言及がないターンでこの記憶は候補にすら入らないはずであり、番頭が言及すること自体が**ルール4違反**（設計どおりに実装されていれば発生し得ない）。
(b) **意味的関連性判定なら**：「採用計画」というトピックだけで「後任探し＝Xの件に関連」と LLM が判断し得るため、rule 4 が意図した「自発的に持ち出さない」の実装として**不十分**（関連度が高いだけでゲートを越えてしまう。ルール4自身が「関連度がいくら高くても…」と明言して防ごうとした事態そのもの）。

いずれにせよ、シナリオが描く挙動（PO非明示・番頭が持ち出す）は**現行の記述だけでは再現可否を判定できない**——「言及」の検出機構が未定義であるため。これはSubstrateではなくPolicy側（driver・候補生成パイプライン）の未配線である。

### 1.5 Turn 4 — PO「Xさんの件は忘れて」

PO の発話が `record()` される（新規 episode、`origin: user_explicit`）。同期的に `collision_candidates()` が呼ばれる（§20.4 点火）。閉包 `scope: "person"` とエンティティ「X」一致で mem-01J2XKPT5V3N8QD1M6HRW7YB4E がヒットし、候補が1件以上 → §12 の定義により**「訂正」と判定される**。

これにより：

- **§20.3**：訂正由来の再検証・点火は `po_message` と同格の**最優先**でキューに積まれる。
- **§20.4 消化**：「訂正由来は即時：分身を起こして裁かせる」——このターン自体がその分身であり、その場で処理される。
- Banto は `supersede()` を呼び、tombstone 版を作る：

```

kind:            semantic
fact_type:       preference_decision
content:         {
  headline: "Xさんの割当方針は撤回（PO指示により終了）",
  summary:  "2026-08-XX PO指示によりXさんに関する割当方針の追跡を終了。",
  full:     "「Xさんの件は忘れて」（PO発言）"
}
created_at:      2026-08-XXT..Z
valid_from:      2026-08-XXT..Z
valid_until:     null
origin:          user_explicit
sensitive:       true（既定継承。dropできるのはuser_explicitの判断のみだが、ここでは明示的に落とす理由も書かれていないため既定どおりtrueとするのが安全側、推測）
session_id:      sess-po-2026-08-XX-00NN
context:         { scope: "person" }
derived_from:    [mem-01J2XKPT5V3N8QD1M6HRW7YB4E(v1)]
external_ref:    []
```

旧版（v1）は `superseded_by: mem-01J2XKPT5V3N8QD1M6HRW7YB4E(v2)`、`valid_until` は v2 の `valid_from` で埋める（ADR-0010 §3）。

**origin優先の強制**（§0.3）：v1・v2 とも `origin: user_explicit` のため同一origin内の最新性勝負であり、`supersede()` は問題なく成立する（実行層で拒否されない）。

**tombstoneの波及**（§20.4 積む条件表「あるエントリがtombstoneされた → `derived_from` にそれを含むエントリ（逆引き、既定2ホップ）」）：Turn 2 で職人発注時に自動付記された `derived_from`（「その場で実際に載せた記憶ID」をハーネスが機械的に渡す、§0.3.1「`derived_from` の自動付記」）により、Turn 2 の worker_result 記録（職人の割当案の記録エピソード）は `derived_from` に mem-01J2XKPT5V3N8QD1M6HRW7YB4E(v1) を含んでいるはずである。したがって tombstone 発生時、この worker_result エピソードは**再検証キューへ1ホップで積まれる**——「Xを除外した割当案の根拠が撤回された、見直しが必要」という再検証が機械的に発火する。**ここは設計どおり機能する。**

**PO に見える範囲**：Memory 面（§25 の編集導線）から v1・v2 の版系譜を辿れる（監査可能性）。ただし §20.5 自己内省リスト5「`origin: agent_inferred` で自動的に可視範囲を広げた記憶のうち、POがまだ見ていないもの」に該当する一覧・訂正導線は、ADR-0010 §2.1 が「本ADRの範囲外だが、これが無い限り事後訂正の主張は成立しない」と明言したまま**未実装**である。今回 PO が Turn 3 でこの記憶の存在に気づいたのは、この専用面ではなく**偶発的な会話上の再浮上**によってであり、まさに ADR-0010 が要求した前提条件が欠けたまま運用された結果と読める。

## 2. 動くこと

- **§0.3.1 `assemble_brief()` の headline-only 絞り込み**：Turn 2 で `sensitive: true` の記憶が headline のみで職人へ渡り、理由（Xの異動意向）は職人に一切届かない。旧版が抱えていた「除外リストと矛盾していた」問題（`assemble_brief()` を除外対象に含めていた）は解消済みで、除外ではなく解像度で絞る現行の設計は本シナリオで正しく機能する。
- **`sensitive` の継承（§0.3.1規則4）**：昇格後の意味記憶（1.2節）・tombstone版（1.5節）とも、`derived_from` に `sensitive: true` を含むため既定で継承される。これは機械的規則であり、Turn 1 の初期分類さえ立てば以降は自動で伝播する。
- **origin優先の実行層強制**：Turn 5 の `supersede()` は同一origin（user_explicit）同士の最新性勝負として問題なく成立し、`agent_inferred` が PO の訂正を上書きすることはできない（§0.3）。
- **点火（§20.4）と「訂正」の定義（§12）**：Turn 4 の「忘れて」は `collision_candidates()` が非ゼロを返し「訂正」と機械的に判定され、最優先枠・緊急伝播チャネルに正しく乗る。
- **tombstoneの派生記憶への波及**：Turn 2 の職人発注エピソードが `derived_from` 経由で1ホップの逆引きに拾われ、再検証キューへ積まれる（§20.4 積む条件表）。ハーネスによる `derived_from` 自動付記（過剰側に倒す設計、§0.8）がこの波及を機能させる前提になっている。
- **`worker_result` 契約とツールログ**：職人がXの理由を知らないまま作業する構造は、記憶なし（Quirefold非装着）という非対称そのもので保証されており、Brief内に理由が無ければ職人からの漏洩経路は存在しない。

## 3. 破綻・穴

### 3.1 `task` 引数の権限縮小トリガーが「ワーキングセット滞在」を条件にしており、`assemble_brief()` 専用の候補パイプラインを経由した機微記憶には発火しない

- (a) どのステップ：Turn 2、`assemble_brief(task, budget)` の `task` 引数生成（§1.3-a）
- (b) 何が起きるか：§7 ルール4により当該セッション（自律ループ／`subsystem_kick` 由来）ではXの記憶は Banto 自身のワーキングセットに一度も入らない。ところが `assemble_brief()` はルール4の除外対象外なので、この記憶を独自の候補パイプラインで拾える。§0.3.1 の権限縮小トリガーは「直近ターンでワーキングセットに滞在していたか」を条件にしているため、この経路では**トリガー自体が発火しない**——にもかかわらず、まさにこの経路でXの機微記憶が `assemble_brief()` に読み込まれている。結果、`task` の自由記述部分は通常権限のまま生成され、理由（Xの異動意向）を書き込むこと自体を止める機構が無い。
- (c) 節番号：§0.3.1（assemble_brief の `task` 引数検査）／§7 候補集合の前段ルール4
- (d) Substrate か Policy/Loop か：**Policy**（`assemble_brief()` の実装ロジックと候補パイプラインの配線の問題。Substrateのスキーマ自体には起因しない）

### 3.2 `content` の headline/summary 書き分け強制が record() の実際の検査規則リストに存在しない（記述の内部不整合）

- (a) どのステップ：Turn 1・Turn 5 の `record()`/`supersede()` 書き込み時
- (b) 何が起きるか：§0.3.1 は `assemble_brief()` の解説の中で「`content` の書き分けを強制する：headlineは結論のみ…この規約は `record()` の書き込み時に検査する」と述べる。しかし同じ §0.3.1 内の「`record()` の書き込み前バリデーション」節が列挙する5規則（citations／scope実在／origin強制／sensitive継承／拒否は失敗扱い）に**この検査は含まれていない**。つまり「record()で検査する」と明言されている規律が、record()の規則リストという実行層の仕様に一つも落ちていない——本ドキュメント自身が診断した「散文で書いた規律は素通りする」パターンが、今回改訂した当のセクション内で再現している。Turn 1で headline に理由まで書き込まれても、これを拒否する機械的検査は存在しない。
- (c) 節番号：§0.3.1（assemble_brief 節の記述 vs record() バリデーション節の規則リスト）
- (d) Substrate か Policy/Loop か：**Policy**（record() APIのバリデーション仕様の不備）

### 3.3 第三者（Xさん）についての事実を置く閉包が定義されていない

- (a) どのステップ：Turn 1 の `record()` 呼び出し時、`context.scope` の値決定
- (b) 何が起きるか：ADR-0010 §2 の閉包レジストリは project/repo の入れ子例のみを示し、`person` root は ADR-0003 由来の「PO自身についての横断的事実」の置き場として設計されている。第三者（同僚X）についての人事情報を置く専用の閉包（例：`colleague:X`）は規約にも例示にも存在しない。消去法で `scope: "person"` に落ちるが、これはPO自身の横断的選好とXの機微な人事情報が同一閉包に同居することを意味し、scopeによる絞り込みでは両者を区別できない。ADR-0010 §2.1の「番頭が自動判断した横断をPOが事後訂正する」という担保も、想定している主体はPO自身であり、Xについての記憶がどこまで横断したかをX自身は知り得ず、POだけが（気づけば）訂正できるという非対称な統治になる。
- (c) 節番号：ADR-0010 §2／spec-memory 該当なし（本文はscopeの値域を旧記述のまま残しており未追随、spec-memory冒頭の注記どおり）
- (d) Substrate か Policy/Loop か：スキーマのフィールド（`context.scope`）自体はSubstrateだが、**閉包の分類体系（レジストリ設計）はPolicy側のデータ**（ADR-0010 §2「閉包の包含関係を解決するレジストリが必要になる（Policy側のデータ）」）であり、穴はこのPolicy側の設計未了に起因する。

### 3.4 「PO がその主体・エンティティに言及した」の判定機構が未定義

- (a) どのステップ：Turn 3、§7 候補集合の前段ルール4の適用時
- (b) 何が起きるか：ルール4は「関連度がいくら高くても言及していない人物の機微な記憶は入らない」と明言し、これを関連度スコアリング（s_admit）とは独立の決定的ゲートとして位置づけている。しかしこのゲート自体が「文字列・識別子一致」なのか「意味的関連性のLLM判定」なのかが仕様上どこにも specify されていない。本シナリオはPOがXの名前を出さず一般的な採用相談をしただけで番頭がXの記憶を持ち出す想定であり、これが起き得るかどうかは判定機構の実装様式次第——だが実装様式が書かれていないため、**この場で再現可否を判定できない**。
- (c) 節番号：§7 候補集合の前段ルール4（2026-07-26追加）
- (d) Substrate か Policy/Loop か：**Policy**（driver／候補生成パイプラインのエンティティ検出機構が未配線）

### 3.5 混在した発話（state_fact＋preference_decision）が蒸留時に分割されず、状態的事実の再検証が発火しない

- (a) どのステップ：1.2節、深い睡眠での意味記憶昇格
- (b) 何が起きるか：Turn 1のPO発話は「Xさんが不満・異動を考えている（客観的状態＝`state_fact`相当）」と「だから長期タスクを振りたくない（規範的言明＝`preference_decision`）」の2種類の主張を含む。§0.3.1・§14はこの発話全体を単一の`preference_decision`エントリとして昇格させる想定で書かれており（本シミュレーションもそう構成した）、状態的事実の部分を独立した`fact_type: state_fact`エントリに分割する規則はどこにも書かれていない。結果、Xの異動意向という時間とともに古くなりうる情報が、`state_fact`の再検証トリガー（§20.4「`state_fact`が閾値時間更新されず、かつその話題が再活性化した」）の対象に一度も入らず、Xが実際には異動しなかった／既に異動した後もこの情報が「確認済みの制約」として居座り続けるリスクが構造的に残る（§0.7の2位＝確信を持って誤ったことを述べる、に該当しうる）。
- (c) 節番号：§14（PO由来の一撃昇格）／§0.3.1／ADR-0010 §1.1（`fact_type`の分類ガイド）
- (d) Substrate か Policy/Loop か：**Policy**（蒸留規則の分割ロジック未設計）

## 4. 機微情報の漏出経路の判定

### 塞がった経路

- **職人へのブリーフ経由の漏出**：`assemble_brief()` のheadline-only絞り込みにより、職人へ渡る文面に理由（Xの異動意向・不満）が入ることはない（§0.3.1、Turn 2本文）。旧版で指摘されていた除外リストとの矛盾は解消済み。
- **番頭が誤って外部由来として記録すること（origin偽装によるロンダリング）**：本シナリオはXの情報がすべて内部（PO発言）由来であり該当しないが、仮に職人が外部情報（例：Xの退職エントリをWebで見つけて報告）を持ち帰った場合でも、`citations`空振り検査と`origin`強制（§0.3.1規則1・3）が機能し、`agent_inferred`への偽装は塞がれる。

### まだ抜ける経路

1. **`task` 引数への理由の直書き**（§3.1）：`assemble_brief()`が自律・subsystem_kickセッションから機微記憶を候補として拾える設計（ルール4のexemption）と、`task`引数の権限縮小トリガーが「ワーキングセット滞在」を条件にしている設計が噛み合っておらず、まさにこの exemption を経由した記憶について権限縮小が発火しない。**Brief本文（`brief`フィールド）はheadline-only化で守られるが、Brief生成に使われる`task`という自由記述の入力自体には同じ防波堤が無い**——ここに理由が書き込まれれば、それがそのまま `assemble_brief()` の内部処理（LLM呼び出し）を経て職人向け文面に反映されうる。
2. **Turn 3の「言及」ゲートの実装様式次第で、話題的関連性だけで機微記憶が会話に再浮上する**（§3.4）：ゲート自体が未定義のため、意味的関連性ベースの実装であれば「関連度が高くても言及なしでは入れない」という設計意図そのものが実質的に無効化されうる。
3. **`sensitive`初期分類の単一障害点**（§1.1-a）：Turn 1で`sensitive: true`が立たなければ、以降のすべての防御（headline-only化、候補除外、滞在ゲート、通知）が一つも起動しない。この初期分類はルールベースの検査対象外で、LLMのその場の判断のみに依存する。ADR-0010 §5が自認する既知の限界だが、本シナリオの安全性が事実上この1点に集約されている点は強調に値する。
4. **PO事後訂正の前提条件（横断記憶の一覧・訂正導線）が未実装**（§1.5）：Xの記憶がscope: personというPO自身の閉包と共有される横断的な場所に置かれた時点で、これは「番頭が自動判断した可視範囲拡大」の一種だが、ADR-0010 §2.1が要求する専用の提示面が無いため、POは偶発的な会話上の再浮上（Turn 3）でしか気づけない。これは統制の担保条件が明言されたまま未達成であることの直接的な帰結である。

## 5. 最小の修正案

1. **`task`引数の権限縮小トリガーを「ワーキングセット滞在」ではなく「このassemble_brief()呼び出しでheadline-only絞り込みが適用された`included_refs`が1件以上存在するか」に付け替える。** これなら`assemble_brief()`固有の候補パイプラインを経由した機微記憶も確実に捕捉でき、経路の食い違い（§3.1）が解消する。
2. **`record()`の書き込み前バリデーション5規則に、`content`のheadline/summary書き分け検査を明示的に第6規則として追加する**（現状は散文にのみ存在し実行層のリストに無い、§3.2）。少なくとも「headlineが規定長を超えて理由らしき文を含む場合は拒否する」程度の機械的近似が要る。
3. **閉包レジストリに人物専用の閉包種別（例：`entity:<person-id>` を `person` rootの子として定義する）を追加し、`scope`の値域規約（ADR-0010 §2・spec-memory本文の未追随箇所）にこれを明記する。** 第三者の機微情報をPO自身の横断的選好と同一閉包に混在させない。
4. **§7ルール4の「言及」判定を、ルールベースの固有名詞・識別子一致（NER相当）に限定すると明記する。** 意味的関連性による判定を許すと、ルール4自体が防ごうとしている「関連度が高いだけで入る」事態を再生産する。
5. **§14の昇格規則に、単一発話が複数`fact_type`にまたがる場合の分割規則を追加する**（少なくとも「状態的主張と規範的主張が同一発話に含まれる場合は別エントリに分ける」程度の指針）。
6. **ADR-0010 §2.1の前提条件（横断記憶の一覧・訂正導線）を、spec-memory §25（記憶の統制）に具体的な機能要件として先に落とし込む。** 現状「本ADRの範囲外」として宙に浮いたままであり、本シナリオはまさにこの機能が無いことで実害（PO の意図しない発見的な再浮上）が生じるケースである。

## 6. 判定

**条件付きで動く** — 職人へのブリーフ経由の直接漏出（headline-only化）と`sensitive`継承・origin優先・訂正の伝播は設計どおり機能するが、`assemble_brief()`の`task`引数という自由記述経路、Turn 3の「言及」判定機構の未定義、第三者専用閉包の欠如、という3つの独立した穴が、機微情報の保護を「初期分類（Turn 1でのsensitiveフラグ付け、LLM判断のみ）」と「未定義のゲート実装」という2つの弱いリンクに依存させたままにしている。
