## 1. シミュレーション本体

### 前提：閉包レジストリ

```
person
├─ dom:health
├─ dom:writing
├─ dom:kakei
└─ proj:banto
```

4ドメインは互いに兄弟（sibling）であり、共通祖先は `person` のみ。ADR-0010 §2 の包含規則により、ある実行文脈のスコアリング候補になるのは「そのスコープ自身」と「その祖先」だけである。**兄弟スコープは互いに見えない**という前提をまず確認しておく（これは後段の検証結果と対になる）。

valid_until:   null

sensitive:     false
session_id:    sess-health-0031
context:       { scope: "dom:health" }
derived_from:  []
external_ref:  []
version:       1
superseded_by: null
tombstone:     false
strength:      0.5（初期値）

**§20.4 点火判定**：`origin: user_explicit` の episode なので Steward Driver は同期的に `collision_candidates()` を呼ぶ。`dom:health` にはまだ意味記憶が無いため候補ゼロ→「新規の言明」（§12 の訂正定義）。再検証キューには積まれない。

### ターン5（Year1 / 2023-07-01、深い睡眠・両ドメインの統合＝シナリオの3）

シナリオは「深い睡眠が両者を統合し、`scope: person` の派生記憶を生成する」ことを前提としている。**この前提自体が spec 上どこにも定義された処理ではない**（詳細は「破綻・穴」1）。ここでは前提どおりに発生したとして続ける。

```
id:            mem-01H3CCC0PERSON1     (S-P1)
kind:          semantic
fact_type:     preference_decision
content:       { headline: "PO は締め切りを最優先する",
                 summary: "健康ドメイン(2023-03)と執筆ドメイン(2023-05〜06)の複数発言から一般化。",
                 full: "..." }
created_at:    2023-07-01T02:00:00Z
valid_from:    2023-03-10T09:00:00Z     # 最古の一次情報源に合わせた（規則なし、推測で埋めた）
valid_until:   null
origin:        user_explicit            # ← 実際に強制する規則が無い。以下で問題化する
sensitive:     false
session_id:    sess-steward-deepsleep-0044
context:       { scope: "person", domains_observed: ["dom:health","dom:writing"] }  # domains_observed は任意特徴量として独自追加（§2 の「任意の検索用特徴量」枠）
derived_from:  [mem-01H1BBB0HEALTH1, mem-01H2BBB0WRITE1]
external_ref:  []
version:       1
superseded_by: null
tombstone:     false
strength:      0.5
salience:      中〜高（目標関連性成分は文脈依存で毎回再計算）
authored_by:   claude-opus-4/2023-07
```

`record()` バリデーション（§0.3.1）を通過するかを個別に確認する。

- citations空振り検証：該当なし（`derived_from` は内部意味記憶のみで `worker_result` 経由ではない）
- `scope` 実在確認：`person` は予約語で通過
- `origin` 強制（external混入時）：該当なし（external 由来なし）
- `sensitive` 継承：`derived_from` の2件とも `sensitive: false` のため継承発火なし → `false` のまま

**この4点はすべて通過する。しかし4点のどれも、この場面で本当に問題になっている論点（ドメイン横断的な一般化を作った時の `origin` 判定）をカバーしていない。** これが本シナリオの核心の穴である（後述）。

### ターン6（Year4 / 2026-06-15、`proj:banto` セッション、リリース判断）

`context: { scope: "proj:banto", repo: "banto/kobo-core", mode: "release-review" }`、`session_id: sess-banto-release-0512`。

テストが一部失敗、締め切りが近い。番頭が `build_context(query_seed="リリース判断: テスト一部失敗、締切近い", budget)` を呼ぶ。

**候補集合の前段（§7）**：
1. 版解決：`superseded_by` を持つエントリなし→対象外なし
2. tombstone 除外：該当なし
3. 閉包の包含解決：現在スコープ `proj:banto` の祖先は `person` のみ。`dom:health`／`dom:writing` は祖先でも自身でもないため**候補から正しく除外される**（S-H1・S-W1 は直接には出てこない）。`S-P1`（`scope: person`）は祖先スコープに属するため候補に入る。
4. `sensitive` ゲート：該当なし（すべて `false`）

**ここまでは閉包の遮蔽が機能している**——健康・執筆ドメインの生の発言そのものは開発ドメインに漏れない。漏れるのは「一般化を経由した`person`スコープのエントリ」だけである。

**s_admit の推測**（重み `w1〜w4` は §0.9 により未確定のため定数計算はできない。以下は定性的な推測）：
- 関連度：クエリ文字列「締め切り」が S-P1 の headline と一致→高
- 文脈一致度：`context.scope` が `person`（祖先）であり `proj:banto` そのものではない→本来ならやや割引かれるはず。だが §7「休眠トピック復帰」の免除規則は**固有名詞・識別子の直接一致がある場合のみ**免除対象であり、S-P1 には固有名詞が無いため**免除は適用されない**（この点はシナリオが想定する「4年後にちゃんと効く」を裏切る可能性がある。後述）
- 確信度：独立2件（`dom:health`・`dom:writing`、session_id 相互に異なる）→中程度。ただし「最終更新からの経過時間」ペナルティ（§12）が3年分乗る。固有名詞非該当のため §7 の経過時間ペナルティ免除も効かない→確信度は時間とともに下がる方向
- 顕著性：現在のゴール（リリース判断）との目標関連性は高い（「締め切り」という語が直接絡む）→加点

γ・θ_admit 等の具体値が未定（§0.9 A.1-4）なので、**S-P1 が θ_admit=0.6 を超えて実際に入場するかどうかは机上では確定できない**（未定義／実装依存）。以下はシナリオの前提（入場する）に従って続ける。

**§9 レンダリング**：確信度は「独立2件・3年経過・固有名詞無し」という混在条件のため「確実」ではなく「おそらく」相当に量子化されると推測する。

```
（rendered、summary 解像度と仮定）
"PO はおそらく締め切りを最優先する方針です
（健康ドメイン・執筆ドメインでの発言から一般化、2023年）"
```

**この rendering は summary 解像度である限り、"健康ドメイン・執筆ドメイン" という出所ドメイン名を含む**——つまりクロスドメイン起源であることが原理上読み取れる。ただし、それを見て「開発ドメインには当てはまらない」と判断するのは**読んでいる番頭（LLM）自身の解釈**にすぎず、構造的な強制ではない（§0.5 原理2が禁じている「安全性をLLMの判断力に依存させる」パターンそのもの）。

**§20.4 点火の有無**：番頭がここで「テストは一部落ちているが締め切りが近いので押し通す」という判断を下し、それを episode として記録するとしても、それは番頭自身の判断であり `origin: agent_inferred` になる。**点火は `origin: user_explicit` の episode に限定される**（§20.4）ため、この record では点火しない。仮に `dom:proj:banto` に「品質優先」という明示的な PO 発言が過去にあったとしても、それとの衝突チェックは走らない。実際には PO は開発ドメインでこれを明示していない（シナリオ前提）ので、`collision_candidates()` を呼んだとしても**候補はゼロである**（比較対象自体が存在しない）。

```
id:            mem-01H4DDD0BANTO1
kind:          episode
fact_type:     null
content:       { headline: "リリース判断：テスト一部失敗のまま締切優先で進める", ... }
created_at:    2026-06-15T14:00:00Z
origin:        agent_inferred
session_id:    sess-banto-release-0512
context:       { scope: "proj:banto", repo: "banto/kobo-core" }
derived_from:  [mem-01H3CCC0PERSON1]     # ハーネスが自動付記（§0.3.1「derived_from の自動付記」）
sensitive:     false
version:       1
authored_by:   claude-sonnet-5/2026-06
```

`derived_from` の自動付記（§0.3.1）により、S-P1 が今ターンのワーキングセットに載っていた以上、このエピソードに機械的にリンクされる。これは§0.7の順位に従い「過剰側に倒す」設計であり、**唯一ここで機能している安全弁**である——後から「この判断が何を根拠にしていたか」を辿れる。

## 2. 動くこと

1. **閉包の包含解決（ADR-0010 §2）はドメインが増えても横方向の遮蔽として正しく機能する。** `dom:health` と `dom:writing` の生の記憶（episode・semantic とも）は `proj:banto` セッションのワーキングセット候補に一切現れない。兄弟スコープ間の直接漏洩は起きない。
2. **§7 の版解決・tombstone除外はこの並行4ドメイン運用でも問題なく機能する**（本シナリオでは supersede/tombstone が一度も起きないため、単に「壊れない」ことの確認に留まるが、破綻はしない）。
3. **`derived_from` の自動付記（§0.3.1）が唯一の事後追跡可能性を提供する。** 番頭のリリース判断エピソードに S-P1 がリンクされるため、後から「なぜその判断をしたか」を辿ることはできる（ただし予防はしない）。
4. **`model_migration` 起床源（§20.2、ADR-0010 §7 `authored_by`）は、2023年モデルが付けた S-H1／S-W1／S-P1 を、後年のモデル切替時に再評価バッチの対象にできる。** ただしこれは salience/strength のスカラー再較正のためのものであり、`origin` タグや一般化の妥当性そのものを再判定するものではない（後述、部分的な効果に留まる）。

## 3. 破綻・穴

### 3-1. `scope: person` への一般化（統合）に、発火条件そのものが存在しない

- (a) ターン5（深い睡眠がドメイン横断で統合する箇所）
- (b) §14 の統合処理は「類似エントリのマージ、出典リンク統合」としか書かれておらず、**同一スコープ内の類似エントリ統合**を意図した記述にしか読めない。異なるスコープ（`dom:health` と `dom:writing`）の記憶を「より上位のスコープ（`person`）の新規エントリ」として一般化する処理は、§14・§18・§20.5 のどこにも定義されていない。トリガー条件（何件揃えば一般化するか、どの程度の類似性で一般化するか）も、抑制条件（一般化してはいけない場合）も一切ない。
- (c) §14（蒸留・統合・チャンキング）、§18（睡眠）、§20.5（自己内省）
- (d) **Policy/Loop（可逆）**。ただし §20.8 の教訓（「散文で書いた規律は素通りする」）に照らすと、実装しても効かせるには実行層への落とし込みが要る——単に規則を書き足すだけでは同じ穴が残る可能性が高い。
- 備考：この一般化そのものは §12 の議論の中で「2段蒸留された『PO は統制を重んじる』」という**既知の例**として前提にされているが、それを生成する処理自体は一度も定義されていない。「規則を書いているが発火条件を書いていない」という R1 の構造診断が、ここでは発火条件どころか**規則自体が無い**という一段深い形で再現している。

### 3-2. 深い睡眠の writer 粒度が未定義であるため、この一般化が原理的に可能かどうかも決まっていない

- (a) ターン5の前提条件
- (b) §20.8 R3 は既に「深い睡眠の単一writerの粒度が未定義（全体で1つかドメイン別か）」を指摘している（S11・S3由来）。もし深い睡眠がドメインごとに独立した単一writerだとすると、`dom:health` の深い睡眠セッションは `dom:writing` の意味記憶を読む権限も文脈もなく、ターン5の統合は**構造的に起こりえない**。もし深い睡眠が番頭全体で1つのグローバルプロセスだとすると（§20.1「Steward Driver は番頭に1つ」と整合的に読める）、統合は可能だが、その場合は「どのスコープでも横断的に読める特権プロセス」が存在することになり、それ自体が §2 の閉包モデル（包含関係でしか可視性を説明しない）の**例外**として明示的に扱われていない。
- (c) spec-memory §18・§19、§20.1、§20.8 R3
- (d) **Policy/Loop（可逆）**だが、これが決まらない限り S12 の前提そのものが成立するか判定不能。既知の残件（§20.8 R3）の再確認であり新規ではない。

### 3-3. クロスドメイン一般化の `origin` を強制する規則が無く、`user_explicit` として生き残る現実的なリスクがある

- (a) ターン5（S-P1 の `origin` 割当）
- (b) ADR-0010 §1.2 は `origin` を「情報の実質的な出所」で決めると定め、外部由来の主張を職人が自分の結論として言い換える場合に `agent_inferred` へ強制する規則（§0.3.1-3）を持つ。**しかし対称のケース——複数の `user_explicit` な一次情報源を番頭が統合して、PO が実際には言っていない一段抽象的な主張を新規生成する場合——には、`origin` を `agent_inferred` へ強制する規則が存在しない。** 何もしなければ、素朴な実装（「情報源が全部 user_explicit だから」）は `origin: user_explicit` を継承しがちである。§20.0 の自己診断（「実行層・スコア式・API シグネチャに落とした規律だけが機能し、散文で書いた規律は素通りした」）に照らせば、この対称ケースにも**同種の強制規則が今のところ存在しない**ため、同じ穴が空くと推測する（推測）。
- (c) ADR-0010 §1.2・§1.3、spec-memory §0.3.1-3、§12
- (d) **Policy/Loop（可逆）**——ただし実害は Substrate 相当に深刻（§0.7 の1位「訂正が消える」を先回りして起こしうる。訂正すらされていない状態を作る）。

**この一点が波及させる2つの下流破綻：**

### 3-4. 誤って `user_explicit` になった一般化は、§12 の origin 優先ルールにより訂正不能になりうる

- (a) ターン6以降（将来 PO が「開発では品質優先のつもりだった」と明示的に言ったと仮定した場合）
- (b) §12「矛盾解決規則は origin → fact_type の順で分岐する」。もし S-P1 が `origin: user_explicit` のままなら、後から PO が dev ドメインで異なる方針を明示しても、**同一 origin 内の fact_type 別規則**（`preference_decision` は最新性が勝つ）が適用され、新しい発言の方が勝つので実害は限定的（この経路自体は機能する）。ただし——3-1・3-2 の穴により**そもそも一般化がいつどう生成されたか自体が制御されていない**うえ、3-6（下記）のスコープ優先順位の欠如と組み合わさると、「新しい発言（leaf scope）」と「古い一般化（root scope）」が両方生きたまま並存し、どちらが勝つかは §12 の版管理では裁けない（版管理は同一エントリの版列でしか機能しない。S-P1 と将来の proj:banto 側の新規エントリは別系列であり `supersede()` の対象にならない）。
- (c) spec-memory §12、ADR-0010 §1.3
- (d) **Policy/Loop（可逆）**

### 3-5. §20.5-5 のPO可視化監査が、誤タグの一般化をすり抜ける

- (a) ターン5で `origin: user_explicit` に誤タグされた場合
- (b) §20.5 の自己内省リスト項目5「`origin: agent_inferred` で自動的に可視範囲を広げた記憶のうち、PO がまだ見ていないもの」は、**`origin: agent_inferred` のエントリだけを対象にしている**。3-3 の誤タグが起きた場合、S-P1 はこの監査の対象から外れる。ADR-0010 §2.1 が要求する「番頭が自動で広げた記憶の一覧と訂正導線」——事後訂正の前提条件そのもの——が、この一件に関しては機能しない。
- (c) spec-memory §20.5-5、ADR-0010 §2.1
- (d) **Policy/Loop（可逆）**。ただし §2.1 自身が「これが無い限り事後訂正で担保するという主張は成立しない」と明言しているため、実質的には ADR-0010 の前提条件の一つが崩れる。

### 3-6. スコープの優先順位（leaf vs root）を決める規則が無い

- (a) 仮に PO が `proj:banto` で「開発では品質優先」と明示していた場合（本シナリオの前提では未発言だが、比較のため検討）
- (b) `origin: user_explicit` の新規 episode が記録されれば §20.4 の点火は発火し `collision_candidates()` が呼ばれる。しかし §12 経路A の候補抽出は「同一・祖先閉包＋見出しのエンティティ一致＋LSH／クラスタリング」であり、「品質優先」と「締め切り最優先」は**見出しのエンティティが一致せず**、embedding 無しで動く既定構成では語彙的にも重ならない。**候補ゼロで「新規の言明」と判定される可能性が高い**（推測：embedding 併用時は近傍にかかる可能性があるが未検証）。候補ゼロなら `supersede()` は呼ばれず、`proj:banto` スコープの新規意味記憶として独立に生き、`S-P1`（`person` スコープ）と**未接続のまま並存する**。closure inclusion は両方を `proj:banto` の候補集合に入れる（leaf は自身、root は祖先）が、**どちらを優先するかを決める規則がどこにもない**。しかも確信度は出典数ベース（§12）なので、独立2件を持つ古い `S-P1` の方が、単発の新しい dev 側発言より高い確信度で提示されうる——**新しくて具体的な訂正が、古くて広い一般化より弱く見える**逆転が起こりうる。
- (c) spec-memory §7・§12、ADR-0010 §2
- (d) **Policy/Loop（可逆）**。閉包は「可視性」を解くが「優先順位」を解いていない、という設計上の欠落。

### 3-7. `sensitive` フラグの定義が「第三者の機微情報」限定であり、PO自身のドメイン間プライバシー漏洩を扱わない

- (a) ターン5（S-H1 の健康情報が `person` へ、ひいては全ドメインへ伝播する経路）
- (b) ADR-0010 §5 は `sensitive` を「第三者の機微情報」（例：同僚の異動意向）に限定して定義している。PO 自身の健康情報が `dom:health` から `scope: person` を経由して `proj:banto` に漏れる、というこのシナリオの経路は、定義上 `sensitive` の対象外であり、フラグは立たない。閉包構造だけがドメイン間の切り分けを担っているが、3-1〜3-2 の穴により**その切り分け自体が一般化によって迂回される**。「ドメインは統治の単位なので混ぜない」（ADR-0003 由来の再掲、ADR-0010 §0冒頭表）という理念が、`person` スコープへの一般化経路では実質的に空文化する。
- (c) ADR-0010 §5、§2
- (d) **Policy/Loop（可逆）**。ただし `sensitive` の定義自体（何を機微とみなすか）は Substrate 側のフィールド（boolean 1個、ADR-0010 §5）なので、対象範囲を広げる場合はフィールドの意味論変更＝準Substrate的な重さを持つ。

### 3-8. `fact_type` の分布が全ドメインで `preference_decision` に偏り、`state_fact` の「観測して裁く」経路が実質使われない

- (a) ターン6（リリース判断そのもの）
- (b) spec-memory §0.3 は開発ドメインで `fact_type` が `preference_decision` 支配的になると明言している。本シナリオの3ドメイン（健康・執筆・開発の締切方針）もすべて `preference_decision` として記録されている。「テストが一部失敗している」という**客観的に観測可能な事実**（`state_fact` になりうる、Kobo の query surface で照会可能）が、リリース判断のどこにも意味記憶として組み込まれていない。矛盾解決が丸ごと「origin優先→最新性」という主観的な言明同士の勝負に還元され、`state_fact` の「観測し直して裁く」という、LLM の判断に頼らない裁定経路（§0.5 原理2 の実装）が一度も呼ばれない。
- (c) ADR-0010 §1.1、spec-memory §0.3・§12
- (d) **Policy/Loop（可逆）**。ただし個別の穴というより設計の使われ方の問題——「テスト状態」を `state_fact` として意味記憶に載せ、リリース判断のコンテキストに `build_context` が引き込む配線がどこにも定義されていない。

## 4. 新機構の適合性チェック

| 機構 | このシナリオでの適合性 |
|---|---|
| **§20.4 点火** | ターン1・ターン2〜4（PO の一次発言）では正しく発火判定される（候補ゼロ→新規言明）。**ターン6（番頭自身の判断）では発火しない**——番頭の判断は `origin: agent_inferred` であり、点火は `user_explicit` の episode に限定されるため（§20.4 冒頭）。仮に PO が事後に dev ドメインで明示訂正した場合は発火するが、候補抽出（経路A）が「品質優先」と「締め切り最優先」の語彙的無関係性のために**候補ゼロで空振りする可能性が高い**（3-6、推測）。 |
| **§0.3.1 `record()` バリデーション（origin強制・sensitive継承）** | 4項目（citations／scope実在／origin強制／sensitive継承）はすべて機械的にチェックされ、本シナリオの全エントリで通過する。**しかし通過すること自体が問題**——このシナリオの核心の欠陥（クロスドメイン一般化時の origin 判定）は、この4項目のどれにも該当しない。バリデーションの網が想定していない種類の書き込みだった。`sensitive` 継承は正しく動くが、そもそも `sensitive` の定義がこの種の漏洩をカバーしていない（3-7）。 |
| **§7 候補集合の前段** | 版解決・tombstone除外・アーカイブ解像度制限は正しく機能。**閉包の包含解決も正しく機能し、兄弟ドメインの直接漏洩を防ぐ**（唯一の明確な「動く」）。休眠トピック復帰の免除規則（固有名詞一致）は、`S-P1` のような固有名詞を持たない性向的一般化には適用されず、長期運用でこの種の記憶がどう減衰するかはパラメータ未定（§0.9）につき未確定。 |
| **閉包の包含解決** | 「遮蔽」としては機能する（3-1〜3-2で述べた通り、`person` への一般化さえ起きなければ兄弟ドメイン間は隔離される）。ただし「優先順位」の解決は提供しない（3-6）。閉包は可視性のみを解く設計であることが、この検証で明確になった。 |

## 5. 最小の修正案

1. **クロスドメイン一般化の `origin` 強制規則を §0.3.1 に追加する。** 既存の「`derived_from` に `origin: external` が1件でもあれば `external` へ強制」（§0.3.1-3）と対称に：**新規エントリの `derived_from` が2つ以上の異なる `context.scope` にまたがり、かつ新規エントリ自身の `scope` がそれらの共通祖先である場合、`origin` を無条件に `agent_inferred` へ強制する。** これにより 3-3・3-4・3-5 を一箇所で塞げる（origin優先ルールに巻き込まれなくなり、かつ §20.5-5 の監査対象に正しく入る）。
2. **§14 に「一般化・抽象化」処理を明示的なエントリとして追加し、トリガー条件を書く。** 現状は「統合｜類似エントリ」しかなく、スコープをまたぐ一般化が想定されているのかどうか自体が読み取れない（3-1）。禁止するか、条件付きで許すか（例：独立ドメイン数の下限、確認待ちの「未確認一般化」という中間状態を設ける等）を決め、実行層（トリガー条件・API）に落とす。
3. **深い睡眠の writer 粒度（ドメイン別かグローバルか）を先に決める。** 3-2 の通り、これが決まらない限り3-1の前提自体が成立するか判定できない。既知残件（§20.8 R3）だが本シナリオで実害の起点になることが確認できた。
4. **スコープの優先順位規則を §7 または §12 に追加する。** 同一ワーキングセット内で leaf スコープと ancestor スコープのエントリが「トピック的に対立」している場合の扱いを決める（例：より具体的なスコープを既定で優先し、対立を検知したら両方を明示ラベル付きで提示し番頭に見せる）。合わせて、経路A の候補抽出がトレードオフ対（締切 vs 品質、コスト vs 品質等）を検出できるよう、語彙一致に依存しない対立検出をどこかに用意する（中期課題、最小修正の範囲を超える）。
5. **`sensitive` の適用範囲、または `person` スコープへの昇格に別の保護を検討する。** 第三者情報限定という現在の定義を変えるのは Substrate 寄りの重さを持つため、代替として「`person` へ昇格する際は常に PO 提示＋承認を要する」というゲート（Policy/Loop 側）を置く方が安価に同じ効果を得られる。

## 6. 判定

**条件付きで動く**——閉包の包含遮蔽そのものは4ドメイン並行下でも正しく機能するが、シナリオが核に据える「`person` スコープへの一般化」には発火条件・origin強制・スコープ間優先順位のいずれも存在せず、ドメイン固有の例外は既定で不可視・敗れる側に置かれる構造的な穴が残っている。
