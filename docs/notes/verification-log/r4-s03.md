## 1. シミュレーション本体

### 前提：閉包とセッション

```
person
└─ proj:banto
   └─ repo:banto/api   ← 分身A・分身Bとも、便宜上ここに scope を置く（後述、これ自体が課題）
```

「認証」は特定の repo に閉じない横断的関心事だが、`context.scope` の閉包モデル（ADR-0010 §2）は project/repo 階層でしか閉包を持たない。以下では A・B とも `repo:banto/api` で発生したことにして進めるが、**実際には A の設計相談と B の kick が別 repo・別祖先で起きた場合、経路A の「同一閉包または祖先」フィルタは両者を候補ペアとして拾わない**（§12 経路A）。この点は §5「休眠トピックの復帰」が想定する固有名詞一致のフォールバックでも救えない（「認証」は固有名詞ではなく一般語）。**未定義**として先に指摘しておく。

### ターン1（14:03、分身A・PO設計相談）

PO と番頭（分身A）が認証まわりのレビュー方針を相談し、「認証まわりは事故ると被害が大きいので、レビューを厳しめにする」という結論に至る。

分身Aが `record()` する episode：

```
id:            mem-01JZKAAA1E
kind:          episode
fact_type:     null                      # kind:episode は null（ADR-0010 §1.1）
content:       { headline: "認証関連PRのレビューを厳格化する方針",
                 summary: "PO×番頭の設計相談。認証は事故時の被害が大きいためレビューを厳しめにする方針で合意。",
                 full: "(会話ログの要約)" }
created_at:    2026-07-26T14:03:00Z
valid_from:    2026-07-26T14:03:00Z
valid_until:   null
origin:        user_explicit             # ★判定根拠は下記で検証。実は未定義
sensitive:     false
session_id:    sess-A7f3k9
context:       { scope: "repo:banto/api", mode: "design_discussion" }
derived_from:  []
external_ref:  []
version:       1
superseded_by: null
tombstone:     false
strength:      0.5（初期値、推測）
salience:      中〜高（PO判断＝目標関連性が高いと推測）
authored_by:   claude-opus-5/2026-07
```

**origin 判定の検証**：ADR-0010 §1.2 は origin を「情報の実質的な出所」で定義し、`user_explicit`＝「PO の発話」、`agent_inferred`＝「番頭または職人自身の推論・統合・判断」とする。だが本ターンの結論文は PO の逐語ではなく、**対話の中で番頭と PO が共同で到達した言明**である。PO が「そう決めよう」と一言で確認したのか、番頭がまとめた文言に PO が頷いただけなのかで、実質的な出所の判定は変わりうる。

**この場合分けを機械的に判定する規則はどこにも無い。** §0.3.1 に定義されているのは「`derived_from` に `origin: external` が含まれる場合に `origin` を無条件で `external` に強制する」というルール（3.）だけであり、これは外部由来の対称にしか効かない。「PO 発話 vs 番頭の統合」を分ける機械的テストは存在せず、判定は記録する主体（分身A自身）の自己申告に委ねられている。これは §0.9／§0.5 原理2 が全体として距離を置いている「LLM の自己申告」と同種の脆弱性であり、しかも**この1フィールドの値がシナリオの帰趨を丸ごと反転させる**（後述4節）。

以上より、`origin: user_explicit` は**このシミュレーションの前提として置いた値**であり、仕様上その値を保証する規則はない。**未定義**。

**§20.4 点火判定（入口1）**：`origin: user_explicit` の episode が record された。Steward Driver は同期的に `collision_candidates()` を呼ぶ（scope: `repo:banto/api` とその祖先 `proj:banto`／`person`）。この時点で認証レビュー方針に関する既存の意味記憶は無い → 候補ゼロ →「新規の言明」（§12 の訂正の定義）。ピン留めは発生しない（§7 のピン留めは「訂正」のみが対象）。

浅い睡眠（セッション終了時）で候補化。分身Aのセッションが propose() を呼ぶ（あるいは浅い睡眠がepisodeから直接候補を生成する）と仮定して：

```
id:            mem-01JZKAAA2C          (候補、未確定)
kind:          semantic
fact_type:     preference_decision      # 規範的言明（ADR-0010 §1.1）
content:       { headline: "認証関連PRはレビューを厳格化する", summary: "...", full: "..." }
origin:        user_explicit
session_id:    sess-A7f3k9
context:       { scope: "repo:banto/api" }
derived_from:  [mem-01JZKAAA1E]
version:       1（候補）
```

### ターン2（15:10、分身B・Kobo kick起因）

Kobo から `subsystem_kick`（cadence：認証系の軽微修正PRが3件滞留）で分身Bが起床。分身Bは「認証の定型修正は自動化して速度を優先すべき」と判断し、command surface 経由で Kobo に自動マージ設定変更を送る。

```
id:            mem-01JZKBBB1E
kind:          episode
fact_type:     null
content:       { headline: "認証の定型修正PRを自動マージ対象にする設定変更をKoboへ指示",
                 summary: "滞留していた3件の認証系軽微修正について、レビュー負荷より速度を優先し自動マージ設定を変更。",
                 full: "..." }
created_at:    2026-07-26T15:10:00Z
valid_from:    2026-07-26T15:10:00Z
valid_until:   null
origin:        agent_inferred            # 番頭自身の判断。PO発話なし
sensitive:     false
session_id:    sess-B2m8p1
context:       { scope: "repo:banto/api", mode: "autonomous_kick" }
derived_from:  []
external_ref:  [{ system: "kobo", id: "command-9931-set_automerge_policy" }]   # §20.5-6 要件
version:       1
superseded_by: null
tombstone:     false
strength:      0.5（初期値、推測）
salience:      中（推測）
authored_by:   claude-opus-5/2026-07
```

**§20.4 点火判定**：origin は `agent_inferred` なので入口1（user_explicit episode の同期点火）は**発火しない**。入口3（`origin: external` を含む episode）も該当しない。よって**分身Bのこの決定は、記録された瞬間には一切の衝突検査を受けない。**

**分身Bの結論が意味記憶の候補になるか**：ここが本検証の核心の分岐点になる。§14 が定める昇格経路は2つしかない。

1. `recall_count` 閾値超え（統計的）
2. `origin: user_explicit` の無条件昇格

分身Bの結論はどちらにも該当しない——単発の `subsystem_kick` セッションの episode であり、`recall_count` はほぼ0、origin も `agent_inferred`。**`propose()` を誰が・どの条件で呼ぶかは §0.3 に書かれておらず、§14 にも「agent_inferred の単発判断（かつ外部への command 副作用を伴う）を無条件に候補化する」という第3の経路が無い。**

楽観的に「分身Bのセッションが自らこの決定を重要と判断して `propose()` を呼ぶ」と仮定すれば、以下の候補が生まれる（後段のシミュレーションはこの仮定つきで進める。**この仮定自体が仕様に書かれていない**ことを明記する）：

```
id:            mem-01JZKBBB2C          (候補、未確定・仮定)
kind:          semantic
fact_type:     preference_decision
content:       { headline: "認証の定型修正は自動化を優先する", summary: "...", full: "..." }
origin:        agent_inferred
session_id:    sess-B2m8p1
context:       { scope: "repo:banto/api" }
derived_from:  [mem-01JZKBBB1E]
version:       1（候補）
```

### ターン3（15:10〜翌未明、A・B とも走っている最中）

**A・Bが互いの決定を見る手段はあるか**：無い。理由を機能単位で確認する。

- episode ログは「完全並行・追記のみ」（§19）だが、これは**書けることの保証**であって**互いを見せる仕組み**ではない。
- `collision_candidates()` は「既存の**意味記憶**との衝突候補」（§0.3）を返す関数であり、B の生の episode（まだ意味記憶に昇格していない）は対象にならない。よって**分身Aの記録タイミングでBの存在を検出することは、Bが先に記録していたとしても原理的にできない**（意味記憶になっていないため）。
- §20.4 入口1の同期点火は「`origin: user_explicit` の episode が record された時」にのみ発火し、しかも比較対象は既存の意味記憶であって、他の**現在生きているセッション**の in-flight な episode ではない。
- §21 の割り込み裁定は「同じ閉包かつ同じゴールに属する既存の生きた分身」への合流を判定するが、A（設計相談）とB（自動化判断）はゴールが異なるため別分身のまま扱われ、統合されない。
- PO は UI 上で A・B 両方の会話スレッドが同時に生きているのを目視できる可能性はあるが（inversion §6「会話スレッド一覧＝生きてる分身」）、これは**PO の注意力に依存する人間側のアフォーダンスであり、システムが対立を検出して提示する設計された機構ではない**。
- 職人（Worker Agent）はそもそも Quirefold を装着しない（inversion §11.1）ため、両者の存在自体を知りえない。

**結論：走っている最中に両者の対立を検出・提示する設計された経路は存在しない。** これは §19 のスナップショット隔離の意図された帰結（「自分が何もしていないのに前提が途中で変わるべきではない」）そのものだが、その代償として**この日の間、Koboの自動マージ設定はAの方針と矛盾したまま現実に効き続ける**。

### ターン4（夜間、深い睡眠・単一writer）

`timer` 起床源で深い睡眠が走る（§18・§20.2）。候補キューには（楽観的仮定のもとで）`mem-01JZKAAA2C`（A由来）と `mem-01JZKBBB2C`（B由来）が乗っている。

**§14 昇格**：`mem-01JZKAAA2C` は `derived_from` を遡ると `origin: user_explicit` の episode に行き着くため、`recall_count` を問わず無条件昇格。確定版：

```
id:            mem-01JZKAAA2C          (S-A, 確定)
kind:          semantic
fact_type:     preference_decision
origin:        user_explicit
context:       { scope: "repo:banto/api" }
derived_from:  [mem-01JZKAAA1E]
version:       1
superseded_by: null
tombstone:     false
valid_from:    2026-07-26T14:03:00Z
created_at:    2026-07-27T03:00:00Z    # 深い睡眠時刻
```

`mem-01JZKBBB2C`（B由来）はそのまま確定候補として並ぶ。

**§12 経路A・§20.4 入口2（同一バッチ内対立候補）の適用**：安価な一次フィルタ（同一閉包 `repo:banto/api`、エンティティ一致「認証」）が `mem-01JZKAAA2C` と `mem-01JZKBBB2C` を候補ペアとして抽出する。バッチ内・セッション内のLLM判定（制御ループではない、§20.0）で「レビュー厳格化」と「自動化優先」は同一領域における対立方針であると確定する。

**解決規則（§12 origin優先）**：`origin: user_explicit`（A）は `agent_inferred`（B）に無条件で優先する。fact_type別規則（`preference_decision`＝最新性）には進まない——origin優先がそれより先に効くため（B の方が時刻は新しいが、それは無視される）。**A が勝つ。**

**§12「検出結果を裁定へ配線」の実行**：深い睡眠は敗者（B）に対し `supersede()` を呼ぶ。

```
# B の旧版
id:            mem-01JZKBBB2C
superseded_by: mem-01JZKBBB3T
version:       1

# 新版（tombstone）
id:            mem-01JZKBBB3T
kind:          semantic
fact_type:     preference_decision
content:       { headline: "[敗退] 認証の定型修正は自動化を優先する",
                 summary: "(※仕様上、この理由文言をここに書く義務は明記されていない。以下は本シミュレーションでの補完)",
                 full: "..." }
created_at:    2026-07-27T03:05:00Z
valid_from:    2026-07-27T03:05:00Z
origin:        ???                       # ★下記で指摘。未定義
session_id:    sleep-2026-07-27-deep
context:       { scope: "repo:banto/api" }
derived_from:  [mem-01JZKAAA2C, mem-01JZKBBB2C]   # 勝者と敗者の旧版の両方
external_ref:  [{ system: "kobo", id: "command-9931-set_automerge_policy" }]
sensitive:     false
version:       2
superseded_by: null
tombstone:     true
authored_by:   claude-opus-5/2026-07（深い睡眠のモデル、推測）
```

**未定義の指摘**：新版（tombstone版）自身の `origin` を何にすべきか、規則に書かれていない。深い睡眠という制御ループ的処理が生成した版だが、`origin` の3値（user_explicit/agent_inferred/external）のどれにも綺麗に当てはまらない。また `content` に「なぜ敗れたか」の理由文言を書く義務も §12 の追記ルールには無い——ルールが要求しているのは `derived_from` に両者を含めることだけである。つまり「なぜ敗れたか」は**版系譜（derived_from＋各版の origin/fact_type）から機械的に再構成可能**ではあるが、**エントリ自身に理由が明文化される保証は無い**。監査者はこのルール（origin優先）を別途知っている前提で系譜を読む必要がある。

**§20.4 反応側の積み**：「あるエントリが tombstone された」「あるエントリが supersede された」の2条件が `mem-01JZKBBB2C`／`mem-01JZKBBB3T` に対して成立し、`dependents()` の逆引きで子孫（今回は無し、1階層のみ）が再検証キューに積まれる。

### ターン5（深い睡眠の自己内省、§20.5）

自己内省の項目6「裁定が覆った記憶を根拠に、サブシステムへ送った command はないか」を評価する。

`mem-01JZKBBB1E`（Bの episode、`external_ref` に Kobo command を保持）→ その episode から派生した意味記憶候補 `mem-01JZKBBB2C` が今回 supersede/tombstone された、という連鎖を逆引きできる（`derived_from` を辿って episode → 候補、候補が superseded であることを確認）。

**これは発火する——ただし前提が成立していれば、の話である。** 前提とは「B の結論が候補キューに乗り、A と衝突判定され、supersede が実際に呼ばれたこと」。この一連が起きて初めて、item 6 が参照する「根拠エントリの版が変わった」という状態が生まれる。

アテンションカードとして PO に上がる（自動では巻き戻さない、§20.5-6）：「分身Bが送ったKobo自動マージ設定変更（command-9931）の根拠が、PO確認済みの認証レビュー厳格化方針と競合し敗れました。設定を見直すか判断してください。」§21 の通知条件「覆った根拠に基づく外向きの副作用」に該当し、重大度は高（同格でリスト入り）。

**この間、Koboの自動マージ設定は実際に変更されたままである。** 決定①（Kobo完全分離）の代償としてノート側が既に自認している問題（agent-primary-inversion.md §11「分身がKoboにcommandを送って現実を変えた後、その学びが敗れても設定を戻す手順がない」）がそのまま再現している。是正は自動化されない設計だが、**発見されるまでの時間**（深い睡眠のケイデンスは日次/週次、§18）だけ矛盾した実世界状態が持続する。

### ターン6（翌日、分身C）

`po_message`（「認証のPRどうする？」）か、あるいは前日のアテンションカードへの応答として分身Cが fork される（`session_id: sess-C9k2q4`）。

セッション開始時にスナップショットを取得（§19）。`build_context()` は版解決規則（§7）に従い、`superseded_by != null` と `tombstone: true` を除外して最新版のみを候補にする。したがって C に見えるのは：

- `mem-01JZKAAA2C`（S-A、確定・有効）＝「認証はレビュー厳格化」
- `mem-01JZKBBB2C` は候補から**除外**（tombstone された系譜の旧版）
- 明示的に監査目的で版履歴を辿れば `mem-01JZKBBB3T` に到達し、そこから A・B 両方の旧版、origin の違い（user_explicit vs agent_inferred）が確認できる

C は「PO の明示決定（レビュー厳格化）が有効であり、Kobo の自動マージ設定はそれと矛盾する残置物である」と正しく判断できる——**ただし、ここまでの全ての楽観的仮定（B の結論が候補化された）が成立していた場合に限る。**

**もし成立していなければ**（§14 に第3の昇格経路が無いという厳格な読みを取るなら）：`mem-01JZKBBB2C` はそもそも存在せず、`mem-01JZKBBB1E`（生の episode）だけが store に残る。深い睡眠の候補キュー衝突検査（§20.4 入口2）は候補同士しか見ないため、これを一切検査しない。supersede は呼ばれない。自己内省項目6は「根拠エントリの版が変わった」事実そのものが発生しないため、**何も見つけられない**。Kobo の自動マージ設定は**恒久的に**、誰にも気づかれずに残る。分身Cも、A の方針とBが送った command の矛盾を知る手段が無い（`build_context()` は semantic memory から作られ、Kobo の実行ログをその都度読みには行かない。読みに行くのは番頭が明示的に query surface を叩いたときだけ、inversion §11.6-①）。

## 2. 動くこと

- **§14 無条件昇格**：`origin: user_explicit` である限り（分身Aの結論がそう分類される限り）、候補ゼロの新規言明であっても閾値・ピン留め条件を問わず意味記憶へ昇格する。これは実装通りに動く。
- **§12「検出結果を裁定へ配線」**：一度、対立する2つの意味記憶候補が実際に候補キューに乗ってさえいれば、origin優先規則での勝敗決定→敗者への `supersede()` 呼び出し→`tombstone: true`＋`derived_from` に勝者・敗者両方、という手順は仕様通りに機械的に実行できる。版系譜からの遡及も（理由文言なしで）技術的には再構成可能。
- **§7 版解決**：`superseded_by`/`tombstone` を持つ版が `build_context()` の候補から正しく除外され、分身Cは正しい最新状態だけを見る。
- **§20.5-6 のアテンションカード**：B の episode に `external_ref` で command が残っており、かつ B の結論が候補として供された場合、覆った根拠の追跡と PO への通知は機構として発火できる。

## 4. 並行合流の判定

**独立に生まれた2つの対立候補は、改訂後の規則で最後まで裁けるか。** 一度キューに乗ってしまえば裁ける（§12・§14・§7 の該当メカニズムは技術的に整合し、実際に supersede まで到達する）。**しかし裁定の前段——両者を候補として同じ土俵に乗せる段——が非対称であり、ここで途切れる可能性が高い。**

**途切れる箇所（具体）**：§14 の昇格条件が「PO発話」と「想起回数」の2つに限定されているため、**agent_inferred・単発・command副作用ありという分身Bの決定パターンには昇格（候補化）経路が存在しない**。これは偶然の穴ではなく構造的な非対称である——`origin: user_explicit` は無条件昇格という強い扱いを受ける一方、`origin: agent_inferred` の一撃の運用判断（しかも外部システムへの実行副作用を伴う）には対応する強制経路が無い。§20.4 入口2は「候補キュー内の対立を検査する」としか書いておらず、**候補キューに乗ること自体を保証する規則が欠けている**。

**Koboの副作用はPOに上がるか。** 上がる経路（§20.5-6）は存在し、機構としては正しく設計されている。ただし発火条件は「根拠エントリの版が変わったこと」であり、根拠エントリ（Bの結論の意味記憶版）が最初から存在しなければ、版が変わることもなく、**この通知は発生しない**。したがって「Koboの副作用はPOに上がるか」への答えは条件付き：**Bの結論が意味記憶候補になっていれば上がる。なっていなければ上がらず、Kobo設定は誰にも気づかれずに残る。**

加えて、たとえ穴1が塞がれていたとしても、穴2（分身Aの origin 判定の未定義性）が独立に致命的である。分身Aの結論が万一 `agent_inferred` と分類されれば、origin優先も無条件昇格も効かず、**PO立ち会いの結論の方が、Koboの自動判断より後から負ける**という、設計意図と真逆の結果になりうる。この分岐点に対する機械的な安全網（自己申告を検証する規則）は存在しない。

## 5. 最小の修正案

1. **§14 に第3の昇格トリガーを追加する**：episode の `external_ref` に subsystem の command 参照が含まれる場合（＝実世界に副作用を及ぼす決定）、`recall_count` を問わず次の睡眠で無条件に `propose()` する。§20.5-6 が既に要求している「command を送った episode には external_ref を残す」というルールをそのまま流用でき、新しいフィールドは不要。
2. **同一バッチ内対立候補の検査（§20.4 入口2）を深い睡眠だけでなく浅い睡眠にも適用する**、または深い睡眠のケイデンスを短縮する。現行の日次/週次では、Kobo設定の矛盾が発見されるまでの実世界での持続時間が長すぎる。
3. **origin 判定に機械的な補助規則を追加する**：PO との対話から生成された結論について、当該ターン内に PO 自身の確認発話（同意・承認を示す独立した utterance）が episode として別途記録されている場合のみ `user_explicit` を許可し、それが無ければ既定で `agent_inferred` とする。これにより自己申告だけに依存しない最低限のゲートができる。
4. **`supersede()` で生成する新版（tombstone）の `origin`／`content.summary` の書式を規定する**：適用された解決規則（例：「origin優先：user_explicit が agent_inferred に優先」）を summary に機械的に埋め込むテンプレートを定め、監査者がルールを再適用しなくても理由を読めるようにする。
5. **横断的関心事（「認証」等）向けに、閉包とは独立したエンティティタグを経路Aの候補抽出に持たせる**（scope一致に加えて、見出し中の共通キーワード/エンティティのLSH一致だけでも候補化できるようにする。§12 は既に「見出しのエンティティ一致」を経路Aの条件に含めているので、scope不一致でもこの条件だけで拾えるよう明文化する）。

## 6. 判定

**動かない** — §20.4 入口2・§12 配線・§14 無条件昇格の個々の機構は動作するが、それらが接続される前段（分身Bのような agent_inferred・単発・command副作用ありの決定を候補キューに乗せる規則）が定義されておらず、シナリオが検証しようとした当のケース（A/B対立の検出とKoboへの副作用の点検）を確実に捕まえられない。
