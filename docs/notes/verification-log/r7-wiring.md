## 総括

**実装前に決めるべきものが残っている。** §20.8 は U4（深い睡眠のスケーリング）・U5（索引の耐久性・クラッシュ整合）を「2026-07-26 対処（未検証）。残るのはパラメータの具体値」と記録しているが、本チェックはこの評価が時期尚早であることを示す構造的な欠落を複数見つけた。

1. **B1（筆頭）**：U4 の設計の要——「B1〜B6 を Phase 2 に置くことで閉包シャードと両立させた」という主張——を支える唯一の具体的機構（§12「B1〜B6を呼ぶ入口」）は、実際には Phase 2 が `preference_decision` 全件を能動スキャンする処理であり、§18.1 決定1が3箇所（本文・§19・レジストリ）で繰り返し主張する「Phase 1 が判定した候補だけが Phase 2 へ行く／全件走査しない」という設計と正面から矛盾する。**Phase 1 が実際にこの絞り込みを行う規則はどこにも存在しない。** これは「実装前に決めるべきもの」の核心（U4 が対処済みとする writer 粒度と入出力の設計そのもの）に対する構造的な指摘であり、パラメータの具体値の話ではない。
2. **B2**：Phase 1 の並行化の安全性の唯一の根拠として挙げられる I9 は、実際には新規エントリの `scope` 値を制約するだけで、「どの閉包の writer がどの閉包へ書き込んでよいか」というアクセス制御を規定していない。安全性は（もしあるとすれば）I9 ではなく、書かれていない設計上の慣行に依存している。
3. **C4**：U5（索引の耐久性・クラッシュ整合）が要求する冪等性の唯一の論拠（`propose()` 経由の候補キュー重複検出）は、参照先に実在しない規則を根拠にしている。冪等性は現状、宣言だけで未保証。
4. **D1**：シャード台帳・カバレッジカーソルの生成・維持は、未着手のまま残る U8（閉包レジストリのライフサイクル）に暗黙に依存しており、この依存は §20.8 のどこにも記録されていない。

これらは §20.8 の軸分類（(c) 保存層・書き込み経路の形を決めるもの＝後から直すと作り直しを要する）に該当する性質の欠落であり、**「蓄積開始前に決める」対象として U4／U5 が再びオープンとして扱われるべきである。** 少なくとも、B1・B2・C4・D1 の4点が解消されるまで「残るのはパラメータの具体値」という記述は正確ではない。

副次的な指摘（B3・B4・B5・C1〜C3・D2・D3）は、いずれも「規則を書いて配線を忘れる」という本プロトコルが繰り返し指摘してきた同型の欠落であり、既存の是正パターン（§20.7.1 レジストリへの反映、§20.0 の7項目チェック）で個別に閉じられる。
