#### 1.1-a `sensitive: true` は誰が立てるか（未解決のまま）

ADR-0010 §5：「番頭が判断して立て、PO が訂正でき…」。`record()` の書き込み前バリデーション（§0.3.1）は I1〜I8 と `citations` 空振り検査のみを持ち、**新規記録**（`derived_from: []`）の `sensitive` を強制する規則は無い（I2 は「継承」であって初期分類ではない）。したがって Turn 1 でこの値が正しく `true` になるかどうかは、**この1点だけが依然として LLM のその場の判断に懸かっている**。ADR-0010 §5 自身が「立て忘れは起こりうる」と認める既知の限界であり、§8.5 の新設によっても変わっていない。本シナリオでは `true` が立った前提で以下を進める。

#### 1.1-b `subject[]` — R4／S9 の穴 3.3 を解消する新機構（要検証）

R4／S9（§8.5 新設前）は「第三者を表す閉包（例：`colleague:X`）が存在しない」ことを破綻として報告した（旧 3.3）。ADR-0010 §8（2026-07-26 追加）の `subject[]` はこれに対する構造的な答えである。本シナリオでは `scope: "person"`（PO 自身の横断 root、変更不可）に `subject: ["party:X", "self:po"]` を添えることで、**「どこで見えるか」（scope）と「誰についてか」（subject）を分離**できる。B4（§12、下記チェック9）や F4（§7、下記チェック5）がこれを鍵に使う。

**ただし新たな未定義が生じる**：`subject[]` は開いた識別子（列挙にしない、ADR-0010 §8）であり、書き込み時に Banto が `"party:X"` という識別子をどう選ぶかの正規化規則が無い。会話上の表記は「Xさん」であり、`subject` に入る識別子（`"party:X"`）とは文字列として一致しない。この2つを結びつける手段は §8.5.1 の `entity_index` またはエイリアス表 (`alias()`) だが、**「Xさん」→「party:X」の対応を誰がいつ登録するかは仕様のどこにも書かれていない**。`entity_index` の供給元表（§8.5.1）には `subject[]` の値自体（＝正規化後の識別子そのもの）は入るが、そこへ到達する前の自然言語表記からの変換規則は無い。これは Stage 0（§8.5.1）が Turn 3・Turn 4 で正しく解決できるかに直接効く（下記 1.4・1.5、チェック3）。

#### 1.1-c 点火（§20.4）は起きるか

`origin: user_explicit` の episode が `record()` されたので、Steward Driver は同期的に `collision_candidates()` を呼ぶ（§20.4 点火）。既存の意味記憶に X の記述は無いため候補ゼロ → §12 の定義により**「新規の言明」**（訂正ではない）。ピン留め・緊急伝播・最優先枠のいずれにも乗らず、通常の睡眠経路へ入る。

#### s_admit 計算（B について。C はこの時点では未生成）

**Stage 2（§8.5.3）**：`mode == brief` のため F5 は**除外ゲートとしては発火しない**（§8.5.7「brief：除外せず、解像度で絞る」）。F4 は `addressee = worker:coord-07` が `subject[]`（`party:X`, `self:po`）に含まれないため発火しない（該当なし）。よって B は Stage 3 へ進む。

**Stage 3（§8.5.5、重み・値はすべて推測）**：

| 項 | 値 | 根拠 |
|---|---|---|
| `rel_norm`（w1=0.4） | **0.05**（推測） | `query`/`raw_utterance` に「X」も「認証」に関連する内容語も B の headline と重ならない。A1（FTS）不一致、A2（エンティティ）は query に X の識別子が無いため不一致、A4（系譜近傍）は無関係、A5（最近性）は他の直近エントリに劣後。候補には残るが下位 |
| 文脈一致（w2=0.2） | **0.3**（推測） | `scope: person`（root）と実行文脈 `proj:banto` は祖先関係だが同一ではない |
| 確信度（w3=0.2） | **0.7**（推測） | 単一出典・`user_explicit`・経過5日、経過時間ペナルティは軽微 |
| 顕著性（w4=0.2） | **0.75**（推測） | B の salience 値をそのまま使用 |

```
s_admit(B, Turn2) = 0.4×0.05 + 0.2×0.3 + 0.2×0.7 + 0.2×0.75
                   = 0.02 + 0.06 + 0.14 + 0.15 = 0.37
```

`brief` の絶対下限は `θ_ws`（§8.5.7 表）＝ 0.6（推測）。**0.37 < 0.6 → 入場しない。** `brief` は見出し帯を使わないため、落選＝非注入。

**結論（Turn2）**：この instantiation では、B は `assemble_brief()` の候補生成では**関連度不足で入場しない**。F5／F4 のゲートが「せき止めた」のではなく、**クエリが X に触れていないために最初から候補として浮上しない**。したがって Turn 2 のブリーフには X の情報が一切載らない——ただし、これは安全機構が機能した結果ではなく、**Banto 自身もこのターンで X の割当方針を思い出していない、という副作用の裏返り**である（詳細は §4-1）。

**PO に見えるもの**：Banto の通常の発注確認（「Y さんに認証まわりのリファクタ計画を依頼しました」等）。X の名は出ない。**職人に届くもの**：`brief` に X の名も制約も一切含まれない、通常のタスク発注文のみ。

### 1.5 ターン3 — 自律ループの提案（2026-10-10、`timer` 起床）

`timer` が深い睡眠を起こし、その後 Steward Driver が分身を起こして PO へ自発的な提案を返す。この分身のセッションは PO の発話に起因しない（`session_origin: timer`）。

```
req = {
  query:          "Q4のタスク配分状況の要約と提案"（driver生成、推測）,
  raw_utterance:  null または ""                     ← ★1.5-a：このターンにはPO発話が無い
  closure_ctx:    "proj:banto",
  mode:           "context",
  session_origin: "timer",
  addressee:      null,
  ...
}
```

#### 1.5-a `raw_utterance` が定義できない（未定義）

§8.5.0 は `raw_utterance` を「直近の生発話のみ」と定義するが、**PO が発話していないターン（番頭が自発的に話しかける側）に何を渡すかは書かれていない**。null／空文字／直前セッションの最後の発話、のいずれかが妥当な解釈候補だが選択規則が無い。本シナリオでは後続の判定（下記チェック4・8）に影響しないため実害は無いが、**引数シグネチャが「PO が話し、番頭が応じる」形を暗黙の前提にしている**ことを示す一例である。

#### チェック4・8：F5・横断ファンアウトはこのセッションで発火するか

**F5（§8.5.3・§8.5.7）**：`mode == context` の行の条件は「`session_origin == po_message` かつ `mentions` に該当主体」。`session_origin == timer` であるため**AND の第一項がすでに偽**。`mentions` の中身（`raw_utterance` が未定義であることも含め）を問うまでもなく、**B・C は Stage 2 で確実に除外される。** これは「たまたま今回のクエリが弱かったから」ではなく、**構造的に保証された除外**である——AND 条件の1項が `session_origin` という driver 側の機械的事実である以上、`timer` 起床のセッションで F5 を通過する経路は存在しない。

**横断ファンアウト（§8.5.4）**：発火条件は3つの AND（closure leafでない／Stage0が閉包を特定していない／`session_origin == po_message` かつ `mode != brief`）。ここでも `session_origin == timer` が3つ目の条件を満たさないため**発火しない**。§8.5.4 の本文が明言するとおり——「`session_origin` の条件を外すと、自律ループでも横断が発火する」——**この一致は設計どおりであり、`timer` 由来のセッションで子孫方向の横断ファンアウトが起きないことは AND 条件の構造それ自体によって保証されている。**

**結論（このセッションで X の機微情報は滲むか）**：**滲まない。** B・C は候補にすら入らない。

#### 1.5-b しかし——安全と引き換えに、方針も適用されない

ここが本ラウンドの中心的な発見である。§7-F5 は「`sensitive` の記憶を番頭から自発的に持ち出さない」ことを目的に設計されている。本シナリオはその設計が**意図どおりに機能している**ことを示す——だが同じ機構が、**Banto がこの自律提案を作る際に「Xさんには長期タスクを振らない」という PO の既知の方針を一切参照できない**ことも同時に保証してしまう。B・C が Stage 2 で機械的に除外される以上、Banto の提案生成 LLM 呼び出しはこの制約の存在をそもそも知らない。

したがって、Turn 3 の自律提案が実際に X へ長期タスクを提案するかどうかは通常の稼働状況等の判断材料に依存し**本シナリオからは決定できない**が、**「X への配慮が構造的に一切適用されない」ことは確定的に言える**。これは秘匿性（confidentiality）の失敗ではなく、**PO が明示的に述べた方針の遵守（compliance）の失敗**であり、§0.7 の失敗順位には直接対応する項目が無い新しい種類の失敗である（詳細は §4-2）。

**PO に見えるもの**：Banto からの提案メッセージ（例：「Q4の配属案：…」）。X への配慮の有無を PO が読み取れる情報は提案文の中には無い（Banto 自身が配慮していないため）。**職人に届くもの**：このターンでは職人発注は行われていない（提案段階）。

#### チェック3：「Xさん」は `mentions` に入るか

`mentions = resolve_entities(raw_utterance)`（§8.5.1）。「Xさん」という表記が `party:X` に解決されるには、`entity_index` に「Xさん」という**表記**から `party:X` への対応が登録されていなければならない。1.1-b で指摘したとおり、この対応をいつ・誰が作るかは未定義である。ただし本シナリオでは Turn 1 の `content.headline`（"Xさんに長期タスクを振らない方針を検討"）が `entity_index` の供給元（§8.5.1「`content.headline` から抽出した固有名詞・識別子」）に含まれ、その抽出対象に「Xさん」という**トークンそのもの**が含まれていれば、Turn 4 の「Xさん」という同一表記との文字列一致で解決できる。**本シナリオは Turn 1 と Turn 4 で PO が同一の表記（「Xさん」）を使っているため、この経路はおそらく機能する（条件付き）。** ただし表記が変わった場合（「あの同僚」「Xの件」等）は一致せず、これは §4-3 の穴として別途扱う。

以上を前提に `mentions ⊇ {party:X}` として先へ進める。

#### F5（Turn4）：`session_origin == po_message` かつ `mentions` に `party:X` を含む → **両条件成立、除外されない**

#### 「訂正」の判定と点火（§20.4・§12）

`collision_candidates()`（経路A：同一閉包 `person` ＋ エンティティ一致 `party:X`）を同期的に呼ぶ。B がヒット（候補1件以上）→ §12 の定義により**「訂正」と機械的に判定される**。C も `entity_index` 上は `party:X` にひも付くため、経路Aの候補ペア抽出そのものにも直接引っかかりうる（§12 経路A、詳細は §2 の発火チェック）。

- **最優先枠**（§20.3）へ即時キューイング。
- **`pin()`** が同ターンのうちに呼ばれる（§20.4）。対象は**この訂正エピソード自身**（§7「このセッション中のユーザーの訂正」）。
- Banto は `supersede()` を呼び、B の新版（tombstone）を作る：

```
id:              mem-01K6C4XW7QZP2M9NRTF5BJDLV8      (D = Bのversion 2)
kind:            semantic
fact_type:       preference_decision
content:         {
  headline: "Xさんの割当方針は終了（PO指示により撤回）",
  summary:  "2026-10-14 PO指示（『Xさんの件、忘れて』）により本方針の追跡を終了。",
  full:     "「Xさんの件、忘れて」（PO発言、2026-10-14）"
}
created_at:      2026-10-14T14:20:47Z
valid_from:      2026-10-14T14:20:47Z
valid_until:     null
origin:          user_explicit
sensitive:       true                                 ← 継承（誰も明示的に落としていないため既定どおり）
session_id:      sess-po-20261014-0058
context:         { scope: "person" }
derived_from:    [mem-01K5R2H8YD4NWA9TQXF3M7VCZP]      ← Bのversion 1を指す

superseded_by:   null

```

B（v1）は事後的に `superseded_by: mem-01K6C4XW7QZP2M9NRTF5BJDLV8`、`valid_until: 2026-10-14T14:20:47Z` を持つ（ADR-0010 §3「旧版のvalid_untilを新版のvalid_fromで埋める」）。**origin優先の強制**（§0.3・ADR-0010 §1.3）：v1・D とも `origin: user_explicit` のため同一origin内の最新性勝負として `supersede()` は問題なく成立する（実行層で拒否されない）。

#### 経路B — C への波及（§12・§20.4）

「あるエントリが tombstone された（＝B の新版 D が tombstone:true で作られた）」条件により、`dependents(mem-01K5R2H8YD4NWA9TQXF3M7VCZP, depth=2)` が走る。C の `derived_from` はまさにこの ID を指しているため**1ホップで検出される**（既定2ホップの範囲内）。C は再検証キューへ積まれる。

**消化**：訂正由来のため「即時：分身を起こして裁かせる」（§20.4）——本ターン中に処理される想定。ただし実際に C の内容（「配属判断では対象者の異動意向・不満を確認してから割り振る」という一般化された運用ルール）を tombstone するかどうかは**この場に召喚された分身の LLM 判断に委ねられる**。C はもはや X 個人を名指ししない一般則であるため、「Xさんの件を忘れて」という指示が C 自体の妥当性を否定するとは限らない——分身が「これは一般則として残す」と判断すれば、C は tombstone されないまま残り、`subject[]` に `party:X` を含んだまま生き続ける（これは仕様上正しい振る舞いでも誤った振る舞いでもなく、**判定基準がどこにも書かれていない**——再検証キューの「消化」は「まだ正しいかを判断させる」としか定めていない）。

**経路A の直接ヒットとの多重化**：`collision_candidates()` の一次フィルタ（同一閉包＋エンティティ一致）は、C 自身の `entity_index` エントリ（`subject[]` 経由）にも直接ヒットしうる。これは経路B（系譜）とは独立した第二の到達経路であり、**両方が同じ結論（C を再検証対象にする）に収束する**。ただしこれは `subject[]` という**比較的新しい機構**（ADR-0010 §8）が entity_index の供給元になっているために生じる副次的効果であり、`subject[]` が無かった旧設計（R4／S9 当時）では経路Aは C に届かなかった（ADR-0010 自身が「語彙が一つも重ならない」と認めている）。**したがって「経路B が唯一の頼みの綱」という R4／S9 時点の認識は、`subject[]` の導入により部分的に緩和されている。**

**PO に見えるもの**：Banto の確認応答（「かしこまりました。Xさんに関する記録は更新します」等）。**版系譜（B v1→D、C の再検証状態）を PO が実際に確認する手段は Memory 面のみだが、これは §20.7.1 で「⚠ 未実装」と明記されている面である。** PO はこのターンの会話上の応答以上の監査情報を得られない。**職人に届くもの**：このターンでは職人発注は無い。ただし Turn 2 で完了した職人成果物（もし存在すれば）が `derived_from` に B(v1) を含んでいた場合、§20.4「あるエントリが supersede された → derived_from にそれを含むエントリ」条件でその成果物記録も再検証キューへ積まれるはずだが、**1.4 の分析のとおり Turn 2 のブリーフに B は一度も注入されなかったため、`derived_from` の自動付記（§0.3.1）の対象にすらなっていない。したがって Turn 2 の成果物は再検証キューに載らない**——これは「Turn 2 で X の情報が使われなかったので再検証の必要が無い」という意味では一貫しているが、逆に言えば **Turn 2 で Banto が（本来配慮すべきだった）X の状況を無視して行った判断があったとしても、その判断は `derived_from` に何のリンクも持たないため、Turn 4 の訂正によって自動的に見直される対象には決してならない**。

#### 「忘れて」は物理削除ではない

PO の口語的な「忘れて」は削除を連想させるが、実際に起きるのは**新版の作成（tombstone: true）**であり、旧版・新版とも版系譜としてストアに残り続ける（§2 確定論点4・§25「原則削除しない」）。PO が真に期待しているのが「二度と誰にも見えないこと」だとすれば、これは静かな期待値のズレである——番頭側からこれを明示的に PO へ伝え返す規則は、プロトコル層（§23）にも自己モデル（§22）にも存在しない。

## 3. 動くこと

- **I2（`sensitive`継承）・I7（`subject[]`和集合継承）が全段で機能する**（B・C・D）。R4／S9当時は`subject[]`が存在せず検証不能だったが、本ラウンドで実際に3世代にわたり継承が機械的に維持されることを確認した。
- **`origin`継承の合成規則**（§0.3.0）がB・Cの`origin: user_explicit`を確定させる。R4／S9で「未定義」としていた点が解消されている。
- **F5・横断ファンアウトのTurn3での不発火は構造的に保証されている**（AND条件の1項が`session_origin`という機械的事実であるため、確率的な要素が介在しない）。§0.5原理2（LLMの判断力に依存させない）が字義どおり満たされている。
- **経路B（`dependents()`の系譜逆引き）が、語彙の一致しない2段目の派生（C）まで機械的に届く**。既定2ホップの範囲内であれば、抽象化がどれだけ進んでも `derived_from` を辿って再検証キューに載せられることを具体的に確認した。
- **`subject[]`（ADR-0010 §8）が経路A（エンティティ一致ベースの矛盾検出）の到達範囲を副次的に広げている**。`entity_index`の供給元に`subject[]`が含まれるため、語彙を失った派生（C）でも`subject[]`を介して直接ヒットしうる。これは§12執筆時点では想定されていなかった、機構間の建設的な相互作用である。
- **origin優先の実行層強制**（§0.3・ADR-0010 §1.3）：Turn4の`supersede()`は同一origin（user_explicit）内の最新性勝負として問題なく成立する。
- **`brief`モードでのF5・F4の設計は整合している**（§8.5.7の表と§0.3.1・§9の記述に矛盾が無い）。R4／S9当時に指摘されていた「除外リストとの矛盾」は解消済みのままである。

## 4. 破綻・穴

### 4-1. `assemble_brief()`の候補パイプラインと`build_context()`のワーキングセットは別状態であり、`task`引数の権限縮小トリガーは構造的に発火し得ない

- (a) いつ起きるか：Turn 2、`assemble_brief(task, budget)`の`task`引数生成時
- (b) 何が起きるか：§0.3.1の権限縮小切り出しは「直近ターンで`sensitive`エントリがワーキングセットに滞在していたか」を条件にする。しかし§8.5.7が明示するとおり、`mode:brief`の候補生成と`mode:context`のワーキングセットは別のパイプライン・別の状態である。F5の「言及したターン」条件（`mentions`が`raw_utterance`由来）がTurn2のPO発話（Xに触れない）で満たされない以上、BはBanto自身の`context`ワーキングセットに一度も入らない。したがって権限縮小トリガーの発火条件自体が真になり得ない。**R4／S9で指摘した穴が、§8.5の形式化によってむしろ構造的に確定した。**
- (c) 節番号：§0.3.1（`task`引数の権限縮小切り出し）／§8.5.7（mode別の差の表）／§7-F5
- (d) Substrate か Policy/Loop か：**Policy**（`assemble_brief()`と`build_context()`の状態分離という設計そのものに起因する）

### 4-2. F5が「自発的に持ち出さない」を実現する副作用として、「自発的に配慮する（方針を遵守する）」も同時に不可能にする

- (a) いつ起きるか：Turn 2（PO発話がXに触れない場合）・Turn 3（自律ループ）
- (b) 何が起きるか：F5の`mentions`判定はターン単位（当該ターンの`raw_utterance`のみ）である。PO が過去のセッションでXについて明言していても、**現在のターンでXに言及しない限り、以降のどのセッション・どのターンでもBanto自身はB・Cを参照できない**。結果、Xへの配慮が必要な判断（Turn2の割当、Turn3の自律提案）で、Banto は自分が知っているはずの制約を一切考慮せずに判断する。これは秘匿性の失敗ではなく**PO の既知の意向の不遵守**であり、§0.7の失敗順位のどの項目にも明示的に対応しない新種の失敗である（強いて言えば1位「訂正が消える」に類似した性質——ただし§12の「訂正」の定義には該当しないため、ピン留め・緊急伝播の対象にもならない）。
- (c) 節番号：§7-F5／§8.5.0（`raw_utterance`のターン単位性）／§8.5.3 F5／§8.5.7
- (d) Substrate か Policy/Loop か：**Policy**（F5ゲートの粒度設計。ターン単位ではなくセッション単位・タスク単位の永続化を検討する余地がある）

### 4-3. 「Xさん」→`party:X`の正規化・エイリアス確立が誰の責務かが未定義

- (a) いつ起きるか：Turn1（`subject[]`への識別子選択時）〜Turn4（`resolve_entities(raw_utterance)`による解決時）
- (b) 何が起きるか：`subject[]`は開いた識別子（列挙にしない）であり、書き込み時にBantoが「Xさん」をどのような正規化された識別子にするかの規約が無い。本シナリオはTurn1・Turn4で表記が偶然一致する（「Xさん」）ため`content.headline`からの抽出ルールがおそらく機能するが、PO が異なる表現（「あの同僚」「Xの件」など）を使えば一致せず、`resolve_entities()`は`unresolved[]`を返す。この場合`mentions`に`party:X`が入らず、F5のTurn4での通過条件が満たされない可能性がある。さらに悪いことに、`collision_candidates()`の経路Aも同じ`entity_index`を使うため、**「訂正」の判定自体（§12）が候補ゼロで空振りし、PO の「忘れて」が新規の言明として扱われ、B・Cが一切修正されないまま残る**——§0.7の1位（訂正が消える）そのものである。
- (c) 節番号：§8.5.1（`entity_index`の供給元表・`resolve_entities`）／ADR-0010 §8（`subject[]`は開いた識別子）／§12（経路A・「訂正」の定義）
- (d) Substrate か Policy/Loop か：**Policy**（`subject[]`の値自体はSubstrateだが、正規化・エイリアス確立の運用規則はPolicy側で未設計）

### 4-4. 経路Bで再検証キューに積まれたC（2段目の派生）が実際にtombstoneされるかは、キュー消化時のLLM判断に完全に委ねられ、機械的な決着規則が無い

- (a) いつ起きるか：Turn4、C の再検証キュー消化時
- (b) 何が起きるか：`dependents()`によりCは再検証キューへ機械的に積まれる（経路Bは機能する）。しかし§20.4の「消化」は「まだ正しいかを判断させる」としか定めておらず、**Cのように語彙が既に抽象化され、必ずしもXを名指ししていない派生記憶に対して、「PO の訂正がどこまで波及すべきか」を判定する基準が無い**。Cが「Xさんの件を含む一般則」として tombstone されるか、「一般則として独立に有効」として残るかは、その場に召喚された分身の裁量次第であり、再現性・監査可能性が保証されない。
- (c) 節番号：§20.4（消化）／§12（経路B）
- (d) Substrate か Policy/Loop か：**Policy**（再検証キューの消化規則が「LLMに判断させる」以上に具体化されていない）

### 4-5. Turn2でBが一度もブリーフに注入されなかったため、Turn2の職人成果物は`derived_from`のリンクを持たず、Turn4の訂正による再検証キュー（§20.4「supersedeされたエントリのderived_from逆引き」）の対象にならない

- (a) いつ起きるか：Turn4、旧版B(v1)がsupersedeされた時点
- (b) 何が起きるか：`derived_from`の自動付記（§0.3.1）は「実際に注入された記憶ID」を機械的に渡す設計である。1.4節の分析どおりBがTurn2のブリーフに一度も注入されなかった場合、Turn2の職人成果物の記録にはB(v1)への`derived_from`リンクが存在しない。したがって、たとえその成果物が（Xへの配慮の欠如という形で）実質的にB(v1)の内容と矛盾する判断を含んでいたとしても、§20.4の逆引きによる再検証キューには一切乗らない。**「実際に使われたかどうかを機械的にトレースする」という設計の前提（derived_fromの自動付記）が、そもそも参照されなかった記憶については沈黙してしまう**構造的な限界である。
- (c) 節番号：§0.3.1（`derived_from`の自動付記）／§20.4（積む条件表）
- (d) Substrate か Policy/Loop か：**Policy**（`derived_from`のトレース範囲の限界。これを埋める代替手段——例えば「意思決定に関わったが記憶に触れなかった」ことを検知する行動観測——は§0.9の未解決事項）

### 4-6. `id`の版セマンティクスが本文内で確定していない（副次的発見）

- (a) いつ起きるか：Turn4、`supersede()`によるDの生成時
- (b) 何が起きるか：ADR-0010 §1は`id`を単一フィールドとして記述し、旧spec-memory §2は「`id` 安定・不変」としていた（この記述は本文冒頭の注記により「Substrateの反映が§12を除いて未了」であることが明言されている）。一方ADR-0010 §4は「`derived_from`は特定の版を指す（latest追随ではない）」と要求する。この2つを両立させるには、各版が固有の`id`を持つ（`id`は版ごとに新規発行、`version`は同一レコード内のカウンタではなく世代表示）という解釈が必要だが、**`superseded_by`が指す「後継版のID」が新規idを指すのか、同一idの別version行を指すのかが本文のどこにも明示されていない**。本シナリオでは前者（新規id発行）として構成したが、これは検証者の解釈であり仕様の明記ではない。
- (c) 節番号：ADR-0010 §1・§3／spec-memory §2（未反映）
- (d) Substrate か Policy/Loop か：**Substrate**（版とidの対応関係はスキーマそのものの意味論であり、後から変更できない。P3のincident案件として扱うべき）

### 4-7. 「忘れて」の口語的期待（消去）と実際の挙動（tombstone・版系譜として残存）のズレをPOへ明示的に伝え返す規則が無い

- (a) いつ起きるか：Turn4、Bantoの応答生成時
- (b) 何が起きるか：§2確定論点4・§25により物理削除は行われず、tombstone付き新版が作られ旧版も系譜として残る。PO の「忘れて」という表現は文字通りの消去を連想させるが、Bantoがこの期待値のズレを明示的に確認・説明する規則はプロトコル層（§23）にも自己モデル（§22）にも無い。第三者の機微情報という文脈では、この期待値ズレは信頼の毀損につながりうる。
- (c) 節番号：§2（確定論点4）／§25／§23（含めるものの一覧に該当項目なし）
- (d) Substrate か Policy/Loop か：**Policy**（プロトコル層の記述の不足）

## 5. 最小の修正案

1. **`task`引数の権限縮小トリガー（§0.3.1）を「直近ターンでワーキングセットに滞在していたか」から「今回の`retrieve()`呼び出し（`build_context()`・`recall()`・`assemble_brief()`のいずれでも）が`sensitive:true`のエントリを候補として拾ったか」に付け替える。** `ranked[]`が唯一「何が載ったか」を機械的に知る場所である（§8.5.0）ことを踏まえ、そこを直接の発火源にする。
2. **F5の「言及したターン」判定を、ターン単位ではなく「同一セッション内で一度でも言及があったか」に緩和する（sensitiveの滞在ゲート＝即時退場、§7-F5、とは別に、セッション内の`mentions`履歴を持たせる）。** ただし話題転換検出との整合を要検討（緩和しすぎると「自発的に持ち出さない」の意図を弱める）。少なくとも、**Xへの配慮が必要な自律提案（Turn3）を生成する前に、driverが関連する`sensitive`制約の存在有無だけを機械的にチェックし、存在すれば`po_message`セッションへのエスカレーションを促す**、という非開示・非利用の両立案を検討する。
3. **`subject[]`の識別子正規化・エイリアス確立を書き込み経路の不変条件（§0.3.0）に追加する。** 例えば「`subject[]`に人物を追加する場合、`alias()`への登録を同一トランザクションで行う」規則をI8に準じて明記する。
4. **再検証キューの消化（§20.4）に、`fact_type`・`subject[]`の一致度に応じた決着規則の指針を追加する。** 少なくとも「訂正対象の`subject[]`を全て含む派生は既定でtombstone候補とし、部分的にしか含まない一般化は明示的な確認を要する」程度の分岐を置く。
5. **`derived_from`の自動付記が届かない範囲（注入されなかった記憶が意思決定に影響した可能性）を、§0.9の行動観測方式の対象に明示的に含める。**
6. **ADR-0010・spec-memory 双方に、版と`id`の対応関係（新規id発行か同一id+version上書きか）を明記する。** Substrate層の未確定事項として最優先で解消する（P3）。
7. **プロトコル層（§23）に、削除的な表現（「忘れて」「消して」）を受けた際は tombstone・版系譜として残ることを簡潔に確認する一文を含める。**

## 6. 判定

**条件付きで動く（ただしR4／S9からの前進と後退が両方ある）。**

**前進**：`subject[]`（ADR-0010 §8）とI2/I7継承（§0.3.0）により、「第三者についての事実を置く閉包が無い」というR4／S9の中心的な破綻は構造的に解消された。経路B（系譜逆引き）は2段目の抽象化された派生（C）まで機械的に届くことを具体的に確認し、`subject[]`が経路Aの到達範囲まで副次的に広げるという、設計時に意図されていなかった良い相互作用も見つかった。Turn3の横断ファンアウト不発火・F5除外は、AND条件の構造によって確率的要素なしに保証されている。

**後退（新たに見つかった、より根の深い問題）**：F5の「PO直接対話・当該ターンでの言及」というゲート条件は、秘匿性を厳格に守る代償として、**Banto自身がその制約を認識して行動に反映することも同時に不可能にする**。これは本ラウンドで初めて明確化された種類の失敗であり、§0.7の失敗順位のどこにも位置づけられていない（秘匿の失敗でも、確信を持った誤りでも、汚染の永続化でもなく、「知っているはずのことを構造的に思い出せない」という第六の失敗モードに近い）。加えて、`assemble_brief()`の候補パイプラインと`build_context()`のワーキングセットが別状態であるという§8.5の明確化が、R4／S9で指摘した`task`引数の権限縮小トリガーの機能不全を「おそらく起きる」から「構造的に起き得ない」へと確定させた。`subject[]`識別子の正規化・エイリアス確立という新たな未定義も見つかっており、これが機能しない場合は§12の「訂正」判定自体が空振りし、§0.7の1位（訂正が消える）に直結する。
