## 重大度順の上位5件

1. **#1 — §21 の通知トリガー列挙が実態より大幅に少ない。** これは実装が読む「いつ PO に届けるか」の唯一の正典であり、少なくとも7つの通知経路がここに反映されていない。§0.7 の1位・2位（訂正の消失／確信を持って誤る）に直結する通知（self-model 再レビュー、worker 失敗の重大通知、未解決矛盾のダイジェスト等）が、実装者が§21だけを見た場合に漏れる。
2. **#2 — I1〜I6 の実行層強制が `record()` 以外に書かれていない。** §0.3.0 は「経路ごとに書くのをやめ、不変条件として1箇所に置く」ことで trust laundering 等の再発を防ぐために作られた表だが、その「1箇所」から `propose()`・`supersede()`・蒸留層への配線がされておらず、同じ形の欠陥（R4/S10）が再発する構造のまま残っている。
3. **#4 — `subject[]` が Substrate に確定済みなのに本文で一度も参照されない。** Substrate は「記憶の蓄積開始時点」で凍結するため、書き込み側の運用ルールを後から足せない。ADR-0010 が明示した3つの用途（引き継ぎ・機微情報の主体切り分け・ドメイン間プライバシー）が現状すべて機能しない。
4. **#3 — §20.5-4／§20.5-6 の参照ズレが3箇所で発生。** ズレは軽微に見えるが、`§20.8` という「既知の穴を集約する場所」自身に混入しており、レジストリが依拠する引用の信頼性を損なう。
5. **#5 — `memory_signal`・`timer`・`model_migration` の基準優先度が §20.3 に無いのに §20.7.1 が優先度を断定している。** 優先度は「決定的に計算する」ことが §20.0/§20.3 の要求だが、この3起床源については計算の根拠がなく、レジストリの値は事実上ハードコードされた推測になっている。

## レジストリ自体の評価

**§20.7.1 は「規則を書いて配線を忘れる」という当初の欠陥のうち、① 発火・⑤ 入力・② 処理・⑥ 出力先の4欄については検出力を持つ。** 実際、⑤ 欄に ⚠ が明示された「候補生成」の入力未定義は、表がなければ埋没していたはずの穴である。この点は設計として機能している。

**一方、優先度・通知・提示面の3欄は「本文のどこかに書いてあることの要約」として使われており、その本文側の裏付けが弱いまま数値・値が埋められているケースが複数見つかった**（発見#1・#5・#7・#9・#10）。これは表の設計自体の欠陥というより、**運用（埋める際の検証）が甘い**ことに起因するが、表の列構成にも改善の余地がある。

### 改善案

1. **「根拠節番号」列を独立させる。** 現状「機構」列の括弧内節番号（例：`(§20.4)`）が唯一の出典表示だが、これは機構の"定義"がある節を指すだけで、優先度・通知・提示面の値の**出典**を個別に示していない。発見#3（§20.5-4/6 のズレ）は、優先度・通知の値ごとに「この値はどの一文から来たか」を明示させれば機械的に検出できた。列を「① 発火（節番号）」のように、各欄に個別の出典节番号を要求する形に変える。
2. **§21・§20.3・§20.5 を「この表からの導出」と位置づけるなら、逆方向の整合チェックを機構表自体に組み込む。** 現状 P3 は「食い違ったら本表が優先」とだけ定めており、食い違いの**検出**を誰がいつ行うかが無い（本検査のような静的チェックが無ければ気づかれない）。§20.7.1 の末尾に「§21/§20.3/§20.5 の対応する記述と突き合わせたか」というセルフチェック欄、または本検査（§2.4）を毎回この表に対して機械的に走らせる運用を明記する。
3. **Substrate フィールド×書き込み経路のマトリクスを別枠で持つ。** `subject[]` の欠落（発見#4）は §20.7.1 の「機構」単位の行立てでは拾えない構造の穴だった——フィールドそのものが本文のどこにも出現しない場合、機構表に行を足す動機自体が生まれない。ADR-0010 が定義する全フィールド（`sensitive`／`authored_by`／`subject[]`／`external_ref`／`scope`）×「誰が書くか・誰が読むか」の表を §0.3.0 に隣接する形で追加し、空欄を可視化する。
4. **起床源×優先度のマトリクスを完成させる。** §20.2 の6起床源と §20.3 の優先度表を1つの表に統合し、全起床源に基準優先度が埋まっていることを構造的に強制する（発見#5）。現状は2つの独立した表になっており、片方の更新がもう片方に伝播する保証がない。
