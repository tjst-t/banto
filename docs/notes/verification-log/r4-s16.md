### 段階1：プロジェクトの引き継ぎ（proj:banto → Y）

PO が「`proj:banto` を Y に引き継ぐ」と発話する。

**driver（§20）の挙動**：
- 起床源は `po_message`（§20.2）。優先度は最高（§20.3）。
- Steward Driver は既存の生きた分身のうち同一閉包(`proj:banto`)・同一ゴールのものがあればそれに渡し、無ければ fork する（§21）。
- この発話自体が `origin: user_explicit` の episode として `record()` されるので、`collision_candidates()` が同期的に走る（§20.4 点火）。既存の `proj:banto` の意味記憶（例：オーナーシップに関する state_fact があれば）と衝突判定にかかる可能性はあるが、**「プロジェクトを引き継ぐ」という操作そのものに対応する driver のルーチンは存在しない**。§20.2 の6起床源、§20.5 の6項目の自己内省チェックリストのどこにも「引き継ぎ」「他インスタンスへの移譲」に対応する項目がない。
- 結果：PO の発話は普通の episode として記録されるだけで、**「これから proj:banto scope のエントリを外部へ渡す準備をする」という状態遷移を driver は認識しない。** 以降の作業（何を渡すか選ぶ、パッケージを作る）は、番頭のセッションが自由記述のタスクとしてアドホックに行うしかない。

**メモリ側の操作**：§0.3 の公開API（`build_context` / `assemble_brief` / `record` / `propose` / `supersede` / `recall` / `pin` / `unpin` / `compact` / `consolidate` / `dependents` / `changes_since` / `collision_candidates`）を全て見ても、**「scope 配下のエントリ集合を機械的に取り出す」操作が存在しない**。`recall(query)` は「能動的検索（明示リコール用）」であり、意味的類似度検索であって「scope が `proj:banto` およびその子孫であるものを漏れなく列挙する」網羅的スキャンではない。

ここで既に、要求（「proj:banto 配下の記憶を Y へ渡したい」）に応える一次操作が **存在しない** ことが確定する。

### 段階2：機微情報の混在（何を渡すかの選別）

かりに番頭が手作業で「`context.scope == "proj:banto"` （またはその祖先を除く子孫閉包）のエントリを列挙する」スクリプト的操作を即興で行ったとする（API には無いので、これは spec に基づかない振る舞い）。

対象になるもの：E2（procedural, proj:banto）、E3（sensitive, proj:banto）、E5（sensitive, proj:banto）
対象にならないもの：E1（person）、E4（person）

**破綻1（scope フィルタだけでは切り分けられない）**：
- E5 は `scope: proj:banto` なので機械的には「渡す」側に入るが、中身は PO・Y間の人間関係の緩衝方針であり、Y へ見せてよい情報ではない。`sensitive: true` フラグは立っているので「機微である」ことは検出できる——しかし `sensitive: true` は「渡すな」を意味しない。ADR-0010 §5 が定める効果は「職人への指示文に理由を含めない／番頭から自発的に持ち出さない／自動での可視範囲拡大の対象外」であり、**「第三者インスタンスへの引き継ぎパッケージから除外する」という効果は定義されていない**。`sensitive` はこのシナリオのために設計された制御ではなく、援用できるだけである。
- E3 も同様に `proj:banto` かつ `sensitive: true`。Z について「Yに見せてよいか」は本来 proj:banto の運用データとして正当にYへ引き継がれるべき情報にも読めるが、`sensitive` フラグは person/proj の区別と直交しており、**渡す・渡さないの判断材料として使うルールが仕様のどこにもない**。

**破綻2（E2 の derived_from が person scope を指す）**：
- E2（proj:banto, procedural）は E1（person）を `derived_from` に持つ。E2 を Y へ渡すと、E2 の出典リンクは Y の Banto インスタンスには存在しない ID（E1）を指す。これは §4「宙ぶらりんノードの防止」が想定する事象（同一ストア内で出典が tombstone/supersede される場合）とは異なる——**別インスタンスへ渡した瞬間に生まれる「よそのストアに実在するが渡されなかった」宙ぶらりんであり、§4 はこの種類を扱う規定を持たない**（後述§3参照）。
- SKILL.md ファイル自体（`skills/commit-convention/v3/SKILL.md`）はテキストファイルなので中身をコピーすれば Y は使えるが、**「なぜこの手順が存在するか」の由来（PO個人の流儀）はエントリの `derived_from` を辿らないと分からず、そのリンク先は渡されない**。

**破綻3（content 自由記述への漏出はスコープフィルタでは防げない）**：
- `scope` はエントリ単位のタグであって、`content.full` / `content.summary` の文字列そのものを検査する機構ではない。E5.content.summary は既に "根拠は mem-01JC7Y4RELJUDGE01（person scope）" という形で person-scope の存在を平文で言及している。ID自体は Y には無意味な文字列だが、`headline`（"Yへのフィードバックは番頭が言い換えて伝える"）だけで実質的な内容は伝わってしまっており、**scope による切り分けは、内容がすでに scope を跨いで書かれてしまっている場合には無力**。§0.3.1 の「`sensitive: true` は headline のみ職人に見せる」という規律は `assemble_brief()`（職人向け発注）専用であり、**「Y の Banto インスタンスへの一括引き渡し」という別の出力経路には適用されない**（そのような経路が定義されていない以上、適用しようがない）。

### 段階3：撤退（半年後、2027-01-26 頃）

PO が Banto の利用をやめ、記憶を全部手元に残したいと発話する。

**driver の挙動**：段階1と同型。`po_message` 最高優先度で処理されるが、**「全記憶のエクスポート」に対応する API・wake source・自己内省項目のいずれも存在しない**。

**メモリ側**：§0.3 の12操作のどれにも「ストア全体をダンプする」操作がない。`recall()` を強引に流用しても、それは類似度検索であって全件列挙の意味論を持たず、tombstone 済みエントリ・アーカイブ層・`sensitive` エントリを含めるかどうかの挙動が未定義（§7 の候補生成規則は「注入」のためのフィルタであり「取り出し」のためのものではない）。

**エクスポートは spec 自身が「無い」と認めている**：`docs/notes/agent-primary-inversion.md` §0（R3 の記述、および `spec-memory` の元になった検証記録）に明記：

> 「**エクスポート機構が存在しない**（S11）。撤退可能性。小規模なうちに一度通しておかないと、100万件で初めて実行することになる。」

これは本シナリオが検証しようとしている論点そのものを、設計側が既に「未対処」の穴として自認している箇所である。

**物理削除の権限も自己矛盾している**：
- `docs/spec/memory.md` §2 確定論点4：「物理削除はユーザーの明示的要求と法規制対応のみ（§26）」——**PO の明示的要求だけで物理削除が可能と読める**。
- 一方 §25「ユーザーによる記憶の統制」：「**法規制対応** — GDPR 等の明示的削除要件は §2 の『原則削除しない』方針の**唯一の例外**とし、物理削除の正規経路とする」——ここでは GDPR 等の法規制対応だけが唯一の例外とされ、**「PO自身の明示的要求」は物理削除の根拠として書かれていない**。
- さらに §2 が参照する「§26」は本文中に**存在しない**（本ドキュメント冒頭の未確定事項に「存在しない『§26』への参照」として自ら明記済み）。
- 結果：**撤退時に「Banto 側のコピーを物理削除してほしい」という PO の要求に応える規定が、2箇所で矛盾したまま放置されている。** 片方を採れば PO の要求で消せる、もう片方を採れば消せない（GDPR相当の法規制がなければ tombstone + アーカイブ降格に留まる）。

## 2. 動くこと

- **版管理・不変性（§3）自体は健全**：エントリが immutable であることや、tombstone を新版として作る規律（ADR-0010 §3）は、渡す/渡さないの判定に使う分には矛盾を起こさない。少なくとも「どの版が最新か」は機械的に解決できる。
- **`sensitive: true` の継承（§0.3.1 rule 4）は機能する**：E4→E5 のように、機微エントリを出典に持つ派生エントリは自動的に `sensitive: true` を継承する。これにより **「機微かもしれない」候補の洗い出し自体（レビュー対象の抽出）は機械的に行える**——ただし後述の通り、それをもって「渡す／渡さない」を決められるわけではない。
- **`origin` は誰が言ったかの手がかりとして機能する**：`user_explicit` のエントリ（E1, E4）は「PO本人の言明」として識別でき、`agent_inferred`（E2, E3, E5）と機械的に区別できる。これは「PO個人の判断由来か、番頭の推論由来か」の一次分類には使える。
- **`authored_by`（ADR-0010 §7）はモデル世代の履歴情報としては移送後も意味を保つ**：値は「どのモデル/プロンプト版が書いたか」であり、instance に紐づかない。Y のインスタンスが将来 `model_migration` 起床源（§20.2）で再評価バッチを走らせる際、値自体は解釈可能（ただし後述の通り、そのバッチを引き起こす仕組みは移譲イベントに反応しない）。
- **`external_ref`（ADR-0010 §4）はシステム非依存の汎用参照なので、SKILL.md ファイルの参照はそのままコピーして持ち出せる**：`{system: "skill", id: "skills/commit-convention/v3/SKILL.md"}` という形式自体は instance をまたいでも意味を保つ（ファイルそのものをコピーする前提であれば）。

## 3. 破綻・穴

### (1) 一括取り出し（エクスポート）の手段が存在しない
- **段階**：1（引き継ぎ準備）／3（撤退）
- **何が起きるか**：`docs/spec/memory.md` §0.3 の公開API 12個のいずれも、scope 指定・全件指定を問わずストアの中身をシリアライズして取り出す操作を提供しない。`recall()` は明示リコール用の類似度検索であり網羅的スキャンではない。
- **節番号**：`spec-memory` §0.3（API一覧）。`agent-primary-inversion.md` §0（R3 記述、「エクスポート機構が存在しない（S11）」との自認）。
- **Substrate か Policy/Loop か**：**Policy/Loop**（API・driver 側の欠落。Substrate のスキーマ自体はエントリを持ち出す/持ち出さないを決める情報は一応持っている＝§4参照）。

### (2) scope フィルタだけでは機械的に切り分けられない（cross-scope 派生）
- **段階**：2
- **何が起きるか**：E2（proj:banto）が E1（person）を `derived_from` に持ち、E5（proj:banto, sensitive）が E4（person, sensitive）を `derived_from` に持つ。`context.scope` だけで「渡す集合」を切ると、渡す集合の中に person scope への出典参照が紛れ込む。
- **節番号**：ADR-0010 §2（`scope` は閉包識別子。「注入可否」を決める規定であり「持ち出し可否」を決める規定ではない）／`spec-memory` §4（出典と信頼境界。宙ぶらりんの規定は同一ストア内の出典消失のみを扱う）
- **Substrate か Policy/Loop か**：**Substrate**（`derived_from` が scope を跨ぐこと自体は Substrate 上正当な状態であり、スキーマはこの跨ぎを禁止も検知もしない）。切り分けロジックの不在は Policy 側の欠落。

### (3) `sensitive: true` は「渡すな」を意味しない
- **段階**：2
- **何が起きるか**：E3・E5 は `proj:banto` scope かつ `sensitive: true`。フラグが立っていることは検出できるが、ADR-0010 §5 が定める効果（職人への理由非開示・自発的言及禁止・自動可視範囲拡大の対象外）は「引き継ぎパッケージからの除外」を含まない。フラグは**渡す/渡さないの二値判定基準として設計されていない**。
- **節番号**：ADR-0010 §5／`spec-memory` §7-4（`sensitive` の候補集合ゲート、これも「注入」用の制御であって「持ち出し」用ではない）
- **Substrate か Policy/Loop か**：**Policy**（フラグ自体は Substrate にあるが、その解釈規則＝「引き継ぎでどう使うか」が Policy 側に一切定義されていない）

### (4) `content` の自由記述への漏出は scope 分離で防げない
- **段階**：2
- **何が起きるか**：E5 の `content.headline` / `summary` は、proj:banto scope のエントリでありながら PO-Y 間の関係性という person scope 由来の情報を平文で表現してしまっている。scope はエントリのメタデータタグであり、`content` 文字列の中身を検査・サニタイズする機構ではない。§0.3.1 の headline-only 絞り込みは `assemble_brief()`（職人向け発注）専用の規律であり、引き継ぎパッケージ生成には適用されない（そのような生成経路自体が存在しないため）。
- **節番号**：`spec-memory` §0.3.1（`assemble_brief()` のみを対象とする）／§9（解像度階層、注入レンダリングの文脈でのみ規定）
- **Substrate か Policy/Loop か**：**Policy**（構造化された絞り込みが特定の1経路にしか実装されていないことに起因）

### (5) derived_from の宙ぶらりんはインスタンス跨ぎを想定していない
- **段階**：2/3
- **何が起きるか**：`spec-memory` §4「宙ぶらりんノードの防止」は「統合・削除処理は、出典リンクが切れた意味記憶を生まないよう連動させる」「出典が全て消えた事実は確信度を下げるか再検証フラグを立てる」と定めるが、これは**同一ストア内**で出典が消滅する場合（tombstone・アーカイブ）を前提にしている。別インスタンスへの部分移譲によって「よそのストアに実在するが渡されなかった」出典は、この規定が想定する「消滅」とは性質が異なり、**「意図的に渡さなかった」のか「データが壊れている」のかを区別する仕組みが無い**。ADR-0010 §4 も「出典の最新版が supersede/tombstone されたエントリを再検証キューへ積む」規定のみで、同種の欠落を持つ。
- **節番号**：`spec-memory` §4／ADR-0010 §4
- **Substrate か Policy/Loop か**：**Substrate の設計射程外**（ID体系がインスタンス間の名前空間分離を考慮していない。ADR-0010 §3 は `mem-<ULID>` を「分身が中央採番なしに一意採番できる」ためのものと説明しており、対象はあくまで単一インスタンス内の並行分身。インスタンスをまたぐ参照解決は最初から範囲外）

### (6) scope をまたぐ derived_from を持つ**新規合成エントリの scope 割り当てルールが未定義**
- **段階**：2（潜在的には蓄積開始時点から）
- **何が起きるか**：§14（蒸留・チャンキング）は「昇格」「統合」「降格」「チャンキング」の条件と内容を定めるが、**複数の異なる scope を出典に持つ蒸留結果に、どの scope を割り当てるかのルールがどこにもない**。E5 は執筆者（agent）が便宜的に `proj:banto` を選んだという想定にすぎず、`person` を選んでも矛盾は生じない——選択基準自体が存在しない。この不定性がある限り、「scope で切り分ければよい」という前提そのものが崩れる（切り分け対象の scope 値が最初から恣意的にしか決まらない）。
- **節番号**：`spec-memory` §14（蒸留・統合・チャンキング）／§0.3.1（継承規律は `sensitive` のみを対象とし `scope` の継承・合成ルールは扱わない）
- **Substrate か Policy/Loop か**：**Policy**（蒸留プロセスの規則の欠落）

### (7) 閉包レジストリのインスタンス間受け渡しが未定義
- **段階**：1/2
- **何が起きるか**：ADR-0010 §2「閉包の包含関係を解決するレジストリが必要になる（Policy 側のデータ）」とあるが、このレジストリは各インスタンスの `person` を root とする木であり、Y のインスタンスは Y 自身の `person` を root に持つ別の木を持つ。PO の `proj:banto` をそのまま Y の木に接ぎ木する手順（新しい閉包としての登録、命名の整合、既存の同名閉包との衝突解決）が定義されていない。
- **節番号**：ADR-0010 §2／`agent-primary-inversion.md` §0（R3、「閉包レジストリのライフサイクル…死んだプロジェクトの畳み方」を未対処と自認）
- **Substrate か Policy/Loop か**：**Policy**（レジストリは Substrate 外のデータと明記されている）

### (8) driver に「引き継ぎ」「撤退」に対応する起床源・自己内省項目が無い
- **段階**：1/3
- **何が起きるか**：§20.2 の6起床源（`po_message`/`subsystem_kick`/`worker_result`/`memory_signal`/`timer`/`model_migration`）にも、§20.5 の6項目の自己内省チェックリストにも、「インスタンス間の記憶移譲」に相当する概念が存在しない。PO の発話は素の `po_message` として処理されるのみで、その後の一連の作業（選別・パッケージング・監査）を導く決定的な手順が無い。
- **節番号**：`spec-memory` §20.2／§20.5
- **Substrate か Policy/Loop か**：**Loop**

### (9) 物理削除の根拠が §2 と §25 で矛盾している（かつ §26 は存在しない）
- **段階**：3
- **何が起きるか**：§2 は「物理削除はユーザーの明示的要求**と**法規制対応のみ（§26）」とし、PO の明示的要求だけで物理削除が可能と読めるが、§25 は「法規制対応（GDPR等）」のみを「原則削除しない」の**唯一の例外**とする。撤退時に PO が「Banto 側のコピーを消してほしい」と要求しても、これに応える正規経路がどちらの節を優先するかによって存在したりしなかったりする。加えて §2 が参照する「§26」は本文に存在しない（ドキュメント冒頭で自認済み）。
- **節番号**：`spec-memory` §2（確定論点4）／§25（ユーザーによる記憶の統制）／ドキュメント冒頭の未確定事項リスト
- **Substrate か Policy/Loop か**：**Policy**（Governance レイヤー、Part IV）。ただし物理削除の**方針**自体は Part I §0.8「物理削除は原則行わない」という不可逆の設計原理に根ざしており、その原理と例外規定の間の整合は Substrate 層の意思決定に近い。

### (10) self-model（§22）・手続き記憶の実体（SKILL.md）の扱いが未定義
- **段階**：1/3
- **何が起きるか**：
  - self-model はこの PO との関係で「人間が明示的に承認したもの」（§22）として育っている。Y は別の PO であり、Y のインスタンスは Y 自身の self-model を（もしあれば）持つはずである。「PO の Banto の self-model を Y へ渡す」という操作は意味をなすのか——**spec は複数 PO・複数インスタンス間の self-model の関係を一切扱っていない**（沈黙。禁止も許可もされていない）。
  - 手続き記憶（SKILL.md）はファイル実体としてはコピー可能だが、それを指すエントリ（strength・salience・version履歴を持つ）は前述(2)(5)と同じ問題を抱える。ファイルだけコピーして entry を渡さないと「その手順がどれだけ検証されたか（strength）」という情報が失われる。
- **節番号**：`spec-memory` §22（self-model）／§14（procedural の SKILL.md 化）
- **Substrate か Policy/Loop か**：**未定義（沈黙）**。self-model の複数インスタンス間の扱いは Governance（Part IV）の射程内だが記述が無い。

### (11) `authored_by` / `session_id` は移送後に一部意味を失う
- **段階**：2/3
- **何が起きるか**：
  - `authored_by` はモデル世代の識別子としては instance 非依存に解釈可能だが、その**消費者**である `model_migration` 起床源（§20.2）は「実行系の切替」という自インスタンス内のイベントに反応する設計であり、「外部から輸入された authored_by 値の集団」を移行イベントとして扱う規則が無い。
  - `session_id` は「並行識別＋出典独立性判定を兼ねる」（`spec-memory` §2）が、その判定に必要な文脈（実際のセッション内容・会話履歴）はエントリのスキーマに含めない設計（§2「スキーマに含めないもの」）であり、元インスタンスの外部に残る。移送先では session_id は単なる不透明な文字列となり、「本当に独立した出典か」を追加で検証する手段が失われる（Y は監査できない）。
- **節番号**：ADR-0010 §7（`authored_by`）／`spec-memory` §2（`session_id`、スキーマに含めないもの）／§20.2（`model_migration`）
- **Substrate か Policy/Loop か**：**Substrate 設計の射程外**（単一インスタンス運用を前提にしたフィールド設計であり、複数インスタンス間の意味継続は最初から検討されていない）

### (12) 「誰のものか」「削除・持ち出しの権限」が Governance に定義されていない
- **段階**：3
- **何が起きるか**：§24（権限・承認・リソース制限）は「不可逆操作のゲート — 削除・送金・**外部送信**・公開は人間の承認を挟む。実行層で強制する」と定めており、他インスタンスへの記憶移譲は「外部送信」に該当しゲートの対象にはなる。しかし：
  1. 承認者が誰か（PO のみか、受け手 Y の同意も要るか）が定義されていない。
  2. 何を承認するかの**レビュー画面**（(1)のエクスポート機構が存在しないため）が無く、承認は実質的に空の儀式になる。
  3. 撤退時の「番頭が持っていた記憶は誰のものか」という所有権自体について、ADR-0003 由来の「PO主権・透明性」（`agent-primary-inversion.md` §11.2、ADR-0010 §0 の再掲表）という**方針**はあるが、それを実現する**権限モデル**（PO以外の関係者の権利、Bantoベンダー側の保持義務の有無など）は一切書かれていない。
- **節番号**：`spec-memory` §24／§25／ADR-0003 の再掲（ADR-0010 §0 表）
- **Substrate か Policy/Loop か**：**Policy/Governance**（Part IV）。方針の宣言はあるが実行層への落とし込みが無い——これは §20.0 が自ら警告する「散文で書いた規律は素通りする」パターンそのものである。

## 4. 切り分けの可否

**結論：機械的に判定できない。**

- `context.scope` は「注入可否」を決めるための閉包識別子であり、「持ち出し可否」の意味論を最初から持たない（ADR-0010 §2）。scope だけでフィルタすると (2)(4) の通り cross-scope 出典・自由記述漏出を防げない。
- `sensitive: true` は継承される（§0.3.1）ため機微候補の**洗い出し**には使えるが、(3) の通り「渡すな」の判定には使えない。scope と sensitive は直交する2軸であり、どちらか一方だけでは要求（proj:banto だけ渡す、かつ機微は適切に扱う）を満たせない。両方を掛け合わせても、E5（proj:banto かつ sensitive）のように「scope 的には渡す対象だが中身は渡してはいけない」ケースを機械的には弾けない——**このケースを弾くには、エントリの意味内容（誰について書かれているか）を理解する必要があり、それは現行スキーマのどのフィールドにも構造化されていない**（「言及されている主体」を持つフィールドが Substrate に無い）。
- 出典グラフ（`derived_from`）は scope を跨いで自由に張れる（Substrate はこれを禁止しない）ため、「proj:banto のエントリだけを機械的に集める」操作をしても、その集合の中に person scope への参照が漏れる。逆に「person scope を除外する」ことは可能でも、それによって proj:banto 側のエントリの一部（E2, E5）が出典を欠いた状態（宙ぶらりん）になることは避けられない——**両立しない**。
- 何を機械的に判定するにも前提となる「一括取り出し」操作自体が存在しない（§3-(1)）。したがって上記の議論はすべて「もし手作業で実装したら」という仮定の上に立っており、**現状は判定以前に実行する手段がない**。

**足りないもの（切り分けを可能にするために必要な最小限）**：
1. エントリが「誰について書かれているか」を構造化して持つフィールド（主体/エンティティ参照）。現状は `content` の自由記述にのみ存在し、機械可読ではない。
2. 蒸留・チャンキング時に、出典の scope が混在する場合の scope 割り当てルール（§14 に不在）。
3. インスタンス間で `derived_from` を解決する規約（渡す/渡さないを明示するタグ、またはリンク切れの「意図的な非移譲」を示す専用状態）。
4. scope 単位（またはエンティティ単位）でストアをシリアライズ/デシリアライズする API（§0.3 に不在）。

## 5. 最小の修正案

**蓄積を始める前に決めておかないと手遅れになるもの（Substrate 層、優先順）**：

1. **エントリに「対象主体（subject/entity）」参照フィールドを追加する。** 現状 `content` の自由記述にしか主体情報が無く、後から追加しても過去のエントリには遡及できない（§0.6 の「Substrate だけは後から変更できない」がそのまま該当する）。これが無い限り、`sensitive` も `scope` も「誰について書かれた記憶か」を機械的に扱えず、切り分け・第三者情報の選別的除外が原理的に不可能なまま固定化する。
2. **`derived_from` にインスタンス間参照であることを示す名前空間、または「意図的に非移譲」を表す専用マーカーを持たせる。** 現行の `mem-<ULID>` は単一インスタンスの並行分身向けに設計されており（ADR-0010 §3）、インスタンスをまたいだ ID の意味論が最初から無い。後付けすると、既存の3年分のエントリはすべて「移譲時に区別不能な宙ぶらりん」になる。
3. **`scope` の継承・合成ルールを蒸留プロセス（§14）に明記する。** これは Policy 層の変更で足りるので Substrate ほど急を要さないが、蓄積が進むほど scope 不定な合成エントリが増え、後から遡って割り当て直すコストが増大する。

**運用開始前に決めておくべきもの（Policy/Governance 層）**：

4. **エクスポート/インポート API を最低限のバージョンで先に作る。** `agent-primary-inversion.md` 自身が「小規模なうちに一度通しておかないと、100万件で初めて実行することになる」と警告している。件数が増えるほど検証コストが増すのは削除不能な設計原理（§0.8「物理削除は原則行わない」）と同型の非対称性であり、後回しにするほど詰む。
5. **§2 と §25 の物理削除条件の矛盾を解消する。** P3（Spec と実態の矛盾は黙って寄せない）に従い、これは既に incident 案件として認識されている（ドキュメント冒頭）。撤退シナリオはこの矛盾が実害を生む典型例であり、優先度を上げるべき。
6. **「外部送信（他インスタンスへの記憶移譲）」の承認プロセスに、受け手側の同意と、渡す内容のレビュー画面を明記する。** §24 のゲート原則は存在するが、レビュー対象を可視化する機構（ADR-0010 §2.1 が「番頭が自動で広げた記憶の一覧と訂正導線」について述べる要求と同型のものが、移譲についても要る）が無い。

## 6. 判定

**動かない。** ——一括取り出し（エクスポート）の一次操作が API・driver のいずれにも存在せず（設計側もこれを認めている）、存在すると仮定した場合でも `scope` と `sensitive` の2軸だけでは「渡すもの／残すもの」を機械的に切り分けられず（対象主体を構造化するフィールドが無いため）、さらに物理削除の根拠が仕様内部で矛盾している。個々の Substrate フィールド（版管理・origin・sensitive継承）は健全だが、それらを束ねて「移譲」という操作を実行する機構そのものが欠落している。
