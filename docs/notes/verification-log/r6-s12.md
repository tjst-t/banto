### 1.4 ターン4（Year4 / 2026-02-01、深い睡眠・`person` への一般化を試みる）

設問：「PO は締め切り前に無理をしないという一般化が `person` へ上がるか」。

**まず検査すべきは「候補がどう生まれるか」である。** §12「閉包をまたぐ一般化」B1〜B5 は「候補が出たときの合否判定」しか定めていない。候補そのものをどの処理が・いつ・何を根拠に作るかは、`spec-memory` のどこにも記述がない。

- §14（蒸留・統合・チャンキング）の「統合｜類似エントリ｜マージ、出典リンク統合」は、類似エントリの発見手順を独自に定義していない。
- 唯一 spec 内でクローズをまたいだ「類似の候補ペアを作る」処理として定義されているのは §12 経路Aだが、その一次フィルタは明示的に**「同一の閉包（`context.scope`）またはその祖先」**に限定されている（§12「検出は2経路ある」経路A・1）。`dom:health` / `dom:writing` / `proj:banto` は互いに兄弟であり、この条件を満たさない。
- §20.7.1 配線レジストリの「閉包をまたぐ一般化」行は、①発火を「深い睡眠の蒸留で `scope` 拡大候補が出たとき」とだけ書いており、**その候補がどこから来るかを指定していない**（⑤入力欄は「§14 の蒸留・昇格」とあるが、§14 自身がクローズ横断の類似判定を持たない）。

**判定：候補生成の入口が構造的に存在しない。** 唯一のクローズ横断ペア生成機構（§12 経路A）が、まさにこの3閉包間の組み合わせを候補にしないよう作られているため、B1〜B5 に到達する前に止まる。

**加えて、ADR-0010 §2.1／`spec-memory` §20.5-5／§20.7.1 は独立に「Memory 面（一覧・訂正導線）が実装されるまで自動拡大を有効にしない」と明記している。** Memory 面は `spec-ui` に未記載（⚠）。したがって**仮に候補生成の入口が存在したとしても、機構自体が現状オフである**。

以上2つの独立した理由（候補生成の入口が無い／機構自体が前提条件未充足でオフ）により、**ターン4で `person` への一段拡大は起こらない**。

#### 反実仮想：もし候補が生まれたら何が書かれるはずだったか

「実行できない」で終わらせず、`§0.3.0` の合成規則を機械的に適用した場合の値を示す（**この節は生成されない仮想エントリである**）。

まず問題になるのは「3件のうちどれを候補に含めるか」自体が未定義であることである。ターン1（健康）とターン3（banto）は内容として対立するため、候補生成の類似性判定（それ自体が spec に定義されていない）が「同じ性向の言い換え」とみなすか「別の事実」とみなすかで、少なくとも2通りの帰結がありうる。**どちらが起きるかを spec の記述から一意に決めることはできない**（未定義）。

- 変種(i)：3件とも「類似」と誤って束ねた場合 → 内容が自己矛盾する生成物になり、`content` の一貫性が取れない。§0.3.0 の合成規則はこの場合の振る舞いを定めていない（矛盾する出典から1つの `headline` をどう書くかは未規定）。
- 変種(ii)：ターン2・ターン3のみ「類似」と判定し、ターン1（内容が食い違う）を黙って外した場合：

```
id:            mem-04H4CCC0PSN1-candidate  （※生成されない。反実仮想）
kind:          semantic
fact_type:     preference_decision                     # B3：対象は preference_decision のみ
```

B1（2閉包以上で独立観測）・B2（1段のみ＝`dom:writing`/`proj:banto`のLCAは直接`person`なので1段で足りる）・B3（`preference_decision`のみ）・B4（`sensitive:false`・第三者`party:*`なし）はいずれも形式上クリアする。**ただし B1〜B5 のどこにも「兄弟閉包に矛盾する言明がないか」を確認する条件が無い。** ターン1（健康）が正反対の内容を述べていることは、この判定に一切参照されない。つまり——**候補生成の入口さえ存在すれば、B1〜B5 は矛盾を見ないまま2/3の閉包の一致だけで拡大を許してしまう設計になっている**（4-2 で詳述）。

B5（期間あたりの上限）は初回の拡大なので通常は問題にならないと推測されるが、上限値そのものが未定（§0.9）のため判定不能。

**この候補は実際には生成されない**（上記の理由により）。したがって版としては記録されず、`derived_from` の逆引きにも `dependents()` にも現れない。

### 1.5 ターン5（Year4 / 2026-02-15、PO が `person` 水準で問う）

PO：「締め切り前ってどう動くのが自分に合ってる？」

実行文脈は特定ドメインに紐づかない。§21「分身への割り当て」により、直前に生きている同一閉包・同一ゴールの分身がなければ新規に fork される（今回は新規セッション、`closure_ctx = person`）。番頭は `build_context(query_seed, budget)` を呼び、内部で `retrieve({ mode: "context", session_origin: "po_message", closure_ctx: "person", raw_utterance: "締め切り前ってどう動くのが自分に合ってる？", ... })` が唯一の入口として動く（§8.5.0）。

#### §8.5.4 横断ファンアウトの発火判定

3条件（AND）を検査する。

| 条件 | 判定 | 根拠 |
|---|---|---|
| 1. `closure_ctx` が leaf でない | **満たす** | `person` は `dom:health`/`dom:writing`/`dom:kakei`/`proj:banto` を子に持つ |
| 2. Stage 0 が特定の閉包を解決していない | **満たす** | クエリに固有名詞・閉包名が無く `resolve_entities()` は閉包を特定しない（§8.5.1） |
| 3. `session_origin == po_message` かつ `mode != brief` | **満たす** | PO との直接対話、`mode: context` |

→ **§8.5.4 は発火する。** 子孫閉包（`dom:health`・`dom:writing`・`dom:kakei`・`proj:banto`、さらにその子）ごとに上位 `m`（既定2）件を候補に加える。

- `dom:health`：`S-H1` のみが「締め切り」語彙に一致 → 1件
- `dom:writing`：`S-W1` のみ → 1件
- `dom:kakei`：家計ドメインに「締め切り前の行動」に関連する記憶がなく、A1（FTS）が拾わない → 0件
- `proj:banto`：`S-B1` のみ → 1件

**多様性クォータ（§8.5.5 定員内の順序3）・閉包ごとの上位m件（§8.5.4）はいずれも「発火はする」が、本シナリオでは各ドメインに該当エントリが1件しかないため、実際に制限として効く場面がない。** 3,4ドメインいずれかが多数のヒットを持つ密な状況（設問の「数千〜数万件」という前提が本来想定するもの）でこのクォータが機能するかどうかは、**このシナリオの与件だけでは検証できない**（判定不能）。

#### s_admit の計算（4項、Turn5）

**重み・アームのランク・各成分値は仕様に具体値が無いため、以下はすべて「推測」である。** `θ_ws = 0.6`・`θ_evict = 0.2`・RRF定数 `c = 60` は spec に明記された値（§7・§8.5.5）をそのまま使う。`θ_floor`（<θ_ws）・`K_ws`・`K_hl` は具体値が定義されていない（§0.9 A.1-4/7）ため、θ_floor ≈ 0.35、K_ws ≈ 8、K_hl ≈ 20 とおく（すべて推測）。重みは w1=0.4（関連度）, w2=0.15（文脈一致）, w3=0.20（確信度）, w4=0.25（顕著性）とする（推測）。

RRF（推測のアームランク。A1=FTS が「締め切り」で3件とも強くヒット、A2=エンティティは固有名詞が無くいずれも不一致、A3=埋め込みも同傾向、A5=最近性は S-B1>S-W1>S-H1 の順）：

```
rrf(e) = Σ_arms 1/(60+rank)
S-B1: A1=1, A3=1, A5=1 → 3/61 ≈ 0.04918
S-W1: A1=2, A3=2, A5=2 → 3/62 ≈ 0.04839
S-H1: A1=3, A3=4, A5=3 → 1/63+1/64+1/63 ≈ 0.04737
rel_norm = rrf(e) / max(rrf) = rrf(e) / 0.04918
  S-B1 = 1.00 → 推測で丸めて 0.95
  S-W1 = 0.984 → 推測で丸めて 0.90
  S-H1 = 0.963 → 推測で丸めて 0.85
```

**この計算が示す重要な点**：RRF はランクが近いと差が縮む。健康ドメインの3年前の記憶（S-H1）でも「締め切り」という語彙が一致する限り、rel_norm は他の2件とほぼ並ぶ。§7「休眠トピックの復帰」の免除規則は**強いエンティティ一致（A2ヒット）がある場合にのみ**文脈一致・確信度の経過時間ペナルティを免除するが、本ケースは固有名詞が無く A2 が一切ヒットしないため、**免除は一切適用されない**。したがって年数差は rel_norm ではなく、文脈一致・確信度の側で効く。

| entry | rel_norm(w1=0.4) | 文脈一致(w2=0.15) | 確信度(w3=0.20) | 顕著性(w4=0.25) | s_admit |
|---|---|---|---|---|---|
| S-B1（proj:banto, 2025） | 0.95 | 0.30（推測） | 0.55（推測。1年経過・単一出典） | 0.60（推測。質問と直接一致） | **0.685** |
| S-W1（dom:writing, 2024） | 0.90 | 0.30（推測） | 0.45（推測。2年経過・単一出典） | 0.60（推測） | **0.645** |
| S-H1（dom:health, 2023） | 0.85 | 0.30（推測） | 0.35（推測。3年経過・単一出典、免除なし） | 0.60（推測） | **0.605** |

`θ_ws = 0.6`（spec 既定値）と比較すると、**3件とも θ_ws を上回る**。定員 `K_ws ≈ 8`（推測）に対して候補3件は十分収まる。

**判定：S-H1・S-W1・S-B1 の3件とも滞在枠（resident）に入場する。** tier=resident、解像度=要約（§9 割当規則）。

#### 聞き返し（`clarify`、§8.5.5末尾）の判定

条件は「`unresolved[]` が空でなく、かつ滞在枠に入ったエントリの `context.scope` が2つ以上の兄弟閉包にまたがるとき」。**後半（scope が3つの兄弟閉包にまたがる）は満たす。** しかし前半（`unresolved[]` が空でない）は、そもそもクエリに固有名詞的トークンが一つも含まれないため、`resolve_entities()` が「解決を試みて失敗した」対象を持たない——**「解決すべき対象が無い」ことと「解決に失敗した」ことは区別されるはずだが、その区別が `unresolved[]` の定義上どちらに転ぶかが spec に明記されていない**（未定義）。`unresolved[]` を「試みて失敗したものだけ」と読めば空になり、AND 条件が満たされず **`clarify` は発火しない**。この読みが正しいとすれば、**最も横断の程度が大きい（3兄弟閉包にまたがる）ケースほど `clarify` の対象から漏れる**という逆説的な帰結になる。判定は「条件が判定できない」に分類する。

#### 横断の明示（§8.5.4「注入時に、どの閉包を横断したかを明示する」）

`§20.7.1` の配線表は当該行の提示面を「会話」と明記しており、**置き場所自体は定義されている**。番頭の応答には「健康・執筆・proj:banto の3ドメインから拾いました」に相当する開示が入るはずである。ただし `retrieve()` の返り値 `ranked[] = [{entry_id, s_admit, rank, tier, arms_hit[]}]`（§8.5.0）には「この件が横断ファンアウト経由で入ったか」「どの閉包を横断したか」を示す専用フィールドが無い。番頭（または番頭を包むレンダリング層）が `context.scope` を個別に引いて自力で組み立てる必要があり、**その組み立て手順自体はどこにも規定されていない**。「置き場所は決まっているが、材料の受け渡し契約が半分しかない」という状態である。

#### PO への提示（要約解像度、確信度の量子化・推測）

```
（rendered、summary 解像度）
"締め切り前の動き方は、ドメインによって傾向が割れています：
 ・proj:banto（2025年〜）：無理はしない方針（品質低下を避ける）— おそらく
 ・執筆（2024年〜）：締め切り2日前に必ず提出、ギリギリを避ける — おそらく
 ・健康（2023年）：締め切り前は睡眠を削ってでも終わらせる方針 — 未確認（やや古い記憶）
 （健康・執筆・proj:banto の3ドメインから拾いました）"
```

**この時点で番頭は3件を並べて提示できるが、「どちらが今のPOの方針か」を構造的に裁定する機構は無い。** §12 の矛盾解決規則（origin→fact_type）は**同一エントリの版列**にのみ適用され、S-H1・S-W1・S-B1 は互いに `supersede()` の関係にない独立した3系列であるため、優先順位を決める規則が存在しない（この点は R4-S12 3-6 で既に指摘されており、本ラウンドでも未解消のまま残っている）。

#### `derived_from` の自動付記と、person スコープでの新規 episode 記録

Turn5 の会話（PO の質問＋番頭の統合回答）は `record()` で episode として記録される。**このセッション自体が `person` 水準で開始されている**ため、`context.scope` はそのまま `person` になる。

**これが本シナリオで最も重要な観察点である（4-4 で詳述）**：E-SYN は `dom:health`・`dom:writing`・`proj:banto` という3つの兄弟閉包の内容を出典に持ちながら、`scope: person` を**§0.3.0の派生エントリ合成規則を一切経由せずに**獲得している。合成規則（LCA 計算・§12 B1〜B5 の適用）はその見出しどおり「蒸留・昇格・統合が新しいエントリを作るとき」にのみ適用される、と明記されており（§0.3.0冒頭）、**ライブセッション中の `record()` はこの対象に含まれない**。`record()` の `attrs.scope` は呼び出し側（この場合はセッションの exec_context）が直接渡す値であり、「出典の最小共通祖先」という計算は行われない。つまり `scope: person` はターン4の一般化バーを一段も通らずに、**単に「PO が person 水準の質問をしたから」という理由だけで**、健康ドメインの機微に近い内容を含む要約が `person` スコープの記憶として恒久化される。

`propose()` の5条件（§14）を確認する：`origin: user_explicit`（否）／`recall_count` 閾値（未達）／`external_ref` に外向き command（無し）／規範的言明の新規確立（E-SYNは分析であり規範的言明ではないため該当しない、推測）／`origin: external`（無し）。**いずれにも当たらないため、E-SYN は次の浅い睡眠で `propose()` されない。** episode のまま `person` スコープに残り続ける。

#### s_admit の計算（E-SYN、Turn6）

同じ推測の重み（w1=0.4, w2=0.15, w3=0.20, w4=0.25）を用いる。

- 文脈一致：`dom:kakei` 固有の文脈（家計・支出）と一致しない → **0.20**（推測）
- 確信度：`origin: agent_inferred`・単一セッション・作成から数日という新しさはあるが、根拠は他人の言明の統合であり出典独立性は低い → **0.40**（推測）
- 顕著性：現在のゴール（今月の支出確認）との目標関連性はほぼ無関係 → **0.10**（推測）

```
                       = 0.06 + 0.03 + 0.08 + 0.025 = 0.195
```

## 3. 動くこと

1. **V（可視性フィルタ、§8.5.3）による兄弟ドメインの既定遮断は健全に機能する。** ターン6で `S-H1`/`S-W1`/`S-B1` が `closure_filter` に含まれず機械的に除外されることを確認した。これは R4-S12 で確認された「閉包の包含解決」の健全性が、横断ファンアウト導入後も既定動作としては保たれていることを示す。
2. **§8.5.4 の3条件（AND）は仕様通りに機械的に判定できる。** ターン5（`person`・leaf でない・閉包非解決・PO直接対話）で発火し、ターン6（`dom:kakei`・leaf）で不発火になることを、条件式だけから導出できた。LLMの裁量を挟まずに済んでいる（§20.0 の要請どおり）。
3. **セッションスナップショット隔離（§19）が、横断的に読まれた内容の作業記憶レベルでの直接的な持ち越しを防ぐ最終防衛線として機能する。** ターン5の滞在枠にあった3件は、ターン6の新セッションのワーキングセットには一切引き継がれない。
4. **`derived_from` の自動付記（§0.3.1）は E-SYN に対しても機能し、事後追跡可能性を提供する。** 「なぜ番頭がこの分析をしたか」は `derived_from` を辿れば分かる（ただし予防はしない、§0.3.1 の設計どおり）。
5. **RRF によるランク融合（§8.5.5）は N 不変という設計目標を保ったまま、3件を近い rel_norm に収める。** これは意図された挙動であり、古い記憶（S-H1）が語彙一致だけで rel_norm 上は不当に沈まないことを確認した（ただし、これは同時に4-1・4-9で述べる別の問題の土台にもなる）。

## 4. 破綻・穴

### 4-1. B1〜B5 の候補生成トリガーが構造的に存在しない

- (a) ターン4
- (b) 蒸留がクローズ横断の一般化候補をどう作るかが §14 にも §12 にも書かれていない。唯一のクローズ横断ペア生成機構（§12 経路A）は「同一の閉包またはその祖先」に候補生成を明示的に制限しており、兄弟ドメイン間の候補を構造的に生成できない。§20.7.1 の配線表も⑤入力欄を「§14の蒸留・昇格」とするだけで、§14 自身がその手順を持たない。
- (c) §12「閉包をまたぐ一般化」冒頭、§14、§12経路A、§20.7.1
- (d) **Policy/Loop（可逆）**。ただし §20.0 が自認する「規則を書いて配線を忘れる」パターンの再発であり、次に埋めるべき欠落の性質は R1〜R5 とまったく同型。

### 4-2. B1〜B5 に兄弟閉包の矛盾を確認する条件が無い

- (a) ターン4（反実仮想）
- (b) B1 は「異なる閉包で独立に観測されたときだけ広げる」としか要求せず、対立する第3の閉包（本シナリオでは `dom:health`）の存在を確認する条件を持たない。候補生成の入口さえ塞がっていなければ、`dom:writing`／`proj:banto` の一致だけで `dom:health` の対立言明を無視したまま `person` へ拡大しうる設計になっている。
- (c) §12 B1
- (d) **Policy/Loop（可逆）**。4-1 が解消されて初めて顕在化する二次的な穴。

### 4-3. Memory 面未実装によるゲート（既知残件の再確認）

- (a) ターン4
- (b) ADR-0010 §2.1・`spec-memory` §20.5-5・§20.7.1 のいずれも「この面ができるまで自動拡大を有効にしない」と明記しており、本シナリオの時点（実装未着手）では B1〜B5 は無条件にオフである。
- (c) ADR-0010 §2.1、§20.5-5、§20.7.1
- (d) 一部 Governance（実装順序の統治）・一部 Policy（面の不在自体はUI実装の欠如）

### 4-4. `record()` のライブ書き込みが `scope: person` を B1〜B5 を経由せずに獲得する（本ラウンド最大の指摘）

- (a) ターン5（E-SYN の記録）
- (b) §0.3.0 の派生エントリ合成規則（LCA計算・B1〜B5適用）は「蒸留・昇格・統合が新しいエントリを作るとき」に限定されると明記されている。しかしライブセッション中の `record()` は `attrs.scope` を呼び出し側（セッションの exec_context）から直接受け取るだけであり、この合成規則の対象外である。PO が `person` 水準の質問をした、というだけの理由で、健康ドメイン由来の内容を含む要約が `scope: person`（＝全ドメインから可視）の記憶として一段の裁定もなく確定する。§8.5.4 が繰り返し宣言する「書き込み側は緩めない／B1〜B5は一切緩めない」は文字どおり真であり続けるが、**その宣言はこの経路をそもそも守備範囲に含んでいない**。
- (c) §0.3、§0.3.0（冒頭「蒸留・昇格・統合が新しいエントリを作るとき」）、§8.5.4「ADR-0010との関係」節
- (d) **Policy/Loop（可逆）だが実害はSubstrateの1位相当**（§0.7の1位・3位に接続しうる。読みの横断が無警戒に恒久的な書き込みへ転化する経路であるため）

### 4-5. `sensitive` フラグが PO 自身のドメイン間プライバシーを保護しない（既知残件の再確認、E-SYN にも該当）

- (a) ターン5（E-SYN）
- (b) ADR-0010 §5 は `sensitive` を第三者機微限定で定義している。E-SYN は PO 自身の健康ドメインの性向を `person` スコープへ運ぶが、定義上 `sensitive` の対象外のまま false になる。R4-S12 の 3-7 と同型の穴が、B1〜B5 導入後も、しかも B1〜B5 を経由しない別経路（4-4）で再現する。
- (c) ADR-0010 §5
- (d) 既存残件の再現。フラグの意味論変更は Substrate 寄りの重さを持つ。

### 4-6. 横断ファンアウトの開示が恒久的な監査ログを持たない

- (a) ターン5
- (b) 開示は「会話」への即時表示のみ（§8.5.4、§20.7.1の提示面欄）。§21 の通知表（10行）には横断ファンアウトに対応する行が無く、§20.5-5 の監査はB1〜B5経由の書き込み側拡大しか見ていない。PO がその場の応答を読み流せば、横断が起きたという事実自体は生の会話トランスクリプトにしか残らず、事後にダイジェストやアテンションキューで気づく手段が無い。
- (c) §8.5.4、§21、§20.7.1
- (d) Loop/Governance（可逆）

### 4-7. `ranked[]` に「どの経路（祖先／横断）で候補になったか」を示すフィールドが無い

- (a) 恒常（ターン5含む）
- (b) `ranked[] = [{entry_id, s_admit, rank, tier, arms_hit[]}]`（§8.5.0）には横断ファンアウト経由かどうかを示す情報が無い。「注入時にどの閉包を横断したかを明示する」という§8.5.4の要求を実行するための最小限のデータ契約が、`retrieve()` のシグネチャに欠けている。
- (c) §8.5.0、§8.5.4
- (d) Policy（可逆）

### 4-8. 多様性クォータ・流量制限mの実効性がこのシナリオのデータ密度では検証不能

- (a) ターン5
- (b) 設問の前提（各ドメインに数千〜数万件）に反し、本シナリオでは「締め切り」関連の該当記憶がドメインあたり1件しかない。したがって m=2 の上限にもクォータにも一度も抵触せず、「1つの騒がしいプロジェクトが枠を占有しない」という設計目標が実際に働く場面を確認できなかった。
- (c) §8.5.4、§8.5.5順序3
- (d) Policy（可逆）。パラメータの具体値は §0.9 により未定義。

### 4-9. 矛盾検出（§12経路A・経路B）が兄弟ドメイン間の矛盾を原理的に検出できない

- (a) 恒常。特にターン1（健康）とターン3（banto）の内容対立
- (b) 経路A の一次フィルタは「同一の閉包またはその祖先」に限定され、兄弟閉包間の候補ペアを作らない（4-1と同根）。経路B（`derived_from` の系譜波及）も、S-H1 と S-B1 の間に系譜上のリンクが無い限り無力である。結果として、PO が3回にわたって（表面的には）矛盾する方針をドメインごとに述べても、`collision_candidates()` は一度も両者を突き合わせない。§12 の矛盾解決規則（origin→fact_type）は起動すらしない。
- (c) §12「検出は2経路ある」経路A・経路B
- (d) Policy寄りだが、候補生成のスコープ制限自体は実質的な設計判断であり軽い Substrate 隣接性を持つ

## 5. 最小の修正案

1. **クローズ横断の一般化候補を生成する処理を §14 または §12 に明示的に追加する。** 少なくとも「同一の `fact_type: preference_decision` を持つ意味記憶が2つ以上の兄弟閉包に存在するとき、深い睡眠がそれらを候補としてまとめ、B1〜B5 の判定にかける」という形の、決定的な起点を書く。現状は B1〜B5 が「候補が出たとき」を前提にしているのに、候補を出す処理が存在しない。
2. **B1 に矛盾チェックを追加する。** 「対象閉包の兄弟閉包に、同一トピックについて対立する `preference_decision` が存在する場合は自動拡大せず、両論併記のまま人間に提示する」という一文を B1〜B5 に足す。
3. **`record()` の `scope` に、ライブセッションであっても最小限のガードを課す。** 少なくとも「`derived_from` が2つ以上の兄弟閉包にまたがるエントリを、セッションの exec_context がたまたま `person` などの祖先閉包にあるという理由だけで書き込む場合は、`origin` を無条件に `agent_inferred` へ強制し、かつ §20.5-5 の監査対象に含める」という規則を §0.3.0 の不変条件（I1〜I8）に追加する。これにより、B1〜B5 を経由しない書き込み経路（4-4）も同じ監査網に入る。
4. **`retrieve()` の `ranked[]` に `via_fanout: bool` および `crossed_closures[]` を追加する。** §8.5.4 の「注入時に明示する」を実行可能にするための最小限のデータ契約。
5. **§21 の通知表に「横断ファンアウトが発火した」行を追加するか、少なくとも `trace` に横断発火の記録を残し §20.5 の点検対象にする。** 会話内の即時開示だけでは、読み流された場合に恒久的な痕跡が残らない。

## 6. 判定

**条件付きで動く（ただし核心は依然として穴のまま）。** V による兄弟ドメインの既定遮断・§8.5.4 の3条件判定・セッションスナップショット隔離は仕様どおりに機械的に機能し、ターン6での直接的な作業記憶汚染は（今回のクエリでは）起きない。しかし本シナリオが本来問うていた「`person` への一般化」（B1〜B5）は、候補生成の入口が存在しないために一度も起動できず、R4-S12 が指摘した「規則はあるが発火しない」という診断が、規則そのもの（B1〜B5）が追加された後も**入口の欠落という形で再現している**。さらに、B1〜B5 が守っているはずの書き込み側の緩和禁止を、B1〜B5 の管轄外にある別経路（person 水準セッションでのライブ `record()`）が無警戒にすり抜けることを新たに確認した（4-4）。「読みの横断は書きの横断へ漏れない」という §8.5.4 の宣言は、B1〜B5 についてのみ真であり、シナリオが実際に露呈させた漏出経路をカバーしていない。
