# R4 / S5：横断記憶の自動昇格と事後訂正（型厳格ポリシーの誤った持ち出し）

**対象**: `docs/spec/memory.md`（版4.0、2026-07-26 改訂＝§20.4 点火の追加入口1・§20.5 の2ホップ超/ 未提示分の点検・§0.3.1 `derived_from` 自動付記を含む）／[ADR-0010](../../adr/adr-0010-memory-substrate-schema.md)（Substrate 正典、特に §2・§2.1）／`docs/notes/agent-primary-inversion.md` §0・§2・§4
**検証者**: サブエージェント（敵対的レビュー）
**前提**: Banto（番頭）＝Quirefold を装着した永続 AI、職人＝memoryless。PO 裁定＝可視範囲の拡大は番頭が自動判断、PO は事後に見て訂正できる。事前ゲートなし（ADR-0010 §2.1）。
**規律**: 好意的に解釈しない。実行できない箇所は「実行できない」と書く。書いていないことは補って正当化しない（＝「未定義」）。推測は明示する。

### 1.3 Turn 2〜4（2026-07-29 〜 08-02、複数セッション）— PO が繰り返す

PO が同趣旨を複数セッションで繰り返す（「何度も言う」）。各回、新しい episode（mem-0002, mem-0003…）が `origin: user_explicit` で記録され、点火（§20.4）が毎回同期的に走る。この時点で mem-0010（生きた意味記憶）が既に存在するため、`collision_candidates()` の一次フィルタ（同一閉包・エンティティ一致・LSH、§12 経路A）は同一トピックとして **候補を返す可能性が高い**。

**ここで §12 の「訂正」の定義を機械的に適用すると意外な帰結が出る**：

> 訂正 ＝ `origin: user_explicit` の言明であって、`collision_candidates()` が既存の生きた意味記憶を1件以上返したもの。

判定基準は「矛盾しているか」ではなく「候補が1件でもあるか」だけである。PO が同じ方針を**追認**しているだけの発言（矛盾ではなく強化）でも、候補抽出（ルールベース・LSH、LLM不使用）はエンティティ一致で拾うため、字義通り読めば **これも「訂正」に分類されピン留め・最優先枠・緊急伝播チャネルに乗る**。§0.8「見逃しコスト＞ノイズコスト」の方針とは整合する（過剰検知側に倒す設計思想通り）が、追認のたびに最優先枠を専有する点は §20.3 の優先度キューの実務コストとして未評価。

### 1.4 深い睡眠（2026-08-02、`sleep-deep-2026-08-02`）— 可視範囲の自動拡大

ここが本シナリオの核心。番頭（深い睡眠の統合処理）が「複数セッションにまたがって繰り返し明言された＝PO の恒久的な流儀」と判断し、横断記憶を作る。**この判断自体を機械的にゲートする規則は spec のどこにも存在しない**（後述 3-①）。

`supersede(mem-0010, ...)` を試みる形は選べない。理由：mem-0010 の最新版の `origin` は `user_explicit` であり、`supersede()` の origin 優先強制（§0.3「対象の最新版が `origin: user_explicit` のとき、`agent_inferred` からの呼び出しは拒否する」、ADR-0010 §1.3）により、**`agent_inferred` の呼び出しとして既存エントリの scope を書き換える版は作れない**。したがって番頭が可視範囲を広げるには、既存版を supersede するのではなく **新しい別エントリを作る**しかない。

```
id:              mem-0020
kind:            semantic
fact_type:       preference_decision
content:         {
  headline: "PO の恒久的な流儀と推定: 型は厳格に、anyには理由コメント必須（プロジェクト横断）",
  summary:  "banto (proj:banto) で複数セッションにわたり繰り返し明言されたため、番頭がプロジェクト固有ではなく一般的な開発方針と推論した。",
  full:     "（根拠となった各発言への言及）"
}
created_at:      2026-08-02T02:00:00Z
valid_from:      2026-08-02T02:00:00Z
valid_until:     null
origin:          agent_inferred                 ← ここが番頭自身の推論（ADR-0010 §2.1「番頭の自動判断はagent_inferred」）
sensitive:       false
session_id:      sleep-deep-2026-08-02
context:         { scope: "person" }              ← root閉包へ拡大
derived_from:    [mem-0010, mem-0002, mem-0003]
external_ref:    []
version:         1
superseded_by:   null
tombstone:       false
strength:        0.5（推測）
salience:        0.6（推測。頻度成分が効いたと推定）
authored_by:     claude-opus-5/2026-07
```

`derived_from` は正しく元の user_explicit 系列を指しており、§4「出典と信頼境界」の要件は満たす。しかし **mem-0010（`proj:banto` scope, user_explicit）自体は無傷のまま生き続ける**。mem-0020 は同じ内容の**独立した新エントリ**であり、mem-0010 の版ではない。「型は厳格に」という決定が今や2つの独立した生きたエントリ（scope が違う）として並存する。

### 1.6 Turn 6（2026-08〜09 の間）— PO の違和感、しかし気づかない

PO：「なんか指示がズレてる」という漠然とした違和感。これは `origin: user_explicit` の**構造化された言明ではなく**、`collision_candidates()` を発火させる形の episode としても record されない（あるいは record されても既存の意味記憶と語彙・エンティティが一致せず候補ゼロ）。§12 の「訂正」の定義にも §21 の通知条件（訂正由来の再検証・`state_fact` 再観測 supersede・機微判断・予算枯渇・外向き副作用）のいずれにも当たらない。**何も発火しない。**

### 1.7 深い睡眠のたびに走る自己内省（§20.5）— 何が実際に拾われるか

2026-08-02 以降の毎回の深い睡眠で §20.5 の6点検リストが走る。関係する項目を具体的に評価する。

- **§20.5-5**（「`origin: agent_inferred` で自動的に可視範囲を広げた記憶のうち、PO がまだ見ていないもの」）：mem-0020 がまさにこれに該当し、**該当することは検出できる**（機械的に `origin: agent_inferred` かつ `context.scope` が生成時に広がったものを列挙するのは、生成時にそのようなフラグ・記録を残していれば可能。ただし「可視範囲を広げた」をどう機械的に判定するかの規則自体は §20.5-5 の本文に書かれていない＝検出ロジックは未定義。ここでは「広げたことが分かる形で記録されている」という好意的でない最小の前提を置く）。
- 生成された項目は「作業キューに積まれ、次の tick の種になる」（§20.5 冒頭）。**しかしこの項目の優先度がどのバケットに入るかは §20.3 の表に行が無い。** 表にあるのは「訂正に由来する再検証・点火」「`subsystem_kick`」「`worker_result`」「自律的な再検証・調査（低）」のみ。§20.5-5 の出力は消去法で「自律的な再検証・調査｜低｜予算の従属」に落ちるほかない。
- **低優先度＝自律予算（§20.6）に従属する**。「枠を超えたら自律行動を停止し、`po_message` と `subsystem_kick` への応答だけを続ける」。つまり他の作業に押されて恒久的に後回しにされうる。
- **§21 の通知条件（重大度フィルタ）にも該当しない**：5カテゴリ（訂正由来の判断要求・`state_fact` 再観測 supersede・機微判断・予算枯渇・外向き副作用の巻き戻し）のどれにも「自動横断した記憶を PO がまだ見ていない」は入っていない。**つまり検出されても PO への能動的な通知は発生しない。**
- 唯一の提示経路は PO が能動的に「Memory 面」を開き、「番頭が自動で広げた記憶」だけを絞ったフィルタ表示を見ること（ADR-0010 §2.1）。**このビューは spec 中のどこにも実装仕様として存在しない**（`docs/spec/ui.md` を確認したが Memory 面・記憶一覧・訂正導線の記述は無い。grep でも "Memory 面" の一致は ADR-0010 本文と本節の記述のみ）。ADR-0010 §2.1 自身が「本ADRの範囲外だが、これが無い限り『事後訂正で担保する』という主張は成立しない」「実装順序として、自動横断を有効にする前にこの面を用意する」と明記している。**本シナリオでは、この前提条件が満たされる前に自動横断（1.4節）が発生している。**

結論：**§20.5-5 は検出はするが、PO に届く経路が存在しない。** 1ヶ月気づかない状態を改善するかという問いへの答えは「改善しない」。

反応的な再検証キューの積み込み（§20.4「積む条件」表、行1「supersede された→ `derived_from` にそれを含むエントリを逆引き、既定2ホップ」）が発火：
- mem-0031（1ホップ、`derived_from: [mem-0020]`）→ キューへ。
- mem-0040（procedural, `derived_from` に mem-0020 を直接含む＝1ホップ）→ キューへ。

**しかし mem-0040 が実際にキューに積まれた後、どう裁定するかの規則が存在しない。** `kind: procedural` は `fact_type: null` であり、§12 の矛盾解決規則表（`preference_decision` / `state_fact` / `world_fact` の3行）に対応する行が無い。「訂正由来は即時：分身を起こして裁かせる」（§20.4「消化」）と言っても、その分身が何を根拠に SKILL.md を tombstone するか・版を作るかの手続きが未定義（§20.8 の R3「`kind: procedural` の裁定規則が無い」と一致）。

### 1.9 職人が既に書いたコードの扱い

mem-0031（過剰な型ヒント付き pandas コードを記録した episode）は再検証キューに積まれ、分身が裁くとしても、**§20.5-6 のチェック対象は明示的に「サブシステムへ送った command」（Kobo 向け）に限定されている**。§20.8-7 がこの不整合を自ら指摘している：「§20.5-4（原文ママ、実際は20.5-6）の対象が Kobo の command のみで Worker Pool への委譲（＝職人が書いたコード）が漏れる」。つまり **職人が既に書いた過剰な型ヒント付きコードそのものを再レビューさせる機構は spec 上に存在しない**。mem-0031 が再検証キューに積まれて「この判断はもう正しくない」と分身が認識したとしても、それが「このコードを直せ」という具体的な是正アクション（Worker Pool への再発注・PR コメント等）に接続する規則がない。

## 2. 動くこと

- **`derived_from` の自動付記（§0.3.1）は機能する**：mem-0031・mem-0040 はいずれもハーネスが機械的に付記した `derived_from` により mem-0020 を正しく指す。誤った横断記憶を根拠にした委譲は**構造的には**追跡可能（ただし record() が実際に呼ばれた場合に限る。後述 3-⑦）。
- **origin 優先の書き込み時強制（§0.3、ADR-0010 §1.3）は機能する**：番頭が `agent_inferred` の supersede で mem-0010（user_explicit）を直接上書きすることはできない。結果として番頭は新規エントリ（mem-0020）を作る形に迂回するしかなく、**PO の原発言（mem-0010, proj:banto scope）は横断拡大によって汚染・消失しない**。
- **Memory 面からの直接 `supersede()` は §20.4 の追加入口1により無条件で「訂正」とみなされ、最優先枠・緊急伝播チャネルに正しく乗る**。「PO が事後訂正する導線そのものが最優先で伝わらないのは本末転倒」という 2026-07-26 の設計意図はここで実際に満たされている。
- **版解決フィルタ（§7）により旧版（mem-0020）は訂正後に注入されない**：`superseded_by != null` のエントリは `build_context()` / `recall()` の候補から除外される。訂正後、Python プロジェクトへ mem-0020 が再度漏れ出すことはない（新版 mem-0021 は `scope: proj:banto` に戻っているため、Python プロジェクトの祖先閉包にも含まれず注入されない）。
- **`origin: agent_inferred` かつ `sensitive: false` の記憶は素直に横断注入される**——これは「番頭が自動で可視範囲を広げPOが事後に見る」という裁定が意図した基本動作そのものであり、機構としては ADR-0010 §2 の閉包包含判定通りに動く。

## 4. 事後訂正モデルの判定

PO 裁定「番頭が自動で広げ、PO は事後に訂正する（事前ゲートなし）」は、**訂正が起きた後の挙動に限れば成立する**が、**それを成立させるための前提条件（PO が事後に気づける経路）が欠落しているため、モデル全体としては成立しない**。

具体的に示す。

1. **成立している部分**：Memory 面から PO が直接 `supersede()` を呼んだ**後**は、origin 優先の実行層強制・§20.4 の追加入口1・§19 の緊急無効化チャネル・§7 の版解決フィルタが噛み合い、訂正は最優先で伝播し、旧版は再注入されない。ここは 2026-07-26 の改訂が意図した通り動く。
2. **成立していない部分（本質）**：「PO は事後に見て訂正できる」という文言は、**PO が能動的に見に行く UI（Memory 面の「番頭が自動で広げた記憶」フィルタ表示）の存在を前提にしている**。ADR-0010 §2.1 はこれを自ら「前提条件」と呼び、「本ADRの範囲外」「これが無い限り事後訂正で担保するという主張は成立しない」「自動横断を有効にする前にこの面を用意する」と明記している。**このシナリオでは、その前提条件が用意される前に自動横断（1.4節）が発生している。** ADR 自身の実装順序の指示に反する状態が起きている。
3. **§20.5-5 が代替の安全網になっていない**：唯一「PO がまだ見ていない自動横断記憶」を能動的に検出する仕組み（§20.5-5、2026-07-26 追加）は、検出後の扱いが §20.3 の優先度表にも §21 の通知条件にも接続されておらず、実質的に「自律予算に従属する低優先度の作業キュー項目」に埋没する。したがって §20.5-5 は「1ヶ月気づかない」状態を**改善しない**——シナリオの通り、PO は結局「偶然 Memory 面を開いて気づく」以外の経路を持たない。
4. **したがって、事後訂正モデルが実際に機能するのは「PO が自発的に、定期的に Memory 面を確認する習慣を持つ場合」に限られる。** これは「事前ゲートを置かない代わりに事後の可視性で担保する」という裁定の趣旨（能動的な確認をPOに強制しない）と矛盾する——事後の安全網が能動的な確認に依存してしまっている。
5. 加えて、訂正が実行された**後**も、procedural memory（SKILL.md、③）と職人が既に書いたコード成果物（④）については是正の受け皿が定義されておらず、「訂正すれば正しい状態に戻る」という暗黙の期待も部分的にしか満たされない。

## 5. 最小の修正案

1. **横断化（scope broadening）の発火条件を実行層の規則として定義する**（§7 または §14 に追加）。例：「同一 entity/topic の `origin: user_explicit` エピソードが、相異なる `session_id` で N 回（例: 3回）、かつ `collision_candidates()` が毎回ゼロ（＝矛盾ではなく一貫した再確認）である場合にのみ、深い睡眠は横断スコープの新規エントリ生成を提案してよい」。散文のままでは §20.0 の教訓通り機能しない。
2. **§20.5-5 の出力を §20.3 の優先度表に明示的に接続する**：例えば「`origin: agent_inferred` の scope 拡大記憶で、生成から K 日（例:7日）経過しても PO 未提示のものは、`state_fact` 再観測 supersede と同格の通知カテゴリとして §21 へ追加する」。低優先度の自律キューに埋没させない。
3. **Memory 面（「番頭が自動で広げた記憶」一覧＋訂正導線）の実装を、自動横断機能そのものの有効化条件として明記する。** ADR-0010 §2.1 が既にそう書いているので、これは実質「書いてある通りに実装順序を守れ」という運用規律の徹底——spec-ui にこの面の最小要件（一覧・フィルタ・supersede 導線）を明記して初めて閉じる。
4. **`kind: procedural` を §12 の矛盾解決規則表に組み込む**（例：「procedural は起点の semantic 記憶が supersede/tombstone されたら常にアーカイブ降格候補とし、PO 承認を経て新版 SKILL.md を発行する」）。R3 の自認済みギャップを実際に埋める。
5. **§20.5-6 の対象を Worker Pool 委譲（職人が書いたコード）にも拡張する**：「覆った根拠に基づく委譲」を command と同列に扱い、アテンションカードとして PO に上げる（自動修正はしない、既存方針のまま）。
6. **逆方向（過少横断）の自己内省チェックを §20.5 に追加するか、非対称であることを明記する。** 少なくとも「この設計は over-broadening 側にしか目を向けていない」という限界を spec に明記し、隠さない。
7. **通常の Worker Pool 委譲についても record() を必須化する**（citations 必須と同格の Policy 規則として）。`derived_from` 自動付記の保証を「record() が呼ばれれば機能する」から「record() は必ず呼ばれる」に強化しない限り、追跡可能性の主張は条件付きのままである。

## 6. 判定

**動かない** — 訂正が実行された後の伝播機構（origin優先・§20.4追加入口1・版解決フィルタ・緊急伝播）は設計通り機能するが、「PO が事後にこの横断を認識できる」という事後訂正モデルの根幹は、§20.5-5の検出結果が優先度・通知のどちらにも配線されておらず、かつ提示の前提条件であるMemory面自体が仕様として存在しないため、成立しない。PO が偶然UIを開かない限り、シナリオ通り1ヶ月気づかないままになる。
