# R4 / S13：検索品質の N 依存（記憶100万件）

**対象**: `docs/spec/memory.md`（版4.0、2026-07-26）／[ADR-0010](../../adr/adr-0010-memory-substrate-schema.md)（Substrate 正典）
**検証者**: サブエージェント（敵対的レビュー）
**規律**: 好意的に解釈しない。実行できない箇所は「実行できない」と書く。書いていないことは「未定義」とする。推測は明示する。

---

## 1. シミュレーション本体

### 1.1 前提設定

7年運用、4ドメイン・数十プロジェクト（本シミュレーションでは40プロジェクトと**推測**）。記憶100万件の内訳は問題文の指定通り：episode 90万・semantic 9万・procedural 1万。

PO 発話：「認証まわりの方針って今どうなってる？」——固有名詞を含まない、閉包を明示しない、標準的な状態確認クエリ。ドメインは開発（Kobo）と**推測**する。

`「認証」に関連するエントリは数千件ある` という問題設定を、字面・LSH一次フィルタ通過後の候補数として **3,000件** と置く（問題文の「数千件」の範囲内で代表値として選定。以降の計算の起点）。

### 1.2 決定的に確認できたこと：スコアは絶対値であり正規化されていない

§7 の入場スコア式

```
s_admit = w1・関連度 + w2・文脈一致 + w3・確信度 + w4・顕著性
```

を Part I・II 全体で検索したが、**候補集合内での相対順位づけ（softmax・z-score・rank normalize 等）を行うという記述は一切ない**。各項は候補ごとに独立に計算される絶対値であり、`θ_admit = 0.6` はこの絶対値に対する固定の下限である。

これは以下を意味する：**「同一トピックに言及するエントリの総数」が増えれば、閾値を超える候補の絶対数はそれに比例して増えうる**。θ_admit 自体は N の関数ではないため、識別力（有用な少数だけを通す機能）は N が増えるほど弱まる方向に働く。ここまでは書かれている式から機械的に導ける結論であり、推測ではない。

一方、**w1〜w4 の具体値はどこにも与えられていない**（§0.9-4「全パラメータの具体値」が未解決事項として明記）。以下のシミュレーションのため、`w1=0.4（関連度）, w2=0.25（文脈一致）, w3=0.2（確信度）, w4=0.15（顕著性）` を**推測**として置く（4項の合計が1になるよう仮定。s_admit の値域を[0,1]とみなせば θ_admit=0.6 という値も解釈可能になるため）。

### 1.3 検索候補生成の機構そのものが本文に存在しない【最重要の発見】

θ_admit 超過件数を計算する前に、そもそも「クエリ文字列から3,000件の候補をどう取り出すか」という**マッチング／索引の機構**を spec-memory・ADR-0010 の全文から探したが、**見つからなかった**。

- §8「クエリ生成」は "何を材料にクエリを作るか"（直近発話・ゴール・ワーキングセット・実行文脈）を述べるが、**クエリから候補への変換手段**（全文検索か、ベクトル近傍か、両方か）を定義していない。
- §12 経路A は「LSH／クラスタリングで候補ペアを絞る」と述べるが、これは**矛盾検出**の一次フィルタであり、`build_context()` の候補生成に流用されるとはどこにも書いていない。
- §15 は「局所探索」「歯状回のパターン分離（LSH）」を脳アナロジーの技法一覧として列挙するだけで、§7 の候補生成手順（版解決→tombstone除外→アーカイブ解像度制限→sensitive除外、の4ステップ）の**どこに挿入されるかを指定していない**。
- ADR-0010 §4 は「embedding はスキーマに持たず索引の再生成で済む」と述べ、embedding を Substrate の外に置くことは決めているが、**embedding を使うと確定しているわけではなく**、§0.9-5「関連度スコアが埋め込みだけで足りるか、LLM判定が要るか」は未解決のまま残る。

**したがって「3,000件」という候補数自体、この仕様からは導出できない。** 問題文が与えた前提として採用し、以降は「もし何らかの索引で3,000件に絞れたなら」という条件付きの計算として進める。これは実行できない箇所を実行できないと明記する規律に従うもの。R1〜R3 の検証は主に Policy/Loop の「発火条件」の欠落を指摘したが、本ラウンドで初めて**検索そのものの土台（クエリ→候補）が未設計**であることが判明した。これは §16 の Hermes Agent 比較（FTS5 全文検索を明記）との対比でも際立つ——比較対象のベースラインは索引技術を明記しているのに、Quirefold 自身はしていない。

### 1.4 θ_admit=0.6 を超える候補数の試算（推測）

3,000件の候補に対し、版解決（§7-1）とtombstone除外（§7-2）を適用する。過去7年、認証方針は各プロジェクトで平均3〜5回改版されたと**推測**すると、生存版（最新版のみ）は概ね 3,000 × 0.6〜0.7 ≈ **1,800〜2,100件**に減る（版として残る旧版はスコアリング対象から除外されるが、索引自体からは消えない点は §1.3 で述べた通り）。ここでは 2,000件を代表値とする。

次に `context.scope` による閉包フィルタ（ADR-0010 §2：現在の閉包＋祖先のみ可視）を適用する。ここで**PO の質問の実行文脈が特定プロジェクトに紐づいているか**で結果が大きく分岐する：

| ケース | 前提 | フィルタ後 | 根拠 |
|---|---|---|---|
| **(a) プロジェクト内で質問** | exec_context が `proj:X` に固定 | ~150〜300件（推測。当該プロジェクト自身の履歴＋祖先＝ドメイン直下の横断方針） | §2 の祖先包含ルールが機能し、他プロジェクト固有のエピソードは候補から外れる |
| **(b) 横断的な状態確認**（本シナリオの文面はこちら） | exec_context が特定プロジェクトに紐づいていない（スタンドアップ的な広い質問） | ~1,500〜2,000件（ほぼ減らない） | 祖先包含ルールは「今いる閉包の祖先」しか許可しないため、今いる閉包がドメイン root や person root なら、**どのプロジェクトの認証方針も「祖先」にならず、そもそも見えないか、逆に閉包解決ができずフィルタが実質機能しない**（§7「休眠トピックの復帰」が自認する循環問題と同型） |

問題文の「認証」質問はプロジェクト名を含まない状態確認質問であり、(b) に近いと判断する。この場合、閉包フィルタは実質的に機能しない（後述 3-(5)）。

続いて s_admit を計算する。関連度は3,000件がすべて「認証」という語で一次フィルタを通過している以上、平均的に中〜高（推測：平均0.55、標準偏差0.15の分布）。文脈一致度は (b) のケースでは差別化要因にならない（推測：平均0.3、ほぼ横並び）。確信度は経過時間ペナルティを受けるため平均0.5、顕著性は現在のゴールに紐づくもの以外低い（平均0.3）。

```
平均 s_admit ≈ 0.4×0.55 + 0.25×0.3 + 0.2×0.5 + 0.15×0.3
            = 0.22 + 0.075 + 0.10 + 0.045
            = 0.44
```

平均は 0.6 を下回るが、分布の右裾（関連度が特に高い＝実際に「方針」を明言した意味記憶エントリ）は 0.6 を超える。各プロジェクトが認証方針の意味記憶を平均2〜3件（現行版＋直近の議論の痕跡）持つとすれば、40プロジェクト×2.5 ≈ 100件、加えてエピソードのうち特に強い一致を示すもの（インシデント報告・レビュー記録）を50〜200件と見込み、**合計 150〜300件が θ_admit=0.6 を超える**、と推測する。

### 1.5 ワーキングセットの実効容量との比較

§6 はトークン・注意・プレフィックスキャッシュの3種の予算を挙げるが、**具体的な数値配分（コンテキスト窓のサイズ、ワーキングセットに割く割合）はどこにも書かれていない**。§0.9-4 が「予算配分比率」を未解決事項として明記しており、これは実行できない——「ワーキングセットの上限は§6の予算に収まるか」という問いに、仕様上は**答えが存在しない**。

やむを得ず一般的な値で試算する（推測）。仮に「準静的」層に4万トークンを配当し、見出し解像度（~10トークン/件）で全件を注入するなら4,000件収容できるが、§7 は繰り返し「小集合」「少数の出入り」と表現しており、実運用で意図されている作業集合サイズはおそらく数十件（推測：20〜50件）。要約解像度（~50トークン）まで含めれば実効容量は数百件程度に下がる。

いずれの見積もりでも、**150〜300件が θ_admit を超える一方、実効容量は数十〜数百件**であり、5〜10倍の入場希望が容量を上回る。この「一度に大量の新規候補が入場資格を得る」状況に対する選抜規則が存在するかを次節で検証する。

### 1.6 予算超過時の選抜規則の有無

§7「追い出しは予算駆動かつバッチ」は次のように書く：

> 予算超過 — まとめて大きく空ける（例: 予算の70%まで一気に落とす）

これは**既存の滞在エントリの退場**を扱う規則であり、「複数ターンにわたって蓄積した資格保持者のうち、どれだけ・どういう順で維持するか」を暗黙に扱っているように読める。しかし本シナリオのように**1回のクエリで150〜300件が同時に入場資格を得るバースト**に、この規則が適用されるとはどこにも明記されていない。仮に好意的に適用されると仮定しても、**「70%まで落とす」だけで、落とした後に残す70%を何順（s_admit降順か、他の基準か）で選ぶかの規則がない**。

`recall(query)`（能動リコール）は別途あるが、これは「明示リコール用」（§0.3）であり、`build_context()` が自動組み立てる際の絞り込みには使われない。

**結論：150〜300件 vs 実効容量数十〜数百件、という本シナリオが生む過負荷に対し、どれを選ぶかを決める規則は spec-memory のどこにも存在しない。実行できない。**

## 2. 動くこと

- **版解決（§7-1）・tombstone除外（§7-2）は N・候補数によらず機械的に働く。** LLM を使わない決定的フィルタであり、100万件でも1件でも同じコストで動く。
- **`origin: user_explicit` に対する `collision_candidates()` の即時点火（§20.4）は本シナリオでは正しく発火しない。** PO の発話は疑問文（「〜どうなってる？」）であり、§20.4 の疑問文除外規則（疑問語判定、ルールベース）がこれを正しく「新規の言明ではなく質問」と判定し、不要な衝突検査・再検証キュー投入をスキップする。driver 側の無駄な仕事を増やさない点で意図通り。
- **driver のキュー優先度計算（§20.3）は N に依存しない。** `po_message` は常に最高優先度であり、件数に関わらず即座に処理対象になる。分身の割当（既存分身へ渡すか fork するか、§21）もルールベースで N に依存しない。
- **文脈一致度（w2）による他ドメイン混入の抑止は、実行文脈が特定の閉包に正しく紐づいている限り機能する**（エントリ3の試算）。これは ADR-0010 §2 の祖先包含ルールが健全であることの裏付け。
- **アーカイブ降格は物理削除ではなく解像度制限として働き、§0.8「物理削除は原則行わない」の方針とは矛盾しない。** 後から必要になったときに見出しだけでも見つかる、という設計意図（§7-3）自体は一貫している。
- **強度（strength）を「弱い事前分布」に降格したこと自体は一貫している。** 減衰が主要な識別軸として機能していない（できていない）ことは、そもそも§13が「主役ではない」と自認しているので設計上の欠陥ではない。

## 3. 破綻・穴

### (1) 検索候補生成の機構が未設計

**(a) どの規模でも** — N に関わらず、クエリ文字列から候補集合を作る手段（全文検索・ベクトル近傍・両者の併用）が spec-memory・ADR-0010 のどこにも定義されていない。
**(b) 何が起きるか** — 「候補が3,000件」という前提自体がシミュレーションのための仮置きであり、仕様からは導出できない。実装時に初めて決める設計判断（§0.9-5 embedding要否）が、θ_admit の識別力そのものを左右する変数として残っている。
**(c) 節番号** — §7（候補集合の前段）、§8（クエリ生成）、§12経路A、§15、ADR-0010 §4。
**(d) Substrate か Policy/Loop か** — **Policy**（Substrateはembeddingを持たないと決めただけで、これは正しい判断。索引・検索アルゴリズムの設計自体がPolicy層に存在していない）。

### (2) θ_admit は絶対値であり、N・トピック頻度が増えるほど通過件数が増える

**(a)** N=100万・「認証」候補3,000件規模。**(b)** 推定150〜300件が閾値を超える（1.4節）。正規化・rank-normalize が無いため、この件数は corpus 規模とトピックの言及頻度に比例して際限なく増えうる。**(c)** §7（入場スコア式）。**(d)** Policy。

### (3) 予算超過時の選抜規則が存在しない（バーストアドミッション）

**(a)** 1ターンで入場資格保持者数が実効容量を大きく上回ったとき（本シナリオでは5〜10倍、1.5節）。**(b)** §7「予算駆動かつバッチ」の退場規則は既存滞在者の累積オーバーフローを想定した書き方であり、同一ターン内の大量新規入場に適用されるかが不明。仮に適用しても「70%まで落とす」の選抜基準（何を優先して残すか）が書かれていない。**(c)** §6・§7。**(d)** Policy。

### (4) 解像度階層（§9）に s_admit との対応規則がない

**(a)** 候補が θ_admit を超えた後、見出し／要約／全文のどれで注入するかを決める基準が量的な形で存在しない。**(b)** 150〜300件を予算内に収めるには解像度の使い分けが必須だが、「スコアが高いほど高解像度」のような規則がどこにも書かれていない。**(c)** §9。**(d)** Policy。

### (5) 閉包の可視性ルールは祖先方向のみで、横断（子孫方向）検索が未定義

**(a)** 実行文脈が特定プロジェクトの葉ノードに紐づいていない、より上位（ドメイン・person root）での質問のとき。**(b)** ADR-0010 §2 は「現在の閉包＋その祖先が候補になる」としか定義しない。今回のような「今どの店にもいない」状態からの横断質問（「dozens of projectsに散らばる認証方針」）は、祖先方向の包含だけでは原理的に届かない対象を含む。§7「休眠トピックの復帰」自身が「実行文脈自体が『どの話題か』に依存するため循環する」と自認しており、これは提案された緩和策（閉包レジストリの直接ルックアップ）でも横断ケースそのものは解決されない。**(c)** ADR-0010 §2、spec §7（休眠トピックの復帰）。**(d)** ADR-0010 §2 の規則自体（祖先包含）は健全な**Substrate**判断であり変更不要。ただし「横断検索」という機能が**Policy**層のどこにも存在しない。

### (6) アーカイブ降格は検索対象プールを一切縮小しない

**(a)** N に関わらず常に成立する設計上の性質（規模が大きいほど影響が顕在化）。**(b)** §7-3「アーカイブ層は検索対象から除外しない」と明記されているため、900万件規模のエピソードのうち大半がアーカイブされても、字面・LSH一次フィルタの走査対象からは一切消えない。減衰・アーカイブに「検索コスト抑制」を期待する読み方（§13「§16の検索コスト抑制」という記述）と、§7-3 の明示的な非除外規則は**内部で緊張関係にある**——§13は減衰の残る役割として「検索コスト抑制」を挙げるが、§7はアーカイブされても検索対象から外さないと明記しており、両者は同じデータについて逆方向のことを述べている。**(c)** §7-3、§13。**(d)** Policy（内部矛盾。P3 案件に相当）。

### (7) 見逃し・過剰混入が同一クエリで同時に起きる

**(a)** 本シナリオの構造そのもの。**(b)** エントリ1・2・3の試算が示す通り、同一の「認証」クエリに対し、①現役プロジェクトの方針は正しく入場する、②重要だが固有名詞を伴わない古いインシデント（エントリ2）は救済条件（強いエンティティ一致）に当たらず見逃される、③実行文脈が曖昧なら他ドメインの同名概念（エントリ3）が紛れ込みうる——**「関連度は高いが文脈不一致で削れるべきものが削れず、文脈不一致で削るべきでない重要な過去が削れる」という逆転が同時に起こりうる**。**(c)** §7「休眠トピックの復帰」（固有名詞がない場合の救済不発火）、§11（文脈一致度）。**(d)** Policy。

### (8) §16 の評価指標は本シナリオの型のクエリでは測定点を生まない

**(a)** N に関係なく、訂正を伴わない状態確認クエリ全般。**(b)** 見逃し率は「訂正イベント起点」（§16）で測るため、本シナリオのように PO が訂正しなければ測定対象そのものが発生しない。ノイズ率は自己申告方式の信頼性が未検証（§0.9最優先）で、行動観測代替（§16.1）は開発ドメイン限定かつコード編集・テストのような客観的行動が伴う場面向けであり、本シナリオのような対話的な状態確認では観測対象になる「行動」が乏しい。**(c)** §16、§16.1、§0.9-1。**(d)** Loop/評価基盤（Policy寄り）。

## 4. スケール限界の一覧

1. **同一トピックの生存版数（版解決後）が作業集合の実効容量を超えると、どれを入場させるかが未定義になる。** 壊れる条件：1クエリあたりの θ_admit 超過候補数 > 作業集合容量（本シミュレーションでは推定150〜300件 vs 数十〜数百件、5〜10倍）。§7・§6。Policy。
2. **既存の「予算超過」退場規則（§7）は、同一ターン内バースト入場を想定した選抜基準を持たない。** 壊れる条件：新規入場資格者数が単独で容量を上回る瞬間（複数ターンでの漸増ではなく、1回の質問で即座に発生する場合）。§7。Policy。
3. **アーカイブ降格・減衰は検索コストを一切下げない（§7-3が検索除外を禁じているため）。** 壊れる条件：なし（N とともに常に成立）。900万件規模でエピソードの大半がアーカイブされても一次フィルタの走査対象は縮小しない。§7-3、§13。Policy内の矛盾。
4. **検索候補生成の索引機構が spec に存在しないため、θ_admit通過件数・識別力そのものが実装依存で未検証。** 壊れる条件：常に成立（N非依存の欠落）。§7、§8、§15、ADR-0010 §4。Policy。
5. **閉包の可視性が祖先方向のみで、実行文脈が特定プロジェクトに紐づかない横断質問（今回のシナリオ）では、複数プロジェクトにまたがる認証方針への到達が構造的に保証されない。** 壊れる条件：exec_context がドメイン・person root 水準で、質問が複数の子孫閉包にまたがる内容のとき。ADR-0010 §2、spec §7。Substrateの規則自体は健全、Policyに横断検索機能が欠落。
6. **固有名詞を伴わない一般名詞トピック（「認証」）では、休眠トピック救済（§7、強いエンティティ一致免除）が発火せず、重要な古いエピソードが見逃される。** 壊れる条件：救済対象になりうる記憶が固有名詞・識別子を持たない一般概念に紐づくとき（本シナリオはまさにこれ）。§7「休眠トピックの復帰」。Policy。
7. **関連度スコアの算出手段（embedding か LLM 判定か）が未確定のまま候補数が数千規模になると、LLM判定案ではコストが候補数に線形比例して増大し、embedding無し案では識別力が下がって(2)を悪化させる。** 壊れる条件：embedding を初期実装で見送り（ADR-0010 §4 が許容する選択）、かつ広く言及されるトピックのクエリが発生したとき。§0.9-5、§15、ADR-0010 §4。Policy。
8. **深い睡眠の全件処理が N の増加とともに一晩の窓を超える（既に R3/S11 で試算済み：5万件で約7時間、100万件で約6日）。** 本シナリオの規模（100万件）はまさにこの限界の直上にあり、パラメータ再調整・アーカイブ降格・矛盾解消のケイデンス（日次／週次、§18）に間に合わなくなる。壊れる条件：シャーディングなしで単一writer（§19・§20.1）が全件走査する設計のまま N が数十万件を超えたとき。§14・§18・§20.1。Loop（既知・R3で指摘済み、本ラウンドで再確認）。
9. **§16 の評価指標は、訂正を伴わない状態確認型クエリに対して測定点を生まない。** 壊れる条件：このクエリ形式（本シナリオ）が全クエリの相当割合を占めるようになったとき、評価カバレッジが訂正発生パターンに偏り、システムの実際の性能の大部分が測定されないまま運用される。§16、§0.9-1。Loop/評価基盤。

## 5. 最小の修正案

**蓄積を始める前に決めておかないと手遅れになるもの（優先度順）：**

1. **`context` の閉包命名規約に、プロジェクト／ドメイン以外の「横断トピック」ノードを設けるか否かを決める。** 「認証方針」のようにプロジェクト横断で参照されたい概念に閉包上の居場所を用意しないと、限界5・6が恒常化する。この決定は ADR-0010 §2 が定義した「閉包識別子は開いている」という設計そのままで実現できる（Substrate変更は不要）が、**レジストリの命名規律・粒度は蓄積開始前に決めないと、後から数十万件を再スコープする移行コストを負う**（既に R3 が「閉包レジストリのライフサイクル」を未定義事項として指摘済み、本ラウンドで実害の例＝限界5として再確認）。
2. **関連度スコアの算出手段（embedding 採用可否）を初期実装の段階で決める。** ADR-0010 §4 は embedding をスキーマ外に置き「後から索引を再生成すればよい」としているが、限界7が示す通り、embedding無しで開始した場合の識別力低下は N が増えるほど顕在化する。「後から入れれば良い」は理屈上正しいが、N=100万規模での全件再埋め込みは相当なコストになるため、**軽くても構わないので開始時に何らかの embedding を入れておくことを推奨**（Substrate変更ではなくPolicy/インフラの判断だが、遅らせるほど高くつく）。
3. **候補生成のパイプライン（クエリ→索引→候補集合）を、§7 の候補集合の前段規則（版解決・tombstone除外・アーカイブ解像度・sensitive除外）の**前に**明記する。** 現状これが完全に欠落しているため（限界4）、θ_admit を含む Part II 全体の挙動がこの1点に懸けられている。これは実装設計の話であって Substrate ではないが、**実装より先に置くべき最優先の Policy 決定**（§16 が「実装より先に計測基盤を置く」と述べるのと同じ理由——先に測れないものは後からも測れない）。
4. **予算超過時のバースト選抜規則（限界1・2）と、解像度割当規則（限界4-2/(4)）に、s_admit を用いた明示的な優先順位（例：降順に予算が尽きるまで採用し、採用したものの中で上位X%のみ全文、以降は要約→見出し）を定義する。** 完全に可逆な Policy 変更のため蓄積開始前である必要はないが、**未定義のまま運用を始めると「なぜこの記憶が出てこなかったか」が事後に一切説明できない**（§16「可観測性」の要求そのものが成立しなくなる）ため、実装着手前に決めることを強く推奨する。
5. **§7-3（アーカイブは検索対象から除外しない）と §13（減衰の残る役割は検索コスト抑制）の矛盾を解消する。** どちらを優先するか（アーカイブされたものを一次フィルタの走査対象からも外すのか、外さないが解像度だけ絞るのかを維持し「検索コスト抑制」という表現を§13から削るのか）を決める。P3 の incident 案件として扱うべき。

## 6. 判定

**条件付きで動く**——決定的な前段フィルタ（版解決・tombstone除外・questionフィルタ・優先度計算）は N に依存せず健全に機能するが、θ_admit を超える候補の選抜・解像度割当・横断閉包検索・候補生成の索引機構という**検索の核心部分**が本シナリオの規模と質問形式（固有名詞なし・横断的）の組み合わせで軒並み未定義であり、現状の記述だけでは「PO の質問に何が返るか」を予測できない。
