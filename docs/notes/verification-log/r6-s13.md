# R6 / S13：検索品質の N 依存（記憶100万件）

**対象**: `docs/spec/memory.md`（版4.0、2026-07-26、§8.5 新設後）／[ADR-0010](../adr/adr-0010-memory-substrate-schema.md)（Substrate 正典）

**規律**: 好意的に解釈しない。実行できない箇所は「実行できない」と書く。書いていないことは補って正当化しない（未定義は未定義と書く）。節番号を必ず添える。推測は「推測」と明示する。

## 1. シミュレーション本体

### 1.0 前回（R4／S13）との関係

R4／S13 は「クエリ文字列から候補集合を作る索引・検索機構がそもそも存在しない」ことを見つけた（§8.5 新設の直接の契機）。本ラウンドは同じシナリオ・同じ発話を、新設された §8.5（Stage 0〜5）に対して走らせ、**土台ができたことで実際に何が変わったか／変わっていないか**を検査する。

### 1.1 前提設定

7年運用、4ドメイン・数十プロジェクト。本シミュレーションでは前回同様 **40プロジェクト**（**推測**、問題文の「数十」の代表値）、うち developer ドメイン（Kobo 配下）で「認証」に関連する実体を持つものを **15〜20プロジェクト**（**推測**）とする。「認証」関連エントリ数千件は問題文の指定。

PO 発話：「認証まわりの方針って今どうなってる？」。疑問形であり、固有名詞・閉包名を含まない。

### 1.2 検索候補生成パイプラインの構造は存在する（R4／S13 からの前進）

§8.5.0 は `retrieve(req) → { ranked[], clarify?, trace }` を「候補生成の唯一の入口」と定め、`build_context()` / `recall()` / `assemble_brief()` は必ずこれを通す（§0.3・§8.5.0）。Stage 0〜5 の6段が決定的に定義されている（§8.5.0 の表）。**したがって「候補を作る機構自体が存在しない」という R4／S13 の最上位の指摘は、構造としては解消している。** 以下、実際にこのシナリオでどこまで動くかを段ごとに追う。

### 1.3 Stage -1：`retrieve(req)` の各項は誰が用意するか（§8.5.0）

`req = { query, raw_utterance, closure_ctx, goal_stack, exec_context, mode, session_origin, addressee, budget, n }`。

| 項 | 由来 | このシナリオでの値 |
|---|---|---|
| `raw_utterance` | 呼び出し側（Session Loop）が直近発話をそのまま渡す | 「認証まわりの方針って今どうなってる？」。**埋まる** |
| `query` | §8 の材料4種（直近発話・アクティブなゴール・ワーキングセット内容・実行文脈）を合成したもの。**誰がどう合成するかの手続きは §8 にも §8.5.0 にも書かれていない**（文字列連結か、重み付き語集合かは未定義） | 材料自体は集まるが、**合成手続きが未定義のため厳密な中身は判定できない** |
| `closure_ctx` | 「driver の `exec_context` を閉包レジストリで解決したもの」（§8.5.0）。解決の実行主体は明記されていない | **判定できない**（下記 1.3.1） |
| `goal_stack` / `exec_context` | driver 提供（§0.3） | 形式上は埋まる。ただし本シナリオの発話はゴール・実行文脈に紐づかない広い質問なので、中身は汎用的（推測：具体的な認証タスクへの紐付けなし） |
| `mode` | 呼び出し元が固定（`build_context()` なら `context`） | `context`。**埋まる** |
| `session_origin` | セッションの起床源（§20.2） | PO のチャット発話 → `po_message`。**埋まる** |
| `addressee` | `mode != brief` のとき null | `null`。**埋まる** |
| `budget` | §6 の3予算から `budget_allocator` が算出 | 形式上は埋まるが、具体的な数値（トークン配分比率）は §0.9 が未解決事項として明記しており**値は不明** |
| `n` | `mode != recall` のとき null | `null`。**埋まる** |

#### 1.3.1 `closure_ctx` が未定義であることの帰結【本シナリオ最大の未決定要因】

**PO が「今どのプロジェクトにもいない」広い質問をした場合、`exec_context` が何を指すかを spec-memory・ADR-0010 のどちらも定義していない。** これは §8.5.4 の横断ファンアウトの発火条件1「`closure_ctx` が leaf でない」の真偽を直接左右する。

- **分岐(a)**：`closure_ctx` が `person`（root）または `domain:*` のような非 leaf に解決される場合 → §8.5.4 の条件1が真になり、横断ファンアウトが発火しうる。
- **分岐(b)**：banto のセッションが「直前に開いていたプロジェクト」を既定の実行文脈として引き継ぐ実装（多くの単一ワークスペース型ハーネスで自然な挙動）である場合、`closure_ctx` は `proj:X`（leaf）に解決される → 条件1が偽になり、**横断ファンアウトは発火しない**。

**spec-memory・ADR-0010 のどちらにも、実行文脈が特定プロジェクトに紐づいていない場合の既定値（「ホーム」擬似閉包の有無等）が定義されていない。** これは §8.5 が新設される前から存在した R4／S13-(5) の指摘（祖先方向しか見えない）の**入口側の未決定**であり、§8.5.4 自体は解決策を持つが、その解決策が発火するかどうかを決める入力が未定義のままである。

以下、**分岐(a)（横断ファンアウトが発火する）を主経路として計算を進める**が、**分岐(b) の場合は本節以降の資産一式が成立しない**ことを明記する。分岐(b) では、PO は「今開いているプロジェクトの認証方針＋その祖先」しか見えず、他の14〜19プロジェクトの認証方針には原理的に到達しない。しかも 1.7 で示す通り、この場合は `clarify`（聞き返し）も発火しない——「認証」は固有名詞ではないため Stage 0 は「複数候補から選べていない」状態を作らず、`unresolved[]` が空のまま終わる可能性が高い（§8.5.5「聞き返しの発火」参照）。**PO は自分が一部の答えしか受け取っていないことに気づく手段を持たない。**

### 1.4 Stage 0：エンティティ解決（§8.5.1）

`resolve_entities("認証まわりの方針って今どうなってる？")` を実行する。`entity_index` の供給元（閉包レジストリの識別子・表示名／`subject[]`／`external_ref`／`content.headline` から抽出した固有名詞・識別子／エイリアス表）のいずれにも「認証」という表記そのものは登録されない——「認証」は一般名詞であり、固有名詞・識別子の抽出規則（英数字を含むトークン、既知の識別子書式、レジストリ既知語との完全一致）に当たらない。

**結果**：`closures=[]`, `subjects=[]`, `refs=[]`, `entries=[]`。`mentions = resolve_entities(raw_utterance)` も同様に空。

- `closure_filter` は「解決できなければ実行文脈（`closure_ctx`）のまま」（§8.5.1）。**したがって `closure_filter` の中身は 1.3.1 の未決定に完全に従属する。**
- これは仕様自身が §7「休眠トピックの復帰」末尾で認めている制限と一致する：「一般名詞のトピックには救済が効かない（『認証』にはエンティティ一致が無い。R4／S13）」。**新しい機構はこの制限を解消するようには設計されていない**（見出し帯で受ける、という設計判断のまま）。

### 1.5 Stage 1：アーム検索と候補数の N からの切り離し（§8.5.2）

必須アーム A1（FTS）・A2（エンティティ）・A4（系譜近傍）・A5（最近性）＋任意 A3（ベクトル、D6 により初期実装では不採用と**推測**）。各アームは固定上限 `k_arm` を返す（値は §0.9 の未解決パラメータ。**推測**：`k_arm = 50`）。

- **A2 は 1.4 の結果よりゼロ件。**「認証」に対する強いエンティティ一致は本シナリオでは一件も発生しない。
- A1・A4・A5 は `closure_filter` の範囲内で動く。`closure_filter` が `proj:banto-web` 単体（分岐(b)）なら候補は数十件規模、`person` 祖先のみ（分岐(a)、横断ファンアウト抜きで見た場合）ならほぼゼロ件（`scope` が文字通り `person` のエントリはほぼ存在しないため）。

**構造的な結論（分岐に関係なく成立）**：`Σ k_arm` は N に依存しない定数であり、A1〜A5 それぞれが最大 `k_arm` 件しか返さない以上、**候補集合の絶対上限は N=100万件でも数百件のオーダーに収まる**（§8.5.2 の主張どおり）。これは §8.5 が実際に構造として持ち込んだ改善であり、R4／S13-(2)「θ_admit 超過件数が corpus 規模に比例して際限なく増える」への直接の答えとして機能する。**ここは仕様の記述から機械的に導ける結論であり、推測ではない。**

### 1.6 Stage 1 拡張：横断ファンアウト（§8.5.4）— 分岐(a)前提での計算

3条件（①`closure_ctx` が非 leaf、②Stage 0 が閉包を解決していない、③`session_origin == po_message` かつ `mode != brief`）のうち②③は本シナリオで確定して真（1.4・1.3 参照）。①は 1.3.1 のとおり未決定。

**分岐(a) を仮定して先へ進める**。子孫閉包ごとに上位 `m=2`（既定値、spec 明記）。認証関連の実体を持つ 15〜20 プロジェクト閉包から、各上位2件＝**30〜40件**が候補に加わる（**推測**）。ドメイン水準の閉包（4つ）からも上位2件ずつ＝最大8件が加わりうる。

**Stage 1 終了時点の候補集合サイズ（推測）**：A1/A4/A5 のベース検索（数件〜数十件、`closure_ctx` 自身のスコープ分）＋ファンアウト（30〜48件）＋アーカイブ二段照会分（1.6.1）を合わせて、**おおむね 50〜130件**。R4／S13 が仮置きした「3,000件」から大幅に縮小している。**候補数が N・トピック言及頻度に「比例して際限なく増える」という R4／S13-(2) の失敗形は、この規模では起きていない。**

#### 1.6.1 二段照会（アーカイブ層）— どちらが走るか

A2 は本シナリオで常時ゼロ（1.4）なので、条件(i)「A2 完全一致」は不成立。条件(ii)「active 層のヒットが定員（`K_ws + K_hl`）に満たないとき」を見る。`K_hl` の値は未解決パラメータ（**推測**：`K_hl = 150`）。1.6 で見積もった active 層ヒット数（50〜130件、うちアーカイブされていない現行分がさらに少ない）は `K_ws + K_hl`（**推測** `30 + 150 = 180`）を下回る可能性が高い——**したがって archive 層の追加走査は条件(ii)により発火すると推測できる**。

この判定は `K_hl` の具体値に強く依存する。`K_hl` を大きく取る運用（見出し帯を広く取ることが §0.8 の重み付けに沿う、§8.5.5）であるほど条件(ii)は満たされやすい。**値そのものが未定義である以上、断言はできない**——「条件付きで発火する（パラメータ依存）」に留める。

### 1.7 具体エントリ（ADR-0010 §1 の共通コア全フィールド）

以下4件を候補として想定する。**s_admit の重み `w1〜w4` は §7 のまま値が与えられていないため、`w1=0.4（rel_norm）, w2=0.25（文脈一致）, w3=0.2（確信度）, w4=0.15（顕著性）` を推測として置く**（4項和=1、θ_ws=0.6 と整合させるための仮定。R4／S13 と同じ置き方を踏襲）。閾値は `θ_ws=0.6`（spec 明記）、`θ_floor`（**推測**：0.35。`θ_ws` より低いこと以外は spec に値がない）、RRF 定数 `c=60`（spec 明記）。

```

        + 0.2×0.75(確信度・user_explicit・比較的新しい) + 0.15×0.55(顕著性・中)

**§8.5.4 の横断ファンアウトは「子孫閉包」を走査する際にドメインを問わない。** `closure_ctx = person`（分岐(a)）なら、`domain:kakei` も `domain:kobo` と同じく `person` の子孫であり、3条件（①〜③）はドメインに関わらず成立する。**したがって「認証」という語が developer ドメインと家計ドメインの両方に偶然存在する場合、ファンアウトはドメインを区別せず両方を候補に加える。** これは §0.2 が要求する「Substrate に開発固有語彙を入れない」設計（Quirefold は複数ドメインに開く前提）の裏面として、**検索側にもドメイン親和性の概念が無い**ことを意味する。

```
s_admit = 0.4×0.35(rel_norm・弱い一致) + 0.25×0.00(文脈一致・ドメイン不一致)
        + 0.2×0.55(確信度・比較的新しい) + 0.15×0.10(顕著性・低)
        = 0.140 + 0 + 0.11 + 0.015

### 1.9 定員内の順序（§8.5.5）

1. ピン留め：本ターンは訂正を含まないので該当なし。
2. 保護枠：話題転換直後（前ターンまでのワーキングセットは無関係）と仮定すれば該当なし（**推測**）。
3. 多様性クォータ：横断ファンアウトが効いている前提（分岐(a)）なら、子孫閉包ごとに1件を先取りする。**ただしこれは「θ_ws をクリアした候補の中での」順序規則であり、θ_ws 未達の候補（エントリ1・2を含む）を救済しない。** 「40プロジェクトのうち上位1つだけが全部通る、という潰れ方を防ぐ」（§8.5.4）という設計意図は、**θ_ws を超えた候補が複数閉包から出ている場合にのみ効く**。本シナリオの推測値のように、ほぼ全ての候補が θ_ws 未満に沈む場合、多様性クォータは実質的に空振りする。
4. `s_admit` 降順：滞在枠に入る候補があれば、ここで確定する。
5. 不応期：本ターンは初回アクセスなので該当なし。

### 1.10 §9 解像度割当とトークン予算

tier→解像度の対応は決定的（§9 表）：滞在枠→要約（〜50トークン）、見出し帯→見出し（〜10トークン）、非注入→注入なし。エントリ1・2は見出し（各〜10トークン）、エントリ3・4は注入されない。

### 1.11 driver 側で起きること（§20）

- **起床源**：PO のチャット発話であり `po_message`（§20.2）。優先度は常に最高（§20.3）で、他の作業を押しのけて処理される。
- **点火（§20.4）は発火しない。** 発話は疑問形（「〜どうなってる？」）であり、§20.4「言明と疑問文を区別する」のルールベース判定（疑問語・疑問符の有無）により、**新規の言明ではなく質問と判定され、`collision_candidates()` の同期実行はスキップされる**。これは意図どおりの動作であり、R4／S13 の「動くこと」節で確認済みの挙動が本ラウンドでも維持されている。
- **再検証キューへの新規投入は無い。** 本ターンは既存記憶を否定する主張を含まないため、§20.4 の「積む条件」表のいずれにも該当しない。
- **候補生成パイプライン（§8.5）自体は同期実行**（§20.7.1 の配線レジストリ「候補生成パイプライン」行：優先度＝「—（同期。キューに乗らない）」）。driver のキューには乗らず、このターンの中で完結する。

**もし直後に PO が「いや、それはもう古い、WebAuthn に移行した」と続けた場合**：それは `user_explicit` の言明になり、§20.4 の点火条件（`origin: user_explicit` の episode 記録）が満たされ、`collision_candidates()` が同期実行され、エントリ1（現行方針として提示したもの）が衝突候補として上がり、そのターンのうちにピン留めされる——という経路は本シナリオの1ターン目には現れないが、機構としては存在し発火条件も明確である。

## 3. 動くこと

- **候補集合の上限が N から構造的に切り離された**（項目3）。R4／S13 が最も重く指摘した「候補が corpus 規模に比例して際限なく増える」という失敗形は、この設計のもとでは起きない。100万件でも各アームは定数 `k_arm` しか返さない。
- **`rel_norm` は定義上 N 不変**（項目7）。候補集合内での相対順位づけという解法は、θ_ws の識別力が N で崩れるという R4／S13-(2) の後半部分に構造的な答えを与えている。
- **Stage 2 の決定的フィルタは仕様どおりに機械的に効く**（項目5）。特に F5（機微情報のゲート）は「番頭から自発的に持ち出さない」という規律を、本シナリオで実際に第三者言及エントリを落とすところまで再現した。
- **点火（§20.4）の疑問文除外は正しく機能する**（1.11）。PO の状態確認質問が誤って「訂正」として扱われ、無用な衝突検査・ピン留めを起こすことはない。
- **見出し帯という受け皿は、仕様が主張する通りの数値例（s_admit=0.40）で実際に機能する**（エントリ2）。ただし「機能する」の中身は「見出しとして存在を示す」までであり、内容の到達は番頭の能動的展開に懸かる（1.8）。

## 4. 破綻・穴

### (a) `closure_ctx` の既定値が未定義であり、横断ファンアウトが発火するかどうかを仕様だけからは決められない

**(a) いつ起きるか**：PO が特定プロジェクトに紐づかない広い質問をする、まさに本シナリオの発話そのもの。**(b) 何が起きるか**：§8.5.4 の発火条件1「`closure_ctx` が leaf でない」の真偽が決まらないため、横断ファンアウトが発火するのかしないのかが不定になる。発火しなければ PO は自分が「今いる」1プロジェクトの答えしか受け取れず、しかも `clarify` も発火しないため一部の答えしか得ていないことに気づけない（1.3.1）。**(c) 節番号**：§8.5.0（`closure_ctx` の定義）、§8.5.4（発火条件①）。**(d)** Policy（Substrate の `scope` 定義自体は健全。実行文脈の解決という Policy 側の配線が欠けている）。

### (b) 単独の正答であっても、θ_ws を跨ぐかどうかが仕様の記述だけからは決まらない

**(a)** PO の質問に対する最も直接的で正しい答え（エントリ1、現行かつ user_explicit の方針）が候補になったとき。**(b)** 推測した重みのもとで s_admit=0.5875、θ_ws=0.6 をわずかに下回り滞在枠に入らない（1.7・1.8）。w2（文脈一致度）の値をわずかに動かすだけで判定が反転する境界線上にあり、`w1〜w4` の具体値が未定（§0.9-4）である以上、**「PO の質問に対する正答が要約で提示されるか、見出しだけで止まるか」を仕様の記述だけからは予測できない**。**(c)** §7（`s_admit` 式）、§8.5.5（二段判定）、§0.9-4（パラメータ未確定）。**(d)** Policy。

### (c) 文脈一致度（w2）は広域・横断質問を構造的に不利にする

**(a)** 実行文脈が特定プロジェクトに紐づかない質問全般（本シナリオの質問形式そのもの）。**(b)** w2 は「記録時の文脈と現在の実行文脈の一致」を測るため、実行文脈自体が広い（あるいは無い）質問では、**内容がどれだけ的確でも w2 の寄与が一様に低く沈む**。θ_ws は固定の絶対値であり、この構造的な下押しを補正する仕組みが無い。「横断的な状態確認クエリ」というシナリオの類型そのものが、s_admit の設計から不利になる。**(c)** §7（`s_admit` 式・第2項）、§11-4（文脈一致度の定義）。**(d)** Policy（構造上の設計判断であり、重みの具体値の問題ではない）。

### (d) 多様性クォータは θ_ws 未達の候補を救済しない

**(a)** 横断ファンアウトで複数プロジェクトの候補が集まったが、その多くが θ_ws を下回っているとき（本シナリオの例示3件が全てこれに該当）。**(b)** §8.5.5 の多様性クォータは「θ_ws をクリアした候補の中で、閉包ごとに1件を先取りする」順序規則であり、θ_ws 未達の候補を滞在枠へ引き上げる効果は無い。「40プロジェクトのうち上位1つだけが全部通る、という潰れ方を防ぐ」という設計意図（§8.5.4）は、**候補の大半が θ_ws 未満に沈む横断質問では実質的に空振りする**。**(c)** §8.5.4、§8.5.5（定員内の順序、項3）。**(d)** Policy。

### (e) 横断ファンアウトはドメインを区別せず、ドメイン親和性の無い混入を許す構造を持つ

**(a)** `closure_ctx` が `person` root など複数ドメインの共通祖先に解決され、かつ複数ドメインに同じ語（「認証」）が偶然存在するとき。**(b)** §8.5.4 の3条件はドメインを区別せず、developer ドメインの質問に家計ドメインのエントリ（エントリ3）が候補として混入しうる。本シナリオの推測値では s_admit（w2=0・w4=低）が θ_floor を下回り実際には注入されなかったが、これは Stage 1/2 の構造的なガードではなく Stage 3 のスコアリングの結果に過ぎない。recall_count・salience が高い家計エントリであれば同じ経路で混入する。**(c)** §8.5.4（発火条件、ドメイン制約が無い）。**(d)** Policy。

### (f) `k_arm` によるアーム段の切り捨ては、事後の可観測性（§16）が個別エントリ単位で説明できない

**(a)** N が大きく、あるトピックに thousands 件が該当する状況全般（本シナリオそのもの）。**(b)** `arm.search()` の契約は上位 `k_arm` 件のみを `{entry_id, rank}` で返す。ある特定のエントリが「k_arm の外に落ちて候補にすら入らなかった」場合、そのエントリの ID・順位を記録する規定が無いため、`trace` はこの種の見逃しを個別エントリ単位で説明できない。Stage 2 のフィルタ落ちは説明できるが、**Stage 1 で候補に入らなかったものは説明できない**という非対称が残る。N=100万規模ではこちらが支配的な見逃し経路になりうる。**(c)** §8.5.2（アームのインターフェース）、§16（可観測性）。**(d)** Policy。

### (g) 横断ファンアウトの開示（「どの閉包を横断したか」）に実行層の強制箇所が無い

**(a)** 横断ファンアウトが発火するたび（分岐(a)が成立する場合すべて）。**(b)** §8.5.4 は「注入時に、どの閉包を横断したかを明示する」と述べ、§20.7.1 の配線レジストリも提示面を「会話」と記す。しかし §20.0 が要求する「④どこで強制するか」に相当する記述——このテキストを実際に生成する箇所——が本文に無い。散文の規律のまま残っている可能性がある（§20.0 自身が「散文の規律は素通りする」と警告している対象そのもの）。**(c)** §8.5.4、§20.7.1（横断ファンアウトの行）。**(d)** Loop（driver の配線）。

### (h) 死んだプロジェクトの閉包ライフサイクルが未定義であり、7年前のインシデントが今も到達可能かが不確定

**(a)** 過去に終了・畳まれたプロジェクトの記憶を、後年になってから general な質問で呼び戻そうとするとき（エントリ2がまさにこれ）。**(b)** R3 の残件（§20.8「閉包レジストリのライフサイクル…死んだプロジェクトの畳み方」）が未対処のまま残っており、`proj:legacy-auth-gw` のような閉包が今もレジストリ上で解決可能か、`scope` の値としてまだ有効かが不明。もし畳まれて識別子が失効していれば、V（可視性フィルタ）がこのエントリを弾く可能性がある。**(c)** §20.8（R3 残件）、§8.5.3（V フィルタ）。**(d)** Policy／Loop（閉包レジストリの仕様がそもそも本書に無い）。

## 5. 最小の修正案

1. **`exec_context` / `closure_ctx` の既定値を定義する。** PO がどのプロジェクトにも紐づかないセッション（ホーム画面・全体状況確認等）にいるときの既定閉包（例：`person` root、または新設する擬似閉包）を spec-memory または spec-multi-project 側に明記する。§8.5.4 の発火条件①はこの値に完全に従属しており、定義しない限り横断ファンアウトが「機構として存在するが、いつ動くか誰にも分からない」状態が続く。
2. **`w1〜w4`・`θ_floor`・`K_ws`・`K_hl` の暫定値を、蓄積開始前に少なくとも仮決めする。** §0.9 は「実装と eval を経ないと決まらない」としているが、本ラウンドの計算が示す通り、**これらの値次第で「PO の質問に対する唯一の正答が要約で出るか見出しで止まるか」が反転する**。暫定値すら無いまま蓄積を始めると、この閾値近傍の挙動は実装者の裁量に完全に委ねられる。
3. **横断質問（ファンアウト発火時）に限り、θ_ws のクリアと無関係に「閉包ごとの代表1件は滞在枠相当（要約解像度）で提示する」規則を検討する。** 現状の多様性クォータは θ_ws をクリアした候補にしか効かず（4-(d)）、「複数プロジェクトの roundup」という §8.5.4 の設計意図を、θ_ws 未達が支配的な横域質問では満たせない。
4. **横断ファンアウトにドメイン親和性の弱いフィルタ、または最低限の警告ログを足す。** 現状は closure 木のトポロジーのみで子孫を辿り、ドメインを区別しない（4-(e)）。完全な自動判定は難しくても、異なるドメイン間での混入が起きたことを `trace` に明示的に記録し、事後にパターンとして検知できるようにする。
5. **`trace` に Stage 1 の `k_arm` 切り捨てに関する集計情報（アームごとの切り捨て件数）を追加する。** 個別エントリ単位の説明は難しくても、「A1 で上位 `k_arm` 件に絞った結果、推定 X 件が候補に入らなかった」という集計は記録可能であり、見逃しの規模を事後に把握する手がかりになる。
6. **横断ファンアウトの開示テキスト生成を、§0.3.1 の `assemble_brief()` と同様に構造化された出力（例：`ranked[]` に `crossed_closures[]` を追加）として `retrieve()` の返り値に明記する。** 散文の約束（「明示する」）のままにせず、実行層の契約に落とす。
7. **閉包レジストリのライフサイクル（畳む・改名する・死んだプロジェクトを扱う）を定義する。** R3 の残件が未対処のまま7年運用シナリオで実害（エントリ2の到達可能性）として顕在化した。

## 6. 判定

**条件付きで動く。**

R4／S13 が指摘した最上位の欠落——「クエリから候補集合を作る機構がそもそも存在しない」——は §8.5 の新設によって解消された。候補集合の N からの切り離し（アームの `k_arm` 上限）と `rel_norm` の N 不変性は、仕様の記述から機械的に確認でき、推測に頼らず「動く」と言い切れる。これは本ラウンドで最も確度の高い前進である。

しかし本シナリオ固有の型——**固有名詞を含まない、横断的な状態確認クエリ**——に対しては、次の3点が未解決のまま残る。

1. **横断ファンアウトが発火するかどうかを決める入力（`closure_ctx` の既定値）が未定義**であり、機構自体の発火可否が判定できない（§2 項目6）。
2. たとえ発火しても、**この質問に対する唯一の正答（エントリ1）が滞在枠と見出し帯のどちらに入るかが、未確定のパラメータ（`w1〜w4`・`θ_floor`）次第で反転する境界線上にある**（§2 項目9、§4-(b)）。
3. **一般名詞トピックへの休眠救済は仕様自身が「効かない」と認めている**制限のままであり（§2 項目8）、見出し帯という受け皿は存在するが、内容への到達は番頭の能動的な展開判断に懸かっており、driver・memory どちらの決定的機構にも保証されていない。

土台（索引・候補生成・N 不変な正規化）は健全に構築された。**残っているのは「土台の上で、この質問の型に対して実際に良い答えが返るか」という、まさに本シナリオが問うていた問いであり、それは依然として仕様の記述だけからは確定できない。**
