# R6 / S18【新軸】：複数 PO・権限の異なる利用者

**対象**: `docs/spec/memory.md`（v4.0）／`docs/adr/adr-0010-memory-substrate-schema.md`（Substrate 正典）／`docs/VISION.json`
**検証者**: 敵対的シミュレーション（新軸・過去ラウンド未検証）
**規律**: 好意的に解釈しない。書いていないことは補って正当化しない。節番号を必ず添える。推測は「推測」と明示する。

**前提の確認（VISION.json）**：`target_users` は単数形で明記される——「AIエージェント群を率いて並行開発を行う**単独の**プロダクトオーナー（PO）」。`out_of_scope` に「チーム利用・マルチテナント（PO一人の道具として設計）」が明示されている。**したがって S18 は VISION が公式に対象外と宣言した領域そのものである。** これは「対象外だから検証しない」理由にはならない——本シナリオの目的は前提が破れたときに何が壊れるかを具体化することであり、以下はその報告である。ただし「VISION がこの前提を対象外と明記している」という事実自体は§6判定の一部として記録する。

---

## 1. シミュレーション本体

### 1.1 (1) 2人目の参加

Y が `proj:banto` の共同オーナーになる。Y の発話は `record()` を通じて `origin: user_explicit` の episode として記録される（spec §2 共通コア）。

**この時点で何が起きるか**：Substrate のどのフィールドにも「これは A の発話か Y の発話か」を区別する専用の場所が無い（詳細は検査表 #1）。`session_id` は「並行識別＋出典独立性判定」（spec §2 共通コア）のためのものであり、人間の身元とは無関係——同一人物が2つのセッションを開けば `session_id` は2つに分かれるし、逆に複数人が同じセッションIDを共有する構造を禁じる規定もない。`origin: user_explicit` は「PO の発話」という**カテゴリ**であって「どの PO か」という**識別子**ではない（ADR-0010 §1.2 の定義：「PO の発話」の "PO" は単数形の暗黙前提）。

**A に見えるもの**：変化なし。従来通り `proj:banto` と `person`（祖先閉包）配下の全記憶。
**Y に見えるもの**：新規セッションを開いた瞬間から、`proj:banto` scope と `person` scope（祖先）の記憶が ADR-0010 §2 の閉包包含規則に従って注入される。Y が「これは A 個人の流儀であり team の規約ではない」と判別する手段は無い——`context.scope: person` はそれが「横断する」ことしか示さず、「誰の person か」を示さない（検査表 #9 に直結）。

### 1.2 (2) 方針の対立

A の既存意味記憶 **E1**（後掲、`preference_decision`「レビューは全部見たい」）に対し、Y が「軽微な変更は自動マージでいい」（**E2**、後掲）と述べる。

**driver（§20）の挙動を段階的に追う**：

1. **起床源**（§20.2）：Y の発話は `po_message` として単一の作業キューに入る。起床源の定義（§20.2 の表）には「どの人間の po_message か」という下位区分が無い——`po_message` は5種類の起床源のうちの1つのenum値であり、A の発話と Y の発話は同一の起床源種別として扱われる。
2. **優先度**（§20.3）：`po_message` は base=最高。区別が無いので Y の発話も A の発話と同格で最優先枠に入る。
3. **点火**（§20.4）：「`origin: user_explicit` の episode が `record()` されたら、Steward Driver は同期的に `collision_candidates()` を呼ぶ」。Y の episode は同一閉包 `proj:banto` の既存意味記憶 E1 と語彙的に近接するため、候補が1件以上返る。**この時点で機械的に「訂正」と判定される**（§12「訂正 ＝ `origin: user_explicit` の言明であって `collision_candidates()` が既存の生きた意味記憶を1件以上返したもの」）。この定義は発話者が誰かを問わない。
4. **ピン留め**（§7・§20.4）：候補が1件以上あるので、Y の新しい episode はそのターンのうちに `pin()` される。「訂正はピン留めし、確率的な機構に一切委ねない」（§0.8）の対象に、A ではなく Y の発話が入る。
5. **緊急伝播**（§19）：ピン留め対象の訂正は「緊急無効化チャネル」の対象になる。実体は `changes_since(cursor)`（§19）——**もし A がこの瞬間まさに別セッションで作業中なら、A の生きた分身のワーキングセットから E1 が無効化される**。A は自分が何も言っていないのに、Y の発話によって自分のセッションの前提が書き換わる。これは §19「体験として悪い——自分が何もしていないのに前提が途中で変わる」が明示的に禁じたい体験そのものだが、その禁止は「他セッションの活動」全般に対してであって「他の人間の発話」に対する追加の防御ではない。
6. **矛盾解決**（§12・ADR-0010 §1.3）：`fact_type: preference_decision` の規則は「最新性が勝つ。ただし origin 優先が先に効く」。E1・E2 はともに `origin: user_explicit` なので origin 優先は発火せず（両方とも同一カテゴリ）、**fact_type 別規則＝最新性のみで裁定される**。Y の発言時刻が新しいため E2 が勝つ。
7. **裁定の配線**（§12「検出結果を裁定へ配線する」）：深い睡眠が敗者側（E1）に対し `supersede()` を呼び、`tombstone: true` の新版 **E1-v2** を作る。`derived_from` に E1(v1) と E2 の両方を含める。
8. **再検証・通知**：訂正由来は即時消化（§20.4）、通知は個別（§21「訂正由来の再検証で PO の判断が要ると判定されたもの」）。**この通知が A に届くとき、それは「あなたの以前の方針は Y の発言によって上書きされました」という内容になるはずだが、通知の文面規則（§21）はそこまで踏み込んでおらず、A・Y のどちらに宛てた通知かという宛先の概念自体が spec に無い**（検査表 #4・#8 に関連）。

**A に見えるもの**：次にセッションを開くと（あるいはリアルタイムで緊急伝播により）、レビュー全件確認の方針が「自動マージ可」に置き換わっている。E1(v1) は監査可能な旧版として残るが、**現に注入される記憶は E2 側**であり、A から見ると「自分が言っていないのに方針が変わった」状態になる。§0.7 の1位（ユーザーの訂正が消える）が定義する被害を、A が Y 起因で受ける。
**Y に見えるもの**：自分の発言が「訂正」として最優先で処理され、即座に反映される。Y にとっては正常に機能しているように見える——Y は自分の発言が A の既存決定を破棄したことにも、緊急伝播が起きたことにも気づく手段が無い（§20.4 のピン留め・緊急伝播はセッション内部の処理であり、Y への「あなたはいま A の方針を上書きしました」という明示は spec に規定が無い）。

### 1.3 (3) 機微情報の非対称

A が過去に Y について書いた判断が `sensitive: true`・`subject: ["party:Y"]` で数十件ある（例：**E3**、後掲）。深い睡眠で蒸留された派生 **E4**（後掲）も存在する。

**F5 ゲートの検査**：§7-F5／§8.5.3 の F5 は「`sensitive: true` は、PO との直接対話（`session_origin == po_message`）で、かつ PO がその主体・エンティティに言及したターンでのみ候補に入れる」。判定は `resolve_entities(raw_utterance)` が返す `mentions`。

Y が話しかけているセッションの `session_origin` は **`po_message` である**（Y は「PO」ではなく「共同オーナー」だが、起床源の enum に Y 専用の値は無い＝(1) で確認済み）。したがって F5 の第一条件「PO との直接対話」は Y のセッションでも常に真になる。第二条件「PO がその主体に言及したターン」は `mentions` が `party:Y` を含むかどうかで決まる——**Y が自分自身について何か発言すれば（「なんで私だけレビューが厳しいんですか」等）、`resolve_entities()` は `party:Y` を解決し、`mentions` に含める。** F5 はこの状況と「A が Y について話している状況」を区別しない。**結果、E3・E4 は Y 自身のセッションで、Y が自分自身に言及した瞬間に候補資格を得る。**

F5 は元来 ADR-0010 §5 の「番頭から自発的に持ち出さない」の実装であり、想定していたのは「A が Y について何度も話す3人称の状況」である。ADR-0010 §5 が課す3つの義務（職人への理由非開示・自発的非開示・自動可視範囲拡大の対象外）のどれも「**主体自身に見せない**」を明示的に定めていない——この保護目的自体が ADR-0010 に存在しない。

**F4（`subject[]` 除外）は救えない**：§8.5.3 Stage2 の F4 行は明記されている——「`mode == brief` のとき、`addressee` が `subject[]` に含まれるものを除外する」。(3) は Y が Banto と直接対話する場面であり `mode == context`（または `recall`）。`req` のシグネチャ（§8.5.0）でも `addressee` は「`mode == brief` のときの宛先（職人）。他モードでは null」と明記されている。**`mode == context/recall` には「話者自身が subject である場合に除外する」という F4 相当の規則が存在しない。** これは節番号付きで明確に**未定義**と判定できる（§8.5.3 に該当行が無い、§8.5.7 の mode 別差分表にも該当セルが無い）。

**s_admit の計算（(3)）— E4 を候補として評価**（重み・値は推測。式は §7・§8.5.5 のまま）：

```
s_admit = w1·rel_norm + w2·文脈一致 + w3·確信度 + w4·顕著性
```

推測パラメータ：`w1=0.4, w2=0.2, w3=0.2, w4=0.2`（§8.5.5 に重みの具体値は無いため按分で仮置き）

| 項 | 値（推測） | 根拠（推測の中身） |
|---|---|---|
| rel_norm | 0.50 | Y の発話が `party:Y` に言及し A2（エンティティ完全一致）がヒット。RRF融合後の相対順位として中程度と仮定 |
| 文脈一致 | 0.70 | 同一閉包 `proj:banto` 内での発話なので一致度は高いと仮定 |
| 確信度 | 0.55 | E4 は `agent_inferred` 寄りの蒸留物（後述の合成規則により実際は `user_explicit` を継承——下記参照）で経過時間ペナルティがかかるとして中程度と仮定 |
| 顕著性 | 0.55 | E3 の salience(0.65) を上限として合成（§0.3.0 合成規則）、やや下げて仮定 |

`s_admit = 0.4×0.50 + 0.2×0.70 + 0.2×0.55 + 0.2×0.55 = 0.20 + 0.14 + 0.11 + 0.11 = 0.56`

`θ_ws = 0.6`（spec 確定値）。`0.56 < θ_ws` → 滞在枠には入らない。`θ_floor`（推測 0.30、spec は具体値未確定）を上回るため **tier = headline（見出し帯）**。

**ここが致命的な点**：headline 解像度であっても `content.headline` はそのまま提示される。I5（§0.3.0）は「`headline` は結論のみ」と定めるだけで、`sensitive` の場合に headline 自体を丸める規則は §9 に無い（§9 の `sensitive` 規則は `assemble_brief()` 限定——「`sensitive: true` は tier に関わらず `assemble_brief()` では `headline` のみ」——**これは「headline だけ載せる」という**解像度の絞り込みであって「headline すら見せない」ではない）。したがって Y のセッションでは「Y は独断で進めがちだと A が判断した」に類する結論文がそのまま画面に現れる。**F5 が「候補に入れる」を許してしまった時点で、tier が headline に落ちても保護にならない。**

### 1.4 (4) 権限の差

Y は `repo:banto/web` にしか関与すべきでない。

ADR-0010 §2 の閉包メカニズムを精読すると：「注入可否は閉包の包含関係で決まる：**現在の実行文脈が属する閉包**と、その祖先に属する記憶が候補になる」。この一文の主語は「現在の実行文脈（`closure_ctx`）」であり、「その実行文脈を設定できるのは誰か」を制御する記述が存在しない。`closure_ctx` は driver の `exec_context`（§0.3「driver が提供するもの」：「リポジトリ・作業モード等」）から解決される——**つまり closure_ctx は「今どこで作業しているか」の申告であり、人間の身元に紐づく許可リストではない。** Y が `proj:banto` 全体を指すクエリを発すれば、closure_ctx をそこに設定することを止める機構は無い。

§2.2 の追記も同じ方向で書かれている：「PO 自身は全閉包のオーナーであり、子孫方向は『見えない』のではない」——この一文は単一 PO を前提に「PO は全部見てよい」と述べているのであり、**複数の人間がいて、そのうち一部だけが「全閉包のオーナー」である場合の記述が無い**。

### 1.5 (5) 横断ファンアウト

Y が `proj:banto` 水準で「認証の方針どうなってる？」と訊く。§8.5.4 の発火条件（決定的、3つの AND）：

1. `closure_ctx` が leaf でない（`proj:banto` は子（`repo:banto/web`、`repo:banto/api` 等）を持つ）→ **真**
2. Stage 0 が特定の閉包を解決していない（「認証」は一般名詞でリポジトリを名指ししていない）→ **真**
3. `session_origin == po_message` かつ `mode != brief` → **真（Y のセッションでも真。(1)(3)と同じ理由）**

**3条件がすべて満たされ、ファンアウトが発火する。** §8.5.4 は「PO 主体のセッションに限る」という条件を `session_origin == po_message` **だけ**で表現しているが、この条件は「自律ループでないこと」しか区別しておらず、「A か Y か」を区別しない（検査表 #4・#7）。

**s_admit の計算（(5)）— `repo:banto/api` の認証方針エントリ E5（後掲）を候補として評価**（推測は明示）：

同じ重み `w1=0.4, w2=0.2, w3=0.2, w4=0.2`（推測）

| 項 | 値（推測） | 根拠（推測の中身） |
|---|---|---|
| rel_norm | 0.55 | 「認証」は一般名詞でA2（エンティティ完全一致）が効かない（§7「一般名詞のトピックには救済が効かない」）。A1(FTS)頼みでやや低めと仮定 |
| 文脈一致 | 0.35 | `repo:banto/api` は Y の主活動域 `repo:banto/web` と異なる。文脈一致度は低いと仮定。エンティティ免除が効かないため経過時間ペナルティ等の減点も免除されない |
| 確信度 | 0.75 | `origin: user_explicit` の確立済み preference_decision。相応に高いと仮定 |
| 顕著性 | 0.50 | 中程度と仮定 |

`s_admit = 0.4×0.55 + 0.2×0.35 + 0.2×0.75 + 0.2×0.50 = 0.22 + 0.07 + 0.15 + 0.10 = 0.54`

`0.54 < θ_ws(0.6)` → 滞在枠には入らないが `θ_floor`（推測）は上回り **tier = headline**。多様性クォータ（§8.5.5：「横断モードのときだけ、子孫閉包ごとに1件」）と閉包あたり定員 `m=2`（§8.5.4）の枠内に収まる想定。

**headline として提示された時点で漏れが成立する**うえ、§8.5.4 は「注入時に、どの閉包を横断したかを明示する」ことを明示的に要求している——**これは PO が横断に気づけるようにする担保のための規定だが、Y のセッションでは同じ規定が逆に作用し、「`repo:banto/api` から拾いました」と Y に対して能動的に開示してしまう。** (4) で Y に見せたくないはずの `repo:banto/api` の存在そのものが、保護のための開示メカニズムによって Y に伝わる。

**A に見えるもの**：変化なし。
**Y に見えるもの**：`repo:banto/web` 以外の閉包（`repo:banto/api` 等）の認証方針の見出しと、その出典閉包名。(4) の意図（Y は `repo:banto/web` のみ）が閉包メカニズムでは実現されていないことの直接証拠。

### 1.6 (6) A の離脱

1年後、A がプロジェクトを離れる。

- **`person` scope の記憶**：ADR-0010 §2 の閉包包含規則は「祖先」に基づいて注入されるだけで、「その祖先エントリを記録した人間が今もいるか」を問わない。A の個人的な流儀（`scope: person`、例：r4-s16 で検証済みの「コミットは Why 中心」型のエントリ）は、A が離脱した後も **Y のセッションに注入され続ける**。これが「チームの規約として妥当だから残すべき」なのか「A 個人の趣味であり Y には無関係」なのかを判定する仕組みが無い——両者を区別する情報自体が Substrate に存在しない（`subject[]` は「誰についてか」であって「誰の視点の記憶か」ではなく、E1 型のエントリの `subject[]` は通常 `["self:po"]` のような値になり、A・Y の区別に使えない。検査表 #1 と同根）。
- **self-model（§22）**：Banto インスタンスに1つしかなく、「誰の番頭か」を持つフィールドが無い。§20.5-8 の再レビュー契機は「`last_reviewed` から一定期間経過」「`model_migration`」の2つのみで、**「PO が交代した」はどちらにも該当しない**——つまり A 離脱は self-model の再レビューを一度も引き起こさない。A の在任中に承認された口調・判断の優先順位（§22 のフォーマット案の「1. ユーザーの安全性 2. タスクの正確性 3. 応答速度・簡潔さ」等）が、Y の下でも無条件に有効であり続ける。
- **§25 のユーザー統制**：直接編集・削除の導線は「ユーザー」を単数として書かれている。A 離脱後、この導線に対する権限が Y に自動的に引き継がれるのか、Y が新たに主権者として認定される手続きが要るのかは規定が無い。

**Y から見た番頭は誰の番頭か**という問いへの spec 上の答え：**規定が無い。** Banto は「誰の記憶を持ち、誰の性格を体現しているか」を一度も明示的に問わない設計になっている（単一 PO 前提のため、この問い自体が発生しない設計）。

### 1.7 具体エントリ（ADR-0010 §1 共通コア・全フィールド）

上の各段で「後掲」とした5エントリを、ADR-0010 §1 の共通コアの実フィールド順で書き下す。値はすべて仮の具体値（プレースホルダではなく実際の値の形）。

#### E1 — A の方針（`preference_decision`、(2)の敗者）

```

kind          semantic
fact_type     preference_decision
content       headline: "proj:banto のレビューは全て A が目視する"

              full:     "2025-08-03T10:02:00Z の episode より。「まだ自動マージは早い、全部見る」との発言を反映。"
created_at    2025-08-03T10:05:00Z
valid_from    2025-08-03T10:02:00Z
valid_until   null   （後に2026-07-20T14:33:00Zで埋まる想定。ADR-0010 §3「旧版のvalid_untilを新版のvalid_fromで埋める」）
origin        user_explicit
sensitive     false
session_id    sess-2025-08-03-a-01
context       { scope: "proj:banto" }
derived_from  [mem-01K1AREVIEWEPISODE1]
external_ref  []
version       1
```

## 3. 動くこと

- **origin優先（user_explicit > agent_inferred/external）自体は健在**：AもYも、番頭自身の推論に自分の発言を無断で上書きされることはない（ADR-0010 §1.3・§0.3「supersede()はorigin優先を実行層で強制する」）。壊れているのは「user_explicit同士」の扱いであって、「PO対エージェント」の防御線ではない。
- **版管理による監査可能性は失われない**：(2)でE1が敗れても、E1(v1)は`superseded_by`で辿れる旧版として残り、tombstone版E1-v2の`derived_from`にE1(v1)とE2の両方が記録される（§12「検出結果を裁定へ配線する」）。**何が起きたかは追跡できる**——問題は「現在アクティブなのはどちらか」の裁定基準であって、記録の消失ではない。
- **`sensitive`のI2継承・`subject[]`のI7和集合は世代を超えて機能する**：E3→E4の蒸留でも`sensitive: true`と`subject: ["party:Y", ...]`は正しく継承される（§0.3.0 I2・I7）。継承のメカニズム自体は正しく動く——**破綻しているのはこの先の読み出しゲート（F4/F5）側であって、書き込み側の継承規律ではない。**
- **ファンアウトの流量制御（m=2、閉包あたり定員、多様性クォータ）は決定的に機能する**：§8.5.4の量的な歯止めは人間の識別が無くても動く。**問題は「誰に対して」ではなく「何を」流すかを止められないことであり、量の制御と質（権限）の制御は別軸**という診断が明確に立つ。
- **矛盾の検出（§12経路A）自体は正しく発火する**：EY2の記録時にE1が候補として引っかかるのは設計通り。**壊れているのは検出後の裁定基準（最新性のみ）であり、検出機構そのものではない。**

## 4. 破綻・穴

### 4.1 origin では発話者を区別できない（#1・#2 の根）

- (a) いつ起きるか：Y が最初に発話した瞬間から常に。
- (b) 何が起きるか：`origin: user_explicit`はカテゴリであって身元でないため、A の発言かY の発言かをSubstrateのどのフィールドからも機械的に読み取れない。この欠如が(2)(3)(5)(6)全てに伝播する根本原因。
- (c) 節番号：ADR-0010 §1（共通コア）・§1.2・§7（`authored_by`の定義）・§8（`subject[]`の定義）
- (d) **Substrate**。新規フィールド（人間の識別子）が要る。既存フィールドの意味を転用しても（例：`subject[]`に発話者を書く）ADR-0010 §8が定めた「主体＝誰についてか」の意味論と衝突し、二重の意味を持たせることになる。

### 4.2 Y の発言が A の方針を「訂正」として無条件に上書きする

- (a) いつ起きるか：Y が既存の`preference_decision`と語彙的に衝突する発言をした瞬間（(2)）。
- (b) 何が起きるか：§12のfact_type別規則（最新性）が同一origin内でしか働かないため、Yの発言がAの確立済み方針を最新性だけで上書きする。ピン留め・緊急伝播（§19）・最優先キュー（§20.3・§20.4）という「訂正保護」の全機構が、A自身の自己訂正と同じ強度でYの上書きに動員される。Aが同時にセッション中であれば、Aの生きたワーキングセットが本人の発言なしに無効化されうる（§19緊急無効化チャネル）。
- (c) 節番号：spec §12（矛盾解決規則）・§0.7（1位）・§19（緊急伝播）・§20.4（点火・ピン留め）
- (d) **Policy/Loop**（規則自体はPolicy層）だが、**根本原因は4.1のSubstrate欠如**——actor識別が無い限りPolicy側でどう規則を書き直しても「同一origin内の主体差」を条件に含められない。

### 4.3 敗者版（tombstone）が「誰の主張が敗れたか」を構造化フィールドで残せない

- (a) いつ起きるか：4.2の裁定が確定し、深い睡眠がE1に対しtombstone版E1-v2を作る瞬間。
- (b) 何が起きるか：E1-v2の`subject[]`は§0.3.0のI7（和集合）によりE1・E2両方の`subject[]`の和集合になるが、E1もE2も典型的には`subject: ["self:po"]`のような値になり（(2)の具体例参照）、**「A対Yの対立だった」という情報がsubject[]から読み取れない**。復元できるのは`content.full`の自由文だけであり、これはADR-0010 §8が`subject[]`導入で回避しようとした「主体が自由文の解釈に落ちる」問題（§8「可視範囲・機微性・引き継ぎの3つがすべて自由文の解釈に落ちる」）の再発である。
- (c) 節番号：spec §0.3.0（派生エントリのフィールド合成規則・I7）・§12（検出結果を裁定へ配線する）・ADR-0010 §8
- (d) **Substrate**（`subject[]`の値域と合成規則の設計が起点）。

### 4.4 sensitiveゲートは「主体自身が話者」の場合を想定していない

- (a) いつ起きるか：Y が自分自身に言及するあらゆる発話（(3)）。
- (b) 何が起きるか：F5は「PO発話か」×「主体に言及したか」の2条件しか見ず、話者と主体の一致・不一致を区別しない。Yが自分自身について何か言えば、AがYについて書いたsensitiveな判断（E3・E4）が候補資格を得る。F4（`subject[]`除外）は`mode == brief`限定であり、`context`/`recall`モードには相当する規則が存在しない。s_admit計算（§1.3）ではtier=headlineに落ちるが、headline自体に`content.headline`の結論文が乗るため、tierが下がっても情報は漏れる。
- (c) 節番号：spec §7-F5・§8.5.3（Stage2 F4/F5行）・§8.5.7（mode別差分表）・ADR-0010 §5
- (d) **Policy**（F5の判定条件を拡張すれば原理的に直せる）が、判定条件に「話者の識別子」が要るため**4.1のSubstrate欠如に依存**。ADR-0010 §5自体にもこの保護目的（主体自身から隠す）を明記する改訂が要る。

### 4.5 閉包は権限ではなくロケーションの既定値でしかない

- (a) いつ起きるか：Y が `repo:banto/web` に限定されるべきという運用上の要求が生まれた瞬間（(4)）から常に。
- (b) 何が起きるか：ADR-0010 §2は「現在の実行文脈が属する閉包」を主語にした可視範囲の既定則であり、「誰がその実行文脈を設定してよいか」を制御しない。Yが`proj:banto`水準やそれ以上でBantoに話しかけることを止める機構が存在しないため、(4)の要求はそもそも実現不能。
- (c) 節番号：ADR-0010 §2・§2.2
- (d) **Substrate/Policy 境界の欠落**——スキーマとしての`scope`はSubstrateだが、「誰がどの`closure_ctx`を設定してよいか」を制御するアクセス制御層はSubstrateにもPolicyにも一度も定義されていない。新設が要るのはGovernance層寄りの新規機構。

### 4.6 横断ファンアウトが(4)の権限意図を積極的に破る

- (a) いつ起きるか：Y が `proj:banto` 水準で閉包を特定しない質問をした瞬間（(5)）。
- (b) 何が起きるか：§8.5.4の3条件がすべて満たされ発火する。「PO主体のセッションに限る」という歯止めが`session_origin`のみで表現されているため、AとYを区別できない。加えて「どの閉包を横断したかを注入時に明示する」という**A向けに設計された透明性の担保**が、Yに対しては`repo:banto/api`のような本来見せたくない閉包の存在そのものを能動的に開示する結果になる。
- (c) 節番号：spec §8.5.4
- (d) **Policy**（発火条件へのアクター識別追加が必要）だが4.1・4.5に依存。

### 4.7 `person` rootの単一性が2人の個人領域を強制合流させる

- (a) いつ起きるか：Y が参加した瞬間から構造的に(常時)。
- (b) 何が起きるか：`person`は非パラメータのリテラル予約語。AとYそれぞれの個人的な流儀・判断が同一の閉包識別子に同居し、(2)の対立が`proj:banto`だけでなく`person`水準でも起こりうる。祖先方向の横断注入（ADR-0010 §2）は「誰のperson scopeか」を区別せず全て`proj:banto`へ流れ込む。
- (c) 節番号：ADR-0010 §2
- (d) **Substrate**（予約語の設計そのもの）。

### 4.8 A離脱時のオフボーディング手順・self-model所有権が未定義

- (a) いつ起きるか：A がプロジェクトを離れた瞬間（(6)）。
- (b) 何が起きるか：A の`person` scope記憶は祖先包含規則により Y のセッションへ注入され続ける（除外する機構が無い）。self-modelの再レビュー契機（§20.5-8）は「`last_reviewed`経過」と「`model_migration`」の2つのみで「PO交代」を含まない。§25の統制導線の主権者引き継ぎ手続きが無い。
- (c) 節番号：spec §20.5（自己内省の点検表・8行目）・§22・§25、ADR-0010 §2
- (d) **Policy/Loop**（点検項目の追加は可逆）だが、「誰の記憶か」を判定する入力（4.1）が無いと機械的なオフボーディング処理自体が組めない。

## 5. 最小の修正案

**筆頭（蓄積開始前にしか直せないもの）**

1. **[Substrate・最優先] 共通コアに人間の発話者を識別するフィールドを追加する。** 例：`actor_id`（開いた識別子、列挙にしない——ADR-0010 §7・§8と同じ規律）。現状 `authored_by` はLLM実行系専用、`subject[]`は内容の主体専用であり、いずれも流用すると意味論が二重化する。このフィールドが無いと、検査表#1・#2・#3・#4・#5・#8が原理的にPolicy層で修正不能である（Policyの規則は識別できる入力にしか条件を書けない）。**蓄積開始後に追加しても過去のuser_explicitエントリは「誰の発話か」を永久に区別できない**——ADR-0010が`authored_by`・`subject[]`について繰り返す「今しか直せない」という論理がそのまま適用される。

2. **[Substrate・最優先] `person` 予約語をパラメータ化する。** `person` → `person:<actor_id>` のように、単一リテラルをやめる（1のactor_idに依存）。現行のまま複数PO運用に入ると、既存の`scope: "person"`という文字列参照（`derived_from`の先の閉包解決、エイリアス表、外部の`external_ref`等）を含む全エントリの移行が後から必要になり、閉包識別子は`derived_from`を通じて監査系譜に刻まれているため、書き換えは版系譜の意味を壊さずには行えない可能性が高い。

**次点（Policy/Loopで対応可能。ただし1・2に依存）**

3. **[Policy] §12のfact_type別規則に「同一originでもactor_idが異なる場合は無条件の最新性優先を止める」規則を追加する。** 異なる主体間の対立は「訂正」ではなく「未解決の矛盾」（§12「未解決の矛盾を溜めない」の保留状態）として扱い、両論併記のうえPOへ通知する経路に流す。

4. **[Policy] F5に「話者自身のactor_idがsubject[]に含まれる場合は候補から除外する」規則を追加する。** `mode == context/recall`向けのF4相当ゲートを新設し、§8.5.3のStage2表・§8.5.7のmode別差分表に行を足す。ADR-0010 §5の3義務に「主体自身に見せない」を明記的に追加する。

5. **[Governance・新設] closure_ctxの設定をアクター単位の許可閉包集合でゲートする層を追加する。** ADR-0010 §2の可視範囲既定則とは別のレイヤーとして、「誰がどの`closure_ctx`を選べるか」を管理する。Substrateの`scope`は変更しない（可視範囲の意味論はそのまま）。

6. **[Policy] §8.5.4の横断ファンアウト条件3に「actor_idが全閉包オーナーであること」を追加する。** 現行の`session_origin == po_message`だけでは自律ループの除外にしかならない。

7. **[Governance] self-modelに所有者/対象範囲の属性を追加し、§20.5-8の再レビュー契機に「PO変更」を追加する。** §25の統制導線に主権者の引き継ぎ手続きを明記する。

8. **[Policy] §20.5の自己内省点検表にオフボーディング点検を新設する。** 離脱者の`person`（パラメータ化後は`person:<離脱者id>`）scopeエントリの凍結・アーカイブ・提示可否を機械的に判定する行を追加する。

## 6. 判定

**VISION.jsonが「PO一人」を明示的な設計対象とし、マルチテナントを明示的にout_of_scopeとしている**（`target_users`・`out_of_scope`）以上、S18はプロジェクトの現在の意図からは対象外である。しかし前提が破れたときに壊れる箇所は具体的かつ広範である。

- **Substrateレベルの欠陥が2つ確定した**：(a) `origin: user_explicit`から人間の身元を辿る手段がどこにも無い（検査表#1）、(b) `person`予約語が非パラメータのリテラルで複数人の個人領域を強制合流させる（検査表#9）。どちらも「後から足しても過去のエントリに遡及できない」というADR-0010自身の凍結ルールに該当し、**もし複数PO運用が将来ロードマップに入る可能性があるなら、蓄積開始前の今のうちに手当てする以外に選択肢が無い**。
- **この2つの欠陥は独立ではなく連鎖する**：actor識別の欠如が、(2)の誤裁定・(3)のsensitiveゲート漏洩・(5)のファンアウト漏洩・(6)のオフボーディング不能という4つの実害すべての直接原因になっている（検査表#2・#4・#5・#7・#8はすべて#1に依存すると根拠列で明記した）。単一の穴が複数シナリオに波及する構造は、R4/S13が検索機構の欠如について示したのと同型である。
- **閉包（`scope`）は可視範囲の既定値であって、人間に対するアクセス制御ではない**という検査表#6の疑いは確認された。(4)「Yはrepo:banto/webのみ」は現行の仕様のどの組み合わせでも表現不可能であり、これは新規の機構（アクター単位の許可閉包集合）を要する未定義の完全な穴である。
- **一方で書き込み側の継承規律（I1〜I8）と版管理による監査可能性は複数PO化しても壊れない**（§3）。これは「何が起きたか」を後から追える保証がSubstrateの他の部分では機能し続けていることを示しており、**穴は"記録が消える"型ではなく"識別できない/権限で止められない"型**に集中している。この診断がそのまま§5の修正の優先順位（actor識別の新設が筆頭）を導いている。

**結論**：S18は「対象外」と切り捨てられるが、対象外であることと無害であることは別である。`person`予約語とactor識別の欠如という2つのSubstrate決定は、複数PO化の可能性が万一将来生じた場合に備えて**蓄積開始前の今この時点で**re-visitする価値がある。それ以外（F4/F5の拡張、閉包アクセス制御層、オフボーディング点検）はPolicy/Loop層の可逆な追加で対応でき、急ぐ必要はない。
