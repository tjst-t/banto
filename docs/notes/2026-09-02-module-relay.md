# 検討ログ：Module 間呼び出しは host 中継に変更した（2026-09-02）

> ## ⚠ この文書は仕様ではない。**検討のログ**である
>
> **仕様は `docs/specs/v4-architecture.md`。** 決まったことを知りたいなら
> そちらを読む。この文書には検討の経緯・却下した案・訂正の履歴がそのまま残る。

## 発端

モックが一段落し、Module 間の RPC（Repo→Vault 等）の実装をもう少し詰めたい、
という相談から始まった。前日（2026-09-01）決めた「control-plane / data-plane
分離」——呼び出し前に core へ許可だけ求め、許可後の実データは Module 同士が
直結する——を具体化しようとしたところ、2つの詰めが要ることが分かった：

1. **transport**：Module 同士が直結するには、宛先ごとに host 経由とは別の
   接続口が要る。stdio Module は1プロセスにつき stdin/stdout が1本しかない
   （§2.5 実測済み）ので、Module B が追加で listen する口（Unix domain socket 等）
   を持たせ、そのアドレスを host が呼び出し元に配る、という設計が必要になる
2. **なりすまし対策**：「core に先に聞く」のは行儀のよい Module の前提でしか
   ない。第三者 Module が negotiation を飛ばして直結することを防ぐには、
   許可トークンの発行・検証が要る——これは仕様が §2.7（セキュリティ境界、
   まだ未着手）に TODO として持ち越していた

ここでユーザーから「問題を難しくしてしまっているかも」という指摘が出た。

## ユーザーの提案：性能問題が無い限り host が全部中継する

> 最初、性能問題とかでない限りは全データを host が中継でどうかな？
> それなら監査も何もないし。

これは要件 C10「モジュールは他のモジュールのツールインターフェースを
**直接呼べる**。Banto は**経路に入らない**」と文言上正面から矛盾する。
C10 は【ユーザー】ソースで、具体例が Repo→Vault だったので、その場で
矛盾を指摘して確認を取った。

### なぜ C10 が「経路に入らない」だったか

Vault の ssh-agent の例（D3・D5 の具体化）が理由——「秘密鍵は Vault の
プロセスから一度も出ない」という構造上の強い保証を、host を通さないことで
実現していた。中継すると、この保証が崩れないかが論点になった。

### 実際に確認したら、矛盾は見た目ほど深くなかった

`docs/requirements.md` D3 を読み直すと、実際に禁じているのは
**「鍵そのものが AI の文脈に出ない」**ことで、「core のプロセスメモリを
一過性に通過しない」ことまでは要求していない。ssh-agent の例が
「Vault のプロセスから一度も出ない」と書いているのは**ソケットパスの
やり取りに限った、より強い個別の設計**であって、D3 そのものの最低ラインは
それより緩い。

ユーザーの追加条件——**「host上で中継しているデータは他から見えないようにして
保存も一切しない」**——を足せば、この個別の強い保証も壊れない。ソケットパスや
alias の解決結果が host のプロセスメモリを一瞬通っても、ディスクにも
Event Store にも Canvas にも出さず、AI の文脈にも出さないなら、D3 にも
ssh-agent の例の意図にも反しない。

## 決定：host 中継に変更し、C10 の文言も改訂する

`docs/specs/v4-architecture.md` §2.5「Module 間の呼び出し——host が中継する」に
書いた。要点：

- **中継口は1つ。** host が自分自身の MCP 面（C13）に、`tools/call` /
  `resources/read` / `prompts/get` それぞれの薄い転送 tool を持つ。Module は
  みなこの同じ1箇所にだけ繋ぐ
- **権限確認・承認キャッシュは変更なし**（呼び出し元・宛先・名前の組み合わせ
  ごとに初回のみ確認、以降は Project 内で自動許可）
- **記録はメタデータだけ。** 引数・戻り値の中身は Event Store に書かない
- **実データは host のプロセスメモリを一過性に通過するだけ**——保存・提示は
  一切しない

## 副作用として消えた2つの論点

- **transport 問題**：Module 同士が直結しないので、宛先ごとの別接続口
  （Unix domain socket 等）を設計する必要が無くなった
- **なりすまし対策**：Module は host としか話さないので、許可を飛ばした
  直結という攻撃面自体が構造的に存在しない。§2.7 の TODO から削除した

どちらも「中継方式をやめて分離方式に戻す」判断があれば、また同時に
戻ってくる論点である（下記）。

## resource・prompt にも同じ形で対応する

当初の C10・旧「control-plane/data-plane 分離」の議論はどちらも tool 呼び出し
だけを想定していた。ユーザーから「tool 呼出しだけじゃなくて、リソースアクセスも
対応したい」という要望が出たが、中継方式なら `resources/read` 用の転送 tool を
同じ形でもう1つ用意するだけで済み、transport を増やす必要が無い。
`prompts/get` も同様に対応した。

## 将来の課題として残したもの

**中継が性能上のボトルネックになる、あるいは大容量データ（バイナリ添付等）の
中継が問題になる、という実測ベースの理由が出てきたら**、旧案
（control-plane / data-plane 分離・直結）に戻す道は仕様に残してある
（§2.5「将来の課題として残す：直結への分離」）。ただし戻すときは、
上で消えた2論点（transport・なりすまし対策）を同時に片づける必要がある。
**いまはまだ困っていないので、設計コストは使わない**（規則7）。
