**新しく作るものより、既に在るもののほうが多い。** 案の大半は

## 1. 概念を3つに分ける

いま**宣言1つが「実装」と「その1本」を兼ねている**。だから
「もう1本 Infisical」がコードの改変になる。

| 層 | 何を言うか | 例 |
|---|---|---|
| **実装** | 何を起動できるか。**どこに立つかの札**が付く | 同梱の `vault-infisical`／`npx @modelcontextprotocol/server-filesystem` |
| **登録** | その実装の、**名前つきの1本**。自分のデータ置き場と設定を持つ | `vault-infisical`（自前）と `vault-infisical-cloud` |
| **有効化** | どこで使うか | banto 全体で止める／Project ごとに AI へ見せる |

### 1.1 「実装」は独立した入れ物にしない（当面）

**登録（宣言）だけを持つ。** 「同じ実装をもう1本」は**宣言の複製**として表す。

理由：いま要るのは「もうそこにあるものを起動する」だけで、実装を独立した
入れ物にすると**更新・バージョン・アンインストールの層**が一緒に付いてくる
（規則10——必要になってから足す）。

ただし**どこから来たかの印は残す**——後から実装の層を足せるように：

```
origin: { kind: "bundled" }                              // 同梱
origin: { kind: "server.json", url: "...", name: "..." } // 取り込んだ
origin: { kind: "manual" }                               // 人が直接書いた
```

`origin` は**表示と由来の記録だけに使い、起動の判断には使わない**
（規則3——同じことを2箇所で決めない）。

## 2. 導出するもの（人が設定しない）

規則3（真実は一箇所）と規則1（自己申告を信頼しない）から。

| 導出するもの | どう決まるか |
|---|---|
| **どこに立つか**（instance／Project ごと） | **`${projectRoot}` を launch に書いたかどうか**（§3） |
| **起動できるか** | **測る。** 状態として持たない（§4） |
| **プロセスが立っているか** | 登録が有効 ∧（どこかの Project が見せる ∪ 誰かが `dependsOn` で要求する）。遅延起動 |
| **使える状態か** | Module 自身の `readiness()` |
| **同じ role を何本まで** | AI に見える面かどうかから導く（§5） |

## 3. 「どこに立つか」は、書いたものから導く——聞かない

### 3.1 なぜ聞かないか

「この MCP は Project のフォルダを触りますか？」と聞くと、
**間違えたときの被害が左右で釣り合わない**：

| 誤答 | 何が起きるか |
|---|---|
| 本当は触るのに **「触らない」** | プロセスが1本になり全 Project が共有。`${projectRoot}` が渡らないので **banto の起動場所**を見る（`connectStdioModule` は `cwd` を渡していない）。閉じ込めは**構造上かけられない**。結果 **Project A の会話から Project B のファイルに届く**。しかも**動いてしまうので気づかない** |
| 本当は触らないのに **「触る」** | Project の数だけプロセスが立つ。設定が Project ごとに分かれる（`moduleDataDir` は `name-projectId`）。**面倒なだけで壊れない** |

**片方は静かに Project の壁が消え、もう片方は手間が増えるだけ。**
ここまで釣り合わない設問を人に投げるのは設計の誤り。

### 3.2 導き方

フォルダを扱う MCP サーバは、**起動時の引数でフォルダを受け取る**のが慣習：

```
npx @modelcontextprotocol/server-filesystem /path/to/folder
```

したがって：

> **`launch` のどこかに `${projectRoot}` が書かれていれば `scope: "project"`、
> 書かれていなければ `scope: "instance"`。**

**これは既に強制されている**——`${projectRoot}` を instance の宣言に書くと
起動前に落ちる（`declaration.ts:79-84`）。仕組みは在って、**GUI がそれを
見せていないだけ**。

画面では引数欄の隣に「**この Project のフォルダ**」を差し込むボタンを置き、
押した瞬間に「この Module は Project ごとに立ちます」と出す。

### 3.3 導けない場合

引数に**絶対パスを直接書いた**ときは導けない（instance になる）。
これは**画面にそのパスが書いてあるので隠れない**。
「この Project のフォルダ」ボタンを目立たせ、絶対パスを打った場合は
**「全 Project が同じフォルダを見ます」と画面に出す**（黙って通さない）。

### 3.4 自己申告との関係

同梱 Module は `scope` を自己申告するが、**申告はより厳しい方向にだけ効く**
（既存の決定）。`${projectRoot}` からの導出と食い違ったら**起動しない**
（規則8——黙ってどちらかに寄せない）。

## 4. 「起動できるか」は状態として持たない

`npx` は実行のたびに取りに行き、ファイルは消えることがある。
**「インストール済み」を状態として持つと、いつか実態と食い違う**（規則1・規則3）。

- 画面に **「試す」** を置く。押したら**実際に起動して `initialize` まで通す**
- 持ってよいのは **「最後に試したときの結果と時刻」**だけ。それは
  「いま起動できる」の保証ではない、と画面に書く
- 試した結果は**捨てる**（プロセスを落とす）。本番の接続とは別

**人に見せる状態は3つ**：

| 表示 | 意味 | 次の一手 |
|---|---|---|
| **使える** | 立っていて `readiness` も OK | — |
| **設定が要る** | 立っているが未設定 | 設定画面へ |
| **繋がらない** | 起動に失敗 | 理由＋「試す」 |

## 5. AI に見える面では、同じ role は1本まで

### 5.1 規律

> **AI に見える面（agent 可視性の tool／resource）では、同じ role を名乗る
> Module は1本まで。** 複数持ちたいなら**束ねる窓口**を立て、窓口だけを AI に見せる。
> **Module 間（`dependsOn`）では何本でもよい**——`relayListTargets` で呼ぶ側が選ぶ。

根拠は実測（2026-09-12）：backend が2本になった瞬間、AI には `requestAlias` が
2つ並び、**選ぶ材料が無い**ので走らせるたびに選ぶ先が変わった。
`vault-directory` はこの問題のために生まれた。

### 5.2 導出であって、宣言ではない

**宣言に「1本だけ」と書かせない**（規則3）。
`vault-infisical` を何本立ててもよいのは `agentFacing: false` で
A 面を持たないから。`vault-directory` が1本なのは A 面そのものだから。

**host が Project の代理サーバへ登録するときに検査し、2本目を理由つきで断る。**

### 5.3 呼ぶ側の決め打ちをやめる

この規律があれば、Shell の `"vault-directory"` 直書きは
**「role `vault-directory` を名乗る唯一の1本」**に書き換えられる
（0件・2件以上なら止まる——規則2）。

## 6. 有効化の軸は2つ

| 軸 | 置き場 | 何のため |
|---|---|---|
| **登録が有効か** | instance | 完全に止める |
| **その Project の AI に見せるか** | Project | いまある Module 画面 |

**2つ要る理由**：`vault-directory` は Shell の依存なので、
**誰も AI に見せていなくても立つ必要がある**。
「どの Project でも見せない＝立てない」にすると裏方が落ちる。

**プロセスが立つかは導出**（§2）。人は起動ボタンを押さない。

## 7. 秘密を宣言に書かせない

### 7.1 問題

`mcpServers` の慣習は `env: { "GITHUB_TOKEN": "ghp_..." }`。
ところが **banto の宣言は Event Store に残る**（§5.1）ので、
**書いた瞬間に記録へ永久に残る**。`vault-infisical` の資格情報を宣言に
書かないと決めたのと同じ理由。

### 7.2 案：差し込み語を1つ足す

```
env: { GITHUB_TOKEN: "${secret:github-token}" }
```

起動の直前に host が Vault から引いて差し込む。

- 差し込み語の仕組みと「**知らない語は起動前に落とす**」規律は既に在るので、
  1語足すだけ
- **どの Project のために起動する Module か**が host には分かっているので、
  「その Project が使ってよい秘密か」を既存の判定（2026-09-13 の刻印）で通せる
- **記録に残るのは名前だけ。** 値は残らない
- `scope: "instance"` の Module では Project が決まらない——**共通の秘密だけ**
  引ける（Project の秘密は引けない。規則2——曖昧なら断る）

### 7.3 画面

登録の `env` 欄では、値を**「直接入力」と「金庫から」で選ばせる**。
直接入力を選んだら **「この値は記録に残ります」**と出す（隠さない）。

## 8. リモート MCP——起動の形は2つになる

「受け入れる起動の形は1種類だけ」（2026-09-06）は**起動するもの**の話で、
リモートは起動しない。§5.1 は `remotes` を認めているので方向は矛盾しないが、
**形が2つになることは明示的に決め直す**（規則8——黙って増やさない）。

| 形 | 中身 | 閉じ込め |
|---|---|---|
| **起動する** | `command` / `args` / `env` | Landlock を掛けられる（Project ごとのとき） |
| **繋ぐだけ** | `url` / `headers` | **掛けられない**（自分のプロセスではない） |

`headers` の値も §7 と同じ（`${secret:...}`）。

**リモートは「どこへ出ていくか」が見えない**——subprocess の第三者 Module とは
性質が違う。画面でそう言う。

---

## 9. 閉じ込めは、別の軸として扱う

いまの閉じ込めは**同梱 Module 向け**に作ってある（許すのは Project の根・PATH・
node・自分のデータ置き場・banto の置き場）。

`npx` で動く MCP は `~/.npm` を読むので、**このまま掛けるとほぼ確実に落ちる**。

落ちるなら理由は出る（黙って壊れない）が、体験は悪い。したがって：

- **閉じ込めは `scope` から自動で決めない。** 登録ごとの明示の設定にする
- 既定は？ → **未決**（§12）

## 10. 消すとき・名前を変えるとき

| 操作 | どうする |
|---|---|
| **登録を消す** | 宣言を消す。**データは消さない**が既定——その Module のデータ置き場も、Vault に置いた秘密も。「まとめて消す」は別操作・別の確認 |
| **名前を変える** | **できるが、中継の承認はやり直しになる**（許可は Module 名で引く。`vault`→`vault-local` の改名で実測済み）。画面でそう言う |
| **同梱を消す** | 消せない（既定に戻せる形で無効化だけ） |

## 11. 画面（案）

```
設定 › Module

【banto 全体で動くもの】
  vault-local            使える                     [設定] [試す]
  Infisical（自前）       使える                     [設定] [試す] [複製]
  Infisical（Cloud）     設定が要る → 設定へ          [設定] [試す] [複製]
  Vault のまとめ役        使える

【Project ごとに動くもの】
  shell                  3 つの Project で動作中
  filesystem             3 つの Project で動作中

【よその MCP サーバ】
  github                 繋がらない：npx が見つかりません   [試す]

                                            [＋ MCP サーバを繋ぐ]
```

**「＋ MCP サーバを繋ぐ」**の中身：

```
名前:      github
繋ぎ方:    ( ) 起動する   ( ) URL に繋ぐ
コマンド:  npx
引数:      -y  @modelcontextprotocol/server-github
           [＋ この Project のフォルダ]  ← 押すと Project ごとになる
環境変数:  GITHUB_TOKEN = ( ) 直接入力  (•) 金庫から [github-token ▾]

           ⓘ この Module は banto 全体で1本立ちます
              （「この Project のフォルダ」を使うと Project ごとになります）

                                        [試す]  [繋ぐ]
```

- **`server.json` の URL を貼る／ファイルを選ぶ**と、上の欄が埋まる
- **`mcpServers` の JSON を貼る**でも埋まる（Claude Code から持ってくる用）
- **「試す」を通さないと「繋ぐ」は押せない**——規則1（自己申告を信頼しない）

Project の設定は**いまある画面のまま**（この一覧からチェックを付けるだけ）。

## 12. まだ決めていないこと

1. **よその MCP の閉じ込めの既定**（§9）。厳しくすると動かない、緩めると
   第三者コードが野放し
2. **Project ごとに「同じ実装の別の1本」を使い分けたいか**
   （Project A は自前 Infisical、B は Cloud）。いまの形（登録は instance、
   Project は見せる/見せないだけ）では**直接の表現が無い**
3. **`dependsOn` の解決を人が上書きしたいか**
   （「この Project の Shell はこちらの Vault を使う」）
4. **名乗らない Module の `isolation` と `handlesSecrets` の既定**。
   `handlesSecrets: false` なら tool ごとの可視性が要らず全部 AI に見える
   ——よその MCP はそれでよいか
5. **「試す」で起動したプロセスの後始末**と、試験中に副作用のある MCP
   （起動しただけで書き込むもの）をどう扱うか
6. **同梱 Module を複製したときの更新**。同梱は差し込み語なので一緒に上がるが、
   よその MCP のバージョンは登録ごとに散る

## 追記：レビューで判明した、案の前提の誤り（2026-09-15）

### 誤り1：「GUI が無い」は正しくない。**画面は既に設計されていて、繋がっていないだけ**

`banto/apps/frontend/components/banto/settings/` に
`role-list.tsx` / `add-module-dialog.tsx` / `edit-module-dialog.tsx` /
`disable-impact-dialog.tsx` が**本実装のツリーに在る**。
ただし `feature-flags.ts` の `CONNECTED_FEATURES.settings` は **`false`**
——**モックの固定データで動いていて、host に繋がっていない**（規則13 で隠してある）。

つまりこの案がやることは「新しい画面を設計する」ではなく、
**既にある画面を host に繋ぐ**ことだった。確かめずに「無い」と書いたのは
規則1 の違反（測る前に決めた）。

### 誤り2：§11 の画面案は、**既に決まっている §6.1 と食い違う**

`docs/specs/v4-frontend.md` §6.1（決定済み）：

> **階層1：banto 全体**——中心を Module 一覧ではなく**役割（role）一覧**にする
> （同じ役割の複数実装が辞書として共存してよいので）。役割ごとに、満たす実装・
> プロセス境界・**無ければ何が断るか**・Module 自身の設定を表示。
> **有効/無効の切替はライブでよい**——切替をイベントとして記録し、
> それに依存する tool は次に呼ばれた瞬間はっきり断る

§11 はこれをフラットな Module 一覧に描き直し、**有効/無効の切替も
「押す前に何が壊れるかの提示」も落としていた**。
モック（`role-list.tsx` ＋ `disable-impact-dialog.tsx`）には両方とも在る。

**§11 は棄却し、既にある役割中心の画面を出発点にする。**

### 誤り3：§6「有効化の軸は2つ」は、**新しい提案ではなく既に在るもの**

モックの `MockModuleImplementation` は既に `enabled` を実装ごとに持ち、
**無効化したとき何が断るかを `dependsOn` から導出**している
（`types.ts:265-269`——「`breaksIfDisabled` のような手書きの写しは持たない、規則3」）。
案が「2つ要る」と言ったことは正しいが、**発明ではなく、既にそう作ってある**。

### 直った前提のもとで、この案に残る中身

新しいのは次だけ：

1. **`${projectRoot}` から scope を導く**（§3）——聞かない
2. **`${secret:...}`**（§7）——宣言に秘密を書かせない
3. **リモート MCP で起動の形が2つになる**（§8）——明示的に決め直す
4. **AI に見える面では role ごとに1本**（§5）——ただし**モックは既に
   「1つの役割に複数の実装が共存してよい」前提で作られている**ので、
   §5 と §6.1 の関係を整理し直す必要がある（**A 面を持つ実装が2本のときだけ
   断る**、という形なら両立するはず。要検討）
5. **「起動できるか」を状態として持たない**（§4）
6. **消すとき・改名するときの扱い**（§10）

**それ以外は、既にある画面とモデルを host に繋ぐ作業。**

### 誤り4：§7 は、**既に決まっている決定と黙って衝突していた**（規則8 の違反）

`docs/specs/v4-architecture.md:1984-2006`（**決定・2026-09-02 改訂**）：

> `mcpServers` の `env`（stdio）・`headers`（remote）に書く値が秘密情報のとき、
> §2.5「alias 方式」を使える。**ただし alias 方式は必須ではない。**
> `env` に値を直接書く（例：ローカル開発中の使い捨てトークン）ことも妨げない
> ——banto は「書ける形」を1つに絞らない。
> 記法は `"env": {"API_KEY": "$my-alias"}` のように **`$` 前置**。

しかもその直後に、Shell の `envSecrets`（裸の alias 名）との**表記の違いは
意図したもの**だという整合性の確認まで書いてある。

**案の §7 は、これを読まずに書いた。** 衝突は2つ：

| | 決定（2026-09-02） | 案（§7） |
|---|---|---|
| 記法 | **`$my-alias`**（`$` 前置） | `${secret:...}` |
| 直書き | **妨げない**（形を1つに絞らない） | 「書かせない」 |

**技術的には案のほうが筋が良い**——`${secret:...}` は差し込み語の機構
（`declaration.ts:75-87`「知らない語は起動前に落とす」）に乗るが、
`$my-alias` はその検査を素通りする。**だが、それは「決め直す」であって
「1語足すだけ」ではない。** 旧決定を明示的に置き換えると書く必要がある。

「直書きを妨げない」のほうは、**旧決定のままでよい可能性が高い**
（使い捨てトークンを直接書きたい場面は実在する）。案の「書かせない」は
行き過ぎで、**「書けるが、記録に残ると画面で言う」**が旧決定と両立する形。

### 誤り5：§7 に決めていないことが4つあった

### 誤り6：§5 の検査位置が、競合で非決定的になる

（刻印 → backend の group 絞り込み → `relay.call_recorded` の監査）。

`${secret:...}` の展開は `expandLaunch`（起動直前）で起きるので、

§7.2 の「既存の判定で通せる」は、その判定が relay の中にあることを見落としていた。

もう1つ：**`${secret:...}` は `command` と `args` にも書ける**
（`declaration.ts:113-115` は command・args・env を**全部**走査する）。

**直す方向**：
- **env の値でのみ許可**し、command・args に現れたら起動前に落とす
- 起動時の秘密引きも**刻印・group 絞り込み・監査を通す**
- **閉じ込め無しの Module に `${secret:...}` を許すか**を明示的に決める

  閉じ込め無しの任意コードに秘密を手渡す形になる）

### 誤り15：リモート MCP は「外へ出ていく経路」で、脅威モデルに行が無い

`v4-security.md` の表は**全て subprocess 前提**で、

`headers` に秘密を入れれば、**秘密が毎回 machine 外へ送られる**。

**この案でいちばん明確に足すべきは、この行。**

### 誤り16：「試す」は承認前の任意コード実行

「試す」は `initialize` まで通す＝**起動コマンドが走る**。
案は「試すを通さないと繋ぐは押せない」としたので、

## 実装しながら設計が変わったところ

### 「scope の導出」は安全の柵にならない——試験が教えた

案は「`project` と名乗って `${projectRoot}` を使わないのは食い違いだから落とす」
と書いたが、**既存の repair の試験が落ちて、それが強すぎると分かった**。

**Project ごとに分けたい理由はフォルダだけではない**——Project ごとに別の状態を
持ちたい Module は、根を受け取らなくても分かれていてよい。

そして逆に、**「Project のフォルダを歩くのに instance と名乗る」は導出では防げない**
（自前の置き場に状態を持つサーバは根を受け取らない）。
つまり **§3 の導出は画面の既定を決めるためのもので、守っているのは閉じ込めのほう**。
案が「導出で守れる」と読める書き方をしていたのは誤りで、仕様ではそう書き直した。

### 予約 role の検査は parse に置く

最初は読み込み（`loadModuleDeclarations`）に置いたが、**保存（`setModuleDeclarations`）
が素通りする**ことに試験で気づいた。壊れた宣言を Event Store に残さないためには
**入口が1つ**でなければならない（規則2）。

### `valueFree` を締めたら、試験が20分ハングした

`host-relay-endpoint.test.ts` の Module は手書きの meta で、`origin` が付いていない
＝外から繋いだ扱いになり、**承認ゲートに入って誰も答えないまま待ち続けた**。

これは**仕様どおりの振る舞い**（第三者の valueFree は承認を聞く）で、
試験が「同梱のつもり」を表現していなかっただけ。試験に `bundledMeta()` を入れた。

## 反映後の実機確認で見つかった、記録の穴（2026-09-15／規則8）

反映後に実機を見たら、**私が知らないうちに秘密が1つ消えていた**
（`vault-infisical` の `github-ssh`）。自分の変更のせいかを確かめようとして、
監査の記録を引いた：

```
{"callerModule":"vault-directory","targetModule":"vault-infisical",
 "kind":"tool","name":"deleteAlias","allowed":true,
 "reason":"人が画面で行った管理操作","ok":true,"ts":"2026-09-15T14:37:58.929Z"}
```

**どの alias を消したのかが、記録に無い。** `name` は tool の名前で、
`RelayAuditRecord` は引数を1つも持たない。

仕様は違うことを言っている（`v4-architecture.md:1107`）：

> **引数のうち、値そのものではなく「何を指しているかの識別子」
> （例：Vault の alias 名）は記録してよい**

つまり**「記録してよい」と決めてあるのに、記録していない**。その結果、
**「誰がどの秘密を消したか」が後から追えない**——監査として肝心のところが空。

**これは今回の Module の仕事とは別件**なので、ここに記録して上げる（規則8）。
直すなら `RelayAuditRecord` に「引数のうち識別子だけ」を足す
——どのキーが識別子かは宛先が知っているので、**安全側に倒すなら
tool ごとに明示した項目だけ**（`name`・`group`・`identity` など）を拾う形。

なお `github-ssh` が消えた原因は**特定できていない**。記録から言えるのは
「画面から `vault-infisical` に対する削除が1回あった」までで、対象は分からない。
