# 記録：試験の確認手順が、本物のリモートへ `git push` を通した

> 2026-08-20。**publish された変更は無い**（no-op で終わった）。
> ただし `git push origin main` は実際に実行された。原因は私の確認手順にある。

## 何が起きたか

`repo` モジュールの「vault が無いとき `push` が断る」試験が空振りしていないかを、
**ガードを外して落ちることを確かめる**やりかたで検証した（教訓2）。

```
optional: [{ module: 'vault', tools: [...], usedBy: ['push'] }]
                                            ↑ これを外して試験を走らせた
```

`usedBy` を外すと `push` は断らなくなり、`core.push()` が実行される。このとき
`RepoCore` の根は `process.env['BANTO_REPO_ROOT'] ?? process.cwd()` で、
**cwd は banto 自身の作業ツリーだった。** つまり `git push origin main` が
本物のリモート（github.com/tjst-t/banto）に対して走った。

## なぜ実害が無かったか（3つ重なっただけ）

| | |
|---|---|
| ローカル `main` == `origin/main`（ed560e2d） | push は Everything up-to-date の no-op |
| 押したのは `main` であって作業中の `v3` ではない | v3 には上流が無く、そもそも push できない |
| 資格情報ヘルパも `~/.git-credentials` も無い | 書き込みが要る操作なら認証で止まっていた |

**どれも設計で担保したものではない。** ローカル `main` が1コミットでも進んでいたら、
レビューを経ていないものが publish されていた。

## 本当の原因

`push` が断るかどうかという**アプリケーションの判断**だけが、本物のリモートへの
操作を止めていた。その1枚を剥がしたら、下に何も無かった。

根に既定値があったことが効いている——`?? process.cwd()` は「設定を忘れたら
そのとき居たディレクトリを掴む」という意味で、要件 C8c が `isolation` について
言っていること（**既定値は「忘れられる」機構そのものである**）が、そのまま別の
フィールドで再現した。

## 直したこと

`requiredRoot()` を module-kit に置き、`fs` と `repo` の根から既定値を外した。
設定を忘れると**起動時に落ちる**。

```
BANTO_REPO_ROOT が設定されていない。作業範囲の根に既定値は無い
——cwd に落とすと、そのとき居たディレクトリに対して操作が走る
```

`shell` の許可リストも空が既定＝何も実行できない、で揃っている。

確認：`usedBy` を外して `push` を呼んでも、根が明示されている限り本物の
リポジトリには届かない。

## 私の手順の問題

ガードを外して試験が落ちることを確かめるやりかた自体は正しい（教訓2）。
問題は、**外した先で何が起きるかを見ていなかった**こと。

`read` や `list` なら外しても無害だが、`push` は外向きの副作用を持つ。
**ガードを外す前に、ガードが無い経路が何をするのかを読む。** 副作用が外へ出る
ものなら、ガードではなく入力（この場合は根）のほうを無害にしてから外す。

## 人に上げること

教訓に足すかどうかは人が決める。候補：

> **ガードを外して確かめるときは、外した先の副作用を先に読む。**
> 「弾かれること」の確認のために弾かれない状態を作るのだから、そこで
> 何が起きるかは、確認そのものの一部である。
