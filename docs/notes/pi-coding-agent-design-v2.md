# エージェント駆動開発プラットフォーム 設計まとめ v2

pi coding agent をランタイムとして claude-skills の開発手法を構造化する、独立プロダクトの設計。
（v1 からの主な更新：独立プロダクト化の決定、全体アーキテクチャ、escalate 勧告方式、Sprint 廃止とかんばん＋ケイデンス、バックログモデル、3層自己改善ループ、自動アップデート）

## 1. 目的と基本方針

- claude-skills レポジトリで実践しているスプリント/オートパイロット型開発手法に最適化した、自分専用のエージェント駆動開発環境を作る。
- **Claude Code の置き換えは狙わない**。差別化はオーケストレーション層。pi の価値は「ハーネス全体を自分が所有できること」。
- ワークフローを「プロンプトのお願い」ではなく**構造として強制**する。
  - skill / プロンプト = 判断が要る「知識」の層（LLM が従うかは確率的）
  - コード = フェーズ遷移・ゲート・通信路を「機械的制約」にする層
- 原則：**機構は「チェックが必ず行われること」だけを保証し、チェックの中身はテキスト（プロンプト・設定）に追い出す**。

## 2. プロダクトの位置づけ

- **独立プロダクトとして開発する**（Palmux2 への合流はしない）。GUI 含めてしっかり作り込む価値があると判断。
- Palmux2 には依存しない。tmux 管理や stream-json 連携の実装は**必要に応じて参照する**のみ。Palmux2 は素の Claude Code 用ツールとして残る（実質メンテナンスモード化は自然な世代交代として許容）。
- pi は**無改造のエージェントランタイム**として扱う。フォークしない。カスタマイズは Extension（Pi Package）と SDK/RPC 駆動の範囲で行い、届かない場合は upstream に Extension API 拡張を提案する。フォークは最後の手段。
- 役割分担：本プロダクト＝ガバナンスレイヤー＋PO コックピット。pi＝ランタイム。Surface（GUI/CLI/TUI）＝消耗品。
- 本当の資産は3つ：**daemon のステートマシン、Extension Pack、タスク定義スキーマ**。

## 3. 全体アーキテクチャ

```
┌─ Surfaces（薄いクライアント。ロジック禁止）──────────────┐
│  Web GUI（アテンションキュー / ボード / バックログ編集）      │
│  CLI（status / approve / enqueue）   tmux（対話セッション）  │
└──────────────┬────────────────────────┘
               │ HTTP API + WebSocket（イベント購読）
┌─ Core Daemon（本体・決定的コード。LLMを置かない）─────────┐
│  ステートマシン / キュー / spawn管理（spawn台帳を永続化）      │
│  タスク定義watcher / イベントログ(JSONL) / ケイデンス生成      │
└───┬────────────────┬──────────────────┘
    │ RPC (JSONL / LF区切り自前実装)   │ SDK (in-process)
┌─ Session層（piプロセス群、無改造）──────────────────────┐
│  headless RPC: 実行者 / 一括監査                            │
│  SDK単発: 同期QA / status_reporter / 差分要約                │
│  TUI: 検討・レビュー（bridge Extensionでdaemonと接続）        │
└───────────────┬──────────────────────┘
┌─ Extension Pack（Pi Package）─────────────────────────┐
│  enqueue_task / classify_change / request_design            │
│  ask_designer / スクリーンショットツール / daemon bridge       │
└─────────────────────────────────────┘
        契約層 = リポジトリ内artifact（タスク定義 / ADR / inbox）
```

- 「pi 拡張 vs SDK 組み込み」の答え：バックボーンは SDK/RPC による組み込み（daemon が全セッションのライフサイクルを握る）。Extension は「セッションの中にプロダクトの規律を持ち込む手段」。両方使うが役割は直交。
- **ロジックは daemon と Extension Pack にだけ書く**。TUI/GUI 固有コードに判断を持たせない。これにより対話体験の器（v1: pi TUI + tmux → 将来: Web チャット）を後から差し替え可能にする。
- 実装言語は TypeScript。モデルは opencode エンドポイント経由で差し替え可能に。

## 4. 3つの役割

1. **検討エージェント**（素の pi TUI + Extension、対話型）
   - 技術検討、ロードマップ、Epic 分解、タスク定義作成、ADR 正式化、ケイデンス処理。PO が直接会話する相手。
   - **オーケストレータの管理外**。接続はプロセスではなくリポジトリのファイルのみ（疎結合の要）。検討用 worktree で起動し、成果物だけ main へ。
2. **オーケストレータ = Core Daemon**（決定的コード）
   - 最も信頼性が必要な層に非決定性を入れない。LLM が必要な判断（分解・要約・再計画）は SDK 単発セッションをスポットで呼ぶ。
3. **実行者エージェント群**（headless RPC spawn）
   - ブランチ worktree で実装専任（cwd 分離・クラッシュ隔離・tmux で人間介入可）。
   - 自己監査は**別コンテキストのセッション**に差分だけ渡す（同一コンテキストの甘い自己評価を構造で防ぐ）。

## 5. バックログモデルと粒度

- **不変単位＝「1回のレビューセッションで見きれる差分」**。ボトルネックは PO レビュー帯域なので、タスクサイズは実装コストではなくレビューコストで切る。1 タスク＝1 worktree＝1 ブランチ＝1 レビュー。
- 階層は **Epic → Task（+checklist）の2段だけ**。3段以上は作らない。
  - **Epic**（複数タスク跨ぎの機能）：検討レイヤーの構造物。実行キューには載せない。分解は**ローリング方式**（直近分のみ。escalate で計画が書き換わるため先まで細かく切らない）。進捗は GUI が `parent` を集計表示するだけ（Epic に状態管理を持たせない）。
  - **バッチタスク**（細かいバグ・小修整）：チェックリスト形式の1タスク定義に束ね、1 worktree・1 レビューでまとめて処理。
- タスク投入の正規ルートは検討エージェントの `enqueue_task`（書式検証＋コミット）。雑タスク用に `enqueue` CLI の逃げ道を用意するが、同じ検証コードを通す（裏口を作らない）。キックは PO の操作ではなく、コミットを daemon が検知して自動実行。

## 6. フロー制御：Sprint 廃止、かんばん＋ケイデンス

- **Sprint は実行単位として廃止**。実行は連続フロー。制御装置は時間箱ではなく **WIP 制限**（レビュー待ちキュー上限）。「sprint」という語は新プロダクトでは使わない（旧 claude-skills の「スプリント」＝1実行サイクルは新語彙では「タスク」）。
- レーンは3つ：**Now**（実行中＋レビュー待ち、WIP 上限つき）/ **Next**(順序付きキュー) / **Later**（Epic・未分解バックログ）。
- **ケイデンス**（統治のリズム）：daemon が定期的に「ケイデンス実行」カードを**合成キューアイテム**としてアテンションキューに自動生成。開くと検討エージェントがケイデンスモードで起動し、議題（未承認 ADR、勧告却下ログの集計、improvement-inbox、Epic 分解残、WIP/改善枠の配分見直し）が自動で並ぶ。
  - 頻度はパラメータ（2〜3日に1度程度を想定）。
  - 設計根拠：キューは「放置するとタスクが止まる」緊急項目には効くが、「放置すると仕組みが静かに劣化する」非緊急項目（ADR 正式化、集計して初めて意味を持つログ）は構造的に沈む。緊急→キュー、重要非緊急→ケイデンス。ただしケイデンス自体をキューに載せることで、PO の日常は「キューを上から潰すだけ」に一本化。

## 7. レビューフロー

- reviewフェーズ入り→アテンションキューにカード→開くと tmux ウィンドウが自動準備：ペイン1＝レビュー用 pi セッション（タスク定義＋差分注入済み）、ペイン2＝dev server 起動済み（起動コマンドはタスク定義に記載）。人間の準備作業ゼロが目標。
- **GUI 開発ではレビューループが実質メインの開発ループ**。修整の嵐は正常。受け入れ条件は挙動に絞って厳密に、見た目・UX は「レビューループで磨く」と明記（前工程で視覚品質を仕様化しない）。
- `/fix` ループ：1修整＝1論理コミット。視覚情報は2段構え——PO からはスクショ貼付、agent は自前のスクリーンショットツール（Playwright 等）で修整後に自己確認してから報告。
- 再監査は修整ごとに回さず、`/approve` 時に**マージ前ゲートとして一括1回**。
- **classify_change 必須＋勧告方式**：
  - Extension の tool_call フックで、編集前に `classify_change` の実行をコードで強制（「判定が行われること」の保証。熱中による問い立て忘れを構造で防ぐ）。
  - 判定は2層：機械層（スコープ外パス・累積 diff 閾値＝ただの条件分岐）＋ LLM 層（受け入れ条件・公開 IF・データモデル・既存 ADR との抵触判定、理由付き）。
  - escalate 判定が出ても**ブロックしない**。「escalate を推奨します。理由：…」と提示し、**最終判断は PO**。却下は軽くログに残す——PO の監査ではなく**分類器のチューニングデータ**として。分類器は過敏側に振ってよい（誤検知コスト＝警告1行、見逃しコストのほうが高い）。
- `/escalate`：レビュー会話から新タスク定義ドラフトを生成→PO 確認→enqueue。新ブランチは現 worktree から切る（積んだ小修整を捨てない）。元タスクは superseded。アドホックタスクも正規キュー・正規ゲートを通す（レビューセッションでの大改修＋直接マージは禁止）。
- `/adr`：会話中の設計判断をドラフト化して docs/adr へ。**正式化（Accepted）はケイデンスの検討フローで行う**（熱い文脈での即時確定を避け、main の検討レイヤーを設計判断の関所として維持）。

## 8. エージェント間通信（3本のみ。すべてリポジトリと daemon を通す）

1. **タスク定義**（設計→実装）：スコープ、スコープ内パス、受け入れ条件、監査基準、起動コマンド、parent、governance フラグ。
2. **design-inbox**（実装→設計、非同期メールボックス）：`request_design` ツールが構造化ファイルをコミット。ADR ドラフトもこの一種。
   - advisory：タスク続行。検討エージェントの session_start フックで提示。
   - blocking：daemon がタスクを paused に遷移、優先キューへ。決定→タスク定義更新→自動再開。
3. **同期 QA**（実装→設計、即答用）：`ask_designer` → daemon が短命 QA セッションを SDK で spawn（ロードマップ＋関連 ADR 注入）→回答して破棄。回答は必ず inbox にログ。回答に「タスク定義の変更を要する→escalate せよ」の選択肢を持たせ、重い判断の抜け道化を防ぐ。

**状況照会（status_reporter）**：「btw いまどう？」に対し、動いているエージェントには触らず**外から読む**——①daemon の状態、②対象セッションの JSONL ログ末尾、③worktree の diff stat を短命 SDK セッション（安いモデル）で要約。入口は検討エージェントの `report_status` ツール、CLI/UI の digest 表示の両方。介入したい場合は照会と別物として tmux アタッチで直接対話（読むだけの照会と割り込む介入をコマンドレベルで分離）。

## 9. UI（PO コックピット）

UI の第一原理は俯瞰ではなく「**いま自分の判断を待っているものは何か**」。PO レビュー帯域の配分装置として設計。

1. **アテンションキュー**（トップ）：レビュー待ち、blocking 検討依頼、エスカレーション、ケイデンスカード。ブロックしているタスク数でソート、滞留日数表示。見るべきは動いているものではなく止まっているもの。
2. **エージェントボード**：行＝タスク、列＝フェーズのかんばん（Now/Next/Later）。**daemon のステートマシンをそのまま描画するビューア**に徹する（UI 側に独自状態を持たせない）。
3. **バックログ編集 GUI**：独自 DB を持たず、**タスク定義ファイル群の構造化エディタ**。左に Epic ツリー＋未割当、右に Now/Next レーン。ドラッグで割当・並べ替え→daemon API→ファイル書換＋コミット。真実は常にファイルなので、AI 経由の編集と GUI 編集が同じ真実を違う入口から触る形になる（Palmux2 での「JSON は AI しか触れない」問題の根治）。Now レーンにはレビュー見込み時間のキャパ表示。
4. **ドリルダウン**：カードクリックでその worktree の pi セッション（tmux ペイン）へ。
- 注意：ダッシュボードは沼。v1 は「アテンションキューのリスト＋クリックで tmux へ」だけ。

## 10. 自己改善ループ（3層モデル）

claude-skills の「Skill の見直し自体も Skill に入れる」思想の構造化版。

- **層A：プロンプト資産**（システムプロンプト、監査チェックリスト、classify_change 判定プロンプト、skill MD）→ エージェントが直接編集提案できる。ただしコミット＝PO レビュー対象（エージェントが自分の監査基準を勝手に緩める経路を塞ぐ）。
- **層B：ポリシーパラメータ**（閾値、WIP 上限、ケイデンス間隔、スコープ規則）→ 宣言的設定ファイル。テキスト編集で改善。
- **層C：機構コード**（daemon、Extension 本体）→ **エージェントは提案まで、判断は PO**（escalate と同じ原則）。ケイデンスで改善案が出たら検討エージェントがその場でタスク定義ドラフトまで起こし、PO は enqueue する/しない/後で の三択。採用後はセルフホスティングの正規フロー（実装→監査→レビュー）に合流。

**ループの機構**：
- incident 収集：監査セッションの検知（検証漏れ、テスト逃れ等）や PO の `/incident` を `improvement-inbox/` に自動蓄積。skill 時代と違い課題の収集が機械化される。
- ケイデンスで集計：1件ずつでなくパターンで見る（「類似4件：テスト検証まわり」）。
- **「ずる」への処方原則**：誤解・知識不足→層A/Bで修正。虚偽報告・手抜き→**層Cへ昇格**（自己申告を信じない機構化。例：テストは daemon がマージ前ゲートで自分で実行して結果を見る）。incident が繰り返されたらプロンプト層から機構層へ昇格させる一方向の流れを規約化——使うほど「騙せない部分」が増える方向に進化させる。
- 統治コードに触るタスクは `governance: true` タグ：バッチに混ぜない、レビューを流し読みしない対象として UI で強調（「ゲートを緩める改善提案」への最後の砦は PO が diff を読むこと）。
- 自己改善タスクは Next に小さな固定枠（例：5タスクに1つ）。「手が空いたら」にしない。

## 11. 自動アップデート（層C のセルフデプロイ）

PO の許可ゲート＝層C タスクのマージ承認。承認後を機械化する：

1. **隔離検証**：候補ビルドを別 state ディレクトリ＋fixture リポジトリで起動し、E2E シナリオ集（合成タスク enqueue→spawn→遷移→ゲート発火→マージの一周）を **LLM モックの実行者**で実行。機構の正しさは決定的なので LLM なしで検証可能。余裕があればシャドー実行（本番イベントログを read-only で食わせ、現行 daemon と判断差分を突合）。
2. **スワップ**：グリーンなら入れ替え。**Nix パッケージ＋profile switch** で世代管理とロールバックを得るのが自然。起動後ヘルスチェック失敗で自動ロールバック。
3. **前提条件（本当に重要な2つ）**：
   - **daemon の再起動可能性**：spawn 台帳（pid・タスクID）を永続化し、新 daemon が実行中の pi 子プロセスを孤児として引き取れること。クラッシュ復旧のためにも初期から必須。
   - **E2E シナリオ集の質**：自動更新の安全性はテスト網羅性と同値。**incident 由来の層C改善はその再現シナリオを E2E に追加してからマージする**規約とし、検証スイートを改善ループと一緒に育てる。
4. 導入は段階的に：最初は「検証グリーン→通知→手動 update」の半自動、スイートが信用できてから全自動へ。
5. 限界の認識:LLM の判断品質（分類器の精度等）はこのパイプラインでは守れない。判断をできるだけ層A/Bに置く原則が安全弁（コードは壊れると止まる、プロンプトは壊れると静かに劣化する）。

## 12. 新規開発を始める流れ

現在の習慣「Claude チャットで概要→MD 持ち込み→実装」に1ステップ挿入する形。

- **Phase 0 — 構想**：チャットで発散・概要固め（現状維持。構造化前の思考に構造を被せない）。
- **Phase 1 — ブートストラップ**：`init` コマンドで雛形（タスク定義スキーマ、docs/adr、design-inbox、improvement-inbox、daemon 設定、Extension 参照）を撒き、MD を docs/vision.md として配置。
- **Phase 2 — 検討セッション#1**：vision.md を読ませてタスク分解。**MD を直接実装の入力にしない**（曖昧さの分解が検討エージェントの仕事。失敗をタスク定義の曖昧さに遡れるのはこの分解があるから）。greenfield では初期 ADR ラッシュ（技術選定3〜5本）＋**最初のタスクは必ず walking skeleton**（触ってレビューするスタイルには動くものが最速で必要）。
- **Phase 3 — 実行**：enqueue→自動 spawn。序盤は依存が直列なので並列度1。並列が効くのはモジュール境界が引けてから。

## 13. 実装順序

1. タスク定義スキーマ（scope paths / governance / parent / checklist / 起動コマンド込み）
2. daemon 最小ループ（watcher→spawn 1並列→レビューキュー）＋ spawn 台帳の永続化
3. 検討エージェント Extension（`enqueue_task`）
4. レビュー Extension（`/fix` `/escalate` `/adr` ＋ classify_change 勧告方式）
5. design-inbox（advisory→blocking）
6. 状態イベント出力→アテンションキュー UI（リスト＋tmux ジャンプのみ）
7. status_reporter、バックログ編集 GUI、ケイデンス（合成カード）
8. improvement-inbox と自己改善ループ、E2E シナリオ基盤
9. 自動アップデート（半自動→全自動）

本プロダクト自体をこの手法の最初の適用対象にする（手動ブートストラップ→walking skeleton→即ドッグフーディング）。並列度は PO レビュー帯域に合わせて絞る。spawn の多重化よりレビューキューが先。
