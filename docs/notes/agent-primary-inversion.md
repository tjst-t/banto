## 1. 構造の逆転（要旨）

- **旧モデル**: banto ＝開発システムが主。AI Agent はその一部品（Planning/Review 等の機能を実現するパーツ）。
- **新モデル**: **記憶を持つ AI 番頭（steward）が主体**。決定的な daemon の上で、PO の代理として「店（まず＝ソフトウェア開発）」を切り盛りする。これまで作り込んだ開発システムのUI（アテンションキュー等）は、**番頭がチャットで不便なところを補うために差し出す道具/盤面**。PO はその番頭を統べる。
- **含意（拡張性）**: 番頭の核（記憶・会話・差配・決定的統治基盤）を、開発固有の道具（タスクモデル・コードレビュー・Environments）から**分離**して設計すれば、将来 別領域も同じ番頭に載る。**開発＝第一の店**、真の意味での番頭への第一歩。
- 名前がそもそもこれを言っていた：番頭＝主人に代わり店の一切を切り盛りし、全部を覚え、客の相談を受け、職人に仕事を差配する人。

## 2. 登場人物（4層）

| 層 | 役割 | 記憶 |
|---|---|---|
| **PO（主人）** | 統べる。本物のトレードオフだけ裁く | — |
| **番頭 AI（steward）** | 人と接する・アーキ/方針/大きな判断・PO代理・差配 | **あり**（二層＝ADR-0003） |
| **daemon** | 決定的統治基盤：イベントソーシング/ステートマシン/ゲート/spawn執行 | 決定的コード |
| **職人＝worker AI** | daemon が spawn・実装/調査/行単位レビュー | **なし**（memoryless） |

- **非対称を原則化**：番頭＝継続と知恵（記憶あり）、職人＝再現可能・監査可能（記憶なし＝隠れ状態なし＝I1「ずるは不可能」）。記憶の有無を役割で分ける。

## 3. bantoの存在理由を壊さない二軸（D2との両立）

bantoが生まれた理由＝「開発手法がプロンプトの遵守期待に依存し、ゲート/監査が**構造的に保証されない**」（VISION.problem / D2「制御ループにLLMを置かない」）。**「番頭が主」＝「統治もお任せ」にしてはいけない。**

- **体験・差配の軸では番頭が主**（話す相手・覚える主体・仕事を回す主体）
- **執行の軸では daemon が主**（ゲート・ステートマシン・真実＝イベントログ＝D3）
- ＝ **番頭は店を切り盛りするが、帳簿はごまかせない。** 番頭でも決定的な台帳の上で動く。POが黙ってゲートを飛ばせないのと同じく、番頭も飛ばせない。

## 4. 番頭の決定境界（D1を「高度」で置換）

エスカレーション条件を1行で：

> **利用者の利用体験を変え、かつ本物のトレードオフ（どちらも選びうる）── このときだけ PO へ。それ以外は番頭が決める。**

- 体験が変わらない → 番頭が決定
- 体験は変わるが、メリデメ明確・開発方針から自明 → 番頭が決定
- 明確な Pros/Cons があり、どちらも選びうる → PO へ（UI も同様）
- **pre-release は壊してよい**＝スキーマ等の“不可逆っぽいもの”も、リリースして外で使われるまでは番頭が決める。
  - 例外：外に累積する副作用（公開パッケージ・外部VMコスト・イベントログの形式そのもの）は one-way 寄りなので別枠。
- **番頭は細かい仕事をしない**：設計調査・実装は職人（memoryless）へ投げてコンテキストを節約。番頭の文脈は「記憶と判断」で使い、調査ログで埋めない。

これは既存 **D1（不可逆＝公開IF/データモデル/依存追加はエスカレート）を、番頭の高度で置き換える精緻化**。「不可逆か」より「**体験を変える本物の分岐か**」の方が PO の帯域を守れる（VISIONの狙いに忠実）。

## 5. 分身（フチコマ）ライフサイクル

- **分身＝番頭のインスタンス**（記憶あり・PO と話す・PO代理で判断）。**職人 ≠ 分身**。アイデンティティと記憶は一つ、身体だけ複数。

```
       ┌ PO発起：あなたが新しい相談トピックを開く
 誕生 ─┤
       └ daemon発起：判断が要る点＝アテンションカード
          │ fork: 共有記憶のスナップ ＋ その文脈を持って起動
          ▼
 生存 ── PO代理で判断（§4の境界）／職人に調査・実装を投げる
        下した決定は即「イベントログ＝唯一の真実」へ push
        ときどき最新の共有記憶を pull（＝フチコマ同期）
          ▼
 収束 ── トピック解決 → 終了。学びを共有記憶(導出層)へ distill
        会話は History へ、記憶は Memory へ合流
```

- **同期は3方向**：① push（決定→ログ、即時。走る分身同士もログ越しに互いの決定を見る）② pull（他分身が更新した共有記憶を取り込む）③ distill（学び→共有記憶の導出層へ append/照合）。
- **破綻しない理由**：決定はログで直列化されるので競合しない（ADR-0003：記憶はログからの導出、競合する真実を持たない）。分身が持ち帰るのは“導出された学び”だけ＝ append 寄り。**帳簿(ログ)が本当の合流点、分身は導出ビュー**。
- **割り込み問題を解く**：Aと話す最中に daemon がYの判断を要求 → **分身Bが fork してカードで現れる**。Aの文脈は壊れない。各関心事が自分のインスタンスを持つ＝破壊的コンテキストスイッチが消える。増殖は**アテンションキューの優先度ソート（滞留×ブロック）が“生きてる分身”を潰す順路**になり暴走しない。

## 6. UIの統一像（チャット vs コックピットの決着）

- **会話スレッド一覧 ＝ 生きてる分身**
- **アテンションキュー ＝ daemon発起の分身の待ち行列**（走査可能な盤面）
- **History ＝ 死んだ分身**
- **Memory ＝ 収束した共有記憶**

＝ 主体は番頭。キュー等は番頭が差し出す走査可能な盤面。「状態は“場所”が要る、会話に保持できない」問題は、**番頭が盤面として差し出す**ことで解ける。作ってきた面が全部この一つのモデルに乗る。

## 7. 何を残し、何を作り直すか

| | 扱い |
|---|---|
| daemon設計（イベントソーシング/ステートマシン/ゲート） | **残す**（番頭はこの上に乗る。D2＝存在理由） |
| 職人/worker モデル（memoryless spawn） | **残す** |
| ADR-0003〜0008・specs（daemon-core/environment/multi-project 等） | **残す**（ほぼ直交。ADR-0003=記憶二層は**核に昇格**） |
| 個別サーフェスの中身（キュー/ボード/Environments…） | **再利用**（番頭の道具/盤面として） |
| VISION | **書き換え**（番頭主体へ） |
| プロトタイプのシェル/操作パラダイム（サイドバー＝家） | **作り直し**（番頭＝家：チャット＋盤面＋分身） |

→ **全捨て・一からは不要**。「頭（VISION＋操作パラダイム＋シェル）を作り直し、substrate と個別サーフェスは再利用」。

## 8. VISION 改訂（案・ドラフト、正式化は記憶システム統合後）

- 現: 「一人のPOがAIエージェントのチームを率いて開発するための統治環境。ガバナンスレイヤー＋POコックピット」
- 案: **「記憶を持つAI番頭（steward）が主体となり、決定的な統治基盤の上で、POの代理として店（第一の店＝ソフトウェア開発）を切り盛りする。POはその番頭を統べ、利用体験を変える本物のトレードオフだけを裁く。番頭はフチコマ的に分身・収束し、コンテキストを超えた記憶で一貫する。開発は番頭が受け持つ最初の領域であり、将来 他領域へ拡張しうる。」**
- success_criteria も要見直し（「会話2枚＋キュー1本」→「番頭に話す＋走査可能な判断待ち行列」等）。

## 9. 新/改訂 principle 候補（番頭）※principles.md 変更は ADR 経由。ここは候補の記録

- **P(番頭-1)** エスカレーション条件＝利用体験を変える本物のトレードオフのみ（§4。D1を高度で置換）。
- **P(番頭-2)** 番頭は細かい仕事をしない＝調査/実装は職人（memoryless）へ委譲し、文脈を節約する。
- **P(番頭-3)** 記憶を持つ番頭／memoryless な職人の非対称（継続 vs 監査可能）。
