# 2026-10-20 containers の道（Backlog #369）

仕様は `docs/specs/v4-security.md` §1「別のサーバの中のコンテナ」の「道」と、その下の「実装済み（#369）」。ここは決め方・
採らなかった案・踏んだもの。

## 起きていた不具合（直す理由）

containers の実行場所の Project で、Module の `BANTO_HOST_MCP_URL` が `http://127.0.0.1:<VM のトンネルの番号>/relay` のまま
コンテナの中に渡っていた。コンテナは自分のネットワーク名前空間を持つので VM の 127.0.0.1 には届かず（fetch failed）、Vault の値・
Repositories・Backlog の push が全部失敗していた。`preparedInContainer` が machine の `preparedFrom` の `bantoOrigin` をそのまま
使い、鍵の窓口（`socketPathInside`）は「まだ見せられません」で断っていた。

## 実装者が決めたこと

- **トンネルはコンテナを用意するときに張る**（親の接続を張るときの `-R` にしない）。決まったパスの UNIX ソケットは、張る前に
  置き場（`/run/user/<U>/banto/p-<id>/`）を作り、前の接続が残したソケットを消す要がある（sshd の `StreamLocalBindUnlink` は no、
  `docs/notes/2026-10-08-remote-runtime.md`）。親を張る前には向こうで何も流せないので、張ったあと `-O forward -R` で頼む。鍵の
  窓口と同じ `addForward` を通す。接続ごとに1回（`conn.tunnel`）
  - 却下：親の接続の引数に `-R <パス>:…` を入れ、張る前に別の ssh で消す——接続を2回張ることになり、`ExitOnForwardFailure` が
    UNIX ソケットの側の理由を出さない（前の実測）
- **中のポートは 29839**（全コンテナで同じ）。コンテナはそれぞれ自分のネットワーク名前空間を持ち、`bind=instance` の口は中の
  127.0.0.1 にしか出ないので、Project ごとに番号を変える理由が無い。よく使われる番号（3000・5173・8000・8080 等）を避け、Linux の
  一時のポートの範囲（既定 32768〜60999）の外にした——前から動いているコンテナに初めて装置を足すとき、中で一時のポートとして
  取られていると待ち受けられない。中のサービスがこの番号で待ち受けるとぶつかる——人に言うのは、ぶつかったときの理由の文で
  足りると判断した
- **鍵の窓口の中のパスは `/run/banto-a-<印>.sock`**（仕様の案は `/run/banto/…`）。Incus の forkproxy は待ち受けの親のフォルダを
  作らない（`main_forkproxy.go` に mkdir が無い）。コンテナを起こし直すと中の `/run` は空になるので、`/run/banto/` にすると、残った
  装置（接続が切れて外せなかったもの）があるとき、Incus がコンテナを起こすときに待ち受けられない。`/run` そのものは必ずある
  - 却下：装置を足す前に中で `mkdir /run/banto`——起こし直したあとに無くなるのは同じ
- **前の接続の鍵の窓口の装置は、次の接続で最初にコンテナを用意するときに外す**。接続が切れたときには Incus を呼べない（呼ぶ口が
  その接続）。同じ接続で用意し直す（`forget` のあと）ときは外さない——いま使っている窓口を外してしまう
- **`security.uid/gid` は向きで番号を変える**。頼みは「中の番号（`ProjectContainerSpec.inside`）から取る」だったが、Incus の
  forkproxy のソースを読むと、`security.uid/gid` は**繋ぐ側の**名前空間で落とす番号で、`bind=instance`（中で待ち受けて VM へ
  繋ぐ）では VM の側——VM のユーザーの U でないと、sshd が作ったトンネルのソケット（U の持ち物・0600）に繋げない。中の番号を
  使うのは、`bind=instance` の UNIX の待ち受けの持ち主（`uid`/`gid`、中の名前空間で付く）と、`bind=host`（流れの口・公開）の
  `security.uid/gid`。どちらも宣言（`uid`/`gid`/`inside`）から取り、1000 を決め打ちしない（`proxyDevice`）。#457 で中の番号を U に
  すると、両方とも U になる
  - 読んだところ：`cmd/incusd/main_forkproxy.go`——子（待ち受け）は listen の pid の名前空間へ、親（繋ぐ）は connect の pid の
    名前空間へ、それぞれ user namespace が違えば `CLONE_NEWUSER` も足して setns する。親は待ち受けの fd を受け取ったあと
    `switch_uid_gid(security.uid, security.gid)`。子は fd を渡したあと `os.Chown(listen, uid, gid)`・`os.Chmod(listen, mode)`
- **置き場を作る台本に `umask 077` を足した**（machine の転送も通る）。`/run/user/<U>/banto/` の途中のフォルダを `mkdir -p` が
  既定の権限（0755）で作るため。machine の `<置き場>/s` は 0700 の置き場の中なので、振る舞いは変わらない

- **流れの口の VM の待ち受けは `<置き場>/s/st-<印>`**（仕様の条件4の例は `/run/user/<U>/banto/p-<Project>/…`）。`bind=host` の装置は
  VM の側で**待ち受ける**ので、コンテナを起こすたびに Incus がそのパスで待ち受け直す。`/run/user/<U>` は tmpfs で、VM を起こし直すと
  `p-<id>/` は無く（linger で作られるのは `/run/user/<U>` まで、それも Incus がコンテナを起こすより後のことがある）、forkproxy は親の
  フォルダを作らないので、コンテナが起きられなくなる。`<置き場>/s` は VM のディスクにあり、コンテナには見せていない（見せるのは
  `<置き場>/code` と `<置き場>/modules/<接続名>` だけ）ので、条件4（VM だけの場所）を満たす。トンネル・鍵の窓口は VM の側では
  **繋ぐ**だけ（繋ぐときにあればよい）なので `/run/user/<U>/…` のまま
  - 流れの口の装置は外さない（待ち受けの置き場がいつもある。繋ぎ直すたびに同じものを `ensureProxy` で確かめる）
  - VM には symlink を置かない（machine は `<置き場>/s/st-<印>` に Module の待ち受けへの symlink を置き、sshd が辿る）——containers
    で sshd（VM のユーザー）に中の置き場を辿らせない

- **実行場所の種類の3つ目（`remote-containers`）**：Project の記録の `runtime` は `remote:<名前>` だけで、動かし方（`machine`／
  `containers`）は実行場所の登録が持つ。答えが分かれる2つの問い（眠らせる・閉じるときに Service を止めるか）だけ、登録を引く口
  （`RemoteModeOf`）を受ける形にした。根の場所・この機械のコンテナかは、どちらの動かし方でも同じ答えなので記録だけで答える——
  Project の記録の層（`project-thread/store.ts`）は登録を知らず、渡す道を作ると関係の無い層に依存が増える
  - 却下：Project の記録に動かし方を写す——真実が2か所になる（規則3）。動かし方は使っている Project がある間は変えないが、
    登録を消して同じ名前で作り直すと食い違う
  - 登録の無い名前（外された）は前の2択どおり `machine` として扱う
- **眠らせる・閉じるときにコンテナを止める**：`RuntimeRouter.release` は `stop` を別のサーバに渡していなかった（machine は止める箱が
  無い）。containers では、接続が無くても止めるために繋ぐ——接続を閉じてもコンテナと中の Service は動いたままなので、banto を
  起こし直したあとに眠らせたときに止まらないことになる。止められなければ接続は閉じたうえで `RuntimeStopError`（呼び元が受信箱で
  言う、この機械と同じ）
- **起こし直したときに眠っている Project のコンテナを確かめるのは、この機械だけのまま**（`stopSleepingContainers`）。containers で
  同じことをすると、起きるたびに眠っている Project の数だけ VM に繋ぐ。眠らせたときに止めてあり、Incus は止まったコンテナを
  勝手に起こさない（`boot.autostart` は付けていない——VM を起こし直すと、止まる前に動いていたものだけを起こす）ので、残すのは
  人が手で起こした場合だけ

- **資源の画面は別のサーバの読み取り（今の probe）を広げる**。仕様は「コンテナの cgroup `lxc.payload.user-<uid>_<名前>` を読む」。
  この機械は host が cgroup のファイルを直に読む（incusd が詰まっても見張りが止まらない——規則4）。別のサーバでは、張ってある
  接続の上の node の読み取りが同じ役（`incus exec` を通さない）なので、そこに足した。中の内訳は今の単位の分け方を使い回し、
  Project の名前を添える（画面は変えない——1つの実行場所に Project が複数並ぶので、名前が無いとどの Project のものか分からない）
  - 区画の名前は `user-<uid>`（incus-user が作る区画）と決め打ちした。`containers` は制限の無い区画（incus-admin）を断るので
    ほかの形にならない
  - 上限に当たった知らせ：見張り（`ContainerPressureWatch`）の対象に containers の閉じていない Project のコンテナを足し、数えは
    資源の見張りが最後に読めた回のものを使う（10 秒ごとの読み取りと、1分ごとの見張りの間で読み直さない）。繋いでいない実行場所は
    読めずに飛ばす（前の値を使い続けない）
  - 上限の1行（`describeLimits`）は、この機械の設定から計算すると VM と違う値を出してしまうので、読んだ `memory.max`・`pids.max` を
    見せる。上げ方の文も替えた（この機械の設定では変わらない）

- **移すのは引き続き断り、「動いているものを中で数える」だけ入れた**。移す手順（`project-move.ts`）の向こうの側は、VM の SSH ユーザー
  として `tar` の展開・rsync の受け手・`git worktree repair`・置き場の片づけをする（`withSide` の `run` は素の ssh）。containers で
  条件3を満たすには、(1) 移す先のコンテナを根を見せた形で先に作る（いまの作りは Module を起こすときの `prepare` だけ）、(2) 書く
  ものを全部 `incus exec <c> --user <中の番号>` に通す（rsync は `--rsync-path` で中へ）、(3) 移したあとの元のコンテナを止めて残す、
  が要り、移す手順の片側（`Side`）を作り直すことになる。#369 の範囲では大きすぎるので残した（Backlog に積み直す）
  - 「中で数える」は眠らせる前の「止まるもの」（`runningInPlace`）でも使われていて、VM の SSH ユーザーで数えると containers では
    いつも「何も動いていない」になる（Service はコンテナの中のユーザーの systemd）ので、先に直した

- **公開は中継の口にサービスのポートを足して受ける**（`relayProjectAddress` の `port`、返りの `port`、外す口 `relayProjectPortRelease`）。
  仕様は「Publish のたびに VM のポートを選んで装置を足す」だけで、公開の実装との受け渡しは決めていなかった。公開の実装は
  アドレスだけを受けてサービスのポートへ繋いでいたので、VM のポートを知る道が要る
  - 却下：core が公開の記録を見て装置を張る——公開の記録の真実は公開の実装（publish-caddy）が持つ。core が写しを持つと食い違う（規則3）
  - 却下：見積もり（`planPublish`）で張る——承認されずに終わると装置が残る。張るのは `publishRoute` と突き合わせの時（どちらも公開が
    ある時）
  - 突き合わせ（15 秒ごと）も `port` を渡すので、消えた装置（人が消した等）は次の突き合わせで張り直される。張ってあれば装置の
    待ち受けから番号を読み直す（覚えない）
  - **繋いでいなければ確かめない**（投げる）。突き合わせのたびに眠っている Project の VM に繋ぐことになるため。投げると公開の実装は
    `address-unknown` で道に触らず、装置は Incus の設定なので届き続ける
  - VM のポートの範囲は 20000〜29999（よく使われる番号と一時のポートの範囲を避ける）。VM で待ち受けているもの（`ss -Hltn`）も避ける。
    同じ VM の別の banto（別のデータの置き場）と同時に選ぶとぶつかりうるが、そのときは Incus が装置を足すのを断る（理由が出る）
- **外す時**：仕様は「取り消し・Service を消す・移す・閉じるとき」。取り消し（公開をやめる）と閉じるときは外す。閉じるときは、
  接続を手放す前に（`http/app.ts` の閉じる口）その Project の `banto-pub-*` を全部外す——外せなくても閉じる（ログに残す）。**Service を
  消すときは外さない**：Service を消しても公開の記録は残る（この機械でも同じで、行き先に届かなくなるだけ）ので、道だけ外すと
  公開の記録が残ったまま、次の突き合わせで張り直される。公開と Service の繋がりを作るのは公開の側の話で #369 の範囲を越える
  （仕様と違うので人に上げる）。移すは containers ではまだ断る

## レビューの指摘（2026-10-20、別のサブエージェント）と直し

- **H1 閉じた Project の公開 URL が、同じ VM のほかの Project のサービスに繋がる**：閉じるときに装置を外すと VM のポートが空くが、
  publish-caddy の記録と Caddy の道（dial VM:<ポート>）は残る。閉じたあとは接続が無いので突き合わせは「確かめられない」（道に触らない）
  になり、そのあとほかの Project が公開すると最小の空き番号として同じ番号が選ばれ、閉じた Project のホスト名（その認証の設定、無しの
  こともある）でほかの Project のサービスが出ていた
  - 直し (a)：`RemoteSshRuntime.address(projectId, port)` は、閉じた Project なら繋がずに `{unavailable: 閉じています}` を返す（core が
    記録を引く口 `projectClosed` を渡す）。公開の実装の突き合わせは、これで道を 503 にする（この機械のコンテナが止まっているときと同じ）
  - 直し (b)：外したばかりの VM のポートは 10 分のあいだ、ほかに空きがあれば選ばない（`RELEASED_PORT_COOLDOWN_MS`）。(a) だけだと、
    閉じてから次の突き合わせ（15 秒ごと）までの間・公開の実装が落ちている間にほかの Project が公開すると、同じことが起きる。公開を
    やめたときも、Caddy の道を消せなかったら次の突き合わせまで残るので同じ扱いにした。覚えるのはメモリだけ——banto を起こし直すと
    忘れるが、公開の実装も起き直すたびに突き合わせる（閉じたものは (a) で 503）。ほかに空きが無いときは選ぶ（公開を断るより良い）
  - **machine にも同じ形の穴がある**（人に上げる）：machine は閉じると実行場所が空き、次に来た Project が同じポートで待ち受けると、
    閉じた Project の公開の道（宛先の LAN のアドレス:ポート）がそちらに届く。(a) を machine に広げれば塞がるが、machine の振る舞いを
    変えるので #369 では入れていない（規則7）
  - 試験：閉じた p1 の公開は VM に聞かずに「閉じています」、そのあと p2 が公開しても外したばかりの番号を選ばない（(b) を外すと
    外したばかりの番号を選んで落ちる・(a) を外すと「閉じています」が返らず落ちる、を確かめた）
- **L2 装置の名前（`banto-pub-<サービスのポート>`）に Service が入っていない**：同じ Project の別の Service が同じポートで公開されている
  と、片方をやめたときにもう片方の道も外れていた。道は「Project とサービスのポート」で決まる（コンテナの中の 127.0.0.1:<ポート> に繋ぐ
  ので、Service が違っても行き先は同じ）ので、名前は変えず、**公開の実装の側で、同じ (Project, ポート) の記録が残っていれば外させない**
  ようにした
- **M1 公開に失敗した・やめるのに失敗した装置が残り、LAN から認証なしで届き続ける**：公開の途中（届かない・Caddy に書けない・覚えられ
  ない）で失敗すると、host が `resolveAddress` で張った装置（`listen=tcp:0.0.0.0`）だけが残っていた。やめるときに VM に繋がらなくても、
  記録だけ消えて装置が残っていた
  - 直し：公開に失敗したら、別の番号が返っていれば（host がこの公開のために道を張った）外させる。外させ損ねたもの（公開の失敗・
    やめる）は公開の実装の置き場の `releases.json` に覚え、突き合わせで外し直す（同じものは 5 分に1回——外し直すたびに host は
    別のサーバに繋ぎに行くので、繋がらない間に 15 秒ごとに繋がない）。覚えている間に同じ Project の同じポートがまた公開されたら、
    その公開が使うので外さずに忘れる
  - 採らなかった案：突き合わせで「この Project の、記録にあるポート以外の `banto-pub-*` を外す」口を host に足す——記録が1件も無い
    Project（全部やめた・閉じた）を公開の実装は知らないので、その Project の残りを拾えない。拾うには全 Project・全 VM を毎回見に行く
    ことになる。「外させ損ねたもの」を覚える形なら、外させ損ねた分だけを見に行けばよい
