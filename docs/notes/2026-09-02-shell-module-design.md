# 2026-09-02 Shell Module の設計検討

`docs/specs/v4-modules.md` §2.3 として決定した内容の経緯。決めた結論だけを
仕様に書き、検討の過程・却下した案はここに残す。

## 1. tool の語彙・alias 方式

FileSystem と同じく、ゼロから語彙を発明していない（規則12）。ただし FileSystem
と違い、Shell の秘密情報の受け渡し（`envSecrets`）は既にアーキ仕様 §2.5
「具体例：Shell に秘密情報を渡す——alias 方式」で決定済みだったので、今回は
それをそのまま tool 引数の形に落とした。今回新規に決めたのは以下の2点：

- **`secretFiles`**：`.npmrc`・`kubeconfig` のような、値を環境変数ではなく
  ファイルとして必要とする秘密の tool 引数の形。アーキ仕様には原則
  （実行直前に Landlock 根の中へ一時ファイルとして書き出し、実行後に消す）
  しか無く、引数の形までは詰めていなかった
- **`sshIdentity`**：Vault B節の `startSshAgent` は元々 Repo 向けの例だったが、
  Shell が生の `git` コマンドを叩く場面にも同じ経路が要る。ソケットパスは
  秘密ではないので `envSecrets` とは別枠にした

## 2. バックグラウンド実行・複数コマンドの状態管理——作らない

**検討の発端**：`runCommand` 以外に、`listProcesses`/`killProcess` のような
プロセスを識別子で参照する tool を足すべきか。

**却下した案**：Shell 自身にバックグラウンド実行・poll・kill の tool を足す。

**採らなかった理由**：これは「プロセスを識別子で参照し、後から操作する」
という状態そのもので、Shell の契約（1回の呼び出しで終わる、`docs/specs/v4-modules.md`
§2.1 Shell/Environment 比較表）を破る。この種の要求は Environment（§4、
必須ではない・まだ設計していない）の仕事として切り分けた。

## 3. timeout と MCP の既定タイムアウト

`npm install` 等、60秒を超えるコマンドは普通にある（前の実装で得た知見
——MCP の既定タイムアウトは60秒——は v4 でも構造として効く）。

**検討した案は2つ**：

1. バックグラウンド起動＋poll用tool（`startCommand`/`pollOutput` 等）
2. `runCommand` を1回の呼び出しのまま、実行中に `notifications/progress` を
   定期送出してクライアント側のタイムアウトを更新させる

**採った案は2。** 1は§2の理由でShellの契約を破る。2はMCP仕様が既に持つ
仕組み（進捗通知）の使い先が増えるだけで、新しい機構を要らない（規則12）。
副産物として、この進捗通知にstdoutの断片を載せればCanvas側でコマンド完了前
のライブ出力も出せる——ただしこれは実装のオプションであって、契約には現れない。

## 4. resource を持たない

**検討の発端**：FileSystem が `file:///{path}` resource テンプレートを持つのと
同様に、Shell も実行履歴を resource として持つべきか。

**却下した案**：Shell 自身が実行履歴を保持し、`resources/list` で見せる。

**採った案**：resourceは一切持たない。Shellには参照可能な永続オブジェクトが
無い（プロセスは1回で消える）。履歴が要るなら、host中継の呼び出しが既に
記録しているEvent Store（Vault B節と同じメタデータ記録の仕組み）を読む——
Shell自身が履歴を二重に持つのは規則3（真実は一箇所）に反する。

## 5. 「永続・人とAI共有のShellが欲しい」——第3のModuleにしなかった理由

**発端**：ユーザーから「人とAIが両方触れる永続的なShellが欲しいが、これは
別Moduleにすべきか」という問い。

**検討した3つの選択肢**：

1. Shell自体を有状態に拡張する（永続セッションID・attach/detach tool を足す）
2. 第3のModule（例：Terminal/Session）を新設する
3. これはEnvironment（§4「作りたいModule」）の話として扱い、ShellにもEnvironment
   にも新しいModuleを増やさない

**却下した案**：1と2。

- 1は§2・§3で決めた「Shellは状態を持たない」という契約を直接破る。Shell/Environment
  の分岐点（`docs/specs/v4-modules.md` §2.1 比較表）は「状態の有無」で、これは
  MCPの指針（呼び出しをまたぐ状態は明示的な識別子で参照させよ）に沿って
  一度決めたもの——ここを曲げると FileSystem/Shell/Environment 全体の分類基準が崩れる
- 2は、「永続する・識別子で参照する・人もAIも触る」という性質が、Environmentの
  定義（コードを動かす場所を用意する、状態を持ち識別子で参照する）とほぼ
  そのまま重なる。Environmentの元の説明にある「誰が使うか：主にFactory的な
  ものが裏で」は**使われ方**の違いであって、**契約の形**の違いではない——
  契約の形が同じものを3つ目のModuleに分ける理由が無い（規則7の精神——
  むやみに増やさない）

**採った案**：3。Environmentの説明に「人とAIが同じ永続セッションをターン制で
共有する使い方も想定」の一文を足した（`docs/specs/v4-modules.md` §4）だけに
留め、Environment自体の設計（tool/resource/UI）はここでは行わない——Phase 0/1
では作らないModule（CLAUDE.md）であり、いま全部詰める必要が無い。

**同時性についての確認**：ユーザーに「tmuxを2人で覗き込むような、人とAIが
同じセッションに同時にリアルタイムで入出力する必要があるか」を確認したところ、
**ターン制（AIがtool呼び出しでコマンドを投げ、結果が同じ画面の履歴に積まれる）
で十分**という回答だった。これにより、PTYのbroadcast/多重化という新しい技術要素
は不要と分かった——Environmentの`execIn`相当のtool呼び出し＋Canvas側の
セッション履歴表示、という既存の材料（tool呼び出し・承認ゲート・Canvas）の
組み合わせで足りる。この確認が無ければ、真の同時PTYという別種の設計課題
（承認ゲートとの相性も含む）を抱えるところだった。
