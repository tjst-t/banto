# containers の実行場所：登録・前提の確かめ・sudo -n の準備（Backlog #367、2026-10-18）

仕様は `docs/specs/v4-security.md` §1「別のサーバの中のコンテナ」の「実行場所の種類」の下の「実装済み（#367）」。ここは実装者が
決めたことと、採らなかった案。

## 決めたこと（実装者）

- **向こうのコマンドは1つずつ SSH で流す**（`VmAccess.run`——`["incus", …]`・`["sudo", "-n", …]`・`["cat", …]`）。1本の台本に
  まとめると速いが、偽の Incus・偽の sudo に差し替えた単体試験が書けない。登録と「確かめ直す」のときだけなので、10 本前後の接続は許す
- **sudo は台本ではなく、項目ごとのコマンドで打つ**（`sudo -n sh -c …` にしない）。sudoers で「準備の台本だけを許す」形
  （仕様の任意）にするときに、許すコマンドを並べられる。人に見せる直し方も、同じ引数から作る（打つものと見せるものが食い違わない）
- **1項目済ませるごとに様子を引き直す**——incus グループに入れると、次の SSH の接続で incus-user が区画 `user-<uid>` を作り、
  そこで初めて区画の設定（proxy・idmap）を見られる
- **subuid・subgid を書き換えたら Incus を起こし直す**（`systemctl restart incus.service` と `incus admin waitready`）。この機械の
  install.sh・`@banto/container` の前提の確かめの直し方と同じ。**要るかどうかは測っていない**——まっさらな VM で人が測る（完了条件）。
  要らないと分かれば外す
- **確かめ（登録の前）では何も変えない**。済んでいない項目は、sudo -n が通るなら注意（「登録するときに整える」）、通らなければ断る
  ——人が「登録する」を押す前に、何を打つかが画面に出る
- **人が先に整えてあれば sudo -n は注意にとどめる**（断らない）。準備が済んでいれば、sudo は崩れたときに直すためだけに要る
- **繋ぐたびの確かめは sudo しない**。崩れていれば断り、「確かめ直す」で整えると言う（人が押す——仕様の「ほかの時は sudo しない」）
- **区画が `default`（incus-admin に入っている）のユーザーは断る**。制限の無い管理の口に繋がり、区画の制限（proxy・idmap・disk）が
  効かない。banto から incus-admin を外すことはしない（人のサーバのグループを勝手に減らさない）
- **containers の Project は作れるが、Module はまだ起こせない**（Backlog containers-project-module）。新しい Project の画面で
  「1つに1つ」で薄くしない（タスクの指定）。Module を繋ごうとすると名指しして断る——VM のユーザーで直に起こすと、その Project の
  AI が sudo できるユーザーになる。新しい Project の画面の説明にも、まだ Module を起こせないことを書いた

## 採らなかった案

- **同じ動かし方なら同じ宛先に2つ登録するのも断る**：仕様が断るのは「machine と containers を並べる」だけ。containers を2つ
  並べても区画・置き場を共有するだけで、machine の AI に sudo できるユーザーを渡す形にはならない
- **sudo -n が無いとき、いつも断る**：人が先に整えた VM でも使えなくなる。上のとおり注意にとどめた

## E2E

`e2e/specs/remote-runtime-containers-register.spec.ts`。SSH の相手（入れ子のコンテナ）には Incus が無く sudo もできないので、
見られるのは「動かし方を選べる」「machine と同じ宛先を断る」「足りないものと打つコマンドを名指しして断る」「相手を何も変えない」
まで。準備が通ること・何度流しても同じことは単体試験（`containers-host.test.ts`）で見た。本物の VM は banto-dev-vm を使わず、
まっさらな VM で人が別に確かめる。
