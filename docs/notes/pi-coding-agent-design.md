# pi coding agent カスタマイズ構想 — 設計まとめ

claude-skills の開発手法に最適化した、自分専用コーディングエージェントの設計方針。

## 1. 目的と基本方針

- 現状は Claude Code をメインで使用。pi coding agent（badlogic/pi-mono）をカスタマイズし、claude-skills レポジトリで実践しているスプリント/オートパイロット型の開発手法に最適な形のエージェントを作る。
- **Claude Code の置き換えは狙わない**。インナーループ（編集・テスト・修正）の完成度で競うのは消耗戦。pi の価値は「ハーネス全体を自分が所有できること」にあり、差別化はオーケストレーション層に絞る。
- claude-skills のワークフローを「プロンプトのお願い」ではなく**ハーネスの構造として強制**する。
  - skill（Markdown）= 判断が要る「知識」を LLM に渡す層。従うかは LLM 次第
  - Extension/SDK = フェーズ遷移・ツール制限・監査ゲートを「機械的制約」にする層
- 絶対に飛ばされたくない工程（ガバナンス自己監査、レビューゲート）はコード側へ、コーディング規約や設計判断の知識は skill のままプロンプト層に残す。

## 2. pi の仕組み（前提知識）

- **Extension**: TypeScript モジュール。ライフサイクルイベント購読（`pi.on("tool_call", ...)` で実行ブロック可）、カスタムツール登録（`pi.registerTool`）、コマンド登録（`pi.registerCommand`）、`pi.setActiveTools` によるフェーズ別ツール制限が可能。
- **SDK**: `createAgentSession()` でセッションをプログラムから生成。モデル・ツール・SessionManager を指定でき、監査用の別コンテキストセッションなどを自由に組める。
- **RPC モード**: stdin/stdout 上の JSONL でプロセス統合。実行者を子プロセスとして spawn する用途に使う。フレーミングは厳密な LF 区切り（Node readline 等の汎用行リーダーは使用禁止、`\n` 分割を自前実装）。
- pi 自体がサブエージェント・plan mode・permission popup をコアに持たず、Extension や Pi Package で自分のワークフローに合わせて組み立てる思想。

## 3. アーキテクチャ：3つの役割

1. **検討エージェント**（対話型 pi）
   - 技術検討、ロードマップ策定、タスク分解。人間（PO）が直接会話する相手。
   - 検討用ブランチの worktree で動かし、成果物（タスク定義）だけを main にマージ。検討中の書き散らしを main に載せない。
2. **オーケストレータ**（決定的なコード。LLM ではない）
   - タスクキュー管理、実行者の spawn、フェーズゲート（plan → implement → self-audit → PO review）、マージ順序、レビューキュー。
   - 制御ループに LLM を置かない理由：最も信頼性が必要な層に非決定性を入れない。並列実行中に「気を利かせて」手順を飛ばす事故を構造的に防ぐ。
   - LLM が必要な判断（タスク分解、差分要約、コンフリクト時の再計画）は SDK の単発セッションをスポットで呼ぶ。
   - 人間との接点は pi TUI + Extension（`/spawn`, `/status` 等）として被せてよいが、状態遷移はコードが握る。
3. **実行者エージェント群**（RPC spawn）
   - 実装専任。ブランチごとの worktree で動作（cwd 分離、クラッシュ隔離、tmux ペインで人間の途中介入が可能）。
   - 自己監査は実装と同じコンテキストで行わせず、別セッションに差分だけ渡す（甘い自己評価を構造で防ぐ）。

## 4. インターフェース：リポジトリ内の構造化ファイル

- 検討エージェントとオーケストレータの間は IPC ではなく**リポジトリにコミットされた構造化ファイル**で繋ぐ。仕様も手順もリポジトリが真実、という claude-skills の思想と一致。
- **タスク定義**（設計→実装）: スコープ、受け入れ条件、監査基準。検討エージェントに `enqueue_task` カスタムツールを持たせ、書式検証＋コミットをコードで保証する。
- 利点：検討エージェントが落ちてもキューは壊れない。タスク定義が Git 履歴に残り、実行者の失敗をタスク定義の曖昧さに遡って改善できる。

## 5. レビューフロー（実装後の対話的レビュー）

- 対話的レビューは機械化しない。機械化するのは**エスカレーションの分岐点だけ**。
- 実装完了した worktree のレビュー用 pi セッションにアタッチ（タスク定義＋差分＋起動方法をコンテキスト注入）。動かしながら会話でレビュー。
- 分岐点を 3 コマンド（Extension）に集約：
  - `/fix` — インライン修整。同セッションで直してコミット、再監査ゲートへ。デフォルト
  - `/escalate` — 新スプリント化。レビュー会話からタスク定義を起こして enqueue（`enqueue_task` と同じ検証コードを通す）
  - `/adr` — 会話中の設計判断を ADR ドラフトに落とし docs/adr へコミット。タスク ID と相互リンク
- **アドホックスプリントも正規のキューを通す**。レビューセッションでの大改修＋直接マージは監査ゲートを素通りする裏口であり、最も危険なパターン。
- エスカレーション目安：受け入れ条件やスコープに触る修整は escalate、実装詳細の修整は fix。
- レビュー中の ADR は**ドラフト止まり**。正式化（Accepted 化）は検討エージェント側のフローに戻す。触りながらの判断は文脈が熱すぎるため、main の検討レイヤーを設計判断の関所として維持する。

## 6. エージェント間通信

通信の実体はエージェント同士の直接会話ではなく、**オーケストレータ経由の永続メッセージ**。通信路は以下の 3 本のみに限定し、すべてリポジトリとオーケストレータを通す。

1. **タスク定義**（設計→実装）: 前述
2. **design-inbox**（実装→設計、非同期メールボックス）
   - 実装・レビューエージェントの `request_design` ツールが、構造化ファイル（検討事項、背景、関連タスク ID、blocking/advisory）を `design-inbox/` にコミット。ADR ドラフトもこの一種
   - advisory: タスク続行。検討エージェントの session_start フックで inbox を提示し、そこから設計セッションを開始
   - blocking: オーケストレータがタスクを paused に遷移、検討依頼を優先キューへ。決定→タスク定義更新→実装再開
   - 「実装→検討→定義更新→再開」のループ全体が Git 履歴に残る
3. **同期 QA**（実装→設計、即答用）
   - `ask_designer` ツール → オーケストレータが短命の設計 QA セッションを SDK で spawn（ロードマップ＋関連 ADR を注入）→ 回答を返して破棄。回答は必ず inbox にログ
   - 乱用対策：QA 回答に「タスク定義の変更を要する → escalate せよ」の選択肢を持たせ、重い判断を弾く

## 7. UI（Palmux2 の進化方向）

- 軸を「worktree（場所）」から「タスクと役割（仕事）」へ。自分は PO として振る舞う。
- UI の第一原理は俯瞰ではなく「**いま自分の判断を待っているものは何か**」。PO レビュー帯域が既知のボトルネックなので、UI はその帯域の配分装置。
- 3 層構成：
  1. **アテンションキュー**（トップ）: レビュー待ち差分、blocking 検討依頼、承認待ち ADR、エスカレーション。ブロックしているタスク数でソート。動いているものではなく止まっているものを見る
  2. **エージェントボード**（俯瞰）: 行=タスク、列=フェーズのかんばん。オーケストレータのステートマシンを**そのまま描画するだけ**。オーケストレータが状態イベントを JSONL で吐き、WebGUI はビューアに徹する（UI 側に独自状態を持たせない）
  3. **ドリルダウン**: カードクリックでその worktree の pi セッション（tmux ペイン）へ。worktree 指向 UI は詳細ビューに降格して存続。pi の RPC イベントを繋げばアクティビティ表示も可能
- 注意：ダッシュボード作りは沼。v1 は「アテンションキューのリスト＋クリックで tmux ペインへ」だけ。

## 8. 実装順序

1. タスク定義のスキーマ
2. オーケストレータの最小ループ（spawn 1 並列＋レビューキュー）
3. 検討エージェントの `enqueue_task` ツール
4. レビュー 3 コマンド（`/fix` `/escalate` `/adr`）
5. design-inbox（advisory → blocking の順）
6. オーケストレータの状態イベント出力 → アテンションキュー UI
7. 同期 QA、エージェントボード等は運用が回ってから

並列度を上げるほど PO レビューがボトルネックとして先鋭化するため、spawn の多重化よりレビューキュー（差分要約＋承認待ち管理）を先に作る。

## 補足メモ

- 実装言語は TypeScript（pi エコシステムに乗る。pi 秘書と共通基盤化の余地）
- モデルは opencode をエンドポイント（モデルプロバイダ）として利用し、プロバイダ差し替え可能に
- Palmux2 の既存資産（tmux 管理、WebGUI、stream-json 連携の知見）はドリルダウン層とイベント購読でそのまま活きる
