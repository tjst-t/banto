# 記録：ADR-0001 の「88,711 ターン」はターン数ではない

> 2026-08-20、Phase 0 の実装中に見つけた。**規則8 に従い、ADR の数値は書き換えていない。**
> 直すかどうかは人が決める。

## 何が食い違っているか

`docs/adr/adr-0001-architecture.md` の「前提として押さえた計測」に、旧実装の
トランスクリプトを畳んだ数値がある。

```
キャッシュ読み  14,878,227,752  (97.9%)
1ターンの文脈    p50 90,949   p90 465,712   p99 839,320   max 999,622
200k 超のターン  25.4%
1,059 セッション・88,711 ターン
```

このうち **「88,711 ターン」はターン数ではなく、トランスクリプトの
assistant 行数**である。同じ計測をやり直すと：

```
ファイル数                          1,061
assistant 行数                     89,021   ← ADR の 88,711 に対応（計測日以降に増えた分）
相異なる (file, message.id)         49,085   ← これが実際のターン数
倍率                                 1.81
```

## なぜそうなるか

Claude Agent SDK の型定義（`sdk.d.ts`, `SDKAssistantMessage` の説明）にこう書いてある：

> While a response streams the CLI emits one assistant message per completed
> content block, so several consecutive assistant messages can share message.id
> and each carries just that block in message.content

**応答の streaming 中、完了した content block ごとに1通ずつ assistant メッセージが出る。**
それらは同じ `message.id` を持ち、**同じ累積 usage を載せている**。実測でも、
同一 `message.id` 内で4項目の usage が食い違った件は 0 件だった。

## 何に効くか

行単位で数えると：

| 影響 | 中身 |
|---|---|
| ターン数 | 1.81 倍に膨らむ |
| トークン総量 | 同じ値を重複して足すので膨らむ。ADR の 14,878,227,752 も同様 |
| 分位点 | 同じ文脈サイズが繰り返され、**content block が多かったメッセージに重みが寄る** |
| 不在の警報 | 「一度も下がらないターン数」が水増しされ、閾値に早く当たる |

一方、**割合（キャッシュ読み 97.9%）は比較的頑健**で、4項目が一緒に重複するため
おおよそ保たれる（重複度がメッセージごとに違うので厳密には一致しない）。

**「圧縮の発火 0 回」という結論は変わらない。** 横ばいは下降ではないので、
重複が偽の発火を作ることはない。

## 実装側でどうしたか

- `packages/runner`：`message.id` を見て重複を落としてから `turn.usage` を記録する
- `packages/observer`：観測は `turn.usage` だけを畳むので、この段で正しくなる
- トランスクリプトを読む経路では、**重複を落とした数と落とさない数の両方を出す**。
  片方だけにすると、ADR の数値と突き合わせられなくなる

## 人に上げること

1. ADR-0001 の計測欄を直すか。直すなら分位点とトークン総量は**測り直しが要る**
   （割合と「発火 0 回」はそのままでよい）
2. 「ターン」という語を、以後 `message.id` 単位に固定してよいか

## 併せて分かったこと：圧縮は発火していた（2回）

トランスクリプトには `subtype: "compact_boundary"` が **2件・2ファイル**残っている。
`pre_tokens` / `post_tokens` つきの `SDKCompactBoundaryMessage` である。

**usage の下降から導いた発火と、この目印は完全に一致した：**

| | 系列 |
|---|---|
| usage の下降（20% 以上）から導いた発火 | `b5a6faaa…`, `ff19db6a…` |
| `compact_boundary` を持つファイル | `b5a6faaa…`, `ff19db6a…` |

```
ff19db6a…  turn 618→619:  999,622 → 57,442  (94.3% 下降)  ← 同じ位置に compact_boundary
b5a6faaa…  turn 501→502:  999,014 → 55,391  (94.5% 下降)  ← 同じ位置に compact_boundary
```

どちらも 1M の上限に張り付いた直後に落ちている。**自動圧縮は動く。ただし
1,110 セッション中 2 回しか動いていない。** ADR の「1,210 ターン中 0 回」は、
その時点のセッション群については正しい。

### この節の前の版は間違っていた（記録として残す）

最初この節には「`compact_boundary` は 0 件」と書いた。**誤りだった。**
原因は自分の計測ミスで、次の形をしている：

```sh
cd ~/.claude/projects && grep -h -o 'compact_boundary' */*.jsonl 2>/dev/null | wc -l   # → 0
```

プロジェクトのディレクトリ名が `-home-ubuntu-...` と **ハイフンで始まる**ため、
glob の展開結果を grep がオプションとして解釈し `grep: invalid max count` で
失敗していた。`2>/dev/null` がそのエラーを消し、`wc -l` が 0 を返した。
**例外にならない失敗**（教訓13）そのもので、`find … -print0 | xargs -0 grep` で
数え直すまで気づかなかった。

規則1 の「自分の推論にも掛かる」はこういう形で効く。0 件という数字を根拠に
「圧縮の目印は残らない」という設計判断まで一度書いてしまった。

## 実装がこれに合わせて持っている形

圧縮の発火は2つの経路で捕まえる。

- **走行中**：ランタイムの申告（`compaction.reported` に記録）
- **事後**：usage 系列の下降から導く

両方を記録し、**食い違ったら DISCREPANCY として表に出す**。黙ってどちらかに
寄せない。今回はたまたま一致したが、一致することを前提にしない。
