# 携帯の大きさで打った文字がページに届かないことがある（Backlog #260、2026-10-11）

`browser-view.spec.ts` の「9. 携帯」で、指で入力欄を押してキーボードの欄から「けいたい」を打つと、送った本文が
`{"name":""}` になることがあった（#259 の確かめで4回中1回、2026-10-11 02:37 の流し直しでも1回）。
#259 の記録（`2026-10-10-browser-headful.md` の最後）では「Module の口に直接流すと8回中0回」だった。

## 原因

**Module が人の入力を CDP に投げるとき、前の応答を待たずに続けて投げていた**（`BrowserView.input`）。CDP の `Input.*` は
投げた順に処理されるとは限らない。指（`Input.dispatchTouchEvent`）はブラウザのプロセスの入力の経路を通り、触れた点から
タップの判定を経て、あとから入力欄に焦点が来る（mousedown → focus → click）。その直後に投げた `Input.insertText` は
それを追い越し、焦点の無いページに入って消えた。

画面側（隠した入力欄 → insertText）の順番は崩れていなかった：画面は指の start・end を送り、そのあと「キーボード」の
ボタンで隠した入力欄に焦点を移してから打つので、流れには touch start → touch end → insertText の順に載る（WebSocket は
順を保つ）。崩れたのは Module とブラウザの間。

### 測ったもの

Module の口（`BrowserView`）に偽の流れの相手を繋ぎ、展開した Google Chrome 155（画面あり・Xvfb）で、携帯の大きさに
合わせたページの入力欄に touch start・touch end・insertText を続けて流した。ページには touchstart・pointerdown・mousedown・
focusin・click・beforeinput・input を時刻つきで記録させた。混んだ機械は、プローブと Chrome と busy loop 3本を1コアに
固定して模した（同じ機械で別の作業ツリーの E2E が走っていたので、機械全体は混ませない）。

| 形 | 直す前 | 直した後 |
|---|---|---|
| 同じページで続けて（2回目以降は焦点の履歴が残る）・間 0ms | 20回中1回（いつも1回目） | 20回中0回 |
| **毎回読み直したページで初めての指**・間 0ms | **20回中20回** | 20回中0回・40回中0回 |
| 毎回読み直したページで初めての指・間 50ms | 20回中2回 | 20回中0回 |
| 同じページで続けて・間 100ms | 20回中0回 | — |

落ちた回のページの記録には beforeinput・input が無く、入力欄の focusin は insertText の後に来ている。さらに、焦点の
履歴が残っている2回目以降では `input` が `pointerdown` より**前**に記録される回が半分ほどあった——追い越しそのもの。

**E2E で4回に1回だった理由**：携帯の段の指は、そのページで初めての指（パソコンの段はマウス）。E2E は指で押してから
「キーボード」のボタンを押して打つので、画面の上では間が空く。機械が混んで流れの中継（画面 → host → core → Module）が
詰まると、その間が縮んで Module に続けて届き、追い越しが起きる。#259 の「Module の口に直接8回中0回」は、間を空けて
流したか、初めての指でなかったため（2026-10-10 の確かめの記録からは、どちらかまでは読めない）。

## 直し方

`BrowserView.input` を、前の入力の CDP の応答を待ってから次を投げる鎖にした。直した後の記録では、
タッチの end の応答が返った時点でそのタップの焦点・click がページで済んでおり、毎回 focusin → click → beforeinput → input の
順に来た（応答がそこまで待つことは Chrome の文書に書かれていない——測って確かめたこと）。
1つの呼び出しが返らなくても後ろの入力が全部止まらないよう、screencast の張り直しと同じ上限（5 秒、`bounded`）を付けた。

試験：`view.test.ts` に「指で入力欄を押してすぐ打った文字も届く」を足した（読み直したページで touch start・end・insertText を
間を空けずに3回）。直す前の Module では落ち、直した後は通る。

### とらなかった案

- **E2E で指のあとに待ちを足す**：規則6。Module とブラウザの間の順番が保証されていないこと自体が壊れている
- **画面側で、指の後しばらく insertText を遅らせる**：時間で順番を作る形。混んだ機械では足りなくなる
- **タッチのエミュレーション（`Emulation.setTouchEmulationEnabled`）を入れる**：ページから見える端末の性質が変わる
  （v4-modules.md §4.1 の「入力」で入れないと決めている）。順番の問題も解かない

## 残したもの（この件では触らない）

- 映していない間（screencast の張り直しの途中で `cast` が無い間）に来た人の入力は、今も黙って捨てる（`input` の頭）。
  この件の落ち方（指が届き、文字だけ消える）とは形が違い、今回の測定では起きていない。張り直しは「画面に合わせる」・
  タブの切り替え・映す画面の大きさの変化で起きる。見つけたら別の件にする
