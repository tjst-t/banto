# サイドバーの並べ替えと名前の変更（2026-09-11、ユーザー要望）

> 「左のサイドバーだけど、プロジェクトやフォークをドラッグアンドドロップで
> 並び順を変えられるようにしてほしい。また、右クリックでコンテキストメニューを
> 出して、プロジェクトやフォークの名前を変えられる項目を出して、それを
> クリックするとダイアログで変更できるようにしてほしい。」

決まったことは `docs/specs/v4-architecture.md` §2.2 と
`docs/specs/v4-frontend.md` §6.11。ここには**なぜそうしたか**と、
**作りながら実測で見つけたもの**を残す。

## 並べ替えの機構は自作しなかった（規則12）

「並べ替えられる一覧」には名前がある（sortable list）。掴む判定・運んでいる間の
入れ替え・自動スクロール・指とマウスの違いを自分で書くと、同じものを劣化させて
作り直すことになる。**dnd-kit を足した**（規則10——依存を足す理由）。

マウスは「8px 動かしたら」、指は「250ms 押したままなら」で掴み始める。**1つの
センサーで両方をまかなわない**——指で「距離」を見ると、一覧を縦にスクロールする
動きと並べ替えが区別できない（dnd-kit の定石そのまま）。

キーボードでの並べ替えは**付けなかった**。dnd-kit の KeyboardSensor は掴む対象に
`role="button"` を付ける必要があり、行が Link のここでは意味が壊れる。代わりに
メニューに「上へ／下へ」を置いた——掴めない場面（キーボード・細いレール・タッチ）
でも並べ替えられる。

## 並び順の持ち方——「順番そのもの」を1件で持つ

各要素に番号を振る形（`order: 3`）にしなかった。1件動かすたびに全件を書き直す
ことになり、途中で失敗すると番号が飛ぶ。`project.order.set { ids }` という
**順番そのもの**を1つのイベントにした。並びに無いものは後ろへ回す（fail open）
ので、並べ替えた後に作られた Project も一覧から消えない。

## 実測で見つけた3つ（どれも当てずっぽうでは出てこなかった）

1. **名前を変える口が、画面からは呼べなかった。** host に PATCH / PUT を足したが、
   CORS の `access-control-allow-methods` が `GET, POST, OPTIONS` のままだった
   ——preflight で弾かれ、画面には「Failed to fetch」とだけ出た。
   **口を足しただけでは繋がっていない**（規則13 の裏面）。
2. **並べ替えただけで、画面が移っていた。** 行そのものが Link なので、掴んで
   落とした直後の `click` が「その Project を開く」になっていた。掴んだ事実を
   1回覚えて、その直後のクリックを捨てる。
3. **並べ替えると、Fork の名前が入れ替わった。** 既定の呼び名 `Fork N` を
   **登録した順**で振っていたため、並べ替えてリロードすると番号が付け直された。
   名前は人が覚えているものなので、並び順で変わってはいけない——**作られた順**
   （host の `createdSeq`）から出すようにした。人が付けた名前（`explicitTitle`）は
   既定の呼び名と別に持つ（混ぜると、振り直してよいか決められない）。
4. **畳んだ Project が末尾へ押し出されていた。** 画面に出ている（畳んでいない）
   Project の並びだけを送っていたため、host 側で「並びに無いもの」として後ろへ
   回っていた。見えていないものの位置は動かさない。

## 回帰試験で踏んだこと（試験自身の穴）

- **行（`li`）を指して右クリックしない。** 開いている Project の行は下にぶら下がる
  目次まで含む高さなので、(1) 真ん中を押すと Base Thread に当たり、(2) 文字で
  絞ると Fork の名前でも親の Project の行に当たる——「Fork の名前を変える」
  つもりで Project の名前を変えていた。名前そのものから、いちばん近い取っ手へ辿る。
- **一覧はスクロールする。** Project が15件あると、末尾の行の座標へマウスを
  動かしても、そこには一覧の外がある（掴めない）。先に画面へ入れる。
  落とす前に「掴めていること」（`[data-dragging]`）を確かめるようにした
  ——そうしないと、掴めていないことが「並び順が保存されない」に見える。

## ついでに直した間欠（規則6）

全体を通したときだけ `turn-reattach` が落ちた。中身を見ると、待ち条件が
**「リロード後に 60 文字以上出ていること」**——つまり**どれだけ出るかという
AI 次第の量**を見ていた。前置きだけ先に出して本文を最後にまとめて出す走りだと、
45 文字で止まる（実測）。待ちを延ばさず、**見るものを変えた**：帯がそのターンの
出力を運んでいるか（量ではない）と、終わったあとに記録から中身が戻るか。

## 追記：背の高い行が運べなかった（ユーザー報告・2026-09-11）

> 「子要素を開いているProjectを移動しようとすると、ドラッグしている途中で、
> なんか変なぎゅっと圧縮された表現になるし、一番上とかに移動させられない。」

**両方とも「その行だけ背が高い」ことから来ていた**（実測）：

| 症状 | 実測した中身 |
|---|---|
| ぎゅっと圧縮される | 掴んだ行に `scaleY(0.333)` が掛かっていた（96px の行を 32px の行き先に合わせようとする） |
| 一番上に行けない | 一番上の行の上へ運んでも、1つ上までしか動かなかった |

行き先は**真ん中どうし**で決まるので、背の高い行の中心は先頭行の中心より上に
行けない（`restrictToParentElement` で親の外にも出られない）。つまり「届かない」
のは当然の帰結で、**高さが揃っていないことが原因**だった。

直し方は2つ入れた：

1. **運んでいる間だけ目次を畳む**（`expanded && !isDragging`）。これが効いた方
   ——戻すと試験が落ちる（高さ 64 のまま）。畳んだ／開いたという人の選択は
   変えない（落とせば元どおり）。運んでいる間に高さが変わるので、
   `MeasuringStrategy.Always` で測り直す
2. **大きさは運ばない**（`CSS.Transform` → `CSS.Translate`）。1 を入れた後は
   高さが揃うので単独では試験に出ないが、**行が2行になる**（長い名前）等で
   また高さが食い違ったときに潰れないための備え

## 追記：操作の口を「…」に集めた（ユーザー要望・2026-09-11）

> 「左メニューのFork Threadをマウスオーバーすると出てくるの右のマージボタンを
> 「・・・」みたいなボタンにして、タップすると右クリックと同じメニューが出る
> ようにして。あとメニューにマージのメニューも入れるようにして。
> BaseThreadでも、マウスオーバーしたときにたたむボタンの左横に「・・・」ボタンを
> 作って、タップすると右クリックと同じメニューが出るようにして。」

- **中身は1つ、出し方は2つ**。右クリック（ContextMenu）と「…」（DropdownMenu）は
  Radix では別の部品なので、**項目の並びをデータとして1つ持ち**、両方が同じ
  配列から描く（規則3——2つのメニューに同じ内容を書き写さない）
- **「…」は行の中に置く**ので、Dropdown の Root は ContextMenu の外側に要る
  （Trigger が自分の Root を見つけられなくなる）
- **畳む（マージのアイコンで出していたもの）はメニューへ移した**。行に出しっぱなしの
  操作を1つ減らす
- **畳んだレール（58px）には「…」を置かない**——アイコンと並べる余地が無い。
  そこでの操作の口は右クリック／長押し
- 「BaseThreadでも」は、**Project の行**（＝押すと Base Thread が開く行）と読んだ。
  「たたむボタン」はその行の目次の開閉（chevron）で、その左に「…」を置いた

**呼び名の食い違いを1つ残す**（規則8）：この操作のアイコンは合流（GitMerge）だが、
やることは**畳む**（閉じて履歴へ入れる）で、会話を親へ取り込むわけではない。
メニューの文言は製品の語彙に合わせて「畳む」にした。アイコンの方を変えるかは未決。
