# MCP Apps は公式の受け皿（App Bridge）を使う——自分で組まない

2026-09-06。`docs/tasks.json` の `phase1-canvas-embed-foundation` の着手前調査。

## 調べた理由

仕様（`v4-frontend.md` §6.2）は「二重 iframe と postMessage の中継」を受け皿として
決めているが、**tool の結果と Canvas をどう紐づけるか**が書かれていなかった。
自分で決める前に本家を読む（規則12）。

## 分かったこと

### 1. MCP Apps は正式な拡張になっていた（2026-01-26 版）

`modelcontextprotocol/ext-apps` として仕様・SDK・例が公開されている。
うちの仕様が「2026-08-29 に確認」と書いている内容は、その後の正式版とおおむね一致する。

### 2. **公式に host 側の受け皿（App Bridge）がある**

`@modelcontextprotocol/ext-apps`（1.7.5）の `app-bridge` が、まさに
うちが作ろうとしていたものを実装している：

- サンドボックス化した iframe への埋め込み
- postMessage の中継（JSON-RPC）
- **tool 呼び出しの代理**（View → host → MCP サーバ）
- ポリシーの適用（`permissions` / `csp`）

**しかも二重 iframe 方式で、内側は `sandbox: "allow-scripts"`**
（＝`allow-same-origin` を含めない）。**うちの仕様の決定と一致している。**
`ui/notifications/sandbox-proxy-ready` を受けて `sendSandboxResourceReady({ html, sandbox })`
で内側へ流す形。

→ **自分で組まない。公式を使う**（規則12）。仕様が「サンドボックスの作り方を
自分で考えない」と書いた狙いの、いちばん素直な実現。

### 3. 仕様に無かった「紐づけ」が分かった

- **tool 側**：`_meta.ui.resourceUri` で `ui://` 資源を指す。
  `_meta.ui.visibility`（`["model" | "app"]`）もある
- **資源側**：MIME は **`text/html;profile=mcp-app`**（必須）。
  `_meta.ui` に `csp`（`connectDomains` / `resourceDomains` / `frameDomains` /
  `baseUriDomains`）・`permissions`（camera 等）・`prefersBorder`・`domain`
- **ハンドシェイク**：View → host が `ui/initialize`
  （`appCapabilities.availableDisplayModes`）、host → View が `hostContext`
  （`displayMode` / `availableDisplayModes` / `theme` / `styles.variables` /
  `containerDimensions` / `toolInfo` 等）
- **View からの tool 呼び出しは `tools/call`**（core と同じ名前）。
  **仕様は「host が同意を求めてよい」としか言っておらず、必須ではない**
  ——**banto は必ず承認ゲートを通す**（§6.0、決定を明記する）

### 4. `hostContext.styles` で見た目を渡せる

`theme` と `styles.variables`（CSS 変数）を host が View に渡す形が仕様にある。
**モックが決めた色トークンをそのまま渡せる**——Module の画面が banto の見た目に
自然に馴染む。これは「Module 側に banto を知らせない」原則を崩さずにできる。

## 依存を1つ足す（規則10 の理由）

`@modelcontextprotocol/ext-apps` を frontend に足した。理由：
**サンドボックスと postMessage の中継を自作すると、穴があっても静かだから。**
公式実装は仕様の策定元が保守しており、うちが決めた「内側に `allow-same-origin` を
含めない」も満たしている。**自作の理由が無い。**

## まだ確かめていないこと

- **サンドボックスのプロキシ（外側 iframe の中身）をどう用意するか**
  ——`@modelcontextprotocol/ext-apps-sandbox` は npm に無い（404）。
  App Bridge は「プロキシから `sandbox-proxy-ready` が来たら HTML を送る」形なので、
  **プロキシ側のページは host（banto）が用意する**と読める。
  実装時に参照実装（`examples/basic-host`）を読んで確かめる
- CSP の組み立て（`_meta.ui.csp` から実際のヘッダ/属性へ）を App Bridge が
  どこまでやるか

## 参照実装を読んで確定したこと（同日）

`examples/basic-host` を読んだ。

### **host とサンドボックスは別オリジン（MUST）**——うちの仕様は誤っていた

参照実装のプロキシ（`sandbox.ts`）にこう書かれている：

> Double-iframe sandbox architecture: THIS file is the outer sandbox proxy
> iframe on a separate origin. ... **Per the specification, the Host and the
> Sandbox MUST have different origins.**

サーバも host（8080）と sandbox（8081）を**別ポートで**配っている。

うちの §6.2 は A2UI のガイドから「**同一**オリジンの中継 iframe」と書いていた。
**これは公式仕様と食い違う。** 黙って寄せず、§6.2 を訂正した（規則8）。

**なぜ別オリジンが要るか**：内側 iframe は
`sandbox="allow-scripts allow-same-origin allow-forms"` で作られる。
`allow-same-origin` があっても、**そのオリジンは banto ではない**ので、
banto の cookie・localStorage・DOM には届かない。
同一オリジンで中継すると、この前提が崩れる。

### プロキシは host が用意する

`sandbox.html` ＋ そこで動く小さなスクリプトを **banto が配る**。やることは：

- `window.self === window.top` なら即エラー（iframe の外で開かれたら動かない）
- **referrer を検証**して、埋め込み元が banto であることを確かめる
- **自己診断**：`window.top.alert()` が SecurityError にならなければ
  「サンドボックスが安全に組めていない」として**止まる**
  ——**壊れていたら黙って動かない**（規則2 と同じ発想が公式実装にも入っている）
- 内側 iframe を作り、host ↔ 内側 のメッセージを中継する
- **CSP は HTTP ヘッダで**与える（`?csp=` から組む）。meta タグは中身から
  改竄されうるので使わない

### banto での配置

画面は 4175。**サンドボックスは別ポートで配る**必要がある。
実装時に、frontend とは別の静的な口を1つ用意する。

## inline まで通した（同日、`phase1-canvas-embed-foundation` ＋ `phase1-canvas-inline`）

### 通した経路

```
FileSystem Module               listDirectory に _meta.ui.resourceUri
  ui://banto-filesystem/directory（text/html;profile=mcp-app）
        ↓ host が中継（GET /api/threads/:id/ui-resource）
banto の画面（4175）
  └ 外側 iframe … sandbox.banto.tjstkm.net（別オリジン）＝中継だけ
      └ 内側 iframe … Module の HTML が動く
        ↓ 画面が tools/call
POST /api/threads/:id/ui-tool-call → **Inbox の判断待ち** → 承認 → Module
```

### 決めたこと

- **画面からの `tools/call` は必ず承認ゲートを通す。** 仕様は「host が同意を
  求めて**よい**」としか言っていない。banto は必ず通す——画面は Module 発の
  他人のコードで、人が押した憶えのない操作を起こせてはいけない。
  **Runner の canUseTool と同じ Inbox に載せる**（承認する場所を2つに割らない、規則3）
- **住所は host が答える**（`GET /api/ui-config` の `sandboxUrl`）。
  画面に推測させない（規則3）——Caddy 経由か LAN 直か E2E かで値が違う
- **枠はモックが決めた形のまま。** 変わったのは中身だけ
  （固定データ → 本物の Module の画面）

### 確かめたこと（規則1）

**`_meta` は SDK を通っても消えないのか**——以前 `initialize` の応答に載せた
`_meta` が**スキーマで削られて host に届かない**ことを実測している。
tool の `_meta.ui.resourceUri` も同じ経路なので、**本物の Module を立てて確かめた**
（`ui-app-passthrough.test.ts`）。消えなかった。

E2E は「出た」で終わらせず、**できてはいけないこと**まで見る：

- 内側の画面から `window.top` に触れられない（別オリジン）
- 画面から banto の保存領域（host の合言葉が入っている）が見えない
- 画面のボタンを押しても、**承認するまで Module は呼ばれない**
- サンドボックスの `frame-ancestors` に `*` が無い／この口は他に何も配らない

### 途中で踏んだこと

**画面は出たのに中身が空、という一番たちの悪い形**（規則13 そのもの）を2回踏んだ。

1. **tool の結果の形が3通りある。** 会話に載っている結果は、文字列のことも、
   ブロック配列のことも、`{content:[…]}` のこともある。揃えずに渡すと画面には
   何も届かないのに、画面は出たままになる
2. **`ui/notifications/tool-result` の `params` は `CallToolResult` そのもの**
   （`params.result` ではない）。読み違えたまま「一覧を読み取れませんでした」を
   表示していた——**画面側が「読めなかった」と正直に出す作りにしておいたので、
   すぐ場所が分かった**（規則2）

どちらも**ハンドシェイクは全部成功していた**ので、通信ログだけ見ると正常に見えた。
中身（画面に実在するファイル名が並ぶか）を見る E2E でなければ素通りしていた。

## 間欠を1つ潰した——Module の二重起動（同日、規則6）

E2E がときどき落ちるので回数を測った（**3回中1回**）。ログに原因が出ていた：

```
age-keygen: error: failed to open output file ".../vault/identity.txt": file exists
```

### 何が起きていたか

`spawnDeclaredModule` は「もう起動しているか」を見てから実際に登録するまでに
**await が挟まる**。その隙に同じ Module へのもう1本が同じ判定を通ると、
**2つ立ち上がる**。Vault は起動時に鍵を作るので、2本目が「もうファイルがある」で落ちた。

隙は前からあったが、**今回 `ui-tools` の取得をターン開始時に足したことで、
ターン自身の Module 解決と並走するようになり、踏みやすくなった**——
入れたのは自分の変更である。

### 直し方（待ちを延ばさない・リトライを足さない）

**同時に来たものは同じ1本を待つ**。single-flight という名前のある機構なので、
自分で考えずに既知の形を使った（規則12）。`modules/single-flight.ts` に切り出し、
先に落ちるテストを4件書いた——とくに
**「失敗しても次に持ち越さない」**（失敗した1本に永久にぶら下がらない）。

罠が1つ：申告に合わせて宣言を直したあとの**再起動が自分自身を待って止まる**
（同じ鍵で single-flight に再入する）。ここは内側の関数を直接呼ぶ。

### 測り直した結果

4回連続で Vault の二重起動は**再発なし**。

### もう1つの間欠は、機構ではなく機械の混み具合だった（記録・規則6）

二重起動を直したあと、`shell-confinement` が**4回中2回**落ちた。
最初は既知の `ui-codeblock-cjk`（コードブロックで日本語が出ない）を疑ったが、
**測ったら違った**：

| 測ったこと | 結果 |
|---|---|
| その spec を単体で回す | **7回中7回通過**。DOM にも全文が入っている |
| フルスイート（落ちた回） | 所要 **3.1〜3.2分** |
| フルスイート（通った回） | 所要 **1.5〜1.7分** |
| 診断を戻して3回（負荷 3.3〜6.4） | **3回とも15件全通過**、各 89〜92 秒 |

落ちた回は**約2倍遅い**。失敗時の画面には答えが途中まで（`中は読める1`）しか
描かれておらず、**120秒の待ちが、まだ流れている途中で切れた**形と一致する。
この作業ツリーは他の作業と機械を共有しているので、**遅いのは banto ではない**。

**待ちは延ばさない**（規則6）——延ばすと、本当に遅くなったときに気づけなくなる。
数値を残して、次に落ちたら**まず所要時間と負荷を見る**。

## 実機で2つ出た（ユーザー報告・2026-09-06）

**E2E は通っていたのに、実際に触ると2つ壊れていた。** どちらも
「host 側は正しく動いているのに、人には見えていない」形——**API で確かめて
満足していた**のが穴だった（規則14 の言う「操作が通る」で止まっていた）。

### 1. 画面が「N tool calls」の中に畳まれていた

inline があれば tool グループを自動で開く仕組みは**すでにあった**。
ただし**モック側の登録簿しか見ていなかった**ので、実 Module の Canvas が
数に入らず畳まれた。入れ漏れ。

### 2. 画面からの承認が、人に見えなかった

判断待ちは**立っていた**（受信箱に残っていた）。見えなかった理由は2段。

**(a) ターンが終わっても「走行中」が降りていなかった。**
ランタイムは最後の `yield` を受け取ったあと `next()` を呼ばないことがあり、
**その先のコードは実行されない**——`finally` も、ループを抜けた後の行も通らない。
**放置ターンで踏んだのと同じ罠を、同じ場所でもう一度踏んだ。**
走行中のままだと `hasLiveRealRun` が真で、ターン後に立った判断待ちが
会話に描き直されない。**host の終了イベント（`type: "done"`）を受けた時点で降ろす**
——ここは必ずループの中を通る。

**(b) 承認を会話のカードとして出すと、画面自身が消えた。**
会話の組み直しは host の記録（＝テキスト）からしか作れないので、
tool のカード＝画面ごと消える。**押した相手が消える承認**は意味がない。

### 決定：画面からの承認は、その画面のその場に出す

枠の上に「〈Module〉の画面が〈tool〉を実行しようとしています」と
許可する／拒否する を出す。答えは Runner の承認と**同じ口**
（`/api/inbox/:id/answer`）へ送るので、**host から見た承認の経路は1本**（規則3）。
会話側には二重に出さない——画面が面倒を見ている判断待ちは
`restoredJudgmentMessages` から除く。

**リロードすれば画面は消えるので、そのときは会話のカードとして復元される**
（除外は「いまこのブラウザの画面が抱えている間」だけ）。

### テストの穴も直した

承認を **API で立っていること**でしか見ていなかった。いまは
**畳まれずに見えていること**・**画面のその場に承認が出て中身が読めること**・
**人と同じボタンで答えること**（API の裏口を使わない）まで見る。

### inline の置き場を決め直した（2026-09-07、ユーザー指摘）

**「tool コールの折りたたみの中に inline を出す」という要件は、仕様に無かった。**
出どころは**モックの構造**だった——`HumanToolCard` は tool ごとの
`ToolFallback` として呼ばれるので、そこから inline を返すと必然的に
ToolGroup の中に入る。モックはそれを前提に「inline があるときは自動で開く」を
足していた。実装はその構造をそのまま引き継いでいた。

**決め直した：inline は tool コールの折りたたみの外に置く。**
きっかけが AI の tool 呼び出しでも、Canvas は**人が見て操作する面**であって
AI の作業ログではない。畳める領域に入れると、人が畳んだ瞬間に画面が消える。

`mock/` も同じ形に直した——決定は1つ（規則3）。自動で開く条件から
`hasInlineView` を外した（外に出したので、開く必要がなくなった）。

**踏んだこと**：折りたたみの外に並べるとき、`useAuiState` の selector が
**毎回新しい配列を返す**形にしたら、再描画が止まらず**画面ごと落ちた**。
TypeScript は通っていて、E2E で初めて分かった。部品ごとに読む形に直した。

E2E は「見えている」で終わらせず、**tool コールを畳んでも画面が消えない**ことを
見る（置き場の決定そのものを、操作で確かめる）。

### 間欠の犯人を取り違えていた——**描画側だった**（訂正・2026-09-07）

`shell-confinement` の間欠を、いちど「機械の混み具合」と判定した。**これは誤り**。
低負荷でも3回連続で落ちた。**落ちた回の中身を必ず残す**形に変えて測り直したところ、
決着した：

```
[HOST] "…出力（stdout）はそのまま以下のとおりです。\n\n```\n中は読める1788745124738\n```"
[DOM]  ["中は読める178\n"]
```

**host には全文がある。画面のコードブロックだけが途中で止まっている。**
止まる位置は毎回違う（`中` / `中は読める1` / `中は読める178`）ので日本語固有ではない。
**止まった後に来た段落は正しく描けている**ので、通信で落ちているのでもない
——ストリーミング中に**そのコードブロックだけが更新を止める**。

ユーザーが最初に報告した「コードブロックで日本語が表示されない」は、
**日本語が先頭にあったからそう見えていた**だけで、同じ不具合だった。
起票（`ui-codeblock-cjk`）に証拠を書き、backlog から todo に上げた。

**テストは緩めない**（規則6）——本物の不具合を隠すことになる。
フルスイートは約3回に1回、ここで落ちる。

#### この取り違えから学んだこと

最初の判定は「落ちた回は所要が2倍だった」という**相関**だけを根拠にしていた。
**落ちた回の中身を見ていなかった**のが誤りの原因。
間欠を追うときは、**落ちた瞬間の状態を必ず残す仕掛けを先に入れる**
——通ってしまうと何も分からないまま次の実行に進んでしまう。

## 「ボタンを押すと会話が消える」の根（ユーザー報告・2026-09-07）

> 更新するボタンを押したら、そのターンの会話が全部消えて Tool の許可を求めるのが
> 出て、許可したらまたターンの会話が復活するけど、MCP Apps の表示は消える

### 根は SSE の読み方だった

**受信と、描くために渡すのを1本のジェネレータでやっていた**ため、
**描く側が最後まで引き取らないと、その先が読まれない**。実測すると、
ランタイムは最後の yield のあと次を要求しないことがあり、その結果
**ターンの終了イベント（`done`）が一度も処理されない**ことがあった。

これが2つの壊れ方を生んでいた：

- ターンが**「走行中」のまま**残る → そのあとに立った判断待ちが会話に描き直されない
- **文脈使用量が記録されない**（`done` に載っている）

`streamRealTurn` を、**受信を独立した繰り返しで回し、届いた端から渡す**形に変えた。
描く側の都合で受信が止まらない。終了時の処理（使用量の記録・走行中を降ろす）は
**受信した時点**で行う。

### 画面の印は「呼ぶ前」に、Thread 単位で立てる

承認を画面のその場に出す仕組みは入れていたが、**判断待ちの id を知るために
受信箱を取り直した瞬間に、印を立てる前に会話が組み直されていた**。
id は呼んでみないと分からないので、**呼ぶ前に分かっている Thread で覚える**形に変えた。

### E2E がこれを見逃していた理由——**人と同じ順番で操作していなかった**

テストは**ターンが終わる前に**画面のボタンを押していた。終わる前は
「走行中」なので会話は組み直されず、**実機で起きることが起きなかった**。
`done` が届くのを待ってから押すように直したら、**直す前の状態で確かに落ちた**
（`live:false, restored:1` → 会話が組み直されて画面が消える）。

さらに、**要素が生き続けていること**（`isConnected`）で見るようにした
——「見えている」だけだと、いったん消えて作り直されても通ってしまう。
実機で起きたのはまさにそれ（会話が消える→承認→会話は戻るが画面は消える）。

### 教訓

**テストは、人がやる順番でやる。** 「操作が通る」ではなく「人が実際にたどる道」を
なぞらないと、待ちの差だけで別の状態を試すことになる（規則14 の延長）。

## リロードで画面が消える（ユーザー報告・2026-09-07）

会話は host の記録から組み直される。その記録は**文章だけ**（`{seq, role, text}`）
だったので、**tool のカードごと画面が失われていた**。

**画面つき tool の呼び出しを記録に残す**ことにした。残すのは表示の復元に要る分
だけ——`toolCallId` / `toolName` / `server` / `resourceUri` / 引数 / 結果。
**画面を持つ tool だけ**が対象で、それ以外の結果は積まない
（実行の再現は resume-point の仕事。会話の記録を膨らませない）。

- どの tool が画面を持つかの算出は**1箇所**に置いた（受け皿の口とターンの記録が
  同じ答えを見る、規則3）
- read model の版を v6 に上げた（`MessageEntry.uiToolCalls` を足したため）
- 一覧を取れなくてもターンは止めない——画面が出ないだけで会話は続く

E2E に「**リロードしても画面と中身が残る**」を足し、**記録を渡さない状態では
実際に落ちる**ことを先に確かめた（`リロードしたら Module の画面が消えた`）。

## fullscreen（会話の隣に開く）——`phase1-canvas-fullscreen`（2026-09-07）

**起点は画面からの要求**（`ui/request-display-mode`）。仕様の交渉モデルどおり、
**決めるのは host**——出せないなら「出せない」と答える（黙って無視しない）。
FileSystem の画面に「大きく表示」を足して、実際に頼めるようにした。

**出す先はモックが決めた枠のまま**（会話の隣のパネル、ヘッダ・閉じる・全画面・別タブ）。
中身だけが固定データから本物に変わる。

**どの面かは URL に持つ**（`canvas=<Module>:<ui://…>` ＋ `canvasTool=<toolCallId>`）
——リロードしても同じ面が開き直る。真実は URL（規則3）。

会話の奥（inline の Canvas）から「開いて」を伝えるのに、context を1本だけ通した
——props では届かない。運ぶのは合図だけで、**どこに出すかは受け取った側が決める**
（§6.2「Module は『どんな面か』を宣言する。banto が『どこに出すか』を決める」）。

**踏んだこと**：fullscreen 側に tool の**結果**を渡しておらず、枠だけ出て中身が空だった。
Canvas パネルからは会話の parts を読めないので、面と一緒に結果も覚えるようにした。
E2E が「Canvas に中身が出ていない」で捕まえた——**枠が出たで終わらせない**（規則14）。

### 「最初から fullscreen」はどう表すか（ユーザー要望・2026-09-07）

**仕様を確認した：宣言する場所は無い。** tool の `_meta.ui` は
`resourceUri` と `visibility` だけ、資源の `_meta.ui` は `csp` /
`permissions` / `domain` / `prefersBorder` だけ。display mode を動かす道は
`ui/request-display-mode`（画面が頼み、host が決める）1本しかない。

**そこで tool の引数にした**（`displayMode: "inline" | "fullscreen"`）。
AI が指定 → 画面が `tool-input` で受け取る → 立ち上がった直後に自分で頼む。
**banto 側に新しい機構は要らない**（既にある受け皿を通るだけ、規則12）。
名前と語彙は仕様に合わせた——独自の呼び名を作らない（規則11）。

これは**Module の裁量**でもある：どの tool が見せ方を選べるかは Module が決める。
banto は「どこに出すか」を決めるだけで、この分担は崩れていない。

E2E は**人の言葉のまま**確かめる——「フルスクリーンで開いて」と送るだけで、
ボタンは押さない。開かなければ「頼んでも Canvas が開かなかった」で落ちる。

## 設定画面への埋め込み——`phase1-canvas-config`（2026-09-07）

**Module が名乗ったものだけを出す。** 資源の `_meta` に
`dev.banto/canvas: "config"` と書いてあるものを、Project 設定の
「Module の設定」に埋める。**投機的に `ui://<id>/config` を読みにいかない**
——「在るかもしれない」を毎回試すと、無いのか壊れているのかが曖昧になる（§6.2）。

MCP Apps の仕様に「設定画面」は無い（UI のライフサイクルは tool 起点だけ）。
**ここは banto が足した拡張**であると自覚して扱う。

**設定は Thread のものではない**ので、host に Project 単位の口を足した
（`ui-settings` / `ui-resource` / `ui-tool-call`）。承認は**その Project の
Base Thread** に載せる——答える場所を増やさない（規則3）。

### 副産物：**Module 自身の状態の置き場が無かった**

FileSystem に実際に効く設定を持たせようとして分かった：**閉じ込めは Project の
根しか書かせない**ので、Module が自分の設定を保存できない。Project の中に書けば
人のリポジトリを汚す。

`${moduleDataDir}` を足した——**Module ごとに1つ**、banto が用意して、
閉じ込めていてもそこだけは書ける。banto のデータ置き場**全体**は開けない。
これは設定機能の副産物ではなく、**Module 契約の欠けていた部分**だった。

### E2E で見ていること

1. 名乗った Module の設定画面が、設定の中に出る（中身まで）
2. **変えた値が Module 側に残る**（開き直しても戻らない）
3. **その値が実際に効く**（一覧から隠しファイルが消える）
4. 設定画面からの呼び出しも**承認を通る**

### 踏んだこと（テスト側の間違いが2つ、実装の不具合が1つ）

- **実装**：設定は URL が持っているので**リロードしても開いたまま**。テストが
  それを知らずに「もう一度開く」を押し、**その場所にある×を押して閉じていた**。
  ブラウザのコンソールに閉じた経路のスタックを出して特定した
- **テスト**：前のターンの画面を見て「変わっていない」と誤判定していた
  ——新しい一覧が出るまで待つ必要があった
- **実装**：埋め込んだ iframe に焦点が移ると Dialog が閉じうるので、
  この画面では閉じないようにした（触った瞬間に設定画面が消えるのを防ぐ）

### 承認の方針を改めた（ユーザー指示・2026-09-07）

> 同じ MCP の tool にアクセスするのに許可を求めるのは出ないでほしい

2026-09-06 は「**画面からの tools/call は必ず承認ゲートを通す**」と決めていた。
**改める**：**画面が自分の Module を呼ぶときは承認を求めない**。

理由：**その画面を開いたのは人**である。人が開いた画面の中のボタンが、その画面を
出している Module 自身の tool を呼ぶのは、画面が仕事をしているだけで、
「人の知らないうちに何かが起きる」ではない。設定を見るたびに承認を求めるのは、
**承認の意味を薄めるほうに働く**（毎回押すものは、いつか読まずに押す）。

**AI からの tool 呼び出しは今までどおり承認ゲートを通る**——そちらは人が見て
いないところで起きるので、性質が違う。

**他の Module は呼べない**：呼び先は画面が指定するのではなく、その画面がどの
Module のものかで決まる（フロントエンドが握る）。画面から banto の API を直接
叩くこともできない（別オリジン・合言葉を持たない）。

**残る risk を記録する**：Module 自身の画面が、その Module の危ない tool（削除など）を
黙って呼ぶことはできる。**Module を繋ぐこと自体が信頼の線引き**で、その手前は
閉じ込めと可視性で守る。

### 設定の置き場は Module の scope が決める（ユーザー指摘・2026-09-07）

> MCP Apps の設定画面は Project にしか出ない？ Global な設定と使い分けられない？

**instance に1本の Module（Vault）の設定を Project ごとに出すのはおかしい。**
置き場は**その Module の scope から導く**（規則3——別の判断基準を持たない）：

| Module の scope | 設定の置き場 |
|---|---|
| `instance`（Vault） | banto 全体の設定（`/settings` →「Module の設定」） |
| `project`（Shell・FileSystem） | その Project の設定 |

Vault にも設定画面を持たせた（登録されている alias の一覧。**値は返さない**）
——**両方に実物がある状態で**、E2E が「どちらにどれが出るか」を直接見る。

### 別タブで開くと中身が出なかった（ユーザー報告・2026-09-07）

`/canvas-window`（クロム無しで Canvas だけを出す画面）が**モックの固定データを
描いていた**——実 Module の画面を知らなかった。

**別タブは手元の記憶を持たない。** 元のタブが覚えている「どの Module の
どの画面を、どんな引数で呼んで何が返ったか」は新しいタブには無い。
**host の記録（`uiToolCalls`）から引き直す**——真実は host（規則3）。
URL に `thread=<threadId>` を足して、どこから引くかを運ぶ。

E2E に足すときに2つ踏んだ（どちらもテスト側）：

- `window.open(..., "noopener")` で開いた窓は **popup として拾えない**
  ——同じ文脈の新しいページとして現れる
- 「全画面」「別タブで開く」は**携帯幅では出さない**作り（モックの決定）。
  E2E は携帯幅で回しているので、この確認だけ画面を広げる

**直す前に落ちることを先に確かめてから**直した（`thread` を運ばない状態で失敗）。

### 設定画面の形をモックに合わせた（ユーザー指摘・2026-09-07）

> モックでは左メニューに出て、右側を全部使って UI を出しています

最初の実装は「Module の設定」という節を1つ作り、その中に全 Module の Canvas を
縦に積んでいた。**モックはそうなっていない**——左メニューに Module ごとに並び、
選んだものが右側いっぱいに出る。

**モックの `SettingsShell` が既にその枠を持っていた**（`moduleImplementations` を
受け取り、左メニュー下段にフラットに並べ、`module:<id>` の節として描く）。
実 Module をその枠に流し込むだけで済んだ——**枠を作り直す必要は無かった**。
instance でも Project でも同じ枠で、**渡す一覧が変わるだけ**（§6.1 の設計どおり）。

左メニューに出る名前は、Module が資源に付けた `name` をそのまま使う。
両方「この Module の設定」だと見分けられないので、Module 側を
`FileSystem` / `Vault` に直した。

**実機で見た目まで確かめた**——左メニューに Vault、右側の Canvas は 1038×793。

### 設定が保存できない Project があった（ユーザー報告・2026-09-07）

```
MCP error -32603: 設定の置き場が渡されていません（BANTO_FILESYSTEM_DATA_DIR）
```

**MCP サーバ側の問題ではなく banto 側。** その Project は**宣言の写しを
Config に持っていて**（2026-09-06 に自己申告との突き合わせで書き戻したもの）、
それが「設定の置き場」を足す前の版だった。既定の宣言を更新しても、
**写しを持っている Project には届かない**（規則3——写しはいつか食い違う）。

**誤りは「host が必ず用意する値を、宣言に書かせた」こと。**
Module ごとのデータ置き場は host が作り、閉じ込めの許可も host が出している。
**それを渡すかどうかを宣言まかせにする理由が無い。**
`BANTO_MODULE_DATA_DIR` として host が常に渡す形に変えた。

Module 側にテストを足した：「渡されていれば残る」「渡されていなければ
**保存できたふりをしない**」。実機でも、古い宣言を持つその Project で
実際に保存できることを確かめた。

**残る一般問題**：宣言の写しを Config に持つ Project は、既定を更新しても
古いままになる。いまは「host が必ず渡すもの」を宣言から外すことで回避したが、
**写しと既定の関係そのもの**は未整理（`phase1-project-modules-ui` で人が
宣言を触れるようにするときに、合わせて決める）。

### 「写し」をやめた——VS Code に倣う（決定・2026-09-07）

前節の事故（設定が保存できない Project）の**一般形**を直した。

**調べた**：VS Code は同じ問題を、同じ場所で解いている。

- 層を重ねる（既定 → ユーザー → ワークスペース → フォルダ → …→ ポリシー）
- **既定はファイルに書かない**。設定ファイルに入るのは**変えた項目だけ**
- **「プリミティブと配列は置換、オブジェクトはマージ」**
- MCP の設定でも `${workspaceFolder}` のまま保存し、**起動時に解決**（値を焼き込まない）
- 変えた項目は左に色の帯、歯車から「既定に戻す」

**banto も同じ形にした。** 今回の事故は `env` を丸ごと置き換えていたから起きたので、
**キー単位マージなら起きない**。

ひとつ設計を誤りかけた：「丸ごとの写しを差分に圧縮すれば、古い形も新しい形も
同じ道を通る（冪等）」と考えたが、**意味が違うので同じ鍵に混ぜられない**
——差分の「書いていない」は既定のまま、写しの「載っていない」は外した、である。
**鍵を分けた**（`moduleOverlays` に書き、古い `modules` は読むだけ）。
既存のテストが落ちて気づいた。

なお、今日先に直した「host が必ず渡す値は宣言に置かない」は、
**VS Code のポリシー設定と同じ扱い**だった——偶然だが方向は合っていた。

## ランチャー——人が、AI を介さずに開く（`phase1-canvas-launcher`、2026-09-07）

**MCP Apps では AI が tool を呼ぶまで Canvas が出てこない。** だが
「まずファイルを見たい」は AI に頼む用事ではない（要件C3）。

**設定 Canvas と同じ1つの仕組み**で名乗る——資源の `_meta` に
`dev.banto/canvas: "launcher"`。鍵は同じで値だけが違う（増やさない、規則12）。
人に見せる名前と説明は**仕様の `name` / `description` をそのまま**使う
（banto 独自のフィールドを足さない、規則11）。

一覧は host が Project の Module 集合から導出する（`GET …/ui-launchers`）
——画面は別の索引を持たない（規則3）。

### 決めたこと：**tool 起点でないときは `toolInfo` を渡さない**

仕様の `hostContext.toolInfo` は「この App を起こした tool 呼び出し」。
人が入口から開いたときは**そんなものは無い**ので、渡さない。
画面はそれで「人が直接開いた」と分かり、自分で `tools/call` して中身を取りに行く
——§6.2 が言う「launcher も同じ形。Canvas が自分で必要なものを取りに行く」が、
実装としてもそのまま出てきた。

最初 `toolName: "launcher"` という偽の tool 名を渡そうとして、画面が
「tool 起点だ」と誤解し中身が出なかった。**無いものを作らない**が正しい形だった。

### モックと仕様が食い違っていた（規則8）

モックの入口は `?…&fullscreen=1` を付けていた。これは **banto のパネル状態**
（会話を隠す全画面）であって、**仕様の display mode ではない**。
§6.2 は `fullscreen`＝**会話の隣**と決めているので、そちらに合わせた。
黙って寄せず、仕様に注記した。
