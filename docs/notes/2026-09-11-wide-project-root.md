# 広い根（home）を止めるのをやめた（2026-09-11、ユーザー決定）

> 「BantoTest-renamed でいちど Shell を消して、使えなくなったことを確認してから
> つなぎなおしたけど、まだ使えません。」
> →（原因を説明したあと）「home を根にしても別にいいのでは？ というか、
> ちゃんと使えるようにしてほしい。」
> →「Project を作る時に警告する、かつ Project の Module 設定のところでも警告を
> 出す、というのでいいでしょうか？ つまり AI でいろいろやらせたい場合もあるかも
> しれないので。」
> →（鍵だけ外す案に対して）「いや、それ結構なんか複雑になりすぎる気がする。
> 問題になるまでは、全部アクセス可能にしておこう。」

決まったことは `docs/specs/v4-security.md`。ここには**どう切り分けたか**を残す。

## 報告は「繋ぎ直しが効かない」だったが、原因は別だった

実測：その Project の根は `/home/ubuntu` で、**Landlock の検査が shell と
filesystem の起動を止めていた**（2026-09-10 に配線したもの）。つまり
**外す→繋ぎ直す**の操作は正しく効いていて（`selected: true` になっていた）、
起動が別の理由で止まっていた。

**画面がそれを言っていなかった**のが、こちら側の穴。一覧は「使う」としか
出しておらず、「使うと言っても立たない」ことが分からなかった（規則13）。
`GET /api/projects/:id/modules` に **いま繋がっているか・繋げなかった理由** を
足した（起動はしない——一覧を見ただけで全部を起こさない）。

## 止めるか、見せるか

`assertRulesetIsSafe` は2つの違うものを1つの検査で捕まえていた：

1. **導出が静かに広がった**（PATH の realpath の親が紛れ込む等、poc/07 の事故）
2. **人が広い根を選んだ**（home を Project の根にした）

1 は事故なので止める。2 は**人の選択**であって事故ではない。
止めるのをやめ、**選ぶ前に見せる**ことにした（新しい Project／Module 設定の2箇所）。
検査は「人が選んだ根だけを免除する」形に変えたので、1 はいまも捕まる。

## 鍵だけ外す案は却下した

home を根にすると、AI のシェルから banto の合言葉・記録・Claude の資格情報が
読める。「home の直下を1つずつ許可して、その3つだけ許可しない」形にすれば
守れる（Landlock は許可しか書けないので、この形しかない）。

**却下**（ユーザー判断）：複雑になりすぎる。`~` 直下に新しいファイルを作れなく
なるという副作用もあった。**問題になるまでは全部アクセス可能**にしておき、
必要になったらそこから作る。**残るリスクは仕様にそのまま書いた**
——黙って弱くしない（規則2）。

## 追記：Root の呼び名・文言・選び方（2026-09-11、ユーザー指摘）

- **呼び名を `Root パス` に統一**——作る画面が「Base パス」、設定画面が「Root パス」で
  割れていた（規則11）。履歴（Archive）の概要も揃えた
- 説明の文も揃えた：**「Shell・FileSystem などの Module は、この Root パスの中のみ
  アクセス可能」**（元は「この根に閉じ込める」——閉じ込めという言い方が固かった）
- **打っても選んでもよい**——入力欄はそのまま残し、右に「選ぶ」。フォルダを辿る
  ダイアログが開く。一覧は host が答える（`GET /api/fs/directories`、**フォルダの
  名前だけ**）

### 間欠を1件、記録に残す（規則6）

フル実行のうち**1回**、`sidebar-reorder-rename` の「面の題は Project 名だけ」で
「作成する」が押せないまま時間切れになった。同じ試験を単独で走らせると通り、
フル実行をもう一度通したら 55件とも通った（落ちた回の実行は 10.5分・通った回は
5.5分で、機械が重かった回に当たっている）。

**直していない**——原因を機構に特定できていないため。**計測だけ残す**：
1/2 回（重い実行のとき）、単独では 1/1 通過。次に見えたら、待ち条件ではなく
「作成する」が押せるようになる条件（名前と Root が入っているか）を画面から
測るところから始める。

### 追記・2026-09-12——もう1回出た。**症状が一段絞れた**

`vault-ui` の作業中のフル実行で、`frontend-interaction` の「実 Thread には、
やり直しを出さない」が同じ形で落ちた。**相関は同じ**：落ちた回は 10.9分、
その前後に通った回は 6.1分と 5.8分。**通算 1/3 回**（同じコードで前後の実行は
60件とも通過）。
**さらに 2026-09-12 中に2回——通算 3/7 回**（`sidebar`・`fork-from-message`・
`project-modules` と、毎回ちがう spec で出る。共通なのは「重い実行」だけ）。

**新しく分かったこと**：trace のログでは「作成する」は**消えていない**。
`<button disabled …>作成する</button>` として**存在したまま、5分間ずっと無効**
だった。無効になる条件は `!name.trim() || !basePath.trim() || submitting`
なので、**`fill()` は通ったのに React 側の state が空**——つまり
`element was detached`（前回の症状）ではなく、**入力したあとにダイアログが
作り直されて state が初期化されている**。

つまり `openApp` の「行き先が決まりきるまで待つ」では足りていない
——URL が `/p/...` になったあとにも、画面を作り直す出来事が残っている。

### 追記・同日中にもう1回（通算 2/4 回）——**仮説が立った**

`sidebar` の「設定は1つの面」でも同じ形で落ちた（症状・相関とも同じ）。
2回とも **`<button disabled>` のまま**で、消えてはいない。

**仮説（まだ実証していない）：ハイドレーション前に入力している。**
新規 Project のダイアログの入力欄は制御コンポーネント（`value={name}`）なので、
**React が繋がる前に値を入れると、繋がった瞬間に `value=""` で上書きされて
消える**。これなら観測と全部合う：

- ボタンは**在るのに無効**（DOM には値が入ったが、state は空のまま）
- **重い実行でだけ出る**（ハイドレーションが遅れる）
- 後ろの spec ほど出やすい（積み上がった JS で遅くなる）
- 単独実行では出ない

**これが正しければ、試験だけの話ではない**——人が「新しい Project」を押して
すぐ打ち始めると、**打った文字が消える**。試験のリトライで隠さず、画面側を直す
べき筋（規則6——待ちを延ばさない・リトライを足さない）。

### 追記・2026-09-12——**ハイドレーション仮説は外れた。** 別の筋で直した

**先に仮説を潰した。** ダイアログは「新しい Project」を**クリックして開く**
——そのクリックを処理しているのは React のハンドラなので、**開いた時点で
React は既に繋がっている**。ハイドレーション前に打つことはあり得ない。
直す前に確かめてよかった（規則1——測る前に犯人を決めない）。

**再現も試みたが、取れなかった**：Project を20本積んで、ダイアログの開閉と
入力を15回繰り返しても 15/15 で正常。落ちるのは「重い実行」のときだけで、
軽い環境では出ない。

**読んで見つけた筋**：`openApp` は
`page.waitForURL(/\/p\/[0-9a-f-]+/)` で待ちを解いていた。ところが `/` から
先頭の Project へは `router.replace` で移るので、**URL は即座に変わる。
新しい画面が描き終わったことは、まだ何も保証していない**。
`/` と `/p/[id]` は**別の AppShell を持つ**（`helpers.ts` の既存コメント）ので、
その差の間に開いたダイアログは、あとから来る作り直しに巻き込まれる。
**URL は「決着した印」ではなく、決着の予告でしかなかった。**

**直し方**（規則6「待ち条件は実際に期待する中身が出るまで待つ」）：
`/p/[id]` に着いたら、**会話の入力欄が見えるまで**待つ。これは
`/p/[id]` 側にしか無いので、新しい AppShell が本当に描き終わった印になる。

**あわせて、次に出たとき一発で分かるようにした。** `createProject` は
`作成する` が押せないとき、**5分黙って時間切れになる代わりに10秒で**
「入力欄の中身・開いているダイアログの数・URL」を言って落ちる。
中身が入っていれば「state に届いていない（作り直しの疑い）」、
入っていなければ「入力欄そのものが入れ替わった疑い」と、**その場で切り分く**。

**計測**：直した後のフル実行は 62/62 が2回連続で通り、所要も 6.5 分
（落ちた回は 10〜14 分）。**ただし元が 3/7 の間欠なので、2回では「直った」と
言い切れない**——この記録を残して、次のフル実行で見続ける。
