## #216 単体 `delivery/thread-messages.test.ts`「止められたら待つのをやめて断り、判断待ちも畳む」

- 再現：単独で30回は0回落ち。8本を同時に流す（負荷をかける）と40回中4回落ちた——判断待ちが受信箱に `live` のまま
- 原因（製品の側）：`ThreadMessaging.ask` は、ターンが止められたとき待ちを解いてすぐ返し、受信箱への「畳んだ」の書き込み
  （`inbox.answerJudgment`）は投げっぱなしだった。`send` が返った時点で、判断待ちがまだ `live` のことがある。試験は
  10ms 待って見ていた
- 直し：畳む書き込みを待ってから返す（`folding`）。試験の 10ms の待ちは外した——返った時点で畳み終えていることを見る
- 確かめ：8本同時で80回中0回落ち。直しを外すと（待ちの無い試験で）24回中24回落ちる
- **Fable のレビューで見つかった穴も塞いだ**：止める合図の聞き手は `raiseJudgment` のあとに付くので、判断待ちを出している最中に
  止められると鳴らず、判断待ちが live のまま残る——あとで人が許すと止めたターンの送信が届いた。登録の直後に止められていないかを見て
  畳み（approval-gate の `watch.isEnded()` と同じ形）、許されたあとも止められていれば送らない。試験を足した（直しを外すと、送りが
  返らず試験が時間切れで落ちる）
- **同じ形は中継の承認（`relay/approval-gate.ts`）にもあった**：聞いた呼び出しが終わって畳むとき、書き込みを投げっぱなしで
  返していた（返った時点で判断待ちがまだ live、相乗りの列が先に空く）。書き終えてから返すようにし、書き込みをわざと遅らせる
  試験を足した（直しを外すと落ちる）。負荷をかけただけでは、既存の試験は直しを外しても40回中0回しか落ちなかった
- 書き込みの失敗は握りつぶさず `console.warn` で出す

## #215 E2E `background-work-human`「待たずに頼みました」が2つ見える

- 再現：単独で3回中1回落ちた（Received: 2）
- 原因（試験の側）：trace の DOM で、2つは「AI の文」と「`runSubagent` の tool のカードの結果」だった。サブエージェントが
  Vault の在りかを聞く中継の承認（subagent → vault-directory の lookupAlias）のカードが出ている間、assistant-ui は同じ発言の
  結果の無い tool 呼び出しを requires-action にし、tool のカードは自動で開く（`ToolFallbackImpl`、2026-10-05 に「自動で
  開くのはそのまま」と決めたもの）。`runSubagent` の結果がその前に来ていれば開かず、後なら開いたまま結果を見せる——
  順番しだい。試験は `page.getByText` で画面の全部を数えていた。承認は3回とも出ていた（`relay-audit`）
- 直し：AI の文だけを数える（`helpers.ts` の `aiTextMentioning`。markdown の段落 `p.aui-md-p` だけ——tool のカードの
  「Result:」の見出しや判断待ちの文の <p> は拾わない）。同じ数え方の `background-work.spec.ts` も直した
- 製品は変えていない：判断待ちの間に関係のない tool のカードまで開くのは 2026-10-05 の決定どおり（開くかどうかだけが
  順番で変わる）。変えるかはユーザーに上げた
- **巻き込み**：この spec が途中で落ちると、答えていない判断待ちが受信箱に残り、同じ回の `inbox.spec.ts`・
  `permission-mode-and-two-approvals.spec.ts` が落ちていた。`afterAll` で、この spec が作った Project の判断待ちを断り、
  お知らせを見たにする（`helpers.ts` の `settleProjectsInbox`）。断る→落ち着くのを待つ→見たにするの順（断った
  せいで裏の仕事が失敗してお知らせが増えることがある）。断れなかったもの（待っている呼び出しがもう無く 409。host に
  強いて畳む口は無い）は黙って通さず、id と出どころを `console.warn` で出す
  - 確かめ：わざと承認のカードの所で落とし、3つの spec を同じ回で流した。片づけありで後の2つは通る、片づけを外すと
    後の2つも落ちる（3 failed）
- **製品も直した（ユーザー判断・2026-10-06）**：承認と関係のない tool のカードは自動で開かない（`ToolFallbackImpl` の `hideApproval`
  のとき）。仕様 v4-frontend.md「答え方」。`background-work-human` に「関係のないカードが開いていない」を足した
  （直しを外すと2回中2回落ちる）。`background-work.spec.ts` の「待たずに頼みましたが2つ」は、勝手に開いたカードの結果を
  数えていた——偽の AI の文には最後の結果の1回だけ。AI の文は1回、2件は「バックグラウンドで 2 件」で見る形に直した
- 確かめ：直した形で `background-work-human` 単独 20回中20回通った（カードを開かなくする前）、開かなくした後も
  5回中5回。`background-work` 3回中3回

## #217 E2E `turn-reattach`「判断待ちに答えたあとに開き直しても…」で最初の承認カードが60秒出ない

- 落ちた回のログ（`/tmp/rck-e2e2.log`、2026-10-05）：送ったターンは `listDirectory` を**承認を聞かずに**走らせ、その
  ターンの session は同じ回の最初のテスト（「走行中にリロードしても…」の Project）のものだった。新しい Project の Module は
  そのあとで繋がっている。つまり発言は**前の Project の Thread** に行った（そちらは承認を求めないモード）
- 原因（試験の側）：`createProject` は「Project の名前が見えたら」作り終えたとみなしていた。名前はサイドバーに先に出るので、
  画面の URL はまだ前の Project のことがある（新しい Project の画面へは `router.push` で移る）。このテストは作った直後に
  `page.reload()` するので、前の Project を開き直していた
- 再現：プローブ（携帯の幅で Project を15回続けて作り、作った直後の URL を見る）で、直す前の形は15回中3回、
  URL が前の Project のままだった
- 直し：`createProject` は作った要求（`POST /api/projects`）の返事の id を拾い、URL がその Project になって入力欄が出るまで
  待つ。同じ根の Project が既にあって作らないとき（要求が無い）は名前で host に引く。どちらでも決まらなければ理由を言って
  落とす（黙って「名前まで」に戻すと、重いときに同じ不具合が静かに戻る。Fable のレビュー）
- 「新しい Project」を押したあと、ダイアログが開いたことを先に見る。直した形のプローブで1回だけ、2つ目の Project を
  作るところで要求を出す前に3分以上止まった（trace 無し。`actionTimeout` が無いので fill 等は試験の上限まで黙って
  待つ）。原因は分かっていない——次に起きたら 15 秒で「ダイアログが開かない」と言う
- 確かめ：同じプローブで直した形は15回中0回（URL は毎回作った Project）。`turn-reattach.spec.ts` を 20 回流し、
  「判断待ちに答えたあとに開き直しても…」は 20 回中 20 回通った。別のテスト「走行中に接続が黙って止まっても…」が
  1回だけ落ちた（最後の行まで出ず「[1]」だけ）——今回の直しとは別の場所で、Backlog に積んだ
