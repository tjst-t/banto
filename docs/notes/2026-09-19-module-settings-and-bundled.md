# Module 設定画面の作り直しと、「同梱」の意味の見直し（2026-09-19）

仕様は `docs/specs/v4-architecture.md`（`GET /api/modules` の表・「外から繋いだ
Module の扱い」）、`v4-security.md` の脅威表「役割のなりすまし」、
`v4-frontend.md` §6.15・§6.26。ここには**なぜそうしたか・却下した案・
実際に踏んだもの**を残す。

## きっかけ

ユーザーの指摘が5つ、順に出た。

1. 「Module の設定画面の UI、冗長なので、テーブルがいいかな」
2. 「Global と Project の Module 設定をなるべく同じような UI に」
   （入り切りはトグル、反映はまとめて保存）
3. 「Global で組み込み以外を無効にすると、消されてしまうのも直して」
4. 「状態の『使うとき』が謎すぎる。『止めてある』も変」
   →「全体的に語彙が謎なので、自然な用語に」
5. 「名前が既定かってチェックいらんやろ。bundled とそれ以外を区別する必要ある？」

## 1〜2：2つの面を同じ形にする

**箱＋札をやめて1枚のテーブルにした。** 以前は1件ずつの箱に札を4〜5個並べて
いたので、**同じ語が縦に何度も出ていた**（「banto 全体で1本」「Project の外は
読めない」…）。列にすれば見出しは1回で済む。

**進め方は Project 側（下書き＋保存）に、部品は Global 側（トグル）に揃えた。**
どちらか一方に寄せるのではなく、**それぞれで良かったほうを採った**という形。

その結果、Global 側の「押した瞬間に『◯◯を止めますか』ダイアログ」は無くなった。
代わりに**行の状態列がその場で赤くなる**のと、**保存の差分**の2箇所で言う
——「押す前に何が壊れるか分かる」という性質（§6.1）は保っている。

**並び順を役割で固定した。** Project 側は「繋いでいる／いない」で分けていたので、
**トグルを押した行がその場で飛んでいた**（押した先が別の行になる）。

## 3：無効にすると消えていた

`listInstanceModules` が、止めたものを一覧に戻すとき**同梱の既定からしか復元して
いなかった**。外から足した Module は既定に無いので、止めた瞬間に一覧から消え、
**消えて見えるのでもう動かせない**状態だった（宣言そのものは差分に残っていたので、
データは失われていない）。

実際にユーザーの環境で `Notion` がこの状態になっていて、修正で戻ってきた。

## 4：語彙

**自分で考えた日本語を内部用語に使っていた**——規則11 で戒めているはずのことを、
画面の文言でやっていた。とくにひどかったもの：

- `使うとき`（＝Project ごとに立つので、使われるまで立たない）
- `◯◯ が断るようになる`（＝依存している Module の呼び出しがエラーを返す）
- `この根では、閉じ込めが効きません`
- `道具`（＝Module／tool）、`合言葉`（＝アクセストークン）

**設定（有効／無効）と実行状態（Running／Stopped…）を言い分ける**形にした。
`Stopped`（人が止めた）と `Not running`（動かす設定だが立っていない）を別の語で
残したのは、混ぜると**直すべきかどうかが読めなくなる**から（規則2）。

`合言葉` → `アクセストークン` はログイン画面にも及んだ。**同じものに2つの名前が
残るほうが悪い**と判断した（指示の範囲外だったのでユーザーに明示して報告）。

## 誤警告——役割ではなく名前で見ていた

`vault-local` を無効にしようとすると「vault-directory・shell が使えなくなります」
と出ていたが、**`vault` を名乗る実装は他に3本ある**ので誤り。

原因は、host が返していた `breaksIfDisabled`（「私が名乗る役割に依存している
Module」の一覧）を画面がそのまま出していたこと。Project 側は最初から
「役割を供給するものが1本も無くなるか」で見ていたので、**2つの面で見方が
食い違っていた**。

判定を役割ベースに揃えたうえで、**`breaksIfDisabled` を API から削除した**。
`satisfies` と `dependsOn` から導けるものを別の形で配ると、また同じ誤読が起きる
（規則3）。

## 5：「同梱」が3つの仕事を兼ねていた

ユーザーの指摘が正しかった。`origin === "bundled"` の判定条件に**名前**が
入っていたせいで、**まったく同じコードでも名前が違えば第三者扱い**になり、
`vault-infisical` を別名でもう1本立てられなかった（`vault` を名乗った時点で弾かれる）。
接続先を増やすには `DEFAULT_MODULE_DECLARATIONS` に足して再デプロイするしかなく、
実際 `vault-infisical-cloud` は 2026-09-15 にそうやって足した2本目だった。

1つの印で決めていたこと：

| 決めていたこと | 本当の根拠 |
|---|---|
| 予約役割を名乗れるか | **誰のコードか**（信用） |
| サンドボックス免除 | **誰のコードか**（信用） |
| 削除できるか | **既定の1本か**（消してもコードから復活するか） |

**削除は権限の話ではなかった。** 既定の宣言はコードの中にあって設定には無いので、
設定から消しても次の起動でまた出てくる——「消してはいけない」のではなく
**消すものが無い**。`removable`（設定に宣言が書かれているか）に置き換えた。

信用の判定からは名前を落とし、`command`＋`args` が同梱実装のどれかと一致するか
だけを見るようにした。**同梱のコードを別名で立てたものは
`origin: "bundled"` かつ `removable: true`** になる——2つは別の問いなので、
一致しないのが正しい。

### 却下した案

- **コピーしてよい役割を `vault` だけに絞る**——`shell`・`filesystem` を複製しても
  Project ごとに同じものが2本立つだけで権限は増えないので、**絞る仕組みを足す
  ほうが複雑**（決定・2026-09-19、ユーザー「放ってよいです」）
- **Module 側で複数接続を持つ（core を触らない）**——Infisical 以外にも
  「同じ実装を別の設定で2本」は出るので、core で解くほうが汎用

## 実装中に踏んだ穴——設定を壊せて、直せなくなる

名前チェックを外した直後に、**同梱と同じコードで `vault-directory` を2本目として
追加したら通ってしまった**。窓口は全体で1本と決まっているので、追加した瞬間に
一覧が 500 を返すようになり、**消そうにも、消す口が一覧を読むので動かない**。

2箇所直した。

- **保存する前に、その差分で本当に読めるかを検査する**（読むときと同じ検査を
  `updateInstanceOverlays` の中で通す）。通らない差分は保存しないので、
  壊れた状態そのものが作れない
- **消す口は一覧を読まない**（設定を直接見る）。万一壊れていても、壊した宣言を
  消して復帰できる——**出口を必ず残す**（規則2）

実際に壊れた稼働中の host から、この修正で復帰できることを確認した。

## B の検証——同梱の Vault もサンドボックスに入れられるか（結論：いまはやらない）

`origin` の用途を減らせるかを測った。**Landlock はファイルだけでネットワークは
縛らない**ので、Infisical への通信は関係ない。それ以外に3つの壁があった。

同梱の Vault 系4本のコードを複製し、`confinement: { root: "none" }` を付けて
起動させた結果：

| 試したもの | 結果 |
|---|---|
| `vault-local` の置き場そのまま（`${dataDir}/vault`） | `EACCES: open '.../banto/vault/aliases.json'` ——**固定の置き場は ruleset に入らない** |
| `vault-local` の置き場を `${moduleDataDir}` へ | `spawn age-keygen EACCES` ——**`age-keygen` を外部コマンドで呼ぶので `files-only` では立たない** |
| 同上＋`profile: "exec"` | **プロセスは立った**。落ちたのは次の壁 |
| `vault-infisical` | `Module が宣言より緩い形を申告しました（confinement）` ——**Module 側の自己申告に confinement が無い** |

つまり、やるなら条件は3つ：

1. **置き場を `${moduleDataDir}` へ移す**——ただし `vault-local` の置き場は
   「改名しても既存の秘密が読めるように」意図的に固定してある（宣言のコメント）。
   移すなら既存の秘密の移行が要る
2. **`exec` profile が要る**（`age-keygen` のため）——PATH 全体の実行を許すので、
   **「閉じ込めた」と言えるほど強くない**。得られるのは「`~/.claude` や banto の
   設定・他 Project を読めない」くらい
3. **Module 側の meta にも confinement を書く**（自己申告が緩いと host が断る）

2 が効き目をかなり削ぐので、**いまはやらない**。`origin` が担う仕事は
「予約役割を名乗れるか」と「サンドボックス免除」の2つのまま残る。

将来やるなら、`age` を外部コマンドではなくライブラリで呼ぶ（`files-only` で
済むようにする）ところから。

## 見たこと（規則1・規則14）

- core の単体試験 **215 件**（回帰3本追加：同じコードの別名コピー・既定は消せない・
  読めなくなる差分は保存しない）
- **フル E2E 96 件すべて通過**（9.4 分）。回帰2本追加
  （外から足した Module を無効にしても消えない／役割で見ているか）
- 稼働中の host で実測：Infisical の3本目を別名で追加 → `origin=bundled`・
  `removable=true` → 削除まで通る。第三者のコードが `vault`・`vault-directory` を
  名乗る／URL 接続が `vault` を名乗るのは、いずれも今までどおり断る

# 続き（2026-09-20）：公式モジュールの目録と、追加する面の作り直し

## 「同梱の判定から名前を外す」だけでは、画面から増やせなかった

前日に core を直して「同じコードなら別名で立てられる」ようにしたが、**画面から
増やす道が無かった**——「Module を追加」は `satisfies: []` を固定で送るので、
`vault` を名乗る Module は作れない。**配管は通したが蛇口が無い**状態で、
「Infisical を増やせるようになった」という報告は不正確だった。

最初は一覧の行に「複製」を置いたが、ユーザーの判断で**目録に作り直した**：

> `vault-infisical` は bundled ではあるけど、誰でも使うものではない。デフォルトでは
> この設定画面に出さず、「Module を追加」から追加できるほうがいい。

これが正しい。既定に入れておくと**使わない人の画面に未設定の行が常に出る**し、
**要る人は1本しか持てない**（接続先ごとに1本要るのに、既定はコードにあるので
増やせない）。既定は4本（`vault-local`・`vault-directory`・`shell`・`filesystem`）に
なり、`vault-infisical` は `BUNDLED_CATALOG` へ移した。

## 画面に役割を組み立てさせない

目録にしても複製にしても、肝は同じ：**宣言を組み立てるのは host**。

画面に `satisfies` を入力できる欄を作ると、**貼り付けた JSON が `vault-directory`
（Vault の窓口）を名乗る経路**が画面から復活する。窓口を乗っ取れば alias 名を
全部観測でき、値の取得先を自分の実装へ向けられる。だから口は
`POST /api/modules/catalog/:id` で、**画面が送るのは目録の id と名前だけ**。

## 入れ子タブのデザイン

ユーザー指摘：「メインタブとサブタブが似たような表記になっていて、バグっぽい」。

**原則：2段のナビゲーションに同じ見た目を使わない。** 形・幅・重さのうち2軸以上を
変える。1段目は全幅の下線タブ、2段目は中身の幅だけのピル。

**そして3段目は作らない。** `このサーバで起動／URL に接続` と
`Vault から／直接入力` は「どこに居るか」ではなく**入力の1項目**なので、
ラベルを付けてフォームに降ろした。タブが3段重なる問題が構造ごと消える。

あわせて直したもの：面の上の説明文を削除（タブを見れば分かる）、塗り潰しの青を
`追加` の1つだけに（モード切替が青で競合していた）、説明の段落3つを1行に、
承知の箱の赤一色をやめて相手のホスト名だけ赤に、ピルが全幅に伸びる不具合
（縦並びの親から `stretch` を受けていた）。

## 語彙

- `banto 同梱` → **`公式モジュール`**（ユーザー指摘）
- `貼り付ける` / `自分で書く` → **`カスタム`** の中の **`JSON を貼り付け` / `手動で入力`**
  ——粒度の違うものを横に並べていた。語は既存ソフトの慣習（Import / Add manually）に合わせた
- **`金庫` を全廃して `Vault` に**（ユーザー指摘）。Module の名前も役割名も `vault`
  なのに説明文だけ「金庫」で、**同じものに2つの名前**があった。画面・host の
  メッセージ・仕様書まで揃えた

## 実装中に踏んだもの

1. **同梱タブで「手動で入力」の欄も一緒に出ていた。** `mode === "paste" ? A : B` の
   `else` が manual だったので、第3の値を足したときに B が漏れた
2. **入れても左の一覧に設定画面が出なかった。** 開き直すまで気付けない
   ——入れる目的は「そこに接続先を入れる」ことなので、出ないと次の一歩が踏めない
   （規則13）。Module が増減したことを知らせる細い口を足した
3. **試験どうしの汚染。** core は全 spec で1つなので、別の spec が入れた
   `vault-infisical` が残る。前提を作る口（`installInfisical`）を冪等にし、
   目録の試験は一意な名前を使うようにした
4. **画面の再起動を忘れて「設定に何も出ない」。** ビルドしたのに 4175 を起動し直して
   いなかった（Next はチャンク名がビルドごとに変わる）。この日だけで2回踏んだ

## 見たこと（規則1・規則14）

- core **216件**（目録から2本入れて役割が付き消せる／知らない id は断る、を追加）
- vault-directory **40件**・vault-infisical **17件**・shell **16件**
- `instance-modules.spec.ts` **11件**（目録から2本入れて設定画面が2枚出る／既定には
  削除が出ない、を追加）
- 実機：既定4本 → 目録から追加 → 一覧と左の設定画面に出る → `…` から消せる

## 間欠（測ったが直さない）

`vault-request-inline.spec.ts`「AI が秘密を求めると…」が、**フル実行のときだけ**
3分タイムアウトした（`requestAlias` を呼んでも入力欄が出ない）。

| 測り方 | 結果 |
|---|---|
| フル実行の中（1回目） | 落ちる（3.0分でタイムアウト） |
| 単独で2回 | **2/2 通過**（9.6秒・9.2秒） |
| フルを2つに割って（45件＋54件） | **99件すべて通過** |

**AI のターンが返ってこなかった類**で、機構の側に再現する壊れは見つからなかった。
待ちを延ばしたりリトライを足したりはしない（規則6）——**直さない選択をしたので、
ここに記録を残す**。次に落ちたらこの回数に足す。

なお**フル実行は途中で外から止められることがある**（背景で回すと、セッションの
区切りで殺される）。**前面で2つに割って流す**と最後まで通る——9.6分は前面の
上限に近いので、割るのが確実。
