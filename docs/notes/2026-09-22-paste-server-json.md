# `server.json` を貼って入れる（2026-09-22）

ユーザー：「あとは、servers.json を張り付けてインストール、というパターンも
できるといいね」

## 貼る場所は増やさなかった

既にある「JSON を貼り付け」の欄が、**貼られたものを見てどちらの形か決める**：

- `mcpServers` が在る → 今までの道（Claude Desktop などの設定を取り込む）
- `name` が在って `mcpServers` が無い → **`server.json` として読む**

**人にどちらの形か判定させない。** 人は自分が持っているものを貼るだけ。
タブを増やすと「どっちに貼ればいいのか」を人が考えることになる。

`server.json` そのものでも、registry の応答ごと（`{server:…, _meta:…}`）でも
受ける——人は自分が見ている画面からコピーするので、どちらの形でも来る。

## 画面は1本で済んだ

読むのは host（`/api/modules/registry/inspect`）で、返すのは**検索の1件と
同じ形**。だから画面は `RegistryModulePicker` に「この1件だけ」と渡すだけで、
名前・要る設定・秘密の扱い・外へ出る承知が**そのまま同じ部品**で出る（規則3）。

貼り付け専用の画面を作っていたら、**秘密の扱いが片方だけ直る**類の食い違いが
必ず生まれていた。

**出所は「貼り付け」**という札にした。registry を引いていないので、
提供元とも第三者とも言えない——名前空間の検証すら通っていない
（貼った人が書いた文字列でしかない）。

## 境界は動かしていない

貼られるのは `server.json` の**形だけ**で、宣言は今までどおり host が組み立てる
——役割は名乗らせない（`satisfies: []`）・閉じ込めは外せない・秘密は名前だけが
宣言に残る・聞かれていない欄は差せない。

むしろ `mcpServers` を貼る道より**狭い**：あちらは `command`/`args` を自由に
書けるが、こちらは `planFor` と npm の取得を通る。

## 実機で見つけて直した：エラーが内部をそのまま見せていた

繋ぎ方の無い `server.json` を貼ったら、画面にこう出た：

```
banto host /api/modules/registry/inspect が 400 を返しました:
{"error":"繋ぎ方が書かれていません（`packages` か `remotes` のどちらかが要ります）"}
```

**人が読むのは中の1文**で、口の名前でも状態番号でもない（規則2）。
`client.ts` の `request()` を直し、**host が理由を書いていればそれをそのまま出す**
形にした。理由が無いときだけ、何が起きたかを言うために口と番号を出す。

これは registry だけの話ではない——**この口を使う全ての画面**が、今まで同じ
見せ方をしていた。

## いちばん効いた発見：**自分の単体テストが走っていなかった**

`npm test` の合計が、テストを6本足しても **381 のまま**だったので数え直した。

```
packages/core/package.json:
  "test": "node --test dist/**/*.test.js"      ← 引用符が無い
```

**引用符が無いと shell が展開する。** そして `sh` に globstar は無いので
`**` は `*` と同じ——`dist/<dir>/<file>.test.js` の**2階層しか当たらない**。
`dist/modules/registry/*.test.js` は3階層目なので、

> **registry のために書いた単体テスト32本は、一度も `npm test` で走っていなかった。**

（直接 `node --test <file>` で走らせていたので、緑なのは確かめていた。
だが**フックには入っていなかった**——放っておけば静かに腐る。）

引用符を付ければ node 自身が展開し、`**` が効く。同じ書き方をしていた
7つの workspace をまとめて直した：**381 → 413（+32）、落ちているものは無し**。

**私の誤りとして記録する。** 直前の2つのコミットに「単体 381 passed」と書いたが、
**その数には自分が書いたテストが入っていなかった**。合計を自己申告のまま
信じていた（規則1 を、まさに自分の測定でやっていた）。**数が動くはずの変更で
数が動かなかったら、そこで止まって数え直す。**

# 追記：タブの位置と、その直しが掘り出したもの（2026-09-22）

## タブが中身の下に回り込んでいた

ユーザー指摘：「カスタムの MCP Registry を探す、のときのトグルの位置が
下に行っているのがおかしい」。

registry の面だけ **JSX でタブより前に書いていた**。だから「MCP Registry を探す」を
選んだときだけ、**どれを選んでいるかを示すものが、示される中身の後ろ**に来ていた。
順番を直しただけ。

回帰は**位置で見る**——「出ている」では捕まらない（前も出てはいた）。
3つのサブタブそれぞれで、タブの `y` が中身の `y` より小さいことを見る。
**直す前に落ちることを確かめた**：`「registry」を選ぶと、タブが中身より下に
来ている（タブ 442 / 中身 265）`。

## フル E2E が間欠で落ちた——原因は前日の私の直し

タブを直したあとのフル E2E で `vault-request-inline` が落ちた。**2回落ちて、
落ちるテストが毎回違った**（`:29` → `:164`）＝間欠。単独では通る。

ログを見ると **`[fake-runner]` の行が1本も無い**——偽 Runner はターンの最初に
必ず1行出すので、**ターンが host まで一度も届いていない**。

犯人は**前日に私が入れた1行**だった：

```ts
await ensureUiTools(thread.id);   // 2026-09-21 に void から変えた
```

「画面を持つ tool の一覧」を聞き終わってからターンを始める形にしたのだが、
その先（`listUiToolsForThread`）は **全 Module を直列に、上限無しで** `listTools()`
していた。つまり **Module が1本でも答えなければ、会話そのものが始まらない**。
前日の直しは「Canvas が開かない」を直す代わりに、**会話が始まらない**という
もっと重い壊れ方を持ち込んでいた。

**直したのは2箇所**（どちらも「会話が始まることのほうが大事」という同じ判断）：

1. **host**：並べて聞き、**1本ずつに上限（5秒）**を置く。答えない1本はそこだけ
   落として、**何が答えなかったかはログに残す**（規則2・4）。以前は1本の失敗が
   「画面ゼロ」に化けていたので、**むしろ良くなった**
2. **画面**：`Promise.race` で**待ち切らない**（5秒）。普段は 0.2 秒で返る（実測）

**これは「待ちを足して隠す」ではない**（規則6）——越えたときに何が起きるかが
決まっている（その Module の画面が出ないだけ）。隠しているのは詰まりではなく、
**詰まりの影響範囲を会話から切り離した**。

計測：直す前の後半は 8.8分（うち3分が1件の詰まり）、直した後は **5.8分で 72 passed が2回**。

## 自分への申し送り

**前日「3本が同時に緑になった」と喜んだ直しが、別の壊れ方を作っていた。**
`void` → `await` は1文字の変更に見えるが、**その先が何を待つのかを見ていなかった**
——`ensureUiTools` の中身（全 Module への直列の問い合わせ）を読まずに待ちに変えた。
**待ちに変えるときは、何を待つことになるのかを最後まで辿る。**
