> 設計の真実は `docs/spec/` のまま。本ノートは、プロトタイプの反復で**確定した操作モデル・作った面・記録済みの決定（ADR-0003〜0008）・未決の大論点**を残し、次の検討を再開できるようにするもの。

## 1. 確定した操作モデル（反復で収束）

- **統合シェル**（左サイドバー＋メイン領域）。左サイドバーは**常設・開閉（畳むとアイコンレール）・ドラッグでリサイズ**。開閉ボタンはサイドバー内。
- **目的地はサイドバーで切替**。会話・詳細は**「潜る/戻る」全画面フォーカス**（メイン領域を置換、左ナビは維持）。タブは廃止（開きすぎてカオスになる問題を回避）。
- **全遷移はアプリ内**。`history.pushState/popstate` で**ブラウザの戻る/進む**も有効。「← 戻る」＝ history.back()。
- **プロジェクトの切替は面の性質で分ける**:
  - 横断面（Queue / Board / Improvements / History）＝全プロジェクト1本、画面内フィルタ
  - プロジェクト面（Planning / Backlog / Environments）＝画面内でプロジェクト切替
  - サイドバーのグローバル切替は**廃止**（冗長だった）。
- **レビュー＝「会話 ＋ 切替式の証拠ペイン [Diff / Terminal / App]」**。Diff=コード、Terminal=CLI実行、App=共有ブラウザ（CDP、spec-ui §1.5）。差分レビュー・tmux端末・共有ブラウザを1面に統合。
- **相談（Consult）＝どの判断点からも降りる会話**。文脈注入→選択肢の再構成→同じ判断に戻る（spec-ui §2）。エフェメラル。
- **解説レイヤー**（右上「💡 解説を重ねる」トグル）: 完成UIの上に、フローティング注釈＋**レビュー用コメント（要ADR注記・spec説明バナー）を重畳**。素の状態＝最終形が見える。
- 一貫パターン: **Planning=会話 / Review=証拠＋会話 / Backlog=一覧＋会話**（“アーティファクト＋会話”）。
- **アクセス情報は1箇所に集約**（Environments/Review）。「そこだけ見ればアクセスできる」原則。main は常設で別PCから触れる。

## 2. 作った面（サイドバー順）

- **Decisions**（最上段＝一番触る）: Attention Queue（3部構成カード・滞留×ブロックのスコア順）／ Improvements（**週次**メタケイデンス＝ループの健康＋改善提案、**PO主体の指摘**＝二重処理 spec §2）
- **Work**: Planning（会話→仕様起草→タスク化）／ Backlog（Epic→Task編集＋チャット、ファイル書換コミット）／ Projects（取り込み3経路 Clone/ゼロから/ローカル・**マルチアカウント**・**複数repo**・Provider割当）／ Environments（main 常設＋ブランチ/VM環境・アクセス集約）
- **Progress**: Board（Now/Next/Later・健康状態・nudge/handoff）
- **Records**: History（過去会話の振り返り）／ Memory（二層・独立メニュー）
- **System**: Settings（Gitアカウント／LLMエンドポイント／モデル自動選定／実行環境Providers／通知／詳細=層B）
- **フォーカス（潜る先）**: Review / Consult / Terminal / カード詳細 / タスク定義エディタ / プロジェクト登録

## 5. 【未決・大論点】UIパラダイム — ここを腰を据えて考える

**問い**: 一番いいのは、①今の**コックピット**（サイドバー＋構造化サーフェス＋どこでも呼べるチャット）か、②**チャットファースト**（統一チャットが家、キュー/ボード等は会話内のブロック）か、③その**ハイブリッド**か。

### 議論で出た論点（再開の土台）

1. **「話す場所でAIのできることが変わる」は違和感 → 是正済みの考え**: AIは**一人・能力は一律**（どこからでも何でも頼める）、**ゲート（承認・不可逆）は daemon が場所に関係なく執行**（D2）、場所は“権限”ではなく“文脈”を与えるだけ。当初案の「場所でツールをスコープ」は過剰だった。
2. **チャット統一に振り切るとき唯一ぶつかる壁＝アテンションキュー**: bantoの第一原理は「いま判断を待つものは何か＝注意力の配分装置」。キューは**ソート済み・走査可能・常設**のリスト。チャットは**線形・流れて消える**。素朴に会話ログへ埋めると一覧性が死ぬ。Environments の「そこだけ見ればアクセスできる」も同様 ── **状態は“場所”が要る、会話には保持できない**。
3. **だから二択ではなく二層**: 
   - チャット＝どこでも呼べる「動かす/行く/話す」層（一人のAI・あなたの記憶＝ADR-0003）
   - 構造化サーフェス＝「状態/参照」層（キュー・ボード・Environments…常設で走査可能）
   - 両者は貫通（AIが会話内にキュー/ボードをブロックで召喚、サーフェス側に「相談」が埋まる）。
   - **チャットファーストも成立し得る ── ただしキュー等を“ピン留めの常設ブロック”（流れて消えない）にするなら**。
4. **決めるのは「チャット vs コックピット」ではなく「どちらを家（アンカー）にするか」**。

### 判断の観点（次に詰める）

- bantoの本質は「統治レイヤー＋POコックピット」。チャットが家になることが、この本質（走査可能な注意配分・統治ゲートの明瞭さ）と両立するか。
- VISION「POの一日を会話2枚＋判断キュー1本に圧縮」との整合。
- 見て決めるのが速い（候補: チャットファースト版を別ファイルでモックし、今のコックピットと並べて比較）。

## 6. その他の未決スレッド

- **どこでもAIアシスタント（⌘K「bantoに聞く」）**: 全画面から一人のAIを呼び、banto自身の情報＋設定Toolで操作。カオス回避＝一人・一律能力・daemonゲート・場所=文脈。**「AIがどの面で何ができるか」の権限モデルは要ADR**（D1/D2、秘密/設定を触るため）。UIパラダイム決定と絡むので同時に詰める。
- **記憶システムの深掘り**: 別プロジェクトで温めていた大きめの構想を banto に取り込めるかの検討。**保留**（PO判断で今のスコープから切り離し）。
- **P3 追記待ち（ドキュメント反映）**: ADR/決定に合わせて後でまとめて更新する:
  - `spec-ui` ← 記憶の二層（ADR-0003）
  - `spec-environment` ← Provider登録＋割当（ADR-0006）、sops を Git 認証にも拡張（ADR-0007）
  - `spec-multi-project` ← モデル全体設定（ADR-0004）、複数repo・ID空間の repo 粒度拡張（ADR-0008）
  - `VISION` success_criteria[2] ＋ `spec-improvement-loop` §6 ← 月次→**週次**
- **VISION / S30a8fd スコープ確定**: daily=「会話2枚＋キュー1本」は保持でよいか、支える設定/管理レイヤー（Projects/Settings/Environments/Memory）の記述を足すか。S30a8fd v1（キュー＋tmux）を最初の一枚として維持するか広げるか。**UIパラダイム決定後に確定**。
