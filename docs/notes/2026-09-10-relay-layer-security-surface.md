# 2026-09-10 host の配線・解決層を「3つ目の自作地帯」として名指しする

出発点：`docs/notes/2026-09-09-repo-review.md` の横断的観察と、それを受けたユーザーの
指示（「ここをやらないといけないのでは」）。この作業は仕様の**自己認識**を直すもので、
新しい機構は足さない。

## 主張

仕様書の冒頭は「独自なのは2つだけ」（Project/Thread モデル・全機能を MCP の向こうに
置く）と言うが、②を決めた瞬間、MCP が素では持っていないもの——可視性
（agent/module/管理者）・Module 間中継・初回承認ゲート・代理サーバ方式・トークン配布
——を自作せざるを得なくなった。**host の配線・解決層（§2.5）が、実質的な3つ目の
発明品**である。

リポジトリ全体レビュー（2026-09-09）で見つかった深刻な問題——中継トークンの
子プロセス漏れ・承認ゲート未実装・監査が Event Store に残らない・Elicitation の混線・
60秒タイムアウト——は、**ほぼ全部この層に集中していた**。

## 公平な棚卸し：設計は思ったより存在する

読み直すと、この層の**個々の決定**は既に仕様にある：

- 中継は host 経由・プロセスごとの bearer token・起動のたびに再発行（§2.5、2026-09-02〜03）
- 初回のみ承認ゲート、以降は同じ Project 内で自動許可（§2.5）
- 監査はメタデータだけ Event Store に記録、実データは一過性に通過（§2.5）
- 可視性は「フィルタで隠す」でなく「代理サーバに最初から存在しない」（§10 item 9）
- 第三者 Module に in-process を開かない（§10 item 9、2026-09-03）

**無いのは、この層を1つのセキュリティ面として名指しし、「MCP のインターフェースに
乗らない経路」を列挙すること。** v4-security.md には「Landlock が縛らないもの
（把握して設計する）」という優れた表が既にあるのに、**「中継が縛らないもの」の表が
無かった**。v4-security.md の実効スコープは Shell/FileSystem の OS 閉じ込めに
留まっていて、中継層は誰の担当でもなかった——だから env 継承や /proc のような
「境界の外周」が、どの文書の検査対象にもならないまま実装まで流れた。

§10 item 11 が「セキュリティ境界はまだ設計していない」と言い、§10.2 が「済」と言う
矛盾（レビュー発見 2.5）は、この自己認識の揺れの現れ。item 11 の列挙（強制の層・
Project の根・in-process・鍵の置き場）は実際には決定済みで、**本当に残っていたのは
item 11 に書かれていなかったこの中継層のほう**だった。

## MCP に乗らない経路の列挙（v4-security.md に書き戻した本体）

| 経路 | 何が境界を越えるか | 設計の状態 |
|---|---|---|
| 子プロセスの env 継承 | `BANTO_HOST_MCP_TOKEN` が AI の書いたコマンドに渡る | 決定（2026-09-10）：渡さない |
| `/proc` の読み取り許可 | 同一ユーザーの environ からトークンが読める | 未決（許可リストから外せるか要実測） |
| 画面 API（ui-tool-call） | authToken だけで `module` 可視の tool も呼べる | 未決（強制の置き場。§6.2 の矛盾解消と同時に） |
| 初回承認ゲート・監査 | 決定済みだが未実装 | 実装待ち（tasks.json） |
| Elicitation の宛先 | 並行ターンで別ターンに届く | 実装待ち（コード内 TODO） |
| トークン・セッション・プロセスの回収 | revoke されず増える | 実装待ち（寿命は決定済み） |

Canvas の sandbox（§6.2）はこの表に入れない——レビューで CSP の fail closed を
確認済みで、こちらは既に「守られている外周」。

## 却下した案

- **「独自性は2つ」の記述自体を「3つ」に書き換える**——採らない。§2.5 は「発明したくて
  発明した」ものではなく②の帰結なので、冒頭の独自性の主張は変えず、**セキュリティの
  平面でだけ**この層を一級にする（v4-security.md に節を足す）ほうが、文書の焦点が
  ぶれない。
- **中継層の脅威モデルを新しい別ファイルにする**——採らない。仕様と検討ログを混ぜない
  規律の下で、決定は v4-security.md へ、経緯はこのノートへ、で足りる。ファイルを
  増やすと「セキュリティの決定は v4-security.md にしか無い」という良い性質が壊れる。

## どこに何を書いたか

- `docs/specs/v4-security.md`：「host の中継・可視性の層も、同じ境界である」節を追加
  （上の表が本体）。
- `docs/specs/v4-architecture.md` §10 item 11：決定済みの列挙を消し込み、残る本体を
  「中継層の外周」に差し替え（§10.2 との矛盾解消）。
- `docs/tasks.json`：実装待ち3件（env 剥がし・承認ゲート＋監査・回収と Elicitation 経路）
  と未決2件（/proc・画面 API の強制の置き場）を起票。

なお、レビューで挙がった残る[高]2件（`assertRulesetIsSafe` の未配線・Event Store の
fsync/切り詰め）は中継層の外なのでこの束には入れていない。未起票のまま残っている。
