# Browser の人の画面を動画で流す（2026-10-12〜13）

仕様は `docs/specs/v4-modules.md` §4.1「動画で流す——H.264 と WebCodecs」。ここは経緯。

- 2026-10-12 ユーザー「結構遅延が多いけど仕組み上しょうがない？ 動画を滑らかに再生できない？」。設計役の見立て（案X：
  Xvfb→GStreamer→H.264→流れの口→WebCodecs／案Y：WebRTC／案Z：今の JPEG を詰める）を Fable のサブエージェント
  （d80bc5ec）に確かめさせた。結論：案X。本質は遅延より帯域（今の JPEG は倍率2で 95〜175 Mbit/s）。H.264 は同じページで
  4〜5 Mbit/s・30fps。穴は4つ（ページの大きさの上書きと取り込み・キーフレームの大きさ・静止中の CPU・TCP で詰まった絵）。
  CDP の base64 は原因ではない（設計役の見立ての誤り）。Chrome の中で取り込んで圧縮する案は倍率2で取り込みが毎秒 13.7 枚で律速。
  借りる先は RustDesk（TCP で H.264、要求時キーフレーム、速さの適応）。
- 同日 ユーザー「案Xで進める。まず段1」。段1 の測定役（サブエージェント 12b865ea）が (a)(b) を測り、(c) の試しのページ
  （tmp-video-probe/server.mjs）を作った。設計役が Service video-probe として起こし Publish した。
- 試しのページを Android で開くと、サーバへ頼むボタンが全部効かなかった。原因は banto の Publish：banto のログインで守った
  公開先の forward_auth の問い合わせに Upgrade・Connection を付けたまま渡し、banto 本体の upgrade の受け口が 404 を返して
  いた（公開したサービスの WebSocket が全部開けなかった）。直して release（d66bf976）。
- 2026-10-12 16:06 ごろ ユーザーが Android 10・Chrome 154 で測った（写し4枚）。数字は仕様の (c)。iPhone・1280×800・
  キーフレームの要求の描き直しは取れていない。

## 段2（映像だけ・パソコン、Backlog #281、2026-10-13）

- 前の実装役が段2 の途中（video.ts・窓で大きさを決める session.ts・GStreamer を入れる install.ts）でエージェントの EPIPE で
  切れ、wip のコミット（247defc5）から続けた。残っていたのは人の画面の復号（view-app）・試験・仕様。
- **前の実装役の残した穴**（続けた役が見つけたもの）：
  - 人の入力を screencast の CDP の口に載せていた——動画で映している間は screencast を張らないので、動画の画面からの入力が
    捨てられていた。入力の口を分けた
  - ＋（newTab）で開いたタブが前に出ていなかった——登録の間に「選んでいるタブを前に出し直す」が前のタブを前に出し、
    そのあと選び直したが前に出さなかった。動画では前のタブの絵が新しいタブの名前で流れる
  - 選んだ直後の絵の頭が、まだ前に出ていないタブの名前だった——「前に出し終えたタブ」を持つようにした
- **静止で止まったまま流れ直さない**：試験で5回中2回。原因は Xlib の列（ほかの呼び出しの間に読み込まれた知らせは fd を
  読めるようにしない）。50ms ごとに `XPending` でも読むようにして6回中0回。
- **窓を変えた直後の大きさが落ち着かない**：3手のあとページの `innerWidth` が一度合ってから、画面いっぱい（1920×1080）等を
  40〜130ms 通って戻ることがあった（プローブで5回中3回。`Browser.getWindowBounds` には出ない）。150ms 続けて同じになるまで待つ。
  新しい窓（起こした最初のタブ・ポップアップ）を合わせる間も、ページの大きさを変えるときと同じく流さないことにした。
- **穴①（幅 500 未満）**：候補2つのうち「狭いときだけ上書きを併せる」を取った（仕様 (a)）。「最小 500 で描いて縮める」は
  ページの幅が画面と違ってしまい、携帯の幅で見たい人の目的に合わない。
- **穴②（ポップアップ）**：候補2つのうち「新しい窓をタブとして前後を合わせる」を取った（仕様 (a)）。「取り込みを窓ごとに」は
  全画面の1窓の形を崩す。
- **キオスク形にしたので、ページから見える窓の外と中が同じ大きさになった**（外 1280×887 → 1280×800）。#259 で決めた「人の
  ブラウザと同じ形」のうち「窓あり（枠つき）」と食い違う。全画面にした人のブラウザと同じ形で、headless の印（外 0×0）では
  ないので受け入れ、単体試験の確かめを「外と中が同じ」に替えた——**人に上げる**（規則8）。枠つきに戻すなら、取り込みを窓の
  中身の位置からにするか、上書きを併せる形に戻すかを決め直すことになる。
- 幅 390 の上書きを入れた直後の、まだ何も読み込んでいない空のタブ（＋）は `innerWidth` が 500 のまま 2 秒たつことがあった
  （Module のログに「ページの大きさが 390x640 になりませんでした（500x640）」が残る）。空のタブは白いだけで絵は変わらない。
  読み込めば合う。追っていない。
- レビュー（3回目）：圧縮の子が標準入力を GLib の fd 監視＋`sys.stdin.readline()` で1行ずつ読んでいたため、続けて書いた2行目が
  Python のバッファに残り、次の指示まで処理されなかった（Xlib の列と同じ種類の穴を stdin 側に残していた）。`os.read` で読んで
  自分で行に分ける形にした。試験は「続けて2行（key→stop・stop→start・start→key）」。start→key は x264 が作り直した直後の
  要求を最初の IDR にまとめるので枚数では見えず、続けて書いた stop がすぐ効くこと（書いた順に処理する）で確かめた。
