# 2026-09-10 60秒の壁——進捗を送り続けて、長い仕事とゆっくりの承認を通す

`docs/tasks.json` の `shell-progress-keepalive`。MCP の呼び出しは**待つ側の
既定タイムアウトが60秒**で、`npm install` のような長いコマンドはそこで死ぬ。
`docs/specs/v4-modules.md` §2.3 は「実行中に `notifications/progress` を定期送出
してクライアント側のタイムアウトを更新させる」と決めていたが、実装は秘密を
解決した瞬間しか送っていなかった。

## まず測った（規則1——直す前に、どこで切れるか見る）

隔離した host（別データディレクトリ・別ポート）で、AI に
`sleep 90 && echo finished-after-90s` を実行させた：

```
+3.4s  [tool_use]    mcp__shell__runCommand {"command":"sleep 90 …","timeout":200}
+63.4s [tool_result] ERROR "MCP error -32001: Request timed out"
```

`timeout: 200` を渡していても関係ない——**死んだのはコマンドではなく MCP の
呼び出しのほう**。AI 自身も「shell モジュールは生きている（直後の `echo` は通る）。
その手前の MCP の待ち時間上限だ」と正しく診断していた。

## 直した形——**3ホップとも**送る

待つ側は1つではない。**どこか1つでも黙ると、そこが60秒で切れる**：

```
Runner ──HTTP──▶ 代理サーバ ──▶ Shell ──HTTP──▶ host の中継 ──▶ Vault
        (a)              (b)          (c)
```

- **(b)** Shell が実行中10秒ごとに「実行中（N秒経過、出力 M 文字）」を送る
  ——代理サーバは元から `resetTimeoutOnProgress` で待っており、これで延びる
- **(a)** 代理サーバは受け取った進捗をそのまま Runner へ転送する（既存）。
  SDK は `onprogress` を渡すと `progressToken` を自動で付けるので、
  **Runner 側も進捗を受け取ってタイムアウトを更新していた**ことが実測で分かった
- **(c)** 中継の承認待ちでは、host が10秒ごとに「人の承認を待っています」を
  Shell へ送る。**Shell はそれを自分の呼び出し元へそのまま流す**
  （`HostRelayClient` が `onprogress` を受けて `runCommand` の進捗として上げる）
  ——ここを繋がないと (c) は生きても (b)(a) が切れる

`progressToken` が付いてこない呼び出しには送りようがない（そのときは従来どおり
60秒で切れる）。**推測で送らない。**

## 測った結果

| 見たこと | 前 | 後 |
|---|---|---|
| `sleep 90` を AI に実行させる | +63.4s で `-32001 Request timed out` | **+93.4s で `finished-after-90s` が返る** |
| 中継の承認を**わざと90秒**待たせる | （60秒で外側が失敗する想定） | **+94.0s に許可 → +94.1s に `got=SLOW-APPROVAL-OK`** |

単体の回帰も足した（間隔は試験用に短くできるようにした——本番は10秒のまま）：

- 実行中に進捗が繰り返し出る／**コマンドが終わったら止まる**（タイマーを残さない）
- 承認待ちの間に呼び出し元へ進捗が届く／**答えたら止まる**

単体121+12件・E2E 27件・typecheck 通過。

## 残していること

進捗に **stdout の断片を載せれば、コマンド完了前のライブ出力が出せる**
（§2.3 の「副産物」）。今回は載せていない——載せるなら「どこまで送ったか」を
持つ必要があり、Canvas 側の受け皿（`shell-terminal-view`）と一緒に決めたい。
