## A. 会話の構造

| # | 要件 | 出所 |
|---|---|---|
| **A1** | プロジェクトを単位として並べられる | 【ユーザー】 |
| **A2** | 1つのプロジェクトの中に、複数の会話が同時に存在できる | 【ユーザー】 |
| **A3** | 会話は分岐できる。同じ文脈から複数の試みが並ぶ | 【ユーザー】 |
| **A4** | **分岐は安く切れる。** ブランチを増やすことが費用の理由で躊躇されない | 【計測】【レビュー】 |
| **A5** | 全プロジェクト・全会話を横断して「**いま自分を待っているもの**」が1画面で分かる | 【レビュー】 |
| **A6** | **判断待ちは1つのキューに集まる。** 出所は問わない | 【決定】 |
| **A7** | 判断待ちが**滞留したとき**、端末へ届く（push）。**発生時には鳴らさない** | 【決定】 |
| **A8** | 会話は閉じても残り、読み返せる／再開できる | 【決定】 |

> **A2・A3 の満たし方を変えた**（2026-08-22・決定22）。以前は「開いた分だけ横に並ぶ列」
> （最大3本、それ以上は増やせない設計）で満たしていた。列は本質的にスケールしない。
> いまは、**フォークはスレッドの中に「フォークのカード」として並び**（同時に見比べられる）、
> **展開して読むのは1つずつ**（開いた元の上に層で重ねる）。「並ぶ」はカードの一覧が、
> 「同時に存在できる」はサイドバーの「開いているもの」の点が担保する
> ——要件の文言は変えていないが、満たし方が変わったことは記録しておく（規則8）。

### A6. 判断待ちのキュー

出所が違っても、人にとっては同じ「自分が見ないと進まないもの」である。3本の列を作れば見に行く先が3つになり、目的に逆行する。

| 出所 | 例 |
|---|---|
| 会話 | 「この方針でよいか」 |
| Factory | マージ承認（B4 で待つ設定のとき） |
| 機構 | **F1 の警報**（文脈が下がっていない 等） |

**判断は選択肢を出せる。ただし答えは選択肢に閉じない**（ユーザーの指示・2026-08-21）。
立てる側は選択肢（`approve` / `reject` など）を添えられるが、**どれも選べないときは
自由に書いて答えられる**——立てた側が答えの形を全部知っているとは限らない。
**答えは、その判断が属する会話に返る**（ADR 決定18）。

### A7. 発生ではなく滞留で鳴らす

| 段 | 動作 | 条件 |
|---|---|---|
| 0 | 何もしない | 普通の進行。オーバービューに状態として載るだけ |
| 1 | キューに立つ | 判断待ちが発生 |
| 2 | **端末へ push** | 段1 が一定時間**解消しなかった**／人が明示指定 |

> **Slack はメンションが「発生」で鳴る。Banto は「滞留」で鳴る。**
> 目的は「人が思い出さなくてよい」であって「即座に反応させる」ではない。しきい値は人が変えられる。

**受け入れ**：5プロジェクト・20会話が同時に存在する状態で、判断待ちが1画面に列挙される。画面を閉じていても、滞留した判断待ちが端末に届く。

## B. Factory（平行開発の自動化）

| # | 要件 | 出所 |
|---|---|---|
| **B1** | プロジェクトに Factory を紐づけられる | 【ユーザー】 |
| **B2** | 依頼を投げると **ワークツリー作成 → 実装 → テスト → main へマージ** が自動で進む | 【ユーザー】 |
| **B3** | サブエージェントが自動で起動し、**複数の依頼が同時に走る** | 【ユーザー】 |
| **B4** | **既定では人を待たない。** Factory ごとの設定で、マージ前に待たせられる | 【決定】 |
| **B5** | 途中で落ちても、落ちた地点から再開できる | 【決定】 |
| **B6** | 何が起きたかを後から追える | 【決定】 |

**B4 の理由**：認知負荷を下げるのが目的なので、既定で人を呼ぶのは目的に反する。ただし待たせたい Factory もあるので設定で選べる。待つ場合の受け皿は A6 のキュー。

**受け入れ**：3つの依頼を同時に投げて3つとも main に入る。1つ失敗させても他の2つは進む。落として再起動しても、途中から続く。

### C13. 口を1つにする

**要件として無かったので、実装が2つの機構に割れた**（2026-08-21 に露見）。C10 は
「モジュールは**他のモジュールの**ツールを直接呼べる」としか言っておらず、
中核の機能を使う道を定めていなかった。そのため Factory と worker（実装するサブ
エージェント）だけが MCP に乗らず、**素の TypeScript の口**という第二の機構になった。

> **中核が提供するものも、モジュールが提供するものも、同じ口にする。**

これで「これは中核か、モジュールか」を毎回考える必要がなくなる。**中核とモジュールの
違いは、口ではなく出荷元だけになる**——中核同梱のものは中核の資源（Runner・
イベントログ）を内側で握ってよいが、**外から見える口は他のモジュールと同じ**。

**任意の書き込みは開けない。** ログの面が出すのは型の決まった操作だけで、
「何でも追記できる」道は作らない（決定7 が壊れる）。

### C14. AI が画面を指す

C3 は「GUI は人が開くこともできるし、**AI が開くこともできる**」としか言っておらず、
**AI が何を手がかりに開くのか**を定めていなかった。ここがその具体化である。

> **AI に「画面を開け」と言わせない。AI は「これがそれだ」と指すだけにする。**

**この機構には名前がある**（規則12）。MCP の **`resource_link`**（道具の結果に混ぜる
「指し」）と **`resources/list` / `resources/read`**（モジュールが自分の URI 空間を持つ）。
使っている SDK に**すでに入っている**（実測 2026-08-21・`@modelcontextprotocol/sdk` 1.30.0）。

```
道具の結果 = [ {type:'text', text:'更新しました'},
              {type:'resource_link', uri:'banto://fs/file?path=README.md', mimeType:'text/markdown'} ]
```

**指すだけにする理由**は3つあって、どれも既にある決めごとから出ている：

1. **真実が2つにならない。** AI が画面を直接操作できると、「AI が開いたつもりの面」と
   「実際に開いている面」が別々に存在する（規則3）
2. **勝手に画面が飛ばない。** 指しは会話に並ぶだけで、開くかどうかは人が決める
   ——要件 A7 の「発生では鳴らさない。滞留で鳴る」と同じ考え
3. **読み返せる。** 指しは道具の結果としてイベントログに載るので、
   要件 A8（会話は閉じても残る）が**何も足さずに**効く

**画面の側は「URI をどう開くか」だけを知る。** モジュールは自分の URI 形と
mimeType を宣言し、ホストがそれを面に割り当てる。**人も同じ URI を開ける**（要件 C2）。

**モジュールが自前の面を持ち込むときの境界は、`isolation` と同じ2択**（決定20）——
`in-page`（束ねの中の React）と `sandboxed`（iframe）。既定値は持たない。
**プロセスで信用していないものを、画面で信用しない。**

### C8. ロジックの単一性と、プロセス境界を分ける

**C8a：ロジックは1つ**

```
モジュール
  ├── core                    ドメインロジック。ここに1つだけ
  ├── ツールインターフェース    core への薄い委譲（AI 向け・MCP）
  └── データ API               core への薄い委譲（GUI 向け）
```

- **インターフェースの形は共通化しない。** 縛るのは実装の単一性であって、インターフェースの形ではない
- **インターフェースにロジックを置かない**

> **C8a は構造の裏付けを失った規約である。** 以前は「1モジュール＝1プロセス」が、状態を
> 共有せざるを得ない形で二重実装を物理的に面倒にしていた。C8b でその縛りを外したので、
> C8a は規約として守るしかない。受け入れられると判断する理由は、**破れたときの症状が
> 「GUI にその機能が無い」という目に見える形で出るから**——この設計で繰り返し刈ってきた
> 失敗（圧縮の不発・モデルの誤答・指定の黙殺）は静かに壊れる類だったが、これは違う。

**C8b：契約と境界は独立**

Claude Agent SDK の `createSdkMcpServer` により、**MCP の契約のまま in-process で動かせる**。
したがって「MCP という契約」と「プロセス境界」は独立に選べる。

| 境界 | 使う場面 |
|---|---|
| in-process | 通常。IPC 無し・1プロセス・1デバッガ |
| subprocess | 落ちやすいもの（Shell / Browser）・鍵を持つもの（Vault）・TypeScript でないもの |

**C8c：`isolation` に既定値を持たせない**

- マニフェストの `isolation` は**必須**。書かなければ起動しない
- **既定値を置かない理由**：既定値は「忘れられる」機構そのものである。「落ちてもホストが
  生きる」「鍵が AI 実行と同居しない」という安全要件を、既定値の陰で静かに消させない
- **宣言は自己申告なので、判定できる分は機械で押さえる**——秘匿情報を扱うと宣言した
  モジュールは `in-process` を拒否する／エントリが TypeScript でないものは必然的に subprocess
- 境界は**モジュール台帳に常時表示**する

### C6. 他言語モジュールの位置づけ

最短経路は TypeScript の in-process なので、**他言語は subprocess を建てるぶん一段高い。
この非対称は契約の対価として受け入れる。**

ただし「形式的には可能」で終わらせない。**Phase 1 の完了条件に、TypeScript でない
モジュールが1本実際に動いていることを入れる**（Python の 30 行で足りる）。雛形と
ドキュメントだけでは、書いた瞬間から古くなる。契約を決めている最中がいちばん安く、
6本書いてから「契約が他言語を通せない」と分かるのが最悪である。

### C5. 標準モジュール

| モジュール | 役割 | Phase |
|---|---|---|
| **Repo** | **リポジトリ（clone・リモート・閲覧・コミット）と worktree。GitHub 身元の割り当て** | **0/1**（worktree は 2・鍵は 3） |
| Shell | | **0/1** |
| ファイル | | **0/1** |
| Environment | 検証用環境を立てる | 3 |
| 公開 | Environment を外部へ（Caddy / port / Cloudflared 等） | 3 |
| WorkerPool | サブエージェントを起動する | 3 |
| Vault | 秘匿情報を管理し、必要に応じて注入する | 3 |
| Browser | **AI と人が同時に使える** | 3 |
| Backlog | 今後実装するものやバグを記憶する | 3 |

**Phase 0/1 で作るのは3つだけ**（【レビュー】）。Factory が1本通るのに要る最小集合。**契約は先に決め、中身は後**——モジュールを増やす前に、Factory の一本の体験を磨き切る。

**Repo と Git を分けない理由**：`log`/`diff`/`blame`/`branch` の閲覧も、clone も worktree も
鍵の割り当ても、すべて「リポジトリという1つの対象への操作」である。分けると core が2つになり、
C8 に逆行する。**Channel（プロジェクト）の実体を提供するのも Repo。** Factory は worktree を
Repo に頼む——Factory に git の知識を持たせない。

### 複数 GitHub アカウント（要件 D5）

| 持ち物 | どこ |
|---|---|
| どのリポジトリにどの身元を使うかの**割り当て表** | Repo |
| 公開鍵の GitHub への登録 | Repo |
| **秘密鍵そのもの・鍵ペアの生成** | **Vault** |

**鍵ペアを作るのは Vault。Repo は公開鍵しか受け取らない。** Repo が生成すると秘密鍵が一度
Repo を通る。Vault が生成すれば秘密鍵は Vault から一度も出ない——D3 を運用ではなく構造で守る。
実行時も `ssh-agent` を Vault が持ち、Repo は socket のパスだけ受け取る。

**受け入れ**：新しいモジュールを1つ足すのに、Banto 中核のコードを1行も変えない。
2つの GitHub アカウントに属するリポジトリを、同時に clone / push できる。

## D. 実行と安全

| # | 要件 | 出所 |
|---|---|---|
| **D1** | 検証用の環境を立てられる | 【ユーザー】 |
| **D2** | 立てた環境を外部から見えるようにできる | 【ユーザー】 |
| **D3** | 秘匿情報は Vault が持ち、必要なときだけ注入される。**鍵そのものが AI の文脈に出ない** | 【ユーザー】 |
| **D4** | AI が触れる範囲は、明示的に許した範囲に限られる | 【決定】 |
| **D5** | **複数の GitHub アカウントを使い分けられる。** 割り当ては Repo、鍵は Vault | 【ユーザー】 |

**Claude の複数アカウントは要件に入れない**（【決定】）。実測で文脈が本来の十数倍に膨らんで
いたので、F1 の観測を入れて圧縮が効いた状態で測り直してから判断する。**対症療法より根治を先に。**
必要になったときは、Runner の引数に資格情報が1つ増えるだけで足りる——G の「スレッド生存中は
不変・変更＝新スレッド」がそのまま効くので、新しい概念は要らない。

> **GitHub の身元と Claude の身元を1つの概念にまとめない。** 前者は**対象で決まる静的な経路**、
> 後者は**資源の残りで決まる動的な選択**。共通しているのは「Vault が持ち、AI の文脈に出ない」
> （D3）だけで、それは既に書いてある。

## E. 表面

| # | 要件 | 出所 |
|---|---|---|
| **E1** | Web アプリ／PWA。端末を選ばず、どこからでも同じように使える | 【ユーザー】 |
| **E2** | 狭い画面（スマートフォン）で崩れない | 【決定】 |
| **E3** | 会話とモジュール GUI が、広い画面では並び、狭い画面では切り替わる | 【決定】 |
| **E4** | 相手の言葉が Markdown として描かれる（見出し・箇条・表・コード）。コードには色が付き、写せる | 【ユーザー】 |
| **E5** | 会話は末尾に追従する。**ただし遡って読んでいる間は飛ばない** | 【ユーザー】 |
| **E6** | 誰の言葉かが分かる | 【ユーザー】 |
| **E7** | 明暗を切り替えられ、選択が残る | 【ユーザー】 |
| **E8** | **日本語入力の変換確定で送信されない** | 【ユーザー】 |
| **E9** | 色・字の大きさ・余白・角は、**決めた段だけを使う**。面が独自の値を持たない | 【ユーザー】 |
| **E10** | 判断待ちは、会話の最後尾にそのまま出る。**常設の判断待ち欄は無い** | 【ユーザー】 |
| **E11** | 出所・プロジェクトを問わず、いま自分を待っているものが1箇所（受信箱）で分かる | 【ユーザー】 |

> **E4〜E9 を足した**（2026-08-21・【ユーザー】：「今実装した機能についての UX も v2 に
> しっかり合わせてほしい」）。機能を増やす話ではないので、対象は
> **すでに実装済みの機能の見え方と触り心地**に限る。
>
> **E9 が土台**。v2 は自分の失敗を「字 17 段・枠 107 箇所・色 39 種」と記録し、
> 値の出どころを1枚（`theme/tokens.css`）に集めることで直した。v3 は同じ状態に
> 戻っていた。**他を直しても、E9 が無いと同じところへ戻る。**
>
> **E8 は不具合に近い。** 変換中の Enter を見ていなかったので、
> **日本語を打つと変換確定のたびに送信されていた**——毎日使う道では致命的である。
>
> 色の役は5つだけで、**塗ってよいのは「あなたの番」の1色だけ**。他は点・左罫・字にしか
> 出さない。だからいちばん強い色が常に「あなたの番」を指す。
>
> **2026-08-22、UX を作り直した**（【ユーザー】：「いまの GUI は全部一度捨てて、
> `13-tsuzukima-kai.html`（意匠見本）の UX で作ってほしい」）。1本の会話が同時に複数の列で
> 並ぶ構え（列を増やすほどスケールしない）から、**サイドバー＋層で重なる会話パネル**へ

## F. 費用と持続性

| # | 要件 | 出所 |
|---|---|---|
| **F1** | 文脈が単調に増え続けない。**増え続けていることを機構が検知する** | 【計測】 |
| **F2** | **観測は Banto Core が外側から行う。材料は各ターンの `usage`。LLM を呼ばない** | 【決定】 |
| **F3** | 使用量が見える | 【計測】 |
| **F4** | **（要件ではなく Phase 2 の検証項目）** 平行数を上げたとき、費用が**どこで線形に曲がるか**を測る | 【計測】【レビュー】 |

> **F4 の種別を変えた**（2026-08-21・【レビュー】）。「線形以上に増えない」を守るべき要件として
> 読むと、**線形を超えた時点で要件違反と誤判定する。** 枝が分かれて長く伸びれば共有
> プレフィックスの割合は減るので、いずれ線形に近づくのは自然な挙動である。理由は
> ADR-0001 決定15。
>
> **測った**（2026-08-21・`packages/factory/src/concurrency.measure.test.ts`）。
> **曲がる点は平行数6までに現れなかった。** 見えたのは別の形で、
> **費用は3あたりで改善が止まり、時間だけが伸び続ける**——3より上げて買えるのは
> 速さであって費用ではない。直列（1）に対して、3 で費用 0.70〜0.83 倍・時間 0.34〜0.46 倍、
> 6 で費用 0.76 倍・時間 0.22 倍。**平行にすると高くなるだろうという見立ては外れた。**
> 限界：小さな依頼・各点1回・共有プレフィックスは system prompt が支配的。

### F1. 警報は2種類要る

| 種類 | 例 |
|---|---|
| **量** | 文脈サイズが閾値を超えた／base が肥えた |
| **不在** | **文脈が一度も下がらないまま N ターン経過した**（＝圧縮が発火していない） |

**鋭いのは不在のほう。**「増えている」は正常な会話でも起きるが、「一度も下がらない」は機構の故障を名指しする。

**背景（計測・2026-08-20 測り直し）**：**圧縮は 1M の上限に触れたときだけ発火する。** 旧実装の 919 セッションのうち、最大文脈が 990k を超えた 2 本は両方とも発火し、990k 未満の 917 本は 1 本も発火しなかった。200 ターン以上の長い会話 38 本のうち **35 本は一度も文脈が下がらず**、その最大文脈の中央値は **601,568**——**60 万トークンを超えても圧縮は動かない。何も失敗しないので、気づかれない。**

> **「起きなかったこと」は自動では見つからない。期待を明示したときだけ検知できる。**

警報は A6 のキューに入る。

## G. 会話のベース（base）

分岐を安くするための構造。

```
Thread = base（依頼・制約・決まったこと。小さく安定）
       + 以降のメッセージ（そこからの作業履歴）
```

| # | 規則 |
|---|---|
| **R1** | **fork の既定は base から。**「いまの続きから」は明示オプション |
| **R2** | **base は追記のみ。書き換えない**（追記なら既存のブランチのキャッシュは壊れない） |
| **R3** | 追記できるのは「**決まったこと**」だけ。「経過」は入れない |
| **R4** | **既存のブランチは追記を見ない。** 古い base のまま完結する |
| **R5** | **書き換えは許すが、そのときブランチは継承しない。** 書き換え＝新しい会話の始まり |
| **R6** | 既定では AI が「base に反映すべき」と判断して追記し、**人が消せる**。明示操作も持つ |
| **R7** | **プロジェクトについて恒久的に真なことは、base ではなくリポジトリのファイルに書く** |
| **R8** | base のサイズを計測し、**閾値を超えたら追記を拒否する**（警報ではなくゲート）。同時に R5 を選択肢として A6 のキューに出す。**会話の切り替えは自動でしない** |

### R3 の判定

**「次のブランチがこれを知らないと困るか」** の一問。要約による圧縮ではなく**種類による選別**なので、安く、判断がぶれない。

| base に入る | 入らない |
|---|---|
| 依頼・制約 | 作業の経過 |
| この方針は採らない、と決めたこと | 試したことの全部 |
| この API はこう動く、と確かめたこと（※R7 も見る） | ツール出力 |

### R7. 3つの置き場

| 置き場 | 何を | 範囲 | 読み手 |
|---|---|---|---|
| **base** | この会話で決まったこと | 1会話とそのブランチ | その会話のブランチ |
| **リポジトリのファイル** | プロジェクトについて恒久的に真なこと | プロジェクト | 全会話・人・将来の自分 |
| ~~記憶ストア~~ | 人の好み・やり方 | — | **作らない** |

**記憶ストアを作らない理由**：置きたかったものの大半は、実はファイルに置くべきものだった。リポジトリはすでに永続で、人も AI も読め、git で履歴が残り、レビューもできる。専用ストアを作ると**リポジトリと二重管理**になる。残る「人の好み・やり方」は要件から出てこなかった。

## 通底する原則

要件ではないが、設計判断のたびに戻る2つ。

> **観測は、観測される機構の外側に置く。** 中に置くと、機構が止まったとき観測も一緒に止まる。
>
> **任せてよいのは仕事であって、仕事が行われていることの確認ではない。**

**B2（Factoryの自動進行）・完了通知・緊急停止も実装済み**（決定36・2026-08-26）。
依頼を投げると、`advance_runs`/`POST /api/runs/advance`を一度も呼ばずに

**ワークツリー・依存キャッシュの使い回しも実装済み**（決定37・2026-08-26）。

Factoryは言語・ツールチェーンを知らないので、どこをキャッシュするかは

**Environmentの汎用モジュール化も実装済み**（決定38・2026-08-26）。`env-docker`/

## Phase と完了条件

**完了条件は「要件を満たす」ではなく「計測が実際に走り、数値を返す」**（【レビュー】）。この会話で担保されたのは設計であって、実装で再現される保証ではない。

| Phase | 内容 | 完了条件 |
|---|---|---|
| **0** | 会話・base/fork・イベントログ・オーバービュー・観測 | **F2 の観測が実際に走り、文脈サイズと圧縮の発火回数を数値で返す。** 判断待ちが1画面に出る |
| **1** | モジュール契約の確定と repo / shell / ファイル | **契約が確定し、その契約で3つ書けた。** ツールを足してもキャッシュが落ちない（数値で確認）。**TypeScript でないモジュールが1本、実際に動いている** |
| **2** | Factory | 3依頼を同時に投げて3つとも main に入る。落として再起動しても続く |
| **2.5** | **モジュール GUI の契約**（C1・C3・C4・C14） | **AI がファイルを更新し、その `resource_link` を指し、人がそれを画面で開ける。** 既存モジュール1つで実際に載る |
| **3** | 残りの標準モジュール6つ | |
| **4** | **画面の作り込み**（E1〜E11） | 狭い画面で崩れない。判断待ち・フォーク・設定・モジュールの面が画面から扱える。**字の段が7を超えない（本物のブラウザで数える）** **← 2026-08-21 に達成、2026-08-22 に UX を作り直して再達成（決定22）** |
| **5** | 旧 Banto を止める | |

> **2.5 と 4 を足した**（2026-08-21・【ユーザー】）。**表に GUI の Phase が1つも無かった。**
> E1〜E3 は要件なのに、どの Phase も担当していなかった——そのため画面は
> 「API を足すたびに同じコミットで面を付ける」副産物になり、v2 から大きく劣化した。
>
> **2.5 を 3 より前に置く理由**：C1（モジュールは GUI を持ち込む）と C14 の契約を
> 決めずにモジュールを6本書くと、**6本書いてから「この枠では載らない」と分かる。**
> C6 の他言語モジュールで「契約を決めている最中がいちばん安い」と書いたのと同じ構図である。
>
> **4 を 5 より前に置く理由**：**画面が v2 を置き換えられるまで、旧 Banto は止められない。**
> 順序が表に無かったので、ここで明示する。
>
> **Phase 4 の完了条件は満たした**（2026-08-21・本物のブラウザで11件）。ただし
> **条件に書いてあることだけが済んだ**のであって、v2 に在ったものが全部揃ったわけではない
> ——Command Palette、各モジュールの作り込まれた面（Git・環境・Browser 等）は無い。
> それらは**要件に無い**ので、要るなら要件の側に足してから作る（規則8）。
>
> **E4〜E9 を足して測り直した**（2026-08-21・本物のブラウザで17件）。
> 実測：**字の段は4**（11px×32・12px×20・13px×26・15px×7）。
> 追加で測っているのは、Markdown が要素になること・声が書体で分かれること・
> 開いた時点で末尾に居ること・**変換中の Enter で送らないこと**・明暗が残ること。
>
> **測れていないもの**（規則1：測っていないことは言わない）：
> **「遡って読んでいる間は飛ばない」の側は測れていない**——途中でイベントを差し込む口が
> 画面の外に無いため。仕掛け（`use-stick-to-bottom`）がその判定を持っている、
> というところまでしか言えない。
>
> **なお v2 に在って、まだ無いもの**：Command Palette、思考（reasoning）の折りたたみ、
> 道具の呼び出しの行、添付。**道具の行はイベントに載っていない**ので、
> 画面だけでは足せない（host 側の話）。
>
> **GUI を作り直して測り直した**（2026-08-22・決定22・本物のブラウザで19件）。
> 実測：**字の段は4**（11px・12px・13px・15px）。段が減ったのは、コードの字を
> `0.92em`（相対単位）で作っていた箇所を見つけて直したため——**相対単位は祖先の
> 大きさで実際の px が揺れる**ので、E9 の「決めた段だけを使う」に反する
> （撮って気づいたのではなく、この試験自体が見つけた——数えられるものは試験で守る、
> の実例）。
>
> フォーク・受信箱からの回答・作業パネルの層・狭い画面での崩れなさを、
> 実データに近い形（同一スレッドに2件の判断待ち・共有ログ）で測っている。
> **`decision.resolved` イベントは `threadId` を持たないため、per-thread の
> `/api/events?threadId=` には届かない**ことを実測で確認した——画面側は
> 答えの配達に使われる `message.recorded`（`queryId: "decision:<id>"`）で判定する
> よう直した。これは前回の実装から気づかずに引き継いでいた誤り。
